GPU Warp Stall 分析：调度状态、Nsight Compute 指标与源码归因

一个 CUDA kernel 可以让许多 warp 同时驻留，但它们推进到不同位置后，能发射的指令也会不同。做乘加运算的 warp 可能正在等刚才的 global load，另一个 warp 则还有独立算术可做。分析性能时，Nsight Compute 会把这些等待列为 warp stall。报告中的高值说明某类等待经常出现；接下来要找到它是否留下了发射空档，以及代码中的哪项工作值得改变。

最容易走偏的是看到 long_scoreboard，就直接去改显存访问。这个名称先说明一条指令正在等 L1TEX 路径上的结果。它可能等在乘加指令上，真正发出请求的 load 却在前面几行。下面从这段 load-use 关系进入报告，把 scheduler、采样位置、producer 和一次具体改动接起来。

快速索引：判断是否有发射空档 · 跟读 Long Scoreboard 案例 · 解释改动结果 · 查其他 stall reason · 采集报告

1. 先看 scheduler 是否还有工作可发射

已经获得 SM 执行资源、尚未释放这些资源的 warp 属于 active 集合。对一次调度机会而言，下一条指令能够发射的候选称为 eligible warp，其余处于等待状态。Scheduler 从候选中选择 warp；selected 表示本次成功发射，not_selected 表示已经就绪但没有被选中。以这组状态观察当前候选，可以写成：

\[ W_{\mathrm{active}}=W_{\mathrm{stalled}}+W_{\mathrm{eligible}},\qquad W_{\mathrm{eligible}}=W_{\mathrm{selected}}+W_{\mathrm{not\ selected}}. \]

例如，Warp A 因 load 结果未返回而等待，Warp B 发射一条加法，Warp C 也已就绪但没有被选中。这次调度同时出现 stalled、selected 和 not selected，发射机会却得到了利用。如果所有候选都不能发射，这次机会才会空置，形成 issue gap。这些状态按 NCU 2026.1 Scheduler Statistics 的视角组织；它们不能直接当作 kernel 时间的几个互斥百分比。

在 Details → Scheduler Statistics 中先看发射空档和 Eligible Warps Per Scheduler。如果 Active 很高而 Eligible 很低，增加 resident warp 未必能解决问题，现有 warp 可能在等待同一类结果；如果 Active 本身偏低，则需要结合Occupancy 的资源预算与 grid 供给查明原因。Warp State Statistics 随后用来选择值得回溯的等待类型。只有发射统计和等待分布放在一起，才有优化优先级。

2. 沿一个 Long Scoreboard 热点回到 load

考虑循环中的一个片段：从 global memory 读取一个值，用它更新 accumulator，同时推进两项独立的整数状态。下面是教学用 SASS 示意，省略地址准备、控制字段和周围循环。L、A、C、B 是本文的指令标签，不是实测 PC。除 L 产生的 R8 外，假定其他输入均已就绪；两条整数加法也不改变 load 地址或乘加结果。

L: LDG.E R8, [R2]
A: IADD3 R12, R12, 0x1, RZ
C: FFMA R16, R8, R20, R16
B: IADD3 R24, R24, 0x1, RZ

2.1 采样可能停在 FFMA

L 发射后，内存请求继续执行。A 不读取 R8，因此可以继续推进；轮到 C 时，若 R8 还没有返回，C 会等待这个 producer。按 Long Scoreboard 的定义，这是对 L1TEX 操作结果的依赖。B 虽然独立，却排在 C 后面；在固定的这段 SASS 中，它不能绕过 C 来填补等待。

现在给诊断设定一个明确入口：Scheduler Statistics 显示发射空档，而 Source 页的 Warp Stall Sampling (Not-issued Samples) 把 Long Scoreboard 热点定位到 C。在这组假设下，C 是值得调查的 stalled consumer。它并不表示 FFMA 的算术延迟很长，也还没有说明 L 的数据来自哪一级缓存或显存。

2.2 用依赖视图寻找产生 R8 的指令

选中 C 后，查看 Input Scoreboard Dependencies。在本例只有 R8 这一项未完成依赖的设定下，依赖会回到 L。Attributed Stalls 则把相关 Long/Short Scoreboard 的 Not-issued 样本归到产生依赖的指令位置，方便从 producer 一侧排序。NCU Source 文档明确区分了这两个位置。

这一步把调查对象从 C 的乘加转移到 L 的读取及其使用时机。若真实指令还依赖多个未完成的 load，依赖视图可能列出多个 producer，不能凭一个寄存器名字就选定原因。分析更复杂的控制字段与依赖标识时，可继续阅读GPU Scoreboard 机制。

2.3 选择一个能在 SASS 上确认的改动

先沿 L 检查地址与工作量。如果访存不合并，同样的有效数据可能需要更多 sector；若实际 producer 是 local-memory load，并伴随 spill，问题就回到寄存器使用。Cache hit、访问 sector 与相应层级的吞吐帮助区分这些情况。接近可持续上限的 DRAM 吞吐可以支持带宽受限的判断，Long Scoreboard 本身没有给出这个结论。

本例选取另一个可检验方向：保留同一次 load 和全部算术，只把 B 放到 C 前面。由于设定中 B 与 L、A、C 没有相关的数据或控制依赖，这个重排保持计算语义，目标顺序变为：

L: LDG.E R8, [R2]
A: IADD3 R12, R12, 0x1, RZ
B: IADD3 R24, R24, 0x1, RZ
C: FFMA R16, R8, R20, R16

现在 L 与 C 之间有两条独立指令，原来只有一条。可从这个静态对照确定的是：同一 warp 在碰到 consumer 前多了一项可执行工作，load 次数和算术次数保持不变。它既没有降低内存访问量，也没有证明 load 会更快返回。如果编译器本来就生成了这个顺序，源代码改写没有形成新的实验条件；应以两份实际 SASS 为准。

真实代码中可以通过调整循环中的独立计算、增加独立 accumulator 或预取距离来争取这种重叠。不过源码顺序不能强制最终排布，增加独立状态还可能拉长寄存器 live range。实际尝试应先验证结果，再检查反汇编和资源用量，确认得到的究竟是不是预期变体。

3. 改动结果能支持什么判断

前面的例子已经确定了 consumer、producer 和候选改动，运行时结果仍需要采集。把原报告设为 baseline，先比较同样工作量下的 kernel duration，再检查发射统计、动态指令次数和热点分布。几种结果会把下一步带向不同方向：

对照结果可以作出的判断继续检查
SASS 顺序没有改变尚未形成扩大 load-use 距离的对照实际指令排布，以及是否存在其他可移动工作
顺序如预期变化，访存和算术次数近似不变，发射空档减少且耗时稳定下降支持独立工作覆盖了更多等待资源用量、其他热点和不同输入规模
C 的归一化 stall 值下降，但耗时未改善不能据此认定优化成功分母变化、采样波动、其他阶段或新成本
寄存器用量上升，出现 spill 或驻留下降重叠机会伴随资源代价完整 kernel 的净收益，必要时减小展开或预取范围

即便改动缩短了 kernel 时间，若访问量、缓存行为和寄存器数也一起变化，就仍有多个可能机制。报告应该写清楚哪些观察与解释一致，哪些尚未分离。对这个教学片段，可靠结论先止于依赖关系和指令间隔；表中的任何运行时结果都不是本文声称已经取得的测量。

复测时固定输入、launch 配置和测量边界，记录 GPU、软件版本与编译选项，完成预热并进行重复计时。保持时钟策略和并发 GPU 工作可比。这样保留下来的变化，才有条件推广到完整 kernel，而不只是让某一列数据变小。

4. 热点属于其他等待时，调查对象随之改变

上面的 C 等待已经发出的 load。若热点位于 L 自身，reason 是 lg_throttle，等待对象变成了接收新请求的队列空间。此时应检查新内存指令的数量、宽度和提交密度；提前发射更多 load 还可能增加压力。区分等待发生在 producer 发射的哪一侧，可以避免把同一个改动套到相反的问题上。

对照第一类等待第二类等待
long_scoreboard / lg_throttleConsumer 等已有 L1TEX 操作完成新 local/global 指令等接收空间
short_scoreboard / mio_throttleConsumer 等已有 MIO 操作完成新 MIO 指令等接收空间
wait / math_pipe_throttle固定延迟算术的结果依赖新算术指令等 execution pipe 可用
barrier / membar等待参与线程到达同步点等待内存屏障的完成条件

若 producer 属于 shared memory，wavefront、bank conflict 和访问宽度会成为相关证据；MIO Throttle 一文给出了独立的访问对照。若热点是 barrier，则要沿控制流检查较晚到达的参与者为何延迟；静态 named-barrier 资源还可能限制驻留，这部分见CUDA Named Barrier。其他 reason 可从下面的分类索引进入。

附录 A：采样与统计单位

All、Not-issued 与 producer attribution

Warp Sampling 在固定 cycle 间隔选择一个 active warp，记录其 PC 和 scheduler state。同一时刻 scheduler 可能发射另一个 warp，因而 All Samples 包含被其他工作覆盖的等待。Not-issued Samples 限定在 scheduler 没有发射指令的采样周期。两组数据可能来自不同 replay pass，不能逐项相减、相除或换算成节省时间。

Source 页内容用途
Warp Stall Sampling (All Samples)定位经常观察到等待的 PC
Warp Stall Sampling (Not-issued Samples)定位与发射空档同周期出现的等待，要求 compute capability 7.0 或更高
Attributed Stalls把 Long/Short Scoreboard 的 Not-issued 样本归到 producer
Input Scoreboard Dependencies从当前 consumer 寻找未完成的 producer
Instructions Executed检查该源码位置或 SASS 的动态执行量

Warp cycles per issued instruction

Warp State Statistics 把状态汇总为每条已发射指令对应的平均 warp cycles，描述一个 warp 的相邻发射之间怎样等待。这个单位与 kernel wall time 百分比不同。增加指令数可能压低归一化比值，缩短 kernel 也可能减少原始样本量；解释前后变化时，两者都需要结合动态工作量与耗时。

选中指标后，Metric Details 给出名称、单位和定义；Raw 页可查看原始计数。源码关联需要匹配二进制的行号信息，同时查看 SASS，避免把经过移动、合并或消除的源码操作直接当成机器指令。

附录 C：构建与采集命令

CUDA C++ 的最小采集范围

下面以已有的 kernel.cu 和可执行程序为命令示例。-lineinfo 保留源码行号，不启用完整调试模式；section 则覆盖前文使用的 scheduler、状态、Source 和访存信息：

nvcc -O3 -lineinfo kernel.cu -o kernel

ncu \
  --section SpeedOfLight \
  --section SchedulerStats \
  --section WarpStateStats \
  --section SourceCounters \
  --section MemoryWorkloadAnalysis \
  -o stalls \
  ./kernel

ncu-ui stalls.ncu-rep

SchedulerStats 检查发射，WarpStateStats 汇总状态，SourceCounters 提供采样和源码归因，MemoryWorkloadAnalysis 检查访存。使用本机支持的 section 与 metric：

ncu --list-sections
ncu --query-metrics --query-metrics-mode suffix \
  --metrics smsp__pcsamp_warps_issue_stalled_long_scoreboard

限定 Python workload 与 replay 范围

对会启动子进程的 workload，可以按 kernel 名称和 launch 次数缩小采集范围。下面的 kernel_name 与 workload.py 需要替换成实际目标。--set full 适合初次调查，通常会增加采集时间和 replay 次数：

ncu \
  --target-processes all \
  --set full \
  --kernel-name regex:kernel_name \
  --launch-skip 0 \
  --launch-count 1 \
  -o stalls \
  python workload.py

NCU 的 replay 可能重复执行 kernel，并调整缓存、时钟或执行并发条件。应先选择有代表性且可重放的一次 launch，确认输入和应用状态能恢复，再扩展到完整步骤。Profiler 条件下的解释要与实际运行环境中的计时一起保留。

GPU Warp Stall Analysis: Scheduler States, Nsight Compute Metrics, and Source Attribution

Many warps can reside in a CUDA kernel at once, but they reach different points in their instruction streams. A warp doing multiply-add work may be waiting for a global load while another still has independent arithmetic to issue. Nsight Compute reports these waits as warp stalls. A high value identifies a frequently observed wait; the next task is to establish whether it leaves issue gaps and which work in the code is worth changing.

A common wrong turn is to see long_scoreboard and immediately start changing device-memory accesses. The name first establishes that an instruction awaits a result from the L1TEX path. Sampling may stop at a multiply-add, while the load that made the request is several lines earlier. The load-use example below connects scheduler activity, the sampled location, its producer, and one concrete change.

Quick access: Check for issue gaps · Follow the Long Scoreboard example · Interpret the change · Look up other reasons · Collect a report

1. Check whether the scheduler has work to issue

A warp belongs to the active set while it holds execution resources on the SM. At an issue opportunity, candidates able to issue their next instruction are eligible warps; the others are waiting. The scheduler chooses among the candidates. selected records a successful issue, while not_selected records a ready warp that was not chosen. This view of the current candidates gives:

\[ W_{\mathrm{active}}=W_{\mathrm{stalled}}+W_{\mathrm{eligible}},\qquad W_{\mathrm{eligible}}=W_{\mathrm{selected}}+W_{\mathrm{not\ selected}}. \]

For example, Warp A waits for a load result, Warp B issues an addition, and Warp C is ready but not selected. Stalled, selected, and not selected all appear at this opportunity, yet the issue slot is used. If no candidate can issue, the opportunity is unused: an issue gap. These states follow the perspective of NCU 2026.1 Scheduler Statistics. They are not mutually exclusive percentages of kernel time.

Start with issue gaps and Eligible Warps Per Scheduler in Details → Scheduler Statistics. High Active with low Eligible may mean that existing warps wait on the same class of results, so adding resident warps need not solve the problem. Low Active calls for inspecting occupancy resource limits and grid supply. Warp State Statistics then helps choose the wait to trace. Issue activity and the wait distribution together establish priority.

2. Follow a Long Scoreboard hotspot back to its load

Consider a loop fragment that loads a value from global memory, uses it to update an accumulator, and advances two independent integer states. The following is teaching SASS, omitting address preparation, control fields, and the surrounding loop. L, A, C, and B are instruction labels, not measured PCs. Assume all inputs except the R8 produced by L are ready, and that neither integer addition changes the load address or multiply-add result.

L: LDG.E R8, [R2]
A: IADD3 R12, R12, 0x1, RZ
C: FFMA R16, R8, R20, R16
B: IADD3 R24, R24, 0x1, RZ

2.1 Sampling can stop at the FFMA

After L issues, its memory request continues executing. A can proceed because it does not read R8. At C, a pending R8 makes the consumer wait for its producer. This matches the Long Scoreboard definition: dependence on an L1TEX operation. Although B is independent, it follows C and cannot bypass it in this fixed SASS sequence.

Give the diagnostic walkthrough a specific entry condition: Scheduler Statistics shows issue gaps, and Warp Stall Sampling (Not-issued Samples) on the Source page locates the Long Scoreboard hotspot at C. Under these assumptions, C is a stalled consumer worth investigating. That does not mean the FFMA arithmetic has high latency, and it does not yet establish whether L obtained its data from a cache or device memory.

2.2 Find the instruction producing R8

Select C and inspect Input Scoreboard Dependencies. With R8 as the only outstanding dependency in this example, the dependency leads back to L. Attributed Stalls assigns the related Long/Short Scoreboard Not-issued samples to the producer location, providing a way to rank the work that created dependencies. The NCU Source documentation distinguishes these locations.

The investigation has now moved from C's arithmetic to L's access and its use distance. If an actual instruction depends on several outstanding loads, the dependency view may list multiple producers; a register name alone does not choose the cause. GPU Scoreboard Mechanism develops the control fields and dependency identifiers in more detail.

2.3 Choose a change that can be checked in SASS

First inspect L's addresses and work. Uncoalesced access can require more sectors for the same useful data. If the actual producer is a local-memory load with spill evidence, the investigation returns to register use. Cache hits, sectors, and throughput at the relevant level help separate these possibilities. DRAM throughput near its sustainable limit supports a bandwidth-bound interpretation; Long Scoreboard alone does not establish it.

This example tests a different direction: retain the same load and arithmetic, but move B ahead of C. Under the stated absence of data or control dependencies between B and the other instructions, the reorder preserves computation. The target sequence becomes:

L: LDG.E R8, [R2]
A: IADD3 R12, R12, 0x1, RZ
B: IADD3 R24, R24, 0x1, RZ
C: FFMA R16, R8, R20, R16

Two independent instructions now separate L and C, where there was one before. The static comparison establishes one additional piece of work available to this warp before it reaches the consumer, with unchanged load and arithmetic counts. It neither reduces memory traffic nor establishes that the load returns faster. If the compiler already produces this order, the source edit has not created a new experimental condition. Compare actual SASS from both binaries.

In a real loop, rearranging independent computations, using independent accumulators, or increasing prefetch distance can expose this overlap. Source order does not force final scheduling, and additional independent state can lengthen register live ranges. Validate output, then inspect disassembly and resource use to establish what variant was actually produced.

3. What the change can establish

The example has identified a consumer, its producer, and a candidate change. Runtime results still need collection. Set the original report as the baseline, compare kernel duration for the same amount of work, and then inspect issue activity, dynamic instruction counts, and hotspot distributions. Different results lead to different next steps:

Comparison resultSupported interpretationCheck next
SASS order is unchangedThe intended increase in load-use distance did not materializeActual instruction order and other movable work
Expected reorder, similar memory/arithmetic counts, fewer issue gaps, and repeatably lower timeSupports more waiting being covered by independent workResources, other hotspots, and other input sizes
C's normalized stall value falls without a timing benefitThe metric change does not establish a successful optimizationDenominators, sampling variation, other stages, and new costs
Register use rises, with spills or reduced residencyMore overlap carries a resource costNet benefit in the complete kernel; possibly reduce unrolling or prefetch distance

Even a faster kernel can leave several candidate explanations if traffic, cache behavior, and register use change together. Report which observations support the interpretation and which effects remain coupled. For this teaching fragment, the established result stops at dependencies and instruction spacing. None of the runtime outcomes in the table is presented as a measurement obtained here.

Keep inputs, launch configuration, and timing boundaries fixed. Record GPU, software versions, and compiler options; warm up and repeat the timing. Keep clock policy and competing GPU activity comparable. These checks determine whether a change belongs in the complete kernel rather than merely improving one report column.

4. Other waits change the object of investigation

C waits for a load that has already issued. If the hotspot is instead at L with lg_throttle, the wait concerns queue space for a new request. Inspect memory-instruction count, width, and submission density. Issuing more loads early could increase that pressure. Locating the wait on the appropriate side of producer issue avoids applying one change to opposing problems.

Appendix A: Sampling and statistical units

All, Not-issued, and producer attribution

Warp Sampling selects an active warp at a fixed cycle interval and records its PC and scheduler state. The scheduler may issue another warp at that instant, so All Samples includes waits covered by other work. Not-issued Samples restricts observation to cycles without an issued instruction. The groups may come from different replay passes and cannot be subtracted, divided, or converted into recoverable time entry by entry.

Warp cycles per issued instruction

Warp State Statistics presents average warp cycles per issued instruction, describing states between a warp's successive issues. This unit differs from a percentage of kernel wall time. More instructions can lower a normalized ratio, and a shorter kernel can also produce fewer raw samples. Interpret changes alongside dynamic work and duration.

Metric Details provides the selected metric's name, unit, and definition; Raw exposes the underlying values. Source correlation needs line information matching the binary. Inspect SASS alongside it, since source operations may have been moved, merged, or eliminated.

Appendix C: Build and collection commands

A focused CUDA C++ collection

The command example assumes an existing kernel.cu and executable. -lineinfo preserves source lines without enabling full debug mode. The sections cover the scheduler, state, Source, and memory information used above:

nvcc -O3 -lineinfo kernel.cu -o kernel

ncu \
  --section SpeedOfLight \
  --section SchedulerStats \
  --section WarpStateStats \
  --section SourceCounters \
  --section MemoryWorkloadAnalysis \
  -o stalls \
  ./kernel

ncu-ui stalls.ncu-rep

SchedulerStats checks issue activity, WarpStateStats aggregates states, SourceCounters supplies sampling and source attribution, and MemoryWorkloadAnalysis inspects memory work. Query sections and metrics supported by the installed tool:

ncu --list-sections
ncu --query-metrics --query-metrics-mode suffix \
  --metrics smsp__pcsamp_warps_issue_stalled_long_scoreboard

Limit Python workload and replay scope

For a workload that starts child processes, kernel-name and launch-count filters narrow the collection. Replace kernel_name and workload.py below with the actual targets. --set full is useful for an initial survey, usually at the cost of longer collection and more replay passes:

ncu \
  --target-processes all \
  --set full \
  --kernel-name regex:kernel_name \
  --launch-skip 0 \
  --launch-count 1 \
  -o stalls \
  python workload.py

NCU replay can execute a kernel repeatedly, and profiling can change cache, clock, or concurrency conditions. Start with a representative replayable launch, verify that inputs and application state can be restored, then expand to the full step. Retain timing from the actual execution environment alongside the profiler-based explanation.
