GPU Warp Stall 分析：调度状态、Nsight Compute 指标与源码归因

每到一个 issue opportunity，warp scheduler 都要从多个 resident warp 中寻找一条可发射的下一条指令。单个 warp 可能因数据依赖、同步条件或目标执行路径的接收能力暂时等待，scheduler 则继续检查其他 warp。Nsight Compute 用 warp-state metric 记录这组调度行为。只有把这些状态放回完整的发射过程，才能区分被其他 warp 覆盖的等待与已经形成 issue gap 的性能限制。

Metric 定义和 UI 名称以 Nsight Compute 2026.1 的公开文档为基线。Metric 可用性仍取决于 GPU 架构和工具版本；实际分析以当前报告的 Metric Details 和本机 ncu --query-metrics 结果为准。

0. 从调度状态到 issue gap

Resident warp 在退出前属于 active 集合。每到一个 issue opportunity，active warp 按下一条 SASS 指令的就绪状态分为 stalled 与 eligible；scheduler 再从 eligible 集合中选择本次发射的 warp：

\[ W_{\mathrm{active}} = W_{\mathrm{stalled}} + W_{\mathrm{eligible}}, \qquad W_{\mathrm{eligible}} = W_{\mathrm{selected}} + W_{\mathrm{not\ selected}}. \]

selected 表示 warp 的当前指令在本次机会中成功发射；not_selected 表示指令已经 ready，但 scheduler 选择了另一个 eligible warp。两者记录 eligible warp 的调度结果，区别于描述阻塞条件的 stall reason。较高的 not_selected 往往意味着 scheduler 手中仍有候选 warp，延迟是否得到覆盖则取决于 issue slot 是否持续被利用。

GPU Occupancy 的驻留资源模型与性能含义详细说明了 resident、active、eligible 和 selected 的关系。Occupancy 给出 scheduler 可搜索的 resident warp 上限，stall reason 则说明这些 warp 当前受什么条件约束。实际 issue slot 的利用情况把驻留规模与等待状态连接成一个性能问题。

Skipped issue slot 表明等待已经形成发射缺口；持续发射期间的 stall 分布主要描述各 warp 的等待构成，优化优先级还需要更多证据。

1. Long Scoreboard 的完整诊断链

Issue gap 只是诊断起点，具体限制还要沿着停住的指令回溯。下面的示意 SASS 用一条 load-use 依赖串起 scheduler、consumer、producer 与内存子系统；代码用于说明证据关系，不对应某次实测报告。

LDG.E R8, [R2]        // producer: starts an L1TEX request
IADD3 R12, R12, 1     // independent work
FFMA R16, R8, R20, R16
                      // consumer: cannot issue until R8 is ready

诊断先在 Scheduler Statistics 中确认 issue gap。Skipped issue slot 与持续偏低的 Eligible Warps Per Scheduler 共同说明 scheduler 缺少可发射指令；此时仍需定位造成缺口的具体依赖。

确认缺口后，在 Source 页切换到 Warp Stall Sampling (Not-issued Samples)。若 long_scoreboard 样本集中在 FFMA，这条指令就是采样时停住的 consumer，它正在等待某个 L1TEX producer 的结果。热点位置由此确定了等待发生在哪里，但还没有确定延迟来自哪里。

Producer 归因补上了这条因果链。Attributed Stalls 将 Long/Short Scoreboard 的 not-issued 样本归到建立 scoreboard 的 producer，Input Scoreboard Dependencies 则从当前 consumer 指向它等待的 producer。在这个例子中，两种视图都会把依赖带回 LDG。

定位到 LDG 以后，证据范围才收敛到它的地址路径。Local-memory 指令与 spill 支持寄存器溢出判断；cache hit、sector 和访问合并指标支持局部性判断；接近平台上限的 DRAM throughput 支持设备级 DRAM 带宽饱和判断，局部 cache 或接口吞吐限制则需要相应层级的 metric。若这些信号都不充分，而 load 与第一次使用之间距离很短，优化方向会转向增加独立工作或提前发射 load。

最后的验证应只改变上一步指向的机制，并在相同输入下比较 kernel duration、issued work、eligible warps 和目标子系统。代码改动缩短总时间，且整条证据链随之发生一致变化，才说明这个 Long Scoreboard 限制得到了改善。

3. 依赖等待与队列反压

数据依赖与队列反压位于指令发射的两侧。依赖等待发生在 producer 已经发射之后，consumer 等待结果或完成事件；队列反压发生在新指令发射之前，目标 queue 或 execution pipe 暂时无法接收它。这个时间边界决定了两类状态需要不同的证据。

long_scoreboard 表示 consumer 指令正在等待某个 L1TEX 路径结果，因此首先是 producer 完成延迟的信号。低 cache hit rate、非合并访问、地址散乱和 local-memory spill 都可能延长这段依赖；load 与第一次使用之间缺少独立指令，也会让相同延迟更早暴露。它本身不能证明 DRAM 带宽已经饱和。Per-warp 逻辑依赖标识与 producer 归因方法见《GPU Scoreboard 机制：Warp 依赖跟踪、SASS 控制与 Long/Short Stall》。

lg_throttle 的官方定义是 warp 正等待 local/global memory instruction queue 出现空位。此时问题偏向新请求的提交速率：load/store 过密、访问粒度过小或同一段代码集中提交大量内存指令。一个 kernel 可以同时出现 long_scoreboard 与 lg_throttle，但两者需要不同的证据。

容易混淆的组合前者在等什么后者在等什么区分方法
long_scoreboard / lg_throttle既有 load 的结果新 memory instruction 的队列空间同时看 cache、DRAM/L1/TEX 吞吐与 Source 上的 producer-consumer 距离
short_scoreboard / mio_throttle既有 MIO 操作的结果新 MIO instruction 的队列空间检查 shared-memory wavefront、bank conflict 和热点 SASS opcode
wait / math_pipe_throttle已发射算术指令的结果新算术指令所需的 execution pipe观察依赖链长度与对应 pipe utilization
barrier / membar其他 warp 到达 rendezvous内存操作满足 fence 顺序前者检查 warp 间工作量，后者检查内存语义和 outstanding operation

short_scoreboard 表示 consumer 正在等待非 L1TEX 的 MIO producer。Shared-memory bank conflict 是其中一种可能的 producer 延迟，MUFU 结果和动态分支也会进入相关依赖路径。NCU 的 Scoreboard Dependencies 先确定 producer，shared-memory 等子系统指标再区分具体原因。关于新 MIO 指令发射前的队列反压，见《GPU MIO Throttle：队列反压、成因与诊断》。

barrier 等待持续到所需参与者全部到达。诊断因此从最后到达的 warp 沿控制流向前检查工作量、内存延迟和分支分歧。Named barrier 的静态资源还可能减少 resident block 数；这一部分属于 occupancy 限制，见 CUDA Named Barrier：CTA 内分组同步与 Occupancy 约束。

这些状态定义说明了 warp 在等待什么，但源码归因还需要知道 NCU 如何采样状态、如何把样本绑定到 program counter。统计口径决定了后续 Source 页面中的数值能够支持哪一层结论。

4. PC sampling 的统计口径

NCU 从两个尺度呈现调度状态。Warp State Statistics 汇总 kernel 执行期间的 warp 状态，并在 UI 中换算为每条 issued instruction 的平均 warp cycles；Source Counters 使用 smsp__pcsamp_* 指标，把周期性采样得到的 program counter 和 scheduler state 关联到具体指令。前者描述等待构成，后者定位等待发生的位置。Warp Sampling 会按固定间隔从 active warp 中随机选择样本，因此得到的是观测分布，而非逐周期的完整执行时间线。

在 PC sampling 中，Scoreboard stall 的热点 PC 通常对应尚未发射的 consumer 指令，如第 1 节中的 FFMA。Source 页的 Attributed Stalls 与 Input Scoreboard Dependencies 再把这段等待追溯到 producer。将 CUDA source、PTX 和 SASS 三层同时展开，才能把源码位置与编译器重排后的实际指令距离对应起来。

Warp Stall Sampling (All Samples) 与 Warp Stall Sampling (Not-issued Samples) 可能来自不同 replay pass。两列的绝对样本数不保证严格相减或逐项对应，适合比较热点分布，不应当作精确周期计数。

Warp State Statistics 常用的单位是 warp cycles per issued instruction。它表示相邻 issued instructions 之间归入各状态的平均 warp cycles，并不是 kernel wall time 的百分比分解。比较两个 kernel 时还要同时查看 duration、issued instructions 和 scheduler 发射情况，避免只压低归一化比值却增加总工作量。

5. 采集 NCU 报告

要把前述采样位置映射到源码，CUDA C++ 构建需要保留行号信息。-lineinfo 不会启用完整调试模式，通常适合性能分析构建：

nvcc -O3 -lineinfo kernel.cu -o kernel

ncu \
  --section SpeedOfLight \
  --section SchedulerStats \
  --section WarpStateStats \
  --section SourceCounters \
  --section MemoryWorkloadAnalysis \
  -o stalls \
  ./kernel

ncu-ui stalls.ncu-rep

SchedulerStats 判断 issue slot 是否空置；WarpStateStats 给出状态分布；SourceCounters 负责 PC sampling 与源码归因；MemoryWorkloadAnalysis 用于验证 scoreboard 或 memory queue 判断。Section 名称会随版本调整，可先执行：

ncu --list-sections
ncu --query-metrics-mode suffix \
  --metrics smsp__pcsamp_warps_issue_stalled_long_scoreboard

初次排查也可以用 --set full，代价是 replay pass 和采集时间明显增加。对 PyTorch 或其他会启动子进程的 workload，先缩小 kernel 和 launch 范围：

ncu \
  --target-processes all \
  --set full \
  --kernel-name regex:kernel_name \
  --launch-skip 0 \
  --launch-count 1 \
  -o stalls \
  python workload.py

性能计数器采集常需要 replay kernel。输入数据、随机状态、文件 I/O 或跨 kernel 的依赖如果不能重复执行，报告可能失真。先用代表性且可重放的最小 workload 固定问题，再扩大到完整训练步骤。

6. NCU UI 分析路径

采集完成后，UI 分析沿同一条因果链展开：先确认 scheduler 是否出现发射缺口，再找到贡献等待的 PC，最后回溯 producer 并核对子系统证据。

从调度器空闲到 SASS producer 的定位顺序

6.1 Details：确认 issue slot 的利用情况

在 Details 页展开 Scheduler Statistics。先看 Active Warps Per Scheduler、Eligible Warps Per Scheduler、Issued Warps 和 Issue Slot Utilization。常见关系如下：

  • Active 很高、Eligible 很低、issue slot 经常空置：resident warp 很多，但大多数同时 stalled。
  • Eligible 持续大于 1、Issued 接近硬件发射上限：scheduler 已有足够选择，继续提高 occupancy 通常没有直接收益。
  • Active 偏低且 Eligible 间歇归零：回到 Occupancy section，检查寄存器、shared memory、block size、barrier 和 grid wave。

随后展开 Warp State Statistics。图表按每条 issued instruction 的平均 warp cycles 展示状态。先排除 selected 与 not_selected，再从数值最高的真实 stall reason 开始。若 issue slot 没有明显空置，这一步只用于理解执行特征，不应直接生成优化结论。

6.2 Source Counters：找到采样集中的 PC

Source Counters section 会汇总 PC sampling。切到 Source 页后，可按以下列排序：

Source 页列含义使用方法
Warp Stall Sampling (All Samples)包含 issued 与 not-issued 状态的全部样本观察该 PC 在整个采样中的权重
Warp Stall Sampling (Not-issued Samples)没有成功发射时的样本定位阻止发射的热点状态
Attributed Stalls把 long/short scoreboard 的 not-issued 样本归到相关 producer寻找需要提前、合并或改变的生产指令
Scoreboard DependenciesScoreboard producer-consumer 边及其 stall 归因从 consumer 回溯 load、shared-memory 或其他动态 producer
Instructions Executed该源码行或指令的动态执行量区分高频小代价与低频长等待

Source 页应同时显示 CUDA source、PTX 和 SASS。若只看到 SASS，先确认编译时加入 -lineinfo，再通过 Source 页面导入匹配的源码。不要仅凭高层源码行推断指令顺序，编译器可能合并、移动或删除操作。

6.3 Metric Details、Raw 与 Compare

选中指标后打开 Metric Details，核对 metric name、unit、raw value 和 NVIDIA 给出的定义。Raw 页适合确认派生指标背后的 counter，特别是百分比、平均值和 per-issued-instruction 指标。优化前后的报告使用 Compare，并把原报告设为 baseline；先比较 kernel duration，再比较 issued work、scheduler 和目标子系统。

7. 从证据到代码改动

代码改动应作用在证据链已经定位的环节。Scoreboard 指向已发射 producer 的完成依赖，需要分别检查 producer 延迟与 producer-consumer 距离；throttle 指向新指令的接收条件，需要检查指令到达率、目标 queue 或 execution pipe；barrier 指向参与者的到达差异，需要沿控制流寻找最后到达的 warp。Taxonomy 表中的“优先核对”列给出了每类 reason 的第一组验证信号。

Occupancy 只有在新增 resident warp 能提高 Eligible Warps Per Scheduler 时，才可能帮助覆盖第一类等待。若 scheduler 已持续发射，牺牲寄存器来换 occupancy 可能引入 spill，并把限制转成 long_scoreboard。同样，降低某项归一化 stall 值若伴随更多 issued instructions，也不构成性能改进。

优化前后应固定输入、GPU clocks、launch 参数和软件版本，先比较 kernel duration，再检查 issued work、eligible warps、stall 热点和目标子系统是否按同一机制变化。由此，issue gap → eligible 不足 → consumer → producer → subsystem evidence 才构成一条可复核的因果链。

GPU Warp Stall Analysis: Scheduler States, Nsight Compute Metrics, and Source Attribution

At each issue opportunity, a warp scheduler searches its resident warps for an issuable next instruction. One warp may be waiting on a data dependency, a synchronization condition, or acceptance by the target execution path while the scheduler checks the others. Nsight Compute records this scheduling behavior with warp-state metrics. Interpreting those states in the full issue process separates waits hidden by other warps from performance limits that leave issue slots unused.

The metric definitions and UI names below use the public Nsight Compute 2026.1 documentation as their baseline. Metric availability still depends on GPU architecture and tool version. For a concrete report, use Metric Details and the output of the installed ncu --query-metrics.

0. From scheduler state to an issue gap

A resident warp belongs to the active set until it exits. At each issue opportunity, the readiness of its next SASS instruction places it in either the stalled or eligible set. The scheduler then chooses a warp from the eligible set to issue:

\[ W_{\mathrm{active}} = W_{\mathrm{stalled}} + W_{\mathrm{eligible}}, \qquad W_{\mathrm{eligible}} = W_{\mathrm{selected}} + W_{\mathrm{not\ selected}}. \]

selected means that the warp's current instruction issued at this opportunity. not_selected means that the instruction was ready, but the scheduler chose another eligible warp. These states record scheduling outcomes for eligible warps, unlike stall reasons that describe blocking conditions. A high not_selected value often means that the scheduler still has candidates; issue-slot utilization determines whether those candidates actually cover the latency.

GPU Occupancy: Residency Resource Model and Performance Interpretation describes resident, active, eligible, and selected warps in detail. Occupancy bounds the resident warps available to the scheduler, while stall reasons describe the conditions currently constraining those warps. Observed issue-slot utilization connects residency and waiting state into a performance question.

A skipped issue slot marks a wait that has become an exposed issue gap. During continuous issue, the stall distribution mainly describes how individual warps spend their waiting time; ranking optimizations requires further evidence.

1. A complete Long Scoreboard diagnostic chain

An issue gap is only the starting point; the limiting dependency still has to be traced from the waiting instruction. The illustrative SASS below uses one load-use dependency to connect scheduler behavior, consumer, producer, and the memory subsystem. It shows the evidence relationship rather than data from a measured report.

LDG.E R8, [R2]        // producer: starts an L1TEX request
IADD3 R12, R12, 1     // independent work
FFMA R16, R8, R20, R16
                      // consumer: cannot issue until R8 is ready

The diagnosis starts by confirming an issue gap in Scheduler Statistics. Skipped issue slots together with persistently low Eligible Warps Per Scheduler show that the scheduler lacks issuable work. The specific dependency responsible for that gap remains to be located.

With the gap established, switch the Source page to Warp Stall Sampling (Not-issued Samples). If long_scoreboard samples cluster on the FFMA, that instruction is the sampled consumer waiting for an L1TEX producer. The hotspot now identifies where the wait occurs, but not where its latency originates.

Producer attribution completes the next link. Attributed Stalls assigns Long/Short Scoreboard not-issued samples to the producer that created the scoreboard, while Input Scoreboard Dependencies links the selected consumer to the producer it awaits. In this example, both views lead back to the LDG.

Once the LDG is identified, the evidence can narrow to its address path. Local-memory instructions and spill evidence support a register-spill diagnosis. Cache-hit, sector, and coalescing metrics support a locality diagnosis. DRAM throughput near the platform limit supports device-level DRAM bandwidth saturation; local cache or interface throughput limits require metrics from that level. If those signals are weak and little independent work separates the load from its first use, the optimization hypothesis shifts toward increasing that distance or issuing the load earlier.

Validation changes only the mechanism identified by the preceding evidence, then compares kernel duration, issued work, eligible warps, and the target subsystem under the same input. A lower total time accompanied by consistent movement along the evidence chain shows that the Long Scoreboard limit has improved.

3. Dependency waits and queue backpressure

Dependency waits and queue backpressure occur on opposite sides of issue. A dependency wait begins after a producer has issued, while its consumer awaits a result or completion event. Queue backpressure prevents a new instruction from issuing because its target queue or execution pipe cannot accept it. That timing boundary determines the evidence needed for each state.

long_scoreboard means that a consumer instruction is waiting for a result from the L1TEX path, so it first indicates producer-completion latency. A low cache hit rate, uncoalesced accesses, scattered addresses, or local-memory spills can extend that dependency. Too little independent work between a load and its first use can expose the same latency sooner. The metric alone does not establish DRAM-bandwidth saturation. GPU Scoreboard Mechanism: Warp Dependency Tracking, SASS Control, and Long/Short Stalls develops the per-warp logical identifiers and producer-attribution model.

The official definition of lg_throttle says that the warp waits for space in the local/global memory instruction queue. The restriction applies to the submission rate of new requests: dense load/store sequences, narrow accesses, or a burst of memory instructions in one region of code. A kernel may show both long_scoreboard and lg_throttle, but they require different evidence.

Commonly confused pairWhat the first waits forWhat the second waits forHow to distinguish them
long_scoreboard / lg_throttleThe result of an existing loadQueue space for a new memory instructionInspect cache, DRAM/L1/TEX throughput, and producer-consumer distance in Source
short_scoreboard / mio_throttleThe result of an existing MIO operationQueue space for a new MIO instructionInspect shared-memory wavefronts, bank conflicts, and hotspot SASS opcodes
wait / math_pipe_throttleThe result of an issued arithmetic instructionThe execution pipe needed by a new arithmetic instructionCompare dependency-chain length with utilization of the corresponding pipe
barrier / membarOther warps reaching a rendezvousMemory operations satisfying fence orderingFor barrier, inspect workload skew; for membar, inspect memory semantics and outstanding operations

short_scoreboard means that a consumer is waiting for a non-L1TEX MIO producer. A shared-memory bank conflict is one possible source of producer latency; MUFU results and dynamic branches also use related dependency paths. Nsight Compute's Scoreboard Dependencies first identify the producer, after which shared-memory and other subsystem metrics distinguish the cause. For queue backpressure before a new MIO instruction issues, see GPU MIO Throttle: Queue Backpressure, Causes, and Diagnosis.

A barrier wait continues until all required participants arrive. Diagnosis therefore starts with the last-arriving warp and traces backward through control flow to compare workload, memory latency, and divergence. Named barriers can also reduce resident-block count through a static resource limit; that is an occupancy issue covered by CUDA Named Barriers: CTA-Local Synchronization and Occupancy Constraints.

These state definitions establish what a warp is waiting for. Source attribution also depends on how Nsight Compute samples that state and associates a sample with a program counter. Those sampling semantics determine which conclusions the Source-page values can support.

4. PC-sampling semantics

Nsight Compute presents scheduling state at two scales. Warp State Statistics aggregates warp states over the kernel and presents average warp cycles per issued instruction. Source Counters uses smsp__pcsamp_* metrics to associate periodically sampled program counters with specific scheduler states. The former describes the composition of waiting time; the latter locates where that waiting occurs. Warp Sampling randomly selects an active warp at a fixed interval, producing an observed distribution rather than a complete cycle-by-cycle history.

In PC sampling, a Scoreboard hotspot usually lands on the unissued consumer instruction, such as the FFMA in Section 1. The Source page's Attributed Stalls and Input Scoreboard Dependencies then trace that wait back to the producer. Expanding CUDA source, PTX, and SASS together connects the source location to the actual distance after compiler scheduling.

Warp Stall Sampling (All Samples) and Warp Stall Sampling (Not-issued Samples) may come from different replay passes. Their absolute sample counts need not subtract or match item by item. Use them to compare hotspot distributions, not as exact cycle counters.

Warp State Statistics commonly uses warp cycles per issued instruction. The value is the average number of warp cycles assigned to each state between issued instructions, not a percentage breakdown of kernel wall time. When comparing kernels, inspect duration, issued instructions, and scheduler issue behavior as well. A lower normalized value can hide an increase in total work.

5. Collecting an Nsight Compute report

Mapping those samples back to source requires line information in the CUDA C++ build. -lineinfo does not enable full debug mode and is normally suitable for profiling builds:

nvcc -O3 -lineinfo kernel.cu -o kernel

ncu \
  --section SpeedOfLight \
  --section SchedulerStats \
  --section WarpStateStats \
  --section SourceCounters \
  --section MemoryWorkloadAnalysis \
  -o stalls \
  ./kernel

ncu-ui stalls.ncu-rep

SchedulerStats shows whether issue slots are idle. WarpStateStats provides the state distribution. SourceCounters supplies PC sampling and source attribution. MemoryWorkloadAnalysis tests scoreboard and memory-queue hypotheses. Section names can change between versions, so list the current set first:

ncu --list-sections
ncu --query-metrics-mode suffix \
  --metrics smsp__pcsamp_warps_issue_stalled_long_scoreboard

--set full is useful for an initial survey, but it increases replay passes and collection time. For PyTorch and other workloads that launch child processes, first restrict the kernel and launch range:

ncu \
  --target-processes all \
  --set full \
  --kernel-name regex:kernel_name \
  --launch-skip 0 \
  --launch-count 1 \
  -o stalls \
  python workload.py

Performance-counter collection often replays a kernel. A report can be distorted when input data, random state, file I/O, or cross-kernel dependencies cannot be reproduced. Isolate the problem with a representative, replayable workload before expanding the collection to a full training step.

6. Nsight Compute UI workflow

Once collection is complete, the UI follows the same causal chain: confirm an issue gap at the scheduler, locate the PC that contributes the wait, then trace its producer and verify the corresponding subsystem.

Diagnostic path from idle issue slots to the producer SASS

6.1 Details: establish issue-slot utilization

Expand Scheduler Statistics on the Details page. Begin with Active Warps Per Scheduler, Eligible Warps Per Scheduler, Issued Warps, and Issue Slot Utilization. Common patterns include:

  • High Active, low Eligible, and frequent idle issue slots: many warps reside on the SM, but most are stalled at the same time.
  • Eligible stays above one and Issued approaches the hardware issue limit: the scheduler has sufficient choice, so more occupancy is unlikely to help directly.
  • Active is low and Eligible intermittently reaches zero: return to the Occupancy section and inspect registers, shared memory, block size, barriers, and grid waves.

Then expand Warp State Statistics. The chart shows average warp cycles per issued instruction. Exclude selected and not_selected, then begin with the largest actual stall reason. If issue slots are not substantially idle, use this distribution to understand execution rather than treating it as an optimization order.

6.2 Source Counters: locate sampled PCs

The Source Counters section aggregates PC samples. On the Source page, sort by the following columns:

6.3 Metric Details, Raw, and Compare

Open Metric Details for a selected metric and check its name, unit, raw value, and NVIDIA's definition. The Raw page is useful for tracing derived percentages, averages, and per-issued-instruction values back to their counters. Use Compare for before-and-after reports and set the original as the baseline. Compare kernel duration first, then issued work, scheduler behavior, and the target subsystem.

7. From evidence to a code change

A code change should act on the stage identified by the evidence chain. A scoreboard state concerns completion of an issued producer, so inspect both producer latency and producer-consumer distance. A throttle state concerns acceptance of a new instruction, so inspect arrival rate, the target queue, or the execution pipe. A barrier state concerns arrival skew among participants, so follow control flow to the last warp that reaches the rendezvous. The “Check first” column in the taxonomy table supplies an initial validation signal for each reason.

Occupancy can cover the first class of waits only when additional resident warps increase Eligible Warps Per Scheduler. If the scheduler already issues continuously, reducing register use to raise occupancy can introduce spills and move the limit to long_scoreboard. Likewise, lowering a normalized stall value while executing more instructions is not a performance improvement.

Keep the input, GPU clocks, launch parameters, and software versions fixed. Compare kernel duration first, then verify that issued work, eligible warps, the sampled hotspot, and the target subsystem changed according to the same mechanism. This turns issue gap → too few eligible warps → consumer → producer → subsystem evidence into a reviewable causal chain.
