GPU Warp Stall 分析：调度状态、Nsight Compute 指标与源码归因

Warp stall 表示 warp 的下一条指令暂时不能发射。原因可能来自指令获取、数据依赖、执行管线、同步协议，也可能只是 kernel 收尾时等待尚未完成的内存操作。Nsight Compute 会给出这些状态的采样分布，但分布本身还不是瓶颈结论。分析必须从 scheduler 是否空置开始，再把 stall 样本落到源码、PTX/SASS 和对应硬件子系统。

0. Stall 在调度模型中的位置

一个 resident warp 尚未退出时属于 active warp。每到一次调度时刻，它要么 stalled，要么 eligible。Eligible warp 中只有一部分在当前时刻被 scheduler 选中，其余记作 not selected：

\[ W_{\mathrm{active}} = W_{\mathrm{stalled}} + W_{\mathrm{eligible}}, \qquad W_{\mathrm{eligible}} = W_{\mathrm{selected}} + W_{\mathrm{not\ selected}}. \]

selected 与 not_selected 会出现在 Warp State Statistics 中，却不是通常意义上的 stall reason。前者表示本次成功发射，后者表示指令已经 ready，只是 scheduler 选择了另一个 eligible warp。较高的 not_selected 往往说明延迟隐藏充足。

GPU Occupancy 的计算模型、资源约束与 Nsight Compute 指标详细说明了 resident、active、eligible 和 selected 的关系。Occupancy 决定 scheduler 最多能从多少个 resident warp 中寻找工作；warp stall 分析回答的是这些 warp 为什么没有变成 eligible。高 occupancy 无法保证高 issue efficiency，低 occupancy 也不必然导致性能不足。

先检查 scheduler 是否存在 skipped issue slot。若每个可用 issue slot 都能持续发射指令，某类 stall 样本很高也可能已经被其他 warp 完全隐藏。此时优化 stall reason 未必能缩短 kernel 时间。

2. 依赖等待与队列反压

依赖等待与队列反压经常被混在一起。它们对应两种不同的限制。

long_scoreboard 表示 consumer 指令正在等待某个 L1TEX 路径结果。它首先是延迟信号，不等于 DRAM 带宽已经饱和。低 cache hit rate、非合并访问、地址散乱、local-memory spill 都可能拉长依赖，也可能只是 load 与第一次使用之间没有足够的独立指令。

lg_throttle 表示 local/global memory 指令队列接近容量上限。此时问题偏向发出请求的速率：load/store 过密、访问粒度过小或同一段代码集中提交大量内存指令。一个 kernel 可以同时出现 long_scoreboard 与 lg_throttle，但两者需要不同的证据。

容易混淆的组合前者在等什么后者在等什么区分方法
long_scoreboard / lg_throttle既有 load 的结果新 memory instruction 的队列空间同时看 cache、DRAM/L1/TEX 吞吐与 Source 上的 producer-consumer 距离
short_scoreboard / mio_throttle既有 MIO 操作的结果新 MIO instruction 的队列空间检查 shared-memory wavefront、bank conflict 和 MIO 利用率
wait / math_pipe_throttle已发射算术指令的结果新算术指令所需的执行管线观察依赖链长度与对应 pipe utilization
barrier / membar其他 warp 到达 rendezvous内存操作满足 fence 顺序前者检查 warp 间工作量，后者检查内存语义和 outstanding operation

short_scoreboard 也不能直接翻译成 shared-memory bank conflict。Bank conflict 是一种可能的 producer 延迟，MUFU 结果和动态分支同样会进入相关依赖路径。NCU 的 Scoreboard Dependencies 与 shared-memory 指标能进一步缩小范围。

若 barrier 较高，等待者所在的 barrier 指令通常不是根因，根因在最后到达的 warp 上。应沿控制流向前检查各 warp 的工作量、内存延迟和分支分歧。Named barrier 的静态资源还可能减少 resident block 数；这一部分属于 occupancy 限制，见 CUDA Named Barrier：CTA 内分组同步、指令语义与 Occupancy 约束。

3. PC sampling 的统计口径

Warp stall metrics 来自周期性的 PC sampling。采样器从 active warp 中选择样本，记录它的 program counter 和当前调度状态。因此它描述的是观测分布，不是每个周期、每个 warp 的完整时间线。

Scoreboard stall 通常归到 consumer 指令。例如下面的 FFMA 需要 LDG 产生的寄存器，采样时 program counter 停在尚未发射的 FFMA：

LDG.E R8, [R2]        // producer: starts the memory request
IADD3 R12, R12, 1    // independent work
FFMA R16, R8, R20, R16
                      // consumer: long_scoreboard samples appear here

只看 Source 页某一行的 stall 样本，容易得出“FFMA 很慢”的错误结论。Source 页的 Attributed Stalls 与 Scoreboard Dependencies 用于把 consumer 上的等待追溯到 producer。源码、PTX 和 SASS 三层同时展开时，才能看到编译器重排后的真实距离。

Warp Stall Sampling (All Samples) 与 Warp Stall Sampling (Not-issued Samples) 可能来自不同 replay pass。两列的绝对样本数不保证严格相减或逐项对应，适合比较热点分布，不应当作精确周期计数。

Warp State Statistics 常用的单位是 warp cycles per issued instruction。它把样本换算为每发射一条指令平均经历的 warp cycles，并不是所有 stalled warp 的百分比。比较两个 kernel 时还要同时查看 duration、issued instructions 和 scheduler 发射情况，避免只压低归一化比值却增加总工作量。

4. 采集 NCU 报告

CUDA C++ 应保留行号信息。-lineinfo 不会启用完整调试模式，通常适合性能分析构建：

nvcc -O3 -lineinfo kernel.cu -o kernel

ncu \
  --section SpeedOfLight \
  --section SchedulerStats \
  --section WarpStateStats \
  --section SourceCounters \
  --section MemoryWorkloadAnalysis \
  -o stalls \
  ./kernel

ncu-ui stalls.ncu-rep

SchedulerStats 判断 issue slot 是否空置；WarpStateStats 给出状态分布；SourceCounters 负责 PC sampling 与源码归因；MemoryWorkloadAnalysis 用于验证 scoreboard 或 memory queue 判断。Section 名称会随版本调整，可先执行：

ncu --list-sections
ncu --query-metrics-mode suffix \
  --metrics smsp__pcsamp_warps_issue_stalled_long_scoreboard

初次排查也可以用 --set full，代价是 replay pass 和采集时间明显增加。对 PyTorch 或其他会启动子进程的 workload，先缩小 kernel 和 launch 范围：

ncu \
  --target-processes all \
  --set full \
  --kernel-name regex:kernel_name \
  --launch-skip 0 \
  --launch-count 1 \
  -o stalls \
  python workload.py

性能计数器采集常需要 replay kernel。输入数据、随机状态、文件 I/O 或跨 kernel 的依赖如果不能重复执行，报告可能失真。先用代表性且可重放的最小 workload 固定问题，再扩大到完整训练步骤。

5. NCU UI 分析路径

从调度器空闲到 SASS producer 的定位顺序

5.1 Details：先判断有没有空 issue slot

在 Details 页展开 Scheduler Statistics。先看 Active Warps Per Scheduler、Eligible Warps Per Scheduler、Issued Warps 和 Issue Slot Utilization。常见关系如下：

  • Active 很高、Eligible 很低、issue slot 经常空置：resident warp 很多，但大多数同时 stalled。
  • Eligible 持续大于 1、Issued 接近硬件发射上限：scheduler 已有足够选择，继续提高 occupancy 通常没有直接收益。
  • Active 偏低且 Eligible 间歇归零：回到 Occupancy section，检查寄存器、shared memory、block size、barrier 和 grid wave。

随后展开 Warp State Statistics。图表按每条 issued instruction 的平均 warp cycles 展示状态。先排除 selected 与 not_selected，再从数值最高的真实 stall reason 开始。若 issue slot 没有明显空置，这一步只用于理解执行特征，不应直接生成优化结论。

5.2 Source Counters：找到采样集中的 PC

Source Counters section 会汇总 PC sampling。切到 Source 页后，可按以下列排序：

Source 页列含义使用方法
Warp Stall Sampling (All Samples)包含 issued 与 not-issued 状态的全部样本观察该 PC 在整个采样中的权重
Warp Stall Sampling (Not-issued Samples)没有成功发射时的样本定位阻止发射的热点状态
Attributed Stalls从 consumer 等待回溯到相关 producer寻找真正需要提前、合并或优化的生产指令
Scoreboard Dependencies寄存器依赖关系及其 stall 归因检查 load-use、shared-use 和长依赖链
Instructions Executed该源码行或指令的动态执行量区分高频小代价与低频长等待

Source 页应同时显示 CUDA source、PTX 和 SASS。若只看到 SASS，先确认编译时加入 -lineinfo，再通过 Source 页面导入匹配的源码。不要仅凭高层源码行推断指令顺序，编译器可能合并、移动或删除操作。

5.3 Metric Details、Raw 与 Compare

选中指标后打开 Metric Details，核对 metric name、unit、raw value 和 NVIDIA 给出的定义。Raw 页适合确认派生指标背后的 counter，特别是百分比、平均值和 per-issued-instruction 指标。优化前后的报告使用 Compare，并把原报告设为 baseline；先比较 kernel duration，再比较 issued work、scheduler 和目标子系统。

Occupancy 只在第一、第二类场景中可能直接帮助隐藏等待，而且前提是新增 resident warp 能提高 Eligible Warps Per Scheduler。若理论 occupancy 已被寄存器或 shared memory 装箱限制，可在 occupancy 文章中的 block-size 周期波动模型下评估调整空间。反之，如果 scheduler 已持续发射，牺牲寄存器来换 occupancy 可能引入 spill，并把问题转成 long_scoreboard。

7. 分析检查表

  1. 固定比较对象。使用相同输入、GPU clocks、launch 参数和软件版本，先记录 kernel duration。
  2. 确认 issue slot 是否空置。没有发射缺口时，不把 stall 分布当作首要瓶颈。
  3. 分离 scheduler 状态。selected 与 not_selected 不是阻塞原因。
  4. 从状态进入源码。使用 Source Counters、Not-issued Samples、Attributed Stalls 和 Scoreboard Dependencies。
  5. 找到 producer。Scoreboard 样本通常停在 consumer；同时查看 PTX/SASS，确认真实依赖距离。
  6. 用子系统指标验证。Scoreboard 不等于带宽饱和，throttle 也不等于单条指令延迟。
  7. 重新测量总时间。优化应减少 duration，并避免通过增加指令数、spill 或 replay 工作量换取更好看的单项指标。

Warp stall 分析的核心不是寻找最大的柱状条，而是建立一条可验证的因果链：scheduler 出现发射缺口，某类等待使 eligible warp 不足，样本集中在特定 consumer，依赖回溯到具体 producer，对应硬件子系统也支持同一判断。链条闭合后，代码修改才有明确目标。
