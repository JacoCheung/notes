Codex 会话持久化机制：rollout JSONL 与 SQLite 状态库

Codex 的本地状态不是一个单一数据库。会话正文、列表索引、运行时状态、诊断日志和 memory 任务被拆在不同文件里。这种拆分有明确的工程目的:resume 需要顺序重放事件,列表页需要快速查询,后台 agent/job 需要断点恢复,日志需要单独服务排错。

看到 state_5.sqlite、logs_2.sqlite、rollout-*.jsonl 时,不要先假设它们都保存了一份完整对话。真正接近 transcript 的是 rollout JSONL。SQLite 文件更多是索引、运行状态、日志、目标进度和 summary 管线。

下文的 JSONL 和 SQL 表都是示意,用来说明数据形态和职责边界,不是稳定 schema。state_5.sqlite 里的 _5 或具体表名也不应被当成公开接口。

1. 存储边界

CODEX_HOME 默认是 ~/.codex。官方文档说它放 config、auth、logs、sessions、skills 和 standalone package metadata。CODEX_SQLITE_HOME 控制 SQLite-backed state 的位置,默认也在 CODEX_HOME 下。

本文只讨论本地持久化。远端同步、账号权限和产品侧 retention policy 不在这里展开。另一个边界也要先记住:官方文档确认了 CODEX_HOME、CODEX_SQLITE_HOME、session transcripts、archived sessions、thread rollout、SQLite-backed state DB 这些概念,但没有承诺 state_5.sqlite 里的表名和字段会稳定。

2. 10 轮会话写入路径

假设有一条 thread,标题叫 整理 FP8 note,工作目录是 /Users/me/projects/notes。这段 10 轮会话的写入路径如下:

轮次 事件 写入位置
1用户提交 review 请求rollout JSONL 追加用户消息; session_index / state 更新 preview 和时间
2Codex 搜索文件并读取 HTMLrollout 记录 tool call 和结果片段; logs 可能记录命令事件
3用户授权直接修改rollout 追加新 turn; state 更新时间戳
4Codex 调用 apply_patch 修改文章rollout 记录 file change item; state 更新时间
5Codex 执行 python3 scripts/build-index.pyrollout 记录命令输出; logs 可能写入 INFO / WARN
6用户要求压缩正文rollout 追加用户消息; thread preview 可能更新
7Codex 重写文章结构rollout 记录 patch、assistant 消息和相关命令
8用户要求提交并推送rollout 追加用户消息
9Codex 执行 commit / pushrollout 记录 git 命令和输出片段; logs 可能记录诊断事件
10用户询问本地 session 文件含义rollout 继续追加; memories 后续可能基于这条 thread 生成摘要

需要区分的是:10 轮会话不会平均分散到所有文件里。逐轮正文主要进 rollout。列表、状态库、日志库和 memory 库只保存各自需要的那部分信息。

3. 文件职责

下表按文件归纳存储内容。读它时可以先看两列:是否接近正文 和 风险边界。前者回答"能不能还原聊天",后者回答"分享前是否需要清理"。

文件 存储内容 主要用途 是否接近正文 风险边界
sessions/YYYY/MM/DD/rollout-*.jsonl append-only 事件流:session metadata、用户消息、assistant 消息、tool call、命令输出片段、cwd、模型、turn/item 事件、rollback marker、context compaction item。 恢复 thread、继续会话、archive / unarchive、rollback。官方 app-server 文档里的 persisted thread log / thread rollout 主要指这类文件。 是。它最接近完整聊天记录。 敏感级别最高。可能包含 prompt、代码、路径、命令输出和工具结果。
session_index.jsonl thread id、标题、preview、更新时间、cwd、rollout 路径。 聊天列表、快速定位、最近会话展示。Codex 不必每次扫描所有 rollout 文件。 否。它是索引,不是正文。 会暴露项目名、工作目录、thread 标题和会话预览。
state_5.sqlite thread 元信息、cwd、rollout path、archived / visible 状态、更新时间、spawn 关系、动态工具、agent jobs、remote control enrollment 等 runtime state。 thread 列表查询、状态恢复、子 agent 管理、动态工具恢复、后台 job 管理。官方把这类库称为 SQLite-backed state DB。 否。它保存状态和索引,不承担完整 transcript。 包含路径、标题、状态、工具配置和部分 preview。_5 更像内部 schema 版本,不要当稳定接口。
logs_2.sqlite 结构化日志:timestamp、level、target、thread_id、file、line、message、错误、警告、部分命令或输出片段。 排查 app-server / CLI / tool execution 问题,也服务 feedback / diagnostics。 否。它是运行日志。 日志不是全文,但路径、命令、错误栈和输出片段经常足够还原上下文。
goals_1.sqlite goal objective、status、token budget、tokens used、elapsed time、continuation deferral。 恢复长期 goal、跟踪 continuation、记录预算和执行进度。 否。 可能暴露任务目标、预算和执行状态。没有使用 goal 时,这个库可能只有少量记录。
memories_1.sqlite memory / summarization job、stage outputs、thread summary、从旧 chat 提取的偏好或项目上下文。 后台 memory 更新、thread 摘要生成、跨会话上下文恢复。真正可读的 memory 文件还可能在 ~/.codex/memories/ 下。 不是逐字正文,但可能是正文的压缩摘要。 summary 可能比原文更集中地暴露工作偏好、项目、常用路径和习惯。
*.sqlite-wal SQLite write-ahead log。数据库写入先落到这里,之后再合并回主库。 SQLite WAL 模式的写入机制。 跟随主库。 不是独立业务库,但可能暂存尚未 checkpoint 回主库的数据。
*.sqlite-shm SQLite shared-memory 协调文件,用于 WAL 模式下的并发读写协调。 SQLite 并发控制。 否。 不是业务数据入口。Codex 正在运行时看到它是正常现象。

4. 内容示例

上一节讲职责,这一节看数据形态。字段名仍然是示意,不能直接当作解析器依据;真正的内部 schema 会随 Codex 版本变化。

rollout JSONL 示例

{"type":"turn.started","turn_id":"turn_1"}
{"type":"user_message","turn_id":"turn_1","text":"帮我 review 这篇 note"}
{"type":"assistant_message","turn_id":"turn_1","text":"我先看一下文章结构和现有 series。"}
{"type":"item.started","turn_id":"turn_1","item":{"type":"command_execution","command":"rg --files posts"}}
{"type":"item.completed","turn_id":"turn_1","item":{"type":"command_execution","exit_code":0,"output":"posts/fp8-scaling-recipes.html\nposts/pytorch-record-stream.html\n..."}}
{"type":"turn.completed","turn_id":"turn_1","usage":{"input_tokens":12400,"output_tokens":820}}
{"type":"turn.started","turn_id":"turn_4"}
{"type":"user_message","turn_id":"turn_4","text":"直接修改"}
{"type":"item.started","turn_id":"turn_4","item":{"type":"file_change","path":"posts/fp8-scaling-recipes.html"}}
{"type":"item.completed","turn_id":"turn_4","item":{"type":"file_change","summary":"updated title and table section"}}

如果某轮触发 compaction 或 rollback,同一个 rollout 里还可能追加 context compaction item 或 rollback marker。app-server 文档明确说 rollback 会把 marker persist 到 rollout log。也就是说,rollout 不是简单的"聊天消息数组",它是 thread 生命周期的事件账本。

session_index.jsonl 示例

{"thread_id":"thr_fp8","name":"整理 FP8 note","preview":"帮我 review 这篇 note","cwd":"/Users/me/projects/notes","rollout_path":"sessions/2026/07/21/rollout-019f....jsonl","updated_at_ms":1784629000000}
{"thread_id":"thr_layout","name":"torch linear 和 layout","preview":"我这个表格写得有问题吗?","cwd":"/Users/me/projects/notes","rollout_path":"sessions/2026/07/20/rollout-019e....jsonl","updated_at_ms":1784540000000}

这个文件看起来轻,但它仍然会泄漏项目名、工作目录、thread 标题和会话预览。

state_5.sqlite 示例

threads
thread_id | name          | cwd                       | rollout_path                         | archived | model       | updated_at_ms
thr_fp8   | 整理 FP8 note | /Users/me/projects/notes  | sessions/2026/07/21/rollout-...jsonl | 0        | gpt-5-codex | 1784629000000

thread_spawn_edges
parent_thread_id | child_thread_id | status
thr_fp8          | thr_fp8_review  | completed

thread_dynamic_tools
thread_id | tool_name | enabled_at_ms
thr_fp8   | github    | 1784628300000

agent_jobs
job_id | thread_id | kind             | status
job_7  | thr_fp8   | subAgentReview   | completed

这类库解释了两个现象:Codex 打开聊天列表很快,删除 thread 时也不能只删一个 JSONL 文件。app-server 的 delete 文档说,删除 persisted thread 时会移除 rollout files 和 associated metadata。

logs_2.sqlite 示例

logs
ts_ms         | level | thread_id | target          | message
1784628100000 | INFO  | thr_fp8   | codex.tool.exec | running command: python3 scripts/build-index.py
1784628112000 | WARN  | thr_fp8   | codex.tool.exec | command exited non-zero
1784628113000 | ERROR | thr_fp8   | app_server      | failed to parse post metadata at posts/fp8-scaling-recipes.html

官方 troubleshooting 文档也提醒,分享日志前要先检查敏感信息。这条规则来自实际风险:路径、命令和错误输出经常足够还原上下文。

goals_1.sqlite 示例

thread_goals
thread_id | objective                       | status | token_budget | tokens_used | elapsed_ms

如果没有使用 goal 或 continuation,这个库可能只有几行。这不表示文件无效,只表示这条功能线当前没有多少状态。

memories_1.sqlite 示例

jobs

mem_1  | summarize_thread | thr_fp8          | completed

stage1_outputs

memory 不一定马上生成。官方文档说 Codex 会等 chat idle 足够久,并且会在后台更新。它还会跳过 active 或 short-lived sessions。

5. 敏感数据边界

从分享、打包、提交 issue 的角度看,这些文件可以按以下顺序处理:

  1. auth.json:当成密码。官方文档也这么说。
  2. rollout-*.jsonl:当成完整聊天记录。里面可能有 prompt、代码、命令输出、路径、tool result。
  3. memories/ 和 memories_1.sqlite:当成压缩后的工作偏好和项目上下文。它不一定逐字保存原文,但 summary 可能暴露偏好和项目。
  4. logs_2.sqlite:当成诊断日志。它不是全文,但可能有足够多的片段。
  5. state_5.sqlite / session_index.jsonl:当成索引和元信息。不能因为"不是正文"就直接公开。

排查 resume 问题时,先看 rollout。排查列表展示问题时,看 session index 和 state DB。排查 Codex 运行错误时,看 logs。排查偏好和历史上下文来源时,看 memories。不要把这些文件打成一个包直接发出去:它们暴露的信息类型不同,清理方式也不同。
