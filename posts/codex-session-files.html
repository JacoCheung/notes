Codex 会话持久化机制：rollout JSONL 与 SQLite 状态库

一条 Codex 会话会持续产生多种状态：用户与 assistant 的消息构成会话历史，工具调用和命令输出记录执行过程，thread 标题与工作目录用于列表和恢复，日志服务于故障诊断，memory 则保存后续任务可能复用的摘要。Codex 将这些信息分开持久化，因此 ~/.codex 中会同时出现 JSONL、SQLite 数据库以及 SQLite 的 WAL 辅助文件。

公开接口给出了这套存储的逻辑边界：session transcript 和持久化 thread log 位于 CODEX_HOME，其中 thread log 使用 JSONL；sqlite_home 保存 agent jobs 与其他可恢复运行状态。state_5.sqlite、logs_2.sqlite 等文件名及其 schema 属于具体版本的实现形态。一个 10 轮会话足以把各类文件的职责、排障入口和敏感性串联起来。

证据范围：下文用 schematic record 表示具体 JSONL 字段、SQLite 文件名、表名和列名，不把它们作为稳定的磁盘 schema。公开且受支持的集成入口是 app-server protocol 与配置项；内部文件不具备 API 兼容性承诺。

1. 存储边界

CODEX_HOME 默认指向 ~/.codex，用于保存 config、auth、logs、sessions、skills 和 standalone package metadata。CODEX_SQLITE_HOME 决定 SQLite-backed state 的位置；未单独配置时，它也位于 CODEX_HOME 下。

从持久化职责看，本地数据可以分成两层。事件层保存 thread 中依次发生的 turn 与 item，适合恢复会话正文和执行轨迹；状态层保存列表、索引、后台作业以及其他可恢复 metadata，适合快速查询当前状态。日志和 memory 分别面向诊断与跨会话复用。本文讨论这四类本地数据，范围不包括远端同步、账号权限和产品侧 retention policy。

2. 10 轮会话写入路径

文件之间的分工在会话推进过程中最容易看清。假设一条名为 整理 FP8 note 的 thread 运行在 /Users/me/projects/notes，下面用 10 个 turn 展开其逻辑写入路径：

轮次 事件 写入位置

3用户授权直接修改rollout 追加新 turn；state 更新时间戳
4Codex 调用 apply_patch 修改文章rollout 记录 file change item；state 更新时间
5Codex 执行 python3 scripts/build-index.pyrollout 记录命令输出；logs 可能写入 INFO / WARN

表中的“写入位置”表示 thread、turn 与 item 在逻辑上归入哪类持久化数据。实际磁盘写入可以批处理或延后，日志与 memory 也可能由后台任务异步生成；公开文档没有规定逐 turn 的文件写入时序。

5. 敏感数据边界

不同文件暴露的信息粒度不同。准备分享日志、打包目录或提交 issue 时，可以按敏感性从高到低处理：

  1. auth.json：按密码处理，官方文档采用相同的安全级别。
  2. rollout-*.jsonl：按完整聊天记录处理，其中可能包含 prompt、代码、命令输出、路径和 tool result。
  3. memories/ 和 memories_1.sqlite：按压缩后的工作偏好与项目上下文处理。Summary 可能集中呈现原文中的偏好和项目信息。
  4. logs_2.sqlite：按诊断日志处理，零散记录也可能提供足够多的任务线索。
  5. state_5.sqlite / session_index.jsonl：按索引与元信息处理，其中的路径、标题和 preview 同样需要脱敏。

文件职责也决定了排障入口：resume 问题对应 rollout，thread 列表问题对应 session index 与 state DB，运行错误对应 logs，历史偏好或上下文来源对应 memories。分享前应分别审查并脱敏，而不是把整个目录作为一份诊断包发布。

Codex Session Persistence: Rollout JSONL and SQLite State

A Codex session produces several kinds of state. User and assistant messages form the conversation history; tool calls and command output record execution; thread titles and working directories support listing and resumption; logs serve diagnostics; and memory stores summaries that later tasks may reuse. Codex persists these concerns separately, which is why ~/.codex can contain JSONL streams, SQLite databases, and SQLite WAL support files at the same time.

The public interfaces define the logical boundary of this storage. Session transcripts and the persistent thread log live under CODEX_HOME, and the thread log uses JSONL. sqlite_home stores agent jobs and other resumable runtime state. Filenames such as state_5.sqlite and logs_2.sqlite, along with their schemas, belong to a particular implementation version. A ten-turn example below shows what category of information each file may carry and how that distinction affects troubleshooting and disclosure.

Evidence boundary: The concrete JSONL fields, SQLite filenames, tables, and columns below are schematic records rather than a stable on-disk schema. The app-server protocol and documented configuration are the supported integration surfaces, while internal files carry no API compatibility guarantee.

1. Storage Boundary

CODEX_HOME defaults to ~/.codex and contains configuration, authentication data, logs, sessions, skills, and standalone package metadata. CODEX_SQLITE_HOME selects the location of SQLite-backed state; unless configured separately, that location is also under CODEX_HOME.

Local persistence has two primary layers. The event layer records the turns and items that occur in a thread, making it suitable for reconstructing conversation and execution history. The state layer stores listings, indexes, background jobs, and other resumable metadata for efficient lookup. Logs and memory then serve diagnostics and cross-session reuse, respectively. This article covers those four local categories; remote synchronization, account permissions, and product retention policies remain outside its scope.

2. Write Path for a Ten-Turn Session

The division of responsibility becomes clearer as a session advances. Suppose a thread titled 整理 FP8 note runs in /Users/me/projects/notes. The following ten turns illustrate its logical persistence path:

Turn Event Possible write location
1The user requests a reviewAppend the user message to rollout JSONL; update preview and timestamps in the session index or state
2Codex searches for files and reads HTMLRecord tool calls and result fragments in the rollout; logs may record command events
3The user authorizes direct editsAppend a new turn to the rollout; update the state timestamp
4Codex uses apply_patch to edit an articleRecord a file-change item in the rollout; update state
5Codex runs python3 scripts/build-index.pyRecord command output in the rollout; logs may contain INFO or WARN entries
6The user asks for a shorter articleAppend the user message to the rollout; the thread preview may change
7Codex rewrites the article structureRecord patches, assistant messages, and related commands in the rollout
8The user asks for a commit and pushAppend the user message to the rollout
9Codex commits and pushesRecord Git commands and output fragments in the rollout; logs may contain diagnostic events
10The user asks what the local session files meanContinue appending to the rollout; a later memory job may summarize the thread

The “possible write location” column assigns each thread, turn, and item to a logical storage category. Physical writes may be batched or delayed, and background jobs may generate logs or memory later. Public documentation does not specify per-turn disk-write ordering.

Files close to the transcript can preserve prompts, code, and tool output. Compact indexes and state databases may still disclose project names, paths, or task objectives.

5. Sensitive-Data Boundary

Each file exposes a different granularity of information. When preparing logs, an archive, or an issue report, handle them in descending order of sensitivity:

  1. auth.json: treat it as a password. Official documentation uses the same guidance.
  2. rollout-*.jsonl: treat it as a complete conversation record. It may include prompts, code, command output, paths, and tool results.
  3. memories/ and memories_1.sqlite: treat them as compressed work preferences and project context. They may not preserve the original text verbatim, but summaries can reveal preferences and project details.
  4. logs_2.sqlite: treat it as diagnostic logging. It is not the full transcript, but it may contain revealing fragments.
  5. state_5.sqlite and session_index.jsonl: treat them as indexes and metadata. Files do not become safe to publish merely because they are not the conversation body.

The same responsibilities determine the troubleshooting entry point: resume failures map to the rollout, thread-list problems to the session index and state database, runtime errors to logs, and unexpected historical context to memory. Review and redact each category separately before disclosure instead of publishing the entire directory as one diagnostic bundle.
