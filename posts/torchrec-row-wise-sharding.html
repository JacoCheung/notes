TorchRec Row-wise Sharding

Row-wise sharding 是 TorchRec 分布式 embedding 的一种分片方式，通过跨 rank 划分表行扩展存储与查表能力。本文以 ShardedEmbeddingCollection 为对象，介绍 KJT 输入组织、ID 分发、本地 lookup、输出顺序恢复与梯度回传，并用源码链接和序列图标明 forward、backward 中的 NCCL 通信、主机同步与数据依赖。

本文分析 TorchRec 提交 1d87b8f79b7bb 中的 ShardedEmbeddingCollection，采用多 rank、CUDA/NCCL 和 eager 模式。它返回 unpooled sequence embeddings。基础例子使用固定 batch stride、无权重的 KJT，去重和通信 codec 单独作为可选分支说明。实现机制以这份 TorchRec 源码为依据；Pooled EmbeddingBag 的输出通信走另一条路径。

1. 行分片与 KJT

假设 embedding 表有 8 行，每行 D 个元素，均匀分在两个 rank 上：rank 0 持有全局行 0-3，rank 1 持有全局行 4-7。每个 rank 都有自己的训练样本，但样本中的 ID 可以指向任何一段表。

请求 rank 0 的一个 feature发往 rank 0发往 rank 1
全局 ID：[6, 2, 6, 1]本地 ID：[2, 1]本地 ID：[2, 2]，对应全局行 6
最终需要的向量[E6, E2, E6, E1]，保持原始 occurrence 顺序

在这个等长、连续分片的例子中，owner = id // 4，local_id = id % 4。实际分桶还会读取分片的 block sizes 等信息，不能把这个简化公式直接用于所有 sharding plan。TorchRec 用 KeyedJaggedTensor（KJT）携带 feature keys、展平后的 ID values，以及各样本的 lengths / offsets；路由 ID 时必须一起重排这些边界信息。bucketize_kjt_before_all2all

每次 lookup 在 rank 之间传输的是 ID 请求和查到的向量，embedding 表仍由各 rank 持有自己的分片。本地 lookup 处理来自所有请求 rank 的 ID，只访问本 rank 的行，然后把结果发回请求方。row-wise sequence sharding 组件

2. Forward 数据流

ShardedModule.forward 创建 context 后，依次执行输入分发、本地计算和输出分发。省略类型标注后，调用顺序如下：

ctx = module.create_context()
dist_input = module.input_dist(ctx, features).wait().wait()
output = module.compute_and_output_dist(ctx, dist_input)
# output 是 lazy awaitable；消费结果时才完成输出等待与重建。

两个 wait() 各完成一段工作。第一个取得接收尺寸并发起 KJT payload 通信；第二个消费 payload，重建本地 lookup 所需的 KJT。随后，compute_and_output_dist 查本地表并发起输出通信。ShardedModule.forward；EC compute 与 output_dist

图 1 按模块阶段概括通信。对于本文固定 stride、无 weights 的 KJT，每个 rank 的一个 row-wise group 在 forward 中发起 4 次 AllToAll：输入 splits、lengths、ID values 各 1 次，输出 embedding vectors 1 次。输入阶段先发起 splits，第一次 wait 时再发起 lengths 和 ID values。图中 IN / OUT 色块分别汇总这 3 次和 1 次调用；计数对应使用 NCCL backend 的 PyTorch collective，不是底层 NCCL send/recv 或 GPU kernel 的数量。Backward 的梯度通信另见第 5 节。SplitsAllToAllAwaitable；KJT 的 payload awaitable；sequence AllToAll 的 forward / backward

3. Input Distribution

输入重排映射

ShardedEmbeddingCollection.input_dist 先按 sharding / lookup 需要的顺序重排 feature，再按组拆分。若开启 use_index_dedup，它会调用 jagged_unique_indices，保存原始 features 和 reverse_indices，并把去重后的 KJT 交给分桶逻辑。这是在请求 rank 的输入上做去重，并不是一次跨 rank 的全局去重。ShardedEmbeddingCollection.input_dist；EC 去重与 inverse mapping

Row-wise 分桶把 ID 按目标 rank 分组，生成 owner-local IDs 和新的 lengths，同时保存 unbucketize_permute_tensor。这张映射负责撤销路由导致的重排；可选的 reverse_indices 则负责把 unique 结果展开为原始的每一次出现。两者用途不同，不能互相替代。bucketize_kjt_before_all2all

两阶段 AllToAll

每个 rank 要接收多少 ID，取决于本批次的请求分布。TorchRec 因此先交换 split-size metadata，再按已知尺寸分配接收 buffer 并传输真正的 KJT 数据。

  1. 发起 splits 通信。 SplitsAllToAllAwaitable 发起异步 dist.all_to_all_single，交换各 rank 之间需要发送的数据尺寸。
  2. 第一次 wait。 先消费 splits 的 Work，再把 CUDA 上的尺寸通过 _safe_tolist_2d 转成 Python lists。CPU 必须读到这些数值，才能决定接收尺寸。随后构造 tensors awaitable，并在其构造过程中发起 payload 通信。
  3. 传输 payload。 对于本文的基础 KJT，主要是 lengths 和 ID values 各自的 AllToAll；有 weights 或 variable stride 时，实际 tensor 列表会变化。
  4. 第二次 wait。 消费 payload 的 Work，执行 KJT.dist_init，把接收到的布局 recat 为 lookup 所需的 feature 布局，并整理 KJT metadata。

Awaitable[Awaitable[KJTList]] 对应的正是这两个阶段：外层确定接收尺寸并发起传输，内层把收到的数据整理成可用输入。因此，第一次 wait 返回时，ID payload 仍可能在传输。SplitsAllToAllAwaitable；KJT 的 payload awaitable

等待与主机同步

CPU 等待不只发生在接收 splits 之后。发起通信前，KJT.dist_splits() 就需要主机上的 length_per_key。若这个 metadata 尚未缓存，TorchRec 会对 CUDA lengths 求和，再通过 _safe_tolist 取回 Python list。接收 payload 后，固定 stride 分支的 dist_init() 又会对新 KJT 调用 sync()，整理它的 length_per_key 和 offsets metadata。KJT.dist_splits；length_per_key 的按需计算；KJT.dist_init 的重排与 sync

图 3 用 D1、D2、D3 分别标出发送尺寸准备、接收尺寸读回和 KJT metadata 重建。非空 CUDA tensor 经过 safe-list 路径时，会先做 D2H，再显式同步当前 stream；已缓存的 metadata 可以直接复用。Splits 的 _wait_impl 也说明了转成主机 list 时的 CPU 等待。CUDA metadata 的 D2H 与 stream synchronize；SplitsAllToAllAwaitable

异步 collective 的 Work.wait() 标出消费通信结果的位置。仅凭这个调用，无法断定 CPU 会等待整张 GPU，也无法推断 NCCL 内部所有 stream 的行为。读图时应把这类通信依赖与必须拿到主机数值的 metadata 同步分开。

Recat 在本地重排数据，把通信接收时的 rank / feature 布局转成 lookup 所需的布局，这一步不发起跨 rank 通信。完成后，row owner 就有了各请求 rank 发来的 ID，可以开始查表；embedding 向量将在后面的输出分发阶段送回。

4. Lookup 与输出恢复

本地 Lookup

GroupedEmbeddingsLookup 将本地 KJT 按兼容的 embedding 配置拆组，调用对应的 embedding kernel。以 fused backend 为例，BatchedFusedEmbedding 构造的 TBE 使用 PoolingMode.NONE，向 backend 传入 IDs 和 offsets，得到每个 ID 对应的向量。这里没有新增跨 rank collective。图中的 backend 计算与 TorchRec 包装层分开标出，便于区分输入准备和查表；具体 kernel 实现和数量取决于输入与 backend。GroupedEmbeddingsLookup.forward；BatchedFusedEmbedding 的 backend 配置

调用 backend 前，TorchRec 还会取得 KJT offsets，并把 values / offsets 转成对应 backend 配置的 index / offset dtype。这些本地准备操作应与真正的查表区分开，不应仅凭它们处在 lookup 调用范围内就算成一次 embedding 访存。BaseBatchedEmbedding.forward 的 IDs / offsets 转换

输出 AllToAll

SequenceEmbeddingsAllToAll 把向量从 row owners 送回请求 ranks。All2All_Seq_Req.forward 先用 forward_recat 整理发送布局，按需执行通信 codec 的 encode，再发起异步 AllToAll。输出被消费时，All2All_Seq_Req_Wait.forward 消费通信请求并按需 decode。SequenceEmbeddingsAllToAll 与 unbucketize；sequence AllToAll 的 forward / backward

Lazy Wait 与顺序恢复

收到向量后，恢复顺序分成两层：先通过 unbucketize_permute_tensor 回到分桶前的输入顺序；如果输入做过去重，再通过 reverse_indices 展开回原始 occurrences。最后按 feature 拆分并附上原始 lengths，构造 Dict[str, JaggedTensor]。默认路径用 index_select 展开，源码也提供可选的 gather 分支；两者承担相同的 occurrence 恢复任务。construct_jagged_tensors

例如启用去重后，[2, 6, 2] 可以表示为 unique IDs [2, 6] 和映射 [0, 1, 0]。通信回来的 unique embeddings 是 [E2, E6]，展开后仍然必须得到 [E2, E6, E2]。Unique 的实际排列由算子返回，例子只说明 inverse mapping 的作用。

5. Backward 与参数更新

输出 embedding 的梯度沿 autograd 图回传，依次经过顺序恢复操作、反向 AllToAll 和本地 embedding kernel。图 7 展示整条路径，图 8 至图 12 展开各阶段；图中的 forward wrapper 和实际执行 backward 的 autograd node 分开列出。

输出重建的反向传播

Backward 从下游对每个输出 embedding 的梯度开始。按 feature 拆开的向量先汇回对应的布局；若 forward 展开过 duplicate occurrences，反向要把这些位置的梯度加回同一个 unique 位置。例如 [2, 6, 2] 的三个 occurrence 梯度 [g0, g1, g2]，给 unique IDs 的梯度就是 [g0 + g2, g1]。接着，unbucketize 对应的张量操作把梯度恢复为输出 AllToAll 接收时的 bucket 布局。这是对 forward 中 tensor 操作的求导，不是依次调用各个 nn.Module.backward()。construct_jagged_tensors；SequenceEmbeddingsAllToAll 与 unbucketize

反向 AllToAll

All2All_Seq_Req_Wait.backward 先发起反向 AllToAll，把请求 rank 上的向量梯度送回 row owners；它交换 forward 的 send / receive splits，并按需使用 backward codec。随后，沿 dummy tensor 建立的 autograd 依赖，All2All_Seq_Req.backward 消费这个请求，按需 decode，再用 backward_recat 恢复本地 lookup 的布局。若 GRADIENT_DIVISION 开启，还会除以 process-group size。sequence AllToAll 的 forward / backward

请求端通信等待

发起反向通信后，dummy gradient 继续推动 autograd 执行 request-side backward。这个节点先调用 req.wait()，再 decode、执行 backward recat，并按配置缩放梯度，最后把结果交回本地 lookup。

本地 Embedding 更新

向量梯度回到本地 lookup 后，fused TBE 路径由 backend 在 backward 中完成其配置的 embedding 更新。TorchRec 暴露的 EmbeddingFusedOptimizer.step() 在此实现中设置 backend 的 learning rate，并不是另一次独立的逐行更新。模型其他参数由各自的 optimizer 管理，其他 compute kernel 的更新方式则取决于其实现。BatchedFusedEmbedding 的 backend 配置；EmbeddingFusedOptimizer.step

整数输入边界

输入 ID、lengths、offsets 是整数，EC 的输入准备和分发运行在 torch.no_grad() 内。因此，本文这条反向路径不会再把输入阶段的 splits、lengths、IDs AllToAll 各倒放一遍。需要跨 rank 返回的是 embedding 输出的梯度。ShardedEmbeddingCollection.input_dist

对于单个通信组、无额外 KJT 字段的基础路径，AllToAll 调用分别传输输入 splits、lengths、values，输出 embeddings，以及反向 embedding gradients。这个计数描述调用层面的五类通信。多个 sharding group、可选字段和后面的 metadata 融合会改变调用组织方式，NCCL kernel 数量也不能直接由它推出；其他模型参数的通信另计。SplitsAllToAllAwaitable；KJT 的 payload awaitable；sequence AllToAll 的 forward / backward

TorchRec row-wise sharding

Row-wise sharding distributes embedding-table rows across ranks to scale storage and lookup in TorchRec. Using ShardedEmbeddingCollection, this article covers KJT inputs, ID distribution, local lookup, output reconstruction and gradient return. Source-linked sequence diagrams identify NCCL communication, host synchronization and data dependencies in forward and backward execution.

The implementation described here is ShardedEmbeddingCollection at TorchRec commit 1d87b8f79b7bb, running in eager mode across multiple ranks with CUDA/NCCL. It returns unpooled sequence embeddings. The baseline uses an unweighted KJT with fixed batch stride; deduplication and communication codecs appear as optional branches. All implementation explanations refer to this TorchRec source. 1. Row sharding and KJT

Consider an eight-row embedding table with D elements per row. Rank 0 owns global rows 0-3 and rank 1 owns rows 4-7. Each rank receives its own training examples, whose IDs may refer to either shard.

One feature requested by rank 0Send to rank 0Send to rank 1
Global IDs: [6, 2, 6, 1]Local IDs: [2, 1]Local IDs: [2, 2], both referring to global row 6
Required output[E6, E2, E6, E1], in original occurrence order

For this equally sized, contiguous partition, owner = id // 4 and local_id = id % 4. The actual bucketization code takes shard block sizes and other metadata; this simple formula is not universal. TorchRec carries feature keys, flattened ID values, and per-example lengths / offsets in a KeyedJaggedTensor (KJT). Routing values must preserve the corresponding sequence boundaries. bucketize_kjt_before_all2all

Each lookup exchanges ID requests and result vectors while the table remains partitioned across ranks. A local lookup handles requests from all participating ranks, reads only its own table shard, and sends the results back to the requesters. Row-wise sequence sharding components

2. Forward data flow

ShardedModule.forward creates a context, distributes input, then runs local computation and output distribution. With type annotations omitted, the call order is:

ctx = module.create_context()
dist_input = module.input_dist(ctx, features).wait().wait()
output = module.compute_and_output_dist(ctx, dist_input)
# Consuming the lazy output completes output waiting and reconstruction.

The two waits represent different stages. The first obtains receive sizes and launches KJT payload communication. The second consumes that payload and reconstructs the KJT needed by the local lookup. compute_and_output_dist then performs local computation and initiates output distribution. ShardedModule.forward; EC compute and output_dist

Figure 1 summarizes communication by module stage. With the fixed-stride, unweighted KJT used here, each rank issues 4 forward AllToAll calls per row-wise group: one each for input splits, lengths, and ID values, plus one for output embedding vectors. Splits launch first; the first wait then launches lengths and ID values. The IN / OUT bands summarize these 3 and 1 calls. These are PyTorch collective calls using the NCCL backend; the count does not describe underlying NCCL send/recv operations or GPU kernels. 3. Input distribution

Input permutation maps

ShardedEmbeddingCollection.input_dist orders features for the sharding and lookup layout, then splits them into groups. With use_index_dedup, it calls jagged_unique_indices, saves the original features and reverse_indices, and sends the deduplicated KJT into bucketization. This deduplicates inputs on the requesting rank; it is not a cross-rank global deduplication operation. ShardedEmbeddingCollection.input_dist; EC deduplication and inverse mapping

Row-wise bucketization groups IDs by destination rank, producing owner-local IDs and new lengths. It also saves unbucketize_permute_tensor, which reverses the routing permutation. The optional reverse_indices mapping expands unique results back to their original occurrences. These mappings solve distinct problems. bucketize_kjt_before_all2all

Two-stage AllToAll

Receive sizes depend on this batch's requests. TorchRec first exchanges split-size metadata, then allocates receive buffers and transfers the KJT payload.

  1. Launch splits. SplitsAllToAllAwaitable issues asynchronous dist.all_to_all_single for the sizes exchanged between ranks.
  2. First wait. Consume the splits Work and convert CUDA sizes to Python lists through _safe_tolist_2d. The host needs these values to determine receive sizes. Constructing the tensors awaitable then launches payload communication.
  3. Transfer payload. The baseline KJT sends lengths and ID values in separate AllToAll calls. Weights or variable stride can change the tensor list.
  4. Second wait. Consume payload Work handles and run KJT.dist_init, recatting the received data into the lookup layout and preparing KJT metadata.

Awaitable[Awaitable[KJTList]] reflects these two stages. The outer awaitable determines receive sizes and starts the transfer; the inner one turns the received data into usable input. The ID payload may still be in flight when the first wait returns. SplitsAllToAllAwaitable; KJT payload awaitables

Waits and host synchronization

Host waiting is not limited to receiving splits. Before communication starts, KJT.dist_splits() requires host-side length_per_key. If uncached, TorchRec reduces CUDA lengths and obtains a Python list through _safe_tolist. After receiving payload, the fixed-stride branch of dist_init() calls sync() on the new KJT to prepare its length and offset metadata. KJT.dist_splits; On-demand length_per_key computation; KJT.dist_init: permutation and sync

Figure 3 labels send-size preparation, receive-size readback, and KJT metadata reconstruction as D1, D2, and D3. For a nonempty CUDA tensor, the safe-list path performs D2H and explicitly synchronizes the current stream. Cached metadata can be reused. The splits _wait_impl also describes CPU waiting during conversion to a host list. CUDA metadata D2H and stream synchronization; SplitsAllToAllAwaitable

An asynchronous collective's Work.wait() marks where TorchRec consumes communication results. The call alone does not establish that the CPU waits for the entire device, or explain all internal NCCL stream behavior. Keep this communication dependency separate from metadata operations that require values on the host.

Recat transforms the received rank / feature layout into the layout required by the local lookup. It is a local permutation, not another cross-rank transfer. The row owner now has its requests, but has not yet returned embedding vectors.

4. Lookup and output reconstruction

Local lookup

GroupedEmbeddingsLookup splits the local KJT into compatible embedding groups and calls their embedding kernels. In the fused path, BatchedFusedEmbedding configures TBE with PoolingMode.NONE, passing IDs and offsets to obtain vectors for the distributed ID occurrences. This stage adds no cross-rank collective. The diagram separates backend computation from TorchRec wrappers to distinguish input preparation and table access. Kernel implementations and counts depend on the input and backend. GroupedEmbeddingsLookup.forward; BatchedFusedEmbedding backend configuration

Before calling the backend, TorchRec obtains KJT offsets and converts values / offsets to the backend's configured index / offset dtypes. These local preparation operations are distinct from the table lookup, even though they occur within the lookup call's scope. BaseBatchedEmbedding.forward: ID / offset conversion

Output AllToAll

SequenceEmbeddingsAllToAll returns vectors from row owners to requesting ranks. All2All_Seq_Req.forward applies forward_recat to prepare the send layout, optionally encodes the payload, and launches asynchronous AllToAll. When the output is consumed, All2All_Seq_Req_Wait.forward consumes the request and optionally decodes the result. SequenceEmbeddingsAllToAll and unbucketize; Sequence AllToAll forward / backward

Lazy waits and order restoration

Reconstruction has two layers. First, unbucketize_permute_tensor restores the pre-bucketization order. If IDs were deduplicated, reverse_indices expands unique embeddings back to occurrences. The result is split by feature and paired with the original lengths to form Dict[str, JaggedTensor]. The default expansion uses index_select; an optional gather branch serves the same purpose. construct_jagged_tensors

For example, [2, 6, 2] can be represented by unique IDs [2, 6] and the inverse map [0, 1, 0]. Returning [E2, E6] must still produce [E2, E6, E2] for the caller. The operator determines the actual unique ordering; the example illustrates the mapping.

5. Backward and parameter updates

Output embedding gradients flow through the reconstruction operations, reverse AllToAll, and the local embedding kernel. Figure 7 shows the full path; Figures 8 through 12 expand its stages. Forward wrappers and the autograd nodes that execute backward appear as separate actors.

Backward through reconstruction

Backward starts from downstream gradients for each output embedding. Gradients from feature splits rejoin the corresponding layout. If forward expanded duplicate occurrences, backward adds their gradients into the same unique position: occurrence gradients [g0, g1, g2] for [2, 6, 2] become [g0 + g2, g1] for the unique IDs. Differentiating unbucketization then restores the bucket layout received by output AllToAll. These are derivatives of tensor operations, not successive calls to wrapper modules' backward() methods. construct_jagged_tensors; SequenceEmbeddingsAllToAll and unbucketize

Backward AllToAll

All2All_Seq_Req_Wait.backward launches the reverse AllToAll, returning embedding gradients from requesting ranks to row owners. It swaps the forward send / receive splits and optionally applies a backward codec. The dummy-tensor autograd edge then leads to All2All_Seq_Req.backward, which consumes the request, optionally decodes, and applies backward_recat to recover the local lookup layout. When GRADIENT_DIVISION is enabled, it also divides by process-group size. Sequence AllToAll forward / backward

Request-side communication waits

After reverse communication launches, the dummy gradient advances autograd to the request-side backward. That node consumes the request, decodes, applies backward recat, optionally scales the gradient, and returns it to the local lookup.

Local embedding updates

In the fused TBE path, the backend performs its configured embedding update during backward after receiving the local lookup gradients. TorchRec's EmbeddingFusedOptimizer.step() sets the backend learning rate in this implementation; it is not a second independent row update. Other model parameters still use their configured optimizers, and other compute kernels need not follow this fused behavior. BatchedFusedEmbedding backend configuration; EmbeddingFusedOptimizer.step

Integer-input boundary

IDs, lengths, and offsets are integers, and EC prepares and distributes input under torch.no_grad(). Consequently, this backward path does not reverse each input splits, lengths, and ID AllToAll. It sends the differentiable embedding output gradients back to their owners. ShardedEmbeddingCollection.input_dist

For one communication group with the baseline KJT fields, the inventory is input splits, lengths, and values; output embeddings; and reverse embedding gradients. These five AllToAll calls are not a fixed NCCL kernel count. Additional sharding groups, optional fields, and later metadata fusion change how calls are organized. Communication for other model parameters is outside this inventory. SplitsAllToAllAwaitable; KJT payload awaitables; Sequence AllToAll forward / backward

A batch follows this dependency chain: route IDs → local lookup → return and reconstruct embeddings → downstream computation → return gradients → local update. Input distribution also has a CPU dependency: the host must read split sizes before launching the corresponding payload. These dependencies also constrain which work can overlap across batches.
