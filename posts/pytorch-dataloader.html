PyTorch DataLoader 工作原理

PyTorch DataLoader 把数据集中的样本组织成训练批次。对于按索引访问的 map-style Dataset，Sampler 决定读取哪些样本，BatchSampler 决定如何分批，Dataset 完成读取与处理，collate_fn 将样本组装成模型输入。本文以五个样本为例，说明这条路径在主进程、单个 worker、多个 worker 和 DDP 训练中的执行方式，以及预取、返回顺序和分布式分片如何配合。

本文固定分析 PyTorch 2.8.0 的普通 map-style Dataset。序列图中的消息链接到该版本源码。num_workers=0 表示没有子进程，num_workers=1 才表示一个独立的数据加载 worker；worker 通常是进程，不是线程。

1. 索引与批次

五个组件

Map-style Dataset 建立索引到样本的映射，典型接口是 dataset[index]。索引不一定是整数；本文使用 0…4，并固定采样顺序为 [3, 0, 4, 1, 2]。Dataset 可以从文件解码图片、查询数据库或处理内存数据；它不负责决定本轮采样顺序。Dataset

组件职责本例
Sampler产生样本索引3, 0, 4, 1, 2
BatchSampler将索引分组[3,0], [4,1], [2]
Dataset按索引读取并处理样本dataset[3] 得到 x=[3,30]、y=1
collate_fn将样本列表合成 batch两个 x 堆成 shape 为 [2,2] 的 tensor
DataLoader / iterator协调采样、读取、预取与交付每次 next(iterator) 返回一批

BatchSampler 处理的是索引列表，collate_fn 接收的是已经读出的样本列表。两者之间发生实际的数据访问。默认配置下，shuffle=False 对应 SequentialSampler，shuffle=True 对应 RandomSampler；提供 batch_size 时，DataLoader 通常再包一层 BatchSampler。Sampler / BatchSampler / collate_fn；SequentialSampler / RandomSampler

五个样本

样本 i 的特征为 [i, 10i]，标签为 i % 2。这个 Dataset 返回确定性的内存数据，便于检查索引流向。附带的 worker 字段只用于观察执行位置：-1 表示训练进程，0、1 表示该 DataLoader 的子进程。

import torch
from torch.utils.data import Dataset, Sampler, BatchSampler, DataLoader, get_worker_info

ORDER = [3, 0, 4, 1, 2]

class FiveSamples(Dataset):
    def __len__(self):
        return 5

    def __getitem__(self, index):
        worker = get_worker_info()
        return {
            "index": index,
            "x": torch.tensor([index, 10 * index], dtype=torch.float32),
            "y": index % 2,
            "worker": -1 if worker is None else worker.id,
        }

class FixedOrder(Sampler):
    def __iter__(self):
        return iter(ORDER)

    def __len__(self):
        return len(ORDER)

if __name__ == "__main__":
    loader = DataLoader(
        FiveSamples(),
        batch_sampler=BatchSampler(FixedOrder(), batch_size=2, drop_last=False),
        num_workers=0,
    )
    for batch in loader:
        print(batch["index"].tolist(), batch["x"].tolist())
[3, 0] [[3.0, 30.0], [0.0, 0.0]]
[4, 1] [[4.0, 40.0], [1.0, 10.0]]
[2]    [[2.0, 20.0]]

这里显式传入 batch_sampler，以便看清分组过程。使用自定义 batch_sampler 时，不再同时配置 batch_size、sampler、shuffle 或 drop_last；这些职责已由它接管。最后的 [2] 被保留，因为 BatchSampler 的 drop_last=False。BatchSampler

2. 单进程与单 worker

主进程读取

创建 DataLoader 对象主要保存配置；iter(loader) 创建迭代器。num_workers=0 时，next(iterator) 在训练进程内取出下一批索引，读取样本并执行 collate_fn。模型计算期间没有 DataLoader 子进程在后台读取下一批。DataLoader.__iter__；_SingleProcessDataLoaderIter

# Conceptual execution with automatic batching, num_workers=0,
# and a Dataset without __getitems__.
for indices in batch_sampler:
    samples = [dataset[index] for index in indices]
    batch = collate_fn(samples)
    yield batch

这是默认逐样本访问路径的等价示意。内部的 _MapDatasetFetcher 负责连接 Dataset 与 collate_fn；支持批量读取的 __getitems__ 会替换列表中的逐次读取，后文单独说明。_MapDatasetFetcher.fetch

一个独立 worker

num_workers=1 会创建一个子进程。主进程仍运行 Sampler 和 BatchSampler，将 (任务编号, 索引列表) 放进该 worker 的 index queue。Worker 对整批索引执行读取、变换和 collate_fn，再把 (任务编号, batch) 放入 result queue；主进程取出 batch 交给训练循环。Workers / pin-memory thread；Task dispatch / replenishment；Worker task loop

这已经允许 CPU 数据准备与训练进程的工作重叠，但同一个 worker 仍按顺序处理它收到的任务。单 worker 并不会把一批中的两条样本变成两个并行读取任务。普通 map-style Dataset 的副本可以访问完整索引空间，实际读取哪些索引由主进程派发。

3. 多 worker 与预取

整批任务分发

保持前面的 Dataset、Sampler 和 batch size 不变，只把 worker 数改成 2：

# Use the same FiveSamples / FixedOrder definitions.
if __name__ == "__main__":
    loader = DataLoader(
        FiveSamples(),
        batch_sampler=BatchSampler(FixedOrder(), batch_size=2, drop_last=False),
        num_workers=2,             # Change to 1 for one subprocess.
        multiprocessing_context="spawn",
        prefetch_factor=2,
        in_order=True,
    )
    for batch in loader:
        print(batch["index"].tolist(), batch["worker"].tolist())

在本文版本、默认 in_order=True 的普通 map-style 路径中，初始任务轮流发给活跃 worker。这个例子中 worker 0 收到 task 0=[3,0] 与 task 2=[2]，worker 1 收到 task 1=[4,1]。一个任务对应一批索引，同一批通常由一个 worker 完整读取并组装。增加 worker 数是在不同批次之间并行，而不是自动把一批拆给所有 worker。Task dispatch / replenishment

预取窗口

启用自动 batching 时，prefetch_factor 的单位是每个 worker 的批任务。两个 worker、prefetch_factor=2，初始化会尝试派发最多四个任务；本例只有三批，所以只能发出三个。较大的数据集会在交付结果后继续补充任务。这个窗口涵盖排队、执行和已完成待交付的任务，不表示内存里始终有四个已经完成的 batch。Prefetch initialization；Task dispatch / replenishment

预取只提前准备未来需要的数据。若稳定状态下读取速度持续低于训练消耗速度，单纯增大窗口不能弥补吞吐差距，还会增加数据、队列和乱序结果的内存占用。Dataset 的 Python 对象、解码缓存与每个 worker 的进程开销也要另计。

完成顺序与交付顺序

假设 dataset[3] 比其他样本慢，worker 1 的 task 1 可能先完成。默认 in_order=True 时，主进程根据任务编号缓存这个结果，等 task 0 到达后再按 0、1、2 交付。因此“按序”是按 Sampler / BatchSampler 的任务顺序，不是把样本 ID 排成 0、1、2、3、4。Ordered result delivery

in_order=False 允许先交付先到达的结果，能减少慢批次造成的等待，但会改变训练看到的数据顺序。如果某类样本总是解码更快，训练前缀也可能偏向这类样本。它不保证某一种乱序；启动时间、系统调度和存储延迟都会影响结果。对顺序和可复现性有要求时，应明确保留默认设置。Ordered result delivery

进程状态与生命周期

本文显式使用 spawn。Dataset 类、collate_fn 和 worker_init_fn 应定义在模块顶层，创建迭代器的代码放进 if __name__ == "__main__":，使子进程能够导入并重建这些对象。不要用不可序列化的 lambda 充当 spawn worker 的初始化函数。文件句柄和数据库连接通常应在各 worker 内按需创建。

默认每次创建新迭代器都会启动 worker，遍历结束后关闭。persistent_workers=True 则跨轮保留 worker 及其 Dataset 实例，减少重启开销；主进程里修改 dataset.epoch 并不会自动更新这些副本，worker_init_fn 也不会每轮重新执行。需要随 epoch 改变的状态必须显式传递。DataLoader.__iter__；Worker task loop

采样随机性与 worker 内的数据增强随机性是两层状态。此版本在 worker 启动时初始化 PyTorch、Python random，以及可用时的 NumPy RNG；自行创建的随机生成器或其他库仍需明确管理。get_worker_info() 提供 worker ID、seed 和本进程 Dataset。固定采样顺序并不自动保证随机增强在不同 worker 数下完全一致。Worker RNG initialization；get_worker_info

4. Batch 的组织与搬运

默认堆叠与变长补齐

default_collate 会递归处理字典等结构，将同一字段的 tensor 堆叠，给结果增加 batch 维度；本例第一批的 x 为 [2,2]，y 为 [2]。它不会自动为变长 tensor 补齐。若样本 i 改为长度 i+1 的序列，第一批两条序列的长度就是 4 和 1，需要自定义 collate_fn。default_collate；collate / torch.stack

from torch.nn.utils.rnn import pad_sequence
from torch.utils.data import default_collate

class RaggedSamples(FiveSamples):
    def __getitem__(self, index):
        sample = super().__getitem__(index)
        sample["x"] = torch.arange(1, index + 2, dtype=torch.float32)
        return sample

def pad_collate(samples):
    sequences = [sample["x"] for sample in samples]
    batch = default_collate([
        {key: value for key, value in sample.items() if key != "x"}
        for sample in samples
    ])
    batch["lengths"] = torch.tensor([len(sequence) for sequence in sequences])
    batch["x"] = pad_sequence(sequences, batch_first=True, padding_value=0)
    batch["mask"] = torch.arange(batch["x"].shape[1])[None, :] < batch["lengths"][:, None]
    return batch

第一批得到 x=[[1,2,3,4],[1,0,0,0]]、lengths=[4,1]。Mask 区分有效位置与 padding，避免把补入的 0 当作真实输入。使用 DataLoader(RaggedSamples(), …, collate_fn=pad_collate) 时，num_workers=0 在主进程执行补齐；num_workers>0 在收到该批任务的 worker 内执行。

批量读取接口

实现可选的 Dataset.__getitems__(indices) 后，fetcher 会把整批索引交给它，而不是逐次调用 __getitem__。数据库批查询、连续文件读取可以利用这个接口；返回结果仍应是按请求顺序排列的样本列表，之后依然调用 collate_fn。下面只是接口示意，列表循环本身没有带来 I/O 加速。_MapDatasetFetcher.fetch

class BulkSamples(FiveSamples):
    def __getitems__(self, indices):
        # Demonstrates the interface, not faster I/O. A real backend could
        # issue one batch query, then restore this requested index order.
        return [self[index] for index in indices]

若显式设置 batch_size=None 且没有 batch_sampler，则关闭自动 batching：Sampler 每次给一个 key，fetcher 取一个样本，默认使用 default_convert。此时用户提供的 collate_fn 接收单个样本，而非样本列表，不能套用本文的整批任务示意。Sampler / BatchSampler / collate_fn；_MapDatasetFetcher.fetch

Pin memory 与 H2D

通常让 Dataset 和 collate_fn 返回 CPU tensor。CUDA 可用且启用 pin_memory=True 时，DataLoader 将 batch 中的 CPU tensor 放入页锁定（page-locked）主机内存，便于高效地传到 GPU。自动 pinning 位于 collate_fn 之后、batch 返回给训练循环之前；具体执行位置取决于 num_workers。_SingleProcessDataLoaderIter；Workers / pin-memory thread；Pin-memory thread

配置读取数据、执行 collate_fn执行自动 pin_memory
num_workers=0训练进程中调用 next 的线程，通常是主线程同一线程，在 next 调用内同步执行
num_workers>0worker 子进程训练进程中的专用 pin-memory 线程

多 worker 路径中，pin-memory 线程从 worker result queue 取出已组装的 batch，完成 pinning 后放入训练进程内的 data queue。训练线程再按迭代器的交付规则取出 batch。DDP 下，每个 rank 都有自己的这条路径；pin-memory 线程不属于读取数据的 worker。Pin-memory thread；Workers / pin-memory thread

num_workers=0：
训练线程：读取 → collate_fn → pin_memory → 返回 batch

num_workers>0：
worker：读取 → collate_fn → result queue
训练进程 / pin-memory 线程：result queue → pin_memory → data queue
训练进程 / 训练线程：data queue → 按交付规则返回 batch

前面的两张序列图采用默认的 pin_memory=False，因此没有画出这个可选阶段。Pinned memory 仍是 CPU 内存，DataLoader 不会因此自动把 batch 送到 GPU。真正的 H2D 由训练代码中的 .to(device) 发起：

# The training/rank process performs H2D, not a DataLoader worker.
for batch in loader:  # loader has pin_memory=True on a CUDA system
    x = batch["x"].to(device, non_blocking=True)
    y = batch["y"].to(device, non_blocking=True)
    prediction = model(x)

non_blocking=True 允许异步提交搬运；H2D 与计算是否实际重叠还取决于 stream、数据依赖和硬件。同一 CUDA stream 上紧接着使用 x 的计算仍要等搬运完成。自定义 batch 类型需要实现相应的 pin_memory 支持；普通 tensor 字典可由默认逻辑递归处理。

5. DDP 中的数据读取

Rank 与 worker

DDP 通常由每张 GPU 对应一个训练进程，每个 rank 都有自己的 Dataset、DataLoader 和 worker 池。DDP 负责模型副本之间的梯度同步，不会自动切分 DataLoader 的输入；map-style 数据通常用 DistributedSampler 进行分片。DDP 官方说明。

分片先于本地分批：各 rank 用相同 seed 和 epoch 产生同一份全局索引排列，再按 indices[rank:total_size:world_size] 取属于自己的位置，最后由各自的 BatchSampler 分批。DistributedSampler 在各 rank 本地计算这些索引，通常不需要每轮做一次索引广播。DistributedSampler

全局排列： [3, 0, 4, 1, 2]
补齐到 6： [3, 0, 4, 1, 2, 3*]
rank 0：   [3,    4,    2]  → [3,4], [2]
rank 1：      [0,    1,    3*] → [0,1], [3*]

N=5、world_size=2，DistributedSampler(drop_last=False) 会把开头的索引补到末尾，使两个 rank 各拿到三个位置。星号表示补入的样本 3；它是重复采样，不是第六个新样本。这里 PyTorch 2.8 的 seed=193、epoch=0 恰好生成前文的排列。实际训练依靠一致的 seed 与 set_epoch，而不应依赖跨版本完全相同的随机排列。

两个 rank、每个 num_workers=2，意味着两个训练进程加四个 DataLoader 子进程。各 rank 的 worker 0 彼此独立，worker ID 不是 global rank。对普通 map-style Dataset，不要再按 worker ID 手工过滤一遍索引，否则可能把主进程已经分好的任务错误丢弃；IterableDataset 的分片责任不同，不属于本文路径。

DistributedSampler 的 drop_last 处理能否均分给各 rank，DataLoader / BatchSampler 的 drop_last 处理各 rank 的尾批是否够大。Loader 丢尾批并不普遍保证消除所有补齐重复项；它只是在这个小例子中恰好丢掉了补入的位置。评估时若要求每条样本只计一次，应使用明确的评估分片或按样本 ID 去重统计。DistributedSampler；BatchSampler

每轮重排与训练步数

训练每个 epoch 前调用 sampler.set_epoch(epoch)，再创建 DataLoader 迭代器。DistributedSampler 使用 seed+epoch 生成排列；不调用 set_epoch 会重复相同的采样顺序。所有 rank 必须共享 sampler seed、数据集长度和稳定的索引含义；worker 的随机增强 seed 则可以按 rank 区分。DistributedSampler

若每个 rank 都有 W 个 worker、预取系数为 P，自动 batching 下全局最多尝试派发约 world_size × W × P 个预取任务，受剩余数据限制。batch_size 是每个 rank 的大小；完整批次、无梯度累积时，一个训练 step 的样本位置数为 world_size × batch_size。尾批和补齐可能改变实际大小或不同样本数。

标准 DDP 训练要求各 rank 按兼容顺序参与梯度 collective。DistributedSampler 的均分使每个 rank 的迭代长度一致；使用过滤样本、自定义分片或不等长数据集时，需要重新检查步数。只给 DataLoader 设置 shuffle=True 而不做 rank 分片，通常会让每个 rank 都遍历完整数据集。

可运行的 DDP 例子

完整示例脚本包含前面的 Dataset、collate_fn 和命令行入口。以下是其中的 DDP 训练函数：同一数据路径既能用 CPU/Gloo 验证，也能用 CUDA/NCCL 运行。代码中的 worker_options 在 workers>0 时设置 spawn 与 prefetch_factor=2，在 workers=0 时省略这些参数。

def run_ddp(args):
    local_rank = int(os.environ["LOCAL_RANK"])
    device = torch.device("cuda", local_rank) if args.device == "cuda" else torch.device("cpu")
    if device.type == "cuda":
        torch.cuda.set_device(device)
    dist.init_process_group("nccl" if device.type == "cuda" else "gloo")
    try:
        rank = dist.get_rank()
        dataset = FiveSamples()
        sampler = DistributedSampler(
            dataset, shuffle=True, seed=193, drop_last=args.drop_sampler,
        )
        loader = DataLoader(
            dataset, sampler=sampler, batch_size=2, drop_last=args.drop_batch,
            num_workers=args.workers, collate_fn=trace_collate,
            pin_memory=device.type == "cuda",
            generator=torch.Generator().manual_seed(1000 + rank),
            **worker_options(args.workers),
        )
        torch.manual_seed(0)
        model = DistributedDataParallel(
            torch.nn.Linear(2, 2).to(device),
            device_ids=[local_rank] if device.type == "cuda" else None,
        )
        optimizer = torch.optim.SGD(model.parameters(), lr=0.001)
        for epoch in range(args.epochs):
            sampler.set_epoch(epoch)
            for step, batch in enumerate(loader):
                x = batch["x"].to(device, non_blocking=device.type == "cuda")
                y = batch["y"].to(device, non_blocking=device.type == "cuda")
                optimizer.zero_grad()
                loss = torch.nn.functional.cross_entropy(model(x), y)
                loss.backward()
                optimizer.step()
                print({"rank": rank, "epoch": epoch, "step": step,
                       "indices": batch["index"].tolist(),
                       "sample_workers": batch["worker"].tolist(),
                       "collate_worker": batch["collate_worker"]}, flush=True)
    finally:
        dist.destroy_process_group()
# 保存完整脚本为 dataloader-demo.py；在安装 PyTorch 的环境中运行
python dataloader-demo.py --workers 0
python dataloader-demo.py --workers 1
python dataloader-demo.py --workers 2 --slow
python dataloader-demo.py --workers 2 --ragged
python dataloader-demo.py --workers 2 --bulk

# 两个 CPU rank，每个 rank 一个读取 worker
torchrun --standalone --nproc-per-node=2 dataloader-demo.py --ddp --workers 1

# 两张可见 GPU，每个 rank 两个读取 worker
torchrun --standalone --nproc-per-node=2 dataloader-demo.py --ddp --device cuda --workers 2

Epoch 0 在 rank 0 输出 [3,4]、[2]，rank 1 输出 [0,1]、[3]；不同进程的打印行可能交错。Epoch 1 会换一份排列。使用 --drop-sampler 和 --drop-batch 可以分别观察上面两种丢弃策略。

6. 源码与排查

现象优先检查
样本错误、异常难定位先用 num_workers=0 查看 Dataset / collate 的直接调用栈，再恢复多进程。
Worker 已完成一批，训练仍等待检查是否被更早的慢任务阻塞；区分完成顺序和 in_order 交付顺序。
Worker 越多反而越慢检查存储争用、进程启动、序列化、CPU 线程竞争和 batch 过小；测量稳定态，而非只测首批。
改变 epoch 后 worker 状态没变检查 persistent_workers 与 Dataset 副本；set_epoch 只改变 sampler 的索引排列。
DDP 样本重复或步数不符检查 rank 分片、两层 drop_last、补齐项和各 rank 的 Dataset 长度。

PyTorch DataLoader internals

PyTorch DataLoader organizes dataset samples into training batches. For a map-style Dataset, a Sampler chooses indices, a BatchSampler groups them, the Dataset reads and transforms samples, and collate_fn assembles model inputs. A five-sample example connects these responsibilities to loading in the training process, one worker, multiple workers, and DDP, including prefetching, delivery order, and rank sharding.

This article follows ordinary map-style datasets in PyTorch 2.8.0. Diagram messages link to that source revision. num_workers=0 means no subprocess; num_workers=1 means one separate loading worker. Workers are processes, not loading threads.

1. Indices and batches

Five components

A map-style Dataset maps a key to a sample through dataset[index]. Keys need not be integers; this example uses 0 through 4 and the fixed order [3, 0, 4, 1, 2]. Reading a sample may involve image decoding, database access, or an in-memory transformation. The Dataset does not choose the epoch's sampling order. Dataset

BatchSampler handles indices; collate_fn receives samples already fetched. Actual data access happens between them. Without a custom sampler, shuffle=False selects SequentialSampler and shuffle=True selects RandomSampler. With batch_size enabled, DataLoader normally wraps the sampler in BatchSampler. Sampler / BatchSampler / collate_fn; SequentialSampler / RandomSampler

Five samples

Sample i has features [i, 10i] and label i % 2. Removing I/O and random augmentation makes index flow easy to inspect. The worker field records where retrieval runs: -1 for the training process, or a worker ID local to this loader.

import torch
from torch.utils.data import Dataset, Sampler, BatchSampler, DataLoader, get_worker_info

ORDER = [3, 0, 4, 1, 2]

class FiveSamples(Dataset):
    def __len__(self):
        return 5

    def __getitem__(self, index):
        worker = get_worker_info()
        return {
            "index": index,
            "x": torch.tensor([index, 10 * index], dtype=torch.float32),
            "y": index % 2,
            "worker": -1 if worker is None else worker.id,
        }

class FixedOrder(Sampler):
    def __iter__(self):
        return iter(ORDER)

    def __len__(self):
        return len(ORDER)

if __name__ == "__main__":
    loader = DataLoader(
        FiveSamples(),
        batch_sampler=BatchSampler(FixedOrder(), batch_size=2, drop_last=False),
        num_workers=0,
    )
    for batch in loader:
        print(batch["index"].tolist(), batch["x"].tolist())
[3, 0] [[3.0, 30.0], [0.0, 0.0]]
[4, 1] [[4.0, 40.0], [1.0, 10.0]]
[2]    [[2.0, 20.0]]

An explicit batch_sampler exposes the grouping step. When supplying it, leave batch_size, sampler, shuffle, and drop_last unset on DataLoader: the batch sampler owns those decisions. Its drop_last=False retains the final [2]. BatchSampler

2. Main process and one worker

Loading in the main process

DataLoader construction primarily stores configuration; iter(loader) creates the iterator. With num_workers=0, each next call gets indices, fetches samples, and runs collation inside the training process. No DataLoader subprocess prepares a future batch while the model runs. DataLoader.__iter__; _SingleProcessDataLoaderIter

# Conceptual execution with automatic batching, num_workers=0,
# and a Dataset without __getitems__.
for indices in batch_sampler:
    samples = [dataset[index] for index in indices]
    batch = collate_fn(samples)
    yield batch

This is a conceptual equivalent of the default per-sample path. Internally, _MapDatasetFetcher connects the Dataset to collate_fn. The optional __getitems__ batch-fetch interface replaces the individual fetches, as discussed below. _MapDatasetFetcher.fetch

One separate worker

num_workers=1 creates one subprocess. Sampler and BatchSampler still run in the main process, which queues (task ID, index list). The worker fetches, transforms, and collates that entire task, then places (task ID, batch) into a result queue for the training process. Workers / pin-memory thread; Task dispatch / replenishment; Worker task loop

This already permits data preparation to overlap work in the training process. The worker itself processes its tasks sequentially; it does not automatically turn two samples within a batch into parallel reads. Its ordinary map-style Dataset replica can address the full dataset, but only fetches the indices dispatched to it.

3. Multiple workers and prefetch

Whole-batch tasks

Keep the same Dataset, Sampler, and batch size, then set the worker count to two:

# Use the same FiveSamples / FixedOrder definitions.
if __name__ == "__main__":
    loader = DataLoader(
        FiveSamples(),
        batch_sampler=BatchSampler(FixedOrder(), batch_size=2, drop_last=False),
        num_workers=2,             # Change to 1 for one subprocess.
        multiprocessing_context="spawn",
        prefetch_factor=2,
        in_order=True,
    )
    for batch in loader:
        print(batch["index"].tolist(), batch["worker"].tolist())

In this version's ordinary map-style path with in_order=True, initial tasks cycle through active workers. Worker 0 receives task 0=[3,0] and task 2=[2]; worker 1 receives task 1=[4,1]. One worker normally fetches and collates an entire batch. More workers parallelize different batches, rather than automatically dividing one batch among workers. Task dispatch / replenishment

The prefetch window

With automatic batching, prefetch_factor counts batch tasks per worker. Two workers with a factor of two attempt to dispatch up to four tasks initially. Only three batches exist here, so only three tasks are sent. For longer datasets, delivering results triggers replenishment. The window spans queued, executing, and completed tasks awaiting delivery; it does not mean four completed batches are always ready in memory. Prefetch initialization; Task dispatch / replenishment

Prefetch moves future work earlier. Increasing the window cannot close a sustained throughput gap when loading remains slower than consumption. It also increases memory used by tasks, batches, and buffered results; Dataset objects, decoding caches, and process overhead add further costs.

Completion versus delivery

If dataset[3] is slow, worker 1 may finish task 1 first. With the default in_order=True, the main process buffers that result by task ID and delivers tasks 0, 1, and 2 in order. Ordered delivery follows Sampler / BatchSampler order; it does not sort sample IDs numerically. Ordered result delivery

in_order=False can deliver an available later result without waiting for an earlier task. This reduces blocking by slow batches but changes training order. If one class consistently decodes faster, the training prefix may also become skewed. No particular out-of-order sequence is guaranteed: startup, scheduling, and storage latency all matter. Preserve the default when order and reproducibility are requirements. Ordered result delivery

Process state and lifetime

The examples explicitly use spawn. Define Dataset classes, collate_fn, and worker_init_fn at module scope, and guard iterator creation with if __name__ == "__main__":. Subprocesses must be able to import and reconstruct those objects; an unpicklable lambda is unsuitable for worker initialization. Open file handles and database connections generally belong inside each worker.

Normally a new iterator starts workers and exhaustion shuts them down. persistent_workers=True retains processes and their Dataset instances across epochs. Mutating dataset.epoch in the parent does not automatically update those replicas, and worker_init_fn does not rerun every epoch. Epoch-dependent state needs explicit communication. DataLoader.__iter__; Worker task loop

Sampling randomness and augmentation randomness are separate. This version seeds PyTorch, Python random, and, when available, NumPy as workers start. Custom generators and other libraries still need explicit management. get_worker_info exposes the local worker ID, seed, and Dataset. A fixed sampling order alone does not guarantee identical augmentation when the worker count changes. Worker RNG initialization; get_worker_info

4. Batch structure and transfer

Stacking and padding

default_collate recursively handles structures such as dictionaries and stacks matching tensor fields, adding a batch dimension. The first batch has x shape [2,2] and y shape [2]. It does not automatically pad unequal tensor lengths. If sample i instead contains a sequence of length i+1, the first batch contains lengths four and one and needs custom collation. default_collate; collate / torch.stack

from torch.nn.utils.rnn import pad_sequence
from torch.utils.data import default_collate

class RaggedSamples(FiveSamples):
    def __getitem__(self, index):
        sample = super().__getitem__(index)
        sample["x"] = torch.arange(1, index + 2, dtype=torch.float32)
        return sample

def pad_collate(samples):
    sequences = [sample["x"] for sample in samples]
    batch = default_collate([
        {key: value for key, value in sample.items() if key != "x"}
        for sample in samples
    ])
    batch["lengths"] = torch.tensor([len(sequence) for sequence in sequences])
    batch["x"] = pad_sequence(sequences, batch_first=True, padding_value=0)
    batch["mask"] = torch.arange(batch["x"].shape[1])[None, :] < batch["lengths"][:, None]
    return batch

The first batch becomes x=[[1,2,3,4],[1,0,0,0]], with lengths=[4,1]. A mask distinguishes valid positions from padding. Pass pad_collate to DataLoader with RaggedSamples: padding runs in the main process for num_workers=0, or inside the worker assigned that batch for num_workers>0.

Batched fetching

The optional Dataset.__getitems__(indices) receives an entire index list instead of repeated __getitem__ calls. A backend could use one database query or combine file reads. It should return a list of samples in requested order; collate_fn still runs afterward. This example demonstrates the interface only: its Python loop does not itself accelerate I/O. _MapDatasetFetcher.fetch

class BulkSamples(FiveSamples):
    def __getitems__(self, indices):
        # Demonstrates the interface, not faster I/O. A real backend could
        # issue one batch query, then restore this requested index order.
        return [self[index] for index in indices]

Setting batch_size=None without batch_sampler disables automatic batching. The sampler supplies one key, the fetcher obtains one sample, and default_convert is the default conversion. A custom collate_fn then receives a single sample, not a sample list; the whole-batch task diagrams do not apply to that mode. Sampler / BatchSampler / collate_fn; _MapDatasetFetcher.fetch

Pin memory and H2D

Dataset and collate_fn normally return CPU tensors. With CUDA available and pin_memory=True, DataLoader places the batch's CPU tensors in page-locked host memory for efficient GPU transfer. Automatic pinning runs after collate_fn and before the batch reaches the training loop. Its execution location depends on num_workers. _SingleProcessDataLoaderIter; Workers / pin-memory thread; Pin-memory thread

With workers, the pin-memory thread consumes assembled batches from the worker result queue, pins them, and puts them into a data queue within the training process. The training thread then obtains batches according to the iterator's delivery rules. Each DDP rank has its own path; the pin-memory thread does not belong to a loading worker. The two sequence diagrams above use the default pin_memory=False and omit this optional stage. Pinned memory is still CPU memory; DataLoader does not automatically move the batch to the GPU. The training code initiates H2D through .to(device):

# The training/rank process performs H2D, not a DataLoader worker.
for batch in loader:  # loader has pin_memory=True on a CUDA system
    x = batch["x"].to(device, non_blocking=True)
    y = batch["y"].to(device, non_blocking=True)
    prediction = model(x)

non_blocking=True permits asynchronous transfer submission. Actual overlap with computation also depends on streams, dependencies, and hardware; a consumer on the same CUDA stream still waits for its copy. Custom batch classes need pin_memory support, whereas ordinary tensor dictionaries are traversed by the default implementation.

5. Reading data under DDP

Ranks and workers

A typical DDP setup assigns one training process to each GPU, with a Dataset, DataLoader, and worker pool per rank. DDP synchronizes model gradients; it does not shard DataLoader inputs automatically. Map-style training commonly uses DistributedSampler for that job. DDP documentation.

Rank sharding precedes local batching. Each rank computes the same global permutation using the same seed and epoch, selects indices[rank:total_size:world_size], and passes its indices to its local BatchSampler. These computations are rank-local and normally need no epoch-by-epoch index broadcast. DistributedSampler

Global order: [3, 0, 4, 1, 2]
Pad to six:   [3, 0, 4, 1, 2, 3*]
Rank 0:      [3,    4,    2]   → [3,4], [2]
Rank 1:         [0,    1,    3*] → [0,1], [3*]

With N=5 and world_size=2, DistributedSampler(drop_last=False) appends indices from the start so each rank receives three positions. The star marks another occurrence of sample 3, not a sixth distinct sample. PyTorch 2.8 happens to produce our example permutation with seed=193 and epoch=0. Training should rely on consistent seeds and set_epoch, not identical random permutations across releases.

Two ranks with num_workers=2 each create two training processes and four loader subprocesses. Their worker 0 processes are distinct; worker IDs are not global ranks. For an ordinary map-style Dataset, applying another worker-ID filter can discard indices already assigned by the parent. IterableDataset has different sharding responsibilities and is outside this article's execution path.

Epochs and training steps

Call sampler.set_epoch(epoch) before creating the DataLoader iterator for that epoch. DistributedSampler generates its permutation from seed+epoch; without set_epoch it repeats the same order. Ranks must agree on sampler seed, dataset length, and stable index meanings. Worker augmentation seeds can instead differ by rank. DistributedSampler

With W workers per rank and prefetch factor P, automatic batching attempts a global prefetch window of roughly world_size × W × P tasks, limited by remaining data. batch_size is per rank. Full batches without gradient accumulation give world_size × batch_size sample positions per training step; tails and padding can change actual sizes or distinct-sample counts.

Ordinary DDP training requires compatible gradient collective participation across ranks. Equal sampler lengths give equal iteration lengths; filtering, custom sharding, or different dataset sizes require another check. Setting shuffle=True alone without rank sharding generally makes every rank traverse the full dataset.

Runnable DDP example

The complete example script includes the Dataset, collation functions, and command-line entry point. Its DDP training function below supports CPU/Gloo and CUDA/NCCL. The worker_options helper sets spawn and prefetch_factor=2 only when workers>0.

def run_ddp(args):
    local_rank = int(os.environ["LOCAL_RANK"])
    device = torch.device("cuda", local_rank) if args.device == "cuda" else torch.device("cpu")
    if device.type == "cuda":
        torch.cuda.set_device(device)
    dist.init_process_group("nccl" if device.type == "cuda" else "gloo")
    try:
        rank = dist.get_rank()
        dataset = FiveSamples()
        sampler = DistributedSampler(
            dataset, shuffle=True, seed=193, drop_last=args.drop_sampler,
        )
        loader = DataLoader(
            dataset, sampler=sampler, batch_size=2, drop_last=args.drop_batch,
            num_workers=args.workers, collate_fn=trace_collate,
            pin_memory=device.type == "cuda",
            generator=torch.Generator().manual_seed(1000 + rank),
            **worker_options(args.workers),
        )
        torch.manual_seed(0)
        model = DistributedDataParallel(
            torch.nn.Linear(2, 2).to(device),
            device_ids=[local_rank] if device.type == "cuda" else None,
        )
        optimizer = torch.optim.SGD(model.parameters(), lr=0.001)
        for epoch in range(args.epochs):
            sampler.set_epoch(epoch)
            for step, batch in enumerate(loader):
                x = batch["x"].to(device, non_blocking=device.type == "cuda")
                y = batch["y"].to(device, non_blocking=device.type == "cuda")
                optimizer.zero_grad()
                loss = torch.nn.functional.cross_entropy(model(x), y)
                loss.backward()
                optimizer.step()
                print({"rank": rank, "epoch": epoch, "step": step,
                       "indices": batch["index"].tolist(),
                       "sample_workers": batch["worker"].tolist(),
                       "collate_worker": batch["collate_worker"]}, flush=True)
    finally:
        dist.destroy_process_group()
