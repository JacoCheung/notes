GPU 互联的软件与驱动

GPU 之间的通信有两类常见数据路径：通过 NVLink / PCIe 访问另一张卡的显存，或通过网卡执行 RDMA。CUDA 驱动建立显存映射，Linux RDMA 驱动建立网卡资源，NCCL 和 NVSHMEM 在这些资源之上组织传输。沿着一块数据从 GPU 0 到 GPU 1 的过程，可以看清 CPU proxy、IBGDA、GPUNetIO Verbs 与 NCCL GIN 各自承担的工作。

源码基线：NCCL 2.32.3、NVSHMEM 3.8.0、rdma-core 61.0，核对日期 2026-11-09。图中链接固定到 commit；序列图是源码路径示意，activation bar 表示逻辑活动范围，不表示实测耗时。

1. 路径总览

1.1 API、提交与搬运

设 GPU 0 已生成一块数据，GPU 1 需要读取它。一次传输包含三个不同的问题：谁发起通信操作，谁向硬件提交请求，数据经过哪里。CPU 调用 ncclAllReduce() 只回答第一个问题。网络请求可能由 CPU proxy 提交，数据仍可直接在 GPU 显存和网卡之间传输。

1.3 CUDA peer

CUDA peer 路径使用 GPU 可访问的地址映射：CPU 驱动建立权限与页表，GPU 的 load/store 经 NVLink / PCIe 访问对端显存。RDMA 路径使用 NIC 队列、MR 和访问 key。两者的地址解释与请求提交机制不同。Linux userspace verbs

GPU P2P 访问 已包含 peer load/store、同进程与跨进程映射、P100 PTE、NCCL LSA，以及 NVLink / PCIe 的链路选择。跨 OS 的 FABRIC handle 与 IMEX 见该文的 跨节点映射。下面保留驱动管理组件的索引与共享时序，便于和网络路径对照。

2. NCCL CPU proxy

普通 NCCL NET/IB 路径由 CPU proxy 推进网络请求。libnccl.so 组织 collective，proxy 经 libibverbs 与 libmlx5 提交 WR；启用 GPUDirect RDMA 后，NIC 直接搬运 GPU buffer。连接与内存注册先完成，后续 chunk 复用这些资源。

2.1 连接与队列

以两台主机上的 GPU buffer 为例，连接建立阶段要让两端知道“通过哪条队列、访问哪段内存、凭什么权限访问”。这些信息先由 CPU 组织，再供 CPU 或 GPU 的提交代码使用。

对象含义在一次写入中的用途
PDProtection Domain，资源的保护域关联 QP 与注册内存的访问权限。
MR / lkey / rkeyMemory Region 及本地 / 远端访问 key标识可被网卡访问的 buffer、范围与权限；远端地址和 rkey 需要交换。
QPQueue Pair，发送 / 接收工作队列承载 WR 对应的硬件 WQE；具体使用哪条队列取决于操作类型。
WR / WQEWork Request / Work Queue Element描述源地址、长度、目标地址、rkey 等。WR 是软件请求，WQE 是硬件队列表示。
Doorbell向网卡通知队列进展的机制让 NIC 发现新工作；DBR 等内存记录与 MMIO doorbell 有不同作用。
CQ / CQECompletion Queue / Entry报告已请求的完成通知与错误。批处理或 selective signaling 下不要求每个 WQE 都生成一个 CQE。

普通 RDMA Write 直接访问远端 MR，无需为每次写入配对一个 receive buffer。Send/Recv，以及带 immediate 的某些操作，有不同的接收资源与通知要求。接收方何时消费 buffer，还需要通信库或应用定义同步协议。

2.2 显存注册

CUDA 分配得到的 GPU 虚拟地址，解决的是 GPU 如何访问这段内存。网卡还需要自己的访问授权与 DMA 地址映射。注册会为 buffer 建立 NIC 可用的资源和 key；GPU 页表中的 peer 映射与 NIC 的 MR 是不同对象。

注册路径主机侧操作内核协作
Peer memory对支持的 GPU 分配执行 MR 注册。RDMA 驱动通过 nvidia-peermem 与 NVIDIA GPU 驱动协作，维护页面和 DMA 映射。
DMA-BUF导出 GPU buffer 为 DMA-BUF fd，再通过 ibv_reg_dmabuf_mr() 等接口注册。GPU exporter 与 RDMA importer 经 DMA-BUF 协作；支持的配置可不加载 nvidia-peermem。

“零拷贝”在这里指 payload 可避免经过 CPU 内存中转。初始化消息、地址与 key 的交换、队列控制和完成状态仍然存在。nvidia-peermem 为访问建立条件，payload 不会逐字节经过这个内核模块。

2.3 提交与完成

CPU 调用 ncclAllReduce() 时，NCCL 为 collective 选择算法与连接方式，组织 GPU kernel 和需要的主机工作。一个 AllReduce 可以同时包含节点内 peer 传输与节点间网络传输。下面只展开普通 NET/IB transport 中一个发送 chunk，并假设这段连接已启用 GPUDirect RDMA。API 入口

sendProxyProgress() 检查 GPU / FIFO 的进展，确认 chunk 可发送后调用网络插件的 isend。内置 IB 实现在具备发送条件时构造 verbs 请求，交给 ibv_post_send()；mlx5 用户态 provider 写队列并通知网卡。网卡通过 DMA 读取 GPU payload，经网络发往对端。proxy 的 ready / isend / test · NET/IB 发送 · mlx5 provider

发送完成后，proxy 的 test 路径轮询 completion，并更新 GPU 可见的进度。接收侧也有 recvProxyProgress()，处理接收请求、完成及必要的可见性工作。示意图把这部分压缩为远端 NIC / GPU；它并不表示接收侧完全没有 CPU 协作。

2.4 路径选择

CPU 在这里提交的是描述符与控制信息，GPU payload 可以走 GDR。没有可用的 GDR、使用 socket 后端或遇到其他路径时，数据流会不同。NCCL 的网络插件接口也允许不同实现，因此不能把 ncclAllReduce() 等同于某条固定的 verbs 调用链。

新版 NCCL 的 host API 还可能选择使用 GIN 的 kernel。CPU 发起 collective 与 kernel 内发起网络请求可以同时成立；本节的 CPU proxy 路径，是按实际 transport 和执行方式定义的。分析一条 trace 时，应同时核对算法、transport、GDR 注册和 proxy 活动。Host API 的 GIN kernel 选项

3. NVSHMEM CPU proxy

NVSHMEM 的 device API 可以由 GPU 发起，再交给 CPU proxy 执行网络提交。本章以远端目标选用 PROXY、主机 transport 为 IBRC 的路径为例；本地可直接访问的 peer 仍可使用 load/store。device 分派 · transport 选择

3.1 PE 与 symmetric heap

NVSHMEM 给应用提供一侧通信接口：调用方指定目标 PE，即可 put/get 对方的 symmetric memory。各 PE 以一致的 collective 分配顺序建立对应对象。symmetric address 表达的是“对方对应的分配与偏移”；应用不应把它理解为所有进程拥有相同数值的虚拟地址。NVSHMEM 编程模型

对于 GPU 0 → GPU 1 的例子，两个 PE 各自分配 dst 和 signal。PE 0 写入 PE 1 的 dst，再发布与数据有序关联的信号；PE 1 等待信号后消费数据。

#include <nvshmem.h>
#include <nvshmemx.h>

// Two PEs, one thread per PE, one transfer, signal initially zero.
__global__ void send_once(void* dst, const void* src,
                          size_t bytes, uint64_t* signal) {
    if (nvshmem_my_pe() == 0) {
        nvshmem_putmem_signal_nbi(dst, src, bytes, signal,
                                 1, NVSHMEM_SIGNAL_SET, 1);
        nvshmem_quiet();
    } else {
        nvshmem_signal_wait_until(signal, NVSHMEM_CMP_GE, 1);
        // This PE can now consume its local dst.
    }
}

这是设备侧片段：两个 PE 各绑定一张 GPU，dst、signal 已通过 symmetric allocation 建立，signal 初值为 0，src 数据已就绪。两端以单 block、单线程执行一次；包含跨 PE 等待的 kernel 使用 nvshmemx_collective_launch。完整的初始化与 collective launch 形式可参考 官方 ring-bcast 示例。

put_signal_nbi 把数据和远端通知关联起来；quiet 完成调用线程先前发出的操作，signal_wait_until 让接收方按协议等待数据。发送完成与接收方已经计算完毕是两件事：复用远端 buffer 时，仍需接收方确认或分轮次管理。多线程 PE 需要先保证其他线程的操作已发出，再由调用线程执行 quiet。Memory ordering · 信号接口

3.2 请求与完成

libnvshmem_host.so 建立 PE、symmetric heap 和 transport，IBRC 经 verbs/provider 建立连接并注册显存。Linux 的 ib_uverbs / ib_core、mlx5_ib / mlx5_core 和 GPU 内存注册接口参与资源准备，见 显存注册。

kernel 发布包含目标 PE、地址和长度的请求，CPU proxy 消费请求，再由 IBRC 构造 RDMA WR 并执行 ibv_post_send()。CPU 推进 CQ 完成；GPU 的 quiet 与接收端 signal wait 按 NVSHMEM 的契约等待。这里由 CPU 生成网卡请求，payload 仍可从 GPU 显存直接经 NIC 传输。IBRC 提交 · IBRC completion

4. NVSHMEM IBGDA

IBGDA 是 NVSHMEM 的 InfiniBand GPUDirect Async transport，包含直接管理 mlx5 队列的实现。主机端建立资源与 GPU 可访问的 NIC 映射；设备端写 WQE、发布队列进度并触发 doorbell。ibgda_post_send() 中可看到内存顺序操作、DBR 更新和 ibgda_ring_db()。这里的“IB”也不意味着底层只能使用 InfiniBand 链路：支持的 mlx5 配置还可使用 RoCE。主机映射 · GPU 提交

4.1 资源与配置

IBGDA 的主机实现经 verbs / mlx5 建立 QP、CQ 和 MR，并准备 GPU 可访问的队列与 NIC 映射。GPU 显存仍需通过 peer-memory 或 DMA-BUF 等支持的方式注册；新增的准备是让设备代码拥有提交队列所需的地址、key 和状态。IBGDA 主机映射

NVSHMEM_IB_ENABLE_IBGDA=1 ./your_nvshmem_app

将环境变量传给每个 PE。launcher 负责进程数量与 GPU 绑定；该配置需要相应构建和平台支持。

4.2 GPU 提交

应用仍使用 同一段 put / signal 代码。IBGDA device transport 直接构造 WQE，按内存顺序发布队列状态，再通知 NIC；本地完成与远端信号分别满足 quiet 和消费端的依赖。CPU 在传输前建立资源，GPU 接管这条路径中的队列推进。WQE 与 doorbell · 完成语义

4.3 Doorbell 模式

NVSHMEM_IBGDA_NIC_HANDLER=auto 默认优先使用 GPU；平台不支持时回退到 CPU。gpu、cpu 与 cpu_host_memory 可显式选择处理方式，后两者使用不同的 CPU 可访问内存机制。NIC handler 配置

图中展开 GPU 直接 doorbell。CPU 辅助模式增加一次主机推进：GPU 准备 WQE 并发布待提交进度，CPU 执行 doorbell 工作。核对性能时需要区分“谁写 WQE”和“谁敲 doorbell”。

5. NVSHMEM GPUNetIO

这条路径由 NVSHMEM 选择 GPUNETIO_GDAKI device transport。NVSHMEM 保留 PE、symmetric address 与同步语义，GPUNetIO 提供队列操作。它与直接管理 mlx5 队列的 IBGDA 是两种替代实现。分派入口 · QP 建立

5.1 资源导出

6. NCCL GIN / GDAKI

6.1 Window 与资源

GIN（GPU-Initiated Networking）是 NCCL Device API 的网络通信部分。应用可在自己的 CUDA kernel 中决定何时传输、传给哪个 rank，并把通信放在产生或消费数据的位置。Host 侧仍负责 communicator、内存 window、signal 和网络 context 的建立。

// NCCL 2.32.3. Run on both ranks after communicator initialization.
void *src, *dst;
ncclWindow_t srcWin, dstWin;
ncclMemAlloc(&src, bytes);
ncclMemAlloc(&dst, bytes);
ncclCommWindowRegister(comm, src, bytes, &srcWin, NCCL_WIN_COLL_SYMMETRIC);
ncclCommWindowRegister(comm, dst, bytes, &dstWin, NCCL_WIN_COLL_SYMMETRIC);

ncclDevCommRequirements reqs = NCCL_DEV_COMM_REQUIREMENTS_INITIALIZER;
reqs.ginType = NCCL_GIN_TYPE_GDAKI;   // explicitly request this backend
reqs.ginConnectionType = NCCL_GIN_CONNECTION_FULL;
reqs.ginContextCount = 1;
reqs.ginSignalCount = 1;
ncclDevComm devComm;
ncclDevCommCreate(comm, &reqs, &devComm);

这是 NCCL 2.32.3 的初始化片段，省略错误检查与普通 communicator 初始化。两个 rank 都建立对应的 src / dst window；bytes 一致，src 已初始化，最终需要同步 kernel 并释放 devComm、window 和内存。显式指定 GDAKI 后，设备环境不支持时创建会失败。

ginType 可请求特定后端；保持默认值表示允许可用后端。GIN 同时存在 CPU proxy 与 GDAKI 等实现，ncclGin API 名称本身不能决定网卡由谁提交。资源需求结构 · 后端选择

NCCL GDAKI 的注册实现同时包含 DMA-BUF 和 GPU MR 注册路径；实际选择依赖分配类型、驱动及平台能力。NCCL 还要求由多个 cuMem segment 支撑的 GIN buffer 使用 DMA-BUF。GDAKI 注册源码 · GIN 要求

6.2 Kernel 内提交

下面让两个 rank 各向对方写一块数据。每个 rank 只启动一个线程，signal 0 初始为 0，整个示例只执行一轮。使用固定的期望值 1，避免“先读当前 signal 再加 1”与对方提前发送发生竞态。

#include <nccl_device.h>

// Exactly two ranks; launch <<<1, 1>>> once per rank.
__global__ void exchange_once(ncclDevComm comm, ncclWindow_t srcWin,
                             ncclWindow_t dstWin, size_t bytes) {
    ncclGin gin{comm, 0};
    int peer = 1 - comm.rank;
    gin.put(ncclTeamWorld(comm), peer,
            dstWin, 0, srcWin, 0, bytes,
            ncclGin_SignalInc{0});
    gin.waitSignal(ncclCoopThread{}, 0, 1); // incoming data is ready
    gin.flush(ncclCoopThread{});          // local src can be reused
}

ncclGin_SignalInc 把远端信号递增与写入完成关联起来，接收方通过 acquire 语义的 waitSignal 等待。flush 保障本地发送源可以复用；它单独不保证数据已经落定在远端内存。重复执行时需要按轮次维护 signal，并协调接收 buffer 的复用。put / flush / waitSignal 契约

在这个版本的 GDAKI 实现中，putImplMode() 读取 window 对应的 key 与偏移，然后调用 doca_gpu_dev_verbs_put*。主机侧则通过 GPUNetIO 创建 QP 并导出 device 描述符。GIN 提供 rank、window 和同步语义，GDAKI 后端把操作落到 GPU 可访问的网络资源上。 GIN → GPUNetIO · QP 建立与导出

6.3 顺序与完成

时刻已经成立的条件接下来仍需等待的条件
WQE 已构造请求描述符已准备好。正确发布队列并通知 NIC。
Doorbell 已提交网卡收到或可以观察到新工作通知。DMA、网络事务及相应完成条件。
GIN flush 返回该 cooperative group 发出的 put 的源 buffer 可安全复用。远端数据落定、接收方消费；按 signal 等接口确认。
接收方等待关联 signal 返回满足该信号 API 的数据完成与顺序保证。接收 kernel 真正完成消费；下一轮覆盖前需要协调。

多线程版本还必须明确哪些线程生产了源数据、哪些线程共同调用通信接口，以及内存顺序作用域。把单线程示例直接扩展为每个线程敲一次同一个 doorbell，会引入队列并发和顺序问题。GPUNetIO 与 GIN 都提供资源共享和协作范围的约定，应按 API 使用。

7. NCCL GIN / CPU proxy

GIN CPU proxy 保留 ncclGin 的 rank、window 与 signal 接口。GPU kernel 发布请求描述符，主机 progress 线程把描述符转换成网络操作。下面采用内置 IB RMA 后端：它经 CPU verbs 提交 WR，启用 GDR 的 NIC 直接访问已注册的 GPU buffer。描述符处理 · IB 提交

7.1 后端与资源

内存分配、window 注册和 device communicator 的生命周期与 GDAKI 示例一致。创建前把需求中的后端改为 proxy；主机建立共享请求队列、进度计数和网络连接。

ncclDevCommRequirements reqs = NCCL_DEV_COMM_REQUIREMENTS_INITIALIZER;
reqs.ginType = NCCL_GIN_TYPE_PROXY;
reqs.ginConnectionType = NCCL_GIN_CONNECTION_FULL;
reqs.ginContextCount = 1;
reqs.ginSignalCount = 1;
ncclDevComm devComm;
ncclDevCommCreate(comm, &reqs, &devComm);

这是替换原初始化片段中 reqs 与创建调用的部分。其余分配、注册、运行和释放保持对应；实际构建与网络环境须支持所选后端。需求结构 · 后端选择

7.2 描述符与完成

proxyGinPollGfd() 读取 GPU 发布的描述符，proxyGinProcessGfd() 分派到 RMA backend 的 iput / iputSignal。IB backend 构造 WR 并通过 ibv_post_send() 提交。随后主机检查 request 的完成，更新 GPU 可见的 counter。GFD 消费与分派 · WR 提交 · 完成计数

7.3 接口与分工

同一段 ncclGin kernel仍然适用，flush 的本地源复用保证、signal 的接收端依赖也保持不变。变化在提交链：GDAKI 在 GPU 上构造网卡 WQE；GIN CPU proxy 由 GPU 发布 GIN 描述符，再由 CPU 生成并提交网络请求。后者也区别于 GPUNetIO 的 CPU 辅助 doorbell——辅助模式中 WQE 已经由 GPU 构造。

普通 NCCL NET/IB CPU proxy 推进的是 collective kernel 的 chunk；GIN CPU proxy 消费的是用户 kernel 发出的 GIN 操作。两条路径都可使用 CPU verbs 和 GPUDirect RDMA，但上层协议与进度对象不同。

GPU interconnect software and drivers

GPU communication commonly takes one of two data paths: peer-memory access over NVLink / PCIe, or RDMA through a network adapter. CUDA drivers establish GPU mappings, Linux RDMA drivers establish NIC resources, and NCCL or NVSHMEM organize transfers using those resources. Following a block of data from GPU 0 to GPU 1 reveals the roles of CPU proxies, IBGDA, GPUNetIO Verbs and NCCL GIN.

2. NCCL CPU proxy

In the ordinary NCCL NET/IB path, a CPU proxy progresses network requests. libnccl.so organizes the collective; the proxy submits WRs through libibverbs and libmlx5. With GPUDirect RDMA enabled, the NIC transfers GPU buffers directly. Connection and memory setup precede the chunks that reuse those resources.

2.1 Connections and queues

For GPU buffers on two hosts, setup establishes which queue to use, which memory to access, and which permissions authorize access. The CPU organizes this information for subsequent CPU or GPU submission.

ObjectMeaningRole in a write
PDProtection DomainAssociates QPs and registered memory within an access-protection domain.
MR / lkey / rkeyMemory Region and local / remote access keysIdentify NIC-accessible memory, bounds and permissions. Peers exchange remote addresses and rkeys.
QPQueue PairHolds hardware work queues. Which queue is used depends on the operation.

An ordinary RDMA Write accesses a remote MR without a matching receive buffer for every write. Send/Recv and some operations with immediate data have different receive-resource and notification requirements. The communication library or application must also define when the receiver can consume the buffer.

2.2 GPU memory registration

A CUDA allocation supplies a GPU virtual address. The NIC still needs its own access authorization and DMA mappings. Registration establishes NIC resources and keys; a GPU peer mapping and a NIC MR are different objects.

Zero-copy here means payload can avoid staging through CPU memory. Initialization messages, address/key exchange, queue control and completion state remain. nvidia-peermem enables access; it does not forward every payload byte through the kernel.

2.3 Submission and completion

When the CPU calls ncclAllReduce(), NCCL selects an algorithm and connections, and organizes GPU kernels and any required host work. One collective may combine local peer transfers with network transfers. This sequence isolates one outgoing chunk in the ordinary NET/IB transport, assuming GPUDirect RDMA is enabled for the connection. API entry

sendProxyProgress() checks GPU / FIFO progress, then calls the network plugin's isend when a chunk is ready. The internal IB implementation constructs verbs work when transmission can proceed and submits through ibv_post_send(). The mlx5 userspace provider writes the queue and notifies the NIC. The NIC DMA-reads GPU payload and transmits it to the peer. Ready / isend / test · NET/IB send · mlx5 provider

The proxy's test path polls completion and updates GPU-visible progress. The receiver also has recvProxyProgress() for receive requests, completion and any required visibility work. The sequence summarizes that side as a remote NIC / GPU; it does not imply an absence of receiver-side CPU participation.

2.4 Path selection

The CPU submits descriptors and control information, while GPU payload can use GDR. Unavailable GDR, socket backends or other transports change the data path. NCCL's plugin interface also allows other implementations, so ncclAllReduce() does not identify a fixed verbs call chain.

Newer NCCL host APIs can select kernels that use GIN. A CPU-initiated collective can therefore contain kernel-initiated networking. The CPU proxy path in this section is defined by its actual transport and execution method. Trace analysis should check the algorithm, transport, GDR registration and proxy activity together. 3. NVSHMEM CPU proxy

A GPU can initiate an NVSHMEM device operation and delegate network submission to a CPU proxy. This chapter follows a remote target using the PROXY device path and IBRC host transport. Directly accessible local peers can still use loads/stores. Device dispatch · Transport selection

3.1 PEs and the symmetric heap

NVSHMEM provides one-sided operations: a caller names a target PE and puts/gets its symmetric memory. PEs establish corresponding objects through consistent collective allocation order. A symmetric address identifies the corresponding allocation and offset at another PE; it does not require the application to assume identical numerical virtual addresses in every process. NVSHMEM programming model

For GPU 0 → GPU 1, both PEs allocate dst and signal. PE 0 writes PE 1's dst and publishes an ordered signal. PE 1 waits for that signal before consuming the data.

#include <nvshmem.h>
#include <nvshmemx.h>

// Two PEs, one thread per PE, one transfer, signal initially zero.
__global__ void send_once(void* dst, const void* src,
                          size_t bytes, uint64_t* signal) {
    if (nvshmem_my_pe() == 0) {
        nvshmem_putmem_signal_nbi(dst, src, bytes, signal,
                                 1, NVSHMEM_SIGNAL_SET, 1);
        nvshmem_quiet();
    } else {
        nvshmem_signal_wait_until(signal, NVSHMEM_CMP_GE, 1);
        // This PE can now consume its local dst.
    }
}

Device-side excerpt: two PEs each own one GPU; dst and signal are symmetric allocations, signal starts at 0, and src is ready. Execute once with one block and one thread per PE, using nvshmemx_collective_launch for this kernel with cross-PE waiting. The official ring-bcast example shows initialization and collective launch.

put_signal_nbi associates payload with remote notification. quiet completes prior operations issued by the calling thread, and signal_wait_until expresses the receiver's dependency. Send completion does not mean the receiver has finished computation: reusing remote storage still needs an acknowledgement or an iteration protocol. With multiple issuing threads, order their operations before the thread that calls quiet. Memory ordering · Signals

3.2 Requests and completion

libnvshmem_host.so establishes PEs, the symmetric heap and transports. IBRC creates connections and registers GPU memory through verbs/providers. Linux ib_uverbs / ib_core, mlx5_ib / mlx5_core and GPU registration interfaces prepare resources as described under GPU memory registration.

The kernel publishes a request identifying the PE, addresses and length. The CPU proxy consumes it, and IBRC builds RDMA WRs and calls ibv_post_send(). CPU progress observes CQ completion; GPU quiet and the receiver signal wait follow NVSHMEM completion contracts. The CPU constructs NIC requests while payload can move directly from GPU memory through the NIC. IBRC submission · IBRC completion

4. NVSHMEM IBGDA

IBGDA is NVSHMEM's InfiniBand GPUDirect Async transport, including an implementation that directly manages mlx5 queues. Host code establishes resources and GPU-accessible NIC mappings. Device code writes WQEs, publishes queue progress and rings the doorbell. ibgda_post_send() contains ordering operations, DBR updates and ibgda_ring_db(). Supported mlx5 configurations can also use RoCE; the name does not restrict the physical network to InfiniBand. Host mapping · GPU submission

The application uses the same put / signal kernel. The IBGDA device transport builds WQEs, publishes queue state with the required ordering, then notifies the NIC. 4.3 Doorbell mode

NVSHMEM_IBGDA_NIC_HANDLER=auto prefers GPU doorbells and falls back to the CPU when unsupported. Explicit choices include gpu, cpu and cpu_host_memory; the latter two use different CPU-accessible memory mechanisms. NIC handler configuration

The sequence shows direct GPU doorbells. CPU-assisted mode adds host progress: the GPU prepares WQEs and publishes pending work, while the CPU performs doorbell work. Distinguish who writes the WQEs from who rings the doorbell when interpreting performance.

5. NVSHMEM GPUNetIO

NVSHMEM selects the GPUNETIO_GDAKI device transport for this path. NVSHMEM retains PE, symmetric-address and synchronization semantics; GPUNetIO supplies queue operations. It is an alternative to IBGDA, which manages mlx5 queues directly. Dispatch · QP creation

6. NCCL GIN / GDAKI

6.1 Windows and resources

GIN (GPU-Initiated Networking) is the networking part of NCCL's Device API. A user CUDA kernel can decide when and where to transfer, placing communication near data production or consumption. The host still establishes communicators, memory windows, signals and network contexts.

// NCCL 2.32.3. Run on both ranks after communicator initialization.
void *src, *dst;
ncclWindow_t srcWin, dstWin;
ncclMemAlloc(&src, bytes);
ncclMemAlloc(&dst, bytes);
ncclCommWindowRegister(comm, src, bytes, &srcWin, NCCL_WIN_COLL_SYMMETRIC);
ncclCommWindowRegister(comm, dst, bytes, &dstWin, NCCL_WIN_COLL_SYMMETRIC);

ncclDevCommRequirements reqs = NCCL_DEV_COMM_REQUIREMENTS_INITIALIZER;
reqs.ginType = NCCL_GIN_TYPE_GDAKI;   // explicitly request this backend
reqs.ginConnectionType = NCCL_GIN_CONNECTION_FULL;
reqs.ginContextCount = 1;
reqs.ginSignalCount = 1;
ncclDevComm devComm;
ncclDevCommCreate(comm, &reqs, &devComm);

NCCL 2.32.3 setup excerpt; error handling and ordinary communicator initialization are omitted. Both ranks establish corresponding src / dst windows with the same bytes, initialize src, then eventually synchronize the kernel and release the device communicator, windows and allocations. Explicitly requesting GDAKI makes creation fail when that backend is unavailable.

ginType can request a particular backend; its default allows an available backend. GIN has CPU proxy, GDAKI and other implementations. The ncclGin API name alone does not determine who submits NIC work. Resource requirements · Backend selection

NCCL GDAKI contains both DMA-BUF and GPU MR registration paths. Allocation type, driver and platform capabilities determine the choice. GIN buffers backed by multiple cuMem segments require DMA-BUF. Registration source · GIN requirements

6.2 Kernel submission

Here each rank writes one block to its peer. Each rank launches one thread; signal 0 starts at zero, and the example runs once. Waiting for the fixed expected value 1 avoids a race between reading the current signal and an early peer send.

#include <nccl_device.h>

// Exactly two ranks; launch <<<1, 1>>> once per rank.
__global__ void exchange_once(ncclDevComm comm, ncclWindow_t srcWin,
                             ncclWindow_t dstWin, size_t bytes) {
    ncclGin gin{comm, 0};
    int peer = 1 - comm.rank;
    gin.put(ncclTeamWorld(comm), peer,
            dstWin, 0, srcWin, 0, bytes,
            ncclGin_SignalInc{0});
    gin.waitSignal(ncclCoopThread{}, 0, 1); // incoming data is ready
    gin.flush(ncclCoopThread{});          // local src can be reused
}

ncclGin_SignalInc associates a remote signal increment with write completion; the receiver waits with acquire semantics. flush makes the local send source safe to reuse. By itself it does not guarantee that data has settled in remote memory. Repeated execution requires iteration-aware signals and coordination before overwriting receiver storage. put / flush / waitSignal contracts

In this GDAKI implementation, putImplMode() resolves window keys and offsets and calls doca_gpu_dev_verbs_put*. Host code creates QPs through GPUNetIO and exports device descriptors. GIN supplies rank, window and synchronization semantics; GDAKI implements operations using GPU-accessible network resources. GIN → GPUNetIO · QP setup and export

7. NCCL GIN / CPU proxy

GIN CPU proxy retains the ncclGin rank, window and signal interfaces. A GPU kernel publishes descriptors, and host progress translates them into network operations. This path uses the built-in IB RMA backend: CPU verbs submits WRs, while a GDR-enabled NIC directly accesses registered GPU buffers. Descriptor processing · IB submission

7.1 Backend and resources

Memory allocation, window registration and device-communicator lifetime follow the GDAKI example. Request the proxy backend before creation. Host setup establishes shared request queues, progress counters and network connections.

reqs.ginContextCount = 1;
reqs.ginSignalCount = 1;

This replaces the requirements and creation portion of the setup example; allocation, registration, execution and teardown remain paired. The build and network environment must support the selected backend. Requirements · Selection

7.2 Descriptors and completion

proxyGinPollGfd() reads GPU-published descriptors; proxyGinProcessGfd() dispatches to the RMA backend's iput / iputSignal. The IB backend builds WRs and posts them through ibv_post_send(). Host progress checks request completion and updates GPU-visible counters. GFD consumption and dispatch · WR submission · Completion counters

7.3 Interface and responsibilities

The same ncclGin kernel remains applicable. Local-source reuse after flush and receiver signal dependencies retain their contracts. Submission changes: GDAKI constructs NIC WQEs on the GPU; GIN CPU proxy publishes GIN descriptors on the GPU and constructs network requests on the CPU. GPUNetIO CPU-assisted doorbells have another division of work: the GPU has already constructed the WQEs.

Ordinary NCCL NET/IB CPU proxies progress collective-kernel chunks; GIN CPU proxies consume GIN operations from user kernels. Both can use CPU verbs and GPUDirect RDMA, with different upper-level protocols and progress objects.
