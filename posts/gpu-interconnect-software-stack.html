GPU 互联的软件与驱动

网卡从内存中的描述符环读取工作，靠一个 doorbell 寄存器得知新工作到达。本文用一个例子贯穿全文：把 4 KiB 数据发往另一个节点。这个例子依次经过 socket、RDMA verbs、GPUDirect RDMA，以及 NCCL、NVSHMEM 和 NCCL GIN 的各个后端。每一步只改其中一件事：payload 放在哪里、谁写描述符，或者谁敲 doorbell。即使请求由 CPU 提交，payload 也能经 GPUDirect RDMA 直接在显存与网卡之间传输。

源码基线：Linux 6.12、rdma-core 61.0、NCCL 2.32.3、NVSHMEM 3.8.0，核对日期 2026-11-10；其他组件的版本见源码索引。链接固定到 tag 或 commit。序列图展示源码调用顺序，activation bar 标示参与者的逻辑活动范围。

1. 网卡与 RDMA

本章与 GPU 无关，只讲后文要用到的网卡机制：描述符环与 doorbell、socket 路径、RDMA verbs，以及 mlx5 驱动的分工。熟悉 verbs 的读者可以直接跳到第 2 章。

1.1 网卡是一台 PCIe 设备

网卡通过 PCIe 的 BAR（Base Address Register）暴露一段地址，这段地址对应设备寄存器。CPU 对这段地址执行普通的 load / store，就是一次 MMIO（memory-mapped I/O）访问，经 PCIe 到达网卡。反方向上，网卡的 DMA 引擎自己读写主机内存，使用的地址由驱动通过 Linux DMA API 取得；启用 IOMMU 时，这个地址还要经 IOMMU 翻译。DMA 地址与映射

驱动和网卡通过内存中的描述符环（descriptor ring）交接工作：每个描述符写明操作、buffer 地址和长度，网卡按序号读取。mlx5 网卡发送一次数据分四步：

步骤执行者动作
① 写描述符CPU在发送队列 SQ 的环中写一个 WQE（Work Queue Element），记录操作类型、buffer 地址和长度。
② 敲 doorbellCPU先在内存中的 DBR（Doorbell Record）记下新的生产者序号，再写 BAR 中 UAR（User Access Region）页上的 doorbell 寄存器。后者是一次 MMIO 写，经 PCIe 到达网卡。
③ 执行网卡DMA 读取 WQE 及其指向的数据，按协议发往网络。
④ 完成网卡DMA 写一条 CQE（Completion Queue Entry）到完成队列 CQ 的环中，按配置触发中断，或等待软件轮询。

①② 是软件的工作，③④ 是网卡的工作。以太网驱动和 RDMA 使用同一套结构，区别在于 ①② 由谁执行。后文逐级改变这个执行者：

1.2 Socket 基线：内核写描述符

A 用 TCP 把 4 KiB 发给 B。发送端从一次系统调用开始：

send(fd, buf, 4096, 0)                 # 系统调用，进入内核
  tcp_sendmsg_locked()                 # 把 4 KiB 拷进 skb 的页（内核缓冲区）
  tcp_write_xmit() … dev_queue_xmit()  # 加 TCP/IP 头，交给网卡驱动
    mlx5e_xmit()                       # DMA 映射数据页，在 SQ 环写 WQE    ①
      mlx5e_notify_hw()                # 写 DBR，再写 UAR doorbell        ②
网卡 A：DMA 读取数据，切成以太网帧发出                                ③

B 的网卡不知道这 4 KiB 属于哪个用户 buffer，只能先写进驱动预先投递的接收 buffer，再交给 B 的 CPU：

网卡 B：DMA 写入预先投递的接收 buffer，写 CQE，触发中断               ④
mlx5_eq_comp_int() → napi_schedule()       # 中断里只调度 NAPI
mlx5e_napi_poll() → mlx5e_poll_rx_cq()     # 软中断中读 CQE，构造 skb
  napi_gro_receive() … tcp_v4_rcv()        # TCP 处理，挂进 socket 接收队列
recv(fd, buf, 4096, 0)                     # 系统调用：拷贝到用户 buffer

这里的 ①② 由内核中的 mlx5e 以太网驱动执行，即级别 1。一次传输因此要付出两端各一次系统调用、各一次 4 KiB 拷贝、两端 CPU 的协议处理，以及接收端的中断。拷贝不容易省掉：Linux 文档指出，MSG_ZEROCOPY 用页面固定和完成通知的开销代替逐字节拷贝，通常只对约 10 KB 以上的写入有效；4 KiB 的 send 用它通常得不到收益。MSG_ZEROCOPY 整条路径的延迟取决于 CPU、网卡和中断合并配置，需要在目标机器上实测，本文不给固定数字。

“经过网卡”不等于 RDMA。上面的 ③④ 也是网卡执行的 DMA，但网卡只在描述符环与网络之间搬运字节，决定数据最终落到哪个用户 buffer 的是 B 的 CPU。RDMA 把远端内存操作交给网卡：请求带着对端地址和访问 key，由对端网卡校验后直接写进目标内存。

B 的 CPU 不在图中：它不调用接口，也不处理中断。B 的网卡用 rkey 找到预先注册的 MR，检查地址范围和远端写权限后直接 DMA 写入（⑤⑥）。A 的 CQE 只说明本端请求已经完成，B 上的程序并不知道数据已经到达；需要通知时，A 还要再发一条消息，或使用带 immediate 的写。第 6 章会回到这个问题。

旁注：其他 verbs 操作

RDMA Read 方向相反：A 发出 B 的地址和 rkey，B 的网卡读出数据返回，两端 CPU 同样不参与。Send/Recv 是双边操作：接收方先用 ibv_post_recv() 投递接收 buffer，到达的 Send 填入其中，并在接收方产生 CQE；RDMA Write with immediate 也会消耗接收方的一个接收请求，并在那里产生 CQE。原子操作（fetch-and-add、compare-and-swap）由远端网卡对 8 字节远端内存执行。UD（Unreliable Datagram）不建立连接，只支持 Send/Recv，单条消息不超过一个 MTU。RoCE 与 InfiniBand 使用同一套 verbs 和传输语义；RoCE v2 把 InfiniBand 传输层封装在 UDP/IP 中，在以太网上传输。

2. 显存作为 RDMA buffer

把例子中两端的 buffer 换成 cudaMalloc() 分配的显存，其余不变：A 的 CPU 仍调用 ibv_post_send()，①② 仍由 libmlx5 执行，级别仍是 2。改变的只有网卡 DMA 的对象。DMA、RDMA 和 GPUDirect RDMA 是逐级扩展的三种机制：

机制解决的问题典型数据路径
DMA设备直接读写本机内存（1.2 节）。本机网卡 ↔ 主机内存
RDMA
Remote Direct Memory Access		网卡执行远端内存操作：请求指定远端地址、长度和访问 key，对端网卡检查注册范围与权限后传输数据（1.3 节）。A 主机内存 ↔ A 网卡 ↔ 网络 ↔ B 网卡 ↔ B 主机内存

GPUDirect RDMA 下，A 的网卡在 ③ 中经 PCIe 直接读 A 的显存，B 的网卡在 ⑥ 中直接写 B 的显存，payload 不经主机内存中转。网卡访问的是 GPU 在 PCIe BAR 上暴露的地址，读写方式与访问主机内存相同。GPUDirect RDMA 变化集中在注册：ibv_reg_mr() 必须为显存取得网卡可用的 DMA 地址。

5. GPU 自己敲 doorbell

最后把 ② 也交给 GPU。1.4 节已经看到，CPU 敲 doorbell 只是对 UAR 页的一次 store。GPU 要做同样的事，需要两样东西：GPU 页表中指向这页 UAR 的映射，以及一条能变成 PCIe 写的 MMIO store。有了这两样，kernel 就能直接发起网卡操作，即 GDAKI（GPUDirect Async Kernel-Initiated）。

5.1 把 UAR 映射进 GPU 页表

UAR 的 CPU 映射沿用 1.4 节的做法。IBGDA 和 GPUNetIO 用 mlx5dv_devx_alloc_uar() 申请专用的 UAR，它与 QP 的 UAR 走同一个分配函数：经命令 fd 分配，再 mmap() 进进程。返回的 uar->reg_addr 是进程内可访问 doorbell 的 CPU 虚拟地址。UAR 接口 接下来由 CUDA 为同一段 I/O 区域再建立一个 GPU 映射。下面的函数提取自 NVSHMEM ibgda_nic_mem_gpu_map() 的注册步骤：

#include <cuda_runtime.h>
#include <cstdint>

// cpu_reg = uar->reg_addr; bytes = this UAR's register span.
cudaError_t map_uar_to_gpu(void* cpu_reg, size_t bytes,
                          uint64_t** gpu_doorbell_ptr) {
    *gpu_doorbell_ptr = nullptr;
    unsigned flags = cudaHostRegisterPortable
                   | cudaHostRegisterMapped
                   | cudaHostRegisterIoMemory;
    cudaError_t rc = cudaHostRegister(cpu_reg, bytes, flags);
    if (rc != cudaSuccess) return rc;

    void* device_alias = nullptr;
    rc = cudaHostGetDevicePointer(&device_alias, cpu_reg, 0);
    if (rc != cudaSuccess) {
        cudaHostUnregister(cpu_reg);
        return rc;
    }
    *gpu_doorbell_ptr = static_cast<uint64_t*>(device_alias);
    return cudaSuccess;
}

cpu_reg 取自 uar->reg_addr；bytes 取该 UAR 的寄存器跨度：本文版本的专用 NC 分支使用 8 字节，BF 分支按设备报告的 log_bf_reg_size 计算。UAR 类型与大小

Mapped 请求 GPU 地址映射；IoMemory 声明这段地址是第三方 PCIe 设备的 MMIO 空间，按非缓存一致、连续的区域处理；Portable 让注册对所有 CUDA context 生效。cudaHostGetDevicePointer() 返回 GPU 使用的地址，数值可以与 CPU 指针不同。CUDA 注册语义 NVSHMEM 把它写入 dev_qp->tx_wq.bf，并把同一个 UAR 的 page_id 配入 QP；GPUNetIO 的 doca_gpu_verbs_export_uar() 执行同样的注册与取址，再交给 GDAKI 等设备路径。GPU 与 QP 停止使用该 UAR 后，先 cudaHostUnregister(cpu_reg)，再释放 UAR。QP 的 UAR 配置 · GPUNetIO 导出

驱动内部，公开的 I/O memory 导入路径先检查 CPU VMA 的 VM_IO / VM_PFNMAP 属性，沿 CPU 映射取得 UAR 页的 PFN，再建立标记为 MEMDESC_FLAGS_PEER_IO_MEM 的描述符。描述符使用 ADDR_SYSMEM 地址类别，并处理 GPU 可见的总线地址和 IOMMU 映射。CPU 映射与 PFN · I/O memory 描述符

本系列第 4 篇的 P2P 访问也是在 GPU 页表里建一条指向其他设备的映射：PTE 的 aperture 选 peer，目标是另一张 GPU 的显存，load / store 经 NVLink 或 PCIe 到达对端。UAR 映射的 PTE 选 system non-coherent aperture，目标地址落在网卡 BAR 的 MMIO 页上，store 变成发往网卡的 PCIe 写。两种映射都由 CPU 侧驱动建立，建立之后 GPU 的访问不需要 CPU 参与。

// VER3 encoding example, following Hopper's UVM PTE builder.
// Input: GPU-visible NIC page address, 4 KiB aligned, below 2^52.
uint64_t encode_uar_pte(uint64_t nic_page_addr) {
    constexpr uint64_t address_mask = ((1ULL << 52) - 1) & ~0xfffULL;
    constexpr uint64_t pcf = 0x19;  // REGULAR_RW_NO_ATOMIC_UNCACHED_ACD
    constexpr uint64_t kind = 0x6;  // GENERIC_MEMORY
    return (nic_page_addr & address_mask)  // ADDRESS [51:12]
         | (kind << 8)                   // KIND [11:8]
         | (pcf << 3)                    // PCF [7:3]
         | (3ULL << 1)                   // SYSTEM_NON_COHERENT [2:1]
         | 1ULL;                         // VALID [0]
}

本例低 12 位为 0x6CF = (0x6 << 8) | (0x19 << 3) | (3 << 1) | 1。如果 GPU 可见的 NIC 页地址为 0x0000800012345000，编码结果就是 0x00008000123456CF；GPU 虚拟地址的页内偏移 0x20 会定位到 NIC 地址 0x0000800012345020。这些地址用于演算，实际值由驱动的资源映射决定。

5.2 从 store 到 PCIe

GPU 提交线程先写好 WQE、更新 DBR，再写 UAR，顺序与 1.4 节的 CPU 代码相同。下面抽出一次 64 位 doorbell 写入，对应 GPUNetIO 的 fence + st.mmio.relaxed 提交方式。%0 是 GPU 地址，%1 是已按 mlx5 格式与字节序编码的 doorbell 值。GPUNetIO 门铃提交

// Called by the submitting thread after preparing WQEs and the DBR.
// mlx5_db_be: the correctly encoded 64-bit mlx5 doorbell value.
__device__ __forceinline__
void ring_uar(uint64_t* gpu_doorbell_ptr, uint64_t mlx5_db_be) {

1. NICs and RDMA

This chapter leaves GPUs out and covers the NIC mechanisms the rest of the post relies on: descriptor rings and doorbells, the socket path, RDMA verbs and the mlx5 drivers. Readers who know verbs can skip to chapter 2.

1.1 The NIC as a PCIe device

A NIC exposes device registers through addresses in a PCIe BAR (Base Address Register). An ordinary CPU load or store to those addresses is an MMIO (memory-mapped I/O) access that travels over PCIe to the NIC. In the other direction, the NIC's DMA engine reads and writes host memory itself, at addresses the driver obtains from the Linux DMA API; with an IOMMU enabled, the IOMMU translates them as well. DMA addresses and mappings

The driver and the NIC hand over work through descriptor rings in memory: each descriptor names an operation, a buffer address and a length, and the NIC reads the descriptors in order. An mlx5 NIC sends data in four steps:

StepPerformed byAction
① Write the descriptorCPUWrite a WQE (Work Queue Element) into the send queue (SQ) ring, recording the operation, buffer address and length.
② Ring the doorbellCPURecord the new producer index in the DBR (Doorbell Record) in memory, then write the doorbell register on a UAR (User Access Region) page in the BAR, an MMIO write that reaches the NIC over PCIe.
③ ExecuteNICDMA-read the WQE and the data it points to, then transmit the data.
④ CompleteNICDMA-write a CQE (Completion Queue Entry) into the completion queue (CQ) ring, then raise an interrupt or wait for software to poll, as configured.

1.2 Socket baseline: the kernel writes the descriptor

A sends 4 KiB to B over TCP. The sender starts with a system call:

send(fd, buf, 4096, 0)                 # system call into the kernel
  tcp_sendmsg_locked()                 # copy 4 KiB into skb pages (kernel buffer)
  tcp_write_xmit() … dev_queue_xmit()  # add TCP/IP headers, hand off to the driver
    mlx5e_xmit()                       # DMA-map the data pages, write a WQE   ①
      mlx5e_notify_hw()                # write the DBR, then the UAR doorbell  ②
NIC A: DMA-read the data and send it as Ethernet frames                     ③

B's NIC does not know which user buffer the 4 KiB belongs to. It writes the data into receive buffers the driver posted in advance and leaves the rest to B's CPU:

NIC B: DMA-write into a posted receive buffer, write a CQE, interrupt  ④
mlx5_eq_comp_int() → napi_schedule()       # the interrupt only schedules NAPI
mlx5e_napi_poll() → mlx5e_poll_rx_cq()     # softirq: read CQEs, build skbs
  napi_gro_receive() … tcp_v4_rcv()        # TCP processing, socket receive queue
recv(fd, buf, 4096, 0)                     # system call: copy to the user buffer

Here the mlx5e Ethernet driver in the kernel performs ① and ②: level 1. A transfer therefore costs a system call and a 4 KiB copy on each side, protocol processing on both CPUs, and an interrupt on the receiver. The copy is hard to remove: the Linux documentation notes that MSG_ZEROCOPY trades the per-byte copy for page-pinning and completion-notification overhead and is generally only effective for writes over about 10 KB, so a 4 KiB send usually gains nothing from it. MSG_ZEROCOPY End-to-end latency depends on the CPU, the NIC and interrupt coalescing and must be measured on the target machine; this post quotes no figure.

Passing through a NIC does not make a transfer RDMA. Steps ③ and ④ above are DMA by the NIC as well, but the NIC only moves bytes between its descriptor rings and the network; B's CPU decides which user buffer the data finally reaches. RDMA hands remote memory operations to the NIC: the request carries the peer's address and an access key, and the peer's NIC validates them and writes directly into the destination memory.

RDMA Read runs the other way: A sends B's address and rkey, and B's NIC returns the data without either CPU. 4. The GPU writes the WQE; the CPU only rings the doorbell

A level-3 proxy builds a WR for every request, which libmlx5 encodes as a WQE. If the GPU writes mlx5 WQEs itself, the CPU keeps only ②. That requires an SQ ring in GPU memory that the GPU can write and the NIC can DMA-read, registered with the NIC like the payload in chapter 2, and a GPU that maintains the queue state and polls the CQ. Who performs ② depends on whether the GPU can map the UAR (chapter 5); when it cannot, the CPU rings the doorbell: level 4.

5. The GPU rings the doorbell itself

The last step hands ② to the GPU too. Section 1.4 showed that a CPU doorbell is one store to a UAR page. To do the same, the GPU needs a mapping of that UAR page in its page table and an MMIO store that becomes a PCIe write. With both, a kernel can initiate NIC operations directly; this is GDAKI (GPUDirect Async Kernel-Initiated).

5.1 Mapping the UAR into the GPU page table

The CPU mapping of the UAR works as in section 1.4. IBGDA and GPUNetIO request a dedicated UAR with mlx5dv_devx_alloc_uar(), which uses the same allocator as a QP's UAR: allocation on the command fd, then mmap(). The returned uar->reg_addr is a CPU virtual address for doorbell access in that process. UAR interface CUDA then creates a GPU mapping of the same I/O region. This helper follows the registration steps in NVSHMEM's ibgda_nic_mem_gpu_map():

#include <cuda_runtime.h>
#include <cstdint>

// cpu_reg = uar->reg_addr; bytes = this UAR's register span.
cudaError_t map_uar_to_gpu(void* cpu_reg, size_t bytes,
                          uint64_t** gpu_doorbell_ptr) {
    *gpu_doorbell_ptr = nullptr;
    unsigned flags = cudaHostRegisterPortable
                   | cudaHostRegisterMapped
                   | cudaHostRegisterIoMemory;
    cudaError_t rc = cudaHostRegister(cpu_reg, bytes, flags);
    if (rc != cudaSuccess) return rc;

    void* device_alias = nullptr;
    rc = cudaHostGetDevicePointer(&device_alias, cpu_reg, 0);
    if (rc != cudaSuccess) {
        cudaHostUnregister(cpu_reg);
        return rc;
    }
    *gpu_doorbell_ptr = static_cast<uint64_t*>(device_alias);
    return cudaSuccess;
}

Pass uar->reg_addr as cpu_reg and the UAR's register span as bytes. In the pinned version, the dedicated NC branch uses 8 bytes; the BF branch derives the size from the device's log_bf_reg_size. UAR type and size

Mapped requests a GPU mapping; IoMemory declares the range to be MMIO space of a third-party PCIe device, treated as non-cache-coherent and contiguous; Portable makes the registration valid for all CUDA contexts. cudaHostGetDevicePointer() returns the address for GPU access, which can differ numerically from the CPU pointer. CUDA registration semantics NVSHMEM stores it in dev_qp->tx_wq.bf and configures the QP with the same UAR's page_id; GPUNetIO's doca_gpu_verbs_export_uar() performs the same registration and pointer lookup for device paths such as GDAKI. Once the GPU and QP have stopped using the UAR, call cudaHostUnregister(cpu_reg) before freeing the UAR. QP UAR configuration · GPUNetIO export

Inside the driver, the open I/O memory import path checks the CPU VMA for VM_IO / VM_PFNMAP, obtains the UAR page's PFN through the CPU mapping, and creates a descriptor marked MEMDESC_FLAGS_PEER_IO_MEM. // VER3 encoding example, following Hopper's UVM PTE builder.
// Input: GPU-visible NIC page address, 4 KiB aligned, below 2^52.
uint64_t encode_uar_pte(uint64_t nic_page_addr) {
    constexpr uint64_t address_mask = ((1ULL << 52) - 1) & ~0xfffULL;
    constexpr uint64_t pcf = 0x19;  // REGULAR_RW_NO_ATOMIC_UNCACHED_ACD
    constexpr uint64_t kind = 0x6;  // GENERIC_MEMORY
    return (nic_page_addr & address_mask)  // ADDRESS [51:12]
         | (kind << 8)                   // KIND [11:8]
         | (pcf << 3)                    // PCF [7:3]
         | (3ULL << 1)                   // SYSTEM_NON_COHERENT [2:1]
         | 1ULL;                         // VALID [0]
}

The low 12 bits are 0x6CF = (0x6 << 8) | (0x19 << 3) | (3 << 1) | 1. For a GPU-visible NIC page address of 0x0000800012345000, the encoded PTE is 0x00008000123456CF. A GPU virtual address with page offset 0x20 then targets NIC address 0x0000800012345020. These addresses illustrate the calculation; actual values come from the driver's resource mapping.

5.2 From store to PCIe

The GPU submitting thread writes the WQEs, updates the DBR and then writes the UAR, in the same order as the CPU code in section 1.4. This helper isolates one 64-bit doorbell write following GPUNetIO's fence + st.mmio.relaxed submission pattern. %0 is the GPU address, and %1 is a doorbell value already encoded in mlx5 format and byte order. GPUNetIO submission

// Called by the submitting thread after preparing WQEs and the DBR.
// mlx5_db_be: the correctly encoded 64-bit mlx5 doorbell value.
__device__ __forceinline__
void ring_uar(uint64_t* gpu_doorbell_ptr, uint64_t mlx5_db_be) {
    asm volatile("fence.acq_rel.sys;" ::: "memory");
    asm volatile("st.mmio.relaxed.sys.global.b64 [%0], %1;"
                 : : "l"(gpu_doorbell_ptr), "l"(mlx5_db_be)
                 : "memory");
}

fence.acq_rel.sys provides both acquire and release ordering; here its release semantics publish the submitting thread's earlier writes, matching the barriers at lines 768 and 774–778 of the code in section 1.4: when the NIC sees the doorbell, the WQEs and the DBR must already be written. .mmio specifies device-register access semantics, and .sys selects system scope. The instruction sequence requires a toolchain supporting PTX 8.2 MMIO and an sm_70 or later target. PTX store semantics · Fence semantics

6. Completion and ordering
