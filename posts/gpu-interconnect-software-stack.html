GPU 互联的软件与驱动

普通 NCCL、NVSHMEM 与 NCCL GIN 提供了三种组织 GPU 通信的方式：CPU 发起 collective、基于 symmetric memory 的一侧通信，以及用户 kernel 内的网络操作。NVSHMEM 和 GIN 各有可选后端，决定请求由 CPU proxy 还是 GPU 推进；驱动为这些后端建立网卡队列、显存注册和地址映射。即使请求由 CPU proxy 提交，payload 仍可通过 GPUDirect RDMA 直接在显存与网卡之间传输。

库和内核模块是完整路径的依赖。libibverbs 提供接口，libmlx5 实现 mlx5 用户态队列操作，mlx5_ib 管理内核侧 RDMA 资源，nvidia-peermem 参与显存注册协作。在支持的配置下，DMA-BUF 可替代这一注册协作机制；NCCL / NVSHMEM 仍负责上层通信语义与进度。具体依赖见 软件与驱动。verbs 与驱动分工 · peer-memory · DMA-BUF

1.2 DMA 与 RDMA

普通以太网卡收到数据包后，就可以把数据 DMA 写入本机内存中的接收缓冲区。DMA（Direct Memory Access，直接内存访问）让设备按驱动建立的地址映射读写内存，数据搬运由设备完成。CPU 负责准备缓冲区、描述符和映射，并处理提交与完成。Linux DMA 地址与映射

机制解决的问题典型数据路径
DMA设备直接读写本机可访问的内存。本机 NIC ↔ 主机内存
RDMA
Remote Direct Memory Access		网卡执行远端内存操作。RDMA Read/Write 请求指定远端地址、长度和访问 key，网卡检查注册范围与权限并执行传输。A 主机内存 ↔ A NIC ↔ 网络 ↔ B NIC ↔ B 主机内存
GPUDirect RDMA将 GPU 显存接入第三方设备的直接 DMA 路径；用于 RDMA 通信时，NIC 可直接访问已注册的显存。A 显存 ↔ A NIC ↔ 网络 ↔ B NIC ↔ B 显存

“经过网卡”不等于“远程直接内存访问”。普通 TCP/IP 收发也使用本机 DMA。RDMA 增加了网卡能够理解的远端内存操作、访问保护和完成机制；两端提前完成内存注册，并交换远端访问所需的地址和 key。GPUDirect RDMA 则把显存纳入这套访问路径。RDMA 操作 · GPUDirect RDMA

内存与队列对象

一次 RDMA Read 需要先授权内存访问，再提交读取请求，最后取得完成结果。这几个环节分别使用以下对象。

术语含义与职责
MR · Memory Region
内存区域		向 RDMA 设备注册的一段内存，记录地址范围、访问权限和映射。它可以对应主机内存，也可以对应受支持的 GPU 显存。
lkey / rkey
本地 / 远端访问 key		注册 MR 时取得的访问标识。lkey 用于本地 buffer，rkey 交给对端，用于远端内存访问校验。
PD · Protection Domain
保护域		关联本地 QP、MR 等资源，限定哪些队列可以使用哪些注册内存。
QP · Queue Pair
队列对		包含发送队列 SQ 和接收队列 RQ。RDMA Read/Write 由发起方提交到 SQ；RQ 存放接收请求，为 Send 等操作准备接收 buffer。
WR · Work Request
工作请求		软件提交的操作描述。例如“把 B 的 4096 字节读入 A”，包含操作类型、本地 buffer、长度，以及远端地址和 rkey。
WQE · Work Queue Element
工作队列项		网卡可解析的硬件格式描述符，放在工作队列中。CPU verbs 路径由 provider 把 WR 编码为 WQE；GPU 发起路径可由设备代码构造 WQE。
Doorbell
门铃		通知网卡有新工作的机制。mlx5 先更新内存中的 DBR（Doorbell Record，队列进度记录），再写入映射的 MMIO doorbell，推动网卡处理 WQE。
CQ / CQE
Completion Queue / Entry		CQ 是完成队列，CQE 是其中的一条完成记录，包含成功或错误状态。发送侧可选择哪些成功完成的请求生成 CQE，再从 CQ 取回结果。

以启用完成通知的 CPU verbs 请求为例，路径是：构造 WR → provider 写入 WQE → 敲 doorbell → NIC 执行 → 从 CQ 读取 CQE。MR 提供请求访问内存时所需的映射与权限。RDMA 对象 · 内存注册 · 请求与完成选项 · mlx5 门铃实现

A 要把 B 显存中的 4 KiB 数据读入自己的显存。两端已建立可靠连接（RC）的队列对 QP，并将相应 buffer 注册为内存区域 MR。B 授予源 MR 远端读权限，将远端地址和 rkey 交给 A；A 的目标 MR 允许本地写入。A 提交请求时指定 B 的地址与 rkey，以及自己的目标地址与 lkey。两种 key 分别标识远端和本地的内存访问资源。MR 与访问权限 · RDMA Read 请求字段

2. 普通 NCCL

普通 NCCL NET/IB 路径由 CPU proxy 推进网络请求。libnccl.so 组织 collective，proxy 经 libibverbs 与 libmlx5 提交 WR；启用 GPUDirect RDMA 后，NIC 直接搬运 GPU buffer。连接与内存注册先完成，后续 chunk 复用这些资源。

2.1 连接与队列

跨主机传输前，CPU 为两端准备队列、内存地址及访问权限。这些信息随后供 CPU 或 GPU 的提交代码使用。

每端建立 PD，将 QP 与注册的 MR 关联到同一保护域，并为 QP 关联 CQ。两端交换连接信息，以及远端访问所需的 MR 地址和 rkey。对象定义见 1.2 节的内存与队列对象。

普通 RDMA Write 直接访问远端 MR，无需为每次写入配对一个 receive buffer。Send/Recv，以及带 immediate 的某些操作，有不同的接收资源与通知要求。接收方何时消费 buffer，还需要通信库或应用定义同步协议。

2.2 显存注册

CUDA 分配提供 GPU 可用的虚拟地址。网卡访问同一段 buffer，还需要访问授权与 DMA 地址映射。内存注册为此建立 NIC 资源和 key；GPU 页表中的 peer 映射与 NIC 的 MR 分别服务于两种访问机制。

3. NVSHMEM

NVSHMEM 用 PE 和 symmetric memory 表达跨 GPU 的一侧通信。应用使用同一组 put/get 与同步接口，device transport 按目标可达性和配置选择 peer 访问、CPU proxy、IBGDA 或 GPUNetIO。以下网络后端复用相同的应用示例。device 分派 · transport 选择

3.1 PE 与 symmetric heap

NVSHMEM 提供一侧通信接口：调用方指定目标 PE，即可 put/get 对方的 symmetric memory。各 PE 按一致的 collective 分配顺序建立对应对象。symmetric address 标识对方对应的分配与偏移，各进程的虚拟地址数值不必相同。NVSHMEM 编程模型

对于 GPU 0 → GPU 1 的例子，两个 PE 各自分配 dst 和 signal。PE 0 写入 PE 1 的 dst，再发布与数据有序关联的信号；PE 1 等待信号后消费数据。

#include <nvshmem.h>
#include <nvshmemx.h>

// Two PEs, one thread per PE, one transfer, signal initially zero.
__global__ void send_once(void* dst, const void* src,
                          size_t bytes, uint64_t* signal) {
    if (nvshmem_my_pe() == 0) {
        nvshmem_putmem_signal_nbi(dst, src, bytes, signal,
                                 1, NVSHMEM_SIGNAL_SET, 1);
        nvshmem_quiet();
    } else {
        nvshmem_signal_wait_until(signal, NVSHMEM_CMP_GE, 1);
        // This PE can now consume its local dst.
    }
}

示例中，两个 PE 各绑定一张 GPU，dst、signal 已通过 symmetric allocation 建立，signal 初值为 0，src 数据已就绪。两端各以单 block、单线程执行一轮，通过 nvshmemx_collective_launch 启动包含跨 PE 等待的 kernel。初始化与 collective launch 的完整写法见 官方 ring-bcast 示例。

put_signal_nbi 将数据传输与远端通知关联；quiet 完成调用线程先前发出的操作，接收方通过 signal_wait_until 等待数据。复用远端 buffer 还需确认接收方已完成消费，或按轮次管理 buffer。多个线程发出操作时，应先保证其他线程的操作已发出，再由调用线程执行 quiet。Memory ordering · 信号接口

3.5 UAR 与 GPU 页表

IBGDA 与 GPUNetIO 的 GPU doorbell 都需要访问 NIC 寄存器。这里结合两者的注册代码解释 UAR 映射；NCCL GIN / GDAKI 使用 GPUNetIO 时也复用这一机制。

UAR（User Access Region）是网卡暴露给应用的寄存器访问区域，其中包含 doorbell / BlueFlame 寄存器。GPU 直接敲门铃，需要让一个 GPU 虚拟地址指向 NIC BAR 中的这块区域。CPU 在初始化时建立映射，GPU 随后通过这个地址执行 MMIO store。UAR 接口

注册地址

mlx5dv_devx_alloc_uar() 分配 UAR。其 provider 通过 /dev/infiniband/uverbsN 的 fd 执行资源分配与 mmap，返回的 uar->reg_addr 是进程内可访问 doorbell 的 CPU 虚拟地址。NVIDIA 驱动再为同一 I/O 区域建立 GPU 映射。provider 的 ioctl 与 mmap

以下函数提取 NVSHMEM ibgda_nic_mem_gpu_map() 的注册步骤。cpu_reg 取自 uar->reg_addr；bytes 取对应 UAR 的寄存器跨度：本文版本的专用 NC 分支使用 8 字节，BF 分支按设备报告的 log_bf_reg_size 计算。NVSHMEM 注册实现 · UAR 类型与大小

#include <cuda_runtime.h>
#include <cstdint>

// cpu_reg = uar->reg_addr; bytes = this UAR's register span.
cudaError_t map_uar_to_gpu(void* cpu_reg, size_t bytes,
                          uint64_t** gpu_doorbell_ptr) {
    *gpu_doorbell_ptr = nullptr;
    unsigned flags = cudaHostRegisterPortable
                   | cudaHostRegisterMapped
                   | cudaHostRegisterIoMemory;
    cudaError_t rc = cudaHostRegister(cpu_reg, bytes, flags);
    if (rc != cudaSuccess) return rc;

    void* device_alias = nullptr;
    rc = cudaHostGetDevicePointer(&device_alias, cpu_reg, 0);
    if (rc != cudaSuccess) {
        cudaHostUnregister(cpu_reg);
        return rc;
    }
    *gpu_doorbell_ptr = static_cast<uint64_t*>(device_alias);
    return cudaSuccess;
}

Mapped 请求 GPU 地址映射，IoMemory 将输入解释为设备 I/O 资源，并标记为非缓存一致、物理连续的区域；Portable 扩大注册的 CUDA context 适用范围。cudaHostGetDevicePointer() 返回 GPU 使用的地址；CPU 与 GPU 的指针数值可以不同。驱动内部按页处理映射，bytes 描述本次注册的区间。CUDA 注册语义

NVSHMEM 将返回值写入 dev_qp->tx_wq.bf，并把同一个 UAR 的 page_id 配入 QP。GPUNetIO 的 doca_gpu_verbs_export_uar() 也执行这组注册与取址操作，随后交给 GDAKI 等 device 路径使用。GPU 与 QP 停止使用该 UAR 后，先 cudaHostUnregister(cpu_reg)，再释放 UAR。QP 的 UAR 配置 · device 指针传递 · GPUNetIO 导出

PTE 的目标与属性

公开驱动的 I/O memory 导入路径会检查 CPU VMA 的 VM_IO / VM_PFNMAP 属性，沿 CPU 映射取得设备资源的 PFN，再建立标记为 MEMDESC_FLAGS_PEER_IO_MEM 的描述符。描述符使用 ADDR_SYSMEM 地址类别，并处理 GPU 可见的总线地址及 IOMMU 映射；这里的 system aperture 也承载设备 MMIO。CPU 映射与 PFN · I/O memory 描述符

Hopper 的 VER3 PTE 将权限与缓存属性合并进 PCF（Permission Control Flags）字段。公开驱动中的 Blackwell UVM 复制 Hopper 的 MMU HAL，并沿用 make_pte_hopper() 构造叶子 PTE；Blackwell 的页大小扩展由其他 HAL 成员处理。下面用这条构造路径解释两代 GPU 的 4 KiB 映射。GH100 的 VER3 位定义 · Hopper PTE 构造 · Blackwell 的 HAL 继承

本例选择普通用户 kernel 可读写、GPU uncached、禁用 GPU 原子访问和访问计数器的 PCIe UAR 映射。字段值按公开格式编码；实际注册时，CUDA 驱动根据平台和映射策略生成页表。

APERTURE 选择系统一致性通路，PCF 中的 UNCACHED 选择 GPU 缓存策略。下面将本例字段组合成一个 64 位值，展示 make_pte_hopper() 的编码方式；CUDA 注册负责实际页表的建立。aperture 选择 · 字段组合

// VER3 encoding example, following Hopper's UVM PTE builder.
// Input: GPU-visible NIC page address, 4 KiB aligned, below 2^52.
uint64_t encode_uar_pte(uint64_t nic_page_addr) {
    constexpr uint64_t address_mask = ((1ULL << 52) - 1) & ~0xfffULL;
    constexpr uint64_t pcf = 0x19;  // REGULAR_RW_NO_ATOMIC_UNCACHED_ACD
    constexpr uint64_t kind = 0x6;  // GENERIC_MEMORY
    return (nic_page_addr & address_mask)  // ADDRESS [51:12]
         | (kind << 8)                   // KIND [11:8]
         | (pcf << 3)                    // PCF [7:3]
         | (3ULL << 1)                   // SYSTEM_NON_COHERENT [2:1]
         | 1ULL;                         // VALID [0]
}

本例低 12 位为 0x6CF = (0x6 << 8) | (0x19 << 3) | (3 << 1) | 1。如果 GPU 可见的 NIC 页地址为 0x0000800012345000，编码结果就是 0x00008000123456CF；GPU 虚拟地址的页内偏移 0x20 会定位到 NIC 地址 0x0000800012345020。这些地址用于演算，实际值由驱动的资源映射决定。

从 store 到 PCIe

GPU 提交线程先写好 WQE、更新 DBR，再写 UAR。DBR 是内存中的队列进度记录；UAR doorbell 是设备寄存器。下面抽出一次 64 位门铃写入，对应 GPUNetIO 的 fence + st.mmio.relaxed 提交方式。示例用 fence.acq_rel.sys 提供所需的发布顺序；%0 是 GPU 地址，%1 是已按 mlx5 格式与字节序编码的门铃值。GPUNetIO 门铃提交 · MMIO store

// Called by the submitting thread after preparing WQEs and the DBR.
// mlx5_db_be: the correctly encoded 64-bit mlx5 doorbell value.
__device__ __forceinline__
void ring_uar(uint64_t* gpu_doorbell_ptr, uint64_t mlx5_db_be) {
    asm volatile("fence.acq_rel.sys;" ::: "memory");
    asm volatile("st.mmio.relaxed.sys.global.b64 [%0], %1;"
                 : : "l"(gpu_doorbell_ptr), "l"(mlx5_db_be)
                 : "memory");
}

fence.acq_rel.sys 包含 acquire 与 release 两种顺序约束，这里使用其 release 语义发布提交线程先前的写入。.mmio 指定设备寄存器访问语义，.sys 指定系统作用域。这个指令组合要求支持 PTX 8.2 MMIO 的工具链及 sm_70 以上目标。多个线程协作写队列时，提交线程还需通过库的同步协议确认其他线程已完成写入。PTX store 语义与支持范围 · Fence 语义

4.2 Kernel 接口

示例中的两个 rank 各向对方写入一块数据，每个 rank 启动一个线程，只执行一轮，signal 0 初值为 0。等待固定值 1，可避免以“当前 signal 值加 1”作为等待目标时与对端提前发送发生竞态。

#include <nccl_device.h>

// Exactly two ranks; launch <<<1, 1>>> once per rank.
__global__ void exchange_once(ncclDevComm comm, ncclWindow_t srcWin,
                             ncclWindow_t dstWin, size_t bytes) {
    ncclGin gin{comm, 0};
    int peer = 1 - comm.rank;
    gin.put(ncclTeamWorld(comm), peer,
            dstWin, 0, srcWin, 0, bytes,
            ncclGin_SignalInc{0});
    gin.waitSignal(ncclCoopThread{}, 0, 1); // incoming data is ready
    gin.flush(ncclCoopThread{});          // local src can be reused
}

ncclGin_SignalInc 把远端信号递增与写入完成关联起来，接收方通过 acquire 语义的 waitSignal 等待。flush 保障本地发送源可以复用；它单独不保证数据已经落定在远端内存。重复执行时需要按轮次维护 signal，并协调接收 buffer 的复用。put / flush / waitSignal 契约

2. Ordinary NCCL

In the ordinary NCCL NET/IB path, a CPU proxy progresses network requests. libnccl.so organizes the collective; the proxy submits WRs through libibverbs and libmlx5. With GPUDirect RDMA enabled, the NIC transfers GPU buffers directly. Connection and memory setup precede the chunks that reuse those resources.

2.1 Connections and queues

Before a cross-host transfer, the CPU prepares queues, memory addresses and access permissions for both endpoints. CPU or GPU submission code then uses this information.

Each endpoint creates a PD, associates its QP and registered MRs with that domain, and assigns CQs to the QP. The endpoints exchange connection information and the MR addresses and rkeys needed for remote access. Section 1.2 defines these memory and queue objects.

An ordinary RDMA Write accesses a remote MR without a matching receive buffer for every write. Send/Recv and some operations with immediate data have different receive-resource and notification requirements. The communication library or application must also define when the receiver can consume the buffer.

2.2 GPU memory registration

A CUDA allocation supplies a GPU virtual address. NIC access to the same buffer requires authorization and DMA mappings. Registration establishes NIC resources and keys; GPU peer mappings and NIC MRs serve distinct access mechanisms.

3.1 PEs and the symmetric heap

NVSHMEM provides one-sided communication: a caller specifies a target PE and puts/gets its symmetric memory. PEs establish corresponding objects through consistent collective allocation order. A symmetric address identifies the corresponding allocation and offset at a peer; numerical virtual addresses need not be identical across processes. NVSHMEM programming model

For GPU 0 → GPU 1, both PEs allocate dst and signal. PE 0 writes PE 1's dst and publishes an ordered signal. PE 1 waits for that signal before consuming the data.

#include <nvshmem.h>
#include <nvshmemx.h>

// Two PEs, one thread per PE, one transfer, signal initially zero.
__global__ void send_once(void* dst, const void* src,
                          size_t bytes, uint64_t* signal) {
    if (nvshmem_my_pe() == 0) {
        nvshmem_putmem_signal_nbi(dst, src, bytes, signal,
                                 1, NVSHMEM_SIGNAL_SET, 1);
        nvshmem_quiet();
    } else {
        nvshmem_signal_wait_until(signal, NVSHMEM_CMP_GE, 1);
        // This PE can now consume its local dst.
    }
}

The example uses two PEs, each bound to one GPU. dst and signal are symmetric allocations; signal starts at 0 and src is ready. Each PE executes one round with one block and one thread. nvshmemx_collective_launch launches the kernel containing cross-PE waits. put_signal_nbi associates data transfer with remote notification. quiet completes prior operations issued by the calling thread; the receiver uses signal_wait_until to wait for data. Reusing remote storage also requires confirmation that the receiver has finished consuming it, or an iteration protocol. 3.5 UAR and GPU page tables

Both IBGDA and GPUNetIO require GPU access to NIC registers for direct doorbells. Their registration code illustrates the UAR mapping below. NCCL GIN / GDAKI uses the same mechanism through GPUNetIO.

A UAR (User Access Region) exposes NIC registers to an application, including doorbell / BlueFlame registers. For a GPU to ring a doorbell directly, its virtual address must map to that region of the NIC BAR. CPU initialization establishes the mapping; the GPU then issues an MMIO store through the mapped address. UAR interface

Registering the address

mlx5dv_devx_alloc_uar() allocates a UAR. The provider allocates resources and calls mmap through a /dev/infiniband/uverbsN file descriptor. The returned uar->reg_addr is a CPU virtual address for doorbell access in that process. The NVIDIA driver can map the same I/O region into GPU address space. Provider ioctl and mmap

This helper follows the registration steps in NVSHMEM's ibgda_nic_mem_gpu_map(). Pass uar->reg_addr as cpu_reg and the register span as bytes. In the pinned version, the dedicated NC branch uses 8 bytes; the BF branch derives the size from the device's log_bf_reg_size. NVSHMEM registration · UAR type and size

#include <cuda_runtime.h>
#include <cstdint>

// cpu_reg = uar->reg_addr; bytes = this UAR's register span.
cudaError_t map_uar_to_gpu(void* cpu_reg, size_t bytes,
                          uint64_t** gpu_doorbell_ptr) {
    *gpu_doorbell_ptr = nullptr;
    unsigned flags = cudaHostRegisterPortable
                   | cudaHostRegisterMapped
                   | cudaHostRegisterIoMemory;
    cudaError_t rc = cudaHostRegister(cpu_reg, bytes, flags);
    if (rc != cudaSuccess) return rc;

    void* device_alias = nullptr;
    rc = cudaHostGetDevicePointer(&device_alias, cpu_reg, 0);
    if (rc != cudaSuccess) {
        cudaHostUnregister(cpu_reg);
        return rc;
    }
    *gpu_doorbell_ptr = static_cast<uint64_t*>(device_alias);
    return cudaSuccess;
}

Mapped requests a GPU mapping. IoMemory identifies a device I/O region and marks it as non-cache-coherent and physically contiguous; Portable extends registration across CUDA contexts. cudaHostGetDevicePointer() returns the address for GPU access, which can differ numerically from the CPU pointer. The driver handles page mappings internally; bytes describes the registered range. CUDA registration semantics

NVSHMEM stores the GPU pointer in dev_qp->tx_wq.bf and configures the QP with the same UAR's page_id. GPUNetIO's doca_gpu_verbs_export_uar() performs the same registration and pointer lookup for device paths such as GDAKI. Once the GPU and QP have stopped using the UAR, call cudaHostUnregister(cpu_reg) before freeing the UAR. QP UAR configuration · Device pointer assignment · GPUNetIO export

// VER3 encoding example, following Hopper's UVM PTE builder.
// Input: GPU-visible NIC page address, 4 KiB aligned, below 2^52.
uint64_t encode_uar_pte(uint64_t nic_page_addr) {
    constexpr uint64_t address_mask = ((1ULL << 52) - 1) & ~0xfffULL;
    constexpr uint64_t pcf = 0x19;  // REGULAR_RW_NO_ATOMIC_UNCACHED_ACD
    constexpr uint64_t kind = 0x6;  // GENERIC_MEMORY
    return (nic_page_addr & address_mask)  // ADDRESS [51:12]
         | (kind << 8)                   // KIND [11:8]
         | (pcf << 3)                    // PCF [7:3]
         | (3ULL << 1)                   // SYSTEM_NON_COHERENT [2:1]
         | 1ULL;                         // VALID [0]
}

The low 12 bits are 0x6CF = (0x6 << 8) | (0x19 << 3) | (3 << 1) | 1. For a GPU-visible NIC page address of 0x0000800012345000, the encoded PTE is 0x00008000123456CF. A GPU virtual address with page offset 0x20 then targets NIC address 0x0000800012345020. These addresses illustrate the calculation; actual values come from the driver's resource mapping.

From store to PCIe

The GPU submitting thread prepares WQEs, updates the DBR, then writes the UAR. The DBR records queue progress in memory; the UAR doorbell is a device register. This helper isolates a 64-bit doorbell write following GPUNetIO's fence + st.mmio.relaxed submission pattern. It uses fence.acq_rel.sys to provide the required release ordering. %0 is the GPU address, and %1 is a doorbell value already encoded in mlx5 format and byte order. GPUNetIO submission · MMIO store

// Called by the submitting thread after preparing WQEs and the DBR.
// mlx5_db_be: the correctly encoded 64-bit mlx5 doorbell value.
__device__ __forceinline__
void ring_uar(uint64_t* gpu_doorbell_ptr, uint64_t mlx5_db_be) {
    asm volatile("fence.acq_rel.sys;" ::: "memory");
    asm volatile("st.mmio.relaxed.sys.global.b64 [%0], %1;"
                 : : "l"(gpu_doorbell_ptr), "l"(mlx5_db_be)
                 : "memory");
}

fence.acq_rel.sys provides both acquire and release ordering; here, its release semantics publish the submitting thread's prior writes. .mmio specifies device-register access semantics, and .sys selects system scope. This instruction sequence requires a toolchain supporting PTX 8.2 MMIO and an sm_70 or later target. With multiple queue producers, the submitting thread must also use the library's synchronization protocol to establish that their writes are ready. 4.2 Kernel interface

The example has two ranks, each writing one block to its peer. Each rank launches one thread for one round, with signal 0 initially zero. Waiting for the fixed value 1 avoids the race that arises when the wait target is computed as the current signal value plus one and the peer sends early.

#include <nccl_device.h>

// Exactly two ranks; launch <<<1, 1>>> once per rank.
__global__ void exchange_once(ncclDevComm comm, ncclWindow_t srcWin,
                             ncclWindow_t dstWin, size_t bytes) {
    ncclGin gin{comm, 0};
    int peer = 1 - comm.rank;
    gin.put(ncclTeamWorld(comm), peer,
            dstWin, 0, srcWin, 0, bytes,
            ncclGin_SignalInc{0});
    gin.waitSignal(ncclCoopThread{}, 0, 1); // incoming data is ready
    gin.flush(ncclCoopThread{});          // local src can be reused
}

ncclGin_SignalInc associates a remote signal increment with write completion; the receiver waits with acquire semantics. flush makes the local send source safe to reuse. By itself it does not guarantee that data has settled in remote memory.
