CUDA 分层与 Linux 驱动

CUDA 程序把 CPU 上的资源管理与 GPU 上的并行计算连接起来。一次内存分配或 kernel launch，会涉及用户态运行库、驱动建立的地址空间与提交资源，以及 GPU 的执行引擎。Linux 的设备文件和系统调用构成了其中一条可观察的边界。

本文从 CUDA 软件栈的层级展开，定位各组件的公开源码，再用一个计算 40 + 1 + 1 的 H100 程序，将 API 调用、设备文件与驱动入口对应起来。它也是 Inside CUDA 系列的起点：沿着程序的执行路径理解 GPU driver 和 Linux 模块。

1. 基础架构

1.1 执行空间

CUDA 栈横跨三个执行空间：应用进程中的 CPU 用户态代码、Linux 内核中的驱动代码，以及 GPU 上的固件和计算程序。libcuda.so.1 是用户态驱动，仍然运行在 CPU 上；nvidia.ko 是 Linux 内核模块；CUDA 的 __global__ kernel 则由 GPU 执行。“驱动”“内核模块”和“GPU kernel”在这里分别指不同对象。

计算应用可以直接使用 Driver API，也可以通过 Runtime API 或 NCCL、cuBLAS 等库使用 GPU。计算库内部如何组合 Runtime 与 Driver API 取决于实现；图中画出的是主要依赖。监控和显示各有用户态入口，共用部分底层资源管理能力。

1.4 固件与硬件

GSP 是 GPU 上的管理处理器。GSP-RM 固件承接一部分设备初始化和管理工作；主机上的 Kernel RM 通过 RPC 等机制与它协作。CUDA kernel 的计算主体仍由 SM 执行。GPU 的 MMU 完成地址转换，Copy Engine 承担适用的搬运任务，显存控制器连接 HBM 或 GDDR。GSP 说明 · 主机侧 GSP 管理源码

初始化时，CPU 软件为设备建立资源、页表、映射与提交通道；设备执行时，命令处理器、SM、Copy Engine 和互联硬件完成相应工作。UVM 自身也会提交迁移或页表更新所需的 GPU 工作。UVM push 提交代码

图中的绿色虚线表示 GPU 之间的 P2P 数据路径，可经 NVLink 或 PCIe。驱动建立访问所需的映射和权限，设备执行数据传输；具体路径取决于拓扑与平台支持。GPU P2P 显存访问一文介绍 peer 映射与远端显存访问。

2. Linux 接口与实测

内核模块提供驱动实现，设备文件提供用户态访问入口。.ko 加载后运行在内核态；/dev/nvidia* 是字符设备节点，记录 major/minor 设备号及访问权限。一个模块可以提供多个节点：例如 nvidia.ko 同时服务于 /dev/nvidiactl 和各 GPU 的 /dev/nvidia0、nvidia1 等接口。Linux 根据节点的设备号找到已注册的字符设备及其操作表。Linux VFS

本文版本的 nvidia.ko 在初始化时调用 nv_register_chrdev()：先用 register_chrdev_region() 注册设备号范围，再通过 cdev_init() 关联 nvidia_fops，最后用 cdev_add() 将字符设备加入内核。GPU 接口与控制接口分别注册，共用这张操作表。nvidia-uvm.ko 则通过 alloc_chrdev_region() 动态分配设备号，并注册关联 uvm_fops 的字符设备。核心驱动注册函数 · 初始化调用点 · UVM 注册

内核中的注册与 /dev 中的节点创建是两个步骤。节点可由发行版的设备管理机制或 NVIDIA 工具按对应设备号创建、设置权限；NVIDIA 用户态驱动在需要时也可调用 nvidia-modprobe 加载模块并创建节点。cdev_add() 本身不创建 /dev/nvidia0 这个路径；节点存在也不保证对应驱动已成功加载。NVIDIA 设备节点创建机制

2.2 open、ioctl 与 mmap

nvidia_fops 和 uvm_fops 都是 Linux 内核 struct file_operations 类型的结构体实例。这个类型定义在 include/linux/fs.h 中，.open、.unlocked_ioctl、.mmap 等成员是函数指针。Linux 定义操作接口，驱动填入自己的回调函数；例如 nvidia_fops 的 .open 指向 nvidia_open。Linux 类型定义 · nvidia_fops · uvm_fops

/dev/nvidiactl 和 /dev/nvidia0 等核心驱动设备使用 nvidia_fops，/dev/nvidia-uvm 使用 uvm_fops。设备打开后，对应的内核 struct file 对象通过 f_op 指向这张操作表。进程持有的 fd 是文件描述符表中的索引；后续系统调用通过 fd 找到该对象，再调用操作表中的回调。因此，相同的文件操作接口可以进入不同驱动的实现。Linux VFS 的文件对象与操作表

接口Linux 与驱动如何协作
open / openat按路径定位设备，进入驱动的 open 回调，建立每次打开所需的状态；成功后返回 fd。用户代码中的 open 也可能在日志中表现为 openat。
ioctl(fd, request, arg)将命令号和参数交给驱动。驱动检查命令、复制或验证用户态参数，再进入 RM / UVM 命令处理。
mmap(..., fd, offset)通过驱动的 mmap 回调，在进程 CPU 虚拟地址空间建立获准的映射；可能涉及驱动管理的内存或设备资源。

ioctl 的第三个参数常常是 CPU 用户态结构体的地址，里面还可以包含对象 handle、标志和其他参数。mmap 返回的是 CPU 虚拟地址；cudaMalloc 返回的 GPU 可用地址及其物理显存分配，不能直接按某一条 Linux mmap 的长度与返回值解释。NVIDIA ioctl 参数处理 · 设备 mmap 实现

2.3 Hello CUDA

程序在 GPU 上对一个整数执行两次加一，然后将结果复制回 CPU。每个阶段的 BEGIN / END 都是主机写入 stderr 的标记，用来界定 syscall 日志中的区间。

hello.cu cuda.ltrace.conf trace.sh 实测摘录 JSON

#include <cuda_runtime.h>
#include <cstdio>
#include <cstdlib>

static void check(cudaError_t status, const char* call) {
    if (status != cudaSuccess) {
        std::fprintf(stderr, "FAIL %s: %s\n", call, cudaGetErrorString(status));
        std::exit(1);
    }
}

// Markers are host writes, useful for locating each phase in strace output.
#define CALL(expr) do { \
    std::fprintf(stderr, "BEGIN %s\n", #expr); \
    check((expr), #expr); \
    std::fprintf(stderr, "END %s\n", #expr); \
} while (0)

__global__ void hello(int* result) {
    *result += 1;
}

int main() {
    std::setvbuf(stderr, nullptr, _IONBF, 0);
    CALL(cudaSetDevice(0));
    int* device = nullptr;
    int host = 40;
    CALL(cudaMalloc(&device, sizeof(int)));
    CALL(cudaMemcpy(device, &host, sizeof(int), cudaMemcpyHostToDevice));
    for (int launch = 1; launch <= 2; ++launch) {
        std::fprintf(stderr, "BEGIN kernel launch %d\n", launch);
        hello<<<1, 1>>>(device);
        check(cudaGetLastError(), "hello launch");
        std::fprintf(stderr, "END kernel launch %d\n", launch);
        CALL(cudaDeviceSynchronize());
    }
    CALL(cudaMemcpy(&host, device, sizeof(int), cudaMemcpyDeviceToHost));
    CALL(cudaFree(device));
    std::printf("Hello from CUDA: %d (expected 42)\n", host);
    return host == 42 ? 0 : 1;
}
# Run in the directory containing the three downloaded files.
# CUDA 12.4 + H100; use your GPU's supported target if different.
nvcc -std=c++17 -O0 -lineinfo -arch=sm_90 --cudart shared \
  hello.cu -o hello
ldd ./hello
./hello
# Hello from CUDA: 42 (expected 42)

-arch=sm_90 对应本次 H100，其他 GPU 需要选择其支持的架构。--cudart shared 让 Runtime 调用保留可跟踪的动态链接边界。若动态加载器找不到 libcudart.so.12，应配置所用 Toolkit 的库路径；下载的 trace.sh 会在编译时加入该路径。

ldd 用于检查程序的动态链接依赖。运行时才加载的库不一定出现在其中；本例的 libcuda.so.1 加载过程会在后面的 strace 中出现。

2.4 采集调用

ltrace 观察动态库函数调用，strace 观察进程进入 Linux 内核的系统调用。下面分别运行两次程序，避免两个 ptrace 工具争用同一个目标。两份日志的地址与时间戳属于各自运行，不能按时间直接拼成一棵调用树。

# Separate runs: API-call capture and full syscall capture
strace -f -ttt -T -yy -s 160 -o syscalls.txt ./hello \
  >hello.stdout.txt 2>hello.stderr.txt
ltrace -F ./cuda.ltrace.conf -f -tt -e 'cuda*' \
  -o api.txt ./hello >api.stdout.txt 2>api.stderr.txt

# Filter after capture, preserving the complete original log
grep -nE '/dev/nvidia|BEGIN |END |ioctl\(|mmap\(' syscalls.txt
grep 'cuda' api.txt

strace -f 包含创建的线程和子进程；-ttt 输出绝对时间，-T 记录 syscall 耗时，-yy 展开 fd 对应的路径及设备信息。这里先采集完整 syscall，再筛选阅读，才能检查某个区间是否真的没有系统调用。ptrace 会扰动执行耗时，这些数据用于分析路径。strace

CUDA layers and the Linux driver

A CUDA program connects resource management on the CPU with parallel execution on the GPU. Allocating memory or launching a kernel involves user-space libraries, driver-established address spaces and submission resources, and GPU execution engines. Linux device files and system calls expose one observable boundary in that path.

This first article in Inside CUDA maps the software layers to public source, then traces an H100 program that computes 40 + 1 + 1. The example connects CUDA API calls, device files and Linux driver entry points.

1. Architecture

1.1 Execution spaces

The stack spans CPU user space, the Linux kernel, and firmware and compute programs running on the GPU. libcuda.so.1 is a user-mode driver executing on the CPU. nvidia.ko is a Linux kernel module. A CUDA __global__ kernel executes on the GPU. Each use of “driver” or “kernel” refers to a specific execution environment.

Applications may use the Driver API directly, the Runtime API, or libraries such as NCCL and cuBLAS. The exact combination of Runtime and Driver APIs inside a library is implementation-dependent; the diagram shows principal dependencies. Monitoring and display have separate entry points and share some underlying resource-management services.

2. Linux interfaces and tracing

Kernel modules implement drivers; device files expose interfaces to user space. A loaded .ko runs in kernel space. A /dev/nvidia* character-device node records major/minor device numbers and access permissions. One module can serve several nodes: nvidia.ko handles both /dev/nvidiactl and per-GPU interfaces such as /dev/nvidia0 and nvidia1. Linux uses a node's device numbers to locate the registered character device and its operations table. Linux VFS

In the pinned driver, initialization calls nv_register_chrdev(): register_chrdev_region() reserves device numbers, cdev_init() associates the character device with nvidia_fops, and cdev_add() adds it to the kernel. GPU and control interfaces are registered separately with the same operations table. nvidia-uvm.ko uses alloc_chrdev_region() to allocate device numbers dynamically, then registers a character device associated with uvm_fops. Core registration · Initialization calls · UVM registration

Kernel registration and node creation in /dev are separate steps. Distribution device-management mechanisms or NVIDIA tools create nodes with the corresponding device numbers and permissions. NVIDIA user-space drivers can also invoke nvidia-modprobe to load modules and create nodes when needed. cdev_add() does not itself create the path /dev/nvidia0; an existing node does not establish that the driver loaded successfully. 2.2 open, ioctl and mmap

nvidia_fops and uvm_fops are both instances of the Linux kernel's struct file_operations. Defined in include/linux/fs.h, this type contains function pointers such as .open, .unlocked_ioctl and .mmap. Linux defines the operation interface; each driver supplies its callbacks. For example, nvidia_fops.open points to nvidia_open. Linux type definition · nvidia_fops · uvm_fops

Core-driver devices such as /dev/nvidiactl and /dev/nvidia0 use nvidia_fops; /dev/nvidia-uvm uses uvm_fops. After a device is opened, the kernel's struct file object points to its operations table through f_op. The process holds an fd, an index into its file-descriptor table. Subsequent syscalls use that fd to find the file object and invoke the appropriate callback. The same file-operation interface can therefore reach different driver implementations. Linux VFS file objects and operations

InterfaceLinux / driver interaction
open / openatLocate the node, invoke the driver's open callback, initialize per-open state and return an fd. A library open call may appear as openat in a syscall trace.
ioctl(fd, request, arg)Pass a request and arguments to the driver, which validates or copies parameters and dispatches an RM / UVM command.
mmap(..., fd, offset)Use the driver's mmap callback to establish an allowed CPU virtual mapping of driver-managed memory or device resources.

An ioctl argument is often the CPU address of a parameter structure containing handles, flags and additional arguments. mmap returns a CPU virtual address. A cudaMalloc result and its physical GPU allocation cannot be inferred from the size and result of one Linux mmap call. NVIDIA ioctl argument handling · Device mmap implementation

static void check(cudaError_t status, const char* call) {
    if (status != cudaSuccess) {
        std::fprintf(stderr, "FAIL %s: %s\n", call, cudaGetErrorString(status));
        std::exit(1);

// Markers are host writes, useful for locating each phase in strace output.
#define CALL(expr) do { \
    std::fprintf(stderr, "BEGIN %s\n", #expr); \
    check((expr), #expr); \
    std::fprintf(stderr, "END %s\n", #expr); \
} while (0)

__global__ void hello(int* result) {
    *result += 1;
}

int main() {
    std::setvbuf(stderr, nullptr, _IONBF, 0);
    CALL(cudaSetDevice(0));
    int* device = nullptr;
    int host = 40;
    CALL(cudaMalloc(&device, sizeof(int)));
    CALL(cudaMemcpy(device, &host, sizeof(int), cudaMemcpyHostToDevice));
    for (int launch = 1; launch <= 2; ++launch) {
        std::fprintf(stderr, "BEGIN kernel launch %d\n", launch);
        hello<<<1, 1>>>(device);
        check(cudaGetLastError(), "hello launch");
        std::fprintf(stderr, "END kernel launch %d\n", launch);
        CALL(cudaDeviceSynchronize());
    }
    CALL(cudaMemcpy(&host, device, sizeof(int), cudaMemcpyDeviceToHost));
    CALL(cudaFree(device));
    std::printf("Hello from CUDA: %d (expected 42)\n", host);
    return host == 42 ? 0 : 1;
}

Neither launch interval nor either cudaDeviceSynchronize interval contains a new syscall. GPU work still completes and the program returns 42. In this execution, submission and completion waiting required no new Linux entry within these main-thread intervals.

A driver can establish mappings and submission resources during initialization, then use them to submit work and observe completion. The trace is consistent with that explanation, but does not record user-space memory writes, queue formats or a doorbell protocol. Absence of a syscall also does not identify the exact polling or completion mechanism.

The counts describe one execution. Driver version, first module loading, memory pools, stream state and workload can change the path. Four ioctls are not a cudaMalloc contract. A launch with no new syscall still relies on prior driver setup.

The example establishes two checkable paths: cudaMalloc through RM / UVM ioctls to public command definitions, and kernel launches to a computed GPU result. The first crosses the Linux syscall boundary. The second, after initialization, needs no new main-thread syscall in this capture. Distinguishing those paths makes the driver's role easier to locate.
