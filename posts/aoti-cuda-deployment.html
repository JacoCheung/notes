PyTorch AOTInductor 的 CUDA C++ 部署与运行时机制

PyTorch 模型从开发环境进入 C++ 服务时，编译时工作、模型资产和运行时依赖必须重新划分。AOTInductor 把模型捕获、Inductor lowering、GPU kernel 生成和打包放到离线阶段，再由 C++ loader 装载产物并执行。这个边界决定了 .pt2 的内容、运行进程所需的 libtorch 组件，以及 custom op 在编译期和运行期必须分别提供的契约。

本文的 API、文件路径与运行时调用链按公开的 PyTorch v2.12.0 源码和 2.12 AOTInductor 文档核对。torch._inductor、.pt2 包内容和生成符号都可能随版本或编译配置变化;文中的伪代码与流程图是源码阅读模型,不是稳定 ABI 或固定文件清单。

1. AOTI 的部署边界

AOTI 面向具有以下约束的部署环境：

  • C++ 运行进程：推理服务、模拟器或嵌入式环境以 C++ binary 作为入口，并希望从运行路径中移除 CPython。
  • 离线编译：torch.compile 首次执行涉及 Dynamo 捕获、Inductor codegen 与 GPU binary 编译；部署构建需要提前承担这部分成本。
  • 保留 PyTorch 编译语义：PyTorch 2.12 文档已将 TorchScript 标记为 deprecated，ONNX 也要求导出端与运行端共同支持相同的算子语义。AOTI 延续 torch.export 与 Inductor 的编译路径。

AOTInductor（AOTI） 是把 ExportedProgram 编译为 PT2 archive，并由 libtorch C++ loader 执行该 archive 的部署路径。在本文固定的 PyTorch 2.12 版本中，这条路径分为：

  • Python 构建端把 torch.export 得到的图交给 Inductor，完成目标配置所需的 codegen、编译与打包。
  • 构建产物是 .pt2 archive。具体成员随配置变化，可包含模型库、C++/object 产物、Triton cubin、权重、常量和 ProxyExecutor 元数据。
  • C++ 端链接与构建端版本匹配的 libtorch，并用 torch::inductor::AOTIModelPackageLoader 加载 archive。官方示例通过 ${TORCH_LIBRARIES} 链接，执行路径不依赖 Python interpreter 或 libtorch_python。

2. 端到端流程

图中的上半部分在 Python 构建环境完成模型捕获、lowering、编译与 archive 打包，下半部分则由 C++ 运行进程加载同一份 archive 并调用模型入口。一份同时包含 native op、可融合 pointwise op 和 custom op 的例子模型沿这条路径依次经过 export、Inductor lowering、Triton codegen、.pt2 打包和 C++ 加载，由此显露五个阶段各自处理的对象。

3. 例子模型

下面的模型同时包含 native op、可融合 pointwise op 和 custom op，三类节点会在后续 lowering 中进入不同路径：

# model.py
import torch
from torch import nn

# --- 1) 注册一个 custom op ---
# 语义: y = x * scale + bias_per_channel
# 用 PyTorch 2.12 的 torch.library.custom_op 注册
@torch.library.custom_op("mylib::scale_add", mutates_args=())
def scale_add(x: torch.Tensor, scale: float, bias: torch.Tensor) -> torch.Tensor:
    return x * scale + bias

# Inductor / FakeTensor 用的 meta 实现 (shape / dtype 推导)
@scale_add.register_fake
def _(x, scale, bias):
    return torch.empty_like(x)

# --- 2) 一个用到 native + custom op 的 Module ---
class ToyModel(nn.Module):
    def __init__(self):
        super().__init__()
        self.fc1 = nn.Linear(128, 256)        # native: aten::linear / aten::mm
        self.fc2 = nn.Linear(256, 64)
        self.bias = nn.Parameter(torch.randn(64))

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        h = self.fc1(x)                       # native GEMM
        h = torch.nn.functional.gelu(h)       # native, fusible elementwise
        h = self.fc2(h)                       # native
        h = torch.ops.mylib.scale_add(h, 2.0, self.bias)  # custom op
        return h.relu()                       # native pointwise op

model = ToyModel().eval().cuda()
example_inputs = (torch.randn(4, 128, device="cuda"),)

每组算子承担一个观察点：

  • nn.Linear 会落到 aten::linear / aten::mm 等矩阵乘路径。常规 CUDA 配置通常调用外部 GEMM 库；具体 backend 与生成代码取决于版本、shape 和编译配置，应以生成源码为准
  • F.gelu 与 .relu() 都可进入 Inductor 的 pointwise lowering；中间的 scale_add 是 opaque custom op，默认会阻断跨 op 融合
  • scale_add 以 operator schema 进入 FX graph，用来追踪 AOTI 对用户自定义算子的编译和运行时契约。

4. 阶段 1:torch.export

4.1 API 用法

# export.py
import torch
from torch.export import export, Dim
from model import ToyModel, scale_add, example_inputs

model = ToyModel().eval().cuda()

# dynamic batch 维度声明(可选;不写就是固定 shape)
batch = Dim("batch", min=1, max=64)
dynamic_shapes = {"x": {0: batch}}

ep = export(model, example_inputs, dynamic_shapes=dynamic_shapes)
# ep: ExportedProgram

print(ep.graph_module.code)         # 可读的 FX graph 源
print(ep.graph_signature)            # inputs/outputs 的 schema

ep.graph_module.code 会打印类似:

def forward(self, p_fc1_weight, p_fc1_bias, p_fc2_weight, p_fc2_bias, p_bias, x):
    linear = torch.ops.aten.linear.default(x, p_fc1_weight, p_fc1_bias)
    gelu = torch.ops.aten.gelu.default(linear)
    linear_1 = torch.ops.aten.linear.default(gelu, p_fc2_weight, p_fc2_bias)
    scale_add = torch.ops.mylib.scale_add.default(linear_1, 2.0, p_bias)
    relu = torch.ops.aten.relu.default(scale_add)
    return (relu,)

这份 exported graph 建立了三个后续条件：

  • 算子以 torch.ops.{namespace}.{op}.{overload} 形式出现在图中，Python 控制流已按 export 语义转换或约束。
  • 权重被提升为 graph input（如 p_fc1_weight），并通过 ep.state_dict / ep.constants 关联到原 Parameter。
  • Custom op mylib::scale_add 与 ATen op 处在同一 FX graph 中，Inductor 因而能够把它识别为一个 operator node。

4.2 内部流程

torch.export 内部分四步:

  1. Dynamo trace:用 TorchDynamo 的 frame-eval hook 拦截 Python 字节码执行,把所有 torch.* 调用记录成 FX node。 用户代码里的 if / for 在 trace 时被具体 input shape 选定一条路径(symbolic shape 的情况下走 torch._dynamo.guards 注册条件守卫)。
  2. FakeTensor propagation:每个 FX node 用 FakeTensor 推一遍,确定输出 shape / dtype。 custom op 在这一步必须有 register_fake 注册的 meta 实现,否则 export 会失败。
  3. Decomposition:某些"复合"算子(aten::linear 在某些 dispatch 下会拆成 aten::mm + aten::add)被分解。 export 默认走 core ATen decomposition table,可以通过参数控制是否分解到更底层。
  4. Graph signature 抽取:把 graph 的输入分类为(user inputs / parameters / buffers / tokens),输出分类为(user outputs / mutated buffers),形成 ExportSignature。

这些步骤对应以下 PyTorch 源码:

路径角色
torch/export/__init__.py公开 API 入口
torch/export/_trace.pytrace 主流程
torch/_dynamo/eval_frame.pyDynamo Python 端
torch/csrc/dynamo/eval_frame.cframe eval C hook(编进 libtorch_python.so)
torch/_subclasses/fake_tensor.pyFakeTensor propagation
torch/_decomp/__init__.pydecomposition table
torch/export/exported_program.pyExportedProgram 数据结构

结合《PyTorch Linux 共享库的构建与加载关系》来看，export 阶段会使用 libtorch_python.so 中的 Python/C++ 桥，而 dispatcher 与 ATen core 位于 libtorch core 侧；具体 ELF 依赖仍以安装产物为准。

5. 阶段 2:Inductor lowering

5.1 API 用法

将 ExportedProgram 编译并打包为 .pt2 的最小调用如下：

import torch._inductor

package_path = torch._inductor.aoti_compile_and_package(
    ep,                                  # 上一步的 ExportedProgram
    package_path="model.pt2",         # 输出文件
    inductor_configs={
        "max_autotune": True,         # 在编译时枚举 Triton config 选最快
        "aot_inductor.embed_kernel_binary": True,
            # 把 cubin 直接嵌进 .so 而不是单独存放(单文件部署更方便)
    },
)
# package_path == "model.pt2"

这一调用完成三项工作：

  1. 将 ExportedProgram 的 FX graph 交给 Inductor compiler frontend。
  2. Inductor 将图 lower 为 ATen 调用、生成的 Triton kernel 以及对应的 C++ glue code。
  3. 系统工具链生成 .so，AOTI 再将其与 cubin、权重和元数据共同打包为 .pt2。

5.2 Inductor 内部:Native op vs Custom op vs Fused kernel

Inductor 把每个 FX node 按下面三条路径之一处理:

类型例子Inductor 做什么调用方式
Native heavyweight aten::linear, aten::matmul, aten::conv2d 通常 lower 到外部 ATen/库调用或对应 AOTI shim;具体形式由算子和配置决定 生成的外部调用或 aoti_torch_* shim;应以生成源码为准
Fusible elementwise / reduction aten::gelu, aten::relu, pointwise add / mul 合并相邻的 elementwise + 部分 reduction 进一个 Triton kernel C++ 里 triton_kernel_fused_(...) → cuLaunchKernel(cubin)
Custom op mylib::scale_add 默认保持 opaque;AOT 模式下可由 ProxyExecutor 调已注册的 dispatcher 实现,也可提供 decomposition/lowering aoti_torch_proxy_executor_call_function(...) 或显式 lowering

对应本例,Inductor 把 graph lower 成下面形态的伪 C++:

// AOTI 生成代码的逻辑示意;类名和 helper 名不是稳定接口
AOTIRuntimeError AOTInductorModel::_run_impl(
    AtenTensorHandle* input_handles,
    AtenTensorHandle* output_handles,
    AOTIProxyExecutorHandle proxy_executor, ...)
{
    // 1) aten::linear → 生成的外部调用,通常最终使用 cuBLAS
    auto buf0 = generated_linear_call(x, fc1_weight, fc1_bias);

    // 2) Inductor fused triton kernel: gelu + linear_1 是分开两次调用
    //    因为 linear_1 又是 cuBLAS,夹在两个 elementwise 之间。
    auto buf1 = empty_strided_cuda({4, 256}, ...);
    triton_poi_fused_gelu_0(buf0, buf1, ...);     // elementwise gelu

    auto buf2 = generated_linear_call(buf1, fc2_weight, fc2_bias);

    // 3) 默认 custom op 是 opaque 调用;只有显式 decomposition / lowering / triton_op 才能进入融合
    aoti_torch_proxy_executor_call_function(proxy_executor, op_index, ...);

    // 4) relu 仍可作为普通 aten pointwise 被 lowering 成 Triton kernel
    auto buf4 = empty_strided_cuda({4, 64}, ...);
    triton_poi_fused_relu_1(buf3, buf4, ...);

    output_handles[0] = buf4;
    return AOTI_SUCCESS;
}

这段生成代码是便于阅读的逻辑模型。PyTorch v2.12.0 的 codegen为 AOT mode fallback 生成 ProxyExecutor 路径；同文件中的 aoti_torch_call_dispatcher 服务于 non-AOT 的 StableIValue 兼容路径。

torch.library.custom_op 注册的是 compiler-visible、语义 opaque 的 operator node。register_fake 为 torch.export 和 FakeTensor propagation 提供输出 shape、dtype 与 device；decomposition、lowering rule 或 torch.library.triton_op 这类 compiler-visible wrapper 则负责向 Inductor 暴露可融合语义。只有后一类集成才能把 scale_add 与后续 relu 合入同一 Triton kernel（详见第九节）。

文件 / 模块做什么

这一阶段由 Python 驱动，但生成的 C++ 源仍需系统编译器构建为共享库；默认临时目录通常位于 /tmp/torchinductor_$USER/。最终 ELF 的 DT_NEEDED 取决于 PyTorch 构建方式、目标设备和链接参数，不能预先固定为某三项库；应检查实际编译命令或对产物运行 readelf -d。

6. 阶段 3:Triton codegen + cubin

Inductor 为某组节点选择 Triton codegen 后，Python 到 cubin 的编译由外部 triton 包完成。PyTorch 共享库中的 Python 桥与 runtime 分工可参见《PyTorch Linux 共享库的构建与加载关系》。生成路径依次为：

  1. Inductor 把生成的 Triton kernel 源(Python 文本)写到 /tmp/torchinductor_$USER/<hash>/triton_poi_fused_scale_add_relu_1.py 之类的位置
  2. 调 triton.jit 触发 Triton compiler:Python AST → Triton IR → MLIR → PTX → cubin
  3. Triton 与 Inductor 会缓存编译中间产物；缓存根目录可由环境和配置改变，不能把某个本机目录视为包格式的一部分
  4. GPU binary 可以按编译配置嵌入模型库或作为配套文件进入 PT2 archive；具体成员和路径不是稳定 ABI

生成的典型 Triton kernel 形如:

# /tmp/torchinductor_user/abcd/triton_poi_fused_scale_add_relu_1.py
import triton
import triton.language as tl

@triton.jit
def triton_poi_fused_scale_add_relu_1(
    in_ptr0,        # buf2: 上游 linear_1 输出, [4, 64]
    in_ptr1,        # bias: [64]
    out_ptr0,       # buf3: [4, 64]
    xnumel,         # 总 element 数 = 256
    XBLOCK: tl.constexpr):
    xoffset = tl.program_id(0) * XBLOCK
    xindex = xoffset + tl.arange(0, XBLOCK)[:]
    xmask = xindex < xnumel
    x0 = xindex % 64                        # bias 的 broadcast 索引
    tmp0 = tl.load(in_ptr0 + xindex, xmask)
    tmp1 = tl.load(in_ptr1 + x0, xmask)     # 加载 bias
    tmp2 = tmp0 * 2.0                       # scale_add 的 scale 部分
    tmp3 = tmp2 + tmp1                      # scale_add 的 add 部分
    tmp4 = tl.maximum(tmp3, 0.0)            # relu
    tl.store(out_ptr0 + xindex, tmp4, xmask)

当 decomposition、lowering rule 或 torch.library.triton_op 向 compiler 暴露 scale_add 的内部表达时，* scale + bias 与后续 relu 可以形成上面的 fused kernel，并合并为一次 load → compute → store。register_fake 仍只承担抽象执行和元数据推断。

在常见默认配置中可以观察到类似的缓存路径，但它们只用于诊断，不属于部署接口:

~/.triton/cache/<hash>/triton_poi_fused_scale_add_relu_1.cubin   # Triton 自己缓存
~/.cache/torch/inductor/<hash>/triton_poi_fused_scale_add_relu_1.{py,cubin,json}
                                                                # Inductor 缓存 + metadata

配套 metadata 可记录 num_warps、num_stages、shared-memory 大小与 grid 计算等 launch 信息。其承载位置与 runtime 调用形式均属于版本相关实现。

7. 阶段 4:打包成 .pt2

.pt2 是 zip 容器。以下只展示 PyTorch v2.12.0 打包器使用的逻辑目录;生成文件名和是否携带源码、对象文件或独立 GPU binary 由编译配置决定:

data/aotinductor/model/<generated-files>
data/aotinductor/model/<model>.so
data/aotinductor/model/weights_config.json   # 使用独立权重时
data/weights/<weight-files>
data/constants/<constant-files>
archive_format
archive_version

Triton codegen 涉及以下文件:

文件内容
data/aotinductor/<model>/AOTI 生成文件;打包器可接收 .so、.cpp、对象文件及配套 JSON
data/weights/按打包策略保存或去重后的模型权重
data/constants/tensor constants 与 custom objects 等 payload
archive_format / archive_versionPT2 archive 格式标识

打包代码位于 torch/_inductor/package/，核心入口是 torch._inductor.package.package_aoti。AOTI package 与 torch.export.save 都使用 PT2 archive 规范，但 payload 目录和必需成员不同：前者保存编译产物及相关模型资产，后者保存 exported program。两者不应按同一份内部文件清单解析。

8. 阶段 5:C++ runtime 加载

8.1 C++ loader 示例

// runner.cpp
#include <torch/torch.h>
#include <torch/csrc/inductor/aoti_package/model_package_loader.h>

#include <iostream>
#include <vector>

int main(int argc, char** argv) {
    if (argc < 2) {
        std::cerr << "usage: " << argv[0] << " model.pt2\n";
        return 1;
    }

    // 1) 加载 .pt2
    torch::inductor::AOTIModelPackageLoader loader(argv[1]);

    // 2) 准备输入(跟 export 时的 example_inputs shape/dtype 一致)
    auto device = torch::Device(torch::kCUDA, 0);
    auto x = torch::randn({4, 128}, torch::TensorOptions().device(device));
    std::vector<torch::Tensor> inputs = {x};

    // 3) 执行
    auto outputs = loader.run(inputs);

    // 4) 拿结果
    torch::Tensor y = outputs[0];      // CUDA tensor
    std::cout << "output shape: " << y.sizes() << "\n";
    std::cout << "output mean: "  << y.mean().item<float>() << "\n";
    return 0;
}

8.2 编译命令

# 假设你装了 PyTorch wheel(libtorch + headers 都齐了)
TORCH_DIR=$(python -c "import torch, os; print(os.path.dirname(torch.__file__))")

g++ -std=c++17 -O3 \
    -I$TORCH_DIR/include \
    -I$TORCH_DIR/include/torch/csrc/api/include \
    -L$TORCH_DIR/lib \
    -Wl,-rpath,$TORCH_DIR/lib \
    runner.cpp -o runner \
    -ltorch -ltorch_cpu -ltorch_cuda -lc10 -lc10_cuda

./runner model.pt2

这段命令是 Linux CUDA 构建示意。官方教程更推荐通过 CMake 的 ${TORCH_LIBRARIES} 使用匹配版本的 libtorch。PyTorch v2.12.0 将 package loader 和通用 runner 列入 inductor_core_resources,不需要为它链接 libtorch_python。

8.3 Package 加载序列

按 model_package_loader.cpp,构造过程可以概括为:

  1. 读取 archive 目录,把目标模型目录及相关 constants 解压到临时目录
  2. 若包内已有 .so 就直接使用;否则可根据包内 .cpp、对象文件与 compile options 生成 .so
  3. 读取 AOTI metadata 中的 device key,从 runner registry 选择对应 device runner
  4. 把模型 .so、runner 数量、device 与生成文件目录交给 runner;若存在 weight blob,再更新 constant buffer

loader.run(inputs) 的步骤:

  1. 把输入 at::Tensor 转成 AtenTensorHandle 数组
  2. 调用模型容器导出的 AOTInductorModelContainerRun(或 single-threaded 变体),同时传入 stream 与可选 ProxyExecutor
  3. 把返回的 tensor handles 转回 at::Tensor

model_container_runner.cpp 通过 AOTInductorModelContainerCreateWithDevice、AOTInductorModelContainerRun 等导出符号进入 model-container C ABI。Triton/CUDA kernel 的装载和启动由生成产物及对应 runner 完成，因此具体形式取决于编译配置。

包加载链对应以下公开源码;共享库归属可结合《PyTorch Linux 共享库的构建与加载关系》核对:

路径角色
torch/csrc/inductor/aoti_package/model_package_loader.cppAOTIModelPackageLoader 实现;属于 core resources
torch/csrc/inductor/aoti_runner/model_container_runner.cpp加载模型库并解析 model-container C ABI
torch/csrc/inductor/aoti_runner/model_container_runner_cuda.cppCUDA 特化 runner(在 libtorch_cuda.so)
torch/csrc/inductor/aoti_torch/shim_common.cppC-ABI shim 的 host-side 实现
torch/csrc/inductor/aoti_torch/shim_cuda.cppCUDA 版 shim(在 libtorch_cuda.so)

把这些文件连起来，运行时路径是：libtorch core 中的 package loader 解包并选择 runner，通用 runner 动态加载模型 .so 并调用 model-container C ABI，CUDA runner 与生成模型再使用相应 CUDA runtime 和 shim。最终 ELF 边界与 kernel launch 形式由构建配置和生成产物共同决定。

9. Custom op 的处理细节

Custom op 需要同时满足图捕获、编译 lowering 和运行时实现三类契约。示例中的 scale_add 已通过 fake impl 满足 export 与 shape 推断，后续集成则根据是否保留 external call、是否向 Inductor 暴露语义，以及运行进程是否包含 Python 分为三种路径。

9.1 策略 A:让 Inductor 把它当 fallback(默认)

默认 fallback 把 mylib::scale_add 保留为 external operator call：

  • Inductor 在 AOT 模式下生成 external fallback，并把调用描述写入 .pt2，供 ProxyExecutor 使用。
  • 运行时由 ProxyExecutor 查找已注册的 operator 实现；固定版本的 archive spec 将调用描述保存为可选 JSON。
  • 该节点维持 opaque 边界，因此相邻 Triton pointwise kernel 在它的两侧分别生成。

本例的 eager 实现仍是 Python 函数，无 Python 的 C++ runtime 不能执行它。部署时有两种选择：

  • 把 op 用 C++ 重写并通过 TORCH_LIBRARY_IMPL 注册给对应 DispatchKey,然后让 C++ runner 链接你的实现 .so
  • 在有 Python 的加载路径中注册 Python/CUDA 实现；这不会自动让同一实现出现在无 Python 的 C++ 进程中

9.2 策略 B：注册版本相关的 Inductor lowering

from torch._inductor import lowering

@lowering.register_lowering(torch.ops.mylib.scale_add)
def _scale_add_lowering(x, scale, bias):
    # 用 Inductor 的内部 IR 表达式拼出来,会被自动 fuse 进相邻 elementwise
    return lowering.add(lowering.mul(x, scale), bias)

显式 lowering 可以让当前 Inductor 版本把 scale_add 表达为内部原语，并与相邻 elementwise 进行 fusion。torch._inductor.lowering 是内部接口，注册代码必须跟随所用 PyTorch 版本维护；register_fake 只负责抽象执行与元数据推断。

9.3 策略 C：为 Python 运行路径注册 Triton 实现

下面的 register_kernel("cuda") 让 custom op 在 Python 进程中调用 Triton kernel：

import triton
import triton.language as tl

@triton.jit
def _scale_add_triton_kernel(x_ptr, bias_ptr, out_ptr, scale, n_elements, BLOCK: tl.constexpr):
    pid = tl.program_id(0)
    offsets = pid * BLOCK + tl.arange(0, BLOCK)
    mask = offsets < n_elements
    x = tl.load(x_ptr + offsets, mask)
    b = tl.load(bias_ptr + offsets % bias_dim, mask)
    tl.store(out_ptr + offsets, x * scale + b, mask)

@scale_add.register_kernel("cuda")
def _(x, scale, bias):
    out = torch.empty_like(x)
    n = x.numel()
    grid = (triton.cdiv(n, 1024),)
    _scale_add_triton_kernel[grid](x, bias, out, scale, n, BLOCK=1024)
    return out

这项注册提供运行时实现，但不会自动把 custom op 的内部 Triton 调用暴露给 Inductor，也不足以支持无 Python 的 C++ runtime。需要 compiler-visible tracing 时应使用该版本公开的 torch.library.triton_op 方案；需要纯 C++ AOTI fallback 时仍要提供可在 C++ 进程加载的实现。

9.4 仅暴露 pybind 的第三方 op 接入路径

若第三方 CUDA 入口只暴露为普通 pybind 函数，没有注册 operator schema、fake 实现和 C++ backend，PyTorch 编译栈就缺少稳定的组合契约。Dynamo 对具体函数的处理可能是 graph break、拒绝导出或依赖额外规则，不能把任意 pybind 调用视为可直接部署的 op。

第一步:Python 端用 custom_op 把 pybind 函数包成 op

import torch
import third_party_lib   # 只有 pybind binding 的第三方库

@torch.library.custom_op("mylib::fa_fwd", mutates_args=())
def fa_fwd(q: torch.Tensor, k: torch.Tensor, v: torch.Tensor,
           softmax_scale: float) -> torch.Tensor:
    # 内部直接调 pybind,语义对 PyTorch 是 opaque
    return third_party_lib.flash_attn_forward(q, k, v, softmax_scale)

@fa_fwd.register_fake
def _(q, k, v, softmax_scale):
    # Meta 推断:只产生 empty tensor,不实际算
    return torch.empty_like(q)

这一步让 Dynamo / export 在 FX graph 中看到 torch.ops.mylib.fa_fwd。PyTorch v2.12.0 的 AOT fallback 通过 ProxyExecutor 描述该 external call；对应 JSON 会按 PT2 archive 规范写入包中。

Python 包装本身不会进入无 Python 的部署进程，因此仍要提供并加载 C++/CUDA operator 实现。

第二步:用 TORCH_LIBRARY 写一个 C++ shim,链进 runner

第三方库一般自带 C++ 入口(pybind 只是它的薄包装)。 写一个独立的 shim .so 注册同名 op,在 C++ runtime 启动时 dlopen 它:

// my_third_party_shim.cpp,编成 libfa_shim.so
#include <torch/library.h>

// 第三方库的真实 C++ 入口(头文件或 dlsym 拿到)
extern at::Tensor third_party_flash_attn_forward(
    const at::Tensor& q, const at::Tensor& k, const at::Tensor& v,
    double softmax_scale);

at::Tensor fa_fwd_cuda_impl(const at::Tensor& q, const at::Tensor& k,
                            const at::Tensor& v, double softmax_scale) {
    return third_party_flash_attn_forward(q, k, v, softmax_scale);
}

// schema 必须跟 Python 端 custom_op 完全一致
TORCH_LIBRARY(mylib, m) {
    m.def("fa_fwd(Tensor q, Tensor k, Tensor v, float softmax_scale) -> Tensor");
}
TORCH_LIBRARY_IMPL(mylib, CUDA, m) {
    m.impl("fa_fwd", fa_fwd_cuda_impl);
}

集成约束

  1. schema 必须前后一致：Python 端 custom_op 与部署进程中的 C++ 注册必须描述同一个 operator schema，否则 ProxyExecutor/dispatcher 无法按预期调用实现。
  2. in-place 改输入要声明 mutates_args：带 out 参数的 op 应准确声明写入对象，例如 mutates_args=("out",)；否则 functionalization 可能按错误的纯函数语义建模该算子。
  3. 训练场景需显式注册 autograd 公式：custom_op 默认不包含 backward 定义；训练时使用 fa_fwd.register_autograd(setup_context=..., backward=...) 注册，纯推理部署可以省略该步骤。
  4. 先完成 operator 注册：无论采用静态链接还是 dlopen，模型执行前都要让目标 backend 实现进入 dispatcher。是否需要 RTLD_GLOBAL 取决于库的符号依赖，不是 TORCH_LIBRARY 的统一要求。
  5. 不要把普通 pybind 可调用性等同于可导出性：先用 custom-op 或项目提供的编译集成建立 schema、fake/meta 和运行时实现，再实际运行 export/AOTI 测试。

10. 部署约束与版本边界

  1. GPU 目标兼容性：包内可能包含面向特定 SM 的 cubin，也可能包含其它生成物。部署前应检查 archive 和编译配置，并在每种目标 GPU 上验证；“部署 GPU 更新”本身不是兼容保证。
  2. PyTorch 版本：本文不把 .pt2 或内部 AOTI C ABI 视为跨版本稳定接口。最稳妥的基线是构建端与运行端使用匹配的 PyTorch/libtorch 版本。
  3. Dynamic shape：需要变化的维度应在 export 时用 Dim 声明。未声明的维度通常按示例输入专门化，运行时检查可能拒绝不匹配的 size、dtype 或 stride。
  4. Custom op 必须有 fake impl:没注册 register_fake 的 custom op export 时直接报错。
  5. State / 控制流：Python 控制流和可变状态能否导出取决于 export 支持范围。需要保留动态控制流时，应采用该版本支持的 higher-order operator，并通过目标输入集验证。
  6. 构建和加载成本：耗时取决于模型、目标、autotune 与缓存状态。应分别测量 export、AOTI 编译、打包和冷加载，不能套用固定分钟数或秒数。
  7. Python-free runtime：PyTorch v2.12.0 官方 C++ 示例通过 ${TORCH_LIBRARIES} 链接 AOTI loader，不要求 Python interpreter。最终动态库集合应以 CMake link line 和部署产物的 ELF 依赖为准。

CUDA C++ Deployment and Runtime Mechanics of PyTorch AOTInductor

Moving a PyTorch model from a development environment into a C++ service requires an explicit division between compile-time work, model assets, and runtime dependencies. AOTInductor places model capture, Inductor lowering, GPU-kernel generation, and packaging in an offline stage, then executes the result through a C++ loader. This boundary determines the contents of a .pt2 package, the libtorch components required by the deployment process, and the separate compile-time and runtime contracts required by custom operators.

APIs, source paths, and runtime call chains in this article were checked against the public PyTorch v2.12.0 source and the 2.12 AOTInductor documentation. torch._inductor, .pt2 contents, and generated symbols can change with version and build configuration; the pseudocode and diagrams are source-reading models, not a stable ABI or fixed file manifest.

1. AOTI's Deployment Boundary

AOTI targets deployments with three recurring constraints:

  • A native serving process. Inference services, simulators, and embedded environments may standardize on C++ or Rust binaries, making a Python interpreter an avoidable runtime dependency.
  • Predictable cold start. torch.compile performs Dynamo tracing, Inductor code generation, and Triton binary compilation on its first execution. Moving these steps offline removes that compilation work from service startup.
  • PyTorch compiler semantics across the deployment boundary. The PyTorch 2.12 documentation marks TorchScript as deprecated. ONNX introduces a separate exporter/runtime contract, whereas AOTI keeps graph export and lowering within the PyTorch compiler stack.

AOTInductor (AOTI) is PyTorch's ahead-of-time deployment path for compiling an exported program into packaged native artifacts that a matching libtorch runtime can load. In the pinned PyTorch 2.12 release, the path has three stages:

  • On the Python side, torch.export captures the graph and Inductor performs the code generation, compilation, and packaging required by the selected target configuration.
  • The output is a .pt2 archive. Its members depend on configuration and may include model libraries, C++ or object files, Triton cubins, weights, constants, and ProxyExecutor metadata.
  • On the C++ side, link the libtorch distribution matching the compiler version and use torch::inductor::AOTIModelPackageLoader to load the .pt2. The official C++ example uses ${TORCH_LIBRARIES}; runtime does not require a Python interpreter or libtorch_python.

2. End-to-end flow

The upper half of the diagram performs model capture, lowering, compilation, and archive packaging in the Python build environment. The lower half loads that archive in the C++ runtime and invokes the compiled model entry point. The example that follows traces the same path through five stages: export, Inductor lowering, Triton code generation, .pt2 packaging, and C++ loading.

3. The example model

The example combines native operators, fusible pointwise operators, and a custom operator. These three node categories enter different lowering paths:

# model.py
import torch
from torch import nn

# --- 1) Register a custom op ---
# Semantics: y = x * scale + bias_per_channel
# Registered with torch.library.custom_op in PyTorch 2.12.
@torch.library.custom_op("mylib::scale_add", mutates_args=())
def scale_add(x: torch.Tensor, scale: float, bias: torch.Tensor) -> torch.Tensor:
    return x * scale + bias

# Meta implementation for FakeTensor / Inductor (shape / dtype inference).
@scale_add.register_fake
def _(x, scale, bias):
    return torch.empty_like(x)

# --- 2) A Module that uses both native and custom ops ---
class ToyModel(nn.Module):
    def __init__(self):
        super().__init__()
        self.fc1 = nn.Linear(128, 256)        # native: aten::linear / aten::mm
        self.fc2 = nn.Linear(256, 64)
        self.bias = nn.Parameter(torch.randn(64))

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        h = self.fc1(x)
        h = torch.nn.functional.gelu(h)
        h = self.fc2(h)
        h = torch.ops.mylib.scale_add(h, 2.0, self.bias)   # custom op
        return h.relu()

Each operator group exposes one part of the compilation path:

  • nn.Linear: this reaches matrix-multiplication paths such as aten::linear and aten::mm. A normal CUDA configuration commonly uses an external GEMM library, but the exact backend depends on the release, shape, and compiler configuration; inspect the generated source.
  • F.gelu and .relu(): both have pointwise lowerings. The intervening opaque scale_add custom op blocks cross-op fusion unless a decomposition or compiler-visible lowering is supplied.
  • scale_add: a custom operator whose schema, abstract implementation, compiler lowering, and deployment implementation can be examined separately.

4. Phase 1: torch.export

4.1 API

import torch
from torch.export import export, Dim
from model import ToyModel, example_inputs

model = ToyModel().eval().cuda()
batch = Dim("batch", min=1, max=64)
ep = export(model, example_inputs, dynamic_shapes={"x": {0: batch}})

print(ep.graph_module.code)         # readable FX graph

The printed graph looks like:

def forward(self, p_fc1_weight, p_fc1_bias, p_fc2_weight, p_fc2_bias, p_bias, x):
    linear = torch.ops.aten.linear.default(x, p_fc1_weight, p_fc1_bias)
    gelu = torch.ops.aten.gelu.default(linear)
    linear_1 = torch.ops.aten.linear.default(gelu, p_fc2_weight, p_fc2_bias)
    scale_add = torch.ops.mylib.scale_add.default(linear_1, 2.0, p_bias)
    relu = torch.ops.aten.relu.default(scale_add)
    return (relu,)

The exported graph establishes three conditions for the later stages:

  • Every operator is normalized into torch.ops.{namespace}.{op}.{overload} form, giving the graph an operator-level representation independent of Python module attribute access.
  • Weights are lifted into graph inputs (p_fc1_weight and related values), while ep.state_dict and ep.constants retain the mapping to the original state.
  • The custom operator mylib::scale_add appears beside ATen operators, so later compiler stages can identify its schema even though its body remains opaque.

4.2 Internals

torch.export is a single function but it does four things internally:

  1. Dynamo trace: TorchDynamo's frame-eval hook intercepts Python bytecode, recording every torch.* call as an FX node. if and for in user code are specialised against the concrete input shapes at trace time (with symbolic shape mode adding guards via torch._dynamo.guards).
  2. FakeTensor propagation: each FX node is run with FakeTensor to determine output shape and dtype. Custom ops MUST have a register_fake meta implementation here or export fails.
  3. Decomposition: certain composite ops (aten::linear in some dispatch paths) decompose into more primitive ones (aten::mm + aten::add). Export uses the core-ATen decomposition table by default; you can control how far decomposition goes.
  4. Graph signature: graph inputs are classified into (user inputs / parameters / buffers / tokens) and outputs into (user outputs / mutated buffers), producing an ExportSignature.

5. Phase 2: Inductor lowering

5.1 API

import torch._inductor

package_path = torch._inductor.aoti_compile_and_package(
    ep,
    package_path="model.pt2",
    inductor_configs={
        "max_autotune": True,
        "aot_inductor.embed_kernel_binary": True,

This single call does three things: feed the ExportedProgram's FX graph into the Inductor compiler frontend, lower it into a mix of ATen calls and generated Triton kernels with C++ glue, then build a .so and package it with the cubins, weights, and metadata into a .pt2.

5.2 Native op vs custom op vs fused kernel

Inductor routes each FX node through one of three paths:

KindExamplesInductor's actionCall form
Heavyweight native aten::linear, aten::matmul, aten::conv2d Usually lower to an external ATen/library call or an AOTI shim; exact form depends on the op and configuration Generated external call or aoti_torch_* shim; inspect the generated source
Fusible elementwise / reduction aten::gelu, aten::relu, pointwise add / mul Merge adjacent elementwise (and some reduction) ops into a single Triton kernel C++ triton_kernel_fused_(...) → cuLaunchKernel(cubin)

For this example, Inductor produces roughly the following pseudo-C++:

// Logical sketch of generated AOTI code; class/helper names are not stable APIs
AOTIRuntimeError AOTInductorModel::_run_impl(
    AtenTensorHandle* input_handles,
    AtenTensorHandle* output_handles,
    AOTIProxyExecutorHandle proxy_executor, ...)
{
    auto buf0 = generated_linear_call(x, fc1_weight, fc1_bias);   // commonly reaches cuBLAS

    auto buf1 = empty_strided_cuda({4, 256}, ...);
    triton_poi_fused_gelu_0(buf0, buf1, ...);                             // elementwise gelu

    auto buf2 = generated_linear_call(buf1, fc2_weight, fc2_bias); // commonly reaches cuBLAS

    aoti_torch_proxy_executor_call_function(proxy_executor, op_index, ...); // opaque fallback

    auto buf4 = empty_strided_cuda({4, 64}, ...);
    triton_poi_fused_relu_1(buf3, buf4, ...);                            // lowered aten::relu

    output_handles[0] = buf4;
    return AOTI_SUCCESS;
}

This sketch models the control flow rather than a stable generated ABI. In the PyTorch v2.12.0 code generator, AOT-mode fallbacks use a ProxyExecutor; aoti_torch_call_dispatcher in the same file serves a separate, non-AOT StableIValue-compatible path.

A compiler-visible, semantically opaque custom operator is an operator whose schema and abstract metadata are available to the compiler while its computation remains an external call. torch.library.custom_op creates that boundary by default, and register_fake supplies the output shape, dtype, and device for export and FakeTensor propagation. Fusion with the following relu requires an explicit decomposition or lowering rule, or a compiler-visible Triton wrapper such as torch.library.triton_op (see §9).

6. Phase 3: Triton codegen + cubin

After Inductor selects Triton code generation for a fused region, the external triton package compiles the generated Python source into a GPU binary. This stage sits between Inductor scheduling and AOTI packaging; Build and Load Relationships of PyTorch Linux Shared Libraries describes the corresponding boundary between Python compiler components and runtime libraries.

  1. Inductor writes the generated Triton source (Python text) to a path like /tmp/torchinductor_$USER/<hash>/triton_poi_fused_scale_add_relu_1.py.
  2. It invokes triton.jit to trigger compilation: Python AST → Triton IR → MLIR → PTX → cubin.
  3. Triton and Inductor cache compiler intermediates. Their cache roots can be changed by environment and configuration and are not part of the package format.
  4. The GPU binary may be embedded in the model library or packaged as a companion file, depending on compiler configuration. Archive member names are not a stable ABI.

A typical generated kernel looks like:

# /tmp/torchinductor_user/abcd/triton_poi_fused_scale_add_relu_1.py
import triton
import triton.language as tl

@triton.jit
def triton_poi_fused_scale_add_relu_1(
    in_ptr0, in_ptr1, out_ptr0, xnumel, XBLOCK: tl.constexpr):
    xoffset = tl.program_id(0) * XBLOCK
    xindex = xoffset + tl.arange(0, XBLOCK)[:]
    xmask = xindex < xnumel
    x0 = xindex % 64
    tmp0 = tl.load(in_ptr0 + xindex, xmask)
    tmp1 = tl.load(in_ptr1 + x0, xmask)        # load bias
    tmp2 = tmp0 * 2.0                          # scale_add scale part
    tmp3 = tmp2 + tmp1                         # scale_add add part
    tmp4 = tl.maximum(tmp3, 0.0)               # relu
    tl.store(out_ptr0 + xindex, tmp4, xmask)

This fused form requires Inductor to see the computation through an explicit decomposition or lowering rule, or through a compiler-visible API such as torch.library.triton_op. With that semantic information, * scale + bias and the trailing relu can collapse into one load → compute → store pass. A standalone register_fake declaration supplies abstract metadata only.

Common default configurations may expose paths like these. They are diagnostic cache locations, not deployment interfaces:

~/.triton/cache/<hash>/triton_poi_fused_scale_add_relu_1.cubin
~/.cache/torch/inductor/<hash>/triton_poi_fused_scale_add_relu_1.{py,cubin,json}

Companion metadata may record launch information such as num_warps, num_stages, shared-memory size, and the grid formula. Its storage location and the runtime launch path are version-specific implementation details.

8. Phase 5: C++ runtime

8.1 C++ Loader Example

// runner.cpp
#include <torch/torch.h>
#include <torch/csrc/inductor/aoti_package/model_package_loader.h>
#include <iostream>
#include <vector>

int main(int argc, char** argv) {
    if (argc < 2) {
        std::cerr << "usage: " << argv[0] << " model.pt2\n";
        return 1;
    }

    torch::inductor::AOTIModelPackageLoader loader(argv[1]);

    auto device = torch::Device(torch::kCUDA, 0);
    auto x = torch::randn({4, 128}, torch::TensorOptions().device(device));
    std::vector<torch::Tensor> inputs = {x};

    auto outputs = loader.run(inputs);

    torch::Tensor y = outputs[0];
    std::cout << "output shape: " << y.sizes() << "\n";
    std::cout << "output mean: "  << y.mean().item<float>() << "\n";
    return 0;
}

8.3 Package loading sequence

According to model_package_loader.cpp, construction can be summarized as follows:

  1. Read the archive directory and extract the selected model directory plus related constants to a temporary directory.
  2. Use an existing .so, or compile one from packaged .cpp, object files, and compile options.
  3. Read the AOTI device key from metadata and select a device runner from the runner registry.
  4. Pass the model .so, runner count, device, and generated-file directory to that runner; update the constant buffer if a weight blob is present.

loader.run(inputs):

  1. Convert input at::Tensor objects to an AtenTensorHandle array.
  2. Call the model container's exported AOTInductorModelContainerRun function (or its single-threaded variant), passing the stream and optional ProxyExecutor.
  3. Convert returned tensor handles back to at::Tensor.

model_container_runner.cpp resolves model-container C ABI exports such as AOTInductorModelContainerCreateWithDevice and AOTInductorModelContainerRun. The generated artifact owns the version-specific loading and launch path for Triton or CUDA kernels.

The relevant public sources are below; see Build and Load Relationships of PyTorch Linux Shared Libraries for shared-library boundaries:

PathRole

The resulting call chain has three layers: the package loader in libtorch core extracts the archive and selects a runner; the generic runner dynamically loads the model .so and invokes the model-container C ABI; the CUDA runner and generated model use the required CUDA runtime and shims. Exact ELF boundaries and kernel-launch forms remain properties of the selected build and generated artifact.

9. Custom op handling details

A custom operator crosses three distinct contracts: its schema identifies the operation, its fake implementation supports export and abstract execution, and its lowering or runtime implementation supplies executable semantics. The scale_add example uses these contracts to distinguish three integration strategies.

9.1 Strategy A: let Inductor fall back (default)

With the schema and fake implementation alone, Inductor treats mylib::scale_add as an opaque external operation:

  • The operation remains outside Triton fusion regions.
  • AOT mode emits an external fallback and packages its call description for ProxyExecutor.
  • At runtime, ProxyExecutor invokes the registered operator implementation; the pinned PT2 archive specification stores these calls in an optional JSON file.

A Python-free AOTI runner therefore needs a loadable C++ or CUDA implementation registered through TORCH_LIBRARY_IMPL for the appropriate DispatchKey. The runner links or dlopens that implementation before loading the package. By comparison, register_kernel("cuda") or device_types=["cuda"] supplies an implementation to a Python process and does not establish the C++ runtime registration.

9.2 Strategy B: register a version-specific Inductor lowering

from torch._inductor import lowering

@lowering.register_lowering(torch.ops.mylib.scale_add)
def _scale_add_lowering(x, scale, bias):
    return lowering.add(lowering.mul(x, scale), bias)

After this explicit registration, the pinned Inductor version can express scale_add in its internal IR and fuse it with surrounding elementwise ops. torch._inductor.lowering is an internal API and must be maintained with the selected PyTorch version. A fake implementation remains limited to abstract execution and metadata inference.

9.3 Strategy C: register a Triton implementation for Python execution

The following register_kernel("cuda") implementation lets the custom op call a Triton kernel in a Python process:

import triton
import triton.language as tl

@triton.jit
def _scale_add_triton_kernel(x_ptr, bias_ptr, out_ptr, scale, n_elements, BLOCK: tl.constexpr):
    pid = tl.program_id(0)
    offsets = pid * BLOCK + tl.arange(0, BLOCK)
    mask = offsets < n_elements
    x = tl.load(x_ptr + offsets, mask)
    b = tl.load(bias_ptr + offsets % bias_dim, mask)
    tl.store(out_ptr + offsets, x * scale + b, mask)

@scale_add.register_kernel("cuda")
def _(x, scale, bias):
    out = torch.empty_like(x)
    n = x.numel()
    grid = (triton.cdiv(n, 1024),)
    _scale_add_triton_kernel[grid](x, bias, out, scale, n, BLOCK=1024)
    return out

This registration supplies a runtime implementation; it does not automatically expose the Triton body to Inductor and is not sufficient for a Python-free C++ runtime. Use the pinned release's torch.library.triton_op integration when compiler-visible tracing is required. A standalone AOTI fallback still needs an implementation that the C++ process can load.

9.4 Third-party ops exposed only through pybind, never registered with the dispatcher

A plain pybind CUDA entry without an operator schema, fake implementation, and C++ backend lacks the integration contract expected by the PyTorch compiler stack. Depending on the function and tracing rules, Dynamo may graph-break, reject export, or require an explicit integration; pybind callability alone does not make an operation deployable through AOTI.

The integration contracts differ as follows:

Python-free AOTI deployment needs both a compile-time contract and a runtime implementation.

Step 1: wrap the pybind call in custom_op on the Python side

import torch
import third_party_lib   # pybind-only third-party module

@torch.library.custom_op("mylib::fa_fwd", mutates_args=())
def fa_fwd(q: torch.Tensor, k: torch.Tensor, v: torch.Tensor,
           softmax_scale: float) -> torch.Tensor:
    # Call into pybind directly; the semantics are opaque to PyTorch.
    return third_party_lib.flash_attn_forward(q, k, v, softmax_scale)

@fa_fwd.register_fake
def _(q, k, v, softmax_scale):
    # Meta inference: produce an empty tensor of the right shape / dtype.
    return torch.empty_like(q)

After this step, Dynamo and export see torch.ops.mylib.fa_fwd in the FX graph. In PyTorch v2.12.0, AOT fallback describes the external call through ProxyExecutor and packages the corresponding JSON according to the PT2 archive specification.

The Python wrapper itself is not available in a Python-free deployment process, so the runtime still needs a C++/CUDA operator implementation.

Step 2: write a TORCH_LIBRARY C++ shim and link it into the runner

Third-party libraries usually expose a real C++ entry point underneath the pybind wrapper. Build a separate shim .so that registers the same op against the dispatcher, then dlopen it at C++ runtime startup:

// my_third_party_shim.cpp — built into libfa_shim.so
#include <torch/library.h>

// Real C++ entry from the third-party library (header or dlsym).
extern at::Tensor third_party_flash_attn_forward(
    const at::Tensor& q, const at::Tensor& k, const at::Tensor& v,
    double softmax_scale);

at::Tensor fa_fwd_cuda_impl(const at::Tensor& q, const at::Tensor& k,
                            const at::Tensor& v, double softmax_scale) {
    return third_party_flash_attn_forward(q, k, v, softmax_scale);
}

// Schema must match the Python-side custom_op registration exactly.
TORCH_LIBRARY(mylib, m) {
    m.def("fa_fwd(Tensor q, Tensor k, Tensor v, float softmax_scale) -> Tensor");
}
TORCH_LIBRARY_IMPL(mylib, CUDA, m) {
    m.impl("fa_fwd", fa_fwd_cuda_impl);
}

Build the shim:

g++ -shared -fPIC -std=c++17 -O3 \
    -I$TORCH_DIR/include -I$TORCH_DIR/include/torch/csrc/api/include \
    -I/path/to/third_party_headers \
    my_third_party_shim.cpp \
    -L$TORCH_DIR/lib -ltorch -ltorch_cpu -ltorch_cuda -lc10 -lc10_cuda \
    -L/path/to/third_party -lflash_attn \
    -o libfa_shim.so

Load the shim before constructing AOTIModelPackageLoader so its TORCH_LIBRARY static registration completes first. This example uses RTLD_NOW | RTLD_LOCAL; use RTLD_GLOBAL only when the third-party library's symbol-visibility contract requires it:

#include <dlfcn.h>
// ...
void* shim = dlopen("./libfa_shim.so", RTLD_NOW | RTLD_LOCAL);
if (!shim) { std::cerr << dlerror() << "\n"; return 1; }

torch::inductor::AOTIModelPackageLoader loader("model.pt2");
// loader.run(inputs) now dispatches correctly into fa_fwd_cuda_impl.

Integration constraints

  1. Schema must match on both sides. The Python custom_op and deployment-time C++ registration must describe the same operator schema so ProxyExecutor and the dispatcher can invoke the expected implementation.
  2. Declare mutates_args for in-place outputs. An operator with an out parameter should identify the written argument, for example mutates_args=("out",). Otherwise, functionalization may model the operator with incorrect pure-function semantics.
  3. Training requires an explicit autograd formula. A custom_op has no backward definition by default. Register one with fa_fwd.register_autograd(setup_context=..., backward=...); inference-only deployment can omit this step.
  4. Complete operator registration before execution. Whether linked statically or loaded with dlopen, the target backend implementation must be registered before the model runs. RTLD_GLOBAL is a dependency-specific choice, not a universal TORCH_LIBRARY requirement.
  5. Do not equate pybind callability with exportability. Establish the schema, fake/meta behavior, and runtime implementation through a supported integration, then run export and AOTI tests on the actual target.

10. Deployment Constraints and Version Boundaries

  1. GPU target compatibility. An archive may contain cubins for particular SM targets as well as other generated files. Inspect the archive and compile configuration, then validate every deployment GPU; a newer GPU alone does not guarantee compatibility.
  2. PyTorch version pinning. This article does not treat .pt2 or the internal AOTI C ABI as a cross-version stable interface. Matching PyTorch/libtorch versions are the conservative deployment baseline.
  3. Dynamic shapes. Declare dimensions that may vary through Dim during export. Other dimensions are normally specialized from the example inputs, and runtime checks may reject mismatched size, dtype, or stride.
  4. Custom op must have a fake impl. A custom op without register_fake fails export outright.
  5. State and control flow. Export support for Python control flow and mutable state is version- and pattern-dependent. Use supported higher-order operators for dynamic control flow and validate the target input set.
  6. Build and load cost. Timing depends on the model, target, autotuning, and cache state. Measure export, AOTI compilation, packaging, and cold loading separately instead of assuming fixed minute or second ranges.
  7. Python-free runtime. The PyTorch v2.12.0 C++ tutorial links the AOTI loader through ${TORCH_LIBRARIES} without requiring a Python interpreter. Determine the final shared-library set from the CMake link line and the deployed artifact's ELF dependencies.
