HTTP 代理与应用配置

HTTP 代理为 Web 应用提供请求转发和隧道服务，常用于出口管理、访问控制和为特定应用指定出口。本文介绍 HTTP 转发与 CONNECT 的工作原理，梳理 macOS 系统设置、Electron 启动参数及环境变量的作用范围，并分析内网代理与 VPN 的协作、源站可见的信息及 Tinyproxy 的部署方法。

1. HTTP 代理机制

显式正向代理适合 Web 出口管理、访问日志与认证、为特定应用指定出口，以及通过有权访问目标的代理取得连接服务。HTTP 代理需要应用或网络库配合，普通 socket、ICMP 和任意 UDP 不会因系统代理开关而自动转发。

对象协议位置处理单位
HTTP/1.1 正向代理TCP/IP 应用层，通常对应 OSI L7HTTP 请求 / 响应
HTTP CONNECT应用层建立通道，随后转发字节目标 host:port，之后通常是源站 TLS
TCP / IP传输层 / 网络层负责当前连接的数据传输与路由
三层 VPN在 IP 路径接入，外层封装另计完整内层 IP 包

普通 HTTP 转发需要代理解析请求。HTTPS 经 CONNECT 转发时，代理在握手成功后传递 TLS 字节流。两种模式都会在代理两侧建立独立的 TCP 连接，但代理对应用内容的可见性不同。

HTTP 请求转发

HTTP 代理通过请求行中的完整 URL 获得目标地址。例如，访问 http://example.com/docs 时，客户端连接代理并发送以下请求；代理解析 example.com，创建或复用到源站的连接，再转发请求。序列图展示新建连接的情况。

GET http://example.com/docs HTTP/1.1
Host: example.com

完整 URL 的写法叫 absolute-form。代理连接源站后，通常发送 GET /docs HTTP/1.1 这样的 origin-form。客户端到代理、代理到源站是两条独立的 TCP 连接，各自维护序列号、重传和流量控制；普通 HTTP 内容对代理可见。请求目标的语法见 RFC 9112 §3.2。

CONNECT 隧道

CONNECT 为客户端与源站之间的 TLS 会话建立一条字节通道。客户端通过普通 HTTP 代理访问 HTTPS 站点时，先发送目标主机名和端口：

CONNECT example.com:443 HTTP/1.1
Host: example.com:443

代理连接 example.com:443 并返回成功的 2xx 响应后，这条连接切换为双向字节转发。客户端随后通过通道与源站完成 TLS 握手，并传输加密的 HTTP 请求。后续 TLS 数据直接进入字节流，无需再包装成 GET 或 POST。RFC 9110 §9.3.6定义了这一切换。

TLS 会话由客户端和源站共同维护，代理转发两条 TCP 连接之间的 TLS 字节。代理能看到 CONNECT 中的主机名、端口以及流量大小和时序，但正常转发时没有源站 TLS 会话密钥，无法直接读取 HTTPS 正文。部署额外信任证书的 TLS 检查代理会改变这个加密边界。图中绿色箭头表示 TLS 的逻辑端点，字节仍经过代理两侧的 TCP 连接。参见 TLS 1.3 协议概览。

HTTPS 代理与 TLS

macOS 的「安全 Web 代理（HTTPS）」字段指定访问 HTTPS URL 时使用的代理。Chromium 将这项系统配置映射为普通 HTTP 代理，因此字段名称本身不表示客户端到代理的连接使用 TLS。这个命名区别在 GetProxyServerScheme() 中有明确说明。

curl 的 --proxy https://proxy.example:8443 则指定使用 TLS 连接代理。访问 HTTPS 源站时，客户端与代理之间的外层 TLS 承载 CONNECT，通道内部再承载客户端与源站之间的 TLS。两次握手的对端不同。教程采用普通 HTTP 代理地址 http://127.0.0.1:18888，Tinyproxy 的同一个端口同时处理 HTTP 转发和 HTTPS CONNECT。curl：代理协议前缀。

2. macOS 代理配置

配置作用域

代理配置保存在所选的网络服务中。设置入口是「系统设置 → 网络 → Wi-Fi 或以太网等网络服务 → 详细信息 → 代理」，HTTP、HTTPS、SOCKS、自动代理配置（PAC）和绕过域名各有对应选项。Wi-Fi 与以太网分别保存配置，修改其中一项不会同时修改另一项。Apple：更改代理设置。

应用通过网络库读取这些配置。Apple 的 URLSessionConfiguration.connectionProxyDictionary 默认采用系统代理设置，也允许应用提供自己的配置。因此，即使两个应用运行在同一台 Mac 上，它们也可能选择不同的连接路径。URLSession 文档描述了这一配置关系。

流量来源仅设置 macOS HTTP / HTTPS 代理后的行为
使用系统代理配置的浏览器或 URLSession 应用按 URL 类型、绕过规则、PAC 等选择代理或直连；应用自身的覆盖配置仍可能改变结果。
终端中的 curl通常需要 --proxy 或 curl 支持的环境变量；不能假设它会读取 GUI 设置。
直接调用 BSD socket 的程序、普通 ssh 命令仍连接程序指定的地址；如需代理，要由程序、转发工具或其他网络机制显式处理。
ping、任意 UDP 流量不会因为启用 HTTP 代理而变成 HTTP 请求。

系统代理的作用范围取决于哪些应用采用这份配置。终端环境变量是另一套配置入口：修改 GUI 不会替 shell 设置 http_proxy，已有的 shell 变量也不会自动更新系统代理。curl 支持的变量见其代理环境变量说明。

连接建立

访问 https://example.com/docs 时，采用代理配置的应用会根据 URL 和规则选择连接端点。若结果为 proxy.example:18888，应用创建的 TCP socket 就连接该代理。内核按路由表发送目的地址为代理的 IP 包；CONNECT 握手则由应用写入这条连接。

URL: https://example.com/docs
  → 应用 / 网络库查询代理规则
  → 选择 proxy.example:18888
  → socket.connect(proxy_ip, 18888)
  → TCP / IP 把字节送到代理
  → 在这条连接上发送 CONNECT example.com:443

HTTP 请求和 CONNECT 握手都是应用层数据，内核负责传输这些字节。匹配绕过规则时，应用选择直连；程序未读取代理配置时，连接目标仍由程序自己的逻辑决定。Chromium 的 macOS 代理配置读取代码展示了系统配置如何进入应用的代理决策。

3. Electron 代理配置

网络库与 Session

Electron 应用可能同时包含 Chromium 页面请求、主进程 Node.js 请求、原生模块和子进程。代理设置的生效范围必须对应到发出请求的网络库，不能只按进程名称判断。以下两种 fetch 虽然同名，配置来源却不同。

请求来源网络实现应检查的配置
页面加载、渲染进程 fetch / XHR / WebSocketChromium，属于相应 SessionSession 代理、Chromium 启动参数或系统配置
electron.net.fetch() / net.request()Chromium默认 Session，或显式指定的 Session；ses.fetch() 使用所属 Session
Node.js http / https / Node 内置 fetchNode.js 及其 agent / dispatcher对应版本的环境代理支持或显式代理实现
原生模块、子进程、更新组件取决于具体实现各自配置；不能由窗口请求的结果推断

Electron 的 net 使用 Chromium 网络库，而主进程中的 Node 内置 fetch 属于 Node 网络栈。设置一个窗口的 Session，不会自动重写任意 Node socket。Electron net 文档。

启动参数

对采用默认代理配置的 Chromium 请求，--proxy-server 可以覆盖系统代理。将应用正常退出后，从终端运行实际的可执行文件；示例中的 App 名和代理地址需要替换。已运行应用的单实例逻辑可能只把新启动请求转交给旧进程，使新参数没有应用到原来的网络上下文。

"/Applications/Example.app/Contents/MacOS/Example" \
  --proxy-server="http://10.77.0.10:18888" \
  --log-net-log="$HOME/Desktop/example-netlog.json"

这会让受该配置控制的 HTTP、HTTPS 和 WebSocket 请求选用内网代理，并记录 Chromium NetLog。它不是对整个进程的网络包重定向。--proxy-bypass-list 可以指定绕过规则；--no-proxy-server 会覆盖其他代理启动参数。需要认证时使用应用的代理认证接口，不能假设在该参数 URL 中嵌入用户名密码就会生效。Electron 启动参数。

显式 Session 配置

应用开发者可以为独立的 Session 设置代理，并在创建窗口或发起请求前等待配置完成。此例将窗口与 persist:internal 绑定，避免把配置写在一个 Session、请求却发在另一个 Session：

const { app, BrowserWindow, session } = require('electron');

app.whenReady().then(async () => {
  const ses = session.fromPartition('persist:internal');
  await ses.setProxy({
    mode: 'fixed_servers',
    proxyRules: 'http://10.77.0.10:18888',
    proxyBypassRules: 'localhost,127.0.0.1,[::1]'
  });
  await ses.closeAllConnections();
  console.log(process.versions);
  console.log(await ses.resolveProxy('https://example.com/'));

  const win = new BrowserWindow({ webPreferences: { session: ses } });
  await win.loadURL('https://example.com/');
}).catch(console.error);

resolveProxy() 返回这个 URL 的代理选择结果，不证明代理能连接或请求已经成功。切换配置时，旧连接池可能继续使用原路径；closeAllConnections() 用于验证新连接，但会中断这个 Session 的现有连接，应在启动阶段或明确允许重连时调用。Session API。

mode: "system" 明确选择系统配置；mode: "direct" 选择不使用代理；fixed_servers 与 pac_script 使用各自提供的规则。显式 system 与“完全不设置代理”并不相同：后者还可能受命令行参数影响。单个 fixed server 失败时，没有自动改用 macOS 公网代理的保证；回退列表必须来自当前有效配置或应用代码。ProxyConfig 模式与回退列表。

环境变量

export http_proxy=http://10.77.0.10:18888
export https_proxy=http://10.77.0.10:18888
export no_proxy=localhost,127.0.0.1,::1
"/Applications/Example.app/Contents/MacOS/Example"

这组变量只进入该终端及其后代进程的环境。Finder 或 Dock 启动的应用通常不继承当前 shell 的 export；应用即使拿到变量，也需要网络库主动读取。HTTP_PROXY、HTTPS_PROXY、ALL_PROXY 和 NO_PROXY 都不是能强制接管 Chromium 流量的操作系统指令。curl、Node、第三方 agent 与应用自己的实现，对名称、大小写和绕过规则可能有不同约定。curl 环境代理约定。

较新的独立 Node.js 提供环境代理支持，但仍需启用，且受版本与请求 API 约束。例如，在支持该功能的 Node 运行时中：

NODE_USE_ENV_PROXY=1 HTTPS_PROXY=http://10.77.0.10:18888 \
  node -e "require('node:https').get('https://example.com/', r => { console.log(r.statusCode); r.resume(); })"

Node 的 HTTP 文档把内置代理支持标记为自 v24.5.0、v22.21.0 加入。Electron 内嵌的 Node 版本、启动方式和选项支持必须另行核对；不能把独立 Node 的结果直接推广到 Electron 页面。process.versions 可记录实际 Electron / Chromium / Node 版本。Node 内置代理支持；Electron 环境变量。

4. 内网代理与 VPN

客户端到代理

设代理为 10.77.0.10:18888，只有经 VPN 才能到达。应用先选择这个代理，再创建到 10.77.0.10 的 TCP 连接；系统查询的是代理 IP 的路由。即使目标 URL 是公网 https://example.com/，第一段连接也会因代理位于 VPN 网段而进入隧道。

代理到源站

VPN 网关将内层包交给代理后，代理收到 CONNECT 目标并解析源站域名，再按代理机器自己的路由连接源站。这段连接可能经代理所在网络的公网 NAT、另一个 VPN，或显式上游代理。Mac 的系统代理设置不会自动复制到这台代理服务器。

因此，“内网代理怎样从 VPN 出去”包含两个不同条件：客户端经 VPN 到达代理，代理所在网络允许它访问目标。代理没有公网出口时，VPN 连接成功仍可能得到 CONNECT 失败或超时。源站看到的出口地址来自代理这一侧，而不是由 Mac 的隧道地址直接决定。客户端的 packet VPN 路径见 VPN 原理与路由。

5. 源站可见性

目标服务器能直接观察连接来源和收到的应用数据。已经在中间节点结束的 CONNECT、SOCKS、SSH 或 VPN 封装不会随请求自动到达源站。判断请求是否经过代理，需要区分协议直接提供的证据与基于出口地址的推断。

连接与请求信息

本节的观察点是站点对外接受连接的服务器。如果站点使用 CDN 或负载均衡，后端直接连接的对端是该中间节点，需要通过可信的转发信息还原外部连接来源。

访问方式目标站点直接看到什么不会自动收到什么
普通 HTTP 正向代理代理出口或其上游 NAT 的地址；代理转发的 HTTP 请求，可能含转发相关 header代理之前所有节点的完整链路记录
HTTPS 经普通 CONNECT / SOCKS代理出口地址，以及客户端送来的 TLS 握手和 TLS 内的请求CONNECT 或 SOCKS 握手本身；它们在代理处结束
SSH -L / -Dsshd 一侧目标连接的来源地址；若 HTTPS 未被中途终止，仍收到客户端的 TLSSSH 协议头和 SSH 加密 channel；它们在 sshd 处结束
VPN，经出口 NAT 上网VPN 出口 NAT 地址，以及客户端的应用流量客户端到 VPN 网关之间的外层 VPN 封装
VPN，路由部署而不做 NAT被路由的客户端源地址，例如企业分配的隧道地址外层 VPN 协议头及隧道握手

HTTP 规范要求代理在转发的 HTTP 消息中添加 Via，记录中间节点；Forwarded 或常见的 X-Forwarded-For 则可按实现和配置传递客户端信息。服务器接受这类信息需要可信的代理关系，客户端自行填写的 header 不能证明真实路径。部署中也可能存在省略这些字段的代理，因此字段缺失不能证明请求直连。参见 Via 规范和 Forwarded 的可信度限制。

保持端到端 TLS 的 CONNECT 代理无法修改其中的 HTTP header 而不破坏 TLS 完整性校验，packet VPN 本身也不生成 HTTP 转发头。源站仍会收到应用主动发送的账号、cookie 和其他请求数据；出口地址改变并不会移除这些身份信息。

出口 IP 识别

互联网请求没有一个通用字段声明其经过 VPN、SOCKS 或 SSH。服务器可以将源地址与已知 VPN、公共代理或托管机房网段比较，再结合账号和访问行为作判断。MaxMind 的匿名 IP 数据库提供这些分类，也说明部分 VPN 网段可能只被标为 hosting provider。

出口 IP 分类描述地址的归属或已知用途，无法单独还原具体转发协议。保持端到端 TLS 的代理通常还会保留客户端握手特征，因此 TLS 指纹也不能简单视为代理程序的指纹。确认完整路径需要客户端配置、可信代理或 VPN 日志等额外证据。目标服务器的一条访问日志通常只能支持有限推断。

6. Tinyproxy 部署

代理部署包含服务端监听和客户端选路两部分。验证时先用显式指定代理的 curl 请求检查服务，再配置 macOS 应用，可以分别确认代理链路和系统设置是否生效。

监听配置

本地示例将 Tinyproxy 绑定到 IPv4 loopback 127.0.0.1:18888。该地址可供本机进程访问，包括其他登录用户的进程。macOS 上的安装命令依赖 Homebrew：

brew install tinyproxy

Debian / Ubuntu VM 使用对应的系统包。软件包可能同时启动发行版的默认服务；本例使用独立配置和 18888 端口：

sudo apt-get update
sudo apt-get install tinyproxy

在运行代理的机器上创建配置文件，并启动前台进程：

proxy_demo_dir="$HOME/.config/tinyproxy-demo"
mkdir -p "$proxy_demo_dir"
cat > "$proxy_demo_dir/tinyproxy.conf" <<'EOF'
Port 18888
Listen 127.0.0.1
Timeout 600
Allow 127.0.0.1
ConnectPort 443
EOF

tinyproxy -d -c "$proxy_demo_dir/tinyproxy.conf"

Listen 和 Port 确定监听端点，Allow 限制客户端地址。ConnectPort 443 限制 CONNECT 的目标端口；普通 HTTP 转发不受这项端口限制。启动参数 -c 选择配置文件，-d 使进程保持前台运行并输出日志。18888 是非特权端口，启动无需 sudo。参见 Homebrew 安装页、Tinyproxy 快速开始和配置手册。

请求验证

HTTP 请求验证代理能否解析 URL 并转发请求；HTTPS 请求还要验证 CONNECT 之后的 TLS 和源站响应。代理进程保持运行，在另一个终端执行：

curl --noproxy "" --proxy http://127.0.0.1:18888 \
  -v http://example.com/ -o /dev/null

curl --noproxy "" --proxy http://127.0.0.1:18888 \
  -v https://example.com/ -o /dev/null

--proxy 显式选择代理，--noproxy "" 清除本次请求的绕过列表，避免已有 NO_PROXY 影响实验。-v 输出握手，-o /dev/null 丢弃响应正文。

HTTP 请求行应包含完整 URL，响应状态表示这次请求的结果：

> GET http://example.com/ HTTP/1.1
< HTTP/1.1 200 OK

HTTPS 的日志依次包含 CONNECT 响应、TLS 握手和源站响应。以下是 Tinyproxy 1.11.3 在 Linux 上使用上述配置时的实测节选：

> CONNECT example.com:443 HTTP/1.1
< HTTP/1.1 200 Connection established
* SSL connection using TLSv1.3 / TLS_AES_256_GCM_SHA384
*  SSL certificate verify ok.
> GET / HTTP/2
< HTTP/2 200

200 Connection established 表示代理通道已经建立；TLS 握手、证书校验和源站请求发生在此之后。样例中的 CONNECT 使用 HTTP/1.1，源站连接在 TLS 内协商为 HTTP/2，两者彼此独立。具体协议版本、加密套件和响应状态会随环境变化，验证时应确认各阶段均已完成。

客户端配置

macOS 按网络服务保存代理端点。修改前记录服务名称、代理地址、绕过规则和 PAC 设置，便于实验后恢复。命令中的 Wi-Fi 应与第一条命令列出的服务名称一致：

networksetup -listallnetworkservices
networksetup -getwebproxy "Wi-Fi"
networksetup -getsecurewebproxy "Wi-Fi"
networksetup -getproxybypassdomains "Wi-Fi"
networksetup -getautoproxyurl "Wi-Fi"
scutil --proxy

对于没有需要保留的 PAC 或管理策略的网络服务，以下命令分别设置 HTTP 和 HTTPS 的代理端点：

sudo networksetup -setwebproxy "Wi-Fi" 127.0.0.1 18888 off
sudo networksetup -setsecurewebproxy "Wi-Fi" 127.0.0.1 18888 off

这两条命令会启用对应代理，末尾的 off 表示关闭代理身份认证。GUI 的 HTTP 和 HTTPS 项也应分别填写地址 127.0.0.1、端口 18888；只设置 HTTP 不会同时设置 HTTPS。参数定义见 Mac 上的 networksetup -help 和 Apple 的 networksetup 文档。

scutil --proxy 用于核对系统发布的配置，Tinyproxy 日志则用于确认请求确实到达代理。采用系统配置的浏览器访问外部网站后，日志应出现对应请求；若未出现，应检查绕过域名、应用覆盖配置和旧连接复用。

终端程序使用各自支持的配置入口。curl 除了接受 --proxy，还可以读取当前 shell 的环境变量：

export http_proxy=http://127.0.0.1:18888
export https_proxy=http://127.0.0.1:18888

https_proxy 指定 HTTPS 目标使用的代理，值中的 http:// 指定连接代理的协议。因此，这两个变量可以使用同一个 HTTP 代理地址。其他程序支持哪些变量，由其自身实现决定。

配置恢复

如果两项系统代理在实验前均为关闭状态，恢复命令为：

sudo networksetup -setwebproxystate "Wi-Fi" off
sudo networksetup -setsecurewebproxystate "Wi-Fi" off

如果原先已有代理，应恢复记录下来的原值。若两个环境变量也是本次新设的，再执行 unset http_proxy https_proxy；原先存在则恢复原值。最后回到 Tinyproxy 的终端按 Ctrl-C 停止服务。

VPN 内监听

前面的 Tinyproxy 示例只监听 loopback。若要作为仅 VPN 可达的代理，可以在拥有 10.77.0.1 的 VPN VM 上，将独立配置的监听与客户端允许范围改为：

Listen 10.77.0.1
Allow 10.77.0.2
Port 18888
ConnectPort 443

这里 10.77.0.1 是 VPN 原理与路由 中服务器自己的地址；第四篇使用的 10.77.0.10 是另一个场景中的内网代理。监听地址必须确实属于本机，并配合主机防火墙与认证策略限制访问。Mac 可用 curl --noproxy "" --proxy http://10.77.0.1:18888 https://example.com/ 验证两段连接。

7. 故障排查

代理请求依赖本地监听、代理到源站的连接，以及最终应用协议。最早失败的阶段决定排查范围。在运行 Tinyproxy 的 Mac 上，监听状态可由以下命令确认：

lsof -nP -iTCP:18888 -sTCP:LISTEN

Linux VM 上对应的检查命令是 ss -ltnp 'sport = :18888'。监听正常后，HTTP 与 HTTPS 验证请求可将失败范围缩小到代理握手、远端连接或 TLS。结合前台日志判断具体原因：

HTTP proxies and application configuration

HTTP proxies provide request forwarding and tunnels for web applications, with uses including egress management, access control and application-specific network access. This article covers HTTP forwarding and CONNECT, the scope of macOS settings, Electron launch options and environment variables, and the operation of private proxies over VPNs. It also examines what an origin server can observe and provides a Tinyproxy deployment guide.

1. HTTP proxy mechanics

Explicit forward proxies suit managed web egress, request logging and authentication, per-application exit selection, and access through a permitted intermediary. They require application support; enabling a proxy does not automatically relay arbitrary sockets, ICMP or UDP.

ObjectProtocol positionUnit handled
HTTP/1.1 proxyTCP/IP application layer, typically OSI L7HTTP messages
CONNECTApplication-level setup, then byte relayTarget host:port, followed commonly by origin TLS
TCP / IPTransport / networkThe current connection and its route
Layer-3 VPNIP-path interface with a separate outer encapsulationWhole inner IP packets

HTTP forwarding requires the proxy to parse requests. HTTPS through CONNECT switches to relaying TLS bytes after setup. Both modes use separate TCP connections on either side of the proxy, but expose different application data to it.

HTTP forwarding

An HTTP proxy obtains the destination from the full URL in the request line. For http://example.com/docs, the client connects to the proxy and sends the request below. The proxy resolves example.com, opens or reuses an origin connection, and forwards the request. The diagram shows new connections.

GET http://example.com/docs HTTP/1.1
Host: example.com

This request target is called absolute-form. Toward the origin, the proxy typically sends GET /docs HTTP/1.1, using origin-form. The two TCP connections have independent sequence numbers, retransmissions and flow control. Plain HTTP content is visible to the proxy. See RFC 9112 §3.2.

CONNECT tunneling

CONNECT establishes a byte stream for a TLS session between client and origin. Through an ordinary HTTP proxy, the client requests a destination hostname and port:

CONNECT example.com:443 HTTP/1.1
Host: example.com:443

After connecting to example.com:443, the proxy returns a successful 2xx response and switches to bidirectional byte forwarding. The client completes its TLS handshake with the origin through that stream, then sends encrypted HTTP requests. Those TLS bytes need no additional GET or POST wrapper. RFC 9110 §9.3.6 defines the transition.

Client and origin maintain the TLS session while the proxy relays its bytes between two TCP connections. The proxy sees the CONNECT hostname and port, traffic sizes and timing. Normal forwarding gives it no origin TLS session keys and no direct access to the HTTPS body. TLS inspection using an additional trusted certificate changes this encryption boundary. The green arrows identify logical TLS endpoints; the bytes still traverse both TCP legs. TLS 1.3 overview.

HTTPS proxies and TLS

The macOS Secure Web Proxy (HTTPS) field selects the proxy for HTTPS destination URLs. Chromium maps this setting to an ordinary HTTP proxy, so the field name does not establish TLS on the client-to-proxy connection. GetProxyServerScheme() explains the naming distinction.

curl's --proxy https://proxy.example:8443 instead specifies TLS to the proxy. For an HTTPS origin, that outer TLS session carries CONNECT and the inner TLS session between client and origin. The two handshakes have different peers. The tutorial uses http://127.0.0.1:18888, where one Tinyproxy listener handles HTTP forwarding and HTTPS CONNECT. curl proxy prefixes.

2. macOS proxy settings

Configuration scope

Proxy settings belong to the selected network service. System Settings → Network → Wi-Fi or Ethernet → Details → Proxies provides separate HTTP, HTTPS, SOCKS, PAC and bypass entries. Wi-Fi and Ethernet retain separate configurations. Apple proxy settings guide.

Applications read that policy through their networking libraries. Apple's URLSessionConfiguration.connectionProxyDictionary uses system settings by default and allows an application to supply its own configuration. Two applications on the same Mac can therefore select different connection paths. URLSession documentation.

Traffic sourceEffect of setting only the macOS HTTP / HTTPS proxy
Browser or URLSession app using system policySelects a proxy or direct access according to URL scheme, bypass rules and PAC, subject to application overrides.
Command-line curlNormally needs --proxy or supported environment variables. Do not assume it reads the GUI setting.
Raw BSD sockets or a normal ssh invocationConnects to the address the program specifies. Proxying needs explicit support or a separate forwarding mechanism.
ping or arbitrary UDPDoes not turn into HTTP traffic.

System proxy coverage depends on which applications adopt the configuration. Shell environment variables are a separate input: changing the GUI does not set http_proxy in a terminal, and setting that variable does not update the system proxy. curl documents the variables it supports in its proxy environment reference.

Connection setup

For https://example.com/docs, an application using proxy policy evaluates the URL and rules before selecting an endpoint. If it selects proxy.example:18888, it opens a TCP socket to that address. The kernel routes packets to the proxy; the application writes the CONNECT handshake to the connection.

URL: https://example.com/docs
  → application / network library evaluates proxy policy
  → selects proxy.example:18888
  → socket.connect(proxy_ip, 18888)
  → TCP / IP delivers bytes to the proxy
  → application sends CONNECT example.com:443

HTTP requests and CONNECT handshakes are application data carried by the kernel. A bypass match selects a direct connection. A program that does not read proxy settings retains its own destination-selection logic. Chromium's macOS configuration reader shows how system settings enter an application's proxy policy.

3. Electron proxy configuration

Network libraries and sessions

An Electron application can use Chromium requests, Node.js requests, native modules and child processes. Proxy scope follows the request implementation, not simply the process name. In particular, renderer fetch and Node fetch have different network backends.

Request sourceImplementationConfiguration to inspect
Page loads, renderer fetch / XHR / WebSocketChromium and the associated SessionSession proxy, Chromium switches or OS settings
electron.net.fetch() / net.request()ChromiumDefault or explicitly selected Session; ses.fetch() uses that Session
Node http / https / built-in fetchNode agents / dispatchersVersion-specific environment support or explicit proxy implementation
Native code, children, update componentsImplementation-specificTheir own configuration; window behavior is insufficient evidence

Electron net uses Chromium networking; Node built-in fetch uses the Node stack. Configuring a window Session does not redirect arbitrary Node sockets. Electron net API.

Command-line configuration

For Chromium requests using default proxy configuration, --proxy-server overrides the OS setting. Quit the application normally, then launch its actual executable with the appropriate name and address. A single-instance application may otherwise hand startup arguments to an existing process without rebuilding its network context.

"/Applications/Example.app/Contents/MacOS/Example" \
  --proxy-server="http://10.77.0.10:18888" \
  --log-net-log="$HOME/Desktop/example-netlog.json"

The switch selects a proxy for affected HTTP, HTTPS and WebSocket traffic; it does not redirect every packet from the process. NetLog records Chromium activity. Bypass rules are separate, and --no-proxy-server overrides other proxy switches. Credentials embedded in this switch URL are not supported as a general authentication mechanism. Electron switches.

Explicit session configuration

Developers can configure a dedicated Session before opening a window or issuing requests. This example binds the window to the same configured Session:

const { app, BrowserWindow, session } = require('electron');

app.whenReady().then(async () => {
  const ses = session.fromPartition('persist:internal');
  await ses.setProxy({
    mode: 'fixed_servers',
    proxyRules: 'http://10.77.0.10:18888',
    proxyBypassRules: 'localhost,127.0.0.1,[::1]'
  });
  await ses.closeAllConnections();
  console.log(process.versions);
  console.log(await ses.resolveProxy('https://example.com/'));

  const win = new BrowserWindow({ webPreferences: { session: ses } });
  await win.loadURL('https://example.com/');
}).catch(console.error);

resolveProxy() reports selection, not reachability or request success. Pooled connections can retain an earlier path. Closing this Session’s connections permits a fresh check, but interrupts those connections; do it at startup or when reconnection is acceptable. Session API.

ProxyConfig selects one mode: system, direct, fixed servers, PAC or automatic discovery. Explicit system is different from leaving configuration unset, which can still honor command-line options. Failure of a single fixed proxy does not imply fallback to the OS proxy; a fallback must be supplied by the active list or application logic. ProxyConfig.

Environment variables

export http_proxy=http://10.77.0.10:18888
export https_proxy=http://10.77.0.10:18888
export no_proxy=localhost,127.0.0.1,::1
"/Applications/Example.app/Contents/MacOS/Example"

These variables enter the terminal’s process environment and its descendants. Finder or Dock launches generally do not inherit exports from that shell. Even inherited values need a network library that reads them. HTTP_PROXY, HTTPS_PROXY, ALL_PROXY and NO_PROXY are not OS-level packet-redirection commands. Naming, case and bypass semantics differ among clients. curl environment conventions.

Recent standalone Node versions offer environment proxy support when enabled for supported APIs. For example:

NODE_USE_ENV_PROXY=1 HTTPS_PROXY=http://10.77.0.10:18888 \
  node -e "require('node:https').get('https://example.com/', r => { console.log(r.statusCode); r.resume(); })"

The Node HTTP documentation marks built-in proxy support as introduced in v24.5.0 and v22.21.0. Electron’s bundled version and supported startup options must be checked separately; standalone Node behavior does not establish renderer behavior. Record process.versions for the actual runtime. Node proxy support; Electron environment variables.

4. A proxy behind a VPN

Client-to-proxy connection

Suppose 10.77.0.10:18888 is reachable only over VPN. The application selects that proxy and opens TCP to its address. Routing therefore looks up the proxy IP, even when the URL identifies a public origin such as example.com.

Proxy-to-origin connection

After receiving CONNECT, the proxy resolves the origin and uses its own host routes. Its connection may use a public NAT, another VPN or an explicitly configured upstream proxy. The Mac’s system proxy settings are not transmitted to that machine.

Reaching a private proxy and reaching the origin from that proxy are separate conditions. A working VPN can still lead to a failed CONNECT if proxy egress is unavailable. The origin-facing address belongs to that second leg. VPN fundamentals and routing explains the packet tunnel.

5. Origin visibility

A destination directly observes the connection source and the application data it receives. CONNECT, SOCKS, SSH and VPN encapsulation end at their respective intermediaries. Identifying a proxied request therefore involves distinguishing protocol evidence from inferences about the source address.

Connection and request data

The observation point here is the server accepting the site's public connections. With a CDN or load balancer, a backend instead sees that intermediary as its immediate peer and needs trusted forwarding information to identify the external connection source.

Access pathDirectly visible to the destinationNot automatically delivered
Plain HTTP forward proxyProxy egress or upstream NAT address; forwarded HTTP, possibly with forwarding headersA complete record of all preceding network hops
HTTPS through ordinary CONNECT / SOCKSProxy egress address and the client's TLS handshake and enclosed requestsThe CONNECT or SOCKS handshake, which ends at the proxy
SSH -L / -DThe source of sshd's target-side connection, including client TLS when preserved end to endSSH headers or encrypted channels, which end at sshd
VPN with internet egress NATVPN egress NAT address and client application trafficThe outer VPN encapsulation between client and gateway
Routed VPN without NATThe routed client source, such as its assigned corporate tunnel addressOuter VPN headers and tunnel setup exchanges

HTTP requires proxies to append Via to forwarded HTTP messages. Forwarded or X-Forwarded-For can additionally carry client information, depending on implementation and configuration. Accepting those fields requires a trusted proxy relationship: client-supplied headers do not establish the actual route. Deployed proxies may also omit such fields, so their absence does not prove a direct connection. See Via semantics and Forwarded trust considerations.

A CONNECT relay preserving origin TLS cannot change enclosed HTTP headers without breaking TLS integrity. A packet VPN generates no HTTP forwarding headers itself. Accounts, cookies and other data sent by the application still reach the site; changing the exit address does not remove that identity information.

Exit IP classification

Internet requests carry no universal field declaring the use of VPN, SOCKS or SSH. Servers can compare source addresses against known VPN, public proxy and hosting networks, then combine those classifications with account and behavioral signals. MaxMind's Anonymous IP fields provide these categories and note that some VPN ranges may appear only as hosting providers.

An exit-address category describes ownership or known use, without establishing the forwarding protocol. A relay preserving origin TLS normally also preserves the client's handshake characteristics, so its TLS fingerprint does not simply become the proxy's fingerprint. Confirming the complete route requires additional evidence such as client configuration or trusted proxy and VPN logs. A destination access log usually supports a narrower inference.

6. Tinyproxy deployment

A working proxy requires both a listener and clients configured to use it. Explicit curl requests test the service independently of macOS settings; application configuration can then be verified against that working connection path.

Listener setup

The local example binds Tinyproxy to IPv4 loopback 127.0.0.1:18888. Local processes, including those of other logged-in users, can reach this address. Installation on macOS uses Homebrew:

brew install tinyproxy

Debian / Ubuntu VMs use the distribution package. Installation may also start a default service; this example uses its own configuration and port 18888:

sudo apt-get update
sudo apt-get install tinyproxy

Create the configuration and start the foreground process on the machine hosting the proxy:

proxy_demo_dir="$HOME/.config/tinyproxy-demo"
mkdir -p "$proxy_demo_dir"
cat > "$proxy_demo_dir/tinyproxy.conf" <<'EOF'
Port 18888
Listen 127.0.0.1
Timeout 600
Allow 127.0.0.1
ConnectPort 443
EOF

tinyproxy -d -c "$proxy_demo_dir/tinyproxy.conf"

Listen and Port select the listening endpoint; Allow restricts client addresses. ConnectPort 443 restricts CONNECT destinations, without applying that port restriction to ordinary HTTP forwarding. -c selects the configuration file and -d keeps the process in the foreground with terminal logs. Port 18888 requires no root privileges. Sources: Homebrew formula, Tinyproxy quick start, configuration manual.

Request verification

The HTTP request tests URL parsing and forwarding. HTTPS also tests TLS and the origin response after CONNECT. With the proxy running, execute these requests in another terminal:

curl --noproxy "" --proxy http://127.0.0.1:18888 \
  -v http://example.com/ -o /dev/null

curl --noproxy "" --proxy http://127.0.0.1:18888 \
  -v https://example.com/ -o /dev/null

--proxy selects the endpoint explicitly. --noproxy "" clears the bypass list for this invocation, including effects from an existing NO_PROXY. -v shows protocol details; -o /dev/null discards the body.

The HTTP request line contains the full URL, followed by the response status:

> GET http://example.com/ HTTP/1.1
< HTTP/1.1 200 OK

The HTTPS log contains a CONNECT response, a TLS handshake and an origin response. This excerpt was recorded with Tinyproxy 1.11.3 on Linux using the configuration above:

> CONNECT example.com:443 HTTP/1.1
< HTTP/1.1 200 Connection established
* SSL connection using TLSv1.3 / TLS_AES_256_GCM_SHA384
*  SSL certificate verify ok.
> GET / HTTP/2
< HTTP/2 200

200 Connection established confirms the proxy tunnel. TLS negotiation, certificate validation and the origin request follow it. The sample uses HTTP/1.1 for CONNECT and HTTP/2 negotiated with the origin inside TLS; those versions are independent. Versions, cipher suites and response codes can vary, so verification checks completion of each stage.

Client configuration

macOS stores proxy endpoints per network service. Record the service name, proxy values, bypass rules and PAC configuration before changing them so the original state can be restored. Replace Wi-Fi with the name listed by the first command:

networksetup -listallnetworkservices
networksetup -getwebproxy "Wi-Fi"
networksetup -getsecurewebproxy "Wi-Fi"
networksetup -getproxybypassdomains "Wi-Fi"
networksetup -getautoproxyurl "Wi-Fi"
scutil --proxy

For a service without an existing PAC or managed policy to preserve, set the HTTP and HTTPS endpoints separately:

sudo networksetup -setwebproxy "Wi-Fi" 127.0.0.1 18888 off
sudo networksetup -setsecurewebproxy "Wi-Fi" 127.0.0.1 18888 off

These setters enable their respective proxies. The trailing off disables proxy authentication. The GUI likewise needs address 127.0.0.1 and port 18888 in both HTTP and HTTPS entries; setting HTTP alone leaves HTTPS unchanged. Parameter definitions are available in networksetup -help and Apple's networksetup documentation.

scutil --proxy verifies the published system configuration; Tinyproxy logs establish that a request reached the proxy. An external website request from a browser using system policy should appear in those logs. Missing requests call for checking bypass rules, application overrides and reused connections.

Terminal programs use their own configuration inputs. In addition to --proxy, curl accepts environment variables from the current shell:

export http_proxy=http://127.0.0.1:18888
export https_proxy=http://127.0.0.1:18888

https_proxy selects the proxy for HTTPS destinations, while http:// in its value selects the protocol used to connect to the proxy. Both variables can therefore name the same HTTP proxy. Support in other programs depends on their implementation.

Configuration restoration

If both system proxy entries were disabled before the experiment, restore that state with:

sudo networksetup -setwebproxystate "Wi-Fi" off
sudo networksetup -setsecurewebproxystate "Wi-Fi" off

If a proxy was already configured, restore its recorded values instead. Run unset http_proxy https_proxy only if those variables were newly introduced; otherwise restore their earlier values. Finally press Ctrl-C in the Tinyproxy terminal.

Listening inside the VPN

The earlier Tinyproxy example binds loopback. On the VPN VM that owns 10.77.0.1, a separate VPN-facing instance can instead use:

Listen 10.77.0.1
Allow 10.77.0.2
Port 18888
ConnectPort 443

10.77.0.1 is the server address from the VPN fundamentals and routing lab; 10.77.0.10 belongs to the separate routing scenario. The bind address must exist locally. Apply host filtering and authentication appropriate to the intended clients. From the Mac, curl --noproxy "" --proxy http://10.77.0.1:18888 https://example.com/ tests both connection legs.

7. Troubleshooting

A proxied request depends on a local listener, the proxy's origin connection and the final application protocol. The earliest failing stage determines where to investigate. On a Mac hosting Tinyproxy, inspect the listener with:

lsof -nP -iTCP:18888 -sTCP:LISTEN

On a Linux VM, the equivalent check is ss -ltnp 'sport = :18888'. Once the listener is available, the HTTP and HTTPS verification requests narrow failures to proxy negotiation, the remote connection or TLS. Correlate the result with the proxy's foreground log:

ObservationFirst checks
Connection to proxy refusedProcess, port and bind address. Mac and VM loopback addresses name different machines.
Connection to proxy times outRoute, firewall and listening interface. A successful ping does not establish TCP port reachability.
407 Proxy Authentication RequiredThe proxy responded; inspect client credentials and proxy authentication settings.
CONNECT returns non-2xxAllow rules, ConnectPort, proxy-side DNS and target TCP access. Use logs rather than inferring the cause from one status code.
TLS fails after CONNECT 200Certificate, trust chain, hostname and protocol. -k hides certificate failures and is not a successful verification.
Browser works, terminal tool failsEach program's actual configuration, environment and bypass list.
curl works, browser bypasses proxyActive network service, HTTPS field, PAC, exceptions and browser overrides; create a new connection and inspect logs.

curl -v records client-side connection and protocol progress. Proxy logs describe request handling and origin connections; SSH's -v adds tunnel setup information. Correlating those observations for one request locates the failing segment and the configuration or access policy to inspect.
