Roofline 性能模型可视化

Roofline 把计算吞吐与内存带宽放在同一张图上：硬件决定屋顶线，负载的算术强度决定它落在屋顶线的哪一段。这个工具支持叠加多张 GPU 的屋顶线，并通过矩阵形状、数据类型和 Attention 参数观察理论上限的变化。

交互工具

添加硬件和负载后，将鼠标移到交点，查看算术强度、带宽约束和计算上限。窄屏下图表位于参数面板上方；复杂对比可独立打开工具。

Roofline Performance Visualization

Roofline places compute throughput and memory bandwidth on the same chart. Hardware defines the ceiling; a workload’s arithmetic intensity determines which part of that ceiling applies. Overlay GPU rooflines and change matrix dimensions, data types, or attention shapes to explore their theoretical bounds.

读图与单位

横轴是算术强度 I = FLOPs / Bytes，单位为 FLOP/Byte；纵轴是 TFLOP/s。设峰值算力为 P（TFLOP/s），HBM 带宽为 B（GB/s），模型给出的上限与转折点分别为：

性能上限 = min(P, B × I / 1000)
转折点 I* = 1000 × P / B

斜线段受带宽限制，水平段受计算吞吐限制。图中的交点是负载在这些假设下的理论上限，不是实测性能。这一关系来自 Berkeley Lab 的 Roofline 模型。

操作说明

  • Hardware Rooflines：从预设库选择 GPU 和精度，或输入自定义的峰值算力与带宽。列表支持编辑、隐藏和删除。
  • Workloads：选择 GEMM、Batched GEMM 或 Attention，设置形状和元素精度，再添加到图中。参数修改后，算术强度会重新计算。
  • X log / Y log：分别切换两轴的线性与对数刻度。Fit 按当前可见数据调整范围，Reset 恢复示例配置。

硬件、负载和坐标轴选项保存在当前浏览器的本地存储中，刷新页面可以恢复。计算在浏览器中完成，不需要 GPU 或后端服务。

负载假设

GEMM

对 A[M,K] × B[K,N] → C[M,N]，乘加按 2 FLOPs 计算。设每个元素占 b 字节，工具使用：

FLOPs = 2MNK
Bytes = (MK + KN + MN) × b

这个字节数对应读取 A、B 各一次并写回 C 一次，不包含读取旧 C、额外的中间结果或重复 HBM 访问。Batched GEMM 假设各 batch 使用独立矩阵，FLOPs 和 Bytes 同乘 batch 数，因此该模型中的算术强度保持不变。

Attention

Attention 使用非 causal 的两个矩阵乘近似：设 batch 为 B、head 数为 H、序列长度为 S、head dim 为 D，则 FLOPs 为 4BH S²D。理想 HBM 流量只统计 Q、K、V 的读取和 O 的写回，为 4BHSDb。

这是假设注意力矩阵不写回 HBM 的理想估算，忽略 softmax 等额外运算，也忽略 tiling 导致的数据重复读取。它不是任意 FlashAttention 实现的实际访存量。

比较边界

硬件预设沿用迁移时的参考值，方便构建模型；精确分析应核对具体型号、功耗配置、计算指令和数据类型。负载元素精度决定字节数，硬件精度决定计算上限，工具不会自动替你匹配两者。比较 FP16 负载时，应选择相应的 FP16 算力，而不是直接套用 FP8 峰值。

真实负载还受到缓存、占用率、指令效率和启动开销等因素影响。Roofline 用于建立约束和解释测量结果；要判断实际性能，应结合 profiler 获得同一内存层级的流量与执行时间。

Reading the chart

The horizontal axis is arithmetic intensity, I = FLOPs / Bytes, in FLOP/Byte; the vertical axis is TFLOP/s. With peak compute P in TFLOP/s and HBM bandwidth B in GB/s:

Performance ceiling = min(P, B × I / 1000)
Ridge point I* = 1000 × P / B

The sloping segment is bandwidth-bound; the plateau is compute-bound. Intersections show theoretical bounds, not measured performance, following Berkeley Lab’s Roofline model.

Controls

  • Hardware Rooflines: select a GPU and precision from the preset library, or enter custom peak throughput and bandwidth. Edit, hide, or remove entries in the list.
  • Workloads: select GEMM, batched GEMM, or attention, configure dimensions and element precision, then add the workload. Editing its parameters recalculates its intensity.
  • X log / Y log: switch each axis between linear and logarithmic scales. Fit adjusts the range to visible data; Reset restores the example.

Hardware, workloads, and axis settings persist in this browser’s local storage. All calculations run in the browser; no GPU or backend service is required.

Workload assumptions

GEMM

For A[M,K] × B[K,N] → C[M,N], a multiply-add counts as 2 FLOPs. With b bytes per element:

FLOPs = 2MNK
Bytes = (MK + KN + MN) × b

The byte count assumes one read of A and B and one write of C. It omits reading an old C, extra intermediates, and repeated HBM accesses. Batched GEMM assumes independent matrices, multiplying both counts by the batch size; intensity therefore stays unchanged in this model.

Attention

The non-causal attention approximation counts two matrix products: 4BH S²D FLOPs for batch B, heads H, sequence length S, and head dimension D. Ideal HBM traffic counts only reads of Q, K, V and a write of O: 4BHSDb bytes.

This assumes the attention matrix is never written to HBM. It omits softmax and other operations, as well as repeated reads caused by tiling. It does not predict the actual traffic of an arbitrary FlashAttention implementation.

Comparison limits

Hardware presets retain the reference values from the migrated tool. For a precise analysis, verify the device variant, power configuration, instruction path, and data type. Workload precision controls byte counts; hardware precision controls peak compute. The tool does not match them automatically. An FP16 workload should use an appropriate FP16 ceiling rather than an FP8 peak.

Cache behavior, occupancy, instruction efficiency, and launch overhead can reduce achieved performance. Use profiler measurements of traffic at the same memory level and execution time to assess a real workload.
