CUDA Graph 与 autocast：backward 应在 context 之外执行

Autocast 应只包住 forward 和 loss 计算，backward 应在启用的 autocast context 之外执行。这条规则也适用于 CUDA Graph capture。make_graphed_callables() 内部也会执行 backward。若调用这个 API 时 autocast 开着，backward 就可能在错误的精度环境下被捕获；之后即使在 autocast 外调用 loss.backward()，仍会重放这张已经捕获的图。在 autocast 下执行 backward 会带来两个不同层面的副作用：一是重新 cast backward 的操作数，改变梯度计算的精度；二是在 autograd worker 上意外启用 cast cache，使 graph 依赖一个可能在 replay 前失效的张量地址。

规则：forward 决定精度路径，backward 沿图执行

PyTorch 的 AMP 文档建议只对 forward 和 loss 开启 autocast。常规写法的边界非常明确：

with torch.autocast("cuda", dtype=torch.bfloat16):
    output = model(x)
    loss = loss_fn(output, target)

loss.backward()

Forward 已经确定了算子实际收到的 dtype、保存给 backward 的 tensor，以及需要沿反向图传播的 cast 关系。例如，一个 FP32 参数在 forward 中先 cast 到 BF16，再参与矩阵乘法，反向图就会包含把对应梯度传回 FP32 参数的转换。Backward 不需要重新开启 autocast 来“找回”这条精度路径。

“Backward 的 dtype 由 forward 决定”在这里指沿 forward 建立的计算图和各 backward 算子的规则执行。它不表示所有反向中间值或累加器必须是同一种 dtype，也不表示关闭 autocast 后整个 backward 就会变成 FP32。Forward 中刻意保留的 FP32 子区域，其反向计算同样不应被外层 autocast 再次降精度。

本文范围：标准 eager autograd 与 torch.cuda.make_graphed_callables，源码固定为 PyTorch v2.12.0。下文的 worker 状态传播缺口属于该版本实现，不应直接推广到所有版本；torch.compile 与自定义 autograd.Function 的 AMP 协议需要单独分析。

隐藏在 make_graphed_callables 里的 backward

下面的代码看上去只是在用 AMP 捕获模型，但它把内部 backward 一起放进了 autocast：

with torch.autocast(
    "cuda",
    enabled=True,
    dtype=torch.bfloat16,
    cache_enabled=False,
):
    graphed = torch.cuda.make_graphed_callables(model, (x,))

make_graphed_callables() 会 warmup forward/backward，随后分别捕获 forward graph 和 backward graph。固定版本的 warmup 与 backward capture 都通过 torch.autograd.grad() 执行反向计算，调用周围没有关闭 autocast。于是，API 调用时的外层 context 同时影响 forward 和 backward。

  1. Warmup执行 forward，再调用 autograd；此时已经可能产生 backward cast 和 cache。
  2. Capture forward记录模型 forward 发起的 CUDA 工作。
  3. Capture backward再次调用 autograd，记录它实际发起的 CUDA 工作及使用的地址。
  4. Replay重放已经捕获的 kernel 与参数；不会重新运行原始 Python forward 或逐个重新 dispatch 原始 backward 算子。

因此，在训练循环中把 loss.backward() 放到 autocast 外，只能保证那次调用的环境正确。如果 backward graph 在 capture 时已经录错，replay 时关闭 autocast 不会重写图中的 cast、GEMM 或地址参数。PyTorch issue #120930也报告了这类 eager 与 graphed backward 不一致的问题。

副作用一：backward 额外 cast，破坏 FP32 计算语义

用一个明确要求 FP32 的线性层来隔离问题。参数是 FP32，输入也提供 FP32；forward 内部显式关闭 autocast：

import torch


class FP32Linear(torch.nn.Module):
    def __init__(self):
        super().__init__()
        self.linear = torch.nn.Linear(
            1, 1, bias=False, device="cuda", dtype=torch.float32
        )
        with torch.no_grad():
            self.linear.weight.fill_(1.0)

    def forward(self, x):
        with torch.autocast("cuda", enabled=False):
            return self.linear(x)

设 x = [[1.001]]、w = [[1.0]]，loss 为输出求和。数学上 y = x · w，所以 ∂loss/∂w = x，FP32 基线应保留约 1.001 的梯度。

Forward 内的 enabled=False 只作用于当时的动态执行范围。函数返回后，外层 BF16 autocast 恢复；稍后 API 调用 autograd.grad() 时，它仍然开启。FP32 forward 创建的 backward node 内部会调用矩阵乘法，而 mm 本身就是 autocast 可以拦截的算子。

这一点可从 mm_mat1_backward / mm_mat2_backward 与 CUDA lower-precision 算子列表交叉确认：backward 的实现调用 mm，而 mm 在 BF16 autocast 下会转换符合条件的 FP32 操作数。它不会因为这次调用来自 backward，就自动跳过 autocast。

阶段正确的 FP32 路径Backward 被 BF16 autocast 包住
ForwardFP32 输入与权重，FP32 输出同样是 FP32，表面看不出差别
计算权重梯度使用保存的 FP32 输入与 FP32 上游梯度操作数先 cast 到 BF16，再执行矩阵乘法
数值约 1.001BF16(1.001) = 1.0，结果约为 1.0
最终 weight.gradFP32，保留基线精度可以仍为 FP32，但先前丢失的精度无法恢复

最后一行很容易误导排查：autograd 在校验返回梯度时，可以按目标 metadata 把梯度转回 FP32，见 validate_outputs()。因此，检查 weight.grad.dtype == torch.float32 不足以证明 backward 的数值路径正确。这种错误可能静默发生，同时多出 FP32 → BF16、BF16 → FP32 的转换。

把梯度差异与 cache 问题分开观察

下面的代码接在 FP32Linear 定义后运行。这里刻意让 x.requires_grad=False，只求权重梯度；其 backward 的矩阵乘法操作数不满足后文的 leaf cache 条件，从而集中观察第一个副作用。该设置仅用于这个最小例子。

# Requires a CUDA device with BF16 support.
torch.backends.cuda.matmul.allow_tf32 = False
torch.set_printoptions(precision=7)
x = torch.tensor([[1.001]], device="cuda", dtype=torch.float32)

baseline = FP32Linear()
bad = FP32Linear()
good = FP32Linear()

# Reference: forward under the outer context; backward outside it.
with torch.autocast("cuda", dtype=torch.bfloat16, cache_enabled=False):
    reference_y = baseline(x)
reference_y.sum().backward()
reference_grad = baseline.linear.weight.grad.detach().clone()

# Wrong boundary: the API's internal backward also sees autocast.
with torch.autocast("cuda", dtype=torch.bfloat16, cache_enabled=False):
    bad = torch.cuda.make_graphed_callables(bad, (x,))

# This whole model requests FP32, so capture needs no enabled autocast.
with torch.autocast("cuda", enabled=False):
    good = torch.cuda.make_graphed_callables(good, (x,))

bad.zero_grad(set_to_none=True)
good.zero_grad(set_to_none=True)
bad_y = bad(x)
bad_y.sum().backward()
good_y = good(x)
good_y.sum().backward()
torch.cuda.synchronize()

print("reference:", reference_grad)
print("bad:      ", bad.linear.weight.grad)
print("good:     ", good.linear.weight.grad)
print("bad grad dtype:", bad.linear.weight.grad.dtype)
print("bad equals reference:", torch.equal(
    bad.linear.weight.grad, reference_grad
))

torch.testing.assert_close(bad_y, reference_y, rtol=0, atol=0)
torch.testing.assert_close(good_y, reference_y, rtol=0, atol=0)
torch.testing.assert_close(
    good.linear.weight.grad, reference_grad, rtol=0, atol=0
)

在上述受影响路径下，预期 reference/good 的权重梯度约为 1.001，bad 约为 1.0，三者的 forward 输出一致。这里给出的是由固定版本源码与 BF16 舍入推导的预期，未作为 GPU 实测输出；实际运行时应记录 PyTorch 版本与 GPU 型号。

副作用二：worker 意外启用 cache，replay 引用失效地址

第二个副作用还需要额外条件：backward 中出现可缓存的 cast，并且捕获的 graph 依赖了不能跨 replay 保持有效的缓存存储。它解释了为什么外层已经写了 cache_enabled=False，仍可能发生 illegal memory access（IMA）。

Thread-local 不等于所有状态都会一起传播

在这里讨论的 CUDA autograd 路径中，backward node 由 autograd 的设备 worker thread 执行。调用线程创建 GraphTask 时保存 ThreadLocalState；worker 在执行 node 前用 ThreadLocalStateGuard 恢复其中的状态。源码入口分别是 GraphTask::thread_locals_ 与 worker 的 TLS guard。

关键在于，这份快照只保存了指定字段。v2.12.0 的 ThreadLocalState.cpp 保存、恢复 dispatch key set 和各设备的 autocast dtype，却没有保存、恢复 cache_enabled。

状态调用线程Backward worker原因
autocast_enabledTrueTrue开关通过 dispatch key set 传播
CUDA autocast dtypebfloat16bfloat16快照显式传播 dtype 数组
cache_enabledFalse保留 worker 自身值，默认 True该字段未被快照传播
Context nesting已进入外层 context保留 worker 自身 nesting恢复 TLS 不会调用 Python context 的 __enter__

这里的“继承”是 Engine 在任务执行前显式恢复状态，不是操作系统自动复制所有 thread-local 变量。make_graphed_callables() 的入口检查也只读取调用线程的 cache 开关，因此无法排除 worker 上重新启用缓存的路径。

Cache 开关是 thread-local，cache 容器是进程内共享的

还必须区分开关和数据容器。固定版本的 autocast_mode.cpp 中，cache_enabled、dtype 和 nesting 是 thread-local；get_cached_casts() 返回的 cast map 则是由 mutex 保护的共享容器。它以源 tensor 的 TensorImpl* 为 key，并持有低精度 cast tensor。

因此，worker 可以往共享 map 插入缓存，而调用线程退出最外层 autocast context 时，又可以通过 clear_autocast_cache() 清空这个 map。调用线程设置的 cache_enabled=False 既不能阻止另一线程插入，也不会跳过 context 退出时的清理。

cached_cast() 也并非缓存所有转换。主要条件包括：源是 FP32、requires_grad=True、leaf、非 view，目标是当前设备的低精度 dtype，且当前线程允许 cache；实现还排除了 inference mode 和已被特殊缓存管理的 tensor。普通中间 activation 或转置 view 不一定满足这些条件，所以这条路径取决于模型及 backward 实际传给算子的 tensor。

这也能接回同一个 FP32Linear：若把输入改成 requires_grad=True，这个实数 1×1 例子的权重梯度会走 mm_mat2_backward 的布局分支，将保存的输入 x 作为 mm 操作数。此时 x 是 FP32、需要梯度的非 view 叶子，符合缓存条件。于是同一个例子可以从“仅发生额外舍入”进入“backward 还可能建立 cache”的路径；是否最终报 IMA 仍取决于后续存储生命周期。

从 warmup cache 到 replay 的悬空依赖

最清晰的失效路径是在 warmup 中创建 cache，在 capture 中命中它。不能简单把所有情况都概括为“capture 内创建临时 tensor，退出 context 就一定 IMA”：PyTorch 的 graph-private pool 会保护 capture 期间分配的存储，而 warmup 创建的外部缓存并不自动获得同样的保护。

阶段CPU / autocast 行为GPU graph 的依赖
1. Warmup backwardWorker 在 autocast 与 cache 都开启时，将符合条件的 FP32 tensor 转成 BF16，map 持有副本 CC 在 capture 之前分配
2. Capture backward对同一源 tensor 的转换命中 cache，直接返回 CGEMM 记录 C.data_ptr()；这次 cache hit 不会录入重新生成 C 的 cast
3. 退出外层 autocast调用线程 nesting 回到 0，清空共享 map；若没有其他持有者，C 的存储交还 allocatorGraph 中的地址参数仍然保留
4. Replay backward不再执行 Python cache lookup，也不会重新建立 tensor 的所有权继续访问旧地址；存储若已释放或复用，可能 IMA 或读到错误数据

退出 context 的清理见 autocast.__exit__()。CUDA Graph 保存的是 CUDA 工作及地址参数，持有 CUDAGraph 不等于持有每个外部输入 tensor；PyTorch graph memory management 明确要求 replay 使用的地址保持有效。

IMA 是这种生命周期错误的一种结果，不是必然立即出现的症状。Allocator 可能暂时保留那块显存，也可能把它复用给另一个 tensor；于是错误可能表现为旧值、被覆盖的数据、其他 tensor 被破坏，或后续 CUDA 同步点才报告 IMA。即使人为延长 C 的生命周期，若 graph 没有捕获刷新副本的 cast，输入或参数更新后仍可能使用旧的低精度数据。

正确用法：把 autocast 限定在 forward 内

对上面的纯 FP32 模型，直接在 autocast 关闭时调用 make_graphed_callables() 即可。对确实需要混合精度的模型，更通用的办法是让被捕获模块的 forward() 自己管理 autocast，API 的外层保持关闭。这样，每次 forward 返回后，内部 warmup/backward capture 都回到 autocast 关闭的环境。

# Uses FP32Linear from above; it can also wrap a mixed-precision model.
class ForwardAutocast(torch.nn.Module):
    def __init__(self, inner):
        super().__init__()
        self.inner = inner

    def forward(self, x):
        with torch.autocast(
            "cuda", dtype=torch.bfloat16, cache_enabled=False
        ):
            return self.inner(x)


model = ForwardAutocast(FP32Linear())
x = torch.tensor([[1.001]], device="cuda", dtype=torch.float32)

# Forward opts into AMP locally; both internal backward phases see it off.
with torch.autocast("cuda", enabled=False):
    graphed = torch.cuda.make_graphed_callables(model, (x,))

graphed.zero_grad(set_to_none=True)
with torch.autocast("cuda", dtype=torch.bfloat16, cache_enabled=False):
    output = graphed(x)
    loss = output.sum()
loss.backward()
torch.cuda.synchronize()

torch.testing.assert_close(
    graphed.inner.linear.weight.grad, x, rtol=0, atol=0
)

FP32Linear 内层的 enabled=False 仍然生效，因此这个例子的 forward/backward 都保持应有的 FP32 路径。换成普通混合精度模型时，其 forward 仍可按 AMP 规则选择精度，backward 则沿它生成的图执行。保留 cache_enabled=False 是为了满足 graph capture 的缓存约束；关闭 backward 的 autocast 则同时阻止重新选择精度和本文所述的额外缓存路径。

若维护的是自定义 make_graphed_callables 实现，应在 warmup 与 capture 两处 torch.autograd.grad() 周围关闭 autocast，且让 forward 的 AMP 策略与真实训练一致。只改 replay 时的 context，或只修 capture 而留下 warmup，不足以完整纠正这条执行路径。

如何验证这两条路径

首先用前面的数值例子比较 forward 输出和参数梯度。Forward 一致、最终 .grad 也是 FP32，但梯度已经被 BF16 舍入，是第一个问题的直接信号。Profiler 中额外的 cast 可以提供旁证，数值对照才是正确性判断的依据。

然后用一个不做 cacheable 矩阵乘法的探针，单独检查 worker 的 TLS。下面故意在 autocast 内调用 backward，仅用于诊断；在 eager、capture 之外执行它：

import threading
import torch


def show_state(label):
    print(label, {
        "thread": threading.get_ident(),
        "enabled": torch.is_autocast_enabled("cuda"),
        "dtype": torch.get_autocast_dtype("cuda"),
        "cache": torch.is_autocast_cache_enabled(),
    })


class TLSProbe(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x):
        return x * 2

    @staticmethod
    def backward(ctx, grad_output):
        show_state("backward worker")
        return grad_output * 2


x = torch.ones(1, device="cuda", requires_grad=True)
with torch.autocast("cuda", dtype=torch.bfloat16, cache_enabled=False):
    show_state("caller")
    TLSProbe.apply(x).sum().backward()

对默认 cache 开关尚未被其他代码修改的 worker，本文源码对应的预期是：两个线程都看到 autocast 开启、dtype 为 BF16，调用线程看到 cache=False，worker 看到 cache=True。这只能证明状态传播缺口；要确认某次 IMA 的原因，还需要把 cache 插入/命中的 tensor 地址、清理后的存储生命周期与 graph 中的访问对应起来。本文没有把这个探针当作 IMA 的必现复现。

需要维护的边界：forward 决定精度路径，backward 沿图求导；这条边界必须同时成立于普通执行、warmup 和 capture。Replay 只能执行已经捕获的内容，无法补救 capture 时错误的 autocast 状态或失效的外部存储依赖。

CUDA Graphs and Autocast: Backward Should Run Outside the Context

Autocast should cover forward and loss computation; backward should run outside an enabled autocast context. The same boundary matters during CUDA Graph capture. make_graphed_callables() also executes backward internally. If autocast is enabled when this API is called, backward may be captured under the wrong precision settings. A later loss.backward() outside autocast still replays that captured graph. Running backward under autocast can have two effects: backward operands are cast again, changing gradient precision; and an autograd worker can unexpectedly enable the cast cache, leaving the graph dependent on storage that may expire before replay.

Forward establishes the precision path

The PyTorch AMP documentation recommends limiting autocast to forward and loss computation:

with torch.autocast("cuda", dtype=torch.bfloat16):
    output = model(x)
    loss = loss_fn(output, target)

loss.backward()

Forward has already established the actual operand dtypes, tensors saved for backward, and cast relationships recorded in the autograd graph. If an FP32 parameter is cast to BF16 before a forward matrix multiplication, its gradient path includes the conversion back to the FP32 parameter. Backward does not need ambient autocast to recover that path.

“Forward determines backward precision” means following the graph established by forward and the rules of its backward operators. It does not require every intermediate or accumulator to have one dtype, and disabling autocast does not turn all backward computation into FP32. A forward region deliberately kept in FP32 should also retain its intended backward precision.

Scope: standard eager autograd and torch.cuda.make_graphed_callables, with source pinned to PyTorch v2.12.0. The worker-state propagation gap below describes this implementation, not every release. torch.compile and custom autograd.Function AMP protocols require separate treatment.

The backward hidden inside the capture API

This apparently forward-oriented capture also places the API's internal backward under autocast:

with torch.autocast(
    "cuda",
    enabled=True,
    dtype=torch.bfloat16,
    cache_enabled=False,
):
    graphed = torch.cuda.make_graphed_callables(model, (x,))

The API warms up forward and backward, then captures separate graphs for each. Both warmup and backward capture invoke torch.autograd.grad() without disabling the surrounding autocast context.

  1. WarmupRun forward and autograd. Backward casts and cache entries can already be created here.
  2. Capture forwardRecord the CUDA work launched by forward.
  3. Capture backwardRun autograd again and record its CUDA work and address arguments.
  4. ReplayLaunch the recorded work. The original Python forward and individual backward operator dispatches are not rerun.

Moving the later loss.backward() outside autocast fixes the environment of that invocation. It cannot rewrite casts, GEMMs, or address arguments already recorded in the backward graph. PyTorch issue #120930 reports the corresponding discrepancy between eager and graphed backward.

Effect 1: additional casts change FP32 gradient semantics

Consider a linear layer that explicitly requests FP32. Both its parameter and the supplied input are FP32:

import torch


class FP32Linear(torch.nn.Module):
    def __init__(self):
        super().__init__()
        self.linear = torch.nn.Linear(
            1, 1, bias=False, device="cuda", dtype=torch.float32
        )
        with torch.no_grad():
            self.linear.weight.fill_(1.0)

    def forward(self, x):
        with torch.autocast("cuda", enabled=False):
            return self.linear(x)

With x = [[1.001]], w = [[1.0]], and a sum loss, y = x · w and ∂loss/∂w = x. The FP32 reference gradient should retain approximately 1.001.

The inner enabled=False applies only while forward executes. Returning restores the outer BF16 autocast context. When the capture API later calls autograd.grad(), that context is active again. The backward node for the FP32 forward calls matrix multiplication, which is itself eligible for autocast.

The mm_mat1_backward / mm_mat2_backward implementations call mm, and mm has a CUDA lower-precision policy. Being called from backward does not automatically bypass that policy.

StageIntended FP32 pathBackward under BF16 autocast
ForwardFP32 operands and outputIdentical FP32 output
Weight gradientUses the saved FP32 input and FP32 upstream gradientCasts operands to BF16 before matrix multiplication
ValueApproximately 1.001BF16(1.001) = 1.0, yielding approximately 1.0
Final weight.gradFP32 with reference precisionCan still be FP32, with the earlier precision loss preserved

Autograd can convert a returned gradient to the target metadata dtype during validate_outputs(). Checking that weight.grad.dtype is FP32 therefore does not establish numerical correctness. The path may include extra FP32 → BF16 and BF16 → FP32 conversions while silently losing precision.

Isolate the numerical effect from caching

Run this after the class definition. Here x.requires_grad=False deliberately requests only the weight gradient. The operands of its backward matrix multiplication do not satisfy the leaf-cache conditions discussed below, isolating the first effect for this particular model.

# Requires a CUDA device with BF16 support.
torch.backends.cuda.matmul.allow_tf32 = False
torch.set_printoptions(precision=7)
x = torch.tensor([[1.001]], device="cuda", dtype=torch.float32)

baseline = FP32Linear()
bad = FP32Linear()
good = FP32Linear()

# Reference: forward under the outer context; backward outside it.
with torch.autocast("cuda", dtype=torch.bfloat16, cache_enabled=False):
    reference_y = baseline(x)
reference_y.sum().backward()
reference_grad = baseline.linear.weight.grad.detach().clone()

# Wrong boundary: the API's internal backward also sees autocast.
with torch.autocast("cuda", dtype=torch.bfloat16, cache_enabled=False):

# This whole model requests FP32, so capture needs no enabled autocast.
with torch.autocast("cuda", enabled=False):
    good = torch.cuda.make_graphed_callables(good, (x,))

good.zero_grad(set_to_none=True)
bad_y = bad(x)
bad_y.sum().backward()

For the affected path, the expected reference/good gradients are approximately 1.001 and the bad gradient approximately 1.0, with matching forward outputs. These are predictions from the pinned implementation and BF16 rounding, not reported GPU measurements. Record the actual PyTorch version and GPU when running the example.

Effect 2: an unexpected worker cache outlives its safe boundary

The memory-lifetime failure needs additional conditions: a cacheable cast during backward, and a graph dependency on cached storage that does not remain valid across replay. This explains how illegal memory access (IMA) can occur despite cache_enabled=False in the outer context.

Thread-local state is propagated selectively

In this CUDA autograd path, device worker threads execute backward nodes. A GraphTask stores the caller's ThreadLocalState, and the worker restores its fields with ThreadLocalStateGuard before running a node. See GraphTask::thread_locals_ and the worker TLS guard.

The snapshot includes only specified fields. In v2.12.0, ThreadLocalState.cpp saves and restores the dispatch key set and per-device autocast dtypes, but not cache_enabled.

StateCallerBackward workerReason

This is explicit Engine state restoration, not automatic operating-system inheritance of every thread-local variable. The API's entry check also reads the caller's cache flag only; passing that check does not establish the worker's cache state.

A thread-local flag controls a shared cache

The flag and the container have different scopes. In the pinned autocast_mode.cpp, cache enablement, dtype, and nesting are thread-local. The cast map returned by get_cached_casts() is shared within the process and protected by a mutex. Its key identifies the source TensorImpl; its value holds the lower-precision tensor.

A worker can therefore insert an entry, and the caller can clear that same entry when its outermost autocast context exits. Setting the caller's cache_enabled=False neither prevents another thread from inserting nor skips the exit-time cache clear.

Not every cast is cached. cached_cast() requires an eligible FP32 source with requires_grad=True, leaf status, no view, the configured lower-precision destination, and an enabled cache on the executing thread. It also excludes inference mode and tensors handled by a special caching mechanism. Intermediate activations and transpose views may not qualify; the actual backward operands matter.

The same FP32Linear connects these conditions: setting its input to requires_grad=True makes the saved real-valued 1×1 input x a cache-eligible operand in the layout-specific mm_mat2_backward branch for the weight gradient. It is an FP32 leaf requiring gradients and is not a view. The example can therefore progress from extra rounding to a backward cache entry; an eventual IMA still depends on the subsequent storage lifetime.

From a warmup cache entry to a dangling replay dependency

The clearest failure path creates the cached tensor during warmup and reuses it during capture. A temporary created inside capture is not automatically an IMA: the graph-private pool protects capture-time allocations. An external cache allocation from warmup does not automatically receive that protection.

PhaseCPU / autocast behaviorGPU graph dependency
1. Warmup backwardThe worker casts an eligible FP32 tensor to BF16; the shared map holds copy CC is allocated before capture
2. Capture backwardA cache hit returns C for the same source tensorGEMM records C.data_ptr(); no cast refreshing C is recorded for this hit
3. Exit outer autocastCaller nesting reaches zero and clears the map; without another owner, C's storage returns to the allocatorThe recorded address remains in the graph
4. Replay backwardNo Python cache lookup or tensor ownership is reconstructedThe old address is accessed; released or reused storage can cause IMA or wrong results

Exit-time cleanup is in autocast.__exit__(). Keeping a CUDAGraph object does not keep every external tensor alive. The graph memory-management contract requires replay addresses to remain valid.

IMA is one possible outcome, not an inevitable immediate symptom. The allocator may retain or reuse the storage. Replay can read stale or overwritten data, corrupt another tensor, or report IMA at a later synchronization point. Even retaining C would not solve stale contents after an input or parameter update if no refreshing cast was captured.

Put the autocast boundary inside forward

The FP32-only model needs no enabled autocast during capture. For a mixed-precision model, let its forward manage autocast locally and keep the capture API's surrounding context disabled. Each forward then returns to an environment where the internal warmup and capture backward run with autocast off.

# Uses FP32Linear from above; it can also wrap a mixed-precision model.
class ForwardAutocast(torch.nn.Module):
    def __init__(self, inner):
        super().__init__()
        self.inner = inner

    def forward(self, x):
        with torch.autocast(
            "cuda", dtype=torch.bfloat16, cache_enabled=False
        ):
            return self.inner(x)


model = ForwardAutocast(FP32Linear())
x = torch.tensor([[1.001]], device="cuda", dtype=torch.float32)

# Forward opts into AMP locally; both internal backward phases see it off.
with torch.autocast("cuda", enabled=False):
    graphed = torch.cuda.make_graphed_callables(model, (x,))

graphed.zero_grad(set_to_none=True)
with torch.autocast("cuda", dtype=torch.bfloat16, cache_enabled=False):
    output = graphed(x)
    loss = output.sum()
loss.backward()
torch.cuda.synchronize()

torch.testing.assert_close(
    graphed.inner.linear.weight.grad, x, rtol=0, atol=0
)

The inner FP32 region remains effective. A mixed-precision replacement can choose forward dtypes through AMP while backward follows the resulting graph. Disabling the forward cache respects capture's cache constraint; disabling backward autocast prevents both the unintended precision selection and the additional cache path described here.

If maintaining a custom capture helper, disable autocast around torch.autograd.grad() in both warmup and capture, while preserving the intended forward AMP policy. Changing replay alone cannot repair the captured graph; changing capture alone still leaves warmup running backward under the wrong context.

Verify numerical behavior and worker state separately

First compare forward outputs and parameter gradients using the numerical example. Matching forward results and FP32 .grad storage can coexist with BF16-rounded gradients. Additional profiler casts support the diagnosis; the numerical comparison establishes the correctness difference.

Next, inspect worker TLS independently with a probe that performs no cacheable matrix multiplication. This intentionally runs backward under autocast for diagnosis. Run it eagerly, outside capture:

import threading
import torch


def show_state(label):
    print(label, {
        "thread": threading.get_ident(),
        "enabled": torch.is_autocast_enabled("cuda"),
        "dtype": torch.get_autocast_dtype("cuda"),
        "cache": torch.is_autocast_cache_enabled(),
    })


class TLSProbe(torch.autograd.Function):
    @staticmethod
    def forward(ctx, x):
        return x * 2

    @staticmethod
    def backward(ctx, grad_output):
        show_state("backward worker")
        return grad_output * 2


x = torch.ones(1, device="cuda", requires_grad=True)
with torch.autocast("cuda", dtype=torch.bfloat16, cache_enabled=False):
    show_state("caller")
    TLSProbe.apply(x).sum().backward()

For a worker whose default cache flag has not been modified, the pinned implementation predicts enabled BF16 autocast in both threads, with cache=False in the caller and cache=True in the worker. This establishes only the state-propagation gap. Attributing a particular IMA also requires connecting cache insertion/hit addresses, storage lifetime after clearing, and the graph's accesses. The probe is not a guaranteed IMA reproducer.

The boundary to preserve: forward establishes precision, and backward differentiates that graph. Preserve this boundary during ordinary execution, warmup, and capture. Replay cannot repair an incorrect capture-time autocast state or an expired external storage dependency.
