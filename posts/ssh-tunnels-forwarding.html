SSH 转发与隧道

SSH 端口转发利用已有的 SSH 连接访问远端服务，也能让远端主机访问本地开发环境。本文比较 -L、-D 和 -R 的监听位置、连接方向与适用场景，解释应用数据在 SSH channel 中的传输方式，并给出反向隧道、后台运行及与 HTTP 代理和 VPN 组合使用的配置示例。

1. 协议层次与连接

应用协议的嵌套

SSH 与 HTTP 都运行在 TCP/IP 应用层。应用层可以包含多个协议：HTTP 定义请求内容，SSH 可以把这些字节作为 channel 的载荷。SSH 转发程序从 socket 读取应用数据时，内核已处理 TCP/IP；写入另一个 socket 后，再由该连接的 TCP/IP 负责传输。原始 TCP 头、序列号和 ACK 不会跟着 HTTP 字节进入 SSH channel。

三段 TCP

以浏览器访问本地转发端口为例，一条浏览器 TCP 连接对应一个 SSH forwarding channel。客户端与 sshd 之间的 SSH TCP 连接还可以复用多个 channel。每段 TCP 独立处理重传和流量控制。SSH channel 机制。

连接端点TCP 中的载荷
A浏览器 → Mac SSH 监听端口HTTP 字节，或 HTTPS 的 TLS 字节
BMac SSH 客户端 → VM sshdSSH 协议数据，加密 channel 内承载应用字节
CVM sshd → 目标服务从 channel 恢复出的应用字节

HTTP 服务收到原始 HTTP 请求，SSH 不需要理解 GET 或状态码。访问 HTTPS 时，SSH 解密后仍可得到源站 TLS 密文；TLS 在浏览器和源站之间结束。packet VPN 的单位则是完整 IP 包，其内层 TCP 通常仍由原客户端和目标维护。

2. 本地与动态转发

SSH 端口转发通过加密 channel 传送应用字节。-L 在启动命令中固定目标，-D 则由每条连接的 SOCKS 握手提供目标。SOCKS 负责选址，SSH 负责远端连接和加密传输，两者可以组成同一条数据路径。

本地转发（-L）

ssh -L 适用于访问一个已知的主机和端口。例如，VM 上的 HTTP 服务只监听 127.0.0.1:8000，Mac 可以将本地 18080 转发到该地址。在 Mac 上执行以下命令，alice@vm.example 替换为实际 SSH 登录地址：

ssh -N -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:18080:127.0.0.1:8000 alice@vm.example

# Run in another Mac terminal / 在 Mac 的另一个终端执行
curl --noproxy "*" http://127.0.0.1:18080/

第一个 127.0.0.1:18080 是 Mac 上的监听端点；后面的 127.0.0.1:8000 是 sshd 从 VM 一侧连接的目标。两个 loopback 地址指向两台不同机器。应用连接本地 18080 后，可以直接发送原来的 HTTP 字节，无需额外发送 SOCKS 或 CONNECT 握手。OpenSSH：-L。

固定目标也可以是 sshd 能访问的其他主机和端口。SSH 客户端把应用数据装进 direct-tcpip channel，经 SSH 连接送到 sshd；sshd 打开目标连接并转发字节。SSH 加密覆盖客户端到 sshd 这一段，sshd 到目标服务是否加密取决于被转发的应用协议。RFC 4254 §7.2。

动态转发（-D）

SOCKS5 客户端先连接 SOCKS 服务，协商认证方法，然后在 CONNECT 请求中给出目标地址和端口。目标地址可以是 IP，也可以是域名。握手后转发应用字节，因此它可以承载 HTTP、TLS 或其他 TCP 应用协议，无需理解 HTTP URL、header 或 body。RFC 1928定义了这些字段。

ssh -D 在本地启动 SOCKS 入口，由应用为每条连接指定目标：

ssh -N -o ExitOnForwardFailure=yes \
  -D 127.0.0.1:1080 alice@vm.example

# Run in another Mac terminal / 在 Mac 的另一个终端执行
curl --noproxy "" --proxy socks5h://127.0.0.1:1080 https://example.com/

SOCKS 握手由 Mac 上的 SSH 客户端处理。它读取目标地址，通过已经建立的 SSH 连接请求 VM 上的 sshd 打开目标 socket。VM 无需另外运行 SOCKS 服务，每条新连接也可以选择不同目标。OpenSSH：-D。

命令中的 socks5h:// 让 curl 把目标域名交给代理。在这条 SSH 路径上，最终由 VM 一侧解析目标域名。若写 socks5://，curl 先在本机解析，再把 IP 交给 SOCKS 服务。这个区别是 curl 的选项语义，不能假设所有应用都提供相同开关。curl：SOCKS5 hostname。

上面的 SSH 命令都使用 -N 保持转发而不运行远程命令，按 Ctrl-C 结束。ExitOnForwardFailure=yes 会在本地监听等转发设置失败时退出；它并不预先验证每个最终目标是否可达。远端 sshd 也必须允许相应的 TCP forwarding。OpenSSH 配置说明。

3. 远程转发与反向隧道

远端监听

-R 把监听端口放在 SSH 服务端，目标连接由 SSH 客户端一侧发起。因此，一台没有可入站公网地址的 Mac 可以主动连接 VM，然后让 VM 通过该连接访问 Mac 的开发服务。所谓反向，指后续服务访问相对最初 SSH 建连方向是反过来的；SSH TCP 连接仍由 Mac 发起。

# Mac: serve a dedicated directory
python3 -m http.server 8000 --bind 127.0.0.1 --directory /path/to/public-files

# Mac, another terminal: establish the reverse forward
ssh -NT -o ExitOnForwardFailure=yes \
  -R 127.0.0.1:18080:127.0.0.1:8000 alice@vm.example

# VM: reach the Mac service through the remote listener
curl http://127.0.0.1:18080/

-R 127.0.0.1:18080:127.0.0.1:8000 中，第一个 loopback 属于 VM，第二个属于 Mac。VM 上的 18080 只允许 VM 本机访问。Mac 只需能主动连出到 VM 的 SSH 端口；该示例不要求在家庭路由器上暴露 Mac 的 8000。OpenSSH -R。

监听范围与权限

sshd 默认将远程转发限制为 loopback。若要让第三台机器直接连接 VM 的转发端口，需要选择相应监听地址，并由服务端的 GatewayPorts、防火墙和访问策略允许。GatewayPorts clientspecified 允许客户端指定绑定地址；配置权限不等于目标可达。AllowTcpForwarding、PermitListen、PermitOpen 等还可限制转发类型、监听端点或目标。sshd 配置手册。

端口监听成功后，目标服务仍可能没有启动。ExitOnForwardFailure=yes 检查转发设置能否建立，不会提前测试未来每一条目标连接。先确认监听，再执行一次真实 HTTP 请求，才能验证完整路径。

Packet VPN 可以承载 TCP、UDP 和 ICMP；具体部署仍可在隧道两端按协议或目标过滤流量。

5. HTTP 与 VPN 协作

HTTP 代理与 SSH

应用只支持 HTTP 代理时，ssh -L 可以将远端代理映射为本地端口。假设 Tinyproxy 监听 VM 的 127.0.0.1:18888，Mac 上的本地入口可设为 127.0.0.1:18889。代理保持运行，在 Mac 上建立以下转发：

ssh -N -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:18889:127.0.0.1:18888 alice@vm.example

# Run in another Mac terminal / 在 Mac 的另一个终端执行
curl --noproxy "" --proxy http://127.0.0.1:18889 https://example.com/
Mac 应用
  → HTTP 代理协议 → Mac 127.0.0.1:18889
  → SSH 加密 channel → VM sshd
  → VM 127.0.0.1:18888 上的 Tinyproxy
  → 目标站点

macOS 的 HTTP 和 HTTPS 代理字段使用本地入口 127.0.0.1:18889。应用仍发送 HTTP 代理请求，SSH 将其送到 VM，由 Tinyproxy 解析并连接源站。这个组合保留了 HTTP 代理接口，使远端代理可以继续只监听 loopback，并加密 Mac 到 VM 的传输。

SSH 连接进入 VPN

当 VM 的 SSH 地址仅能通过 VPN 到达时，SSH 创建的 TCP socket 目的地是该 VM，内核据此将其送入隧道。应用仍连接本地 -L 或 -D 入口；VPN 不需要解析其中的 HTTP。VM 的 sshd 再连接 Tinyproxy，Tinyproxy 最后建立源站连接。每个新建连接都遵循建立它的机器上的路由。

Mac 浏览器
  → 本机 TCP → SSH 客户端
  → SSH 加密 channel，内部承载 HTTP CONNECT / 源站 TLS
  → 内层 IP / TCP：Mac → VM 的 SSH 地址
  → VPN 封装：外层 IP / UDP / 加密的内层包（WireGuard 示例）
  → VPN 网关解封装 → VM sshd
  → VM 本机 TCP → Tinyproxy
  → 代理的源站 TCP → HTTPS 服务器

最外层 VPN 加密在 VPN 对端结束，SSH 加密在 sshd 结束，源站 TLS 则可以继续到 HTTPS 服务器。VPN 网关看到解封装后的 SSH 流量，不会因此得到 SSH channel 的明文；sshd 解密 SSH 后，也不因此取得源站 TLS 密钥。相关分层见 VPN 原理与路由，代理两段连接见 HTTP 代理与应用配置。

6. 后台运行与生命周期

Mac 使用 -fNT 在认证后进入后台，只运行转发。下面的专用 control socket 记录这条隧道，便于查看 PID 和定点关闭；目标是 VM 上的 8765 服务，本地入口为 18765。

ssh -fNT -M -S ~/.ssh/blog-vm.sock \
  -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
  -L 127.0.0.1:18765:127.0.0.1:8765 alice@vm.example

# Check the dedicated connection and the forwarded service
ssh -S ~/.ssh/blog-vm.sock -O check alice@vm.example
curl -I http://127.0.0.1:18765/

# Stop this dedicated tunnel
ssh -S ~/.ssh/blog-vm.sock -O exit alice@vm.example

后台运行不等于自动重连或开机启动。ServerAlive 参数用于检测失效连接；隧道退出后需重新启动。control socket 应专用于这条转发，关闭它会终止该 SSH 连接承载的 channel。前台命令可以直接用 Ctrl-C 结束。OpenSSH 命令手册。

7. 网关访问控制

协议可见性

HTTP 代理不可用而 SSH 可用，可能源于两条连接匹配了不同规则。例如，允许连接某台 VM 的 SSH、同时阻止明文 HTTP 代理请求的网关，会对以下路径作出不同处理：

直接使用 HTTP 代理：
Mac → 网关 → proxy:18888
             可见 TCP 目标，以及明文 GET absolute-URL / CONNECT host:port

经 SSH 搬运 HTTP 代理流量：
Mac → 网关 → VM:ssh-port
             可见 SSH 连接；密钥交换后，channel 内容被 SSH 加密
             HTTP 代理握手在 SSH channel 里面
VM sshd → Tinyproxy → 源站

直接使用 HTTP 代理时，网关可以检查目标地址、端口以及明文 HTTP 字段。将同样的请求放入 SSH channel 后，未终止或解密 SSH、也没有端点可见性的网关，无法继续用明文 HTTP 规则检查其中的握手。网关仍能看到 SSH 连接的端点与流量特征；加密前交换的 SSH-2.0-... 版本标识也提供了协议识别线索。RFC 4253 §4.2。

SSH 连接本身经企业 VPN 传输时，本地链路上的观察者看到 VPN 外层，企业 VPN 网关解封装后看到 SSH。VPN 解密只移除 VPN 这一层封装，SSH channel 仍受独立的 SSH 加密保护。

访问控制规则

拦截点 / 规则HTTP 代理与 SSH 可能表现不同的原因
只限制 GUI 代理配置或特定应用它约束的是配置或应用行为；另一个进程的 socket 可能适用不同规则。
阻止某代理 IP 或 TCP 端口SSH 使用不同目的端点时，可能不匹配该规则；若同一 IP 被整体封禁，换协议也无效。

远端出口或目标服务器封禁本地 SSH 建连成功，也不能保证远端能连接代理或目标。

防火墙可通过签名、协议解析和启发式分析识别应用流量，并结合已配置的解密策略检查内容。更换默认端口不会消除协议特征。Palo Alto App-ID 文档描述了这些分类机制。

SSH 成功仅能说明这条 SSH 路径在当时可用。要把 HTTP 代理失败归因于策略拦截，还需要对应的拒绝日志、规则命中记录或连接阶段证据。监听地址错误、代理 ACL、认证失败和远端 DNS 故障也会产生代理不可用的现象。

排查时分别观察本地监听、SSH 握手、目标连接和 HTTP 响应。lsof -nP -iTCP:18765 -sTCP:LISTEN 检查 Mac 监听，ssh -v 输出 channel 创建信息，curl -v 检查最终请求。

SSH forwarding and tunnels

SSH port forwarding uses an SSH connection to reach remote services or make a local development service accessible from a remote host. This article compares the listeners, connection directions and uses of -L, -D and -R, explains how SSH channels carry application data, and provides examples for reverse tunnels, background operation and combinations with HTTP proxies and VPNs.

1. Protocols and connections

Application protocol nesting

HTTP and SSH both belong above TCP in the TCP/IP application layer. HTTP defines request meaning; SSH can carry those bytes as channel payload. A socket read supplies application bytes after the kernel has processed TCP/IP. Sending them through another socket creates another transport path. The original TCP headers, sequence numbers and acknowledgements do not enter the SSH channel.

Three TCP connections

A browser connection to a local forward gets a forwarding channel. Multiple channels can share the SSH TCP connection. Each TCP leg has separate transport state. SSH channel mechanism.

ConnectionEndpointsTCP payload
ABrowser → local SSH listenerHTTP bytes, or origin TLS for HTTPS
BSSH client → sshdSSH messages carrying encrypted channel data
Csshd → target serviceApplication bytes recovered from the channel

The HTTP service handles the original request. SSH need not parse GET or status codes. With HTTPS, removing SSH encryption can leave origin TLS ciphertext, whose endpoints remain the client and origin. A packet VPN instead carries complete IP packets and normally preserves the original inner TCP endpoints.

2. Local and dynamic forwarding

SSH port forwarding carries application bytes through encrypted channels. -L fixes the destination in the command; -D obtains it from each connection's SOCKS handshake. SOCKS selects the destination while SSH provides the remote connection and encrypted transport.

Local forwarding (-L)

ssh -L exposes a known host and port through a local listener. For an HTTP service listening on the VM's 127.0.0.1:8000, the Mac can forward local port 18080 to that service. Run this on the Mac, replacing alice@vm.example with the actual SSH login:

ssh -N -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:18080:127.0.0.1:8000 alice@vm.example

# Run in another Mac terminal / 在 Mac 的另一个终端执行
curl --noproxy "*" http://127.0.0.1:18080/

The first address, 127.0.0.1:18080, listens on the Mac. The second, 127.0.0.1:8000, is reached from sshd on the VM. These loopback addresses refer to different machines. The application sends its original protocol to port 18080 without a SOCKS or CONNECT handshake. OpenSSH -L.

The fixed target can also be another host reachable by sshd. The client carries application bytes in a direct-tcpip channel over SSH; sshd opens the target socket and relays them. SSH encrypts the SSH client-to-server hop. Encryption from sshd to the final service depends on the application protocol. RFC 4254 §7.2.

Dynamic forwarding (-D)

A SOCKS5 client connects to the proxy, negotiates an authentication method, then sends a CONNECT request containing an IP address or hostname and a port. After setup, the proxy relays application bytes. It can carry HTTP, TLS or another TCP application without understanding URLs or HTTP headers. RFC 1928.

ssh -D opens a local SOCKS listener, allowing the application to specify a destination for each connection:

ssh -N -o ExitOnForwardFailure=yes \
  -D 127.0.0.1:1080 alice@vm.example

# Run in another Mac terminal / 在 Mac 的另一个终端执行
curl --noproxy "" --proxy socks5h://127.0.0.1:1080 https://example.com/

The Mac's SSH client processes the SOCKS handshake. It reads the requested destination and asks sshd on the VM to open the target socket over the established SSH connection. The VM needs no separate SOCKS daemon, and each new connection can select a different destination. OpenSSH -D.

curl's socks5h:// passes the hostname to the proxy; along this SSH path, destination resolution happens on the VM. With socks5://, curl resolves locally and sends an IP address. This distinction belongs to curl's interface; other clients may expose different DNS controls. curl SOCKS5 hostname option.

Both SSH commands use -N to forward without running a remote command. Stop them with Ctrl-C. ExitOnForwardFailure=yes catches forwarding setup failures, such as inability to bind a listener, but does not preflight every final destination. The server must permit the requested TCP forwarding. OpenSSH configuration.

3. Remote forwarding

Remote listener

With -R, the SSH server hosts the listener and the SSH client side opens the target connection. A Mac without a publicly reachable inbound address can initiate SSH to a VM and expose its local development service there. “Reverse” describes the service-access direction relative to the initial SSH connection, which still originates on the Mac.

# Mac: serve a dedicated directory
python3 -m http.server 8000 --bind 127.0.0.1 --directory /path/to/public-files

# Mac, another terminal: establish the reverse forward
ssh -NT -o ExitOnForwardFailure=yes \
  -R 127.0.0.1:18080:127.0.0.1:8000 alice@vm.example

# VM: reach the Mac service through the remote listener
curl http://127.0.0.1:18080/

In -R 127.0.0.1:18080:127.0.0.1:8000, the first loopback belongs to the VM and the second to the Mac. Only VM-local clients can use this listener. No inbound mapping for the Mac service is required on the home router. OpenSSH -R.

Binding and permissions

sshd defaults to loopback-only remote forwarding. A listener reachable by a third machine needs a suitable bind address, server GatewayPorts policy and firewall permission. GatewayPorts clientspecified permits client-selected binding. AllowTcpForwarding, PermitListen and PermitOpen can restrict the forwarding type, listener or target. sshd configuration.

A successfully established listener does not prove that the future target connection works. ExitOnForwardFailure checks forwarding setup, not every destination connection. Make an actual application request after checking the listener.

VPNs suit broad private-IP reachability and datagram traffic. A few TCP ports with existing SSH access can use forwarding without adding subnet routes. This comparison covers -L, -D and -R TCP forwarding rather than every tunnel feature available through SSH.

Browser SOCKS resolution policies also differ; see Chromium's proxy documentation.

SOCKS5 specifies UDP ASSOCIATE, but implementations need not support it. OpenSSH dynamic forwarding accepts SOCKS CONNECT, so ssh -D is not a general UDP proxy. The HTTP/1.1 CONNECT and SSH forwards described here do not transport ping's ICMP packets or automatically capture QUIC / HTTP/3. See SOCKS5 UDP and OpenSSH's channel_decode_socks5().

A packet VPN can carry TCP, UDP and ICMP, with deployment policy still able to filter protocols or destinations at either end.

5. HTTP and VPN composition

HTTP proxies over SSH

For an application that supports HTTP proxies, ssh -L can expose a remote proxy on a local port. Tinyproxy listening on the VM's 127.0.0.1:18888 can be reached through 127.0.0.1:18889 on the Mac. With Tinyproxy running, create this forward on the Mac:

ssh -N -o ExitOnForwardFailure=yes \
  -L 127.0.0.1:18889:127.0.0.1:18888 alice@vm.example

# Run in another Mac terminal / 在 Mac 的另一个终端执行
curl --noproxy "" --proxy http://127.0.0.1:18889 https://example.com/
Mac application
  → HTTP proxy protocol → Mac 127.0.0.1:18889
  → encrypted SSH channel → VM sshd
  → Tinyproxy on VM 127.0.0.1:18888
  → destination

The macOS HTTP and HTTPS proxy fields use the local endpoint 127.0.0.1:18889. The application sends HTTP proxy requests through SSH; Tinyproxy parses them on the VM and connects to the origin. The application retains its HTTP proxy interface, the remote proxy remains on loopback, and SSH encrypts the Mac-to-VM hop.

SSH over a VPN

If the VM SSH address is reachable only through VPN, routing sends the SSH TCP connection into the tunnel. The application still connects to its local -L or -D listener. The VM sshd connects to Tinyproxy, which opens the origin connection. Each connection follows the routes of the machine that creates it.

Mac browser
  → local TCP → SSH client
  → encrypted SSH channel carrying CONNECT / origin TLS
  → inner IP / TCP: Mac → VM SSH address
  → outer IP / UDP / encrypted packet (WireGuard example)
  → VPN gateway decapsulation → VM sshd
  → VM-local TCP → Tinyproxy
  → proxy-origin TCP → HTTPS server

VPN encryption ends at the VPN peer, SSH encryption at sshd, and origin TLS at the HTTPS server. VPN decapsulation does not reveal SSH channel plaintext. SSH decryption does not supply the origin TLS key. See VPN fundamentals and routing and HTTP proxies and application configuration.

6. Background operation

On a Mac, -fNT backgrounds the connection after authentication without running a remote command. A dedicated control socket identifies the tunnel for PID checks and precise shutdown. This example forwards local 18765 to the VM’s service on 8765:

ssh -fNT -M -S ~/.ssh/blog-vm.sock \
  -o ExitOnForwardFailure=yes \
  -o ServerAliveInterval=30 -o ServerAliveCountMax=3 \
  -L 127.0.0.1:18765:127.0.0.1:8765 alice@vm.example

# Check the dedicated connection and the forwarded service
ssh -S ~/.ssh/blog-vm.sock -O check alice@vm.example
curl -I http://127.0.0.1:18765/

# Stop this dedicated tunnel
ssh -S ~/.ssh/blog-vm.sock -O exit alice@vm.example

Backgrounding does not add automatic reconnection or startup at boot. ServerAlive detects an unresponsive connection; restart the command after it exits. Keep the control socket dedicated to this tunnel, since closing it ends the channels on that SSH connection. Foreground examples end with Ctrl-C. OpenSSH manual.

7. Gateway access control

Protocol visibility

HTTP proxy failure alongside SSH success can result from different rule matches. For example, a gateway allowing SSH to a VM while blocking cleartext HTTP proxy requests would treat these paths differently:

Direct HTTP proxy:
Mac → gateway → proxy:18888
      visible: TCP destination and cleartext absolute URL / CONNECT target

HTTP proxy carried over SSH:
Mac → gateway → VM:ssh-port
      visible: SSH connection; channel data is encrypted after key exchange
      the HTTP proxy handshake travels inside that channel
VM sshd → Tinyproxy → origin

Direct HTTP proxying exposes the destination endpoint and cleartext HTTP fields to the gateway. Inside an SSH channel, those fields are unavailable to a gateway without SSH termination, decryption or endpoint visibility. The gateway still sees SSH endpoints and traffic characteristics. The initial SSH-2.0-... version identification is exchanged before encryption and provides a protocol-identification signal. RFC 4253 §4.2.

When SSH itself crosses a corporate VPN, a local-path observer sees the VPN wrapper. The corporate VPN gateway sees SSH after decapsulation. Removing VPN encryption leaves the independently encrypted SSH channel intact.

Access control rules

Rule / enforcement pointWhy behavior can differ
GUI proxy policy or application-specific restrictionA configuration or app rule may differ from the rule applied to another process's sockets.
Blocked proxy IP or TCP portA different SSH endpoint might not match. Blocking the entire same IP also blocks SSH to it.
Cleartext HTTP / CONNECT inspectionRequests inside SSH are encrypted at this point. Outer TLS to an HTTPS proxy likewise changes visibility.
SSH or encrypted-tunnel application blockSSH can be blocked too; identification need not rely on port 22.
Managed egress, endpoint filtering or default denySSH has no automatic exemption. Process, routing, destination and application policies all matter.
Remote egress or destination restrictionA successful SSH connection does not prove remote access to the proxy or origin.

Firewalls can identify application traffic using signatures, protocol decoding and heuristics, alongside configured decryption policies. Changing a default port does not remove protocol characteristics. Palo Alto's App-ID documentation describes these classification mechanisms.

Successful SSH establishes that this SSH path was available at that time. Attributing HTTP proxy failure to enforcement requires supporting evidence: denial logs, rule matches or observations of the failing connection stage. Listener errors, proxy ACLs, authentication failures and remote DNS errors can also make a proxy unavailable.

Inspect the listener, SSH handshake, target connection and application response separately. On the Mac, lsof can identify the listener on 18765; ssh -v records channel setup and curl -v records the application request.
