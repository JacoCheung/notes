PyTorch DDP 梯度规约机制：Reducer、Bucket 与 NCCL AllReduce

数据并行训练让每个 rank 独立执行 forward 与 backward，因此 autograd 首先得到的是各 rank 的局部参数梯度。优化器更新之前，这些副本需要形成一致的规约结果。PyTorch DDP 在本地梯度累加与优化器之间放置 Reducer：它把参数梯度组织成 bucket，按就绪顺序启动 collective，并借助异步通信覆盖一部分后续 backward 计算。规约时机、collective 数量和 world-size scaling 都由这条路径共同决定。

执行模型与版本边界

本文讨论标准 torch.nn.parallel.DistributedDataParallel，每个 rank 保存完整参数、完整梯度和完整优化器状态。公开 API 语义以 PyTorch 2.12 文档为准，源码说明固定在 PyTorch commit 9c603a7。batched_grad_copy、skip_all_reduce_unused_params 等实现细节属于该版本；自定义 communication hook、join() 和稀疏梯度也会改变部分路径。

标准 DDP 的基本规约单元是梯度 bucket。设一个 DDP 实例在 bucket 重建后包含 \(B\) 个 bucket，常规同步 backward 的默认路径会为每个 ready bucket 发起一次梯度 AllReduce。参数数量、bucket 数量和底层 NCCL kernel 数量由此属于三个不同层次。

从 wgrad 到 bucket

以 Linear 为例，rank \(r\) 上的 forward 和权重梯度写成：

\[ Y_r = X_r W^{\mathsf T}, \qquad G_r = \frac{\mathrm{d}L_r}{\mathrm{d}W} \]

GEMM 或其他 backward kernel 计算 rank \(r\) 的局部梯度 \(G_r\)。autograd 随后完成 fan-in 累加，把结果写入参数的 .grad，再调用 DDP 注册在梯度累加器上的 post hook。wgrad kernel 与 DDP 通信由此处在相邻但独立的阶段。hook 的挂载对象可参见 grad_fn、next_functions 与 AccumulateGrad 一文。

Reducer 构造阶段为每个可训练参数取得梯度累加器并注册 post hook。Reducer::autograd_hook() 的注释明确写明：调用发生在参数梯度已经累加到梯度 Tensor 之后。

从 Python 语义看，这段流程可以缩写为：

# 语义化伪代码，不是 PyTorch 的 Python 实现

local_backward_kernel(param)       # 计算当前分支贡献的 wgrad
accumulate_into(param.grad)        # 合并本 rank 的 fan-in 梯度
ddp_post_accumulate_hook(param)    # 通知 Reducer: 该参数已就绪

bucket = reducer.bucket_of(param)
bucket.write(param.grad)
bucket.pending -= 1

DDP 的 “gradient ready” 表示该参数在当前 backward 中应接收的本地梯度贡献已经完成 autograd 累加。这个事件把单个参数的求导阶段交接给 bucket 管理阶段。

AllReduce 的触发时机

每个 bucket 维护一个未就绪参数计数 pending。参数 hook 运行时，Reducer 把梯度写入该参数对应的 bucket view，并将 pending 减一。计数归零说明这个 bucket 已经可以通信。对应源码在 mark_variable_ready()。

ready 状态说明 bucket 已收齐本地梯度，collective 的实际发起还要满足跨 rank 顺序一致性。DDP 按 bucket index 规约，避免不同 rank 以不同顺序进入 collective 而造成错配或挂起。若 bucket 1 先于 bucket 0 就绪，它会等待 bucket 0；bucket 0 就绪后，Reducer 可以连续发起两者。这个顺序约束写在 mark_bucket_ready() 中。

一次同步 backward 中的计算与通信重叠

通信是异步发起的。后面的 backward kernel 可以继续在计算 stream 上运行。最后一个 bucket 被调度后，autograd 安排收尾回调；finalize_backward() 处理各 bucket 的通信 future，并把规约结果映射回参数梯度。

对该 commit 的 NCCL backend，finalize_backward() 对 future 执行 wait() 后，WorkNCCL::synchronizeStream()/wait() 用 NCCL end event 阻塞当前 CUDA stream。默认非 blocking-wait 路径建立的是 stream 依赖，不等价于一次 cudaDeviceSynchronize()；因此 loss.backward() 的 CPU 返回时，GPU 上的 NCCL 工作仍可能尚未完成。

图中的三个 AllReduce 按 bucket index 发起。这里的 overlap 只表达 NCCL 通信可以与后续 backward 计算交叠；图本身不主张三个 bucket collective 在 GPU 上并发，实际时间关系应以 profiler trace 为准。

Collective 与 kernel 数量

一次 backward 可以从参数、逻辑 collective 和 GPU kernel 三个层次计数。参数先聚合进 bucket，DDP 为 ready bucket 发起 collective，通信 backend 再把 collective 实现为底层 GPU 活动，因此三种数量没有一一对应关系。

配置 一次 backward 的梯度 collective 补充通信
默认同步 backward \(B\) 次 AllReduce，每个梯度 bucket 一次 无
no_sync() 内的 backward 0 次 梯度只在本地 .grad 中累加
离开 no_sync() 后的首个同步 backward \(B\) 次 AllReduce 规约对象包含此前累计的本地梯度
find_unused_parameters=True，动态图路径 通常仍为 \(B\) 次 另有一次参数使用位图 AllReduce；它不是梯度 bucket
自定义 communication hook 每个 ready bucket 调用一次 hook hook 可以发起零次、一次或多次 collective
skip_all_reduce_unused_params=True 允许跳过完全由未使用参数组成的 bucket 各 rank 的未使用参数集合必须保持一致

\(B\) 受 bucket 容量、参数大小、dtype、device 和稀疏梯度影响。默认 bucket_cap_mb 是 25 MiB，但 \(B\) 不一定严格等于总梯度字节数除以 25 MiB 后向上取整。DDP 还会根据首轮 backward 的梯度到达顺序重建 bucket，以改善计算与通信重叠。官方 DistributedDataParallel 2.12 文档给出了 bucket 容量及相关参数的定义。

find_unused_parameters=True 的动态图路径需要在 rank 之间同步参数使用情况。all_reduce_local_used_map() 对一份整型位图执行额外 AllReduce；这次通信不携带 wgrad，也不计入上面的 \(B\) 次梯度 collective。

一次 bucket AllReduce 对应一次 ProcessGroup::allreduce 调用。在传统 NCCL host API 路径中，每个 rank 的 profiler 通常会为它显示一个 ncclDevKernel_AllReduce_... 通信 kernel；NCCL 2.31.2 的 环境变量文档说明传统 channel 模型按 channel 启动 CUDA block。这里描述的是常见实现形态，不是 DDP API 对 kernel 数量或名称的保证。NCCL grouping、CUDA Graph、device API 以及其他 backend 都可能改变逻辑 collective 与底层活动的映射。

NCCL SUM 与 DDP 平均梯度

设 data parallel group 有 \(P\) 个 rank，第 \(r\) 个 rank 的本地梯度是 \(G_r\)。DDP 默认结果为：

\[ G_{\mathrm{DDP}} = \frac{1}{P}\sum_{r=0}^{P-1}G_r \]

NCCL 2.31.2 AllReduce 文档将 AllReduce 定义为带 reduction operator 的 collective；SUM operator 让每个 rank 收到逐元素求和结果。DDP 在这个 SUM 之上建立平均语义。PyTorch 默认调用 _AllReduceBySumCommHook，该 hook 最终使用 ProcessGroup::allreduce。

平均发生在 SUM 之前。默认路径把每个本地梯度先除以 div_factor，通常就是 process group 的大小 \(P\)，随后调用 SUM：

\[ \operatorname{NCCL\_SUM}\left( \frac{G_0}{P},\frac{G_1}{P},\ldots,\frac{G_{P-1}}{P} \right) = \frac{1}{P}\sum_{r=0}^{P-1}G_r \]

例如两个 rank 的标量梯度分别为 6 和 10。各 rank 先得到 3 和 5，NCCL SUM 后都得到 8。把除法放在通信前还能降低 FP16 等窄格式在求和时溢出的风险。PyTorch 的内置 AllReduceCommHook 也明确采用先除后加的顺序。

div_factor 在普通训练中等于 process group size。使用 DDP join() 处理不均匀输入时，它可以按配置取初始 world size 或仍在参与训练的有效 rank 数量。

自定义 communication hook 的语义不同

注册 register_comm_hook() 后，Reducer 不再预除 world_size。官方 API 文档明确要求 hook 自己负责需要的平均操作。下面这种 hook 只做 SUM，得到的梯度会比默认 DDP 大 \(P\) 倍：

def sum_only_hook(process_group, bucket):
    return (
        torch.distributed.all_reduce(
            bucket.buffer(),
            group=process_group,
            async_op=True,
        )
        .get_future()
        .then(lambda fut: fut.value()[0])
    )

若要保持默认 DDP 数值语义，应在 hook 中显式除以 group size，或直接参考 PyTorch 的 allreduce_hook。

wgrad scaling 的位置

Reducer 在已就绪参数梯度进入 bucket 通信路径时执行 world-size scaling。Linear、Conv 或 attention 的 wgrad kernel 负责产生本地梯度，随后当前实现根据该梯度与 bucket 的存储关系选择缩放路径：

梯度存储状态 缩放位置 源码行为
param.grad 与 bucket view 不共享存储 参数梯度写入 bucket 时 用 mul_out(bucket_view, grad, 1 / div_factor) 合并复制与缩放
gradient_as_bucket_view=True，两者已经 alias 参数被标记 ready 时 对相应 bucket view 原地 div_
batched_grad_copy=True 整个 bucket ready 时 先批量复制，再对 flat bucket 做一次 div_
注册自定义 communication hook 由 hook 决定 Reducer 跳过默认除法

前两条路径位于 mark_variable_ready_dense()。批量复制路径在 flush_deferred_copies() 中。默认路径在参数梯度就绪时完成缩放；批量路径等整个 bucket 就绪后统一缩放，随后发起 SUM AllReduce。

loss reduction、梯度累积与 AMP

world-size 平均只是训练数值路径中的一项缩放。loss reduction 决定本地梯度的归一化方式，gradient accumulation 决定多个 microbatch 如何合并，AMP 则在通信前后保留并解除 loss scale。把这些位置分开，才能判断最终 wgrad 的系数。

缩放来源 发生位置 DDP 是否自动处理
loss 的 mean 或 sum 本地 loss 定义 否，DDP只接收由该 loss 产生的局部梯度
data parallel group 平均 Reducer 与 communication hook 默认处理，除数通常为 group size
gradient accumulation 的 \(1/K\) loss 或优化器侧约定 否，no_sync() 不会自动除以累计步数
AMP loss scale 的 \(s\) 与 \(1/s\) GradScaler.scale() 与 unscale_()/step() 否，DDP 规约的是仍带 loss scale 的梯度

局部 mean loss

若每个 rank 的 local batch 大小都为 \(N\)，本地 loss 是样本均值：

\[ L_r = \frac{1}{N}\sum_{i=1}^{N}\ell_{r,i} \]

DDP 再对 \(P\) 个 rank 的梯度取平均，结果正好对应 global batch \(PN\) 上的均值梯度：

\[ \frac{1}{P}\sum_{r=0}^{P-1}\frac{\mathrm{d}L_r}{\mathrm{d}W} = \frac{1}{PN}\sum_{r=0}^{P-1}\sum_{i=1}^{N} \frac{\mathrm{d}\ell_{r,i}}{\mathrm{d}W} \]

如果各 rank 的有效样本数不同，简单 rank 平均不再等同于按样本数加权的 global mean。DDP 不会从梯度 Tensor 推断各 rank 的样本权重。

no_sync() 与 \(K\) 个 microbatch

no_sync() 让前 \(K-1\) 个 microbatch 的梯度继续累加在本地 .grad 中，并把通信推迟到离开上下文后的同步 backward。此时规约对象是本地累加结果：

\[ G_r^{\mathrm{acc}} = \sum_{j=1}^{K}G_{r,j}, \qquad G_{\mathrm{DDP}}^{\mathrm{acc}} = \frac{1}{P}\sum_{r=0}^{P-1}G_r^{\mathrm{acc}} \]

这个结果保留 microbatch 求和语义。若目标是 \(K\) 个 microbatch 的均值梯度，通常要把每个 microbatch loss 除以 \(K\)，或者在等价位置应用该比例。官方 no_sync() 2.12 文档也说明同步发生在退出上下文后的首个 forward-backward，并要求 forward 位于同一 no_sync() 上下文内。

AMP GradScaler

AMP 先把 loss 乘以 \(s\)，所以 DDP 看到的是 \(sG_r\)。AllReduce 的线性性质保证：

\[ \frac{1}{P}\sum_{r=0}^{P-1}sG_r = s\left(\frac{1}{P}\sum_{r=0}^{P-1}G_r\right) \]

随后 GradScaler.unscale_(optimizer) 或 GradScaler.step(optimizer) 在 optimizer step 前除以 \(s\)。AMP inverse scale 位于优化器路径，DDP 的 world-size scaling 位于 bucket 准备路径，两者通过 AllReduce 的线性性质保持可组合。

运行时观测 bucket 与 collective

DDP 的诊断数据可以查看最终 bucket 大小。_get_ddp_logging_data() 是内部诊断接口，适合分析，不宜作为训练逻辑依赖：

ddp_info = ddp_model._get_ddp_logging_data()

print(ddp_info.get("bucket_sizes"))
print(ddp_info.get("bucket_cap_bytes"))
print(ddp_info.get("prev_iteration_grad_ready_order_indices"))

TORCH_DISTRIBUTED_DEBUG=INFO/DETAIL 可以增加 DDP 初始化、运行统计和 collective 一致性检查日志，字段会随版本与 debug level 变化。实际 collective 数量应由 torch.profiler、Nsight Systems 或 NCCL Flight Recorder 中的逻辑事件确认，例如当前 trace 出现的 nccl:all_reduce 或 c10d::allreduce_。PyTorch 2.12 的 collective profiling 文档给出了 profiler 用法。

GPU trace 中的 ncclDevKernel_AllReduce_... 是传统 NCCL 路径常见而非稳定承诺的 kernel 名。统计 bucket 数时，仍应先数 collective 事件，再展开其中某一次 collective 对应的 GPU 活动。NCCL 2.31.2 文档对 channel 与 CUDA block 的关系有明确说明。

AllReduce 与 reduce-scatter 的所有权差异

标准 DDP 的参数和梯度在各 rank 上完整复制，因此默认用 AllReduce：规约后每个 rank 都拿到同一份完整梯度。ReduceScatter 则只把规约结果的一段留在每个 rank，适合梯度或优化器状态已经分片的训练方式。

训练方式 梯度通信 通信后每个 rank 持有的梯度
PyTorch DDP 默认 AllReduce 完整且相同
FSDP / ZeRO 类分片优化 常用 ReduceScatter 只保留本 rank 负责的 shard
DDP 自定义 communication hook 由 hook 决定 必须满足后续优化器与参数布局的约定

通信 primitive 由规约后的 Tensor 所有权决定。标准 DDP 需要每个 rank 持有完整梯度，因而采用 AllReduce；Megatron distributed optimizer、ZeRO 和 FSDP 把梯度分片与 optimizer state 布局纳入设计，通常以 ReduceScatter 让每个 rank 保留负责的 shard。分析 collective 数量时，应先确认训练方式的所有权约定。

Gradient Reduction in PyTorch DDP: Reducer, Buckets, and NCCL AllReduce

In data-parallel training, every rank executes forward and backward independently, so autograd first produces local parameter gradients. Those replicas need a consistent reduced result before the optimizer update. PyTorch DDP places a Reducer between local gradient accumulation and the optimizer: it groups gradients into buckets, starts collectives as buckets become ready, and uses asynchronous communication to overlap part of the remaining backward computation. Reduction timing, collective count, and world-size scaling all follow from this path.

Execution model and version scope

The subject is standard torch.nn.parallel.DistributedDataParallel, where every rank stores full parameters, full gradients, and full optimizer state. Public API semantics follow the PyTorch 2.12 documentation, and source-level statements are pinned to PyTorch commit 9c603a7. Details such as batched_grad_copy and skip_all_reduce_unused_params belong to that version. Custom communication hooks, join(), and sparse gradients can alter parts of the path.

A gradient bucket is the basic reduction unit in standard DDP. Suppose bucket rebuilding leaves a DDP instance with \(B\) buckets. During an ordinary synchronized backward pass, the default path starts one gradient AllReduce for every ready bucket. Parameter count, bucket count, and the number of lower-level NCCL kernels therefore belong to separate layers.

From wgrad to buckets

For a Linear layer, the forward computation and weight gradient on rank \(r\) are:

\[ Y_r = X_r W^{\mathsf T}, \qquad G_r = \frac{\mathrm{d}L_r}{\mathrm{d}W} \]

The GEMM or other backward kernel computes the local gradient \(G_r\) for rank \(r\). Autograd then performs fan-in accumulation, writes the result into the parameter's .grad, and calls DDP's post hook on the gradient accumulator. The wgrad kernel and DDP communication are adjacent but separate stages. The hook is attached to the class of object discussed in grad_fn, next_functions, and AccumulateGrad.

During Reducer construction, PyTorch obtains the gradient accumulator for each trainable parameter and registers a post hook. The comment on Reducer::autograd_hook() states that the hook is called after the gradient has been accumulated into its gradient tensor.

At the Python semantic level, the path can be summarized as:

# Semantic pseudocode, not PyTorch's Python implementation

local_backward_kernel(param)       # compute this branch's local wgrad
accumulate_into(param.grad)        # merge local fan-in contributions
ddp_post_accumulate_hook(param)    # tell Reducer that the parameter is ready

bucket = reducer.bucket_of(param)
bucket.write(param.grad)
bucket.pending -= 1

DDP's “gradient ready” event means that autograd has collected the local contributions expected for that parameter in the current backward pass. The event hands the parameter from differentiation to bucket management.

When AllReduce starts

Each bucket maintains a count of parameters whose gradients are not ready. When a parameter hook runs, the Reducer writes the gradient into the matching bucket view and decrements that count. A count of zero makes the bucket eligible for communication. The relevant implementation is mark_variable_ready().

The ready state means that a bucket has collected its local gradients; launching its collective also requires a consistent order across ranks. DDP reduces buckets by index so that ranks do not enter collectives in conflicting sequences. If bucket 1 becomes ready before bucket 0, it waits. Once bucket 0 is ready, the Reducer can launch both in order. This constraint appears in mark_bucket_ready().

Computation and communication overlap in one synchronized backward pass

Communication is launched asynchronously, so later backward kernels can continue on the compute stream. After the last bucket is scheduled, autograd arranges a final callback. finalize_backward() processes each bucket's communication future and maps the reduced result back to parameter gradients.

For the NCCL backend at this commit, finalize_backward() calls wait() on the future, and WorkNCCL::synchronizeStream()/wait() makes the current CUDA stream wait on NCCL's end event. On the default non-blocking-wait path, this establishes a stream dependency rather than calling cudaDeviceSynchronize(). NCCL work on the GPU may therefore still be in flight when loss.backward() returns on the CPU.

The diagram launches three AllReduce calls in bucket-index order. The overlap shown means that NCCL communication may overlap with later backward computation. It does not claim that the three bucket collectives execute concurrently on the GPU; a profiler trace is needed to establish their actual timing.

Collectives and kernel counts

A backward pass can be counted at three levels: parameters, logical collectives, and GPU kernels. Parameters are packed into buckets, DDP issues a collective for each ready bucket, and the communication backend realizes that collective as lower-level GPU activity. These counts have no one-to-one mapping.

Configuration Gradient collectives per backward pass Additional communication
Default synchronized backward \(B\) AllReduce calls, one per gradient bucket None
Backward inside no_sync() 0 Gradients accumulate only in local .grad tensors
First synchronized backward after leaving no_sync() \(B\) AllReduce calls The reduction includes locally accumulated gradients from earlier passes
find_unused_parameters=True with a dynamic graph Usually still \(B\) One additional AllReduce synchronizes a parameter-usage bitmap; it is not a gradient bucket
Custom communication hook The hook is called once per ready bucket The hook may issue zero, one, or several collectives
skip_all_reduce_unused_params=True Buckets containing only unused parameters may be skipped The unused-parameter set must remain identical across ranks

\(B\) depends on bucket capacity, parameter sizes, dtype, device, and sparse gradients. The default bucket_cap_mb is 25 MiB, but \(B\) is not necessarily the total gradient size divided by 25 MiB and rounded up. DDP can rebuild buckets using the gradient arrival order observed during the first backward pass to improve compute-communication overlap. The official PyTorch 2.12 DistributedDataParallel documentation defines bucket capacity and the related options.

The dynamic-graph path for find_unused_parameters=True must synchronize parameter usage across ranks. all_reduce_local_used_map() performs an extra AllReduce over an integer bitmap. It carries no wgrad data and is not part of the \(B\) gradient collectives.

One bucket AllReduce corresponds to one ProcessGroup::allreduce call. With the traditional NCCL host API path, a profiler on each rank commonly shows one ncclDevKernel_AllReduce_... communication kernel for that call. The NCCL 2.31.2 environment variable documentation states that the traditional channel model launches a CUDA block per channel. This is a common implementation shape, not a DDP API guarantee about kernel count or names. NCCL grouping, CUDA Graphs, the device API, and other backends can change how logical collectives map to lower-level activity.

NCCL SUM and DDP gradient averaging

Let the data-parallel group contain \(P\) ranks, with local gradient \(G_r\) on rank \(r\). The default DDP result is:

\[ G_{\mathrm{DDP}} = \frac{1}{P}\sum_{r=0}^{P-1}G_r \]

The NCCL 2.31.2 AllReduce documentation defines AllReduce as a collective with a reduction operator; SUM gives every rank the elementwise sum. DDP builds its averaging semantics around that SUM. PyTorch's default path calls _AllReduceBySumCommHook, which eventually invokes ProcessGroup::allreduce.

The averaging division occurs before SUM. The default path divides each local gradient by div_factor, normally the process-group size \(P\), and then invokes SUM:

\[ \operatorname{NCCL\_SUM}\left( \frac{G_0}{P},\frac{G_1}{P},\ldots,\frac{G_{P-1}}{P} \right) = \frac{1}{P}\sum_{r=0}^{P-1}G_r \]

If two ranks have scalar gradients 6 and 10, they first hold 3 and 5; NCCL SUM then gives both ranks 8. Dividing before communication also lowers overflow risk when narrow formats such as FP16 are summed. PyTorch's built-in AllReduceCommHook explicitly uses divide-then-add order.

In ordinary training, div_factor is the process-group size. When DDP join() handles uneven inputs, configuration determines whether it uses the initial world size or the number of ranks still participating.

Custom communication hooks have different semantics

After register_comm_hook() is installed, the Reducer no longer performs the default world-size division. The public API documentation requires the hook to implement any desired averaging. The following hook performs SUM only, so its gradients are \(P\) times larger than default DDP gradients:

def sum_only_hook(process_group, bucket):
    return (
        torch.distributed.all_reduce(
            bucket.buffer(),
            group=process_group,
            async_op=True,
        )
        .get_future()
        .then(lambda fut: fut.value()[0])
    )

To preserve default DDP numerics, divide by the group size inside the hook or follow PyTorch's allreduce_hook.

Where wgrad scaling occurs

The Reducer applies world-size scaling while a ready parameter gradient enters the bucket communication path. A Linear, convolution, or attention wgrad kernel produces the local gradient first; the current implementation then chooses a scaling path according to the storage relationship between that gradient and its bucket:

Gradient storage state Scaling point Source behavior
param.grad does not share storage with the bucket view While copying the parameter gradient into the bucket mul_out(bucket_view, grad, 1 / div_factor) combines the copy and scale
gradient_as_bucket_view=True, and the two already alias When the parameter is marked ready The corresponding bucket view is divided in place with div_
batched_grad_copy=True When the entire bucket is ready Gradients are copied in a batch, then the flat bucket receives one div_
A custom communication hook is registered Chosen by the hook The Reducer skips the default division

The first two paths are implemented in mark_variable_ready_dense(). The batched-copy path is in flush_deferred_copies(). Default paths scale when a parameter gradient becomes ready; the batched path waits for the whole bucket, scales the flat buffer, and then starts SUM AllReduce.

Loss reduction, gradient accumulation, and AMP

World-size averaging is only one scale in the training numerics. Loss reduction determines local-gradient normalization, gradient accumulation combines microbatches, and AMP preserves and later removes a loss scale around communication. Separating these locations makes the final wgrad coefficient explicit.

Source of scaling Where it occurs Handled automatically by DDP
Loss mean or sum Local loss definition No. DDP receives the local gradient produced by that loss
Data-parallel group average Reducer and communication hook Yes on the default path; the divisor is normally the group size
\(1/K\) for gradient accumulation Loss or optimizer-side convention No. no_sync() does not divide by the number of accumulated steps
AMP loss scale \(s\) and inverse scale \(1/s\) GradScaler.scale() and unscale_()/step() No. DDP reduces gradients that still carry the loss scale

Local mean loss

If every rank has a local batch of \(N\) samples and defines its local loss as a sample mean:

\[ L_r = \frac{1}{N}\sum_{i=1}^{N}\ell_{r,i} \]

DDP then averages the gradients from \(P\) ranks. The result is exactly the mean gradient over a global batch of \(PN\) samples:

\[ \frac{1}{P}\sum_{r=0}^{P-1}\frac{\mathrm{d}L_r}{\mathrm{d}W} = \frac{1}{PN}\sum_{r=0}^{P-1}\sum_{i=1}^{N} \frac{\mathrm{d}\ell_{r,i}}{\mathrm{d}W} \]

When ranks contain different numbers of valid samples, a simple rank average no longer equals a sample-weighted global mean. DDP cannot infer per-rank sample weights from gradient tensors.

no_sync() with \(K\) microbatches

no_sync() keeps gradients from the first \(K-1\) microbatches accumulating in local .grad tensors and defers communication to the synchronized backward pass after the context. The reduction then consumes the locally accumulated result:

\[ G_r^{\mathrm{acc}} = \sum_{j=1}^{K}G_{r,j}, \qquad G_{\mathrm{DDP}}^{\mathrm{acc}} = \frac{1}{P}\sum_{r=0}^{P-1}G_r^{\mathrm{acc}} \]

The result retains microbatch-sum semantics. To obtain the mean gradient over \(K\) microbatches, training code normally divides each microbatch loss by \(K\), or applies the same factor at an equivalent point. The official PyTorch 2.12 no_sync() documentation also states that synchronization occurs on the first forward-backward after the context and that the forward pass belongs inside that context.

AMP GradScaler

AMP first multiplies the loss by \(s\), so DDP observes \(sG_r\). Linearity of AllReduce gives:

\[ \frac{1}{P}\sum_{r=0}^{P-1}sG_r = s\left(\frac{1}{P}\sum_{r=0}^{P-1}G_r\right) \]

Before the optimizer step, GradScaler.unscale_(optimizer) or GradScaler.step(optimizer) divides by \(s\). AMP inverse scaling sits on the optimizer path, while DDP world-size scaling sits on the bucket preparation path; linearity of AllReduce lets the two compose.

Runtime inspection of buckets and collectives

DDP's diagnostic data includes final bucket sizes. _get_ddp_logging_data() is an internal diagnostic interface: it is useful for analysis but should not become a dependency of training logic.

ddp_info = ddp_model._get_ddp_logging_data()

print(ddp_info.get("bucket_sizes"))
print(ddp_info.get("bucket_cap_bytes"))
print(ddp_info.get("prev_iteration_grad_ready_order_indices"))

TORCH_DISTRIBUTED_DEBUG=INFO/DETAIL adds DDP initialization data, runtime statistics, and collective consistency checks; exact fields depend on the version and debug level. Confirm the actual collective count with logical events in torch.profiler, Nsight Systems, or NCCL Flight Recorder, such as nccl:all_reduce or c10d::allreduce_ in the current trace. The PyTorch 2.12 collective profiling documentation shows the profiler workflow.

ncclDevKernel_AllReduce_... is a common kernel name in traces from the traditional NCCL path, not a stable interface. Count collective events first when determining bucket count, and only then inspect the GPU activity associated with an individual collective. The NCCL 2.31.2 documentation describes the relationship between channels and CUDA blocks.

Gradient ownership after collective reduction

Standard DDP replicates full parameters and gradients on every rank, so its default operation is AllReduce: after reduction, every rank holds the same complete gradient. ReduceScatter retains only one partition of the reduced result on each rank, which suits training systems that already shard gradients or optimizer state.

Training method Gradient communication Gradient held by each rank afterward
PyTorch DDP AllReduce by default Complete and identical
FSDP / ZeRO-style sharding Commonly ReduceScatter Only the shard assigned to that rank
DDP with a custom communication hook Chosen by the hook Must satisfy the layout expected by the later optimizer and parameter path

The communication primitive follows the ownership required after reduction. Standard DDP needs a complete gradient on every rank and therefore uses AllReduce. Megatron's distributed optimizer, ZeRO, and FSDP incorporate gradient shards and optimizer-state layout into their communication design, commonly using ReduceScatter so that each rank retains its assigned shard. Collective counts should be interpreted only after this ownership contract is identified.
