PyTorch DDP 梯度规约机制：Reducer、Bucket 与 NCCL AllReduce

loss.backward() 并不会等所有参数的梯度算完以后，再对整份模型梯度做一次 AllReduce。DDP 把参数梯度组织成若干 bucket。一个 bucket 内的梯度全部就绪后，Reducer 立即发起异步通信，让后续 backward 计算与前面 bucket 的通信重叠。本文沿着这条执行路径说明规约何时发生、一次 backward 会发起多少次 collective，以及 NCCL SUM 如何得到平均梯度。

0. 讨论范围

本文讨论标准 torch.nn.parallel.DistributedDataParallel，每个 rank 保存完整参数、完整梯度和完整优化器状态。源码说明以 PyTorch main commit 9c603a7 为基准。自定义 communication hook、join() 和稀疏梯度会改变部分细节，相关差异在对应章节单列。

DDP 的规约对象是梯度 bucket，不是参数，也不是整个模型。设一个 DDP 实例在 bucket 重建后有 \(B\) 个梯度 bucket。常规同步 backward 中，默认通信路径会为每个 bucket 发起一次梯度 AllReduce。

1. 从 wgrad 到 bucket

以 Linear 为例，rank \(r\) 上的 forward 和权重梯度写成：

\[ Y_r = X_r W^{\mathsf T}, \qquad G_r = \frac{\mathrm{d}L_r}{\mathrm{d}W} \]

GEMM 或其他 backward kernel 只计算本 rank 的局部梯度 \(G_r\)。DDP 不参与这个 wgrad kernel。局部梯度经过 autograd 的 fan-in 累加并写入参数的 .grad 后，DDP 注册在梯度累加器上的 post hook 才会运行。这个 hook 的挂载方式与 grad_fn、next_functions 与 AccumulateGrad 一文讨论的是同一层对象。

Reducer 构造阶段为每个可训练参数取得梯度累加器并注册 post hook。Reducer::autograd_hook() 的注释明确写明：调用发生在参数梯度已经累加到梯度 Tensor 之后。

从 Python 语义看，这段流程可以缩写为：

# 语义化伪代码，不是 PyTorch 的 Python 实现

local_backward_kernel(param)       # 计算当前分支贡献的 wgrad
accumulate_into(param.grad)        # 合并本 rank 的 fan-in 梯度
ddp_post_accumulate_hook(param)    # 通知 Reducer: 该参数已就绪

bucket = reducer.bucket_of(param)
bucket.write(param.grad)
bucket.pending -= 1

所以 DDP 所说的 "gradient ready" 不是某个 GEMM 刚刚结束，而是这个参数在当前 backward 中应收集的本地梯度已经完成 autograd 累加。

2. AllReduce 的触发时机

每个 bucket 维护一个未就绪参数计数 pending。参数 hook 运行时，Reducer 把梯度写入该参数对应的 bucket view，并将 pending 减一。计数归零说明这个 bucket 已经可以通信。对应源码在 mark_variable_ready()。

bucket ready 并不保证立刻发起通信。所有 rank 必须以相同顺序调用 collective，否则可能发生错配或挂起。DDP 因此按 bucket index 规约。若 bucket 1 先于 bucket 0 就绪，bucket 1 会暂时等待；bucket 0 就绪后，Reducer 可以连续发起 bucket 0 和 bucket 1。这个顺序约束写在 mark_bucket_ready() 中。

一次同步 backward 中的计算与通信重叠

通信是异步发起的。后面的 backward kernel 可以继续在计算 stream 上运行。最后一个 bucket 被调度后，autograd 安排收尾回调；finalize_backward() 处理各 bucket 的通信 future，并把规约结果映射回参数梯度。

对 NCCL backend，这里的等待主要建立 CUDA stream 之间的依赖。NCCL future 带有通信 stream 的设备信息，后续在当前 stream 上读取 .grad 会排在规约之后。默认情况下，loss.backward() 的 CPU 返回不等于执行了一次 cudaDeviceSynchronize()；此时 NCCL kernel 仍可能在 GPU 上运行。

图中的三个 AllReduce 按 bucket index 入队。这里的 overlap 指 NCCL 通信与后续 backward 计算重叠，不表示同一 process group 的三个 bucket collective 同时执行。

3. Collective 与 kernel 数量

这里要区分三种计数：参数数量、DDP 发起的逻辑 collective 数量、NCCL 在 GPU 上执行的 kernel 数量。它们没有一一对应关系。

配置 一次 backward 的梯度 collective 补充通信
默认同步 backward \(B\) 次 AllReduce，每个梯度 bucket 一次 无
no_sync() 内的 backward 0 次 梯度只在本地 .grad 中累加
离开 no_sync() 后的首个同步 backward \(B\) 次 AllReduce 规约对象包含此前累计的本地梯度
find_unused_parameters=True，动态图路径 通常仍为 \(B\) 次 另有一次参数使用位图 AllReduce；它不是梯度 bucket
自定义 communication hook 每个 ready bucket 调用一次 hook hook 可以发起零次、一次或多次 collective
skip_all_reduce_unused_params=True 允许跳过完全由未使用参数组成的 bucket 各 rank 的未使用参数集合必须保持一致

\(B\) 受 bucket 容量、参数大小、dtype、device 和稀疏梯度影响。默认 bucket_cap_mb 是 25 MiB，但 \(B\) 不一定严格等于总梯度字节数除以 25 MiB 后向上取整。DDP 还会根据首轮 backward 的梯度到达顺序重建 bucket，以改善计算与通信重叠。官方 DistributedDataParallel 文档给出了 bucket 容量及相关参数的定义。

find_unused_parameters=True 的动态图路径需要在 rank 之间同步参数使用情况。all_reduce_local_used_map() 对一份整型位图执行额外 AllReduce；这次通信不携带 wgrad，也不计入上面的 \(B\) 次梯度 collective。

一次 bucket AllReduce 对应一次 ProcessGroup::allreduce 调用。在传统 NCCL host API 路径中，每个 rank 的 profiler 通常会为它显示一个 ncclDevKernel_AllReduce_... 通信 kernel。NCCL channel 一般对应这个 kernel 内的 CUDA block / CTA，不是若干个独立 kernel。这里说的是常见实现形态，不是 DDP API 对 profiler trace 的保证。NCCL grouping、CUDA Graph、device API 以及 PyTorch 的 copy-engine collective 都可能改变逻辑 collective 与底层活动的映射。

4. NCCL SUM 与 DDP 平均梯度

设 data parallel group 有 \(P\) 个 rank，第 \(r\) 个 rank 的本地梯度是 \(G_r\)。DDP 默认结果为：

\[ G_{\mathrm{DDP}} = \frac{1}{P}\sum_{r=0}^{P-1}G_r \]

NCCL 并不替 DDP 决定平均语义。NCCL AllReduce 文档把 AllReduce 定义为带 reduction operator 的 collective；当 operator 为 SUM 时，每个 rank 都收到逐元素求和结果。PyTorch 默认 调用 _AllReduceBySumCommHook，该 hook 最终使用 ProcessGroup::allreduce，没有改成 AVG operator。

平均发生在 SUM 之前。默认路径把每个本地梯度先除以 div_factor，通常就是 process group 的大小 \(P\)，随后调用 SUM：

\[ \operatorname{NCCL\_SUM}\left( \frac{G_0}{P},\frac{G_1}{P},\ldots,\frac{G_{P-1}}{P} \right) = \frac{1}{P}\sum_{r=0}^{P-1}G_r \]

例如两个 rank 的标量梯度分别为 6 和 10。各 rank 先得到 3 和 5，NCCL SUM 后都得到 8。把除法放在通信前还能降低 FP16 等窄格式在求和时溢出的风险。PyTorch 的内置 AllReduceCommHook 也明确采用先除后加的顺序。

div_factor 在普通训练中等于 process group size。使用 DDP join() 处理不均匀输入时，它可以按配置取初始 world size 或仍在参与训练的有效 rank 数量。

自定义 communication hook 的语义不同

注册 register_comm_hook() 后，Reducer 不再预除 world_size。官方 API 文档明确要求 hook 自己负责需要的平均操作。下面这种 hook 只做 SUM，得到的梯度会比默认 DDP 大 \(P\) 倍：

def sum_only_hook(process_group, bucket):
    return (
        torch.distributed.all_reduce(
            bucket.buffer(),
            group=process_group,
            async_op=True,
        )
        .get_future()
        .then(lambda fut: fut.value()[0])
    )

若要保持默认 DDP 数值语义，应在 hook 中显式除以 group size，或直接参考 PyTorch 的 allreduce_hook。

5. wgrad scaling 的位置

world-size scaling 不在 Linear、Conv 或 attention 的 wgrad kernel 内。它发生在 Reducer 处理已就绪参数梯度时。当前实现根据梯度与 bucket 的存储关系选择不同路径：

梯度存储状态 缩放位置 源码行为
param.grad 与 bucket view 不共享存储 参数梯度写入 bucket 时 用 mul_out(bucket_view, grad, 1 / div_factor) 合并复制与缩放
gradient_as_bucket_view=True，两者已经 alias 参数被标记 ready 时 对相应 bucket view 原地 div_
batched_grad_copy=True 整个 bucket ready 时 先批量复制，再对 flat bucket 做一次 div_
注册自定义 communication hook 由 hook 决定 Reducer 跳过默认除法

前两条路径位于 mark_variable_ready_dense()。批量复制路径在 flush_deferred_copies() 中。默认路径在参数梯度就绪时完成缩放；批量路径等整个 bucket 就绪后统一缩放，随后发起 SUM AllReduce。

6. loss reduction、梯度累积与 AMP

训练代码里还有几种缩放会改变 wgrad 数值。它们与 DDP 的 world-size 平均属于不同层次。

缩放来源 发生位置 DDP 是否自动处理
loss 的 mean 或 sum 本地 loss 定义 否，DDP只接收由该 loss 产生的局部梯度
data parallel group 平均 Reducer 与 communication hook 默认处理，除数通常为 group size
gradient accumulation 的 \(1/K\) loss 或优化器侧约定 否，no_sync() 不会自动除以累计步数
AMP loss scale 的 \(s\) 与 \(1/s\) GradScaler.scale() 与 unscale_()/step() 否，DDP 规约的是仍带 loss scale 的梯度

局部 mean loss

若每个 rank 的 local batch 大小都为 \(N\)，本地 loss 是样本均值：

\[ L_r = \frac{1}{N}\sum_{i=1}^{N}\ell_{r,i} \]

DDP 再对 \(P\) 个 rank 的梯度取平均，结果正好对应 global batch \(PN\) 上的均值梯度：

\[ \frac{1}{P}\sum_{r=0}^{P-1}\frac{\mathrm{d}L_r}{\mathrm{d}W} = \frac{1}{PN}\sum_{r=0}^{P-1}\sum_{i=1}^{N} \frac{\mathrm{d}\ell_{r,i}}{\mathrm{d}W} \]

如果各 rank 的有效样本数不同，简单 rank 平均不再等同于按样本数加权的 global mean。DDP 不会从梯度 Tensor 推断各 rank 的样本权重。

no_sync() 与 \(K\) 个 microbatch

no_sync() 只关闭通信。前 \(K-1\) 个 microbatch 的梯度继续累加在本地 .grad 中，离开上下文后的同步 backward 再规约总和：

\[ G_r^{\mathrm{acc}} = \sum_{j=1}^{K}G_{r,j}, \qquad G_{\mathrm{DDP}}^{\mathrm{acc}} = \frac{1}{P}\sum_{r=0}^{P-1}G_r^{\mathrm{acc}} \]

公式里没有自动出现 \(1/K\)。若目标是 \(K\) 个 microbatch 的均值梯度，通常要把每个 microbatch loss 除以 \(K\)，或者在等价位置处理这个比例。官方 no_sync() 文档也说明同步发生在退出上下文后的首个 forward-backward。

AMP GradScaler

AMP 先把 loss 乘以 \(s\)，所以 DDP 看到的是 \(sG_r\)。AllReduce 的线性性质保证：

\[ \frac{1}{P}\sum_{r=0}^{P-1}sG_r = s\left(\frac{1}{P}\sum_{r=0}^{P-1}G_r\right) \]

随后 GradScaler.unscale_(optimizer) 或 GradScaler.step(optimizer) 在 optimizer step 前除以 \(s\)。这一步不是 DDP 的 wgrad scaling，也不发生在 NCCL 内。

7. 运行时如何确认 bucket 与 collective

DDP 的诊断数据可以查看最终 bucket 大小。_get_ddp_logging_data() 是内部诊断接口，适合分析，不宜作为训练逻辑依赖：

ddp_info = ddp_model._get_ddp_logging_data()

print(ddp_info.get("bucket_sizes"))
print(ddp_info.get("bucket_cap_bytes"))
print(ddp_info.get("prev_iteration_grad_ready_order_indices"))

设置 TORCH_DISTRIBUTED_DEBUG=DETAIL 也会在 DDP 初始化和运行日志中打印 bucket 信息。要确认实际 collective，应使用 torch.profiler、Nsight Systems 或 NCCL Flight Recorder，按 nccl:all_reduce、c10d::allreduce_ 等逻辑事件统计。PyTorch 的 collective profiling 文档给出了 profiler 的用法。

GPU trace 中的 ncclDevKernel_AllReduce_... 用来分析传统 NCCL 路径的实际执行。统计 bucket 数时，仍应先数 collective 事件，再展开其中某一次 collective 对应的 GPU 活动。NCCL 文档对 channel 与 CUDA block 的关系有明确说明。

8. DDP 与 reduce-scatter 的边界

标准 DDP 的参数和梯度在各 rank 上完整复制，因此默认用 AllReduce：规约后每个 rank 都拿到同一份完整梯度。ReduceScatter 则只把规约结果的一段留在每个 rank，适合梯度或优化器状态已经分片的训练方式。

训练方式 梯度通信 通信后每个 rank 持有的梯度
PyTorch DDP 默认 AllReduce 完整且相同
FSDP / ZeRO 类分片优化 常用 ReduceScatter 只保留本 rank 负责的 shard
DDP 自定义 communication hook 由 hook 决定 必须满足后续优化器与参数布局的约定

因此，看到训练框架使用 ReduceScatter 时，不能直接套用标准 DDP 的 "每个 bucket 一次 AllReduce"。Megatron distributed optimizer、ZeRO 和 FSDP 会把梯度分片与 optimizer state 布局纳入通信设计，规约结束后的 Tensor 所有权已经不同。
