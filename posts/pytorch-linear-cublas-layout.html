PyTorch Linear 与 cuBLAS GEMM 的布局对应

torch.nn.Linear 在模型代码中接收 row-major Tensor，底层 GEMM 接口却可能按另一套布局约定描述同一块内存。分析 profiler 中的 TN、NT 或 NN 时，需要先把 PyTorch 的矩阵公式转换到 cuBLAS 的 column-major 视图。这个转换同时决定操作数顺序、transpose mode 和求和规约维度；在 Hopper 上，它还决定 FP8 GEMM 能否直接满足 WGMMA 的固定输入布局。

同一缓冲区的两种矩阵视图

为隔离布局问题，下面只讨论二维、实数、contiguous row-major Tensor，并省略 bias。记 \(X\in\mathbb{R}^{m\times k}\)、\(W\in\mathbb{R}^{n\times k}\)、\(Y\in\mathbb{R}^{m\times n}\)。对任意 row-major 矩阵 \(Z\)，用 \(\widehat{Z}\) 表示 cuBLAS 对同一缓冲区的 column-major 解释。若 \(Z\) 的 shape 是 \(a\times b\)，那么：

\[ \widehat{Z}=Z^{\mathsf T}\in\mathbb{R}^{b\times a}. \]

因此，row-major 公式 \(C=AB\) 对应的 column-major 输出是 \(\widehat{C}=C^{\mathsf T}=B^{\mathsf T}A^{\mathsf T}\)。这里的转置只改变矩阵视图，不复制或重排缓冲区。Linear 的三组公式都可以沿用这条等式推导。

Linear 前向与反向的 GEMM

表中的两个字母依次表示 cuBLAS 的 transa 与 transb。字母 N 保持 column-major 矩阵不变，T 对它转置。

目标 PyTorch row-major 公式 同一输出缓冲区的 cuBLAS column-major 公式 cuBLAS 操作数 transpose mode reduction axis
前向 \(Y=XW^{\mathsf T}\) \(\widehat{Y}=WX^{\mathsf T}=\operatorname{op}_{T}(\widehat{W})\operatorname{op}_{N}(\widehat{X})\) A=w, B=x TN \(k\), input dimension
weight gradient \(\mathrm{d}W=\mathrm{d}Y^{\mathsf T}X\) \(\widehat{\mathrm{d}W}=X^{\mathsf T}\mathrm{d}Y=\operatorname{op}_{N}(\widehat{X})\operatorname{op}_{T}(\widehat{\mathrm{d}Y})\) A=x, B=dy NT \(m\), flattened batch dimension
input gradient \(\mathrm{d}X=\mathrm{d}Y W\) \(\widehat{\mathrm{d}X}=W^{\mathsf T}\mathrm{d}Y^{\mathsf T}=\operatorname{op}_{N}(\widehat{W})\operatorname{op}_{N}(\widehat{\mathrm{d}Y})\) A=w, B=dy NN \(n\), output dimension

transpose mode 描述交换操作数之后，cuBLAS 如何解释 A 与 B。以 wgrad 为例，PyTorch 计算 \(\mathrm{d}W=\mathrm{d}Y^{\mathsf T}X\)，同一输出缓冲区的 column-major 视图则保存 \(\widehat{\mathrm{d}W}=X^{\mathsf T}\mathrm{d}Y\)。调用顺序由此变为 A=x、B=dy，mode 为 NT；乘积沿 flattened batch 维 \(m\) 求和。

GEMM 的规约维度是两个输入共有、但没有保留在输出 shape 中的维度。矩阵乘法沿这个维度执行乘加，因而可以直接比较输入与输出 shape 来确定 reduction axis。

Linear 沿用前文的 \(m\)、\(k\)、\(n\)。Attention 中，\(S_Q\) 与 \(S_K\) 分别表示 query 和 key/value 序列长度，\(d\) 是 query/key head dimension，\(d_v\) 是 value head dimension；batch、head 和 attention scale 等不改变下表规约轴的维度与因子均予以省略。

模块 目标 GEMM 与 shape 输出 shape reduction axis
Linear forward \(X_{m\times k}W^{\mathsf T}_{k\times n}\) \(Y_{m\times n}\) \(k\), input_dim
Linear wgrad \(\mathrm{d}Y^{\mathsf T}_{n\times m}X_{m\times k}\) \(\mathrm{d}W_{n\times k}\) \(m\), flattened batch
Linear dgrad \(\mathrm{d}Y_{m\times n}W_{n\times k}\) \(\mathrm{d}X_{m\times k}\) \(n\), output_dim
Attention \(\mathrm{d}P\) \(\mathrm{d}O_{S_Q\times d_v}V^{\mathsf T}_{d_v\times S_K}\) \(\mathrm{d}P_{S_Q\times S_K}\) \(d_v\), value head dimension
Attention \(\mathrm{d}Q\) \(\mathrm{d}S_{S_Q\times S_K}K_{S_K\times d}\) \(\mathrm{d}Q_{S_Q\times d}\) \(S_K\), seq_K
Attention \(\mathrm{d}K\) \(\mathrm{d}S^{\mathsf T}_{S_K\times S_Q}Q_{S_Q\times d}\) \(\mathrm{d}K_{S_K\times d}\) \(S_Q\), seq_Q
Attention \(\mathrm{d}V\) \(P^{\mathsf T}_{S_K\times S_Q}\mathrm{d}O_{S_Q\times d_v}\) \(\mathrm{d}V_{S_K\times d_v}\) \(S_Q\), seq_Q

Linear wgrad 的 PyTorch 输出 shape 是 [output_dim, input_dim]。cuBLAS 对同一缓冲区的 column-major 视图为 \(\widehat{\mathrm{d}W}\in\mathbb{R}^{k\times n}\)，即 [input_dim, output_dim]；转置视图不改变规约维度 \(m\)。

这张表是一组布局假设下的代数映射，不证明某次 PyTorch 运行选择了特定 GEMM backend 或 kernel。ATen 可以根据 dtype、shape、stride 和平台选择 cuBLASLt 或其他实现；非 contiguous 输入也可能先产生副本或采用不同 leading dimension。cuBLASLt 可以通过 matrix layout descriptor 直接描述 row-major 输入，因此实际调用不一定显式交换操作数；datatype 对底层 kernel 的布局约束仍然存在。

Hopper FP8 的 transpose 与 TN 约束

前面的 TN、NT 和 NN 属于 GEMM 接口层；kernel 还要把这些逻辑矩阵映射到 Tensor Core 指令接受的 operand layout。分析 Hopper 时，transpose 需要按所在层次理解：

层次 表示 含义 是否重排整块内存
数学公式 \(A^{\mathsf T}\) 交换矩阵的行列坐标 公式本身不规定存储实现
cuBLAS API CUBLAS_OP_T GEMM 按转置后的逻辑视图解释 matrix descriptor 通常只是访问语义，不生成转置副本
Hopper WGMMA imm-trans-a, imm-trans-b 指令按另一组坐标映射消费 shared-memory tile 不物化完整的转置 tensor

WGMMA 的指令级 transpose

Hopper 的 wgmma.mma_async 由一个 warpgroup 执行 \(D=A B+D\)。PTX matrix descriptor 描述 shared memory 中的 tile；基础布局规定 \(A\) 为 row-major、\(B\) 为 column-major。FP16/BF16 变体在 shared-memory operand 上提供 imm-trans-a 和 imm-trans-b，允许指令在读取 tile 时切换逻辑方向。下面是 PTX ISA 9.0 中两类指令的语法模板：

// FP16/BF16: descriptor operand 带有 transpose immediate
wgmma.mma_async.sync.aligned.shape.dtype.f16.f16
    d, a-desc, b-desc, scale-d,
    imm-scale-a, imm-scale-b, imm-trans-a, imm-trans-b;

// FP8: E4M3/E5M2 语法没有 transpose immediate
wgmma.mma_async.sync.aligned.shape.dtype.atype.btype
    d, a-desc, b-desc, scale-d,
    imm-scale-a, imm-scale-b;

因此，“Tensor Core 支持 transpose”在这里有严格范围：Hopper WGMMA 可以直接改变 FP16/BF16 shared-memory descriptor operand 的读取方向。FP8、TF32 和整数变体没有这组 immediate operand。这个能力作用于输入 tile 的解释方式，与输出 accumulator 的 datatype 或 epilogue layout 是两件事。

FP8 的 K-major 布局

FP8 WGMMA 沿用固定的基础布局：\(A_{M\times K}\) 采用 row-major，\(B_{K\times N}\) 采用 column-major。row-major A 的 \(K\) 维连续，column-major B 的 \(K\) 维同样连续，所以两个 operand 都是 K-major。缺少 imm-trans-a/b 意味着指令不能把相反方向的 shared-memory tile 直接切换成这种布局。

同一个物理要求放到 column-major cuBLAS 语义下，就表现为 TN：row-major 的 \(M\times K\) 缓冲区会被看作 column-major 的 \(K\times M\) 矩阵，需要 T 才得到逻辑 operand A；column-major 的 \(K\times N\) operand B 直接使用 N。cuBLAS 13.0 因而要求 Hopper（compute capability 9.0）的 tensor-scaled 与 block-scaled FP8 kernel 使用 transposed A、non-transposed B。这里的 T 是 descriptor operation，并不等于执行一次独立的 transpose kernel。

Linear 训练中的影响

前文的布局推导可以直接判断三次 Linear GEMM 是否满足 Hopper FP8 的 TN contract：

路径 cuBLAS mode 直接满足 FP8 TN 不匹配时需要处理的输入方向
forward TN 是 row-major \(W\) 与 \(X\) 可通过输出转置视图直接映射
wgrad NT 否 \(X\) 与 \(\mathrm{d}Y\) 都需准备以规约轴 \(m\) 为连续维的表示，或重写 GEMM
dgrad NN 否 \(W\) 需要以规约轴 \(n\) 为连续维的转置表示，或重写 GEMM

Forward 的 TN 来自 \(\widehat{Y}=W X^{\mathsf T}\)，只改变同一缓冲区的矩阵视图。wgrad 与 dgrad 的自然映射分别是 NT 和 NN；若它们要使用 Hopper FP8 Tensor Core，kernel 或上层框架必须准备符合 TN/K-major 要求的 operand。可行方法包括在 quantize 时写出所需方向、在 global-to-shared 搬运中重排 tile，或者交换 operand 并利用 \((AB)^{\mathsf T}=B^{\mathsf T}A^{\mathsf T}\) 计算输出的转置视图。

当同一 tensor 会以两个方向参与多次 GEMM 时，系统也可以保留两份 FP8 物理表示，以额外存储换取重复使用。独立的 transpose 或 repack 会增加内存流量；若转换能够与 quantization、tile load 或 epilogue 融合，成本则取决于具体 kernel。FP8 的 transpose 限制约束的是 A/B tile 的供给方式，矩阵乘法的数学结果和 accumulator 精度由另外的指令字段决定。

PyTorch Linear and cuBLAS GEMM Layout Mapping

torch.nn.Linear receives row-major tensors in model code, while the underlying GEMM interface may describe the same memory through a different layout convention. Interpreting profiler labels such as TN, NT, and NN therefore begins by translating the PyTorch equations into cuBLAS column-major views. That translation determines the operand order, transpose mode, and reduction dimension together; on Hopper, it also determines whether an FP8 GEMM directly satisfies the fixed WGMMA input layout.

Two matrix views of one buffer

To isolate the layout issue, assume two-dimensional, real-valued, contiguous row-major tensors and omit the bias. Let \(X\in\mathbb{R}^{m\times k}\), \(W\in\mathbb{R}^{n\times k}\), and \(Y\in\mathbb{R}^{m\times n}\). For a row-major matrix \(Z\), let \(\widehat{Z}\) denote the column-major matrix that cuBLAS sees in the same buffer. If \(Z\) has shape \(a\times b\), then:

\[ \widehat{Z}=Z^{\mathsf T}\in\mathbb{R}^{b\times a}. \]

A row-major product \(C=AB\) consequently becomes \(\widehat{C}=C^{\mathsf T}=B^{\mathsf T}A^{\mathsf T}\) in the column-major view. This transpose changes only the matrix interpretation; it does not copy or rearrange the buffer. The same identity derives all three Linear equations below.

GEMMs in Linear forward and backward

The two mode letters denote cuBLAS transa and transb, in that order. Letter N leaves a column-major matrix unchanged, while T transposes it.

Target PyTorch row-major equation cuBLAS column-major equation for the same output buffer cuBLAS operands Transpose mode Reduction axis
forward \(Y=XW^{\mathsf T}\) \(\widehat{Y}=WX^{\mathsf T}=\operatorname{op}_{T}(\widehat{W})\operatorname{op}_{N}(\widehat{X})\) A=w, B=x TN \(k\), input dimension
weight gradient \(\mathrm{d}W=\mathrm{d}Y^{\mathsf T}X\) \(\widehat{\mathrm{d}W}=X^{\mathsf T}\mathrm{d}Y=\operatorname{op}_{N}(\widehat{X})\operatorname{op}_{T}(\widehat{\mathrm{d}Y})\) A=x, B=dy NT \(m\), flattened batch dimension
input gradient \(\mathrm{d}X=\mathrm{d}Y W\) \(\widehat{\mathrm{d}X}=W^{\mathsf T}\mathrm{d}Y^{\mathsf T}=\operatorname{op}_{N}(\widehat{W})\operatorname{op}_{N}(\widehat{\mathrm{d}Y})\) A=w, B=dy NN \(n\), output dimension

The transpose mode describes how cuBLAS interprets A and B after the operands have been swapped. For wgrad, PyTorch computes \(\mathrm{d}W=\mathrm{d}Y^{\mathsf T}X\), while the column-major view of the same output buffer stores \(\widehat{\mathrm{d}W}=X^{\mathsf T}\mathrm{d}Y\). The call consequently uses A=x, B=dy, and mode NT, with reduction over the flattened batch dimension \(m\).

The GEMM reduction dimension is the dimension shared by both inputs but absent from the output shape.Multiplication and accumulation take place along this dimension, so comparing the operand shapes with the result identifies the reduction axis directly.

Linear retains the \(m\), \(k\), and \(n\) notation introduced above. For attention, \(S_Q\) and \(S_K\) denote the query and key/value sequence lengths, \(d\) is the query/key head dimension, and \(d_v\) is the value head dimension. Batch, head, and attention-scale terms are omitted because they do not change the reduction axes below.

Module Target GEMM and shapes Output shape Reduction axis
Linear forward \(X_{m\times k}W^{\mathsf T}_{k\times n}\) \(Y_{m\times n}\) \(k\), input_dim
Linear wgrad \(\mathrm{d}Y^{\mathsf T}_{n\times m}X_{m\times k}\) \(\mathrm{d}W_{n\times k}\) \(m\), flattened batch
Linear dgrad \(\mathrm{d}Y_{m\times n}W_{n\times k}\) \(\mathrm{d}X_{m\times k}\) \(n\), output_dim
Attention \(\mathrm{d}P\) \(\mathrm{d}O_{S_Q\times d_v}V^{\mathsf T}_{d_v\times S_K}\) \(\mathrm{d}P_{S_Q\times S_K}\) \(d_v\), value head dimension
Attention \(\mathrm{d}Q\) \(\mathrm{d}S_{S_Q\times S_K}K_{S_K\times d}\) \(\mathrm{d}Q_{S_Q\times d}\) \(S_K\), seq_K
Attention \(\mathrm{d}K\) \(\mathrm{d}S^{\mathsf T}_{S_K\times S_Q}Q_{S_Q\times d}\) \(\mathrm{d}K_{S_K\times d}\) \(S_Q\), seq_Q
Attention \(\mathrm{d}V\) \(P^{\mathsf T}_{S_K\times S_Q}\mathrm{d}O_{S_Q\times d_v}\) \(\mathrm{d}V_{S_K\times d_v}\) \(S_Q\), seq_Q

PyTorch gives Linear wgrad the output shape [output_dim, input_dim]. The cuBLAS column-major view of the same buffer is \(\widehat{\mathrm{d}W}\in\mathbb{R}^{k\times n}\), or [input_dim, output_dim]; the transposed view leaves the reduction dimension \(m\) unchanged.

This table is an algebraic mapping under explicit layout assumptions. It does not establish which GEMM backend or kernel a particular PyTorch run selects. ATen may choose cuBLASLt or another implementation according to dtype, shape, stride, and platform; non-contiguous inputs may also require a copy or different leading dimensions. cuBLASLt can describe row-major inputs directly through matrix layout descriptors, so an actual call need not swap operands explicitly; datatype-specific layout constraints on the selected kernel still apply.

Transpose and TN constraints for Hopper FP8

The TN, NT, and NN modes above belong to the GEMM interface. A kernel must still map those logical matrices to operand layouts accepted by its Tensor Core instruction. On Hopper, transpose has three distinct meanings:

Layer Notation Meaning Does it rearrange the full buffer?
Mathematics \(A^{\mathsf T}\) Exchanges matrix row and column coordinates The equation does not prescribe storage
cuBLAS API CUBLAS_OP_T Makes GEMM interpret a matrix descriptor through its transposed logical view Normally changes access semantics without creating a copy
Hopper WGMMA imm-trans-a, imm-trans-b Consumes a shared-memory tile through a different coordinate mapping Does not materialize a complete transposed tensor

Instruction-level transpose in WGMMA

Hopper wgmma.mma_async executes \(D=A B+D\) across a warpgroup. PTX matrix descriptors identify tiles in shared memory; the base layout places \(A\) in row-major order and \(B\) in column-major order. FP16/BF16 variants expose imm-trans-a and imm-trans-b for shared-memory operands, allowing the instruction to change the logical direction in which it consumes a tile. The following templates come from the PTX ISA 9.0 syntax:

// FP16/BF16: descriptor operands include transpose immediates
wgmma.mma_async.sync.aligned.shape.dtype.f16.f16
    d, a-desc, b-desc, scale-d,
    imm-scale-a, imm-scale-b, imm-trans-a, imm-trans-b;

// FP8: E4M3/E5M2 syntax has no transpose immediate
wgmma.mma_async.sync.aligned.shape.dtype.atype.btype
    d, a-desc, b-desc, scale-d,
    imm-scale-a, imm-scale-b;

“Tensor Core transpose support” therefore has a precise scope here: Hopper WGMMA can change the read orientation of FP16/BF16 operands supplied through shared-memory descriptors. FP8, TF32, and integer variants do not expose those immediate operands. This facility controls the interpretation of input tiles; accumulator datatype and epilogue layout are separate properties.

The fixed K-major layout for FP8

FP8 WGMMA retains the fixed base layout: row-major \(A_{M\times K}\) and column-major \(B_{K\times N}\). The \(K\) dimension is contiguous in both cases, so both operands are K-major. Because FP8 has no imm-trans-a/b, an oppositely oriented shared-memory tile cannot be switched to this layout by the instruction itself.

The same physical requirement appears as TN under column-major cuBLAS semantics. A row-major \(M\times K\) buffer is seen as a column-major \(K\times M\) matrix and needs T to become logical operand A; a column-major \(K\times N\) operand B uses N directly. cuBLAS 13.0 consequently requires transposed A and non-transposed B for tensor-scaled and block-scaled FP8 kernels on Hopper, compute capability 9.0. The T is a descriptor operation here, not a separate transpose kernel.

Consequences for Linear training

The earlier layout derivation now determines whether each Linear GEMM satisfies the Hopper FP8 TN contract directly:

Path cuBLAS mode Directly matches FP8 TN Operand handling when it does not match
forward TN Yes Row-major \(W\) and \(X\) map directly through the transposed output view
wgrad NT No Both \(X\) and \(\mathrm{d}Y\) need representations contiguous along reduction axis \(m\), or the GEMM must be reformulated
dgrad NN No \(W\) needs a transposed representation contiguous along reduction axis \(n\), or the GEMM must be reformulated

The forward TN mapping follows from \(\widehat{Y}=W X^{\mathsf T}\) and changes only the matrix view of each buffer. The natural wgrad and dgrad mappings are NT and NN. To run them on Hopper FP8 Tensor Cores, a kernel or framework must prepare operands that meet the TN/K-major requirement. It may write the required orientation while quantizing, rearrange a tile during the global-to-shared transfer, or swap operands and use \((AB)^{\mathsf T}=B^{\mathsf T}A^{\mathsf T}\) to compute a transposed output view.

When one tensor participates in repeated GEMMs in both orientations, a system may retain two physical FP8 representations and trade storage for reuse. A standalone transpose or repack adds memory traffic; fusing the conversion with quantization, tile loading, or the epilogue changes that cost according to the kernel. The FP8 transpose restriction governs how A and B tiles are supplied. The mathematical result and accumulator precision are controlled separately.
