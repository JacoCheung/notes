TorchRec Sparse Dist Pipeline

TorchRec 的 sparse dist pipeline 通过跨 batch 调度，将后续输入的准备和分发与当前 batch 的训练重叠。本文比较 TrainPipelineSparseDist 与 PrefetchTrainPipelineSparseDist 的执行流程，重点说明两阶段输入通信、batch context 交接、CUDA stream 依赖和 embedding prefetch 的缓存条件，并用序列图与时间线呈现启动、稳定运行和排空过程。

本文分析 TorchRec 提交 1d87b8f79b7bb 中的两种 sparse dist pipeline，以多 rank、eager CUDA/NCCL 下的 ShardedEmbeddingCollection 为例。它返回 unpooled sequence embeddings，基础输入是固定 batch stride、无权重的 KJT。实现机制以这份 TorchRec 源码为依据。

Row-wise sharding 把 embedding 表按行分到多个 rank。每个 rank 的样本可能请求其他 rank 持有的行，所以输入分发要把 ID 送到对应的 row owner。KeyedJaggedTensor（KJT）携带 feature keys、ID values 和 lengths / offsets。Row owner 收到输入后查本地表，再通过输出 AllToAll 把向量发回请求方；backward 则沿相反方向回传向量梯度。Pipeline 主要提前调度输入准备和分发，本地 lookup、输出通信和 backward 仍由当前 batch 的模型执行。row-wise sequence sharding 组件；ShardedEmbeddingCollection.input_dist；sequence AllToAll 的 forward / backward

输入分发分两次等待。第一次消费 split-size metadata，读回接收尺寸并发起 KJT payload 通信；第二次消费 payload，重建本地 lookup 所需的 KJT。第一次返回时，payload 仍可能在传输。Pipeline 可以把这两个阶段安排在不同位置，提前推进后续 batch 的输入准备。各次 AllToAll 的细分调用也可参阅本系列的row-wise 输入分发。ShardedModule.forward；SplitsAllToAllAwaitable；KJT 的 payload awaitable

这里的 CPU 同步来自 metadata：发送前需要准备各 rank 的 split sizes，第一次 wait 要把接收尺寸从 CUDA 读成 Python lists，第二次 wait 的固定 stride 分支还会整理新 KJT 的 lengths / offsets。非空 CUDA tensor 走 _safe_tolist 路径时，会做 D2H 并同步当前 stream；已经缓存的 metadata 可以跳过重新计算。单独看到 Work.wait()，则不能据此断定 CPU 会等待整张 GPU。KJT.dist_splits；KJT.dist_init 的重排与 sync；CUDA metadata 的 D2H 与 stream synchronize

序列图从上往下表示主机提交顺序和逻辑依赖。Activation bar 表示调用或访问区间，错开的窄条表示嵌套 self-call，虚线空心条表示尚未消费的请求；stream 泳道和 bar 长度不代表实测 GPU 耗时。蓝色标 H2D、红色标 D2H / host sync、紫色标 AllToAll，黄色标 request wait，绿色标 stream 依赖。D1 / D2 / D3 与 row-wise 文章的读回位置一一对应；V1 / V2 标出固定版本中的额外校验读回。实际 stall 次数取决于 metadata 缓存和执行路径。点击消息或文件行号可打开源码，所有图默认适应宽度。

1. Pipeline 调度机制

训练处理 batch i 时，下一批 i+1 的 ID 已经可以从输入中取出。它的 row-wise 输入分发不依赖当前 batch 的模型输出，所以 TorchRec 可以提前发起这部分工作。当模型执行到下一批的 embedding 调用时，就可以继续处理之前发起的请求。

TorchRec 通过 tracing / rewrite 找到输入可以提前取出的 sharded module，并改写它的 forward。调度器提前创建 module context、调用 input_dist；模型执行到该模块时，runtime wrapper 从当前 batch 的 context 取回请求和状态，再调用 compute_and_output_dist。本地 lookup、输出 AllToAll 和 backward 仍按原有依赖执行。只有满足改写条件的调用才能采用这种调度。启动 input_dist 与融合 splits；PipelinedForward

Input Dist 的启动与等待

  • start_sparse_data_dist(batch, ctx)：调用输入分发，并组织可融合的 splits 通信。兼容的 metadata 可按 process group 合并；这不意味着所有 ID payload 合成了一个 collective。
  • wait_sparse_data_dist(ctx)：消费 fused splits awaitables，把得到的 tensors requests 存入 input_dist_tensors_requests。在这个过程中发起 payload 通信；函数返回时，payload 仍可在进行。

两种 pipeline 把第二次 wait 放在不同位置。普通版本在 PipelinedForward 中等待并重建输入；prefetch 版本在 prefetch_embeddings 中完成这一步，因为缓存预取需要已经分发好的 ID。start / wait_sparse_data_dist；prefetch_embeddings 的第二次 wait 与状态交接

Pipeline 改变这些操作的调度位置。KJTAllToAllForward 仍会调用 dist_splits() 取得主机发送尺寸，融合 splits 也仍需读回接收尺寸。第二次 wait 则必须把收到的 KJT 整理好，才能交给 lookup 或 prefetch。Pipeline 的 split sizes 准备；KJT.dist_init 的重排与 sync

Fused splits 的额外主机同步（V1）

在本文固定版本的 eager CUDA 路径中，fused-splits 构造阶段引入了额外的主机读回：FusedKJTListSplitsAwaitable 在发起 splits AllToAll 前，逐个对 CUDA split tensor 调用 _safe_tolist，执行 D2H，并通过 current_stream().synchronize() 阻塞 CPU，直到当前 stream 的前序工作和拷贝完成。融合 splits 前的校验读回；CUDA metadata 的 D2H 与 stream synchronize

这是该版本校验实现带来的额外开销。关闭 TORCHREC_OVERFLOW_DEBUG 仍会执行读回与同步，因为调试开关在读回之后的检查函数内判断。循环按 split tensor 执行，因此图中一个 V1 标记可能包含多次同步调用。

V2 则位于 splits 的第一次 wait 内，对发送端 _input_tensor 调用 _safe_tolist_2d。这次校验读回同样发生在检查函数判断调试开关之前，并产生 D2H 与主机等待。第一次 wait 中的发送端校验读回

这些校验读回由 PR #3978（a950331f5）引入，最早包含它们的周版本是 v2026.04.13.00；正式发布的 1.6.0 尚未包含，1.7.0 已包含。最初使用 CUDA tensor 的 .tolist()，随后 PR #4131（ec5baf373） 将其替换为 safe-list 路径，保留主机读回，并显式同步当前 stream。本文固定的 1d87b8f79b7bb 已包含这两次改动。

V1 属于 pipeline 的 fused-splits 构造路径；直接调用 row-wise 模块时不经过这一融合步骤。V2 位于两条路径共用的 SplitsAllToAllAwaitable._wait_impl，因此本系列两篇文章都标注 V2。两篇文章使用相同的源码提交。

Stream 依赖与生命周期

交接输入和 module context 时，TorchRec 分别处理执行顺序和存储生命周期。wait_stream 让消费者的 GPU 工作等待生产者；record_stream 记录 tensor 在另一个 stream 上的使用，避免 allocator 过早复用它的存储。通信结果是否就绪仍由执行依赖保证，record_stream 不承担等待。_wait_for_batch 的 stream 依赖与 record_stream；PipelinedForward

2. 普通 Sparse Dist Pipeline

普通 sparse dist pipeline 分别调度 H2D、input distribution 和训练，最多容纳三个在途 batch。稳定态时，i 做本次 forward / backward，i+1 做输入分发，i+2 从 dataloader 入队并拷到 GPU。以下采用默认配置 enqueue_batch_after_forward=False。TrainPipelineSparseDist.progress

# 稳定态语义示意；省略边界检查与配置分支。
zero_grad()
wait_for_current_batch(i)
start_sparse_data_dist(i + 1)   # 发起 splits
enqueue_batch(i + 2)           # H2D
losses, output = model(i)      # wrapper 内做 i 的第二次 wait
wait_sparse_data_dist(i + 1)   # 第一阶段 wait；发起 payload
backward(losses)
optimizer_step()
dequeue_batch(i)

当 batch i 的 forward 到达 embedding 模块，PipelinedForward 从 context 取出当前 batch 的 tensors request，在 data_dist stream 的上下文中调用 request.wait()，完成 KJT 重建。训练 stream 随后等待 data_dist stream 的相关工作，并接过输入与 context，继续 lookup 和输出通信。PipelinedForward

下一批 i+1 的 splits 在当前 forward 之前发起；它的 payload 要等当前 forward 返回后、backward 提交前才发起。这样，splits 有机会与当前 forward 重叠，payload 有机会与当前 backward 重叠。设置 enqueue_batch_after_forward=True 会把 H2D 入队移到 forward 之后，仍采用普通 pipeline 的调度。TrainPipelineSparseDist.progress

普通版本没有单独调度 cache prefetch，lookup 内部的缓存管理由 backend 配置决定。实际能重叠多少工作，还取决于 metadata 的 CPU 等待、collective 次序、GPU 资源竞争和 kernel 时长。多个 stream 提供了调度空间，并不保证通信耗时都能被计算覆盖。

3. Prefetch Pipeline

Prefetch 版本在 input distribution 之后，单独调度 embedding prefetch。需要缓存的 backend 用分发后的 owner-local IDs 提前准备本地查表所需的缓存；真正的 lookup 仍在当前 batch 的 forward 中执行。ShardedEmbeddingModule.prefetch 把各组输入交给对应 lookup 的 prefetch。ShardedEmbeddingModule.prefetch；lookup.prefetch 与 backend 配置检查

Payload 与 Prefetch 调度

在固定版本里，下一批的 wait_sparse_data_dist(i+1) 被放在当前 forward 之前，所以下一批的 ID payload 有机会与当前 forward 重叠。当前 forward 返回后，_prefetch(i+1) 才消费 payload、重建 KJT，并发起 prefetch；之后提交当前 batch 的 backward / optimizer，最后再启动 i+2 的 splits。PrefetchTrainPipelineSparseDist.progress / _prefetch

# 稳定态语义示意；i+1 的 splits 已在此前启动。
zero_grad()
wait_for_prefetch(i)
enqueue_batch(i + 2)
wait_sparse_data_dist(i + 1)   # 先发起下一批 payload
losses, output = model(i)      # 消费 i 的 post-prefetch input/context
clear_consumed_prefetch_state(i)
prefetch(i + 1)                # 第二次 wait + backend prefetch
backward(losses)
optimizer_step()
start_sparse_data_dist(i + 2)  # 准备下一次 progress
dequeue_batch(i)

prefetch_embeddings 在 data_dist stream 中做第二次 request.wait()；prefetch stream 等待该 stream 后，调用模块的 prefetch，并保存 module_input_post_prefetch 与 module_contexts_post_prefetch。下次 forward 的 PrefetchPipelinedForward 直接取这两份状态，让训练 stream 等待 prefetch stream，再执行 compute_and_output_dist，不再在那里消费 input payload request。prefetch_embeddings 的第二次 wait 与状态交接；PrefetchPipelinedForward

Prefetch 后端约束

GroupedEmbeddingsLookup 只为需要预取的 compute kernel 执行 prefetch，例如 FUSED_UVM_CACHING，其他路径可以直接返回。代码检查的 TBE backend 还要求正确设置 prefetch_pipeline，否则 TorchRec 会记录错误，指出 backward 使用的 cache locations 可能不正确。缓存位置的正确性依赖这些 backend 配置和约束，单独增加 CUDA stream 无法保证。需要 prefetch 的 compute kernel；lookup.prefetch 与 backend 配置检查

在 progress() 中，主机先调用 _prefetch(i+1)，再提交 backward(i)。源码没有在这两次调用之间设置统一的 host barrier 来等待下一批 prefetch 完成。两者能否重叠、backend 如何保护 cache locations，要结合 stream 和 cache 约束判断；图中的提交顺序也不能直接换算成 GPU 并行耗时。PrefetchTrainPipelineSparseDist.progress / _prefetch

图中的 H2D、input distribution、prefetch 和训练泳道按工作角色划分，底层可能还有其他 CUDA/NCCL streams。这个版本另外创建了一个新 Stream 对象，变量名为 _default_stream，并通过 forward_stream 参数传给 prefetch helper。这里的变量名并不表示 CUDA 默认 stream。prefetch 相关 stream 的构造；prefetch_embeddings 的第二次 wait 与状态交接

启动、稳态与排空

启动时，普通版本先为第一批发起 input distribution，执行第一次 wait，取得 tensors request，再把第二批入队。Prefetch 版本还要完成第一批的第二次 wait 和 prefetch，然后启动第二批的 splits。第一批没有前一批计算可以覆盖这些准备工作，所以启动耗时要单独分析。普通 pipeline 的入队、出队与填充；prefetch pipeline 的填充

进入稳定态后，batch 与 context 始终配对移动。Runtime 消费模块请求时，会从对应字典中 pop；batch 出队时，也要移走匹配的 context。这里假设被改写的 embedding 模块每次 forward 只调用一次，重复消费会报错。队列最多容纳三批，实际在途数量可以更少，显存占用也不能简单按单批大小乘三。普通 pipeline 的入队、出队与填充；PipelinedForward

默认 execute_all_batches=True 时，dataloader 耗尽后仍会执行已经入队的批次；没有 i+1 或 i+2 时，相应预备步骤会被跳过。评估模式则不会执行 training 分支中的 backward / optimizer。首尾阶段因此与上面的三批稳定态序列不同。普通 pipeline 的入队、出队与填充；TrainPipelineSparseDist.progress；PrefetchTrainPipelineSparseDist.progress / _prefetch

TorchRec sparse dist pipeline

TorchRec sparse distribution pipelines overlap preparation and distribution of later inputs with training of the current batch. This article compares TrainPipelineSparseDist and PrefetchTrainPipelineSparseDist, covering two-stage input communication, batch-context handoff, CUDA stream dependencies and embedding-cache requirements. Sequence diagrams and a timeline show startup, steady-state operation and drain.

This article examines the two sparse distribution pipelines at TorchRec commit 1d87b8f79b7bb, using multi-rank eager CUDA/NCCL ShardedEmbeddingCollection. It returns unpooled sequence embeddings. The baseline input is an unweighted KJT with fixed batch stride. Implementation explanations refer to this TorchRec source.

Row-wise sharding divides embedding-table rows across ranks. A rank's samples can request rows owned by other ranks, so input distribution routes IDs to their row owners. A KeyedJaggedTensor (KJT) carries feature keys, ID values, and lengths / offsets. Each owner looks up its local rows and returns vectors through output AllToAll; backward sends vector gradients in the reverse direction. Pipeline scheduling advances input preparation and distribution. Local lookup, output communication, and backward still execute as part of the current batch's model work. Row-wise sequence sharding components; ShardedEmbeddingCollection.input_dist; Sequence AllToAll forward / backward

Input distribution has two waits. The first consumes split-size metadata, reads receive sizes onto the host, and launches the KJT payload. The second consumes that payload and reconstructs the KJT for local lookup. Payload may still be in flight when the first wait returns. A pipeline can schedule these stages separately to prepare later batches ahead of use. For individual AllToAll calls, see row-wise input distribution in this series. ShardedModule.forward; SplitsAllToAllAwaitable; KJT payload awaitables

Host synchronization comes from metadata: split sizes must be prepared before sending, the first wait converts received CUDA sizes to Python lists, and the fixed-stride branch of the second wait prepares the new KJT's length and offset metadata. For nonempty CUDA tensors, _safe_tolist performs D2H and synchronizes the current stream. Cached metadata can avoid recomputation. A Work.wait() call alone does not establish that the CPU waits for the entire device. KJT.dist_splits; KJT.dist_init: permutation and sync; CUDA metadata D2H and stream synchronization

1. Pipeline scheduling

While the model processes batch i, IDs for batch i+1 can already be obtained from the next input. Their distribution does not depend on the current batch's model output. TorchRec can advance this preparation so that execution reaches the embedding module with an existing request.

The scheduler rewrites eligible sharded-module forwards, creates their contexts, and calls input_dist early. When model execution reaches a rewritten module, a runtime wrapper retrieves the request and state for the current batch and continues with compute_and_output_dist. Local lookup, output AllToAll, and backward dependencies remain. Tracing and rewriting determine eligibility; arbitrary sharded calls inside a model do not automatically qualify. Starting input_dist and fusing splits; PipelinedForward

Input distribution launch and wait

  • start_sparse_data_dist(batch, ctx) initiates input distribution and organizes compatible splits communication. Metadata can be fused by process group; this does not merge every ID payload into one collective.
  • wait_sparse_data_dist(ctx) consumes fused splits awaitables and stores tensors requests in input_dist_tensors_requests. It launches payload communication along the way; that payload can still be in flight when the function returns.

The two pipelines place the second wait in different functions. The ordinary version waits and reconstructs input in PipelinedForward. The prefetch version does so in prefetch_embeddings, because cache prefetch needs IDs that have already been distributed. start / wait_sparse_data_dist; prefetch_embeddings: second wait and state handoff

Pipelining changes where these operations run in the schedule. KJTAllToAllForward still calls dist_splits() for host send sizes, fused splits still require host receive sizes, and the second wait must prepare a usable KJT before lookup or prefetch. For one batch, the primary dependencies remain D1 → splits → D2 → payload → D3. Within one progress(i), the ordinary schedule is D1(i+1) → D3(i) → D2(i+1); the prefetch schedule is D2(i+1) → D3(i+1) → D1(i+2). Interleaving batches changes the order in which these labels appear.

Additional host synchronization in fused splits (V1)

On the pinned eager CUDA path, fused-splits construction adds a host readback: before launching splits AllToAll, FusedKJTListSplitsAwaitable calls _safe_tolist on each CUDA split tensor. Each conversion performs D2H and calls current_stream().synchronize(), blocking the CPU until preceding work on that stream and the copy complete. Stream dependencies and lifetimes

TorchRec handles execution order and storage lifetime separately when handing off distributed input and module context. wait_stream makes consumer GPU work wait for the producer. record_stream records tensor use on another stream so the allocator does not reuse its storage too early. Execution dependencies determine when communication results are ready; recording the stream does not perform that wait. _wait_for_batch: stream dependencies and record_stream; PipelinedForward

2. Standard sparse dist pipeline

The ordinary pipeline schedules H2D, input distribution, and training, with room for up to three batches in flight. In steady state, i runs forward / backward, i+1 advances input distribution, and i+2 enters the queue and is copied to the GPU. The sequence uses the default enqueue_batch_after_forward=False. # Steady-state pseudocode: boundary checks and configuration branches omitted.
zero_grad()
wait_for_current_batch(i)
start_sparse_data_dist(i + 1)   # launch splits
enqueue_batch(i + 2)           # H2D

optimizer_step()

When forward for batch i reaches an embedding module, PipelinedForward pops its tensors request and calls request.wait() in the data_dist stream context, reconstructing the KJT. The training stream then joins that stream's work, receives the input and context, and continues with lookup and output distribution. PipelinedForward

For i+1, splits launch before the current forward, whereas payload launches after forward returns and before backward is submitted. This creates opportunities for splits to overlap current forward work, and payload to overlap current backward work. Setting enqueue_batch_after_forward=True moves H2D enqueue after forward; it does not add an independent prefetch stage. TrainPipelineSparseDist.progress

The ordinary version has no separately scheduled cache prefetch. The backend configuration controls caching within lookup. Host metadata waits, collective ordering, GPU resource contention, and kernel duration determine how much work can overlap. Multiple streams allow overlap but do not guarantee that computation hides all communication time.

3. Prefetch pipeline

The prefetch version schedules embedding prefetch after input distribution. Backends that need caching use the distributed owner-local IDs to prepare the cache before lookup. The lookup itself still runs in the current batch's forward. ShardedEmbeddingModule.prefetch passes each group's input to the corresponding lookup's prefetch method. ShardedEmbeddingModule.prefetch; lookup.prefetch and backend configuration checks

Payload and prefetch scheduling

In the pinned implementation, wait_sparse_data_dist(i+1) runs before the current forward, allowing the next ID payload to overlap forward computation. After forward returns, _prefetch(i+1) consumes the payload, reconstructs the KJT, and schedules prefetch. The scheduler then submits current backward / optimizer work and starts splits for i+2. prefetch_embeddings performs the second request.wait() on the data_dist stream. The prefetch stream joins it, calls the module's prefetch, and saves module_input_post_prefetch and module_contexts_post_prefetch. On the next forward, PrefetchPipelinedForward consumes those objects, makes the training stream wait for the prefetch stream, and invokes compute_and_output_dist. It no longer consumes an input payload request there. prefetch_embeddings: second wait and state handoff; PrefetchPipelinedForward

Prefetch backend constraints

GroupedEmbeddingsLookup enters its prefetch path only for compute kernels requiring it, such as FUSED_UVM_CACHING; otherwise it can return immediately. For the TBE backends checked in the code, prefetch_pipeline must also be configured correctly. TorchRec logs an error otherwise, warning that backward cache locations may be wrong. Adding a CUDA stream alone does not establish the complete cache correctness protocol. Compute kernels that require prefetch; lookup.prefetch and backend configuration checks

The host calls _prefetch(i+1) before submitting backward(i). The progress() implementation does not insert a universal host barrier requiring next-batch prefetch to finish before current backward. Actual overlap and protection of cache locations depend on backend stream and cache constraints. These source-level submission sequences are not measured GPU timelines. Fill, steady state, and drain

At startup, the ordinary version begins input distribution for the first batch, performs its first wait to obtain a tensors request, and enqueues the second batch. The prefetch version also completes the first batch's second wait and prefetch before starting splits for the second batch. The first batch has no preceding computation to cover this preparation, so startup needs to be considered separately. Ordinary pipeline enqueue, dequeue, and fill; Prefetch pipeline fill

In steady state, batches and contexts move together. Runtime pops a module's request from the corresponding dictionary when consuming it, and dequeue must remove the matching context. Rewritten embedding modules are assumed to run once per model forward; repeated consumption raises an error. The queue holds up to three batches. Fewer may be in flight, and memory usage cannot be inferred by multiplying the size of one batch by three. Ordinary pipeline enqueue, dequeue, and fill; PipelinedForward

With the default execute_all_batches=True, already queued batches continue after the dataloader is exhausted. Preparation is skipped when i+1 or i+2 does not exist. Evaluation omits the training branch's backward and optimizer calls. These startup and drain sequences therefore differ from the full three-batch steady-state diagrams.
