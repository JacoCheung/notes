FP8 缩放机制与训练 Recipe

LLM 训练中的线性层和 attention 包含大量 GEMM，FP8 可以降低 operand 的存储与传输成本，并使用相应的 Tensor Core 路径。8 bit 浮点格式的动态范围和有效精度有限，训练系统因而要为量化值配套 scale，并明确 scale 粒度、更新时间、同步范围与算子边界。这组共同决定数值行为和执行成本的约定构成 FP8 training recipe。本文从数值格式与量化公式出发，逐步连接到 MXFP8 GEMM、Transformer Engine attention 和 BF16 fake quantization。

0. 范围

本文讨论 LLM 训练中的 FP8 mixed precision，范围包括 Transformer block 内的线性层、MLP 与部分 attention 计算。FP8 在这些计算密集位置充当局部加速类型；optimizer state、master weights、loss、softmax、normalization 与 reduction 通常保留 BF16 或 FP32，以满足各自的动态范围和累加精度要求。

分析 recipe 需要区分数值格式与系统策略两个层面：

层面问题例子
format一个 FP8 值本身怎么编码E4M3, E5M2
recipe训练系统怎么使用这些值DelayedScaling, current scaling, MXFP8 block scaling, HYBRID format

E4M3 与 E5M2 定义单个 FP8 值的 bit layout。HYBRID 属于格式选择策略，它把 forward 与 backward 张量映射到不同格式；MXFP8 属于 block scaling 机制，它把 scale 粒度细化到 32 个值，并采用 E8M0 scale。后续各节沿着这一区分展开。

1. FP8 数值格式

FP8 仍然是浮点数:1 bit 符号位,再把剩下的 bit 分给 exponent 和 mantissa。E4M3 给 exponent 4 bit,给 mantissa 3 bit。E5M2 给 exponent 5 bit,给 mantissa 2 bit。

格式取舍常见位置备注
E4M3范围较窄,有效精度较高weights, activations, forward GEMMNVIDIA 文档给出的最大有限值约为 448
E5M2范围更宽,有效精度较低activation gradients, backward GEMMNVIDIA 文档给出的最大有限值约为 57344,支持 inf
HYBRIDforward 用 E4M3,backward 用 E5M2Transformer Engine 默认 FP8 训练格式之一这是 format 选择策略,不是新的 bit layout

这种分配反映了常见训练张量的取舍：forward 的权重与 activation 往往更受 mantissa 精度影响，梯度则更容易出现较大的动态范围，因此 backward 常使用 exponent 更宽的 E5M2。具体模型仍需通过 amax、saturation 与收敛曲线验证格式选择。

2. scale 的位置

外部 scaling 把各个 tensor 的数值分布映射到 FP8 的有限网格。同一个 LLM 中，不同 tensor 的 amax 可能相差数个数量级，例如 0.02 与 2000。独立 scale 既让较大值进入可表示范围，也让常见值使用分辨率更高的码点区域。

实际系统一般把高精度 tensor x 映射成 FP8 raw data q,同时保存一个 scale。常见有两种等价写法。Transformer Engine 文档采用乘法 scale 习惯:

scale = FP8_MAX / amax(x)
q = cast_fp8(x * scale)
x_hat = q / scale

也有人把反方向的量叫 scale:

s = amax(x) / FP8_MAX
q = cast_fp8(x / s)
x_hat = q * s

两种写法互为倒数，因此代码与论文中的 scale 名称必须连同运算方向一起阅读。q 是 FP8 code；原始数值域中的近似值由 (q, scale) 或 (q, scale_inv) 共同确定。

# TE 习惯:保存 scale 和 scale_inv = 1 / scale
q_i = cast_fp8(x_i * scale_i)
r_i = decode_fp8(q_i)
x_hat_i = descale(r_i, scale_i) = r_i / scale_i

# 若代码里保存的是 scale_inv
x_hat_i = r_i * scale_inv_i

解码先把 FP8 bit pattern 还原为网格值 r_i，再由 scale 或 scale inverse 映射回 tensor 的数值域。因此，量化张量的完整语义由 raw FP8 data 与 scale metadata 共同组成。

MXFP8 把同一公式应用到 block 粒度。若每 32 个值组成一个 block，元素 i 属于 b(i)=floor(i/32)，则：

q_i = cast_fp8(x_i * scale_b(i))
r_i = decode_fp8(q_i)
x_hat_i = r_i * scale_inv_b(i)

在 GEMM 里,这个 block 通常沿那次 matmul 的 reduction 维度放。这样每个 dot product 的 32-element chunk 都能用自己的 scale,而不是被整行、整列或整个 tensor 的 outlier 牵着走。

scale 主要处理两件事:

  • 把 tensor 的最大值压到 FP8 可表示范围内,减少 overflow 或 saturation。
  • 让 tensor 中的大多数值落在更有分辨率的区域,少把 mantissa 浪费在空区间上。

BF16 依靠更宽的 exponent 覆盖训练中常见的数值范围；FP8 则把这部分适配工作显式交给 scale 与 recipe。

3. recipe 分类图

FP8 recipe 由多条相互独立的决策轴组成。下图分别列出 format、scale 粒度、amax 更新、张量覆盖范围与分布式同步；一个实际配置可以同时采用 HYBRID format、delayed scaling、per-tensor FP32 scale 和跨 TP group 的 amax reduction。

FP8 Scaling Mechanisms and Training Recipes

Linear layers and attention account for a large share of the GEMMs in LLM training. FP8 reduces operand storage and transport costs and enables the corresponding Tensor Core paths, but its limited dynamic range and effective precision require an external scale. The scale granularity, update policy, synchronization domain, and operator boundaries jointly define the numerical behavior and execution cost of an FP8 training recipe. This article begins with formats and quantization equations, then connects them to MXFP8 GEMM, Transformer Engine attention, and BF16 fake quantization.

0. Scope

This article covers FP8 mixed precision in LLM training, focusing on linear layers, MLPs, and selected attention paths inside Transformer blocks. FP8 serves as a local acceleration type in these compute-intensive regions. Optimizer state, master weights, loss computation, softmax, normalization, and reductions generally remain in BF16 or FP32 to meet their dynamic-range and accumulation requirements.

A recipe spans two distinct layers:

LayerQuestionExamples
formatHow one FP8 value is encodedE4M3, E5M2
recipeHow the training stack uses those valuesDelayedScaling, current scaling, MXFP8 block scaling, HYBRID format

E4M3 and E5M2 define the bit layout of an individual FP8 value. HYBRID is a format-selection policy that maps forward and backward tensors to different formats. MXFP8 is a block-scaling mechanism with one E8M0 scale per 32 values. The rest of the article follows this separation.

1. FP8 formats

FP8 is still floating point: 1 sign bit, with the remaining bits split between exponent and mantissa. E4M3 uses 4 exponent bits and 3 mantissa bits. E5M2 uses 5 exponent bits and 2 mantissa bits.

FormatTradeoffCommon placementNote
E4M3Narrower range, more useful precisionweights, activations, forward GEMMNVIDIA docs list the maximum finite value at about 448
E5M2Wider range, less useful precisionactivation gradients, backward GEMMNVIDIA docs list the maximum finite value at about 57344, with inf support
HYBRIDE4M3 for forward, E5M2 for backwardOne default FP8 training format in Transformer EngineA format policy, not a new bit layout

This split reflects a common training tradeoff. Forward weights and activations often benefit from mantissa precision, while gradients are more likely to require additional exponent range. A concrete model still needs validation through amax traces, saturation rates, and convergence behavior.

2. Where scale lives

External scaling maps each tensor distribution onto the finite FP8 grid. Tensor amax values inside one LLM can differ by several orders of magnitude, such as 0.02 and 2000. Independent scales keep large values within range while placing common values in regions with useful resolution.

A training stack usually maps a high precision tensor x into FP8 raw data q, plus a scale. Transformer Engine documents the multiplicative convention:

scale = FP8_MAX / amax(x)
q = cast_fp8(x * scale)
x_hat = q / scale

Some systems name the inverse quantity as the scale:

s = amax(x) / FP8_MAX
q = cast_fp8(x / s)
x_hat = q * s

The two forms differ by a reciprocal, so a scale name must be read together with the operation that uses it. Here, q is an FP8 code. The pair (q, scale) or (q, scale_inv) determines the approximate value in the original tensor domain.

# TE convention: keep scale and scale_inv = 1 / scale
q_i = cast_fp8(x_i * scale_i)
r_i = decode_fp8(q_i)
x_hat_i = descale(r_i, scale_i) = r_i / scale_i

# If the code stores scale_inv
x_hat_i = r_i * scale_inv_i

Decoding first maps the bit pattern to the FP8 grid value r_i; scale or scale inverse then maps it into the tensor's value domain. Raw FP8 data and scale metadata therefore form one complete quantized representation.

MXFP8 applies the same rule at block granularity. If one block covers 32 values and element i belongs to b(i)=floor(i/32), then:

q_i = cast_fp8(x_i * scale_b(i))
r_i = decode_fp8(q_i)
x_hat_i = r_i * scale_inv_b(i)

In GEMM, the block usually follows the reduction dimension of that matmul. Each 32-element dot-product chunk can then use its own scale instead of being dominated by an outlier from a full row, full column, or full tensor.

Scaling mainly does two things:

  • It keeps the largest values inside the representable range, reducing overflow or saturation.
  • It places common values into regions with useful resolution, instead of wasting mantissa codes on empty space.

BF16 covers common training ranges through a wider exponent. FP8 delegates that adaptation explicitly to scales and the surrounding recipe.

4. scale 粒度

scale 粒度决定一个 scale 覆盖多少元素。粒度越粗,metadata 越少,kernel 越简单,但 outlier 会影响更多元素。粒度越细,数值更稳,但 scale 的存储、加载、同步和 layout 都会变复杂。

粒度做法适合场景代价
per tensor整个 tensor 共用一个 FP32 scaleHopper 上常见 FP8 训练路径一个 outlier 会拉大整个 tensor 的范围
per axis按 row 或 column 维护 scale权重或 activation 分布沿某一维差异明显scale load 和 layout 约束增加
software block按小块维护 scale,例如 1x128 或 128x128需要处理 outlier,硬件未提供原生 microscalingkernel 和转置路径更复杂
MXFP8沿 scaling 方向每 32 个逻辑连续值一个 E8M0 scaleBlackwell Tensor Core 原生支持的 microscalingscale 方向和转置副本需要特别处理

per-tensor scaling 下，每个 tensor 只有一个 scale，梯度的动态范围仍对 exponent 提出较高要求，因此早期 FP8 recipe 常采用 HYBRID。MXFP8 缩小每个 block 内的动态范围，使更多 tensor 可以使用 E4M3，并把更多 bit 留给 mantissa。

MXFP8 中的“连续”描述 scaling 方向上的逻辑相邻关系。对 row-major X[M,K]，沿 K 的 32 个值通常也在内存中连续；对 row-major W[K,N]，沿 K 的 32 个值则以 N 为 stride。两者在数学上都沿 reduction 维度 K 分 block，存储访问形式却不同。实际 kernel 会按需要生成 columnwise copy、scale layout、padding 或 swizzle，以满足 Tensor Core 的布局要求。

矩阵乘的 block scale 沿该次运算的 reduction 维度组织。以 Y = X[M,K] @ W[K,N] 为例，两个 operand 都沿 K 分块，因为每个输出元素都在 K 上完成 dot product。若 W 以 row-major [K,N] 存储，这个 K 方向对应 columnwise；若 Linear 以 [N,K] 存储权重并计算 W.T，同一数学方向对应 rowwise。TE 中的 rowwise/columnwise 是存储与消费视角下的布局名称，数学定义仍以 reduction 轴为准。

# 数学语义
Y[m, n] = sum_k X[m, k] * W[k, n]

# block scale 要贴着 reduction chunk
X[m, k:k+32]      # 沿 K
W[k:k+32, n]      # 也沿 K

5. MXFP8 GEMM 的数学语义

把 GEMM 写成 C[M,N] = A[M,K] @ B[K,N]。MXFP8 block-scaled MMA 接收带有 block scale 的输入 operand：沿 K 的每个 32-value chunk 共享一个 scale，MMA 将解码并缩放后的值累加到 FP32 accumulator。其数学语义可以写成：

a_hat[m, k] = decode_fp8(qA[m, k]) * scale_inv_A[m, floor(k / 32)]
b_hat[k, n] = decode_fp8(qB[k, n]) * scale_inv_B[floor(k / 32), n]

acc_fp32[m, n] = sum_k a_hat[m, k] * b_hat[k, n]

CUTLASS 的 tcgen05 文档将其写成 D = (SFA * A) * (SFB * B) + C，其中 scale factor 沿 GEMM-K 组织。SFA 与 SFB 分别属于 A、B operand；输出 C 若需要量化，会在 epilogue 中生成自己的 scale。

因此，Tensor Core 的数值路径包含三个层次：MXFP8 payload 与 E8M0 block scale 构成输入，MMA 产生 FP32 accumulator tile，epilogue 决定最终写回 BF16、FP16、FP32 或重新量化后的 FP8/MXFP8。

MXFP8 A/B + E8M0 scale
  -> block-scaled MMA
  -> FP32 accumulator tile
  -> epilogue store as BF16, FP16, FP32, or re-quantized FP8/MXFP8

当 epilogue 把 C 存为 MXFP8 时，它要在输出空间 C[M,N] 中选择 block 并生成 output scale。输入 scale 服务已经完成的 K 规约，输出 scale 则服务 C 的下一次消费，两者属于不同的量化边界。

qC[m, n] = cast_fp8(acc_fp32[m, n] / scale_inv_C[block(m, n)])
C_hat[m, n] = decode_fp8(qC[m, n]) * scale_inv_C[block(m, n)]

TE 的 Quantizer.set_usage(rowwise=..., columnwise=...) 描述 output tensor 的后续消费布局。MXFP8 quantizer 在两种一维 block layout 之间选择：

usagescale shape含义
rowwise[prod(shape[:-1]), shape[-1] / 32]沿最后一维每 32 个值一个 scale。
columnwise[prod(shape[:-1]) / 32, shape[-1]]沿 flattened leading dimension 每 32 个值一个 scale。

表里的 shape 是逻辑形状。TE 源码还会按 kernel 要求把 scale tensor padding 到指定倍数,并要求参与 MXFP8 quantization 的维度满足 block 对齐。

TE Linear 的 forward epilogue 会把 output_quantizer 传给 general_gemm。如果调用方传入 fp8_output=True,Linear 取 GEMM1_OUTPUT quantizer,并把它设成 rowwise=True, columnwise=False。普通 C[M,N] 的 MXFP8 Linear output 会沿 N 方向量化:

C[m, n:n+32] 共享一个 output scale

QKV projection 的 output quantizer 沿 packed feature 维量化，也就是 [M, 3*H*D] 的最后一维。attention 的两次 matmul 则要求 Q/K 沿 head dim D 分块，V 沿 sequence 维 Sk 分块。reshape 只能改变 FP8 payload 的逻辑视图，无法重新定义既有 scale 对应的 block membership；因此，projection output 要成为 MXFP8 attention operand，需要在 DPA 边界按新的 reduction 方向重新量化。

6. amax 更新方式

scale 通常来自 amax,也就是 tensor 的最大绝对值。recipe 需要决定什么时候拿到这个 amax,以及用它怎样更新下一次的 scale。

策略怎么做优点风险
current scaling用当前 tensor 的 amax 计算当前 scalescale 跟分布同步amax reduction 和 cast 可能进入 critical path
just-in-time output scaling先产生高精度输出,再统计 amax 并量化数值上直接多 pass 代价高,NVIDIA 文档认为训练中通常不可取
delayed scaling记录历史 amax,用前几次的统计决定本次 scale性能路径干净,Transformer Engine 常用分布突变时 scale 会滞后
static scalingscale 来自校准或离线规则推理路径简单预训练分布持续变化,不适合作为默认训练策略

DelayedScaling 的状态一般包含 amax history、history 长度、取 history 最大值还是最近值、margin、format、以及分布式 reduce 规则。从实现角度看,它是一套 operator state。每个参与 FP8 的 tensor 都要能找到自己的 scale 和 amax 记录。

7. 训练系统里的 recipe

把前面的轴组合起来,常见 recipe 大致有下面几类。

recipe组成使用动机排查点
FP8 delayed HYBRIDper-tensor FP32 scale,forward E4M3,backward E5M2,历史 amaxHopper 时代的稳妥默认项amax history 是否过长,梯度 outlier 是否频繁
FP8 current scaling当前 amax,通常仍是 per-tensor 或 per-axis scalescale 跟随更快,便于实验amax reduction 是否拖慢 step time
FP8 block scaling小块 scale,format 多为 E4M3 或 HYBRID减轻 outlier 对整块 tensor 的影响转置、scale layout、kernel 支持
MXFP8每 32 个值一个 E8M0 scale,Blackwell 原生路径更细粒度 scaling,减少对 E5M2 的依赖scale rounding、转置副本、rowwise/columnwise 方向
calibrated FP8 inference离线 scale,常用于 W8A8 或 KV cache 量化部署简单,吞吐和显存收益明确校准集是否覆盖真实分布

训练 recipe 还要划定 FP8 的算子边界。常见实现把 GEMM operand 放入 FP8 路径，同时让 accumulation、bias、residual add、LayerNorm、RMSNorm、softmax、loss 与 optimizer state 保持更高精度。这些位置更依赖累加范围或归一化稳定性，而且通常不是 step time 中最值得压缩的部分。

分布式训练还要规定 amax 的同步域。TP 或 FSDP group 内的 rank 可以使用局部统计，也可以规约出共享统计；这项选择会影响 checkpoint 一致性、recompute、通信融合和调试。Transformer Engine 的 reduce_amax 等选项用于表达性能、确定性与局部分布适配之间的取舍。

8. TE MHA 的实现例子

Transformer Engine 的 MHA 数据流依次经过 QKV projection、dot product attention（DPA）和 output projection。FP8 recipe 可以控制 DPA 内部计算，也可以控制这三个模块之间的 tensor dtype；backend selector 再根据硬件、cuDNN、layout 与 recipe 类型选择可执行路径。TE v2.16 的 MXFP8 attention 把 DPA 视为独立 consumer，在其入口按 attention 的 reduction 方向量化 Q/K/V。

fp8_dpa 是 DPA 计算开关：FP8 autocast 开启且该字段为 true 时，backend selector 才进入 FP8 attention 分支。fp8_mha 是模块边界开关，用于尝试移除 QKV projection 与 DPA、DPA 与 output projection 之间的 BF16/FP16 cast。fp8_recipe.mxfp8() 则是 recipe 类型谓词，用来识别 MXFP8BlockScaling。三者分别回答计算模式、边界 dtype 与 scaling 类型。

开关或判断控制范围对 MHA 数据流的影响
fp8_dpaDPA 内部允许 DPA 把输入量化到 FP8,在 FP8 attention backend 中计算,再按边界需要返回高精度或 FP8。
fp8_mhaMHA 边界尝试让 QKV projection 直接输出 FP8 给 DPA,并让 DPA 输出 FP8 给 output projection。
mxfp8()recipe 类型判断当前 recipe 是否使用 MXFP8 block scaling；DPA 是否进入 FP8 路径仍由 fp8_dpa 控制。

两种配置对应两级 FP8 覆盖范围。fp8_dpa=True, fp8_mha=False 让 QKV projection 返回高精度 tensor，并在 DPA 边界完成量化；fp8_dpa=True, fp8_mha=True 进一步尝试让 QKV projection 直接输出 FP8，并把 DPA 的 FP8 输出交给 output projection。因此，fp8_mha=True 的运行语义建立在 FP8 DPA 上，而 fp8_dpa=True 可以独立使用。recipe dataclass 仅存储两个 bool 字段，最终可用性由 backend selector 判定。

attention 有两次 matmul:

S = Q[B,H,Sq,D] @ K[B,H,Sk,D]^T
O = P[B,H,Sq,Sk] @ V[B,H,Sk,Dv]

QK^T 的 reduction 维度是 D,Q 和 K 的 MXFP8 block scale 沿 D。P@V 的 reduction 维度是 Sk,P 和 V 的 scale 沿 Sk。如果 V 按 [B,H,Sk,Dv] 存,沿 Sk 就不是最后一维,TE 术语里会落到 columnwise。

attention matmuloperandreduction 维度TE v2.16 MXFP8 forward 用法
Q @ K^TQDrowwise
Q @ K^TKDrowwise
P @ VVSkcolumnwise
 
# TE v2.16 combine_and_quantize() 的 forward MXFP8 方向,概念化写法
Q: rowwise=True,  columnwise=False   # 沿 D
K: rowwise=True,  columnwise=False   # 沿 D
V: rowwise=False, columnwise=True    # 沿 Sk

这里出现了两个相邻却不同的量化边界。QKV projection 是普通 GEMM，输入 X 与权重 W 的 block scale 沿该 Linear 的 reduction 维度组织；DPA 包含两次 attention matmul，Q/K 服务 QK^T，V 服务 P@V。同一份 payload 进入新的消费者时，scale 布局必须匹配后者的 reduction 方向。

TE v2.16 用 qkv_fp8_output 控制 QKV projection 的 output dtype。该条件要求 FP8 autocast、fp8_mha=True、无 RoPE，并排除 current scaling 与 MXFP8；随后，代码把这个布尔值作为 fp8_output=qkv_fp8_output 传给 QKV 的 LayerNormLinear 或 Linear。

qkv_fp8_output = (
    fp8
    and fp8_mha
    and rotary_pos_emb is None
    and not float8_current_scaling
    and not mxfp8_scaling
)

MXFP8 采用另一条边界路径。QKV GEMM 先产生 bs(hd)、sb(hd) 或 t(hd) 等 packed layout，而 MXFP8 attention 要按 s 与 d 方向组织 bhsd、sbhd 或 thd 中的 block scales。于是 projection 以 module 的高精度 dtype 返回，DPA 准备逻辑再按 attention 的 reduction 方向量化 Q/K/V。

DPA output 使用独立的 dpa_fp8_output gate：TE v2.16 将其写成 fp8 and (fp8_dpa or fp8_mha) and not mxfp8_scaling。因此该版本的 MXFP8 DPA 把 O 以高精度边界 tensor 交给 output projection。_update_output_quantizer_roles 记录 QKV linear 到 DPA、DPA 到 output projection 及对应 backward 边的 quantizer role。

TE v2.16 可落地的 MXFP8 attention 数据流是:

QKV projection:
  MXFP8 GEMM 内部使用 projection 自己的 scale 方向
  输出回 BF16/FP16 Q, K, V

DPA:
  按 attention reduction 维度重新量化 Q/K/V
  Q/K 沿 D,V 沿 Sk
  FusedAttention 执行 FP8 DPA

backend selector 给出了 MXFP8 MHA 的版本边界。TE v2.16 先由 fp8_dpa 进入 FP8 attention 分支；若 recipe 为 MXFP8 且 fp8_mha=True，selector 会禁用 FusedAttention。下面的对象可以完成构造，但该版本不会据此获得端到端 MXFP8 MHA backend：

MXFP8BlockScaling(
    fp8_dpa=True,
    fp8_mha=True,
)

该版本可用的 MXFP8 配置通常保留高精度 MHA 边界：

MXFP8BlockScaling(
    fp8_dpa=True,
    fp8_mha=False,
)

selector 还要求 sm100+、满足版本要求的 cuDNN，以及 qkv_format != "thd" 等条件。任一条件失败都会关闭 FusedAttention，并可能使当前组合缺少可用的 FP8 attention backend。

9. 用 BF16 GEMM 模拟 MXFP8

BF16 GEMM 可以承载 MXFP8 的数值 reference：输入先按 MXFP8 block scale 规则量化到 FP8，再反量化回 BF16，最后调用原有 GEMM。该 fake quantization 路径复现量化与反量化误差；Tensor Core 吞吐、寄存器布局和 scale load 开销仍属于真实 MXFP8 kernel 的性能特征。

BF16 A, B
  -> MXFP8 fake quantize
  -> dequantize back to BF16
  -> BF16 GEMM

对一个 32-value reduction block,可以按下面的语义写 reference。这里 scale_inv 对应 TE 里常见的反 scale,MXFP8 的 E8M0 scale 约束用 power-of-2 rounding 模拟:

scale_inv_b = pow2ceil(amax(block) / FP8_MAX_E4M3)
q_i = cast_fp8_e4m3(x_i / scale_inv_b)
x_hat_i = decode_fp8(q_i) * scale_inv_b

下面的代码以数学 GEMM C = A[M,K] @ B[K,N] 为输入约定。A 沿最后一维 K 分 block，B 沿第一维 K 分 block。PyTorch Linear 常用 weight[N,K] 存储，对应路径由后面的 linear_mxfp8_sim 处理。

import torch
import torch.nn.functional as F

FP8_MAX_E4M3 = 448.0
MXFP8_BLOCK = 32

def pow2ceil(x):
    x = torch.clamp(x, min=2.0 ** -126)
    return torch.pow(2.0, torch.ceil(torch.log2(x)))

def fake_mxfp8_along_last_dim(x, block=MXFP8_BLOCK):
    # x: [..., K], block 沿最后一维 K
    k = x.shape[-1]
    pad = (-k) % block

    x_fp32 = x.float()
    if pad:
        x_fp32 = F.pad(x_fp32, (0, pad))

    k_pad = x_fp32.shape[-1]
    xb = x_fp32.reshape(*x_fp32.shape[:-1], k_pad // block, block)

    amax = xb.abs().amax(dim=-1, keepdim=True)
    scale_inv = pow2ceil(amax / FP8_MAX_E4M3)
    scale_inv = torch.where(amax == 0, torch.ones_like(scale_inv), scale_inv)

    q = (xb / scale_inv).to(torch.float8_e4m3fn)
    x_hat = q.to(torch.bfloat16) * scale_inv.to(torch.bfloat16)
    x_hat = x_hat.reshape(*x_fp32.shape)
    return x_hat[..., :k]

def fake_mxfp8_along_first_dim(x, block=MXFP8_BLOCK):
    # x: [K, N], block 沿第一维 K
    k, n = x.shape
    pad = (-k) % block

    x_fp32 = x.float()
    if pad:
        x_fp32 = F.pad(x_fp32, (0, 0, 0, pad))

    k_pad = x_fp32.shape[0]
    xb = x_fp32.reshape(k_pad // block, block, n)

    amax = xb.abs().amax(dim=1, keepdim=True)
    scale_inv = pow2ceil(amax / FP8_MAX_E4M3)
    scale_inv = torch.where(amax == 0, torch.ones_like(scale_inv), scale_inv)

    q = (xb / scale_inv).to(torch.float8_e4m3fn)
    x_hat = q.to(torch.bfloat16) * scale_inv.to(torch.bfloat16)
    x_hat = x_hat.reshape(k_pad, n)
    return x_hat[:k, :]

def mxfp8_gemm_sim(A, B, fp32_accum=False):
    # A: [M, K], B: [K, N]
    A_hat = fake_mxfp8_along_last_dim(A)
    B_hat = fake_mxfp8_along_first_dim(B)

    if fp32_accum:
        return A_hat.float() @ B_hat.float()
    return A_hat.to(torch.bfloat16) @ B_hat.to(torch.bfloat16)

Linear 权重常见存储是 weight[N,K],计算写成 X @ weight.T。这时 X 和 weight 的 reduction 维度 K 都在最后一维,所以 fake quantize 都可以沿 last dim 做:

def linear_mxfp8_sim(x, weight, bias=None, fp32_accum=False):
    # x: [M, K], weight: [N, K]
    x_hat = fake_mxfp8_along_last_dim(x)
    w_hat = fake_mxfp8_along_last_dim(weight)

    if fp32_accum:
        y = x_hat.float() @ w_hat.float().T
    else:
        y = x_hat.to(torch.bfloat16) @ w_hat.to(torch.bfloat16).T

    if bias is not None:
        y = y + bias
    return y

这段模拟可以用于两类对照。评估 MXFP8 cast 对既有 BF16 GEMM 的影响时，保留 BF16 GEMM；构造更稳定的数值 reference 时，设置 fp32_accum=True 并让最后的 matmul 使用 FP32 accumulation。

10. PyTorch 视角

PyTorch 的 float8 dtype 是 unscaled 的。torch.float8_e4m3fn 和 torch.float8_e5m2 只描述 raw data 的格式,并不自动携带 scale。scale 需要由上层建模代码、tensor subclass 或专门的 kernel API 管理。PyTorch dev-discuss 里提到的 torch.scaled_mm 就是这种分层设计:matrix 是 FP8,scale 作为单独参数传入。

因此，FP8 训练由 autocast 之外的一组运行时状态共同完成。autocast 负责 dtype promotion 与 cast；训练栈还要维护 per-tensor scale、amax history、分布式 reduction、module rewrite、backward 保存版本，并尽量让编译器融合这些附加操作。

诊断 FP8 训练时，可以按数值分布与执行开销检查四组信号：

  • 每类 tensor 的 amax 曲线是否突然跳变。
  • scale 是否长期被某些 outlier 拉大。
  • E4M3 路径是否出现明显 saturation,梯度是否需要 E5M2 或更细粒度 scale。
  • amax reduce 和 cast 是否抵消了 FP8 GEMM 的收益。

这些信号分别覆盖分布突变、outlier、格式饱和与额外开销，也把“启用 FP8”落实为可测量的 recipe 行为。

4. Scale granularity

Scale granularity decides how many values share one scale. Coarser granularity has less metadata and simpler kernels, but one outlier can affect more values. Finer granularity is usually more robust numerically, but scale storage, loads, synchronization, and layout get more complicated.

GranularityMechanismWhere it fitsCost
per tensorOne FP32 scale for the whole tensorCommon Hopper FP8 training pathOne outlier stretches the whole tensor range
per axisScale per row or columnWeights or activations with axis-specific distributionsMore scale loads and layout constraints
software blockScale small blocks, such as 1x128 or 128x128Outlier handling without native microscalingMore complex kernels and transpose paths
MXFP8One E8M0 scale per 32 logically consecutive values along the scaling directionNative Blackwell Tensor Core microscalingScale direction and transpose copies need care

Per-tensor scaling explains why early FP8 recipes often used HYBRID. With only one scale per tensor, gradients still put heavy pressure on dynamic range, so E5M2 is useful. MXFP8 reduces the dynamic range inside each block, allowing many tensors to use E4M3 and spend more bits on mantissa.

In MXFP8, "consecutive" describes logical adjacency along the scaling direction. For row-major X[M,K], 32 values along K are usually contiguous in memory. For row-major W[K,N], the same mathematical direction advances with stride N. Both operands are block-scaled along the reduction dimension K, but their storage access differs. A kernel may materialize a columnwise copy, scale layout, padding, or swizzle to satisfy the Tensor Core layout.

Matrix-multiplication block scales follow the reduction dimension of the operation. In Y = X[M,K] @ W[K,N], both operands are blocked along K because every output element is a dot product over that dimension. For row-major W[K,N], this K direction is columnwise. For the usual Linear storage W[N,K] with a computed W.T, the same mathematical direction is rowwise. TE's rowwise and columnwise terms describe storage and consumer layouts; the mathematical definition remains the reduction axis.

# Mathematical semantics
Y[m, n] = sum_k X[m, k] * W[k, n]

# Block scale follows the reduction chunk
X[m, k:k+32]      # along K
W[k:k+32, n]      # also along K

5. MXFP8 GEMM semantics

Write GEMM as C[M,N] = A[M,K] @ B[K,N]. MXFP8 block-scaled MMA accepts input operands with block scales: every 32-value chunk along K shares one scale, and the MMA accumulates decoded and scaled values into FP32. Its mathematical semantics can be written as:

a_hat[m, k] = decode_fp8(qA[m, k]) * scale_inv_A[m, floor(k / 32)]
b_hat[k, n] = decode_fp8(qB[k, n]) * scale_inv_B[floor(k / 32), n]

acc_fp32[m, n] = sum_k a_hat[m, k] * b_hat[k, n]

The CUTLASS tcgen05 documentation writes this as D = (SFA * A) * (SFB * B) + C, with scale factors organized along GEMM-K. SFA and SFB belong to operands A and B. An output that is quantized in the epilogue receives its own scale.

The Tensor Core path therefore has three layers: MXFP8 payloads and E8M0 block scales form the inputs, MMA produces an FP32 accumulator tile, and the epilogue writes BF16, FP16, FP32, or a re-quantized FP8/MXFP8 result.

MXFP8 A/B + E8M0 scale
  -> block-scaled MMA
  -> FP32 accumulator tile
  -> epilogue store as BF16, FP16, FP32, or re-quantized FP8/MXFP8

When the epilogue stores C as MXFP8, it selects blocks in the output space C[M,N] and produces output scales. Input scales serve the completed K reduction, while output scales serve C's next consumer; they belong to different quantization boundaries.

qC[m, n] = cast_fp8(acc_fp32[m, n] / scale_inv_C[block(m, n)])
C_hat[m, n] = decode_fp8(qC[m, n]) * scale_inv_C[block(m, n)]

TE's Quantizer.set_usage(rowwise=..., columnwise=...) describes how the output tensor will be consumed. An MXFP8 quantizer selects between two one-dimensional block layouts:

usagescale shapemeaning
rowwise[prod(shape[:-1]), shape[-1] / 32]One scale per 32 values along the last dimension.
columnwise[prod(shape[:-1]) / 32, shape[-1]]One scale per 32 values along the flattened leading dimension.

The shapes in the table are logical shapes. TE also pads scale tensors to kernel-friendly multiples and requires MXFP8-quantized dimensions to satisfy block alignment.

TE Linear passes output_quantizer into general_gemm in the forward epilogue. If the caller sets fp8_output=True,Linear takes the GEMM1_OUTPUT quantizer and sets it to rowwise=True, columnwise=False. A normal C[M,N] MXFP8 Linear output is quantized along N:

C[m, n:n+32] shares one output scale

The QKV projection output quantizer follows the packed feature dimension, the last dimension of [M, 3*H*D]. Attention's two matmuls require Q/K blocks along head dimension D and V blocks along sequence dimension Sk. Reshaping changes the logical view of the FP8 payload but does not redefine the block membership carried by its scales. An MXFP8 projection output therefore needs re-quantization at the DPA boundary along the new reduction directions.

6. Amax update policy

The scale usually comes from amax, the maximum absolute value of a tensor. A recipe must decide when that amax is known and how it updates the next scale.

PolicyMechanismBenefitRisk
current scalingUse the current tensor amax for the current scaleScale follows the current distributionAmax reductions and casts may enter the critical path
just-in-time output scalingProduce high precision output, compute amax, then quantizeNumerically directExtra passes are expensive; NVIDIA docs describe it as impractical for training
delayed scalingKeep amax history and use previous statistics for this stepClean performance path, common in Transformer EngineScale can lag sudden distribution changes
static scalingUse calibration or offline rulesSimple inference pathPre-training distributions drift, so it is not a default training strategy

DelayedScaling state usually contains amax history, history length, max versus most recent selection, margin, format, and distributed reduction rules. Implementation-wise, it is operator state. Every tensor that participates in FP8 needs a way to find its scale and amax record.

7. Recipes in training systems

Combining the axes above gives a few common recipe families.

RecipeCompositionMotivationDebug focus
FP8 delayed HYBRIDper-tensor FP32 scale, E4M3 forward, E5M2 backward, historical amaxConservative Hopper-era defaultHistory length, gradient outliers
FP8 current scalingcurrent amax, often per-tensor or per-axis scaleScale follows faster and is easy to experiment withAmax reduction overhead

A training recipe also defines the FP8 operator boundary. Common implementations place GEMM operands on the FP8 path while keeping accumulation, bias, residual add, LayerNorm, RMSNorm, softmax, loss, and optimizer state in higher precision. These operations rely more heavily on accumulation range or normalization stability and are often outside the most valuable part of the step to compress.

Distributed training also defines the synchronization domain for amax. Ranks in a TP or FSDP group may use local statistics or reduce a shared statistic; that choice affects checkpoint consistency, recompute, communication fusion, and debugging. Transformer Engine options such as reduce_amax express the tradeoff among performance, determinism, and adaptation to local distributions.

8. Transformer Engine MHA example

Transformer Engine MHA passes data through the QKV projection, dot product attention (DPA), and output projection. An FP8 recipe may control computation inside DPA as well as tensor dtypes at the boundaries between these modules. The backend selector then chooses an executable path from the hardware, cuDNN version, layout, and recipe type. In TE v2.16, MXFP8 attention treats DPA as an independent consumer and quantizes Q/K/V at its entrance along attention-specific reduction directions.

fp8_dpa is the DPA computation switch: the backend selector enters the FP8 attention branch when FP8 autocast is active and this field is true. fp8_mha is the module-boundary switch; it asks TE to remove BF16/FP16 casts between QKV projection and DPA, and between DPA and output projection. fp8_recipe.mxfp8() is a recipe-type predicate that identifies MXFP8BlockScaling. The three checks describe computation mode, boundary dtype, and scaling type, respectively.

switch or checkscopeeffect on MHA data flow
fp8_dpaDPA internalsAllows DPA to quantize inputs to FP8, run in an FP8 attention backend, then return high precision or FP8 at the boundary.
fp8_mhaMHA boundariesTries to make QKV projection output FP8 directly into DPA, and DPA output FP8 directly into the output projection.
mxfp8()recipe typeChecks whether the current recipe uses MXFP8 block scaling; fp8_dpa still controls entry into FP8 DPA.

The two configurations define different FP8 coverage. With fp8_dpa=True, fp8_mha=False, QKV projection returns a high-precision tensor and DPA quantizes at its boundary. With both fields true, TE additionally tries to make the QKV projection emit FP8 and pass the FP8 DPA output into the output projection. The runtime meaning of fp8_mha=True therefore builds on FP8 DPA, while fp8_dpa=True remains useful by itself. The recipe dataclass stores two boolean fields; the backend selector determines whether the requested combination is executable.

Attention has two matmuls:

S = Q[B,H,Sq,D] @ K[B,H,Sk,D]^T
O = P[B,H,Sq,Sk] @ V[B,H,Sk,Dv]

For QK^T, the reduction dimension is D, so Q and K use MXFP8 blocks along D. For P@V, the reduction dimension is Sk, so P and V use blocks along Sk. If V is stored as [B,H,Sk,Dv], Sk is not the last dimension, which maps to columnwise in TE terminology.

attention matmuloperandreduction dimTE v2.16 MXFP8 forward usage
Q @ K^TQDrowwise
Q @ K^TKDrowwise
P @ VVSkcolumnwise
 
# Conceptualized from TE v2.16 combine_and_quantize()
Q: rowwise=True,  columnwise=False   # along D
K: rowwise=True,  columnwise=False   # along D
V: rowwise=False, columnwise=True    # along Sk

These are adjacent but distinct quantization boundaries. QKV projection is a normal GEMM whose X and W block scales follow the Linear reduction dimension. DPA contains two attention matmuls: Q/K serve QK^T, while V serves P@V. When a payload enters a new consumer, its scale layout must match that consumer's reduction direction.

TE v2.16 controls the QKV projection output dtype with qkv_fp8_output. The condition requires active FP8 autocast, fp8_mha=True, and no RoPE, while excluding current scaling and MXFP8. The resulting boolean is passed as fp8_output=qkv_fp8_output into the QKV LayerNormLinear or Linear.

qkv_fp8_output = (
    fp8
    and fp8_mha
    and rotary_pos_emb is None
    and not float8_current_scaling
    and not mxfp8_scaling
)

MXFP8 uses a different boundary path. The QKV GEMM first produces packed layouts such as bs(hd), sb(hd), or t(hd), while MXFP8 attention organizes block scales along s and d in bhsd, sbhd, or thd. The projection therefore returns the module's high-precision dtype, and DPA preparation re-quantizes Q/K/V along the attention reduction directions.

DPA output has a separate dpa_fp8_output gate, written in TE v2.16 as fp8 and (fp8_dpa or fp8_mha) and not mxfp8_scaling. The MXFP8 path in this version therefore passes O to the output projection as a high-precision boundary tensor. _update_output_quantizer_roles records quantizer roles for QKV linear to DPA, DPA to output projection, and the matching backward edges.

TE v2.16 lands on this MXFP8 attention path:

QKV projection:
  MXFP8 GEMM uses projection-specific scale directions
  output returns to BF16/FP16 Q, K, V

DPA:
  re-quantize Q/K/V along attention reduction dimensions
  Q/K along D, V along Sk
  FusedAttention runs FP8 DPA

The backend selector defines the version boundary for MXFP8 MHA. TE v2.16 first uses fp8_dpa to enter the FP8 attention branch. When the recipe is MXFP8 and fp8_mha=True, the selector disables FusedAttention. The following object can be constructed, but this version does not obtain an end-to-end MXFP8 MHA backend from it:

MXFP8BlockScaling(
    fp8_dpa=True,
    fp8_mha=True,
)

The usable MXFP8 configuration in this version normally keeps high-precision MHA boundaries:

MXFP8BlockScaling(
    fp8_dpa=True,
    fp8_mha=False,
)

The selector also requires sm100+, a sufficiently recent cuDNN, and conditions such as qkv_format != "thd". A failed check disables FusedAttention and may leave the requested combination without a usable FP8 attention backend.

9. Simulating MXFP8 with BF16 GEMM

A BF16 GEMM can serve as the compute stage of an MXFP8 numerical reference. Inputs are quantized to FP8 with MXFP8 block scales, dequantized back to BF16, and then passed to the existing GEMM. This fake-quantization path reproduces quantization and dequantization error; Tensor Core throughput, register layout, and scale-load overhead remain properties of a real MXFP8 kernel.

BF16 A, B
  -> MXFP8 fake quantize
  -> dequantize back to BF16
  -> BF16 GEMM

For one 32-value reduction block, a reference can use the following semantics. scale_inv is the inverse scale commonly stored by TE, and the E8M0 constraint is approximated with power-of-2 rounding:

scale_inv_b = pow2ceil(amax(block) / FP8_MAX_E4M3)
q_i = cast_fp8_e4m3(x_i / scale_inv_b)
x_hat_i = decode_fp8(q_i) * scale_inv_b

The code below uses mathematical GEMM C = A[M,K] @ B[K,N] as its input convention. A is blocked along its last dimension K, while B is blocked along its first dimension K. The later linear_mxfp8_sim path handles the usual PyTorch Linear storage weight[N,K].

import torch
import torch.nn.functional as F

FP8_MAX_E4M3 = 448.0
MXFP8_BLOCK = 32

def pow2ceil(x):
    x = torch.clamp(x, min=2.0 ** -126)
    return torch.pow(2.0, torch.ceil(torch.log2(x)))

def fake_mxfp8_along_last_dim(x, block=MXFP8_BLOCK):
    # x: [..., K], block along the last dimension K
    k = x.shape[-1]
    pad = (-k) % block

    x_fp32 = x.float()
    if pad:
        x_fp32 = F.pad(x_fp32, (0, pad))

    k_pad = x_fp32.shape[-1]
    xb = x_fp32.reshape(*x_fp32.shape[:-1], k_pad // block, block)

    amax = xb.abs().amax(dim=-1, keepdim=True)
    scale_inv = pow2ceil(amax / FP8_MAX_E4M3)
    scale_inv = torch.where(amax == 0, torch.ones_like(scale_inv), scale_inv)

    q = (xb / scale_inv).to(torch.float8_e4m3fn)
    x_hat = q.to(torch.bfloat16) * scale_inv.to(torch.bfloat16)
    x_hat = x_hat.reshape(*x_fp32.shape)
    return x_hat[..., :k]

def fake_mxfp8_along_first_dim(x, block=MXFP8_BLOCK):
    # x: [K, N], block along the first dimension K
    k, n = x.shape
    pad = (-k) % block

    x_fp32 = x.float()
    if pad:
        x_fp32 = F.pad(x_fp32, (0, 0, 0, pad))

    k_pad = x_fp32.shape[0]
    xb = x_fp32.reshape(k_pad // block, block, n)

    amax = xb.abs().amax(dim=1, keepdim=True)
    scale_inv = pow2ceil(amax / FP8_MAX_E4M3)
    scale_inv = torch.where(amax == 0, torch.ones_like(scale_inv), scale_inv)

    q = (xb / scale_inv).to(torch.float8_e4m3fn)
    x_hat = q.to(torch.bfloat16) * scale_inv.to(torch.bfloat16)
    x_hat = x_hat.reshape(k_pad, n)
    return x_hat[:k, :]

def mxfp8_gemm_sim(A, B, fp32_accum=False):
    # A: [M, K], B: [K, N]
    A_hat = fake_mxfp8_along_last_dim(A)
    B_hat = fake_mxfp8_along_first_dim(B)

    if fp32_accum:
        return A_hat.float() @ B_hat.float()
    return A_hat.to(torch.bfloat16) @ B_hat.to(torch.bfloat16)

PyTorch Linear usually stores weights as weight[N,K] and computes X @ weight.T. In that case, the reduction dimension K is the last dimension for both X and weight, so both fake-quantization calls use the last-dimension helper:

def linear_mxfp8_sim(x, weight, bias=None, fp32_accum=False):
    # x: [M, K], weight: [N, K]
    x_hat = fake_mxfp8_along_last_dim(x)
    w_hat = fake_mxfp8_along_last_dim(weight)

    if fp32_accum:
        y = x_hat.float() @ w_hat.float().T
    else:
        y = x_hat.to(torch.bfloat16) @ w_hat.to(torch.bfloat16).T

    if bias is not None:
        y = y + bias
    return y

This simulation supports two comparisons. Keep the BF16 GEMM when measuring how MXFP8 casts affect an existing BF16 path. Set fp32_accum=True and accumulate the final matmul in FP32 when building a more stable numerical reference.

10. PyTorch view

PyTorch float8 dtypes are unscaled. torch.float8_e4m3fn and torch.float8_e5m2 describe the raw data format; they do not automatically carry a scale. The modeling layer, a tensor subclass, or a specialized kernel API must manage the scale. The PyTorch dev-discuss post uses torch.scaled_mm as the example: matrices are FP8, scales are separate arguments.

FP8 training therefore combines autocast with additional runtime state. Autocast handles dtype promotion and casts; the training stack also maintains per-tensor scales, amax history, distributed reductions, module rewrites, saved-tensor policy for backward, and compiler fusion for the added operations.

FP8 diagnosis can track four groups of signals across numerical behavior and execution cost:

  • whether amax curves jump suddenly for specific tensor classes;
  • whether scales are held too large by recurring outliers;
  • whether E4M3 paths show saturation, especially for gradients;
  • whether amax reductions and casts erase the FP8 GEMM speedup.

Together, these signals cover distribution shifts, outliers, format saturation, and runtime overhead, turning FP8 enablement into measurable recipe behavior.
