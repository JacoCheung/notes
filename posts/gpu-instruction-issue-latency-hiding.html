NVIDIA GPU 指令发射与延迟隐藏机制

CUDA kernel 编译为 SASS 后，每个 warp 沿当前控制路径上的指令序列向前推进。Warp scheduler 在每个 issue opportunity 从下一条指令已经 ready 的 warp 中选择 eligible 候选，并把指令送往相应的 execution pipe 或内存路径。若某个 warp 到达依赖尚未完成的 consumer，scoreboard 会暂时撤销它的 eligible 资格；此时，其他 resident warp 仍可接替发射。只有所有候选 warp 都无法填充 issue slot，等待才会暴露为 issue bubble。单 warp 的指令顺序、编译器安排的独立工作、跨 warp 调度和动态依赖检查共同决定了延迟能否被覆盖。

1. 发射顺序、完成顺序与 warp 调度

GPU 的发射顺序、完成顺序和 warp 调度属于不同层级。CUDA Programming Guide 将 SM 描述为按顺序发射指令，并说明 GPU 不依赖分支预测和推测执行。在本文讨论的 scheduler 视角中，每个 warp 提供当前执行路径上的下一条 SASS 指令，同一 SM 上的多个 warp 则由 scheduler 交错推进。

层级顺序由谁决定运行时行为
单个 warp 的 SASSptxas 生成最终指令序列scheduler 检查该 warp 的下一条指令；这条指令被依赖或资源阻塞时，后面的指令不会动态越过它。
多个 resident warp硬件 warp scheduler每个 instruction issue cycle 选择一个 eligible warp，并按架构允许的宽度发射一条或多条指令。不同 warp 的指令因此交错出现。
同一 warp 中的独立工作编译器静态调度编译器可以在保持程序语义的前提下，把不相关的算术或 load 提前，形成 ILP。
执行完成与返回各执行 pipe 和内存层次较晚发射的短延迟算术可能先于较早发射的 global load 完成。这是 out-of-order completion，不是 scheduler 越过被阻塞的下一条指令。

Scoreboard 把静态指令序列与动态完成时间连接起来。固定延迟算术的 producer-consumer 距离可以由编译器调度信息表达；global load、shared-memory load 等操作的完成时间取决于运行时状态，consumer 会等待相应的 scoreboard dependency。依赖满足后，该 warp 重新成为 eligible。

依赖未满足时，scheduler 通过切换 warp 寻找可发射工作，而不是越过同一 warp 当前被阻塞的 SASS 指令。这一点构成了它与 CPU 式动态乱序窗口的边界。Volta 及之后的 Independent Thread Scheduling 改变了 divergence、yield 和 reconvergence 的粒度，并未给每个 warp 增加一个搜索后续独立指令的乱序窗口。

固定延迟和可变延迟需要不同的依赖表达方式。公开专利 US9612836B2 给出了一种具体实现：coupled pipe 表示已知完成距离的执行路径，decoupled pipe 表示完成距离不确定、发射与写回之间可以存在 FIFO 的路径，texture unit 和 load/store unit 是后者的示例。该实现利用编译器标注的 producer-consumer 控制信息和硬件 scoreboard 状态检查处理可变完成时间。

证据边界：coupled/decoupled 是这份专利实施例中的实现术语，不是所有量产 GPU 的公开分类。专利中的 scoreboard 数量、计数方式、FIFO 和 DEPBAR 算法不能外推到任意架构。公开文档支持 in-order issue、动态依赖和 NCU stall 分类，但没有披露当前 GPU 完整的 scheduler queue、仲裁逻辑或 scoreboard 物理结构。

2. 四条指令的发射过程

下面这段 SASS 序列把静态排布、动态依赖和跨 warp 调度放到同一个例子中。假定 ptxas 最终保留了所示顺序：

I0: LDG  R8,  [R2]
I1: IADD R10, R11, R12
I2: FFMA R16, R8,  R20   // RAW dependency on I0
I3: IADD R21, R22, R23   // independent of R8

I0 发射后，global load 在 L1TEX 与更下层的内存通路中继续执行。I1 不读取 R8，因此可以随后发射。到达 I2 时，scoreboard 若仍显示 R8 对应的结果未返回，该 warp 会被归为 Long Scoreboard stall。

I3 虽然不依赖 R8，却位于被阻塞的 I2 后面。通常的 per-warp 顺序发射模型不会在运行时扫描更远的指令并让 I3 越过 I2。此时 scheduler 转而检查其他 resident warp。等 I0 的完成信号解除依赖，原 warp 才能发射 I2，然后到达 I3。

编译器仍可能改变这段最终顺序。如果数据依赖、控制流、别名关系和内存语义都允许，ptxas 可以把 I3 排到 I2 前面，甚至把 I0 提得更早。应以目标架构的 SASS 为准，而不是假定 CUDA C++ 或 PTX 的文本顺序就是最终发射顺序。

固定这段 SASS 顺序后，运行时能够利用的独立工作来自 I1 和其他 resident warp。下面的时间线展示 scheduler 如何在 Warp A 等待 I0 时发射 Warp B、Warp C，而不改变 Warp A 内部的顺序。

3. 减少 issue bubble 的四类机制

图中的 c2 至 c5 是 Warp A 的等待区间，Warp B 和 Warp C 的指令填入其中后，scheduler 仍能持续利用 issue slot。这种重叠就是 latency hiding；当所有候选 warp 都无法提供可发射指令时，等待才表现为 issue bubble。减少 bubble 的方法由此分为两类：前三项增加与等待重叠的可发射工作，第四项直接缩短 producer latency。

  1. 更多 eligible warps：提高合理范围内的 occupancy，让 scheduler 在一个 warp 等待时还有其他 warp 可选。occupancy 只提供 resident warp 上限；寄存器、shared memory 和 block 装箱仍可能减少实际候选数。
  2. 增加 ILP：展开循环、并行维护多个 accumulator，或让编译器把独立地址计算和算术放到 consumer 前面。ILP 会增加 live range，过度展开可能因寄存器压力降低 occupancy。
  3. 预取与分阶段重叠：把 load 提前到消费位置之前，或使用双缓冲，使当前 tile 的计算与下一 tile 的搬运重叠。预取距离必须覆盖延迟，同时不能把队列和寄存器占满。
  4. 降低 producer latency：改善 coalescing 与局部性、提高 cache hit rate、减少 shared-memory bank conflict，或把复用数据放入更近的存储层。这个方向减少等待本身，不属于延迟隐藏。

这些机制分别作用于不同层级：GPU Occupancy 的驻留资源模型与性能含义解释 resident warp 的资源上限，GPU Scoreboard 机制展开动态依赖与 SASS 控制语义，GPU Warp Stall 分析则把依赖等待放回完整的 stall 分类和 Source/SASS 归因流程。

4. Nsight Compute 的两组 stall 采样

延迟隐藏发生在 scheduler 层，因此需要同时观察“某个 warp 正在等待”和“该 scheduler 是否仍能发射其他工作”。Nsight Compute 13.3 Metrics Reference 用两组 source-level warp stall sampling 提供这两个视角：

NCU 视图Long Scoreboard metric采样条件
Warp Stall Sampling (All Samples)smsp__pcsamp_warps_issue_stalled_long_scoreboard采样到 warp 正在等待 L1TEX scoreboard dependency 即计数，不要求 scheduler 在同一周期空发射。
Warp Stall Sampling (Not-issued Samples)smsp__pcsamp_warps_issue_stalled_long_scoreboard_not_issued只在该 warp scheduler 没有发射任何指令的周期计数；该组指标要求 compute capability 7.0 或更高。

普通 Long Scoreboard 样本可以与另一个 warp 的成功发射同时出现，它用于定位经常等待的程序位置。Not-issued 把观察限制在该 warp scheduler 没有发射指令的周期，因此更接近 issue bubble，但仍不能证明 Long Scoreboard 是唯一原因；同一时刻可能还有其他 warp 受 barrier、fetch 或 execution-pipe throttle 限制。

推断边界：这些指标来自周期性统计采样，只覆盖被采样到的 warp 和周期。NCU UI 明确提示 All 和 Not-issued 可能在不同 profiling pass 采集，数值并不严格相关；不同视图中的原始 sample count 或归一化百分比都不能直接相除。两组视图用于建立“等待可能已被覆盖”或“等待可能与 issue bubble 重合”的诊断假设，完整归因还需要 Scheduler Statistics 和 SASS 证据。

在 Source 页面，可以切换 Warp Stall Sampling (All Samples) 和 Warp Stall Sampling (Not-issued Samples)，再按 source 或 SASS 行排序。Scoreboard 的 Attributed Stalls 会把 not-issued Long/Short 样本归因到 producer 行；实际停住的是 consumer，因此 producer 和当前高亮的 stalled instruction 可能不是同一行。

5. Long Scoreboard 的诊断假设

由于两组 sample count 不能直接换算，诊断应分别使用 All 与 Not-issued 视图内部的 hotspot 排名，由此建立两类待检验模式。Scheduler Statistics 再用 smsp__issue_active、eligible warps 和 skipped issue slots 判断等待是否暴露到发射吞吐；比较应来自同一 kernel 配置与稳定的重复采集。

5.1 假设 A：该 PC 在 All 视图靠前，未进入 Not-issued 热点

All 视图把该 PC 排在前列，说明采样经常在这里观察到等待；它没有进入 Not-issued 视图的主要热点，则提供“其他工作可能覆盖了等待”的候选解释。若 smsp__issue_active 保持较高、eligible warps 通常非零且 skipped issue slots 较少，TLP 或 ILP 覆盖等待的解释才得到加强。此时继续提高 occupancy 未必有收益，还可能降低 cache locality。

5.2 假设 B：同一 PC 在两个视图中均为热点

同一 PC 在两个视图中都进入热点集合，支持“Long Scoreboard 等待可能与 issue bubble 重合”的假设。只有 smsp__issue_active 偏低、eligible warps 不足且 skipped issue slots 明显时，访存延迟暴露到 issue 吞吐的判断才得到加强。随后再检查 ILP、occupancy、预取距离、coalescing 和 cache miss；若同时有 throttle 或 barrier，还要结合其 not-issued 热点和 pipe 利用率确定优先级。

6. Issue bubble 的源码归因流程

上述两类模式只确定了候选 PC。要把 issue bubble 归因到具体机制，还需把 scheduler 统计、Source 采样、SASS 依赖和内存系统指标串成同一条证据链：

  1. 先看 Scheduler Statistics。Issue active 偏低、eligible warps 不足且 skipped issue slots 明显，共同表明 scheduler 缺少可发射工作。
  2. 在 Source 页面分别检查 All 与 Not-issued。All 用于定位频繁等待，Not-issued 用于提出与发射空洞重合的候选位置。
  3. 切换到 SASS，确认 stalled consumer、scoreboard producer 以及两者之间已有多少独立指令。不要只看 CUDA 源码行。
  4. 区分 latency、queue backpressure 和 bandwidth。Long Scoreboard 是完成依赖；lg_throttle/tex_throttle 是发射队列反压；DRAM 接近峰值才支持带宽瓶颈判断。
  5. 一次只改变一个因素，例如预取距离、unroll、block size 或数据布局，并重新核对寄存器数、occupancy、cache hit rate 和 kernel time。

NVIDIA GPU Instruction Issue and Latency Hiding

After a CUDA kernel is compiled to SASS, each warp advances through the instruction sequence on its current control-flow path. At every issue opportunity, the warp scheduler selects among eligible warps whose next instruction is ready and sends the chosen instruction toward the corresponding execution pipe or memory path. When a warp reaches a consumer whose dependency is still outstanding, the scoreboard temporarily removes that warp from the eligible set, while other resident warps may continue issuing. The wait becomes an issue bubble only when no candidate warp can fill the issue slot. Per-warp instruction order, compiler-scheduled independent work, cross-warp scheduling, and dynamic dependency checks together determine whether latency is covered.

1. Issue order, completion order, and warp scheduling

Issue order, completion order, and warp scheduling belong to different layers of GPU execution. The CUDA Programming Guide describes SMs as issuing instructions in order and explains that GPUs do not rely on branch prediction or speculative execution. From the scheduler perspective used here, each warp supplies the next SASS instruction on its current execution path, while the scheduler interleaves multiple warps resident on the same SM.

LevelWho determines orderRuntime behavior
SASS within one warpptxas emits the final sequenceThe scheduler checks the warp's next instruction. If it is blocked by a dependency or resource, later instructions do not dynamically pass it.
Resident warpsHardware warp schedulerAt each instruction issue cycle, the scheduler selects one eligible warp and issues one or more instructions as the architecture permits. Instructions from different warps are interleaved.
Independent work in one warpStatic compiler schedulingThe compiler may move independent arithmetic or loads earlier while preserving program semantics, exposing ILP.
Execution completionExecution pipes and the memory hierarchyA later short-latency arithmetic instruction may finish before an earlier global load. This is out-of-order completion, not dynamic issue past a blocked next instruction.

The scoreboard connects the static instruction stream to dynamic completion time. Fixed-latency producer-consumer spacing can be represented in compiler scheduling controls. Completion of global and shared-memory loads depends on runtime conditions, so a consumer waits for the relevant scoreboard dependency. Once the dependency clears, the warp becomes eligible again.

When a dependency is outstanding, the scheduler finds issuable work by switching warps rather than bypassing the blocked SASS instruction in the same warp. This behavior sets the boundary with a CPU-style dynamic out-of-order window. Independent Thread Scheduling since Volta changes the granularity of divergence, yielding, and reconvergence, but does not give each warp a window that searches later instructions for independent work.

Fixed and variable latency require different dependency representations. Public patent US9612836B2 gives one concrete implementation: a coupled pipe has a known completion distance, whereas a decoupled pipe has an unknown completion distance and may include a FIFO between dispatch and execution. Texture and load/store units are examples of the latter. The embodiment handles variable completion time with compiler-marked producer-consumer controls and hardware scoreboard-state checks.

Evidence boundary: coupled and decoupled are implementation terms from this patent embodiment, not a published classification for every shipping GPU. Its scoreboard count, counter behavior, FIFOs, and DEPBAR algorithm cannot be projected onto arbitrary architectures. Public documentation supports in-order issue, dynamic dependencies, and NCU stall categories, but does not disclose the complete scheduler queues, arbitration policy, or physical scoreboard implementation of current GPUs.

2. Issue behavior of four instructions

The following SASS sequence places static layout, dynamic dependencies, and cross-warp scheduling in one example. Assume that ptxas preserves the shown order in the final binary:

I0: LDG  R8,  [R2]
I1: IADD R10, R11, R12
I2: FFMA R16, R8,  R20   // RAW dependency on I0
I3: IADD R21, R22, R23   // independent of R8

After I0 issues, the global load continues through L1TEX and possibly lower levels of the memory hierarchy. I1 does not read R8, so it can issue next. When the warp reaches I2, a pending result for R8 makes the warp report a Long Scoreboard stall.

Although I3 is independent of R8, it appears after the blocked I2. The usual per-warp in-order issue model does not scan farther ahead and dynamically issue I3 first. The scheduler checks other resident warps instead. When completion of I0 clears the dependency, the original warp can issue I2 and then reach I3.

The compiler may still change the final order. If data dependencies, control flow, aliasing, and memory semantics permit, ptxas can place I3 before I2 or move I0 earlier. Inspect SASS for the target architecture rather than assuming that CUDA C++ or PTX text order is the issue order.

With this SASS order fixed, the independent work available at runtime comes from I1 and other resident warps. The timeline below shows the scheduler issuing work from Warps B and C while Warp A waits for I0, without changing Warp A's internal order.

3. Four mechanisms that reduce issue bubbles

Cycles c2 through c5 in the diagram are Warp A's wait interval. Instructions from Warps B and C fill that interval, allowing the scheduler to keep using issue slots. This overlap is latency hiding; the wait becomes an issue bubble when every candidate warp lacks an issuable instruction. The mechanisms below therefore fall into two groups: the first three add work that can overlap the wait, while the fourth directly shortens producer latency.

  1. More eligible warps: raise occupancy within a useful range so the scheduler has alternatives while one warp waits. Occupancy supplies only a residency ceiling; registers, shared memory, and block packing determine the actual candidates.
  2. More ILP: unroll loops, keep independent accumulators, or let the compiler place address calculations and arithmetic before a consumer. ILP extends live ranges, so excessive unrolling can lower occupancy through register pressure.
  3. Prefetching and staged overlap: move loads ahead of consumption or use double buffering to overlap computation on one tile with movement of the next. Prefetch distance must cover latency without exhausting registers or queues.
  4. Lower producer latency: improve coalescing and locality, raise cache hit rates, reduce shared-memory bank conflicts, or place reused data in a nearer storage level. This reduces the wait itself and is latency reduction rather than latency hiding.

These mechanisms act at different levels. GPU Occupancy: Residency Resource Model and Performance Interpretation derives resident-warp limits, GPU Scoreboard Mechanism covers dynamic dependencies and SASS control semantics, and GPU Warp Stall Analysis places dependency waits in the full stall taxonomy and Source/SASS attribution workflow.

4. Two Nsight Compute stall-sampling groups

Latency hiding occurs at the scheduler level, so measurement must capture both a warp's wait and whether its scheduler can still issue other work. The Nsight Compute 13.3 Metrics Reference provides those perspectives through two source-level warp-stall sampling groups:

NCU viewLong Scoreboard metricSampling condition
Warp Stall Sampling (All Samples)smsp__pcsamp_warps_issue_stalled_long_scoreboardCounts a sampled warp waiting on an L1TEX scoreboard dependency regardless of whether the scheduler issued another instruction in that cycle.
Warp Stall Sampling (Not-issued Samples)smsp__pcsamp_warps_issue_stalled_long_scoreboard_not_issuedCounts only cycles in which that warp scheduler issued no instruction. This metric group requires compute capability 7.0 or later.

A regular Long Scoreboard sample can coexist with a successful issue from another warp and is useful for locating program positions that wait frequently. Not-issued restricts observations to cycles where that warp scheduler issued nothing, so it is closer to an issue bubble. It still does not prove that Long Scoreboard was the only cause: other resident warps may simultaneously be blocked by barriers, fetch, or execution-pipe throttling.

Inference boundary: these metrics come from periodic statistical sampling and cover only the sampled warps and cycles. The NCU UI warns that All and Not-issued data can be collected in different profiling passes, so their values do not strictly correlate. Neither raw sample counts nor normalized percentages from the two views can be divided directly. The views establish hypotheses that a wait may be covered or may coincide with an issue bubble; complete attribution also requires Scheduler Statistics and SASS evidence.

In the Source page, switch between Warp Stall Sampling (All Samples) and Warp Stall Sampling (Not-issued Samples), then rank source or SASS rows. Scoreboard Attributed Stalls assigns not-issued Long/Short samples to the producer location. The blocked instruction is the consumer, so the attributed producer and the currently stalled instruction can be different rows.

5. Long Scoreboard diagnostic hypotheses

Because sample counts from the two groups cannot be converted directly, diagnosis should rank hotspots within the All and Not-issued views separately. Those rankings produce two testable patterns. Scheduler Statistics then uses smsp__issue_active, eligible warps, and skipped issue slots to determine whether the wait is exposed to issue throughput. Comparisons should use stable repeated collections of the same kernel configuration.

5.1 Hypothesis A: the PC ranks highly in All but not among Not-issued hotspots

A high rank in the All view shows that sampling often observes a wait at this PC. Its absence from the main Not-issued hotspots suggests that other work may cover the wait. The TLP or ILP explanation becomes stronger when smsp__issue_active remains high, eligible warps are usually nonzero, and skipped issue slots remain low. Raising occupancy further may then provide little benefit and can reduce cache locality.

5.2 Hypothesis B: the same PC is a hotspot in both views

When the same PC enters the hotspot set in both views, Long Scoreboard waits may coincide with issue bubbles. The exposed-latency interpretation becomes stronger only when smsp__issue_active is low, eligible warps are scarce, and skipped issue slots are substantial. Then inspect ILP, occupancy, prefetch distance, coalescing, and cache misses. Concurrent throttle or barrier hotspots and execution-pipe utilization still determine whether Long Scoreboard is the leading cause.

6. Issue-bubble attribution workflow

The two patterns above identify candidate PCs. Attributing an issue bubble to a concrete mechanism requires scheduler statistics, Source sampling, SASS dependencies, and memory-system metrics to form one evidence chain:

  1. Start with Scheduler Statistics. Low issue active, scarce eligible warps, and substantial skipped issue slots together show that the scheduler lacks issuable work.
  2. Inspect All and Not-issued separately in the Source page. All locates frequent waits; Not-issued proposes candidate locations that coincide with issue gaps.
  3. Move to SASS and identify the stalled consumer, its scoreboard producer, and the independent instructions already placed between them. Do not rely only on CUDA source lines.
  4. Separate latency, queue backpressure, and bandwidth. Long Scoreboard is a completion dependency; lg_throttle/tex_throttle indicate issue-queue backpressure; near-peak DRAM traffic supports a bandwidth diagnosis.
  5. Change one factor at a time, such as prefetch distance, unrolling, block size, or layout, then recheck registers, occupancy, cache hit rate, and kernel time.
