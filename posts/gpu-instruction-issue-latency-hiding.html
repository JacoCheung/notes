NVIDIA GPU 指令发射与延迟隐藏机制

在读取数组、更新 accumulator 的 CUDA 循环中，global load 发出后，结果通常还要经过内存层次才能供算术指令使用。这段时间里，GPU 需要找到其他能做的工作：同一 warp 中排在 consumer 前面的独立计算，或其他 warp 的下一条指令。编译器把工作放在哪里，scheduler 在运行时选谁，决定了等待期间还有多少发射机会得到利用。

下面只跟踪四条指令。第二条和第四条都是独立整数加法，第三条却要等第一条 load。这个很小的例子能把几个容易混在一起的过程分开：指令发出了，结果是否已经完成；代码里还有独立工作，当前 warp 是否能执行到它；当前 warp 停住后，scheduler 又能从哪里找到工作。

快速索引：跟踪四条指令 · 区分编译器与 scheduler · 看多 warp 时间线 · 对照 profiler 现象 · 选择后续改动

1. 四条指令停在何处

先把编译后的指令顺序固定下来。以下是 SASS 风格的教学片段，补全寄存器操作数，省略地址准备和控制字段；它不是某个 kernel 的反汇编记录。I0 至 I3 只是指令标签。假定所有 lane 沿同一路径执行，除 I0 产生的 R8 外，其他输入都已经就绪，目标执行路径在需要时可以接收指令。

I0: LDG.E R8, [R2]
I1: IADD3 R10, R11, R12, RZ
I2: FFMA R16, R8, R20, R16
I3: IADD3 R21, R22, R23, RZ

1.1 发射把工作交出去，完成才让结果可用

I0 发射后，load 请求进入内存路径，返回的数据将写入 R8。I1 使用 R11 和 R12，不需要等这个值，因此可以在后续发射机会中执行。若它的整数加法较早完成，此时便会出现“后发射的 I1 先完成，先发射的 I0 还在执行”的状态。顺序发射允许不同操作的完成顺序不同。

走到 I2 后，情况改变了。FFMA 的一个输入来自 R8；如果 I0 尚未完成，scoreboard 依赖会阻止 I2 发射。NCU 把等待 L1TEX 操作结果的这种状态称为 Long Scoreboard。此时已经发出的 I0 仍可继续执行，停住的是等待结果的 consumer。

1.2 I3 独立，但还没有成为下一条指令

I3 的寄存器与 R8 无关，却位于 I2 后面。在 CUDA 13.2 描述的顺序发射模型中，当前 warp 沿已生成的指令序列推进。I2 被阻塞时，scheduler 不会为这个 warp 扫描后续指令，再把 I3 挑出来先执行。I0 返回并解除依赖后，warp 才能发射 I2，然后到达 I3。NVIDIA 的连续 load 讨论也用这一区别解释 warp 为什么停住。

固定这段顺序时，I0 与 consumer 之间只有 I1 可供同一 warp 执行。因此，“存在独立指令”和“现在有可发射的独立指令”有不同的条件。I3 要参与这段重叠，需要改变最终 SASS 的排布；原顺序下的运行时调度只能寻找其他 warp。

2. 谁能改变指令顺序

2.1 编译器把独立工作放到 consumer 前面

ptxas 在生成 SASS 时可以进行静态指令调度。对本例，I3 不读写 I0、I1、I2 使用的寄存器，也不改变控制流或内存地址。在这些条件下，候选顺序可以是：

I0 → I1 → I3 → I2

此时 load 与第一次使用之间有两条独立加法，原来只有一条。改变发生在编译阶段，运行时仍按新生成的顺序推进。真实代码还可能包含别名、异常路径、同步和内存顺序约束；移动 load 或其他操作必须保持这些语义。关于 ptxas 重排的公开讨论给出了提前安排 load 的实例，同时指出较长 live range 带来的寄存器代价。

源代码中增加一个临时变量或交换两行，并不保证目标架构上的 SASS 改变。检查结果时，先看最终顺序，再比较独立工作量和寄存器数。若编译器已经将 I3 放在 I2 前面，这个方向就没有新增的静态重叠空间。

2.2 Scheduler 选择其他已经就绪的 warp

运行时的选择发生在 warp 之间。每个 resident warp 的执行上下文保留在 SM 上，scheduler 可以从下一条指令已就绪的 eligible warp 中选择候选。Warp A 等待 I2 时，Warp B 的下一条算术或 Warp C 的独立访存都可能提供工作。CUDA Hardware Multithreading 描述了这种交错执行方式。

这也解释了为什么有些状态要等到运行时才知道：I0 的完成会受实际地址、缓存和内存请求状态影响，scoreboard 把完成事件连接到 I2 的依赖检查。依赖解除后，还要满足目标路径可接收等条件，warp 才能成为可发射候选。Scoreboard 机制一文展开这些依赖的表达。

3. 等待怎样被其他 warp 的工作覆盖

3.1 固定返回时刻的一段教学排程

下面暂时保留最初的 I0 → I1 → I2 → I3 顺序。只画一个 scheduler，并用每次机会至多发射一条指令的模型表示 q0 至 q7。假定 I0 的结果在 q6 前就绪，B/C 在 q2 至 q5 提供的指令均可发射。这些是教学条件，不是某代 GPU 的周期或延迟测量。

Warp A 在 q2 至 q5 都等待 I2，但 scheduler 依次发射 B0、C0、B1、B2，没有留下空格。A 的等待没有消失，load 也没有因此提早返回；改变的是等待期间有其他工作完成发射。这种把独立工作与等待重叠的安排就是 latency hiding。

在保持同一个返回时刻的对照模型中，如果移除 B/C 的可发射工作，q2 至 q5 就成为 issue bubble。I3 仍无法越过 I2。这个对照说明了 bubble 的条件：在该次发射机会里，没有候选 warp 能提供可发射指令。真实设备的发射宽度、指令间隔与选择策略按架构而定，图中的单发射排程只用于说明这个条件。

3.2 增加重叠与缩短延迟作用在不同地方

对这幅图有几种不同改法。让编译器把 I3 提到 I2 前面，会增加 Warp A 在等待前可执行的工作；让更多 warp 提供 eligible 指令，会增加 scheduler 的候选；提前请求下一个 tile，则会把搬运与当前 tile 的计算重叠。它们都需要实际可发射的独立工作，额外的 resident warp 数量本身不够。

另一个方向是让 I0 更早完成，例如改善访存合并与局部性，或把复用数据放进更近的存储层。对 shared-memory producer，还可以检查 bank conflict。这个方向直接减少等待，和用其他工作覆盖等待应分别评价。更多独立状态、预取与双缓冲可能占用寄存器、shared memory 或队列空间，收益需要连同这些成本一起看。

4. 在报告中区分 warp 等待与发射空档

时间线里，q2 的 Warp A 可以产生 Long Scoreboard 样本，而同一个 scheduler 正在发射 Warp B。NCU 的 All Samples 允许观察到这种组合；Not-issued Samples 则只在 scheduler 没有发射指令的采样周期记录状态。两者的定义见 NCU 2026.2 和 Source 页面说明。

5. 从这个模型选择下一次改动

对实际 kernel，先确认 compiler 已经留下多少独立工作。如果 I0 与 I2 之间仍然很近，可以测试调整展开、增加独立 accumulator 或预取距离，并检查最终 SASS；如果同一 warp 的重叠空间已经有限，则结合occupancy 的资源与运行模型判断是否还有可增加的 eligible 工作。若 producer 所在路径已经饱和，继续堆叠请求可能增加反压，需要回到工作量和访问方式。

每次尝试都保留原始输入与计算语义，核对寄存器、shared memory、spilling 和动态指令数量，并重复比较 kernel duration。独立工作增加且发射空档减少，可以支持延迟覆盖更充分的解释；若只是某个 warp 的等待样本减少而总时间未改善，则仍要检查其他成本。后续优化应沿着未被覆盖的等待或新增代价继续，而不是把所有 stall 都当成需要消除的事件。

附录 B：独立线程调度与依赖实现

Independent Thread Scheduling 的范围

从 Volta 开始，Independent Thread Scheduling 维护 per-thread 执行状态，使线程能在 sub-warp 粒度分歧、yield 与重新会合。它处理的是线程执行路径与参与集合。本文固定了所有 lane 沿同一路径的四条 SASS；上述能力没有让这里的 I3 自动越过当前路径上被阻塞的 I2。

固定与可变完成时间的一个实现例子

公开专利 US9612836B2 用 coupled pipe 描述具有已知完成距离的执行路径，用 decoupled pipe 描述完成距离不确定的路径，后者可以通过 FIFO 暂存已提交指令。它用编译器标注的控制信息与硬件 scoreboard 检查处理可变完成时间。这个实施例提供了理解依赖控制的具体材料；其中的 queue、scoreboard 数量和 DEPBAR 算法不应当作所有量产 GPU 的统一规格。

NVIDIA GPU Instruction Issue and Latency Hiding

In a CUDA loop that reads an array and updates an accumulator, a global load must travel through the memory hierarchy before arithmetic can use its result. During that interval, the GPU needs other work: independent computations placed before the consumer in the same warp, or the next instruction of another warp. Where the compiler places work and which warp the scheduler chooses determine how many issue opportunities remain occupied during the wait.

The example below follows just four instructions. The second and fourth are independent integer additions, but the third needs the result of the first load. It separates three practical questions: whether an issued instruction has completed, whether existing independent work is reachable by the current warp, and where the scheduler can find work once that warp stops.

1. Where the four instructions stop

First fix the compiled instruction order. This is a teaching fragment in SASS style, with register operands shown and address preparation and control fields omitted. It is not recorded disassembly from a kernel. I0 through I3 are instruction labels. Assume every lane follows the same path, all inputs except the R8 produced by I0 are ready, and the target execution paths can accept instructions when needed.

I0: LDG.E R8, [R2]
I1: IADD3 R10, R11, R12, RZ
I2: FFMA R16, R8, R20, R16
I3: IADD3 R21, R22, R23, RZ

1.1 Issue hands work off; completion makes its result available

After I0 issues, the load request enters the memory path and will return data into R8. I1 uses R11 and R12, so it can issue later without waiting for that value. If its integer addition finishes first, the later-issued I1 has completed while the earlier-issued I0 is still executing. In-order issue permits different completion orders for different operations.

The situation changes at I2. One FFMA input comes from R8, so an outstanding I0 result creates a scoreboard dependency that prevents I2 from issuing. NCU calls this wait for an L1TEX result Long Scoreboard. The already-issued I0 can continue executing; the blocked instruction is its consumer.

1.2 I3 is independent but is not the next instruction yet

I3 does not depend on R8, but it follows I2. Under the in-order issue model described by CUDA 13.2, the warp advances through its generated instruction stream. When I2 is blocked, the scheduler does not scan farther ahead in that warp and select I3 to execute first. Once I0 completes and clears the dependency, the warp can issue I2 and then reach I3. NVIDIA's discussion of consecutive loads uses this distinction to explain a stalled warp.

With this sequence fixed, only I1 is available to the same warp between I0 and its consumer. Existing independent work and currently issuable independent work therefore have different requirements. Making I3 overlap this interval requires a different final SASS order. Runtime scheduling with the original sequence must look to other warps.

2. Who can change instruction order

2.1 The compiler places independent work before the consumer

ptxas performs static instruction scheduling while generating SASS. In this example, I3 neither reads nor writes registers used by I0, I1, or I2, and changes no control flow or memory address. Under those conditions, a candidate order is:

I0 → I1 → I3 → I2

Two independent additions now separate the load from its first use instead of one. The change takes place during compilation; runtime execution still follows the newly generated sequence. Real code may also have aliasing, exceptional paths, synchronization, and memory-order constraints. Moving a load or another operation must preserve those semantics. A public discussion of ptxas scheduling describes early load placement and the register cost of longer live ranges.

Adding a temporary variable or swapping source lines does not guarantee different SASS for the target architecture. Check final order, independent work, and register count. If the compiler already places I3 ahead of I2, that direction offers no additional static overlap in this fragment.

2.2 The scheduler selects another ready warp

Runtime selection occurs between warps. A resident warp's execution context remains on the SM, allowing the scheduler to choose among eligible warps whose next instruction can issue. While Warp A waits at I2, Warp B's next arithmetic instruction or Warp C's independent memory access may supply work. CUDA Hardware Multithreading describes this interleaving.

Some conditions can only be resolved at runtime. Completion of I0 depends on actual addresses, caches, and memory-request state; the scoreboard connects the completion event to I2's dependency check. Even after that dependency clears, acceptance by the target path and other issue conditions must hold. GPU Scoreboard Mechanism develops the dependency representation.

3. How other warps cover the wait

3.1 A teaching schedule with a fixed return point

Retain the original I0 → I1 → I2 → I3 order for now. The diagram shows one scheduler with at most one instruction issued at each opportunity q0 through q7. Assume I0's result is ready before q6 and that the B/C instructions supplied at q2 through q5 can issue. These are teaching conditions, not cycle or latency measurements from a GPU.

Warp A waits at I2 throughout q2 through q5, while the scheduler issues B0, C0, B1, and B2 without an empty opportunity. A still waits, and its load does not return earlier because of this activity. Other work is issued during the interval. This overlap of independent work with waiting is latency hiding.

In a comparison model retaining the same return point, removing the issuable B/C work makes q2 through q5 issue bubbles. I3 still cannot pass I2. This establishes the condition for a bubble: no candidate warp can supply an issuable instruction at that opportunity. Hardware issue width, instruction spacing, and selection policy depend on architecture. The single-issue schedule here only illustrates the condition.

3.2 More overlap and shorter latency act in different places

Several changes affect different parts of the figure. Moving I3 before I2 during compilation adds work available to Warp A before it waits. More warps providing eligible instructions add scheduler candidates. Requesting the next tile early overlaps its movement with computation on the current tile. All require actual issuable independent work; a higher resident-warp count alone does not provide it.

Another direction is to finish I0 sooner by improving coalescing and locality or keeping reused data in closer storage. For a shared-memory producer, bank conflicts are another candidate. This directly reduces waiting and should be distinguished from covering it with other work. Independent state, prefetching, and double buffering may consume registers, shared memory, or queue space, so assess their benefit together with those costs.

4. Distinguish warp waits from issue gaps in a report

At q2 in the figure, Warp A could produce a Long Scoreboard sample while the same scheduler issues Warp B. NCU All Samples allows this combination; Not-issued Samples records states only in sampled cycles when the scheduler issues no instruction. The definitions appear in NCU 2026.2 and the Source page documentation.

Other warps may simultaneously wait on barriers, instruction fetch, or a target pipe. A Not-issued Long Scoreboard sample therefore does not exclude other restrictions. All and Not-issued can also come from different profiling passes; their sample-count ratio does not measure how much latency was hidden. Use them to locate candidates, then interpret those candidates with scheduler activity and actual duration.

To trace the sampled PC back to I0, the Long Scoreboard example in Warp Stall Analysis follows consumer, producer, metrics, and a concrete change. While Warp A is stalled, its scheduler may still issue instructions from other warps.

5. Use the model to choose the next change

For a real kernel, first establish how much independent work the compiler has exposed. If I0 and I2 are still close, test unrolling, independent accumulators, or prefetch distance, then inspect final SASS. If overlap within one warp is limited, use the occupancy resource and runtime model to assess whether more eligible work is available. If the producer's path is already saturated, piling on requests can increase backpressure; return to work volume and access patterns.

Preserve inputs and computational semantics for each comparison. Check registers, shared memory, spilling, and dynamic instruction counts, and repeat the kernel-duration measurement. More independent work with fewer issue gaps supports better latency coverage. If only a warp's wait samples fall while total time stays unchanged, investigate other costs. Continue from the uncovered wait or new tradeoff rather than treating every stall as an event that must disappear.

Appendix B: Independent thread scheduling and dependency implementation

The scope of Independent Thread Scheduling

Since Volta, Independent Thread Scheduling maintains per-thread execution state and supports divergence, yielding, and reconvergence at sub-warp granularity. It concerns thread execution paths and participating sets. The example fixes four SASS instructions on one path followed by all lanes; those capabilities do not automatically move I3 past the blocked I2 on that path.

One implementation for fixed and variable completion times

Public patent US9612836B2 uses coupled pipe for a path with a known completion distance and decoupled pipe for a path whose completion distance is unknown. The latter may hold dispatched instructions in a FIFO. The embodiment handles variable completion through compiler-marked controls and hardware scoreboard checks. It is concrete material for understanding dependency control; its queues, scoreboard counts, and DEPBAR algorithm are not a uniform specification for shipping GPUs.
