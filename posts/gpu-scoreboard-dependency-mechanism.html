GPU Scoreboard 机制：Warp 依赖跟踪、SASS 控制与 Long/Short Stall

CUDA kernel 读入数据后，通常还要用这些值做乘加、计算地址或判断分支。Load 已经发射，结果却未必已经回到寄存器；同一个 warp 在这段时间里还可能有别的指令可做。硬件需要分清哪些工作能够继续，哪些工作必须等结果。Scoreboard 就出现在这条 load 到后续指令的依赖关系上。

分析报告时，这段等待可能落在一条 FFMA 上。它所在的行有很多 Long Scoreboard 样本，值得检查的 producer 却是前面那条 LDG。要从报告找对改动位置，需要同时理解指令的先后关系、编译器留下的依赖控制，以及 profiler 如何记录和归因等待。

1. 一次读取与随后消费结果的指令

考虑一个执行乘加的 warp：先从 global memory 读出一个输入，中间做一次独立的整数加法，再把读出的值乘入累加器。下面是为了说明依赖而写的 SASS 示意，省略地址计算和目标相关修饰；它不是某次编译输出或测量记录。

I0: LDG.E R8, [R2]
I1: IADD3 R10, R11, R12, RZ
I2: FFMA R16, R8, R20, R16
I3: IADD3 R21, R22, R23, RZ

I0 产生 R8，因此称为这条依赖的 producer；I2 读取 R8，是对应的 consumer。假定其他操作数已经就绪，I1 不需要等待这次 load，而 I2 必须等到 R8 可用。这是一条 read-after-write（RAW）数据依赖。

Scoreboard 是与尚未完成的操作关联的动态依赖状态；scheduler 用它判断 warp 当前指令要求的完成条件是否已经满足。 对这个例子，只需把 load 对应的状态记成 pending 或已满足。寄存器保存数值，scoreboard 保存判断能否继续所需的控制状态。NCU 的依赖视图据此连接等待中的指令和它的前驱操作。

这个区别在 cache 命中时仍然存在。命中可能缩短 load 的完成时间，consumer 仍然需要等待结果就绪。它等待多久，要看 producer 的完成时刻和 consumer 抵达这条依赖的时刻，而不能从 FFMA 的算术延迟直接得出。

2. Warp 在哪里停下，又如何继续

I0 发射后，load 在执行路径中前进，对应依赖进入 pending。随后 I1 可以发射。若 warp 到达 I2 时 load 还没有完成，I2 的输入条件不满足，这个 warp 暂时不能提供这条指令的发射机会。

I3 虽然也不读取 R8，但在给定的 SASS 序列中排在 I2 后面。这里采用同一条 warp 指令路径按既定顺序发射的模型；等待期间，scheduler 可以从自己管理的其他 eligible warp 中选择指令。CUDA 的Hardware Multithreading描述了这种选择 warp 下一条就绪指令的发射方式。

编译器能改变 consumer 到达的时刻

如果程序语义允许，编译器可以把 I3 放到 I2 前面。这给 load 多留出一段独立工作，consumer 可能在结果已经就绪时才到达。这里利用的是同一 warp 内的指令级并行（ILP）；其他 warp 提供的工作则覆盖跨 warp 的等待。两者都能减少空闲发射机会，却有不同的资源代价。

例如展开循环，把下一轮 load 提前，常会同时保留更多输入和中间结果，增加寄存器的存活区间。需要检查编译后的顺序、registers/thread 和是否出现 spill，再判断更大的 load-use 距离是否划算。Occupancy 对这种资源变化的解释见驻留与性能判断。

3. 编译结果如何表达这条等待

程序在 CUDA C++ 和 PTX 层表达数据依赖，目标代码还需要安排等待。对可静态调度的固定延迟指令，编译器能够安排发射间隔；对于需要动态跟踪的操作，SASS 控制信息把 producer 的完成事件与 consumer 的等待关联起来。

Jia 等人的Volta 微基准研究，第 2.1 节分析了 Maxwell、Pascal 和 Volta 的 read/write barrier index、wait mask 与 stall 字段。以下沿用这些字段的阅读语义，并用 SB0 表示示例中的依赖标识。它们属于目标相关的机器码控制信息；PTX 程序的可移植契约不包含这些位的位置。

// Control annotations, not literal disassembler syntax
I0: LDG.E R8, [R2]             // write dependency = SB0
I1: IADD3 R10, R11, R12, RZ    // no wait on SB0
I2: FFMA R16, R8, R20, R16     // wait mask includes SB0

Write dependency 将 I0 的结果就绪事件关联到 SB0，wait mask 则要求 I2 在该条件满足后才能发射。一条指令可能需要等多个标识。若用集合 $P$ 表示尚未满足的依赖、$W$ 表示当前指令要求全部满足的依赖，那么 $W\cap P\ne\varnothing$ 就足以阻止它因这些依赖而就绪。这个集合模型用于解释等待条件，不规定硬件用位、计数器还是其他结构保存状态。

Read dependency 保护尚未读完的源寄存器

前面的 RAW 等待保护 producer 的目的寄存器。另一个方向是 write-after-read（WAR）：某条异步或解耦操作还没有读完源寄存器，后续指令准备覆盖它。上述微基准研究将这类约束解释为 read dependency。一个 store 的教学示意是：

// A read-dependency example, not a compiled trace
STG.E [R2], R8       // protect consumption of source R8 with SB1
MOV R8, RZ          // wait on SB1 before overwriting R8

这里等待的是旧 R8 被该操作消费，而不是等某条 load 产生新 R8。因此，仅沿着“谁写了当前输入寄存器”追踪，可能漏掉另一类 scoreboard 依赖。NCU 的官方依赖表同时涵盖 RAW、WAR，以及部分状态更新和内存顺序相关条件。

显式 DEPBAR 与工具中的依赖标识

CUDA Binary Utilities 13.0.3将 DEPBAR 列为 Dependency Barrier。NVIDIA 专利 US9612836B2描述过按标识和阈值等待 outstanding-operation counter 的一种实现。它说明显式等待可以针对一组操作的进度；专利中的计数器宽度和电路组织不能直接移作所有 GPU 的规格。

NCU 2026.2 的 Instructions & Dependencies 文档用六个 scoreboard 标识显示依赖边。阅读时可以沿同一标识找到 producer 和 consumer，但不应据此计算某个 SM 最多有多少笔访存在途。标识的复用、同一标识关联的操作以及目标指令的完成规则，超出了“六列”本身能回答的范围。

4. Long 与 Short 指向哪一种 producer

回到最初的 LDG → FFMA。如果 consumer 因这次 global load 尚未完成而等待，NCU 把相应样本归入 Long Scoreboard。将 producer 换成产生同一输入的 shared-memory LDS，相应等待通常归入 Short Scoreboard。分类跟随被等待的操作，样本所在的 FFMA 仍然可以是同一种指令。

NCU 分类官方定义对应的操作沿 producer 继续检查
Long ScoreboardL1TEX 的 local、global、surface、texture 操作访问合并、cache 命中、请求数量、local spill、依赖式地址计算
Short Scoreboard非 L1TEX 的 MIO 操作，常见为 shared memory，也包括特殊数学和动态分支Shared-memory wavefront 与 bank conflict、load-use 距离、MUFU 或分支目标依赖

这些是 NCU 2026.2 Warp Stall Reasons的分类。Long/Short 没有以某个周期阈值划界：shared load 也可能让 consumer 等很久，global load 也可能很快完成。诊断时仍要回到具体 opcode 和访问行为。

Shared-memory bank conflict 会增加一次访问需要处理的工作，因而可能推迟结果可用的时刻。但 Short Scoreboard 本身不能证明存在 bank conflict，紧密的 load-use 依赖也会产生等待。若 producer 还没发射，正在等 MIO queue 接收，则对应的是MIO Throttle 的发射前反压，还没有进入这里讨论的结果等待阶段。

5. 在 NCU 中区分等待位置与归因位置

最初的例子给报告留下两个值得查看的地址：I2 是停下来的 consumer，I0 是产生这条依赖的 load。NCU 的普通 Warp Stall Sampling 列按采样到的程序位置显示等待；Source 页的 Attributed Stalls 则把 Long/Short Scoreboard 的 Not-issued 样本归到对应 producer。两列的热点可以位于不同的行。

从 FFMA 样本回到 LDG

若报告在 I2 的 PC 上显示 Long Scoreboard，先在 SASS 视图选择它，再查看 Input Scoreboard Dependencies。这个视图列出它需要等待的前驱操作；沿依赖链接到 I0 后，Output Scoreboard Dependencies可反查哪些 consumer 在等这条 load。一个 consumer 可能同时等待多个 producer，不能把整行的所有等待都交给找到的第一条边。

在这组关系中，I2 的 Not-issued 样本和 I0 的 Attributed Stalls 回答不同问题：前者给出 scheduler 没有发射指令时所采到的等待位置，后者帮助查找造成这类等待的 producer。官方Source Page还说明，All 与 Not-issued 样本可能来自不同 profiling pass，数值不必严格逐项对应。这些采样读数也不是某一次 load 的精确延迟。

让 producer 的类型决定下一份证据

找到 I0 后，如果它是一条 global load，就结合该位置的访问模式、sector 数与 cache 行为判断等待来源；若它来自 local-memory spill，还要回看寄存器压力。若 producer 是 LDS，则查看实际与理想 shared wavefront 以及 bank-conflict 指标。没有冲突时，继续检查 consumer 是否过早抵达，而不是继续尝试消除并不存在的冲突。

最后回到 Scheduler Statistics：等待出现时，其他 warp 能否持续提供 eligible 指令，issue slots 是否有明显空闲？如果发射已经被其他工作覆盖，减少某一行的等待样本未必能缩短 kernel。若依赖链限制了前进，则在相同输入和工作量下比较一个单项改动，并记录 SASS 顺序、资源占用和独立计时结果。

6. 从依赖链决定改动位置

对于 LDG → FFMA 这条链，改善 load 的访问行为是在改变 producer；提前 load 或在 consumer 前安排独立工作，可以扩大 producer 发射到 consumer 使用之间的间隔；增加可用 warp 则是在增加等待期间的其他工作。沿同一条链区分这些作用，才容易解释改动后的报告。比如 consumer 的样本减少，同时寄存器增加并引入 spill，就需要把新增的 local-memory producer 也放进分析。

本文的示例建立了依赖关系，没有给出哪一种方案必然更快的测量结论。实际优化的结束条件是正确性保持、目标工作量的运行时间稳定改善，并且报告能解释收益或新增成本。进一步的发射条件见指令发射与延迟隐藏，整体读报告的方法见Warp Stall 分析。

GPU Scoreboard Mechanism: Warp Dependency Tracking, SASS Control, and Long/Short Stalls

After a CUDA kernel loads data, it usually uses those values in arithmetic, address calculations, or a branch decision. A load can have issued while its result is still unavailable in a register. The same warp may have other instructions it can execute during that interval. Hardware must distinguish work that can proceed from work that needs the result. Scoreboarding manages the dependency between that load and the instructions that follow it.

In a profiling report, this wait may appear on an FFMA. The line has many Long Scoreboard samples, but the producer worth investigating is an earlier LDG. Finding the right place to change requires the instruction order, the dependency controls left by the compiler, and the profiler's distinction between sampling and attribution.

1. A load and the instruction that consumes its result

Consider a warp doing a multiply-add: it loads an input from global memory, performs an independent integer addition, and then uses the input in an accumulator update. This SASS illustration omits address calculations and target-specific modifiers. It is a dependency example, not recorded compiler output or a measurement.

I0: LDG.E R8, [R2]
I1: IADD3 R10, R11, R12, RZ
I2: FFMA R16, R8, R20, R16
I3: IADD3 R21, R22, R23, RZ

I0 produces R8 and is the producer on this dependency. I2 reads R8 and is its consumer. Assuming the other operands are ready, I1 does not need this load to complete, while I2 must wait for R8. This is a read-after-write (RAW) data dependency.

A scoreboard is dynamic dependency state associated with outstanding operations. The scheduler uses it to determine whether the completion conditions required by a warp's current instruction have been met. For this example, the load's condition can be represented as pending or satisfied. The register holds the value; the scoreboard holds control state needed to decide whether execution can proceed. NCU's dependency view connects a waiting instruction to its predecessor operations.

A cache hit still leaves this dependency to resolve. The hit may shorten load completion, but the consumer needs the result to be ready. Its wait depends on when the producer completes and when the consumer reaches the dependency. The arithmetic latency of FFMA alone does not give that interval.

2. Where the warp stops and how it resumes

After I0 issues, the load progresses along its execution path and the associated dependency is pending. I1 can then issue. If the load is incomplete when the warp reaches I2, that instruction's input condition is unsatisfied and the warp cannot currently offer it for issue.

I3 also does not read R8, but it follows I2 in the given SASS sequence. This example models one warp instruction path issuing in its established order. During the wait, the scheduler can select an instruction from another eligible warp that it manages. CUDA's Hardware Multithreading describes issue as selecting a warp ready to execute its next instruction.

The compiler can change when the consumer arrives

When program semantics permit, the compiler can place I3 before I2. This adds independent work while the load is outstanding, so the consumer may arrive after the result is already ready. It uses instruction-level parallelism (ILP) within one warp. Work from other warps covers waits across warps. Both can reduce idle issue opportunities, but their resource costs differ.

For example, unrolling a loop and advancing the next iteration's load often keeps more inputs and intermediates live. Inspect the compiled order, registers per thread, and any spills before judging the larger load-use distance. The occupancy performance discussion explains how those resource changes affect residency.

3. How compiled code expresses the wait

CUDA C++ and PTX express program dependencies; target code also needs a way to schedule waiting. For fixed-latency instructions that can be scheduled statically, the compiler can arrange issue distance. For operations requiring dynamic tracking, SASS control information links a producer's completion event to its consumers' waits.

Section 2.1 of Jia et al.'s Volta microbenchmark study analyzes read/write barrier indices, wait masks, and stall fields on Maxwell, Pascal, and Volta. The annotations below use that reading model, with SB0 as the example dependency identifier. These are target-specific machine-code controls. Their bit positions are not part of PTX's portable program contract.

// Control annotations, not literal disassembler syntax
I0: LDG.E R8, [R2]             // write dependency = SB0
I1: IADD3 R10, R11, R12, RZ    // no wait on SB0
I2: FFMA R16, R8, R20, R16     // wait mask includes SB0

The write dependency associates I0's result-ready event with SB0. The wait mask requires I2 to await that condition before issue. One instruction can wait on several identifiers. If $P$ is the set of unsatisfied dependencies and $W$ is the set the current instruction requires to be fully satisfied, then $W\cap P\ne\varnothing$ is enough to block readiness on those dependencies. This set model explains the wait condition without prescribing bits, counters, or another physical representation.

Read dependencies protect source registers still in use

The RAW dependency protects a producer's destination. The opposite direction is write-after-read (WAR): an asynchronous or decoupled operation has not finished consuming a source register when a later instruction wants to overwrite it. The microbenchmark study describes read dependencies for this constraint. A store provides a useful illustration:

// A read-dependency example, not a compiled trace
STG.E [R2], R8       // protect consumption of source R8 with SB1
MOV R8, RZ          // wait on SB1 before overwriting R8

This wait protects consumption of the old R8, rather than a load producing a new value in it. Tracing only the writer of each current input register can therefore miss another kind of scoreboard dependency. NCU's official dependency table includes RAW, WAR, and conditions involving state updates or memory ordering.

Explicit DEPBAR and identifiers in the tool

CUDA Binary Utilities 13.0.3 lists DEPBAR as a Dependency Barrier. NVIDIA's patent US9612836B2 describes an implementation that waits on an outstanding-operation counter selected by identifier and compared against a threshold. This illustrates how an explicit wait can track progress across a group of operations. The patent's counter width and circuitry are not specifications for every GPU.

NCU 2026.2's Instructions & Dependencies documentation displays dependency edges using six scoreboard identifiers. Following an identifier can connect producers and consumers; counting the columns does not establish an SM's maximum number of outstanding memory operations. Identifier reuse, associated operations, and target-instruction completion rules require additional information.

4. Which producer Long and Short identify

Return to LDG → FFMA. If the consumer waits because this global load is incomplete, NCU classifies the sample as Long Scoreboard. Replacing the producer with a shared-memory LDS producing the same input normally makes the corresponding wait Short Scoreboard. The class follows the operation being awaited; the sampled FFMA can remain the same instruction type.

NCU classOperations in the documented definitionEvidence to inspect at the producer
Long ScoreboardL1TEX local, global, surface, or texture operationsCoalescing, cache hits, request counts, local spills, and dependent address calculations
Short ScoreboardNon-L1TEX MIO operations, commonly shared memory, also special math and dynamic branchesShared wavefronts and bank conflicts, load-use distance, MUFU or branch-target dependencies

These classes follow NCU 2026.2 Warp Stall Reasons. They do not use a cycle-count threshold: a shared load can keep a consumer waiting, while a global load may complete quickly. The opcode and access behavior still determine the next diagnostic step.

A shared-memory bank conflict increases the work needed to process an access and can delay its result. Short Scoreboard alone does not establish a bank conflict; a tight load-use dependency also produces waiting. If the producer has yet to issue because it is waiting for room in the MIO queue, the condition is MIO Throttle's pre-issue backpressure. The result wait discussed here has not started.

5. Separate the waiting location from the attributed location

The initial example gives the report two relevant addresses: I2 is the waiting consumer, and I0 is the load that produces the dependency. Ordinary Warp Stall Sampling columns show waits at the sampled program location. The Source page's Attributed Stalls instead attributes Long/Short Scoreboard Not-issued samples to the corresponding producer. The two columns can highlight different lines.

Follow FFMA samples back to LDG

If the report shows Long Scoreboard at I2's PC, select it in the SASS view and inspect Input Scoreboard Dependencies. This view lists the predecessor operations it needs to await. Follow the dependency link to I0, then use Output Scoreboard Dependencies to find the consumers waiting on that load. A consumer may await several producers; finding the first edge is not enough to assign every wait on its line to that producer.

In this relationship, I2's Not-issued samples and I0's Attributed Stalls answer different questions. The former shows a sampled waiting location on cycles when the scheduler issued no instruction. The latter helps identify the producer responsible for such waits. The official Source Page documentation also notes that All and Not-issued samples can come from different profiling passes and need not correspond exactly. These samples do not measure the precise latency of an individual load.

Use the producer type to choose supporting evidence

Once I0 is identified as a global load, inspect its access pattern, sectors, and cache behavior. If it is a local-memory spill instead, revisit register pressure. For an LDS producer, compare actual and ideal shared wavefronts together with bank-conflict metrics. If no conflict appears, examine whether the consumer reaches the dependency too soon instead of trying to remove a nonexistent conflict.

Then return to Scheduler Statistics. Can other warps keep providing eligible instructions during the wait, or are issue slots substantially idle? A wait already covered by other work may be reduced without shortening the kernel. If the dependency chain limits progress, compare one change at a time on the same input and amount of work, recording SASS order, resource use, and independent timing.

6. Choose the change from the dependency chain

On the LDG → FFMA chain, improving access behavior changes the producer. Advancing the load or placing independent work before the consumer can increase the interval between producer issue and consumer use. Adding available warps provides more work during the wait. Separating these effects makes the revised report easier to interpret. If consumer samples fall while register use rises and spills appear, the new local-memory producers also belong in the analysis.

The example establishes the dependency relationship, without a measured claim that one approach must be faster. A successful optimization preserves correctness, produces a repeatable timing improvement for the target workload, and has profiler evidence that explains the benefit or added cost. Instruction issue and latency hiding covers the remaining issue conditions; Warp Stall analysis develops the broader report-reading process.
