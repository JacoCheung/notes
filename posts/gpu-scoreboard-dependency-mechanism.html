GPU Scoreboard 机制：Warp 依赖跟踪、SASS 控制与 Long/Short Stall

一个 warp 的指令按照编译后的 SASS 顺序进入发射阶段。整数加法等固定延迟操作可以由编译器安排 producer-consumer 间隔；global load、shared-memory load 和特殊数学操作的完成时间受运行时状态影响，需要硬件继续跟踪。Scoreboard 承担这部分动态依赖管理：它记录尚未完成的操作，并把依赖是否满足的信息交给 warp scheduler。

这套机制横跨编译与执行。编译阶段，SASS 控制信息把 producer、dependency identifier 和 consumer 连接起来；运行阶段，scheduler 在发射前查询对应状态。Nsight Compute 沿同一组依赖关系呈现 Long/Short Stall，因此 Long 与 Short 要放在完整的 Scoreboard 模型中理解。

1. Scoreboard 的定义与职责

Scoreboard 是 GPU 为 warp 维护的动态依赖状态集合。当一条完成时间无法静态确定的 producer 指令发射时，与它关联的状态进入 pending；执行单元报告完成后，该状态得到满足。若 warp 当前指令要求等待的状态仍为 pending，scheduler 就不会把这条指令列入本周期的可发射候选。

Nsight Compute 的 Instructions & Dependencies 文档将这类状态用于同步数据依赖、状态更新和内存顺序。数据本身仍保存在寄存器、cache 或内存系统中；Scoreboard 保存的是“相关操作是否完成”这一控制状态。

一个典型依赖经历以下生命周期：

  1. 分配：ptxas 在目标相关的 SASS 控制信息中，为 producer 与 consumer 建立共同的 dependency identifier。
  2. 置为 pending：producer 发射后，对应的 read dependency 或 write dependency 开始等待完成事件。
  3. 查询：consumer 成为 warp 的当前指令时，scheduler 检查它的 wait mask 与 pending 状态是否相交。
  4. 满足：L1TEX、MIO 等执行路径返回完成事件，依赖状态得到满足，consumer 随后可以重新进入 eligible 集合。

后文的分类、SASS 控制字段和 profiler 视图，都可以放回这四次状态变化中理解。

2. GPU Scoreboard 的分类

Scoreboard 可以按依赖语义、producer 路径和逻辑标识三个维度观察。三个维度描述的是同一组运行时依赖状态的不同属性。

分类维度类别含义
依赖语义Write dependency / RAWProducer 的 destination 尚未写回；读取该 destination 的 consumer 需要等待。
依赖语义Read dependency / WARDecoupled producer 尚未完成 source operand 的读取；准备覆盖这些寄存器的后续指令需要等待。
依赖语义状态更新与内存顺序指令等待某项架构状态更新或顺序条件成立。
Producer 路径Long Scoreboard依赖由 L1TEX 处理的 local、global、surface 或 texture 操作建立。
Producer 路径Short Scoreboard依赖由非 L1TEX 的 MIO 操作建立，常见来源包括 shared memory、MUFU 和动态分支。
逻辑标识NCU 展示的六个 scoreboard标识 producer 与等待它的 consumer，便于在 Instructions & Dependencies 表中追踪依赖边。

Long 与 Short 表示 producer 所在的执行路径，而不是按等待周期长短划分。NCU 将两类依赖显示在同一组六个 scoreboard 列中，这六列提供了从 producer 追踪到 consumer 的逻辑标识。无论依赖属于哪一种语义或 producer 路径，scheduler 最终都要用这些逻辑状态判断当前指令能否发射。

3. Warp scheduler 的依赖判定

对于每个 resident warp，scheduler 判断的是它在编译后 SASS 序列中当前位置上的指令。CUDA C++ Programming Guide 13.2 将发射过程描述为：scheduler 选择一个准备执行“下一条指令”的 warp。Scheduler 可以在 warp 之间切换；同一 warp 内仍按 SASS 顺序推进，因此当前位置上的 blocked 指令会挡住后续指令。

I0: LDG  R8,  [R2]       // variable-latency producer
I1: IADD R10, R11, R12   // independent of R8
I2: FFMA R16, R8, R20    // consumes R8
I3: IADD R21, R22, R23   // independent, but ordered after I2 in SASS

I0 发射后，与结果 R8 关联的 write dependency 进入 pending。I1 不等待该状态，因此能够继续发射。轮到 I2 时，它的 wait mask 命中尚未满足的 dependency identifier，warp 暂时退出 eligible 集合；I3 虽然与 R8 无关，也不会在运行时越过 I2。Scheduler 转而选择其他 eligible warp。

ptxas 可以在编译期把 I3 重排到 I2 之前，以增加同一 warp 内的 ILP。运行时的 Scoreboard 负责验证既定 SASS 顺序中当前指令的动态依赖，warp 之间的延迟隐藏则由 scheduler 完成。

Scoreboard 把异步 producer 的完成事件接回 warp scheduler

图中的运行时判定需要 SASS 提供两类信息：producer 将完成事件登记到哪个 dependency identifier，以及 consumer 发射前要等待哪些 identifier。控制字段正是编译结果与动态 Scoreboard 状态之间的接口。

4. SASS 的 Scoreboard 控制

CUDA C++ 与 PTX 描述程序语义，ptxas 在生成目标 GPU 的 SASS 时安排静态延迟，并为需要动态跟踪的依赖分配控制字段。NVIDIA Developer Forums 的 SASS 讨论以及公开的调度控制字段分析给出了下面这套实用的阅读模型：

SASS 控制信息作用典型依赖
Write dependency barrier ID把 producer 的 destination 写回事件关联到一个 identifierConsumer 读取该 destination，形成 RAW 依赖
Read dependency barrier ID把 decoupled producer 的 source operand 读取事件关联到一个 identifier后续指令覆盖这些 source registers，形成 WAR 依赖
Wait barrier mask列出当前指令发射前必须满足的 dependency identifiersMask 与 pending 状态相交时，当前指令不可发射
Static stall count编码编译器安排的最小发射间隔固定延迟、可静态调度的 producer-consumer 关系

下面的代码只表达控制语义，具体反汇编格式随工具和目标架构变化：

LDG.E R8, [R2]       // write dependency = SBx
IADD3 R12, R12, 1    // no wait on SBx
FFMA R16, R8, R20, R16
                      // wait mask contains SBx

LDG 发射后，SBx 进入 pending。中间的 IADD3 可以发射；FFMA 则等待 SBx 对应的写回事件。常规反汇编输出往往把 dependency ID 和 wait mask 放在机器码控制信息中，因此依赖关系需要结合 SASS control fields 或 NCU 的 Input/Output Scoreboard Dependencies 阅读。

DEPBAR 是 SASS 中显式等待 dependency-barrier 状态的指令。CUDA Binary Utilities 13.0.3 将其归类为 Dependency Barrier；NVIDIA 专利 US9612836B2 给出了一种按 scoreboard identifier 与阈值等待的实现。普通 producer-consumer 关系通常直接编码在控制字段中，DEPBAR 负责表达需要独立指令的显式等待或排序。

公开资料能够确认 dependency identifier、producer barrier、consumer wait mask 与完成事件之间的控制关系。在这层稳定语义上，Nsight Compute 再按建立依赖的 producer 路径区分 Long 与 Short；精确 bit 编码、identifier 的物理容量和 scheduler 内部实现不属于跨架构稳定的公开 ABI。

5. Long 与 Short Scoreboard

Nsight Compute 根据建立依赖的 producer 路径，将等待样本归为 Long Scoreboard 或 Short Scoreboard。两类状态沿用相同的 dependency identifier 和 wait-mask 机制。

类别Producer 路径常见 SASS典型延迟来源
Long ScoreboardL1TEXLDG、LDL、texture/surface loadCache miss、散乱访问、指针追逐、local-memory spill
Short Scoreboard非 L1TEX 的 MIOLDS、MUFU、BRX/JMXShared-memory load-use 距离、bank conflict、特殊数学与动态目标解析

Long Scoreboard 的典型依赖如下。Load 经过 L1TEX 发射以后，consumer 一直等待对应的 write dependency；L1/L2 miss、无法合并的访问或数据依赖链会延长 pending 区间。

LDG.E R8, [R2]       // L1TEX producer, write dependency = SB0
IADD3 R12, R12, 1    // independent work
FFMA R16, R8, R20, R16
                      // consumer waits on SB0: Long Scoreboard

Short Scoreboard 使用同一套 producer、identifier、wait mask 和完成事件模型，只是 producer 经过 MIO 的非 L1TEX 路径。例如，shared-memory bank conflict 会把一次请求拆成更多 wavefront，使 LDS 的完成事件更晚到达；紧邻的 consumer 因而等待更久。

LDS R8, [R2]         // MIO producer, write dependency = SB1
FFMA R16, R8, R20, R16
                      // consumer waits on SB1: Short Scoreboard

Long/Short 将等待先定位到 producer 路径，producer opcode、memory workload 和访问模式再把范围收敛到 cache hierarchy、访问合并、bank conflict 或指令间距等具体因素。沿着这条依赖关系，profiler 才能把抽象的 pending 状态映射回 SASS。

6. Nsight Compute 中的观测

Nsight Compute 的 Source 页面把采样到的 stall 与编译后的 SASS 对齐。Instructions & Dependencies 表进一步暴露当前指令的 Input Scoreboard Dependencies 和 Output Scoreboard Dependencies：前者列出当前 consumer 等待的 producers，后者列出等待当前 producer 的 consumers。这两组边让运行时 stall 回到具体的依赖关系。

  1. 定位 consumer：在 Source Counters 中找到 long_scoreboard 或 short_scoreboard 的热点 SASS PC。
  2. 沿输入依赖回溯：查看该指令的 Input Scoreboard Dependencies，确认它等待哪个 identifier。
  3. 定位 producer：沿依赖边找到 producer，并检查其 opcode、write/read dependency 类型及 Output Scoreboard Dependencies。
  4. 按路径补充证据：Long 继续检查 cache、sector、DRAM 和 local spill；Short 继续检查 shared wavefront、bank conflict、MUFU 或动态分支。
  5. 评估性能影响：回到 Scheduler Statistics，检查 eligible warps 和 issue-slot 利用率，判断其他 warp 是否覆盖了这段等待。

这五步定位的是 Scoreboard 依赖。为了把它与相邻机制区分开，还要按指令发射边界做一次核对：Long/Short Scoreboard 等待已经发射的 producer，throttle 等待新指令的接收资源，静态 wait 与 CTA barrier 则分别对应固定延迟和参与者 arrival。下表集中列出这些边界。

NCU stall 或同步机制发生阶段等待条件
long_scoreboardL1TEX producer 已发射Local/global/surface/texture 操作完成
short_scoreboardMIO producer 已发射Shared memory、MUFU 或动态分支等操作完成
lg_throttle新的 local/global 指令发射前Local/global instruction queue 出现空位
mio_throttle新的 MIO 指令发射前MIO instruction queue 出现空位
wait固定延迟 producer 已发射静态调度的执行依赖满足
CTA/named barrier线程或 warp 到达同步点规定的参与者完成 arrival

诊断从 consumer PC 沿 dependency identifier 回到 producer，再根据 producer 路径选择后续证据。完整的发射模型见《NVIDIA GPU 指令发射与延迟隐藏机制》；队列反压见《GPU MIO Throttle：队列反压、成因与诊断》；整体 stall 分类见《GPU Warp Stall 分析：调度状态、Nsight Compute 指标与源码归因》。

GPU Scoreboard Mechanism: Warp Dependency Tracking, SASS Control, and Long/Short Stalls

A warp reaches the issue stage in compiled SASS order. The compiler can schedule producer-consumer distance for fixed-latency operations such as integer addition. Global loads, shared-memory loads, and special-function operations complete according to runtime conditions and therefore require continued hardware tracking. The scoreboard provides that tracking: it records outstanding operations and tells the warp scheduler whether their dependencies have been satisfied.

The mechanism spans compilation and execution. During compilation, SASS control information connects a producer, a dependency identifier, and its consumers. At runtime, the scheduler queries the corresponding state before issue. Nsight Compute presents Long and Short stalls along the same relationships, so those labels belong within the broader scoreboard model.

1. Definition and role of a scoreboard

A scoreboard is a set of dynamic dependency states maintained for a warp. When a producer with statically indeterminate completion time issues, its associated state becomes pending. A completion event later satisfies that state. If the warp's current instruction waits on any state that remains pending, the scheduler excludes the instruction from the issue candidates for that cycle.

The Nsight Compute Instructions & Dependencies documentation describes scoreboards as synchronizing data dependencies, state updates, and memory ordering. The value itself resides in registers, caches, or the memory system; the scoreboard holds control state that says whether the associated operation has completed.

A typical dependency follows this lifecycle:

  1. Assignment: during target-specific SASS generation, ptxas establishes a common dependency identifier between the producer and its consumers.
  2. Pending state: after the producer issues, the corresponding read or write dependency begins waiting for a completion event.
  3. Query: when the consumer becomes the warp's current instruction, the scheduler tests its wait mask against pending state.
  4. Satisfaction: a completion event from L1TEX, MIO, or another execution path satisfies the dependency, after which the consumer may re-enter the eligible set.

The classifications, SASS controls, and profiler views in the following sections all map back to these four state transitions.

2. GPU scoreboard classifications

A scoreboard can be viewed along three dimensions: dependency semantics, producer path, and logical identifier. These dimensions describe different attributes of the same runtime dependency state.

DimensionCategoryMeaning
Dependency semanticsWrite dependency / RAWThe producer's destination has not been written; a consumer that reads the destination must wait.
Dependency semanticsRead dependency / WARA decoupled producer has not finished reading its source operands; a later instruction that overwrites those registers must wait.
Dependency semanticsState update and memory orderingThe instruction waits for an architectural state update or ordering condition.
Producer pathLong ScoreboardThe dependency was established by a local, global, surface, or texture operation handled by L1TEX.
Producer pathShort ScoreboardThe dependency was established by a non-L1TEX MIO operation, commonly shared memory, MUFU, or dynamic branching.
Logical identifierThe six scoreboards displayed by NCUThe identifier connects a producer to consumers in the Instructions & Dependencies table.

Long and Short identify the producer's execution path rather than a cycle-count threshold. NCU displays both classes in the same six scoreboard columns, which provide logical identifiers for tracing a producer to its consumers. Regardless of dependency semantics or producer path, the scheduler ultimately uses this logical state to decide whether the current instruction may issue.

3. Dependency checks in the warp scheduler

For each resident warp, the scheduler evaluates the instruction at the current position in its compiled SASS sequence. The CUDA C++ Programming Guide 13.2 describes issue as selecting a warp that is ready to execute its “next instruction.” The scheduler can switch among warps, while each warp still advances in SASS order; a blocked current instruction therefore holds back later instructions in that warp.

I0: LDG  R8,  [R2]       // variable-latency producer
I1: IADD R10, R11, R12   // independent of R8
I2: FFMA R16, R8, R20    // consumes R8
I3: IADD R21, R22, R23   // independent, but ordered after I2 in SASS

After I0 issues, the write dependency associated with R8 becomes pending. I1 does not wait on that state and can issue. When I2 becomes current, its wait mask matches an unsatisfied dependency identifier, temporarily removing the warp from the eligible set. Although I3 is independent of R8, it does not pass I2 at runtime. The scheduler instead selects another eligible warp.

ptxas can move I3 ahead of I2 at compile time when program semantics allow, thereby increasing ILP within the warp. At runtime, the scoreboard validates dynamic dependencies for the current instruction in the fixed SASS order, while the scheduler hides latency across warps.

The scoreboard feeds asynchronous completion state back to the warp scheduler

The runtime decision shown in the figure requires SASS to provide two pieces of information: the dependency identifier on which a producer registers its completion event, and the identifiers that a consumer must await before issue. Control fields form the interface between compiled code and dynamic scoreboard state.

4. Scoreboard controls in SASS

CUDA C++ and PTX define program semantics. While generating SASS for a target GPU, ptxas schedules static latency and assigns control fields to dependencies that need runtime tracking. A public NVIDIA Developer Forums discussion and an open analysis of scheduling control fields support the following practical reading model:

SASS control informationRoleTypical dependency
Write dependency barrier IDAssociates the producer's destination-write event with an identifierA consumer reads the destination, forming a RAW dependency
Read dependency barrier IDAssociates source-operand consumption by a decoupled producer with an identifierA later instruction overwrites those source registers, forming a WAR dependency
Wait barrier maskLists dependency identifiers that must be satisfied before the current instruction issuesThe instruction cannot issue while the mask intersects pending state
Static stall countEncodes a compiler-scheduled minimum issue distanceFixed-latency producer-consumer relationships that can be scheduled statically

The following snippet expresses control semantics only; concrete disassembly syntax depends on the tool and target architecture:

LDG.E R8, [R2]       // write dependency = SBx
IADD3 R12, R12, 1    // no wait on SBx
FFMA R16, R8, R20, R16
                      // wait mask contains SBx

After LDG issues, SBx becomes pending. The intervening IADD3 can issue, while the FFMA waits for the destination-write event associated with SBx. Default disassembly often places the dependency ID and wait mask in machine-code control information, so the relationship is best read through SASS control fields or NCU's Input/Output Scoreboard Dependencies.

DEPBAR explicitly waits on dependency-barrier state in SASS. CUDA Binary Utilities 13.0.3 classifies it as a Dependency Barrier, and NVIDIA patent US9612836B2 describes one implementation that waits by scoreboard identifier and threshold. Ordinary producer-consumer relationships are commonly encoded in control fields; DEPBAR expresses cases that require a separate wait or ordering instruction.

Public sources establish the control relationship among dependency identifiers, producer barriers, consumer wait masks, and completion events. On top of that stable semantic model, Nsight Compute classifies a dependency as Long or Short according to the producer path that established it. Exact bit encodings, physical identifier capacity, and scheduler internals are not a stable cross-architecture public ABI.

5. Long and Short Scoreboard

Nsight Compute attributes a waiting sample to Long or Short Scoreboard according to the producer path that established the dependency. Both classes use the same dependency-identifier and wait-mask mechanism.

ClassProducer pathCommon SASSTypical sources of delay
Long ScoreboardL1TEXLDG, LDL, texture/surface loadsCache misses, scattered access, pointer chasing, and local-memory spills
Short ScoreboardNon-L1TEX MIOLDS, MUFU, BRX/JMXShared-memory load-use distance, bank conflicts, special math, and dynamic target resolution

The following sequence illustrates a Long Scoreboard dependency. After the load issues through L1TEX, the consumer waits for the corresponding write dependency. An L1/L2 miss, uncoalesced access, or a data-dependent load chain can extend the pending interval.

LDG.E R8, [R2]       // L1TEX producer, write dependency = SB0
IADD3 R12, R12, 1    // independent work
FFMA R16, R8, R20, R16
                      // consumer waits on SB0: Long Scoreboard

Short Scoreboard uses the same producer, identifier, wait-mask, and completion-event model, but the producer follows a non-L1TEX MIO path. A shared-memory bank conflict, for example, splits a request into additional wavefronts and delays the completion event from LDS, thereby extending the consumer's wait.

LDS R8, [R2]         // MIO producer, write dependency = SB1
FFMA R16, R8, R20, R16
                      // consumer waits on SB1: Short Scoreboard

Long or Short first locates the wait on a producer path. The producer opcode, memory-workload evidence, and access pattern then narrow the cause to cache-hierarchy effects, coalescing, bank conflicts, or instruction distance. Following the same dependency relationship allows the profiler to map abstract pending state back to SASS.

6. Observing scoreboards in Nsight Compute

The Nsight Compute Source page aligns sampled stalls with compiled SASS. Its Instructions & Dependencies table also exposes Input Scoreboard Dependencies and Output Scoreboard Dependencies for the selected instruction. Inputs identify the producers that the current consumer waits on; outputs identify consumers waiting on the current producer. These edges connect a runtime stall to a concrete dependency relationship.

  1. Locate the consumer: use Source Counters to find the SASS PC with concentrated long_scoreboard or short_scoreboard samples.
  2. Trace input dependencies: inspect Input Scoreboard Dependencies and identify the dependency identifier being awaited.
  3. Locate the producer: follow the edge to the producer and inspect its opcode, read/write dependency type, and Output Scoreboard Dependencies.
  4. Add path-specific evidence: for Long, inspect caches, sectors, DRAM, and local spills; for Short, inspect shared-memory wavefronts, bank conflicts, MUFU, and dynamic branches.
  5. Evaluate performance impact: return to Scheduler Statistics and inspect eligible warps and issue-slot utilization to determine whether other warps cover the wait.

These five steps identify a scoreboard dependency. An issue-boundary check then separates it from neighboring mechanisms: Long and Short Scoreboard wait for an issued producer, throttle waits for acceptance resources before a new instruction issues, and static wait and CTA barriers represent fixed latency and participant arrival, respectively. The table collects those boundaries.

NCU stall or synchronization mechanismStageWait condition
long_scoreboardAfter an L1TEX producer issuesCompletion of local/global/surface/texture work
short_scoreboardAfter an MIO producer issuesCompletion of shared memory, MUFU, dynamic branches, or related work
lg_throttleBefore a new local/global instruction issuesA free entry in the local/global instruction queue
mio_throttleBefore a new MIO instruction issuesA free entry in the MIO instruction queue
waitAfter a fixed-latency producer issuesSatisfaction of a statically scheduled execution dependency
CTA/named barrierWhen threads or warps reach a synchronization pointArrival of the required participants

The diagnostic path starts at the consumer PC, follows the dependency identifier back to the producer, and then selects supporting evidence according to the producer path.
