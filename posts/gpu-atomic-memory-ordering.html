NVIDIA GPU 原子内存顺序：CUDA C++ 语义与 PTX 映射

一个 thread 把结果写进 data，再把 ready 设为 1；另一个 thread 看到 1 后取走结果。这是 GPU 工作队列、任务完成标记和对象发布中常见的一步。难点在于：ready 的原子更新只直接约束这个标记，普通 data 的读写还需要一条跨 thread 的顺序关系。

下面从这次数据交接出发，用一个完整的 CUDA C++ 程序推导 release/acquire 为什么成立，再看协议扩展到多个 CTA 时增加了哪些条件，以及这些条件如何落到 PTX。正文以 CUDA 13.2 的公开内存模型与 atomic ABI 为准；接口和 memory order 的完整对照放在附录。

1. 原子 flag 为什么还不能交付普通数据

设 data 和 ready 都已经初始化为 0。data 是普通整数，ready 是 scope 覆盖双方的 atomic 对象，只有一个 producer 写入一次结果。先考虑下面这个缺少同步的错误协议：

// Producer
data = 42;
ready.store(1, relaxed);

// Consumer
if (ready.load(relaxed) == 1)
    value = data;

Producer 的两行有本 thread 内的先后顺序，consumer 的两行也有。Atomic flag 还保证对自身的访问具有原子性。但这几条局部约束没有把 data = 42 与另一个 thread 的 value = data 连起来。Consumer 即使读到了 1，也尚未获得访问普通 payload 所需的同步。

在 CUDA C++ 中，两个潜在并发、相互冲突的普通访问，如果至少一个是写入，又没有 happens-before 关系，就会形成 data race，行为未定义。因此上述程序的问题已经超出“偶尔读到旧值”的范围，不能给它列出一张只含 0 和 42 的合法结果表。判定依据是 CUDA 13.2 的 data-race 规则。

Memory ordering 规定 memory operation 之间需要满足的顺序约束。对于这次交接，我们需要 producer 发布 data 的写入，并让 consumer 在确认这次发布之后读取它。Release store 和 acquire load 正好承担这两个角色。

2. 把一次发布写成完整程序

2.1 单个 CTA、两个 warp、一份 payload

下面只启动一个 64-thread CTA。Thread 0 生产，thread 32 消费，两者分别属于两个 warp；其余 thread 仅参加初始化 barrier。data 和 flag 都放在这个 CTA 的 shared memory 中，flag 使用 block scope。atomic_ref 为已有的整数提供原子访问，FlagStorage 则显式满足它的对齐要求。

#include <cassert>
#include <cstdio>
#include <cuda/atomic>
#include <cuda_runtime.h>

using ReadyRef = cuda::atomic_ref<int, cuda::thread_scope_block>;

struct alignas(ReadyRef::required_alignment) FlagStorage {
    int value;
};

__global__ void message_passing() {
    __shared__ int data;
    __shared__ FlagStorage flag;

    if (threadIdx.x == 0) {
        data = 0;
        flag.value = 0;
    }
    __syncthreads();

    ReadyRef ready(flag.value);

    if (threadIdx.x == 0) {
        data = 42;                                    // A
        ready.store(1, cuda::memory_order_release);    // B
    }
    if (threadIdx.x == 32) {
        while (ready.load(cuda::memory_order_acquire) != 1) {
        }                                             // C: load returns 1
        assert(data == 42);                            // D
    }
}

int main() {
    message_passing<<<1, 64>>>();
    cudaError_t status = cudaGetLastError();
    if (status == cudaSuccess)
        status = cudaDeviceSynchronize();
    if (status != cudaSuccess) {
        std::fprintf(stderr, "%s\n", cudaGetErrorString(status));
        return 1;
    }
    return 0;
}

可以保存为 publication.cu，在有 CUDA Toolkit 的环境中编译；例如面向 sm_80 使用 nvcc -std=c++17 -arch=sm_80 publication.cu -o publication。程序用 assertion 表达需要证明的结果，host 同时检查 launch 与执行错误。

初始化发生在创建任何 ReadyRef 之前，所有 thread 都经过 __syncthreads() 后才进入协议。此后对 flag.value 的访问全部经过 atomic reference；shared storage 的生命周期覆盖这些 reference。初始化 barrier 只解决起始状态，A 发生在 barrier 之后，A 与 D 之间的交接仍由 B 和 C 完成。

2.2 从 reads-from 推到 happens-before

把 consumer 最后一次返回 1 的 load 记为 C。本例只有 B 会写入 1，因此可以确定 C 读到的是 B 的值，这条值来源关系叫 reads-from。B 带 release，C 带 acquire，双方都使用覆盖两个 thread 的 block scope，于是 B 与 C 建立 synchronizes-with。

一次发布的顺序证明

sequenced-before 表示同一 thread 内由语言规定的求值顺序。A 在 B 之前，C 在 D 之前，加上跨 thread 的 B → C，就得到：

A --sequenced-before--> B
B --synchronizes-with-> C
C --sequenced-before--> D

A --happens-before--> D

happens-before 是这些顺序关系及其传递关系形成的约束。在这个一次写入的程序里，A 的写入有序地先于 D，期间也没有其他人改写 data，所以 D 必须得到 42。Payload 本身可以保持普通类型，因为它的访问已经由 flag 上的同步排好了顺序。

Consumer 较早的 load 可能返回初始值 0；它们没有从 B 读取，因此尚未接收这次发布，循环会继续。Acquire 的保证以匹配的 observation 为条件。若一个可复用的 flag 曾被多次写成 1，单凭数值相等就无法认定读到了哪一代发布，后面还要为复用建立协议。

2.3 改动 order 会断开哪条关系

只改 B 或 C 的 order，其他条件保持不变，可以直接用上面的路径检查结果：

B：storeC：loadC 读到 B 的 1 之后
releaseacquireB → C 建立同步，A happens-before D，读取 42。
seq_cstacquire 或 seq_cstStore 仍包含 release，协议成立。
releaseseq_cstLoad 仍包含 acquire，协议成立。
releaserelaxed缺少接收语义，A 与 D 构成 data race，行为未定义。
relaxedacquire 或 relaxed缺少发布语义，A 与 D 构成 data race，行为未定义。

Release/acquire 已经满足这次交接的证明。把两端改为 seq_cst 会增加 SC 顺序约束，但不会为这个单 flag、单次发布增加一个新的 payload 结果保证。acq_rel 同时具有接收和发布两个方向，适用于 RMW 或 fence，不能直接作为普通 load 或 store 的 order。

3. 把协议扩大之前，先补齐通信条件

3.1 Scope 必须覆盖实际参与者

示例使用 block scope，是因为两个 thread 在同一个 CTA。若把 producer 和 consumer 拆到不同 CTA，普通 shared memory 不再是双方都能访问的存储；payload 与 flag 通常要放到共同可访问的 global memory，atomic 的 scope 也要随之扩大。

通信范围两端采用的 scope存储与平台条件
同一 CTAthread_scope_block双方访问同一对象；本文的 shared memory 满足要求。
同一 GPU、同一 memory synchronization domain，跨 CTAthread_scope_device使用双方可访问的存储，并另外满足下一节的调度条件。
CPU 或其他 GPU 参与thread_scope_system核对 allocation 类型、并发访问和对应操作的原子能力。

只扩大 consumer 一侧不能补足 producer 的范围。例如跨 CTA 的 block-scope store 与 device-scope load 不满足双方的 scope 条件，连 flag 的竞争访问也会形成 data race。CUDA 的 message-passing 示例专门给出了这个反例。使用 atomic_ref 时，还应让同时引用同一对象的 reference 使用一致的 Scope。

System scope 的适用性取决于内存和平台。例如 managed memory 的 CPU/GPU 并发原子访问需要核对 concurrentManagedAccess；mapped memory 和 GPU peer memory 则有各自的原子能力条件，见 atomicity 条件。如果应用主动将同一 GPU 的 kernel 分入不同 memory synchronization domain，跨 domain 的排序也需要 system-scope synchronization；默认 domain 内的通信仍可使用 device scope，见 domain 规则。

3.2 正确的顺序还需要能够推进的执行

在主例中，producer 和 consumer 属于同一个 CTA，初始化 barrier 由全部 64 个 thread 执行，producer 写入后即可退出，不等待 consumer 先完成任何动作。这避免了两个参与者互相等待，以及 consumer 占据资源、producer CTA 却无法驻留的问题。

这里用到的是独立于 memory order 的执行保证。CUDA 13.2 执行模型规定，一个 device thread 开始推进后，同一 thread-block cluster 的 thread 也必须最终推进，其中包含同一 CTA。Consumer 轮询的是 shared storage 上的原子读取，producer 则执行有限的工作。例子的 host 最后进入同步 API 等待完成；它没有通过另一个 host 自旋循环等待 kernel 启动。

普通 grid 不保证任意两个 CTA 同时或按指定次序运行。若已经驻留的 consumer CTA 都在自旋，等待尚未调度的 producer CTA，正确的 release/acquire 也不能消除这种资源等待。跨 CTA 协议需要合适的执行安排，例如具有相应保证的 cooperative launch，或把两个阶段拆成具有依赖关系的 kernel。Release/acquire 本身不提供调度公平性或完成时间上界。

3.3 从一次发布到循环使用的队列槽位

主例在发布 42 后不再改写 payload。若 producer 马上开始写下一份数据，而 consumer 仍在读取上一份，第一次 B → C 的同步并没有排好这两次新访问的顺序，payload 仍可能产生 data race。

复用需要反向交接所有权：consumer 完成读取后发布“槽位已空闲”，producer 接收这个确认之后才能覆盖。多轮协议还需要区分代数，避免把上一轮的 ready == 1 当成新一轮完成。Sequence number 或明确的状态机通常承担这个任务；它们的回绕、对象 lifetime 和多 producer 竞争需要各自的证明。主例提供的是其中一个方向的数据交接。

4. 同一份证明如何映射到 PTX

4.1 在指令上找到发布和接收

CUDA C++ 规定源程序的合法行为，编译器必须生成保持这些行为的指令。对于本文 shared-memory、block-scope 的协议，下面的 PTX 片段把 A 到 D 的角色直接写在指令上。地址和寄存器声明省略，这是按公开 ABI 写出的语义示意，并非某次 nvcc 编译的反汇编结果。

// Producer
st.shared.u32              [data], 42;       // A
st.release.cta.shared.u32  [ready], 1;       // B

// Consumer
WAIT:
ld.acquire.cta.shared.u32  %r0, [ready];     // C
setp.ne.u32               %p0, %r0, 1;
@%p0 bra                  WAIT;
ld.shared.u32             %r1, [data];      // D

.release 和 .acquire 标记排序语义，.cta 标记同步范围，.shared 标记地址空间。若协议经前述条件检查后改为 global-memory、device-scope 交接，相关形式是 st.release.gpu.global 和 ld.acquire.gpu.global。改变的是 scope 和地址空间，A → B → C → D 的证明结构保持相同。

PTX Interoperability 13.2 的 atomic ABI也允许用 relaxed operation 配合 fence 表达同一契约：

下面独立的 fence.release/fence.acquire 从 PTX 8.6 引入，要求 sm_90 或更高；面向前例的 sm_80 时，可以将它们各自加强为 fence.acq_rel.cta。这个目标限制属于独立 fence 的 qualifier，不影响 C++ release/acquire 接口，见 PTX fence 的 ISA 与 Target Notes。

// Alternative B, after A
fence.release.cta;
st.relaxed.cta.shared.u32  [ready], 1;

// Alternative C, before D
WAIT_RELAXED:
ld.relaxed.cta.shared.u32  %r0, [ready];
setp.ne.u32               %p0, %r0, 1;
@%p0 bra                  WAIT_RELAXED;
fence.acquire.cta;

Producer 的 payload 写入在 release fence 之前，consumer 的 payload 读取在 acquire fence 之后，退出循环的 atomic load 仍从发布方的 store 取值。这正是 PTX 9.2 的 release/acquire pattern。只在两侧各放一条 fence，而没有中间的通信关系，无法得到这个证明。

4.2 从 PTX 继续向下看，需要目标架构

ABI 允许合规映射混用，也允许加强 order。因此一份源码里的 release/acquire 可能表现为带语义的访存，也可能出现单独 fence。再往下到 SASS，必须指定目标架构和编译器版本后查看实际输出，不能把某一份输出当成所有 GPU 的固定序列。

排序可能有执行成本。CUDA 的 memory fence interference 说明，fence/flush 有时会等待超出源程序同步所需范围的 in-flight transaction。这个公开现象解释了缩小通信范围、减少不必要同步为何可能有价值，但它没有规定 release 必须把所有 cache line 写回 DRAM，也没有规定 acquire 必须清空整级 cache。

查看 ld/st 时也要区分 cache hint 与排序语义。PTX 的 cache operator 用于性能提示，不改变程序的 memory consistency；.volatile 也没有 acquire/release 的发布语义。完整 qualifier 与 atomic ABI 速查放在附录，避免把代码生成细节混进源码的正确性证明。

5. 根据交接的内容选择 order

回到起点：ready 的职责是交付另一个地址上的普通 payload，因此需要发布方 release 和接收方 acquire。若 atomic 只分配独立编号，正确性所依赖的关系会少一些。下面的 device-scope atomic 自己拥有存储；每个 thread 将取得的编号写到独占的输出元素：

#include <cuda/atomic>

__device__ cuda::atomic<unsigned, cuda::thread_scope_device> ticket{0};

__global__ void allocate_ticket(unsigned* out) {
    unsigned i = blockIdx.x * blockDim.x + threadIdx.x;
    out[i] = ticket.fetch_add(1, cuda::memory_order_relaxed);
}

这里假定一维 launch，out 为每个 thread 分配了一个元素，索引与计数器都没有回绕，所有访问处于同一 device scope。Atomic RMW 的不可分割更新以及同一对象的 modification order 足以分配互不重复的编号；编号大小不承诺 thread 的完成顺序。Host 在 kernel 完成后读取输出。若其他 GPU thread 要根据 ticket 的数值判断某个 out[i] 已写好，就增加了新的 publication 要求，当前代码并未提供它。

Atomic 承担的职责所需关系常用 order
只计数或分配编号仅依赖当前对象的原子更新relaxed
写完 payload 后交付状态先前访问进入发布关系release store
接收状态后访问 payload从对应发布接收先行访问acquire load
一次状态更新同时接收旧阶段、交付新阶段RMW 需要接收和发布两个方向acq_rel
证明依赖多个 atomic object 的 SC 顺序在适用的 scope 内增加 SC 全序约束seq_cst

选择 order 前，先把普通数据的生产、交付、消费和回收画出来，就能看出哪些访问必须排成 happens-before。随后选择覆盖参与者的 scope，检查实际 launch 能否推进。对于整组 thread 的阶段性交接，barrier 往往能更直接地表达意图；对于独立 producer/consumer，flag 的 release/acquire 让交接发生在具体数据就绪的位置。性能优化应从这些已成立的关系出发，再比较 kernel 时间，不能通过删掉证明中必需的一条边换取更短的指令序列。

A.2 CAS、wait 与 fence

load、store、exchange、fetch_add/sub/and/or/xor 和 compare-exchange 使用标准 atomic 的参数习惯，省略 order 时通常采用 seq_cst。Compare-exchange 的成功路径是 read-modify-write，失败路径只是读取，因此分别接收两个 order。下面是一段状态转换的 API 片段，其中 phase 是已初始化、scope 合适的 atomic 整数：

int expected = 0;
bool changed = phase.compare_exchange_weak(
    expected, 1,
    cuda::memory_order_acq_rel,  // success: read and write
    cuda::memory_order_acquire  // failure: read only
);

失败时 expected 会取得观察到的值；weak CAS 允许偶发失败。需要最终完成状态转换的算法要按自身状态机处理重试，不能把一次返回 false 当成已完成获取。这个片段只展示两条路径的 order，没有构成一个完整 mutex。

wait 使用 load-side order，notify_one/all 用于通知等待者重新检查状态。Payload 的交接仍取决于相关 store、load 或 fence 的 order。Fence 接口是 cuda::atomic_thread_fence(order, scope)，它没有自己的 atomic object，需要参与协议的 atomic 访问连接双方。

例如保留主例 producer 的 release store，consumer 可以改成下面的形式。退出循环的 relaxed load 必须从 B 读取，load 与 fence 的 scope 都覆盖 producer，D 必须放在 fence 后面。这满足 CUDA 对 atomic-to-fence 同步的规定：

while (ready.load(cuda::memory_order_relaxed) != 1) {
}
cuda::atomic_thread_fence(
    cuda::memory_order_acquire, cuda::thread_scope_block);
int value = data;

B.1 Order 的方向和合法操作

Order承担的排序角色常见操作
relaxed保留对象本身的原子性及 modification order，不单独发布其他地址的数据。Load、store、RMW；relaxed fence 不增加排序。
acquire通过匹配 observation 接收发布，使其作用于后续访问。Load、RMW、fence。
release将先行访问纳入其他 thread 可接收的发布关系。Store、RMW、fence。
acq_rel同一操作包含两个方向。RMW、fence。
seq_cst包含适合该操作的 acquire/release 语义，并加入 SC 顺序约束。Load、store、RMW、fence。
consume历史上针对数据依赖的接收语义；CUDA 文档中的当前实现加强为 acquire。可用于 load-side 操作；新代码通常直接写 acquire。

Acquire 和 release 约束不同方向，不能排成一条统一的强弱直线。忽略 consume 的历史差异后，可以按操作种类读下面的偏序；箭头仅表示排序约束加强，不表示运行时间：

load:   relaxed < acquire < seq_cst
store:  relaxed < release < seq_cst

RMW:                 acquire
                    /       \
       relaxed ----           ---- acq_rel ---- seq_cst
                    \       /
                     release

普通 load 不接受 release/acq_rel，普通 store 不接受 consume/acquire/acq_rel。Compare-exchange 的 failure order 也只能使用 load-side 语义，不能含 release。Acquire 在一般协议中可以从 release sequence 接收发布；本文为使值来源清楚，使用直接从单个 release store 读取的情形。

B.2 C++ 与 CUDA 的版本差异

C++11 至 C++23 的接口包含六个 order 名称。当前 C++ 工作草案的 兼容性附录保留 consume，并将其含义定义为 acquire。CUDA 13.2 的 compiler atomic built-in 文档仍列六个名字，并明确把 __NV_ATOMIC_CONSUME 加强为 __NV_ATOMIC_ACQUIRE。这些版本差异不影响主例直接使用 release/acquire。

移植 CPU 的 std::atomic 算法时，可以复用数据交接的证明思路；CUDA 还需要补上 scope、内存能力和 GPU 执行条件。采用 cuda::std::atomic 并不会自动消除这些前置条件。也不要把 CPU 上某个 order “没有额外指令”的经验直接套到 GPU，代码生成与成本都需要在目标环境中确认。

NVIDIA GPU Atomic Memory Ordering: CUDA C++ Semantics and PTX Mappings

One thread writes a result to data, then sets ready to 1. Another thread sees 1 and retrieves the result. GPU work queues, completion flags, and object publication often contain this handoff. The difficulty is that an atomic update to ready directly protects the flag; the ordinary reads and writes of data still need an ordering relation between the threads.

This article follows that handoff through a complete CUDA C++ program, derives why release/acquire makes it valid, and examines the additional conditions needed across CTAs. It then connects the proof to PTX. The discussion uses the public CUDA 13.2 memory model and atomic ABI; the full interface and memory-order comparisons are in the appendices.

1. Why an atomic flag does not yet deliver ordinary data

Suppose data and ready have both been initialized to 0. The payload is an ordinary integer, the flag is atomic at a scope covering both threads, and a single producer writes one result. Consider this incorrect protocol, which lacks synchronization:

// Producer
data = 42;
ready.store(1, relaxed);

// Consumer
if (ready.load(relaxed) == 1)
    value = data;

The producer's two statements have an order within its thread, as do the consumer's statements. The atomic flag also provides atomicity for its own accesses. Those local constraints do not connect data = 42 to value = data in the other thread. Observing 1 has not established the synchronization needed to read the ordinary payload.

In CUDA C++, potentially concurrent conflicting ordinary accesses, at least one of which writes, form a data race when neither happens before the other. The behavior is undefined. The problem therefore goes beyond occasionally obtaining an old value: a table listing only 0 and 42 would not describe this program's allowed outcomes. The relevant criterion is the CUDA 13.2 data-race rule.

Memory ordering specifies the ordering constraints that memory operations must satisfy. For this handoff, the producer must publish its write to data, and the consumer must read the payload after receiving that publication. A release store and an acquire load provide those two roles.

2. A complete program for one publication

2.1 One CTA, two warps, one payload

The program launches one CTA with 64 threads. Thread 0 produces the result and thread 32 consumes it, placing them in separate warps. The remaining threads participate only in the initialization barrier. Both data and the flag reside in the CTA's shared memory, and the flag uses block scope. An atomic_ref provides atomic access to the existing integer; FlagStorage explicitly satisfies its alignment requirement.

#include <cassert>
#include <cstdio>
#include <cuda/atomic>
#include <cuda_runtime.h>

using ReadyRef = cuda::atomic_ref<int, cuda::thread_scope_block>;

struct alignas(ReadyRef::required_alignment) FlagStorage {
    int value;
};

__global__ void message_passing() {
    __shared__ int data;
    __shared__ FlagStorage flag;

    if (threadIdx.x == 0) {
        data = 0;
        flag.value = 0;
    }
    __syncthreads();

    ReadyRef ready(flag.value);

    if (threadIdx.x == 0) {
        data = 42;                                    // A
        ready.store(1, cuda::memory_order_release);    // B
    }
    if (threadIdx.x == 32) {
        while (ready.load(cuda::memory_order_acquire) != 1) {
        }                                             // C: load returns 1
        assert(data == 42);                            // D
    }
}

int main() {
    message_passing<<<1, 64>>>();
    cudaError_t status = cudaGetLastError();
    if (status == cudaSuccess)
        status = cudaDeviceSynchronize();
    if (status != cudaSuccess) {
        std::fprintf(stderr, "%s\n", cudaGetErrorString(status));
        return 1;
    }
    return 0;
}

Save it as publication.cu and compile in an environment with the CUDA Toolkit. For example, nvcc -std=c++17 -arch=sm_80 publication.cu -o publication targets sm_80. The assertion states the result to be proved, and the host checks launch and execution errors.

Initialization occurs before any ReadyRef is constructed. Every thread passes through __syncthreads() before entering the protocol. All subsequent accesses to flag.value use atomic references, and the shared storage outlives them. The initialization barrier establishes the starting state. Since A occurs after that barrier, B and C still provide the handoff between A and D.

2.2 From reads-from to happens-before

Call the consumer's final load, which returns 1, C. Only B writes 1 in this program, so C obtains its value from B. This value-source relation is called reads-from. B has release semantics, C has acquire semantics, and both use block scope covering the two threads. B and C therefore establish synchronizes-with.

The ordering proof for one publication

Sequenced-before describes the language-defined evaluation order within a thread. A precedes B, and C precedes D. Adding the cross-thread edge from B to C gives:

A --sequenced-before--> B
B --synchronizes-with-> C
C --sequenced-before--> D

A --happens-before--> D

Happens-before combines these ordering relations and their transitive relationships. In this program, which publishes once, A's write is ordered before D and no other thread overwrites data in between. D must therefore obtain 42. The payload can remain an ordinary object because synchronization on the flag has ordered its accesses.

Earlier consumer loads may return the initial value 0. Those loads do not read from B, so they have not received this publication and the loop continues. The acquire guarantee depends on a matching observation. If a reusable flag has been set to 1 several times, equality of the value alone no longer identifies the publication generation; reuse needs an additional protocol.

2.3 Which relation changes when the order changes

Change only the order of B or C, retaining all other conditions, and the path above gives the result:

B: storeC: loadAfter C reads B's value 1
releaseacquireB synchronizes with C, A happens before D, and D reads 42.
seq_cstacquire or seq_cstThe store still includes release semantics, so the protocol is valid.
releaseseq_cstThe load still includes acquire semantics, so the protocol is valid.
releaserelaxedThe receiving semantic is absent. A and D race, giving undefined behavior.
relaxedacquire or relaxedThe publishing semantic is absent. A and D race, giving undefined behavior.

Release/acquire already satisfies this handoff's proof. Using seq_cst at both ends adds SC ordering constraints, but gives this single-flag, single-publication program no additional guarantee about the payload result. acq_rel combines reception and publication; it applies to RMW operations or fences and is not a valid order for a plain load or store.

3. Conditions to establish before expanding the protocol

3.1 Scope must cover the actual participants

The example uses block scope because the two threads belong to one CTA. Moving the producer and consumer to different CTAs changes that assumption. Ordinary shared memory is no longer common storage for both participants; the payload and flag usually move to accessible global memory, and the atomic scope must expand with the communication range.

Communication rangeScope at both endsStorage and platform conditions
Within one CTAthread_scope_blockBoth threads access the same object; the example's shared memory qualifies.
Across CTAs on one GPU, within one memory synchronization domainthread_scope_deviceUse accessible storage and establish the scheduling conditions in the next section.
A CPU or another GPU participatesthread_scope_systemCheck the allocation type, concurrent access support, and atomic capability for the operation.

Widening only the consumer's scope does not repair the producer's range. A block-scope store paired with a device-scope load in another CTA fails the mutual scope requirement; the competing flag accesses themselves race. CUDA's message-passing example gives this counterexample. When using atomic_ref, references concurrently naming the same object must also use a consistent Scope.

System scope depends on the memory and platform. For example, concurrent CPU/GPU atomic access to managed memory requires checking concurrentManagedAccess. Mapped memory and GPU peer memory have their own conditions; see the atomicity requirements. If an application places kernels on the same GPU in separate memory synchronization domains, ordering across those domains also needs system-scope synchronization. Device scope remains sufficient within the default domain; see the domain rules.

3.2 Correct ordering also needs an execution that can progress

In the main example, the producer and consumer belong to one CTA, all 64 threads reach the initialization barrier, and the producer can finish its store and exit without waiting for the consumer. This avoids both circular waiting and a consumer occupying resources while its producer CTA cannot become resident.

The execution guarantee is separate from memory order. The CUDA 13.2 execution model states that once a device thread makes progress, the threads in its thread-block cluster must eventually make progress, including those in the same CTA. The consumer polls an atomic read of shared storage, and the producer performs finite work. The host enters a synchronization API to wait for completion; it does not wait for the kernel to start through a separate host spin loop.

An ordinary grid does not guarantee that arbitrary CTAs execute concurrently or in a chosen order. If resident consumer CTAs spin while their producer CTAs have not been scheduled, correct release/acquire semantics do not remove the resource dependency. Communication across CTAs needs an appropriate execution arrangement, such as a cooperative launch with the required guarantees, or separate kernels connected by a dependency. Release/acquire itself provides neither scheduling fairness nor a bound on completion time.

3.3 From one publication to a reusable queue slot

The main example never overwrites the payload after publishing 42. If the producer immediately starts writing the next payload while the consumer is still reading the previous one, the first B-to-C synchronization has not ordered those new accesses. The payload can race again.

Reuse requires a handoff of ownership in the reverse direction: the consumer publishes that the slot is free after finishing its read, and the producer receives that acknowledgment before overwriting it. A repeated protocol also needs to distinguish generations, so a previous ready == 1 cannot be mistaken for a new completion. Sequence numbers or an explicit state machine usually serve that purpose. Their wraparound, object lifetime, and competition among producers need their own proofs. The main example supplies one direction of the data handoff.

4. How the same proof maps to PTX

4.1 Identify publication and reception in the instructions

CUDA C++ specifies the source program's allowed behavior, and the compiler must generate instructions that preserve it. For the shared-memory, block-scope protocol, the following PTX fragment places the roles of A through D directly on the instructions. Address and register declarations are omitted. This is a semantic illustration based on the public ABI, rather than disassembly from a particular nvcc run.

// Producer
st.shared.u32              [data], 42;       // A
st.release.cta.shared.u32  [ready], 1;       // B

// Consumer
WAIT:
ld.acquire.cta.shared.u32  %r0, [ready];     // C
setp.ne.u32               %p0, %r0, 1;
@%p0 bra                  WAIT;
ld.shared.u32             %r1, [data];      // D

.release and .acquire identify ordering semantics, .cta identifies the synchronization scope, and .shared identifies the address space. After establishing the conditions for a global-memory, device-scope handoff, the corresponding forms are st.release.gpu.global and ld.acquire.gpu.global. The scope and address space change, while the A → B → C → D proof retains its structure.

The PTX Interoperability 13.2 atomic ABI also permits relaxed operations combined with fences to express the same contract:

The standalone fence.release/fence.acquire forms below were introduced in PTX 8.6 and require sm_90 or newer. For the earlier example's sm_80 target, each can be strengthened to fence.acq_rel.cta. This target restriction applies to the standalone fence qualifiers and does not restrict the C++ release/acquire interface; see the PTX fence ISA and Target Notes.

// Alternative B, after A
fence.release.cta;
st.relaxed.cta.shared.u32  [ready], 1;

// Alternative C, before D
WAIT_RELAXED:
ld.relaxed.cta.shared.u32  %r0, [ready];
setp.ne.u32               %p0, %r0, 1;
@%p0 bra                  WAIT_RELAXED;
fence.acquire.cta;

The producer's payload write precedes the release fence, the consumer's payload read follows the acquire fence, and the load that exits the loop still reads from the publishing store. This forms a PTX 9.2 release/acquire pattern. A fence on each side without the intervening communication relation does not establish this proof.

4.2 Looking below PTX requires a target architecture

The ABI permits conforming mappings to be mixed and orders to be strengthened. Release/acquire in source code can therefore appear as memory instructions carrying semantics or as separate fences. To continue to SASS, specify the target architecture and compiler version and inspect their output. One compilation does not define a fixed sequence for every GPU.

Ordering can carry an execution cost. CUDA's discussion of memory fence interference explains that fence and flush operations sometimes wait on in-flight transactions beyond those required by source-level synchronization. This public observation explains why a narrower communication range or fewer unnecessary synchronization operations can matter. It does not specify that release must write every cache line to DRAM or that acquire must empty an entire cache.

When reading ld/st, distinguish cache hints from ordering semantics. PTX cache operators are performance hints and do not change memory consistency; .volatile also lacks acquire/release publication semantics. The appendix collects the qualifier and atomic ABI reference, keeping code-generation details separate from the source program's correctness proof.

5. Choose the order from what is being handed off

The original ready flag delivers an ordinary payload at another address, so the producer needs release and the receiver needs acquire. An atomic that only allocates independent numbers relies on fewer relations. The following device-scope atomic owns its storage, and each thread writes the number it receives to an exclusive output element:

#include <cuda/atomic>

__device__ cuda::atomic<unsigned, cuda::thread_scope_device> ticket{0};

__global__ void allocate_ticket(unsigned* out) {
    unsigned i = blockIdx.x * blockDim.x + threadIdx.x;
    out[i] = ticket.fetch_add(1, cuda::memory_order_relaxed);
}

This assumes a one-dimensional launch, one allocated output element per thread, no index or counter wraparound, and accesses within one device scope. Indivisible RMW updates and the atomic object's modification order suffice to assign distinct numbers. The numbers do not promise thread completion order. The host reads the output after kernel completion. If other GPU threads use the ticket value to decide that an out[i] has been written, that adds a publication requirement which this code does not provide.

Role of the atomicRequired relationUsual order
Only count or allocate numbersDepend only on this object's atomic updaterelaxed
Deliver state after writing a payloadInclude earlier accesses in publicationrelease store
Access a payload after receiving stateReceive earlier accesses from the corresponding publicationacquire load
Receive an old phase and deliver a new phase in one updateThe RMW needs both directionsacq_rel
Depend on SC ordering across several atomic objectsAdd SC total-order constraints within the applicable scopesseq_cst

Before choosing an order, trace how ordinary data is produced, handed off, consumed, and reclaimed. That identifies the accesses which must form happens-before. Then choose a scope covering the participants and check whether the launch can make progress. A barrier often expresses a handoff between phases of a thread group more directly; a release/acquire flag lets independent producers and consumers hand off individual results when they become ready. Performance tuning can then compare kernel time while preserving those established relations. Removing an edge required by the proof is not a valid way to shorten the instruction sequence.

A.2 CAS, wait, and fences

load, store, exchange, fetch_add/sub/and/or/xor, and compare-exchange follow standard atomic parameter conventions. Omitting the order normally selects seq_cst. A successful compare-exchange is a read-modify-write operation, while failure performs only a read, so the two paths accept separate orders. The following API fragment operates on an initialized atomic integer phase with a suitable scope:

int expected = 0;
bool changed = phase.compare_exchange_weak(
    expected, 1,
    cuda::memory_order_acq_rel,  // success: read and write
    cuda::memory_order_acquire  // failure: read only
);

On failure, expected receives the observed value, and weak CAS permits spurious failure. An algorithm that requires the transition to complete must handle retries according to its state machine; a false return does not complete an acquisition. This fragment illustrates the orders on the two paths and does not constitute a complete mutex.

wait takes a load-side order; notify_one/all asks waiting threads to check the state again. Payload handoff still depends on the associated store, load, or fence orders. The fence interface is cuda::atomic_thread_fence(order, scope). A fence has no atomic object of its own, so atomic accesses in the protocol must connect the participants.

For example, retain the main example's producer release store and replace the consumer with the following. The relaxed load that exits the loop must read from B, both the load and fence scopes must cover the producer, and D must follow the fence. This meets the CUDA atomic-to-fence synchronization rule:

while (ready.load(cuda::memory_order_relaxed) != 1) {
}
cuda::atomic_thread_fence(
    cuda::memory_order_acquire, cuda::thread_scope_block);
int value = data;

B.2 Version differences between C++ and CUDA

C++11 through C++23 expose six order names. The current C++ working draft retains consume in its compatibility annex and defines its meaning as acquire. CUDA 13.2's compiler atomic built-in documentation still lists six names and explicitly strengthens __NV_ATOMIC_CONSUME to __NV_ATOMIC_ACQUIRE. These differences do not affect the main example's explicit release/acquire operations.

When porting a CPU algorithm using std::atomic, its data-handoff proof remains a useful starting point. CUDA additionally needs scope, memory capability, and GPU execution conditions. Choosing cuda::std::atomic does not remove those preconditions. Nor does a CPU observation that an order costs no extra instructions transfer directly to a GPU: code generation and cost must be checked in the target environment.

PTX 9.2 distinguishes the primary semantics .weak, .volatile, .relaxed, and .acquire for ld. The corresponding set for st is .weak, .volatile, .relaxed, and .release. Each set is mutually exclusive, with weak as the default. Weak operations depend on other mechanisms for synchronization; scoped relaxed operations are strong operations but do not alone publish or receive data at other addresses.

In the PTX memory model, .volatile has system-scope relaxed semantics plus additional instruction-execution constraints. It is not acquire/release. MMIO has dedicated .mmio rules that cannot be inferred from volatile. The permitted combinations of address space, scope, and cache qualifiers remain subject to each instruction's syntax.
