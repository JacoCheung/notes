Kernel Design Agents 与 KernelWiki：面向 GPU Kernel 优化的证据驱动工作流

GPU kernel 优化是一项受约束的实验工作：实现必须覆盖目标输入域，性能数据必须来自可比较的测量，所用技巧还要落在目标架构与工具链的能力范围内。Coding agent 扩大了候选搜索的速度，也随之增加了记录假设、验证结果和来源证据的负担。Kernel Design Agents 负责组织这条实验流程，KernelWiki 负责提供可追溯的硬件与实现知识；两者共同把候选生成接到可复查的工程决策上。

证据范围：本文分别固定到 Kernel Design Agents commit dda6be3 与 KernelWiki commit b6b4301。项目能力的描述来自这两个公开快照；流程效果仍需在具体任务中验证。

1. 两个项目的分工

Kernel Design Agents，下文简称 KDA，是一套面向性能敏感任务的 agent 工作流。固定版本的 README 与 agent-flow.md 要求先定义任务契约，再围绕候选实现进行正确性验证、性能测量和晋级判断；代码、测试、数据集与生成物由独立的任务仓库保存。

KernelWiki 是 KDA 仓库引用的领域知识 skill。该快照的 README 将范围限定为 NVIDIA Blackwell SM100 与 Hopper SM90 kernel，并列出硬件、技术、kernel、上游 PR、竞赛材料和语言指南等内容。KDA 定义实验流程；KernelWiki 提供候选线索及其来源入口。

KDA、KernelWiki 与任务仓库的职责边界

这套组合包含三种相互独立的证据。KernelWiki 说明某项技术在来源材料中的适用条件；任务仓库的 validation、benchmark 与 profile 记录当前实现的实验结果；KDA 则规定如何保存候选关系并作出晋级决定。历史性能数字适合生成假设，当前环境中的实验负责确认结论。

2. Kernel 优化的证据闭环

Kernel 候选的验收条件同时覆盖数值、测量和架构三个方面。测试套件先判断实现是否保持语义，benchmark 再判断性能变化是否稳定，架构与工具链约束则决定某种实现能否在目标环境成立：

  • 数值约束：不同 dtype、shape、stride 和边界 tile 可能要求不同容差；随机样例通过不代表整个输入域正确。
  • 测量约束：首轮 JIT、GPU 时钟、cache 状态、样本数量和同步位置都会影响计时。单个 latency 数字缺少解释力。
  • 架构约束：wgmma、tcgen05、TMEM、TMA 和 2-SM cooperative MMA 有明确的 compute capability 与工具链边界。

这三类约束使候选历史成为实验的一部分。Baseline 提供共同参照，父子关系记录每次改动基于哪一版实现，验证与性能结果决定候选去留，被拒绝的原因则避免后续搜索重复进入同一分支。KDA 用 task contract 固定验收条件，再用候选记录保存这些决策。

4. 候选与实验记录

KDA 建议把实现工作放在独立 task workspace 中。代码、测试、benchmark harness 和私有约束属于任务仓库；KDA 仓库只保存可复用流程。一个最小目录可以是：

task-workspace/
├── docs/
│   ├── draft.md
│   └── plan.md
├── runs/
├── outputs/
├── profile/
├── benchmark.csv
└── candidates.jsonl

candidates.jsonl 不需要复杂 schema，但至少要能恢复候选之间的关系和结论：

以下记录为格式示例，latency 与退化原因均为示意数据。

{"id":"c0","parent":null,"change":"baseline","correct":true,"p50_us":42.8,"status":"baseline"}
{"id":"c1","parent":"c0","change":"double-buffer K/V TMA load","correct":true,"p50_us":39.6,"status":"keep"}
{"id":"c2","parent":"c1","change":"increase software stages 3 -> 4","correct":true,"p50_us":41.1,"status":"reject","reason":"register pressure reduced occupancy"}

拒绝记录为后续搜索提供负向实验结果。下一轮 agent 读到 c2 的寄存器压力与 occupancy 变化后，可以跳过已经测过的 stage 配置，把预算留给新的假设。最终代码说明“采用了什么”，候选历史补上“为什么采用”；至于下一批假设从哪里来，则进入 KernelWiki 的知识组织与检索范围。

5. KernelWiki 的知识结构

KernelWiki 是一套带 provenance 的结构化知识库。它把原始来源、整理后的知识页和面向检索的索引分为三层：

层目录保存内容主要用途
Sourcesources/PR、官方文档、论文、博客与竞赛材料的来源页追溯原始事实，避免综合结论失去出处
Wikiwiki/hardware、technique、kernel、pattern、language、migration 知识页把分散材料整理成可直接使用的技术说明
Queryqueries/按架构、问题、技术、硬件特性、仓库、kernel 类型和语言生成的索引缩小候选页面集合

每个页面都有 YAML frontmatter。id 是跨页引用的稳定入口，sources 指向证据页，related 和 prerequisites 组成知识图。data/tags.yaml 约束术语，data/aliases.yaml 把 UMMA 归一为 tcgen05、把 B200 归一为 sm100。版本相关能力则通过 version_sensitive 指针连接到中央声明表。

artifacts/ 保存固定到 upstream SHA 的代码、patch 或摘录，PROVENANCE.yaml 记录来源、许可证、文件模式与 SHA-256。知识页据此提供技术概览，artifact 则把概览接回对应版本的实现。检索过程需要先定位知识页，再沿 provenance 展开源码证据。

6. 从问题到源码的查询路径

KernelWiki 的 SKILL.md 定义了五条查询路径。下面列出前三条：

# 1. 自然语言与结构化过滤
python3 scripts/query.py "ping-pong attention" --limit 5
python3 scripts/query.py --architecture B200 --type kernel
python3 scripts/query.py --symptom tail-effect --compact

# 2. 读取指定知识页，并展开它引用的来源
python3 scripts/get_page.py kernel-flash-attention-4 --follow-sources

# 3. 对 wiki 正文与 PR 页做正则搜索
python3 scripts/grep_wiki.py "tcgen05" --only wiki

query.py 负责召回，get_page.py 负责展开具体页面和来源，grep_wiki.py 适合查指令名、API 或代码片段。问题比较宽时，可以先读 references/primer.md；已经知道 kernel 或 PR ID 时，直接调用 get_page.py 更省上下文。

以 kernel-flash-attention-4 为例，页面的 frontmatter 同时记录架构、语言、相关技术、来源和结构化性能数据。正文还整理了 ping-pong scheduling、software exponential 与 2-CTA backward。这里的内容属于知识库作者的综合；工程结论仍应沿 sources 回到论文、博客和上游 PR。

7. 证据等级与可复现性

KernelWiki 用 confidence 描述结论的证据强度，用 reproducibility 描述实现材料能够运行到什么阶段。这两个维度相互正交：来源可靠的架构说明可以停留在概念层，而能够编译的实验代码也可能依赖尚未形成公开契约的行为。

Confidence含义回答时的处理
verified同时有官方文档与上游代码支持仍需注明适用架构与版本
source-reported由论文、主要项目或作者材料报告明确写成来源报告的结论
inferred从多个来源综合推断，没有单一权威陈述把推断与源码事实分开
experimental未文档化技巧或版本敏感行为给出 CUDA、PTX 或工具链版本并要求本地复验

可复现性沿 concept → pseudocode → snippet → runnable → benchmarked 递进。仓库的 validator 要求 technique、kernel 和 language 页面至少达到 snippet。这一等级确认知识页带有可编译片段；把片段接入当前项目仍需满足接口、shape、dtype 与工具链条件。

性能数据也不能脱离上下文。KernelWiki 要求至少同时报告 gpu、dtype、shape、metric、value 和 source_id。缺少任意一项，诸如“比 cuDNN 快 1.2 倍”的描述都很难用于工程决策。

8. 一个 B200 attention 优化任务

假设任务是在 B200 上优化 BF16 attention forward。KDA 与 KernelWiki 可以按以下顺序配合：

  1. 固定契约。列出 shape 集合、reference、容差、允许的 DSL、benchmark 命令和 5% 晋级门槛。
  2. 建立 baseline。运行 correctness suite 与 benchmark，记录 kernel 时间、端到端时间、编译版本和 GPU 时钟策略。
  3. 检索候选。按 sm100、attention、tcgen05、tmem 查询；打开相关 kernel 页并跟随 sources。
  4. 写出假设。例如“用 ping-pong scheduling 隐藏 softmax 延迟”，同时写明它依赖哪些 shape、warp 分工与 TMEM 布局。
  5. 一次实现一个候选。不要同时改 tile shape、stage count 和 epilogue，否则无法归因。
  6. 先验证正确性。覆盖满 tile、尾块、极值和非连续输入；失败的候选不进入性能比较。
  7. 再测量与 profile。重复计时，并用 NCU 判断预期机制是否真的发生，例如 tensor pipe 利用率是否上升、stall 是否从 dependency 转向 memory。
  8. 记录晋级决定。结果写入 benchmark.csv 和 candidates.jsonl。达到契约才晋级，否则记录退化原因并回到下一个候选。

知识证据与实验事实必须分开。KernelWiki 能证明某种技术在特定来源中出现过，也能提供实现入口；只有任务仓库里的 validation、benchmark 和 profile 才能证明它适合当前 kernel。

9. 安装方式与适用边界

KDA 仓库把 KernelWiki 和 NCU report skill 作为 submodule 组织。按照当前 README，可以一次拉取完整工作流：

git clone --recurse-submodules \
  https://github.com/mit-han-lab/kernel-design-agents.git
cd kernel-design-agents

mkdir -p ~/.claude/skills
ln -s "$(pwd)/skills/KernelWiki" ~/.claude/skills/KernelWiki
ln -s "$(pwd)/skills/ncu-report-skill" ~/.claude/skills/ncu-report-skill

也可以只安装 KernelWiki：

git clone https://github.com/mit-han-lab/KernelWiki.git \
  ~/.claude/skills/KernelWiki

cd ~/.claude/skills/KernelWiki
python3 scripts/query.py --tag nvfp4 --type kernel --compact
python3 scripts/get_page.py kernel-flash-attention-4 --frontmatter-only

仓库当前的自动注册说明面向 Claude Code。换用其他 coding agent 时，query.py、get_page.py 和 grep_wiki.py 仍是普通 Python 脚本，但 skill 能否自动发现取决于宿主的扩展机制。

KernelWiki 以 Blackwell 为主，同时保留与 Blackwell 迁移相关的 Hopper 内容。通用 CUDA 问答、host 侧框架集成以及 DeepEP、EPLB、DualPipe 这类分布式系统主题不在收录范围内。正文以英文为准，CuTe DSL、CUDA C++、PTX 和 Triton 是一等语言入口。

知识库也有时间边界。本文写作时，项目 README 标注上游 PR 审计截止到 2026-05-20，文档、release 与 leaderboard 快照验证到 2026-08-18 UTC。查询结果应和本机 CUDA、CUTLASS、Triton 版本一起核对。KDA 本身则被作者称为仍在开发的早期研究原型，适合借鉴其流程，不应把目录结构或文件格式当成稳定 API。

Kernel Design Agents and KernelWiki: An Evidence-Driven Workflow for GPU Kernel Optimization

GPU kernel optimization is a constrained experimental discipline. An implementation must cover the target input domain, performance data must come from comparable measurements, and every technique must fit the target architecture and toolchain. Coding agents expand the rate of candidate exploration, which increases the need to record hypotheses, validation results, and source provenance. Kernel Design Agents organizes that experimental process, while KernelWiki supplies traceable hardware and implementation knowledge. Together they connect candidate generation to reviewable engineering decisions.

Evidence boundary: This article pins Kernel Design Agents to commit dda6be3 and KernelWiki to commit b6b4301. Descriptions of project capabilities come from these public snapshots. Their effectiveness still has to be tested on each concrete task.

1. Responsibilities of the two projects

Kernel Design Agents, abbreviated KDA below, is an agent workflow for performance-sensitive work. The pinned README and agent-flow.md begin with a task contract, then iterate over candidate implementations through correctness validation, performance measurement, and promotion decisions. A separate task repository holds code, tests, datasets, and generated artifacts.

KernelWiki is the domain-knowledge skill referenced by the KDA repository. Its README limits this snapshot to NVIDIA Blackwell SM100 and Hopper SM90 kernels, with material on hardware, techniques, kernels, upstream pull requests, competition entries, and programming-language guidance. KDA defines the experiment process; KernelWiki supplies candidate ideas and routes back to their sources.

Responsibility boundaries among KDA, KernelWiki, and the task repository

This arrangement produces three independent forms of evidence. KernelWiki records the conditions under which a technique appears in its sources. Validation, benchmarks, and profiles in the task repository capture experimental results for the current implementation. KDA defines how candidate relationships and promotion decisions are recorded. Historical performance numbers generate hypotheses; experiments in the target environment establish conclusions.

2. Evidence loops in kernel optimization

A kernel candidate is accepted against numerical, measurement, and architecture constraints. The test suite first establishes semantic fidelity, benchmarks determine whether the performance change is stable, and architecture or toolchain limits determine whether the implementation is valid for the target environment:

  • Numerical constraints: Different dtypes, shapes, strides, and boundary tiles may require different tolerances. Passing a set of random cases does not establish correctness over the whole input domain.
  • Measurement constraints: Initial JIT compilation, GPU clocks, cache state, sample count, and synchronization placement all affect timing. One latency number says very little on its own.
  • Architecture constraints: wgmma, tcgen05, TMEM, TMA, and two-SM cooperative MMA each have explicit compute-capability and toolchain limits.

These constraints make candidate history part of the experiment. The baseline supplies a common reference, parent-child links identify the implementation behind each change, validation and performance results decide promotion, and rejection reasons prevent the search from revisiting a measured branch. KDA fixes the acceptance conditions in a task contract and preserves the decisions in candidate records.

3. KDA execution model

KDA starts with a task contract. The repository's basic-flow.md provides a template for the fields that must be fixed in advance:

The B200 task, 5% threshold, and commands below are illustrative field values, not benchmark results reported by the KDA repository.

FieldQuestion to answerExample for a kernel task
ObjectiveWhat exactly is being optimized?Reduce BF16 attention forward latency on B200
Correctness requirementsWhat counts as a correct result?Cover specified shapes, compare with a reference, and define atol/rtol
ConstraintsWhich implementation paths are allowed?CuTe DSL; unchanged interface; bounded shared-memory use
Validation commandWhich command proves correctness?pytest tests/test_attention.py -q
Evaluation commandWhich command produces comparable metrics?A benchmark script with fixed GPU and shapes
Promotion criteriaWhat must a candidate achieve to survive?All tests pass, p50 improves by at least 5%, and no target shape regresses

The task contract fixes the objective, constraints, and measurement protocol before the search begins, so every candidate is compared under the same conditions. Test shapes, numerical tolerances, and timing methodology remain fixed when a candidate misses its performance threshold.

KDA candidate iteration loop

The pinned process asks the agent to record the baseline, risks, candidate directions, and validation commands in docs/draft.md, then turn that material into an executable docs/plan.md. This leaves the research hypothesis in place before code changes begin, which helps separate a faulty implementation from a faulty hypothesis later.

4. Candidate and experiment records

KDA recommends keeping implementation work in a separate task workspace. Code, tests, the benchmark harness, and private constraints belong to that repository; KDA holds only the reusable process. A minimal layout could be:

task-workspace/
├── docs/
│   ├── draft.md
│   └── plan.md
├── runs/
├── outputs/
├── profile/
├── benchmark.csv
└── candidates.jsonl

candidates.jsonl does not need an elaborate schema, but it should preserve candidate relationships and decisions:

The following entries illustrate the record format. Their latency values and regression explanation are not project measurements.

{"id":"c0","parent":null,"change":"baseline","correct":true,"p50_us":42.8,"status":"baseline"}
{"id":"c1","parent":"c0","change":"double-buffer K/V TMA load","correct":true,"p50_us":39.6,"status":"keep"}
{"id":"c2","parent":"c1","change":"increase software stages 3 -> 4","correct":true,"p50_us":41.1,"status":"reject","reason":"register pressure reduced occupancy"}

A rejection record preserves a negative experimental result. Once the next agent sees the register-pressure and occupancy effect associated with c2, it can skip that measured stage configuration and spend its budget on a new hypothesis. The final code records what survived; candidate history records why. KernelWiki supplies the knowledge structure and retrieval path from which the next set of hypotheses can be formed.

5. KernelWiki knowledge structure

KernelWiki is a structured knowledge base with source provenance. It separates original sources, synthesized knowledge pages, and retrieval-oriented indexes into three layers:

LayerDirectoryContentsMain use
Sourcesources/Source pages for pull requests, official documentation, papers, articles, and competition materialTrace facts back to their origins
Wikiwiki/Knowledge pages for hardware, techniques, kernels, patterns, languages, and migrationsTurn scattered material into usable technical notes
Queryqueries/Indexes generated by architecture, problem, technique, hardware feature, repository, kernel type, and languageNarrow the candidate page set

Every page has YAML frontmatter. id is the stable cross-page reference; sources points to evidence pages; related and prerequisites form a knowledge graph. data/tags.yaml constrains terminology, while data/aliases.yaml normalizes UMMA to tcgen05 and B200 to sm100. Version-sensitive capabilities point to a central declaration table through version_sensitive.

artifacts/ contains code, patches, or excerpts pinned to upstream SHAs. PROVENANCE.yaml records origin, license, file patterns, and SHA-256 values. A knowledge page provides the technical overview, while its artifact reconnects that overview to the matching implementation revision. Retrieval therefore begins with a knowledge page and expands through provenance to source evidence.

6. Query path from a problem to source code

KernelWiki's SKILL.md defines five query paths. The first three are shown below:

# 1. Natural-language and structured filters
python3 scripts/query.py "ping-pong attention" --limit 5
python3 scripts/query.py --architecture B200 --type kernel
python3 scripts/query.py --symptom tail-effect --compact

# 2. Read a knowledge page and expand its cited sources
python3 scripts/get_page.py kernel-flash-attention-4 --follow-sources

# 3. Search wiki and PR pages with a regular expression
python3 scripts/grep_wiki.py "tcgen05" --only wiki

query.py handles retrieval, get_page.py expands a selected page and its sources, and grep_wiki.py is useful for instruction names, APIs, and code fragments. For a broad question, start with references/primer.md. If the kernel or pull-request ID is already known, get_page.py uses less context.

The kernel-flash-attention-4 page, for example, records architecture, language, related techniques, sources, and structured performance data in its frontmatter. The body summarizes ping-pong scheduling, software exponential, and two-CTA backward. These are the knowledge-base author's synthesis; engineering conclusions should still follow sources back to papers, articles, and upstream pull requests.

7. Evidence levels and reproducibility

KernelWiki uses confidence to describe the strength of evidence behind a claim and reproducibility to describe how far the implementation material can run. The dimensions are orthogonal: a well-sourced architecture description may remain conceptual, while compilable experimental code may rely on behavior that has not become a public contract.

ConfidenceMeaningHow to present it
verifiedSupported by both official documentation and upstream codeStill state the applicable architecture and version
source-reportedReported by a paper, primary project, or author materialAttribute the conclusion to that source
inferredSynthesized from several sources without one authoritative statementSeparate the inference from source-code facts
experimentalAn undocumented technique or version-sensitive behaviorGive the CUDA, PTX, or toolchain version and require local verification

Reproducibility progresses through concept → pseudocode → snippet → runnable → benchmarked. The repository validator requires technique, kernel, and language pages to reach at least snippet. That level confirms the presence of a compilable fragment; integration into the current project still depends on its interface, shapes, dtypes, and toolchain.

Performance data also needs context. KernelWiki requires at least gpu, dtype, shape, metric, value, and source_id. Without them, a statement such as “1.2× faster than cuDNN” is difficult to use in an engineering decision.

8. A B200 attention optimization task

Suppose the task is to optimize BF16 attention forward on B200. KDA and KernelWiki can be combined in this order:

  1. Fix the contract. List the shape set, reference, tolerances, permitted DSL, benchmark command, and a 5% promotion threshold.
  2. Establish the baseline. Run the correctness suite and benchmark; record kernel time, end-to-end time, compiler versions, and GPU clock policy.
  3. Retrieve candidates. Query for sm100, attention, tcgen05, and tmem; open the relevant kernel pages and follow their sources.
  4. State the hypothesis. For example, “use ping-pong scheduling to hide softmax latency,” together with the required shapes, warp roles, and TMEM layout.
  5. Implement one candidate at a time. Do not change tile shape, stage count, and epilogue together, because the result would be hard to attribute.
  6. Validate correctness first. Cover full tiles, tails, extreme values, and non-contiguous inputs. A failing candidate does not enter performance comparison.
  7. Measure and profile. Repeat timings, then use NCU to check whether the expected mechanism occurred, such as higher tensor-pipe utilization or a shift in stalls from dependency to memory.
  8. Record the decision. Write the result to benchmark.csv and candidates.jsonl. Promote only when the contract is met; otherwise record the regression and move to the next candidate.

Keep knowledge evidence separate from experimental fact. KernelWiki can show that a technique appeared in a specific source and point to an implementation. Only validation, benchmarks, and profiles in the task repository can establish that it fits the current kernel.

9. Installation and scope

The KDA repository organizes KernelWiki and the NCU report skill as submodules. The current README installs the complete workflow as follows:

git clone --recurse-submodules \
  https://github.com/mit-han-lab/kernel-design-agents.git
cd kernel-design-agents

mkdir -p ~/.claude/skills
ln -s "$(pwd)/skills/KernelWiki" ~/.claude/skills/KernelWiki
ln -s "$(pwd)/skills/ncu-report-skill" ~/.claude/skills/ncu-report-skill

KernelWiki can also be installed by itself:

git clone https://github.com/mit-han-lab/KernelWiki.git \
  ~/.claude/skills/KernelWiki

cd ~/.claude/skills/KernelWiki
python3 scripts/query.py --tag nvfp4 --type kernel --compact
python3 scripts/get_page.py kernel-flash-attention-4 --frontmatter-only

The repository's automatic registration instructions currently target Claude Code. With another coding agent, query.py, get_page.py, and grep_wiki.py remain ordinary Python scripts, but automatic skill discovery depends on the host's extension mechanism.

KernelWiki focuses on Blackwell and retains Hopper material relevant to Blackwell migration. General CUDA questions, host-framework integration, and distributed-system topics such as DeepEP, EPLB, and DualPipe are outside its scope. English is the canonical article language; CuTe DSL, CUDA C++, PTX, and Triton are first-class language entry points.

The knowledge base also has a time boundary. At the time of writing, its README says that upstream pull requests were audited through 2026-05-20, while documentation, release, and leaderboard snapshots were verified through 2026-08-18 UTC. Query results should be checked against the local CUDA, CUTLASS, and Triton versions. KDA describes itself as an early research prototype under active development, so its process is useful, but its directory layout and file formats should not be treated as stable APIs.
