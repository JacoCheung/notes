PyTorch record_stream 与 CUDA Storage 复用

CUDA kernel 排队后，Python 可以继续执行，Tensor 的语言层生命周期因此可能早于 GPU 对其 storage 的最后一次访问。record_stream 解决的是这段生命周期差异：它把 side stream 的使用记录交给 allocator，延迟显存复用，但不建立 stream 之间的执行顺序。

1. 语义边界

本文的 API 语义以 PyTorch 2.12 文档为准，allocator 实现以 PyTorch commit 9c603a7 为观察基准。event 队列和 block 回收的源码分析专指默认 native caching allocator 的普通 eager allocation。cudaMallocAsync、可插拔 allocator 与 CUDA Graph capture 使用不同或额外的控制路径。

tensor.record_stream(stream) 是 Tensor storage 的生命周期标记：它把指定 stream 上的 storage 使用记录交给 PyTorch CUDA caching allocator。Tensor 释放后，allocator 会同时参考 allocation stream 与这些 side stream 的执行进度，再决定显存何时可以复用。stream 之间的先后关系仍由 wait_stream 或 CUDA event 建立。

API约束对象作用边界
s2.wait_stream(s1)执行顺序。让 s2 等 s1 已经排队的工作。不延长 Tensor storage 的生命周期。
x.record_stream(s2)内存生命周期。告诉 allocator:释放 x 时也要考虑 s2。不让 s2 自动等待 s1。
跨 stream 使用同一个 Tensor 时,需要同时处理两类约束:wait_stream 负责读写顺序,record_stream 或手动 event / wait 负责 storage 生命周期。

2. Caching allocator 与 CUDA event

PyTorch 默认的 native CUDA allocator 是 caching allocator。指向某个 storage 的最后一个 Tensor 引用消失时，显存通常不会立即经过 cudaFree 归还给 CUDA，而是回到 allocator 的缓存池。CUDA kernel 异步执行，因此 Python 不再持有这块 storage 并不代表 GPU 已经停止访问它。

固定 commit 中，block 单独保存 allocation stream 和 stream_uses。recordStream() 会忽略 allocation stream，只把额外使用该 block 的 stream 写入 stream_uses。这是因为 allocator 的空闲池本身按 allocation stream 管理，同一 stream 上的旧使用和新使用已经由 stream 顺序约束。

下面的伪代码只保留普通 eager 路径。它对应的是固定 commit 的控制流，不代表所有 allocator backend 或 CUDA Graph capture 路径。

释放路径：为 side stream 记录 event

# 伪代码:对应普通 eager 路径

def deallocate(block):
    if not block.stream_uses:
        free_block(block)  # 进入 allocation stream 对应的空闲池
        return

    for stream in block.stream_uses:  # 只包含额外记录的 side streams
        event = cudaEventCreate()
        cudaEventRecord(event, stream)
        event_queues[stream].append((event, block))
        block.event_count += 1

    block.stream_uses.clear()  # event 完成前 block 不在空闲池

当 GPU 执行到 event 时，说明该 stream 上排在 event 之前的工作已经完成。释放路径是否直接 free_block 或调用 insert_events，见 block free 分支；逐 stream 创建并记录 event 的实现见 insert_events()。

分配路径：查询 event 完成状态

# 伪代码:处理每个 stream 的 event 队列

def process_events():
    for stream, queue in event_queues.items():
        while queue:
            event, block = queue[0]
            if cudaEventQuery(event) == cudaErrorNotReady:
                break  # 同一 stream 上后面的 event 不会先完成

            queue.pop(0)
            block.event_count -= 1
            if block.event_count == 0:
                free_block(block)

cudaEventQuery 是非阻塞查询。固定 commit 在普通分配开始时先调用 process_events()；当某个 block 的 event_count 降到零，才把它送回空闲池。具体查询与计数逻辑见 event processing 源码。CUDA Graph capture 期间不能照常执行 cudaEventQuery，因此该版本会采用延迟回收或 graph-aware reuse 路径。

3. record_stream 的语义

x.record_stream(s2) 向 allocator 记录 x 的 storage 正在被非 allocation stream s2 使用。下列伪代码给出这一语义近似:

# 语义近似,不是 PyTorch 的真实 Python 实现
x.storage.side_stream_uses.add(s2)

这样 x 释放时,allocator 会把 s2 上已经排队的工作纳入判断。所有被记录 side stream 的 event 完成后，这块显存才会进入 allocation stream 对应的空闲池。

这里描述的是 allocator 视角的 storage 生命周期。计算依赖需要由调用方通过 stream wait 或 event 单独表达。

4. 跨 stream 复用风险

x 在 s1 上产生,随后在 s2 上被 g(x) 异步使用:

s1 = torch.cuda.Stream()
s2 = torch.cuda.Stream()

with torch.cuda.stream(s1):
    x = f(a, b, c)      # x 的 storage 在 s1 上写入

# 计算依赖: s2 必须等 s1 写完 x
s2.wait_stream(s1)

with torch.cuda.stream(s2):
    y = g(x)            # g(x) 在 s2 上异步读 x

如果后面 x 的 Python 引用消失,例如 del x 或变量被覆盖,allocator 可能只知道 x 的创建 stream 是 s1。如果没有把 s2 记录进去,后续 s1 上的新分配就可能复用 x 原来的 storage:

# 假设这里 x 已经没有 Python 引用了

with torch.cuda.stream(s1):
    z = torch.rand(shape, device="cuda")  # 可能复用原来 x 的显存

此时 s2 上的 g(x) 可能尚未执行完，而 s1 上的新 rand 与它之间没有等待关系。两个 stream 并行推进时，新写入便可能覆盖 g(x) 仍在读取的显存。

同一 stream 的 FIFO 顺序保护

如果 f、g 和后续新分配都在 s1 上,CUDA stream 的 FIFO 顺序天然保证:

f 写 x  ->  g 读 x  ->  rand 写新内存

即使 allocator 复用了同一块显存,新的写入也会排在旧的读取之后。问题只在跨 stream 时出现,因为 s1 和 s2 是两条可以并行推进的队列。

5. 生命周期管理方式

写法 A:用 record_stream

s1 = torch.cuda.Stream()
s2 = torch.cuda.Stream()

with torch.cuda.stream(s1):
    x = f(a, b, c)

s2.wait_stream(s1)

with torch.cuda.stream(s2):
    y = g(x)

# 内存生命周期: 告诉 allocator s2 也使用了 x 的 storage
x.record_stream(s2)

这样即使 Python 侧 x 被释放,allocator 也会等 s2 上相关工作执行到释放时记录的 event 之后,才复用这块显存。

写法 B:手动同步回 allocation stream

with torch.cuda.stream(s1):
    x = f(a, b, c)

s2.wait_stream(s1)

with torch.cuda.stream(s2):
    y = g(x)

# 在释放 x 或允许 s1 复用它的 storage 前,
# 让创建 stream s1 等待 side stream s2。
s1.wait_stream(s2)

del x

这种写法由调用方显式管理生命周期。它更可控,但同步点放得过早会损失 overlap;放得过晚或遗漏同步,仍会留下数据竞争。

6. 与 wait_stream 的关系

仅调用 record_stream 不会建立计算依赖:

with torch.cuda.stream(s1):
    x = f(a, b, c)

with torch.cuda.stream(s2):
    y = g(x)

x.record_stream(s2)

这段代码只保护 storage 生命周期，没有规定 s2 何时开始读取。若 g(x) 在 f 完成写入之前启动，仍会读取未完成的数据。

两类约束分别对应不同 API:

  • s2.wait_stream(s1):保证 s2 读 x 之前,s1 已经写完。
  • x.record_stream(s2):保证 x 的 storage 不会在 s2 用完前被 allocator 复用。
wait_stream 约束执行顺序;record_stream 约束 storage 生命周期。

PyTorch record_stream and CUDA Storage Reuse

Python can continue after a CUDA kernel has been queued, so a tensor's language-level lifetime may end before the GPU's final access to its storage. record_stream addresses that lifetime gap. It reports side-stream use to the allocator and delays memory reuse, but it does not establish execution order between streams.

1. Semantic boundary

The API semantics in this article follow the PyTorch 2.12 documentation. Allocator details are observed at PyTorch commit 9c603a7. The event queues and block-reclamation path below apply specifically to ordinary eager allocation with the default native caching allocator. cudaMallocAsync, pluggable allocators, and CUDA Graph capture use different or additional control paths.

tensor.record_stream(stream) is a lifetime marker for tensor storage. It reports storage use on the specified stream to the PyTorch CUDA caching allocator. After the tensor is released, the allocator considers both the allocation stream and these side streams before making the block reusable. wait_stream or CUDA events establish ordering between streams.

APIConstraintBoundary
s2.wait_stream(s1)Execution order. Makes s2 wait for work already queued on s1.Does not extend the tensor storage lifetime.
x.record_stream(s2)Memory lifetime. Tells the allocator to consider s2 when x is freed.Does not make s2 wait for s1.
Cross-stream tensor use has two separate constraints: wait_stream orders reads and writes; record_stream or manual events / waits protect the storage lifetime.

2. Caching allocator and CUDA events

PyTorch's default native CUDA allocator caches allocations. When the last tensor reference to a storage disappears, its GPU memory normally returns to the allocator's cache instead of immediately passing through cudaFree. CUDA kernels execute asynchronously, so the absence of a Python reference does not mean the GPU has finished accessing that storage.

At the pinned commit, a block stores its allocation stream separately from stream_uses. recordStream() ignores the allocation stream and records only additional streams that used the block. The allocator's free pools are already stream-specific, so ordering on the allocation stream needs no extra event.

The following pseudocode retains only the ordinary eager path. It summarizes the pinned implementation rather than specifying every allocator backend or CUDA Graph capture path.

Deallocation path: record events on side streams

# Pseudocode: ordinary eager path

def deallocate(block):
    if not block.stream_uses:
        free_block(block)  # return to the allocation stream's free pool
        return

    for stream in block.stream_uses:  # recorded side streams only
        event = cudaEventCreate()
        cudaEventRecord(event, stream)
        event_queues[stream].append((event, block))
        block.event_count += 1

    block.stream_uses.clear()  # block stays out of the free pool

Once the GPU reaches the event, all earlier work on that stream has completed. The branch between direct free_block and insert_events is visible in the block free path; event creation and recording are in insert_events().

Allocation path: query event completion

# Pseudocode: process the per-stream event queues

def process_events():
    for stream, queue in event_queues.items():
        while queue:
            event, block = queue[0]
            if cudaEventQuery(event) == cudaErrorNotReady:
                break  # later events on this stream cannot be complete yet

            queue.pop(0)
            block.event_count -= 1
            if block.event_count == 0:
                free_block(block)

cudaEventQuery is non-blocking. At the pinned commit, an ordinary allocation invokes process_events() before searching the free pool. A block becomes free only when its event_count reaches zero; the query and counter logic are in the event processing source. CUDA Graph capture cannot run the same cudaEventQuery path, so this version defers reclamation or uses graph-aware reuse there.

3. record_stream semantics

x.record_stream(s2) reports that a non-allocation stream s2 is using the storage associated with x. The following pseudocode is a semantic approximation:

# Semantic approximation, not PyTorch's real Python implementation
x.storage.side_stream_uses.add(s2)

When x is freed, the allocator now accounts for queued work on s2. The block enters the allocation stream's free pool only after events for all recorded side streams have completed.

This rule describes storage lifetime from the allocator's perspective. The caller expresses compute dependencies separately with stream waits or events.

4. Cross-stream reuse hazard

Here x is produced on s1, then consumed asynchronously by g(x) on s2:

s1 = torch.cuda.Stream()
s2 = torch.cuda.Stream()

with torch.cuda.stream(s1):
    x = f(a, b, c)      # x's storage is written on s1

# Compute dependency: s2 must wait until s1 has written x
s2.wait_stream(s1)

with torch.cuda.stream(s2):
    y = g(x)            # g(x) reads x asynchronously on s2

If the Python reference to x later disappears, for example through del x or assignment overwrite, the allocator may only know that x was created on s1. Without recording s2, a later allocation on s1 may reuse x's old storage:

# Suppose x has no Python references now.

with torch.cuda.stream(s1):
    z = torch.rand(shape, device="cuda")  # may reuse x's old storage

At this point g(x) on s2 may still be running, while the new rand on s1 has no wait relationship with it. As the streams progress concurrently, the new writes may overwrite memory that g(x) is still reading.

FIFO ordering protects same-stream reuse

If f, g, and the later allocation all run on s1, the CUDA stream FIFO order guarantees:

f writes x  ->  g reads x  ->  rand writes new data

Even if the allocator reuses the same memory, the new write is queued after the old read. The problem appears with multiple streams, because s1 and s2 are independent queues that can make progress concurrently.

5. Lifetime management options

Pattern A: use record_stream

s1 = torch.cuda.Stream()
s2 = torch.cuda.Stream()

with torch.cuda.stream(s1):
    x = f(a, b, c)

s2.wait_stream(s1)

with torch.cuda.stream(s2):
    y = g(x)

# Memory lifetime: tell the allocator that s2 also used x's storage.
x.record_stream(s2)

Now, even if Python releases x, the allocator waits until the relevant work on s2 reaches the recorded event before reusing the storage.

Pattern B: synchronize back to the allocation stream manually

with torch.cuda.stream(s1):
    x = f(a, b, c)

s2.wait_stream(s1)

with torch.cuda.stream(s2):
    y = g(x)

# Before releasing x, or allowing s1 to reuse its storage,
# make the creation stream wait for the side stream.
s1.wait_stream(s2)

del x

This puts lifetime management in the caller's hands. It is more explicit, but the synchronization point matters: too early loses overlap; too late, or missing, leaves the race in place.

6. Relationship with wait_stream

record_stream by itself does not establish a compute dependency:

with torch.cuda.stream(s1):
    x = f(a, b, c)

with torch.cuda.stream(s2):
    y = g(x)

x.record_stream(s2)

This code protects only the storage lifetime; it leaves the start of s2's read unordered. If g(x) begins before f finishes writing, it can observe incomplete data.

The two constraints map to different APIs:

  • s2.wait_stream(s1): before s2 reads x, make sure s1 has finished writing it.
  • x.record_stream(s2): before allocator reuses x's storage, make sure s2 has finished using it.
wait_stream constrains execution order; record_stream constrains storage lifetime.
