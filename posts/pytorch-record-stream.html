PyTorch record_stream 与显存复用

PyTorch 的 CUDA caching allocator 会复用释放的显存。CUDA kernel 异步执行，一个 Tensor 若还在被另一条 stream 读取，它的显存可能在读完之前就分给了新 Tensor。本文说明 allocator 怎样判断显存可以复用、record_stream 改变了什么，以及改用 wait_stream 手动同步的取舍。

API 语义以 PyTorch 2.12 文档为准，allocator 实现以 commit 9c603a7 为观察基准。源码分析只针对默认 native caching allocator 的普通 eager 分配；cudaMallocAsync、可插拔 allocator 和 CUDA Graph capture 使用不同或额外的控制路径。

1. 跨 Stream 的提前复用

为了让通信、拷贝与计算重叠，常把一部分工作放到另一条 stream 上。下例中，x 在 s1 上产生，交给 s2 上的 g 读取：

s1 = torch.cuda.Stream()
s2 = torch.cuda.Stream()

with torch.cuda.stream(s1):
    x = f(a, b, c)      # x 的 storage 在 s1 上分配并写入

s2.wait_stream(s1)      # 计算依赖：s2 等 s1 写完 x

with torch.cuda.stream(s2):
    y = g(x)            # g(x) 在 s2 上异步读 x

del x                   # 最后一个 Python 引用消失（变量被覆盖同理）

with torch.cuda.stream(s1):
    z = torch.rand(shape, device="cuda")  # 可能复用 x 原来的显存

读写顺序没有问题：wait_stream 保证 g 读到的是 f 写完的结果。问题出在释放。del x 时，显存通常不经过 cudaFree，而是回到 allocator 的缓存池；allocator 只知道 x 在 s1 上分配，不知道 s2 也在用。CPU 发射 g 后立即返回，g 此时可能还没执行完。随后在 s1 上分配 z 时，allocator 可以把同一块显存交给它。s1 上的 rand 与 s2 上的 g 之间没有等待关系，新写入可能覆盖 g 正在读的数据。

如果 f、g、rand 都在 s1 上，同样的复用是安全的：stream 按 FIFO 执行，rand 的写入一定排在 g 的读取之后。问题只出现在跨 stream 时，因为两条 stream 是各自推进的队列。下文把 Tensor 分配时所在的 stream 称为分配 stream（这里是 s1），把其他使用它的 stream 称为 side stream（这里是 s2）。

2. Allocator 如何判断可复用

要避免上面的复用，allocator 必须知道 side stream 何时用完这块显存。它以 block 为单位管理显存，相关的是 block 的三个字段：stream 记录分配 stream，stream_uses 记录用过该 block 的 side stream，event_count 记录尚未完成的 event 数。

空闲池按分配 stream 分组，查找空闲块时只接受属于请求 stream 的块，所以 x 的显存只会被 s1 上的分配复用。同一 stream 上的新旧使用已由 FIFO 排序，allocator 因此不在分配 stream 上记录 event；recordStream() 也会忽略分配 stream，只把 side stream 写入 stream_uses。

释放时，stream_uses 决定 block 的去向：

# 伪代码：普通 eager 路径
def deallocate(block):
    if not block.stream_uses:
        free_block(block)               # 直接回到分配 stream 的空闲池
        return
    for stream in block.stream_uses:    # 只包含 side stream
        event = create_event()          # 实际从 event 池中取
        cudaEventRecord(event, stream)  # 排在该 stream 此刻已有的工作之后
        event_queues[stream].append((event, block))
        block.event_count += 1
    block.stream_uses.clear()           # event 完成前 block 不在空闲池

GPU 执行到 event，说明该 stream 上排在它之前的工作都已完成。是否插入 event 的判断见 block free 分支，逐 stream 记录 event 见 insert_events()。

普通分配开始时先调用 process_events()，再查找空闲块：

# 伪代码：每次分配开始时执行
def process_events():
    for stream, queue in event_queues.items():
        while queue:
            event, block = queue[0]
            if cudaEventQuery(event) == cudaErrorNotReady:
                break  # 同一 stream 上后面的 event 不会先完成
            queue.pop(0)
            block.event_count -= 1
            if block.event_count == 0:
                free_block(block)

普通路径下，event 在分配时才用非阻塞的 cudaEventQuery 检查，所以 block 的 event 全部完成后，要到下一次分配才回到分配 stream 的空闲池，见 event processing 源码。CUDA Graph capture 期间不能调用 cudaEventQuery，该版本会推迟到 capture 结束后回收，或在打开相应配置时走 graph-aware 复用路径。

回到第 1 节的例子：del x 时 stream_uses 为空，block 直接回到 s1 的空闲池，所以 z 能拿到它。

3. record_stream 改变了什么

要让 z 拿不到这块显存，释放时 stream_uses 就不能为空。x.record_stream(s2) 把 s2 加入 x 所在 block 的 stream_uses，在例子的 del x 之前加上它：

x.record_stream(s2)     # 告诉 allocator：s2 也使用了 x 的 storage
del x

释放时，allocator 在 s2 上记录一个排在 g 之后的 event。在某次分配发现这个 event 完成之前，block 不会回到 s1 的空闲池，因此 z 这样的分配只有在 g 结束后才可能拿到这块显存。event 在释放时记录，所以受保护的是释放那一刻已排入 s2 的工作；record_stream 在 g 之前还是之后调用都一样，只要在释放之前。

record_stream 只约束 storage 的生命周期，不建立执行顺序。去掉例子中的 s2.wait_stream(s1)、只保留 record_stream，显存不会被提前复用，但 g 可能在 f 写完之前就开始读。两类约束要分别处理：

API约束不负责
s2.wait_stream(s1)执行顺序：s2 等 s1 已排队的工作延长 storage 的生命周期
x.record_stream(s2)内存生命周期：释放 x 时也考虑 s2让 s2 等待 s1

4. 在分配 Stream 上等待

record_stream 面向的场景是：库函数在 side stream 上产出 Tensor，使用者不必关心 stream。代价是轮询：block 何时回池取决于之后每次分配时 GPU 的进度，显存复用可能每次运行都不同。PyTorch 文档因此建议，掌握 Tensor 完整生命周期的调用方可以考虑改为手动同步。

由于 x 的显存只会被 s1 上的分配复用，只要释放前让 s1 等 s2，之后 s1 上的所有工作，包括写入这块显存的工作，都会排在 g 之后。把例子中的 del x 换成：

s1.wait_stream(s2)      # 释放 x 之前，让分配 stream 等 side stream
del x

这时 del x 走直接回池的分支，不涉及 event。CPU 侧可能已经把这块显存分给新 Tensor，而旧 kernel 仍在运行；这不影响正确性，因为新 Tensor 的操作也在 s1 上，会等旧操作完成。

手动同步的代价是要选等待的位置：应放在预计 s2 已完成的地方，文档建议借助 profiler 时间线来找。放得太早，例如紧跟在 g 之后，s1 会立即停下等 g，side stream 失去意义；放得太晚，x 多存活一段时间，多占显存。等待不能移到 del x 之后：只要中间有 s1 上的分配拿到这块显存，就回到第 1 节的竞争。

PyTorch record_stream and memory reuse

PyTorch's CUDA caching allocator reuses freed memory. Because kernels run asynchronously, a tensor still being read on another stream can lose its memory to a new tensor before the read finishes. This article covers how the allocator decides memory is reusable, what record_stream changes, and the trade-offs of synchronizing with wait_stream instead.

API semantics follow the PyTorch 2.12 documentation and allocator details follow commit 9c603a7, for ordinary eager allocation with the default native caching allocator only; cudaMallocAsync, pluggable allocators, and CUDA Graph capture take different or additional paths.

1. Premature reuse across streams

To overlap communication or copies with computation, work is often moved to a second stream. Below, x is produced on s1 and read by g on s2:

s1 = torch.cuda.Stream()
s2 = torch.cuda.Stream()

with torch.cuda.stream(s1):
    x = f(a, b, c)      # x's storage is allocated and written on s1

s2.wait_stream(s1)      # compute dependency: s2 waits until s1 has written x

with torch.cuda.stream(s2):
    y = g(x)            # g(x) reads x asynchronously on s2

del x                   # last Python reference is gone (reassignment works the same way)

with torch.cuda.stream(s1):
    z = torch.rand(shape, device="cuda")  # may reuse x's old storage

The read/write order is fine: wait_stream ensures g sees what f wrote. The free is the problem. At del x the memory normally returns to the allocator's cache rather than going through cudaFree, and the allocator knows only that x was allocated on s1, not that s2 uses it. The CPU returns as soon as g is launched, so g may still be running when z is allocated on s1 and handed the same memory. Nothing orders rand on s1 after g on s2, so the new writes can overwrite data g is still reading.

Had f, g, and rand all run on s1, the reuse would be safe: a stream runs in FIFO order, so the write by rand would queue behind the read by g. The hazard exists only across streams, because streams advance independently. From here on, the stream a tensor was allocated on is its allocation stream (s1 here); any other stream using it is a side stream (s2 here).

2. How the allocator decides reuse

To prevent that reuse, the allocator must know when the side stream is done with the memory. It manages memory in blocks and tracks this with three block fields: stream records the allocation stream, stream_uses the side streams that used the block, and event_count the events still outstanding.

Free pools are grouped by allocation stream: the free-block search accepts only blocks of the requesting stream, so x's memory can be reused only by allocations on s1. Old and new uses on that stream are already ordered by FIFO, so the allocator records no event on the allocation stream; recordStream() ignores it and adds only side streams to stream_uses.

On free, stream_uses decides where the block goes:

# Pseudocode: ordinary eager path
def deallocate(block):
    if not block.stream_uses:
        free_block(block)               # straight back to the allocation stream's free pool
        return
    for stream in block.stream_uses:    # side streams only
        event = create_event()          # the real code takes one from an event pool
        cudaEventRecord(event, stream)  # queued after the work already on that stream
        event_queues[stream].append((event, block))
        block.event_count += 1
    block.stream_uses.clear()           # block stays out of the free pool

Once the GPU reaches an event, all earlier work on that stream has completed. The branch itself is in the block free path; per-stream event recording is in insert_events().

An ordinary allocation first calls process_events() and only then searches the free pool:

# Pseudocode: runs at the start of every allocation
def process_events():
    for stream, queue in event_queues.items():
        while queue:
            event, block = queue[0]
            if cudaEventQuery(event) == cudaErrorNotReady:
                break  # later events on this stream cannot be complete yet
            queue.pop(0)
            block.event_count -= 1
            if block.event_count == 0:
                free_block(block)

On the ordinary path, events are checked (with the non-blocking cudaEventQuery) only at allocation time, so a block whose events have all completed returns to the free pool at the next allocation; see the event processing source. CUDA Graph capture cannot call cudaEventQuery, so this version defers reclamation until capture ends, or uses a graph-aware reuse path when the corresponding option is enabled.

Back to the example in Section 1: at del x, stream_uses is empty, so the block goes straight back to s1's free pool, and z can get it.

3. What record_stream changes

To keep z away from that memory, stream_uses must be non-empty at the free. x.record_stream(s2) adds s2 to the stream_uses of x's block. Add it before del x in the example:

x.record_stream(s2)     # tell the allocator that s2 also used x's storage
del x

At the free, the allocator records an event on s2, queued after g. Until a later allocation finds that event complete, the block stays out of s1's free pool, so an allocation such as z can get the memory only after g has finished. Because the event is recorded at the free, it covers the work queued on s2 at that moment; whether record_stream is called before or after g does not matter, as long as it precedes the free.

record_stream constrains only storage lifetime; it creates no execution order. If the example dropped s2.wait_stream(s1) and kept only record_stream, the memory would not be reused too early, but g could start reading before f finished writing. The two constraints need separate APIs:

APIConstrainsDoes not
s2.wait_stream(s1)Execution order: s2 waits for work already queued on s1Extend the storage lifetime
x.record_stream(s2)Memory lifetime: freeing x also accounts for s2Make s2 wait for s1

4. Waiting on the allocation stream

record_stream is meant for cases like a library function that hands a side-stream tensor to users who should not have to think about streams. The price is polling: when the block returns depends on GPU progress at each later allocation, so memory reuse can differ from run to run. The PyTorch documentation therefore suggests that callers who manage a tensor's full lifetime consider synchronizing manually instead.

Since x's memory can be reused only by allocations on s1, making s1 wait for s2 before the free puts all later work on s1, including any write into that memory, behind g. Replace del x in the example with:

s1.wait_stream(s2)      # before freeing x, make the allocation stream wait for the side stream
del x

del x now takes the direct path back to the pool, with no events. The CPU may hand the memory to a new tensor while the old kernels are still running; that is still correct, because the new tensor's work is also on s1 and waits for them.

The cost of manual synchronization is choosing where the wait goes. It belongs where s2 is expected to have finished, which the documentation suggests finding with a profiler timeline. Too early, say right after g, it stalls s1 on g and the side stream gains nothing; too late, x stays alive and holds memory longer. It cannot move past del x: if an allocation on s1 gets the memory in between, the race from Section 1 returns.
