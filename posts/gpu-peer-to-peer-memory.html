GPU P2P 显存访问

GPU P2P（Peer-to-Peer）让一张 GPU 的 kernel 通过有效映射，直接读写另一张 GPU 的显存。源数据可以留在原来的 GPU 上，消费者使用普通指针访问它，省去经 CPU 内存中转的数据拷贝。这条路径贯穿 CUDA 的访问授权、GPU 地址转换、NCCL Device API，以及 NVLink／PCIe 互联：驱动建立映射，GPU 硬件执行访问，通信库提供 peer 指针与同步接口。

同进程与节点内 IPC 示例采用 Linux 64 位、同一主机内两张支持 P2P 的 GPU 与 cudaMalloc 分配；跨节点示例采用 VMM fabric handle。P100 的 GP100 页表格式用于说明地址转换；NCCL LSA 示例采用 2.32.3（12df1a11afad）的接口、ncclMemAlloc 分配和支持 Device API 的设备。

在 PyTorch 中建立同类 peer 映射并编写计算 kernel，可接着阅读《PyTorch 对称内存与 GPU P2P 访问》第三章：其中逐项对照本章的 CUDA IPC、VMM 与 fabric handle，并给出双卡 Triton 和 MegaMoE 场景。

1. Kernel 与访问映射

同一条 load

设 GPU 1 持有输入，GPU 0 执行计算。下面的 kernel 将输入加一后写入 GPU 0 的本地输出。src 可以指向本地显存，也可以指向已映射、已授权的 peer 显存：

extern "C" __global__ void peer_load(const float* src, float* dst, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        float value = src[i];  // src can refer to local or mapped peer memory.
        dst[i] = value + 1.0f;
    }
}

Kernel 程序员写的仍是 src[i]。同一个已编译 kernel 可以接收这两种地址，指令本身不携带“GPU 1”这样的 CUDA 设备编号。以本文源文件和 CUDA 12.4.131、-O3 -arch=sm_60 的实际编译结果为例：

// PTX: src[i] and the result store
ld.global.f32  %f1, [%rd5];
add.f32        %f2, %f1, 0f3F800000;
st.global.f32  [%rd7], %f2;

// SASS: the source read
LDG.E R2, [R2];

这次全局读取的目标由地址翻译与硬件路由决定，kernel 使用普通 load 即可完成 peer 读取。数据宽度、向量化或缓存提示变化时，编译器也可能选择其他 load 形式。PTX 的 ld 指令 · CUDA peer memory access

同进程映射

访问方向写作 reader → owner：GPU 0 读取 GPU 1，查询就是 cudaDeviceCanAccessPeer(&ok, 0, 1)。查询成功后，在 GPU 0 为当前设备时调用 cudaDeviceEnablePeerAccess(1, 0)。第二个参数是保留 flags，必须为 0。授权是单向的；反向访问需要单独开启。Peer access API

以下片段假设 P2P 能力查询已通过，n 为元素数，bytes = n * sizeof(float)。正文保留关键调用，初始化、错误处理、同步和释放见完整示例。

cudaSetDevice(1);  // Owner
float* remote;
cudaMalloc(&remote, bytes);

cudaSetDevice(0);  // Reader
cudaDeviceEnablePeerAccess(1, 0);
float* local;
cudaMalloc(&local, bytes);

peer_load<<<(n + 255) / 256, 256>>>(remote, local, n);

同一进程的 UVA 让这个分配使用的指针值可直接传给另一张 GPU 的 kernel。UVA 提供统一的虚拟地址组织；P2P 授权提供实际访问能力。示例的 remote 分配始终位于 owner GPU，未使用 Unified Memory 的迁移机制。统一地址与 peer 访问

节点内跨进程映射

UVA 统一的是单个进程内的虚拟地址空间。跨进程时，各进程的 GPU 虚拟地址空间和页表映射各自独立，需要以 CUDA IPC 句柄为中介，将 peer 的显存分配映射到本进程的地址空间。Owner 将分配导出为 cudaIpcMemHandle_t，经普通 OS IPC 传给 Reader；Reader 导入后得到本进程可用的指针。两个指针通过各自的映射访问同一块物理显存。UVA · CUDA IPC

send_handle 和 receive_handle 是示例自定义的 CPU 进程间通信函数。send_handle 将句柄长度和 cudaIpcMemHandle_t 的原始字节写入标准输出；run_ipc.py 经管道转交给 Reader 的标准输入，再由 receive_handle 读回句柄。管道传递的是分配句柄，显存数据由 peer_load 通过 GPU 互联读取。

Owner · GPU 1分配并导出
cudaSetDevice(1);
float* allocation;
cudaMalloc(&allocation, bytes);

cudaIpcMemHandle_t handle;
cudaIpcGetMemHandle(
    &handle, allocation);
send_handle(handle);
Reader · GPU 0导入并读取
cudaSetDevice(0);
auto handle = receive_handle();
void* mapping;
cudaIpcOpenMemHandle(
    &mapping, handle,
    cudaIpcMemLazyEnablePeerAccess);

float* local;
cudaMalloc(&local, bytes);
peer_load<<<(n + 255) / 256, 256>>>(
    static_cast<float*>(mapping),
    local, n);

Reader 调用 cudaIpcOpenMemHandle 建立映射；cudaIpcMemLazyEnablePeerAccess 允许导入操作按需尝试开启设备间访问。使用完成后，Reader 用 cudaIpcCloseMemHandle 关闭映射，Owner 负责释放分配。IPC 导入、地址与生命周期约束

跨节点映射

跨节点时，各节点有独立的 OS、驱动实例和进程地址空间，共享分配需要跨越这些边界识别。cudaIpcMemHandle_t 用于同一节点内的进程间共享；在支持 Multi-Node NVLink 的系统中，VMM 使用 CU_MEM_HANDLE_TYPE_FABRIC 导出 CUmemFabricHandle，让另一节点的驱动导入同一块物理显存，并将它映射到接收进程的 GPU 虚拟地址空间。多节点 CUDA 编程模型 · VMM fabric handle

这条路径要求 GPU 位于可互访的 NVLink fabric 内，节点已配置同一 IMEX domain，导出与导入进程有权使用同一 IMEX channel。IMEX 服务负责跨 OS 协调内存导入、导出及生命周期；驱动建立映射后，GPU 的 load／store 经 NVLink fabric 访问远端显存。IMEX 的职责 · IMEX channel 与访问权限

下面保留导出与导入的关键调用，使用 CUDA 12.4 起提供的 fabric handle。两端已初始化各自的 CUDA context，并确认 CU_DEVICE_ATTRIBUTE_HANDLE_TYPE_FABRIC_SUPPORTED。ownerDevice 与 readerDevice 分别是各自节点上的本地设备编号；bytes 按 cuMemGetAllocationGranularity 查询的分配粒度对齐。Reader 的 local 是预先分配的本地输出，n 是双方约定的 float 元素数。

Owner · Node A分配并导出
CUmemAllocationProp prop{};
prop.type = CU_MEM_ALLOCATION_TYPE_PINNED;
prop.location = {
    CU_MEM_LOCATION_TYPE_DEVICE,
    ownerDevice};
prop.requestedHandleTypes =
    CU_MEM_HANDLE_TYPE_FABRIC;

CUmemGenericAllocationHandle alloc;
cuMemCreate(&alloc, bytes, &prop, 0);

CUmemFabricHandle fabric;
cuMemExportToShareableHandle(
    &fabric, alloc,
    CU_MEM_HANDLE_TYPE_FABRIC, 0);
send_fabric(fabric, bytes);
Reader · Node B导入并读取
CUmemFabricHandle fabric;
size_t bytes;
receive_fabric(fabric, bytes);

CUmemGenericAllocationHandle imported;
cuMemImportFromShareableHandle(
    &imported, &fabric,
    CU_MEM_HANDLE_TYPE_FABRIC);

CUdeviceptr peerVA;
cuMemAddressReserve(
    &peerVA, bytes, 0, 0, 0);
cuMemMap(peerVA, bytes, 0, imported, 0);
CUmemAccessDesc access{};
access.location = {
    CU_MEM_LOCATION_TYPE_DEVICE,
    readerDevice};
access.flags =
    CU_MEM_ACCESS_FLAGS_PROT_READ;
cuMemSetAccess(peerVA, bytes, &access, 1);

auto src =
    reinterpret_cast<const float*>(
        peerVA);
peer_load<<<(n + 255) / 256, 256>>>(
    src, local, n);

send_fabric／receive_fabric 表示应用自定义的 CPU 通信：用 TCP socket 或 MPI 传递 CUmemFabricHandle 的字节和分配大小。Owner 的 alloc 与 Reader 的 imported 是各自进程中的 VMM allocation handle；peerVA 才是 Reader 保留并映射后供 kernel 使用的地址。cuMemSetAccess 为本地 Reader GPU 授予读权限。导出、导入、映射与权限 API

Owner 初始化数据时，也需为 alloc 保留地址、建立映射并授予本地写权限。初始化完成后通知 Reader 就绪，再执行读取；使用结束后，两端等待相关 GPU 操作完成，依次解除各自的映射、释放地址区间和 allocation handle（cuMemUnmap、cuMemAddressFree、cuMemRelease）。句柄传递只完成共享分配的建立，数据就绪与使用结束仍由应用协调。VMM 资源生命周期

同步与权限

映射建立后，程序仍需保证生产者和消费者的执行顺序。可下载的完整示例使用 host 等待：Owner 初始化完成后发布句柄，Reader 的 kernel 完成并关闭映射后发送 ACK，Owner 收到 ACK 后才能安全复用或释放源内存。同进程也可以用跨设备的 cudaStreamWaitEvent 建立 GPU 依赖；节点内跨进程可使用可导出的 CUDA event。跨设备 event 等待 · IPC event

访问授权随分配方式变化：cudaMalloc 的 peer access 由设备间授权或 legacy IPC 导入建立；VMM 分配通过 cuMemSetAccess 授予指定设备访问权；stream-ordered memory pool 也有单独的访问配置。可访问性、读写权限和执行顺序需要分别满足。VMM 接口 · Memory pool 访问接口

2. P100 的地址转换

驱动配置与硬件执行

驱动在映射建立阶段验证目标分配与访问能力，建立虚拟地址到目标内存的映射，并维护 peer 关系、权限与生命周期。cudaDeviceEnablePeerAccess、IPC 导入和 VMM 是不同的 API 入口，具体调用链取决于驱动实现。

映射有效后，SM 发出 global load。GPU 的地址转换硬件使用 TLB 中的翻译结果，或在缺失时查页表，得到目标地址及其属性；互联硬件据此处理 peer 请求并返回数据。正常的已映射访问无需 CPU 驱动逐条介入。结合公开 PTE 格式，可以将这条路径概括为：

CPU / driver: allocation → peer mapping + access permissions
                                    ↓
GPU SM: load VA → address translation → aperture + target address
                                       ├─ local → local memory path
                                       └─ peer  → peer route → remote memory

这是 API 语义与硬件格式支持的机制解释，省略了具体缓存、请求合并和互联内部流水级。下面的 GP100 字段给出了“local 或 peer”如何进入地址翻译结果的公开证据。Pascal MMU Format Changes，第 4 页

PTE 中的目标信息

P100 使用 GP100。NVIDIA 公开的 Pascal MMU 文档描述了最多 49 位的虚拟地址和五级页表格式。这里取 VER2 格式、4 KiB 普通页；GPU 页表头文件同时含有旧格式定义，解读时应使用 NV_MMU_VER2_PTE_* 这一组位位置。GP100 MMU 文档 · GP100 VER2 PTE 定义

文档说 Peer ID 与 PA[39:37] 复用，而头文件把它定位到 PTE[35:33]。两者采用不同的位编号：前者编号物理地址，后者编号编码后的 PTE。页基址省去低 12 位，再从 PTE 的 bit 8 开始存放，所以这些字段相差 4 位。地址字段与 ADDRESS_SHIFT

Peer ID 是硬件映射中的 peer 编号，与 CUDA ordinal、NCCL rank 属于不同的编号体系。具体对应关系由驱动建立。公开驱动中的 kbusGetNvlinkP2PPeerId_GP100 根据拓扑、已有映射和保留 peer slot 取得编号。Peer ID 分配代码

一个编码例子

假设页基址为 0x12345000，目标是 peer slot 3，页内偏移为 0x80。仅设置 Valid、Aperture、Peer ID 和页基址，可写出这个教学用编码：

PTE = ((0x12345000 >> 12) << 8)
    | (3 << 33)   # Peer ID
    | (1 << 1)    # Aperture = peer
    | 1            # Valid
    = 0x0000000601234503

target = peer slot 3, address 0x12345000 + 0x80
PTE[35:33]011 · ID 3
PTE[32:8] = PA[36:12]0x12345
PTE[2:1]01 · peer

PTE = 0x0000000601234503

4 KiB 页，页基址固定为 0x12345000，Valid=1，其余展示外字段设为 0。这里只计算教学用位模式，不读取或修改 GPU 页表。

Aperture 决定目标类别，页内偏移决定该页内的字节位置。上例只编码了目标与有效位；完整 PTE 还需按实际映射配置缓存、内存布局等属性。三位 Peer ID 属于 GP100 格式，现代 GPU 的格式和可寻址范围需按相应硬件资料解读。

3. NCCL Device API LSA

NCCL Device API 将 peer 显存访问开放给用户自己的 CUDA kernel。LSA（Load/Store Accessible）使用 CUDA P2P，支持具有 P2P 连通性的 NVLink 或 PCIe 设备。Host 负责建立 communicator 和内存窗口，kernel 通过窗口取得 peer 指针，再执行普通 load／store。Device API 从 NCCL 2.28 开始提供，本节采用 2.32.3（12df1a11afad）的接口与源码。Device API 使用指南

LSA team 与窗口

LSA team 是可以通过 load／store 相互访问的一组 rank。devComm.lsaRank 表示自己在该 team 中的编号，devComm.lsaSize 表示 team 大小。传给 LSA 接口的是 team 内的 rank，和 CUDA 设备编号属于不同的编号体系。ncclDevComm 字段

窗口 ncclWindow_t 把各 rank 注册的 buffer 组织起来，供 kernel 按“窗口、peer、偏移”寻址。每个 rank 仍拥有自己的物理分配；窗口注册负责建立 peer 映射。下面用两个 rank 演示：二者属于同一个 LSA team，各自读取对方的输入，加一后写入本地输出。输入在 kernel 执行期间保持不变。窗口注册

Host 初始化

每个 rank 的进程或线程先绑定本地 GPU。Rank 0 调用 ncclGetUniqueId 生成 id，通过已有的 CPU 通信方式分发；随后各 rank 执行下面的初始化。继续注册窗口前，检查 props.deviceApiSupport 为 true，并且 props.nLsaTeams == 1，确保这个两 rank 示例中的双方能直接互访。官方示例的能力检查

#include <nccl.h>
#include <nccl_device.h>

cudaSetDevice(localDevice);
ncclComm_t comm;
ncclCommInitRank(&comm, 2, id, rank);

ncclCommProperties_t props = NCCL_COMM_PROPERTIES_INITIALIZER;
ncclCommQueryProperties(comm, &props);
// Required: props.deviceApiSupport && props.nLsaTeams == 1

输入用 ncclMemAlloc 分配，再注册为对称窗口。窗口要求使用支持的 VMM 分配或 NCCL 分配器。ncclCommWindowRegister 是 collective 调用，所有 rank 都要参与；本例按相同顺序注册同样大小的输入。输出仅由本地 GPU 写入，因此用普通 cudaMalloc 分配即可。分配器要求 · 窗口注册 API

size_t bytes = count * sizeof(float);
void* input;
ncclMemAlloc(&input, bytes);

ncclWindow_t win;
ncclCommWindowRegister(
    comm, input, bytes, &win, NCCL_WIN_COLL_SYMMETRIC);

float* output;
cudaMalloc(&output, bytes);  // Used only by this GPU

接着创建 ncclDevComm，为 kernel 预留 barrier 资源。本例启动 4 个 CTA，每个 CTA 使用一个 barrier，因此将 lsaBarrierCount 设为 4。ncclDevCommCreate 是 host 侧 collective 调用，返回的通信描述可以按值传入 kernel。设备通信器与资源需求

constexpr int nCTAs = 4;
constexpr int nThreads = 256;
ncclDevCommRequirements reqs = NCCL_DEV_COMM_REQUIREMENTS_INITIALIZER;
reqs.lsaBarrierCount = nCTAs;

ncclDevComm devComm;
ncclDevCommCreate(comm, &reqs, &devComm);

如果同一线程管理多张 GPU，应把各 rank 的 collective 初始化、窗口注册和设备通信器创建分别放进对应的 ncclGroupStart／ncclGroupEnd 中，等 group 结束后再使用返回的对象。设备通信器的 group 语义 · 窗口的 group 语义

Kernel 访问

ncclGetLsaPointer(win, offset, peer) 返回当前 GPU 可访问的 peer 指针，其中 offset 的单位是字节，peer 是 LSA team 内的 rank。本例从窗口起点读取，所以传入 0；随后 src[i] 按 float 元素索引。LSA 指针接口

__global__ void lsa_peer_load(
    ncclDevComm devComm, ncclWindow_t win,
    float* output, size_t count) {
    ncclLsaBarrierSession<ncclCoopCta> bar{
        ncclCoopCta(), devComm, ncclTeamTagLsa(), blockIdx.x};
    bar.sync(ncclCoopCta(), cuda::memory_order_acquire);

    int peer = (devComm.lsaRank + 1) % devComm.lsaSize;
    const float* src = static_cast<const float*>(
        ncclGetLsaPointer(win, 0, peer));

    for (size_t i = blockIdx.x * blockDim.x + threadIdx.x;
         i < count; i += blockDim.x * gridDim.x) {
        output[i] = src[i] + 1.0f;
    }

    bar.sync(ncclCoopCta(), cuda::memory_order_release);
}

两个 rank 中，(devComm.lsaRank + 1) % devComm.lsaSize 恰好选中对方。ncclGetLsaPointer 的源码根据窗口中的 peer 映射基址、stride 和字节偏移计算地址；数据读取发生在下一步的 src[i]。这里沿用了第一章的普通 load，只是获取 peer 指针的工作交给了 NCCL。ncclGetLsaPointer 实现

LSA rank本地输入预期本地输出
0[0, 1, 2, 3][101, 102, 103, 104]
1[100, 101, 102, 103][1, 2, 3, 4]

同步与执行

两个 rank 都在各自的 stream 中完成输入初始化，再以相同的 grid 和 block 配置启动 kernel：

lsa_peer_load<<<nCTAs, nThreads, 0, stream>>>(
    devComm, win, output, count);

入口 barrier 使用 acquire 语义，等待 team 中对应 CTA 到达后再读取 peer 数据；出口 barrier 使用 release 语义，等待对应 CTA 完成这一轮访问。它们沿用官方 LSA 示例的同步方式。ncclCoopCta() 表示整个 CTA 参与，blockIdx.x 选择这一组对应 CTA 使用的 barrier。官方 kernel · LSA barrier 实现

每个 CTA 的所有线程都必须执行两次 barrier，包括没有分到数据的线程。因此，越界判断放在循环条件中，线程不能在 barrier 前提前返回。不同 CTA 使用不同的 barrier 编号，各 rank 对同一编号的调用顺序必须匹配；并发 kernel 也应使用各自独立的 barrier 资源。Barrier session 的参与范围

资源释放

所有使用这些资源的 kernel 完成后，销毁设备通信器、注销窗口，再释放分配和 host communicator。窗口与通信器可以在多次 kernel 调用间复用，输入 buffer 的复用仍需等待 peer 读取结束。设备通信器生命周期 · 窗口生命周期

// After all kernels using these resources have completed:
ncclDevCommDestroy(comm, &devComm);
ncclCommWindowDeregister(comm, win);
ncclMemFree(input);
cudaFree(output);
ncclCommDestroy(comm);

官方完整 LSA 示例包含 communicator 启动、输入初始化、结果校验和清理。它演示 AllReduce，本节将数据操作简化为 peer 读取与加一，保留相同的窗口和 barrier 使用流程。

4. NVLink 与 PCIe

物理路径

P2P 描述 GPU 间直接访问内存的能力，实际请求可以走 PCIe、直连 NVLink，或由 NVSwitch 转发的 NVLink fabric。NVSwitch 是交换芯片，端点仍然是持有内存和发起访问的 GPU。

PCIe P2P 可能经过 PCIe switch 或平台的 root complex；是否可用取决于拓扑与系统配置。直接访问的 payload 无需在 CPU DRAM 建立中转副本。NVLink／NVSwitch 则提供另外的 GPU 互联路径。CUDA P2P 的拓扑条件 · NVSwitch 软件与硬件结构

链路选择与路由

应用通常指定要访问哪张 GPU 的分配；CUDA 的 peer-access API 没有“这一次 load 走哪根 NVLink”的参数。Pascal Tuning Guide 明确说明：可用 NVLink 连接端点间的传输自动经 NVLink 路由。Peer 映射和系统路由配置将目标与可用链路关联起来，GPU 在执行访问时使用这套配置。NVLink 的透明路由

GPU peer-to-peer memory access

GPU peer-to-peer access lets a kernel address another GPU's device memory through an authorized mapping. The producer's data can stay on its GPU while a consumer reads it through an ordinary pointer, avoiding a staging copy through CPU memory. This connects CUDA access control, GPU address translation, the NCCL Device API, and NVLink or PCIe: the driver establishes mappings, hardware executes accesses, and the communication library provides peer pointers and synchronization interfaces.

The same-process and intra-node IPC examples use 64-bit Linux, two P2P-capable GPUs in one host, and cudaMalloc allocations; the cross-node example uses VMM fabric handles. P100's GP100 page-table format illustrates address translation. The NCCL LSA example uses version 2.32.3, commit 12df1a11afad, ncclMemAlloc allocations, and devices that support the Device API.

For PyTorch peer mappings and custom compute kernels, see PyTorch Symmetric Memory and GPU P2P Access, chapter 3, which cross-references this article’s CUDA IPC, VMM, and fabric-handle paths and includes Triton and MegaMoE examples.

1. Kernels and access mappings

The same load instruction

GPU 1 owns the input; GPU 0 runs a kernel that adds one and stores into its local output. The source may be local memory or authorized, mapped peer memory:

extern "C" __global__ void peer_load(const float* src, float* dst, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i < n) {
        float value = src[i];  // src can refer to local or mapped peer memory.
        dst[i] = value + 1.0f;
    }
}

The programmer writes src[i] in either case. The same compiled kernel accepts either pointer; its instruction does not encode a CUDA device ordinal. Compiling this source with CUDA 12.4.131 and -O3 -arch=sm_60 produced:

// PTX
ld.global.f32  %f1, [%rd5];
add.f32        %f2, %f1, 0f3F800000;
st.global.f32  [%rd7], %f2;

// SASS source read
LDG.E R2, [R2];

Translation and hardware routing determine this load's destination, so an ordinary load suffices for peer access. Changes in data width, vectorization, or cache hints can produce other load forms. PTX ld · CUDA peer access

One process, two GPUs

Express access as reader → owner. GPU 0 reading GPU 1 queries cudaDeviceCanAccessPeer(&ok, 0, 1), then calls cudaDeviceEnablePeerAccess(1, 0) with GPU 0 current. The second argument is reserved flags and must be zero. Access is directional; the reverse direction requires its own enable call. Peer access API

The snippets assume a successful P2P capability check, with n elements and bytes = n * sizeof(float). They show the essential calls; initialization, error handling, synchronization, and cleanup are in the complete examples.

cudaSetDevice(1);  // Owner
float* remote;
cudaMalloc(&remote, bytes);

cudaSetDevice(0);  // Reader
cudaDeviceEnablePeerAccess(1, 0);
float* local;
cudaMalloc(&local, bytes);

peer_load<<<(n + 255) / 256, 256>>>(remote, local, n);

Within this process, UVA permits passing the allocation's pointer to the other GPU. Address-space organization and access authorization are separate requirements. The allocation stays on its owner; this example does not use managed-memory migration. Unified addresses and peer access

Intra-node, cross-process mappings

UVA unifies virtual addressing within a single process. Across processes, each process has its own GPU virtual address space and page-table mappings. A CUDA IPC handle lets the receiving process map the peer's allocation into its own address space. The owner exports the allocation as a cudaIpcMemHandle_t and passes it through OS IPC; the reader imports it to obtain a pointer valid in its process. The two pointers access the same physical allocation through their respective mappings. UVA · CUDA IPC

Cross-node mappings

Nodes have separate OS instances, GPU drivers, and process address spaces. Sharing an allocation requires a handle that identifies it across those boundaries. cudaIpcMemHandle_t supports sharing between processes on one node. On Multi-Node NVLink systems, VMM exports a CUmemFabricHandle using CU_MEM_HANDLE_TYPE_FABRIC. Another node's driver imports the allocation and maps the same physical GPU memory into the receiving process's GPU virtual address space. Multi-node CUDA model · VMM fabric handles

This path requires reachable GPUs within an NVLink fabric, nodes configured in one IMEX domain, and exporter and importer access to the same IMEX channel. IMEX coordinates memory import, export, and lifetime across OS instances. Once the drivers establish the mappings, GPU loads and stores access remote memory over the NVLink fabric. IMEX responsibilities · IMEX channels and permissions

send_fabric and receive_fabric represent application CPU communication: a TCP socket or MPI transfers the CUmemFabricHandle bytes and allocation size. The owner's alloc and the reader's imported are VMM allocation handles local to their processes. peerVA is the address reserved and mapped by the reader for its kernel; cuMemSetAccess grants the reader's local GPU read permission. Export, import, mapping, and access APIs

To initialize the data, the owner also reserves an address range, maps alloc, and grants local write access. It signals readiness after initialization completes, allowing the reader to start. After the GPU operations finish, both sides remove their mappings and release their address reservations and allocation handles with cuMemUnmap, cuMemAddressFree, and cuMemRelease. The application coordinates data readiness and completion separately from sharing the allocation handle. VMM resource lifetime

Ordering and permissions

After establishing a mapping, the application must still order producer and consumer execution. The downloadable examples use host waits: the owner publishes after initialization completes, and the reader acknowledges after its kernel finishes and its mapping closes. The owner can then safely reuse or free the allocation. Same-process streams can also use cross-device event waits, while exported CUDA events support process boundaries within one node. Cross-device event waits · IPC events

Access control follows the allocation type: cudaMalloc peer access uses device peer enablement or legacy IPC import; VMM allocations use cuMemSetAccess for device permissions; stream-ordered pools have separate access settings. Reachability, permissions, and execution ordering must all hold. VMM · Pool access

2. P100 address translation

Setup and execution

During setup, the driver validates the allocation and access capability, establishes mappings and permissions, and maintains peer relationships and lifetimes. Peer enablement, IPC, and VMM are different API entry points; their complete internal call chains are implementation details.

With a valid mapping, the SM issues a global load. Translation uses a cached TLB result or a page-table walk, producing an address and target attributes. Interconnect hardware handles a peer request and returns its data. An ordinary mapped load does not call the CPU driver for each element. The mechanism can be summarized as:

CPU / driver: allocation → peer mapping + access permissions
                                    ↓
GPU SM: load VA → address translation → aperture + target address
                                       ├─ local → local memory path
                                       └─ peer  → peer route → remote memory

This is a mechanism-level explanation inferred from API semantics and the published format. Cache pipelines, transaction merging, and internal interconnect stages are omitted. GP100's PTE fields provide concrete evidence for the target information. Pascal MMU format, page 4

Target fields in a PTE

P100 uses GP100. Its published MMU format supports up to 49-bit virtual addresses and a five-level layout. This example uses a VER2-format, ordinary 4 KiB page. The header also contains older definitions; the positions here come from NV_MMU_VER2_PTE_*. GP100 format · VER2 definitions

The document's PA[39:37] and the header's PTE[35:33] describe different bit-numbering spaces. Dropping twelve page-offset bits and encoding from PTE bit 8 produces the four-bit difference. Address fields and shift

A peer ID identifies a hardware mapping slot, in a separate numbering scheme from CUDA ordinals and NCCL ranks. The driver establishes that correspondence. Its public kbusGetNvlinkP2PPeerId_GP100 code assigns IDs using topology, existing mappings, and reserved peer slots. Peer ID assignment

An encoding example

Take page base 0x12345000, peer slot 3, and byte offset 0x80. Setting only validity, aperture, peer ID, and the base gives:

PTE = ((0x12345000 >> 12) << 8)
    | (3 << 33)   # Peer ID
    | (1 << 1)    # Aperture = peer
    | 1            # Valid
    = 0x0000000601234503

target = peer slot 3, address 0x12345000 + 0x80
PTE[35:33]011 · ID 3
PTE[32:8] = PA[36:12]0x12345
PTE[2:1]01 · peer

PTE = 0x0000000601234503

A 4 KiB page at base 0x12345000, with Valid=1 and other unshown fields zero. This computes an illustrative bit pattern; it does not access GPU page tables.

The aperture selects the target class; the offset selects a byte in the page. The example encodes only the target and validity. A complete PTE also needs cache, layout, and other attributes appropriate to the mapping. The three-bit peer ID belongs to GP100; formats and addressing limits for later GPUs require their own hardware documentation.

3. NCCL Device API LSA

NCCL's Device API exposes peer memory access to user CUDA kernels. LSA (Load/Store Accessible) uses CUDA P2P over NVLink or PCIe where P2P connectivity is available. Host code establishes communicators and memory windows; the kernel obtains peer pointers from those windows and uses ordinary loads and stores. The Device API was introduced in NCCL 2.28. This section uses the interfaces and source from 2.32.3, commit 12df1a11afad. Device API guide

LSA teams and windows

An LSA team contains ranks that can communicate through memory loads and stores. devComm.lsaRank is the local rank within that team; devComm.lsaSize is its size. LSA interfaces use team ranks, which have a separate numbering scheme from CUDA device ordinals. Device communicator fields

A window, ncclWindow_t, organizes registered buffers across ranks so kernels can address data by window, peer, and offset. Each rank owns its physical allocation; window registration establishes the peer mappings. The example uses two ranks in one LSA team. Each reads the other's input, adds one, and writes its local output. Inputs remain unchanged throughout the kernel. Window registration

Host setup

Each rank's process or thread binds its local GPU. Rank 0 obtains id with ncclGetUniqueId and distributes it using the application's CPU communication mechanism. Each rank then performs the setup below. Before registering windows, check that props.deviceApiSupport is true and props.nLsaTeams == 1, so both ranks in this example can access each other directly. Official capability checks

#include <nccl.h>
#include <nccl_device.h>

cudaSetDevice(localDevice);
ncclComm_t comm;
ncclCommInitRank(&comm, 2, id, rank);

ncclCommProperties_t props = NCCL_COMM_PROPERTIES_INITIALIZER;
ncclCommQueryProperties(comm, &props);
// Required: props.deviceApiSupport && props.nLsaTeams == 1

Allocate input with ncclMemAlloc and register a symmetric window. Windows require a supported VMM allocation or the NCCL allocator. ncclCommWindowRegister is collective: every rank participates. This example registers equally sized inputs in the same order. Output is written only by the local GPU, so ordinary cudaMalloc suffices. Allocation requirements · Window API

size_t bytes = count * sizeof(float);
void* input;
ncclMemAlloc(&input, bytes);

ncclWindow_t win;
ncclCommWindowRegister(
    comm, input, bytes, &win, NCCL_WIN_COLL_SYMMETRIC);

float* output;
cudaMalloc(&output, bytes);  // Used only by this GPU

Create ncclDevComm with the barrier resources needed by the kernel. The example launches four CTAs and reserves one barrier per CTA by setting lsaBarrierCount to four. ncclDevCommCreate is a host-side collective call; the returned descriptor can be passed to the kernel by value. Device communicator requirements

constexpr int nCTAs = 4;
constexpr int nThreads = 256;
ncclDevCommRequirements reqs = NCCL_DEV_COMM_REQUIREMENTS_INITIALIZER;
reqs.lsaBarrierCount = nCTAs;

ncclDevComm devComm;
ncclDevCommCreate(comm, &reqs, &devComm);

When one thread manages multiple GPUs, group the ranks' collective initialization, window registration, and device communicator creation in their respective ncclGroupStart/ncclGroupEnd scopes. Use returned objects after the group has completed. Device communicator group semantics · Window group semantics

Kernel access

ncclGetLsaPointer(win, offset, peer) returns a peer pointer accessible from the current GPU. offset is measured in bytes and peer is an LSA team rank. The example passes zero for the window's start, then indexes src[i] in float elements. LSA pointer accessors

__global__ void lsa_peer_load(
    ncclDevComm devComm, ncclWindow_t win,
    float* output, size_t count) {
    ncclLsaBarrierSession<ncclCoopCta> bar{
        ncclCoopCta(), devComm, ncclTeamTagLsa(), blockIdx.x};
    bar.sync(ncclCoopCta(), cuda::memory_order_acquire);

    int peer = (devComm.lsaRank + 1) % devComm.lsaSize;
    const float* src = static_cast<const float*>(
        ncclGetLsaPointer(win, 0, peer));

    for (size_t i = blockIdx.x * blockDim.x + threadIdx.x;
         i < count; i += blockDim.x * gridDim.x) {
        output[i] = src[i] + 1.0f;
    }

    bar.sync(ncclCoopCta(), cuda::memory_order_release);
}

With two ranks, (devComm.lsaRank + 1) % devComm.lsaSize selects the other rank. The ncclGetLsaPointer implementation calculates an address from the window's peer-mapping base, stride, and byte offset. The subsequent src[i] performs the data load. This is the ordinary load from chapter 1, with NCCL providing the peer pointer. Pointer implementation

LSA rankLocal inputExpected local output
0[0, 1, 2, 3][101, 102, 103, 104]
1[100, 101, 102, 103][1, 2, 3, 4]

Synchronization and launch

Each rank initializes its input on its stream before launching the kernel. Both use the same grid and block configuration:

lsa_peer_load<<<nCTAs, nThreads, 0, stream>>>(
    devComm, win, output, count);

The entry barrier uses acquire ordering and waits for the team's corresponding CTAs before reading peer input. The exit barrier uses release ordering and waits for those CTAs to finish the round of accesses. This follows the official LSA example. ncclCoopCta() makes the whole CTA participate, while blockIdx.x selects the barrier used by corresponding CTAs across ranks. Official kernel · Barrier implementation

Every thread in a CTA must execute both barriers, including threads with no data to process. Bounds checking therefore belongs in the loop condition, with no early return before a barrier. Different CTAs use distinct barrier indices, and ranks must call each index in matching order. Concurrent kernels also need independent barrier resources. Barrier participation

Resource lifetime

After all kernels using these resources have completed, destroy the device communicator, deregister the window, then release the allocations and host communicator. Windows and communicators can be reused across kernel launches; reusing an input buffer still requires its peers to finish reading it. Device communicator lifetime · Window lifetime

// After all kernels using these resources have completed:
ncclDevCommDestroy(comm, &devComm);
ncclCommWindowDeregister(comm, win);
ncclMemFree(input);
cudaFree(output);
ncclCommDestroy(comm);

The complete official LSA example includes communicator startup, input initialization, verification, and cleanup. It implements AllReduce. This section simplifies the data operation to a peer read plus one while retaining its window and barrier workflow.

4. NVLink and PCIe

Physical paths

P2P describes direct access to another GPU's memory. Requests may travel over PCIe, a direct NVLink connection, or an NVLink fabric with NVSwitch forwarding. NVSwitch switches traffic; the GPUs issue requests and own the memory.

A PCIe route can traverse switches or a platform root complex, subject to topology and support. Direct payload access needs no staging allocation in CPU DRAM. NVLink and NVSwitch provide other interconnect paths. Topology requirements · NVSwitch structure

Link selection and routing

The application identifies the target allocation; CUDA peer-access APIs expose no per-load NVLink-port parameter. The Pascal guide documents automatic NVLink routing between connected endpoints. Peer mappings and system routing associate the destination with available links, and hardware uses that configuration during execution. Transparent NVLink routing

In the public driver, kbusGetNvlinkP2PPeerId_GP100 selects a peer ID from topology and existing state. Mapping code maintains peer masks and sets USE_NVLINK_PEER through an internal control interface to enable the NVLink peer path. These references cover GP100 architecture functions in driver 620.70.06; the full call chain on a running P100 has not been traced here. Peer ID selection · Peer route enablement
