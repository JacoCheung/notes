NVIDIA GPU 访存层级与 Nsight Compute 数据通路模型

一条 ordinary device-memory global load 从 warp 发射后，先由 load/store 单元处理，再由 L1TEX 查询目标数据。L1 miss 继续进入 L2，L2 miss 才会到达显存侧分区。Nsight Compute 把 scheduler 状态、cache 流量、片上接口和显存控制指标放在同一份报告中，但这些名称描述的是不同阶段和抽象层级。沿着请求与返回过程梳理各单元的角色和证据等级，才能建立可复核的数据通路模型。

1. NCU Memory Chart 的表达边界

Nsight Compute 的 Memory Chart 是一张逻辑性能图。它把指令数、请求数、sector、缓存命中率和链路吞吐量放在同一视图中，用相邻层级的计数变化表示流量在哪里被合并、命中或放大。图中的节点和连线服务于性能归因，其精度不等同于 NVIDIA GPU 的 RTL 框图，也不承诺不同架构采用相同的内部连接。

阅读这张图时，需要先区分三种观察层级：

  • 执行和发射路径：例如 LSU、MIO、MIOC。
  • 缓存与片上网络：例如 L1TEX、GNIC、LRC、LTC/LTS。
  • 显存侧分区：例如 FBP/FBPA、MCC 和 DRAM。

三个层级回答的问题不同：SM 侧指标说明指令能否发射以及依赖是否完成；cache 与片上接口指标说明 request 和 sector 在何处被处理；显存侧指标说明穿透 L2 的流量如何到达 device memory。把观察层级分开后，单元名称才有明确的位置，来自公开文档、metric 语义和专利实施例的关系也可以分别标注。

2. 单元角色与证据层级

沿着上述三个层级，下面的单元共同构成从指令发射到本地显存的观察框架。表中的“公开定义与作用”说明单元能够由资料确认的职责，“与主路径的关系”则限定它在 ordinary global load 模型中的位置。

名称层级公开定义与作用与主路径的关系
LSU SM 发射 Load/Store Unit，负责发射 global、local、shared 的 load、store、atomic 和 reduction 指令。 普通 global load 从这里进入 L1TEX；它描述发射端，不是 cache 层级。
L1TEX SM/GPC cache 组合的 L1/Texture 单元，包含 tag、miss 和 data 阶段；其物理存储资源也用于 shared memory。 Global load 在这里形成 L1 request 并查询所需 sector；miss 流量继续前往 L2。
GNIC 片上网络端点 NVIDIA 公开专利将其展开为 Generic Network Interface Controller，并展示请求、返回和 multicast packet 接口。 只在暴露相关 metric 或符合相应专利实施例时作为架构相关端点，不作为所有 GPU 的固定单元。
LRC L2 前端 L2 Request Coalescer，尝试合并进入 L2 的读请求，处理 programmatic multicast，并通过 ILC 支持写压缩和读数据解压。 处理来自上游单元的 L2 request，再把请求转交 L2 cache。
LTC L2 Level 2 cache 的整体逻辑单元；ltcfabric 是 L2 分区之间的通信 fabric。 表示共享 L2 层级；具体流量通常由各 LTS 的 metric 统计。
LTS L2 slice 一个 L2 cache slice/subpartition，包含 tag、miss 和 data 阶段。 承接进入 L2 的 request；L2 miss 才继续到 device-memory aperture。
FBP / FBPA 显存分区 FBP 是 frame buffer partition；NCU 将 FBPA 定义为位于 LTC 与 DRAM 之间的 memory controller。 表示 L2 与本地 DRAM 之间的显存侧分区，不等同于 DRAM 芯片。
MCC 显存控制 Memory Controller Channel，包含 row sorter/arbiter 和 DRAM controller。 负责把显存侧请求落实为 DRAM 操作；与 FBPA 的内部边界随架构变化。
MIO / MIOC SM 发射与 metric 单元 MIO 展开为 Memory Input/Output；NCU 将 shared-memory、部分 special math 和 dynamic branch 的队列压力与依赖归入 MIO。公开 Metrics Decoder 只给出 MIOC 的名称展开，尚不足以确定它与 MIO 的拓扑关系。 MIO 属于 scheduler 可见的发射和依赖归因层级。主路径不放置职责尚未公开的 MIOC。

2.1 公开定义、metric 语义与专利实施例

NCU Metrics Decoder 直接定义 LSU、L1TEX、LRC、LTC/LTS、FBPA 和 MCC 的职责，也规定接口名采用 sender2receiver。因此，某代 GPU 上出现的 gnic2l1tex 可以说明该 metric 记录 GNIC 向 L1TEX 的传输方向，但 metric 名称本身不能给出队列深度、端口数量或完整物理路由。

NVIDIA 公开专利给出 GNIC 的全称，并在示例实现中展示 tex2gnic、gnic2tex packet interface。这能支持 GNIC 作为一种片上网络端点的工作模型，不能证明每代量产 GPU 都采用相同单元、连线或仲裁顺序。主图用不同线型保留这三种证据等级；这条边界也决定了数据通路能够画到什么精度。

2.2 L1TEX 与 LRC 的合并层级

在公开资料能够连接的路径中，coalescing 出现在两个不同位置。一次 warp load 先在 L1TEX 侧按线程地址和 cache line 组织 L1 request，未命中的部分再进入片上网络。靠近 L2 的 LRC 面对来自多个上游单元的 L2 request，并可能再次合并 read request。因此，两级合并处理的对象和范围并不相同：

warp/L1TEX coalescing: thread addresses → L1 requests and sectors
LRC coalescing:         incoming L2 requests → fewer L2 transactions when possible

这两级合并解释了 request 数量为何会在层级之间变化。明确它们的边界之后，ordinary global load 的主路径就可以按 request、cache lookup 和 miss traffic 的顺序展开。

若暂时去掉证据标记，只保留 ordinary global load 的请求分支，主路径可以压缩为下面的文本形式。这个版本便于随后逐级对照 profiler 的 request、sector 与 wavefront 计数：

Warp → LSU → L1TEX
                   ├─ L1 hit → register
                   └─ L1 miss → on-chip network interface / XBAR → LRC → LTS/LTC
                                                               ├─ L2 hit → return
                                                               └─ L2 miss → FBP memory side → HBM

Load 的返回阶段把命中数据或 fill data 送回发起请求的 SM，并解除目标寄存器上的依赖。NCU 的公开模型给出了 XBAR 到 L1 的 return path，部分架构还暴露 gnic2l1tex 一类返回方向的接口名；这些资料足以说明返回方向，却不足以还原一条跨架构通用的逐单元物理回程。依赖解除后 consumer 才能继续发射，此前的等待通常归入 long_scoreboard。

图中把 FBPA 和 MCC 放在同一个显存侧分区中。NCU 公开文档分别说明了它们的职责，但没有为所有架构给出可复用的精确串联关系。不能仅凭 metric 前缀断言某代 GPU 的内部端口和仲裁顺序。

4. 指令到 request、sector 与 wavefront 的逐级展开

主路径说明了请求经过哪些层级，profiler 数值还取决于每一级采用什么计数单位。同一条 SASS memory instruction 会沿途展开为 request、sector 和 wavefront：

  1. Instruction：一个 warp 执行一条 load/store 指令。
  2. Request：指令进入某个硬件单元后生成的工作请求；一条指令可能产生零个或多个 request。
  3. Sector：L1 和 L2 的最小统计传输块为 32 B；一个 128 B cache line 包含四个 sector。
  4. Wavefront：硬件单元一次能够并行处理的 work package。一个 request 若无法一次处理完，会被拆成多个 wavefront 串行执行。

这些计数的关系必须放回具体层级理解。Nsight Compute 13.3 Profiling Guide 说明，在 Volta 及更新架构上，一条 global/local LSU 指令会生成一个 L1 request；线程地址分散主要增加该 request 涉及的 tag、sector 或 wavefront，并可能在下游形成更多 L2 request。NCU 对 instruction 的通用定义仍允许零个或多个 request，因为它覆盖其他指令类别和硬件单元。Shared-memory bank conflict 则主要放大 wavefront。分析时应沿层级比较相邻计数，而不是只看最终 DRAM bytes。

5. Shared memory、store 与远端内存的路径差异

前面的模型以 ordinary device-memory global load 为中心，因为它同时经过 scheduler、cache 和显存侧层级。Shared memory、store、atomic 以及映射到远端的 global address 会在不同位置分流；识别分流点可以避免把主图机械套用到另一类访问。

5.1 Shared memory

普通 CTA shared-memory 访问在 SM 内完成，不经过 L2 和本地 HBM。NCU 把 shared-memory 指令的队列压力和结果依赖归入 MIO，同时又在 L1TEX 的 shared pipe 中统计 request、wavefront 和 bank conflict。这是两个观察层级：

  • mio_throttle、short_scoreboard 描述 scheduler 看到的队列或依赖状态。
  • l1tex__data_pipe_lsu_wavefronts_mem_shared... 描述 shared-memory 数据路径实际处理的工作。

这两个观察层级需要联合解释：GPU MIO Throttle：队列反压、成因与诊断给出了 queue 与 shared pipe 指标的组合方法，GPU Scoreboard 依赖机制则说明 short/long scoreboard 如何等待 producer 完成。

5.2 Store、atomic 与 reduction

Store 把数据写入内存，不产生需要写回目标寄存器的 load result；内存系统仍要维护写入的顺序、可见性和未完成状态。NCU 文档说明，完整覆盖的 128 B write 可能由 GXC 压缩，LRC 内的 ILC 也支持 write compression，但没有给出适用于所有架构的单一 store acknowledgement 通路。Atomic 与 reduction 会绕过 L1 的普通数据服务并继续交给 L2 侧处理，其应答语义也不同于 ordinary load。因此，主图可以解释 load latency，却不能直接推导所有 store 与 atomic 时序。

5.3 System memory 与 peer memory

Global address space 可以映射到本地 device memory、pinned system memory 或 peer memory。后两者在 L2 miss 后不会进入本地 FBP/HBM，而会走 system/peer aperture、SysL2、NVLink、C2C 或 PCIe 等路径。NCU 的 L2 表会分别统计 Sector Misses to Device、System 和 Peer。

6. 用 NCU 观察各段通路

把层级模型用于实际诊断时，需要在同一份报告中比较相邻位置的计数，而不是先假定某个内部单元存在。Memory Workload Analysis 提供入口，随后再根据目标 GPU 的报告和可用 metric 下钻：

ncu --set full -o memory-report ./app

# 在当前 GPU 上查询可用名称
ncu --query-metrics | rg 'l1tex|lts|fbpa|dram|gnic|lrc'
通路位置优先观察可回答的问题
Warp → L1TEX global/local instruction、L1 request、sector、wavefront、L1 hit rate 线程地址是否放大请求；L1 是否承接了复用；L1 pipe 是否拥塞。
L1TEX → L2 L1 miss sectors、接口 active/stalled、L2 incoming sectors 有多少流量穿过片上网络；接收端是否形成反压。
LTS / LTC lts__t、lts__m、lts__d，L2 hit rate 与 throughput L2 tag、miss、data 哪一级繁忙；L2 是否挡住了 DRAM 流量。
L2 → device memory L2 sector misses to device、FBPA/DRAM throughput、read/write bytes 瓶颈位于 cache miss latency，还是显存控制器和 HBM bandwidth。
Scheduler long_scoreboard、lg_throttle、eligible warp 与 issue slot 访存延迟是否暴露到 warp；请求队列是否在发射前被压满。

PerfWorks metric 的接口部分采用 sender2receiver 命名。例如某代 GPU 上出现的 gnic2l1tex 表示 GNIC 向 L1TEX 发送数据，而不是 L1TEX 发出请求。metric 集合随架构和 NCU 版本变化，实际分析应以报告 tooltip 和 --query-metrics 为准。

7. 从现象定位通路上的瓶颈

相邻层级的计数能够把 scheduler 等待与 cache、片上接口和显存侧流量连接起来。下面几组常见现象展示了这种对应关系，也给出了每种现象需要优先排查的位置。

观察结果优先检查的位置解释
L1 request/sector 很多，DRAM 流量不高 L1TEX、地址合并与 L2 hit 请求可能在 L1/L2 被吸收；此时 DRAM bandwidth 不是主要限制。
L2 miss sectors 与 DRAM bytes 同时很高 数据局部性、tile 大小、FBPA/DRAM throughput 工作集穿透了 L2，需要区分 latency-bound 与 bandwidth-bound。
long_scoreboard 高，但 DRAM throughput 低 访问合并、cache miss latency、并行请求数量 低带宽不代表低延迟；随机、稀疏访问可能等待很久，却无法填满 HBM。
mio_throttle 高 Shared-memory、MUFU 或动态分支 这是 SM 侧 MIO instruction queue 反压，不能直接归因到 L2 或 HBM。
Shared wavefront 远高于 request Bank conflict 与 shared layout 问题位于 SM 内 shared-memory 服务过程，不在 FBP。

实际归因可以从 scheduler 的暴露等待出发，找到对应 SASS，再沿 Memory Chart 检查相邻层级的流量变化。高利用率说明单元承担了较多工作；当吞吐接近上限，并伴随上游反压或下游等待时，它才成为有完整证据链的瓶颈候选。

NVIDIA GPU Memory Hierarchy and the Nsight Compute Data-Path Model

After an ordinary device-memory global load issues from a warp, a load/store unit handles the instruction and L1TEX looks up the target data. An L1 miss proceeds to L2, and only an L2 miss reaches a device-memory partition. Nsight Compute places scheduler state, cache traffic, on-chip interfaces, and memory-control metrics in one report, even though those names describe different stages and abstraction levels. Following the request and return path while separating unit roles from evidence levels produces a reviewable data-path model.

1. Scope of the NCU Memory Chart

The Nsight Compute Memory Chart is a logical performance model. It places instruction counts, requests, sectors, cache hit rates, and link throughput in one view, using changes between adjacent levels to show where traffic is merged, served, or amplified. Its nodes and links support performance attribution; their precision is not that of an NVIDIA GPU RTL diagram, and they do not promise identical internal connections across architectures.

Reading the chart requires three observation levels to be separated:

  • Execution and issue paths: LSU, MIO, and MIOC.
  • Caches and on-chip networking: L1TEX, GNIC, LRC, and LTC/LTS.
  • Memory-side partitions: FBP/FBPA, MCC, and DRAM.

The three levels answer different questions. SM-side metrics describe whether an instruction can issue and whether its dependency has completed. Cache and interface metrics describe where requests and sectors are processed. Memory-side metrics describe how traffic that misses L2 reaches device memory. Once the observation levels are separate, each unit has a clear position and relationships from public documentation, metric semantics, and patent embodiments can be marked independently.

2. Unit roles and evidence levels

Across those three levels, the units below form an observation framework from instruction issue to local device memory. The public-role column records responsibilities established by the sources, while the final column limits each unit's position in the ordinary-global-load model.

NameLevelPublic definition and roleRelationship to the main path
LSU SM issue The Load/Store Unit issues global, local, and shared loads, stores, atomics, and reduction instructions. An ordinary global load enters L1TEX from this unit. LSU describes the issue endpoint, not a cache level.
L1TEX SM/GPC cache The combined L1/Texture unit contains tag, miss, and data stages. Its physical storage resources are also used for shared memory. A global load forms an L1 request and looks up the required sectors here; miss traffic continues toward L2.
GNIC On-chip network endpoint An NVIDIA public patent expands the name as Generic Network Interface Controller and shows request, return, and multicast packet interfaces. It is used as an architecture-dependent endpoint only where exposed metrics or the cited patent embodiment support it, not as a fixed unit on every GPU.
LRC L2 front end The L2 Request Coalescer attempts to merge reads entering L2, handles programmatic multicast, and supports write compression and read-data decompression through ILC. It processes L2 requests from upstream clients before forwarding them to the L2 cache.
LTC L2 The logical Level 2 cache as a whole. ltcfabric is the communication fabric between L2 partitions. It denotes the shared L2 level; concrete traffic is generally counted by metrics on individual LTS units.
LTS L2 slice An L2 cache slice or subpartition containing tag, miss, and data stages. It handles requests entering L2; only an L2 miss proceeds to a device-memory aperture.
FBP / FBPA Memory partition FBP means frame buffer partition. NCU defines FBPA as a memory controller between LTC and DRAM. It represents the memory-side partition between L2 and local DRAM, not the DRAM device itself.
MCC Memory control A Memory Controller Channel includes the row sorter/arbiter and DRAM controller. It turns memory-side requests into DRAM operations; its internal boundary with FBPA is architecture-dependent.
MIO / MIOC SM issue and metric units MIO expands to Memory Input/Output. NCU attributes queue pressure and dependencies from shared memory, some special-math operations, and dynamic branches to MIO. The public Metrics Decoder expands the MIOC name but does not provide enough information to establish its topology relative to MIO. MIO belongs to the scheduler-visible issue and dependency-attribution level. The main path does not place MIOC because its public role is not specified.

2.1 Public definitions, metric semantics, and patent embodiments

The NCU Metrics Decoder directly defines the roles of LSU, L1TEX, LRC, LTC/LTS, FBPA, and MCC, and specifies sender2receiver interface names. A metric such as gnic2l1tex on a particular GPU therefore establishes the recorded transfer direction from GNIC to L1TEX, but the name alone does not disclose queue depth, port count, or a complete physical route.

An NVIDIA public patent expands GNIC and shows tex2gnic and gnic2tex packet interfaces in an example embodiment. This supports a working model of GNIC as one type of on-chip network endpoint. It does not establish the same unit, wiring, or arbitration order for every shipping GPU. The main diagram uses separate line styles for these three evidence levels; this boundary also determines how precisely the data path can be drawn.

2.2 Coalescing at the L1TEX and LRC levels

Within the publicly connected path, coalescing appears at two distinct locations. A warp load first organizes thread addresses into L1 requests and cache lines on the L1TEX side, and only the missed portion proceeds into the on-chip network. LRC sits closer to L2, receives L2 requests from multiple upstream units, and may merge reads again. The two stages therefore operate on different objects and scopes:

warp/L1TEX coalescing: thread addresses → L1 requests and sectors
LRC coalescing:         incoming L2 requests → fewer L2 transactions when possible

These two coalescing stages explain why request counts can change between levels. With their scopes established, the ordinary-global-load path can be followed in the order of request formation, cache lookup, and miss traffic.

3. Global load request and return path

The diagram retains both path and evidence information. Node order shows the observation levels traversed by a request, color separates request and return directions, and line style distinguishes relationships stated directly in official documentation from inferences supported by metric direction. The main path can therefore be read together with the strength of each connection.

Logical model for an ordinary device-memory global load; color shows direction and line style shows evidence level
Logical relationship directly described by official documentation Direction inferred from metric-interface semantics

Removing the evidence annotations and retaining only the ordinary-global-load request branches gives the compact text form below. This version is convenient when matching each level to subsequent request, sector, and wavefront counters:

Warp → LSU → L1TEX
                   ├─ L1 hit → register
                   └─ L1 miss → on-chip network interface / XBAR → LRC → LTS/LTC
                                                               ├─ L2 hit → return
                                                               └─ L2 miss → FBP memory side → HBM

The return stage carries hit or fill data back to the requesting SM and clears the dependency on the destination register. NCU's public model exposes an XBAR-to-L1 return path, and some architectures expose return-facing interfaces such as gnic2l1tex. This evidence establishes the return direction without defining one per-unit physical route shared by every architecture. The consumer can issue after the dependency clears; until then, NCU normally attributes the wait to long_scoreboard.

The diagram places FBPA and MCC inside one memory-side partition. Public NCU documentation describes their responsibilities separately, but it does not publish one precise serial relationship that applies to every architecture. Metric prefixes alone cannot establish a GPU generation's internal ports or arbitration order.

4. Expansion from instructions to requests, sectors, and wavefronts

The main path identifies the levels traversed by a request; profiler values also depend on the counting unit used at each level. One SASS memory instruction expands into requests, sectors, and wavefronts along the path:

  1. Instruction: a warp executes one load or store instruction.
  2. Request: work generated when the instruction enters a hardware unit; one instruction may generate zero or more requests.
  3. Sector: the minimum transfer unit counted at L1 and L2 is 32 bytes. One 128-byte cache line contains four sectors.
  4. Wavefront: a work package that a hardware unit can process concurrently. A request that cannot be handled at once is split into multiple wavefronts and processed serially.

These counters must be interpreted at the level where NCU records them. The Nsight Compute 13.3 Profiling Guide states that, on Volta and newer architectures, one global or local LSU instruction generates one L1 request. Scattered thread addresses mainly increase the tags, sectors, or wavefronts covered by that request and may create more downstream L2 requests. NCU's generic instruction definition still permits zero or more requests because it spans other instruction classes and hardware units. Shared-memory bank conflicts primarily increase wavefronts. Analysis should compare adjacent counters along the hierarchy rather than looking only at final DRAM bytes.

5. Path differences for shared memory, stores, and remote memory

The preceding model centers on an ordinary device-memory global load because it spans scheduler, cache, and memory-side levels. Shared memory, stores, atomics, and global addresses mapped to remote memory diverge at different points. Identifying each divergence keeps the main diagram from being applied mechanically to another access class.

5.1 Shared memory

Ordinary CTA shared-memory accesses complete inside the SM and do not traverse L2 or local HBM. NCU attributes shared-memory instruction queue pressure and result dependencies to MIO, while counting requests, wavefronts, and bank conflicts in the L1TEX shared pipe. These are two observation levels:

  • mio_throttle and short_scoreboard describe queue or dependency states observed by the scheduler.
  • l1tex__data_pipe_lsu_wavefronts_mem_shared... describes work processed by the shared-memory data path.

The two observation levels need to be interpreted together. GPU MIO Throttle: Queue Backpressure, Causes, and Diagnosis combines queue and shared-pipe metrics, while GPU Scoreboard Dependencies explains how short and long scoreboards wait for producers to complete.

5.2 Stores, atomics, and reductions

A store writes data to memory and produces no load result for a destination register; the memory system still maintains ordering, visibility, and outstanding state for the write. NCU documents that GXC may compress a fully covered 128-byte write and that ILC inside LRC supports write compression, but it does not publish one store-acknowledgement route for every architecture. Atomics and reductions bypass ordinary L1 data service and continue to the L2 side, and their response semantics differ from an ordinary load. The main diagram can therefore explain load latency without establishing every store or atomic timing path.

5.3 System and peer memory

The global address space can map to local device memory, pinned system memory, or peer memory. After an L2 miss, the latter two do not enter the local FBP/HBM path. They use system or peer apertures and may pass through SysL2, NVLink, C2C, or PCIe. The NCU L2 table counts Sector Misses to Device, System, and Peer separately.

6. Observing each segment with NCU

Applying the hierarchy to a real diagnosis requires adjacent counters to be compared in the same report, without assuming that a particular internal unit exists. Memory Workload Analysis provides the entry point; further inspection should use the metrics available on the target GPU:

ncu --set full -o memory-report ./app

# Query the names available on the current GPU
ncu --query-metrics | rg 'l1tex|lts|fbpa|dram|gnic|lrc'
Path segmentInspect firstQuestions it can answer
Warp → L1TEX Global/local instructions, L1 requests, sectors, wavefronts, and L1 hit rate Whether thread addresses amplify requests, whether L1 captures reuse, and whether the L1 pipe is congested.
L1TEX → L2 L1 miss sectors, interface active/stalled, and incoming L2 sectors How much traffic crosses the on-chip network and whether the receiver applies backpressure.
LTS / LTC lts__t, lts__m, lts__d, L2 hit rate, and throughput Whether the L2 tag, miss, or data stage is busy and whether L2 absorbs DRAM traffic.
L2 → device memory L2 sector misses to device, FBPA/DRAM throughput, and read/write bytes Whether the limiting factor is cache-miss latency or memory-controller and HBM bandwidth.
Scheduler long_scoreboard, lg_throttle, eligible warps, and issue slots Whether memory latency is exposed to warps and whether a request queue is full before issue.

PerfWorks interface metrics use sender2receiver names. For example, gnic2l1tex on a particular GPU counts data sent from GNIC to L1TEX, not requests issued by L1TEX. Metric sets change with architecture and NCU version, so use report tooltips and --query-metrics for the target system.

7. Locating bottlenecks from observed symptoms

Adjacent-level counters connect scheduler-visible waits to traffic in caches, on-chip interfaces, and memory-side partitions. The following patterns illustrate those relationships and identify the first location to inspect for each observation.

ObservationInspect firstInterpretation
Many L1 requests/sectors but little DRAM traffic L1TEX, address coalescing, and L2 hits Requests may be absorbed by L1 or L2; DRAM bandwidth is not the main limit in that case.
High L2 miss sectors and DRAM bytes Data locality, tile size, and FBPA/DRAM throughput The working set passes through L2. Separate latency-bound behavior from bandwidth-bound behavior.
High long_scoreboard with low DRAM throughput Access coalescing, cache-miss latency, and memory-level parallelism Low bandwidth does not imply low latency. Random or sparse accesses may wait a long time without filling HBM.
High mio_throttle Shared memory, MUFU, or dynamic branches This is backpressure in the SM-side MIO instruction queue, not direct evidence of an L2 or HBM bottleneck.
Shared wavefronts far exceed requests Bank conflicts and shared-memory layout The issue is in shared-memory service inside the SM, not in FBP.

Attribution can begin with a scheduler-visible wait, locate the corresponding SASS, and then follow traffic changes between adjacent levels in the Memory Chart. High utilization shows that a unit is carrying substantial work. It becomes a bottleneck candidate with a complete evidence chain when throughput approaches a limit and upstream backpressure or downstream waiting is also visible.
