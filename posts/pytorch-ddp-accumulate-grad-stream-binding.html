PyTorch DDP AccumulateGrad 的 Stream 绑定机制

单进程单 GPU 的 DDP 训练通常按固定顺序初始化：选择本地 CUDA device，把模型参数放到该 device，再用 DistributedDataParallel 包装模型。这个顺序还会确定 autograd 的执行 stream。DDP 在构造期间取得叶子参数的 AccumulateGrad；节点若在此时创建，便会记录当时的 CUDA current stream。以后梯度到达参数时，autograd Engine 会切换到该 stream，执行梯度累加和 DDP 注册的 hook。默认 stream 训练很少显露这项机制，自定义 stream 和 CUDA Graph capture 则会直接受到它的约束。

执行范围与术语

本文分析标准 torch.nn.parallel.DistributedDataParallel 的 CUDA eager 路径，PyTorch 源码固定在 commit 867370d。TorchRec 与 Megatron-Core 只作为公开工程用法的旁证；两者的 wrapper 还包含分片、专用梯度 buffer 等额外机制。

节点 stream 是 autograd Node 的第一个 accelerator input 在创建 Node 时记录的 stream。Node::stream() 从 input metadata 返回它，Engine 把它当作执行该 Node 的 canonical consumer stream。对叶子参数而言，承担梯度写入职责的 Node 是 AccumulateGrad。叶子 Tensor 本身仍满足 param.grad_fn is None；这个关系可与 PyTorch Autograd 反向图模型 一文配合阅读。

AccumulateGrad 绑定 stream 的时刻是节点创建，而不是每次 hook 调用。DDP 构造通常触发这次创建，但若节点已经存在且仍被持有，Reducer 会复用原节点及其原有 stream。

DDP 构造期间取得并持有 AccumulateGrad

DDP 的 Python 构造函数建立 bucket 后创建 Reducer。官方 DDP design note 将这一步描述为：Reducer 在构造期间为每个参数注册 autograd hook，参数梯度就绪后由 hook 启动规约。Python 入口也把“registering the grad hooks”列为 _ddp_init_helper() 的职责。

具体工作发生在 Reducer 构造函数。它依次处理每个可训练参数：

// 语义化摘录：torch/csrc/distributed/c10d/reducer.cpp
auto grad_accumulator = torch::autograd::impl::grad_accumulator(variable);

hooks_.emplace_back(
    grad_accumulator->add_post_hook(/* Reducer::autograd_hook */),
    grad_accumulator);

// 参数的 autograd metadata 只保存 weak_ptr；Reducer 保存强引用。
grad_accumulators_[variable_index] = std::move(grad_accumulator);

固定版本源码：reducer.cpp, lines 173–237

grad_accumulator(variable) 先检查叶子参数的 weak reference。已有节点会被直接返回；没有节点时，它构造新的 AccumulateGrad。Reducer 再保存强引用，使节点跨 iteration 存活。由此，DDP wrapper 的构造时间通常也就是这些叶子累加节点的创建时间。

普通 eager autograd 的生命周期有所不同。叶子的 autograd metadata 只缓存 AccumulateGrad 的 weak reference；当前计算图仍引用该节点时，它保持存活，计算图及其他强引用释放后，节点便可以销毁。下一张计算图再次为这个叶子请求 gradient edge 时，失效的 weak reference 无法返回旧节点，grad_accumulator() 会在届时的 current stream 下重新创建节点。固定版本源码也明确把“旧计算图及其累加节点在 iteration 之间释放”作为常规生命周期。

DDP 的 Reducer 改变了这个生命周期。grad_accumulators_ 中的强引用独立于单次 forward/backward 图，因此释放 loss 和原计算图并不会销毁这些节点。节点创建时写入的 stream metadata 也随 Reducer 一直保留；仅把下一次 forward 移到 capture stream 不会让它重新绑定。自定义 stream 或 CUDA Graph 训练需要在目标 stream 中构造 DDP，或者显式重建持有这些节点的 wrapper。

创建节点时记录 CUDA current stream

AccumulateGrad 构造函数只有两项主要动作：保存叶子变量，并调用 add_input_metadata(variable)。对应源码如下：

AccumulateGrad::AccumulateGrad(Variable variable_)
    : Node(/*sequence_nr=*/UINT64_MAX), variable(std::move(variable_)) {
  add_input_metadata(variable);
}

InputMetadata 根据参数的 device type 取得该 device 当前的 stream，并把结果存入 stream_：

// torch/csrc/autograd/input_metadata.cpp
auto device_ = options.device();
stream_ = c10::impl::getDeviceGuardImpl(device_.type())->getStream(device_);

固定版本源码：input_metadata.cpp, lines 28–42

因此，GPU 参数所在的 device 决定查询哪个 CUDA device，而 DDP 构造时的 current stream 决定记录哪个 stream。model.cuda(device) 负责参数放置；with torch.cuda.stream(stream): DDP(...) 才直接决定新建 AccumulateGrad 的 stream metadata。两者承担不同职责。

backward 执行前恢复节点 stream

backward kernel 可以在另一个 stream 上产生传给参数的梯度。梯度进入 AccumulateGrad 的 input buffer 后，Engine 读取节点 stream，构造 OptionalStreamGuard，并在调用 Node 及其 post hooks 前把它设为当前 stream。固定版本的 Engine::evaluate_function() 还会检查 incoming gradient 的 producer stream；两者不同时，consumer stream 等待 producer event。

auto opt_parent_stream = inputs.opt_overridden_consumer_stream.has_value()
    ? inputs.opt_overridden_consumer_stream
    : func->stream();

c10::OptionalStreamGuard parent_stream_guard{opt_parent_stream};

if (*opt_parent_stream != *opt_ready_stream) {
  opt_parent_stream->wait(opt_ready_event.value());
}

// 随后在 guard 覆盖的 current stream 下执行 Node 和 post hooks。

这里的“hook 在该 stream 上执行”需要区分 CPU 与 GPU 两层。hook 的 C++/Python 回调代码由 autograd worker thread 调用；OptionalStreamGuard 使回调期间的 CUDA current stream 指向节点 stream，所以回调发起的 CUDA operation 会入队到这个 stream。CPU 回调本身并不会变成 GPU kernel。

DDP 构造时的 stream capture 与 backward 时的 stream restoration

这张图表达的是公开源码中的逻辑关系，并未假定 event pool、队列深度或 GPU 内部调度结构。若 producer 与 consumer 恰好是同一个 stream，stream 内顺序已经满足依赖，额外的跨 stream wait 不再需要。

Reducer hook 与 NCCL stream 属于两个执行层次

AccumulateGrad 更新 param.grad 后，Reducer post hook 把参数标记为 ready；bucket 收齐后，Reducer 才进入 collective 路径。ProcessGroupNCCL 的 stream 同步代码说明，异步 NCCL 通信通常使用其管理的 ncclStream，并通过 event 等待调用时的 current stream。collective dispatch 在 async 模式选择独立 NCCL stream，在同步模式选择 current stream。

因此，AccumulateGrad.stream == S0 表示梯度累加和 Reducer hook 在 S0 的 current-stream context 中运行；它并不把 NCCL kernel 永久绑定到 S0。两者之间由 ProcessGroup 建立所需的 stream dependency。bucket 如何触发 collective，可继续参见 PyTorch DDP 梯度规约机制。

GPU 参数放置先于 DDP wrapper

DDP 构造时需要遍历最终参数集合、检查 device、建立 bucket，并为参数取得梯度累加节点。官方 DistributedDataParallel 手册规定，单 device CUDA module 的 device_ids 指向该 module 已经驻留的 device；当 device_ids=None 时，module 与输入同样需要由调用方放到正确 device。固定版本源码中的 参数说明给出了同一约束。

官方 DDP 教程采用最直接的顺序：

# PyTorch official DDP tutorial
model = ToyModel().to(rank)
ddp_model = DDP(model, device_ids=[rank])

官方教程：Getting Started with Distributed Data Parallel；固定版本源文件：lines 133–147

.cuda(device) 与 .to(device) 在这里承担相同的 device placement 角色。DDP wrapper 不负责把一个普通 CPU module 自动迁移到 device_ids[0]。此外，官方手册明确要求 wrapper 构造后不要替换参数，因为 DDP 已经为构造时看到的参数集合注册梯度规约函数；参见 DDP parameter warning。

TorchRec：先设 device、放置模型，再构造 DDP

TorchRec 的公开 BERT4Rec 示例先根据 LOCAL_RANK 调用 torch.cuda.set_device(device)，随后用 BERT4Rec(...).to(device) 完成参数放置，最后才选择标准 DDP(model_bert4rec, device_ids=device_ids) 或 TorchRec DMP。对应顺序可见 commit 561502d 的 device 初始化、模型放置和 DDP 构造。

Megatron-Core：同时处理 device placement 与自定义 stream

Megatron-Core 的模型构造路径同样先执行 model_module.cuda(torch.cuda.current_device())，再进入 DDP wrapper；meta-device 路径也会在 wrapper 前物化参数。固定版本代码位于 dist_utils.py。

它还显式处理了本文讨论的 stream 约束。全 iteration CUDA Graph 模式选择共享 capture stream，并写明 DDP 初始化必须在该 stream 上进行，以免被保留的 AccumulateGrad 指向另一个 non-capturing stream；随后代码进入 with torch.cuda.stream(ddp_stream) 构造 wrapper。参见同一 commit 的 stream selection。Megatron 自定义 DDP 随后通过临时 view 找到 AccumulateGrad、注册 hook 并保存强引用，见 hook registration。

初始化方式与 stream mismatch 诊断

普通 DDP 训练使用每个 device 的默认 stream，初始化代码可以保持简洁：

local_rank = int(os.environ["LOCAL_RANK"])
device = torch.device("cuda", local_rank)

torch.cuda.set_device(device)
dist.init_process_group("nccl", device_id=device)

model = Model().to(device)  # 或 Model().cuda(local_rank)
ddp = DDP(model, device_ids=[local_rank])

# forward/backward 也在该 device 的默认 current stream 上执行。

训练若固定使用自定义 stream，应让参数放置、DDP 构造和后续 iteration 使用同一个 stream context：

torch.cuda.set_device(device)
train_stream = torch.cuda.Stream(device=device)

with torch.cuda.stream(train_stream):
    model = Model().to(device)
    ddp = DDP(model, device_ids=[local_rank])

with torch.cuda.stream(train_stream):
    output = ddp(batch.to(device, non_blocking=True))
    loss = loss_fn(output, target)
    loss.backward()

多个计算 stream 都可能向同一参数产生梯度时，单个 AccumulateGrad 仍只有一个 canonical consumer stream。autograd 用 event 依赖保证正确性；stream 数量增加时，跨 stream 同步也可能增加。这是性能和 CUDA Graph capture 问题，不会让符合依赖规则的 eager backward 得到错误梯度。

固定版本 PyTorch 提供 torch.autograd.graph.set_warn_on_accumulate_grad_stream_mismatch()。开启后，若 incoming gradient 的 producer stream 与 AccumulateGrad stream 不同，Engine 会给出一次警告。诊断文字直接列出 DDP 持有旧节点这一来源，并建议在后续 forward 所用的同一 stream 中初始化 DDP，参见 InputBuffer mismatch handling。

torch.autograd.graph.set_warn_on_accumulate_grad_stream_mismatch(True)

with torch.cuda.stream(init_stream):
    ddp = DDP(model, device_ids=[local_rank])

with torch.cuda.stream(train_stream):
    ddp(input).sum().backward()
    # init_stream != train_stream 时，可观察到 AccumulateGrad stream mismatch 警告。

CUDA Graph capture 的临时 stream override

CUDA Graph capture 会把 stream 集合及其依赖一起记录下来。假设 DDP 在 non-capturing stream S0 上构造，Reducer 因而长期持有 stream=S0 的 AccumulateGrad；之后 forward/backward 改在 capture stream S_capture 上执行。此时 incoming gradient 的 producer 正在 capture，而节点的 canonical consumer stream 仍指向 capture 之外的 S0。若 Engine 直接让 S0 等待 S_capture 的 event，这条依赖会跨越 capture boundary。

torch.autograd.graph.set_override_stale_capture_stream(True) 为这个场景启用临时替代。InputBuffer::add() 检测到 “capturing producer + stale non-capturing consumer” 后，把 producer 的 S_capture 写入 opt_overridden_consumer_stream。Engine::evaluate_function() 随后优先使用这个值，而不是 func->stream()，所以 AccumulateGrad 及其 Reducer hook 在本次 capture 中以 S_capture 为 current stream。

# 机制示意：静态 input/output buffer 与 warmup 代码省略
capture_stream = torch.cuda.Stream(device=device)
graph = torch.cuda.CUDAGraph()

torch.autograd.graph.set_override_stale_capture_stream(True)
try:
    with torch.cuda.graph(graph, stream=capture_stream):
        loss = ddp(static_input).sum()
        loss.backward()
finally:
    # 该设置是 process-global，并非 thread-local。
    torch.autograd.graph.set_override_stale_capture_stream(False)
节点状态 override 关闭 override 开启
stale stream 是 default stream 0 PyTorch 抛出 RuntimeError，避免 default-stream wait 把 non-capturing stream 拉入 capture。 本次 InputBuffer 使用 producer 的 capturing stream。
stale stream 是 non-default stream 保留原 stream；调用方已把它 join 到 capture 时可以继续，否则由 CUDA runtime 报错。 同样临时替换为 producer 的 capturing stream。

InputBuffer 的字段定义说明了这项替代的生命周期：override 保存在当前 input buffer 中，供该 buffer 的后续 producer 和 Engine 执行共同使用；没有触发 override 时，Engine 仍回退到节点的 func->stream()。实现没有修改 AccumulateGrad 的 InputMetadata.stream_。capture 结束后，节点仍绑定原来的 S0，下一次符合条件的 capture 会再次临时替代。

这个开关还会跳过一种跨 capture boundary 的 end-of-backward leaf sync，适用于 incoming gradients 全部 undefined、无法在 InputBuffer 阶段完成 stream reconciliation 的特殊路径。它是 process-global 的 capture 兼容选项，不是一般的 stream 重绑定接口。能够控制初始化时机时，让 warmup、DDP 构造与 capture 采用一致的 stream 仍然更直接；override 适合处理 DDP 等长期持有的 stale 节点。

归纳起来，device 与 stream 需要分别确定：先用 set_device 和 .to(device)/.cuda(device) 固定参数设备，再在训练所采用的 current stream 中构造 DDP。这样，Reducer 所持有的 AccumulateGrad 从创建开始就与后续 backward 的执行环境一致。

Stream Binding of AccumulateGrad in PyTorch DDP

Single-process, single-GPU DDP training usually follows a fixed initialization order: select the local CUDA device, place the model parameters on that device, and then wrap the model with DistributedDataParallel. This order also establishes an autograd execution stream. During construction, DDP obtains each leaf parameter's AccumulateGrad node. If the node is created at that point, it records the current CUDA stream. When a gradient later reaches the parameter, the autograd Engine switches to the recorded stream before running gradient accumulation and the DDP hook. Default-stream training rarely exposes this behavior; custom streams and CUDA Graph capture make it an explicit constraint.

Scope and terminology

This article follows the CUDA eager path of standard torch.nn.parallel.DistributedDataParallel, with PyTorch pinned to commit 867370d. TorchRec and Megatron-Core are used as public engineering examples, not as definitions of stock DDP behavior; their wrappers also implement sharding and dedicated gradient buffers.

A node stream is the stream recorded for the first accelerator input when an autograd Node is created. Node::stream() returns it from the input metadata, and the Engine treats it as the Node's canonical consumer stream. For a leaf parameter, the Node responsible for writing the gradient is AccumulateGrad. The leaf Tensor itself still has param.grad_fn is None; the relationship is developed in more detail in The PyTorch Autograd Reverse Graph.

AccumulateGrad binds its stream when the node is created, not on every hook invocation. DDP construction normally triggers that creation, but if a retained node already exists, the Reducer reuses the node and its original stream.

DDP obtains and retains AccumulateGrad

After building its buckets, the DDP Python constructor creates a Reducer. The official DDP design note describes this construction step as registering one autograd hook per parameter; a hook starts the reduction path when its parameter gradient becomes ready. The Python entry point likewise lists gradient-hook registration among the responsibilities of _ddp_init_helper().

The Reducer constructor performs the concrete work for every trainable parameter:

// Semantic excerpt: torch/csrc/distributed/c10d/reducer.cpp
auto grad_accumulator = torch::autograd::impl::grad_accumulator(variable);

hooks_.emplace_back(
    grad_accumulator->add_post_hook(/* Reducer::autograd_hook */),
    grad_accumulator);

// Autograd metadata holds only a weak_ptr; Reducer retains a strong reference.
grad_accumulators_[variable_index] = std::move(grad_accumulator);

Pinned source: reducer.cpp, lines 173–237

grad_accumulator(variable) first checks the leaf parameter's weak reference. It returns an existing node or constructs a new AccumulateGrad. The Reducer then keeps a strong reference, allowing the node to survive across iterations. In the usual DDP lifecycle, wrapper construction is therefore also when the leaf accumulation nodes are created.

Ordinary eager autograd has a different lifetime. A leaf's autograd metadata caches only a weak reference to AccumulateGrad. The node remains alive while the current graph or another owner still references it, but it can be destroyed after those strong references are released. When a later graph requests the leaf's gradient edge, an expired weak reference cannot return the old node, so grad_accumulator() creates a new one under the current stream at that time. The pinned source explicitly describes releasing the old graph and its accumulation node between iterations as the normal lifecycle.

The DDP Reducer changes that lifetime. Its strong reference in grad_accumulators_ is independent of any one forward/backward graph, so releasing the loss and the old graph does not destroy these nodes. Their creation-time stream metadata remains in place for as long as the Reducer retains them. Moving only the next forward onto a capture stream therefore does not rebind them. Custom-stream or CUDA Graph training must construct DDP under the intended stream, or explicitly rebuild the wrapper that owns the nodes.

The current CUDA stream is captured at node creation

The AccumulateGrad constructor stores its leaf variable and calls add_input_metadata(variable). The pinned implementation is short:

AccumulateGrad::AccumulateGrad(Variable variable_)
    : Node(/*sequence_nr=*/UINT64_MAX), variable(std::move(variable_)) {
  add_input_metadata(variable);
}

InputMetadata uses the parameter's device type to query that device's current stream, then stores the result in stream_:

// torch/csrc/autograd/input_metadata.cpp
auto device_ = options.device();
stream_ = c10::impl::getDeviceGuardImpl(device_.type())->getStream(device_);

Pinned source: input_metadata.cpp, lines 28–42

The GPU parameter selects which CUDA device is queried, while the current stream during DDP construction determines which stream is recorded. model.cuda(device) handles parameter placement; with torch.cuda.stream(stream): DDP(...) directly controls the stream metadata of newly created AccumulateGrad nodes. These operations solve separate parts of initialization.

The Engine restores the node stream during backward

A backward kernel may produce the incoming parameter gradient on another stream. Once the gradient enters the AccumulateGrad input buffer, the Engine reads the node stream and installs an OptionalStreamGuard before invoking the Node and its post hooks. The pinned Engine::evaluate_function() also checks the incoming gradient's producer stream. When producer and consumer differ, the consumer stream waits on the producer event.

auto opt_parent_stream = inputs.opt_overridden_consumer_stream.has_value()
    ? inputs.opt_overridden_consumer_stream
    : func->stream();

c10::OptionalStreamGuard parent_stream_guard{opt_parent_stream};

if (*opt_parent_stream != *opt_ready_stream) {
  opt_parent_stream->wait(opt_ready_event.value());
}

// The Node and its post hooks now run under this current-stream context.

Saying that the hook runs on this stream spans two execution layers. An autograd worker thread invokes the C++ or Python callback on the CPU. The OptionalStreamGuard makes the node stream current during that callback, so CUDA operations launched by the callback are enqueued there. The CPU callback itself does not become a GPU kernel.

When producer and consumer are already the same stream, stream ordering satisfies the dependency and no cross-stream wait is required.

Reducer hooks and NCCL streams are separate execution layers

After AccumulateGrad updates param.grad, the Reducer post hook marks the parameter ready. The collective path begins only when its bucket is complete. ProcessGroupNCCL stream synchronization shows that asynchronous NCCL communication normally uses a managed ncclStream, with an event making it wait for the caller's current stream. The collective dispatch selects a separate NCCL stream in asynchronous mode and the current stream in synchronous mode.

Consequently, AccumulateGrad.stream == S0 means that gradient accumulation and the Reducer hook run under S0's current-stream context. It does not permanently bind the NCCL kernel to S0. ProcessGroup establishes the required dependency between those execution layers. Bucket readiness and collective launch are covered in PyTorch DDP Gradient Reduction.

GPU parameter placement precedes the DDP wrapper

DDP construction needs the final parameter set and device placement so it can validate devices, build buckets, and obtain each parameter's gradient accumulator. The official DistributedDataParallel reference states that a single-device CUDA module already resides on the sole device named by device_ids. With device_ids=None, the caller must place both the module and its inputs on the correct device. The pinned argument documentation contains the same contract.

The official DDP tutorial uses the direct ordering:

# PyTorch official DDP tutorial
model = ToyModel().to(rank)
ddp_model = DDP(model, device_ids=[rank])

Official tutorial: Getting Started with Distributed Data Parallel; pinned tutorial source: lines 133–147

.cuda(device) and .to(device) serve the same placement role here. The DDP wrapper does not move an ordinary CPU module to device_ids[0] on the caller's behalf. The official reference also warns against replacing parameters after wrapper construction: DDP has already registered reduction functions for the parameter set observed at that time. See the pinned DDP parameter warning.

TorchRec: select the device, place the model, then construct DDP

TorchRec's public BERT4Rec example obtains a device from LOCAL_RANK and calls torch.cuda.set_device(device). It then places the model with BERT4Rec(...).to(device) before choosing either standard DDP(model_bert4rec, device_ids=device_ids) or TorchRec DMP. The sequence is visible in commit 561502d: device initialization, model placement, and DDP construction.

Megatron-Core: device placement and custom-stream construction

Megatron-Core likewise executes model_module.cuda(torch.cuda.current_device()) before entering its DDP wrapper path; its meta-device path materializes parameters before wrapping as well. The pinned implementation appears in dist_utils.py.

It also handles the stream constraint directly. Full-iteration CUDA Graph mode selects the shared capture stream and comments that DDP initialization must use that stream so retained AccumulateGrad nodes do not reference a different non-capturing stream. The code then constructs the wrapper inside with torch.cuda.stream(ddp_stream); see the pinned stream selection. Megatron's custom DDP later reaches AccumulateGrad through a temporary view, attaches a hook, and retains the node, as shown in its hook registration.

Initialization patterns and stream-mismatch diagnostics

Ordinary DDP training uses the default stream of each device, so initialization can remain simple:

local_rank = int(os.environ["LOCAL_RANK"])
device = torch.device("cuda", local_rank)

torch.cuda.set_device(device)
dist.init_process_group("nccl", device_id=device)

model = Model().to(device)  # or Model().cuda(local_rank)
ddp = DDP(model, device_ids=[local_rank])

# Forward and backward also use this device's default current stream.

If training consistently uses a custom stream, parameter placement, DDP construction, and subsequent iterations should share that stream context:

torch.cuda.set_device(device)
train_stream = torch.cuda.Stream(device=device)

with torch.cuda.stream(train_stream):
    model = Model().to(device)
    ddp = DDP(model, device_ids=[local_rank])

with torch.cuda.stream(train_stream):
    output = ddp(batch.to(device, non_blocking=True))
    loss = loss_fn(output, target)
    loss.backward()

When several compute streams produce contributions for one parameter, its single AccumulateGrad still has one canonical consumer stream. Autograd preserves correctness with event dependencies; more producer streams can therefore introduce more cross-stream synchronization. This affects performance and CUDA Graph capture, not the gradient value of an eager backward that follows the dependency rules.

The pinned PyTorch version provides torch.autograd.graph.set_warn_on_accumulate_grad_stream_mismatch(). When enabled, the Engine warns once if an incoming gradient's producer stream differs from the AccumulateGrad stream. The diagnostic names DDP's retained node as one source and recommends initializing DDP under the stream used by later forwards; see the pinned InputBuffer mismatch handling.

torch.autograd.graph.set_warn_on_accumulate_grad_stream_mismatch(True)

with torch.cuda.stream(init_stream):
    ddp = DDP(model, device_ids=[local_rank])

with torch.cuda.stream(train_stream):
    ddp(input).sum().backward()
    # A mismatch warning is observable when init_stream != train_stream.

Temporary stream override during CUDA Graph capture

CUDA Graph capture records a set of streams and their dependencies. Suppose DDP was constructed on a non-capturing stream S0, leaving the Reducer with a long-lived AccumulateGrad whose stream is S0. Forward and backward later run on capture stream S_capture. The incoming gradient producer is now capturing, while the node's canonical consumer still points to S0 outside the capture. Making S0 wait on an event from S_capture would introduce a dependency across the capture boundary.

torch.autograd.graph.set_override_stale_capture_stream(True) enables a temporary substitution for this case. After InputBuffer::add() detects a capturing producer and a stale non-capturing consumer, it stores the producer's S_capture in opt_overridden_consumer_stream. Engine::evaluate_function() then prefers that value over func->stream(), so AccumulateGrad and its Reducer hook run with S_capture current for this capture.

# Mechanism sketch; static buffers and warmup are omitted.
capture_stream = torch.cuda.Stream(device=device)
graph = torch.cuda.CUDAGraph()

torch.autograd.graph.set_override_stale_capture_stream(True)
try:
    with torch.cuda.graph(graph, stream=capture_stream):
        loss = ddp(static_input).sum()
        loss.backward()
finally:
    # This setting is process-global, not thread-local.
    torch.autograd.graph.set_override_stale_capture_stream(False)
Node state Override disabled Override enabled
The stale stream is default stream 0 PyTorch raises RuntimeError before a default-stream wait pulls a non-capturing stream into the capture. The current InputBuffer uses the producer's capturing stream.
The stale stream is a non-default stream The original stream remains. Capture can proceed if the caller joined it; otherwise the CUDA runtime reports the failure. The producer's capturing stream temporarily replaces it as well.

The InputBuffer field definition establishes the lifetime of this substitution. The override belongs to the current input buffer and is shared by later producers feeding that buffer and by the Engine invocation. When no override fires, the Engine still falls back to func->stream(). The implementation does not mutate AccumulateGrad's InputMetadata.stream_. After capture, the node remains bound to S0; a later qualifying capture performs the temporary override again.

The flag also skips one end-of-backward leaf synchronization that would cross the capture boundary. This applies to a special path in which all incoming gradients are undefined and stream reconciliation cannot occur in InputBuffer. The flag is a process-global capture compatibility option, not a general stream-rebinding API. When initialization is controllable, one coherent stream design for warmup, DDP construction, and capture remains the direct setup; the override is useful for stale nodes retained by DDP and similar owners.

Device and stream must therefore be established separately: use set_device and .to(device)/.cuda(device) to fix parameter placement, then construct DDP under the current stream used by training. The AccumulateGrad nodes retained by the Reducer will then agree with the backward execution environment from the moment they are created.
