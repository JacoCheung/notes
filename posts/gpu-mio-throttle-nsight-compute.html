GPU MIO Throttle：队列反压、成因与诊断

CUDA kernel 执行 shared-memory 访问、特殊数学运算或动态分支时，相应的 SASS 指令会进入 MIO（Memory Input/Output）路径。一个 SM 上的多个 resident warp 可能在相近 cycle 到达这类指令，warp scheduler 因而会在短时间内向同一执行路径集中提交工作。下游 instruction queue 负责吸收这段到达突发；当新指令的到达速度暂时超过 queue 的排空速度时，queue 会逐步填满。Nsight Compute 把由此产生的发射等待记录为 MIO Throttle。

这种等待发生在指令发射之前。MIO Throttle 是 warp 的下一条指令需要进入 MIO，而 MIO instruction queue 暂时没有空位时形成的 stall。指令一旦发射，后续数据依赖便转由 scoreboard 等机制跟踪。本文沿用 Nsight Compute 2026.1 的公开定义，并把 instruction queue 作为 profiler 可见的逻辑边界；队列深度、端口、仲裁与物理连接不属于本文的推断范围。

1. MIO 的发射前边界

一条指令进入 eligible 集合，需要同时满足语义就绪和目标路径可接收两个条件。数据依赖与同步状态决定前一个条件，instruction queue 是否有空位决定后一个条件。MIO Throttle 对应接收条件暂时不满足：目标指令尚未发射，warp 仍处于 active 状态，却不能进入 eligible 集合。待指令成功发射后，consumer 对结果的等待才会表现为 Short Scoreboard 等完成依赖。下图把这两个阶段分开。

2. 动态 burst 与 queue 状态

明确发射边界以后，还需要解释 queue 如何从“可接收”变成“已满”。关键在于观察 burst 期间的 queue 状态，而不是只看整个 kernel 的平均指令率。把执行过程划分为宽度为 $\Delta$ 个 cycle 的窗口；$A_k$ 表示窗口 $k$ 内 scheduler 提供给 MIO 的指令需求，$D_k$ 表示同一窗口内从逻辑 queue 排出的条目，二者单位都是每个窗口的 warp-level instructions。$Q_k$ 是窗口开始时的 queue occupancy。于是，一个不指定物理端口和仲裁顺序的离散模型是：

\[ Q_{k+1} = \min\!\left( Q_{\max}, \max\!\left(0, Q_k + A_k - D_k\right) \right). \]

若定义窗口内的需求速率 $\lambda_k=A_k/\Delta$、服务速率 $\mu_k=D_k/\Delta$，则 $\lambda_k>\mu_k$ 只说明该窗口增加 queue occupancy。对于从窗口 $k$ 开始且中途没有排空的 burst，queue 是否填满取决于初始余量以及连续窗口中的累计净流入：

\[ \sum_{i=k}^{k+n-1}(A_i-D_i) \geq Q_{\max}-Q_k. \]

这里的 $Q_{\max}$ 是概念容量，不是公开的硬件队列深度。当 occupancy 到达这个边界，而某个 warp 的下一条指令仍需要 MIO 时，模型进入 NCU 所定义的 queue-full 等待。多个 warp 形成的短 burst 可以满足累计条件，即使更长时间尺度上的平均 $\lambda$ 不大于平均 $\mu$。Profiler 能采样这种等待，却不能仅凭 aggregate metric 还原各窗口的 $A_k$、$D_k$ 或实际到达顺序。

由此，MIO Throttle 描述的是发射需求相对于 queue 排出能力的压力，而非单条指令的数据延迟。这也解释了 occupancy 对该问题的双重影响：更多 resident warp 提供了额外的可调度工作，同时也可能提高 $A_k$。因此，当 MIO 服务速率已经构成限制时，增加 resident warp 仍可隐藏其他延迟，却不会扩大 MIO 的服务能力。两者的关系可结合《GPU Occupancy 的驻留资源模型与性能含义》中的 residency 模型理解。

3. 进入 MIO 的指令及其压力来源

排队模型中的 $A_k$ 和 $D_k$ 只有映射到具体指令后，才能转化为可诊断的原因。公开的 stall taxonomy 把 shared-memory instruction、special-math instruction 和 dynamic branch 列为 MIO 相关类别。因此，分析应先确认热点对应的 SASS opcode，再检查该类指令的到达速率和后端工作量。

3.1 Shared-memory 指令密度过高

连续的 shared-memory load/store 会快速向 MIO 路径提交工作。常见情形包括 fragment 搬运、shared-memory reduction、转置，以及同一数据被多次从 shared memory 读取。即使每次访问都没有 bank conflict，单位时间内的指令数仍可能超过队列和后端能够持续接收的速率。

指令宽度也会改变压力。若同样的数据由多条窄 load/store 完成，scheduler 需要发射更多 MIO 指令。NVIDIA 对 shared-memory 场景给出的建议是减少低宽度操作，条件允许时合并为更少、更宽的访问。

3.2 Bank conflict 增加 wavefront

当 shared-memory 指令数量不足以解释热点时，wavefront 提供了下一层线索。NCU 的 Source Metrics 分别报告 shared-memory instruction、实际 wavefront 和理想 wavefront；一条 warp-level 指令需要额外 wavefront 时，派生指标会把差额反映为 conflict。MIO Throttle 记录 queue-full 等待，而 wavefront 指标描述 shared-memory 操作的执行展开。若把额外 wavefront 视为有效服务速率下降，这仍是一项需要实验验证的排队推断，两个指标同时升高只能提供相关性。

当 Not-issued 样本已经落在 shared-memory opcode 时，诊断再同时观察两组信号：

  • mio_throttle 高且 bank-conflict 指标也高：layout、padding 或 swizzle 是合理候选。
  • mio_throttle 高但 bank conflict 接近零：更可能是 shared 指令数量或宽度本身造成的吞吐压力。

3.3 特殊数学指令集中出现

Special-math instruction 构成了另一类 MIO 输入。其具体 opcode 取决于 GPU 架构和编译结果，SASS 中常见的形式是 MUFU。Softmax、归一化和激活函数可能在很短的区间内密集执行这类指令，因此这类计算即使不访问 shared memory，也可能出现 MIO Throttle。

此时 shared-memory 指标不会给出对应证据。需要在 Source 页面检查 MIO 样本是否落在 MUFU 指令附近，并结合 Instruction Statistics 查看 opcode 与 pipe 分布。

3.4 动态分支增加 MIO 压力

控制流中的 MIO 压力对应 dynamic branch。官方文档列出的典型 SASS 指令包括 BRX 和 JMX；间接跳转、复杂 switch 或运行期计算目标地址的控制流可能生成这类指令。普通静态跳转则属于另一种情形。

动态分支还可能伴随 branch_resolving 或 no_instructions。这几类 stall 反映不同阶段：MIO Throttle 表示分支指令进不了队列，branch resolving 表示目标仍在解析，no instructions 则可能和取指或 instruction-cache miss 有关。

3.5 并发 warp 形成集中到达

前几类原因关注单条指令及其后端工作，而 burst 还取决于多个 warp 的到达相位。在排队模型中，循环展开、更多 active warp 或多个 producer warp 同时推进，都可能让原本分散的 MIO 指令集中到达。此时总指令数未必增加，queue 仍可能被短时 burst 填满。由于普通 PC sampling 缺少时间分辨率，这种到达形态需要通过改变展开、指令间隔或 warp role 后重新测量。

Warp specialization 下，producer warp 可能出现较多 MIO Throttle，而 consumer warp 仍在发射 tensor 或 FMA 指令。单看 stall 分布无法判断等待是否暴露到 kernel 时间；还要检查 scheduler 是否跳过 issue slot。

4. 发射前反压与发射后等待

确定热点 opcode 之后，还要判断等待发生在指令发射的哪一侧。队列反压表示目标指令尚未进入执行路径；结果依赖则表示 producer 已经发出，而 consumer 正在等待完成事件。这个时间边界决定了后续诊断应检查 instruction rate，还是转向 load-use 距离与结果延迟。

5. 从 SASS 形态建立可验证假设

完成 pre-issue / post-issue 分类后，诊断需要回到目标 GPU 上实际执行的 SASS，因为它是连接队列模型与源码的中间层。编译器可能消除未使用结果、复用寄存器中的值、改变访问宽度或重排指令，因此源码中的连续 shared-memory load 或特殊函数调用只能提供候选位置。静态 SASS 邻接同样缺少多个 warp 的到达相位信息。诊断应先把 Not-issued MIO samples 落到实际 SASS，再依据采样所在的 opcode 类别提出假设。

若热点落在 LDS、STS 或 LDSM，对照实验可以只改变 shared-memory 指令需求，例如复用已加载值，或在对齐与 layout 允许时把多条窄访问合成更少的宽访问。基线与变体必须保持输入、输出、block 配置和算法语义一致；计算结果要写入可观察的输出或参与后续可观察计算，并在反汇编中确认目标指令没有被 dead-code elimination 删除。

完成代码变体后，需要把静态变化与运行时结果接起来：动态 shared opcode 数应按预期变化，wavefront 与 bank-conflict 指标给出后端响应，MIO Not-issued samples 在同一热点发生变化，kernel duration 则说明等待是否暴露为性能损失。只有这些观察沿同一方向支持“$A_k$ 减少或 $D_k$ 的有效压力降低”，静态指令形态才构成队列反压的因果证据。对 MUFU 或 BRX/JMX 也可沿用这套方法，只需替换相应的 opcode 计数和代码变体。

6. 从 scheduler 到 SASS 的 NCU 证据链

SASS 热点给出了候选机制，完整诊断还要把它与 scheduler 的实际损失和后端工作量连接起来。证据链依次回答三个问题：MIO 等待是否造成未发射的 issue slot，样本集中在哪些 SASS 指令，相应后端是否存在足够的工作量。Warp State Statistics 中较大的 warp-cycles-per-issued-instruction 数值描述等待规模；scheduler 是否留下 issue gap，则由发射统计确认。

6.2 在 NCU UI 中定位原因

  1. Details → Scheduler Statistics：先看 issue slot 是否经常跳过，以及每个 scheduler 平均有多少 eligible warp。若 issue 基本持续，MIO stall 可能已被其他 warp 隐藏。
  2. Details → Warp State Statistics：确认 MIO Throttle 在每条已发射指令的 warp-cycle 中所占规模，并与 Short Scoreboard、LG Throttle、Long Scoreboard 比较。
  3. Source → Source and SASS：在 Source 页的 Navigate By 中选择 Warp Stall Sampling 或 Not-issued Samples，把 mio_throttle 样本落到 SASS 地址。
  4. 检查 opcode：LDS/STS/LDSM 指向 shared-memory 路径，MUFU 指向特殊数学，BRX/JMX 指向动态分支。
  5. Details → Memory Workload Analysis：只有热点属于 shared memory 时，才继续看 shared wavefront、bank conflict 和访问宽度。
  6. 回到源码建立因果关系：修改一项机制后重新采集。MIO 指标下降但 kernel 时间不变，说明该 stall 可能原本已经被隐藏，或瓶颈转移到了其他 pipe。

PC sampling 是周期采样，不是每次 stall 的完整计数。All Samples 与 Not-issued Samples 还可能来自不同 profiling pass，数值不能逐项相减。它们适合定位热点，不适合当作精确的时间分解。

GPU MIO Throttle: Queue Backpressure, Causes, and Diagnosis

When a CUDA kernel executes a shared-memory access, special-math operation, or dynamic branch, the corresponding SASS instruction enters the MIO (Memory Input/Output) path. Several resident warps on an SM may reach these instructions within a short interval, causing the warp schedulers to concentrate work on the same execution path. A downstream instruction queue absorbs the burst. If arrivals temporarily outpace the queue's drain rate, its occupancy rises until new instructions must wait. Nsight Compute reports that issue wait as MIO Throttle.

This wait occurs before instruction issue. MIO Throttle is the stall formed when a warp's next instruction requires MIO while the MIO instruction queue temporarily has no free entry. Once the instruction issues, mechanisms such as scoreboards take over the remaining data-dependency tracking. This article follows the public definition in Nsight Compute 2026.1 and treats the instruction queue as a profiler-visible logical boundary. Queue depth, ports, arbitration, and physical connections remain outside the article's inference boundary.

1. The pre-issue MIO boundary

An instruction enters the eligible set only when it is both semantically ready and acceptable to its target path. Data dependencies and synchronization state determine the first condition; a free instruction-queue entry determines the second. MIO Throttle corresponds to a temporary failure of the acceptance condition: the target instruction has not issued, and the warp remains active but cannot become eligible. After the instruction issues, a later consumer waiting for its result may instead enter a completion dependency such as Short Scoreboard. The diagram separates these two stages.

Logical diagnostic model: backpressure occurs before issue when the MIO instruction queue is full

This logical boundary also limits how the diagram should be read. The queue represents the acceptance state in the public stall reason and the documented shared-memory, special-math, and dynamic-branch instruction classes. Other NCU hardware models also use MIOC. The Nsight Compute 2022.3 Metrics Guide expands the name as Memory Input/Output Control but does not define its topology relative to the MIO queue. The diagram therefore does not place them in consecutive hardware stages.

2. Dynamic bursts and queue state

With the issue boundary established, the next question is how an accepting queue becomes full. The useful quantity is queue state during a burst rather than the kernel-wide average instruction rate. Divide execution into windows of $\Delta$ cycles. Let $A_k$ be the MIO instruction demand offered by schedulers during window $k$, and let $D_k$ be the entries drained from the logical queue during that window; both are measured in warp-level instructions per window. Let $Q_k$ be queue occupancy at the start of the window. This gives a discrete model that assigns no physical port or arbitration order:

\[ Q_{k+1} = \min\!\left( Q_{\max}, \max\!\left(0, Q_k + A_k - D_k\right) \right). \]

Define the window demand rate as $\lambda_k=A_k/\Delta$ and service rate as $\mu_k=D_k/\Delta$. The condition $\lambda_k>\mu_k$ says only that occupancy rises during that window. For a burst beginning at window $k$ without the queue emptying in between, filling the queue depends on its initial headroom and cumulative net input across consecutive windows:

\[ \sum_{i=k}^{k+n-1}(A_i-D_i) \geq Q_{\max}-Q_k. \]

Here, $Q_{\max}$ is a conceptual capacity, not a published queue depth. When occupancy reaches that boundary while a warp still offers another MIO instruction, the model enters the queue-full wait defined by NCU. A short burst from several warps can satisfy the cumulative condition even when long-run average $\lambda$ does not exceed average $\mu$. The profiler can sample the wait, but an aggregate metric cannot reconstruct $A_k$, $D_k$, or the physical arrival order.

MIO Throttle therefore describes issue demand relative to queue drain capacity rather than the data latency of one instruction. This model also exposes occupancy's dual effect: more resident warps provide additional schedulable work, yet may raise $A_k$ at the same time. Once MIO service rate is the limiting resource, extra resident warps can still hide other latencies but do not increase MIO service capacity. The residency model in GPU Occupancy: Residency Resource Model and Performance Interpretation provides the surrounding scheduler context.

3. Instructions entering MIO and their pressure sources

The queueing variables $A_k$ and $D_k$ become diagnosable only after they are mapped to concrete instructions. The public stall taxonomy associates MIO with shared-memory operations, special math, and dynamic branches. Analysis therefore begins by identifying the SASS opcode at the hotspot, then examining the arrival rate and backend work associated with that instruction class.

3.1 High shared-memory instruction density

Back-to-back shared-memory loads and stores feed work into the MIO path quickly. Common examples include fragment movement, shared-memory reductions, transposes, and repeated reads of the same shared data. Even without bank conflicts, the instruction rate can exceed what the queue and backend can sustain.

Instruction width also affects pressure. Moving the same data with many narrow loads or stores requires the scheduler to issue more MIO instructions. NVIDIA recommends reducing narrow shared-memory operations and combining them into fewer, wider accesses when alignment and layout permit.

3.2 Bank conflicts increase wavefronts

When shared-memory instruction count alone does not explain the hotspot, wavefronts provide the next layer of evidence. Nsight Compute Source Metrics report shared-memory instructions, actual wavefronts, and ideal wavefronts separately. Derived metrics report the excess when one warp-level instruction requires additional wavefronts. MIO Throttle records a full-queue wait, whereas wavefront metrics describe how a shared-memory operation expands during execution. Interpreting extra wavefronts as lower effective service rate remains a queueing hypothesis to test; a rise in both metrics establishes correlation only.

Once Not-issued samples have been localized to shared-memory opcodes, inspect both signal groups:

  • High mio_throttle with high bank-conflict metrics makes layout, padding, or swizzling reasonable candidates.
  • High mio_throttle with almost no bank conflicts points more directly to shared instruction count or width.

3.3 Bursts of special-math instructions

Special-math instructions form another source of MIO traffic. The concrete opcode depends on GPU architecture and compiler output, with MUFU being a common SASS form. Softmax, normalization, and activation functions can execute many such instructions in a short region, so these computations may show MIO Throttle even when they do not access shared memory.

Shared-memory metrics provide no evidence for that case. Use the Source page to check whether MIO samples land near MUFU instructions, then inspect opcode and pipe distributions in Instruction Statistics.

3.4 Dynamic-branch pressure

Control-flow pressure on MIO is associated with dynamic branches. The public documentation lists SASS instructions such as BRX and JMX; indirect jumps, complicated switches, or control flow with runtime-computed targets can generate them. Ordinary static jumps are a separate case.

Dynamic branches may also coincide with branch_resolving or no_instructions. These stalls belong to different stages: MIO Throttle means the branch instruction cannot enter the queue, branch resolving means the target is still being resolved, and no instructions can involve fetch or instruction-cache misses.

3.5 Concentrated arrivals from concurrent warps

The preceding causes concern individual instructions and backend work, while a burst also depends on arrival phase across warps. In the queueing model, loop unrolling, more active warps, or several producer warps making progress together may concentrate MIO arrivals that were previously spread out. The total instruction count can remain unchanged while the burst fills the queue. Because ordinary PC sampling lacks time resolution, this arrival pattern must be tested by changing unrolling, instruction spacing, or warp roles and collecting another report.

With warp specialization, producer warps may show substantial MIO Throttle while consumer warps continue issuing tensor or FMA instructions. A stall distribution alone cannot show whether the wait is exposed in kernel time. Check whether the scheduler skips issue slots.

4. Pre-issue pressure and post-issue waits

After identifying the hotspot opcode, diagnosis must locate the wait relative to instruction issue. Queue backpressure means that the target instruction has not entered its execution path; result dependence means that the producer has issued and a consumer is waiting for completion. This boundary determines whether the investigation should stay with instruction rate or move to load-use distance and result latency.

5. Building a testable hypothesis from SASS

After classifying the wait as pre-issue or post-issue, diagnosis returns to the actual SASS executed on the target GPU, which connects the queue model to source code. A compiler may eliminate unused results, reuse register-resident values, change access width, or reorder instructions, so consecutive shared-memory loads or special-function calls in source provide candidate locations only. Static SASS adjacency likewise lacks arrival-phase information across warps. Diagnosis should first map Not-issued MIO samples to actual SASS and then form a hypothesis from the sampled opcode class.

If the hotspot lands on LDS, STS, or LDSM, a controlled comparison can change only shared-memory instruction demand: reuse an already loaded value, or combine narrow accesses into fewer wider accesses when alignment and layout allow. Keep input, output, block configuration, and algorithmic semantics fixed. Make the result reach an observable output or a later observable computation, and confirm in the disassembly that dead-code elimination did not remove the target instructions.

After building the variant, connect the static change to runtime behavior. Dynamic shared opcode count should move as intended; wavefront and bank-conflict metrics show the backend response; MIO Not-issued samples reveal what happened at the same hotspot; and kernel duration shows whether the wait was exposed as a performance cost. Only consistent movement supporting a reduction in $A_k$ or effective pressure on $D_k$ makes the instruction pattern causal evidence for queue backpressure. The same method applies to MUFU or BRX/JMX after substituting the relevant opcode count and code variant.

6. Building an NCU evidence chain from scheduler to SASS

A SASS hotspot supplies a candidate mechanism; a complete diagnosis must connect it to scheduler loss and backend work. The evidence chain answers three questions in order: whether the MIO wait produces unissued issue slots, which SASS instructions receive the samples, and whether the corresponding backend shows enough work. A large warp-cycles-per-issued-instruction value in Warp State Statistics describes wait volume, while issue statistics determine whether the scheduler leaves issue gaps.

To build that evidence chain, first confirm which metrics exist for the target GPU and installed NCU version. Names vary across architectures and releases, so the strings below are local query patterns rather than a stable cross-version API:

6.2 Diagnosis in the NCU UI

  1. Details → Scheduler Statistics: check skipped issue slots and average eligible warps per scheduler. If issue remains sustained, other warps may already hide the MIO stall.
  2. Details → Warp State Statistics: assess MIO Throttle in warp cycles per issued instruction and compare it with Short Scoreboard, LG Throttle, and Long Scoreboard.
  3. Source → Source and SASS: on the Source page, select Warp Stall Sampling or Not-issued Samples under Navigate By and map mio_throttle samples to SASS addresses.
  4. Inspect opcodes: LDS/STS/LDSM indicate shared memory, MUFU indicates special math, and BRX/JMX indicate dynamic branches.
  5. Details → Memory Workload Analysis: continue to shared wavefronts, bank conflicts, and access width only when the hotspot belongs to shared memory.
  6. Establish causality from source: change one mechanism and collect a new report. If the MIO metric falls but kernel time does not, the stall was probably hidden or the bottleneck moved elsewhere.

PC sampling is periodic sampling, not a complete count of every stall. All Samples and Not-issued Samples may also come from different profiling passes and cannot be subtracted item by item. Use them to locate hotspots, not as an exact decomposition of time.

7. Evidence-driven optimization

Once issue loss, the SASS hotspot, and backend metrics point to the same mechanism, the evidence combination can select the optimization direction. The table maps the four causes above to one testable change while retaining the main cost introduced by each change.

EvidenceLikely causeTestable changeMain cost
High MIO; many shared instructions; few bank conflicts Shared-memory instruction-rate pressure Reuse loaded values, use wider aligned accesses when layout permits, and remove repeated LDS/STS Higher register use
High MIO; high shared wavefronts and bank conflicts Bank conflicts add wavefronts; causality with MIO remains to be tested Add padding, apply a swizzle, or change lane-to-bank mapping Address arithmetic and shared-memory capacity
MIO samples cluster on MUFU Special-function burst Reuse function results, remove unnecessary transcendental calls, or validate polynomial/FMA approximations when the error budget permits Numerical error and additional ordinary arithmetic
MIO samples cluster on BRX/JMX Dynamic-branch pressure Use static specialization, simplify indirect jumps, or restructure control flow Code size and number of compiled variants

Shared-memory instruction-rate pressure can also be addressed by changing the movement mechanism. Starting with Hopper (compute capability 9.0), TMA moves tensors between global and shared memory with bulk asynchronous copies, reducing the data-movement instructions that the scheduler must issue. The corresponding costs are tensor-map descriptors, synchronization, and alignment and layout constraints. The target kernel's SASS and Nsight Compute report must still confirm the effect on MIO pressure.
