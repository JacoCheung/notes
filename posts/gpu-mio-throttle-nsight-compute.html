GPU MIO Throttle 分析

MIO Throttle 是 Nsight Compute 中与指令发射等待有关的一类 warp stall 指标，shared-memory 密集的 kernel 是其常见分析场景。本文说明该指标的观察范围与性能含义，通过 shared tile 的标量和宽访问对照，区分指令数量、bank conflict 与实际耗时，并给出热点定位、指标采集和优化验证的方法。

Shared-memory 热点可能同时包含频繁的窄访问、bank conflict 和已被其他 warp 覆盖的等待。文中的 shared tile 对照分别检查这些因素及其对发射机会的影响，用相同工作量下的 kernel 耗时评估代码与 layout 改动的价值。

阅读重点：先判断 scheduler 是否失去发射机会，再把 MIO 样本定位到具体指令。变体的价值最终由相同工作量下的 kernel 耗时决定。

1. Shared Load 的等待类型

SM 上的 warp scheduler 从驻留 warp 中选择能够发射下一条指令的 warp。对 shared-memory load 来说，数据依赖满足之后，目标路径也必须能接收这条指令。MIO Throttle 是下一条指令需要进入 MIO，而 MIO instruction queue 没有可用条目时记录的发射前等待。Nsight Compute 2026.1 将 shared-memory、special-math 和 dynamic-branch 指令列为相关类别。

以 LDS R8, [R2] 为例：它尚未发射、正在等队列空位时，可以出现 MIO Throttle；它已经发射，而后面的 FADD 正在等 R8 时，对应的则可能是 Short Scoreboard。两种等待会把优化引向不同位置。前者需要检查发射需求与接收能力，后者需要回看产生结果的操作，以及 consumer 前面是否还有可执行的独立工作。

这是一幅基于 profiler 定义的事件图。队列深度、仲裁和内部物理连接并未由该定义给出。更完整的 scheduler 状态可参见《GPU Warp Stall 分析》；结果依赖的跟踪过程见《GPU Scoreboard 机制》。

2. 性能影响评估

2.1 Scheduler 发射指标

一个 warp 等待 MIO 时，同一 scheduler 仍可能选择其他 warp。于是，Warp State Statistics 可以显示较多等待，kernel 却未必因此留下同等规模的空闲时间。读报告时先打开 Details → Scheduler Statistics，看发射是否存在空档、平均有多少 eligible warp；然后用 Warp State Statistics 判断这些等待中 MIO 占多大规模。NCU 的章节说明也把 scheduler 未能持续发射作为进一步分析 stall 的入口。

如果发射机会持续得到利用，单纯降低 MIO 样本数通常没有足够的优先级。如果存在明显发射空档，则继续定位 MIO 等待与哪些指令相关。这里得到的是调查顺序；其他 warp 能填补发射机会，也不保证整个 kernel 的工作安排已经最优。

2.2 指令采样定位

在 Source 页同时显示源码与 SASS，通过 Navigate By 选择 Warp Stall Sampling / Not-issued Samples。这组样本只取自 scheduler 没有发射指令的采样周期。若 MIO 样本集中在 LDS、STS 或 LDSM 一带，才进入 shared-memory 的指令数、访问宽度与 wavefront 分析；若落在 MUFU 或动态分支处，则转向第 4 节。

NCU 的Source 页面文档区分了 All Samples 和 Not-issued Samples。它们可能来自不同 profiling pass，不能逐项相减，也不能把样本比例直接换算成可节省的 kernel 时间。对照实验还需要独立保留耗时测量。

3. Shared Tile 读取对照

这里采用教学演示：代码给出确定的地址和输出，SASS 用于展示一种待验证的编译结果。它没有对应的实测 NCU 报告，也不预设两种写法谁更快。这个小片段把 tile 从 global memory 写入 shared memory，再让每个 warp 读取另一个 warp 准备的数据；实际应用中，这样的读取可以位于 tile 重排或计算阶段。

3.1 对照实验设计

下面是 CUDA C++17 kernel，约定一维 grid 和 block，block 大小为 (128, 1, 1)，输入和输出分别至少包含 128 × gridDim.x 个 float4 和 float，两者不重叠。__syncthreads() 保证 tile 写入完成；循环移位后的 j 让每个 warp 读取另一个 warp 写入的数据。两种实例都按同样的加法顺序生成可观察输出。

template <bool Wide>
__global__ void read_tile(const float4* in, float* out) {
    __shared__ float4 tile[128];
    unsigned t = threadIdx.x;
    unsigned i = blockIdx.x * 128 + t;
    tile[t] = in[i];
    __syncthreads();

    unsigned j = (t + 32) & 127;
    float4 v;
    if constexpr (Wide) {
        v = tile[j];
    } else {
        v.x = tile[j].x;
        v.y = tile[j].y;
        v.z = tile[j].z;
        v.w = tile[j].w;
    }
    out[i] = ((v.x + v.y) + v.z) + v.w;
}

对照 A 实例化 read_tile<false>，逐分量读取；对照 B 实例化 read_tile<true>，使用一次 float4 赋值。block 配置、shared-memory 容量、同步、全局访问和结果表达式保持一致。这个 kernel 只用来展开诊断过程；在这项简单运算里，直接从 global memory 读取也可以得到结果，不能据此评价一个需要 shared-memory 复用的完整算法。

3.2 编译结果核对

源码中有四次成员访问，并不保证机器码中有四条 load。编译器可能把它们合并，也可能因代码上下文改变访问宽度。因此，实验的第一项结果应来自目标 GPU 的反汇编。下面的 SASS 是假设 A 保留四条标量 load、B 生成一条 128-bit load 时的示意，省略地址计算、控制字段和后续运算，不能当作这段源码的实际编译输出：

// A: four scalar loads; illustrative only
LDS       R8,  [R2+0x00]
LDS       R9,  [R2+0x04]
LDS       R10, [R2+0x08]
LDS       R11, [R2+0x0c]

// B: one vector load; illustrative only
LDS.128   R8,  [R2]

若实际输出符合这幅对照，每个完整 warp 在该读取位置的 load 发射数从 4 条变成 1 条，每个 lane 仍然读取 16 字节。128 个线程对应 4 个 warp，因此这段读取的静态路径每个 block 从 16 次 warp-level load 发射变为 4 次。这里计算的只是该片段的发射次数，尚未给出执行时间。若两种实例都已经生成同样的宽 load，对照便没有改变所要研究的指令需求，应停止用它解释 MIO 的变化。

3.3 后端工作量差异

对一个完整 warp，设 lane 编号为 $\ell$，分量编号为 $c\in\{0,1,2,3\}$。代码中的 j 可以写成 $32w+\ell$，其中 $w$ 是被读取的 warp 区段。因此，以 tile 起点为基准的 32-bit word 地址为 $128w+4\ell+c$。公共偏移 $128w$ 不改变模 32 的 bank 编号。按照 CUDA 对 compute capability 5.x 及更新设备的32 个 shared-memory bank 的映射说明，bank 编号是 $(4\ell+c)\bmod32$。A 的每条标量 load 固定一个 $c$，32 个 lane 分布到 8 个 bank，每个 bank 对应 4 个不同的 word；在这个标量访问模型下存在 4 路冲突。

B 读取的地址集合相同，但这些 word 被归入一条更宽的指令。它仍需要处理一个 warp 的 512 字节，不能把“一条 load”理解成“一份后端工作”，也不能把 A 的单条标量冲突倍数直接套给 B。NCU 的 Source Metrics 用实际与理想 shared wavefront 区分访问自身需要的工作和额外展开。Wavefront 在这里是后端可处理的一份工作；一条指令可以产生多份。

因此，这个变体可能同时改变发射次数和访问分组。若 MIO 与 bank conflict 都改善，仅凭这一次对照无法把收益全部归因于“少发射三条指令”。若 wavefront 总量近似不变、发射次数减少，则更接近单独检验指令需求的假设。实际反汇编和计数决定这次实验属于哪种情况。

3.4 实验结论与边界

在这个 tile 示例中，目前确定的是两份源码访问同一组数据、产生同样的计算结果；在假设的 SASS 对照中，B 减少了该位置的 load 发射次数。要进一步声称降低了 MIO 带来的性能损失，还缺运行时证据。下面几种可能结果分别对应不同结论：

对照中观察到的变化能够支持的判断下一步
SASS 与动态 load 次数相同没有形成预期的指令需求对照重新选择实际存在窄 load 的位置
Load 次数减少，MIO Not-issued 样本减少，耗时稳定下降支持改动有益，并与该位置等待减轻的解释一致结合 wavefront 变化区分发射需求与后端展开的影响
MIO 样本减少，耗时没有稳定改善尚未证明这项改动值得保留检查等待是否已被隐藏，或成本是否转移到别处
Load 次数减少，寄存器占用或其他等待上升局部节省伴随新的成本对照完整 kernel 的资源使用和耗时

Warp State Statistics 按已发射指令数归一化，这个分母会随变体变化，PC 样本也有采样波动。表中的判断需要相同输入和工作量下的对照，并结合动态 opcode 次数、实际和理想 wavefront、MIO Not-issued 热点以及独立的计时结果。

4. 其他指令热点

4.1 MUFU 与结果复用

Softmax 或激活函数中的特殊数学运算可能生成 MUFU。如果 MIO 样本集中在这类 opcode 上，上面的 shared-memory 对照就不适用。沿源代码检查同一结果是否重复计算，结合实际 opcode 计数判断复用是否减少了工作。若进一步改用多项式或 FMA 近似，需要单独验证误差范围；结果精度是这个方向的成本。

4.2 动态分支与代码布局

BRX、JMX 一类动态分支也在 NCU 的 MIO 相关指令范围内。只有实际 SASS 出现相应热点时，才考虑简化间接跳转或对运行期选项做静态特化。普通源码中的 if 不足以说明有这类指令。特化可能减少动态控制流，也会增加代码体积和编译变体，应把 instruction-cache 和取指等待一起纳入复测。

4.3 请求集中与队列压力

循环展开或多个 warp 推进到同一段代码，可能把指令需求集中到更短的区间。队列在 burst 期间承受的压力与整个 kernel 的平均指令率不同，但静态 SASS 和汇总采样无法还原 warp 的到达顺序。改变展开程度或指令间隔可以检验这个假设，同时需要记录寄存器数与其他指令的变化。

这也连接到《GPU Occupancy 与资源约束》：更多 resident warp 提供了更多可调度工作，也可能增加同一类指令的集中需求。occupancy 的变化没有直接给出 MIO 的服务能力，仍需从实际发射与耗时判断效果。

5. Kernel 性能验证

先验证输出，再记录 GPU、CUDA/NCU 版本、编译选项、输入规模和 launch 配置。耗时比较需要固定测量边界，完成预热，用 CUDA events 或等价的同步测量反复运行，报告聚合值和波动，并留意时钟与其他 GPU 工作。Profiler 采样用于解释原因；replay 条件下的一次报告不能代替稳定的耗时对照。

若宽访问有效，下一步是在完整 kernel 和其他输入规模上确认收益，而非继续追求更低的 MIO 数字。若已确认访问宽度发生变化，却没有稳定收益，就需要检查局部节省是否被其他成本抵消，或原来的等待是否已被覆盖。后续实验由这次对照留下的疑点决定，例如寄存器用量增加、wavefront 未减少，或者耗时主要落在另一段代码。

附录 B：队列模型边界

把一段执行时间划分成若干窗口，令 $Q_k$ 为窗口开始时的逻辑 queue 条目数，$I_k$ 为窗口内实际获准进入的条目数，$D_k$ 为实际排出的条目数。若这些事件覆盖了条目的全部进出，便有守恒关系：

\[ Q_{k+1}=Q_k+I_k-D_k,\qquad 0\leq Q_k\leq C. \]

$C$ 只是模型中的容量，不代表公开的硬件深度。Scheduler 提出的需求可以多于获准进入的 $I_k$；没有被接收的指令仍在 warp 处等待。需求不能直接代替 $I_k$ 填入守恒式，否则会把受反压阻止的指令算成已经入队。

这个模型说明了两种可调查的方向：减少一段时间内送来的工作，或减少每次访问在后端产生的工作。它也保留一个限制：窗口内先到达、后排出，与先排出、后到达，可能有不同的满队列经历。只有汇总计数时，不能从窗口首尾状态推出每个时刻的等待，更不能反推真实队列深度。

GPU MIO Throttle analysis

MIO Throttle is a Nsight Compute warp-stall metric associated with instruction-issue waits, often investigated in shared-memory-intensive kernels. This article explains its scope and performance implications, compares scalar and wider shared-tile accesses to separate instruction count, bank conflicts and elapsed time, and provides methods for locating hotspots, collecting metrics and validating changes.

A shared-memory hotspot can combine frequent narrow accesses, bank conflicts and waits already covered by other warps. The shared-tile comparison examines these factors and their effect on issue opportunities, using kernel time for equal work to assess code and layout changes.

Reading focus: Check whether the scheduler loses issue opportunities, then locate MIO samples at specific instructions. Judge a variant by kernel time for the same amount of work.

Quick access: 2. Performance impact · 3. Shared-tile access comparison · 3.3 Backend work differences · 3.4 Findings and limits · Appendix A: Metric collection

1. Shared-load wait types

A warp scheduler selects a resident warp that can issue its next instruction. A shared-memory load needs both satisfied dependencies and a path able to accept it. MIO Throttle is the pre-issue wait recorded when the next instruction needs MIO and the MIO instruction queue has no available entry. Nsight Compute 2026.1 lists shared-memory operations, special math, and dynamic branches among the associated instruction classes.

Consider LDS R8, [R2]. It can encounter MIO Throttle while it waits for a queue entry before issue. Once it has issued, a later FADD waiting for R8 may instead encounter Short Scoreboard. These waits point the investigation to different places. The former concerns instruction demand and acceptance; the latter calls for examining the operation producing the result and the independent work available before its consumer.

This is an event diagram based on profiler definitions. Those definitions do not establish queue depth, arbitration, or physical connections. GPU Warp Stall Analysis covers the broader scheduler state model, while GPU Scoreboard Mechanism follows result-dependency tracking.

2. Performance impact

2.1 Scheduler issue metrics

While one warp waits for MIO, its scheduler may issue an instruction from another warp. Warp State Statistics can therefore show substantial waiting without an equivalent amount of idle kernel time. Start with Details → Scheduler Statistics: examine issue gaps and average eligible warps. Then use Warp State Statistics to assess how much of the waiting is associated with MIO. NCU's section descriptions likewise use a scheduler's failure to issue continuously as the entry point for stall analysis.

If issue opportunities remain occupied, reducing MIO samples alone usually has little justification as the next priority. If there are substantial gaps, continue by identifying the instructions associated with the MIO waits. This establishes an investigation order; filling issue opportunities with other warps does not by itself prove that the whole kernel is optimally organized.

2.2 Instruction sample attribution

On the Source page, show source code alongside SASS and select Warp Stall Sampling / Not-issued Samples under Navigate By. These samples come from cycles in which the scheduler issued no instruction. When MIO samples cluster around LDS, STS, or LDSM, investigate shared-memory instruction count, access width, and wavefronts. A hotspot on MUFU or a dynamic branch instead leads to Section 4.

The Source page documentation distinguishes All Samples from Not-issued Samples. They may come from different profiling passes, so their values cannot be subtracted entry by entry. Nor is a sample percentage a direct estimate of time recoverable by an optimization. Keep a separate timing comparison for the variant.

3. Shared-tile access comparison

This is a worked teaching example. The code specifies actual addresses and an observable output; the SASS illustrates a compiler outcome that must be checked. There is no measured NCU report behind it, and it does not assume either version is faster. The small kernel stages a tile from global into shared memory, then has each warp read data prepared by another warp. Such reads can sit within a tile rearrangement or computation stage in a larger application.

3.1 Experiment design

The CUDA C++17 kernel below assumes a one-dimensional grid and blocks of (128, 1, 1) threads, and non-overlapping input and output arrays containing at least 128 × gridDim.x elements of float4 and float, respectively. __syncthreads() completes the tile handoff, and the rotated index j selects data from another warp. Both instantiations produce an observable output using the same addition order.

template <bool Wide>
__global__ void read_tile(const float4* in, float* out) {
    __shared__ float4 tile[128];
    unsigned t = threadIdx.x;
    unsigned i = blockIdx.x * 128 + t;
    tile[t] = in[i];
    __syncthreads();

    unsigned j = (t + 32) & 127;
    float4 v;
    if constexpr (Wide) {
        v = tile[j];
    } else {
        v.x = tile[j].x;
        v.y = tile[j].y;
        v.z = tile[j].z;
        v.w = tile[j].w;
    }
    out[i] = ((v.x + v.y) + v.z) + v.w;
}

Version A instantiates read_tile<false> and reads the components separately. Version B instantiates read_tile<true> and uses one float4 assignment. Block configuration, shared-memory capacity, synchronization, global accesses, and the result expression remain the same. This kernel is an aid to diagnosis: the simple computation could also read global memory directly. It cannot establish the value of shared-memory reuse in a complete algorithm.

3.2 Compiler-output checks

Four member accesses in source do not guarantee four machine loads. The compiler may combine them or change the access width according to the surrounding code. The first experimental result must therefore come from disassembly for the target GPU. The following is schematic SASS, assuming A retains four scalar loads and B generates one 128-bit load. It omits address calculation, control fields, and subsequent arithmetic; it is not recorded compiler output for this kernel:

// A: four scalar loads; illustrative only
LDS       R8,  [R2+0x00]
LDS       R9,  [R2+0x04]
LDS       R10, [R2+0x08]
LDS       R11, [R2+0x0c]

// B: one vector load; illustrative only
LDS.128   R8,  [R2]

If actual disassembly matches this comparison, each full warp issues four loads at this location in A and one in B, while each lane still reads 16 bytes. With four warps in the 128-thread block, the fragment accounts for 16 warp-level load issues per block in A and four in B. This counts instruction issues in the fragment, not execution time. If both instantiations already produce the same wide load, the comparison has not changed the instruction demand under investigation and cannot explain an MIO change on that basis.

3.3 Backend work differences

For a full warp, let $\ell$ be the lane index and $c\in\{0,1,2,3\}$ the component index. The code's j equals $32w+\ell$, where $w$ identifies the warp-sized region being read. Relative to the tile base, the 32-bit word address is $128w+4\ell+c$. The common offset $128w$ leaves the bank index modulo 32 unchanged. Under CUDA's documented 32-bank shared-memory mapping for compute capability 5.x and newer, the bank index is $(4\ell+c)\bmod32$. Each scalar load in A fixes one $c$: the 32 lanes touch eight banks, with four distinct words in each bank. That scalar access model has a four-way conflict.

B reads the same address set, but groups the words into one wider instruction. It still processes 512 bytes for a full warp. One load does not mean one unit of backend work, and the conflict factor from A's individual scalar load cannot simply be transferred to B. NCU Source Metrics distinguish actual and ideal shared wavefronts, separating the work inherent in an access from excess expansion. A wavefront here is a package of backend work; an instruction can produce several.

The variant may therefore change both instruction issue count and access grouping. If MIO and bank-conflict metrics both improve, this single comparison cannot attribute all of the benefit to issuing three fewer instructions. If total wavefronts remain approximately unchanged while issue count falls, the comparison comes closer to isolating instruction demand. Actual disassembly and counts determine which experiment has taken place.

3.4 Findings and limits

In this tile example, both source versions access the same data and compute the same result. Under the assumed SASS comparison, B reduces load issues at that location. A claim that it reduces the performance cost of MIO still needs runtime evidence. The following possible results support different conclusions:

4. Other instruction hotspots

4.1 MUFU and result reuse

Special math in softmax or activation functions may generate MUFU. When MIO samples cluster there, the shared-memory comparison above does not apply. Trace the opcode back to source, check whether a result is computed repeatedly, and use actual opcode counts to establish whether reuse removes work. Replacing the function with a polynomial or FMA approximation requires a separate error-range validation; numerical accuracy is part of that tradeoff.

4.2 Dynamic branches and code layout

Dynamic branches such as BRX and JMX also belong to NCU's MIO-related instruction classes. Consider simplifying indirect jumps or statically specializing runtime options when actual SASS shows the corresponding hotspot. An if in source alone does not establish such an instruction. Specialization can reduce dynamic control flow while increasing code size and the number of compiled variants, so include instruction-cache and fetch waits in the next measurement.

4.3 Request bursts and queue pressure

Loop unrolling or several warps reaching the same code region may concentrate instruction demand into a shorter interval. Queue pressure during a burst differs from the kernel-wide average instruction rate, but static SASS and aggregate samples cannot reconstruct arrival order across warps. Changing unrolling or instruction spacing can test the hypothesis, provided register use and other instruction changes are also recorded.

This connects to GPU occupancy and resource limits. More resident warps supply more schedulable work and may also concentrate demand on one instruction class. A change in occupancy does not establish a change in MIO service capacity. Its effect still has to be judged through issue activity and kernel time.

5. Kernel performance validation

Validate output first, then record the GPU, CUDA and NCU versions, compiler options, input size, and launch configuration. Keep timing boundaries fixed, warm up the workload, and repeat runs using CUDA events or an equivalent synchronized measurement. Report an aggregate and its variation, with attention to clocks and other GPU activity. Profiler samples explain the behavior; one report collected under replay is not a substitute for a stable timing comparison.

If wider accesses help, the next step is to confirm the benefit in the complete kernel and across other input sizes. If the access width did change but timing did not improve, investigate whether another cost offsets the local saving or whether the original wait was already covered. The next experiment should address a specific unresolved observation, such as increased register use, unchanged wavefronts, or time concentrated in another region of code.

Appendix B: Queue-model limits

Divide execution into windows. Let $Q_k$ be the number of logical queue entries at the start of window $k$, $I_k$ the entries actually admitted during it, and $D_k$ the entries actually drained. If those events account for all arrivals and departures, conservation gives:

\[ Q_{k+1}=Q_k+I_k-D_k,\qquad 0\leq Q_k\leq C. \]

$C$ is a model capacity, not a published hardware depth. Scheduler demand can exceed admitted entries $I_k$; an instruction that is not accepted remains waiting at its warp. Substituting demand directly for $I_k$ would count instructions stopped by backpressure as though they had entered the queue.

The model suggests two directions to investigate: reduce the work offered in an interval, or reduce the backend work generated by each access. It also retains a limitation. Arrivals followed by departures can have a different queue-full history from departures followed by arrivals. Aggregate counts and boundary states cannot recover the wait at every instant, or reveal the physical queue depth.
