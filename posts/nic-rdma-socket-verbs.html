网卡与 RDMA：从 socket 到 verbs

DMA 技术允许网卡直接访问 host 内存，但是普通的 TCP socket 模式仍然需要 CPU 参与大量工作，比如处理协议、管理缓冲区（用户态和内核态数据搬运）。而 RDMA 则减少了 CPU 的参与：直接注册用户态内存 buffer、建立访问权限后，应用可以在用户态提交读写请求，由网卡直接访问对端指定的内存。

本文以 4 KiB 跨节点传输为例，对照 TCP socket 与 RDMA Write 的数据路径，结合 mlx5 源码解释描述符、doorbell 和完成队列的协作。重点分析用户态库与内核驱动的分工：如何通过设备文件建立资源与访问权限，如何在用户态提交请求，以及应用如何确认传输完成。

源码基线：Linux 6.12、rdma-core 61.0，核对日期 2026-11-10；send 封装采用 glibc 2.40。链接固定到 tag 或 commit，按节汇总在源码索引中。RDMA Write 序列图按源码调用顺序绘制，activation bar 标示参与者的逻辑活动范围。

1. 网卡与内存

以 PCIe 网卡为例，CPU 与网卡通过两类地址交互。网卡的 BAR（Base Address Register）描述设备的地址窗口；驱动映射其中的寄存器区域后，CPU 的 load / store 就能发起 MMIO（Memory-Mapped I/O，内存映射 I/O）访问。网卡访问主机内存则使用 DMA（Direct Memory Access，直接内存访问），由驱动通过 Linux DMA API 建立映射。IOMMU 位于主机的 I/O 子系统中。启用地址翻译时，网卡用 I/O 虚拟地址（IOVA）发起 DMA 请求；请求经 PCIe 到达主机后，IOMMU 将 IOVA 转换为主机物理地址，并检查访问权限。DMA 地址与映射 · 主机侧 DMA 重映射

CPU 把“从哪里取数据、发多少字节”写成描述符，放进内存中的环形队列；网卡读取描述符后执行传输。在 mlx5 的常规发送路径中，一次请求经过以下四步：

步骤执行者动作
① 写描述符CPU在发送队列 SQ 的环中写一个 WQE（Work Queue Element），记录操作类型、buffer 地址和长度。
② 敲 doorbellCPU先在内存中的 DBR（Doorbell Record）记下新的生产者序号，再写 BAR 中 UAR（User Access Region）页上的 doorbell 寄存器。后者是一次 MMIO 写，经 PCIe 到达网卡。
③ 执行网卡DMA 读取 WQE 及其指向的数据，按协议发往网络。
④ 完成网卡按完成配置将 CQE（Completion Queue Entry）DMA 写入完成队列 CQ，按配置触发中断，或等待软件轮询。

软件负责 ①②，网卡负责 ③④。socket 和 RDMA verbs 都使用这类队列机制：第 2 节的 socket 路径由内核以太网驱动提交工作，第 3 节的 verbs 路径由用户态驱动 libmlx5 提交。两者共用网卡，却把请求提交放在了不同的执行位置。

2. TCP socket 路径

A 通过一条已建立的 IPv4 TCP 连接把 4 KiB 发给 B。这里采用普通的拷贝式 send() / recv()，并取两次调用都完整处理 4096 字节的情况。send() 声明在 <sys/socket.h>，应用先调用 C 库封装，再进入内核。以 Linux x86-64 和 glibc 2.40 为例，发送路径如下：

用户态
  send(fd, buf, 4096, 0)                    # 应用调用 socket 发送接口
    → __libc_send()                         # glibc 的封装
    → sendto(fd, buf, 4096, 0, NULL, 0)      # 选择 sendto 系统调用
                ↓ syscall：进入内核态

内核态
  __sys_sendto()
    → sockfd_lookup_light(fd, ...)          # 根据 fd 查找 socket
    → __sock_sendmsg()
    → sock_sendmsg_nosec()                  # 分派到 socket 的 sendmsg 操作
    → inet_sendmsg()                        # 本例为 IPv4 socket
    → tcp_sendmsg()                         # 按 socket 的协议选择 TCP
    → tcp_sendmsg_locked()                  # 把 4 KiB 拷进 skb 的页
    → tcp_write_xmit() … dev_queue_xmit()   # TCP/IP 发送路径，交给网卡驱动
    → mlx5e_xmit()                          # DMA 映射数据页，在 SQ 环写 WQE  ①
    → mlx5e_notify_hw()                     # 写 DBR，再写 UAR doorbell      ②

网卡 A：DMA 读取数据，按以太网帧发出                                            ③

sendto 的目标地址参数为 NULL, 0，表示使用 socket 已关联的对端。内核根据 fd 找到 socket 后，经操作表选择 IPv4 和 TCP 的实现，再进入原有的协议栈与网卡驱动路径。glibc send 封装 · x86-64 系统调用表 · 内核 sendto 入口 · socket 操作分派 · TCP / UDP 分派 · tcp_sendmsg

在这条 socket 路径中，B 的网卡先把数据写入驱动预先投递的接收 buffer。B 的 CPU 随后处理 TCP/IP 协议，应用通过 recv() 取得数据：

网卡 B：DMA 写入预先投递的接收 buffer，写 CQE，触发中断               ④
mlx5_eq_comp_int() → napi_schedule()       # 中断里只调度 NAPI
mlx5e_napi_poll() → mlx5e_poll_rx_cq()     # 软中断中读 CQE，构造 skb
  napi_gro_receive() … tcp_v4_rcv()        # TCP 处理，挂进 socket 接收队列
recv(fd, buf, 4096, 0)                     # 系统调用：拷贝到用户 buffer

这个例子中，两端各经过一次用户态与内核态之间的数据拷贝；CPU 还负责系统调用、协议处理和驱动队列管理。接收侧用中断唤起 NAPI，再批量处理完成队列。TCP 是字节流，实际程序要根据 send() 和 recv() 的返回值继续处理剩余字节，系统调用次数和中断次数都不与 4 KiB 一一对应。send(2) · recv(2)

拷贝式发送成功返回后，应用可以复用已被内核接收的那部分源 buffer；此时对端应用可能还没有读到数据。MSG_ZEROCOPY 则用页面固定和完成通知替代发送侧拷贝，源 buffer 要等通知后才能复用。Linux 文档给出的经验范围是约 10 KB 以上的写入才通常受益，因此这里的 4 KiB 例子仍采用拷贝路径。MSG_ZEROCOPY

普通 socket 收发已经使用本机 DMA。RDMA 增加的是网卡可执行的远端内存操作：A 在请求中指定 B 的内存地址和访问 key，B 的网卡校验后直接写入该 buffer，省去本次数据交付中的接收端协议栈处理与用户态拷贝。RDMA 操作

3. RDMA Write 路径

仍然传输同一块 4 KiB 数据，改用 RC（Reliable Connection，可靠连接）上的 RDMA Write。两端先注册内存、建立连接，A 再提交写请求。应用调用通用的 verbs API，由设备专用的用户态实现 provider 完成硬件操作；ConnectX 对应的 provider 是 libmlx5。表中 socket 一列用于比较各步骤的用途。

顺序verbs 调用得到什么socket 中的对应
1ibv_open_device()设备 context，内含打开 /dev/infiniband/uverbsN 得到的命令 fd。socket()
2ibv_alloc_pd()保护域 PD（Protection Domain）。QP 使用的本地 MR 属于同一 PD。无
3ibv_reg_mr()内存区域 MR（Memory Region）：固定 buffer 所在的页，为网卡建立地址翻译和访问权限，返回 lkey 与 rkey。本端提交请求时用 lkey；rkey 交给对端，用于远端访问校验。本例通过内核缓冲区拷贝数据
4ibv_create_cq()完成队列 CQ，即内存中的完成环。无
5ibv_create_qp()、ibv_modify_qp()RC 队列对 QP（Queue Pair），含发送队列 SQ 和接收队列 RQ。依次切换到 INIT、RTR、RTS，并填入对端的 QP 号、地址和起始包序号。connect() / accept()
6ibv_post_send()提交一个 RDMA Write WR（Work Request）。libmlx5 把它编码成 WQE 写进 SQ 环（①），再敲 doorbell（②）。send()
7ibv_poll_cq()检查 CQE 为成功状态后，确认请求完成并复用源 buffer。send() 返回
—无本次普通 RDMA Write 无需 B 投递接收请求。B 的 recv()

1–5 属于资源建立的控制路径，需要内核参与；建好的 MR、QP 和 CQ 可以供后续多次传输复用。6–7 是 mlx5 的数据路径，在用户态写队列、敲 doorbell 和轮询完成。双方还需交换 QP 连接参数，B 则把目标地址和 rkey 交给 A。应用可以使用 TCP 交换这些信息，也可以用 rdma_cm 建立连接，再通过应用协议交换内存信息。连接管理

// The same 4 KiB as an RC RDMA Write. PD, MR, CQ and an RTS QP
// exist; remote_addr and rkey arrived from B out of band.
struct ibv_sge sge = {
    .addr = (uintptr_t)buf, .length = 4096, .lkey = mr->lkey,
};
struct ibv_send_wr wr = {
    .sg_list = &sge, .num_sge = 1,
    .opcode = IBV_WR_RDMA_WRITE,
    .send_flags = IBV_SEND_SIGNALED,            // request a CQE
    .wr.rdma = { .remote_addr = remote_addr, .rkey = rkey },
};
struct ibv_send_wr *bad_wr;
if (ibv_post_send(qp, &wr, &bad_wr))            // libmlx5: WQE ①, doorbell ②
    abort();

struct ibv_wc wc;
int n;
while ((n = ibv_poll_cq(cq, 1, &wc)) == 0)      // read the CQ ring; no syscall
    ;
if (n < 0 || wc.status != IBV_WC_SUCCESS)
    abort();

图中的数据传输由两端网卡完成。B 的网卡用 rkey 查找 MR，校验范围与远端写权限，再将数据 DMA 写入目标内存；B 的 CPU 已在初始化时准备好这些资源，本次普通 RDMA Write 无需它投递接收请求或处理中断。A 轮询到成功的完成记录后可复用源 buffer。B 上的程序要知道数据何时就绪，还需要通知协议，例如后续 Send 或 RDMA Write with immediate。RDMA Write 与完成通知

旁注：其他 verbs 操作

RDMA Read 把传输方向反过来：A 提交带有 B 地址和 rkey 的读请求，B 的网卡取回数据，A 等待本端读取完成。B 的 CPU 无需逐次处理读请求。Send/Recv 则要求接收方先用 ibv_post_recv() 投递 buffer；Send 到达后填入 buffer，并产生接收侧 CQE。RDMA Write with immediate 也会消耗接收请求并产生接收侧 CQE，但 payload 仍写入发送方指定的远端地址。

基本的 fetch-and-add 与 compare-and-swap 对远端 8 字节对象执行原子操作。UD（Unreliable Datagram）是无连接传输，支持 Send/Recv，单条消息受路径 MTU 限制。InfiniBand 与 RoCE 共用 verbs 编程模型；RoCE v2 将 InfiniBand 传输层封装在 UDP/IP 中，经以太网传输。操作与传输模式

4. 驱动与设备文件

send() 和 ibv_post_send() 都是应用在用户态调用的函数。两者的区别在于何时进入内核，以及把哪些工作交给内核。普通 TCP socket 将逐次发送交给协议栈；mlx5 的用户态 RDMA verbs 先经内核建立资源，再直接操作获准访问的队列与寄存器。

提交数据send() 经系统调用，把数据交给内核 TCP/IP 协议栈。ibv_post_send() 调用 provider，直接写已映射的队列和 doorbell。
谁处理逐次传输内核协议栈、网卡驱动和网卡共同处理。provider 提交描述符，网卡执行 RDMA 操作。

socket fd 表示通信端点，由 socket() 创建并装入进程的 fd 表。发送数据时，内核协议栈通过 net_device_ops.ndo_start_xmit 调用网络驱动；mlx5e 将这个回调设为 mlx5e_xmit()。这条内核调用路径直接到达驱动，无需再打开网卡的设备文件。socket 创建 · fd 分配 · 网络驱动分派 · mlx5e 回调

创建 QP、CQ 和注册 MR 涉及设备资源、内存固定和访问权限，由内核检查并建立。ibv_create_qp() 的路径把用户态队列内存与网卡的 QP 资源关联起来：

  mlx5_alloc_dbrec()            # 分配 DBR

数据路径

ibv_post_send() 和 ibv_poll_cq() 是 verbs.h 中的内联函数，直接调用 provider 的函数指针，不进入内核。verbs.h libmlx5 把 WR 编码成 WQE：控制段写操作码和 WQE 序号，远端地址段写 remote_addr 与 rkey，数据段写本端地址、长度和 lkey。WQE 编码 写完 WQE 后执行下面这段 doorbell 代码：

755                  int nreq, int inl, int size, void *ctrl)
756  {
757      struct mlx5_context *ctx;
758

765       * Make sure that descriptors are written before
766       * updating doorbell record and ringing the doorbell
767       */

第 780–786 行通知网卡。条件满足时，mlx5_bf_copy() 将 WQE 写入 UAR 页上的 BlueFlame buffer，网卡可以直接取得描述符；条件包括本次只提交一个 WR、UAR 支持 BlueFlame、启用 inline 或偏好 BlueFlame，以及 WQE 大小符合限制。另一分支只写控制段的前 8 字节，其中包含 WQE 序号、操作码和 QP 号。两条分支都使用 MMIO。

第 798 行在释放锁之前刷新写合并缓冲，保证这一轮寄存器写入先于下一个线程的提交；第 799 行切换 BlueFlame buffer 的半区，供下一次 doorbell 使用。锁和屏障共同维护了多个提交者之间的顺序。

ibv_poll_cq() 同样停留在用户态：provider 按所有权位判断 CQ 环中的下一条 CQE 是否已由网卡写好，读出后把消费者序号写回 CQ 的 DBR。mlx5_poll_cq

bf->reg 指向 UAR 在当前进程中的映射。libmlx5 通过命令 fd 分配 UAR，再调用 mmap()；mlx5_ib 用 rdma_user_mmap_io() 映射对应的 BAR 页，BlueFlame 页采用写合并属性，doorbell-only 页采用非缓存属性。映射建立后，CPU 可用 MMIO 写指令通知网卡，无需为每次 doorbell 再执行系统调用。libmlx5 的分配与映射 · mlx5_ib 的 mmap

NICs and RDMA: from sockets to verbs

DMA allows a NIC to access host memory directly, but ordinary TCP sockets still require substantial CPU work, including protocol processing and buffer management (moving data between user and kernel memory). RDMA reduces CPU involvement: after user-space memory buffers are registered directly and access permissions are established, the application can submit read and write requests from user space, and the NIC accesses the specified remote memory directly.

A 4 KiB transfer between nodes provides a common example for comparing TCP sockets and RDMA Write. The mlx5 source shows how descriptors, doorbells and completion queues work together, and how user-space libraries and kernel drivers divide responsibility for establishing resources and permissions through device files, submitting requests from user space and reporting completion to the application.

Source baseline: Linux 6.12 and rdma-core 61.0, checked on 2026-11-10; the send wrapper uses glibc 2.40. Source links are pinned to tags or commits and collected by section in the source index. The RDMA Write sequence diagram follows source-level call order; activation bars mark each participant's logical activity scope.

1. NICs and memory

A PCIe NIC interacts with the CPU through two kinds of address. Its BARs (Base Address Registers) describe device address windows. Once the driver maps a register region, CPU loads and stores issue MMIO (Memory-Mapped I/O) accesses to the device. To access host memory, the NIC uses DMA (Direct Memory Access) mappings established through the Linux DMA API. The IOMMU is part of the host I/O subsystem. With address translation enabled, the NIC issues DMA requests using I/O virtual addresses (IOVAs). After a request reaches the host over PCIe, the IOMMU translates its IOVA to a host physical address and checks access permissions. DMA addresses and mappings · Host DMA remapping

The CPU describes where to read data and how many bytes to send, then places that descriptor in a ring in memory. The NIC reads it and executes the transfer. The conventional mlx5 send path has four steps:

StepPerformed byAction
① Write the descriptorCPUWrite a WQE (Work Queue Element) into the send queue (SQ) ring, recording the operation, buffer address and length.
② Ring the doorbellCPURecord the new producer index in the DBR (Doorbell Record) in memory, then write the doorbell register on a UAR (User Access Region) page in the BAR, an MMIO write that reaches the NIC over PCIe.
③ ExecuteNICDMA-read the WQE and the data it points to, then transmit the data.
④ CompleteNICDMA-write CQEs (Completion Queue Entries) into the completion queue (CQ) as configured, then raise an interrupt or wait for software to poll, as configured.

Software performs ① and ②; the NIC performs ③ and ④. Sockets and RDMA verbs both use this queue mechanism. The socket path in section 2 submits work from the kernel Ethernet driver; the verbs path in section 3 submits it from the user-space driver libmlx5. The hardware is shared, while request submission runs in different places.

2. The TCP socket path

A sends 4 KiB to B over an established IPv4 TCP connection using ordinary copying send() and recv() calls. For this example, each call handles all 4096 bytes. send() is declared in <sys/socket.h>; the application calls a C-library wrapper before entering the kernel. On Linux x86-64 with glibc 2.40, the path is:

User space
  send(fd, buf, 4096, 0)                    # application socket-send API
    → __libc_send()                         # glibc wrapper
    → sendto(fd, buf, 4096, 0, NULL, 0)      # select the sendto system call
                ↓ syscall: enter kernel mode

Kernel space
  __sys_sendto()
    → sockfd_lookup_light(fd, ...)          # find the socket by fd
    → __sock_sendmsg()
    → sock_sendmsg_nosec()                  # dispatch to the socket's sendmsg op
    → inet_sendmsg()                        # IPv4 socket in this example
    → tcp_sendmsg()                         # socket protocol selects TCP
    → tcp_sendmsg_locked()                  # copy 4 KiB into skb pages
    → tcp_write_xmit() … dev_queue_xmit()   # TCP/IP send path to the NIC driver
    → mlx5e_xmit()                          # DMA-map pages, write a WQE in SQ  ①
    → mlx5e_notify_hw()                     # write DBR, then UAR doorbell      ②

NIC A: DMA-read the data and transmit Ethernet frames                           ③

The NULL, 0 destination arguments tell sendto to use the socket's associated peer. After looking up the socket by fd, the kernel dispatches through its operation tables to the IPv4 and TCP implementations, then continues through the protocol stack and NIC driver. glibc send wrapper · x86-64 syscall table · Kernel sendto entry · Socket dispatch · TCP / UDP dispatch · tcp_sendmsg

On this socket path, B's NIC writes into receive buffers posted by the driver. B's CPU then processes TCP/IP, and the application obtains the data through recv():

NIC B: DMA-write into a posted receive buffer, write a CQE, interrupt  ④
mlx5_eq_comp_int() → napi_schedule()       # the interrupt only schedules NAPI
mlx5e_napi_poll() → mlx5e_poll_rx_cq()     # softirq: read CQEs, build skbs
  napi_gro_receive() … tcp_v4_rcv()        # TCP processing, socket receive queue
recv(fd, buf, 4096, 0)                     # system call: copy to the user buffer

This example copies the payload once between user and kernel memory at each endpoint. The CPUs also handle system calls, protocol processing and driver queues. On receive, an interrupt schedules NAPI, which processes completion entries in batches. TCP is a byte stream: applications must use the return values of send() and recv() to handle remaining bytes. Neither system calls nor interrupts have a one-to-one relationship with the 4 KiB transfer. send(2) · recv(2)

After a copying send returns successfully, the application can reuse the portion of its source buffer accepted by the kernel, even if the peer application has not read the data. MSG_ZEROCOPY replaces the sending-side copy with page pinning and a completion notification; the buffer remains in use until that notification. Linux documents a typical benefit above roughly 10 KB per write, so the 4 KiB example here keeps the copying path. MSG_ZEROCOPY

Ordinary socket traffic already uses local DMA. RDMA adds remote-memory operations that the NIC can execute: A names B's address and access key in the request, and B's NIC checks them before writing directly into the destination buffer. This removes the receiving protocol-stack work and user-space copy from that data delivery. RDMA operations

3. The RDMA Write path

The same 4 KiB now travels as an RDMA Write over RC (Reliable Connection). Both endpoints register memory and establish a connection before A posts the write. Applications call the common verbs API; a device-specific user-space implementation, called a provider, performs the hardware operations. For ConnectX, that provider is libmlx5. The socket column compares the purpose of each step.

Steps 1–5 establish resources through the control path and require kernel participation. The resulting MRs, QPs and CQs can serve many transfers. Steps 6–7 form the mlx5 data path: user-space code writes queues, rings doorbells and polls completions. The endpoints also exchange QP connection parameters, and B gives A its destination address and rkey. An application can exchange these over TCP, or use rdma_cm to establish the connection and exchange memory information through its own protocol. Connection management

// The same 4 KiB as an RC RDMA Write. PD, MR, CQ and an RTS QP

The fragment compiles against the rdma-core 61.0 headers and omits the control path. IBV_SEND_SIGNALED requests a CQE for this request. Request fields

The NICs carry out the transfer in the diagram. B's NIC locates the MR using rkey, checks the range and remote-write permission, then DMA-writes the destination. B's CPU prepared those resources during setup; this ordinary RDMA Write requires no per-transfer receive posting or interrupt handling from it. Once A polls a successful completion, it can reuse the source buffer. B's application needs a notification protocol to know when the data is ready, such as a subsequent Send or RDMA Write with immediate data. RDMA Write and notifications

Aside: other verbs operations

RDMA Read reverses the data direction. A posts a read naming B's address and rkey; B's NIC returns the data, and A waits for local read completion. B's CPU does not handle each read request. Send/Recv requires the receiver to post a buffer with ibv_post_recv(); an arriving Send fills it and produces a receive CQE. RDMA Write with immediate data also consumes a receive request and produces a receive CQE, while placing the payload at the remote address specified by the sender.

Basic fetch-and-add and compare-and-swap operations act atomically on an 8-byte remote object. UD (Unreliable Datagram) is connectionless, supports Send/Recv and limits each message to the path MTU. InfiniBand and RoCE share the verbs programming model; RoCE v2 carries the InfiniBand transport in UDP/IP over Ethernet. Operations and transport modes

4. Drivers and device files

Applications call both send() and ibv_post_send() from user space. The difference is when they enter the kernel and which work they delegate to it. Ordinary TCP sockets pass each send to the protocol stack. With mlx5 user-space RDMA verbs, the kernel first establishes resources, then the provider directly operates the queues and registers it has permission to access.

StageOrdinary TCP socketUser-space RDMA verbs
Establish resourcesThe socket() system call creates a communication endpoint and returns a socket fd.The library opens /dev/infiniband/uverbsN and uses ioctl / write / mmap to create queues, register memory and establish mappings.
Submit datasend() enters the kernel through a system call and hands data to the TCP/IP stack.ibv_post_send() calls the provider, which directly writes the mapped queues and doorbell.
Process each transferThe kernel protocol stack, NIC driver and NIC share the work.The provider submits descriptors, and the NIC executes RDMA operations.

A socket fd represents a communication endpoint created by socket() and installed in the process's fd table. To send data, the kernel stack calls the network driver through net_device_ops.ndo_start_xmit; mlx5e assigns mlx5e_xmit() to that callback. This kernel call path reaches the driver directly, without opening a NIC device file. Socket creation · FD allocation · Network-driver dispatch · mlx5e callback

The uverbs fd is a device-resource management interface. Through it, the user-space library requests MRs, QPs, CQs and UAR mappings, while the kernel checks ownership, memory and access rights. Once mapped, the provider can submit queue work in user space. The kernel continues to manage resource lifetime, including explicit release and process exit. Data path

ibv_post_send() and ibv_poll_cq() are inline functions in verbs.h that call the provider's function pointers without entering the kernel. verbs.h libmlx5 encodes the WR as a WQE: the control segment holds the opcode and WQE index, the remote-address segment holds remote_addr and rkey, and the data segment holds the local address, length and lkey. Lines 768–769 publish queue progress. A barrier orders the WQE stores before the DBR update, which records the new producer index in its send slot. Lines 774–778 prepare write-combining access and acquire a lock if several threads share the BlueFlame register.

Lines 780–786 notify the NIC. When the conditions hold, mlx5_bf_copy() writes the WQE into the UAR page's BlueFlame buffer, delivering the descriptor directly. The conditions include one WR in this call, BlueFlame support, inline data or a preference for BlueFlame, and a WQE that fits. The other branch writes only the control segment's first 8 bytes, containing the WQE index, opcode and QP number. Both branches use MMIO.

Line 798 flushes the write-combining buffer before releasing the lock, ordering this register write ahead of another thread's submission. Line 799 switches to the other half of the BlueFlame buffer for the next doorbell. The lock and barriers preserve ordering among submitters.

ibv_poll_cq() also stays in user space: the provider checks the ownership bit to see whether the NIC has written the next CQE in the CQ ring, reads it, and writes the consumer index back to the CQ's DBR. mlx5_poll_cq

bf->reg points to the UAR mapping in the current process. libmlx5 allocates the UAR through the command fd and maps it with mmap(). mlx5_ib uses rdma_user_mmap_io() for the BAR page, selecting write-combining attributes for BlueFlame pages and uncached attributes for doorbell-only pages. Once mapped, CPU MMIO stores can notify the NIC without a system call for each doorbell. Allocation and mapping in libmlx5 · mlx5_ib mmap
