VPN 原理与路由

VPN（虚拟专用网络）将分散的主机与网络连接起来，是远程访问内网、跨站点互联和统一出口管理的常用技术。本文介绍三层 VPN 的协议封装、隧道地址与路由机制，比较 WireGuard、IPsec/IKEv2 和 OpenVPN 的实现特点，并提供 Linux 服务端与 macOS 客户端的 WireGuard 配置及验证教程。

1. VPN 的工作边界

远程访问内网、连接两个站点的网段，以及让一组应用共用指定出口，都适合使用 IP 隧道。应用不必支持 HTTP 或 SOCKS 代理。只访问一台机器上的单个 TCP 服务时，SSH 端口转发通常需要更少配置；只为浏览器选择出口时，HTTP 代理可以把范围限定在相应网络请求。

需求VPN 提供的能力还需配置的部分
访问公司网段为私网 IP 建立可达路径目标网段路由、内部 DNS、服务 ACL
跨站点连接把两个网段通过隧道连接两侧回程路由、地址不重叠
统一公网出口把匹配的 IP 流量送往出口网关网关转发、SNAT 或可路由地址、IPv6 与 DNS
公共 Wi-Fi 上的链路保护加密客户端到 VPN 对端的一段路径应用到源站仍需 HTTPS 等端到端保护

本文讨论 packet VPN。TUN 处理 IP 包，TAP 处理以太网帧；两者不能统一标成同一个层次。macOS 的 utun4 是虚拟三层接口名，编号由系统分配，并不指明使用 WireGuard、IPsec 或其他具体协议。TUN/TAP 文档；Apple utun 实现。

2. 内外层协议栈

三层 VPN 接入 IP 路由路径。应用照常连接目标服务器，例如 connect(origin_ip, 443)；匹配 VPN 路由的数据包进入隧道接口，由 VPN 加密封装并送往网关。网关解封装后把内层包路由到目标，返回包沿相反方向传递。应用无需发送 HTTP 代理请求或 SOCKS 握手。

内层：IP[客户端隧道地址 → 源站] / TCP / TLS / HTTP
                          ↓ VPN 加密封装
外层：IP[Mac 网络地址 → VPN 网关] / UDP / WireGuard 加密数据
                          ↓ VPN 网关解封装、路由，可能做 NAT
源站：收到内层连接的数据包，看不到外层 WireGuard 封装

WireGuard 使用 UDP 传送加密后的 IP 包，因此外层存在 UDP，内层仍可承载 TCP。仅负责路由或 NAT 的 VPN 网关不接受应用 TCP 连接再新建另一条连接：TCP 状态由客户端与源站维护，NAT 按映射改写地址或端口。CONNECT 和 SOCKS 代理则通常在代理两侧维护独立的 TCP 连接。WireGuard 协议说明给出了外层封装。

进入 VPN 的流量由路由及产品策略决定。Split tunnel 选择部分目标或网段；full tunnel 将默认出口导入隧道，实际覆盖仍取决于 IPv4、IPv6、例外路由和 DNS 配置；per-app VPN 按应用限定范围。Apple 的部署指南和VPN 路由说明介绍了这些部署方式。

内层 TCP 与外层 UDP 有各自的端点、端口和状态。抓取 utun 上的包可以观察内层目标，抓取物理接口则会看到发往 VPN Endpoint 的外层包。封装还会增加长度：隧道接口的 MTU 需要为外层头部留出空间。小请求成功而大传输停滞时，应检查 MTU 与路径 MTU 发现。WireGuard 数据包格式。

3. 隧道地址与出口地址

地址示例用途
本地网络地址192.168.1.20Mac 在 Wi-Fi 网络中的地址，可能经家用路由器 NAT 出网
VPN Endpoint203.0.113.10:51820客户端通过现有网络连接的隧道对端
隧道地址Mac 10.77.0.2，服务端 10.77.0.1内层 IP 包的源或目的地址
公网出口地址网关出网口或上游 NAT 地址访问公网且执行 SNAT 时，源站看到的地址

VPN 分配的地址通常只在隧道及连接的私网内有意义，不等于新增一个公网 IP。WireGuard 协议本身不协商地址租约：手工配置中的 Address 由工具设置，托管产品也可通过控制平面分配后下发。服务端的 AllowedIPs = 10.77.0.2/32 将这个内层地址关联到 Mac 的公钥；它不会自动把地址写入 Mac。WireGuard 地址与 peer 的关系。

其他协议可以在建隧道时分配地址。例如，IKEv2 客户端可通过配置载荷请求虚拟 IP，服务端从地址池中分配后返回。静态填写与动态分配解决的是同一个寻址问题，均不意味着客户端获得公网出口地址。strongSwan 虚拟 IP 分配。

源站看到的来源地址取决于出口处理。公网 SNAT 部署通常暴露网关出口地址；企业内部纯路由部署可以保留客户端隧道地址。外层 VPN 头在网关结束，不会作为一个“使用 VPN”字段自动交给网站。账号、cookie 和站点收到的应用数据仍然存在。

4. 流量选择与路由

目的地址与路由前缀

常见三层 VPN 通过安装路由把匹配流量交给虚拟接口。以没有额外策略路由的 IPv4 配置为例，10.77.0.0/24 → utun 比默认路由 0.0.0.0/0 → Wi-Fi 网关 更具体，因此访问 10.77.0.10 的连接进入 VPN，访问公网地址的连接继续走普通出口。选择依据是当前 socket 的目的 IP：使用 HTTP 代理时，这个 IP 是代理的地址。

客户端选路隧道覆盖容易遗漏的条件
Split tunnel只导入指定网段或主机内部 DNS 查询必须能到达相应解析器
Full tunnel导入默认 IPv4 / IPv6 路由，或等价策略VPN Endpoint 的外层连接仍需从底层网络发出
Per-app VPN由系统或管理策略选择应用流量同一目的 IP 的不同进程可以适用不同规则

“最长前缀匹配”描述的是一次常规路由查找，不能概括所有管理策略。Linux 的 ip rule 可以先选择路由表；macOS 还存在 scoped route、按应用 VPN 与 Network Extension 策略。应检查实际接口和目的地址，而不是仅看 VPN 按钮。Apple VPN 部署说明。

IPsec 还支持基于策略的处理：内核按源地址、目的地址及协议等 traffic selector 匹配安全策略，再决定是否保护数据包，不一定存在一个供路由直接选择的隧道接口。路由式 IPsec 使用接口与路由导入流量，数据包仍需满足协商的策略。后面的 WireGuard 实验采用虚拟接口与路由模型。IPsec 策略与路由。

AllowedIPs 与系统路由

WireGuard 有两次不同的选择：操作系统先决定包是否送入 WireGuard 接口；进入后，WireGuard 根据目的地址和 AllowedIPs 选择 peer。接收时，AllowedIPs 又用于检查解密包的源地址是否属于该 peer。wg-quick 会根据 AllowedIPs 创建系统路由，默认路由在 Linux 上还涉及策略规则；直接使用 wg set 则不能假定路由也已配置。wg-quick 手册。

DNS 与 IPv6

VPN 不需要先理解 HTTP 域名才能路由 IP 包。通常由解析器先得到目的 IP，再做选路。内部域名可能要求 split DNS；scutil --dns 展示的解析器作用域与 scutil --proxy 是两套配置。只把 IPv4 默认路由导入 VPN，不能保证 IPv6 也进入隧道；应用可能通过 AAAA 记录建立另一条连接。Full tunnel 也不等于断线阻断：隧道关闭后是否回落到物理出口，由路由恢复及 kill switch 策略决定。

6. WireGuard 配置实验

实验连接一台可通过 UDP 访问的 Ubuntu VM 和一台 Mac，仅把 10.77.0.0/24 导入 VPN。VM 的 VPN 地址为 10.77.0.1，Mac 为 10.77.0.2；该网段必须与现有 LAN、容器和企业 VPN 网段不冲突。203.0.113.10 是文档示例地址，应替换为 VM 的真实可达地址。VM 的云安全组和主机 INPUT 策略需允许 UDP 51820；位于 NAT 后的服务端还需对应的 UDP 端口映射。

服务端与公钥

sudo apt-get update
sudo apt-get install wireguard
sudo install -d -m 700 /etc/wireguard
sudo sh -c 'umask 077; wg genkey > /etc/wireguard/server.key; wg pubkey < /etc/wireguard/server.key > /etc/wireguard/server.pub'
sudo cat /etc/wireguard/server.pub

在 Mac 安装 官方 WireGuard App，创建空隧道，让客户端生成自己的密钥对。将 Mac 的公钥填到 VM 配置；将上一条命令输出的服务端公钥填到 Mac。私钥分别保留在所属机器上。以下占位符必须替换，不能原样运行；服务端私钥来自刚生成的 /etc/wireguard/server.key。

sudoedit /etc/wireguard/wg0.conf
[Interface]
Address = 10.77.0.1/24
ListenPort = 51820
PrivateKey = <SERVER_PRIVATE_KEY>

[Peer]
PublicKey = <MAC_PUBLIC_KEY>
AllowedIPs = 10.77.0.2/32

密钥生成命令只用于首次创建实验配置，重复运行会更换服务端身份。这个单 peer 配置中，服务端接受 Mac 的 10.77.0.2 源地址，并将发往该地址的包送回 Mac。WireGuard 快速开始；wg 配置字段。

Mac 配置

[Interface]
PrivateKey = <MAC_PRIVATE_KEY>
Address = 10.77.0.2/32

[Peer]
PublicKey = <SERVER_PUBLIC_KEY>
Endpoint = 203.0.113.10:51820
AllowedIPs = 10.77.0.0/24
PersistentKeepalive = 25

保留 App 生成的 Mac 私钥，替换服务端公钥与 Endpoint。PersistentKeepalive = 25 让位于 NAT 后的客户端定期维持映射，按网络需要启用；它不负责分配地址。此配置使用 IP 地址验证，未设置 DNS，也未创建全局公网出口。

启动与验证

sudo chmod 600 /etc/wireguard/wg0.conf
sudo wg-quick up wg0
sudo wg show wg0
ip -br address show wg0

在 Mac 激活隧道后，服务端 wg show 应逐步出现 peer 的最新握手与传输计数。为验证应用层链路，可在 VM 的另一个终端临时启动一个仅监听 VPN 地址的 HTTP 服务：

python3 -m http.server 8765 --bind 10.77.0.1 --directory /path/to/public-files

目录应替换为专门用于实验的公开文件目录；若 8765 已被使用，换一个空闲端口并同步调整 curl。VM 的 INPUT 规则还需允许来自 10.77.0.2、经 wg0 到达该 TCP 端口的请求。Mac 执行：

route -n get 10.77.0.1
netstat -rn -f inet
scutil --dns
ping -c 3 10.77.0.1
curl --noproxy '*' http://10.77.0.1:8765/

路由输出应指向实际的 utun 接口；HTTP 响应证明 TCP 和应用数据能通过隧道。ping 单独失败还可能是 ICMP 被策略禁止。--noproxy '*' 明确绕过 curl 的代理配置，使这次测试只观察 VPN 路径。

网关扩展与停止

当前目标就是 VM 自己，因此无需打开 IP forwarding。若扩展到 VM 后面的 LAN，需在 VM 启用转发、允许 FORWARD 流量，并在 LAN 配置返回 10.77.0.0/24 的路由，或按部署需要做 SNAT。若扩展为全隧道，还需网关公网转发与出口策略、可用 DNS，以及 IPv6 的路由或明确处理方案；仅把客户端 AllowedIPs 改成 0.0.0.0/0 不会自动完成这些条件。

结束实验时，在 Mac 停用隧道，在 VM 停止临时 HTTP 服务并执行以下命令。它移除本次 wg0 接口及 wg-quick 管理的路由，保留配置以便下次使用。

sudo wg-quick down wg0

验证范围：配置依据 WireGuard 官方文档整理，命令已检查语法；Linux 与 macOS 的端到端实验尚未实测。

VPN fundamentals and routing

VPNs (virtual private networks) connect remote hosts and networks for private network access, site-to-site connectivity and shared egress. This article explains layer-3 VPN encapsulation, tunnel addressing and routing, compares WireGuard, IPsec/IKEv2 and OpenVPN, and provides a WireGuard configuration and verification guide for a Linux server and a macOS client.

1. VPN scope

Remote access to private subnets, site-to-site connectivity and shared egress are natural uses for an IP tunnel. Applications need no HTTP or SOCKS support. A single TCP service can often be exposed with less configuration using SSH forwarding; an HTTP proxy can limit egress selection to compatible web requests.

RequirementVPN contributionAdditional configuration
Private network accessReachability to private IP addressesRoutes, internal DNS and service ACLs
Site-to-site connectivityA path between subnetsReturn routes and non-overlapping addresses
Shared Internet egressMatching packets enter the gatewayForwarding, SNAT or routed addresses, IPv6 and DNS
Public Wi-Fi protectionEncryption to the VPN peerApplication TLS still protects the path to the origin

This article covers packet VPNs. TUN carries IP packets; TAP carries Ethernet frames. macOS utun4 is a virtual layer-3 interface name with a system-assigned number, not the name of a VPN protocol. See the TUN/TAP documentation and Apple utun implementation.

2. Inner and outer stacks

A layer-3 VPN participates in IP routing. The application connects to its destination normally, for example with connect(origin_ip, 443). Matching packets enter a tunnel interface, are encrypted and encapsulated to the VPN gateway, then decapsulated and routed to the origin. Return packets follow the reverse path. The application needs no HTTP proxy request or SOCKS handshake.

Inner: IP[client tunnel address → origin] / TCP / TLS / HTTP
                           ↓ VPN encryption and encapsulation
Outer: IP[Mac network address → VPN gateway] / UDP / encrypted WireGuard data
                           ↓ decapsulation, routing, optional NAT
Origin: receives inner connection packets, not the outer WireGuard wrapper

WireGuard carries encrypted IP packets over UDP, so an outer UDP transport can carry inner TCP traffic. A gateway performing only routing or NAT leaves TCP state at the client and origin; NAT rewrites addresses or ports according to its mappings. CONNECT and SOCKS proxies normally maintain separate TCP connections on either side. The WireGuard protocol description documents the outer encapsulation.

Routing and product policy determine VPN coverage. Split tunneling selects destinations or networks. Full tunneling directs the default exit through the tunnel, with coverage still dependent on IPv4, IPv6, exceptions and DNS. Per-app VPN restricts coverage by application. Apple's deployment guide and VPN routing documentation describe these deployments.

Inner TCP and outer UDP have their own endpoints, ports and state. A capture on utun exposes the inner destination; a capture on the physical interface shows the outer VPN endpoint. Encapsulation adds bytes, so tunnel MTU must leave room for outer headers. When small requests work but larger transfers stall, inspect tunnel MTU and path MTU discovery. WireGuard packet format.

3. Tunnel and exit addresses

AddressExamplePurpose
LAN address192.168.1.20Mac on Wi-Fi, potentially behind a home NAT
VPN endpoint203.0.113.10:51820Tunnel peer reachable over the existing network
Tunnel addressMac 10.77.0.2; VM 10.77.0.1Source or destination of inner packets
Internet exit addressGateway or upstream NAT addressWhat an Internet origin sees after source NAT

A tunnel address does not grant a new public IP. WireGuard does not negotiate address leases: tools configure Address, or a product control plane allocates and distributes it. The server peer entry AllowedIPs = 10.77.0.2/32 binds that inner address to the Mac public key; it does not configure the Mac interface. WireGuard cryptokey routing.

Other protocols can assign addresses during tunnel setup. An IKEv2 client can request a virtual IP through a configuration payload, and the server can allocate one from a pool. Static and dynamic assignment both provide inner addressing; neither necessarily gives the client a public exit address. strongSwan virtual IP allocation.

Internet SNAT commonly exposes the gateway exit address, while a routed enterprise deployment can preserve the client tunnel address. The outer VPN wrapper ends at the gateway. It does not become an HTTP field declaring VPN use, and changing the exit address does not remove accounts, cookies or other application identity.

4. Traffic selection

Destination routes

A common VPN installs routes to its virtual interface. Without additional policy routing, 10.77.0.0/24 → tunnel is more specific than 0.0.0.0/0 → LAN gateway. Traffic to 10.77.0.10 uses the tunnel; public destinations use the ordinary default. The destination belongs to the current socket. For a proxied request, it is the proxy address.

ModeCoverageAdditional condition
Split tunnelSelected hosts or subnetsInternal DNS must remain reachable
Full tunnelDefault IPv4/IPv6 routes or equivalent policyThe VPN endpoint must still be reachable through the underlay
Per-app VPNSelected application trafficProcess policy may distinguish connections to the same IP

Longest-prefix matching describes a route lookup, not the entire policy system. Linux ip rule can first select a routing table. macOS has scoped routes, per-app VPN and Network Extension policies. Inspect the actual destination and interface rather than inferring routing from a connected status. Apple VPN deployment.

Policy-based IPsec also selects traffic through security policies derived from traffic selectors, such as source, destination and protocol. It need not expose a tunnel interface selected by routing. Route-based IPsec uses interfaces and routes, while packets must still match negotiated policies. The WireGuard lab below uses the interface-and-route model. IPsec policies and routing.

AllowedIPs and OS routes

The OS first decides whether to send a packet to WireGuard. WireGuard then uses its destination and AllowedIPs to select a peer. On receive, AllowedIPs checks the decrypted source address against that peer. wg-quick also derives OS routes from AllowedIPs, with Linux policy rules for default routing. wg set alone does not establish all interface and route configuration. wg-quick manual.

DNS and IPv6

Routing generally operates on IP addresses after resolution. Private names may need split DNS. macOS DNS scope, shown by scutil --dns, is distinct from proxy configuration. An IPv4 default tunnel does not guarantee IPv6 coverage. Full tunneling also does not imply a kill switch: behavior after disconnect depends on route restoration and filtering policy.

A client product and its tunnel protocol are separate choices. Enterprise clients may combine a packet tunnel, application proxy and endpoint filter. Consult WireGuard installation, strongSwan documentation and the OpenVPN manual for platform-specific support.

6. WireGuard configuration lab

This lab links an Ubuntu VM and a Mac, routing only 10.77.0.0/24 through the tunnel. Use a subnet that does not overlap LAN, container or corporate VPN routes. Replace the documentation address 203.0.113.10 with the VM endpoint. Cloud and host input rules must permit UDP 51820; a server behind NAT also needs a UDP port mapping.

Server and public keys

sudo apt-get update
sudo apt-get install wireguard
sudo install -d -m 700 /etc/wireguard
sudo sh -c 'umask 077; wg genkey > /etc/wireguard/server.key; wg pubkey < /etc/wireguard/server.key > /etc/wireguard/server.pub'
sudo cat /etc/wireguard/server.pub

Install the official WireGuard Mac App and create an empty tunnel to generate its key pair. Exchange public keys only. Replace the configuration placeholders with the matching keys; the server private key is in /etc/wireguard/server.key.

sudoedit /etc/wireguard/wg0.conf
[Interface]
Address = 10.77.0.1/24
ListenPort = 51820
PrivateKey = <SERVER_PRIVATE_KEY>

[Peer]
PublicKey = <MAC_PUBLIC_KEY>
AllowedIPs = 10.77.0.2/32

Run key generation only for initial setup: repeating it replaces the server identity. The server associates 10.77.0.2 with the Mac peer for incoming source validation and outgoing delivery. WireGuard quick start; wg configuration.

Mac configuration

[Interface]
PrivateKey = <MAC_PRIVATE_KEY>
Address = 10.77.0.2/32

[Peer]
PublicKey = <SERVER_PUBLIC_KEY>
Endpoint = 203.0.113.10:51820
AllowedIPs = 10.77.0.0/24
PersistentKeepalive = 25

Keep the Mac-generated private key and substitute the server public key and endpoint. The optional 25-second keepalive preserves a NAT mapping; it does not allocate addresses. This IP-based lab sets neither DNS nor a public default tunnel.

Startup and verification

sudo chmod 600 /etc/wireguard/wg0.conf
sudo wg-quick up wg0
sudo wg show wg0
ip -br address show wg0

Activate the Mac tunnel. The server should show a recent handshake and transfer counters as traffic crosses it. For an application test, start a temporary HTTP service in another VM terminal, using a dedicated directory of public test files:

python3 -m http.server 8765 --bind 10.77.0.1 --directory /path/to/public-files

If 8765 is occupied, select a free port and update curl accordingly. The VM input rules must also permit requests from 10.77.0.2 arriving on wg0 at that TCP port. On the Mac:

route -n get 10.77.0.1
netstat -rn -f inet
scutil --dns
ping -c 3 10.77.0.1
curl --noproxy '*' http://10.77.0.1:8765/

The route should identify the actual utun interface. A successful HTTP response verifies the TCP and application path. ICMP may be filtered independently. The explicit curl bypass removes HTTP proxy configuration from this test.

Gateway extension and shutdown

The target is the VPN VM itself, so this lab needs no IP forwarding. Reaching a LAN behind it additionally requires forwarding permission and return routes to 10.77.0.0/24, or appropriate SNAT. Full Internet tunneling also requires gateway egress policy, DNS and an IPv6 plan. Changing AllowedIPs to 0.0.0.0/0 alone supplies none of these gateway capabilities.

Deactivate the Mac tunnel, stop the temporary HTTP process, and remove the VM interface and its wg-quick-managed routes with:

sudo wg-quick down wg0
