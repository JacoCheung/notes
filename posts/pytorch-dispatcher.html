PyTorch Dispatcher 的多维分派与算子执行路径

Python 只暴露一个 torch.add，一次实际调用却可能同时受设备、layout、autograd、张量子类和线程局部 mode 影响。Dispatcher 位于 Python/C++ API 与具体 kernel 之间，负责把同一个 operator schema 映射到这些可组合的行为层。

PyTorch 通过 schema 固定算子契约，通过注册表关联 operator 与各个 dispatch key 的实现，再由有序 DispatchKeySet 和 redispatch 串联包装层与 backend kernel。调用点因此只表达“执行哪个 operator”，设备与 mode 的组合由 dispatcher 在运行时解析。后文先建立这套运行时模型，再沿 aten::add.Tensor 的 CUDA 前向与反向路径连接 schema、注册、torchgen 和数值实现。

实现说明按公开的 PyTorch v2.12.0 源码核对。源码文件名、生成符号和内部 API 会随版本变化；第 6 章的调用链是针对文中输入条件、根据源码与 codegen 模板整理的阅读模型，不是跨版本稳定 API，也不覆盖所有 tensor layout、mode 或编译配置。

1. 调度键:运行时多维分派的基础

Dispatcher 的运行时模型可以归纳为三步:从张量参数和 TLS 状态构造 key set,选择优先级最高的运行时 key,再调用该算子在这个 key 下的 kernel。如果当前 kernel 是包装层,它会缩小 key set 并 redispatch,直到抵达实现数值计算的 backend kernel。

1.1 多维分派的工程约束

一行普通的 y = x + 1 已经包含运行时设备选择。对于不记录梯度的 Dense CPU float32 tensor，数值计算可以简化为 y[i] = x[i] + 1；若系统只支持 CPU 和 CUDA，玩具实现只需要一个设备分支：

// 仅用于说明单一设备维度
Tensor add(const Tensor& x, Scalar s) {
  if (x.is_cuda()) return add_cuda(x, s);
  return add_cpu(x, s);
}

真实调用还可能同时受 layout、autograd、autocast、函数变换和 Python mode 影响：

  • 普通的 autograd-capable 张量本身就携带 Autograd key，并不以 requires_grad 为开关。Autograd wrapper 被选中后，才根据 grad mode 和输入是否需要梯度决定是否创建 AddBackward0；v2.12.0 的 VariableFallbackKernel.cpp 说明了这一层的 fallback 语义。
  • Autocast 的精度策略按算子注册。以 v2.12.0 为界，mm 位于 CUDA lower-precision 列表中，而 add 不在其中；后者通过 fallthrough 保持常规类型提升语义。对应 policy 列表见 autocast_mode.h。
  • FakeTensorMode 主要通过 Python __torch_dispatch__ 子类拦截调用,再借助 Meta kernel 或 decomposition 推导输出元数据,不读取真实张量数据。
  • 稀疏 layout 需要独立的后端实现；同一项加法会进入稀疏算法，而不是 Dense elementwise loop。
  • torch.func.vmap 等函数变换会引入自己的包装层，并为算子增加 batch 维语义。

这些条件可以叠加,但并非每个激活的 TLS key 都有该算子的专用 kernel。Dispatcher 先合并张量 key set 与线程局部 include set,再应用 exclude set 和 fallthrough mask,最后按优先级选择可执行条目。于是每个包装层只处理自己的语义,完成后缩小 key set 并 redispatch。

如果把这组规则写成每个算子内部的条件树,结构会近似下面的玩具代码:

// 仅用于说明组合复杂度，不是 PyTorch 的实现
Tensor run_op(const Tensor& x, const Tensor& y) {
  if (python_mode_active()) return redispatch_from_python(x, y);
  if (autocast_active() && op_has_autocast_policy()) {
    return redispatch_with_cast_inputs(x, y);
  }
  if (autograd_key_active()) return redispatch_from_autograd(x, y);
  if (x.is_sparse() || y.is_sparse()) return sparse_kernel(x, y);
  if (x.is_cuda() || y.is_cuda()) return cuda_kernel(x, y);
  return cpu_kernel(x, y);
}

这种条件树有两项工程成本：

  1. 横切逻辑重复。Autocast、aliasing 和函数变换规则会散落在大量算子中，很难保持一致语义。
  2. 扩展入口封闭。新增 backend 或 mode 需要修改既有条件树，而不能只为其支持的算子增加注册项。
示例 1.1 新后端 Foo 不需要把 is_foo() 条件插进每个调用点。它为支持的算子注册 Foo kernel,未覆盖的算子则按明确的 fallback 或报错行为处理。扩展范围因此由注册项表达,而不是由分散的分支表达。

1.2 按 key 索引的函数表

PyTorch 把"该走哪条路"的决策从算子实现中抽出来,放进按 dispatch key 索引的查找表。

每个算子在 dispatcher 中都有一张按 DispatchKey 索引的 kernel 表。一个 key 可以表示数值后端，也可以表示 Autograd 或 Autocast 这样的包装层。最终表项还包含 backend fallback 与 alias key 展开等计算结果，因此它覆盖的内容多于源码中的显式注册项。

以 aten::add.Tensor 为例,下表只列与本文路径有关的条目。AutocastCUDA 对 add 使用 fallthrough；FakeTensor 也不是一行名为 Fake 的 add kernel:

DispatchKey          →  函数指针 (kernel)
─────────────────────────────────────────────────
CPU                  →  add 的 CPU structured wrapper
CUDA                 →  add 的 CUDA structured wrapper
SparseCPU            →  稀疏 CPU 实现
SparseCUDA           →  稀疏 CUDA 实现
MPS                  →  add 的 MPS 实现
AutogradCPU          →  生成的 Autograd wrapper
AutogradCUDA         →  生成的 Autograd wrapper
Meta                 →  structured meta 路径
AutocastCUDA         →  fallthrough

调用 torch.add(x, y) 时,dispatcher 完成三步:

  1. 构造候选 key set。合并所有张量参数的 key set、TLS include set 和 exclude set。
  2. 应用 fallthrough mask。已为该算子或 backend 注册为 fallthrough 的 key 不参与本次查找。
  3. 选择最高优先级条目。Dispatcher 从剩余 key set 取得最高 key,调用该算子表中的 kernel；包装层随后可以 redispatch。

Redispatch 负责包装层之间的控制转移。当前层处理完语义后，以缩小后的 key set 再次进入 dispatcher，从而跳过自身。下面使用具有 CUDA lower-precision autocast policy 的 torch.mm(x, y)：autocast 开启且输入参与梯度计算时，调用可以依次经过 AutocastCUDA、AutogradCUDA 和 CUDA；Autograd wrapper 是否创建 MmBackward0，仍由 grad mode 与输入属性在 wrapper 内判断。

1.3 DispatchKey 的枚举定义

c10/core/DispatchKey.h 定义所有 dispatch key。以下简化枚举表达功能层次；实际定义采用 functionality 与 backend 的二维拆分，详见 1.4 节。

// 简化示意: 真实定义见 1.4
enum class DispatchKey : uint16_t {
  Undefined = 0,

  // === 后端层(真的算数值)===
  CPU,
  CUDA,
  MPS,            // Apple Metal Performance Shaders
  XLA,            // Google TPU / XLA backend
  Meta,           // 只算 shape 不算数值
  ...
  SparseCPU,
  SparseCUDA,
  ...

  // === Autograd 层(在后端之前,负责建反向图)===
  AutogradCPU,
  AutogradCUDA,
  AutogradXLA,
  ...

  // === 模式层(在 autograd 之前,影响每一次算子调用)===
  ADInplaceOrView,   // in-place / view 的 autograd 元信息
  Tracer,            // 旧 JIT trace 记录
  AutocastCPU,
  AutocastCUDA,
  Fake,              // torchdistx 的遗留 out-of-core key
  Functionalize,     // 消除 alias/mutation
  Python,            // TorchDispatchMode (子类化拦截)
  ...                // 总共约 60 个

  NumDispatchKeys
};

这个简化枚举体现了三项运行时属性：

  • 类型是 uint16_t(16 位无符号整数)。Key 会作为下标编码进 64 位位图，16 位类型足以表示所有 key 及头部位标记。
  • 枚举是有序的。“优先级最高的 key”对应位图中最高位 1 的枚举值。例如 Autocast* 排在 Autograd* 后面，Autograd* 又排在 backend key 后面，因而同一次调用会先处理 autocast policy，再处理 autograd，最后执行 backend kernel。
  • 很多 key 不是张量属性。Autocast 和部分函数变换由 TLS 激活；Python tensor subclass 通过 Python key 进入 __torch_dispatch__；Autograd key 则通常存在于普通 autograd-capable tensor 的 key set 中。上面的 Fake 是 torchdistx 的遗留 key,不是当前 FakeTensorMode 的实现入口。
示例 1.3 普通 CPU tensor 在 requires_grad=False 时仍带有 AutogradCPU。x + 1 先进入 Autograd wrapper,wrapper 发现无需记录梯度后直接 redispatch 到 CPU；把 requires_grad 改为 true 不改变这一层的存在,只改变 wrapper 是否创建 AddBackward0。这一点可由 v2.12.0 的 VariableFallbackKernel.cpp 注释直接确认。

1.4 二维拆分:functionality × backend

若把每种行为与每个 backend 直接展开成笛卡儿积，枚举规模会随两个维度相乘。以新增 Habana（HPU）为例，直接展开需要加入下列条目：

HPU              // dense × Habana
SparseHPU        // sparse × Habana
SparseCsrHPU
QuantizedHPU
NestedTensorHPU
AutogradHPU      // autograd × Habana

这种编码让每个新 backend 增加约六个枚举值，并要求 enum 定义与相关 codegen 同步修改；新增 per-backend functionality 时还会再次扩张。PyTorch 因而把两个维度拆开编码。

2022 年的重构把枚举拆为两个正交集合，并在一张 64 位位图中组合（DispatchKey.h）：

  1. BackendComponent:表示具体后端。当前的位:CPU / CUDA / HIP / XLA / MPS / IPU / XPU / HPU / VE / Lazy / MTIA / MAIA / PrivateUse1‑3 / Meta。一个 static_assert 限定后端数 ≤ 16(DispatchKey.h 里有显式 16 位预算)。BackendComponent 需要与某个 functionality 组合后才构成分派级别。
  2. DispatchKey(功能 functionality)。绝大多数 functionality 只占一格(全局唯一 handler);六个是 "per-backend",需要和某个 BackendComponent 组合才落成一个运行时 key。这六个是:Dense、Quantized、Sparse、SparseCsr、NestedTensor、AutogradFunctionality。

组合规则(toRuntimePerBackendFunctionalityKey()):

(Dense,                CUDABit)  →  CUDA           // Dense CUDA 运行时 key
(Dense,                CPUBit)   →  CPU
(AutogradFunctionality, CUDABit) →  AutogradCUDA
(AutogradFunctionality, CPUBit)  →  AutogradCPU
(Sparse,               CUDABit)  →  SparseCUDA
(Quantized,            CPUBit)   →  QuantizedCPU
...

TORCH_LIBRARY_IMPL(aten, CUDA, m) 对应 (Dense, CUDA) 这一二维坐标。API 表面使用单个 CUDA key，底层位图则同时编码 Dense functionality 与 CUDA backend 位。给 BackendComponent 增加 HPU 位后，六个 per-backend functionality 可以与它组合出相应运行时 key，无需逐项扩展 enum。

示例 1.4 Habana（HPU）后端的 sparse 实现使用 (Sparse, HPU) 组合 key，并可通过 TORCH_LIBRARY_IMPL(aten, SparseHPU, m) 注册 kernel。SparseHPU 与 AutogradHPU 都由 functionality 和 backend 组合得到，无需成为独立枚举项。
边栏 1.4:drift 警告 ezyang 2019 年的 PyTorch internals 没有 BackendComponent 这一层,2020 年的 dispatcher 文章也没有。本节描述的二维拆分来自 2022 年后的实现；早期资料把 SparseCUDA 视为单独枚举值，而 v2.12.0 将其表示为 (Sparse, CUDABit) 的组合。

1.5 DispatchKeySet:64 位位图

DispatchKeySet 是把 functionality 与最多 16 个 BackendComponent 编码进 uint64_t 的运行时集合。每次 operator 调用都以这个 64 位值表示当前候选 key，随后由 lookup 选择最高优先级表项。

位图布局(DispatchKeySet.h 类注释):

这个 64 位整数由三个来源合并得到:

  1. 所有输入张量的 TensorImpl::key_set_ 的并集。每个张量的 TensorImpl 都缓存一个 DispatchKeySet,记录 device、layout 和可参与的功能层。Autograd key 并不编码当前 requires_grad 值。Dispatcher 对所有参数张量的 key set 求并集,由此实现多分派。
  2. TLS local include(线程局部"添加"):由 mode guard 设置。例如进入 with torch.autocast('cuda'): 后，上下文会把 AutocastCUDA 位加入 TLS；每次算子调用时，dispatcher 将 TLS include 与输入 key set 做按位或。
  3. TLS local exclude(线程局部"剔除"):用于 redispatch。autograd kernel 内部调 at::AutoDispatchBelowAutograd guard;,这个 RAII 对象把所有 autograd 位加入 TLS exclude。dispatcher 把 exclude 从位图里减掉,让最高位"自然"落到下一层。

第四个因素是 fallthrough mask。每个算子会缓存哪些 key 的最终条目明确注册为 fallthrough,这些位在 lookup 前被一次性清除。没有注册 kernel 不等于 fallthrough:缺失条目还可能继续查 backend fallback,最终也可能报错。以 Conjugate 为例,只有对应的 fallthrough registration 才能使它进入这张 mask,不能仅凭"该算子没有 Conjugate kernel"推断。

具体到代码,核心一行在 DispatchKeyExtractor.h:23-44:

// aten/src/ATen/core/dispatch/DispatchKeyExtractor.h
inline DispatchKeySet computeDispatchKeySet(
    DispatchKeySet ks,              // 输入参数张量 or 起来的 key_set
    DispatchKeySet key_mask) {      // 算子的 fallthrough mask
  c10::impl::LocalDispatchKeySet local = c10::impl::tls_local_dispatch_key_set();
  return (((ks | local.included_) - local.excluded_) & key_mask);
  //        ↑ 加 include    ↑ 减 exclude     ↑ 应用 fallthrough mask
}

这三段位运算得到 lookup 使用的最终 key set。lookup() 再从中选择最高优先级 key,1.6 节继续展开。

示例 1.5 设 x 和 y 是 CUDA fp32 矩阵,代码在 with torch.autocast('cuda'): 中调用 z = torch.mm(x, y)。

1. 两个输入的并集包含 {CUDABit, Dense, AutogradFunctionality}；这里是否有 AutogradFunctionality 不取决于 requires_grad。
2. autocast 上下文 push 了 AutocastCUDA 到 TLS include。
3. mm 在 v2.12.0 的 CUDA lower-precision policy 中,因此 AutocastCUDA 不会被 fallthrough mask 清除。
4. 最终位图组合 functionality + backend 后,等价于运行时 key 集合 {AutocastCUDA, AutogradCUDA, CUDA}。

这组运行时 key 构成 1.2 节受控例子的初始 key set。Policy 列表见 v2.12.0 的 autocast_mode.h；add 不在这份 lower-precision 列表中。

1.6 优先级阶梯

给定一个 64 位位图,dispatcher 用 highestPriorityTypeId() 取"最高位 1 对应的 functionality"。"最高"指的是位图里最高编号的 set bit: 功能位是按优先级排好的,bit 编号 = 优先级。

下图把常见 functionality 按优先级画出来,从上(最高)到下(最低):

找 key:取位图最高位 1,进入该层 kernel；redispatch 使用调用方传入的缩小 key set。 • autograd 高于 backend:wrapper 先判断是否记录反向,再 redispatch 到数值实现。 • autocast 高于 autograd:有显式 policy 的算子先转换输入,autograd 再观察转换后的调用。 • fallthrough:只有明确注册为 fallthrough 的条目才进入预计算 mask；缺失 kernel 不是同义词。

Catch-all 与 alias key 是两件事。DispatchKey::CatchAll 是 Undefined 的别名,表示注册时没有指定 dispatch key；v2.12.0 的 OperatorEntry 把这类 registration 重定向到 CompositeImplicitAutograd 存储。Alias key 则描述一组 runtime keys 的覆盖范围,在计算最终 dispatch table 时按优先规则填充条目:

  • Autograd 覆盖 backend-specific autograd keys。TORCH_LIBRARY_IMPL(ns, Autograd, m) 因而可以为这些 key 提供同一实现。
  • CompositeImplicitAutograd 适合由其他 dispatched operators 组合出的实现。组成算子保留后端选择与 autograd 语义,但最终条目的覆盖还要服从直接 registration 和其他 composite alias 的优先关系。
  • CompositeExplicitAutograd 表示后端无关但需要单独处理 autograd 的实现；它不会替代应注册的 autograd formula。

这些 alias 提供跨 key 的覆盖语义。它们会参与 computed dispatch table 的填充与 precedence 计算,而一次实际 lookup 仍以 AutogradCUDA、CUDA 等 runtime key 定位条目。具体规则见 v2.12.0 的 OperatorEntry.cpp。

1.7 redispatch 的层间控制转移

包装层完成本层工作后，需要把控制权交给下一优先级 key，同时避免再次命中自身。Redispatch 通过调用方提供的 key set 实现这项层间转移。

Autograd kernel 建立 grad_fn 并记录 next_edges 后，还要继续调用 backend kernel。若直接从顶层重新调用 at::add(x, y)，dispatcher 仍可能再次选中 AutogradCUDA，形成递归。

Dispatcher::redispatch 接收已经调整过的 key set（Dispatcher.h:833-848）：

// 关键注释(从源码):"redispatch treats the inputted DispatchKeySet as is,
//  and does NOT mask out the highest priority bit"
//: 调用方负责把"当前 key"从位图剔掉,再传进来
template <class Return, class... Args>
inline Return Dispatcher::redispatch(
    const TypedOperatorHandle<Return(Args...)>& op,
    DispatchKeySet currentDispatchKeySet,    // ← 调用方已经把当前 key mask 掉
    Args... args) const {
  const KernelFunction& kernel = op.operatorDef_->op.lookup(currentDispatchKeySet);
  return kernel.template call<Return, Args...>(op, currentDispatchKeySet, ...);
}

顶层 Dispatcher::call 根据输入 tensor key set 与 TLS 状态重新计算候选集合；redispatch 直接使用调用方传入的集合。包装层因此能够明确移除已经处理的 key，再选择下一表项。

Autograd kernel 使用 RAII guard 与显式 mask 移除当前层：

  • at::AutoDispatchBelowAutograd(历史名称 AutoNonVariableTypeMode):构造时把所有 autograd functionality 位加入 TLS excluded_，析构时还原。该对象存续期间，所有算子调用的位图都会移除 autograd 位。
  • at::AutoDispatchBelowADInplaceOrView:进一步把 ADInplaceOrView 也加入 exclude。这是 codegen 生成的 VariableType wrapper 标准用法:autograd kernel 通过该 guard 执行 redispatch，随后选择 backend。

两项机制组合后，autograd kernel 的控制流可简化为下面的 codegen 骨架：

// AutogradCUDA kernel for aten::add.Tensor (简化)
Tensor VariableType::add_Tensor(
    c10::DispatchKeySet ks,
    const Tensor& self, const Tensor& other, const Scalar& alpha) {

  // ① 建反向节点(只在需要 grad 时)
  std::shared_ptr<AddBackward0> grad_fn;
  if (compute_requires_grad(self, other)) {
    grad_fn = std::make_shared<AddBackward0>();
    grad_fn->set_next_edges(collect_next_edges(self, other));
  }

  // ② 进入 "below autograd" 范围 → autograd 位被剔出位图
  auto result = [&]() {
    at::AutoDispatchBelowADInplaceOrView guard;
    return at::redispatch::add(
        ks & c10::after_autograd_keyset,    // 显式 mask 当前 key
        self, other, alpha);
  }();

  // ③ 把 grad_fn 挂到输出
  if (grad_fn) set_history(result, grad_fn);
  return result;
}
示例 1.7:完整 redispatch 流程 对于 z = x + y，当 x, y 位于 CUDA 且 requires_grad=True 时，完整路径如下：

(a) 顶层 Dispatcher::call 算出位图 = {AutogradCUDA, CUDA},最高位 = AutogradCUDA,跳到 VariableType::add_Tensor。
(b) 函数体进入 RAII guard AutoDispatchBelowADInplaceOrView:TLS exclude 里加上所有 autograd 位 + ADInplaceOrView 位。
(c) 调 at::redispatch::add(ks & after_autograd_keyset, ...)。after_autograd_keyset 是预算好的"清掉所有 autograd 及以上位"的掩码,显式确保 AutogradCUDA 不会再被选中。
(d) Dispatcher::redispatch 直接用这个位图 lookup,最高位现在是 CUDA,跳到 wrapper_CUDA_add_Tensor。
(e) CUDA wrapper 完成数值计算并返回。
(f) 控制流返回 autograd kernel，set_history(result, grad_fn) 将反向节点关联到输出。

guard 在 (e) → (f) 之间析构，TLS exclude 随之还原，后续顶层调用重新从完整的线程局部状态计算 key set。
Dispatcher 的一次 operator 调用可以包含多次表项选择。functionality 的 bit 顺序决定层次，包装层通过 RAII guard 与显式 mask 移除自身，再由 redispatch 选择下一最高优先级 key。

2. Schema:算子的类型签名

运行时 key 选择需要一个稳定的 operator 身份与参数契约。Schema 记录 aten::add.Tensor 的参数、返回值、overload、alias 与 mutation 语义，使 dispatcher 及其上层工具能够解释同一个调用。

Schema 是由 dispatcher、autograd、JIT、functionalization 与 Python binding 共同读取的接口契约。Dispatcher 用 tensor 参数构造 key set，autograd 与 functionalization 读取 alias 和 mutation 信息，Python binding 据此生成参数解析代码。把 Tensor(a!) 误写为 Tensor(a) 会隐藏实际写入，使依赖该契约的变换产生错误结果。

下面依次说明 schema 的字符串语法、变体命名规则以及它在 YAML 中的声明形式。

2.1 Schema 字段语义

以 aten::add.Tensor 的 schema 为例：

aten::add.Tensor(Tensor self, Tensor other, *, Scalar alpha=1) -> Tensor

这段字符串接近 Python 函数签名，但命名空间、overload、参数分隔符和 alias 标记都参与 operator 契约：

位置片段语义
1aten命名空间。PyTorch 内置算子都在 aten 下;自定义算子(扩展)在自己命名空间下,比如 myops::foo。命名空间隔离了"哪些 op 能被找到",也决定了用哪个 TORCH_LIBRARY* 宏注册(见 3 章)。
2::命名空间分隔符,跟 C++ 一样。
3addop 名。同一个 op 名下可以有多个 overload(像 C++ 的函数重载)。
4.Tensoroverload 名。这是关键: add 有 add.Tensor(两个张量相加)和 add.Scalar(张量加标量)两个 overload。可省略,等于 overload 名为 ""(空串)。dispatcher 把"aten::add.Tensor"作为完整 key 来索引函数表。
5(...)参数列表。
6Tensor self第一个 positional 参数,类型 Tensor,名字 self。约定:类似"Python 方法"中的 self: autograd 会把它当成"主"输入。
7Tensor other第二个 positional 参数,类型 Tensor。
8*关键词分隔符。从这里开始,后面的参数必须用关键字传(add(x, y, alpha=2)),不能位置传。和 Python 函数定义里的 * 完全一样。

类型语法覆盖一系列原语和复合类型:

Tensor?可空张量(对应 C++ std::optional<Tensor>)

Alias 注解（(a) 和 (a!)）把 storage 共享与 mutation 契约传给多个下游组件：
• functionalization 用它决定"这个 op 是否产生副作用,要不要展开成函数式形式"
• autograd 用它决定"这个 op 是否产生 view,要不要建 DifferentiableViewMeta"
• JIT 用它做 alias analysis(两个变量会不会指向同一块内存,影响死代码消除等优化)
• inductor / functorch 都依赖这套注解

把只读 alias (a) 误写成 (a!),会让下游保守地把算子视为有 mutation,可能阻止合法变换；更危险的反向错误是漏掉 !,因为 functionalization 和 alias analysis 将看不见实际发生的写入。Schema 注解只能描述别名与 mutation 契约,不能代替实现测试。
示例 2.1:alias 注解的作用 aten::transpose 的 schema 如下： 
aten::transpose.int(Tensor(a) self, int dim0, int dim1) -> Tensor(a)
Tensor(a) 出现在 self 和返回值上: 它们共享同一个名为 a 的"内存位"。这告诉 dispatcher 下游:转置后的张量和原张量共享存储,改其中一个的元素另一个也变。

对比 aten::clone: 
aten::clone(Tensor self, *, MemoryFormat? memory_format=None) -> Tensor
返回值没有 alias 标记 → 它是新分配的内存,改它不影响 self。

注册时,这个字符串会被 torch::jit::parseSchema 解析进一个 c10::FunctionSchema 结构体,记录每个参数的名字、类型、alias 信息、默认值;然后才登记到 dispatcher 的内部 op 表里。所以"schema 字符串"是源头,FunctionSchema 是它的 in-memory 表示。

2.2 三种变体:functional / in-place / out

很多算子具有副作用能力(in-place 改写、写入预分配的 out 张量)。PyTorch 给这类算子同时提供三种 schema 变体，功能等价但接口不同。add 的三个变体如下：

变体schema
functionaladd.Tensor(Tensor self, Tensor other, *, Scalar alpha=1) -> Tensor
in-placeadd_.Tensor(Tensor(a!) self, Tensor other, *, Scalar alpha=1) -> Tensor(a!)
outadd.out(Tensor self, Tensor other, *, Scalar alpha=1, Tensor(a!) out) -> Tensor(a!)

命名约定:

  • functional:返回新张量。Python 里写 z = x.add(y)。最常用,对应 schema 的"基础形态"。
  • in-place:op 名末尾加 _(下划线),self 加 (a!),返回也是 (a!) 表示"返回的就是改后的 self"。Python 里写 x.add_(y)。它会修改已有 storage 与 version counter,在 aliasing 和 autograd 上不等价于 x = x + y。
  • out:overload 加 .out,多一个 kw-only 的 Tensor(a!) out。Python 里写 torch.add(x, y, out=z),把结果写进预分配的 z。常用于复用内存的优化场景。

三种 schema 分别编码输出分配、原位修改和调用方提供输出的契约:

  1. 接口契约。Python 分别暴露返回新张量、修改既有张量和写入指定张量的调用形式。
  2. 性能。functional 总是分配新内存,in-place 和 out 可复用,对训练阶段的内存峰值差距很大。
  3. autograd 行为。三个变体的处理不同:functional 可以建立 grad_fn,in-place 需要维护 version counter 并可能拒绝对 requires-grad leaf 的写入；当任一参数需要梯度时,out 变体通常不支持 autograd,不能把它视为两者之间的折中。
示例 2.2:三个变体共用实现 三个 schema 可以共享同一组 structured kernel 的 meta() 与 impl() 逻辑,但生成的 functional wrapper 并不会再次 dispatch 到 add.out: 
add.Tensor   :  functional wrapper 分配输出,调用共享 meta() / impl()
add_.Tensor  :  inplace wrapper 绑定 self,调用共享 meta() / impl()
add.out      :  out wrapper 绑定用户提供的 out,调用共享 meta() / impl()
structured_delegate: add.out 指定共享 structured definition 的锚点。Torchgen 为每个变体生成各自的 wrapper class,在 wrapper 内直接进入共同的 structured implementation。v2.12.0 的生成模板见 register_dispatch_key.py。
边栏 2.2:autogen 关键字 某些算子作者只写 functional 一份,告诉 codegen "请按规则补齐 in-place 和 out 变体": 
- func: my_op(Tensor self) -> Tensor
  autogen: my_op.out, my_op_
codegen 看到 autogen: 后会按允许的规则补出相应 schema 与 adapter。生成方向取决于源变体和 operator metadata,不能概括成固定的"out 包装 functional"。实现仍须满足生成变体的 aliasing、resize 与 dtype 契约。

PyTorch 内置算子的 schema 主要声明在 aten/src/ATen/native/native_functions.yaml。每个 YAML 条目除了 schema，还包含供构建期 codegen 使用的元数据：

这里 dispatch: CPU, CUDA: relu 把同一个 at::native::relu 入口注册到两个 backend key。该入口在 Activation.cpp 中构造 TensorIterator 并调用 device dispatch stub,stub 再选择 CPU 或 CUDA kernel；这不是链接器按 device 选择 C++ overload。它说明 dispatcher 之后还可以有算子内部的设备 stub 与 dtype 分派层。

边栏 2.3:Structured codegen 的共享阶段 没有 structured codegen 时,functional / inplace / out 变体要分别处理输出创建、resize、设备检查和 implementation 调用,这些胶水很容易漂移。Structured kernel 把共同工作分成 meta() 与 impl(),再由 codegen 为各个变体生成 wrapper。共享的是实现逻辑与约束,不是一次从 functional schema 到 out schema 的二次 dispatcher 调用。

2.4 derivatives.yaml:反向公式

到目前为止 schema 只描述了"前向行为"。反向(autograd)信息在另一个文件里:tools/autograd/derivatives.yaml。每个 differentiable op 在这里给一段反向公式:

- name: add.Tensor(Tensor self, Tensor other, *, Scalar alpha=1) -> Tensor
  self:  handle_r_to_c(self.scalar_type(),  grad)
  other: handle_r_to_c(other.scalar_type(), maybe_multiply(grad, alpha.conj()))
  result: self_t + maybe_multiply(other_t, alpha)            # forward-mode tangent

- name: relu(Tensor self) -> Tensor
  self: threshold_backward(grad, result, 0)
  result: auto_element_wise

各字段对应的 codegen 语义如下：

  • name: 必须和 native_functions.yaml 里的 schema 完全一致: 这是匹配两边的"主键"。
  • self:、other: 是输入参数名,对应表达式给出该输入的梯度。例如 add 的 other 输入梯度为 grad * alpha.conj()；maybe_multiply 在 alpha == 1 时省去乘法。预定义变量 grad 表示本次 backward 收到的上游梯度。
  • result: 是用于 torch.func.jvp 的前向模式(jvp / tangent)公式。预定义变量 self_t、other_t 表示对应输入的切向量；不提供 jvp 支持时可以省略该字段。
  • auto_element_wise 是个特殊标记,告诉 codegen "这是个 elementwise op,jvp 公式按规则自动推导"。

这些公式采用 codegen 解析的受限 DSL：表达式可以调用其他 at::* operator(如 threshold_backward)、访问输入属性(如 self.scalar_type())，并引用 grad、result、self_t 等预定义变量。

Autograd codegen 为每个 differentiable operator 生成两类代码:

  1. 一个 autograd Node 子类(例如 AddBackward0、ReluBackward0),它的 apply() 方法体就是公式翻译成的 C++ 代码。
  2. 一个 autograd kernel wrapper(注册到 AutogradCPU/AutogradCUDA 等 key),在前向时建这个 Node、挂 next_edges、redispatch 到 backend(就是 1.7 节那段骨架代码)。
示例 2.4:derivatives.yaml 与生成代码的对应 derivatives.yaml 里 add 的反向公式: 
other: handle_r_to_c(other.scalar_type(), maybe_multiply(grad, alpha.conj()))
被 codegen 翻译成 AddBackward0::apply() 里的: 
if (should_compute_output(1)) {
  grad_inputs[1] = handle_r_to_c(other_scalar_type,
                                 maybe_multiply(grad, alpha.conj()));
}
几乎是一比一翻译(只多了"要不要算这个梯度"的判断,因为某些下游可能不需要 other 的梯度,跳过能省计算)。

AddBackward0::apply() 的生成代码及其在 loss.backward() 中的执行路径见 6.8 节。

Schema 为 dispatcher、autograd、JIT、functionalization 和 Python binding 提供共同契约，其中 alias 注解决定 storage 共享与 mutation 语义。native_functions.yaml 保存 operator 声明，derivatives.yaml 保存微分公式；两者分别进入 ATen 与 autograd codegen，并在生成的注册表和 wrapper 中汇合。

3. C++ 注册接口:TORCH_LIBRARY 家族

Schema 确立 operator 契约后，注册接口把契约与实现写入 dispatcher。torch/library.h 中的 TORCH_LIBRARY 家族分别负责声明 schema、扩展 namespace 和为既有 operator 挂接 kernel。

TORCH_LIBRARY、TORCH_LIBRARY_FRAGMENT 和 TORCH_LIBRARY_IMPL 最终都创建一个静态初始化入口,但三种 Library::Kind 对 schema、默认 dispatch key 和 namespace 唯一性的约束不同。

共同机制:通过 file-static initializer,在可执行文件启动或共享库装载时向全局 dispatcher 注册信息。

差异在于注册 schema、追加 namespace 片段,还是为既有 operator 挂接 kernel。理解这层约束后,boxed/unboxed、fallback/fallthrough 和 def/impl 的关系才不会混在一起。

3.1 Library 的三种身份:DEF / FRAGMENT / IMPL

注册入口的核心对象是 torch::Library。每个 TORCH_LIBRARY* 宏都会构造一个 Library 实例，其 Kind 分为三类（torch/library.h:551-553）：

// torch/library.h
class Library {
 public:
  enum Kind { DEF, IMPL, FRAGMENT };
  ...
};

三种 Kind 对应三种语义:

Kind语义触发宏典型用户
DEF给某个 namespace开一个"主"库。整个进程里一个 namespace 名只允许出现一个 DEF；第二个 DEF 会在 Dispatcher::registerLibrary 注册阶段被拒绝。TORCH_LIBRARY(ns, m)自定义扩展(给自己开一个 myops 命名空间)
FRAGMENT给同 namespace追加一片"片段"。同名 fragment 可以来自任意多个翻译单元(TU),拼到一起算一个库。TORCH_LIBRARY_FRAGMENT(ns, m)PyTorch 内部:aten 的 operator schema 分布在多个 codegen 文件中
IMPL给"已存在的某个 op"挂一个 DispatchKey 上的 kernel。不能在这里定义新 schema,只能 m.impl(...) 给现有 op 注册实现。TORCH_LIBRARY_IMPL(ns, key, m)给某后端注册具体实现(aten 的 CUDA wrapper、自定义 op 的 CUDA kernel 等)
示例 3.1:三种 Kind 的实际用例 扩展 my_extension 注册 myops::custom_relu，并分别提供 CPU 与 CUDA 实现。三个 C++ 文件按下列职责拆分：

register_schema.cpp 用 TORCH_LIBRARY(myops, m) → DEF,声明 schema。这一行存在,myops 命名空间才"开"了。
kernel_cpu.cpp 用 TORCH_LIBRARY_IMPL(myops, CPU, m) → IMPL,给 CPU 注册实现。
kernel_cuda.cu 用 TORCH_LIBRARY_IMPL(myops, CUDA, m) → IMPL,给 CUDA 注册实现。

Schema 与 kernel 可以写在同一个 DEF 块。m.impl 既有继承当前 block key 的重载,也有显式接收 dispatch key 的便利重载；torch::dispatch(key, fn) 也能把 key 附在 CppFunction 上。多后端项目通常仍用多个 IMPL 块,因为 block 级 key 更清楚,但这不是 API 的语法限制。
边栏 3.1:三个宏编码不同约束 TORCH_LIBRARY 创建 DEF,不携带 block-level dispatch key；TORCH_LIBRARY_IMPL 创建 IMPL 并携带 key；FRAGMENT 允许多个注册块追加 schema。C10_UID 用于避免 FRAGMENT 与 IMPL initializer 在同一翻译单元中的名字冲突。"一个 namespace 只能有一个 DEF"由 Dispatcher::registerLibrary 在运行时注册阶段检查,不是依赖链接期重复符号完成。

3.2 TORCH_LIBRARY:开新命名空间

TORCH_LIBRARY 的宏定义位于 torch/library.h:982-991:

// torch/library.h
#define TORCH_LIBRARY(ns, m)                                                   \
  static void TORCH_LIBRARY_init_##ns(torch::Library&);                        \
  static const torch::detail::TorchLibraryInit TORCH_LIBRARY_static_init_##ns( \
      torch::Library::DEF,                                                     \
      &TORCH_LIBRARY_init_##ns,                                                \
      C10_STRINGIZE(ns), std::nullopt,                                         \
      __FILE__, __LINE__);                                                     \
  void TORCH_LIBRARY_init_##ns(torch::Library& m)

这个宏展开为三个声明:

  1. 第 1 行:static void TORCH_LIBRARY_init_##ns(torch::Library&);: 前向声明一个函数(##ns 是 token 拼接,如果 ns=myops,这就是 TORCH_LIBRARY_init_myops)。
  2. 第 2-5 行:static const torch::detail::TorchLibraryInit TORCH_LIBRARY_static_init_##ns(DEF, ...);: 构造一个文件级 static 对象。它的构造函数收到这些参数:
    • torch::Library::DEF: 身份标记,这是 DEF 不是 IMPL。
    • &TORCH_LIBRARY_init_##ns: 用户提供的"注册函数"(第 1 行声明的那个),构造函数会调用它。
    • C10_STRINGIZE(ns): namespace 字符串字面量("myops")。
    • std::nullopt: DispatchKey,DEF 时为空。
    • __FILE__, __LINE__: 报错时的位置信息。
  3. 第 6 行:void TORCH_LIBRARY_init_##ns(torch::Library& m): 这是函数的定义头,用户的 { ... } 紧接在宏之后提供函数体。

TORCH_LIBRARY(myops, m) { m.def("..."); } 这一调用形式展开为:

static void TORCH_LIBRARY_init_myops(torch::Library&);
static const torch::detail::TorchLibraryInit TORCH_LIBRARY_static_init_myops(
    torch::Library::DEF,
    &TORCH_LIBRARY_init_myops,
    "myops", std::nullopt,
    "/path/to/myops.cpp", 42);

// 用户的 { ... } 提供这个函数的 body:
void TORCH_LIBRARY_init_myops(torch::Library& m)
{
  m.def("...");
}

关键在文件级 static 对象的初始化时机。对于直接链接的代码,initializer 在进入 main() 前运行；对于 Python 动态扩展,它在共享库被装载时运行。两种情况下,TorchLibraryInit 都会调用注册函数,无需用户再显式调用该函数。

示例 3.2:用法 
// myops_register.cpp
#include <torch/library.h>

TORCH_LIBRARY(myops, m) {
  m.def("custom_add(Tensor self, Tensor other) -> Tensor");
  m.def("custom_relu(Tensor self) -> Tensor");
}
这一段编译并链接进 Python 进程后,torch.ops.myops.custom_add 与 torch.ops.myops.custom_relu 已能被 Python 解析。此时 schema 已进入 dispatcher,实际调用则会因为缺少 backend kernel 而报告 "no kernel registered"。
关键限制:同一个 namespace 在整个进程里只能有一个 TORCH_LIBRARY(ns, ...)。第二个 DEF 会在 Dispatcher::registerLibrary 阶段触发注册错误；若要把 schema 分散到多个 .cpp 文件,应使用 TORCH_LIBRARY_FRAGMENT。

3.3 TORCH_LIBRARY_FRAGMENT:同命名空间拼接

FRAGMENT 解决"同 namespace 跨文件"的需求。看宏(torch/library.h:1001-1023,简化):

// torch/library.h (简化)
#define TORCH_LIBRARY_FRAGMENT(ns, m) _TORCH_LIBRARY_FRAGMENT(ns, m, C10_UID)
#define _TORCH_LIBRARY_FRAGMENT(ns, m, uid)                                \
  static void C10_CONCATENATE(TORCH_LIBRARY_FRAGMENT_init_##ns##_, uid)(   \
      torch::Library&);                                                    \
  static const torch::detail::TorchLibraryInit                             \
      C10_CONCATENATE(TORCH_LIBRARY_FRAGMENT_static_init_##ns##_, uid)(    \
          torch::Library::FRAGMENT,                                        \
          ...,                                                             \
          C10_STRINGIZE(ns), std::nullopt, ...);                           \
  void C10_CONCATENATE(...)(torch::Library& m)

和 TORCH_LIBRARY 比,只有两点不同:

  1. Kind 从 DEF 改成 FRAGMENT: 这告诉 Library 构造函数"不要因为重复 namespace 而 abort"。
  2. 符号名用 C10_UID 唯一化。C10_UID 是 PyTorch 内部的"行号 + counter"宏,每次展开都生成不同的 token。这样同一个 TU 里写 5 个 TORCH_LIBRARY_FRAGMENT(aten, m) { ... },它们的 init 函数名互不冲突。
边栏 3.3:aten namespace 的分片注册 PyTorch codegen 生成的 RegisterCPU.cpp、RegisterCUDA.cpp 和 RegisterSchema.cpp 等文件使用 TORCH_LIBRARY_FRAGMENT(aten, m)。对应的生成逻辑位于 torchgen/gen.py：
# torchgen/gen.py 1761-1776 附近(简化)
if namespace == "aten":
    aten_schema_registrations = schema_registrations_body
else:
    torch_library_macro = (
        "TORCH_LIBRARY_FRAGMENT"
        if namespace in FRAGMENT_NAMESPACES
        else "TORCH_LIBRARY"
    )
aten 包含大量 operator schema,codegen 因而把注册语句分散到多个编译单元。FRAGMENT 允许这些编译单元独立生成 initializer,共同扩展同一个 namespace,也避免把全部注册代码集中在单个初始化函数中。
示例 3.3:同 namespace 跨文件的 fragment 当 myops 按模块拆分注册时，算子族 A 与 B 可以分别位于 a.cpp 和 b.cpp： 
// myops_a.cpp
TORCH_LIBRARY_FRAGMENT(myops, m) {
  m.def("op_a1(Tensor x) -> Tensor");
  m.def("op_a2(Tensor x) -> Tensor");
}

// myops_b.cpp
TORCH_LIBRARY_FRAGMENT(myops, m) {
  m.def("op_b1(Tensor x) -> Tensor");
}
两个文件并存,各自的 TorchLibraryInit 都在 main 之前跑,把对应 schema 添加到 myops 命名空间。

整个进程仍然至多有一个 TORCH_LIBRARY(myops, ...)(DEF),但 FRAGMENT 不要求先存在 DEF。在 v2.12.0 中,只有 DEF 调用 registerLibrary 做 namespace 唯一性检查；FRAGMENT 只要求 namespace 不是通配符 _,随后可以直接定义 operator。对应分支见 library.cpp。

3.4 TORCH_LIBRARY_IMPL:挂载 kernel

schema 是"声明",kernel 才是"实现"。TORCH_LIBRARY_IMPL 是给已存在的 op 挂某个 DispatchKey 上的 kernel 的宏(torch/library.h:1064-1084,简化):

// torch/library.h (简化)
#define TORCH_LIBRARY_IMPL(ns, k, m) _TORCH_LIBRARY_IMPL(ns, k, m, C10_UID)
#define _TORCH_LIBRARY_IMPL(ns, k, m, uid)                                  \
  static void C10_CONCATENATE(TORCH_LIBRARY_IMPL_init_##ns##_##k##_, uid)(  \
      torch::Library&);                                                    \
  static const torch::detail::TorchLibraryInit                              \
      C10_CONCATENATE(TORCH_LIBRARY_IMPL_static_init_##ns##_##k##_, uid)(   \
          torch::Library::IMPL,                                             \
          ...,                                                              \
          C10_STRINGIZE(ns),                                                \
          c10::make_optional(c10::DispatchKey::k),                          \
          ...);                                                             \
  void C10_CONCATENATE(...)(torch::Library& m)

和 FRAGMENT 比的差别:

  • Kind = IMPL。
  • 多了一个参数 c10::DispatchKey::k(k 是用户传的第二个宏参数,如 CPU、CUDA、AutogradCUDA)。块内的每一次 m.impl("op_name", kernel) 都会被附加到 op 在这个 DispatchKey 下的 dispatch 表项里。
示例 3.4:典型用法 
// myops_cpu.cpp: 给 myops::* 在 CPU key 上注册 kernel
TORCH_LIBRARY_IMPL(myops, CPU, m) {
  m.impl("custom_add",  &my_add_cpu);
  m.impl("custom_relu", &my_relu_cpu);
}

// myops_cuda.cu: 给 myops::* 在 CUDA key 上注册 kernel
TORCH_LIBRARY_IMPL(myops, CUDA, m) {
  m.impl("custom_add",  &my_add_cuda);
  m.impl("custom_relu", &my_relu_cuda);
}

// myops_autograd.cpp: 单独一个 autograd 包装,用来挂 grad_fn
TORCH_LIBRARY_IMPL(myops, Autograd, m) {       // Autograd 是 alias key,自动展开到 AutogradCPU/CUDA/...
  m.impl("custom_add", &my_add_autograd);
}
三个文件链接进来之后,myops::custom_add 有 CPU、CUDA 和 Autograd alias registrations。Computed dispatch table 按 alias precedence 填入对应 runtime entries。普通 autograd-capable tensor 会先进入 Autograd 层；是否真的记录梯度由该 wrapper 内部判断,不是 lookup 以 requires_grad 为条件。
特殊形式 TORCH_LIBRARY_IMPL(_, KEY, m):第一个参数下划线表示"所有 namespace 都套用",通常配合 m.fallback(...) 给某个 DispatchKey 注册全局兜底 kernel。一个例子:
// aten/src/ATen/core/VariableFallbackKernel.cpp
TORCH_LIBRARY_IMPL(_, AutogradCUDA, m) {
  m.fallback(autogradNotImplementedFallback());
}
含义:任何 namespace 下的算子如果没有更具体的 AutogradCUDA 条目,都会进入这个 backend fallback。它不会自动推导正确梯度。v2.12.0 的源码注释明确说明该 fallback 只检查 autograd 条件后下传,不是正确 autograd implementation；自定义算子需要注册 autograd formula,或者由可微的 dispatched operators 构成 CompositeImplicitAutograd 实现。证据边界见 VariableFallbackKernel.cpp。

3.5 m.def 与 m.impl 的语义差异

m.def 和 m.impl 是 Library 对象上最常用的两个方法。它们职责完全不同:

m.defm.impl
在哪用DEF / FRAGMENT；源码会拒绝在 IMPL 中调用 defLibrary 的通用方法；最常见于 IMPL,也可在 DEF / FRAGMENT 中配合 catch-all 或显式 key
作用声明 schema:给 operator name 注册类型签名给已声明的 op 挂 kernel:默认继承 block 的 DispatchKey,也可由 CppFunction 显式携带 key
关键参数schema 字符串("custom_add(Tensor self, Tensor other) -> Tensor")op 名("custom_add")+ 函数指针(&my_kernel)
schema 校验第一次 def 锁定签名;后续不能改kernel 签名必须和 schema 解析后的类型兼容(否则注册时 abort)
能否同时挂 kernel可以。未指定 key 时是 no-key/catch-all registration；也可传入 torch::dispatch(key, fn)可以挂 block key、显式 key 或 no-key kernel,具体取决于 block 与 CppFunction

三种常见 m.impl 写法:

// (a) raw function pointer: 框架推断函数签名
m.impl("op_name", &cpu_kernel);

// (b) TORCH_FN 包装:用编译期函数指针封装重载与签名
m.impl("op_name", TORCH_FN(cpu_kernel));

// (c) 强制走 boxed(用于 fallback、interpreter 等不预知签名的场景)
m.impl("op_name", torch::CppFunction::makeFromBoxedFunction<&boxed_fn>());
示例 3.5:schema 类型不兼容 给定 schema: 
m.def("custom_add(Tensor self, Tensor other) -> Tensor");
后来注册 kernel: 
at::Tensor wrong_kernel(const at::Tensor& self, int other) { ... }
m.impl("custom_add", TORCH_FN(wrong_kernel));   // 类型不匹配!
程序启动时(static initializer 执行时)会立即 abort,错误信息大概是: 
Tried to register a kernel for operator myops::custom_add with type
Tensor(const Tensor&, int): but the schema declares type Tensor(Tensor, Tensor).
Schema 是注册契约的单一可信源,每个 kernel 的签名都必须与它兼容。

3.6 Boxed 与 unboxed 调用路径

Dispatcher 查表得到 KernelFunction 后,KernelFunction 根据调用点是否具有静态类型签名选择 unboxed 或 boxed 路径。前者使用 typed C++ 参数,后者使用统一的 IValue stack ABI。

UnboxedBoxed
函数签名原生 C++:Tensor (*)(const Tensor&, const Tensor&, Scalar)统一:void (*)(const OperatorHandle&, DispatchKeySet, Stack*)
参数传递模板直接展开,零拷贝、无类型擦除所有参数被打包成 IValue 压在 Stack(std::vector<IValue>)上,kernel 自己从 stack pop
性能通常省去装箱/拆箱包含 IValue 装箱/拆箱开销;具体差值依编译器、签名和构建配置而定
什么时候用用户代码、codegen 出来的 wrapper: 调用现场知道签名fallback kernel、functorch interpreter、JIT runtime、profiler hook: op-agnostic 的场景

TORCH_FN(fn) 把函数指针包装成编译期可用的 CompileTimeFunctionPointer,对重载消歧和模板签名检查很方便。直接传 &fn 同样可以推断签名并建立 unboxed/boxed adapter；TORCH_FN 本身并不会解锁一条更快的调用路径。

边栏 3.6:m.impl_UNBOXED 的历史 旧版 m.impl_UNBOXED("name", &fn) 明确注册的是 unboxed C++ kernel,不是 boxed-only kernel。v2.12.0 保留了一个只会触发 static_assert 的兼容入口,错误信息要求直接改用 .impl(...)。makeFromBoxedFunction 用于本来就符合 boxed ABI 的函数,不是 impl_UNBOXED 的等价迁移。源码见 torch/library.h。

3.7 Fallback 与 fallthrough

除了 m.def 和 m.impl,Library 还有一个 m.fallback。它的语义是:给整个 DispatchKey 注册一个 op-agnostic 的 kernel,在该 key 下"没有单独 impl 的 op"都走它。

常见两种用法:

m.fallback(torch::CppFunction::makeFallthrough());
    // "我这层不做事,把我的 bit 从位图清掉再走下一层"
    // O(1) 实现:dispatcher 看到这是 fallthrough,直接在 fallthrough_mask 里把这个 key 永久清零

m.fallback(torch::CppFunction::makeFromBoxedFunction<&my_boxed_fallback>());
    // 真的写个 boxed kernel 兜底,比如 functorch 的 vmap interpreter

Fallthrough registration 会进入算子的预计算 mask,lookup 因而可以在调用 kernel 前清除对应 key。它减少了逐层调用,但本文不把成本写成绝对的零；构造 key set、应用 mask 和后续 lookup 仍是运行时工作。

典型 fallthrough 用户:

  • BackendSelect:绝大多数 op 不需要它(只有 factory function 如 torch.randn 才用)。对所有其他 op,BackendSelect fallthrough。
  • Named:仅当 tensor key set 激活 Named 时才会成为候选；算子对该 key 的最终条目可能是 fallthrough 或专用处理。
  • Conjugate / Negative / ZeroTensor:惰性标记存在时才会激活相应 key,随后由具体 registration 或 fallback 决定行为。
  • Tracer:是否激活由 tracing 状态决定,是否跳过则由最终 dispatch entry 决定。

多数调用只激活少量与当前 tensor 和 TLS 状态相关的 key；激活但明确 fallthrough 的 key 又会被 mask 清除。"未激活"与"已激活但 fallthrough"是两种不同情况,前者从未进入候选集,后者由 registration 决定跳过。

设计边界:扩展层可以用 TLS 或 tensor key 激活,并用 fallthrough registration 表示某些 operator 无需处理该层。这样 mode 的语义集中在注册规则中,调用点不需要复制条件树。

3.8 自定义 op 的完整注册路径

前述注册规则可以组合成一条完整路径。下面的自定义 relu 同时提供 CPU、CUDA 与 autograd 实现,代码分布在四个 .cpp 文件中:

// ============ myops_schema.cpp ============
// (1) 用 TORCH_LIBRARY 给 myops 命名空间开 DEF,声明 schema 一次
#include <torch/library.h>

TORCH_LIBRARY(myops, m) {
  m.def("custom_relu(Tensor self) -> Tensor");
}

这一文件提供两件事:① 命名空间 myops 被开通(DEF);② 算子 custom_relu 的 schema 进入 dispatcher 表(但还没有任何 kernel)。Python 端此时调 torch.ops.myops.custom_relu(x) 会报 "kernel not found"。

// ============ myops_cpu.cpp ============
// (2) CPU 实现 + 注册到 (myops, CPU)
#include <ATen/ATen.h>
#include <torch/library.h>

at::Tensor custom_relu_cpu(const at::Tensor& self) {
  return at::clamp_min(self, 0);   // 简单起见:借用现成 at::clamp_min 当实现
}

TORCH_LIBRARY_IMPL(myops, CPU, m) {
  m.impl("custom_relu", TORCH_FN(custom_relu_cpu));
}

该文件的作用：在 CPU key(即二维表示 (Dense, CPUBit))下为 myops::custom_relu 注册具体 kernel。TORCH_FN 向 dispatcher 提供 unboxed 签名。实现内部调用的 at::clamp_min 本身也是 dispatched operator，因此会重新进入 dispatcher 并选择 CPU 的 clamp_min 实现。

// ============ myops_cuda.cu ============
// (3) CUDA 实现 + 注册到 (myops, CUDA)
#include <ATen/ATen.h>
#include <torch/library.h>

at::Tensor custom_relu_cuda(const at::Tensor& self) {
  return at::clamp_min(self, 0);   // 同上,clamp_min 自己有 CUDA kernel
}

TORCH_LIBRARY_IMPL(myops, CUDA, m) {
  m.impl("custom_relu", TORCH_FN(custom_relu_cuda));
}

CUDA 文件以相同方式在 CUDA key 下注册 kernel。此时 dispatcher 表中的 myops::custom_relu 已包含 CPU 与 CUDA 两个 backend 条目。

// ============ myops_autograd.cpp ============
// (4) Autograd 实现:接住 forward,建 grad_fn,前向数学透传到 backend
#include <torch/autograd.h>
#include <torch/library.h>

class CustomReluFn : public torch::autograd::Function<CustomReluFn> {
 public:
  static at::Tensor forward(torch::autograd::AutogradContext* ctx,
                            const at::Tensor& self) {
    // 进入 forward 时手动排除 "AutogradXxx + ADInplaceOrView" key: 否则下面
    // dispatcher 调用会再次落回到本 Function,死循环。
    at::AutoDispatchBelowADInplaceOrView guard;
    // guard 生效期内, AutogradCUDA 已从 TLS 位图剔除,
    // dispatcher 根据 self.device() 选择 CUDA 或 CPU 条目。
    static auto op = c10::Dispatcher::singleton()
        .findSchemaOrThrow("myops::custom_relu", "")
        .typed<at::Tensor(const at::Tensor&)>();
    auto result = op.call(self);
    ctx->save_for_backward({result});
    return result;
  }

  static torch::autograd::variable_list backward(
      torch::autograd::AutogradContext* ctx,
      torch::autograd::variable_list grad_outputs) {
    auto saved = ctx->get_saved_variables();
    auto& result = saved[0];
    // d/dx relu(x) = 1 if x > 0 else 0;保存 result 后可用 (result > 0)
    return { grad_outputs[0] * (result > 0).to(grad_outputs[0].dtype()) };
  }
};

at::Tensor custom_relu_autograd(const at::Tensor& self) {
  return CustomReluFn::apply(self);
}

TORCH_LIBRARY_IMPL(myops, Autograd, m) {   // Autograd 是 alias key,展开到所有 AutogradXxx
  m.impl("custom_relu", &custom_relu_autograd);
}

这是关键一文件,几个细节:

  • torch::autograd::Function:PyTorch 提供的 CRTP 模板基类,子类定义 forward 和 backward。apply() 是基类生成的入口,它会自动处理 grad_fn 建立、next_edges 收集、上下文管理。
  • at::AutoDispatchBelowADInplaceOrView guard;:RAII 对象,构造时把所有 autograd functionality 位 + ADInplaceOrView 位 push 进 TLS exclude。整个 forward 函数体内,dispatcher 不会再走 AutogradCUDA 这一层。
  • 用 c10::Dispatcher::singleton().findSchemaOrThrow 主动查 schema,然后 typed<...>().call(...) 跑。这是 PyTorch 推荐的"在 C++ 里调自定义 op"写法: 等价于 Python 端的 torch.ops.myops.custom_relu(self)。
  • 注册到 Autograd alias:不写具体 AutogradCPU/AutogradCUDA,而是用 alias Autograd: 它会被自动展开到所有具体 autograd keys,一行覆盖全部 backend 的 autograd 情况。

四个文件链接到一起,Python 端使用:

>>> import torch, my_extension
>>> x = torch.randn(3, requires_grad=True, device='cuda')
>>> y = torch.ops.myops.custom_relu(x)
    # dispatcher 算位图 → 最高位 = AutogradCUDA → 跳 custom_relu_autograd
    # → CustomReluFn::apply → forward()
    # → AutoDispatchBelowADInplaceOrView guard 生效
    # → op.call(self) (myops::custom_relu) → 最高位现在 = CUDA → 跳 custom_relu_cuda
    # → at::clamp_min(self, 0) → 走 clamp_min 的 CUDA kernel → 返回
>>> y.sum().backward()
    # autograd engine 调 CustomReluFn::backward(...)
    # → 计算梯度 → 传给 next_edges
组合实现：CompositeImplicitAutograd。custom_relu 完全由 at::clamp_min 组成，其梯度也可沿组成算子的 autograd 路径获得，因此可以注册到 CompositeImplicitAutograd alias，并由内部 operator 保留 backend 与 autograd 分派： 
at::Tensor custom_relu_composite(const at::Tensor& self) {
  return at::clamp_min(self, 0);
}

TORCH_LIBRARY_IMPL(myops, CompositeImplicitAutograd, m) {
  m.impl("custom_relu", &custom_relu_composite);
}
只需一个 .cpp 文件,前面三个 IMPL 块都不需要,因为其中的 at::clamp_min 会再次经过 dispatcher,同时获得 backend 路由和 autograd 支持。对于由现有 op 组合而成的算子,这是首选写法。只有直接实现 CUDA kernel、而非组合 at::* 算子时,才需要 3.8 节所示的四文件结构。

4.4 Meta 与 FakeTensor 的抽象执行路径

Meta 是与 CPU、CUDA 同属 Dense backend family 的 runtime key。Meta tensor 保存 shape、stride 和 dtype 等元数据,但没有可读取的数值 storage。FakeTensorMode 在 Python 层拦截 operator,再使用 Meta kernel、decomposition 或少量专用 fake logic 完成抽象执行。下面只讨论 v2.12.0 中这条常见路径,不把它视为所有 compiler pass 的唯一实现。

4.4.1 Meta key 在 dispatcher 表里的位置

一个 operator 同时有 CPU、CUDA 与 Meta entries 很常见。裸 meta tensor 的 key set 包含 Meta backend component,lookup 因而可以选择该 operator 的 Meta entry。

aten::add.Tensor 在 OperatorEntry 里的 kernel 表(节选):

  DispatchKey::CPU             -> generated CPU structured wrapper
  DispatchKey::CUDA            -> generated CUDA structured wrapper
  DispatchKey::Meta            -> generated Meta structured wrapper
  DispatchKey::AutogradCPU     -> generated Autograd wrapper
  DispatchKey::AutogradCUDA    -> generated Autograd wrapper
  ...

许多原生 structured operators 的 Meta wrapper 由 torchgen 生成,其 meta() 逻辑负责输出 metadata。另一些 operator 依靠手写 Meta kernel 或 decomposition。Python custom operator 通常需要用户提供 fake implementation；少数 schema 可以生成 trivial fake behavior。

4.4.2 FakeTensor:Meta key 之上的薄层

编译与导出流程常使用 FakeTensor(torch._subclasses.fake_tensor.FakeTensor),一个由 FakeTensorMode 管理的 __torch_dispatch__ tensor subclass。二者的关系如下:

裸 meta tensorFakeTensor
设备device='meta'保留 原始 device(cuda:0 / cpu / etc.),storage 仍然空
storage空空
dispatcher 行为以 Meta backend key 查找先经 Python __torch_dispatch__ 拦截,再选择 Meta kernel、decomposition 或专用 fake handler
能不能保留 device 上下文不能能(这是 FakeTensor 存在的主要原因)
谁创建torch.empty(..., device='meta')FakeTensorMode 上下文里创建

在常见路径上,FakeTensorMode 以无真实数据的 tensor 执行 operator,由 Meta kernel 或 decomposition 计算输出 metadata,并保留模拟的原始 device。具备 Meta kernel 往往是 FakeTensor compatibility 的重要条件,但 data-dependent shape、aliasing 和专用 fake handlers 仍可能需要额外逻辑。

4.4.3 register_fake 注册 Meta wrapper

register_fake(fn) 把 Python function 保存在 fake implementation holder 中,再构造一个 wrapper 注册到 Meta key:

@scale_add.register_fake
def _(x, scale, bias):
    return torch.empty_like(x)

# 内部关系(概念化):
fake_impl_holder.register(_fn)
lib.impl("myops::scale_add", constructed_meta_wrapper, "Meta")

因此 API 名称与最终 dispatcher slot 描述的是同一机制的两面:用户编写 FakeTensor behavior,实现层把 wrapper 挂到 Meta。v2.12.0 的 registration 与冲突检查见 fake_impl.py。

4.4.4 torch.export 使用 FakeTensor 传播元数据

下面给出 torch.export.export(model, example_inputs) 的简化数据流,只标出与本文相关的 FakeTensor 部分:

torch.export(model, example_inputs)
   │
   ├─ 1. 用 example_inputs 创建对应的 FakeTensor(保留 shape / dtype / device)
   │
   ├─ 2. 进入 FakeTensorMode 上下文
   │
   ├─ 3. Dynamo 用 symbolic_shapes 给可变维度装 SymInt
   │     (e.g. batch 维 -> s0,而不是具体 8)
   │
   ├─ 4. tracing 与 functionalization 以 FakeTensor 传播 operator metadata
   │     ├─ operator 进入 Python __torch_dispatch__ 拦截
   │     ├─ FakeTensorMode 选择 Meta kernel、decomposition 或专用 fake logic
   │     └─ 输出继续以 FakeTensor 携带 size / stride / dtype / device
   │
   └─ 5. 生成带 graph signature、constraints 与 node metadata 的 ExportedProgram

# 序列化是另一个显式步骤:
torch.export.save(exported_program, "model.pt2")

从这条路径能反推几个事实:

  • Fake execution 不调用对应的真实 backend kernel。这条边界只覆盖 tensor operator 的抽象执行；tracing 仍可能运行 Python 控制逻辑、guard 与注册函数,因此不能据此承诺固定加速比或"整个 export 没有任何真实计算"。
  • Meta kernel 是 shape 推断的重要来源。若某个算子的 fake/meta 实现返回错误的 shape、stride 或 dtype，这些元数据可能继续传播到 export 与 Inductor，最终造成错误的 lowering 或运行时维度不匹配。部分算子也可能通过 decomposition 或专用 fake 实现获得元数据，不能把所有推断路径归结为单一 Meta kernel。
  • 动态 shape 路径要求实现能够处理 SymInt。export 可以把 batch 维表示为 s0；此时 fake/meta implementation 接收的是 SymInt。实现中的 concrete branch 需要通过受支持的 guard 表达，不能把符号维度直接当作 Python 布尔值。
  • 普通 custom op 通常需要 fake implementation。v2.12.0 的 custom_op 会安装一个 Meta wrapper；如果没有注册 fake function 且 schema 不能生成 trivial behavior,wrapper 会明确报错。CompositeImplicitAutograd operator 是例外,它应分解到已有 fake/meta support 的组成算子。

torch.export.export 与 torch.export.save 是分开的 API；后者才创建 .pt2 archive。对应入口见 v2.12.0 的 torch/export/__init__.py。

4.4.5 register_fake 的实现约束

  • 可以组合 PyTorch operators,但不能读取 storage 或数据。x.mul(2)、torch.add(x, y) 与 x * 2 都会继续在 FakeTensorMode 中抽象执行。data_ptr()、.item() 或依赖 tensor 值的 Python 分支则越过了 fake implementation 的证据边界。官方 docstring 明确要求 implementation 只由 PyTorch operations 构成且不直接访问输入或中间 tensor 的 storage/data。
  • shape 推断必须能在 SymInt 上跑:
    • 不能用 if x.size(0) == 8: 之类 concrete check
    • shape 运算用 torch.sym_int / x.shape[0] + 1 这种 SymInt 友好的形式
    • 如果某条逻辑 unavoidable 依赖具体数值,用 torch._check(...) 给 Dynamo 加 guard
  • 不要依赖副作用。Tracing 可能多次调用 fake implementation；文件写入、全局 mutation 或输出日志既不属于 operator metadata,也不能成为 graph 语义的一部分。
  • device 必须符合真实 operator contract。多数逐元素 custom operator 会从输入推导输出设备(device=x.device)；除非算子语义明确固定设备,否则硬编码 cuda:0 会让导出图失去设备可移植性。
  • dtype 必须符合真实 type-promotion 规则。可使用 torch.promote_types 或等价的 PyTorch operation 推导；无条件沿用 x.dtype 可能使抽象输出与实际 kernel 不一致。

4.4.6 几个常见错误案例

# 错误案例 1:读取 tensor 数据来决定输出 shape
@my_op.register_fake
def _(x):
    n = int(x[0].item())
    return torch.empty((n,), device=x.device)

# 正确写法:对 metadata 不变的算子,可以直接组合 PyTorch ops
def _(x):
    return x.mul(2)

# 错误案例 2:concrete check 直接求值 SymInt
@my_op.register_fake
def _(x):
    if x.size(0) % 8 == 0:    # SymInt % 8 -> SymBool,if 强制 guard,export warning/error
        ...

# 正确写法:
def _(x):
    torch._check(x.size(0) % 8 == 0)
    return torch.empty_like(x)

# 错误案例 3:device 硬编码
@my_op.register_fake
def _(x):
    return torch.empty(x.shape, device="cuda")  # 永远在 cuda,导出的 graph 没法 cpu 跑

# 正确写法:
def _(x):
    return torch.empty(x.shape, dtype=x.dtype, device=x.device)

# 错误案例 4:输出多个 tensor 时 shape 计算错误
@split.register_fake
def _(x, n):
    return [torch.empty_like(x) for _ in range(n)]   # 每片应该是 x.shape[0] // n

# 正确写法:
def _(x, n):
    chunk = x.size(0) // n
    return [torch.empty((chunk,) + x.shape[1:], dtype=x.dtype, device=x.device)
            for _ in range(n)]

4.4.7 export 链路上 Meta 之外的入口

除了 register_fake,跟 Meta 推断相关的还有几个 hook 点,容易混:

入口挂的位置用途
register_fake / impl("Meta") dispatcher Meta key shape inference,export 必备
op.register_torch_dispatch(...) dispatcher Python key 定制 FakeTensor 行为(很少用)
FakeTensor._dispatch_impls 表 FakeTensor Python 层 少数 op 在 FakeTensor 层有特化(aten::nonzero 之类 data-dependent op)
Inductor lowering(torch._inductor.lowering) Inductor 把 FX node 翻译成 Inductor IR；register_fake 不完整的 operator 也会在此处阻断编译

普通 custom op 若要参与 FakeTensor-based tracing,通常只需提供 register_fake,无需直接修改 FakeTensor 内部表。训练还需要独立的 autograd registration,编译执行也可能需要 decomposition 或 backend lowering；fake implementation 只负责抽象语义。

4.5 Python registration 共享 C++ dispatcher

Python API 管理 registration handle 与 Python callable,底层仍调用 C++ torch::Library 和 c10::Dispatcher。下图只保留稳定的边界,不把内部 binding 名称当成公开 API:

torch.library.Library("myops", "DEF")
   ↓ # torch/library.py
torch._C._dispatch_library("DEF", "myops", ...)
   ↓
torch::Library handle

lib.define("scale_add(Tensor x, float scale, Tensor bias) -> Tensor")
   ↓
torch::Library::def(parsed_schema)
   ↓
c10::Dispatcher::singleton().registerDef(schema, ...)

op.register_kernel("cuda")(fn_py)
   ↓
Library.impl("scale_add", fn_py, "CUDA")
   ↓

   OperatorName{"myops", "scale_add"},

关键点:

  • Dispatch table 中保存的是能回调 Python callable 的 kernel adapter。它与 tensor subclass 使用的 Python dispatch key 或 PythonFallbackKernel 不是同一概念。
  • 调用 Python kernel 需要进入 Python runtime,通常比纯 C++ kernel 有额外开销；是否值得迁移到 C++ 应以目标 workload 的 profile 为依据。v2.12.0 的 Python Library.impl 到 C++ binding 的边界见 torch/library.py。

4.6 Python 自定义 op 的完整注册

§3.8 的 myops::custom_relu 用 C++ 分开注册 schema、backend 与 autograd。Python 端可以在一份文件中表达同样的 operator contract:

import torch

## 1) Schema + 默认 CompositeExplicitAutograd implementation
@torch.library.custom_op("myops::custom_relu", mutates_args=())
def custom_relu(x: torch.Tensor) -> torch.Tensor:
    # 组合算子可在其组成算子支持的 device 上执行
    return x.clamp(min=0)

## 2) 为 CUDA 注册更优的实现(替换默认)
@custom_relu.register_kernel("cuda")
def _(x: torch.Tensor) -> torch.Tensor:
    # 这里可以调 Triton kernel 或者 cuBLAS / cuDNN 包装
    return x.relu()                          # 示意

## 3) register_fake:让 export / AOTI 推 shape
@custom_relu.register_fake
def _(x):
    return torch.empty_like(x)

## 4) register_autograd:给反向(可选,如训练需要)
def _setup_ctx(ctx, inputs, output):
    (x,) = inputs
    ctx.save_for_backward(x)

def _backward(ctx, grad):
    (x,) = ctx.saved_tensors
    return grad * (x > 0).to(grad.dtype),    # tuple,跟 inputs 一一对应

custom_relu.register_autograd(_backward, setup_context=_setup_ctx)

## 用法,跟 C++ 注册版完全一样:
y = torch.ops.myops.custom_relu(torch.randn(3, device="cuda", requires_grad=True))
y.sum().backward()

对比 §3.8 那四个 C++ 文件,Python 版的好处是:

  • 开发周期短:不用 nvcc / setup.py / 编译;改完就跑
  • 跟 export / FakeTensor 对齐:custom_op 提供稳定 schema,register_fake 负责抽象执行时的 shape / dtype / device 推断

代价:

  • Python kernel 需要回到 Python runtime,调用开销与部署约束都不同于纯 C++ kernel
  • 对 torch.compile / torch.export 来说默认是 opaque op:compiler 不会自动偷看 Python 函数体,也不会因为 fake impl 自动生成 Inductor lowering
  • 不能脱离 Python runtime；AOTI 部署时还需要 C++ shim，见 PyTorch AOTI 的 CUDA C++ 部署链路 §9.4。

4.7 torch.library.opcheck:自动验证一致性

完成 custom op 注册后，应执行 opcheck 验证注册契约：

torch.library.opcheck(
    custom_relu,
    args=(torch.randn(3, 4, device="cuda"),),
)

这一个调用会跑一套不变量测试:

  • test_schema:schema 字符串跟实现函数的签名匹配(参数名、类型、可选性)
  • test_autograd_registration:需要训练时,检查是否通过 register_autograd 或 Autograd key 注册 formula
  • test_faketensor:fake impl 产出的 FakeTensor 跟真实 impl 产出的 Tensor 在 shape / dtype / device 上一致
  • test_aot_dispatch_dynamic:比较 eager 与 compile 路径,并覆盖 dynamic shape、functionalization 与可用时的 backward

这四项是 v2.12.0 的默认集合。opcheck 验证 registration 与 tracing invariants,不替代 torch.autograd.gradcheck 的数值梯度检验；还应在支持的 device、dtype 与 requires-grad 组合上分别提供样例。默认项与边界见 torch/library.py。

5. 构建期自动化:torchgen

ATen 算子的 schema、后端注册、C++ API 与 autograd wrapper 如果全部手写，会产生大量重复代码。PyTorch 因此把算子声明和微分公式放进 YAML，再在构建期生成注册与调用所需的 C++ 文件。

6. 端到端追踪:aten::add on CUDA

aten::add.Tensor 在 Dense CUDA 张量上的前向与反向,把 key 选择、schema、注册接口和 codegen 连接成一条完整执行路径。

设定:两个 CUDA 张量 x, y,都 requires_grad=True。输入程序为: 
z = torch.add(x, y)
z.sum().backward()
下面追踪这两行代码经过的主要 C++ wrapper、dispatcher 槽位与 CUDA 实现。

在没有额外 mode、autocast 或 tensor subclass,且命中 Dense CUDA 实现的前提下,调用会从 Python 进入 dispatcher,经过 autograd 与 CUDA 实现,反向时由 autograd engine 执行生成的 backward node。下面九小节按 v2.12.0 的源码与 codegen 模板整理这条逻辑路径;生成文件的分片编号、wrapper 名称和实际命中的 kernel 仍可能随构建选项变化。

6.1 起点:YAML 声明与微分公式

native_functions.yaml 决定 schema 与 structured codegen，derivatives.yaml 提供 autograd 公式。后续示例均以这两处 v2.12.0 声明为依据。

native_functions.yaml 里的 add.Tensor(functional 变体)和 add.out(structured 锚点)条目(简化):

# native_functions.yaml
- func: add.Tensor(Tensor self, Tensor other, *, Scalar alpha=1) -> Tensor
  device_check: NoCheck
  structured_delegate: add.out      # 复用 add.out 的 structured meta/impl 定义
  variants: function, method        # 生成 at::add 和 Tensor::add 两种入口
  ...

- func: add.out(Tensor self, Tensor other, *, Scalar alpha=1, Tensor(a!) out) -> Tensor(a!)
  structured: True                  # structured kernel 的锚点
  structured_inherits: TensorIteratorBase
  ufunc_inner_loop:                 # 触发 ufunc codegen
    Generic: add (AllAndComplex, BFloat16, Half, ComplexHalf)
    ScalarOnly: add (Bool)

derivatives.yaml 中同一 overload 的反向公式如下：

# tools/autograd/derivatives.yaml
- name: add.Tensor(Tensor self, Tensor other, *, Scalar alpha=1) -> Tensor
  self:  handle_r_to_c(self.scalar_type(),  grad)
  other: handle_r_to_c(other.scalar_type(), maybe_multiply(grad, alpha.conj()))

这些声明再加上 aten/src/ATen/native/ufunc/add.h 中的标量运算，构成后续 codegen 的主要输入。设备检查、类型提升与 TensorIterator 行为还来自相应模板和运行时实现，不能只从这几行 YAML 推断。

6.2 Python → C 绑定层

调用入口是 torch.add(x, y)。CPython 解释器查到 torch.add 是一个 C 函数指针,随后进入 THPVariable_add。"THP" 前缀来自 Torch HPython，是 PyTorch Python C 绑定采用的命名约定。它的源码生成在:

build/.../torch/csrc/autograd/generated/python_torch_functions_2.cpp

_2 是分片号；torchgen 会把较大的生成文件拆成多个分片。THPVariable_add 主要完成四个步骤:

  1. 解析 Python 参数。用 PythonArgParser 按 schema(2.1 节那个字符串)解析,识别出第一个张量是 self、第二个是 other、可选 kw alpha 默认 1。
  2. 拆 Python 包装。用户的 x 实际是 Python 端的 THPVariable 对象(torch.Tensor),内部持有一个 at::Tensor(C++ 张量)。THPVariable_unpack 把 C++ 张量取出来。
  3. 调 C++ API。有了纯 C++ 张量,调 at::add(self, other, alpha)。控制权离开 Python,进入纯 C++ 世界。
  4. 把返回值包回 Python。C++ 返回的 at::Tensor 被 THPVariable_Wrap 包成新的 torch.Tensor 返还给 Python。
边栏 5.2:Python/C++ 边界的包装职责 这一层同时处理对象生命周期与 overload resolution：
① Python 引用计数 vs C++ 智能指针。Python 的 torch.Tensor 用 CPython 引用计数(Py_INCREF/Py_DECREF),C++ 的 at::Tensor 用 intrusive_ptr。两套生命周期管理必须在边界精确转换,否则会 use-after-free。
② 解析 Python 多态参数。Python 用户可以传 (Tensor, Tensor) 也可以传 (Tensor, Scalar) 给同一个 torch.add: 选择哪个 overload(add.Tensor vs add.Scalar)是这一层决定的。C++ 函数本身只接受静态类型签名,需要 Python 端先做 overload resolution。

6.3 C++ API 与 Dispatcher::call

进入 C++ 世界,第一个落点是 at::add(生成在 build/aten/src/ATen/Functions.h):

// build/aten/src/ATen/Functions.h
inline at::Tensor add(const at::Tensor& self, const at::Tensor& other, const at::Scalar& alpha) {
  return at::_ops::add_Tensor::call(self, other, alpha);
}

这只是个 inline 转发,把调用甩给 at::_ops::add_Tensor::call(在 Operators.cpp ~第 612 行):

// build/aten/src/ATen/Operators.cpp
at::Tensor _ops::add_Tensor::call(const at::Tensor& self, const at::Tensor& other, const at::Scalar& alpha) {
  static auto op = create_add_Tensor_typed_handle();   // 进程内只算一次的 TypedOperatorHandle
  return op.call(self, other, alpha);                  // 转给 Dispatcher::call
}

这一层做的是"找到 op 的 TypedOperatorHandle"。TypedOperatorHandle 是 dispatcher 内部的"句柄": 它指向 aten::add.Tensor 这个 op 在 dispatcher 表里的那一行。static 保证这个查表只在第一次调用时跑一次,之后都是缓存。

op.call 最终调用 c10::Dispatcher::call（Dispatcher.h:774-828），进入 1.4 节说明的 key-set 计算与 kernel 查找路径。

示例 5.3:C++ API 与 typed handle 缓存 这个转发层承担两项稳定职责：
① 它给了用户友好的 C++ API。第三方 C++ 代码不想知道 dispatcher 内部细节,只想写 at::add(x, y)。
② 它隐藏了 schema lookup 的缓存。at::_ops::add_Tensor::call 在第一次调用时找 schema(create_add_Tensor_typed_handle()),之后缓存。如果每次都 Dispatcher::call 都要先查 schema,性能会差很多。

6.4 DispatchKeySet 的现场计算

进入 Dispatcher::call(Dispatcher.h:774-828),核心两行:

// Dispatcher::call 核心
auto dispatchKeySet =
    op.operatorDef_->op.dispatchKeyExtractor()
        .template getDispatchKeySetUnboxed<Args...>(args...);
const KernelFunction& kernel = op.operatorDef_->op.lookup(dispatchKeySet);
return kernel.template call<Return, Args...>(op, dispatchKeySet, ...);

第一行计算 DispatchKeySet,第二行查表取得最高优先级 kernel,第三行调用该表项。对于本文设定的 CUDA 输入,状态变化如下:

  1. 位图初始值:每个输入张量贡献自己的 TensorImpl::key_set_。普通 Dense CUDA 张量包含 Dense、CUDA backend component 与 autograd functionality，运行时可解析为 {AutogradCUDA, CUDA}。autograd key 不是由本次调用中 requires_grad 的真假临时加入；是否实际建立反向节点由 wrapper 内的 compute_requires_grad 决定。
  2. TLS local include:没开 autocast、没在 functorch 里,所以 include 为空。
  3. TLS local exclude:第一次进 dispatcher,exclude 也是空。
  4. Fallthrough mask:每个 op 的 dispatch table 在注册期预算了 fallthrough_mask。对 add,BackendSelect、Named、Conjugate 等位都被 mask 清掉。位图维持 {AutogradCUDA, CUDA}。
  5. highestPriorityTypeId():从剩余集合中取得最高 functionality 位，即 AutogradFunctionality(对应运行时 AutogradCUDA)；它在 enum 中排在 Dense 之后，因而具有更高位。

lookup 返回 aten::add.Tensor 在 AutogradCUDA 槽位下的 kernel。该 wrapper 由 autograd codegen 生成并注册；生成文件的分片号与局部符号名不是稳定 API：

// build/.../VariableType_2.cpp(分片号会变)
TORCH_LIBRARY_IMPL(aten, AutogradCUDA, m) {
  ...
  m.impl("add.Tensor", TORCH_FN(/* generated autograd wrapper */));
  ...
}

以下用“autograd wrapper”称呼这个生成函数，避免把某一次构建中的局部名称当成跨版本接口。

6.5 AutogradCUDA wrapper:建图与 redispatch

autograd wrapper 由 derivatives.yaml 与 gen_variable_type.py 中的模板共同生成。下面是保留控制流的伪代码，具体局部变量名会随 codegen 变化：

at::Tensor generated_autograd_add_Tensor(
    c10::DispatchKeySet ks,
    const at::Tensor& self, const at::Tensor& other, const at::Scalar& alpha) {

  // === 步骤 1)若任何输入 requires_grad,准备一个新的 grad_fn 反向节点 ===
  std::shared_ptr<AddBackward0> grad_fn;
  if (compute_requires_grad(self, other)) {
    grad_fn = std::shared_ptr<AddBackward0>(new AddBackward0(), deleteNode);
    grad_fn->set_next_edges(collect_next_edges(self, other));   // 反向边
    grad_fn->alpha = alpha;                                      // 存反向公式要用的
    grad_fn->other_scalar_type = other.scalar_type();
    grad_fn->self_scalar_type  = self.scalar_type();
  }

  // === 步骤 2)把"AutogradCUDA + ADInplaceOrView"从位图剔掉,redispatch ===
  auto _tmp = ([&]() {
    at::AutoDispatchBelowADInplaceOrView guard;     // RAII:进 guard = TLS exclude 加 autograd + ADInplaceOrView
    return at::redispatch::add(
        ks & c10::after_autograd_keyset,             // 显式 mask 当前层及以上
        self, other, alpha);
  })();
  auto result = std::move(_tmp);

  // === 步骤 3)把新算出的 result 挂到 grad_fn,加进 autograd 历史 ===
  if (grad_fn) {
    set_history(flatten_tensor_args(result), grad_fn);   // result.grad_fn = grad_fn
  }
  return result;
}

逐行解读:

  1. compute_requires_grad(self, other):结合 grad mode 与输入属性判断是否需要记录反向。本文的两个输入都需要梯度,结果为 true。
  2. 建 AddBackward0 节点:这是 codegen 生成的 Node 子类(5.8 节看它的 apply())。set_next_edges 把 self.grad_fn 和 other.grad_fn 设为 AddBackward0 的下游边: 反向时梯度按这两条边传出去。alpha、self_scalar_type、other_scalar_type 是反向公式里要用的"上下文",保存到节点里。
  3. at::AutoDispatchBelowADInplaceOrView guard;:RAII 对象,构造时修改 TLS: 把所有 autograd functionality 位 + ADInplaceOrView 位 push 进 exclude 集合。从这一行到 guard 析构,所有 dispatcher 调用都不会再走 autograd 层。
  4. at::redispatch::add(ks & c10::after_autograd_keyset, ...):at::redispatch::add 是另一份 codegen 生成的入口(在 RedispatchFunctions.h),它与 at::add 的差异是额外接收一个 DispatchKeySet，并将其传给 Dispatcher::redispatch。after_autograd_keyset 是预先编译的常量掩码，用于移除所有 autograd 及以上的位，使后续查找从 backend 层继续。
  5. set_history(result, grad_fn):把新节点接到输出的 autograd history。Python 侧随后可通过 result.grad_fn 观察到 AddBackward0。
对这个生成 wrapper 而言，职责是准备反向节点、redispatch 到较低优先级实现，再把结果接入 autograd history；add 的数值计算位于后端实现。不同 backend 会注册到各自的 autograd key，不能据此推断所有算子都共享同一个 wrapper 符号。

6.6 CUDA 后端 wrapper

at::redispatch::add 把控制权交给 Dispatcher::redispatch。这次位图里 AutogradCUDA 已经清掉(被 guard 和 after_autograd_keyset 双重保险),highestPriorityTypeId() 返回 CUDA。

CUDA 槽位的 kernel 注册在生成的 RegisterCUDA.cpp 中。add.Tensor、add_.Tensor 与 add.out 都有自己的 wrapper：

TORCH_LIBRARY_IMPL(aten, CUDA, m) {
  m.impl("add.Tensor", TORCH_FN(wrapper_CUDA_add_Tensor));
  m.impl("add_.Tensor", TORCH_FN(wrapper_CUDA_add__Tensor));
  m.impl("add.out",    TORCH_FN(wrapper_CUDA_add_out_out));
}

structured_delegate: add.out 让三种变体复用同一组 structured meta/impl 定义，但 codegen 不会让 functional wrapper 再调用 out wrapper。register_dispatch_key.py 会为每种变体展开相应模板。functional 变体的控制流可概括为：

at::Tensor wrapper_CUDA_add_Tensor(
    const at::Tensor& self, const at::Tensor& other, const at::Scalar& alpha) {
  structured_add_out_functional op;
  op.meta(self, other, alpha);
  op.impl(self, other, alpha, op.outputs_[0]);
  return std::move(op.outputs_[0]);
}

其中 meta() 建立 TensorIterator、推导输出属性并准备 functional 输出，impl() 执行数值计算。out wrapper 则以调用者提供的张量构造 wrapper，并通过 maybe_get_output(0) 取得输出。上面是根据 v2.12.0 模板整理的伪代码；生成类名和成员名可能随 codegen 调整。

三种 wrapper 的差别 functional wrapper 管理新输出，in-place wrapper 以 self 作为 structured 输出，out wrapper 使用调用者传入的 out。它们各自调用 meta() 与 impl()，共享的是 structured 实现，而不是一条 wrapper 到另一条 wrapper 的函数调用。 
at::Tensor& wrapper_CUDA_add__Tensor(
    at::Tensor& self, const at::Tensor& other, const at::Scalar& alpha) {
  structured_add_out_inplace op(self);
  op.meta(self, other, alpha);
  op.impl(self, other, alpha, op.maybe_get_output(0));
  return self;
}

6.7 Structured kernel 与 ufunc

三种 wrapper 最终都会进入同一份 generated structured impl()。以 out 变体为例：

at::Tensor& wrapper_CUDA_add_out_out(
    const at::Tensor& self, const at::Tensor& other, const at::Scalar& alpha,
    at::Tensor& out) {
  structured_add_out_out op(out);            // 实例化 structured kernel 类
  op.meta(self, other, alpha);               // 阶段 1: meta: 算输出 shape/dtype,设 TensorIterator
  op.impl(self, other, alpha, op.maybe_get_output(0));   // 阶段 2: impl: 真的算
  return out;
}

structured kernel 把"算法"拆成两个标准化阶段:

  1. meta():广播 shape、确定 dtype、初始化 TensorIterator。调用方提供输出 tensor(可能是空的或已分配的),meta 根据输入决定输出该是什么形状,必要时 resize。
  2. impl():数值计算。读 TensorIterator 拿到逐元素迭代器,跑实际的算法。

CUDA ufunc codegen 位于 torchgen/dest/ufunc.py。它生成按 dtype 分派的 kernel、dispatch stub 注册，以及 structured impl() 对 kernel 的直接调用。控制流可概括为：

// build/.../UfuncCUDA_add.cu (简化)
void add_kernel(TensorIteratorBase& iter, const Scalar& alpha) {
  AT_DISPATCH_SWITCH(iter.common_dtype(), "add_cuda",
    AT_DISPATCH_CASE(..., [&] {
      gpu_kernel(iter, CUDAFunctor_add<scalar_t>(/* alpha */));
    })
  );
}

REGISTER_DISPATCH(add_stub, &add_kernel)

TORCH_IMPL_FUNC(add_out)(const Tensor& self, const Tensor& other,
                         const Scalar& alpha, const Tensor& result) {
  add_kernel(*this, alpha);
}

这里有两层 dispatch:

  1. Dispatcher 的 key 选择先确定 CUDA backend wrapper。device、layout、mode 与 autograd 等维度在这一层处理。
  2. AT_DISPATCH_SWITCH再按 iter.common_dtype() 选择模板实例。dtype 不是 DispatchKey，因此这一步发生在 backend 实现内部。

gpu_kernel 接收 TensorIterator 与生成的 functor，最终启动逐元素 CUDA kernel。functor 的 operator() 调用 at::native::ufunc::add；codegen 还会针对 CPU scalar operand 生成专门分支。标量数学定义位于 ATen/native/ufunc/add.h：

// aten/src/ATen/native/ufunc/add.h
template <typename T>
C10_HOST_DEVICE C10_ALWAYS_INLINE T add(T self, T other, T alpha) {
  return self + alpha * other;
}
数值定义最终收敛到 self + alpha * other，其余层分别处理 schema、key 选择、autograd、输出准备、dtype specialization 与 kernel launch。这里描述的是 add 的 v2.12.0 生成路径，不代表所有 ATen 算子都采用 ufunc codegen。
示例 5.7:CPU 与 CUDA 共用 ufunc::add ufunc/add.h 使用 C10_HOST_DEVICE 注解,即 PyTorch 对 CUDA __host__ __device__ 的封装,使该函数可同时生成 host 与 device 代码。

CPU 端的 UfuncCPU_add.cpp 同样包含 ufunc/add.h,并以 SIMD 矢量化的 vectorized_loop2d 驱动该函数；CUDA 端则使用 gpu_kernel。两条执行路径共享标量数学定义,各自提供遍历与发射机制。

前向计算完成后，控制权从 CUDA kernel 返回 generated impl()，再回到 functional wrapper、Dispatcher::redispatch 与 autograd wrapper。随后：

  1. guard 析构,TLS exclude 还原(后续顶层调用又干净了)。
  2. set_history(result, grad_fn) 把反向节点挂到结果。
  3. 返回到顶层 Dispatcher::call,再返回到 at::_ops::add_Tensor::call,再返回到 at::add,再返回到 THPVariable_add,再包装成 Python torch.Tensor 返回给用户。

前向结束。z 拿到手,它的 .grad_fn 是 AddBackward0。

6.8 反向:AddBackward0::apply

用户接着调 z.sum().backward()。backward() 触发 autograd engine(torch/csrc/autograd/engine.cpp):

  1. 从 loss 的 root edge 出发，GraphTask 统计各节点尚未满足的依赖。
  2. 依赖计数归零的节点进入 ready queue；worker 取出任务并执行 Node::apply(grads)。
  3. apply 返回的梯度沿 next_edges 送往上游，同一输入槽位收到的多路梯度在节点执行前合并。

对于该 AddBackward0::apply,codegen 在 build/.../generated/Functions.cpp 中生成近似下列代码:

variable_list AddBackward0::apply(variable_list&& grads) {
  auto& grad = grads[0];                                          // 上游传下来的 dz
  variable_list grad_inputs(2);                                    // 两个输入,两个梯度

  if (should_compute_output(0)) {                                  // self 需要梯度?
    grad_inputs[0] = handle_r_to_c(self_scalar_type, grad);
    // 翻译自 derivatives.yaml:  self: handle_r_to_c(self.scalar_type(), grad)
  }

  if (should_compute_output(1)) {                                  // other 需要梯度?
    grad_inputs[1] = handle_r_to_c(other_scalar_type,
                                   maybe_multiply(grad, alpha.conj()));
    // 翻译自 derivatives.yaml:  other: handle_r_to_c(other.scalar_type(),
    //                                     maybe_multiply(grad, alpha.conj()))
  }

  return grad_inputs;
}

对照 5.1 节抄的反向公式:

self:  handle_r_to_c(self.scalar_type(),  grad)
other: handle_r_to_c(other.scalar_type(), maybe_multiply(grad, alpha.conj()))

生成代码保留了 YAML 公式的运算结构，同时加入输出需求检查、保存变量读取与类型处理等模板逻辑。它不是对 YAML 文本的逐字复制。

该实现还包含以下边界条件：

  • should_compute_output(i):根据对应 edge 是否需要梯度决定是否计算该输入槽位，不只适用于叶子张量。
  • maybe_multiply(grad, alpha.conj()):alpha == 1 时可直接返回 grad，避免一次不必要的乘法。
  • handle_r_to_c:处理"实数 tensor → 复数 grad"的边界情况(数值实部投影),实数运算下基本是 no-op。
  • 没有 at::redispatch:反向公式里的子运算(像 maybe_multiply 内部的 at::mul)直接走顶层 at::* API: 它们自己会走完整 dispatcher,获得"在 CUDA 上跑、记到反向图"的能力。这意味着反向自动支持高阶导:对 AddBackward0::apply 求二阶导,内部的 at::mul 又会建一个 MulBackward0。

返回 grad_inputs 后，engine 沿 next_edges 继续调度。非叶子输入指向其创建算子的 backward node；需要梯度的叶子输入没有 grad_fn，但下游 edge 指向内部的 AccumulateGrad 节点，由它更新叶子的 .grad。

PyTorch Dispatcher: Multidimensional Dispatch and Operator Execution

Python exposes a single torch.add, yet one invocation may be affected by device, layout, autograd, tensor subclasses, and thread-local modes at the same time. The dispatcher sits between the Python/C++ APIs and concrete kernels, mapping one operator schema onto these composable behavior layers.

PyTorch fixes the operator contract in a schema, associates implementations with dispatch keys in a registry, and uses an ordered DispatchKeySet plus redispatch to connect wrappers with a backend kernel. Call sites name the operator; the dispatcher resolves the device and mode combination at runtime. The article first establishes that runtime model, then traces aten::add.Tensor through CUDA forward and backward execution to connect schemas, registration, torchgen, and numerical implementation.

Implementation details were checked against the public PyTorch v2.12.0 source. File names, generated symbols, and internal APIs change across releases. The Chapter 6 call chain is a source-reading model for the stated inputs, not a stable cross-version API or a path covering every tensor layout, mode, and build configuration.

1. Dispatch keys: foundation of runtime multi-dimensional dispatch

The runtime model has three steps: construct a key set from tensor arguments and thread-local state, select the highest-priority runtime key, and call the kernel registered for that operator and key. A wrapper kernel narrows the key set and redispatches until execution reaches the backend kernel that performs numerical work.

1.1 Engineering constraints of multidimensional dispatch

An ordinary y = x + 1 already contains a runtime device choice. For a dense CPU float32 tensor with no gradient history, the numerical work reduces to y[i] = x[i] + 1. A system supporting only CPU and CUDA could express that single dimension with one branch:

// Toy implementation used only to illustrate the device dimension
Tensor add(const Tensor& x, Scalar s) {
  if (x.is_cuda()) return add_cuda(x, s);
  return add_cpu(x, s);
}

Device is only one dispatch dimension. The same expression may also carry layout, autograd, autocast, function-transform, and Python-mode semantics:

  • Ordinary autograd-capable tensors carry an autograd key independently of the current requires_grad value. Once selected, the autograd wrapper checks grad mode and the inputs before deciding whether to create AddBackward0; VariableFallbackKernel.cpp documents the fallback semantics of this layer in v2.12.0.
  • Autocast policy is registered per operator. In v2.12.0, CUDA mm appears in the lower-precision list, while add uses fallthrough and retains normal type-promotion behavior. The corresponding policy list is defined in autocast_mode.h.
  • FakeTensorMode normally intercepts operators through Python __torch_dispatch__, then uses Meta kernels, decompositions, or dedicated fake logic to propagate metadata without reading real tensor data.
  • A sparse layout requires a separate backend implementation; the same addition enters a sparse algorithm rather than a dense elementwise loop.
  • Function transforms such as torch.func.vmap add their own wrapper layer and batch-dimension semantics.

These conditions can stack, but an active TLS key does not imply that every operator has a dedicated kernel for it. The dispatcher combines tensor key sets with TLS include state, applies exclusions and the fallthrough mask, then selects the highest-priority executable entry. Each wrapper handles one concern and redispatches with a reduced key set.

Encoding those rules inside every operator would produce a conditional tree like this toy implementation:

// Illustrates composition complexity; this is not PyTorch's implementation
Tensor run_op(const Tensor& x, const Tensor& y) {
  if (python_mode_active()) return redispatch_from_python(x, y);
  if (autocast_active() && op_has_autocast_policy()) {
    return redispatch_with_cast_inputs(x, y);
  }
  if (autograd_key_active()) return redispatch_from_autograd(x, y);
  if (x.is_sparse() || y.is_sparse()) return sparse_kernel(x, y);
  if (x.is_cuda() || y.is_cuda()) return cuda_kernel(x, y);
  return cpu_kernel(x, y);
}

The conditional-tree design has two engineering costs:

  1. Repeated cross-cutting logic. Autocast, aliasing, and function-transform rules would be copied across a large operator set, making consistent semantics difficult to maintain.
  2. Closed extension points. Adding a backend or mode would require edits to existing condition trees instead of registrations for the operators it supports.
Example 1.1 A new backend Foo registers kernels for the operators it supports. Operators without a Foo implementation follow an explicit fallback or error path, so extension coverage is represented by registrations rather than branches spread across operator bodies.

1.2 A key-indexed function table

PyTorch moves runtime path selection out of operator implementations and into a lookup table indexed by dispatch key.

Each operator owns a kernel table indexed by DispatchKey. A key may represent a numerical backend or a wrapper layer such as Autograd and Autocast. The computed table also incorporates backend fallbacks and alias-key expansion, so it contains more than the registrations written explicitly in source.

For aten::add, a simplified subset of the table looks like this:

DispatchKey          →  function pointer (kernel)
─────────────────────────────────────────────────
CPU                  →  add_cpu
CUDA                 →  add_cuda
SparseCPU            →  add_sparse_cpu
SparseCUDA           →  add_sparse_cuda
MPS                  →  add_mps                  // Apple Metal
AutogradCPU          →  VariableType::add_cpu_wrapper
AutogradCUDA         →  VariableType::add_cuda_wrapper
AutocastCUDA         →  fallthrough
...

A call to torch.add(x, y) proceeds in three steps:

  1. Compute the active keys. Merge tensor key sets with TLS include state, then apply TLS exclusions and the operator's fallthrough mask.
  2. Pick the highest-priority executable entry. A CUDA add under autocast does not stop at AutocastCUDA because that operator is fallthrough there.
  3. Call or redispatch. A wrapper that handles its layer passes a reduced key set to redispatch; the backend implementation performs the numerical work.

Redispatch transfers control between wrapper layers. After handling its own semantics, the current layer enters the dispatcher with a narrowed key set that skips itself. The example below uses torch.mm(x, y), which has a CUDA lower-precision autocast policy. With autocast enabled and gradient participation, its path can include AutocastCUDA, AutogradCUDA, and CUDA; the autograd wrapper still decides separately whether to create MmBackward0.

The figure traces the main path for with torch.autocast('cuda'): z = torch.mm(x, y), with CUDA inputs that participate in autograd:

Each kernel only manages its own layer. The CUDA kernel doesn't need to know autocast exists; autocast doesn't need to know autograd exists. • Registration-based extension. Backends add entries for supported operators without changing call sites. • Composable. The set of bits in the bitmap determines which layers are traversed; their order is determined by priority, fully decoupled from code. • Order guaranteed by design. "autocast must come before autograd" is encoded as the priority of the keys, no longer relying on every op author remembering it. This "layer-by-layer descent, each layer masking itself" pattern has a proper name: redispatch. §1.7 will unpack its implementation.
Aside 1.2: virtual functions, callable storage, and operator dispatch A virtual table selects a method from the dynamic type of one receiver. Dispatcher candidates instead come from the union of all tensor arguments and thread-local state. std::function stores a type-erased callable, but it does not provide operator schemas, key priority, fallback rules, or redispatch. PyTorch therefore needs an operator-level registry with composable runtime selection rather than a particular C++ callable container.

1.3 The actual DispatchKey enum

c10/core/DispatchKey.h defines every dispatch key. The simplified enumeration below shows the functional layers; §1.4 then introduces the actual two-dimensional split between functionality and backend.

// Simplified: real definition in §1.4
enum class DispatchKey : uint16_t {
  Undefined = 0,

  // === Backend layer (actually compute values) ===
  CPU,
  CUDA,
  MPS,            // Apple Metal Performance Shaders
  XLA,            // Google TPU / XLA backend
  Meta,           // Only compute shapes, no values
  ...
  SparseCPU,
  SparseCUDA,
  ...

  // === Autograd layer (above backend, builds backward graph) ===
  AutogradCPU,
  AutogradCUDA,
  AutogradXLA,
  ...

  // === Mode layer (above autograd, intercepts every op call) ===
  ADInplaceOrView,   // in-place / view autograd metadata
  Tracer,            // Old JIT trace recording
  AutocastCPU,
  AutocastCUDA,
  Fake,              // legacy torchdistx key, not FakeTensorMode's entry
  Functionalize,     // Eliminate alias/mutation
  Python,            // TorchDispatchMode (subclass interception)
  ...                // additional functionality entries

  NumDispatchKeys
};

The simplified enumeration exposes three runtime properties:

  • The type is uint16_t (16-bit unsigned). Soon we'll pack keys into a 64-bit bitmap, and a 16-bit index is enough to encode every possible key plus header bits.
  • The enum is ordered. The highest-priority key corresponds to the highest set functionality bit, so later functionality entries carry higher priority. The ordering of Autocast*, Autograd*, and backend keys encodes their wrapper order in the key representation.
  • Many keys are not tensor properties. Autocast and several function transforms are activated through TLS; Python tensor subclasses use the Python key to reach __torch_dispatch__. The Fake entry above is a legacy torchdistx key, not the implementation entry for current FakeTensorMode.
Example 1.3 An ordinary CPU tensor remains autograd-capable even when requires_grad=False, so its runtime path can still select AutogradCPU before CPU. The wrapper then observes that no history is required and redispatches without creating AddBackward0. Changing requires_grad affects graph construction inside the wrapper, not whether the autograd layer exists in the tensor key set.

1.4 Two-dimensional split: functionality × backend

Expanding every behavior/backend pair directly would make the enum grow as the product of both dimensions. Adding Habana (HPU), for example, would require entries such as:

HPU              // dense × Habana
SparseHPU        // sparse × Habana
SparseCsrHPU
QuantizedHPU
NestedTensorHPU
AutogradHPU      // autograd × Habana

This encoding adds about six enum values for each backend and requires matching changes in enum definitions and code generation. A new per-backend functionality expands the set again. PyTorch therefore encodes the two dimensions separately.

A 2022 refactor split the enum into two orthogonal sets that combine in one 64-bit bitmap (DispatchKey.h):

  1. BackendComponent identifies the numerical or metadata backend. The current bits are CPU / CUDA / HIP / XLA / MPS / IPU / XPU / HPU / VE / Lazy / MTIA / MAIA / PrivateUse1‑3 / Meta. A static_assert caps the backend count at 16, reflecting the explicit bit budget in DispatchKey.h. A backend component forms a runtime dispatch key when combined with a functionality.
  2. DispatchKey (functionality). The vast majority of functionalities occupy a single slot (a globally unique handler); six are "per-backend" and need to combine with a BackendComponent to form a runtime key. The six are: Dense, Quantized, Sparse, SparseCsr, NestedTensor, AutogradFunctionality.

The combination rule (toRuntimePerBackendFunctionalityKey()):

(Dense,                CUDABit)  →  CUDA           // runtime key for dense CUDA tensors
(Dense,                CPUBit)   →  CPU
(AutogradFunctionality, CUDABit) →  AutogradCUDA
(AutogradFunctionality, CPUBit)  →  AutogradCPU
(Sparse,               CUDABit)  →  SparseCUDA
(Quantized,            CPUBit)   →  QuantizedCPU
...

TORCH_LIBRARY_IMPL(aten, CUDA, m) registers at the two-dimensional coordinate (Dense, CUDA). The API exposes one CUDA key, while the bitmap encodes both the Dense functionality and CUDA backend bits. Adding an HPU bit to BackendComponent allows all six per-backend functionalities to combine with it without adding separate enum values.

Example 1.4 A sparse implementation for the Habana (HPU) backend uses the combined (Sparse, HPU) key and can register its kernel with TORCH_LIBRARY_IMPL(aten, SparseHPU, m). Both SparseHPU and AutogradHPU are combined runtime keys rather than independent enum entries.
Aside 1.4: drift warning ezyang's 2019 PyTorch internals does not have the BackendComponent layer, and neither does the 2020 dispatcher article. The two-dimensional split described in this section is the post-2022 mechanism; when reading older articles, note that this has shifted: they treat SparseCUDA as a concrete enum value, whereas in today's code it is the combination (Sparse, CUDABit).

1.5 DispatchKeySet: a 64-bit bitmap

DispatchKeySet encodes functionalities and up to 16 BackendComponent values in a uint64_t. Each operator call uses this 64-bit value as its candidate-key set before lookup selects the highest-priority entry.

The bitmap layout (per the class comments in DispatchKeySet.h):

This 64-bit integer is formed by the union of three sources:

  1. The union of all input tensors' TensorImpl::key_set_. Each tensor caches a DispatchKeySet describing device, layout, and the functionality layers it can enter. The autograd key does not encode the current requires_grad value. The dispatcher unions the key sets of all tensor arguments to implement multiple dispatch.
  2. TLS local include (thread-local "add"): pushed by mode guards. For example, entering with torch.autocast('cuda'):, the with block's implementation pushes the AutocastCUDA bit into TLS; on every op call the dispatcher or's the TLS include into the bitmap.
  3. TLS local exclude (thread-local "remove"): used for redispatch. Inside an autograd kernel, at::AutoDispatchBelowAutograd guard; stuffs every autograd bit into TLS exclude via an RAII object. The dispatcher subtracts exclude from the bitmap, so the highest bit "naturally" falls to the next layer.

A fourth factor is the fallthrough mask. Each operator caches the keys whose computed dispatch-table entries are explicitly fallthrough, and those bits are cleared before lookup. A missing kernel is not the same as fallthrough: lookup may continue to a backend fallback or end in an error. Only a fallthrough registration places the key in this mask.

Concretely, the core line lives in DispatchKeyExtractor.h:23-44:

// aten/src/ATen/core/dispatch/DispatchKeyExtractor.h
inline DispatchKeySet computeDispatchKeySet(
    DispatchKeySet ks,              // or'd key_set of input tensors
    DispatchKeySet key_mask) {      // the op's fallthrough mask
  c10::impl::LocalDispatchKeySet local = c10::impl::tls_local_dispatch_key_set();
  return (((ks | local.included_) - local.excluded_) & key_mask);
  //        ↑ add include  ↑ subtract exclude  ↑ apply fallthrough mask
}

These three bit operations produce the final bitmap described in §1.5. lookup() then finds its highest-priority bit, as detailed in §1.6.

Example 1.5 Let x and y be CUDA fp32 tensors, and run z = torch.mm(x, y) inside with torch.autocast('cuda'):.

1. The input union contains {CUDABit, Dense, AutogradFunctionality}; the presence of AutogradFunctionality is not controlled by the current requires_grad value.
2. The autocast context pushed AutocastCUDA into TLS include.
3. In v2.12.0, mm has a CUDA lower-precision autocast policy, so its AutocastCUDA entry is not removed by the fallthrough mask.
4. The final bitmap, after combining functionality + backend, is equivalent to the runtime key set {AutocastCUDA, AutogradCUDA, CUDA}.

Compare with the "peeling the onion" diagram in §1.2: this is exactly that diagram's initial bitmap.

1.6 The priority ladder

Given a 64-bit bitmap, the dispatcher uses highestPriorityTypeId() to take "the functionality corresponding to the highest 1 bit." "Highest" means the highest-numbered set bit: functionality bits are arranged by priority, with bit number = priority.

The figure below draws common functionalities by priority, from top (highest) to bottom (lowest):

Find a key: take the highest set bit; redispatch uses the reduced key set supplied by its caller. • Autograd is above backend: the wrapper decides whether to record history, then redispatches. • Autocast is above autograd: operators with an explicit policy transform inputs before the autograd wrapper sees the call. • Fallthrough: only explicit fallthrough entries enter the precomputed mask; a missing kernel is different.

Catch-all and alias keys are different concepts. DispatchKey::CatchAll aliases Undefined and denotes a registration without an explicit dispatch key; in v2.12.0, OperatorEntry stores such registrations through CompositeImplicitAutograd. Alias keys instead describe coverage over sets of runtime keys when the computed dispatch table is populated.

  • Autograd covers backend-specific autograd keys, allowing one registration to provide an implementation for those entries.
  • CompositeImplicitAutograd is intended for implementations composed from other dispatched operators. Its final coverage still follows precedence rules among direct and alias registrations.
  • CompositeExplicitAutograd denotes a backend-independent implementation whose autograd behavior must be supplied separately.

Alias registrations participate in computed-table filling and precedence. A concrete lookup still resolves entries such as AutogradCUDA or CUDA. The v2.12.0 rules are implemented in OperatorEntry.cpp.

1.7 redispatch: cycle-free inter-layer recursion

After a wrapper finishes its work, control must move to the next lower-priority key without selecting the same wrapper again. Redispatch performs that transition with a key set supplied by the caller.

After the autograd kernel builds grad_fn and records next_edges, execution still has to reach the backend kernel. Re-entering the top-level at::add(x, y) path may select AutogradCUDA again and recurse.

Dispatcher::redispatch accepts the already-adjusted key set (Dispatcher.h:833-848):

// Key comment (from source): "redispatch treats the inputted DispatchKeySet as is,
//  and does NOT mask out the highest priority bit"
//: the caller is responsible for masking out the "current key" from the bitmap before passing it in
template <class Return, class... Args>
inline Return Dispatcher::redispatch(
    const TypedOperatorHandle<Return(Args...)>& op,
    DispatchKeySet currentDispatchKeySet,    // ← caller has already masked the current key
    Args... args) const {
  const KernelFunction& kernel = op.operatorDef_->op.lookup(currentDispatchKeySet);
  return kernel.template call<Return, Args...>(op, currentDispatchKeySet, ...);
}

Compared to Dispatcher::call (the top-level entry): call recomputes the bitmap (or-ing input tensors' key_set + TLS processing); redispatch uses the bitmap passed in directly. This is deliberate: it gives the kernel the flexibility to say "I've decided where to jump next."

An autograd kernel masks its current layer by updating the TLS exclude set through an RAII guard:

  • at::AutoDispatchBelowAutograd (older name AutoNonVariableTypeMode, often seen in old blog posts): on construction it pushes every autograd functionality bit into TLS excluded_; on destruction it restores them. During its lifetime, every op call has its bitmap automatically stripped of the autograd bits.
  • at::AutoDispatchBelowADInplaceOrView: additionally pushes ADInplaceOrView into exclude. This is the standard usage of the codegen-emitted VariableType wrapper: the autograd kernel uses it, then redispatch drops directly to the backend.

Stitching these mechanisms together, the skeleton of a real autograd kernel looks like this (simplified from the codegen output in VariableType_*.cpp):

// AutogradCUDA kernel for aten::add.Tensor (simplified)
Tensor VariableType::add_Tensor(
    c10::DispatchKeySet ks,
    const Tensor& self, const Tensor& other, const Scalar& alpha) {

  // ① Build backward node (only if grad is needed)
  std::shared_ptr<AddBackward0> grad_fn;
  if (compute_requires_grad(self, other)) {
    grad_fn = std::make_shared<AddBackward0>();
    grad_fn->set_next_edges(collect_next_edges(self, other));
  }

  // ② Enter "below autograd" scope → autograd bits removed from the bitmap
  auto result = [&]() {
    at::AutoDispatchBelowADInplaceOrView guard;
    return at::redispatch::add(
        ks & c10::after_autograd_keyset,    // explicitly mask the current key
        self, other, alpha);
  }();

  // ③ Attach grad_fn to the output
  if (grad_fn) set_history(result, grad_fn);
  return result;
}
Example 1.7: full redispatch flow Walk through this code for z = x + y (with x, y on CUDA, requires_grad=True):

(a) Top-level Dispatcher::call computes the bitmap = {AutogradCUDA, CUDA}, highest bit = AutogradCUDA, jumps to VariableType::add_Tensor.
(b) The function body enters the RAII guard AutoDispatchBelowADInplaceOrView: TLS exclude now contains all autograd bits + the ADInplaceOrView bit.
(c) Call at::redispatch::add(ks & after_autograd_keyset, ...). after_autograd_keyset is a precomputed mask that "clears all autograd bits and above," explicitly ensuring AutogradCUDA won't be picked again.
(d) Dispatcher::redispatch looks up directly with this bitmap; the highest bit is now CUDA, jumping to wrapper_CUDA_add_Tensor.
(e) The CUDA wrapper finishes and returns.
(f) Back in the autograd kernel, set_history(result, grad_fn) attaches the backward node and returns.

The guard destructs between (e) and (f), and TLS exclude is restored. The bitmap computation for the next top-level call starts clean again.
One operator invocation may select several dispatcher entries. Functionality bit order determines the layers; each wrapper uses an RAII guard and an explicit mask to remove itself before redispatch selects the next highest-priority key.

2. Schema: the operator type signature

Runtime key selection requires a stable operator identity and argument contract. A schema records the arguments, return values, overload, aliasing, and mutation semantics of aten::add.Tensor, allowing the dispatcher and its surrounding tools to interpret the same call.

The schema is the operator's interface contract. It carries argument and return types, overload identity, aliasing, and mutation metadata consumed by the dispatcher, autograd, JIT, functionalization, and Python bindings. The dispatcher uses tensor arguments when computing the key set; autograd and functionalization use alias annotations to reason about views and mutation; Python bindings generate argument parsing from the same contract. A mistaken annotation such as Tensor(a) in place of Tensor(a!) can therefore change graph semantics rather than merely alter documentation.

This section covers the schema's string grammar, variant naming rules, and concrete representation in YAML.

2.1 Schema field semantics

Take a real schema string:

aten::add.Tensor(Tensor self, Tensor other, *, Scalar alpha=1) -> Tensor

The syntax resembles a Python function signature, while each component carries an independent schema meaning. Reading from left to right gives the following fields:

#PieceSemantics
1atenNamespace. PyTorch's built-in ops live under aten; custom ops (extensions) live in their own namespace, e.g. myops::foo. The namespace isolates "which ops are findable" and determines which TORCH_LIBRARY* macro to register with (see chapter 3).
2::Namespace separator, following C++ notation.
3addThe op name. Multiple overloads can share the same name (like C++ function overloading).
4.TensorThe overload name. This is critical: add has both add.Tensor (adding two tensors) and add.Scalar (adding a tensor and a scalar). Omittable, equivalent to overload name "" (empty string). The dispatcher uses the full string "aten::add.Tensor" as the key into the function table.
5(...)Argument list.
6Tensor selfFirst positional argument, of type Tensor, named self. Convention: like Python method's self, autograd treats it as the "main" input.
7Tensor otherSecond positional argument, type Tensor.
8*Keyword separator. From here, subsequent arguments must be passed by keyword (add(x, y, alpha=2)), not positionally. Exactly the same as Python's * in function definitions.
9Scalar alpha=1Keyword argument, type Scalar, default value 1. When Python writes torch.add(x, y, alpha=3), this value lands here.
10-> TensorReturn type. Multiple return values use tuple syntax, e.g. -> (Tensor, Tensor).

The type syntax covers a range of primitives and composites:

Tensor[]Tensor list (std::vector<Tensor>)
Tensor(a)Alias annotation: this argument shares storage with a "memory slot" named a, but does not write it (read-only view)

Alias annotations ((a) and (a!)) carry storage-sharing and mutation contracts to several downstream components:
• functionalization uses them to identify mutations and determine the required functional form
• autograd uses them to identify views and construct DifferentiableViewMeta when required
• JIT uses them for alias analysis, which informs dead-code elimination and related optimizations
• Inductor and functorch consume the same alias contract

Writing (a) as (a!) by mistake makes functionalization treat an in-place op as functional, getting the backward graph wrong; the other way around, marking a functional op as in-place may produce false alias-conflict reports.
Example 2.1: what alias annotations do Look at aten::transpose's schema: 
aten::transpose.int(Tensor(a) self, int dim0, int dim1) -> Tensor(a)
Tensor(a) appears on both self and the return: they share the same memory slot named a. This tells the dispatcher's downstream: the transposed tensor and the original share storage; mutating one mutates the other.

Contrast with aten::clone: 
aten::clone(Tensor self, *, MemoryFormat? memory_format=None) -> Tensor
The return has no alias annotation → it's a freshly allocated tensor; modifying it doesn't affect self.

At registration time, this string is parsed by torch::jit::parseSchema into a c10::FunctionSchema struct that records each argument's name, type, alias info, and default value; only then is it registered into the dispatcher's internal op table. So the "schema string" is the source of truth, and FunctionSchema is its in-memory representation.

2.2 Three variants: functional / in-place / out

Many operators have "side-effect" capabilities (in-place mutation, writing into a preallocated out tensor). PyTorch gives such operators three schema variants simultaneously, functionally equivalent but with different interfaces. Look at the three variants of add:

VariantSchema
functionaladd.Tensor(Tensor self, Tensor other, *, Scalar alpha=1) -> Tensor
in-placeadd_.Tensor(Tensor(a!) self, Tensor other, *, Scalar alpha=1) -> Tensor(a!)
outadd.out(Tensor self, Tensor other, *, Scalar alpha=1, Tensor(a!) out) -> Tensor(a!)

Naming conventions:

  • functional: returns a new tensor. Python writes z = x.add(y). Most common, corresponds to the schema's "base form."
  • in-place: op name ends with _ (underscore), self annotated with (a!), return also (a!) indicating "the returned tensor is the mutated self." Python writes x.add_(y), equivalent to x = x + y but with no new allocation.
  • out: overload adds .out, with an extra kw-only Tensor(a!) out. Python writes torch.add(x, y, out=z), writing the result into the preallocated z. Commonly used in memory-reuse optimization scenarios.

The three schemas encode distinct allocation and mutation contracts:

  1. Interface contract. Python exposes forms that return a new tensor, mutate an existing tensor, or write into caller-provided storage.
  2. Performance. Functional always allocates new memory; in-place and out can reuse, and the difference in peak training memory is significant.
  3. Autograd behavior. Functional calls can build a grad_fn; in-place calls update version counters and may reject writes to requires-grad leaves; out variants generally do not support autograd when an argument requires gradients.
Example 2.2: how the three variants share an implementation The three schemas can share one structured meta() and impl() definition, but the generated functional wrapper does not dispatch to add.out: 
add.Tensor   :  functional structured wrapper → meta() → impl() → new output
add_.Tensor  :  inplace structured wrapper    → meta() → impl() → self
add.out      :  out structured wrapper        → meta() → impl() → caller's out
The wrappers are separate; structured_delegate: add.out tells codegen which structured definition they share. The v2.12.0 generation template is implemented in register_dispatch_key.py.
Aside 2.2: the autogen keyword Some op authors only write the functional variant and tell codegen to "fill in the in-place and out variants by rule": 
- func: my_op(Tensor self) -> Tensor
  autogen: my_op.out, my_op_
On seeing autogen:, codegen can generate the requested schemas and wrappers according to the operator family. The direction of delegation depends on the source variant and must not be reduced to a universal "out wraps functional" rule.

Aside 2.3: shared phases in structured codegen Without structured codegen, the functional, in-place, and out variants each repeat output creation, resizing, device checks, and implementation calls. The wrappers share implementation logic and output constraints; the functional schema does not redispatch to the out schema.

2.4 derivatives.yaml: backward formulas

So far the schema only describes "forward behavior." Backward (autograd) information lives in another file: tools/autograd/derivatives.yaml. Each differentiable op gets a backward formula here:

- name: add.Tensor(Tensor self, Tensor other, *, Scalar alpha=1) -> Tensor
  self:  handle_r_to_c(self.scalar_type(),  grad)
  other: handle_r_to_c(other.scalar_type(), maybe_multiply(grad, alpha.conj()))
  result: self_t + maybe_multiply(other_t, alpha)            # forward-mode tangent

- name: relu(Tensor self) -> Tensor
  self: threshold_backward(grad, result, 0)
  result: auto_element_wise

Reading it field by field:

  • name: must exactly match the schema in native_functions.yaml: this is the "primary key" matching the two sides.
  • self: and other: are input argument names, and each expression defines the gradient for that input. For add, the gradient for other is grad * alpha.conj(); maybe_multiply skips the multiplication when alpha == 1. The predefined variable grad denotes the upstream gradient received by this backward call.
  • result: is the forward-mode JVP formula used by torch.func.jvp. The predefined variables self_t and other_t denote the input tangents. The field may be omitted when the operator does not provide JVP support.
  • auto_element_wise is a special tag that tells codegen "this is an elementwise op; auto-derive the jvp formula by rule."

These formulas are not Python; they are a restricted DSL consumed by codegen. It supports calling other at::* ops (like threshold_backward), accessing input attributes (like self.scalar_type()), and using predefined variables like grad/result/self_t.

Autograd codegen emits two categories of code for each differentiable operator:

  1. An autograd Node subclass (e.g. AddBackward0, ReluBackward0) whose apply() method body is the formula translated into C++.
  2. An autograd kernel wrapper (registered to AutogradCPU/AutogradCUDA etc.) that during forward builds the Node, attaches next_edges, and redispatches to the backend (the skeleton from §1.7).
Example 2.4: the correspondence between derivatives.yaml and generated code The backward formula for add in derivatives.yaml: 
other: handle_r_to_c(other.scalar_type(), maybe_multiply(grad, alpha.conj()))
gets translated by codegen into this code inside AddBackward0::apply(): 
if (should_compute_output(1)) {
  grad_inputs[1] = handle_r_to_c(other_scalar_type,
                                 maybe_multiply(grad, alpha.conj()));
}
The generated expression preserves the YAML formula and adds an output-requirement guard, allowing computation to be skipped when downstream consumers do not request other's gradient.

§6.8 examines the generated AddBackward0::apply() code and its execution by the autograd engine during loss.backward().

The schema is a shared contract for the dispatcher, autograd, JIT, functionalization, and Python bindings, with alias annotations carrying storage-sharing and mutation semantics. native_functions.yaml records operator declarations and derivatives.yaml records differentiation formulas; the ATen and autograd generators consume them separately and meet in generated registrations and wrappers.

3. The C++ registration interface: the TORCH_LIBRARY family

Once a schema establishes the operator contract, registration associates that contract with implementations in the dispatcher. The TORCH_LIBRARY family in torch/library.h declares schemas, extends namespaces, and attaches kernels to existing operators.

TORCH_LIBRARY, TORCH_LIBRARY_FRAGMENT, and TORCH_LIBRARY_IMPL all create file-static initialization entries, while their Library::Kind values impose different constraints on schemas, default dispatch keys, and namespace ownership.

Their common mechanism is a file-static initializer that registers information with the global dispatcher when an executable starts or a shared library loads.

The three forms differ in whether they define a namespace and schema, extend an existing namespace, or attach a kernel for a dispatch key. That distinction also provides the context for boxed and unboxed calls, fallback and fallthrough, and the relationship between def and impl.

3.1 The three identities of Library: DEF / FRAGMENT / IMPL

The central registration object is torch::Library. Each TORCH_LIBRARY* macro constructs a Library instance whose Kind has three forms (torch/library.h:551-553):

// torch/library.h
class Library {
 public:
  enum Kind { DEF, IMPL, FRAGMENT };
  ...
};

The three Kinds correspond to three semantics:

KindSemanticsTriggering macroTypical user
DEFOpens a "main" library for a namespace. Each namespace name may appear in at most one DEF in the entire process; a second DEF is rejected when Dispatcher::registerLibrary registers it.TORCH_LIBRARY(ns, m)Custom extensions (opening a myops namespace)
FRAGMENTAppends a "fragment" to the same namespace. Same-name fragments may come from any number of translation units (TUs) and are stitched together into one library.TORCH_LIBRARY_FRAGMENT(ns, m)PyTorch internals: operator schemas in the aten namespace are distributed across multiple codegen files
IMPLAttaches a kernel under a DispatchKey to an already existing op. Cannot define a new schema here, only m.impl(...) implementations for existing ops.TORCH_LIBRARY_IMPL(ns, key, m)Registering concrete implementations for a backend (CUDA wrappers in aten, CUDA kernels for custom ops, etc.)
Example 3.1: practical uses for the three Kinds The my_extension extension registers myops::custom_relu with CPU and CUDA implementations. Three C++ files divide the responsibilities as follows:

register_schema.cpp uses TORCH_LIBRARY(myops, m) → DEF, declares the schema. With this line in place, the myops namespace is "opened."
kernel_cpu.cpp uses TORCH_LIBRARY_IMPL(myops, CPU, m) → IMPL, registers the CPU implementation.
kernel_cuda.cu uses TORCH_LIBRARY_IMPL(myops, CUDA, m) → IMPL, registers the CUDA implementation.

Schema and a catch-all kernel may share a DEF block through m.def(...) and m.impl(...). Backend-specific registrations are normally placed in separate IMPL blocks, where the block-level DispatchKey makes each implementation explicit. The API also permits an explicit key carried by CppFunction, so this organization is a clarity convention rather than a syntax restriction.
Aside 3.1: separate macros and registration constraints The three macros encode different Library::Kind values and argument contracts. DEF declares a namespace and carries no block-level DispatchKey; IMPL normally carries one; FRAGMENT and IMPL use C10_UID so multiple initializers can coexist in a translation unit. Namespace uniqueness is checked when DEF reaches Dispatcher::registerLibrary, while symbol uniquification keeps generated initializer names distinct.

3.2 TORCH_LIBRARY: opening a new namespace

Look at the actual TORCH_LIBRARY macro (torch/library.h:982-991):

// torch/library.h
#define TORCH_LIBRARY(ns, m)                                                   \
  static void TORCH_LIBRARY_init_##ns(torch::Library&);                        \
  static const torch::detail::TorchLibraryInit TORCH_LIBRARY_static_init_##ns( \
      torch::Library::DEF,                                                     \
      &TORCH_LIBRARY_init_##ns,                                                \
      C10_STRINGIZE(ns), std::nullopt,                                         \
      __FILE__, __LINE__);                                                     \
  void TORCH_LIBRARY_init_##ns(torch::Library& m)

The macro expands into three declarations:

  1. Line 1: static void TORCH_LIBRARY_init_##ns(torch::Library&); forward-declares a function (##ns is token pasting; if ns=myops, this becomes TORCH_LIBRARY_init_myops).
  2. Lines 2 to 5: static const torch::detail::TorchLibraryInit TORCH_LIBRARY_static_init_##ns(DEF, ...); constructs a file-static object. Its constructor receives:
    • torch::Library::DEF: identity marker; this is a DEF, not an IMPL.
    • &TORCH_LIBRARY_init_##ns: the registration function declared on line 1; the constructor calls it.
    • C10_STRINGIZE(ns): namespace string literal ("myops").
    • std::nullopt: DispatchKey, empty for DEF.
    • __FILE__, __LINE__: location info for errors.
  3. Line 6: void TORCH_LIBRARY_init_##ns(torch::Library& m) is the function's definition header; the { ... } following the macro supplies its body.

The source form TORCH_LIBRARY(myops, m) { m.def("..."); } therefore expands to:

static void TORCH_LIBRARY_init_myops(torch::Library&);
static const torch::detail::TorchLibraryInit TORCH_LIBRARY_static_init_myops(
    torch::Library::DEF,
    &TORCH_LIBRARY_init_myops,
    "myops", std::nullopt,
    "/path/to/myops.cpp", 42);

// The block following the macro supplies this function body:
void TORCH_LIBRARY_init_myops(torch::Library& m)
{
  m.def("...");
}

The registration takes effect through file-static initialization. C++ constructs these objects before main(); the TorchLibraryInit constructor therefore invokes the registration function during process startup and adds the schema to the global dispatcher table. No separate runtime call is required from application code.

Example 3.2: usage 
// myops_register.cpp
#include <torch/library.h>

TORCH_LIBRARY(myops, m) {
  m.def("custom_add(Tensor self, Tensor other) -> Tensor");
  m.def("custom_relu(Tensor self) -> Tensor");
}
Once this code is compiled and linked into the Python process, torch.ops.myops.custom_add and torch.ops.myops.custom_relu can be resolved from Python. Their schemas are present in the dispatcher, while an invocation still reports "no kernel registered" until a backend implementation is attached.
Namespace constraint: a process may contain only one TORCH_LIBRARY(ns, ...) DEF for a namespace. A second DEF triggers an error during registration. Registrations split across multiple .cpp files use TORCH_LIBRARY_FRAGMENT.

3.3 TORCH_LIBRARY_FRAGMENT: extending the same namespace

FRAGMENT addresses the "same namespace across multiple files" need. Look at the macro (torch/library.h:1001-1023, simplified):

// torch/library.h (simplified)
#define TORCH_LIBRARY_FRAGMENT(ns, m) _TORCH_LIBRARY_FRAGMENT(ns, m, C10_UID)
#define _TORCH_LIBRARY_FRAGMENT(ns, m, uid)                                \
  static void C10_CONCATENATE(TORCH_LIBRARY_FRAGMENT_init_##ns##_, uid)(   \
      torch::Library&);                                                    \
  static const torch::detail::TorchLibraryInit                             \
      C10_CONCATENATE(TORCH_LIBRARY_FRAGMENT_static_init_##ns##_, uid)(    \
          torch::Library::FRAGMENT,                                        \
          ...,                                                             \
          C10_STRINGIZE(ns), std::nullopt, ...);                           \
  void C10_CONCATENATE(...)(torch::Library& m)

Compared with TORCH_LIBRARY, only two things differ:

  1. Kind changes from DEF to FRAGMENT: telling the Library constructor "don't abort on a duplicate namespace."
  2. Symbol names are uniquified with C10_UID. C10_UID is PyTorch's internal "line-number + counter" macro, generating a different token at each expansion. So writing five TORCH_LIBRARY_FRAGMENT(aten, m) { ... } blocks in the same TU yields five non-conflicting init function names.
Aside 3.3: fragmented registration of the aten namespace PyTorch code generation emits TORCH_LIBRARY_FRAGMENT(aten, m) blocks across files such as RegisterSchema.cpp. The corresponding generation logic appears in torchgen/gen.py:
# torchgen/gen.py around 1761-1776 (simplified)
if namespace == "aten":
    aten_schema_registrations = schema_registrations_body
else:
    torch_library_macro = (
        "TORCH_LIBRARY_FRAGMENT"
        if namespace in FRAGMENT_NAMESPACES
        else "TORCH_LIBRARY"
    )
The aten namespace contains a large operator set, so codegen distributes registration statements across independently compiled units. FRAGMENT lets those initializers extend one namespace without concentrating every registration in a single generated function.
Example 3.3: fragments across files in the same namespace When myops registrations are split by module, operator families A and B can live in a.cpp and b.cpp respectively: 
// myops_a.cpp
TORCH_LIBRARY_FRAGMENT(myops, m) {
  m.def("op_a1(Tensor x) -> Tensor");
  m.def("op_a2(Tensor x) -> Tensor");
}

// myops_b.cpp
TORCH_LIBRARY_FRAGMENT(myops, m) {
  m.def("op_b1(Tensor x) -> Tensor");
}
Both files coexist; each TorchLibraryInit runs before main and adds the corresponding schemas into the myops namespace.

The process still permits at most one TORCH_LIBRARY(myops, ...) DEF. In v2.12.0, FRAGMENT itself may define operators without a preceding DEF; only DEF invokes registerLibrary for namespace uniqueness, while FRAGMENT rejects the wildcard namespace and proceeds with operator registration. The relevant branch is documented in library.cpp.

3.4 TORCH_LIBRARY_IMPL: attaching a kernel

The schema is the "declaration"; the kernel is the "implementation." TORCH_LIBRARY_IMPL is the macro for attaching a kernel for a given DispatchKey to an existing op (torch/library.h:1064-1084, simplified):

// torch/library.h (simplified)
#define TORCH_LIBRARY_IMPL(ns, k, m) _TORCH_LIBRARY_IMPL(ns, k, m, C10_UID)
#define _TORCH_LIBRARY_IMPL(ns, k, m, uid)                                  \
  static void C10_CONCATENATE(TORCH_LIBRARY_IMPL_init_##ns##_##k##_, uid)(  \
      torch::Library&);                                                    \
  static const torch::detail::TorchLibraryInit                              \
      C10_CONCATENATE(TORCH_LIBRARY_IMPL_static_init_##ns##_##k##_, uid)(   \
          torch::Library::IMPL,                                             \
          ...,                                                              \
          C10_STRINGIZE(ns),                                                \
          c10::make_optional(c10::DispatchKey::k),                          \
          ...);                                                             \
  void C10_CONCATENATE(...)(torch::Library& m)

Differences from FRAGMENT:

  • Kind = IMPL.
  • An extra parameter c10::DispatchKey::k, where k is the macro's second argument, such as CPU, CUDA, or AutogradCUDA. Each m.impl("op_name", kernel) in the block is attached to the operator's entry under that DispatchKey.
Example 3.4: typical usage 
// myops_cpu.cpp: register kernels for myops::* under the CPU key
TORCH_LIBRARY_IMPL(myops, CPU, m) {
  m.impl("custom_add",  &my_add_cpu);
  m.impl("custom_relu", &my_relu_cpu);
}

// myops_cuda.cu: register kernels for myops::* under the CUDA key
TORCH_LIBRARY_IMPL(myops, CUDA, m) {
  m.impl("custom_add",  &my_add_cuda);
  m.impl("custom_relu", &my_relu_cuda);
}

// myops_autograd.cpp: separate autograd wrapper, for attaching grad_fn
TORCH_LIBRARY_IMPL(myops, Autograd, m) {       // Autograd is an alias key, auto-expanded to AutogradCPU/CUDA/...
  m.impl("custom_add", &my_add_autograd);
}
Once the three files are linked, the computed table contains CPU, CUDA, and autograd alias registrations. Ordinary autograd-capable tensors enter the autograd layer independently of the current requires_grad value; the wrapper decides whether to record history.
The special form TORCH_LIBRARY_IMPL(_, KEY, m): the underscore as the first argument means "applies to all namespaces," typically paired with m.fallback(...) to register a global fallback kernel for a DispatchKey. An example:
// aten/src/ATen/core/VariableFallbackKernel.cpp
TORCH_LIBRARY_IMPL(_, AutogradCUDA, m) {
  m.fallback(autogradNotImplementedFallback());
}
Meaning: for any namespace, an operator without a more specific AutogradCUDA entry can reach this backend fallback. It does not synthesize a correct derivative. The v2.12.0 source explicitly describes it as an error-checking passthrough rather than a proper autograd implementation; custom operators need an autograd formula or a differentiable CompositeImplicitAutograd composition. See VariableFallbackKernel.cpp.

Then register a kernel:

The schema remains the registration contract, and every kernel signature must be compatible with it.

3.6 Boxed vs unboxed call paths

Dispatcher lookup returns a KernelFunction, which selects an unboxed or boxed path according to whether the call site has a static type signature. The unboxed path uses typed C++ parameters; the boxed path uses the uniform IValue stack ABI.

3.7 Fallback and fallthrough

Beyond m.def and m.impl, Library also has m.fallback. Its meaning is: register an op-agnostic kernel for the entire DispatchKey; any op without its own impl under that key falls through to this one.

Two common forms:

m.fallback(torch::CppFunction::makeFallthrough());
    // "this layer does nothing; clear my bit from the bitmap and proceed to the next layer"
    // O(1) implementation: the dispatcher sees fallthrough and permanently clears this key from fallthrough_mask

m.fallback(torch::CppFunction::makeFromBoxedFunction<&my_boxed_fallback>());
    // Actually write a boxed kernel as a fallback, e.g. functorch's vmap interpreter

A fallthrough registration contributes to the operator's precomputed mask, allowing lookup to clear the corresponding key before invoking a kernel. This avoids a separate fallback-kernel call, although key-set construction, mask application, and lookup remain runtime work.

Typical fallthrough users:

  • BackendSelect: most ops don't need it (only factory functions like torch.randn use it). For all other ops, BackendSelect is fallthrough.
  • Named: becomes a candidate when the tensor key set activates Named; the computed entry then determines whether handling or fallthrough applies.
  • Conjugate / Negative / ZeroTensor: their lazy markers activate the corresponding keys, after which concrete registrations or fallbacks determine behavior.
  • Tracer: tracing state controls activation, and the computed dispatch entry controls whether the key is handled or skipped.

A typical call activates only the keys contributed by its tensors and current TLS state. Activated keys with explicit fallthrough entries are then removed by the mask. An inactive key and an active key with a fallthrough entry reach the same lookup without representing the same condition.

Operational boundary: an extension layer can be activated by TLS or tensor keys, while fallthrough registrations identify operators that require no work from that layer. The condition therefore lives in the registration model instead of being repeated at every operator call site.

3.8 Complete registration path for a custom op

The preceding registration rules combine into a complete operator path. The following custom relu provides CPU, CUDA, and autograd implementations across four .cpp files:

// ============ myops_schema.cpp ============
// (1) Use TORCH_LIBRARY to open DEF for the myops namespace and declare the schema once
#include <torch/library.h>

TORCH_LIBRARY(myops, m) {
  m.def("custom_relu(Tensor self) -> Tensor");
}

This file provides two things: ① the namespace myops is opened (DEF); ② the operator custom_relu's schema is entered into the dispatcher table (but no kernel yet). Calling torch.ops.myops.custom_relu(x) from Python at this point reports "kernel not found."

// ============ myops_cpu.cpp ============
// (2) CPU implementation + registration to (myops, CPU)
#include <ATen/ATen.h>
#include <torch/library.h>

at::Tensor custom_relu_cpu(const at::Tensor& self) {
  return at::clamp_min(self, 0);   // For simplicity, borrow at::clamp_min as the implementation
}

TORCH_LIBRARY_IMPL(myops, CPU, m) {
  m.impl("custom_relu", TORCH_FN(custom_relu_cpu));
}

This file: attaches a concrete kernel for myops::custom_relu under the CPU key (= the two-dimensional (Dense, CPUBit)). TORCH_FN exposes the unboxed signature to the dispatcher for fast runtime. Note the implementation uses at::clamp_min, itself a dispatched op that internally re-enters the dispatcher to call CPU's clamp_min.

// ============ myops_cuda.cu ============
// (3) CUDA implementation + registration to (myops, CUDA)
#include <ATen/ATen.h>
#include <torch/library.h>

at::Tensor custom_relu_cuda(const at::Tensor& self) {
  return at::clamp_min(self, 0);   // Same as above: clamp_min has its own CUDA kernel
}

TORCH_LIBRARY_IMPL(myops, CUDA, m) {
  m.impl("custom_relu", TORCH_FN(custom_relu_cuda));
}

Symmetrically attaches a kernel to the CUDA key. Now both backend entries for myops::custom_relu in the dispatcher table have kernels.

// ============ myops_autograd.cpp ============
// (4) Autograd implementation: capture forward, build grad_fn, pass forward math through to backend
#include <torch/autograd.h>
#include <torch/library.h>

class CustomReluFn : public torch::autograd::Function<CustomReluFn> {
 public:
  static at::Tensor forward(torch::autograd::AutogradContext* ctx,
                            const at::Tensor& self) {
    // On entering forward, manually exclude "AutogradXxx + ADInplaceOrView" keys: otherwise
    // the dispatcher call below would land back in this Function, looping forever.
    at::AutoDispatchBelowADInplaceOrView guard;
    // Inside the guard, AutogradCUDA has been removed from the TLS bitmap,
    // so the dispatcher call falls to CUDA or CPU (depending on self.device()).
    static auto op = c10::Dispatcher::singleton()
        .findSchemaOrThrow("myops::custom_relu", "")
        .typed<at::Tensor(const at::Tensor&)>();
    auto result = op.call(self);
    ctx->save_for_backward({result});
    return result;
  }

  static torch::autograd::variable_list backward(
      torch::autograd::AutogradContext* ctx,
      torch::autograd::variable_list grad_outputs) {
    auto saved = ctx->get_saved_variables();
    auto& result = saved[0];
    // d/dx relu(x) = 1 if x > 0 else 0; but we saved result, equivalent to (result > 0)
    return { grad_outputs[0] * (result > 0).to(grad_outputs[0].dtype()) };
  }
};

at::Tensor custom_relu_autograd(const at::Tensor& self) {
  return CustomReluFn::apply(self);
}

TORCH_LIBRARY_IMPL(myops, Autograd, m) {   // Autograd is an alias key, expanded to all AutogradXxx
  m.impl("custom_relu", &custom_relu_autograd);
}

This file is the key one; a few details:

  • torch::autograd::Function: a PyTorch-provided CRTP template base class; subclasses define forward and backward. apply() is the base-class-generated entry that automatically handles grad_fn construction, next_edges collection, and context management.
  • at::AutoDispatchBelowADInplaceOrView guard;: an RAII object that pushes all autograd functionality bits + the ADInplaceOrView bit into TLS exclude. Throughout the forward body, the dispatcher won't revisit the AutogradCUDA layer.
  • Use c10::Dispatcher::singleton().findSchemaOrThrow to look up the schema, then typed<...>().call(...) to run it. This is PyTorch's recommended form for "calling custom ops in C++", equivalent to Python's torch.ops.myops.custom_relu(self).
  • Register to the Autograd alias: rather than specific AutogradCPU/AutogradCUDA, use the alias Autograd. It auto-expands to every concrete autograd key, covering autograd cases for all backends in one line.

With the four files linked together, the Python side:

>>> import torch, my_extension
>>> x = torch.randn(3, requires_grad=True, device='cuda')
>>> y = torch.ops.myops.custom_relu(x)
    # dispatcher computes bitmap → highest bit = AutogradCUDA → jump to custom_relu_autograd
    # → CustomReluFn::apply → forward()
    # → AutoDispatchBelowADInplaceOrView guard takes effect
    # → op.call(self) (myops::custom_relu) → highest bit now = CUDA → jump to custom_relu_cuda
    # → at::clamp_min(self, 0) → runs clamp_min's CUDA kernel → returns
>>> y.sum().backward()
    # autograd engine calls CustomReluFn::backward(...)
    # → computes gradient → passes through next_edges
Composite implementation: CompositeImplicitAutograd. Because custom_relu is composed entirely from at::clamp_min and obtains gradients through that operator's autograd path, it can register to the CompositeImplicitAutograd alias and retain backend and autograd dispatch through the inner operator: 
at::Tensor custom_relu_composite(const at::Tensor& self) {
  return at::clamp_min(self, 0);
}

TORCH_LIBRARY_IMPL(myops, CompositeImplicitAutograd, m) {
  m.impl("custom_relu", &custom_relu_composite);
}
A composite implementation can reside in one .cpp file because its inner at::clamp_min call goes through the dispatcher and supplies backend routing and autograd behavior. Operators expressed entirely through existing differentiable operators can use this form. A native implementation that directly launches its own CUDA kernel instead needs explicit backend and autograd registrations such as the four-file pattern in §3.8.

4.4 Abstract execution with Meta and FakeTensor

Meta belongs to the Dense backend family alongside CPU and CUDA. A meta tensor carries shape, stride, and dtype information without readable numerical storage. FakeTensorMode intercepts operators in Python and uses Meta kernels, decompositions, or dedicated fake logic to propagate metadata while preserving a simulated device. The discussion here describes the common v2.12.0 path, not the only implementation used by every compiler pass.

4.4.1 Where Meta sits in the dispatcher table

Following the DispatchKey table from §1.3, Meta is in the same row as CPU / CUDA / XPU, a backend key with value roughly DispatchKey::Meta. It is normal for one op to carry CPU, CUDA, and Meta entries side by side: when a meta tensor passes through the dispatcher, the computed DispatchKeySet's backend bit is Meta, and routing lands on this entry.

aten::add.Tensor kernel table inside OperatorEntry (excerpt):

  DispatchKey::CPU             -> at::native::add_kernel (CPU vectorized)
  DispatchKey::CUDA            -> at::native::add_kernel_cuda
  DispatchKey::Meta            -> at::native::add_meta       # shape inference only
  DispatchKey::AutogradCPU     -> AutogradAdd::apply
  DispatchKey::AutogradCUDA    -> AutogradAdd::apply
  ...

Many structured native operators receive generated Meta wrappers whose meta() logic determines output metadata. Other operators use handwritten Meta kernels or decompositions. Python custom operators normally require a fake implementation, although a small set of schemas can derive trivial fake behavior.

4.4.2 FakeTensor: a thin wrapper above the Meta key

Compilation and export commonly use FakeTensor (torch._subclasses.fake_tensor.FakeTensor), a __torch_dispatch__ tensor subclass managed by FakeTensorMode. Its relationship to a bare meta tensor is summarized below.

On a common path, FakeTensorMode executes an operator with tensors that carry no real data, using a Meta kernel or decomposition and retaining the simulated device on the result. A Meta kernel is often important for compatibility, but data-dependent shapes, aliasing, and dedicated fake handlers can require additional logic.

4.4.3 Registration target of register_fake

register_fake(fn) stores the Python function in a fake-implementation holder and installs a constructed wrapper at the Meta key:

@scale_add.register_fake
def _(x, scale, bias):
    return torch.empty_like(x)

# Conceptual internal relationship:
fake_impl_holder.register(_fn)
lib.impl("myops::scale_add", constructed_meta_wrapper, "Meta")

The API name describes the registered FakeTensor behavior, while the implementation layer attaches its wrapper to Meta. The v2.12.0 registration and conflict checks are in torch/_library/fake_impl.py.

4.4.4 Metadata propagation in torch.export

The following is a simplified view of the FakeTensor-related part of torch.export.export(model, example_inputs):

torch.export(model, example_inputs)
   │
   ├─ 1. Create matching FakeTensors from example_inputs (preserve shape / dtype / device)
   │
   ├─ 2. Enter FakeTensorMode context
   │
   ├─ 3. Dynamo + symbolic_shapes wrap variable dimensions as SymInt
   │     (e.g. batch dim -> s0, not the concrete 8)
   │
   ├─ 4. Tracing and functionalization propagate operator metadata with FakeTensors
   │     ├─ Operator enters Python __torch_dispatch__ interception
   │     ├─ FakeTensorMode selects a Meta kernel, decomposition, or dedicated fake logic
   │     └─ Outputs continue to carry size / stride / dtype / device as FakeTensors
   │
   └─ 5. Build an ExportedProgram with graph signature, constraints, and node metadata

# Serialization is a separate explicit step:
torch.export.save(exported_program, "model.pt2")

A few facts fall out of this path:

  • Fake execution skips the corresponding numerical backend kernel. This boundary covers abstract execution of tensor operators. Tracing may still run Python control logic, guards, and registration functions, so it does not imply a fixed speedup or the absence of every form of concrete computation.
  • Meta kernels are an important source of shape information. Incorrect shape, stride, or dtype metadata from a fake/meta implementation can propagate into export and Inductor, producing an invalid lowering or runtime dimension errors. Some operators obtain metadata through decompositions or dedicated fake implementations, so not every inference path belongs to one Meta kernel.
  • Dynamic-shape paths require SymInt-compatible implementations. Export may represent the batch dimension as s0, in which case the fake/meta implementation receives a SymInt. Concrete branches must be expressed through supported guards rather than coercing symbolic dimensions directly to Python booleans.
  • A custom operator normally needs a fake implementation. In v2.12.0, custom_op installs a Meta wrapper; without a registered fake function, that wrapper reports an error unless the schema supports generated trivial behavior. CompositeImplicitAutograd operators instead decompose into constituent operators with fake/meta support.

torch.export.export and torch.export.save are separate APIs; the latter writes the .pt2 archive. The corresponding entry points are visible in torch/export/__init__.py.

4.4.5 Implementation constraints of register_fake

  • Compose PyTorch operators without reading storage or data. Calls such as x.mul(2), torch.add(x, y), and x * 2 continue under FakeTensorMode. Operations such as data_ptr(), .item(), or Python branches driven by tensor values cross the fake implementation boundary. The public API contract requires a fake implementation to consist of PyTorch operations and forbids direct access to input or intermediate tensor storage.
  • Shape inference must work over SymInts:
    • No concrete checks like if x.size(0) == 8:
    • Use torch.sym_int or SymInt-friendly forms like x.shape[0] + 1 for shape arithmetic
    • If a branch unavoidably depends on a concrete value, use torch._check(...) to register the guard with Dynamo
  • Keep operator metadata independent of side effects. Tracing may invoke a fake implementation more than once; file writes, global mutation, and logging do not belong to the operator's abstract semantics.
  • The output device must match the real operator contract. Most elementwise custom operators derive it from an input, for example with device=x.device. Hard-coding cuda:0 removes device portability unless the operator contract explicitly requires that device.
  • The output dtype must follow the real type-promotion rules. Use torch.promote_types or equivalent PyTorch operations to derive it; unconditionally returning x.dtype can make the abstract output disagree with the numerical kernel.

4.4.6 Common failure modes

# Incorrect case 1: reading tensor data to determine output shape
@my_op.register_fake
def _(x):
    n = int(x[0].item())
    return torch.empty((n,), device=x.device)

# For an operator with unchanged metadata, composing PyTorch ops is valid:
def _(x):
    return x.mul(2)

# Incorrect case 2: directly evaluating a concrete condition over SymInt
@my_op.register_fake
def _(x):
    if x.size(0) % 8 == 0:    # SymInt % 8 -> SymBool, if forces a guard, export warns/errors
        ...

# Correct form:
def _(x):
    torch._check(x.size(0) % 8 == 0)
    return torch.empty_like(x)

# Incorrect case 3: hard-coded device
@my_op.register_fake
def _(x):
    return torch.empty(x.shape, device="cuda")  # always cuda; exported graph cannot run on cpu

# Correct form:
def _(x):
    return torch.empty(x.shape, dtype=x.dtype, device=x.device)

# Incorrect case 4: wrong shape for a multi-output operator
@split.register_fake
def _(x, n):
    return [torch.empty_like(x) for _ in range(n)]   # each shard should be x.shape[0] // n

# Correct form:
def _(x, n):
    chunk = x.size(0) // n
    return [torch.empty((chunk,) + x.shape[1:], dtype=x.dtype, device=x.device)
            for _ in range(n)]

4.5 Python registration and the shared C++ dispatcher

The Python APIs manage registration handles and Python callables while writing to the same torch::Library and c10::Dispatcher registry used by C++ code. The following sketch preserves the stable boundary without treating internal binding names as public APIs:

torch.library.Library("myops", "DEF")
   ↓ # torch/library.py
torch._C._dispatch_library("DEF", "myops", ...)
   ↓
torch::Library handle

lib.define("scale_add(Tensor x, float scale, Tensor bias) -> Tensor")
   ↓
torch::Library::def(parsed_schema)
   ↓
c10::Dispatcher::singleton().registerDef(schema, ...)

op.register_kernel("cuda")(fn_py)
   ↓
Library.impl("scale_add", fn_py, "CUDA")
   ↓
c10::Dispatcher::singleton().registerImpl(
   OperatorName{"myops", "scale_add"},
   c10::DispatchKey::CUDA,
   python_callable_adapter);

Two boundaries matter:

  • The dispatch table stores a kernel adapter capable of invoking the Python callable. This mechanism is distinct from the Python dispatch key and PythonFallbackKernel used by tensor subclasses.
  • Invoking the Python kernel enters the Python runtime and usually adds overhead relative to a pure C++ kernel. A migration decision should be based on operator-level profiling for the target workload. The v2.12.0 boundary from Python Library.impl to its C++ binding is visible in torch/library.py.

4.6 Complete Python registration of a custom op

The C++ version of myops::custom_relu in §3.8 registers schema, backend, and autograd behavior separately. Python can express the same operator contract in one file:

import torch

## 1) Schema + default CompositeExplicitAutograd implementation
@torch.library.custom_op("myops::custom_relu", mutates_args=())
def custom_relu(x: torch.Tensor) -> torch.Tensor:
    # A composite op can run on devices supported by its constituent ops
    return x.clamp(min=0)

## 2) Register a CUDA-specialised implementation (overrides default)
@custom_relu.register_kernel("cuda")
def _(x: torch.Tensor) -> torch.Tensor:
    # Could dispatch into a Triton kernel or a cuBLAS / cuDNN wrapper here
    return x.relu()                          # illustrative

## 3) register_fake: lets export / AOTI infer shape
@custom_relu.register_fake
def _(x):
    return torch.empty_like(x)

## 4) register_autograd: provide a backward (optional, needed for training)
def _setup_ctx(ctx, inputs, output):
    (x,) = inputs
    ctx.save_for_backward(x)

def _backward(ctx, grad):
    (x,) = ctx.saved_tensors
    return grad * (x > 0).to(grad.dtype),    # tuple matching the inputs

custom_relu.register_autograd(_backward, setup_context=_setup_ctx)

## Usage, identical to the C++-registered version:
y = torch.ops.myops.custom_relu(torch.randn(3, device="cuda", requires_grad=True))
y.sum().backward()

Compared with the four-file C++ version in §3.8, the Python registration has two practical advantages:

  • Shorter development cycle: registration changes do not require rebuilding a C++ or CUDA extension.
  • Explicit export and FakeTensor contract: custom_op provides a stable schema, while register_fake supplies shape, dtype, and device inference for abstract execution.

Costs:

  • A Python kernel returns to the Python runtime, giving it different call overhead and deployment constraints from a pure C++ kernel.
  • For torch.compile / torch.export, the op is opaque by default: the compiler does not inspect the Python body and a fake impl does not automatically create an Inductor lowering.
  • Cannot run outside a Python runtime; AOTI deployment needs an extra C++ shim (see PyTorch AOTI deployment to a CUDA C++ runtime, §9.4).

4.7 torch.library.opcheck: automatic invariant verification

After registering a custom op, run opcheck:

torch.library.opcheck(
    custom_relu,
    args=(torch.randn(3, 4, device="cuda"),),
)

The call exercises a suite of invariants:

  • test_schema: the schema string matches the implementation's signature (parameter names, types, optionality).
  • test_autograd_registration: when training is expected, checks that an autograd formula is registered through the supported mechanism.
  • test_faketensor: the fake impl's output FakeTensor agrees with the real impl in shape / dtype / device.
  • test_aot_dispatch_dynamic: compares eager and compiled dispatch while covering dynamic shapes, functionalization, and backward when applicable.

These are the four default checks in v2.12.0. opcheck validates registration and tracing invariants; it does not replace numerical gradient checks such as torch.autograd.gradcheck. Test representative device, dtype, and requires-grad combinations separately. See torch/library.py.

6. End-to-end trace: aten::add on CUDA

Forward and backward execution of aten::add.Tensor on Dense CUDA tensors connects key selection, schemas, registration interfaces, and code generation in one concrete path.

Setting: two CUDA tensors x, y, both requires_grad=True. The input program is: 
z = torch.add(x, y)
z.sum().backward()
The trace follows the principal C++ wrappers, dispatcher slots, and CUDA implementation reached by these two lines.

Assuming no additional mode, autocast, or tensor subclass, and a Dense CUDA implementation, the call enters the dispatcher from Python, passes through autograd and the CUDA implementation, and later reaches a generated backward node through the autograd engine. The nine subsections below organize that logical path from the v2.12.0 source and codegen templates; generated shard numbers, wrapper names, and the selected kernel can still vary with build options.

6.1 Starting point: YAML declarations and derivative formulas

native_functions.yaml determines the schema and structured codegen, while derivatives.yaml supplies the autograd formulas. The following v2.12.0 entries anchor the trace.

The add.Tensor (functional variant) and add.out (structured anchor) entries in native_functions.yaml (simplified):

These declarations and aten/src/ATen/native/ufunc/add.h provide the main codegen inputs. Device checks, type promotion, and TensorIterator behavior also come from templates and runtime code, so the YAML alone is not a complete specification of execution.

6.2 Python → C binding layer

The call begins at torch.add(x, y). CPython resolves torch.add to a C function pointer and enters THPVariable_add. The "THP" prefix comes from Torch HPython and is PyTorch's naming convention for Python C bindings. Its source is generated at:

build/.../torch/csrc/autograd/generated/python_torch_functions_2.cpp

_2 is a shard number; torchgen splits large generated files into several compilation units. THPVariable_add performs four main steps:

  1. Parse Python arguments. Use PythonArgParser to parse per the schema (the string from §2.1), identifying the first tensor as self, the second as other, with optional kw alpha defaulting to 1.
  2. Unwrap the Python object. A Python torch.Tensor is represented by a THPVariable that holds an at::Tensor. THPVariable_unpack extracts that C++ tensor.
  3. Call the C++ API. With pure C++ tensors in hand, call at::add(self, other, alpha). Control leaves Python and enters the pure C++ world.
  4. Wrap the return back to Python. The C++-returned at::Tensor is wrapped by THPVariable_Wrap into a new torch.Tensor and returned to Python.
Aside 5.2: responsibilities of the Python/C++ wrapper boundary This layer owns object lifetime conversion and overload resolution:
① Python reference counting vs C++ smart pointers. Python's torch.Tensor uses CPython refcounting (Py_INCREF/Py_DECREF); C++'s at::Tensor uses intrusive_ptr. Correct conversion at the boundary preserves object lifetime across both systems.
② Parsing polymorphic Python arguments. A Python user can pass either (Tensor, Tensor) or (Tensor, Scalar) to the same torch.add; which overload (add.Tensor vs add.Scalar) to pick is decided by this layer. The C++ function itself accepts only static signatures, so Python-side overload resolution must happen first.

6.3 C++ API and Dispatcher::call

Entering the C++ world, the first landing point is at::add (generated in build/aten/src/ATen/Functions.h):

// build/aten/src/ATen/Functions.h
inline at::Tensor add(const at::Tensor& self, const at::Tensor& other, const at::Scalar& alpha) {
  return at::_ops::add_Tensor::call(self, other, alpha);
}

This inline forwarder delegates to at::_ops::add_Tensor::call, around line 612 of Operators.cpp:

// build/aten/src/ATen/Operators.cpp
at::Tensor _ops::add_Tensor::call(const at::Tensor& self, const at::Tensor& other, const at::Scalar& alpha) {
  static auto op = create_add_Tensor_typed_handle();   // Process-wide TypedOperatorHandle computed once
  return op.call(self, other, alpha);                  // Hand off to Dispatcher::call
}

This layer's job is "find the op's TypedOperatorHandle". TypedOperatorHandle is the dispatcher's internal "handle": it points to the row for aten::add.Tensor in the dispatcher's table. The static ensures this lookup runs only on the first call; subsequent calls hit the cache.

op.call eventually invokes c10::Dispatcher::call (Dispatcher.h:774-828), entering the key-set calculation and kernel lookup path described in §1.4.

Example 5.3: the C++ API and typed-handle cache The forwarding layer has two stable responsibilities:
① It provides the public C++ API. Third-party code can call at::add(x, y) without depending on dispatcher implementation details.
② It hides the schema-lookup cache. at::_ops::add_Tensor::call looks up the schema on the first call (create_add_Tensor_typed_handle()) and caches it. If every call went straight to Dispatcher::call and had to look up the schema each time, performance would degrade significantly.

6.4 On-the-fly DispatchKeySet computation

Entering Dispatcher::call (Dispatcher.h:774-828), the core is two lines:

// Core of Dispatcher::call
auto dispatchKeySet =
    op.operatorDef_->op.dispatchKeyExtractor()
        .template getDispatchKeySetUnboxed<Args...>(args...);
const KernelFunction& kernel = op.operatorDef_->op.lookup(dispatchKeySet);
return kernel.template call<Return, Args...>(op, dispatchKeySet, ...);

The first line computes the bitmap (the DispatchKeySet from §1.5), the second looks up the kernel for the highest bit, the third jumps. For our call, concretely:

  1. Initial bitmap value: each input contributes its TensorImpl::key_set_. An ordinary Dense CUDA tensor includes Dense, the CUDA backend component, and autograd functionality, which resolve to {AutogradCUDA, CUDA}. The autograd key is not inserted according to the current requires_grad value; compute_requires_grad inside the wrapper decides whether to build history.
  2. TLS local include: autocast off, not in functorch, so include is empty.
  3. TLS local exclude: first time entering the dispatcher, so exclude is empty too.
  4. Fallthrough mask: each op's dispatch table precomputed its fallthrough_mask at registration. For add, bits like BackendSelect, Named, Conjugate are masked out. The bitmap stays at {AutogradCUDA, CUDA}.
  5. highestPriorityTypeId(): among the remaining bits, the highest functionality bit is AutogradFunctionality (corresponding to runtime AutogradCUDA), since it sits after Dense in the enum (a higher bit).

lookup returns the kernel in the AutogradCUDA slot of aten::add.Tensor. Autograd codegen emits and registers this wrapper; generated shard numbers and local symbol names are not stable APIs:

// build/.../VariableType_2.cpp (shard number may vary)
TORCH_LIBRARY_IMPL(aten, AutogradCUDA, m) {
  ...
  m.impl("add.Tensor", TORCH_FN(/* generated autograd wrapper */));
  ...
}

The rest of this section calls it the “autograd wrapper” rather than treating one generated symbol name as a cross-version interface.

6.5 AutogradCUDA wrapper: graph construction and redispatch

The wrapper combines the derivatives.yaml entry with templates in gen_variable_type.py. The following pseudocode preserves the control flow while avoiding build-specific local names:

at::Tensor generated_autograd_add_Tensor(
    c10::DispatchKeySet ks,
    const at::Tensor& self, const at::Tensor& other, const at::Scalar& alpha) {

  // === Step 1) If any input requires_grad, prepare a fresh grad_fn backward node ===
  std::shared_ptr<AddBackward0> grad_fn;
  if (compute_requires_grad(self, other)) {
    grad_fn = std::shared_ptr<AddBackward0>(new AddBackward0(), deleteNode);
    grad_fn->set_next_edges(collect_next_edges(self, other));   // backward edges
    grad_fn->alpha = alpha;                                      // stored for the backward formula
    grad_fn->other_scalar_type = other.scalar_type();
    grad_fn->self_scalar_type  = self.scalar_type();
  }

  // === Step 2) Remove "AutogradCUDA + ADInplaceOrView" from the bitmap, then redispatch ===
  auto _tmp = ([&]() {
    at::AutoDispatchBelowADInplaceOrView guard;     // RAII: enter guard = add autograd + ADInplaceOrView to TLS exclude
    return at::redispatch::add(
        ks & c10::after_autograd_keyset,             // explicitly mask the current layer and above
        self, other, alpha);
  })();
  auto result = std::move(_tmp);

  // === Step 3) Attach the freshly computed result to grad_fn, push into autograd history ===
  if (grad_fn) {
    set_history(flatten_tensor_args(result), grad_fn);   // result.grad_fn = grad_fn
  }
  return result;
}

Line by line:

  1. compute_requires_grad(self, other): checks whether any input tensor requires_grad and we're not under torch.no_grad(). In our scenario both inputs require grad → true.
  2. Build the AddBackward0 node: this is a codegen-generated Node subclass (its apply() shown in §5.8). set_next_edges sets self.grad_fn and other.grad_fn as the downstream edges of AddBackward0; backward propagates gradients out along these two edges. alpha, self_scalar_type, other_scalar_type are the "context" needed by the backward formula, stored on the node.
  3. at::AutoDispatchBelowADInplaceOrView guard;: an RAII object that on construction modifies TLS, pushing all autograd functionality bits + the ADInplaceOrView bit into the exclude set. From this line until guard destruction, no dispatcher call goes through the autograd layer.
  4. at::redispatch::add(ks & c10::after_autograd_keyset, ...): at::redispatch::add is another codegen-generated entry (in RedispatchFunctions.h), differing from at::add only in taking an extra DispatchKeySet argument that it forwards to Dispatcher::redispatch. after_autograd_keyset is a precompiled constant mask that "clears all autograd-and-above bits." Equivalently, it explicitly tells the dispatcher: jump to backend next.
  5. set_history(result, grad_fn): attaches the new node to the output's autograd history. Python can then observe AddBackward0 through result.grad_fn.
For this generated wrapper, the responsibilities are to prepare a backward node, redispatch to a lower-priority implementation, and attach the result to autograd history. The numerical work for add resides in the backend implementation. Different backends register their corresponding autograd entries, so this should not be read as a guarantee that every backend shares one wrapper symbol.

6.6 The CUDA backend wrapper

at::redispatch::add hands control to Dispatcher::redispatch. This time AutogradCUDA has been cleared from the bitmap (doubly insured by guard and after_autograd_keyset), and highestPriorityTypeId() returns CUDA.

The generated RegisterCUDA.cpp contains separate wrappers for the functional, in-place, and out variants:

TORCH_LIBRARY_IMPL(aten, CUDA, m) {
  m.impl("add.Tensor", TORCH_FN(wrapper_CUDA_add_Tensor));
  m.impl("add_.Tensor", TORCH_FN(wrapper_CUDA_add__Tensor));
  m.impl("add.out",    TORCH_FN(wrapper_CUDA_add_out_out));
}

structured_delegate: add.out makes the variants share a structured meta/impl definition; it does not make the functional wrapper call the out wrapper. register_dispatch_key.py expands a template for each variant. The functional control flow is approximately:

at::Tensor wrapper_CUDA_add_Tensor(
    const at::Tensor& self, const at::Tensor& other, const at::Scalar& alpha) {
  structured_add_out_functional op;
  op.meta(self, other, alpha);
  op.impl(self, other, alpha, op.outputs_[0]);
  return std::move(op.outputs_[0]);
}

meta() establishes TensorIterator, output properties, and the functional output; impl() performs the numerical work. The out wrapper instead wraps the caller-provided tensor and retrieves it through maybe_get_output(0). This pseudocode follows the v2.12.0 template; generated class and member names can change.

How the three wrappers differ The functional wrapper manages a new output, the in-place wrapper uses self as the structured output, and the out wrapper uses the caller's tensor. Each invokes meta() and impl(); the shared unit is the structured implementation, not a wrapper-to-wrapper call. 
at::Tensor& wrapper_CUDA_add__Tensor(
    at::Tensor& self, const at::Tensor& other, const at::Scalar& alpha) {
  structured_add_out_inplace op(self);
  op.meta(self, other, alpha);
  op.impl(self, other, alpha, op.maybe_get_output(0));
  return self;
}

6.7 Structured kernel and ufunc

All three wrappers eventually enter the same generated structured impl(). The out variant illustrates the wrapper shape:

at::Tensor& wrapper_CUDA_add_out_out(
    const at::Tensor& self, const at::Tensor& other, const at::Scalar& alpha,
    at::Tensor& out) {
  structured_add_out_out op(out);            // instantiate the structured kernel class
  op.meta(self, other, alpha);               // Phase 1: meta: compute output shape/dtype, set up TensorIterator
  op.impl(self, other, alpha, op.maybe_get_output(0));   // Phase 2: impl: the real computation
  return out;
}

Structured kernels split "the algorithm" into two standardized phases:

  1. meta(): broadcasts shape, determines dtype, initializes the TensorIterator. The caller provides an output tensor (possibly empty or already allocated); meta decides the expected output shape from the inputs and resizes if needed.
  2. impl(): numerical computation. Reads the TensorIterator for element-wise iterators and runs the actual algorithm.

The CUDA ufunc generator is implemented in torchgen/dest/ufunc.py. It emits a dtype-dispatched kernel, dispatch-stub registration, and a direct call from the structured impl(). The control flow is approximately:

// build/.../UfuncCUDA_add.cu (simplified)
void add_kernel(TensorIteratorBase& iter, const Scalar& alpha) {
  AT_DISPATCH_SWITCH(iter.common_dtype(), "add_cuda",
    AT_DISPATCH_CASE(..., [&] {
      gpu_kernel(iter, CUDAFunctor_add<scalar_t>(/* alpha */));
    })
  );
}

REGISTER_DISPATCH(add_stub, &add_kernel)

TORCH_IMPL_FUNC(add_out)(const Tensor& self, const Tensor& other,
                         const Scalar& alpha, const Tensor& result) {
  add_kernel(*this, alpha);
}

There are two layers of dispatch here:

  1. Dispatcher key selection chooses the CUDA backend wrapper, handling device, layout, modes, and autograd dimensions.
  2. AT_DISPATCH_SWITCH then selects a template instance from iter.common_dtype(). dtype is not a DispatchKey, so this specialization happens inside the backend implementation.

gpu_kernel receives TensorIterator and a generated functor, then launches the elementwise CUDA kernel. The functor's operator() calls at::native::ufunc::add; codegen also emits special handling for CPU scalar operands. The scalar definition is in ATen/native/ufunc/add.h:

// aten/src/ATen/native/ufunc/add.h
template <typename T>
C10_HOST_DEVICE C10_ALWAYS_INLINE T add(T self, T other, T alpha) {
  return self + alpha * other;
}
The numerical definition reduces to self + alpha * other. The surrounding layers handle schemas, key selection, autograd, output preparation, dtype specialization, and kernel launch. This is the v2.12.0 path for add, not a claim that every ATen operator uses ufunc codegen.
Example 5.7: shared ufunc::add for CPU and CUDA ufunc/add.h uses C10_HOST_DEVICE, PyTorch's wrapper for CUDA __host__ __device__, so the scalar function can generate both host and device code.

The CPU-side UfuncCPU_add.cpp includes the same header and drives the function through SIMD-vectorized vectorized_loop2d; the CUDA side uses gpu_kernel. The execution drivers differ, while both paths share the scalar mathematical definition.

After the CUDA kernel completes, control returns through the generated impl(), the functional wrapper, Dispatcher::redispatch, and the autograd wrapper. Then:

  1. The guard destructs; TLS exclude is restored (subsequent top-level calls compute a clean bitmap again).
  2. set_history(result, grad_fn) attaches the backward node to the result.
  3. Control returns through Dispatcher::call, at::_ops::add_Tensor::call, at::add, and THPVariable_add; the result is then wrapped as a Python torch.Tensor and returned to the caller.

Forward complete. z is in hand, with its .grad_fn set to AddBackward0.

6.8 Backward: AddBackward0::apply

The subsequent z.sum().backward() call starts the autograd engine (torch/csrc/autograd/engine.cpp):

  1. Starting from the loss root edge, GraphTask tracks each node's unsatisfied dependencies.
  2. A node enters a ready queue when its dependency count reaches zero; a worker then invokes Node::apply(grads).
  3. Returned gradients travel along next_edges, and contributions to the same input slot are merged before that node runs.

For our AddBackward0::apply, codegen produces (in build/.../generated/Functions.cpp):

variable_list AddBackward0::apply(variable_list&& grads) {
  auto& grad = grads[0];                                          // upstream-incoming dz
  variable_list grad_inputs(2);                                    // two inputs, two gradients

  if (should_compute_output(0)) {                                  // does self need a grad?
    grad_inputs[0] = handle_r_to_c(self_scalar_type, grad);
    // translated from derivatives.yaml:  self: handle_r_to_c(self.scalar_type(), grad)
  }

  if (should_compute_output(1)) {                                  // does other need a grad?
    grad_inputs[1] = handle_r_to_c(other_scalar_type,
                                   maybe_multiply(grad, alpha.conj()));
    // translated from derivatives.yaml:  other: handle_r_to_c(other.scalar_type(),
    //                                     maybe_multiply(grad, alpha.conj()))
  }

  return grad_inputs;
}

Compare with the backward formula copied in §6.1:

self:  handle_r_to_c(self.scalar_type(),  grad)
other: handle_r_to_c(other.scalar_type(), maybe_multiply(grad, alpha.conj()))

The generated code preserves the formula's operation structure while adding output-demand checks, saved-variable access, and template-provided type handling. It is not a character-by-character copy of the YAML text.

Note a few details:

  • should_compute_output(i): determines whether the corresponding edge requires a gradient; it is not limited to leaf tensors.
  • maybe_multiply(grad, alpha.conj()): when alpha == 1, it can return grad directly and avoid an unnecessary multiply.
  • handle_r_to_c: handles the "real tensor → complex grad" edge case (projects to the real part); for real arithmetic this is essentially a no-op.
  • No at::redispatch: sub-operations in the backward formula (e.g. at::mul inside maybe_multiply) directly use the top-level at::* API. They themselves traverse the full dispatcher, gaining "run on CUDA, record in backward graph" capabilities. This means the backward automatically supports higher-order derivatives: differentiating AddBackward0::apply a second time has the inner at::mul build a new MulBackward0.

After grad_inputs returns, the engine follows next_edges. Non-leaf inputs point to the backward node that created them. A leaf that requires gradients has no grad_fn, but its downstream edge targets an internal AccumulateGrad node, which updates the leaf's .grad.

7.3 Teaching helper for computed tables: PythonDispatcher

from torch._python_dispatcher import PythonDispatcher

dispatcher = PythonDispatcher()
print(dispatcher.rawRegistrations())
print(dispatcher.computedTable())

torch._python_dispatcher.PythonDispatcher is a simplified computed-table teaching tool. It does not single-step real C++ dispatch or capture a call's full TLS and tensor key sets.

8. Version boundaries of older references

The dispatcher API and key representation have changed across PyTorch releases. The following table maps common terms from older material to the v2.12.0 terminology used here.

When old articles sayToday's equivalent / difference
"First device/layout, then dtype, two-pass dispatch" (ezyang 2019)Today's dispatcher has many functionality layers; device/layout is one part of the selection. dtype is switched inside the backend kernel by AT_DISPATCH_* (§6.7)
AutoNonVariableTypeMode (common in 2020 articles)Equivalent to AutoDispatchBelowAutograd. The old name is kept as an alias
No BackendComponent split (all pre-2022 references)After the 2022 refactor, AutogradCUDA = (AutogradFunctionality, CUDABit) two-dim combination, no longer a standalone enum value (§1.4)
VariableTensorId= Autograd (alias) / AutogradCPU/AutogradCUDA (concrete)
DefaultBackend= CompositeExplicitAutograd (alias name retained)
Autocast (no backend suffix)= AutocastCUDA (concrete) / alias retained
m.impl_UNBOXED("name", &fn)Removed. Use m.impl("name", TORCH_FN(fn)) or another typed callable. makeFromBoxedFunction wraps the boxed ABI and is not equivalent (§3.6)

Versioned reading rule: the function table, autograd wrappers, and redispatch model provide a useful guide to the source, while API names, key names, and bitmap representation vary by release. Concrete interfaces should be checked against the source and documentation for the target PyTorch version; the links and conclusions in this article follow the version boundary stated at the beginning.
