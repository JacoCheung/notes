CUDA Named Barrier：CTA 内分组同步、指令语义与 Occupancy 约束

Named barrier 是 CTA 内由编号标识的硬件 rendezvous。它允许若干完整 warp 在同一个 CTA 中独立同步，也支持 producer 只发出到达信号而不等待。与存放在 shared memory 中的 mbarrier 不同，named barrier 使用有限的 CTA barrier 资源，因此可能直接限制一个 SM 能同时驻留的 block 数。

0. Named barrier 在同步层级中的位置

一个 CTA 最常见的同步原语是 __syncthreads()。它要求整个 block 到达同一点，适合所有线程共同完成 shared-memory tile 的生产与消费。问题出现在 warp specialization：同一 CTA 的不同 warp 承担不同角色，producer 负责搬运，consumer 负责计算。此时让全部 warp 在每个阶段都执行 __syncthreads()，会把本可重叠的工作重新串行化。

PTX 为 CTA 提供 0 到 15 共 16 个逻辑 barrier ID。每个 ID 表示一条独立的同步通道；指令还可以给出本轮预计到达的线程数。这个线程数必须是 warp size 的整数倍，因此 named barrier 的自然粒度是完整 warp，而不是任意 lane 集合。

PTX 中的 16 个 ID 是每个 CTA 各自拥有的逻辑命名空间。它不等于“整个 SM 只有 16 个 barrier”。SM 还有一组有限的物理 barrier 容量，编译器根据 kernel 的 barrier 用量为每个 resident CTA 分配资源。

1. 到达、等待与复用

Named barrier 的一次同步称为一个 phase 或 generation。硬件为该 generation 统计到达线程数；达到预设值后，等待者被释放，barrier 自动复位，可以立即进入下一轮。

PTX当前线程是否计入 arrival当前线程是否等待用途
bar.sync id, count是是到达并等待本轮完成
bar.arrive id, count是否发出到达信号后继续执行
bar.red.* id, count, pred是是同步并对参与线程的 predicate 做规约

sync 的完整语义是 arrive and wait，不存在单独的 wait。假设两个 producer warp 执行 arrive，两个 consumer warp 执行 sync，那么 barrier 的参与线程数应为：

\[ N_{\mathrm{arrival}} = 2\times32 + 2\times32 =128. \]

若错误地把 count 写成 64，producer 的两个 warp 到达后 barrier 已经完成；consumer 随后执行的 sync 会落入下一代 barrier，语义随即错位。CuTe DSL 的 NamedBarrier.wait() 也会转发到 arrive_and_wait()，原因正是 named barrier 没有独立的纯等待操作。

同步完成还建立参与线程之间的 CTA 内存顺序。Producer 在 arrival 之前写入 shared memory，consumer 从 matching barrier 返回后可以读取这些数据。它不是跨 CTA 的可见性协议，也不能代替 cluster 或 device scope 的同步。

2. 分组同步解决什么问题

下面的 CTA 有四个 warp。W0、W1 写 shared-memory tile，W2、W3 消费 tile。两个 barrier 分别表达“数据已就绪”和“缓冲区可重用”。Producer 发出 arrive 后可以继续做独立的地址计算或下一次 global-memory 预取；只有在覆盖缓冲区前才等待 consumer。

双 named barrier 的 producer-consumer 协议

Named barrier 常用于 warp-specialized GEMM、transpose、epilogue，以及少量固定 warp group 之间的控制交接。收益来自更小的同步集合和单向 arrival：不相关的 warp 无须停在全 CTA barrier 上，producer 也能把部分工作与 consumer 计算重叠。

3. 为什么 named barrier 会限制 occupancy

一个 block 驻留到 SM 之前，硬件必须一次性为它准备执行期间需要的静态资源，包括 warp slot、寄存器、shared memory、block slot 和 barrier 状态。Named barrier 的逻辑 ID 需要对应的 arrival 计数、等待 warp 和 generation 状态。这些状态由有限的片上资源承载，不会因为某条 barrier 指令暂时没有执行就借给另一个 CTA。

若一个 kernel 为每个 CTA 分配 $H_{\mathrm{CTA}}$ 份 barrier 资源，而该 SM 可提供 $H_{\mathrm{SM}}$，仅由 barrier 给出的 resident block 上限为：

\[ B_{\mathrm{barrier}} = \left\lfloor \frac{H_{\mathrm{SM}}}{H_{\mathrm{CTA}}} \right\rfloor. \]

最终 occupancy 仍由所有资源上限的最小值决定：

\[ B_{\mathrm{resident}} = \min\left( B_{\mathrm{warp}}, B_{\mathrm{block}}, B_{\mathrm{register}}, B_{\mathrm{smem}}, B_{\mathrm{barrier}} \right). \]

Nsight Compute 用以下 launch metrics 暴露这部分信息：

Metric含义阅读方式
launch__barrier_count该 kernel launch 的编译期 barrier 用量查看每 CTA 被分配了多少 barrier 资源
launch__occupancy_limit_barriers只考虑 barrier 时允许的 resident blocks/SM与其他 launch__occupancy_limit_* 取最小值
launch__occupancy_per_barrier_countbarrier count 变化时的 occupancy 曲线用于分析减少 barrier 是否能提高驻留度
 
ncu --metrics \
  launch__barrier_count,\
  launch__occupancy_limit_barriers,\
  launch__occupancy_per_barrier_count \
  ./named_barrier_example

NCU Occupancy Calculator 的输入项叫 num_block_barriers，设备侧容量叫 block_barriers_per_sm。后者与架构有关，不应拿某一代 GPU 的数值套到所有设备上。最可靠的判断来自目标 GPU 上的 NCU 结果，而不是只数源码里出现了几个 barrier ID。

Barrier occupancy limiter 与 Stall Barrier 是两件事。前者是 kernel launch 时的静态准入限制；后者表示 warp 在执行期间等待同步。一个 kernel 可以被寄存器限制 occupancy，却在运行时产生大量 barrier stall；也可以因为 barrier 资源降低 residency，但各 warp 几乎不等待。

Barrier ID 使用立即数时，编译器通常能精确得到需要的 ID 集合。若 ID 来自运行时寄存器，后端可能采取更保守的资源分配。这个行为受架构和工具链版本影响，应使用 nvcc --resource-usage、-Xptxas=-v 与 NCU 交叉确认。对固定协议而言，把 ID 保持为编译期常量也更容易审计。

4. PTX 与 SASS 指令

现代 PTX 使用 barrier.cta.* 拼写；历史更久、仍然常见的别名是 bar.*。两组语法表达的是 CTA named barrier，而不是 memory-backed mbarrier。

操作PTX常见 SASS 家族说明
Arrive and waitbar.sync id, count
barrier.cta.sync id, count		BAR.SYNC当前线程到达并等待
Arrive onlybar.arrive id, count
barrier.cta.arrive id, count		BAR.ARRIVE当前线程到达后继续执行
Predicate reductionbar.red.and/or/popcBAR.RED.*同步并规约 predicate
Warp barrierbar.warp.sync maskWARPSYNC只在一个 warp 内同步，不属于 CTA named barrier
 
bar.sync 1, 128;                 // legacy spelling, implicitly aligned
bar.arrive 2, 128;

barrier.cta.sync 1, 128;        // modern CTA spelling
barrier.cta.arrive 2, 128;

.aligned 要求同一 warp 的线程一致执行相同 barrier 指令。Warp-specialized 分支通常由 threadIdx.x / 32 决定，分支在 warp 内是一致的；若控制流无法满足 aligned 条件，应使用目标架构支持的 non-aligned barrier.cta.* 形式。无论使用哪种形式，参与数量和每代到达次数都必须匹配，否则可能死锁或跨代错位。

SASS 是架构相关的最终机器码，具体修饰符和操作数显示会随 GPU 与反汇编器变化。可以用下列命令确认实际 lowering：

nvcc -arch=sm_90 -lineinfo -Xptxas=-v named_barrier.cu -o named_barrier
cuobjdump --dump-sass named_barrier | grep -E 'BAR|WARPSYNC'

# 或直接查看 cubin
nvdisasm named_barrier.cubin | grep -E 'BAR|WARPSYNC'

BSYNC 是控制流 reconvergence barrier，DEPBAR 用于指令依赖管理。它们虽也带有 barrier 字样，却不等同于 CTA named barrier；分析 occupancy 的 barrier count 时不应把所有包含 BAR 的 SASS 一概相加。

5. Named barrier 出现前后的同步方式

Named barrier 并不是 Hopper 新增的能力。PTX 1.0 已有无显式 thread count 的 bar.sync；PTX 2.0 加入 register operand、thread count、bar.arrive 与 bar.red，这些扩展要求 sm_20 或更高。PTX 6.0 增加 barrier 拼写，PTX 7.8 再补上显式 .cta qualifier。

在只有全 CTA rendezvous 的写法里，producer-consumer 通常有两种选择：

  • 使用 __syncthreads()，让无关 warp 一同等待。代码简单，但破坏角色间的工作重叠。
  • 在 shared/global memory 中维护 flag，配合 atomic、memory fence 与 spin loop。它能表达单向信号，却更容易写错内存顺序，也会产生轮询流量。

Named barrier 把 arrival counter 和等待队列变成硬件管理的 CTA 内协议。后来出现的 mbarrier 又向前一步：barrier 本身成为 shared-memory 对象，具有 phase/token，可以跟踪异步 transaction completion，更适合 cp.async、TMA 和多 stage pipeline。

需求优先机制理由
一个 warp 内交换数据__syncwarp(mask)作用域最小，不占 CTA named-barrier 通道
整个 CTA 共同完成一个阶段__syncthreads()语义直接，参与者不易算错
固定的完整 warp group 之间同步Named barrier可命名多个通道，支持 non-blocking arrival
异步 copy/TMA 完成通知或多 stage pipelinecuda::barrier / mbarrier支持 phase、token 与 transaction count
跨 CTA 协作Cluster barrier、cluster mbarrier 或全局协议Named barrier 的作用域严格限制在 CTA

6. CUDA C/C++：使用 inline PTX

CUDA 没有一个与 PTX named barrier 完全一一对应的常用 C intrinsic。最直接的入口是 inline PTX。下面以 128-thread CTA 为例：两个 producer warp 写 shared memory，两个 consumer warp 读取。ID 1 表示 ready，ID 2 表示 empty。

// named_barrier.cu
#include <cuda_runtime.h>

__device__ __forceinline__ void arrive_ready() {
  asm volatile("barrier.cta.arrive 1, 128;" ::: "memory");
}

__device__ __forceinline__ void wait_ready() {
  // sync also contributes an arrival.
  asm volatile("barrier.cta.sync 1, 128;" ::: "memory");
}

__device__ __forceinline__ void arrive_empty() {
  asm volatile("barrier.cta.arrive 2, 128;" ::: "memory");
}

__device__ __forceinline__ void wait_empty() {
  asm volatile("barrier.cta.sync 2, 128;" ::: "memory");
}

__global__ void producer_consumer(const int* input, int* output) {
  __shared__ int tile[64];

  int tid = threadIdx.x;
  int warp = tid / 32;

  if (warp < 2) {
    tile[tid] = input[tid];
    arrive_ready();

    // Work independent of tile reuse can overlap consumer computation.
    int next_index = tid + blockDim.x;
    asm volatile("" :: "r"(next_index));

    wait_empty();
  } else {
    wait_ready();
    int lane_in_group = tid - 64;
    output[lane_in_group] = 2 * tile[lane_in_group];
    arrive_empty();
  }
}

这里四个 warp 都参与 ID 1 和 ID 2 的每一代同步，所以 count 都是 128。两条分支按 warp ID 划分，warp 内没有 divergence。示例只演示一次交接；循环复用时，双方必须以相同顺序进入下一代 barrier。

把 barrier ID 或 count 封装成运行时参数虽然语法允许，却可能让编译器更保守地分配 barrier 资源。固定协议应优先使用字面量或模板常量，并在目标 GPU 上核对 launch__barrier_count。

7. CUTLASS C++：cutlass::arch::NamedBarrier

CUTLASS 在 include/cutlass/arch/barrier.h 中封装了 named barrier。当前 main 分支保留硬件 ID 1 到 7 供库内部使用；面向用户的构造函数会把 user ID 加 8，因此 user ID 0 到 7 映射到硬件 ID 8 到 15。ID 0 还可能与 __syncthreads() 冲突，不应自行复用。PTX named barrier 的历史远早于 Hopper，但这份 CUTLASS wrapper 当前只在 CUDA 12 及 sm_90+ 目标上启用。

#include <cutlass/arch/barrier.h>

__global__ void cutlass_named_barrier(const int* input, int* output) {
  __shared__ int tile[64];

  int tid = threadIdx.x;
  int warp = tid / 32;

  // user IDs 0 and 1 currently map to hardware IDs 8 and 9.
  cutlass::arch::NamedBarrier ready(128, 0);
  cutlass::arch::NamedBarrier empty(128, 1);

  if (warp < 2) {
    tile[tid] = input[tid];
    ready.arrive_unaligned();

    // Independent producer work.

    empty.arrive_and_wait_unaligned();
  } else {
    ready.arrive_and_wait_unaligned();
    int lane_in_group = tid - 64;
    output[lane_in_group] = 2 * tile[lane_in_group];
    empty.arrive_unaligned();
  }
}

示例在 warp-role 分支内调用 barrier，因此使用 *_unaligned() 版本。若整个 CTA 在同一控制流位置执行同一条 barrier 指令，可以使用 arrive() 或 arrive_and_wait()。CUTLASS 的 sync() 只是 arrive_and_wait() 的别名，并不是纯等待。

库内部的 ReservedNamedBarriers 枚举说明了这些 slot 的实际用途，包括 epilogue、transpose、Stream-K、tensor-memory allocation 和部分 mainloop 协议。向已有 CUTLASS kernel 插入自定义 barrier 时，应使用用户构造函数，避免直接占用内部 ID。

8. CuTe DSL：pipeline.NamedBarrier

CuTe DSL 在 cutlass.pipeline 中提供 NamedBarrier。与 CUTLASS C++ 用户构造函数不同，这里的 barrier_id 是直接的硬件 ID，范围为 0 到 15；当前实现会对 ID 0 发出警告。

import cutlass.cute as cute
import cutlass.pipeline as pipeline

@cute.kernel
def producer_consumer(input_tensor, output_tensor):
    tid = cute.arch.thread_idx()[0]
    warp = cute.arch.make_warp_uniform(cute.arch.warp_idx())

    ready = pipeline.NamedBarrier(barrier_id=1, num_threads=128)
    empty = pipeline.NamedBarrier(barrier_id=2, num_threads=128)

    if warp < 2:
        # Write the shared-memory tile.
        ready.arrive_unaligned()

        # Independent producer work.

        empty.wait_unaligned()       # arrive and wait, not a pure wait
    else:
        ready.wait_unaligned()       # arrive and wait
        # Read the shared-memory tile and compute.
        empty.arrive_unaligned()

wait_unaligned() 的命名容易让人误以为它只等待。源码会明确告警并把它路由到 arrive-and-wait 语义，因此这里的 num_threads 仍是 producer 与 consumer 的总和 128。CUTLASS 官方的 TMA transpose 教程也使用 pipeline.NamedBarrier 协调固定 warp group。

需要直接控制底层形式时，可以使用 CuTe arch wrapper：

cute.arch.barrier_arrive(
    barrier_id=1,
    number_of_threads=128,
    aligned=False,
)

cute.arch.barrier(
    barrier_id=1,
    number_of_threads=128,
)

aligned=False 会选择 non-aligned barrier.cta.arrive 路径。CuTe DSL 接口仍在演进，实际工程应固定 CUTLASS revision，并链接相同 revision 的源码，而不是只依赖类名相似。

9. 正确性与性能检查

  1. 确认作用域。Named barrier 只能同步同一 CTA；跨 CTA 必须换用 cluster 或全局协议。
  2. 按每一代计算 arrival。执行 sync、wait 的线程也计入 count。
  3. 保持 warp-uniform。参与线程数必须是 32 的倍数，同一 warp 不应让部分 lane 绕过 aligned barrier。
  4. 保证调用次数对称。循环中的 producer 与 consumer 必须按相同 generation 反复使用 barrier。
  5. 管理 ID 所有权。不要与 __syncthreads()、CUTLASS 内部协议或其他库代码复用同一硬件 ID。
  6. 分别看静态与动态指标。用 launch__occupancy_limit_barriers 判断驻留限制，用 Warp State Statistics 判断实际等待。
  7. 比较替代方案。若协议需要 transaction completion、phase token 或大量 pipeline stage，memory-backed mbarrier 通常更合适。

Named barrier 的代价来自它表达的状态，而不只是执行一条 BAR 指令。使用较少的 barrier ID、让 ID 保持编译期可见、减少不必要的独立 rendezvous，可能提高 resident block 数；但把多个逻辑阶段强行复用同一 ID，也会引入额外依赖和死锁风险。最终应以协议正确性为前提，再结合 NCU 判断 barrier 是否真的处在 occupancy 的最小项。
