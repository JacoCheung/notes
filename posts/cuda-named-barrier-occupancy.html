CUDA Named Barrier：CTA 内分组同步与 Occupancy 约束

一个 warp-specialized CTA 同时包含搬运 shared-memory tile 的 producer warps 和执行计算的 consumer warps。两组 warp 必须在“数据就绪”和“buffer 可复用”两个时刻交接，同时让其他角色继续执行独立工作。__syncwarp() 覆盖一个 warp 内的 lanes，__syncthreads() 覆盖整个 CTA；固定的跨 warp 子集需要介于两者之间的同步范围。PTX named barrier 提供这种范围：它用 CTA 内编号、按 generation 复用的同步状态协调完整 warp group，而编译后的 barrier 用量还会进入 block 驻留资源模型。

0. Named barrier 在同步层级中的位置

PTX named barrier 是 CTA 作用域、由 ID 选择的同步状态。每个 CTA 有 0 到 15 共 16 个逻辑 ID，每个 ID 独立维护一条同步通道。一次 generation 从 barrier 初始化或上一代完成后的重新初始化开始；当该 ID 记录的 arrival 达到指令给出的 thread count 时，本代完成、等待者被释放，barrier 随后进入下一代。

Thread count 以线程为单位，并且必须是 warp size 的整数倍，因此 named barrier 协调的是完整 warp group。执行 arrive 的 warp 贡献 arrival 后继续执行；执行 sync 的 warp 同样贡献 arrival，并等待本代完成。CTA scope、ID、generation 与 arrival completion 共同构成 named barrier 的操作模型。

这 16 个 ID 构成每个 CTA 的逻辑命名空间。SM 级资源关系以 NCU 报告的 barrier count 和 barrier occupancy limit 为操作边界；公开资料没有披露对应状态阵列的大小、编码和分配电路。

1. 到达、等待与复用

ID 区分并行存在的同步通道，generation 则区分同一通道上先后发生的 rendezvous。程序必须让所有参与 warp 以一致顺序进入各代；named barrier 本身不向程序暴露 phase token。

PTX执行 warp 是否贡献 arrival是否等待其他参与 warp用途
bar.sync id, count是是到达并等待本轮完成
bar.arrive id, count是否发出到达信号后继续执行
bar.red.* id, count, pred是是同步并对参与线程的 predicate 做规约

同一 active barrier 的一代协议必须选择一致的操作族。PTX 将 barrier.red 与 sync 或 arrive 混用定义为不可预测行为；需要 predicate 规约时，所有参与者都应执行 matching barrier.red。

指令里的 count 以线程为单位，但硬件按 warp 记录到达。执行 barrier 的线程先与同一 warp 中尚未退出的线程会合，随后该 warp 的到达才被计入；显式 count 因而必须是 warp size 的整数倍。这里不能把单个 lane 当作可独立到达的参与者。

sync 的完整语义是 arrive and wait，不存在单独的 wait。假设两个 producer warp 执行 arrive，两个 consumer warp 执行 sync，那么 barrier 的参与线程数应为：

\[ N_{\mathrm{arrival}} = 2\times32 + 2\times32 =128. \]

若错误地把 count 写成 64，producer 的两个 warp 到达后 barrier 已经完成；consumer 随后执行的 sync 会落入下一代 barrier，语义随即错位。CuTe DSL 的 NamedBarrier.wait() 也会转发到 arrive_and_wait()，原因正是 named barrier 没有独立的纯等待操作。

同步完成还建立参与线程之间的 CTA 内存顺序。Producer 在 arrival 之前写入 shared memory，consumer 从 matching barrier 返回后可以读取这些数据。它不是跨 CTA 的可见性协议，也不能代替 cluster 或 device scope 的同步。

2. 分组同步协议

下面的 CTA 有四个 warp。W0、W1 写 shared-memory tile，W2、W3 消费 tile。两个 barrier 分别表达“数据已就绪”和“缓冲区可重用”。Producer 发出 arrive 后可以继续做独立的地址计算或下一次 global-memory 预取；只有在覆盖缓冲区前才等待 consumer。

双 named barrier 的 producer-consumer 协议

Named barrier 常用于 warp-specialized GEMM、transpose、epilogue，以及少量固定 warp group 之间的控制交接。收益来自更小的同步集合和单向 arrival：不相关的 warp 无须停在全 CTA barrier 上，producer 也能把部分工作与 consumer 计算重叠。

3. Named barrier 的 occupancy 约束

前两节描述了一个 CTA 在运行时如何使用 barrier generation 完成交接。多个 CTA 同时驻留在 SM 上时，每个 CTA 所需的 barrier 状态还参与 block 准入，因此编译后的 named-barrier 用量成为静态资源约束。PTX 规定 arrival、等待与自动重新初始化语义；NCU Occupancy Calculator 提供每 CTA barrier 用量和目标设备 barrier 容量。下面以这组公开接口建立 occupancy 模型，不延伸到尚未公开的物理存储与分配电路。

若用 $H_{\mathrm{CTA}}$ 表示 profiler 采用的每 CTA barrier 用量，用 $H_{\mathrm{SM}}$ 表示目标设备在该模型中的容量，那么 barrier 单项给出的 resident block 上限可写成：

\[ B_{\mathrm{barrier}} = \left\lfloor \frac{H_{\mathrm{SM}}}{H_{\mathrm{CTA}}} \right\rfloor. \]

最终 occupancy 仍由所有资源上限的最小值决定：

\[ B_{\mathrm{resident}} = \min\left( B_{\mathrm{warp}}, B_{\mathrm{block}}, B_{\mathrm{register}}, B_{\mathrm{smem}}, B_{\mathrm{barrier}} \right). \]

Nsight Compute 用以下 launch metrics 暴露这部分信息：

Metric含义阅读方式
launch__barrier_countNCU 为该 kernel launch 报告的 barrier 数作为 occupancy 模型的每 block barrier 用量读取
launch__occupancy_limit_barriers由已用 barrier 数造成的 occupancy limit与其他 launch__occupancy_limit_* 一起判断实际最小项
launch__occupancy_per_barrier_countbarrier count 变化时的 occupancy 曲线用于分析减少 barrier 是否能提高驻留度

  launch__barrier_count,\
  launch__occupancy_limit_barriers,\
  launch__occupancy_per_barrier_count \
  ./named_barrier_example

NCU Occupancy Calculator 的输入项叫 num_block_barriers，设备侧容量叫 block_barriers_per_sm。后者与架构有关，不应拿某一代 GPU 的数值套到所有设备上。最可靠的判断来自目标 GPU 上的 NCU 结果，而不是只数源码里出现了几个 barrier ID。

静态准入与运行时等待由不同信号描述。launch__occupancy_limit_barriers 给出 kernel launch 时的 resident-block 上限；Stall Barrier 表示 warp 在执行期间等待同步。一个 kernel 可以由寄存器决定 occupancy，同时产生大量 barrier stall；也可以由 barrier 资源降低 residency，而运行时等待很少。

PTX 允许 barrier ID 使用立即数或寄存器，这条规则描述指令如何选择逻辑通道；目标 GPU 上的 launch__barrier_count 才给出 occupancy 模型采用的 barrier 用量。nvcc --resource-usage 与 -Xptxas=-v 可补充核对寄存器、shared memory 等其他静态资源。ptxas 如何分配物理 barrier 状态仍在公开证据边界之外，而固定协议使用常量 ID 更便于审计。

4. PTX 拼写、约束与 SASS

Profiler 给出编译后的 barrier 数量，PTX 与 SASS 则说明这些 barrier 执行了哪一种操作。第 1 节中的三种操作各有两组 PTX 拼写：bar.sync、bar.arrive 与 bar.red.* 是 aligned 别名；barrier.cta.sync、barrier.cta.arrive 与 barrier.cta.red.* 提供现代 CTA 形式。它们常分别 lowering 为 BAR.SYNC、BAR.ARRIVE 与 BAR.RED.*。bar.warp.sync / WARPSYNC 的作用域是单个 warp。

.aligned 要求 CTA 中所有线程执行同一条 barrier 指令，条件比 warp 内一致更严格。Warp-role 分支只让部分 warp 执行某条 barrier，因此必须使用 non-aligned barrier.cta.* 形式，并以 sm_70+ 为目标；在 sm_6x 及更早架构上，未写 .aligned 的形式仍按 aligned 处理。无论使用哪种形式，参与数量和每代到达次数都必须匹配，否则可能死锁或跨代错位。

SASS 是架构相关的最终机器码，具体修饰符和操作数显示会随 GPU 与反汇编器变化。可以用下列命令确认实际 lowering：

nvcc -arch=sm_90 -lineinfo -Xptxas=-v named_barrier.cu -o named_barrier
cuobjdump --dump-sass named_barrier | grep -E 'BAR|WARPSYNC'

# 或直接查看 cubin
nvdisasm named_barrier.cubin | grep -E 'BAR|WARPSYNC'

反汇编中的 BAR.SYNC、BAR.ARRIVE 与 BAR.RED.* 对应 CTA named-barrier 操作；BSYNC 表示控制流 reconvergence，DEPBAR 表示指令依赖管理。分析 occupancy barrier count 时应按指令语义分类，而不是按助记符是否包含 BAR 分类。

5. 同步机制选择

PTX 指令语义确定之后，机制选择取决于参与范围和协议所需的状态。Named barrier 是 CTA 内编号通道，适合固定的完整 warp group，并允许 arrival 方继续执行；mbarrier 是 shared memory 中的 64-bit 可寻址对象，带有 phase 与 arrival state，并可在相应架构上跟踪异步 transaction completion。全 CTA 阶段、异步数据移动和跨 CTA 协作分别对应不同作用域的原语。

需求优先机制理由

整个 CTA 共同完成一个阶段__syncthreads()语义直接，参与者不易算错
固定的完整 warp group 之间同步Named barrier可命名多个通道，支持 non-blocking arrival
异步 copy/TMA 完成通知或多 stage pipelinecuda::barrier / mbarrier支持 phase、token 与 transaction count

6. CUDA C/C++：使用 inline PTX

选择 named barrier 后，同一套 ready/empty 协议可以直接写成 inline PTX。示例以 sm_70+ 为目标，因为 warp-role 分支需要 non-aligned 形式。这个 128-thread CTA 由两个 producer warp 写 shared memory、两个 consumer warp 读取；ID 1 表示 ready，ID 2 表示 empty。

// named_barrier.cu
#include <cuda_runtime.h>

__device__ __forceinline__ void arrive_ready() {
  asm volatile("barrier.cta.arrive 1, 128;" ::: "memory");
}

__device__ __forceinline__ void wait_ready() {
  // sync also contributes an arrival.
  asm volatile("barrier.cta.sync 1, 128;" ::: "memory");
}

__device__ __forceinline__ void arrive_empty() {
  asm volatile("barrier.cta.arrive 2, 128;" ::: "memory");
}

__device__ __forceinline__ void wait_empty() {
  asm volatile("barrier.cta.sync 2, 128;" ::: "memory");
}

__global__ void producer_consumer(const int* input, int* output) {
  __shared__ int tile[64];

  int tid = threadIdx.x;
  int warp = tid / 32;

  if (warp < 2) {
    tile[tid] = input[tid];
    arrive_ready();

    // Work independent of tile reuse can overlap consumer computation.
    int next_index = tid + blockDim.x;
    asm volatile("" :: "r"(next_index));

    wait_empty();
  } else {
    wait_ready();
    int lane_in_group = tid - 64;
    output[lane_in_group] = 2 * tile[lane_in_group];
    arrive_empty();
  }
}

这里四个 warp 都参与 ID 1 和 ID 2 的每一代同步，所以 count 都是 128。两条分支按 warp ID 划分，warp 内没有 divergence。示例只演示一次交接；循环复用时，双方必须以相同顺序进入下一代 barrier。

7. CUTLASS C++：cutlass::arch::NamedBarrier

CUTLASS 在固定 revision include/cutlass/arch/barrier.h 中封装了 named barrier。该 wrapper 需要 CUDA Toolkit 12+ 和 sm_90+。该版本保留 ID 1 到 7 供库内部使用；面向用户的构造函数会把 user ID 加 8，因此 user ID 0 到 7 映射到最终 ID 8 到 15。源码还提醒 ID 0 可能与 __syncthreads() 冲突。这里描述的是该 revision 的 CUTLASS 策略，不是 PTX 对所有库的约定。

#include <cutlass/arch/barrier.h>

__global__ void cutlass_named_barrier(const int* input, int* output) {
  __shared__ int tile[64];

  int tid = threadIdx.x;
  int warp = tid / 32;

  // user IDs 0 and 1 currently map to hardware IDs 8 and 9.
  cutlass::arch::NamedBarrier ready(128, 0);
  cutlass::arch::NamedBarrier empty(128, 1);

  if (warp < 2) {
    tile[tid] = input[tid];
    ready.arrive_unaligned();

    // Independent producer work.

    empty.arrive_and_wait_unaligned();
  } else {
    ready.arrive_and_wait_unaligned();
    int lane_in_group = tid - 64;
    output[lane_in_group] = 2 * tile[lane_in_group];
    empty.arrive_unaligned();
  }
}

示例在 warp-role 分支内调用 barrier，因此使用 *_unaligned() 版本。若整个 CTA 在同一控制流位置执行同一条 barrier 指令，可以使用 arrive() 或 arrive_and_wait()。CUTLASS 的 sync() 是 arrive_and_wait() 的别名，也会贡献一次 arrival。

库内部的 ReservedNamedBarriers 枚举说明了这些 slot 的实际用途，包括 epilogue、transpose、Stream-K、tensor-memory allocation 和部分 mainloop 协议。向已有 CUTLASS kernel 插入自定义 barrier 时，应使用用户构造函数，避免直接占用内部 ID。

8. CuTe DSL：pipeline.NamedBarrier

同一 revision 的 CuTe DSL 在 cutlass.pipeline 中提供 NamedBarrier。与 CUTLASS C++ 用户构造函数不同，这里的 barrier_id 直接对应 PTX ID，范围为 0 到 15；该实现会对 ID 0 发出警告。

import cutlass.cute as cute
import cutlass.pipeline as pipeline

@cute.kernel
def producer_consumer(input_tensor, output_tensor):
    tid = cute.arch.thread_idx()[0]
    warp = cute.arch.make_warp_uniform(cute.arch.warp_idx())

    ready = pipeline.NamedBarrier(barrier_id=1, num_threads=128)
    empty = pipeline.NamedBarrier(barrier_id=2, num_threads=128)

    if warp < 2:
        # Write the shared-memory tile.
        ready.arrive_unaligned()

        # Independent producer work.

        empty.wait_unaligned()       # arrive and wait, not a pure wait
    else:
        ready.wait_unaligned()       # arrive and wait
        # Read the shared-memory tile and compute.
        empty.arrive_unaligned()

在固定源码中，wait_unaligned() 路由到 arrive-and-wait 语义，并贡献一次 arrival，因此这里的 num_threads 仍是 producer 与 consumer 的总和 128。同 revision 的 TMA transpose 教程也使用 pipeline.NamedBarrier 协调固定 warp group。

需要直接控制底层形式时，可以使用 CuTe arch wrapper：

cute.arch.barrier_arrive(
    barrier_id=1,
    number_of_threads=128,
    aligned=False,
)

cute.arch.barrier(
    barrier_id=1,
    number_of_threads=128,
)

aligned=False 会选择 non-aligned barrier.cta.arrive 路径。CuTe DSL 接口仍在演进，实际工程应固定 CUTLASS revision，并链接相同 revision 的源码，而不是只依赖类名相似。

9. 正确性与性能检查

CUDA、CUTLASS 与 CuTe DSL 最终都必须满足同一套 generation 协议。检查实现时，可以沿作用域、arrival 数量、控制流和资源信号逐项核对：

  1. 确认作用域。Named barrier 只能同步同一 CTA；跨 CTA 必须换用 cluster 或全局协议。
  2. 按每一代计算 arrival。执行 sync 或 wait 的 warp 也贡献 arrival，其线程数必须纳入 count。
  3. 统一操作族。同一 active barrier 上的参与者不能混用 barrier.red 与 sync/arrive。
  4. 满足 aligned 条件。参与线程数必须是 32 的倍数；只有整个 CTA 执行同一 barrier 指令时才使用 aligned 形式。Warp-role 分支应在 sm_70+ 上使用 non-aligned 形式。
  5. 保证调用次数对称。循环中的 producer 与 consumer 必须按相同 generation 反复使用 barrier。
  6. 管理 ID 所有权。不要与 __syncthreads()、CUTLASS 内部协议或其他库代码复用同一硬件 ID。
  7. 分别看静态与动态指标。用 launch__occupancy_limit_barriers 判断驻留限制，用 Warp State Statistics 判断实际等待。

静态 occupancy 代价由编译后的 barrier 用量决定。一次优化只有同时满足两个条件才会提高 resident block 数：目标 GPU 上的 launch__barrier_count 确实下降，并且 barrier 原本就是最紧的资源限制。源码中的 ID 数量只描述协议结构，最终计数仍以 profiler 为准；复用 ID 还必须保持 generation 独立，否则会引入额外依赖或死锁。

CUDA Named Barriers: CTA-Local Synchronization and Occupancy Constraints

A warp-specialized CTA contains producer warps that fill a shared-memory tile and consumer warps that compute from it. The groups must hand off at “data ready” and “buffer reusable” points while unrelated work remains able to proceed. __syncwarp() covers lanes within one warp, whereas __syncthreads() covers the entire CTA; a fixed subset spanning several warps needs a scope between them. PTX named barriers provide that scope through numbered CTA-local state reused across generations, and the compiled barrier usage also participates in block-residency limits.

0. Position in the synchronization hierarchy

A PTX named barrier is CTA-scoped synchronization state selected by an ID. Each CTA has 16 logical IDs, numbered 0 through 15, and each ID maintains an independent synchronization channel. A generation begins when the barrier is initialized or reinitialized after the preceding generation. It completes when the arrivals recorded for that ID reach the instruction's thread count, at which point waiting warps are released and the barrier enters the next generation.

The thread count is expressed in threads and must be a multiple of the warp size, so named barriers coordinate groups of complete warps. A warp executing arrive contributes an arrival and continues; a warp executing sync also contributes an arrival and waits for the generation to complete. CTA scope, ID, generation, and arrival completion together define the operational model.

MechanismScopeParticipantsImplementation and resource modelTypical use
__syncwarp(mask)One warpLanes selected by the maskWarp synchronization stateData exchange within a warp
__syncthreads()CTAThe whole blockCTA barrier resource, normally ID 0Full-CTA shared-memory stages
Named barrierCTASelected full warpsCTA barrier resource in the occupancy modelWarp specialization and group rendezvous

The 16 IDs form a logical namespace for each CTA. The SM-level resource relationship is bounded operationally by the barrier count and barrier occupancy limit reported by Nsight Compute. Public documentation does not disclose the size, encoding, or allocation circuitry of the corresponding physical state.

1. Arrival, waiting, and reuse

An ID distinguishes synchronization channels that coexist, while a generation distinguishes successive rendezvous on one channel. All participating warps must enter those generations in a consistent order; a named barrier does not expose a phase token to the program.

PTXExecuting warp contributes an arrivalWaits for other participating warpsPurpose
bar.sync id, countYesYesArrive and wait for the current phase
bar.arrive id, countYesNoSignal arrival and continue
bar.red.* id, count, predYesYesSynchronize and reduce participant predicates

Each generation on an active barrier must use one consistent operation family. PTX defines mixing barrier.red with sync or arrive on the same active barrier as unpredictable behavior. A predicate-reduction protocol therefore requires every participant to execute the matching barrier.red.

The instruction's count is expressed in threads, but arrival is recorded by warp. Threads executing the barrier first rendezvous with non-exited threads in their warp, after which the warp's arrival is counted. An explicit count must therefore be a multiple of the warp size; individual lanes are not independent participants.

The full meaning of sync is arrive and wait; named barriers do not provide a separate pure wait. If two producer warps execute arrive and two consumer warps execute sync, the participant count is:

\[ N_{\mathrm{arrival}} = 2\times32 + 2\times32 =128. \]

If the count is incorrectly set to 64, the two producer warps complete the barrier before the consumers arrive. A later consumer sync then belongs to the next generation, and the protocol becomes misaligned. CuTe DSL's NamedBarrier.wait() also forwards to arrive_and_wait() because this mechanism has no wait-only operation.

Barrier completion also orders CTA memory operations among participants. A producer can write shared memory before arrival, and a consumer can read that data after returning from the matching barrier. This is not a cross-CTA visibility protocol and cannot replace cluster-scope or device-scope synchronization.

2. Group synchronization protocol

The following CTA contains four warps. W0 and W1 write a shared-memory tile; W2 and W3 consume it. Two barriers represent "data ready" and "buffer reusable." After producers issue arrive, they may continue with independent address calculations or prefetch the next global-memory input. They need to wait only before overwriting the shared buffer.

Producer-consumer protocol with two named barriers

Named barriers commonly appear in warp-specialized GEMM, transpose, epilogue, and control handoffs among a small, fixed set of warp groups. The benefit comes from a smaller synchronization set and one-way arrival. Unrelated warps do not stop at a full-CTA barrier, and producers can overlap some work with consumer computation.

3. Named-barrier occupancy constraints

The first two sections describe how one CTA uses barrier generations to hand work off at runtime. When several CTAs reside on an SM, the barrier state required by each CTA also participates in block admission, which makes compiled named-barrier usage a static resource constraint. PTX specifies arrival, waiting, and automatic reinitialization semantics, while the Nsight Compute Occupancy Calculator provides per-CTA barrier usage and target-device capacity. The occupancy model below stays within those public interfaces and does not extend to undisclosed storage or allocation circuitry.

Let $H_{\mathrm{CTA}}$ be the profiler's per-CTA barrier usage and $H_{\mathrm{SM}}$ the corresponding capacity for the target device. The barrier resource alone gives the following resident-block limit:

\[ B_{\mathrm{barrier}} = \left\lfloor \frac{H_{\mathrm{SM}}}{H_{\mathrm{CTA}}} \right\rfloor. \]

Final occupancy is still determined by the minimum of all resource limits:

\[ B_{\mathrm{resident}} = \min\left( B_{\mathrm{warp}}, B_{\mathrm{block}}, B_{\mathrm{register}}, B_{\mathrm{smem}}, B_{\mathrm{barrier}} \right). \]

Nsight Compute exposes this part of the model through the following launch metrics:

MetricMeaningInterpretation
launch__barrier_countThe barrier count reported by NCU for this kernel launchRead it as the per-block barrier usage used by the occupancy model
launch__occupancy_limit_barriersThe occupancy limit imposed by the barriers in useCompare it with other launch__occupancy_limit_* metrics to find the actual minimum
launch__occupancy_per_barrier_countOccupancy as the barrier count changesShows whether reducing barrier usage could increase residency
 
ncu --metrics \
  launch__barrier_count,\
  launch__occupancy_limit_barriers,\
  launch__occupancy_per_barrier_count \
  ./named_barrier_example

The Nsight Compute Occupancy Calculator calls its input num_block_barriers and the device capacity block_barriers_per_sm. The latter is architecture-dependent, so a value from one GPU generation should not be applied to every device. Results collected on the target GPU are more reliable than a count of barrier IDs in source code.

Static admission and runtime waiting use separate signals. launch__occupancy_limit_barriers gives the resident-block limit at kernel launch, while Stall Barrier reports warps waiting for synchronization during execution. Registers may determine a kernel's occupancy even when it has substantial barrier stalls; barrier resources may also reduce residency while runtime waiting remains small.

PTX permits a barrier ID to be an immediate or a register operand; this rule describes how an instruction selects a logical channel. launch__barrier_count on the target GPU supplies the barrier usage consumed by the occupancy model. nvcc --resource-usage and -Xptxas=-v complement it with register, shared-memory, and other static-resource statistics. The physical allocation performed by ptxas remains outside the public evidence boundary, while constant IDs make fixed protocols easier to audit.

4. PTX forms, constraints, and SASS

The profiler reports how many compiled barriers participate in residency; PTX and SASS identify the operations performed by those barriers. The three operations in Section 1 each have two PTX spellings. bar.sync, bar.arrive, and bar.red.* are aligned aliases; barrier.cta.sync, barrier.cta.arrive, and barrier.cta.red.* are the modern CTA forms. They commonly lower to BAR.SYNC, BAR.ARRIVE, and BAR.RED.*, respectively. bar.warp.sync / WARPSYNC has single-warp scope.

The .aligned form requires every thread in the CTA to execute the same barrier instruction, a stronger condition than warp-uniform control flow. A warp-role branch executes a given barrier in only part of the CTA, so it must use a non-aligned barrier.cta.* form and target sm_70+. On sm_6x and earlier targets, a spelling without .aligned is still treated as aligned. In either form, the participant count and number of arrivals per generation must agree. A mismatch can deadlock the CTA or shift participants into different generations.

SASS is architecture-specific machine code, so modifiers and displayed operands vary with the GPU and disassembler. The following commands show the actual lowering:

nvcc -arch=sm_90 -lineinfo -Xptxas=-v named_barrier.cu -o named_barrier
cuobjdump --dump-sass named_barrier | grep -E 'BAR|WARPSYNC'

# Or inspect a cubin directly
nvdisasm named_barrier.cubin | grep -E 'BAR|WARPSYNC'

In disassembly, BAR.SYNC, BAR.ARRIVE, and BAR.RED.* implement CTA named-barrier operations; BSYNC represents control-flow reconvergence, and DEPBAR manages instruction dependencies. Interpret an occupancy barrier count by instruction semantics rather than by whether a mnemonic contains BAR.

5. Choosing a synchronization mechanism

Once the instruction semantics are clear, mechanism selection follows from participant scope and the state required by the protocol. A named barrier is a numbered CTA-local channel for fixed groups of complete warps and permits an arriving group to continue. An mbarrier is an addressable 64-bit object in shared memory with phase and arrival state, and it can track asynchronous transaction completion on architectures that provide the corresponding operations. Full-CTA phases, asynchronous data movement, and cross-CTA cooperation map to primitives with different scopes.

RequirementPreferred mechanismReason
Exchange data within one warp__syncwarp(mask)It has the narrowest scope and uses no CTA named-barrier channel
Complete one phase across an entire CTA__syncthreads()The semantics are direct and participant counts are hard to misstate
Synchronize fixed groups of complete warpsNamed barrierSeveral channels can be named, and arrival need not block
Signal asynchronous copy or TMA completion, or build a multistage pipelinecuda::barrier / mbarrierSupports phases, tokens, and transaction counts
Coordinate across CTAsCluster barrier, cluster mbarrier, or a global protocolA named barrier is strictly CTA-local

6. CUDA C/C++ with inline PTX

Once a named barrier is selected, the ready/empty protocol can be written directly with inline PTX. The example targets sm_70+ because the warp-role branches require non-aligned forms. The 128-thread CTA assigns two producer warps to write shared memory and two consumer warps to read it. ID 1 denotes ready; ID 2 denotes empty.

// named_barrier.cu
#include <cuda_runtime.h>

__device__ __forceinline__ void arrive_ready() {
  asm volatile("barrier.cta.arrive 1, 128;" ::: "memory");
}

__device__ __forceinline__ void wait_ready() {
  // sync also contributes an arrival.
  asm volatile("barrier.cta.sync 1, 128;" ::: "memory");
}

__device__ __forceinline__ void arrive_empty() {
  asm volatile("barrier.cta.arrive 2, 128;" ::: "memory");
}

__device__ __forceinline__ void wait_empty() {
  asm volatile("barrier.cta.sync 2, 128;" ::: "memory");
}

__global__ void producer_consumer(const int* input, int* output) {
  __shared__ int tile[64];

  int tid = threadIdx.x;
  int warp = tid / 32;

  if (warp < 2) {
    tile[tid] = input[tid];
    arrive_ready();

    // Work independent of tile reuse can overlap consumer computation.
    int next_index = tid + blockDim.x;
    asm volatile("" :: "r"(next_index));

    wait_empty();
  } else {
    wait_ready();
    int lane_in_group = tid - 64;
    output[lane_in_group] = 2 * tile[lane_in_group];
    arrive_empty();
  }
}

All four warps participate in every generation of ID 1 and ID 2, so both counts are 128. Branches are selected by warp ID and do not diverge within a warp. The example performs one handoff. In a loop, both sides must enter successive generations in the same order.

7. CUTLASS C++: cutlass::arch::NamedBarrier

CUTLASS wraps named barriers in include/cutlass/arch/barrier.h at revision ffa119a. This wrapper requires CUDA Toolkit 12 or later and sm_90+. That revision reserves IDs 1 through 7 for internal use. The public constructor adds 8 to a user ID, so user IDs 0 through 7 map to final IDs 8 through 15. The source also warns that ID 0 may conflict with __syncthreads(). This is a policy of that CUTLASS revision, not a universal PTX convention.

#include <cutlass/arch/barrier.h>

__global__ void cutlass_named_barrier(const int* input, int* output) {
  __shared__ int tile[64];

  int tid = threadIdx.x;
  int warp = tid / 32;

  // user IDs 0 and 1 currently map to hardware IDs 8 and 9.
  cutlass::arch::NamedBarrier ready(128, 0);
  cutlass::arch::NamedBarrier empty(128, 1);

  if (warp < 2) {
    tile[tid] = input[tid];
    ready.arrive_unaligned();

    // Independent producer work.

    empty.arrive_and_wait_unaligned();
  } else {
    ready.arrive_and_wait_unaligned();
    int lane_in_group = tid - 64;
    output[lane_in_group] = 2 * tile[lane_in_group];
    empty.arrive_unaligned();
  }
}

The barrier calls occur inside warp-role branches, so the example uses the *_unaligned() methods. When an entire CTA executes the same barrier instruction at one control-flow point, arrive() or arrive_and_wait() is appropriate. CUTLASS sync() is an alias for arrive_and_wait() and contributes an arrival.

The library's ReservedNamedBarriers enumeration shows where internal slots are used, including epilogues, transpose, Stream-K, tensor-memory allocation, and several mainloop protocols. Custom synchronization added to an existing CUTLASS kernel should use the public constructor instead of directly claiming an internal ID.

8. CuTe DSL: pipeline.NamedBarrier

At the same revision, CuTe DSL exposes NamedBarrier through cutlass.pipeline. Unlike the CUTLASS C++ public constructor, its barrier_id maps directly to a PTX ID from 0 through 15. The implementation warns when ID 0 is selected.

import cutlass.cute as cute
import cutlass.pipeline as pipeline

@cute.kernel
def producer_consumer(input_tensor, output_tensor):
    tid = cute.arch.thread_idx()[0]
    warp = cute.arch.make_warp_uniform(cute.arch.warp_idx())

    ready = pipeline.NamedBarrier(barrier_id=1, num_threads=128)
    empty = pipeline.NamedBarrier(barrier_id=2, num_threads=128)

    if warp < 2:
        # Write the shared-memory tile.
        ready.arrive_unaligned()

        # Independent producer work.

        empty.wait_unaligned()       # arrive and wait, not a pure wait
    else:
        ready.wait_unaligned()       # arrive and wait
        # Read the shared-memory tile and compute.
        empty.arrive_unaligned()

In the pinned source, wait_unaligned() routes to arrive-and-wait semantics and contributes an arrival. The num_threads value therefore remains the total of the producer and consumer participants, 128. The TMA transpose tutorial at the same revision also uses pipeline.NamedBarrier to coordinate fixed warp groups.

CuTe arch wrappers expose the lower-level forms when direct control is needed:

cute.arch.barrier_arrive(
    barrier_id=1,
    number_of_threads=128,
    aligned=False,
)

cute.arch.barrier(
    barrier_id=1,
    number_of_threads=128,
)

aligned=False selects the non-aligned barrier.cta.arrive path. CuTe DSL interfaces continue to evolve, so production code should pin a CUTLASS revision and link documentation to that same revision instead of relying on similar class names across releases.

9. Correctness and performance checks

CUDA, CUTLASS, and CuTe DSL ultimately obey the same generation protocol. An implementation can be checked in order across scope, arrival count, control flow, and resource signals:

  1. Confirm the scope. A named barrier synchronizes only one CTA. Cross-CTA protocols require cluster or global synchronization.
  2. Count arrivals for every generation. Warps executing sync or wait also contribute arrivals, so their threads belong in the count.
  3. Use one operation family. Participants on the same active barrier must not mix barrier.red with sync/arrive.
  4. Satisfy the aligned condition. The participant count must be a multiple of 32. Use an aligned form only when the entire CTA executes the same barrier instruction; use a non-aligned form on sm_70+ for warp-role branches.
  5. Keep call counts symmetric. Producers and consumers in a loop must reuse each barrier through matching generations.
  6. Manage ID ownership. Do not reuse an ID already claimed by __syncthreads(), a CUTLASS protocol, or another library component.
  7. Separate static and dynamic metrics. Use launch__occupancy_limit_barriers for residency limits and Warp State Statistics for runtime waiting.

Static occupancy cost follows the compiled barrier usage. An optimization can increase resident block count only when it lowers launch__barrier_count on the target GPU and barriers were already the tightest resource limit. Source-level ID count describes protocol structure; the profiler supplies the compiled count. Any ID reuse must also preserve independent generations, or it can introduce extra dependencies or deadlock.
