CUDA Named Barrier：CTA 内分组同步与 Occupancy 约束

一个 CTA 反复处理 shared memory 中的 tile：producer warps 搬入数据，consumer warps 读取并计算。只保护第一次读取还不够。Producer 处理下一块数据时，还必须知道 consumer 已经用完上一块，否则同一块 shared memory 会被提前覆盖。Named barrier 可以把这两次交接分别命名，让发出到达信号的一方继续执行独立工作。读懂这样的循环，需要先跟踪 buffer 的使用权，再计算每个 barrier 的参与人数。

1. 一块 shared buffer 的两次交接

设一个 CTA 有四个 warp：W0、W1 是 producer，负责写入 64 个 float；W2、W3 是 consumer，负责读取这些值并将两倍的结果写回 global memory。所有轮次共用同一个 tile[64]。这段计算很简单，目的是把 buffer 的交接完整地展现出来。

Consumer 开始读之前，需要等 producer 写完，这次交接叫 ready。Consumer 读完之后，需要通知 producer 可以覆盖 buffer，这次交接叫 reuse。两个方向保护的是不同的内存访问：ready 保护读到新数据，reuse 保护旧数据在读取结束前不被破坏。

PTX named barrier 是同一 CTA 内由 ID 选择的同步状态，ID 范围为 0 到 15。对这个循环，令 ID 1 表示 ready，ID 2 表示 reuse。barrier.cta.arrive记录到达后允许执行 warp 继续前进；barrier.cta.sync既记录到达，也等待其他参与者。因此 producer 在 ready 上 arrive、在 reuse 上 sync，consumer 则反过来。

Ready 与 reuse 的循环交接

四个 warp 在这个例子中都参与同步，展示的是 arrival 与等待的分离。Producer 发出 ready 后，可以把下一轮输入先读到寄存器中，同时 consumer 读取当前 shared tile；只有再次写入 tile 之前，producer 才必须经过 reuse。对于更大的 CTA，同样的协议也可以只覆盖指定的完整 warp 组，让其他角色继续工作。

2. 将 ready/reuse 写进一个循环

下面给出完整的 device-side 示例。使用 CUDA 13.1.1 编译，目标为 sm_70+，按 <<<1, 128>>>启动。input 与 output 是互不重叠的设备 buffer，各至少容纳 num_tiles * 64 个 float。Host 端的分配、初始化和计时不在这段 kernel 中；这里没有声称已测得并行收益。

// named_barrier.cu
#include <cuda_runtime.h>

__device__ __forceinline__ void ready_arrive() {
  asm volatile("barrier.cta.arrive 1, 128;" ::: "memory");
}
__device__ __forceinline__ void ready_sync() {
  asm volatile("barrier.cta.sync 1, 128;" ::: "memory");
}
__device__ __forceinline__ void reuse_arrive() {
  asm volatile("barrier.cta.arrive 2, 128;" ::: "memory");
}
__device__ __forceinline__ void reuse_sync() {
  asm volatile("barrier.cta.sync 2, 128;" ::: "memory");
}

// Launch with <<<1, 128>>>. Each buffer holds num_tiles * 64 floats.
__global__ void producer_consumer(const float* input, float* output,
                                  int num_tiles) {
  __shared__ float tile[64];
  const int tid = threadIdx.x;
  const int warp = tid / 32;

  if (num_tiles <= 0) return;  // Uniform across the CTA.

  if (warp < 2) {
    float next_value = input[tid];
    for (int t = 0; t < num_tiles; ++t) {
      tile[tid] = next_value;
      ready_arrive();

      // Fetch into a register while consumers read the shared tile.
      if (t + 1 < num_tiles)
        next_value = input[size_t(t + 1) * 64 + tid];

      reuse_sync();          // Shared tile is now safe to overwrite.
    }
  } else {
    const int rank = tid - 64;
    for (int t = 0; t < num_tiles; ++t) {
      ready_sync();          // Also contributes an arrival.
      output[size_t(t) * 64 + rank] = 2.0f * tile[rank];
      reuse_arrive();         // No further reads of this tile.
    }
  }
}

按第 $t$ 轮跟踪这段代码，producer 先把 next_value 写入 tile，然后到达 ready。Consumer 的 ready sync 完成后才能读取 tile。此时 producer 的下一次 global load 写入自己的寄存器，不覆盖 shared memory，因此可以与 consumer 的读取并行。Consumer 到达 reuse 后不再读取当前 tile，producer 的 reuse sync 完成后才能进入下一轮并覆盖它。

循环结束后的预期结果是每个元素满足 $output[i]=2\times input[i]$，同一位置的 shared-memory 存储在各轮之间反复使用。最后一轮仍完成 reuse 交接，所有参与 warp 的调用次数保持一致；num_tiles <= 0 的返回在整个 CTA 上一致，不会留下其他 warp 等待。

Warp-role 分支中的指令约束

两个分支按 warp ID 划分，一个 warp 的所有 lanes 执行相同路径。它们却没有让整个 CTA 执行同一条 barrier 指令，因此示例使用不带 .aligned 的 barrier.cta.*。bar.sync 和 bar.arrive 是 aligned 别名，不能在这里直接替换。PTX 对 sm_6x 及更早目标还保留 aligned 限制，所以本例要求 sm_70+。这些控制流和内存顺序要求见 PTX 13.1.1 的 barrier 定义。

Inline PTX 中的 "memory" clobber 告诉编译器该语句影响内存访问排序，barrier 指令本身则提供参与线程之间的硬件同步。读写通过同一 CTA 的 matching barrier 建立顺序；跨 CTA 的数据交接需要其他同步机制。

3. 到达计数与下一代 barrier

ready 的参与者包括两组 warp。Producer 的 arrive 贡献 64 个线程，consumer 的 sync 也贡献 64 个线程，所以指令中的 count 为：

\[ N_{\mathrm{ready}}=2\times32+2\times32=128. \]

reuse 只是交换了谁 arrive、谁 sync，参与人数仍为 128。这个 count 的单位是线程，显式给出时必须为 warp size 的整数倍。PTX 的 barrier 指令会先让执行线程与同 warp 中尚未退出的线程会合，再记录 warp 的到达；不能把一个 lane 当作独立的跨 warp 参与者。

同一个 ID 如何区分各轮

当一代 barrier 的 arrival 达到要求时，等待者继续执行，barrier 自动重新初始化，供下一代使用。程序不持有 named barrier 的 phase token，而是通过双方一致的调用顺序维持代际关系。上面的循环每轮都按 ready、reuse 的顺序推进；reuse 阻止 producer 提前覆盖 buffer，下一轮 ready 又阻止 consumer 提前读取。

若把 ready 的 count 错写成 64，一种可能的顺序是两个 producer warp 先到达，立即完成本代。随后 consumer 的 sync 就进入下一代，原本要配对的两组参与者被拆开了。其他交错也可能过早释放部分参与者。程序需要的是四个 warp 的一次交接，所以 count 必须包含执行 sync 的线程。

这也解释了部分 wrapper 的命名：CuTe DSL 的 NamedBarrier.wait() 仍然会 arrive。把它当作 mbarrier 的纯等待接口，会少算 consumer 的参与人数。具体 API 路由列在附录 B。

ID 所有权与协议复用

同一 CTA 的 16 个 ID 是同步通道的逻辑命名空间。将 ready 和 reuse 分配给两个 ID，双方才可以在不同方向上推进。循环重复使用 ID 1，并不会为每轮再消耗一个新 ID；但两个独立协议若同时使用 ID 1，就会把彼此的 arrival 混在一起。

需要复用 ID 时，应先证明上一代已经完成，且所有角色对下一代的顺序一致。直接把 ready 与 reuse 合并以减少 ID，必须重新设计并证明协议。库代码也会占用 ID：__syncthreads() 通常使用 ID 0，CUTLASS 还保留若干内部 ID，插入新同步点前需要核对最终使用的编号。

4. 从两条同步通道到 block 驻留

一个 CTA 在循环中重复使用 barrier 状态；多个 CTA 同时进入 SM 时，则各自需要独立的状态。这部分用量也会进入静态 occupancy 计算。程序中使用 ID 1 和 ID 2，描述的是协议设计；编译器为 kernel 记录了多少 barrier 资源，需要从 launch 数据读取。

记每 CTA 的已编译 barrier 用量为 $H_{\mathrm{CTA}}$，目标设备在 occupancy 模型中的容量为 $H_{\mathrm{SM}}$，barrier 单项可允许的 block 数用下面的容量模型理解：

\[ B_{\mathrm{barrier}}=\left\lfloor\frac{H_{\mathrm{SM}}}{H_{\mathrm{CTA}}}\right\rfloor,\qquad B_{\mathrm{resident}}=\min\left(B_{\mathrm{warp}},B_{\mathrm{block}},B_{\mathrm{register}},B_{\mathrm{smem}},B_{\mathrm{barrier}}\right). \]

这里各个 $B$ 都以 block 为单位。完整的驻留资源分析见 GPU Occupancy 的驻留资源模型。设备的 barrier 容量随架构变化；PTX 的 16 个逻辑 ID 并不直接给出 SM 的物理状态数量。

Metric含义
launch__barrier_countKernel launch 报告的 barrier 用量
launch__occupancy_limit_barriersBarrier 资源允许的 resident blocks
launch__occupancy_per_barrier_countBarrier count 变化时的 active warp 数

这三项名称来自 NCU 2025.3 Launch Metrics。Occupancy Calculator的对应输入为 num_block_barriers，设备容量字段为 block_barriers_per_sm。先读取实际 kernel 的数据，再判断减少 barrier 是否能跨过驻留数量的整数边界。

# Run the application that launches the kernel.
ncu --metrics \
  launch__barrier_count,\
  launch__occupancy_limit_barriers,\
  launch__occupancy_per_barrier_count \
  ./named_barrier_example

驻留受限与等待时间是两件事

launch__occupancy_limit_barriers回答资源最多允许驻留几个 block。运行中的 Stall Barrier 则表示 warp 正在等待同步。在这个 producer/consumer 循环里，如果两组工作量不平衡，快的一组可能花很多时间等慢的一组，即便最终 occupancy 由寄存器限制。

减少 barrier 资源用量，也不必然增加驻留：容量整除后的 block 数可能没变，其他资源也可能接替成为限制项。若一次调整把 barrier limiter 从两个 block 提高到四个，而寄存器只允许三个，最终只能驻留三个。之后是否更快，还要比较 kernel 时间以及两组 warp 的等待情况。

5. 验证一次交接，再验证整个循环

这段代码的正确性依赖两条顺序：写 tile 必须先于 consumer 读取，consumer 的读取必须先于下一次覆盖。检查时可以先用一轮输入确认结果，再用两轮不同的数据覆盖同一个 buffer，最后扩大轮数，检查所有输出。任何一组 warp 的提前退出、不同循环次数或不一致 count，都会破坏这两条顺序。

把协议接入已有 kernel 后，还需要核对 ID 是否与库内部同步冲突，并查看生成的 PTX/SASS 是否保留了预期操作。若要评估收益，用相同输入和计时条件比较原同步方案与新方案，同时记录 compiled barrier count、其他 occupancy limiter 和运行时等待。对这个四 warp 示例，收益候选是 producer 的寄存器预取与 consumer 工作重叠；能否实现、重叠多少，需要实际测量。

当数据搬运改成 TMA 或需要跟踪异步事务完成时，协议还会增加 arrival 以外的完成条件。此时可以继续阅读 TMA 与 mbarrier 内环。Named barrier 的 ready/reuse 设计仍能帮助厘清 buffer 生命周期，但实际完成通知应由所选异步机制承担。

附录 A：CUTLASS C++ 的 ID 映射

CUTLASS 在固定 revision include/cutlass/arch/barrier.h 中封装了 named barrier。该 wrapper 需要 CUDA Toolkit 12+ 和 sm_90+。该版本保留 ID 1 到 7 供库内部使用；面向用户的构造函数会把 user ID 加 8，因此 user ID 0 到 7 映射到最终 ID 8 到 15。源码还提醒 ID 0 可能与 __syncthreads() 冲突。这里描述的是该 revision 的 CUTLASS 策略，不是 PTX 对所有库的约定。

下面只展开一轮交接，用来对照 wrapper 调用。按128线程启动，输入输出各至少64个元素，ready/empty 对应正文的 ready/reuse。

#include <cutlass/arch/barrier.h>

__global__ void cutlass_named_barrier(const float* input, float* output) {
  __shared__ float tile[64];

  int tid = threadIdx.x;
  int warp = tid / 32;

  // user IDs 0 and 1 currently map to hardware IDs 8 and 9.
  cutlass::arch::NamedBarrier ready(128, 0);
  cutlass::arch::NamedBarrier empty(128, 1);

  if (warp < 2) {
    tile[tid] = input[tid];
    ready.arrive_unaligned();

    // Independent producer work.

    empty.arrive_and_wait_unaligned();
  } else {
    ready.arrive_and_wait_unaligned();
    int lane_in_group = tid - 64;
    output[lane_in_group] = 2.0f * tile[lane_in_group];
    empty.arrive_unaligned();
  }
}

示例在 warp-role 分支内调用 barrier，因此使用 *_unaligned() 版本。若整个 CTA 在同一控制流位置执行同一条 barrier 指令，可以使用 arrive() 或 arrive_and_wait()。CUTLASS 的 sync() 是 arrive_and_wait() 的别名，也会贡献一次 arrival。

库内部的 ReservedNamedBarriers 枚举说明了这些 slot 的实际用途，包括 epilogue、transpose、Stream-K、tensor-memory allocation 和部分 mainloop 协议。向已有 CUTLASS kernel 插入自定义 barrier 时，应使用用户构造函数，避免直接占用内部 ID。

附录 B：CuTe DSL 的到达与等待接口

同一 revision 的 CuTe DSL 在 cutlass.pipeline 中提供 NamedBarrier。与 CUTLASS C++ 用户构造函数不同，这里的 barrier_id 直接对应 PTX ID，范围为 0 到 15；该实现会对 ID 0 发出警告。

以下是协议伪代码：保留真实 API 调用，省略 shared-memory tensor 的分配、数据读写和 host launch；它不能单独作为完整 kernel 运行。

import cutlass.cute as cute
import cutlass.pipeline as pipeline

@cute.kernel
def producer_consumer(input_tensor, output_tensor):
    tid = cute.arch.thread_idx()[0]
    warp = cute.arch.make_warp_uniform(cute.arch.warp_idx())

    ready = pipeline.NamedBarrier(barrier_id=1, num_threads=128)
    empty = pipeline.NamedBarrier(barrier_id=2, num_threads=128)

    if warp < 2:
        # Write the shared-memory tile.
        ready.arrive_unaligned()

        # Independent producer work.

        empty.wait_unaligned()       # arrive and wait, not a pure wait
    else:
        ready.wait_unaligned()       # arrive and wait
        # Read the shared-memory tile and compute.
        empty.arrive_unaligned()

在固定源码中，wait_unaligned() 路由到 arrive-and-wait 语义，并贡献一次 arrival，因此这里的 num_threads 仍是 producer 与 consumer 的总和 128。同 revision 的 TMA transpose 教程也使用 pipeline.NamedBarrier 协调固定 warp group。

需要直接控制底层形式时，可以使用 CuTe arch wrapper：

cute.arch.barrier_arrive(
    barrier_id=1,
    number_of_threads=128,
    aligned=False,
)

cute.arch.barrier(
    barrier_id=1,
    number_of_threads=128,
)

aligned=False 会选择 non-aligned barrier.cta.arrive 路径。CuTe DSL 接口仍在演进，实际工程应固定 CUTLASS revision，并链接相同 revision 的源码，而不是只依赖类名相似。

附录 C：同步机制的选择

PTX 指令语义确定之后，机制选择取决于参与范围和协议所需的状态。Named barrier 是 CTA 内编号通道，适合固定的完整 warp group，并允许 arrival 方继续执行；mbarrier 是 shared memory 中的 64-bit 可寻址对象，带有 phase 与 arrival state，并可在相应架构上跟踪异步 transaction completion。全 CTA 阶段、异步数据移动和跨 CTA 协作分别对应不同作用域的原语。

需求优先机制理由
一个 warp 内交换数据__syncwarp(mask)作用域最小，不占 CTA named-barrier 通道
整个 CTA 共同完成一个阶段__syncthreads()语义直接，参与者不易算错
固定的完整 warp group 之间同步Named barrier可命名多个通道，支持 non-blocking arrival
异步 copy/TMA 完成通知或多 stage pipelinecuda::barrier / mbarrier支持 phase、token 与 transaction count
跨 CTA 协作Cluster barrier、cluster mbarrier 或全局协议Named barrier 的作用域严格限制在 CTA

附录 D：PTX 操作与 SASS 检查

barrier.cta.arrive贡献 arrival 后继续执行，barrier.cta.sync贡献 arrival 并等待；barrier.cta.red.*还会对参与者的 predicate 做规约。同一 active barrier 上可以按协议配对 arrive 与 sync，但不能再混入 red，PTX 将后者定义为不可预测行为。

bar.sync、bar.arrive 和 bar.red.*分别是带 .aligned 的别名。Aligned 要求整个 CTA 执行同一条 barrier 指令，不能只检查 warp 内是否一致。Barrier ID 可以是立即数或寄存器，固定协议使用常量 ID 更便于核对所有权。

正文文件包含 device code，可以先生成 cubin，再检查实际 SASS。它没有 host main()，因此这里使用 -cubin：

nvcc -arch=sm_90 -lineinfo -cubin named_barrier.cu -o named_barrier.cubin
nvdisasm named_barrier.cubin | rg 'BAR|WARPSYNC'

CTA barrier 常对应 BAR.SYNC、BAR.ARRIVE 和 BAR.RED.*；单 warp 的 bar.warp.sync 对应 WARPSYNC。BSYNC用于控制流 reconvergence，DEPBAR用于指令依赖管理。实际编码随目标架构变化，按 CUDA Binary Utilities 的指令分类读结果，不能把含有 BAR 字符的指令都算成 named-barrier 资源。

CUDA Named Barriers: CTA-Local Synchronization and Occupancy Constraints

A CTA repeatedly processes tiles in shared memory: producer warps fill the buffer and consumer warps read it to compute. Protecting the first read is only half the protocol. Before producing the next tile, the producers must also know that consumers have finished using the previous one. Otherwise, they overwrite data still being read. Named barriers can give these handoffs separate names and let an arriving group continue independent work. Understanding the loop starts with buffer ownership, followed by the participant count at each barrier.

1. Two handoffs for one shared buffer

Consider a CTA with four warps. W0 and W1 produce a tile of 64 floats; W2 and W3 read it and write twice each value to global memory. Every iteration reuses the same tile[64]. The calculation is deliberately simple so the complete buffer handoff remains visible.

Consumers must wait for producer writes before reading; call this handoff ready. Once they finish reading, consumers must let producers overwrite the buffer; call that handoff reuse. Each protects a different access: ready makes the new data available to readers, while reuse keeps old data intact until those reads finish.

A PTX named barrier is synchronization state selected by an ID within one CTA. IDs range from 0 through 15. Assign ID 1 to ready and ID 2 to reuse. barrier.cta.arrive records arrival and allows the warp to continue; barrier.cta.sync records arrival and waits for the other participants. Producers therefore arrive at ready and synchronize at reuse, while consumers do the reverse.

A repeating ready/reuse handoff

All four warps participate in this example, which demonstrates the separation of arrival from waiting. After signaling ready, producers can fetch the next input into registers while consumers read the current shared tile. Producers need to complete reuse only before their next shared-memory write. In a larger CTA, the same protocol can cover a selected set of complete warps while unrelated roles continue working.

2. A loop with ready and reuse barriers

The complete device-side example below uses CUDA 13.1.1, targets sm_70+, and is launched with <<<1, 128>>>. The device buffers input and output do not overlap and each contains at least num_tiles * 64 floats. Host allocation, initialization, and timing are outside the kernel; no overlap speedup is claimed here.

// named_barrier.cu
#include <cuda_runtime.h>

__device__ __forceinline__ void ready_arrive() {
  asm volatile("barrier.cta.arrive 1, 128;" ::: "memory");
}
__device__ __forceinline__ void ready_sync() {
  asm volatile("barrier.cta.sync 1, 128;" ::: "memory");
}
__device__ __forceinline__ void reuse_arrive() {
  asm volatile("barrier.cta.arrive 2, 128;" ::: "memory");
}
__device__ __forceinline__ void reuse_sync() {
  asm volatile("barrier.cta.sync 2, 128;" ::: "memory");
}

// Launch with <<<1, 128>>>. Each buffer holds num_tiles * 64 floats.
__global__ void producer_consumer(const float* input, float* output,
                                  int num_tiles) {
  __shared__ float tile[64];
  const int tid = threadIdx.x;
  const int warp = tid / 32;

  if (num_tiles <= 0) return;  // Uniform across the CTA.

  if (warp < 2) {
    float next_value = input[tid];
    for (int t = 0; t < num_tiles; ++t) {
      tile[tid] = next_value;
      ready_arrive();

      // Fetch into a register while consumers read the shared tile.
      if (t + 1 < num_tiles)
        next_value = input[size_t(t + 1) * 64 + tid];

      reuse_sync();          // Shared tile is now safe to overwrite.
    }
  } else {
    const int rank = tid - 64;
    for (int t = 0; t < num_tiles; ++t) {
      ready_sync();          // Also contributes an arrival.
      output[size_t(t) * 64 + rank] = 2.0f * tile[rank];
      reuse_arrive();         // No further reads of this tile.
    }
  }
}

In iteration $t$, producers first write next_value into tile and arrive at ready. Consumers can read only after their ready sync completes. The producers' next global load writes a private register rather than shared memory, so it can overlap the consumer reads. Consumers stop reading the current tile before arriving at reuse. Producers complete their reuse sync before the next iteration overwrites that tile.

After the loop, the expected result is $output[i]=2\times input[i]$ for every element, despite reusing the same shared-memory locations each iteration. The final iteration also completes the reuse handoff, keeping the call counts consistent across participating warps. The return for num_tiles <= 0 is uniform across the CTA and leaves no other warp waiting.

Instruction constraints inside warp-role branches

The branches use warp ID, so all lanes of a warp take the same path. The entire CTA does not execute the same barrier instruction, however, so the example uses barrier.cta.* without .aligned. The spellings bar.sync and bar.arrive are aligned aliases and cannot simply replace them here. Targets sm_6x and earlier retain the aligned restrictions, hence the sm_70+ requirement. These control-flow and memory-ordering rules are specified by PTX 13.1.1.

The inline-PTX "memory" clobber tells the compiler that the statement affects memory ordering; the barrier instruction provides hardware synchronization among participants. Matching barriers establish the ordering within this CTA. Cross-CTA handoffs require a different synchronization mechanism.

3. Count arrivals and track the next generation

Both groups participate in ready. Producer arrivals contribute 64 threads, and consumer sync operations contribute another 64, giving:

\[ N_{\mathrm{ready}}=2\times32+2\times32=128. \]

Reuse exchanges the arriving and waiting roles but still has 128 participants. The explicit count is in threads and must be a multiple of the warp size. PTX barrier instructions first rendezvous with non-exited threads in the executing warp, then record the warp's arrival. An individual lane is not an independent participant in this cross-warp protocol.

How one ID distinguishes successive iterations

When a generation reaches its required arrivals, waiters resume and the barrier automatically reinitializes for reuse. The program does not hold a phase token for a named barrier. It keeps generations matched through a consistent call order. Every iteration above proceeds through ready and reuse: reuse prevents an early producer overwrite, and the next ready prevents an early consumer read.

Setting the ready count incorrectly to 64 permits an execution in which both producer warps arrive first and complete the generation. Consumers then synchronize on the next generation, separating the groups that were supposed to meet. Other interleavings can release only part of the intended group too early. The protocol requires one handoff among all four warps, so the count must include threads executing sync.

This explains a wrapper naming detail as well: CuTe DSL's NamedBarrier.wait() still arrives. Treating it like an mbarrier wait-only operation would omit consumers from the count. The API mappings are covered in Appendix B.

ID ownership and protocol reuse

The 16 IDs form a logical synchronization namespace for each CTA. Assigning separate IDs to ready and reuse allows the two handoff directions to progress independently. Repeating ID 1 in a loop does not allocate another ID for every iteration. Two independent protocols using ID 1 concurrently, however, would mix their arrivals.

Before reusing an ID, establish that the previous generation has finished and every role agrees on the next generation's order. Combining ready and reuse to save an ID requires a redesigned and revalidated protocol. Library code also uses IDs: __syncthreads() normally uses ID 0, and CUTLASS reserves several internal IDs. Check the final IDs before adding synchronization to existing code.

4. From two synchronization channels to block residency

A CTA reuses its barrier state through the loop. Multiple CTAs entering the same SM need independent state, and this usage participates in static occupancy calculations. IDs 1 and 2 describe the source-level protocol. Launch data tells us how much barrier resource the compiler records for the kernel.

Let $H_{\mathrm{CTA}}$ be compiled barrier usage per CTA and $H_{\mathrm{SM}}$ the target-device capacity in the occupancy model. The capacity relationship can be understood as:

\[ B_{\mathrm{barrier}}=\left\lfloor\frac{H_{\mathrm{SM}}}{H_{\mathrm{CTA}}}\right\rfloor,\qquad B_{\mathrm{resident}}=\min\left(B_{\mathrm{warp}},B_{\mathrm{block}},B_{\mathrm{register}},B_{\mathrm{smem}},B_{\mathrm{barrier}}\right). \]

Each $B$ is measured in blocks. The full resource calculation is developed in GPU Occupancy: Residency Resource Model. Barrier capacity varies by architecture; the 16 logical PTX IDs do not directly specify a physical state count for the SM.

MetricMeaning
launch__barrier_countBarrier usage reported for the kernel launch
launch__occupancy_limit_barriersResident blocks permitted by barrier resources
launch__occupancy_per_barrier_countActive warp counts as barrier usage changes

These names come from NCU 2025.3 Launch Metrics. The Occupancy Calculator calls the input num_block_barriers and the device-capacity field block_barriers_per_sm. Read the actual kernel data before deciding whether a reduction would cross an integer residency boundary.

# Run the application that launches the kernel.
ncu --metrics \
  launch__barrier_count,\
  launch__occupancy_limit_barriers,\
  launch__occupancy_per_barrier_count \
  ./named_barrier_example

Residency limits and runtime waits

launch__occupancy_limit_barriers reports the block residency permitted by barrier resources. Runtime Stall Barrier reports warps waiting for synchronization. If the producer and consumer workloads are unbalanced, the faster group may spend substantial time waiting even while registers determine the kernel's occupancy.

Reducing barrier resource usage need not increase residency. Integer division may still permit the same number of blocks, or another resource may become the limiter. If a change raises the barrier limit from two blocks to four while registers permit three, the final limit becomes three. Whether that improves performance still depends on kernel time and the two groups' waiting behavior.

5. Validate one handoff, then the whole loop

Correctness requires two orderings: tile writes precede consumer reads, and those reads precede the next overwrite. Start with one iteration to check the result, then use two different tiles through the same buffer and finally increase the iteration count while checking every output. Early exits, unequal loop counts, or inconsistent participant counts can break these orderings.

After integrating the protocol into an existing kernel, check for conflicts with library barrier IDs and inspect the expected operations in generated PTX/SASS. To evaluate performance, compare the old and new synchronization schemes under the same inputs and timing conditions. Record compiled barrier count, other occupancy limiters, and runtime waits. In this four-warp example, the possible gain is overlap between producer register prefetches and consumer work; whether that overlap occurs and how much it helps require measurement.

TMA transfers and other asynchronous operations add completion conditions beyond thread arrival. The TMA and mbarrier inner loop develops that protocol. Ready/reuse reasoning still helps establish the buffer lifetime, while the selected asynchronous mechanism must provide the actual completion notification.

Appendix A: CUTLASS C++ ID mapping

CUTLASS wraps named barriers in include/cutlass/arch/barrier.h at revision ffa119a. This wrapper requires CUDA Toolkit 12 or later and sm_90+. That revision reserves IDs 1 through 7 for internal use. The public constructor adds 8 to a user ID, so user IDs 0 through 7 map to final IDs 8 through 15. The source also warns that ID 0 may conflict with __syncthreads(). This is a policy of that CUTLASS revision, not a universal PTX convention.

The example expands one handoff to show the wrapper calls. Launch 128 threads with at least 64 elements in each input/output buffer; ready/empty correspond to the main example's ready/reuse.

#include <cutlass/arch/barrier.h>

__global__ void cutlass_named_barrier(const float* input, float* output) {
  __shared__ float tile[64];

  int tid = threadIdx.x;
  int warp = tid / 32;

  // user IDs 0 and 1 currently map to hardware IDs 8 and 9.
  cutlass::arch::NamedBarrier ready(128, 0);
  cutlass::arch::NamedBarrier empty(128, 1);

  if (warp < 2) {
    tile[tid] = input[tid];
    ready.arrive_unaligned();

    // Independent producer work.

    empty.arrive_and_wait_unaligned();
  } else {
    ready.arrive_and_wait_unaligned();
    int lane_in_group = tid - 64;
    output[lane_in_group] = 2.0f * tile[lane_in_group];
    empty.arrive_unaligned();
  }
}

The barrier calls occur inside warp-role branches, so the example uses the *_unaligned() methods. When an entire CTA executes the same barrier instruction at one control-flow point, arrive() or arrive_and_wait() is appropriate. CUTLASS sync() is an alias for arrive_and_wait() and contributes an arrival.

The library's ReservedNamedBarriers enumeration shows where internal slots are used, including epilogues, transpose, Stream-K, tensor-memory allocation, and several mainloop protocols. Custom synchronization added to an existing CUTLASS kernel should use the public constructor instead of directly claiming an internal ID.

Appendix B: CuTe DSL arrival and wait interfaces

At the same revision, CuTe DSL exposes NamedBarrier through cutlass.pipeline. Unlike the CUTLASS C++ public constructor, its barrier_id maps directly to a PTX ID from 0 through 15. The implementation warns when ID 0 is selected.

The following is protocol pseudocode. It retains the actual API calls but omits shared-memory tensor allocation, data accesses, and the host launch; it is not a complete runnable kernel.

import cutlass.cute as cute
import cutlass.pipeline as pipeline

@cute.kernel
def producer_consumer(input_tensor, output_tensor):
    tid = cute.arch.thread_idx()[0]
    warp = cute.arch.make_warp_uniform(cute.arch.warp_idx())

    ready = pipeline.NamedBarrier(barrier_id=1, num_threads=128)
    empty = pipeline.NamedBarrier(barrier_id=2, num_threads=128)

    if warp < 2:
        # Write the shared-memory tile.
        ready.arrive_unaligned()

        # Independent producer work.

        empty.wait_unaligned()       # arrive and wait, not a pure wait
    else:
        ready.wait_unaligned()       # arrive and wait
        # Read the shared-memory tile and compute.
        empty.arrive_unaligned()

In the pinned source, wait_unaligned() routes to arrive-and-wait semantics and contributes an arrival. The num_threads value therefore remains the total of the producer and consumer participants, 128. The TMA transpose tutorial at the same revision also uses pipeline.NamedBarrier to coordinate fixed warp groups.

CuTe arch wrappers expose the lower-level forms when direct control is needed:

cute.arch.barrier_arrive(
    barrier_id=1,
    number_of_threads=128,
    aligned=False,
)

cute.arch.barrier(
    barrier_id=1,
    number_of_threads=128,
)

aligned=False selects the non-aligned barrier.cta.arrive path. CuTe DSL interfaces continue to evolve, so production code should pin a CUTLASS revision and link documentation to that same revision instead of relying on similar class names across releases.

Appendix C: Choosing a synchronization mechanism

Once the instruction semantics are clear, mechanism selection follows from participant scope and the state required by the protocol. A named barrier is a numbered CTA-local channel for fixed groups of complete warps and permits an arriving group to continue. An mbarrier is an addressable 64-bit object in shared memory with phase and arrival state, and it can track asynchronous transaction completion on architectures that provide the corresponding operations. Full-CTA phases, asynchronous data movement, and cross-CTA cooperation map to primitives with different scopes.

RequirementPreferred mechanismReason
Exchange data within one warp__syncwarp(mask)It has the narrowest scope and uses no CTA named-barrier channel
Complete one phase across an entire CTA__syncthreads()The semantics are direct and participant counts are hard to misstate
Synchronize fixed groups of complete warpsNamed barrierSeveral channels can be named, and arrival need not block
Signal asynchronous copy or TMA completion, or build a multistage pipelinecuda::barrier / mbarrierSupports phases, tokens, and transaction counts
Coordinate across CTAsCluster barrier, cluster mbarrier, or a global protocolA named barrier is strictly CTA-local

Appendix D: PTX operations and SASS inspection

barrier.cta.arrive contributes an arrival and continues, while barrier.cta.sync contributes an arrival and waits. barrier.cta.red.* also reduces participant predicates. A protocol can pair arrive and sync on the same active barrier, but must not mix red into it; PTX defines that mixture as unpredictable.

bar.sync, bar.arrive, and bar.red.* are aliases with .aligned. Aligned requires the entire CTA to execute the same barrier instruction; warp-uniform control flow alone is insufficient. IDs can be immediate or register operands, while constants make ownership easier to check in a fixed protocol.

The main example contains device code, so generate a cubin before inspecting SASS. It has no host main(); the command therefore uses -cubin:

nvcc -arch=sm_90 -lineinfo -cubin named_barrier.cu -o named_barrier.cubin
nvdisasm named_barrier.cubin | rg 'BAR|WARPSYNC'

CTA barriers commonly appear as BAR.SYNC, BAR.ARRIVE, and BAR.RED.*; single-warp bar.warp.sync corresponds to WARPSYNC. BSYNC handles control-flow reconvergence, while DEPBAR manages instruction dependencies. Encoding varies by target architecture. Use the classifications in CUDA Binary Utilities; a mnemonic containing BAR does not by itself identify a named-barrier resource.
