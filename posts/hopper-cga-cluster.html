Hopper Thread Block Cluster 的执行语义：DSMEM、Cluster Barrier 与跨 CTA TMA

CUDA kernel 通常由彼此独立的 thread block 组成，每个 block 拥有自己的 shared memory，并由硬件在可用 SM 上调度。需要交换 tile 或同步阶段的算法若跨越 block 边界，往往要借助 global memory、原子操作或额外的 kernel launch。Compute Capability 9.0 引入 Thread Block Cluster，在 block 之上增加一个 CUDA 可见的协作层级：若干 CTA 被组织为 cluster，共调度到同一个 GPC，并可使用 cluster-scope 同步和 distributed shared memory。

版本口径：本文以 CUDA C++ Programming Guide 12.6.3、PTX ISA 8.5 和 Hopper（Compute Capability 9.0）为准。文中只把公开文档定义的行为作为保证；资源分派、路由和地址转换的内部实现均视为未公开。

能力对应 CUDA / PTX 原语编程语义
Distributed Shared Memorycluster.map_shared_rank() / PTX mapa访问同一 cluster 中其它 CTA 的 shared memory
Cluster barriercluster.sync() / barrier.cluster.arrivecluster-wide 同步与相应的内存可见性
Cluster mbarriermbarrier.arrive.shared::cluster允许远端 arrive；wait 在 mbarrier 所属 CTA 上完成
TMA → shared::clustercp.async.bulk.tensor.*.shared::cluster.globalbulk async copy 直接落到 cluster 内另一个 CTA 的 smem

CUTLASS 的 Hopper kernel 会按选定的 kernel schedule 组合 cluster shape、TMA 与 mbarrier。固定版本源码由此成为连接 CUDA 编程模型与实际 GEMM 配置的例子，后文据此分析 launch 与配置语义。

1. Cluster 协作作用域

Thread Block Cluster 的编程契约由成员关系、共同驻留和 cluster-scope 操作组成。launch 配置中的 cluster shape 将 grid 划分为若干 CTA 组；CUDA 保证同组 CTA 共调度到一个 GPC。kernel 通过 Cooperative Groups 取得 cluster 内的逻辑 rank 和 shape，并使用 cluster.sync() 建立组内阶段边界。

DSMEM 把这组 CTA 的 shared-memory allocation 纳入同一个可寻址作用域。一个 CTA 先在本地 shared memory 写入数据，cluster 完成同步后，peer CTA 再通过 map_shared_rank() 得到目标 rank 的对应地址并访问数据。成员、同步和地址映射共同构成跨 CTA 生产者—消费者协议；该作用域止于当前 cluster。

2. CUDA 编程契约与证据边界

Cluster kernel 的正确性建立在 CUDA 对调度、地址空间和同步的编程契约上。公开指南足以规定程序可观察的行为；性能分析中的内部拓扑与容量则需要独立的公开证据或目标设备测量。

2.1 CUDA 的共调度保证

CUDA 12.6.3 编程指南规定，同一 cluster 的 thread blocks 会被 co-scheduled。这项保证为 cluster.sync() 和 DSMEM 提供执行前提，其粒度是 cluster 生命周期内的共同驻留，而非某个内部时钟周期的状态描述。

2.2 单个 GPC 约束

同一份指南还规定，cluster 中的所有 thread blocks 被调度到单个 GPC。这个可移植约束确定了协作作用域的放置边界；GPC 内部如何完成资源分派和 DSMEM 路由属于另一层微架构问题。

2.3 资源可行性查询

cluster 是否可用以及能保持多少并发，取决于设备、MIG 配置、cluster shape 和 kernel 资源需求。CUDA 提供两类查询：

  • cudaOccupancyMaxPotentialClusterSize() 查询给定 launch 配置可支持的最大 cluster size；
  • cudaOccupancyMaxActiveClusters() 估算给定配置下可同时活跃的 cluster 数。Hopper Tuning Guide 12.6.3 建议 cluster kernel 使用该接口评估 occupancy。

这两个 API 把设备能力、MIG 配置和 kernel 资源需求汇总为运行时可用性与 occupancy 结果。应用应依据查询值和 launch 返回值选择配置，内部准入结构不属于接口契约。

2.4 DSMEM 地址语义

在 C++ 层，cluster.map_shared_rank(ptr, rank) 将本 CTA 的 shared-memory 地址映射到同一 cluster 中目标 CTA 的对应地址。在 PTX ISA 8.5 中，mapa 生成相应的 .shared::cluster 地址，%cluster_ctarank 等 special register 暴露 cluster 内的逻辑 rank。这些接口共同定义了地址空间、目标 CTA 和指令作用域。

2.5 公开证据的覆盖范围

本文的硬件事实限定为 CUDA 12.6.3、PTX ISA 8.5、Hopper Tuning Guide 与固定版本 CUTLASS 源码直接支持的语义。work distributor、GPC 内资源分派和 DSMEM 物理路由的组织方式未纳入执行模型；kernel 的正确性只依赖共调度、单 GPC、DSMEM 地址与 cluster 同步这些公开保证。

3. cluster 几何与约束

3.1 shape 与层级

加入 cluster 后，Hopper 上与本文相关的执行层级为：

grid  -->  cluster  -->  block (CTA)  -->  warp  -->  thread

Cluster shape 是三维元组 (cluster_dim.x, cluster_dim.y, cluster_dim.z)，描述一个 cluster 包含多少 CTA 以及它们的逻辑排列。常见配置包括：

  • (2, 1, 1)：一维，2 个 CTA
  • (2, 2, 1)：二维，4 个 CTA
  • (4, 2, 1)：二维，8 个 CTA，达到 portable size 上限

3.2 size 上限

  • CUDA 定义的 portable cluster size 上限是 8 CTA；过小的 GPU 或 MIG 配置可能连 8 都不支持。
  • Hopper Tuning Guide 12.6.3 说明 H100 可在 opt-in 后使用 16 CTA 的 non-portable cluster。启用方式是 cudaFuncSetAttribute(..., cudaFuncAttributeNonPortableClusterSizeAllowed, 1)。
  • 实际上限应由 cudaOccupancyMaxPotentialClusterSize() 查询，不能由型号名或假定的每 GPC SM 数推导。

3.3 gridDim 与 clusterDim 的整除约束

CUDA 编程指南要求 grid 的每一维都能被 cluster 的对应维整除：

$$\text{gridDim.x} \bmod \text{clusterDim.x} \;=\; 0,\quad \text{gridDim.y} \bmod \text{clusterDim.y} \;=\; 0,\quad \text{gridDim.z} \bmod \text{clusterDim.z} \;=\; 0$$

不满足整除条件的 launch 配置无效；应用应检查 API 返回值，不应依赖某个固定错误码。常见配置如下：

gridDimclusterDim结果
(8, 1, 1)(2, 1, 1)OK,4 个 cluster
(8, 4, 1)(2, 2, 1)OK,8 个 cluster
(7, 1, 1)(2, 1, 1)报错,7 % 2 ≠ 0
(1, 1, 1)(2, 1, 1)报错,gridDim.x < clusterDim.x
(2, 1, 1)(2, 2, 1)报错,gridDim.y < clusterDim.y

Host 侧通常按问题尺寸采用以下配置方式：

  • 静态问题尺寸：host 按 tile 数计算 grid，并确保 grid 的各维可被 cluster shape 整除。边界 tile 是否采用 padding 或 predication 由具体 kernel 决定。
  • 动态问题尺寸：host 可以选择另一组已编译并验证过的 cluster 配置，或改用非 cluster kernel。CUDA 不会自动把任意 cluster shape 降级为 (1,1,1)。
  • occupancy 查询：使用 cudaOccupancyMaxPotentialClusterSize() 和 cudaOccupancyMaxActiveClusters() 检查设备与 kernel 的实际限制。

4. Cluster size 的编译期与运行期约束

CUDA 允许 cluster shape 固定在 kernel 属性中，也允许 host 在 launch 时提供。两种方式分别服务于静态算法配置和运行时选择，同一个 kernel 定义只采用其中一种。

4.1 编译期:__cluster_dims__(X, Y, Z) kernel 属性

在 kernel 定义上直接添加属性，cluster shape 随 kernel 固定：

// kernel.cu — cluster size 写死成 (2, 2, 1)
#include <cooperative_groups.h>
namespace cg = cooperative_groups;

__global__ __cluster_dims__(2, 2, 1)
void my_kernel(int* x) {
    auto cluster = cg::this_cluster();
    int cta_rank = cluster.block_rank();    // 0..3
    cluster.sync();
    // ...
}

这种方式下，kernel 自带 cluster 形状，launch 时不需要额外指定 cluster attribute，而且运行时不能改成另一种 shape。

当 cluster shape 是算法配置的一部分时，编译期属性最直接。CUTLASS 的 ClusterShape 模板参数就是这一类静态配置。

4.2 运行期:cudaLaunchAttributeClusterDimension 通过 cudaLaunchKernelEx

把 kernel 写成没有 __cluster_dims__ 属性,launch 时通过 attribute 传 cluster shape:

// kernel.cu — 不带 __cluster_dims__
__global__ void my_kernel(int* x) {
    auto cluster = cg::this_cluster();
    int n_cta = cluster.dim_blocks().x * cluster.dim_blocks().y;
    cluster.sync();
}

// host.cpp — launch 时传 cluster shape
cudaLaunchAttribute attrs[1];
attrs[0].id                  = cudaLaunchAttributeClusterDimension;
attrs[0].val.clusterDim.x    = 2;
attrs[0].val.clusterDim.y    = 2;
attrs[0].val.clusterDim.z    = 1;

cudaLaunchConfig_t config = {};
config.gridDim       = dim3(4, 4, 1);   // 必须被 cluster shape 整除
config.blockDim      = dim3(128, 1, 1);
config.dynamicSmemBytes = 0;
config.stream        = stream;
config.attrs         = attrs;
config.numAttrs      = 1;

cudaLaunchKernelEx(&config, my_kernel, x);

当 host 需要根据问题尺寸在已验证的 shape 之间选择时，运行期 attribute 可以复用同一个 kernel 入口，例如 GEMM 按 M、N 选择 1x1、2x1 或 2x2。

4.3 CUTLASS:ClusterShape_MNK 模板参数

以下说明固定到 CUTLASS commit ffa119a。该版本的 Hopper collective builder 把 cluster shape 作为 kernel 配置的一部分：

using ClusterShape_MNK = cute::Shape<cute::_2, cute::_1, cute::_1>;  // 2x1x1 cluster
using TileShape_MNK    = cute::Shape<cute::_128, cute::_256, cute::_64>;

using CollectiveMainloop = cutlass::gemm::collective::CollectiveBuilder<
    cutlass::arch::Sm90,
    cutlass::arch::OpClassTensorOp,
    ElementA, LayoutA, AlignA,
    ElementB, LayoutB, AlignB,
    ElementAccum,
    TileShape_MNK, ClusterShape_MNK,           // 这里
    cutlass::gemm::collective::StageCountAutoCarveout<sizeof(SharedStorage)>,
    cutlass::gemm::collective::KernelTmaWarpSpecialized>::CollectiveOp;

using GemmKernel = cutlass::gemm::kernel::GemmUniversal<
    cute::Shape<int, int, int, int>,    // ProblemShape MNKL
    CollectiveMainloop,
    CollectiveEpilogue>;

ClusterShape_MNK 参与 collective 和 kernel schedule 的实例化，因此不能把它理解为任意可变的运行时参数。固定版本的 cluster_launch.hpp 会构造 cudaLaunchAttributeClusterDimension 并通过 cudaLaunchKernelExC 启动 kernel。

同一文件还提供 launch_with_fallback_cluster()：调用者显式传入 preferred 与 fallback shape；在支持 preferred-cluster attribute 的构建中，helper 将 fallback 作为实际 cluster dimension，并把 preferred shape 写入相应 attribute。该 helper 负责启动调用者已经选定的两组配置，配置搜索仍由上层逻辑完成。

5. 运行时 launch API:cudaLaunchKernelEx 完整签名

运行时指定 cluster shape 时，需要用 cudaLaunchKernelEx 传递 launch attribute。带有编译期 __cluster_dims__ 的 kernel 仍可使用传统 <<<...>>> 语法。

cudaError_t cudaLaunchKernelEx(
    const cudaLaunchConfig_t* config,
    void* kernel_func,
    Args... args);                // 可变参数,与 kernel 签名一致

struct cudaLaunchConfig_t {
    dim3 gridDim;
    dim3 blockDim;
    size_t dynamicSmemBytes;
    cudaStream_t stream;
    cudaLaunchAttribute* attrs;
    unsigned int numAttrs;
};

struct cudaLaunchAttribute {
    cudaLaunchAttributeID id;
    cudaLaunchAttributeValue val;     // union
};

cluster 相关的 attribute:

  • cudaLaunchAttributeClusterDimension: 指定 cluster shape
  • cudaLaunchAttributeClusterSchedulingPolicyPreference: 为不同 cluster 在 GPC 间的放置提供调度偏好，不改变单个 cluster 位于同一 GPC 的保证
  • cudaFuncAttributeNonPortableClusterSizeAllowed: 通过 cudaFuncSetAttribute 为支持的设备启用 non-portable cluster size

完整 host 侧 launch 模板(2x2x1 cluster,gridDim 必须能被 2 × 2 整除):

void launch_with_cluster(int* d_data, int grid_m, int grid_n, cudaStream_t stream) {
    // 1) 检查整除约束
    constexpr int CX = 2, CY = 2;
    if (grid_m % CX != 0 || grid_n % CY != 0) {
        std::abort();                         // 或者降级到 cluster=(1,1,1)
    }

    // 2) 准备 cluster attribute
    cudaLaunchAttribute attrs[1];
    attrs[0].id                = cudaLaunchAttributeClusterDimension;
    attrs[0].val.clusterDim.x  = CX;
    attrs[0].val.clusterDim.y  = CY;
    attrs[0].val.clusterDim.z  = 1;

    // 3) 组装 config
    cudaLaunchConfig_t cfg = {};
    cfg.gridDim          = dim3(grid_m, grid_n, 1);
    cfg.blockDim         = dim3(128, 1, 1);
    cfg.dynamicSmemBytes = 0;
    cfg.stream           = stream;
    cfg.attrs            = attrs;
    cfg.numAttrs         = 1;

    // 4) launch
    cudaLaunchKernelEx(&cfg, my_kernel, d_data);
}

如果 kernel 自带 __cluster_dims__(2, 2, 1)，应直接使用普通 launch 语法，不能在 launch 时改成另一种 cluster shape。

6. 协作原语及其执行关系

共调度只建立共同驻留条件，跨 CTA 协作还需要地址、同步和异步完成协议。Cluster barrier 负责阶段边界，DSMEM 提供远端 shared-memory 地址，mbarrier 跟踪细粒度到达与事务完成，TMA 则把异步数据搬运接入这套协议。

6.1 Cluster barrier

Cluster barrier 是覆盖 cluster 内所有参与线程的同步操作。cluster.sync() 等待这些线程到达同一阶段，并建立文档规定的内存可见性：

auto cluster = cg::this_cluster();
cluster.sync();                                   // 整 cluster barrier

PTX ISA 8.5 提供对应的 barrier.cluster.arrive / barrier.cluster.wait。文档定义了参与线程和内存可见性，但没有给出固定延迟，也没有把它描述成某种具体互连上的 fence。

在分阶段 GEMM 中，各 CTA 可以先完成本地 tile 装载，再通过 barrier 进入跨 CTA 的消费阶段：

// 阶段 1: 各 CTA 把自己负责的 A_tile / B_tile 加载到本地 smem
load_tile_to_smem();
cluster.sync();                                   // 全 cluster 都到位了

// 阶段 2: 各 CTA 现在可以通过 DSMEM 直读对方的 smem 段
cross_cta_use_dsmem();
cluster.sync();                                   // 必要时再 barrier 一次

6.2 Distributed Shared Memory (DSMEM)

DSMEM 是由同一 cluster 内各 CTA 的 shared memory 共同构成的可寻址空间。每块 shared memory 仍由所属 CTA 分配，peer CTA 通过 rank 映射得到对应地址：

__shared__ float local_buf[256];

auto cluster = cg::this_cluster();
int peer_rank = (cluster.block_rank() + 1) % cluster.num_blocks();

float* peer_buf = cluster.map_shared_rank(local_buf, peer_rank);
// peer_buf 现在指向 rank=peer_rank 这个 CTA 的 local_buf 起始
float v = peer_buf[threadIdx.x];                 // 直接跨 CTA 读 smem

地址与同步遵循以下规则：

  • PTX ISA 使用 mapa.shared::cluster 生成 cluster-scope 地址，并提供 ld.shared::cluster.b32、st.shared::cluster.b32 等 load/store 形式。具体编译结果应以当前工具链生成的 PTX/SASS 为准。
  • 公开指南没有规定 DSMEM 的固定延迟或相对 L2 的带宽比例；这些数值需要在目标设备上测量。
  • peer shared memory 的读取需要遵循写入完成后的同步关系：peer 写入 → cluster.sync() → 当前 CTA 通过 map_shared_rank() 读取。

6.3 Cluster scope mbarrier

mbarrier 是 shared memory 中 8 字节对齐的 64-bit opaque object，用 arrival count 和 transaction count 表示异步阶段的完成状态。PTX ISA 8.5 按 owner CTA 与 peer CTA 分配本地和远端操作：

// PTX 语义示意：mbarrier 必须由拥有它的 CTA 在 shared::cta 中初始化
mbarrier.init.shared::cta.b64 [local_mbar], expected_arrivals;
barrier.cluster.arrive;
barrier.cluster.wait;

// 其它 CTA 先用 mapa 得到远端地址，再执行不返回 state 的 remote arrive
mapa.shared::cluster.u64 remote_mbar, local_mbar, owner_cta_rank;
mbarrier.arrive.release.cluster.shared::cluster.b64 _, [remote_mbar];

// owner CTA 在本地 shared::cta 地址上执行 try_wait/test_wait
mbarrier.try_wait.parity.acquire.cluster.shared::cta.b64 done, [local_mbar], phase;

PTX ISA 8.5 的支持表规定：远端 .shared::cluster mbarrier 支持 arrive、expect_tx 和 complete_tx；初始化、等待及其它操作只支持本地 .shared::cta 地址。分阶段协议可以利用 arrival count 与 tx-count 关联生产者、消费者和异步 copy，但具体协议必须由 kernel 明确定义。

6.4 TMA → shared::cluster

Hopper Tuning Guide 将 TMA（Tensor Memory Accelerator）描述为 asynchronous copy engine。其 bulk async copy 的目的地可以是本地 shared memory，也可以是同一 cluster 中其它 CTA 的 shared memory：

// PTX 伪码:bulk async copy 一个 2D tile,目的是 cluster 内 dst_cta_rank 的 smem
cp.async.bulk.tensor.2d.shared::cluster.global.tile.mbarrier::complete_tx::bytes
    [dst_smem_ptr_in_peer_cta], [tensor_map], {coord_x, coord_y}, [mbar_in_peer_cta];

事务关系如下：

  • 目的地址位于 .shared::cluster，可以指向 cluster 内另一个 CTA 的 shared memory。
  • mbarrier::complete_tx::bytes 在 copy 完成时更新指定 mbarrier 的 tx-count；等待操作由拥有该 mbarrier 的 CTA 在本地地址上执行。
  • 一次普通 copy 对应一个目的地址。向多个 CTA 复制需要显式使用 .multicast::cluster 和 CTA mask。PTX ISA 8.5 规定这些指令要求 sm_90 或更高，并建议 multicast 以 sm_90a 为目标以获得合适性能。

7. CUDA C++ 例子

前两个例子使用 CUDA 12.6.3 公开编程接口，可在 Compute Capability 9.0 上编译。mbarrier 与 TMA 的示例停留在 PTX 语义和固定版本源码入口，因为完整程序还需要与工具链匹配的包装层、tensor map 和异步完成协议。

7.1 例 1:Hello cluster: 用 cluster.sync() 同步

// hello_cluster.cu
#include <cstdio>
#include <cooperative_groups.h>
namespace cg = cooperative_groups;

__global__ __cluster_dims__(2, 2, 1)
void hello_cluster() {
    auto cluster = cg::this_cluster();
    int rank_in_cluster = cluster.block_rank();
    int cluster_size   = cluster.num_blocks();

    if (threadIdx.x == 0) {
        printf("[block %d in cluster (%d/%d)] before sync\n",
               blockIdx.x, rank_in_cluster, cluster_size);
    }
    cluster.sync();                                // 全 cluster barrier
    if (threadIdx.x == 0) {
        printf("[block %d in cluster (%d/%d)] after sync\n",
               blockIdx.x, rank_in_cluster, cluster_size);
    }
}

int main() {
    hello_cluster<<<dim3(4, 4, 1), 32>>>();        // 4 cluster, 每个 cluster 4 CTA
    cudaDeviceSynchronize();
}

编译:

nvcc -arch=sm_90 -std=c++17 -O3 hello_cluster.cu -o hello_cluster
./hello_cluster

要点:

  • PTX ISA 8.5 规定 cluster、.shared::cluster 与 TMA bulk-copy 指令要求 sm_90 或更高；只有部分 architecture-specific 特性（例如推荐的 TMA multicast 路径）需要单独考虑 sm_90a。
  • kernel 已声明 __cluster_dims__(2, 2, 1)，launch 因而使用普通的 <<<dim3(4,4,1), 32>>> 语法。gridDim 为 4 × 4，共 16 个 CTA、4 个 cluster；两个维度均满足 4 % 2 = 0 的整除约束。

7.2 例 2:DSMEM 跨 CTA 读: 运行期指定 cluster size

// dsmem_read.cu — 每个 CTA 把自己 rank 写到 smem,再读 peer 的 smem 验证
#include <cstdio>
#include <cooperative_groups.h>
namespace cg = cooperative_groups;

__global__ void dsmem_demo(int* out) {
    __shared__ int local_buf[1];
    auto cluster = cg::this_cluster();

    if (threadIdx.x == 0) local_buf[0] = cluster.block_rank() * 100 + 42;
    cluster.sync();                                // 等 peer 写完

    int peer_rank = (cluster.block_rank() + 1) % cluster.num_blocks();
    int* peer_buf = cluster.map_shared_rank(local_buf, peer_rank);

    if (threadIdx.x == 0) {
        int v = peer_buf[0];                     // 直接跨 CTA 读 smem
        out[blockIdx.x] = v;
    }
    cluster.sync();                                // 确保所有 read 完成再退
}

int main() {
    int* d_out; cudaMalloc(&d_out, 8 * sizeof(int));

    cudaLaunchAttribute attrs[1];
    attrs[0].id               = cudaLaunchAttributeClusterDimension;
    attrs[0].val.clusterDim.x = 4;                 // 1D cluster, size=4
    attrs[0].val.clusterDim.y = 1;
    attrs[0].val.clusterDim.z = 1;

    cudaLaunchConfig_t cfg = {};
    cfg.gridDim          = dim3(8, 1, 1);          // 8 % 4 == 0 → 2 clusters
    cfg.blockDim         = dim3(32, 1, 1);
    cfg.attrs            = attrs;
    cfg.numAttrs         = 1;

    cudaLaunchKernelEx(&cfg, dsmem_demo, d_out);
    cudaDeviceSynchronize();

    int h_out[8];
    cudaMemcpy(h_out, d_out, sizeof h_out, cudaMemcpyDeviceToHost);
    for (int i = 0; i < 8; ++i) printf("block %d read peer = %d\n", i, h_out[i]);
}

9. 兼容性与使用边界

  1. sm_90 与 sm_90a：PTX ISA 8.5 将 cluster、.shared::cluster 和 TMA bulk copy 的最低目标写为 sm_90。TMA multicast 在该版本中建议使用 sm_90a；其它 WGMMA 变体应分别检查各自的 Target ISA Notes。
  2. grid 与 cluster shape：grid 的每一维必须能被 cluster 对应维整除。动态问题尺寸应选择经过验证的 launch 配置；fallback 是应用或库的显式策略，不是 CUDA 自动行为。
  3. occupancy：更大的 cluster 可能降低最大活跃 block 数，但不能用假定的 SM/GPC 数直接计算并发 cluster。使用 cudaOccupancyMaxPotentialClusterSize() 和 cudaOccupancyMaxActiveClusters() 查询。
  4. 单 GPC 保证：同一 cluster 的 block 被调度到一个 GPC。H100 的 16-CTA non-portable cluster 仍需 opt-in，实际支持情况由 occupancy API 判断。
  5. DSMEM 作用域：map_shared_rank(ptr, rank) 的目标必须属于当前 cluster。该接口不提供跨 cluster 的 shared-memory 地址。
  6. 远端 mbarrier：目标必须是有效的 .shared::cluster 地址，并且只能使用 PTX 支持表允许的远端操作。远端 wait 不受支持；owner CTA 应在本地 .shared::cta 地址上等待。
  7. cluster rank：使用 cluster.block_rank() 获取 cluster 内逻辑 rank；blockIdx 仍表示 grid 内 block 坐标。
  8. CUTLASS preferred/fallback：固定 commit 的 helper 接受调用者提供的两组 shape。它不证明 GemmUniversal::Arguments 可在不重新实例化 kernel 的情况下接受任意 cluster shape，也不代表库会自动搜索最优 fallback。

Execution Semantics of Hopper Thread Block Clusters: DSMEM, Cluster Barriers, and Cross-CTA TMA

A CUDA kernel normally consists of independently scheduled thread blocks, each with its own shared memory. Algorithms that exchange tiles or synchronize phases across block boundaries therefore tend to use global memory, atomics, or another kernel launch. Compute Capability 9.0 adds Thread Block Clusters as a CUDA-visible cooperation level above the block: several CTAs form a cluster, are co-scheduled on one GPC, and may use cluster-scope synchronization and distributed shared memory.

Version scope: this article follows the CUDA C++ Programming Guide 12.6.3, PTX ISA 8.5, and Hopper (Compute Capability 9.0). Only behavior defined by those public documents is treated as a guarantee. The internal implementation of resource dispatch, routing, and address translation is not public.

CapabilityCUDA / PTX primitiveProgramming semantics

Cluster barriercluster.sync() / barrier.cluster.arriveAll threads in all CTAs of the cluster align

CUTLASS Hopper kernels combine cluster shapes, TMA, and mbarriers according to the selected kernel schedule. A pinned source revision therefore provides a concrete link between the CUDA programming model and a complete GEMM launch configuration.

1. Cluster cooperation scope

The Thread Block Cluster programming contract combines membership, common residency, and cluster-scope operations. The cluster shape in the launch configuration partitions the grid into CTA groups, and CUDA guarantees that the CTAs in one group are co-scheduled on a single GPC. Inside the kernel, Cooperative Groups exposes the logical rank and shape, while cluster.sync() establishes phase boundaries across the group.

DSMEM brings the shared-memory allocations of those CTAs into one addressable scope. A CTA writes data to its local shared memory; after cluster synchronization, a peer maps the corresponding address for the target rank through map_shared_rank() and accesses the data. Membership, synchronization, and address mapping together form a cross-CTA producer-consumer protocol whose scope ends at the current cluster.

2. CUDA Contract and Evidence Boundary

Cluster correctness rests on CUDA's contracts for scheduling, address spaces, and synchronization. The public guides specify the observable behavior needed by a program; internal topology and capacity claims require separate public evidence or measurements on the target device.

2.1 CUDA co-scheduling guarantee

The CUDA 12.6.3 Programming Guide states that thread blocks in a cluster are co-scheduled. This guarantee establishes the common-residency condition needed by cluster.sync() and DSMEM; it applies over the cluster's execution lifetime rather than defining an internal clock-cycle state.

2.2 Single-GPC constraint

The same guide guarantees that all thread blocks in a cluster are scheduled on a single GPC. This portable constraint fixes the placement boundary of the cooperation scope. Resource dispatch and DSMEM routing inside that GPC remain separate microarchitectural questions.

2.3 Resource feasibility queries

Cluster feasibility and concurrency depend on the device, MIG configuration, cluster shape, and kernel resource use. CUDA provides two relevant queries:

  • cudaOccupancyMaxPotentialClusterSize() queries the maximum cluster size supported by a launch configuration.
  • cudaOccupancyMaxActiveClusters() estimates the number of active clusters for a configuration. The Hopper Tuning Guide 12.6.3 recommends using it for cluster-kernel occupancy.

These APIs combine device capability, MIG configuration, and kernel resource use into runtime feasibility and occupancy results. Applications select configurations from the query values and launch return codes; the internal admission structures are outside the interface contract.

2.4 DSMEM address semantics

At the C++ level, cluster.map_shared_rank(ptr, rank) maps a shared-memory address in the current CTA to the corresponding address in another CTA of the cluster. In PTX ISA 8.5, mapa produces the corresponding .shared::cluster address, while special registers such as %cluster_ctarank expose the logical rank. Together, these interfaces define the address space, target CTA, and instruction scope.

2.5 Scope of the public evidence

The hardware facts used here are limited to semantics directly supported by CUDA 12.6.3, PTX ISA 8.5, the Hopper Tuning Guide, and the pinned CUTLASS source. Work distribution, GPC-local resource allocation, and the physical organization of DSMEM routing are outside this execution model. Kernel correctness relies only on the public guarantees for co-scheduling, one-GPC placement, DSMEM addresses, and cluster synchronization.

3. Cluster geometry and constraints

3.1 Shape and hierarchy

With clusters included, the hierarchy relevant to this discussion is:

grid  -->  cluster  -->  block (CTA)  -->  warp  -->  thread

A cluster shape is the 3D tuple (cluster_dim.x, cluster_dim.y, cluster_dim.z). It specifies both the CTA count and their logical arrangement. Common configurations include:

  • (2, 1, 1): one-dimensional, 2 CTAs.
  • (2, 2, 1): two-dimensional, 4 CTAs.
  • (4, 2, 1): two-dimensional, 8 CTAs, the portable upper bound.

3.2 Size limits

  • CUDA defines 8 CTAs as the portable cluster-size limit; smaller GPUs or MIG configurations may support fewer than 8.
  • The Hopper Tuning Guide 12.6.3 says H100 supports a non-portable 16-CTA cluster after opt-in with cudaFuncSetAttribute(..., cudaFuncAttributeNonPortableClusterSizeAllowed, 1).
  • Use cudaOccupancyMaxPotentialClusterSize() for the device-specific limit instead of deriving it from a product name or an assumed SMs-per-GPC count.

3.3 gridDim divisibility constraint

The CUDA Programming Guide requires each grid dimension to be divisible by the corresponding cluster dimension:

$$\text{gridDim.x} \bmod \text{clusterDim.x} \;=\; 0,\quad \text{gridDim.y} \bmod \text{clusterDim.y} \;=\; 0,\quad \text{gridDim.z} \bmod \text{clusterDim.z} \;=\; 0$$

A launch configuration that violates divisibility is invalid. Applications should check the API result instead of depending on a fixed error code. Common configurations:

gridDimclusterDimResult
(8, 1, 1)(2, 1, 1)OK, 4 clusters
(8, 4, 1)(2, 2, 1)OK, 8 clusters
(7, 1, 1)(2, 1, 1)error, 7 % 2 ≠ 0
(1, 1, 1)(2, 1, 1)error, gridDim.x < clusterDim.x
(2, 1, 1)(2, 2, 1)error, gridDim.y < clusterDim.y

Host code normally handles problem sizes through these configuration paths:

  • Static problems: compute the grid from the tile count on the host and make every grid dimension divisible by the cluster shape. Padding or predicating boundary tiles is a kernel-specific decision.
  • Dynamic problems: choose another compiled and validated cluster configuration, or use a non-cluster kernel. CUDA does not automatically downgrade an arbitrary shape to (1,1,1).
  • Occupancy queries: use cudaOccupancyMaxPotentialClusterSize() and cudaOccupancyMaxActiveClusters() to check the limits for the device and kernel.

4. Cluster size: compile-time vs runtime

CUDA can bind the cluster shape to a kernel attribute or accept it from the host at launch. The two forms serve static algorithm configuration and runtime selection respectively; a kernel definition uses one form.

4.1 Compile-time: __cluster_dims__(X, Y, Z) kernel attribute

Annotate the kernel directly so that its cluster shape is fixed with the kernel:

// kernel.cu — cluster size is fixed at (2, 2, 1)
#include <cooperative_groups.h>
namespace cg = cooperative_groups;

__global__ __cluster_dims__(2, 2, 1)
void my_kernel(int* x) {
    auto cluster = cg::this_cluster();
    int cta_rank = cluster.block_rank();    // 0..3
    cluster.sync();
    // ...
}

With this style the kernel carries its cluster shape. The launch site does not need a cluster attribute, and the shape cannot be changed at runtime.

The compile-time attribute fits algorithms whose cluster shape is part of the kernel configuration. CUTLASS's ClusterShape template parameter is one such static configuration.

4.2 Runtime: cudaLaunchAttributeClusterDimension via cudaLaunchKernelEx

Leave the kernel free of __cluster_dims__, supply the shape at launch as an attribute:

// kernel.cu — no __cluster_dims__
__global__ void my_kernel(int* x) {
    auto cluster = cg::this_cluster();
    int n_cta = cluster.dim_blocks().x * cluster.dim_blocks().y;
    cluster.sync();
}

// host.cpp — pass cluster shape at launch
cudaLaunchAttribute attrs[1];
attrs[0].id                  = cudaLaunchAttributeClusterDimension;
attrs[0].val.clusterDim.x    = 2;
attrs[0].val.clusterDim.y    = 2;
attrs[0].val.clusterDim.z    = 1;

cudaLaunchConfig_t config = {};
config.gridDim       = dim3(4, 4, 1);   // must divide by cluster shape
config.blockDim      = dim3(128, 1, 1);
config.dynamicSmemBytes = 0;
config.stream        = stream;
config.attrs         = attrs;
config.numAttrs      = 1;

cudaLaunchKernelEx(&config, my_kernel, x);

The runtime attribute lets the host choose among validated shapes for the problem while reusing one kernel entry, for example selecting 1x1, 2x1, or 2x2 from GEMM dimensions M and N.

5. Runtime launch API: full cudaLaunchKernelEx signature

A runtime cluster shape requires cudaLaunchKernelEx so that launch attributes can be supplied. A kernel with a compile-time __cluster_dims__ annotation can still use the classic <<<...>>> syntax.

cudaError_t cudaLaunchKernelEx(
    const cudaLaunchConfig_t* config,
    void* kernel_func,
    Args... args);                // variadic, matches the kernel signature

struct cudaLaunchConfig_t {
    dim3 gridDim;
    dim3 blockDim;
    size_t dynamicSmemBytes;
    cudaStream_t stream;
    cudaLaunchAttribute* attrs;
    unsigned int numAttrs;
};

struct cudaLaunchAttribute {
    cudaLaunchAttributeID id;
    cudaLaunchAttributeValue val;     // union
};

Cluster-related attributes:

  • cudaLaunchAttributeClusterDimension: pass the cluster shape
  • cudaLaunchAttributeClusterSchedulingPolicyPreference: a placement preference for different clusters across GPCs; it does not change the one-GPC guarantee for each cluster
  • cudaFuncAttributeNonPortableClusterSizeAllowed: set with cudaFuncSetAttribute to opt into non-portable sizes on supported devices

A complete host-side launch template (2x2x1 cluster, gridDim must divide by 2 × 2):

void launch_with_cluster(int* d_data, int grid_m, int grid_n, cudaStream_t stream) {
    // 1) Check the divisibility constraint
    constexpr int CX = 2, CY = 2;
    if (grid_m % CX != 0 || grid_n % CY != 0) {
        std::abort();                         // or fall back to cluster=(1,1,1)
    }

    // 2) Build the cluster attribute
    cudaLaunchAttribute attrs[1];
    attrs[0].id                = cudaLaunchAttributeClusterDimension;
    attrs[0].val.clusterDim.x  = CX;
    attrs[0].val.clusterDim.y  = CY;
    attrs[0].val.clusterDim.z  = 1;

    // 3) Assemble the config
    cudaLaunchConfig_t cfg = {};
    cfg.gridDim          = dim3(grid_m, grid_n, 1);
    cfg.blockDim         = dim3(128, 1, 1);
    cfg.dynamicSmemBytes = 0;
    cfg.stream           = stream;
    cfg.attrs            = attrs;
    cfg.numAttrs         = 1;

    // 4) Launch
    cudaLaunchKernelEx(&cfg, my_kernel, d_data);
}

If the kernel carries __cluster_dims__(2, 2, 1), launch it with the ordinary syntax; its cluster shape cannot be changed at launch.

6. Collaboration Primitives and Execution Relationships

Co-scheduling establishes common residency; cross-CTA cooperation still needs addressing, synchronization, and asynchronous completion protocols. Cluster barriers delimit phases, DSMEM supplies remote shared-memory addresses, mbarriers track arrivals and transaction completion, and TMA connects asynchronous transfers to that state.

6.1 Cluster barrier

A cluster barrier is a synchronization operation covering all participating threads in the cluster. cluster.sync() waits for those threads to reach the same phase and establishes the documented memory visibility:

auto cluster = cg::this_cluster();
cluster.sync();                                   // cluster-wide barrier

PTX ISA 8.5 provides the corresponding barrier.cluster.arrive / barrier.cluster.wait instructions. It defines participation and memory visibility, but neither a fixed latency nor a particular interconnect implementation.

In a staged GEMM, each CTA can finish loading its local tile before the cluster enters the cross-CTA consumption phase:

// Phase 1: each CTA stages its own A_tile / B_tile into local smem
load_tile_to_smem();
cluster.sync();                                   // every CTA is in place

// Phase 2: each CTA can now read peer smem through DSMEM
cross_cta_use_dsmem();
cluster.sync();                                   // barrier again if needed

6.2 Distributed Shared Memory (DSMEM)

DSMEM is an addressable space formed from the shared-memory allocations of CTAs in one cluster. Each allocation remains owned by its CTA, while peers obtain the corresponding address through rank mapping:

__shared__ float local_buf[256];

auto cluster = cg::this_cluster();
int peer_rank = (cluster.block_rank() + 1) % cluster.num_blocks();

float* peer_buf = cluster.map_shared_rank(local_buf, peer_rank);
// peer_buf now points to local_buf at the CTA with rank=peer_rank
float v = peer_buf[threadIdx.x];                 // cross-CTA smem read

Addressing and synchronization follow these rules:

  • PTX uses mapa.shared::cluster to produce a cluster-scope address and provides load/store forms such as ld.shared::cluster.b32 and st.shared::cluster.b32. Inspect the generated PTX/SASS for the toolchain in use.
  • The public guides do not define a fixed DSMEM latency or a bandwidth ratio relative to L2; those values must be measured on the target device.
  • Synchronisation: before reading peer smem, the peer must have finished writing it. The canonical pattern is: peer writes → cluster.sync() → this CTA reads via map_shared_rank.

6.3 Cluster-scope mbarrier

An mbarrier is an opaque, 8-byte-aligned 64-bit object in shared memory whose arrival count and transaction count represent asynchronous phase completion. PTX ISA 8.5 assigns local and remote operations according to owner and peer CTA roles:

// PTX semantics: the owner CTA initializes the object in shared::cta
mbarrier.init.shared::cta.b64 [local_mbar], expected_arrivals;
barrier.cluster.arrive;
barrier.cluster.wait;

// A peer maps the remote address and performs an arrive that returns no state
mapa.shared::cluster.u64 remote_mbar, local_mbar, owner_cta_rank;
mbarrier.arrive.release.cluster.shared::cluster.b64 _, [remote_mbar];

// The owner waits through its local shared::cta address
mbarrier.try_wait.parity.acquire.cluster.shared::cta.b64 done, [local_mbar], phase;

The PTX ISA 8.5 support table allows arrive, expect_tx, and complete_tx on a remote .shared::cluster mbarrier. Initialization, waiting, and the remaining operations use the owner's local .shared::cta address. A staged protocol can combine arrival counts and tx-count with producers, consumers, and asynchronous copies, with the kernel defining their phase relationship.

6.4 TMA → shared::cluster

The Hopper Tuning Guide describes TMA (Tensor Memory Accelerator) as an asynchronous copy engine. Its destination may be the local CTA's shared memory or another CTA's shared memory in the same cluster:

// PTX (sketch): bulk-async copy a 2D tile to a peer CTA's smem in the cluster
cp.async.bulk.tensor.2d.shared::cluster.global.tile.mbarrier::complete_tx::bytes
    [dst_smem_ptr_in_peer_cta], [tensor_map], {coord_x, coord_y}, [mbar_in_peer_cta];

The transaction relationships are:

  • The destination is in .shared::cluster and may refer to another CTA's shared memory in the cluster.
  • mbarrier::complete_tx::bytes updates the selected mbarrier's tx-count when the copy completes. The owning CTA performs the wait through its local address.
  • A normal copy has one destination address. Copying to multiple CTAs requires explicit .multicast::cluster and a CTA mask. PTX ISA 8.5 requires sm_90 or newer for these instructions and advises targeting sm_90a for multicast performance.

7. CUDA C++ examples

The first two examples use public CUDA 12.6.3 interfaces and compile for Compute Capability 9.0. The mbarrier and TMA parts remain at PTX semantics and pinned source references rather than presenting unverified wrapper code as runnable.

7.1 Example 1: Hello cluster, synchronising with cluster.sync()

// hello_cluster.cu
#include <cstdio>
#include <cooperative_groups.h>
namespace cg = cooperative_groups;

__global__ __cluster_dims__(2, 2, 1)
void hello_cluster() {
    auto cluster = cg::this_cluster();
    int rank_in_cluster = cluster.block_rank();
    int cluster_size   = cluster.num_blocks();

    if (threadIdx.x == 0) {
        printf("[block %d in cluster (%d/%d)] before sync\n",
               blockIdx.x, rank_in_cluster, cluster_size);
    }
    cluster.sync();                                // cluster-wide barrier
    if (threadIdx.x == 0) {
        printf("[block %d in cluster (%d/%d)] after sync\n",
               blockIdx.x, rank_in_cluster, cluster_size);
    }
}

int main() {
    hello_cluster<<<dim3(4, 4, 1), 32>>>();        // 4 clusters, 4 CTAs each
    cudaDeviceSynchronize();
}

Compile:

nvcc -arch=sm_90 -std=c++17 -O3 hello_cluster.cu -o hello_cluster
./hello_cluster

Notes:

  • PTX ISA 8.5 requires sm_90 or newer for cluster, .shared::cluster, and TMA bulk-copy instructions. Architecture-specific features such as the recommended TMA multicast path need separate consideration of sm_90a.
  • The kernel carries __cluster_dims__(2, 2, 1), so the launch site is plain <<<dim3(4,4,1), 32>>>. gridDim is 4 × 4 = 16 CTAs = 4 clusters; 4 % 2 = 0 satisfies the divisibility constraint.

7.2 Example 2: DSMEM cross-CTA read with a runtime cluster size

// dsmem_read.cu — each CTA writes its rank into smem, reads the peer's smem to verify
#include <cstdio>
#include <cooperative_groups.h>
namespace cg = cooperative_groups;

__global__ void dsmem_demo(int* out) {
    __shared__ int local_buf[1];
    auto cluster = cg::this_cluster();

    if (threadIdx.x == 0) local_buf[0] = cluster.block_rank() * 100 + 42;
    cluster.sync();                                // wait for peer write

    int peer_rank = (cluster.block_rank() + 1) % cluster.num_blocks();
    int* peer_buf = cluster.map_shared_rank(local_buf, peer_rank);

    if (threadIdx.x == 0) {
        int v = peer_buf[0];                     // cross-CTA smem read
        out[blockIdx.x] = v;
    }
    cluster.sync();                                // ensure reads complete before exit
}

int main() {
    int* d_out; cudaMalloc(&d_out, 8 * sizeof(int));

    cudaLaunchAttribute attrs[1];
    attrs[0].id               = cudaLaunchAttributeClusterDimension;
    attrs[0].val.clusterDim.x = 4;                 // 1D cluster, size 4
    attrs[0].val.clusterDim.y = 1;
    attrs[0].val.clusterDim.z = 1;

    cudaLaunchConfig_t cfg = {};
    cfg.gridDim          = dim3(8, 1, 1);          // 8 % 4 == 0 → 2 clusters
    cfg.blockDim         = dim3(32, 1, 1);
    cfg.attrs            = attrs;
    cfg.numAttrs         = 1;

    cudaLaunchKernelEx(&cfg, dsmem_demo, d_out);
    cudaDeviceSynchronize();

    int h_out[8];
    cudaMemcpy(h_out, d_out, sizeof h_out, cudaMemcpyDeviceToHost);
    for (int i = 0; i < 8; ++i) printf("block %d read peer = %d\n", i, h_out[i]);
}

7.3 mbarrier: follow the PTX support table

A remote mbarrier protocol distinguishes the owner CTA from peer CTAs that access it. Initialization and waiting use the owner's .shared::cta address. A peer maps a .shared::cluster address with mapa and issues the remote operations listed by the ISA. The complete operation set and memory semantics are defined by PTX ISA 8.5 mbarrier.

7.4 TMA: start from PTX and pinned source

PTX ISA 8.5 cp.async.bulk.tensor defines asynchronous tensor copies between global memory and .shared::cluster, mbarrier completion, and optional multicast. C++ wrapper arguments, tensor-map construction, and synchronization protocols can change with the toolchain. Runnable implementations should follow a CUDA sample or CUTLASS source pinned to the project's version.

9. Compatibility and usage boundaries

  1. sm_90 and sm_90a: PTX ISA 8.5 lists sm_90 as the minimum target for clusters, .shared::cluster, and TMA bulk copies. It advises sm_90a for TMA multicast; check the Target ISA Notes separately for each WGMMA variant.
  2. Grid and cluster shapes: every grid dimension must be divisible by the matching cluster dimension. Dynamic problems need a validated launch configuration. Fallback is explicit application or library policy, not automatic CUDA behavior.
  3. Occupancy: a larger cluster may reduce the maximum number of active blocks, but concurrency cannot be calculated from an assumed SMs-per-GPC count. Query cudaOccupancyMaxPotentialClusterSize() and cudaOccupancyMaxActiveClusters().
  4. Single-GPC guarantee: all blocks of one cluster are scheduled on one GPC. H100's non-portable 16-CTA cluster still requires opt-in, and actual support should be queried.
  5. DSMEM scope: the target rank of map_shared_rank(ptr, rank) must belong to the current cluster. The API does not create a shared-memory address across clusters.
  6. Remote mbarrier: the target must be a valid .shared::cluster address and the operation must appear in the PTX remote-support table. Remote wait is unsupported; the owner CTA waits through its local .shared::cta address.
  7. Cluster rank: use cluster.block_rank() for the logical rank within the cluster. blockIdx remains the block coordinate within the grid.
  8. CUTLASS preferred/fallback: the pinned helper accepts two shapes supplied by its caller. It does not establish that GemmUniversal::Arguments accepts an arbitrary cluster shape without a different kernel instantiation, nor that the library searches for an optimal fallback.
