VPN 与多重代理选路

VPN 与多份代理配置共存时，同一应用的请求可能使用不同的连接端点和网络出口。本文以 macOS 上的 VPN、应用专用内网代理和系统公网代理为场景，分析代理选择与 IP 路由如何组合，在明确的假设下归纳五类外部连接路径，并讨论 DNS、UDP、绕过规则与失败回退的影响。交互推演和诊断命令用于对照配置与实际连接。

1. 场景与假设

节点示例地址约束
P₁：应用专用 HTTP 代理10.77.0.10:18888只有通过 VPN 才能到达
P₂：macOS 系统 HTTP / HTTPS 代理203.0.113.80:18888位于公网；公网地址也可能匹配 VPN 默认路由
O：HTTPS 源站198.51.100.40:443公网目标，用于比较客户端连接路径
VPNutun 接口与相应网关支持私网路由；全隧道时还具备所需公网转发与出口

公网地址使用文档地址段，不代表真实可连接的服务。分析先限定为 IPv4、新建 TCP 连接、一个外部目标和显式 HTTP/1.1 代理；不加入额外代理链、透明拦截或特殊 per-app 路由。代理的服务与出口正常。缓存、DNS、IPv6、UDP、loopback 和失败分支在后文单列。

2. 两次路径选择

应用选择连接端点

采用 P₁ 的请求连接 10.77.0.10；采用系统配置的请求连接 P₂；匹配 bypass 或不使用代理的请求连接 O。应用专用代理通常覆盖它所管理的请求，而不是把请求先送到系统代理再送到应用代理。系统配置仍可被同一应用中另一个网络库或 Session 使用。

以 Electron 为例，窗口 Session 可固定使用 P₁，另一个 Session 可显式设为 system；Node 或原生模块又可能独立直连。具体选择规则与 HTTP 代理与应用配置 中的配置作用域对应。

系统路由所选端点

内核看到的是当前 socket 的目的 IP，而不是应用最初的 URL。它对 P₁、P₂ 或 O 的地址进行选路。P₁ 只能经 VPN；P₂ 和 O 虽是公网地址，仍可能匹配 VPN 的默认路由。因此，DIRECT 只表示不经应用代理，不能推出物理直出。

3. 五类外部连接路径

在上述简化模型下，可归纳出五类成功路径。这里统计的是可能出现的拓扑类别，不是同一个请求必定尝试五条路径；某个确定请求只使用当时实际选中的路径，失败后的重试另计。

路径有效代理选择Mac 到首个端点源站连接由谁发起
A应用 P₁Mac → VPN → P₁P₁ 按自己的路由连接 O
B系统 P₂Mac → 普通网络 → P₂P₂ 按自己的路由连接 O
C系统 P₂Mac → VPN → P₂P₂ 按自己的路由连接 O
DDIRECT / bypassMac → 普通网络 → OMac
EDIRECT / bypassMac → VPN → OMac；中间 VPN 网关做路由或 NAT

“P₁ + 普通网络”不是第六类成功路径，因为它违反仅 VPN 可达的前提。若客户端仍尝试该路径，结果是连接失败，而不是自动生成一个经过 P₂ 的链。代理服务器自身使用其他出口或上游代理时，会产生额外下游拓扑；它们不包含在这五类客户端路径中。

5. 绕过、回退与失败

DIRECT 的含义

bypass 是代理选择阶段的结果，通常让当前请求直连源站；它不会自动选择 macOS 的另一个代理，也不会撤销 VPN 路由。若应用设置 P₁，同时把某个域名放进 bypass，这个域名可能走 D 或 E。环境变量 NO_PROXY 只有在当前网络库读取它时才参与这个判断，不能套用到所有 Chromium Session。

显式回退列表

需要回退时，可以在有效 PAC 配置中明确列出候选。例如以下返回值表示依次尝试候选代理，最后允许 DIRECT：

function FindProxyForURL(url, host) {
  return "PROXY 10.77.0.10:18888; PROXY 203.0.113.80:18888; DIRECT";
}

这是候选列表，语义不等于串行通过两个代理。哪些连接错误触发下一候选、失败状态缓存多久，都由网络栈决定；代理返回一个 HTTP 错误也不一定触发相同回退。若实际配置只有 P₁，P₁ 不可达通常导致该请求失败。Electron 的 proxyRules 也支持显式候选列表与 direct://，但语法不同于 PAC。Electron 回退配置；Chromium 代理回退。

VPN 断开

断线后的结果与“VPN 开着但数据路径失效”不同。如果 VPN 路由被移除且没有阻断策略，公网 P₂ 与 O 可能恢复普通网络路径；仅 VPN 可达的 P₁ 仍然不可达。如果路由保留、流量进入失效隧道，请求可能超时。启用 kill switch 时，原本可直出的流量也可能被拒绝。客户端断线策略不能从代理配置中推导出来。

6. 路径验证

配置与连接证据

验证需要把应用的代理选择、socket 对端和系统选路对应起来。以下公网 IP 仅用于演示命令格式，实际检查时替换为代理与源站当前使用的地址：

scutil --proxy
scutil --dns
route -n get 10.77.0.10
route -n get 203.0.113.80
route -n get 198.51.100.40
netstat -rn -f inet
netstat -rn -f inet6
lsof -nP -a -p <PID> -i

在 Electron 中对实际发请求的 Session 调用 await ses.resolveProxy(url)，并使用 NetLog 记录新请求。scutil --proxy 只显示系统配置；lsof 应检查真正持有 socket 的网络服务或 helper PID，而不只检查主进程。普通 route 查询提供路由证据，但 per-app 或 scoped 策略下还需实际连接和抓包验证。Session 代理解析。

逐条请求验证

# Private proxy: expect CONNECT through the VPN-reachable proxy
curl --noproxy "" --proxy http://10.77.0.10:18888 -v https://example.com/ -o /dev/null

# Public system proxy, made explicit for this curl test
curl --noproxy "" --proxy http://203.0.113.80:18888 -v https://example.com/ -o /dev/null

# No HTTP proxy; the IP route can still select the VPN
curl --noproxy '*' -v https://example.com/ -o /dev/null

显式 curl 测试验证三种端点是否可达，不代表 Electron 已选用了相同配置。对照客户端日志、代理访问日志和源站记录，可以确定第一段与第二段连接。源站记录的出口 IP 可辅助定位，但无法单独证明客户端使用了哪份代理设置。

接口上的数据

# Replace utun4 and en0 with the interfaces actually in use
sudo tcpdump -ni utun4 'host 10.77.0.10 and tcp port 18888'
sudo tcpdump -ni en0 'udp port 51820'

在 WireGuard 场景中，隧道接口上的包可显示内层代理 IP；物理接口上可看到到 VPN Endpoint 的外层 UDP。系统使用其他 VPN 协议时需要相应过滤表达式。TLS 请求正文仍受应用加密保护；抓包中看不到正文，不代表没有经过该接口。

Routing with VPNs and multiple proxies

When a VPN coexists with several proxy configurations, requests from one application can use different endpoints and exits. This case study examines a macOS VPN, an application-specific private proxy and a public system proxy. It derives five external connection paths under explicit assumptions, examines DNS, UDP, bypass and fallback behavior, and provides an interactive model and commands for checking actual connections.

1. Scenario and assumptions

NodeExampleConstraint
P₁: application proxy10.77.0.10:18888Reachable only through VPN
P₂: system HTTP / HTTPS proxy203.0.113.80:18888Public address, potentially selected by VPN default routing
O: HTTPS origin198.51.100.40:443Public destination for the comparison
VPNTunnel interface and gatewayPrivate reachability; full-tunnel mode also has working public egress

The public IPs are documentation addresses, not live services. The initial model uses IPv4, new TCP connections, one external origin and explicit HTTP/1.1 proxies. It excludes extra proxy chains, transparent interception and special per-app routes. Proxy services and downstream egress work. DNS, IPv6, UDP, local destinations, caching and failures are considered separately.

2. Two path decisions

Application endpoint selection

A request using P₁ connects to 10.77.0.10. A system-configured request connects to P₂. Bypass or no-proxy requests connect to O. Application proxy configuration normally selects an endpoint for its requests; it does not implicitly chain through the system proxy. Another Session or library in the same application may still use the system configuration.

For example, one Electron Session can use P₁ while another explicitly uses system mode, and a Node or native request can connect directly. HTTP proxies and application configuration describes those scopes.

Routing the selected endpoint

The kernel routes the current socket destination: P₁, P₂ or O. P₁ requires VPN. Public P₂ and O can also match VPN default routes. DIRECT means no application proxy; it does not mean no VPN.

3. Five external path classes

Under these assumptions there are five viable topology classes. These are possible paths across configurations and requests, not five paths that one request automatically tries. Each concrete connection uses the choice made at that time; retries are separate attempts.

PathProxy selectionMac to first endpointOrigin connection owner
AApplication P₁Mac → VPN → P₁P₁
BSystem P₂Mac → ordinary network → P₂P₂
CSystem P₂Mac → VPN → P₂P₂
DDIRECT / bypassMac → ordinary network → OMac
EDIRECT / bypassMac → VPN → OMac; the gateway routes or performs NAT

P₁ over the ordinary network is not a sixth successful class: it violates the VPN-only premise. Such an attempt fails rather than creating a chain through P₂. Additional proxy-side tunnels or upstream proxies create more downstream topologies outside this client-side model.

5. Bypass, fallback and failure

DIRECT semantics

Bypass normally selects the origin directly. It does not select another OS proxy or remove VPN routes. A bypassed domain can use D or E. NO_PROXY matters only to a library that reads it; it is not a universal Chromium Session setting.

Explicit fallback lists

An effective PAC can explicitly return candidate proxies and then permit a direct attempt:

function FindProxyForURL(url, host) {
  return "PROXY 10.77.0.10:18888; PROXY 203.0.113.80:18888; DIRECT";
}

This is a candidate list, not a serial chain. The network stack determines which failures trigger fallback and how failed proxies are cached. An HTTP error response does not necessarily trigger the same handling as an unreachable proxy. With only P₁ configured, its failure normally fails the request. Electron proxyRules also supports candidate lists and direct:// with a different syntax. ProxyConfig; Chromium fallback.

VPN loss

Disconnecting a VPN differs from leaving routes pointed at a broken tunnel. Removing tunnel routes can restore ordinary access to P₂ or O if filtering permits, while P₁ remains unreachable. Retained routes can instead lead to timeouts. A kill switch can block otherwise reachable underlay traffic. Proxy settings do not determine this disconnect policy.

Configuration and sockets

Correlate proxy selection, socket peers and routing. Replace documentation addresses with the actual proxy and origin addresses:

scutil --proxy
scutil --dns

route -n get 203.0.113.80

Use await ses.resolveProxy(url) on the Session that makes the Electron request, and collect a NetLog for new requests. scutil shows OS settings, not every application override. Inspect the helper or network-service PID that owns the socket. Route lookup is evidence, but per-app and scoped policy can require packet or live-connection confirmation. Session proxy resolution.

Individual requests

# Private proxy: expect CONNECT through the VPN-reachable proxy
curl --noproxy "" --proxy http://10.77.0.10:18888 -v https://example.com/ -o /dev/null

# Public system proxy, made explicit for this curl test

curl --noproxy '*' -v https://example.com/ -o /dev/null

Explicit curl probes test endpoint reachability; they do not prove Electron selected the same endpoint. Correlate client progress with proxy and origin logs. An origin exit IP can help locate egress but cannot establish which client configuration was used.

Interface traffic

# Replace utun4 and en0 with the actual interfaces
sudo tcpdump -ni utun4 'host 10.77.0.10 and tcp port 18888'
sudo tcpdump -ni en0 'udp port 51820'

For WireGuard, the tunnel capture exposes inner packets addressed to the private proxy, while the physical capture shows outer UDP to the VPN endpoint. Other VPN protocols require different filters. Application TLS can still conceal content even when packets are visible on the interface.
