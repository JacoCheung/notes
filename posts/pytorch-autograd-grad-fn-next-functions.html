PyTorch Autograd 图结构解析：grad_fn、next_functions 与 AccumulateGrad

本文以 autograd 和 functional 为起点,整理 Python 侧 grad_fn、next_functions 与 C++ 侧 Node、Edge、InputBuffer 的对应关系。链式法则本身不展开,重点放在建图语义、backward 调度、fan-in 梯度规约,以及 Megatron-Core DDP 如何通过 identity/view op 接入 leaf 参数的梯度累加器。

0. 本文范围

PyTorch 官方 autograd mechanics 文档把 autograd 描述成一张由 Function 对象组成的反向图:forward 执行真实计算时,同时记录用于 backward 的图;反向从输出根节点走向输入叶子节点。这里的 Function 对应 C++ 里的 Node,而 Python 里 Tensor 的 .grad_fn 是进入这张 Node 图的入口。

本文只讨论 eager autograd 的常规路径。AOTAutograd、torch.compile、functorch、forward-mode AD 和 distributed autograd 都有额外层次,不纳入讨论。

1. Tensor 图与 Node 图

分析 autograd 时容易混在一起的是两张图。

对象 Python 侧看到什么 C++ 侧对应什么 含义
非叶子 Tensor y.grad_fn Node* 产生 y 的反向节点,例如 AddBackward0、SinBackward0。
叶子 Tensor p.grad_fn is None AccumulateGrad 叶子没有 grad_fn,但需要梯度时会有一个梯度累加器。它可以从下游节点的 next_functions 里看到。
反向边 (fn, input_nr) Edge(function, input_nr) function 是目标 Node,input_nr 是梯度要写入目标 Node 的哪个输入槽位。
下游到上游 node.next_functions Node::next_edges() 名字叫 next,但方向是 backward 的下一跳,也就是 forward 图里的上游。

Edge 在源码里只有两个字段:function 和 input_nr。Node 通过 next_edge(index)、next_edges() 维护这些边。这个结构解释了一个现象:多输出 op 的多个输出 Tensor 可以共享同一个 backward Node,只是它们携带的 output slot 不同。

Tensor.grad_fn 与 Node.next_edges 的关系

所以不要把 next_functions 读成“forward 的下一个 op”。它是 backward 图的边表。沿着它走,方向是从 loss 走回 leaves。

2. forward 如何建图

一个需要梯度的 op 在 forward 期间通常经历几步:

  1. 检查输入 Tensor 里是否有 requires_grad=True 的变量。
  2. 如果需要建图,创建这个 op 对应的 backward Node。
  3. 从输入 Tensor 收集反向边。非叶子输入返回自己的 grad_fn 与 output_nr;叶子输入返回它的 AccumulateGrad 与 slot 0。
  4. 执行真实 forward kernel。
  5. 把输出 Tensor 的 history 设置为刚创建的 backward Node,并记录输出属于这个 Node 的第几个输出槽位。

源码上可以对照几个位置。collect_next_edges 会对输入调用 gradient_edge。gradient_edge 对非叶子返回 grad_fn,对叶子返回 grad_accumulator。set_history 则把输出 Tensor 连接到当前 backward Node。自定义 C++ autograd::Function 的 apply 路径里,也能看到 collect_next_edges、set_next_edges、执行 forward、包装输出这条流程。

叶子 Tensor 的 .grad_fn 是 None,这不是说它没有出现在反向图里。它的反向入口是 AccumulateGrad,由下游 Node 的 next_functions 指过去。

3. next_functions 如何读

用一个二输出 identity op 展示。这个例子保留 Notion 原文里的二输出结构,同时增加两条消费同一输出的分支,让 fan-in 规约出现在图上。

import torch

class PairIdentity(torch.autograd.Function):
    @staticmethod
    def forward(ctx, a, b):
        return a, b

    @staticmethod
    def backward(ctx, grad_u, grad_v):
        return grad_u, grad_v

a = torch.randn(4, requires_grad=True)
b = torch.randn(4, requires_grad=True)

u, v = PairIdentity.apply(a, b)
p = u * 2.0
q = u.sin()
loss = (p + q + v).sum()

需要读出两个层次:

  • u.grad_fn 和 v.grad_fn 都指向同一个 PairIdentityBackward。
  • u 是 PairIdentityBackward 的第 0 个输出,v 是第 1 个输出。所以下游节点指回它时,边分别写成 (PairIdentityBackward, 0) 和 (PairIdentityBackward, 1)。

用数学符号写,这个 forward 是:

\[ (u, v) = \operatorname{PairIdentity}(a, b), \quad p = 2u, \quad q = \sin(u), \quad L = \sum_i (p_i + q_i + v_i) \]

反向时,同一个 u 被两条分支消费:

\[ \mathrm{d}u = \mathrm{d}p \cdot 2 + \mathrm{d}q \cdot \cos(u) \]

在这个例子里 \(\mathrm{d}p = 1\)、\(\mathrm{d}q = 1\),所以 \(\mathrm{d}u = 2 + \cos(u)\)。这两个分支的梯度不会让 PairIdentityBackward 执行两次。它们先进同一个 InputBuffer 的 slot 0,累加成一个 \(\mathrm{d}u\),然后 PairIdentityBackward 只执行一次。

包含多分支 fan-in 规约的反向图

如果在 Python 里打印,你通常会看到类似下面的结构,具体类名后缀会随版本和表达式嵌套略有差别:

loss.grad_fn
# SumBackward0

loss.grad_fn.next_functions[0][0]
# AddBackward0

# 其中某个 AddBackward0 的 next_functions 会指向:
#   (MulBackward0, 0)
#   (SinBackward0, 0)
#

#

#   (PairIdentityBackward, 1)
#
# PairIdentityBackward.next_functions 中有:
#   (AccumulateGrad(a), 0)
#   (AccumulateGrad(b), 0)

4. 多分支梯度的 fan-in 规约

回到规约问题:同一个 Tensor 被多个下游 op 消费时,反向产生的多个梯度 Tensor 是不是在图里形成一个独立规约节点?

对普通 eager backward 来说,Python 能遍历到的 grad_fn 图里不会多出一个显式的 AddBackward 节点专门做这件事。PyTorch engine 在内部给每个待执行 Node 准备一个 InputBuffer。源码注释把 NodeTask.inputs_ 称作所有流入梯度的隐式加法节点。因此,fan-in 规约是 engine 的执行状态,不是用户图上的新 Node。

它的行为可以按 slot 理解。对 PairIdentityBackward 来说:

  • MulBackward0 产生一份给 slot 0 的梯度。
  • SinBackward0 也产生一份给 slot 0 的梯度。
  • v 那条分支产生一份给 slot 1 的梯度。

InputBuffer::add(pos, grad) 看到第一份 slot 0 梯度时直接放入 buffer;看到第二份 slot 0 梯度时做 old + grad,或者在安全条件满足时用 add_ 复用 storage。所有依赖计数归零后,engine 才把这个 buffer 交给 PairIdentityBackward.apply([du, dv])。

InputBuffer 按 input_nr 聚合梯度

如果使用 backward(create_graph=True) 或某些高阶梯度路径,累加本身可能进入更高阶图,源码里也能看到 GradMode 打开时用 old_var + var。但训练里常见的 loss.backward() 路径,这个规约主要是 engine 内部状态。

5. backward 的迭代顺序

把 backward 说成 DFS 或 BFS 都不够准确。PyTorch engine 更接近“依赖计数 + ready queue”的迭代调度。

  1. 从 root edge 出发,遍历 next_edges(),统计每个 Node 还有多少下游依赖没有完成。这个计数放在 GraphTask.dependencies_。
  2. root Node 先进入 ready queue。单 loss 的常规路径可能直接用 loss 的 grad_fn;多 root 时会有额外的 root 聚合节点。
  3. worker 从 ready queue 取一个 NodeTask,调用 call_function 执行该 Node 的 backward。
  4. 当前 Node 产生的每个输出梯度,按照 fn.next_edge(i) 找到上游 Node 和 input_nr,调用对方的 InputBuffer::add(input_nr, grad)。
  5. 上游 Node 的依赖计数减 1。减到 0 时,它带着已经填好的 InputBuffer 进入 ready queue。
Engine 执行循环: dependency count + ready queue

执行顺序有两个层面。

第一层是拓扑约束:一个 Node 的所有下游用户都完成后,它才能执行。上面的 fan-in 例子里,PairIdentityBackward 要等 MulBackward0、SinBackward0 和 v 那条分支都把梯度写进 buffer 后才能运行。

第二层是 ready queue 的优先级。源码里同一 reentrant depth 下会比较 sequence_nr(),通常 forward 越晚创建的 Node,backward 越先执行。AccumulateGrad 例外,它的 sequence number 被设为 UINT64_MAX,所以一旦 ready 会被尽早调度。多设备、多线程、stream 同步和 reentrant backward 会让实际顺序更复杂,因此不要把 next_functions 的元组顺序当成数值累加顺序的稳定 ABI。

6. AccumulateGrad 与 leaf .grad

AccumulateGrad 是 leaf Tensor 的终点 Node。它的 apply 不再向上游返回梯度,而是把输入梯度写到 leaf 的 .grad 里。源码注释也把它称作 sink:接收一个输入,没有输出,副作用是累加梯度。

这也解释了为什么用户可以间接拿到 AccumulateGrad:

p = torch.randn(4, requires_grad=True)
y = p * 2

y.grad_fn
# MulBackward0

y.grad_fn.next_functions[0][0]
# AccumulateGrad for p

但 p.grad_fn 仍然是 None。叶子节点对外的 Tensor API 不把 accumulator 暴露在 .grad_fn 上,而是在内部用 grad_accumulator(p) 管理。只要某个需要梯度的 op 消费了这个 leaf,下游 Node 的 next_functions 就会指到它。

7. Megatron-Core DDP 的应用

Megatron-Core DDP 用到了上面这条性质。它要在每个参数的梯度累加完成后执行自己的逻辑:把 param.grad 加到 param.main_grad,清空 param.grad,并在开启 overlap 时通知 bucket 这个参数的梯度已经 ready。直接限制是参数属于 leaf Tensor,访问 param.grad_fn 得到的是 None。

Megatron-Core 的做法是先创建一个廉价的 view/identity 式 op:

# NVIDIA/Megatron-LM core_r0.10.0
if param.requires_grad:
    # Expand so we get access to grad_fn.
    param_tmp = param.expand_as(param)
    # Get the gradient accumulator function.
    grad_acc = param_tmp.grad_fn.next_functions[0][0]
    grad_acc.register_hook(self._make_backward_post_hook(param))
    self.grad_accs.append(grad_acc)

expand_as 对 shape 相同的参数来说不需要复制数据,但它会产生一个非叶子 Tensor param_tmp。这个 Tensor 有 grad_fn,通常是 ExpandBackward0 或同类 view backward Node。由于 param_tmp 的输入是 leaf 参数,所以 param_tmp.grad_fn.next_functions[0][0] 指向原参数的 AccumulateGrad。

Megatron-Core DDP 通过 identity/view op 取得 leaf 参数的 AccumulateGrad

后面的 hook 逻辑在同一个文件里。_make_backward_post_hook 会在参数属于某个 bucket 时检查 param.grad,把它加到 param.main_grad,随后设置 param.grad = None。如果配置了 overlap_grad_reduce,它还会调用 register_grad_ready(param),让 bucket 可以在梯度就绪后发起 all-reduce 或 reduce-scatter。

这个技巧有两个前提:

  • expand_as 必须真的创建出可追踪的非叶子 Tensor。如果 requires_grad=False 或处在不建图上下文里,这条路拿不到 accumulator。
  • 拿到的 grad_acc 要保存下来。Megatron 把它放进 self.grad_accs,避免 hook 挂载的对象过早释放。

也要注意边界。grad_fn 和 next_functions 可以用于调试、观察和少量内部集成,但它们不是给普通模型代码改图用的稳定抽象。Megatron 这样做服务于训练系统里的梯度 bucket 和通信 overlap,同时也让代码与 PyTorch autograd 内部结构发生耦合。
