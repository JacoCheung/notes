PyTorch Autograd 图结构解析：grad_fn、next_functions 与 AccumulateGrad

本文以 autograd 和 functional 为起点,只站在 Python 可观察对象上解释 grad_fn 与 next_functions。链式法则本身不展开,重点放在 forward 如何挂上 grad_fn、backward 如何沿 next_functions 执行、fan-in 梯度如何累加,以及 Megatron-Core DDP 如何通过 identity/view op 接入 leaf 参数的梯度累加器。

0. 本文范围

PyTorch 官方 autograd mechanics 文档把 autograd 描述成一张由 Function 对象组成的反向图:forward 执行真实计算时,同时记录用于 backward 的图;反向从输出 Tensor 走向输入 leaves。在 Python 里,Tensor 的 .grad_fn 就是进入这张反向图的入口。

本文只讨论 eager autograd 的常规路径。文章里的“图”和“边”都指 Python 里能通过 .grad_fn、.next_functions 观察到的结构。

1. Tensor 与 grad_fn 图

先把几个 Python 侧对象分清楚。

对象 Python 侧看到什么 含义 典型打印
非叶子 Tensor y.grad_fn 产生 y 的反向函数,例如 AddBackward0、SinBackward0。 <AddBackward0 ...>
叶子 Tensor p.grad_fn is None 用户直接创建并设置 requires_grad=True 的 Tensor。叶子没有 grad_fn,这一点不要和 AccumulateGrad 混在一起。 None
next_functions y.grad_fn.next_functions 当前反向函数的上游依赖。沿着它走,方向是从 loss 走回输入 Tensor。 ((fn0, 0), (fn1, 0))
叶子累加器 AccumulateGrad 它不是 leaf 的 grad_fn。它是 autograd 为 leaf 准备的梯度累加函数,只能从下游 next_functions 间接看到。 <AccumulateGrad ...>
tuple 第二项 (fn, input_nr) 同一个反向函数可能对应多个输出。input_nr 标记梯度要进入这个反向函数的哪个输入槽位。 (PairIdentityBackward, 1)

下面这段代码对应第一张图。它只用了一个乘法和一个加法,因此 y.grad_fn 是 AddBackward0。这个 AddBackward0 有两个输入来源:一个是中间结果 x = a * b,另一个是 leaf Tensor c。

import torch

a = torch.randn(4, requires_grad=True)
b = torch.randn(4, requires_grad=True)
c = torch.randn(4, requires_grad=True)

x = a * b
y = x + c

print(y.grad_fn)
# <AddBackward0 ...>

print(y.grad_fn.next_functions)
# (
#   (<MulBackward0 ...>, 0),
#   (<AccumulateGrad ...>, 0),
# )
Tensor.grad_fn 与 grad_fn.next_functions 的关系

所以不要把 next_functions 读成“forward 的下一个 op”。它是 backward 图的边表。沿着它走,方向是从 loss 走回 leaves。

2. forward 如何建图

从 Python 侧看,一个需要梯度的 op 在 forward 期间会留下几类信息:

  1. 检查输入 Tensor 里是否有 requires_grad=True 的变量。
  2. 如果需要建图,输出 Tensor 会带上 grad_fn,例如 AddBackward0。
  3. grad_fn.next_functions 会记录这个 op 的输入来自哪里。输入是非叶子 Tensor 时,它指向该 Tensor 的 grad_fn;输入是叶子 Tensor 时,它指向该 leaf 对应的 AccumulateGrad。
  4. 叶子 Tensor 本身仍然没有 grad_fn。AccumulateGrad 不是 leaf 的 .grad_fn,只是反向图最终把梯度写回 leaf .grad 的入口。
  5. 多输出 op 的多个输出可以共享同一个 grad_fn,tuple 里的第二个整数用来区分梯度回到这个 grad_fn 的哪个输出槽位。

继续看第一张图里的例子。x = a * b 产生非叶子 Tensor x,所以 x.grad_fn 是 MulBackward0。再执行 y = x + c 时,y.grad_fn 是 AddBackward0,它的 next_functions 第一项指向 x.grad_fn,第二项指向 leaf c 的 AccumulateGrad。

叶子 Tensor 的 .grad_fn 一定是 None。如果在下游 next_functions 里看到了 AccumulateGrad,含义是“反向到这里以后把梯度累加到这个 leaf 的 .grad”,不是“这个 leaf 有 grad_fn”。

3. next_functions 如何读

用一个二输出 identity op 展示。这个例子保留 Notion 原文里的二输出结构,同时增加两条消费同一输出的分支,让 fan-in 规约出现在图上。

import torch

class PairIdentity(torch.autograd.Function):
    @staticmethod
    def forward(ctx, a, b):
        return a, b

    @staticmethod
    def backward(ctx, grad_u, grad_v):
        return grad_u, grad_v

a = torch.randn(4, requires_grad=True)
b = torch.randn(4, requires_grad=True)

u, v = PairIdentity.apply(a, b)
p = u * 2.0
q = u.sin()
loss = (p + q + v).sum()

需要读出两个层次:

  • u.grad_fn 和 v.grad_fn 都指向同一个 PairIdentityBackward。
  • u 是 PairIdentityBackward 的第 0 个输出,v 是第 1 个输出。所以下游反向函数指回它时,tuple 分别写成 (PairIdentityBackward, 0) 和 (PairIdentityBackward, 1)。

用数学符号写,这个 forward 是:

\[ (u, v) = \operatorname{PairIdentity}(a, b), \quad p = 2u, \quad q = \sin(u), \quad L = \sum_i (p_i + q_i + v_i) \]

反向时,同一个 u 被两条分支消费:

\[ \mathrm{d}u = \mathrm{d}p \cdot 2 + \mathrm{d}q \cdot \cos(u) \]

在这个例子里 \(\mathrm{d}p = 1\)、\(\mathrm{d}q = 1\),所以 \(\mathrm{d}u = 2 + \cos(u)\)。这两个分支的梯度不会让 PairIdentityBackward 执行两次。它们先在 PairIdentityBackward 的第 0 个梯度槽位上累加成一个 \(\mathrm{d}u\),然后 PairIdentityBackward 只执行一次。

包含多分支 fan-in 规约的反向图

如果在 Python 里打印,你通常会看到类似下面的结构,具体类名后缀会随版本和表达式嵌套略有差别:

loss.grad_fn
# SumBackward0

loss.grad_fn.next_functions[0][0]
# AddBackward0

# 其中某个 AddBackward0 的 next_functions 会指向:
#   (MulBackward0, 0)
#   (SinBackward0, 0)
#
# MulBackward0.next_functions 中有:
#   (PairIdentityBackward, 0)
#
# SinBackward0.next_functions 中也有:
#   (PairIdentityBackward, 0)
#
# 另一路 v 会指向:
#   (PairIdentityBackward, 1)
#
# PairIdentityBackward.next_functions 中有:
#   (AccumulateGrad(a), 0)
#   (AccumulateGrad(b), 0)

4. 多分支梯度的 fan-in 规约

回到规约问题:同一个 Tensor 被多个下游 op 消费时,反向产生的多个梯度 Tensor 是不是在图里形成一个独立规约节点?

对普通 eager backward 来说,Python 能遍历到的 grad_fn 图里不会多出一个显式的 AddBackward 节点专门做这件事。你能观察到的是:同一个上游反向函数只执行一次,它收到的某个 grad_x 已经是多个下游分支相加后的结果。

它的行为可以按 slot 理解。对 PairIdentityBackward 来说:

  • MulBackward0 产生一份给 slot 0 的梯度。
  • SinBackward0 也产生一份给 slot 0 的梯度。
  • v 那条分支产生一份给 slot 1 的梯度。

可以把它理解为 PairIdentityBackward 有一个待填充的梯度参数表。第一条分支填入 slot 0,第二条分支也写入 slot 0,于是这两份梯度先相加。等 slot 0 和 slot 1 都准备好以后,autograd 才调用一次 PairIdentityBackward.backward(ctx, grad_u, grad_v)。

class PairIdentity(torch.autograd.Function):
    @staticmethod
    def forward(ctx, a, b):
        return a, b

    @staticmethod
    def backward(ctx, grad_u, grad_v):
        print("grad_u =", grad_u)  # 已经包含 u * 2 和 u.sin() 两条分支
        print("grad_v =", grad_v)
        return grad_u, grad_v
grad_fn.next_functions 按 input_nr 聚合梯度

所以“有没有独立规约节点”的回答是:从 Python 的 grad_fn.next_functions 图上看,没有。规约发生在某个反向函数真正被调用之前,最后体现为它收到的 grad_u 已经合并。

5. backward 的迭代顺序

从 Python 图上看,backward 从 loss.grad_fn 开始,沿着 next_functions 逐步走回 leaves。它不是简单地把某个分支一路走到底:如果一个上游反向函数被多个下游分支依赖,它要等这些分支的梯度都准备好以后才会被调用。

  1. loss.backward() 先把初始梯度交给 loss.grad_fn。
  2. 当前 grad_fn 运行自己的 backward,得到对它输入 Tensor 的梯度。
  3. 每一份输入梯度按照 next_functions 里的 (fn, input_nr) 送给上游反向函数的对应槽位。
  4. 如果同一个槽位收到多份梯度,先相加。
  5. 某个上游反向函数需要的梯度都准备好以后,它才会被调用。
  6. 走到 AccumulateGrad 时,梯度被写入对应 leaf Tensor 的 .grad。
backward 从 loss.grad_fn 沿 next_functions 迭代

执行顺序有两个层面。

第一层是依赖约束:一个反向函数的所有下游梯度都准备好后,它才能执行。上面的 fan-in 例子里,PairIdentityBackward 要等 MulBackward0、SinBackward0 和 v 那条分支都贡献梯度后才能运行。

第二层是同一批可执行反向函数之间的调度顺序。这个顺序不适合作为写模型逻辑的依据。对理解 next_functions 更重要的是依赖关系:某条边指向谁,以及 tuple 里的 input_nr 是多少。

6. AccumulateGrad 与 leaf .grad

AccumulateGrad 是 leaf Tensor 的梯度累加函数。它不是 leaf 的 grad_fn。leaf Tensor 的 grad_fn 仍然是 None。

这也解释了为什么用户可以间接拿到 AccumulateGrad:

p = torch.randn(4, requires_grad=True)
y = p * 2

y.grad_fn
# MulBackward0

y.grad_fn.next_functions[0][0]
# AccumulateGrad for p

这段代码的边界是:用户拿不到 p.grad_fn,因为它就是 None;但用户可以从消费 p 的下游反向函数里看到 AccumulateGrad。反向走到这个对象时,梯度会被累加到 p.grad。

7. Megatron-Core DDP 的应用

Megatron-Core DDP 用到了上面这条性质。它要在每个参数的梯度累加完成后执行自己的逻辑:把 param.grad 加到 param.main_grad,清空 param.grad,并在开启 overlap 时通知 bucket 这个参数的梯度已经 ready。直接限制是参数属于 leaf Tensor,访问 param.grad_fn 得到的是 None。

Megatron-Core 的做法是先创建一个廉价的 view/identity 式 op:

# NVIDIA/Megatron-LM core_r0.10.0
if param.requires_grad:
    # Expand so we get access to grad_fn.
    param_tmp = param.expand_as(param)
    # Get the gradient accumulator function.
    grad_acc = param_tmp.grad_fn.next_functions[0][0]
    grad_acc.register_hook(self._make_backward_post_hook(param))
    self.grad_accs.append(grad_acc)

expand_as 对 shape 相同的参数来说不需要复制数据,但它会产生一个非叶子 Tensor param_tmp。这个 Tensor 有 grad_fn,通常能看到 ExpandBackward0 或同类 view 反向函数。由于 param_tmp 的输入是 leaf 参数,所以 param_tmp.grad_fn.next_functions[0][0] 指向原参数的 AccumulateGrad。

Megatron-Core DDP 通过 identity/view op 取得 leaf 参数的 AccumulateGrad

后面的 hook 逻辑在同一个文件里。_make_backward_post_hook 会在参数属于某个 bucket 时检查 param.grad,把它加到 param.main_grad,随后设置 param.grad = None。如果配置了 overlap_grad_reduce,它还会调用 register_grad_ready(param),让 bucket 可以在梯度就绪后发起 all-reduce 或 reduce-scatter。

这个技巧有两个前提:

  • expand_as 必须真的创建出可追踪的非叶子 Tensor。如果 requires_grad=False 或处在不建图上下文里,这条路拿不到 accumulator。
  • 拿到的 grad_acc 要保存下来。Megatron 把它放进 self.grad_accs,避免 hook 挂载的对象过早释放。

也要注意边界。grad_fn 和 next_functions 可以用于调试、观察和少量内部集成,但它们不是给普通模型代码改图用的稳定抽象。Megatron 这样做服务于训练系统里的梯度 bucket 和通信 overlap,同时也让代码与 PyTorch autograd 内部结构发生耦合。
