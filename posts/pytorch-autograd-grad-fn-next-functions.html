PyTorch Autograd 反向图模型：grad_fn、next_functions 与 AccumulateGrad

PyTorch eager 模式在执行 forward 运算的同时，记录 backward 所需的反向关系。模型一旦出现分支、共享 Tensor 或参数 hook，只看 forward Tensor 已经无法解释梯度沿哪条路径回传，以及何时写入 leaf 的 .grad。Python 暴露的 grad_fn 与 next_functions 提供了进入这张反向图的观察入口；沿着这些对象，可以建立 Node、梯度槽位、fan-in 累加和 AccumulateGrad 之间的完整关系。

图模型与版本边界

PyTorch 2.12 autograd mechanics 将 autograd 描述为一张由 Function 对象组成的反向图。forward 执行实际计算并记录求导历史，backward 再从输出 Tensor 逆向传播到输入 leaves。在 Python 侧，非叶子 Tensor 的 .grad_fn 指向产生它的反向 Node，Node 的 .next_functions 则记录梯度继续传播的目标。

下文讨论 PyTorch 2.12 eager autograd 的常规路径，“图”和“边”均指上述 Python 可观察结构。关于 fan-in 的调度描述来自可复现实验，不扩展为未公开的 engine 实现承诺。Megatron-Core 案例固定在 commit 7ee599a，后续版本可能采用不同的 hook 接口。

Tensor 与 grad_fn 图

理解这张反向图需要区分几个 Python 侧对象。

对象 Python 侧看到什么 含义 典型打印
非叶子 Tensor y.grad_fn 产生 y 的反向函数，例如 AddBackward0、SinBackward0。 <AddBackward0 ...>
叶子 Tensor p.grad_fn is None 用户直接创建并设置 requires_grad=True 的 Tensor；它没有生成自身的 operation，因此 grad_fn 为 None。 None
next_functions y.grad_fn.next_functions 当前反向函数的上游依赖。沿着它走，方向是从 loss 走回输入 Tensor。 ((fn0, 0), (fn1, 0))
叶子累加器 AccumulateGrad 本文版本 eager 图中的 leaf 梯度累加节点。反向传播到这里时，梯度写入对应 leaf 的 .grad；下游 Node 的 next_functions 可以间接指向它。 <AccumulateGrad ...>
tuple 第二项 (fn, input_nr) 公开 API 返回 (Node | None, int)。在本文的多输出实验中，这个整数区分目标 Node 的输出梯度槽位；具体内部语义不属于稳定的模型接口。 (PairIdentityBackward, 1)

下面的最小程序包含一个乘法和一个加法。y.grad_fn 因而是 AddBackward0，它的两个输入分别来自中间结果 x = a * b 与 leaf Tensor c。

import torch

a = torch.randn(4, requires_grad=True)
b = torch.randn(4, requires_grad=True)
c = torch.randn(4, requires_grad=True)

x = a * b
y = x + c

print(y.grad_fn)
# <AddBackward0 ...>

print(y.grad_fn.next_functions)
# (
#   (<MulBackward0 ...>, 0),
#   (<AccumulateGrad ...>, 0),
# )
Tensor.grad_fn 与 grad_fn.next_functions 的关系

next_functions 是当前反向 Node 的出边表，边的方向与求导传播一致，从 loss 逐步走向 leaves。名称中的 “next” 描述 backward 的下一跳，而不是 forward 的执行顺序。

forward 建图过程

当一个 operation 的输入需要梯度时，forward 结果会留下以下可观察关系：

  1. 检查输入 Tensor 里是否有 requires_grad=True 的变量。
  2. 如果需要建图，输出 Tensor 会带上 grad_fn，例如 AddBackward0。
  3. grad_fn.next_functions 会记录这个 op 的输入来自哪里。输入是非叶子 Tensor 时，它指向该 Tensor 的 grad_fn；输入是叶子 Tensor 时，它指向该 leaf 对应的 AccumulateGrad。
  4. 叶子 Tensor 的 grad_fn 保持为 None；对应的 AccumulateGrad 位于反向边的终点，负责把梯度写入 leaf .grad。
  5. 多输出 op 的多个输出可以共享同一个 grad_fn，tuple 里的第二个整数用来区分梯度回到这个 grad_fn 的哪个输出槽位。

回到第一张图，x = a * b 产生非叶子 Tensor x，因此 x.grad_fn 是 MulBackward0。执行 y = x + c 后，y.grad_fn 成为 AddBackward0；它的 next_functions 第一项指向 x.grad_fn，第二项指向 leaf c 的 AccumulateGrad。这两类输入共同构成反向图的递归连接规则。

叶子 Tensor 的 .grad_fn 为 None；它对应的 AccumulateGrad 由消费该 leaf 的下游 Node 通过 next_functions 指向。两者分属 Tensor 属性与反向图 Node 两个层次。

next_functions 的边与槽位

二输出 identity op 可以同时显露 tuple 槽位和 fan-in 行为。下面增加两条消费同一输出的分支，让 fan-in 规约出现在图上。

import torch

class PairIdentity(torch.autograd.Function):
    @staticmethod
    def forward(ctx, a, b):
        return a, b

    @staticmethod
    def backward(ctx, grad_u, grad_v):
        return grad_u, grad_v

a = torch.randn(4, requires_grad=True)
b = torch.randn(4, requires_grad=True)

u, v = PairIdentity.apply(a, b)
p = u * 2.0
q = u.sin()
loss = (p + q + v).sum()

本文把这段代码在 PyTorch 2.12 eager 模式下呈现的参数合并行为称为 slot 模型。官方 Node.next_functions 文档只公开返回类型，没有把 tuple 整数的内部语义或 slot 聚合方式定义为稳定契约；生成类名的数字后缀也可能随版本变化。

需要读出两个层次:

  • u.grad_fn 和 v.grad_fn 都指向同一个 PairIdentityBackward。
  • u 是 PairIdentityBackward 的第 0 个输出，v 是第 1 个输出。在本文版本的打印结果里，下游反向函数指回它时，tuple 分别写成 (PairIdentityBackward, 0) 和 (PairIdentityBackward, 1)。

用数学符号写，这个 forward 是：

\[ (u, v) = \operatorname{PairIdentity}(a, b), \quad p = 2u, \quad q = \sin(u), \quad L = \sum_i (p_i + q_i + v_i) \]

反向时，同一个 u 被两条分支消费：

\[ \mathrm{d}u = \mathrm{d}p \cdot 2 + \mathrm{d}q \cdot \cos(u) \]

在这个例子里 \(\mathrm{d}p = 1\)、\(\mathrm{d}q = 1\)，所以 slot 0 最终需要接收 \(\mathrm{d}u = 2 + \cos(u)\)。图中的 MulBackward0 与 SinBackward0 都通过 (PairIdentityBackward, 0) 指向这个槽位。多条边如何形成一次 Node 调用，则由下一节的 fan-in 规约解释。

多分支梯度的 fan-in 规约

fan-in 梯度规约是指多个下游分支为同一上游输入产生梯度贡献后，autograd 在调用目标反向 Node 之前，按梯度槽位合并这些贡献。共享 Tensor u 同时进入乘法与正弦分支时，两条反向路径都会向 PairIdentityBackward 的 slot 0 写入梯度。

在这段普通 eager backward 实验中，规约由目标 Node 执行前的梯度参数聚合体现：PairIdentityBackward 只执行一次，收到的 grad_u 已经包含两条分支之和。Python 可遍历的 grad_fn 图不会为这次聚合额外暴露一个 AddBackward Node。

它的行为可以按 slot 理解。对 PairIdentityBackward 来说:

  • MulBackward0 产生一份给 slot 0 的梯度。
  • SinBackward0 也产生一份给 slot 0 的梯度。
  • v 那条分支产生一份给 slot 1 的梯度。

可以把 PairIdentityBackward 理解为持有一张待填充的梯度参数表。两条 u 分支共同填充 slot 0，v 分支填充 slot 1。等本次 backward 中所有相关依赖都完成后，autograd 调用一次 PairIdentityBackward.backward(ctx, grad_u, grad_v)。

class PairIdentity(torch.autograd.Function):
    @staticmethod
    def forward(ctx, a, b):
        return a, b

    @staticmethod
    def backward(ctx, grad_u, grad_v):
        print("grad_u =", grad_u)  # 已经包含 u * 2 和 u.sin() 两条分支
        print("grad_v =", grad_v)
        return grad_u, grad_v
fan-in 梯度聚合的 slot 模型

这幅图用 slot 表示梯度参数的聚合位置。Python 通过 next_functions 可以遍历相连的 Node 及其 tuple 整数，但不能把 slot 本身作为独立图对象访问。

backward 的依赖顺序

backward 从 loss.grad_fn 接收初始梯度，再沿 next_functions 向 leaves 推进。Node 的可执行条件由依赖决定：当多个下游分支汇入同一个上游 Node 时，engine 先收集这些分支的梯度贡献，再调度该 Node。

  1. loss.backward() 先把初始梯度交给 loss.grad_fn。
  2. 当前 grad_fn 运行自己的 backward，得到对它输入 Tensor 的梯度。
  3. 每一份输入梯度按照 next_functions 里的 (fn, input_nr) 送给上游反向函数的对应槽位。
  4. 同一个槽位收到多份梯度时，先完成相加。
  5. 某个上游反向函数需要的梯度都准备好以后，engine 调用该函数。
  6. 走到 AccumulateGrad 时，梯度被写入对应 leaf Tensor 的 .grad。
backward 从 loss.grad_fn 沿 next_functions 迭代

这套顺序包含依赖约束与 ready Node 调度两个层面。依赖约束要求 PairIdentityBackward 等待 MulBackward0、SinBackward0 和 v 分支的贡献；当多个 Node 同时 ready 时，engine 可以选择其中的执行次序。模型逻辑应依赖图中的边和槽位关系，而不依赖同批 ready Node 的具体先后顺序。

AccumulateGrad 与 leaf .grad

AccumulateGrad 是本文版本 eager 图中观察到的 leaf 梯度累加 Node。反向传播到达它时，梯度并入相应 leaf Tensor 的 .grad。根据官方 leaf 文档，用户创建且需要梯度的 leaf 没有生成自身的 operation，所以 p.grad_fn 为 None；消费 p 的下游 Node 则可以通过 next_functions 指向这个累加器。

这条连接使 Python 代码能够从下游 Node 间接取得 AccumulateGrad：

p = torch.randn(4, requires_grad=True)
y = p * 2

y.grad_fn
# MulBackward0

y.grad_fn.next_functions[0][0]
# AccumulateGrad for p

AccumulateGrad 的类名属于实现观察，并未作为普通模型代码的稳定接口单独承诺。这个边界在框架代码利用 Node hook 时尤其重要。

Megatron-Core DDP 的参数 hook

Megatron-Core DDP 需要在每个参数的本地梯度累加完成后执行一组动作：把 param.grad 加入 param.main_grad，清空 param.grad，并在启用 overlap 时通知 bucket 该参数已经 ready。AccumulateGrad 正好位于这一就绪时刻，但参数本身是 leaf，param.grad_fn 为 None。固定版本的实现通过临时非叶子 Tensor 暴露通往累加器的反向边。

源码先创建一个开销很小、行为近似 identity 的 view operation：

# NVIDIA/Megatron-LM core_r0.10.0
if param.requires_grad:
    # Expand so we get access to grad_fn.
    param_tmp = param.expand_as(param)
    # Get the gradient accumulator function.
    grad_acc = param_tmp.grad_fn.next_functions[0][0]
    grad_acc.register_hook(self._make_backward_post_hook(param))
    self.grad_accs.append(grad_acc)

expand_as 等价于按另一个 Tensor 的尺寸调用 expand；这里 shape 没有变化，不需要复制参数数据，但会产生一个可追踪的非叶子 Tensor param_tmp。在固定 commit 配套的 PyTorch eager 运行中，它通常显示为 ExpandBackward0 或同类 view 反向函数；具体生成类名并非 Megatron 的接口约束。固定源码依赖的是 param_tmp.grad_fn.next_functions[0][0] 能取得原参数的梯度累加节点。

Megatron-Core DDP 通过 identity/view op 取得 leaf 参数的 AccumulateGrad

后面的 hook 逻辑位于同一份固定版本源码中。_make_backward_post_hook 会在参数属于某个 bucket 时检查 param.grad，把它加到 param.main_grad，随后设置 param.grad = None。如果配置了 overlap_grad_reduce，它还会调用 register_grad_ready(param)。后续发起 all-reduce 还是 reduce-scatter，由同一版本的 DDP 配置与 bucket 实现决定。

这条访问路径依赖两个条件：

  • expand_as 必须创建出可追踪的非叶子 Tensor；requires_grad=False 或禁用 autograd 记录的上下文不会产生这条反向边。
  • grad_acc 必须保持存活。Megatron 将它保存在 self.grad_accs 中，维持承载 hook 的对象生命周期。

PyTorch 2.12 还提供公开的 Tensor.register_post_accumulate_grad_hook()，在 leaf Tensor 的 .grad 更新后运行。只需要 leaf post-accumulation 回调的扩展代码可以优先评估这个公开接口；这里保留 AccumulateGrad Node hook，是因为它对应固定 Megatron commit 的实际实现。

这个案例把整张反向图串联起来：grad_fn 提供入口，next_functions 指向 leaf 的累加器，fan-in 保证 hook 看到已经合并的本地梯度。Megatron 借此连接梯度 bucket 与通信 overlap，同时接受对 PyTorch autograd 内部结构的版本耦合。

The PyTorch Autograd Reverse Graph: grad_fn, next_functions, and AccumulateGrad

PyTorch eager mode records the reverse relationships required by backward while it executes forward operations. Once a model contains branches, shared tensors, or parameter hooks, forward tensors alone no longer explain where gradients travel or when they reach a leaf's .grad. The Python-visible grad_fn and next_functions objects provide an entry point into that reverse graph and connect its nodes, gradient slots, fan-in accumulation, and AccumulateGrad endpoints.

Graph model and version scope

The PyTorch 2.12 autograd mechanics note describes autograd as a reverse graph of Function objects. Forward execution performs the requested computation and records its differentiation history; backward travels from output tensors toward input leaves. In Python, a non-leaf tensor's .grad_fn points to the reverse node that produced it, and the node's .next_functions records the destinations for further gradient propagation.

The discussion covers the ordinary PyTorch 2.12 eager autograd path, and “graph” and “edge” refer to these Python-visible structures. The fan-in scheduling model is derived from a reproducible experiment rather than presented as an undisclosed engine contract. The Megatron-Core example is pinned to commit 7ee599a; later releases may use a different hook interface.

Tensors and the grad_fn graph

The Python-facing objects are easier to read once their roles are separated.

Object Visible from Python Meaning Typical output
Non-leaf tensor y.grad_fn The backward function that produced y, such as AddBackward0 or SinBackward0. <AddBackward0 ...>
Leaf tensor p.grad_fn is None A tensor created directly by the user with requires_grad=True. Because no operation produced it, its grad_fn is None. None
next_functions y.grad_fn.next_functions The upstream dependencies of the current backward function. Following them moves from the loss toward input tensors. ((fn0, 0), (fn1, 0))
Leaf accumulator AccumulateGrad The leaf-gradient accumulation node observed in the eager graph examined here. Backward writes into the leaf's .grad at this node, which can be reached through a downstream node's next_functions. <AccumulateGrad ...>
Second tuple item (fn, input_nr) The public API returns a (Node | None, int) pair. In the multi-output experiment below, the integer distinguishes output-gradient slots on the target node; its internal interpretation is not a stable model API. (PairIdentityBackward, 1)

The following minimal program contains one multiplication and one addition. Its y.grad_fn is consequently AddBackward0, with inputs from the intermediate value x = a * b and the leaf tensor c.

import torch

a = torch.randn(4, requires_grad=True)
b = torch.randn(4, requires_grad=True)
c = torch.randn(4, requires_grad=True)

x = a * b
y = x + c

print(y.grad_fn)
# <AddBackward0 ...>

print(y.grad_fn.next_functions)
# (
#   (<MulBackward0 ...>, 0),
#   (<AccumulateGrad ...>, 0),
# )
Relationship between Tensor.grad_fn and grad_fn.next_functions

next_functions is the outgoing edge list of the current reverse node. Following these edges moves from the loss toward the leaves; “next” refers to the next backward destination rather than forward execution order.

Graph construction during forward

When an operation receives an input that requires gradients, its forward result leaves the following observable relationships:

  1. Autograd checks whether any input tensor has requires_grad=True.
  2. If the operation must be recorded, the output tensor receives a grad_fn, such as AddBackward0.
  3. grad_fn.next_functions records where each input came from. For a non-leaf input, it points to that tensor's grad_fn. For a leaf input, it points to the leaf's AccumulateGrad.
  4. The leaf tensor keeps grad_fn=None. Its AccumulateGrad node is the endpoint of a reverse edge and writes the arriving gradient into the leaf's .grad.
  5. Several outputs of one operation can share a grad_fn. The integer in each tuple distinguishes the output slot whose gradient flows back to that node.

In the earlier example, x = a * b creates a non-leaf tensor, so x.grad_fn is MulBackward0. After y = x + c, y.grad_fn is AddBackward0. Its first next_functions entry points to x.grad_fn, while the second points to the AccumulateGrad node for leaf c. These two cases form the recursive connection rule of the reverse graph.

A leaf tensor has .grad_fn=None, while the downstream node that consumes it can point to the corresponding AccumulateGrad through next_functions. The tensor attribute and the reverse-graph node belong to separate layers of the model.

Edges and slots in next_functions

A two-output identity operation makes the tuple entries visible. Two consumers of the same output also make fan-in reduction appear in the graph.

import torch

class PairIdentity(torch.autograd.Function):
    @staticmethod
    def forward(ctx, a, b):
        return a, b

    @staticmethod
    def backward(ctx, grad_u, grad_v):
        return grad_u, grad_v

a = torch.randn(4, requires_grad=True)
b = torch.randn(4, requires_grad=True)

u, v = PairIdentity.apply(a, b)
p = u * 2.0
q = u.sin()
loss = (p + q + v).sum()

This article uses slot model for the argument-aggregation behavior observed when this program runs under PyTorch 2.12 eager mode. The official Node.next_functions documentation specifies the return type but does not define either the tuple integer's internal meaning or slot aggregation as a stable contract. Numeric suffixes on generated class names can also change between versions.

There are two levels to read:

  • u.grad_fn and v.grad_fn refer to the same PairIdentityBackward object.
  • u is output 0 of PairIdentityBackward, while v is output 1. In the output observed for this version, downstream backward functions point back to them as (PairIdentityBackward, 0) and (PairIdentityBackward, 1).

Mathematically, the forward computation is:

\[ (u, v) = \operatorname{PairIdentity}(a, b), \quad p = 2u, \quad q = \sin(u), \quad L = \sum_i (p_i + q_i + v_i) \]

During backward, two branches contribute gradients to the same u:

\[ \mathrm{d}u = \mathrm{d}p \cdot 2 + \mathrm{d}q \cdot \cos(u) \]

In this example, \(\mathrm{d}p = 1\) and \(\mathrm{d}q = 1\), so slot 0 must eventually receive \(\mathrm{d}u = 2 + \cos(u)\). Both MulBackward0 and SinBackward0 reach that slot through (PairIdentityBackward, 0). The fan-in mechanism in the next section explains how these edges become one node invocation.

Backward graph with multi-branch fan-in reduction

Printing the graph from Python usually produces a structure like the one below. Exact numeric suffixes vary with the PyTorch version and expression nesting.

loss.grad_fn
# SumBackward0

loss.grad_fn.next_functions[0][0]

#   (PairIdentityBackward, 0)

# SinBackward0.next_functions also contains:
#   (PairIdentityBackward, 0)

#   (PairIdentityBackward, 1)
#
# PairIdentityBackward.next_functions contains:
#   (AccumulateGrad(a), 0)
#   (AccumulateGrad(b), 0)

Fan-in gradient reduction

Fan-in gradient reduction is the process of combining contributions from several downstream branches by gradient slot before the target reverse node runs. When the shared tensor u enters both the multiplication and sine branches, each reverse path contributes to slot 0 of PairIdentityBackward.

In this ordinary eager-backward experiment, reduction appears as aggregation of the target node's gradient arguments: PairIdentityBackward runs once, and its grad_u already contains the sum of both branches. The Python-visible grad_fn graph exposes no additional AddBackward node for this aggregation.

A slot model describes the behavior of PairIdentityBackward:

  • MulBackward0 contributes one gradient to slot 0.
  • SinBackward0 contributes another gradient to slot 0.
  • The branch through v contributes one gradient to slot 1.

Conceptually, PairIdentityBackward holds a pending table of gradient arguments. The two u branches fill slot 0 together, while the v branch fills slot 1. After all relevant dependencies in the current backward pass complete, autograd calls PairIdentityBackward.backward(ctx, grad_u, grad_v) once.

class PairIdentity(torch.autograd.Function):
    @staticmethod
    def forward(ctx, a, b):
        return a, b

    @staticmethod
    def backward(ctx, grad_u, grad_v):
        print("grad_u =", grad_u)  # includes both u * 2 and u.sin()
        print("grad_v =", grad_v)
        return grad_u, grad_v
Slot model of fan-in gradient accumulation

The diagram uses slots to represent where gradient arguments are aggregated. Python can traverse the connected nodes and tuple integers through next_functions, but the slots are not independently accessible graph objects.

Dependency order during backward

Backward supplies an initial gradient to loss.grad_fn and then follows next_functions toward the leaves. Dependencies determine when a node becomes executable: when several downstream branches converge on one upstream node, the engine gathers their gradient contributions before scheduling that node.

  1. loss.backward() supplies the initial gradient to loss.grad_fn.
  2. The current grad_fn executes its backward function and produces gradients for its input tensors.
  3. Each input gradient is routed through the corresponding (fn, input_nr) entry in next_functions.
  4. If one slot receives several gradients, they are added.
  5. An upstream backward function runs after the gradients it requires are ready.
  6. At AccumulateGrad, the gradient is written into the corresponding leaf tensor's .grad.
Backward follows next_functions from loss.grad_fn

This order has two layers: dependency constraints and scheduling among ready nodes. The dependency constraint makes PairIdentityBackward wait for MulBackward0, SinBackward0, and the branch through v. Once several nodes are ready together, the engine may choose their relative order. Model logic should depend on graph edges and gradient slots, not on the particular ordering of that ready set.

AccumulateGrad and leaf .grad

AccumulateGrad is the leaf-gradient accumulation node observed in the eager graph used here. When backward reaches it, the arriving gradient is merged into the corresponding leaf tensor's .grad. According to the official leaf tensor documentation, a user-created leaf requiring gradients was not produced by an operation, so p.grad_fn is None. A downstream node that consumes p can still point to its accumulator through next_functions.

That connection lets Python code reach an AccumulateGrad object indirectly:

p = torch.randn(4, requires_grad=True)
y = p * 2

y.grad_fn
# MulBackward0

y.grad_fn.next_functions[0][0]
# AccumulateGrad for p

The AccumulateGrad class name is an implementation observation rather than a separately promised stable API for ordinary model code. That boundary matters when framework code attaches hooks to the node.

The Megatron-Core DDP parameter hook

Megatron-Core DDP needs to run several actions after a parameter's local gradient accumulation completes: add param.grad into param.main_grad, clear param.grad, and, when overlap is enabled, notify the bucket that the parameter is ready. AccumulateGrad sits at this readiness point, while the parameter itself is a leaf with param.grad_fn=None. The pinned implementation exposes the reverse edge to the accumulator through a temporary non-leaf tensor.

The source first creates an inexpensive view operation with identity-like behavior:

# NVIDIA/Megatron-LM core_r0.10.0
if param.requires_grad:
    # Expand so we get access to grad_fn.
    param_tmp = param.expand_as(param)
    # Get the gradient accumulator function.
    grad_acc = param_tmp.grad_fn.next_functions[0][0]
    grad_acc.register_hook(self._make_backward_post_hook(param))
    self.grad_accs.append(grad_acc)

expand_as is equivalent to calling expand with another tensor's shape. The shape does not change here, so parameter data need not be copied, but the operation produces a tracked non-leaf tensor, param_tmp. With the pinned commit and its eager PyTorch runtime, the generated backward class is commonly printed as ExpandBackward0 or a related view backward function. Megatron does not depend on that generated class name. It depends on param_tmp.grad_fn.next_functions[0][0] reaching the original parameter's gradient accumulator.

Megatron-Core DDP reaches a leaf parameter's AccumulateGrad through a view operation

The hook implementation appears later in the same pinned file. _make_backward_post_hook checks param.grad when the parameter belongs to a bucket, adds it to param.main_grad, and then sets param.grad = None. With overlap_grad_reduce enabled, it also calls register_grad_ready(param). Whether the system later starts an all-reduce or a reduce-scatter depends on the DDP configuration and bucket implementation in that version, not on this hook alone.

This access path depends on two conditions:

  • expand_as must create a tracked non-leaf tensor. With requires_grad=False or in a context where autograd recording is disabled, this route does not expose the accumulator.
  • The returned grad_acc must stay alive. Megatron stores it in self.grad_accs so that the object carrying the hook is not released too early.

PyTorch 2.12 also provides the public Tensor.register_post_accumulate_grad_hook(), which runs after a leaf tensor's .grad has been updated. Extension code that only needs a leaf post-accumulation callback can evaluate that public interface first. The AccumulateGrad node hook remains relevant here because it is the concrete implementation in the pinned Megatron commit.

The case now connects the full reverse-graph model: grad_fn provides the entry point, next_functions reaches the leaf accumulator, and fan-in ensures that the hook observes the combined local gradient. Megatron uses that path to connect gradient buckets with communication overlap while accepting version coupling to PyTorch autograd internals.
