Triton JIT Specialization 机制：参数特化、编译变体与缓存

一个 Triton kernel 通常要处理多种 shape、dtype、地址对齐和 launch 配置。若每组运行时数值都重新编译，启动成本与缓存体积会迅速增长；若所有调用共用一份 binary，编译器又会失去 tile shape、常量分支和对齐信息。@triton.jit 通过 specialization 在两者之间划分编译等价类：参数类型、编译期常量、对齐属性和编译选项共同构成 key，同一个 key 复用已有 kernel，新的 key 生成新的编译变体。

0. Specialization 模型

JIT 是在程序运行期间按需触发编译的执行模型；specialization 是用一组静态属性确定编译变体的划分规则。前者决定编译时机，后者决定哪些调用共享结果。

普通 CUDA kernel 在 launch 时接收参数值，预先编译的设备代码只保留参数类型。Triton 可以把选定参数提升为编译期常量，也可以从普通运行时参数提取类型和对齐属性。于是，同一个 Python 函数会对应一组 GPU kernel：

\[ \text{Python JIT function} \quad\longrightarrow\quad \{K_0,K_1,\ldots,K_n\}. \]

每个 $K_i$ 都对应一组参数签名、常量、编译属性和 launch options。本文沿 Triton 固定版本 a2d75c0 的 launch 路径展开；整数特化规则具有版本差异，旧版本需要按其对应源码解释。

1. 从 kernel launch 到编译变体

@triton.jit
def copy_kernel(
    x,
    y,
    n,
    BLOCK: tl.constexpr,
):
    offsets = tl.arange(0, BLOCK)
    mask = offsets < n
    values = tl.load(x + offsets, mask=mask)
    tl.store(y + offsets, values, mask=mask)

copy_kernel[(1,)](x, y, 1024, BLOCK=256)

装饰器首先创建 JITFunction，记录 Python signature、函数源码、被调用的其他 JIT function 和使用到的全局值。程序执行 kernel[grid](...) 后，运行时才绑定本次参数并进入 specialization 与缓存查询。

一次 Triton kernel launch 的 JIT 路径

JITFunction.run() 先调用 binder 生成 specialization，再计算 key 并查询当前 device 的 kernel cache。cache miss 时，signature、constexpr 和属性被打包成 ASTSource，然后进入编译器。

2. Descriptor 与 Specialization Key

Specialization descriptor 是运行时参数映射到编译属性后的结构化表示。create_function_from_signature() 按参数类别生成 descriptor，再由这些 descriptor 组成 key。固定版本中的规则可以整理为：

普通 floatfp32否

Triton 的 specialization reference test 给出了对应的 Python 参考实现。由表中规则可以直接得到两个边界：

  • 普通 Tensor 参数不会自动把 shape 和 stride 放进 specialization key。kernel 看到的主要是 pointer 类型和对齐属性。
  • 普通整数并非每个数值都生成一个 kernel。当前实现主要按整数宽度和 backend 属性拆分，数值 1 会提升为 constexpr。

3. tl.constexpr 的编译期语义

tl.constexpr 按精确值进入 key，也会成为 ASTSource.constants。编译器因此可以在 AST 转 TTIR 之前就使用它：

@triton.jit
def reduce_kernel(
    x,
    y,
    n,
    BLOCK: tl.constexpr,
    USE_FAST_PATH: tl.constexpr,
):
    offsets = tl.arange(0, BLOCK)
    values = tl.load(x + offsets, mask=offsets < n)

    if USE_FAST_PATH:
        values = fast_transform(values)
    else:
        values = accurate_transform(values)

    tl.store(y + offsets, values, mask=offsets < n)

BLOCK=256 和 BLOCK=512 是两个编译变体。USE_FAST_PATH=True 与 False 也是两个变体；未选择的分支不会留到运行时。循环次数、tile shape、算法分支和 dtype policy 适合作为 constexpr，因为这些值会改变程序结构。

把任意数据维度都声明成 constexpr 则会迅速放大编译数量。若业务出现 40 种 sequence length，而 kernel 并不需要针对每个长度展开循环，那么 N: tl.constexpr 会产生 40 份近似的 binary。

4. 普通参数的隐式特化

即使参数没有标成 constexpr，Triton 仍会提取对优化有用的属性。当前通用 backend 用字母 D 表示 tt.divisibility=16：

  • 整数能被 16 整除时，descriptor 带 D。
  • pointer 地址按 16 byte 对齐时，descriptor 带 D。

实现位于 backend 的 get_int_specialization() 与 get_tensor_specialization()。这些属性为编译器提供消除 mask、选择向量化访问或简化地址计算的机会；某个具体 kernel 是否发生这些优化，仍要查看生成的 IR 或目标代码。

继续使用前面的 copy_kernel，以下调用展示了 key 的拆分：

调用n descriptorx descriptorBLOCK是否复用 A
A：n=1024，对齐 pointeri32 + D*fp32 + D256基准变体
B：n=2048，对齐 pointeri32 + D*fp32 + D256是
C：n=1000，对齐 pointeri32*fp32 + D256否
D：n=1024，非对齐 pointeri32 + D*fp32256否
E：n=1024，对齐 pointeri32 + D*fp32 + D512否

A 与 B 的运行时数值不同，但 descriptor 相同，因此共用 kernel。C 失去整数整除属性，D 失去 pointer alignment 属性，E 改变了 constexpr。五次调用最终产生四个变体。

launch grid 通常不是 specialization key 的一部分。若 n 是普通运行时整数，grid=(triton.cdiv(n, BLOCK),) 可以随调用变化而不触发编译。grid 使用的 BLOCK 本身是 constexpr，所以改变 BLOCK 仍会生成新变体。

5. 运行时缓存与编译缓存

Descriptor 确定运行时 key 以后，查询依次经过进程内 cache 与 persistent cache。前者复用当前进程已经加载的 kernel 对象，后者复用跨进程保存的编译产物。

Triton JIT 的两级缓存查询路径

JITFunction 的进程内 per-device cache

在一个 Python 进程内，每个 JITFunction 按 device 保存 kernel_cache。这一级 cache 的作用域是当前进程与对应的 JITFunction；运行时 key 由 specialization descriptor 和编译 options 组成：

\[ \text{runtime key} = (\text{specialization},\text{options}). \]

num_warps、num_stages、num_ctas 等属于 options。参数完全相同但 num_warps 不同，仍然是两个 kernel。key 的构造与查询见 compute_cache_key()。

编译器的 persistent cache

内存 cache miss 后，Triton 构造 ASTSource。它的 hash 包含：

  • 当前函数以及传递依赖的源码 hash
  • 参数 signature
  • constexpr 的精确值
  • alignment 和 divisibility 属性
  • backend target、编译 options 与会使缓存失效的环境变量

ASTSource.hash() 负责 source 一侧，compile() 再加入 target 和 options，随后查询磁盘上的编译产物。新 Python 进程命中 persistent cache 时，可以跳过完整 lowering 流程。

磁盘 cache miss 有两类来源。Source、signature、constexpr、target、options 或参与 cache invalidation 的环境变量发生变化，会生成新的 persistent key；缓存目录不可访问、产物组不完整或 metadata 校验失败，则会让已有 key 无法恢复有效产物。

6. 控制 specialization 数量

普通整数和 pointer 的隐式属性可能带来额外变体。若某个参数的取值很多，而 kernel 不依赖它的整除或对齐信息，可以关闭相应规则：

@triton.jit(do_not_specialize=["n"])
def dynamic_kernel(x, y, n, BLOCK: tl.constexpr):
    ...

do_not_specialize 关闭 n 的运行时 value/alignment specialization。不同的普通 i32 n 共用一个变体。

@triton.jit(do_not_specialize_on_alignment=["n"])
def dynamic_kernel(x, y, n, BLOCK: tl.constexpr):
    ...

do_not_specialize_on_alignment 只关闭 alignment/divisibility 属性。其他规则仍保留，例如当前实现仍可能把整数 1 提升为 constexpr。两个参数都支持用名字或参数位置指定，具体初始化逻辑见 JITFunction.__init__()。

关闭 specialization 不会改变 kernel 的数学语义，但会减少编译器可用的静态信息。变体数量下降以后，某些形状可能失去向量化或无 mask 路径。它是编译时间、代码体积和运行性能之间的取舍。

7. Autotune key 与触发条件

@triton.autotune 是按运行时输入选择 triton.Config 的测量机制。它为一个 tuning key 运行候选配置、记录耗时并保存胜出的 config。Specialization JIT 随后负责为候选配置与参数属性生成可执行 kernel。前者的缓存单位是“输入对应的最佳配置”，后者的缓存单位是“可复用的编译变体”。

Key 的声明与运行时组成

key 接收 kernel 形参名列表。官方 matrix multiplication tutorial 以 M、N、K 划分调优输入域；任一维度取值改变，都会得到另一个 tuning key。参数名与示例可在固定版本的 matmul autotune decorator 中核对。

@triton.autotune(
    configs=[
        triton.Config(
            {"BLOCK_M": 64, "BLOCK_N": 64, "BLOCK_K": 32},
            num_warps=4,
        ),
        triton.Config(
            {"BLOCK_M": 128, "BLOCK_N": 64, "BLOCK_K": 32},
            num_warps=8,
        ),
    ],
    key=["M", "N", "K"],
)
@triton.jit
def matmul_kernel(
    a_ptr, b_ptr, c_ptr,
    M, N, K,
    BLOCK_M: tl.constexpr,
    BLOCK_N: tl.constexpr,
    BLOCK_K: tl.constexpr,
):
    ...

在本文固定的 Triton revision 中，运行时先按 key 声明的顺序读取参数值，随后追加所有带 dtype 属性的 kernel argument 类型。对于上面的调用，tuning key 可以表示为：

tuning_key = (
    M, N, K,
    str(a.dtype), str(b.dtype), str(c.dtype),
)

这段构造逻辑位于 Autotuner.run()。Tensor 地址和 pointer alignment 不会自动进入 tuning key；它们属于 JIT specialization。实践中通常选择 shape、stride、模式标志或显式 bucket 等能够改变最佳 config 的标量参数，而不把 pointer 参数列入 key。

新 key 的调优路径

Autotuner 首先查询进程内的 self.cache。miss 后，候选集先经过 early_config_prune 和 performance model；剩余多个配置时才执行 benchmark。固定版本的 运行路径可以简化为以下伪代码：

tuning_key = selected_argument_values + tensor_dtypes

if tuning_key not in process_cache:
    candidates = prune(configs)

    if len(candidates) == 1:
        best = candidates[0]
    elif disk_result_exists(tuning_key, candidates):
        best = restore_best_config()
    else:
        timings = benchmark_each(candidates)
        best = argmin(timings)

    process_cache[tuning_key] = best

launch(process_cache[tuning_key])

新的 tuning key 在两个条件同时满足时触发 benchmark：disk cache 没有恢复已有结果，并且 prune 后仍有多个候选。若只剩一个 config，运行时直接选中它。cache_results 默认关闭；开启后，磁盘 key 还包含 Triton cache identity、target backend、kernel source hash、cache-invalidating 环境变量和候选配置集合，具体字段见 check_disk_cache()。

Autotune miss 与 JIT miss

一次 autotune miss 会运行候选 config，但每次候选 launch 仍独立查询 JIT cache。新的 tuning key 因而表示“需要重新测量”，不必然表示“所有候选都要重新编译”。JIT miss 也可以出现在 autotune hit 路径上：pointer alignment 改变可能产生新的 specialization，而 shape 与 dtype 对应的 tuning key 仍然命中，此时 Triton 沿用此前选出的 config，只编译缺失的 variant。

变化Autotune cacheJIT cache
M/N/K 中的 key value 改变miss，重新测量或从 disk 恢复每个候选分别查询，可能 hit 也可能 miss

输入长度高度离散时，直接把原始长度放入 key 会让调优次数随取值数量增长。若一段长度区间共享相近的性能特征，可以在 wrapper 中计算 bucket，并把 bucket 作为显式 kernel argument 和 autotune key；这种合并需要用 benchmark 验证，避免把最佳配置不同的输入压入同一条目。

Autotune 会为同一个 key 多次执行 kernel。Kernel 修改输出、计数器或其他持久状态时，需要使用 reset_to_zero、restore_value 或 hook 在候选之间恢复状态。triton.autotune 的固定版本文档同时给出了这些接口；TRITON_PRINT_AUTOTUNING=1 可打印实际发生的调优及胜出配置。

8. 追踪 Specialization 与 Cache Miss

出现首次迭代很慢或 cache 目录快速增长时，可以先检查三个位置：

  1. 列出所有 tl.constexpr，确认它们是否真的改变 tile、循环或控制流。
  2. 检查 shape/stride 参数是否在 16 的整除边界两侧频繁跳动，以及 pointer 是否来自带 offset 的 view。
  3. 检查 autotune config 和 num_warps/num_stages，它们同样扩大编译组合。

TRITON_CACHE_DIR 可以指定 persistent cache 位置。TRITON_KERNEL_DUMP=1 会把各阶段 IR 写入 TRITON_DUMP_DIR，适合比较两个 specialization 的 TTIR 或 PTX。调试缓存命中时还可以使用 TRITON_ALWAYS_COMPILE=1 强制重编译；这些环境变量的当前定义在 knobs.py 中。

两个 Hook 对应两级 Cache

knobs.runtime.jit_cache_hook 是进程内 JIT cache miss 的观察点。JITFunction._do_compile() 在构造 ASTSource 之前调用它，并通过 specialization_data 提供 signature、constexpr、argument attributes、options、runtime key 和 target。该事件说明当前进程尚未保存这个 specialization；后续 persistent cache 是否命中，要等编译器完成查询才能确定。hook 的字段和调用位置见固定版本的 JITHook protocol、serialize_specialization_data() 和 _call_hook()。

knobs.compilation.listener 位于 compile() 的 persistent cache 路径。metadata group 恢复成功时，listener 收到 cache_hit=True；完整 lowering 与产物写回结束后，listener 收到 cache_hit=False。Triton 的 compilation listener 单元测试也覆盖了这两种状态。因此，一条 JIT specialization 事件紧接着 disk_cache_hit=false，才表示该 specialization 进入编译器后又发生 persistent cache miss。

这两个 hook 是 Triton 固定版本中的进程级 instrumentation knob，并非稳定的公共 API。回调签名和 payload 需要随安装版本核对。jit_cache_hook 应返回 False 或 None；返回 True 会让 _do_compile() 提前返回，正常编译和 kernel launch 都会被跳过。

可复现实验：Pointer 地址对齐产生两个变体

Pointer alignment 展示了一个只改变地址、不改变 dtype、shape、BLOCK 或 launch options 的 specialization。固定版本的 native_specialize_impl 对 Tensor 调用 data_ptr()；当地址满足 16-byte 对齐时，它返回内部 descriptor "D"。随后 BaseBackend.parse_attr() 把 "D" 转成 [["tt.divisibility", 16]]。其语义等价于：

if ValuesA.data_ptr() % 16 == 0:
    attrs["ValuesA"] = [["tt.divisibility", 16]]
else:
    attrs["ValuesA"] = []

真实实现不会直接用参数名写入 attrs。它先按参数位置保存 descriptor，再在 _pack_args() 中生成 attribute path；下面的日志函数把这些 path 还原为 ValuesA、Out 等参数名，便于比较。

# trace_specialization.py
import json
import os
import time

import torch
import triton
import triton.language as tl
from triton import knobs


def _rank():
    return os.environ.get("RANK", "unknown")


def _named_path_map(keys, values, signature):
    parameter_names = list(signature)
    result = {}
    for path, value in zip(keys, values):
        if path and isinstance(path[0], int) and path[0] < len(parameter_names):
            label = parameter_names[path[0]]
            label += "".join(f"[{index}]" for index in path[1:])
        else:
            label = str(path)
        result[label] = value
    return result


def _jit_specialization(**event):
    compile_info = event["compile"]
    specialization = json.loads(compile_info["specialization_data"])
    signature = specialization["signature"]

    print(
        json.dumps(
            {
                "event": "TRITON_JIT_SPECIALIZATION",
                "time_ns": time.monotonic_ns(),
                "rank": _rank(),
                "pid": os.getpid(),
                "kernel": specialization["name"],
                "signature": signature,
                "constants": _named_path_map(
                    specialization["constant_keys"],
                    specialization["constant_vals"],
                    signature,
                ),
                "attrs": _named_path_map(
                    specialization["attrs_keys"],
                    specialization["attrs_vals"],
                    signature,
                ),
                "options": specialization["options"],
                "target": specialization["target"],
                "runtime_key": event["key"],
                "manual_warmup": event["is_manual_warmup"],
            },
            default=str,
        ),
        flush=True,
    )

    # A truthy return value skips normal compilation and launch.
    return False


def _compilation_result(*, src, metadata, metadata_group, times, cache_hit):
    print(
        json.dumps(
            {
                "event": "TRITON_COMPILE_RESULT",
                "time_ns": time.monotonic_ns(),
                "rank": _rank(),
                "pid": os.getpid(),
                "kernel": getattr(src, "name", "unknown"),
                "compiler_hash": metadata.get("hash"),
                "disk_cache_hit": cache_hit,
                "compiler_path_ms": times.total / 1000.0,
                "lowering_ms": times.total_lowering / 1000.0,
            }
        ),
        flush=True,
    )


@triton.jit
def copy_kernel(ValuesA, Out, BLOCK: tl.constexpr):
    offsets = tl.arange(0, BLOCK)
    tl.store(Out + offsets, tl.load(ValuesA + offsets))


def _aligned_view(storage, size):
    byte_offset = (-storage.data_ptr()) % 16
    assert byte_offset % storage.element_size() == 0
    element_offset = byte_offset // storage.element_size()
    return storage[element_offset : element_offset + size]


def main():
    if not hasattr(knobs.runtime, "jit_cache_hook"):
        raise RuntimeError(f"Triton {triton.__version__} lacks jit_cache_hook")
    if not hasattr(knobs.compilation, "listener"):
        raise RuntimeError(f"Triton {triton.__version__} lacks compilation.listener")

    block = 256
    input_storage = torch.arange(block + 4, device="cuda", dtype=torch.float32)
    output_storage = torch.empty(block + 4, device="cuda", dtype=torch.float32)
    aligned = _aligned_view(input_storage, block)
    misaligned = aligned.as_strided((block,), (1,), storage_offset=aligned.storage_offset() + 1)
    out = _aligned_view(output_storage, block)

    assert aligned.data_ptr() % 16 == 0
    assert misaligned.data_ptr() % 16 == aligned.element_size()
    assert out.data_ptr() % 16 == 0

    old_jit_hook = knobs.runtime.jit_cache_hook
    old_listener = knobs.compilation.listener
    knobs.runtime.jit_cache_hook = _jit_specialization
    knobs.compilation.listener = _compilation_result

    print(
        json.dumps(
            {
                "event": "TRITON_JIT_TRACKING_ENABLED",
                "version": triton.__version__,
                "cache_dir": os.environ.get("TRITON_CACHE_DIR"),
            }
        ),
        flush=True,
    )

    try:
        for label, values in (
            ("aligned-1", aligned),
            ("aligned-2", aligned),
            ("misaligned-1", misaligned),
            ("misaligned-2", misaligned),
        ):
            print(
                json.dumps(
                    {
                        "event": "TRITON_CALL",
                        "label": label,
                        "ValuesA_ptr_mod_16": values.data_ptr() % 16,
                    }
                ),
                flush=True,
            )
            copy_kernel[(1,)](values, out, BLOCK=block)
            torch.cuda.synchronize()
            torch.testing.assert_close(out, values)
    finally:
        knobs.runtime.jit_cache_hook = old_jit_hook
        knobs.compilation.listener = old_listener


if __name__ == "__main__":
    main()

Triton JIT Specialization: Arguments, Kernel Variants, and Caching

A Triton kernel commonly serves many shapes, dtypes, address alignments, and launch configurations. Compiling every runtime value would inflate startup cost and cache size, while forcing every call through one binary would discard static tile shapes, constant branches, and alignment facts. @triton.jit uses specialization to partition calls into compilation-equivalence classes. Argument types, compile-time constants, alignment properties, and compilation options form the key; an existing key reuses its kernel, while a new key produces another compiled variant.

0. Specialization Model

JIT is an execution model that triggers compilation on demand while the program runs. Specialization is the rule that maps a set of static properties to a compiled variant. The first determines when compilation occurs; the second determines which calls share its result.

A conventional CUDA kernel receives argument values at launch, while its ahead-of-time device code retains only parameter types. Triton can promote selected arguments to compile-time constants and extract types and alignment properties from ordinary runtime arguments. One Python function can therefore represent a family of GPU kernels:

\[ \text{Python JIT function} \quad\longrightarrow\quad \{K_0,K_1,\ldots,K_n\}. \]

Each $K_i$ corresponds to one argument signature, set of constants, compilation properties, and launch options. This article follows the launch path in pinned Triton revision a2d75c0. Integer-specialization rules vary by release, so older versions should be read against their matching source.

1. From Kernel Launch to a Compiled Variant

@triton.jit
def copy_kernel(
    x,
    y,
    n,
    BLOCK: tl.constexpr,
):
    offsets = tl.arange(0, BLOCK)
    mask = offsets < n
    values = tl.load(x + offsets, mask=mask)
    tl.store(y + offsets, values, mask=mask)

copy_kernel[(1,)](x, y, 1024, BLOCK=256)

The decorator first creates a JITFunction that records the Python signature, function source, called JIT functions, and referenced global values. When the program executes kernel[grid](...), the runtime binds the current arguments and enters specialization and cache lookup.

JIT path for one Triton kernel launch

JITFunction.run() first invokes the binder to produce a specialization, computes the key, and queries the kernel cache for the current device. On a cache miss, Triton packages the signature, constexpr values, and properties into an ASTSource and passes it to the compiler.

2. Descriptors and Specialization Keys

A specialization descriptor is a structured representation that maps a runtime argument to compilation properties. create_function_from_signature() builds one descriptor per argument and combines them into the key. The pinned revision follows these rules:

Triton's specialization reference test provides a Python reference model for this behavior. Two boundaries follow directly from those rules:

  • An ordinary tensor argument does not automatically add its shape and strides to the specialization key. The kernel primarily sees the pointer type and alignment properties.
  • An ordinary integer does not produce one kernel per numeric value. The current implementation mainly separates integer widths and backend properties; the value 1 is promoted to constexpr.

3. Compile-Time Semantics of tl.constexpr

A tl.constexpr argument enters the key by exact value and becomes part of ASTSource.constants. The compiler can use it before lowering the AST to TTIR:

@triton.jit
def reduce_kernel(
    x,
    y,
    n,
    BLOCK: tl.constexpr,
    USE_FAST_PATH: tl.constexpr,
):
    offsets = tl.arange(0, BLOCK)
    values = tl.load(x + offsets, mask=offsets < n)

    if USE_FAST_PATH:
        values = fast_transform(values)
    else:
        values = accurate_transform(values)

    tl.store(y + offsets, values, mask=offsets < n)

BLOCK=256 and BLOCK=512 are separate compiled variants. So are USE_FAST_PATH=True and False; the branch not selected does not survive as a runtime branch. Loop counts, tile shapes, algorithmic branches, and dtype policies are suitable constexpr values because they alter program structure.

Declaring every data dimension as constexpr can quickly multiply compilation work. If a workload contains 40 sequence lengths and the kernel does not need to unroll a distinct loop for each one, writing N: tl.constexpr creates 40 similar binaries.

4. Implicit Specialization of Ordinary Arguments

Even when an argument is not constexpr, Triton extracts properties that may help optimization. The current generic backend uses D to denote tt.divisibility=16:

  • An integer descriptor receives D when the value is divisible by 16.
  • A pointer descriptor receives D when the address is aligned to 16 bytes.

The implementation is in the backend methods get_int_specialization() and get_tensor_specialization(). These properties give the compiler opportunities to remove masks, select vectorized accesses, or simplify address calculations. Whether a particular kernel realizes those optimizations must be verified in generated IR or target code.

Using the earlier copy_kernel, the following calls show how keys split:

Calln descriptorx descriptorBLOCKReuses A?
A: n=1024, aligned pointeri32 + D*fp32 + D256Reference variant
B: n=2048, aligned pointeri32 + D*fp32 + D256Yes
C: n=1000, aligned pointeri32*fp32 + D256No
D: n=1024, unaligned pointeri32 + D*fp32256No
E: n=1024, aligned pointeri32 + D*fp32 + D512No

A and B have different runtime values but identical descriptors, so they share a kernel. C loses the integer-divisibility property, D loses the pointer-alignment property, and E changes a constexpr value. The five calls produce four variants.

The launch grid is normally not part of the specialization key. When n is an ordinary runtime integer, grid=(triton.cdiv(n, BLOCK),) may change between calls without triggering compilation. BLOCK, however, is constexpr, so changing it still creates a new variant.

5. Runtime Cache and Compilation Cache

Once the descriptor determines the runtime key, lookup proceeds through an in-process cache and then a persistent cache. The first reuses kernel objects already loaded by the current process; the second reuses compilation artifacts across processes.

Two-level cache lookup in Triton JIT

JITFunction In-Process Per-Device Cache

Within one Python process, each JITFunction keeps a kernel_cache indexed by device. The scope of this cache is the current process and that JITFunction. Its runtime key consists of the specialization descriptor and compilation options:

\[ \text{runtime key} = (\text{specialization},\text{options}). \]

num_warps, num_stages, and num_ctas are options. Calls with identical arguments but different num_warps values still use separate kernels. See compute_cache_key() for key construction and lookup.

Compiler Persistent Cache

After an in-memory cache miss, Triton constructs an ASTSource. Its hash includes:

  • The source hash of the current function and its transitive dependencies
  • The argument signature
  • Exact constexpr values
  • Alignment and divisibility properties
  • The backend target, compilation options, and cache-invalidating environment variables

ASTSource.hash() covers the source side. compile() adds the target and options before querying compiled artifacts on disk. A new Python process that hits this persistent cache can skip the full lowering flow.

Disk-cache misses come from two classes of change. Source, signature, constexpr values, target, options, or cache-invalidating environment variables produce a new persistent key. An inaccessible cache directory, incomplete artifact group, or failed metadata validation prevents an existing key from restoring a valid artifact.

6. Controlling the Number of Specializations

Implicit properties of ordinary integers and pointers may create extra variants. If an argument takes many values and the kernel does not rely on its divisibility or alignment, the corresponding rule can be disabled:

@triton.jit(do_not_specialize=["n"])
def dynamic_kernel(x, y, n, BLOCK: tl.constexpr):
    ...

do_not_specialize disables runtime value and alignment specialization for n. Different ordinary i32 n values then share a variant.

@triton.jit(do_not_specialize_on_alignment=["n"])
def dynamic_kernel(x, y, n, BLOCK: tl.constexpr):
    ...

do_not_specialize_on_alignment disables only alignment and divisibility properties. Other rules remain active; for example, the current implementation may still promote integer 1 to constexpr. Both arguments accept parameter names or positions. See JITFunction.__init__() for the initialization logic.

Disabling specialization does not alter the kernel's mathematical semantics, but it removes static information from the compiler. Fewer variants may cost some shapes their vectorized or mask-free path. The setting trades compilation time and code size against runtime performance.

7. Autotune Keys and Trigger Conditions

@triton.autotune is a measurement mechanism that selects a triton.Config for a runtime input. For one tuning key, it runs candidate configurations, records their timings, and caches the winner. Specialization JIT then produces executable kernels for the candidate configurations and argument properties that reach the launch path. The autotune cache stores “the best configuration for an input,” while the JIT cache stores reusable compiled variants.

Key Declaration and Runtime Composition

The key parameter is a list of names from the kernel signature. Triton's matrix multiplication tutorial partitions the tuning domain by M, N, and K; changing any dimension produces another tuning key. The declaration appears in the pinned matmul autotune decorator.

@triton.autotune(
    configs=[
        triton.Config(
            {"BLOCK_M": 64, "BLOCK_N": 64, "BLOCK_K": 32},
            num_warps=4,
        ),
        triton.Config(
            {"BLOCK_M": 128, "BLOCK_N": 64, "BLOCK_K": 32},
            num_warps=8,
        ),
    ],
    key=["M", "N", "K"],
)
@triton.jit
def matmul_kernel(
    a_ptr, b_ptr, c_ptr,
    M, N, K,
    BLOCK_M: tl.constexpr,
    BLOCK_N: tl.constexpr,
    BLOCK_K: tl.constexpr,
):
    ...

In the Triton revision pinned by this article, the runtime first reads the declared argument values in key order and then appends the type of every kernel argument that exposes a dtype attribute. For the call above, the tuning key can be represented as:

tuning_key = (
    M, N, K,
    str(a.dtype), str(b.dtype), str(c.dtype),
)

The construction is implemented in Autotuner.run(). Tensor addresses and pointer-alignment attributes are not added to the tuning key automatically; they belong to JIT specialization. Useful keys are scalar shape, stride, mode, or explicit-bucket arguments that can change the winning configuration, rather than pointer arguments.

The Path Taken by a New Key

Autotuner first queries its in-process self.cache. After a miss, early_config_prune and the performance model reduce the candidate set; benchmarking is required only when multiple candidates remain. The pinned runtime path can be reduced to the following pseudocode:

tuning_key = selected_argument_values + tensor_dtypes

if tuning_key not in process_cache:
    candidates = prune(configs)

    if len(candidates) == 1:
        best = candidates[0]
    elif disk_result_exists(tuning_key, candidates):
        best = restore_best_config()
    else:
        timings = benchmark_each(candidates)
        best = argmin(timings)

    process_cache[tuning_key] = best

launch(process_cache[tuning_key])

A new tuning key triggers benchmarking when two conditions hold: the disk cache does not restore a prior result, and pruning leaves more than one candidate. A single remaining config is selected directly. cache_results is disabled by default. When enabled, the disk key also contains Triton's cache identity, the target backend, kernel source hash, cache-invalidating environment variables, and the candidate-config set; the exact fields are in check_disk_cache().

Autotune Misses and JIT Misses

An autotune miss runs candidate configurations, but every candidate launch still queries the JIT cache independently. A new tuning key therefore means “measure again,” not necessarily “compile every candidate again.” A JIT miss can also occur on an autotune-hit path: a pointer-alignment change may create a new specialization while the shape-and-dtype tuning key remains a hit. Triton then keeps the previously selected config and compiles only the missing variant.

ChangeAutotune cacheJIT cache
A key value among M/N/K changesMiss; benchmark or restore from diskEach candidate queries it separately and may hit or miss
Same key; pointer changes from 16-byte aligned to misalignedHit; reuse the winning configSpecialization attribute changes and creates a new variant
Neither key nor specialization changesHitHit

Using every raw length as a key value makes tuning frequency grow with the number of distinct lengths. If a range of lengths has similar performance characteristics, a wrapper can compute a bucket and pass it as an explicit kernel argument and autotune key. Such coalescing should be validated by benchmarks because inputs with different optimal configurations must remain in separate entries.

Autotune executes the kernel multiple times for one key. A kernel that modifies outputs, counters, or other persistent state must use reset_to_zero, restore_value, or hooks to restore state between candidates. The pinned triton.autotune documentation defines these interfaces. TRITON_PRINT_AUTOTUNING=1 prints each actual tuning event and its winning config.

8. Tracing Specialization and Cache Misses

When the first iteration is slow or the cache directory grows quickly, inspect three areas:

  1. List every tl.constexpr and check whether it truly changes a tile, loop, or control-flow branch.
  2. Check whether shape or stride arguments frequently cross divisibility-by-16 boundaries and whether pointers come from views with offsets.
  3. Check autotune configurations and num_warps or num_stages; these settings also multiply compilation combinations.

TRITON_CACHE_DIR selects the persistent-cache location. TRITON_KERNEL_DUMP=1 writes each IR stage under TRITON_DUMP_DIR, which is useful when comparing the TTIR or PTX of two specializations. TRITON_ALWAYS_COMPILE=1 forces recompilation while debugging cache hits. The current definitions of these environment variables are in knobs.py.

Two Hooks Observe Two Cache Levels

knobs.runtime.jit_cache_hook is an observation point for an in-process JIT cache miss. JITFunction._do_compile() calls it before constructing an ASTSource, and specialization_data carries the signature, constexpr values, argument attributes, options, runtime key, and target. The event establishes that the current process does not hold this specialization; persistent-cache status is known only after the compiler performs its lookup. The fixed-revision definitions are in the JITHook protocol, serialize_specialization_data(), and _call_hook().

knobs.compilation.listener runs inside the persistent-cache path of compile(). It receives cache_hit=True when a metadata group restores a compiled kernel and cache_hit=False after full lowering and artifact writeback. Triton's compilation-listener test covers both states. A JIT specialization event followed by disk_cache_hit=false therefore identifies a specialization that missed both the process-local and persistent caches.

These hooks are process-wide instrumentation knobs in the pinned Triton revision, not a stable public API. Their callback signatures and payloads must be checked against the installed version. A jit_cache_hook should return False or None; returning True makes _do_compile() return early, skipping normal compilation and the kernel launch.

Reproducible Experiment: Pointer Alignment Creates Two Variants

Pointer alignment supplies a specialization where the address changes while dtype, shape, BLOCK, and launch options remain fixed. In the pinned native_specialize_impl, Triton calls data_ptr() on a tensor and returns the internal descriptor "D" for a 16-byte-aligned address. BaseBackend.parse_attr() then converts "D" into [["tt.divisibility", 16]]. The behavior is equivalent to:

if ValuesA.data_ptr() % 16 == 0:
    attrs["ValuesA"] = [["tt.divisibility", 16]]
else:
    attrs["ValuesA"] = []

The implementation does not write directly to an attrs dictionary keyed by argument name. It first records a descriptor by argument position, then _pack_args() creates attribute paths. The logger below maps those paths back to names such as ValuesA and Out.

# trace_specialization.py
import json
import os
import time

import torch
import triton
import triton.language as tl
from triton import knobs


def _rank():
    return os.environ.get("RANK", "unknown")


def _named_path_map(keys, values, signature):
    parameter_names = list(signature)
    result = {}
    for path, value in zip(keys, values):
        if path and isinstance(path[0], int) and path[0] < len(parameter_names):
            label = parameter_names[path[0]]
            label += "".join(f"[{index}]" for index in path[1:])
        else:
            label = str(path)
        result[label] = value
    return result


def _jit_specialization(**event):
    compile_info = event["compile"]
    specialization = json.loads(compile_info["specialization_data"])
    signature = specialization["signature"]

    print(
        json.dumps(
            {
                "event": "TRITON_JIT_SPECIALIZATION",
                "time_ns": time.monotonic_ns(),
                "rank": _rank(),
                "pid": os.getpid(),
                "kernel": specialization["name"],
                "signature": signature,
                "constants": _named_path_map(
                    specialization["constant_keys"],
                    specialization["constant_vals"],
                    signature,
                ),
                "attrs": _named_path_map(
                    specialization["attrs_keys"],
                    specialization["attrs_vals"],
                    signature,
                ),
                "options": specialization["options"],
                "target": specialization["target"],
                "runtime_key": event["key"],
                "manual_warmup": event["is_manual_warmup"],
            },
            default=str,
        ),
        flush=True,
    )

    # A truthy return value skips normal compilation and launch.
    return False


def _compilation_result(*, src, metadata, metadata_group, times, cache_hit):
    print(
        json.dumps(
            {
                "event": "TRITON_COMPILE_RESULT",
                "time_ns": time.monotonic_ns(),
                "rank": _rank(),
                "pid": os.getpid(),
                "kernel": getattr(src, "name", "unknown"),
                "compiler_hash": metadata.get("hash"),
                "disk_cache_hit": cache_hit,
                "compiler_path_ms": times.total / 1000.0,
                "lowering_ms": times.total_lowering / 1000.0,
            }
        ),
        flush=True,
    )


@triton.jit
def copy_kernel(ValuesA, Out, BLOCK: tl.constexpr):
    offsets = tl.arange(0, BLOCK)
    tl.store(Out + offsets, tl.load(ValuesA + offsets))


def _aligned_view(storage, size):
    byte_offset = (-storage.data_ptr()) % 16
    assert byte_offset % storage.element_size() == 0
    element_offset = byte_offset // storage.element_size()
    return storage[element_offset : element_offset + size]


def main():
    if not hasattr(knobs.runtime, "jit_cache_hook"):
        raise RuntimeError(f"Triton {triton.__version__} lacks jit_cache_hook")
    if not hasattr(knobs.compilation, "listener"):
        raise RuntimeError(f"Triton {triton.__version__} lacks compilation.listener")

    block = 256
    input_storage = torch.arange(block + 4, device="cuda", dtype=torch.float32)
    output_storage = torch.empty(block + 4, device="cuda", dtype=torch.float32)
    aligned = _aligned_view(input_storage, block)
    misaligned = aligned.as_strided((block,), (1,), storage_offset=aligned.storage_offset() + 1)
    out = _aligned_view(output_storage, block)

    assert aligned.data_ptr() % 16 == 0
    assert misaligned.data_ptr() % 16 == aligned.element_size()
    assert out.data_ptr() % 16 == 0

    old_jit_hook = knobs.runtime.jit_cache_hook
    old_listener = knobs.compilation.listener
    knobs.runtime.jit_cache_hook = _jit_specialization
    knobs.compilation.listener = _compilation_result

    print(
        json.dumps(
            {
                "event": "TRITON_JIT_TRACKING_ENABLED",
                "version": triton.__version__,
                "cache_dir": os.environ.get("TRITON_CACHE_DIR"),
            }
        ),
        flush=True,
    )

    try:
        for label, values in (
            ("aligned-1", aligned),
            ("aligned-2", aligned),
            ("misaligned-1", misaligned),
            ("misaligned-2", misaligned),
        ):
            print(
                json.dumps(
                    {
                        "event": "TRITON_CALL",
                        "label": label,
                        "ValuesA_ptr_mod_16": values.data_ptr() % 16,
                    }
                ),
                flush=True,
            )
            copy_kernel[(1,)](values, out, BLOCK=block)
            torch.cuda.synchronize()
            torch.testing.assert_close(out, values)
    finally:
        knobs.runtime.jit_cache_hook = old_jit_hook
        knobs.compilation.listener = old_listener


if __name__ == "__main__":
    main()

The second call for each specialization hits the process-local cache and emits neither event. The second process rebuilds its process-local cache, so both first calls still invoke the JIT hook; their persistent keys already exist under the shared directory, and the compilation listener should report disk_cache_hit=true.
