Python Import 机制：绝对导入与相对导入

Python 的 import 系统处理的是模块名称和 package 上下文，而不是文件路径本身。解释器先识别当前模块的运行时身份，再结合 sys.modules、sys.path 与 package 的 __path__ 解析目标名称。由此可以统一解释绝对导入、相对导入、namespace package，以及直接运行文件与 python -m 之间的行为差异。

版本范围：本文按 Python 3.14 的语言参考描述。相对导入对 __package__ 的兼容处理带有明确版本边界，见下文。

1. 基础概念#

Module（模块）#

一个 .py 文件通常可作为 source module 加载；module 也可能来自扩展库、内建模块或自定义 loader。首次 import 后，module 对象会进入 sys.modules。只要对应缓存项仍在，普通的重复导入就不会再次执行模块代码。

Package（包）#

Package 是带有 __path__ 的 module，因此 import 系统可以沿这些搜索位置继续查找子 module 与子 package。磁盘上包含 __init__.py 的目录通常形成 regular package；PEP 420 namespace package 则由 finder 根据同名目录动态组织。

__init__.py 的作用#

  1. 标记：让目录被当作 regular package 识别。
  2. 初始化代码：第一次 import pkg 时执行一次（即使只是 from pkg.a import x 也会先执行 pkg/__init__.py）。
  3. re-export 门面：常见用法是在里面 from .a import Foo，让外面可以直接写 from pkg import Foo。
  4. 定义 __all__：控制 from pkg import * 暴露哪些名字。

顶级 package（top-level package）#

顶级 package 是 import 系统从某个 sys.path 条目直接解析出的 package；它既可以是 regular package，也可以是 namespace package。

举例：sys.path 里有 /home/me/proj，而 /home/me/proj/app/__init__.py 存在，那 app 就是顶级 package。app.pkg、app.pkg.sub 是它的子 package，但不是顶级。

顶级 package 的边界由 sys.path 的条目决定。同一目录结构在不同启动位置或安装方式下，可能得到不同的顶级名称。

Namespace package（PEP 420）#

Namespace package 是一种由多个 namespace portion 共同提供搜索位置的 package。PathFinder 在父路径的多个条目中收集同名目录，并把它们组织为可动态更新的 __path__；这些共享层级不放置 __init__.py。它与 regular package 的差异如下：

regular package namespace package
__init__.py 必须有 必须没有
__file__ 有 没有可代表整个包的单一路径；实现可能不设置或设为 None
__path__ 子模块搜索位置序列 可动态合并多个 portion 的定制 iterable；CPython 中常显示为 _NamespacePath
用途 单一 wheel 拥有整个 package 多个 wheel 拼接同一个 import 命名空间

典型场景：两个发行包分别在 /env/a/acme/plugins/ 与 /env/b/acme/plugins/ 提供子 package，并故意不在共享层级放 __init__.py。当两个父路径都在搜索路径中时，Python 可把这些 portion 合并为同一个 acme.plugins 命名空间。

跨路径合并要求匹配项都以 namespace portion 参与。PathFinder 一旦在扫描中找到同名 regular package，便返回该 package；其它位置的 namespace portion 不再并入它。错误 6 展示了这一规则如何改变可见的子 package。

2. import 的解析流程#

sys.path 决定能找到什么#

解析 import X 时，解释器先在 sys.modules 中查找点分名称 X。缓存未命中时，finder 沿 sys.path 解析顶级名称，再沿每一级 package 的 __path__ 继续搜索。

sys.path 的常见来源包括：

  • 启动脚本所在目录；执行 python a.py 时，a.py 的目录进入 sys.path[0]。
  • 执行 python -m pkg.mod 时的当前工作目录。
  • PYTHONPATH 环境变量。
  • 解释器配置的 site-packages。

__name__、__spec__.parent 和 __package__#

__name__ 标识模块名；在 Python 3.14 中，显式相对导入优先以 __spec__.parent 确定所属 package。

启动方式 __name__ __spec__.parent __package__
python app/pkg/a.py（直接跑文件） "__main__" __spec__ is None None 或 ""
python -m app.pkg.a（按模块跑） "__main__" "app.pkg" "app.pkg"
被别处 import app.pkg.a "app.pkg.a" "app.pkg" "app.pkg"

Python 3.14 的显式相对导入以 __spec__.parent 为 package 起点；__package__ 在前者未设置时提供兼容回退。该回退自 Python 3.13 起弃用，并计划在 Python 3.15 移除。每增加一个前导点，解析位置便从起点向上移动一级。

直接用 python a.py 运行包内文件时，__main__.__spec__ 通常为 None，也没有可用的 package 回退值，因此 from . import b 无法确定起点。

绝对导入 vs 相对导入#

  • 绝对导入：from app.pkg import b，从 sys.path 根开始解析完整名称。目标来源更明确，但 package 被重命名或移动后仍需更新引用。
  • 相对导入：from . import b、from ..sib import e，基于当前模块的 package 上下文计算。它不能跨出顶级 package；直接按文件启动的脚本通常没有这个上下文，而通过 -m 启动的入口模块可以使用。

PEP 8 推荐绝对导入；相对导入用于 package 内部 同辈/近亲互引。

dotted name 的逐段解析#

from a.b.c import d 并不是一步到位，而是按 . 一段段走，每段独立决定它是 regular / namespace package 还是普通 module：

  1. 找 a：沿 sys.path 找叫 a 的目录 / 文件，写进 sys.modules['a']。
  2. 找 a.b：在 a.__path__ 里找 b，再走一遍 finder。如果 a 是 namespace package，a.__path__ 可能是多个物理目录的合集，b 可能来自其中任何一个。
  3. 找 a.b.c：在 a.b.__path__ 里找 c。
  4. 从 a.b.c 这个 module 对象上取属性 d；若属性不存在，import-from 还会尝试加载子模块 a.b.c.d，仍失败才抛出 ImportError。

每一步加载的 module 都写进 sys.modules。只要缓存项仍在，重复 import 会直接命中，不再走 finder；删除对应缓存项后，下一次 import 才会重新搜索。

import 对 package 命名空间的写入#

子模块加载完成后，import 系统还会更新父 package 的命名空间。这里有两项直接影响 import a.b 与 from a import b 行为的规则。

(a) import a.b 会把 b 设为 a 的属性。 该绑定由 import 系统在加载子模块时完成，因此空的 __init__.py 也具备这一行为：

import a.b           # 哪怕 a/__init__.py 完全为空
a.b.foo()            # 也能 work：import 系统已经把 b 绑到 a 上了

(b) from a import b 在 a 上没有属性 b 时，会尝试加载子模块 a.b。 成功加载后，上一条规则又把 b 绑定到 a。这项回退只处理单层 attribute；from a import b.c 不符合该语句的语法。

同名子模块 / 同名顶级 package 的歧义#

import 系统只看名字，不区分"逻辑上是同一个包"。两种常见歧义：

  • 同名顶级 package 撞车：若某条路径提供 regular package 或普通 module，PathFinder 会返回该对象，不会再把其他同名目录并入其中；只有隐式 namespace portion 才会跨搜索位置合并。可用 foo.__spec__.origin 与 foo.__spec__.submodule_search_locations 排查实际来源。
  • 同名子模块不同含义：例如 acme.backends.cuda.ops 与 acme.backends.triton.ops 是两个完全不同的 module，只是末尾名称相同。绝对模块名负责区分它们，调用方可再用 import ... as cuda_ops / as triton_ops 建立清晰别名。

3. 典型例子#

假设项目结构（sys.path 里有 /proj，所以 app 是顶级 package）：

/proj/
  app/                  <- 顶级 package
    __init__.py
    main.py             <- 入口：python -m app.main
    pkg/
      __init__.py
      a.py
      b.py
      sub/
        __init__.py
        c.py
    sib/
      __init__.py
      e.py
      sub2/
        __init__.py
        f.py

例 1：同目录导入兄弟 module#

app/pkg/a.py 想用 app/pkg/b.py 里的 foo：

# 相对（推荐用于 package 内部）
from . import b
from .b import foo

# 绝对（也合法）
from app.pkg import b
from app.pkg.b import foo

. 表示"当前 package"，也就是 __package__ == "app.pkg"。

例 2：从兄弟 package 导入#

app/pkg/a.py 想用 app/sib/e.py 里的 bar：

# 相对：两个点退到 app，再进 sib
from ..sib import e
from ..sib.e import bar

# 绝对
from app.sib import e
from app.sib.e import bar

注意 .. 不能越过顶级 package。这里 pkg 和 sib 都是 app 的子 package，.. 退到 app 是合法的。app 可以是 regular package，也可以是 PEP 420 namespace package；关键不是磁盘上有没有 app/__init__.py，而是解释器能否把 app.pkg.a 作为 package module 加载，并正确设置 __package__ == "app.pkg"。

例 3：从兄弟 package 的下一级导入#

app/pkg/a.py 想用 app/sib/sub2/f.py 里的 baz：

# 相对
from ..sib.sub2 import f
from ..sib.sub2.f import baz

# 绝对
from app.sib.sub2 import f
from app.sib.sub2.f import baz

例 4：脚本入口#

app/main.py 作为入口，引用其它模块：

# main.py —— 推荐用 -m 启动：python -m app.main
from app.pkg.a import something    # 绝对，最稳
from .pkg.a import something       # 相对，要求 __spec__.parent == "app"，即用 -m 启动

4. 常见错误及其成因#

错误 1：ImportError: attempted relative import with no known parent package#

$ cd /proj/app/pkg
$ python a.py

a.py 包含 from . import b。直接运行该文件时，a.py 的 __name__ == "__main__"，而 __spec__ 与 __package__ 没有提供 app.pkg 这一 package 上下文，因此解释器无法确定相对导入的起点。

修复方式：

  • 在 /proj 下执行 python -m app.pkg.a，让解释器按 module 加载它并设置 __package__ == "app.pkg"。
  • 将 a.py 设计为独立脚本并使用绝对导入 from app.pkg import b，同时确保 /proj 位于 sys.path。

错误 2：ModuleNotFoundError: No module named 'app'#

$ cd /home/me
$ python -m app.main

当前目录是 /home/me，因此 sys.path[0] 为 /home/me。该搜索位置没有名为 app 的直接子项，解释器无法解析顶级 package app。

修复方式：

  • 执行 cd /proj && python -m app.main。
  • 通过 PYTHONPATH=/proj python -m app.main 显式加入项目根目录。
  • 使用 pyproject.toml 与 pip install -e . 把项目安装为 editable package。

名称拼写错误也可能产生相同异常。例如，from app.pgk.a import x 将 pkg 写成了 pgk；错误信息只表明该限定名称无法解析，不会区分搜索路径缺失与拼写错误。

错误 3：ImportError: attempted relative import beyond top-level package#

# app/__init__.py 里写：
from ..util import helper

app 已经是顶级 package，.. 会尝试移动到其 package 边界之外。该层级不存在可供解析的父 package，因此 Python 抛出此错误。

错误信息中的 "top-level package" 指相对导入起点所属的顶级 package，此处为 app。磁盘目录是否还有更外层的父目录不影响这一边界；顶级 package 由有效的 sys.path 搜索位置决定。

处理方式：使用绝对导入 from util import helper（前提是 util 也是顶级 package），或者把 util 移入 app 并作为 app.util 导入。

错误 4：__init__.py 循环 import → ImportError: cannot import name 'X'#

# app/pkg/__init__.py
from .a import Foo

# app/pkg/a.py
from . import b           # 触发 pkg/__init__.py 重入

# app/pkg/b.py
from .a import Foo        # 此时 a 还没执行完，Foo 尚未定义

报错形式是 ImportError: cannot import name 'Foo' from partially initialized module 'app.pkg.a'。

处理方式：拆分交叉依赖，例如按需在函数体内 import，或把共享逻辑下沉到独立 module；__init__.py 顶层只 re-export 不会形成回环的符号。

错误 5：sys.path[0] 改变顶级 package 可见性#

$ cd /proj/app
$ python pkg/a.py

a.py 中的 from app.pkg import b 会抛出 ModuleNotFoundError: No module named 'app'。执行 python pkg/a.py 时，解释器把 /proj/app/pkg 放入 sys.path[0]，而项目根目录 /proj 不在有效搜索位置中；因此 app 不是任何 sys.path 条目的直接子项。

处理方式：包内模块通常从项目根目录用 python -m app.pkg.a 启动，使解释器建立完整的 package 身份。

错误 6：__init__.py 使 namespace composition 失效#

假设 /env/a/acme/plugins/alpha 与 /env/b/acme/plugins/beta 原本共同组成 acme.plugins。如果搜索顺序靠前的 /env/a/acme/plugins/ 被补上 __init__.py，结果是：

  • PathFinder 会把该位置的 acme.plugins 作为 regular package 返回。
  • acme.plugins.__path__ 不再包含另一个 namespace portion。
  • /env/b 中的 acme.plugins.beta 因而不可见。

报错形式可能是 ModuleNotFoundError: No module named 'acme.plugins.beta'，即使对应目录确实存在。

处理方式：需要跨发行包合并时删除该 __init__.py；采用 regular package 时，则把所有子包安装到其有效搜索位置。选择取决于 package 的所有权边界。

5. 检查清单#

碰到 import 报错时，按顺序排查：

  1. python -c "import sys; print(sys.path)" —— 顶级 package 的父目录在不在里面？
  2. python -c "import app; print(app.__spec__)" —— origin 与 submodule search locations 是否符合预期？
  3. 出错的文件里打印 __name__、__spec__ 以及 getattr(__spec__, "parent", None) —— 相对导入的起点对不对？
  4. 启动命令是 python file.py 还是 python -m pkg.file？前者通常不会为 __main__ 建立 package spec。
  5. __init__.py 是不是在导入时就触发了循环？

Python Import Mechanism: Absolute vs Relative

Python's import system resolves module names and package context rather than file paths in isolation. It identifies the current module's runtime identity, then combines sys.modules, sys.path, and each package's __path__ to locate the target. This model accounts for absolute imports, relative imports, namespace packages, and the behavioral difference between executing a file directly and using python -m.

Version scope: this article follows the Python 3.14 language reference. The compatibility fallback through __package__ has an explicit version boundary described below.

1. Foundations#

Module#

A .py file can normally be loaded as a source module; modules may also come from extension libraries, built-ins, or custom loaders. After the first import, the module object enters sys.modules. Ordinary repeat imports do not execute its code again while that cache entry remains.

Package#

A package is a module with a __path__, which gives the import system locations in which to search for submodules and subpackages. A directory containing __init__.py normally forms a regular package; finders assemble a PEP 420 namespace package dynamically from matching directories.

The role of __init__.py#

  1. Marker: tells Python to treat the directory as a regular package.
  2. Initialization code: runs once on the first import pkg (even from pkg.a import x first executes pkg/__init__.py).
  3. Re-export façade: a typical idiom is to write from .a import Foo inside it, so that callers can use from pkg import Foo directly.
  4. Defining __all__: controls which names from pkg import * exposes.

Top-level package#

A top-level package is resolved directly from an entry in sys.path. It may be either a regular package or a namespace package.

Example: sys.path contains /home/me/proj, and /home/me/proj/app/__init__.py exists, therefore app is a top-level package. app.pkg and app.pkg.sub are its sub-packages, but they are not top-level.

Entries in sys.path determine the top-level boundary. The same directory tree can therefore acquire different top-level names under different launch locations or installation layouts.

Namespace package (PEP 420)#

A namespace package is a package whose search locations are supplied by multiple namespace portions. PathFinder collects matching directories from the parent search path and exposes them through a dynamically updated __path__; the shared levels omit __init__.py. The differences from a regular package are:

regular package namespace package
__init__.py required must be absent
__file__ present no single path represents the whole package; an implementation may omit it or set it to None
__path__ a sequence of submodule search locations a custom iterable that can combine portions dynamically; CPython commonly displays _NamespacePath
Purpose one wheel owns the whole package multiple wheels splice into the same import namespace

A typical use case is two distributions contributing subpackages under /env/a/acme/plugins/ and /env/b/acme/plugins/, while deliberately omitting __init__.py at the shared levels. When both parent locations are searchable, Python can combine those portions into one acme.plugins namespace.

Cross-location composition requires every matching location to participate as a namespace portion. If PathFinder encounters a regular package with the same name, it returns that package and does not merge the other namespace portions into it. Failure 6 shows how this rule changes subpackage visibility.

2. The import resolution process#

sys.path decides what can be found#

To resolve import X, the interpreter first looks up the dotted name X in sys.modules. On a cache miss, finders search sys.path for the top-level name, then continue through each package's __path__.

Common sources of sys.path entries include:

  • The startup script's directory; python a.py places the directory containing a.py at sys.path[0].
  • The current working directory for python -m pkg.mod.
  • The PYTHONPATH environment variable.
  • Interpreter-configured site-packages directories.

__name__, __spec__.parent, and __package__#

__name__ identifies the module. In Python 3.14, explicit relative imports primarily use __spec__.parent to identify its package.

How it was launched __name__ __spec__.parent __package__
python app/pkg/a.py (run as a file) "__main__" __spec__ is None None or ""
python -m app.pkg.a (run as a module) "__main__" "app.pkg" "app.pkg"
Imported elsewhere as import app.pkg.a "app.pkg.a" "app.pkg" "app.pkg"

In Python 3.14, explicit relative imports use __spec__.parent as the package anchor; __package__ provides a compatibility fallback when that value is unavailable. The fallback has been deprecated since Python 3.13 and is scheduled for removal in Python 3.15. Each additional leading dot moves one level upward from the anchor.

When a package file is run directly with python a.py, __main__.__spec__ is normally None and there is no usable package fallback, so from . import b has no anchor.

Absolute imports vs. relative imports#

  • Absolute import: from app.pkg import b. Resolves the full name from a sys.path root. The target is explicit, but callers still need updates when a package is renamed or moved.
  • Relative import: from . import b, from ..sib import e. Computed from the current module's package context. It cannot cross past the top level. A file launched directly normally lacks that context, while an entry module launched with -m may use relative imports.

PEP 8 recommends absolute imports; relative imports are appropriate for intra-package sibling/close-relative references.

Segment-by-segment resolution of a dotted name#

from a.b.c import d is not resolved in one step. It walks the .s segment by segment, and each segment is independently decided to be a regular package, a namespace package, or a plain module:

  1. Find a: walk sys.path looking for a directory or file named a, write it into sys.modules['a'].
  2. Find a.b: look for b in a.__path__, running the finder once more. If a is a namespace package, a.__path__ may be a union of several physical directories, and b may come from any of them.
  3. Find a.b.c: look for c in a.b.__path__.
  4. Fetch attribute d from the module object a.b.c. If it is absent, import-from also attempts to load submodule a.b.c.d; if that fails, it raises ImportError.

Every module loaded along the way is written into sys.modules. While the relevant cache entry remains, a repeat import returns it without running the finder. Deleting that entry causes the next import to search again.

How import updates a package namespace#

After loading a submodule, the import system also updates the parent package's namespace. Two rules determine the behavior of import a.b and from a import b.

(a) import a.b sets b as an attribute on a. The import system creates this binding as part of submodule loading, so an empty __init__.py has the same behavior:

import a.b           # even if a/__init__.py is completely empty
a.b.foo()            # this still works: the import system already bound b onto a

(b) If from a import b finds no attribute b on a, it attempts to load the submodule a.b. A successful load then binds b to a under the first rule. This fallback handles one attribute level; from a import b.c is outside the statement's grammar.

Ambiguity from same-named submodules / top-level packages#

The import system only looks at names; it does not understand "logically the same package". Two common ambiguities:

  • Two top-level packages with the same name collide: if one search location supplies a regular package or plain module, PathFinder returns that object rather than merging other same-named directories into it. Only implicit namespace portions compose across locations. Inspect foo.__spec__.origin and foo.__spec__.submodule_search_locations to diagnose the actual source.
  • Same-named submodules meaning different things: acme.backends.cuda.ops and acme.backends.triton.ops are distinct modules despite sharing the final component. Their absolute names distinguish them; callers can add explicit aliases such as cuda_ops and triton_ops.

3. Worked examples#

Assume the following project layout (sys.path contains /proj, so app is the top-level package):

/proj/
  app/                  <- top-level package
    __init__.py
    main.py             <- entry point: python -m app.main
    pkg/
      __init__.py
      a.py
      b.py
      sub/
        __init__.py
        c.py
    sib/
      __init__.py
      e.py
      sub2/
        __init__.py
        f.py

Example 1: importing a sibling module in the same directory#

app/pkg/a.py wants foo from app/pkg/b.py:

# relative (recommended for intra-package use)
from . import b
from .b import foo

# absolute (also valid)
from app.pkg import b
from app.pkg.b import foo

The single . means "the current package", that is, __package__ == "app.pkg".

Example 2: importing from a sibling package#

app/pkg/a.py wants bar from app/sib/e.py:

# relative: two dots back up to app, then descend into sib
from ..sib import e
from ..sib.e import bar

# absolute
from app.sib import e
from app.sib.e import bar

Note that .. cannot cross past the top-level package. Here both pkg and sib are sub-packages of app, so .. reaching app is legal. app may be a regular package or a PEP 420 namespace package; what matters is not whether app/__init__.py exists on disk, but whether the interpreter loaded app.pkg.a as a package module and set __package__ == "app.pkg".

Example 3: importing from one level down inside a sibling package#

app/pkg/a.py wants baz from app/sib/sub2/f.py:

# relative
from ..sib.sub2 import f
from ..sib.sub2.f import baz

# absolute
from app.sib.sub2 import f
from app.sib.sub2.f import baz

Example 4: the script entry point#

app/main.py is the entry point and pulls in other modules:

# main.py — recommended launch: python -m app.main
from app.pkg.a import something    # absolute, most robust
from .pkg.a import something       # relative, requires __spec__.parent == "app", i.e. launched with -m

4. Common Failures and Their Causes#

Failure 1: ImportError: attempted relative import with no known parent package#

$ cd /proj/app/pkg
$ python a.py

a.py contains from . import b. When run as a file, a.py's __name__ == "__main__", while __spec__ and __package__ provide no app.pkg package context. The interpreter therefore has no anchor for the relative import.

Resolution paths:

  • Run python -m app.pkg.a from /proj, so the interpreter loads it as a module and sets __package__ == "app.pkg".
  • Design a.py as a standalone script and use the absolute import from app.pkg import b, with /proj present on sys.path.

Failure 2: ModuleNotFoundError: No module named 'app'#

$ cd /home/me
$ python -m app.main

The current directory is /home/me, so sys.path[0] is /home/me. That search location has no direct child named app, so the interpreter cannot resolve the top-level package.

Resolution paths:

  • Run cd /proj && python -m app.main.
  • Add the project root explicitly with PYTHONPATH=/proj python -m app.main.
  • Use pyproject.toml and pip install -e . to install the project as an editable package.

A spelling error can produce the same exception. For example, from app.pgk.a import x writes pgk instead of pkg; the message reports an unresolved qualified name without distinguishing a missing search path from a misspelling.

Failure 3: ImportError: attempted relative import beyond top-level package#

# Inside app/__init__.py:
from ..util import helper

app is already the top-level package, so .. attempts to move beyond its package boundary. No parent package exists at that level, and Python raises this error.

In this diagnostic, "top-level package" means the top-level package containing the relative-import anchor, here app. Parent directories outside app/ on disk do not change that boundary; the effective sys.path entries determine which package is top-level.

Resolution: use the absolute import from util import helper when util is also a top-level package, or relocate it under app and import it as app.util.

Failure 4: a circular import in __init__.py → ImportError: cannot import name 'X'#

# app/pkg/__init__.py
from .a import Foo

# app/pkg/a.py
from . import b           # triggers re-entry into pkg/__init__.py

# app/pkg/b.py
from .a import Foo        # at this point a has not finished executing, Foo is not yet defined

The error shows up as ImportError: cannot import name 'Foo' from partially initialized module 'app.pkg.a'.

Resolution: break apart the cross-dependency by importing lazily inside a function or moving shared logic into a lower-level module. Top-level re-exports in __init__.py should preserve an acyclic import graph.

Failure 5: sys.path[0] changes top-level package visibility#

$ cd /proj/app
$ python pkg/a.py

a.py's from app.pkg import b raises ModuleNotFoundError: No module named 'app'. Running python pkg/a.py places /proj/app/pkg at sys.path[0], while the project root /proj is absent from the effective search path. Consequently, app is not a direct child of any sys.path entry.

Resolution: launch package modules from the project root with python -m app.pkg.a, allowing the interpreter to establish the complete package identity.

Failure 6: __init__.py disables namespace composition#

Suppose /env/a/acme/plugins/alpha and /env/b/acme/plugins/beta originally compose the acme.plugins namespace. If an __init__.py is added to the earlier search location /env/a/acme/plugins/, then:

  • PathFinder returns acme.plugins from that location as a regular package.
  • acme.plugins.__path__ no longer includes the other namespace portion.
  • acme.plugins.beta under /env/b is consequently not discoverable.

The resulting error may be ModuleNotFoundError: No module named 'acme.plugins.beta', even though the directory exists.

Resolution: remove __init__.py when the level must compose across distributions. For a regular package, install every subpackage into its effective search locations. The choice follows package ownership.

5. Diagnostic checklist#

When you hit an import error, work through these in order:

  1. python -c "import sys; print(sys.path)": is the parent directory of the top-level package present?
  2. python -c "import app; print(app.__spec__)": do the origin and submodule search locations match what you expected?
  3. In the failing file, print __name__, __spec__, and getattr(__spec__, "parent", None): is the relative-import anchor correct?
  4. Is the launch command python file.py or python -m pkg.file? The former normally does not establish a package spec for __main__.
  5. Does __init__.py trigger a cycle at import time?
