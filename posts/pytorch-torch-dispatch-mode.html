PyTorch TorchDispatchMode 的双向调度机制

PyTorch 的 dispatcher 既要把 ATen 算子送到 CPU、CUDA 和 autograd 实现，也要允许 FakeTensor、代理追踪与分布式张量在 Python 中改写算子语义。TorchDispatchMode 提供了这条跨语言路径：C++ dispatcher 把调用交给 Python handler，handler 可以返回结果，也可以重新进入 dispatcher 继续分派。本文按公开的 PyTorch v2.12.0 源码追踪这条回路；常规 key 选择与 redispatch 的背景见 《PyTorch Dispatcher 的多维分派与算子执行路径》。

1. Python 介入 dispatcher 的位置

常规算子调用由 dispatcher 选择最高优先级的 DispatchKey，各层处理本层语义后再向下 redispatch。TorchDispatchMode 与 tensor subclass 在其中加入一个受控的 C++/Python 回路：Python key 触发 boxed fallback，fallback 经 PyInterpreterVTable 调用 Python handler；当 handler 调用 func(*args, **kwargs) 时，算子重新进入 dispatcher。mode 暂存与 key 屏蔽分别控制重入和优先级，使多个 Python 覆盖层能够按既定顺序组合。

1.1 Dispatcher 调用链

这条回路建立在 dispatcher 的基本模型上：算子按 DispatchKey 选择实现,包装层完成本层工作后可以继续 redispatch。

PyTorch 的 dispatcher 是一张按 DispatchKey 索引的函数表。每个 ATen 算子(aten::add、aten::matmul 等)拥有自己的一张表,表里每一行对应一个"行为层":CUDA 后端、CPU 后端、Autograd 包装、Autocast 包装等。一次调用做四件事:

  1. 从输入张量的属性和 TLS 状态算出一个 64 位位图(DispatchKeySet),表示当前激活了哪些 key。
  2. 取位图中最高优先级的 key。
  3. 跳到该 key 对应的函数指针。
  4. 所选 kernel 可以缩小 key set 并 redispatch，使控制权落到下一层。例如 Autograd kernel 建立反向图节点后，再把数值计算交给 CUDA kernel。

优先级阶梯从高到低大致是:模式层(Python / Functionalize / Autocast 等)→ Autograd 层 → Backend 层(CPU / CUDA / MPS 等)。这种排序让"先记反向图再算数值"、"先降精度再 autograd"这些层级约束自动得到保证。

Dispatcher 以 redispatch 连接多个行为层。每层处理本层语义、调整 key set，再把调用交给下一层。

1.2 算子级拦截

图捕获、fake execution、分布式张量和算子日志都需要在 ATen 算子进入具体 backend 实现前运行 Python 逻辑。handler 可以检查或替换参数、记录调用，也可以直接返回符合 schema 的结果。

功能它要拦截每个 op 来做什么
make_fx 与 AOTAutograd 的 ATen graph capture追踪器执行待捕获函数，并把经过代理模式的 ATen 调用记录为 fx.Graph 节点。AOTAutograd 还会构造并追踪联合 forward/backward 函数。
FakeTensorMode (shape inference)在不分配设备 storage 的条件下执行算子元数据传播，得到输出的 shape、dtype、stride 与模拟 device。
DTensor (分布式)张量在多 GPU 上分片(shard)了。一个 add 操作要变成:① 检查输入分片方式;② 必要时插 all-reduce;③ 每个 rank 局部算 add;④ 包装回 DTensor。这些决策必须在 op 调用现场做。
调试 / 日志在 mode 的动态作用域内记录可覆盖 ATen 调用的名称、参数类型或输入 shape。

这些功能共享同一项工程需求：C++ dispatcher 必须在算子级别调用 Python 扩展逻辑，同时保持 libtorch 的纯 C++ 使用方式。PyTorch 没有把 Python 函数直接塞进每个算子的 dispatch 表，而是在 Python key 上注册统一 fallback，再由 fallback 找到当前 mode 或 tensor subclass。

1.3 代表性使用场景

三个短例分别展示 mode、代理追踪和 tensor subclass 的外部行为。第 5 章再说明它们在 v2.12.0 中采用的具体路径。

(a) FakeTensorMode

import torch
from torch._subclasses.fake_tensor import FakeTensorMode

with FakeTensorMode():
    x = torch.randn(1024, 1024, device="cuda")     # 不分配显存
    y = torch.randn(1024, 512,  device="cuda")
    z = x @ y                                       # 不跑 matmul
    print(z.shape, z.dtype, z.device)
    # 输出: torch.Size([1024, 512]) torch.float32 cuda:0

这段代码不为 x、y 或 z 分配 CUDA storage，也不启动 CUDA matmul kernel。FakeTensorMode 拦截相关 factory 与矩阵运算调用，通过 meta kernel、专用 fake 实现或 decomposition 推导输出 metadata。并非每个 ATen 算子都有独立的 meta kernel，缺少 fake 支持的算子仍可能报错。

(b) make_fx / ProxyTorchDispatchMode

import torch
from torch.fx.experimental.proxy_tensor import make_fx

def f(x, y):
    return (x + y).relu()

gm = make_fx(f, tracing_mode="fake")(torch.randn(3, 4), torch.randn(3, 4))
gm.graph.print_tabular()
# opcode         name    target              args        kwargs
# placeholder    x       x                   ()          {}
# placeholder    y       y                   ()          {}
# call_function  add     aten.add.Tensor     (x, y)      {}
# call_function  relu    aten.relu.default   (add,)      {}
# output         output  output              ((relu,),)  {}

make_fx 执行一次 f(x, y)，并由 ProxyTorchDispatchMode 把经过代理路径的 ATen 调用记录到 fx.Graph。这类 torch-dispatch tracing 也是 AOTAutograd 图捕获机制的一部分，但它不等同于 Dynamo 的 Python bytecode capture。

(c) DTensor

import torch
from torch.distributed.tensor import DTensor, DeviceMesh, Shard, Replicate, distribute_tensor

mesh = DeviceMesh("cuda", torch.arange(4))                          # 4 GPU 网格
x = distribute_tensor(torch.randn(1024, 1024), mesh, [Shard(0)])    # 行分片
w = distribute_tensor(torch.randn(1024, 512),  mesh, [Replicate()]) # 复制
y = x @ w                                                            # 自动决定通信 + 局部算
# y 是 DTensor,placement=[Shard(0)],每个 rank 持有 256x512 的本地结果

这条 @ 表达式进入 aten::matmul 后由 DTensor 截获。DTensor 根据输入 placement 推导输出 placement、所需 collective communication 与各 rank 的局部运算，随后再调用底层 matmul kernel。

FakeTensor 与 Proxy tracing 使用 infra mode，DTensor 则以 tensor subclass 参与调度。它们共享 C++ 到 Python 的协议入口，但 handler 顺序、后续执行和 fallback 条件并不相同。

1.4 Python API 钩子的边界

__torch_function__ 在可覆盖的 Python API 层分派，适合重定义 torch.* 函数和 Tensor method 的外部语义。它不会自动观察绕过该 Python API 层、直接进入 dispatcher 的 C++ 调用。

  • Autograd engine 发起的 dispatcher 调用。只要调用没有重新经过可覆盖的 Python API，__torch_function__ 就不会收到通知。
  • Dispatcher decomposition 产生的子算子。这些调用可能直接从 C++ 或生成代码进入 dispatcher。
  • C++ kernel 或自定义算子再次调用 ATen。内部调用是否可见取决于它是否重新进入 dispatcher 以及当时的 key guard，不能由 Python API 包装层统一观察。

__torch_dispatch__ 把覆盖点下移到 dispatcher 的 Python key，因此能观察更多 ATen 层调用。它仍不是“进程中所有算子调用”的无条件探针：fallthrough、显式 redispatch、禁用 guard 和不重新进入 dispatcher 的 kernel 内部代码都会形成边界。

这条 C++/Python 回路由下列部件共同完成：

职责v2.12.0 实现

2. C++ → Python 的实现路径

Python key 把算子从 dispatcher 的 C++ 表项送入 Python runtime。下面沿 PyTorch v2.12.0 源码追踪这条路径中的依赖隔离、对象映射、GIL 获取、参数转换、handler 调用、结果回传与重入控制；其它版本应以对应 tag 或 commit 为准。

2.1 c10 与 CPython 的依赖边界

libc10.so 是可由纯 C++ 程序使用的核心库，因此跨语言调用首先受到一条依赖约束：

约束:libc10.so(PyTorch 的核心 C++ 库)不能直接依赖 CPython 的头文件或 libpython.so。libtorch_python.so 才能依赖 CPython。

这条边界使 libtorch 能在没有 Python runtime 的进程中使用，例如：

  • 移动端推理:把 PyTorch 模型编译成 C++ 可执行文件,运行时没有 Python。
  • JIT/lite-interpreter 部署:Android / iOS 的 PyTorch 应用。
  • 嵌入式系统:Jetson Nano 上跑模型,Python 是可选的。
  • 纯 C++ 服务：进程直接使用 LibTorch C++ API，在不嵌入 CPython 的条件下执行模型。

Dispatcher 的注册表数据结构、key 枚举和 KernelFunction 位于 libc10，Python handler 则依赖 CPython。跨越这条依赖边界需要由上层提供实现，而核心库只保留抽象接口。

PyTorch 用反转控制（IoC）连接两侧：

  1. libc10 定义抽象接口 PyInterpreterVTable，用纯虚函数描述核心库需要的 Python 能力。
  2. libtorch_python(实际加载 CPython 的层)在静态初始化时填充这个 vtable 的具体实现,把指针塞回 c10 的全局变量。
  3. 运行时 c10 调用 Python 相关功能时只经过 vtable 虚函数，因此编译和链接 libc10 都无需引入 libpython.so；加载 libtorch_python 后，vtable 指向可用实现。
  4. 纯 C++ 进程使用 no-op vtable，相关虚函数会返回受控错误。

因此，dispatcher 通过 vtable 发起跨语言调用，CPython 相关实现留在 libtorch_python.so。这个接口就是下一节的 PyInterpreterVTable。

2.2 PyInterpreterVTable:抽象接口

vtable 定义在 c10/core/impl/PyInterpreter.h 第 75-175 行附近。完整结构(裁剪):

// c10/core/impl/PyInterpreter.h
struct C10_API PyInterpreterVTable {
  virtual ~PyInterpreterVTable() = default;

  // 调试用:返回 "cpython" 或 "noop"
  virtual std::string name() const = 0;

  // === 引用计数管理 ===
  virtual void incref(PyObject* pyobj) const = 0;
  virtual void decref(PyObject* pyobj) const = 0;
  virtual bool try_incref(const c10::impl::PyObjectSlot& pyobj_slot) const = 0;
  virtual size_t refcnt(PyObject* pyobj) const = 0;

  // === Tensor 操作 ===
  virtual c10::intrusive_ptr<TensorImpl> detach(const TensorImpl* self) const = 0;

  // === ★ 关键的"分派到 Python"方法 ===
  virtual void dispatch(const c10::OperatorHandle& op,
                        torch::jit::Stack* stack) const = 0;

  virtual void python_op_registration_trampoline(
      const c10::OperatorHandle& op, c10::DispatchKey,
      c10::DispatchKeySet keyset, torch::jit::Stack* stack,
      bool with_keyset, bool with_op) const = 0;

  virtual void python_dispatcher(const c10::OperatorHandle& op,
      c10::DispatchKeySet, torch::jit::Stack* stack) const = 0;

  // === 元数据查询 ===
  virtual c10::IntArrayRef strides(const TensorImpl* self) const = 0;
  virtual c10::Device device(const TensorImpl* self) const = 0;
  // ... 还有 sizes / numel / dim / sym_size 等十几个
};

struct C10_API PyInterpreter {
  const PyInterpreterVTable* vtable_;
  const PyInterpreterVTable& operator*() const noexcept { return *vtable_; }
  const PyInterpreterVTable* operator->() const noexcept { return vtable_; }
  void disarm() noexcept;             // 进程退出时切换到 noop_vtable
};

三组虚函数,各管一类事:

组用途调用位置
引用计数(incref/decref/refcnt)管理 c10 持有的 Python 对象的生命周期TensorImpl 析构时、PyObjectSlot 操作时
Dispatch(dispatch、python_op_registration_trampoline、python_dispatcher)把 C++ op 调用转发到 PythonPythonFallbackKernel(2.4 节)和 torch.library 注册 Python 实现的 op
元数据(strides/sizes/device 等)Tensor subclass 重写 shape 信息时,C++ 通过 vtable 反查TensorImpl::sym_sizes_custom() 等

本文重点是第二组中的 dispatch 虚函数。它在 libtorch_python 中由 ConcretePyInterpreterVTable::dispatch 实现,第 2.6 节会沿这条路径继续分析。

示例 2.2:disarm 的作用 PyInterpreterHolder 的静态生命周期可能晚于 CPython 中对象的可用期。其析构函数调用 PyInterpreter::disarm(),把解释器切换到 c10 的无操作 vtable,从而避免后续 C++ 析构路径再进入已经不可用的 CPython。具体的引用计数操作由 vtable 实现和包装对象的所有权代码负责,不是 PyObjectSlot 的成员方法。

2.3 PyObjectSlot:解释器关联与包装指针

Vtable 规定跨语言调用接口，PyObjectSlot 则把 C++ tensor 表示映射回所属 Python 对象。tensor subclass 依赖这项映射：dispatcher 持有 TensorImpl*，而待执行的 __torch_dispatch__ 定义在对应的 Python 类上。

每个 TensorImpl 内嵌一个 PyObjectSlot。在 PyTorch v2.12.0 中,这个 slot 保存两个原子指针:拥有该包装的 PyInterpreter 标记,以及指向 Python THPVariable 包装的 PyObject*。定义见固定版本的 c10/core/impl/PyObjectSlot.h:

// c10/core/impl/PyObjectSlot.h (结构摘录)
struct C10_API PyObjectSlot {
 public:
  PyObjectSlot() : pyobj_interpreter_(nullptr), pyobj_(nullptr) {}

  PyInterpreter* pyobj_interpreter() const {
    return pyobj_interpreter_.load(std::memory_order_acquire);
  }
  PyObject* load_pyobj() const {
    return pyobj_.load(std::memory_order_acquire);
  }
  void clear() {
    pyobj_.store(nullptr, std::memory_order_release);
    pyobj_interpreter_.store(nullptr, std::memory_order_release);
  }

 private:
  std::atomic<PyInterpreter*> pyobj_interpreter_;
  std::atomic<PyObject*> pyobj_;
};

嵌入到 TensorImpl 里(c10/core/TensorImpl.h 第 2974 行附近):

class TORCH_API TensorImpl : public c10::intrusive_ptr_target {
  ...
  impl::PyObjectSlot pyobj_slot_;       // 64 位构建中为两个指针

 public:
  impl::PyObjectSlot* pyobj_slot()       { return &pyobj_slot_; }

TensorImpl.h 对大小的静态断言表明,该结构在 64 位构建中是 16 字节,在 32 位构建中是 8 字节。初始状态下两个指针都为空;Python 包装路径会关联解释器和包装对象:

  1. 普通 torch.Tensor 被 Python 包装时:THPVariable_WrapWithType 读取已有 slot,按需创建 THPVariable,再由 PyObjectPreservation 路径初始化关联。后续包装可以复用现有对象。
  2. Tensor subclass 被构造时:Python 绑定的 subclass 构造路径建立包装关联,并调用 set_python_dispatch(true) 使 TensorImpl 带上 DispatchKey::Python。_make_wrapper_subclass 还要求类实现 __torch_dispatch__。
两个条件:tensor subclass 路径既依赖 TensorImpl 的 Python key,也依赖 PyObjectSlot 中匹配的解释器标记与 Python 包装。前者触发 fallback,后者把 C++ tensor 映射回正确的 Python 对象。

vtable 和 pyobj_slot 提供了所需的基础设施,实际跳转由一个 boxed kernel 完成。它以 m.fallback 形式注册到 Python key 上(另有几个相关 key),实现位于 aten/src/ATen/core/PythonFallbackKernel.cpp。

当 Python 是当前最高优先级 key 时，dispatcher 调用 pythonFallback。函数体在第 52 行附近完成 mode 与 subclass 的路径选择，下面的节选只保留相关分支：

// aten/src/ATen/core/PythonFallbackKernel.cpp
void pythonFallback(const c10::OperatorHandle& op,
                    c10::DispatchKeySet dispatch_keys,
                    torch::jit::Stack* stack) {

  // tls_on_entry 由 PythonTLSSnapshot fallback 设置。
  TORCH_INTERNAL_ASSERT(tls_on_entry.has_value());

  // 屏蔽低于 Python 的 dispatch key。
  // 当前 mode 的暂存发生在 Python 参数分派层,见 2.5 节。
  c10::impl::ExcludeDispatchKeyGuard exclude_guard(after_Python_keyset);

  const auto& schema = op.schema();
  const auto num_arguments = schema.arguments().size();

  // === ② 路径 A: 模式栈(mode stack)非空 → 用栈顶的 mode 处理
  //
  // TorchDispatchModeTLS 是 C++ 端的一个线程局部模式栈;
  // 每次 Python 端进 `with SomeMode():` 就 push 一个 mode 对象到这。
  // pythonFallback 拿栈顶的 mode,调它的 pyinterpreter()->dispatch(...)。
  const auto mode_stack_len = c10::impl::TorchDispatchModeTLS::stack_len();
  if (mode_stack_len > 0) {
    const auto& cur_mode = c10::impl::TorchDispatchModeTLS::get_stack_at(mode_stack_len - 1);
    cur_mode->pyinterpreter()->dispatch(op, stack);
    // ↑ 通过 vtable 进入 Python,调用 mode.__torch_dispatch__(...)
    return;
  }

  // === ③ 路径 B: 没有模式,但有 tensor subclass 在输入里
  //
  // 走完输入参数,找:① 是否真有 tensor 带 Python key;② 任意一个有 pyobj_slot 的 tensor
  // 用作 PyInterpreter 入口。
  bool tensors_with_python_key_present = false;
  c10::impl::PyInterpreter* interpreter = nullptr;
  for (const auto& ivalue : torch::jit::last(*stack, num_arguments)) {
    if (ivalue.isTensor()) {
      auto* t = ivalue.unsafeToTensorImpl();
      if (t->key_set().has(c10::DispatchKey::Python)) {
        tensors_with_python_key_present = true;
      }
      if (!interpreter && t->pyobj_slot()->load_pyobj()) {
        interpreter = t->pyobj_slot()->pyobj_interpreter();
      }
    }
    // ... List / Optional 形式参数也走相同逻辑(略)
  }

  if (interpreter) {
    if (tensors_with_python_key_present) {
      // 真有 subclass 想拦截这次调用 → 跳 Python
      (*interpreter)->dispatch(op, stack);
    } else {
      // 输入里有 PyInterpreter 但都不带 Python key:把 Python 位 mask 掉,
      // 让 dispatcher 用 redispatch 继续走下一层: 没人想拦,正常算就行
      c10::DispatchKeySet keyset = dispatch_keys.remove(c10::DispatchKey::Python);
      c10::impl::LocalDispatchKeySet local_keyset = c10::impl::tls_local_dispatch_key_set();
      c10::impl::ForceDispatchKeyGuard no_python_guard(
        local_keyset.included_.remove(c10::DispatchKey::Python),
        local_keyset.excluded_);
      op.redispatchBoxed(keyset, stack);
    }
    return;
  }

  TORCH_INTERNAL_ASSERT(0, "Hit Python dispatch key but no arguments had PyInterpreter");
}

这段 fallback 依次保存入口 TLS、选择 mode 或 subclass、屏蔽相应 key，并通过 interpreter vtable 转交 boxed 参数：

  1. 入口状态与 guard:pythonFallback 断言 tls_on_entry 已由 PythonTLSSnapshot fallback 设置。after_Python_keyset 屏蔽低于 Python 的 key,但不包含 Python 本身。当前 mode 的暂存发生在后续 Python 参数分派层。
  2. ② 路径 A:mode stack 非空。这是 FakeTensorMode、ProxyTorchDispatchMode 这些 mode 的入口。它们在 __enter__ 时把自己 push 进 TorchDispatchModeTLS,__exit__ 时 pop。pythonFallback 只取栈顶: LIFO 优先级。
  3. ③ 路径 B:输入张量带 Python key。这是 tensor subclass 路径(如 FakeTensor 作为参数传给某 op)。tensors_with_python_key_present 检查 key,interpreter 找一个有 pyobj_slot 的张量作为入口。两个条件都满足才真跳。
  4. 路径 B 的保护分支:如果找到 Python 包装,但扫描结果没有 tensor 携带 Python key,代码移除该 key 并 redispatch。这是处理聚合参数和 key-set 扫描假阳性的防御路径,不应概括为所有普通 torch.Tensor 的常规路径。
边栏 2.4:mode 与 subclass 的组合顺序 pythonFallback 先检查 mode stack,因此最外层 C++ 入口先由栈顶 mode 的解释器接管。不过完整的 Python 多重分派顺序还由 dispatch_on_mode 与 dispatch_on_subclass 决定。在 v2.12.0 中,用户 mode 和用户 subclass 优先于基础设施 mode;基础设施 mode 可以返回 NotImplemented,再交给 subclass 或下一 mode。仅凭 fallback 中两个分支的排列,不能推出所有 mode 都无条件压过所有 subclass。

2.5 Mode 暂存与 key 屏蔽

2.4 节的 guard:

c10::impl::ExcludeDispatchKeyGuard exclude_guard(after_Python_keyset);

这个 guard 只负责 dispatch-key 优先级的一部分。PyTorch v2.12.0 源码把 after_Python_keyset 注释为 All the keys below the Python key:它不包含 Python 本身。

after_Python_keyset 在 PythonFallbackKernel.cpp 第 27 行附近定义:

constexpr c10::DispatchKeySet after_Python_keyset =
    c10::DispatchKeySet(c10::DispatchKeySet::FULL)
    ^ (c10::DispatchKeySet(c10::DispatchKeySet::FULL_AFTER, c10::DispatchKey::Python)
       | c10::DispatchKeySet(c10::DispatchKey::Python));

ExcludeDispatchKeyGuard 构造时把这些较低优先级的位加入 TLS exclude,析构时恢复。Mode 的重入控制则在另一处完成:dispatch_on_mode 在调用当前 mode 的 __torch_dispatch__ 前构造 StashTorchDispatchModeGuard,暂时把当前 mode 从 TLS 栈移走。

示例 2.5: mode 透传时发生了什么 在 with OuterMode(): z = x + y 中,顶层调用先进入 PythonFallbackKernel。调用 OuterMode.__torch_dispatch__ 前,dispatch_on_mode 暂存 OuterMode。若方法体执行 return func(*args, **kwargs),嵌套调用不会再次命中同一个 mode;它会继续交给下一层 mode、tensor subclass 或常规 dispatcher 路径。方法返回后,OuterMode 被恢复到 TLS 栈。

Tensor subclass 不依赖这项 mode 栈暂存。Subclass 若直接用原 subclass 参数再次调用 func,仍可能重入自身;常见实现会先 unwrap 参数,或使用相应的 dispatch-disable guard。

2.6 ConcretePyInterpreterVTable::dispatch

pythonFallback 在 mode 路径调用 cur_mode->pyinterpreter()->dispatch(op, stack)。这个虚函数在固定版本的 torch/csrc/PyInterpreter.cpp 第 290 至 344 行实现:

// torch/csrc/PyInterpreter.cpp
void ConcretePyInterpreterVTable::dispatch(
    const c10::OperatorHandle& op, torch::jit::Stack* stack) const {

  const auto& schema = op.schema();
  const auto num_arguments = schema.arguments().size();
  auto arguments = torch::jit::pop(*stack, num_arguments);   // 从 stack 弹出参数

  // === ① 获取 GIL: 跨界第一步
  py::gil_scoped_acquire g;

  // === ② 找 op 对应的 Python API 函数(例如 torch.ops.aten.add.Tensor)
  std::vector<PyObject*> overloaded_args;
  py::handle torch_api_function_overload = getTorchApiFunction(op);

  // === ③ 扫描 IValue 参数,收集"带 Python key 的 tensor"(subclass)
  for (const auto idx : c10::irange(arguments.size())) {
    const auto& ivalue = arguments[idx];
    if (ivalue.isTensor()) {
      const auto& tensor = ivalue.toTensor();
      if (isPythonTensor(tensor)) {
        append_overloaded_tensor(&overloaded_args, py::cast(tensor).ptr());
      }
    }
    // 还处理 list / optional-list 内的 tensor(略)
  }

  // === ④ 把所有 IValue 转成 PyObject 形式的 (args, kwargs)
  auto args_kwargs = parseIValuesToPyArgsKwargs(op, arguments);
  auto args = std::move(args_kwargs.first);
  auto kwargs = std::move(args_kwargs.second);

  // === ⑤ 调用 Python: 找 __torch_dispatch__,带 mode stack 优先级 + types MRO
  PyObject* obj = handle_torch_function_no_python_arg_parser(
      overloaded_args, args.ptr(), kwargs.ptr(), nullptr,
      torch_api_function_overload.ptr(), nullptr,
      &op, &arguments, TorchFunctionName::TorchDispatch);

  // === ⑥ 把 Python 返回值转回 IValue 并压回 stack
  pushPyOutToStack(op, stack,
      py::reinterpret_steal<py::object>(obj),
      "__torch_dispatch__");
}

这六步覆盖从 C++ boxed 参数到 Python handler，再回到 dispatcher stack 的完整转换：

  1. ① py::gil_scoped_acquire g;：获取 GIL，使当前线程能够安全调用 CPython API；RAII 对象在函数返回时释放 GIL。
  2. ② getTorchApiFunction(op):从 op 名("aten::add.Tensor")找对应的 Python 函数对象(torch.ops.aten.add.Tensor)。这个函数对象后续被传给 Python 端,Python 端 __torch_dispatch__ 的 func 参数就是它。
  3. ③ 扫描"覆盖"列表:走一遍 IValue 输入,找带 Python key 的张量,收集到 overloaded_args。Python 端需要这个列表才能按 MRO 顺序找哪个 subclass 的 __torch_dispatch__ 应该被调。
  4. ④ parseIValuesToPyArgsKwargs:把所有 IValue 转成 Python 对象(args 是 tuple、kwargs 是 dict)。对 tensor 参数,py::cast(tensor) 会优先从 pyobj_slot_ 取已有的 Python 包装,没有才新建；这里正是 2.3 节所述反向关联参与对象转换的位置。
  5. ⑤ handle_torch_function_no_python_arg_parser:实际"调 Python" 的步骤。它走 TorchDispatchModeTLS 栈 + overloaded_args 的 MRO,找第一个有 __torch_dispatch__ 的对象,把 (func, types, args, kwargs) 传进去。具体的调度优先级:
       (a) Mode stack 从顶到底依次尝试,直到一个返回非 NotImplemented;
       (b) Subclass 按 MRO 顺序尝试 overloaded_args 里的对象。
    具体 mode vs subclass 的优先级,见 §3.3。
  6. ⑥ pushPyOutToStack:Python 返回了一个 PyObject(可能是张量、tuple、scalar 等)。把它转回 IValue,push 到 stack 上。dispatcher 顶层从 stack 取就是最终结果。

这条路径包含 GIL 获取、参数扫描、IValue 与 Python 对象转换、Python handler 执行和按 schema 回写结果。本文没有给出这些步骤的固定耗时:实际成本取决于算子 schema、参数数量、Python handler、GIL 竞争和构建版本。第 7 章据此讨论成本边界,不引用未经该版本基准验证的常数。

跨语言路径由三项状态协同完成：vtable 隔离 libc10 与 CPython 依赖，PyObjectSlot 关联解释器和 Python wrapper，mode 暂存与 key mask 分别控制重入和优先级。Tensor subclass 还需要在自己的表示转换中处理自身重入。

3. TorchDispatchMode 的 Python 协议

C++ fallback 把 boxed 算子交给 Python 后，TorchDispatchMode 协议规定 handler 如何接收调用、返回结果以及发起嵌套调度。动态作用域由 with 管理，__torch_dispatch__ 接收规范化的 operator 与参数，而 func(*args, **kwargs) 用于继续执行剩余调度层。

3.1 类与 with 块

TorchDispatchMode 基类定义在 torch/utils/_python_dispatch.py 第 72 行附近。简化:

# torch/utils/_python_dispatch.py
class TorchDispatchMode:
    """A ``TorchDispatchMode`` allows you to override the meaning of all
    ``__torch_dispatch__`` overridable functions within a dynamic scope ...
    Independent subclasses of TorchDispatchMode are compositional: modes can
    be pushed onto a stack using ``with MyMode():``. When you call functions
    in the PyTorch API inside your ``__torch_dispatch__`` implementation,
    by default, they will forward on to the next mode on the mode stack."""

    supports_higher_order_operators = False

    def __init__(self, _dispatch_key=None):
        if _dispatch_key is not None:
            self.__dict__["_dispatch_key"] = _dispatch_key   # e.g. PreDispatch
        self.old_dispatch_mode_flags: deque[bool] = deque()

    def __torch_dispatch__(self, func, types, args=(), kwargs=None):
        raise NotImplementedError                            # 子类必须实现

    def __enter__(self):
        global _is_in_torch_dispatch_mode
        self._lazy_init_old_dispatch_mode_flags()
        self.old_dispatch_mode_flags.append(_is_in_torch_dispatch_mode)
        _is_in_torch_dispatch_mode = True
        _push_mode(self)                                     # ★ 把自己 push 到 TLS 模式栈
        return self

    def __exit__(self, exc_type, exc_val, exc_tb):
        mb_dk_or_mode_key = self.__dict__.get("_dispatch_key", None) \
                            or self.__dict__.get("_mode_key", None)
        global _is_in_torch_dispatch_mode
        _is_in_torch_dispatch_mode = self.old_dispatch_mode_flags.pop()
        _pop_mode(mb_dk_or_mode_key)                          # ★ pop

__enter__ 和 __exit__ 共同维护 mode 的动态作用域：

  • __enter__ 调用 _push_mode(self)。CPython binding 随后进入 c10::impl::TorchDispatchModeTLS::push(mode),把 mode 压入 C++ 的线程局部模式栈,并通过 c10::impl::tls_set_dispatch_key_included(DispatchKey::Python, true) 将 Python key 加入 TLS include 集合。下一次 dispatcher 计算 key set 时,该位参与候选项选择。
  • __exit__ 按相反顺序 pop mode；模式栈清空后,Python key 从 TLS include 集合移除。

3.3 mode 与 subclass 的处理顺序

pythonFallback 为 mode stack 与 tensor subclass 提供两条入口。前者由动态作用域激活，后者由参与运算的 tensor 类型激活；两种入口对应不同的状态归属和重入规则。

(A) Mode 路径:全局拦截

Mode 路径继承 TorchDispatchMode,并由 with 块激活。它具有以下运行特征:

  • 动态作用域覆盖:with 块中的 ATen 调用都可进入该 mode,包括没有 tensor 输入的 factory ops,如 torch.empty 与 torch.arange。TLS 激活不依赖输入中已有 subclass tensor。
  • 由 TLS include 触发 Python key,作用范围是整个 with 块的动态作用域(包括它内部调用的任何函数)。
  • 同时多个 mode 时构成LIFO 栈,栈顶优先。

(B) Subclass 路径:只在某些张量参与时拦截

Subclass 路径在 torch.Tensor 子类的 __torch_dispatch__ classmethod 中定义算子语义:

class MyTensor(torch.Tensor):
    @classmethod
    def __torch_dispatch__(cls, func, types, args=(), kwargs=None):
        kwargs = kwargs or {}
        # 伪代码:先把 MyTensor 解包成内部普通 tensor
        unwrapped_args = tree_map(unwrap_my_tensor, args)
        unwrapped_kwargs = tree_map(unwrap_my_tensor, kwargs)
        out = func(*unwrapped_args, **unwrapped_kwargs)
        return tree_map(wrap_my_tensor, out)

直接用原始 MyTensor 参数调用 func 会再次选中同一个 subclass。真实实现必须定义表示方式,并通过解包或相应 guard 避免自身重入;上面的代码只描述控制流。

特点:

  • 只在 MyTensor 实例参与某次 op 调用时触发。普通 torch.Tensor 之间的 op 跟它无关。
  • PyTorch 的 subclass 构造路径会建立 Python 包装关联并设置 Python dispatch 状态。用户代码通常通过 torch.Tensor._make_subclass 或 _make_wrapper_subclass 等受版本约束的入口创建对象,而不是直接修改 dispatch key。
  • 看不到 factory op(没 tensor 输入,subclass 无从插入)。要拦截 factory op,需要 mode 路径。
边栏 3.3:Mode 与 subclass 的状态归属 Mode 把语义附着在一段动态执行作用域上,因此能够覆盖 factory op；subclass 把语义附着在 tensor 类型及其实例上,因此只在相关对象参与调用时激活。两种入口可以配合使用：FakeTensorMode 创建的张量本身也是 FakeTensor subclass。离开 with 块后,后续 operator 仍可通过 tensor 类型识别这些对象。mode 负责创建动态环境,subclass 保存数据语义。

(C) 同时存在时的处理顺序

pythonFallback 首先检查 mode stack,随后处理 tensor subclass 路径:

if mode_stack_len > 0 {
    cur_mode->pyinterpreter()->dispatch(...);
    return;
}
// 没 mode,才考虑 subclass
if interpreter && tensors_with_python_key_present {
    (*interpreter)->dispatch(...);
}

这段代码只选择进入哪个 PyInterpreter,并不独自决定全部 Python handler 的先后。python_arg_parser.cpp 的多重分派按用户 mode、用户 subclass、基础设施 mode 或 subclass 的分组处理候选项。基础设施 mode 常用 NotImplemented 把不属于自己的组合交给下一候选项。

3.4 嵌套调度如何继续

func 是 OpOverload;调用它会再次进入 dispatcher。对 mode 而言,Python 参数分派层已经用 StashTorchDispatchModeGuard 暂存当前 mode:

def __torch_dispatch__(self, func, types, args=(), kwargs=None):
    kwargs = kwargs or {}
    # 可能做一些拦截逻辑 ...
    return func(*args, **kwargs)         # 再次进入 dispatcher

OpOverload.__call__ 通过 Python/C++ 绑定重新调用 ATen operator。随后 dispatcher 根据当前 TLS 和输入重新选 key;它不是固定跳到某个 backend。

StashTorchDispatchModeGuard 已在嵌套调用前暂存当前 mode。调用重新进入 dispatcher 后，下一层 mode 或输入中的 tensor subclass 仍可参与；当 Python 覆盖层耗尽时，算子继续进入常规 autograd 与 backend 调度。

边界:对 mode,调用 func 可以继续到下一 mode、tensor subclass、autograd 或 backend。对 subclass,若参数仍包含原 subclass,同样的调用可能重入自身。该行为依赖内部 guard 与参数分派实现,调试其它版本时应核对对应源码。

3.5 与 __torch_function__ 的边界

PyTorch 还有一个更早的协议叫 __torch_function__。两者名字相似容易混,但拦截位置完全不同:

__torch_function____torch_dispatch__

5. 三类协议使用者

同一套跨语言协议可以承载不同的 operator 语义。FakeTensorMode 传播元数据，ProxyTorchDispatchMode 记录 ATen graph，DTensor 则根据 placement 规划局部计算与通信。三者共享 dispatcher 入口，却使用不同的 handler 状态和返回值约束。

5.1 FakeTensorMode:无数据执行

FakeTensorMode 是一种元数据执行环境：它用 shape、dtype、stride 和模拟 device 表示 tensor，并在不访问数值 storage 的条件下传播算子输出信息。

用途:

  • torch.compile 的图构建:Inductor 在 codegen 前需要各 operator 的输出 metadata；FakeTensor 执行提供这些信息而不运行对应的数值 kernel。
  • 内存规划分析:编译器和分析工具可以利用中间 tensor 的 shape、dtype 与 stride 估算存储需求；allocator 行为和临时 workspace 仍需结合实际执行验证。
  • 动态形状(symbolic shapes):当输入维度由符号表示时,fake execution 传播各中间 tensor 的符号 shape 表达式。

5.3 DTensor:分布式张量

DTensor 为 tensor 数据附加分布式 placement。当 x @ w 这样的表达式进入 handler 时，框架推导：

  1. 输入 x 在 rank 0/1/2/3 上各自持有第 0 维的 1/4(行分片);
  2. 权重 w 在所有 rank 上都有完整一份(replicated);
  3. x @ w 在每个 rank 上执行局部 matmul，输出自然保持行分片，因此不需要 collective；
  4. x.T @ x 产生 partial sum，需要通过 all-reduce materialize 完整结果。

DTensor.__torch_dispatch__ 把每个 operator 与对应的 sharding propagation 和通信规则连接起来。torch/distributed/tensor/_api.py 定义 DTensor 类,torch/distributed/tensor/_dispatch.py 承载实际 dispatch 与 sharding 逻辑。

简化的 DTensor.__torch_dispatch__ 流程:

  1. 从 func 看是什么 op,在 OpDispatcher.sharding_propagator 里查"这个 op 的 sharding 传播规则"。例如 aten::mm 的规则:Shard(0) @ Replicate → Shard(0)。
  2. 检查输入张量的实际 placement 是否符合规则需要。如果不符合,插入collective 通信(all_gather / reduce_scatter / all_reduce / all_to_all)做 redistribute。
  3. 每个 rank 调底层 aten::mm 跑局部 matmul。
  4. 把输出包成新的 DTensor,带 sharding spec。
边栏 5.3: DTensor 是数据驱动的协议 DTensor 以 tensor subclass 保存 placement，所有使用该 tensor 的 operator 都会继承分布式语义。FakeTensorMode 则以动态作用域控制元数据执行。前者把语义附着在数据上，后者把语义附着在一段执行上下文上。

5.4 DTensor 的 C++ 快路径

2025 年下半年的 PR #167051 将常见 DTensor operator 的 sharding 决策移入 C++ 路径。基础 DTensor 因而可以先尝试 C++ fast path，再由常规 Python multiple dispatch 覆盖未命中的对象与行为。

动机是减少常见 DTensor 算子反复进入 Python handler 的开销。实际收益取决于模型、算子粒度、placement 与通信模式；PR 不能支撑一个跨 workload 固定成立的微秒数或 step 百分比。

这条 C++ fast path 的识别与回退关系如下：

  1. v2.12.0 的特殊识别与分派位于 torch/csrc/utils/python_arg_parser.cpp 的 Python 参数 multiple-dispatch 路径，而不是 PythonFallbackKernel。
  2. 基础 DTensor 或继承其基础 __torch_dispatch__ 的 subclass 可进入 dispatchDTensorOp；不满足识别条件的对象仍按常规 Python multiple dispatch 处理。

基础 DTensor.__torch_dispatch__ 仍然存在。对 subclass 而言，它可以委托回基础实现并重新进入 C++ fast path；因此不能概括成“Python 方法只处理复杂 op 的 fallback”。公开实现见 torch/distributed/tensor/_api.py。

class DTensor(torch.Tensor):
    _op_dispatcher: op_dispatch.OpDispatcher = op_dispatch.OpDispatcher()

    @classmethod
    def __torch_dispatch__(cls, func, types, args=(), kwargs=None):
        # 示意：subclass 可委托给基础 DTensor 语义，
        # 具体 fast-path 资格由 python_arg_parser.cpp 判断
        def unwrap(t):
            if isinstance(t, DTensor) and type(t) is not DTensor:
                return DTensor(t._local_tensor, t._spec, requires_grad=t.requires_grad)
            return t
        args = torch.utils._pytree.tree_map(unwrap, args)
        kwargs = torch.utils._pytree.tree_map(unwrap, kwargs or {})
        return func(*args, **kwargs)

这里优化的是基础 DTensor 的常见 Python multiple-dispatch 路径，不是把所有 __torch_dispatch__ handler 一般化为 C++ 实现。复杂行为、subclass 参与方式与 fast-path 覆盖范围都应以对应版本源码为准。

7.3 实现约束

约束 1:引用关系 TensorImpl ↔ PyObject ↔ Mode

pyobj_slot_ 关联 PyObject*,Python wrapper 则持有 intrusive_ptr<TensorImpl>。Mode 若把 tensor 保存在自身字段中,还会延长这条引用链的生命周期。长期存活的 mode 应使用 weakref 保存非拥有引用,或在 __exit__ 中显式清理缓存。

约束 2:嵌套 mode 的 LIFO 次序

调用 mode handler 时，当前 mode 会被临时移出栈。handler 内执行 func(*args, **kwargs) 会重新进入调度，因此下一层 mode 或 tensor subclass 仍有机会处理该算子。若 handler 直接返回自行构造的结果，才会终止这次链式处理。super().__torch_dispatch__ 属于 Python 继承语义，不能替代 mode stack 的调度。

约束 3:_DISPATCH_HANDLE_DIRECTLY 的覆盖范围

FakeTensor 的部分查询 op,包括 size、stride、device 和 dim,可通过 _DISPATCH_HANDLE_DIRECTLY 与 in_kernel_invocation_manager 在通用 handler 路径之外处理。依赖完整 op 日志的 mode 需要先核对 fake_tensor.py 中的直接处理集合；若目标是用户级 API 调用,也可在边界清楚的场景组合 __torch_function__。

约束 4:tls_on_entry 不变量

PythonFallbackKernel.cpp 第 17-23 行的注释:

// This TLS is used to track the state of the dispatcher to be able to restore
// it when calling back into python.  It has the following invariant:
//  - It must be empty while python code is executed.
//  - It should only be set once even for multiple dispatcher calls that do not come back to python.
thread_local std::optional<c10::impl::LocalDispatchKeySet> tls_on_entry;

Mode handler 通过 func(*args, **kwargs) 发起下一次 dispatch,由框架维护该 TLS 不变量。绕过此入口手动调用 op.redispatchBoxed(...) 可能触发 "Accessing torch dispatch state outside of __torch_dispatch__ is not allowed" 错误。

约束 5:Python 退出时的 disarm

Python teardown 会 disarm vtable。C++ 侧若在 static 容器中缓存带 pyobj_slot 的 TensorImpl,其析构顺序必须早于解释器失效,否则可能触发 "attempted to call dispatch on a Tensor with nontrivial PyObject after corresponding interpreter died" 断言。相应缓存可在 atexit 前清空,或由拥有者在析构时调用 pyobj_slot.clear()。

约束 6:FakeTensorMode 的基础设施槽位

Bidirectional Dispatch with PyTorch TorchDispatchMode

The PyTorch dispatcher routes ATen operators to CPU, CUDA, and autograd implementations, while FakeTensor, proxy tracing, and distributed tensors need to redefine operator semantics in Python. TorchDispatchMode supplies that cross-language path: the C++ dispatcher transfers a call to a Python handler, which may return a result or re-enter the dispatcher. This article traces the loop in the public PyTorch v2.12.0 source; the related PyTorch Dispatcher: Multidimensional Dispatch and Operator Execution article covers ordinary key selection and redispatch.

1. Where Python enters the dispatcher

Ordinary dispatch selects the highest-priority DispatchKey, lets that layer process its semantics, and then redispatches toward the backend. TorchDispatchMode and tensor subclasses add a controlled C++/Python loop to that chain. The Python key invokes a boxed fallback, the fallback reaches a Python handler through PyInterpreterVTable, and a handler call to func(*args, **kwargs) enters the dispatcher again. Mode stashing controls re-entry while key masking preserves dispatch priority, allowing several Python override layers to compose.

1.1 Dispatcher call chain

Only one dispatcher property is required as background: an operator is selected through a DispatchKeySet, and kernels may redispatch after completing the work owned by their layer.

PyTorch's dispatcher is a function table indexed by DispatchKey. Each ATen operator (aten::add, aten::matmul, etc.) owns its own table, where each row corresponds to a "behavior layer": CUDA backend, CPU backend, autograd wrapper, autocast wrapper, and so on. A single call does four things:

  1. Compute a DispatchKeySet from input tensor attributes and thread-local state.
  2. Take the highest-priority key in the bitmap.
  3. Jump to the function pointer registered under that key.
  4. The selected kernel may update the active key set and redispatch to the next layer.

The ordering of keys determines whether interception happens before or after layers such as autograd and the device backend. The precise order is versioned dispatcher state, not a fixed three-level abstraction.

Python interception is a continuation of dispatcher execution. The C++ fallback transfers control through PyInterpreterVTable, while mode stashing and key masking determine where a nested operator call resumes.

1.2 Operator-level interception

Operator-level tools need a hook below the public torch.* API. That hook can inspect arguments, select an alternate implementation, record a graph node, or return a value without running the ordinary backend kernel.

1.4 Python API hook boundary

__torch_function__ overrides supported public Python APIs. __torch_dispatch__ sits at ATen dispatch and therefore observes a different boundary, including operator calls initiated below the public Python wrapper when they pass through its dispatch position.

  • Calls initiated by C++ components need not re-enter a public torch.* wrapper.
  • Calls produced by decompositions can be dispatched directly as lower-level ATen operators.
  • Custom operators calling ATen operators can remain entirely below the Python API layer.

The lower hook provides broader operator coverage, but no mode is guaranteed to observe every conceptual operation. Visibility still depends on dispatch-key order, decompositions, direct handlers, and whether a component redispatches through ATen.

2. The C++ → Python implementation path

The Python key moves an operator from a C++ dispatcher entry into the Python runtime. The PyTorch v2.12.0 source path below covers dependency isolation, object mapping, GIL acquisition, argument conversion, handler invocation, result conversion, and re-entry control. Use the matching tag or commit when debugging another release.

2.1 The dependency boundary between c10 and CPython

libc10.so is a core library that pure C++ programs can use, which imposes a dependency constraint on cross-language dispatch:

Constraint: libc10.so (PyTorch's core C++ library) cannot directly depend on CPython headers or libpython.so. Only libtorch_python.so may depend on CPython.

This boundary keeps libtorch usable in processes without a Python runtime, including:

  • Mobile inference: compile a PyTorch model into a C++ executable, with no Python at runtime.
  • JIT / lite-interpreter deployment: Android / iOS PyTorch apps.
  • Embedded systems: running models on a Jetson Nano, where Python is optional.
  • Pure C++ services: a process can execute a model through the LibTorch C++ API without embedding CPython.

The dispatcher registry, key enumeration, and KernelFunction live in libc10, while Python handlers depend on CPython. The upper layer must implement the crossing while the core library retains only an abstract interface.

PyTorch connects the two sides through inversion of control (IoC):

  1. libc10 defines the abstract PyInterpreterVTable, whose pure virtual methods describe the Python capabilities required by the core library.
  2. libtorch_python, the layer linked against CPython, installs the concrete vtable during static initialization and writes its pointer into a c10 global.
  3. At runtime, c10 calls Python-related functionality through the vtable, so compiling and linking libc10 does not require libpython.so. Once libtorch_python is loaded, the vtable points to the concrete implementation.
  4. Pure C++ processes use the no-op vtable, which reports controlled errors for Python-only operations.

The dispatcher therefore initiates cross-language calls through the vtable, leaving CPython-specific implementation in libtorch_python.so. The interface itself is PyInterpreterVTable.

2.2 PyInterpreterVTable: the abstract interface

2.3 PyObjectSlot: interpreter association and wrapper pointer

The vtable defines the cross-language call interface. PyObjectSlot maps a C++ tensor representation back to its Python object. Tensor subclasses rely on this mapping because the dispatcher holds a TensorImpl*, while the relevant __torch_dispatch__ method belongs to the associated Python class.

Every TensorImpl embeds a PyObjectSlot. In PyTorch v2.12.0, the slot stores two atomic pointers: the PyInterpreter that owns the association and a PyObject* for the Python THPVariable wrapper. The fixed-version definition is in c10/core/impl/PyObjectSlot.h:

// c10/core/impl/PyObjectSlot.h (structural excerpt)
struct C10_API PyObjectSlot {
 public:
  PyObjectSlot() : pyobj_interpreter_(nullptr), pyobj_(nullptr) {}

  PyInterpreter* pyobj_interpreter() const {
    return pyobj_interpreter_.load(std::memory_order_acquire);
  }
  PyObject* load_pyobj() const {
    return pyobj_.load(std::memory_order_acquire);
  }
  void clear() {
    pyobj_.store(nullptr, std::memory_order_release);
    pyobj_interpreter_.store(nullptr, std::memory_order_release);
  }

 private:
  std::atomic<PyInterpreter*> pyobj_interpreter_;
  std::atomic<PyObject*> pyobj_;
};

Embedded into TensorImpl (c10/core/TensorImpl.h, around line 2974):

class TORCH_API TensorImpl : public c10::intrusive_ptr_target {
  ...
  impl::PyObjectSlot pyobj_slot_;       // two pointers in a 64-bit build

A static assertion in TensorImpl.h records a size of 16 bytes for 64-bit builds and 8 bytes for 32-bit builds. Both pointers begin as null; the Python wrapping paths establish the interpreter and wrapper association:

  1. When a regular torch.Tensor is wrapped for Python, THPVariable_WrapWithType checks the existing slot, creates a THPVariable when needed, and initializes the association through PyObjectPreservation. Later wrapping can reuse that object.
  2. When a tensor subclass is constructed, the Python binding creates the wrapper association and calls set_python_dispatch(true), adding DispatchKey::Python to its TensorImpl. _make_wrapper_subclass also requires the class to define __torch_dispatch__.
Two conditions: the tensor-subclass path needs the Python key on TensorImpl and a matching interpreter plus wrapper association in PyObjectSlot. The key selects the fallback; the association maps the C++ tensor back to the correct Python object.

// aten/src/ATen/core/PythonFallbackKernel.cpp
void pythonFallback(const c10::OperatorHandle& op,
                    c10::DispatchKeySet dispatch_keys,
                    torch::jit::Stack* stack) {

  // tls_on_entry was set by the PythonTLSSnapshot fallback.
  TORCH_INTERNAL_ASSERT(tls_on_entry.has_value());

  // Mask dispatch keys below Python.
  // The current mode is stashed later by the Python argument-dispatch layer.
  c10::impl::ExcludeDispatchKeyGuard exclude_guard(after_Python_keyset);

  const auto& schema = op.schema();
  const auto num_arguments = schema.arguments().size();

  // === (2) Path A: the mode stack is non-empty → route through the top mode.
  //
  // TorchDispatchModeTLS is the C++-side thread-local mode stack;
  // each Python `with SomeMode():` pushes a mode object onto it.
  // pythonFallback grabs the top mode and calls its pyinterpreter()->dispatch(...).
  const auto mode_stack_len = c10::impl::TorchDispatchModeTLS::stack_len();
  if (mode_stack_len > 0) {
    const auto& cur_mode = c10::impl::TorchDispatchModeTLS::get_stack_at(mode_stack_len - 1);
    cur_mode->pyinterpreter()->dispatch(op, stack);
    // ↑ goes through the vtable into Python, eventually calls mode.__torch_dispatch__(...)
    return;
  }

  // === (3) Path B: no mode, but inputs contain a tensor subclass.
  //
  // Walk the input arguments looking for: (1) any tensor carrying the Python key;
  // (2) any tensor with a pyobj_slot, used as the PyInterpreter entry point.
  bool tensors_with_python_key_present = false;
  c10::impl::PyInterpreter* interpreter = nullptr;
  for (const auto& ivalue : torch::jit::last(*stack, num_arguments)) {
    if (ivalue.isTensor()) {
      auto* t = ivalue.unsafeToTensorImpl();
      if (t->key_set().has(c10::DispatchKey::Python)) {
        tensors_with_python_key_present = true;
      }
      if (!interpreter && t->pyobj_slot()->load_pyobj()) {
        interpreter = t->pyobj_slot()->pyobj_interpreter();
      }
    }
    // ... List / Optional arguments go through the same logic (omitted)
  }

  if (interpreter) {
    if (tensors_with_python_key_present) {
      // Some subclass really wants to intercept this call → jump to Python
      (*interpreter)->dispatch(op, stack);
    } else {
      // Inputs have a PyInterpreter but none carry the Python key:
      // mask the Python bit out and let the dispatcher redispatch to the next layer
      // No handler was selected, so continue dispatch normally.
      c10::DispatchKeySet keyset = dispatch_keys.remove(c10::DispatchKey::Python);
      c10::impl::LocalDispatchKeySet local_keyset = c10::impl::tls_local_dispatch_key_set();
      c10::impl::ForceDispatchKeyGuard no_python_guard(
        local_keyset.included_.remove(c10::DispatchKey::Python),
        local_keyset.excluded_);
      op.redispatchBoxed(keyset, stack);
    }
    return;
  }

  TORCH_INTERNAL_ASSERT(0, "Hit Python dispatch key but no arguments had PyInterpreter");
}

The function selects between mode and subclass dispatch while preserving the dispatcher state required for re-entry:

  1. Entry state and guard: pythonFallback asserts that tls_on_entry was set by the PythonTLSSnapshot fallback. after_Python_keyset masks keys below Python but does not include Python itself. The current mode is stashed later by Python argument dispatch.
  2. (2) Path A: mode stack non-empty. This is the entry point for modes such as FakeTensorMode and ProxyTorchDispatchMode. They push themselves onto TorchDispatchModeTLS in __enter__ and pop in __exit__. pythonFallback takes only the top mode (LIFO priority).
  3. (3) Path B: input tensor carries the Python key. This is the tensor-subclass path, for example when a FakeTensor appears as an argument. tensors_with_python_key_present checks the key, and interpreter finds a tensor whose pyobj_slot supplies the entry point. Both conditions are required before control enters the Python handler.
  4. Path B's defensive branch: if a Python wrapper is found but the scan finds no tensor carrying the Python key, the code removes that key and redispatches. This handles false positives from aggregate arguments and key-set scanning; it is not the ordinary path for every regular torch.Tensor.
Aside 2.4: mode and subclass composition order pythonFallback checks the mode stack first, so the outer C++ entry initially uses the top mode's interpreter. The full Python multiple-dispatch order is then controlled by dispatch_on_mode and dispatch_on_subclass. In v2.12.0, user modes and user subclasses precede infrastructure modes, and an infrastructure mode may return NotImplemented so that a subclass or another mode can handle the call. The branch order alone does not imply that every mode unconditionally wins over every subclass.

2.5 Mode stashing and key masking

The guard from §2.4:

c10::impl::ExcludeDispatchKeyGuard exclude_guard(after_Python_keyset);

This guard handles only the dispatch-key-priority part. In PyTorch v2.12.0, the source describes after_Python_keyset as All the keys below the Python key; it does not contain Python itself.

after_Python_keyset is defined in PythonFallbackKernel.cpp around line 27:

constexpr c10::DispatchKeySet after_Python_keyset =
    c10::DispatchKeySet(c10::DispatchKeySet::FULL)
    ^ (c10::DispatchKeySet(c10::DispatchKeySet::FULL_AFTER, c10::DispatchKey::Python)
       | c10::DispatchKeySet(c10::DispatchKey::Python));

ExcludeDispatchKeyGuard adds those lower-priority keys to TLS exclude for its lifetime. Mode re-entry is controlled elsewhere:dispatch_on_mode constructs a StashTorchDispatchModeGuard before calling the current mode's __torch_dispatch__, temporarily removing that mode from the TLS stack.

Example 2.5:pass-through from a mode For with OuterMode(): z = x + y, the top-level call first reaches PythonFallbackKernel. Before OuterMode.__torch_dispatch__ runs, dispatch_on_mode stashes OuterMode. If the method returns func(*args, **kwargs), the nested call cannot immediately select the same mode; it proceeds to the next mode, a tensor subclass, or the regular dispatcher path. The outer mode is restored when the method returns.

Tensor subclasses do not use this mode-stack stash. Calling func again with the same subclass arguments can re-enter the subclass, so implementations commonly unwrap arguments or use an appropriate dispatch-disable guard.

2.6 ConcretePyInterpreterVTable::dispatch

In the mode path, pythonFallback calls cur_mode->pyinterpreter()->dispatch(op, stack). The fixed-version implementation is in torch/csrc/PyInterpreter.cpp at lines 290 through 344:

// torch/csrc/PyInterpreter.cpp
void ConcretePyInterpreterVTable::dispatch(
    const c10::OperatorHandle& op, torch::jit::Stack* stack) const {

  const auto& schema = op.schema();
  const auto num_arguments = schema.arguments().size();
  auto arguments = torch::jit::pop(*stack, num_arguments);   // pop args off the stack

  // === (1) acquire the GIL: step one across the boundary
  py::gil_scoped_acquire g;

  // === (2) find the op's Python API function (e.g. torch.ops.aten.add.Tensor)
  std::vector<PyObject*> overloaded_args;
  py::handle torch_api_function_overload = getTorchApiFunction(op);

  // === (3) scan IValue args, collecting "tensors that carry the Python key" (subclasses)
  for (const auto idx : c10::irange(arguments.size())) {
    const auto& ivalue = arguments[idx];
    if (ivalue.isTensor()) {
      const auto& tensor = ivalue.toTensor();
      if (isPythonTensor(tensor)) {
        append_overloaded_tensor(&overloaded_args, py::cast(tensor).ptr());
      }
    }
    // also handles tensors inside list / optional-list (omitted)
  }

  // === (4) convert all IValues into PyObject (args, kwargs)
  auto args_kwargs = parseIValuesToPyArgsKwargs(op, arguments);
  auto args = std::move(args_kwargs.first);
  auto kwargs = std::move(args_kwargs.second);

  // === (5) call into Python: find __torch_dispatch__, by mode-stack priority + types MRO
  PyObject* obj = handle_torch_function_no_python_arg_parser(
      overloaded_args, args.ptr(), kwargs.ptr(), nullptr,
      torch_api_function_overload.ptr(), nullptr,
      &op, &arguments, TorchFunctionName::TorchDispatch);

  // === (6) convert Python return value back to IValue and push onto the stack
  pushPyOutToStack(op, stack,
      py::reinterpret_steal<py::object>(obj),
      "__torch_dispatch__");
}

These are the 6 actual boundary-crossing steps. Section by section:

  1. (1) py::gil_scoped_acquire g;: acquires the GIL before the C++ thread calls CPython APIs. The RAII object releases it when the function scope exits.
  2. (2) getTorchApiFunction(op): from the op name ("aten::add.Tensor") look up the corresponding Python function object (torch.ops.aten.add.Tensor). This function object is passed to Python later, becoming the func argument of __torch_dispatch__.
  3. (3) Collect the "overloaded" list: walk the IValue inputs, find tensors carrying the Python key, and collect them into overloaded_args. The Python side needs this list to determine, by MRO order, which subclass's __torch_dispatch__ to invoke.
  4. (4) parseIValuesToPyArgsKwargs: convert all IValues into Python objects (args becomes a tuple, kwargs a dict). For tensor arguments, py::cast(tensor) first tries the existing wrapper from pyobj_slot_, falling back to constructing a new one. This is where the reverse pointer of §2.3 earns its keep.
  5. (5) handle_torch_function_no_python_arg_parser: the actual "call Python" step. It walks the TorchDispatchModeTLS stack plus the MRO of overloaded_args, finds the first object with a __torch_dispatch__, and passes (func, types, args, kwargs) to it. The specific dispatch priority:
       (a) mode stack from top to bottom, until one returns something other than NotImplemented;
       (b) subclasses in MRO order, walking overloaded_args.
    See §3.3 for the exact mode vs subclass ordering.
  6. (6) pushPyOutToStack: Python returns a PyObject (possibly a tensor, tuple, scalar, etc.). Convert it back to an IValue and push it onto the stack; the top-level dispatcher picks it up as the final result.

This path includes GIL acquisition, argument scanning, IValue and Python-object conversion, Python handler execution, and schema-based result conversion. This article does not assign a fixed duration to those steps: the cost depends on the operator schema, argument count, Python handler, GIL contention, and build. Section 7 therefore states the cost boundary without relying on constants that were not benchmarked for this version.

Three pieces of state complete the cross-language path: the vtable isolates libc10 from CPython, PyObjectSlot associates an interpreter with a Python wrapper, and mode stashing plus key masking control re-entry and priority. Tensor subclasses also handle self-reentry in their representation conversion.

3. The TorchDispatchMode Python protocol

After the C++ fallback transfers a boxed operator to Python, the TorchDispatchMode protocol defines how a handler receives the call, returns a result, or starts nested dispatch. A with block owns the dynamic scope, __torch_dispatch__ receives the normalized operator and arguments, and func(*args, **kwargs) continues through the remaining dispatch layers.

3.1 The class and the with block

The TorchDispatchMode base class is defined in torch/utils/_python_dispatch.py around line 72. Simplified:

# torch/utils/_python_dispatch.py
class TorchDispatchMode:
    """A ``TorchDispatchMode`` allows you to override the meaning of all
    ``__torch_dispatch__`` overridable functions within a dynamic scope ...
    Independent subclasses of TorchDispatchMode are compositional: modes can
    be pushed onto a stack using ``with MyMode():``. When you call functions
    in the PyTorch API inside your ``__torch_dispatch__`` implementation,
    by default, they will forward on to the next mode on the mode stack."""

    supports_higher_order_operators = False

    def __init__(self, _dispatch_key=None):
        if _dispatch_key is not None:
            self.__dict__["_dispatch_key"] = _dispatch_key   # e.g. PreDispatch
        self.old_dispatch_mode_flags: deque[bool] = deque()

    def __torch_dispatch__(self, func, types, args=(), kwargs=None):
        raise NotImplementedError                            # subclasses must implement

    def __enter__(self):
        global _is_in_torch_dispatch_mode
        self._lazy_init_old_dispatch_mode_flags()
        self.old_dispatch_mode_flags.append(_is_in_torch_dispatch_mode)
        _is_in_torch_dispatch_mode = True
        _push_mode(self)                                     # push self onto the TLS mode stack
        return self

    def __exit__(self, exc_type, exc_val, exc_tb):
        mb_dk_or_mode_key = self.__dict__.get("_dispatch_key", None) \
                            or self.__dict__.get("_mode_key", None)
        global _is_in_torch_dispatch_mode
        _is_in_torch_dispatch_mode = self.old_dispatch_mode_flags.pop()
        _pop_mode(mb_dk_or_mode_key)                          # pop

The key parts are __enter__ and __exit__:

  • __enter__ calls _push_mode(self), which is the core of the Python ↔ C++ bridge. Through the CPython binding it calls c10::impl::TorchDispatchModeTLS::push(mode), so the mode enters the C++-side thread-local mode stack. It also calls c10::impl::tls_set_dispatch_key_included(DispatchKey::Python, true) to set the Python bit in the TLS include set. The next time the dispatcher computes the bitmap, the Python bit will be 1.
  • __exit__ reverses everything: the mode leaves the C++ stack, and if the stack becomes empty, the Python bit is removed from the TLS include set.

So the actual effect chain of a with MyMode(): statement is:

Python:  with MyMode():
            # __enter__ → _push_mode(mode)
C++:     TorchDispatchModeTLS::push(mode_pyobj)
            # mode enters the C++ stack, Python key enters TLS include
Python:    # user code ...
            z = x + y   # aten::add fires the dispatcher
C++:        Dispatcher::call(aten::add)
              # compute bitmap: tensors' key_set has no Python bit, but TLS include does!
              # resulting bitmap = {Python, AutogradCUDA, CUDA}
              # highest bit = Python → pythonFallback
            pythonFallback(...)
              # mode_stack_len > 0 → take the mode path
              # call mode.pyinterpreter->dispatch(...)
Python:       mode.__torch_dispatch__(func=aten.add.Tensor, types=(Tensor,Tensor), args=(x,y))
              # mode interception logic ...
              return func(*args, **kwargs)   # current mode is temporarily stashed

              # the next mode, subclass, autograd, or backend may handle it
              ...continue dispatch and return z

3.3 Mode and subclass handler order

pythonFallback exposes separate entries for the mode stack and tensor subclasses. A mode is activated by dynamic scope, whereas a subclass is activated by participating tensor objects; the two paths therefore differ in state ownership and re-entry behavior.

(A) Mode path: global interception

The mode path subclasses TorchDispatchMode and is activated by a with block. It has the following runtime properties:

  • Dynamic-scope coverage: ATen calls within the with block can enter the mode, including factory ops such as torch.empty and torch.arange. TLS activation does not require an existing subclass tensor among the inputs.
  • Triggered by TLS include setting the Python key; the scope of effect is the entire dynamic scope of the with block (including any function called from within).
  • When multiple modes are present they form a LIFO stack, top of stack first.

(B) Subclass path: intercept only when certain tensors participate

Define a subclass of torch.Tensor and put the interception logic into its __torch_dispatch__ classmethod:

class MyTensor(torch.Tensor):
    @classmethod
    def __torch_dispatch__(cls, func, types, args=(), kwargs=None):
        kwargs = kwargs or {}
        # Pseudocode: unwrap MyTensor into its ordinary inner tensor.
        unwrapped_args = tree_map(unwrap_my_tensor, args)
        unwrapped_kwargs = tree_map(unwrap_my_tensor, kwargs)
        out = func(*unwrapped_args, **unwrapped_kwargs)
        return tree_map(wrap_my_tensor, out)

Calling func with the original MyTensor arguments selects the same subclass again. A real implementation must define its representation and prevent self-reentry by unwrapping or using an appropriate guard; the snippet shows only the control flow.

Characteristics:

  • Triggered only when a MyTensor instance participates in an op call. Ops between plain torch.Tensor instances do not involve it.
  • PyTorch's subclass construction paths establish the Python wrapper association and Python dispatch state. User implementations commonly create objects through version-sensitive entry points such as torch.Tensor._make_subclass or _make_wrapper_subclass rather than editing dispatch keys directly.
  • Factory ops have no tensor input from which to activate the subclass. Their interception therefore uses the mode path.
Aside 3.3: state ownership in modes and subclasses A mode attaches semantics to a dynamic execution scope and can therefore cover factory ops. A subclass attaches semantics to a tensor type and its instances, so it activates only when those objects participate in a call. The two entries can cooperate: tensors created under FakeTensorMode are also FakeTensor subclasses. After the with block exits, later operators can still identify those objects from their tensor type. The mode creates the dynamic environment, while the subclass preserves the data semantics.

(C) Handler order when both are present

pythonFallback checks the mode stack first and then considers the tensor-subclass path:

if mode_stack_len > 0 {
    cur_mode->pyinterpreter()->dispatch(...);
    return;
}
// no mode → consider subclass
if interpreter && tensors_with_python_key_present {
    (*interpreter)->dispatch(...);
}

This branch chooses which PyInterpreter receives the initial C++ entry; it does not determine the complete ordering of Python handlers. Multiple dispatch in python_arg_parser.cpp groups candidates as user modes, user subclasses, and infrastructure modes or subclasses. Infrastructure modes commonly return NotImplemented so that a subclass or another mode can handle combinations outside their scope.

3.4 Nested dispatch continuation

func is an OpOverload, so calling it enters the dispatcher again. For a mode, the Python argument-dispatch layer has already stashed the current mode with StashTorchDispatchModeGuard:

def __torch_dispatch__(self, func, types, args=(), kwargs=None):
    kwargs = kwargs or {}
    # maybe some interception logic ...
    return func(*args, **kwargs)         # enter the dispatcher again

OpOverload.__call__ invokes the ATen operator through the Python/C++ binding. The dispatcher then selects a key from the current TLS state and inputs; there is no fixed jump to a particular backend.

StashTorchDispatchModeGuard removes the current mode before the nested call re-enters the dispatcher. The same mode is therefore not selected immediately, while another mode or tensor subclass may still intercept the operator. After the Python override layers are exhausted, dispatch continues through the regular autograd and backend keys.

Boundary: for a mode, calling func can continue to another mode, a tensor subclass, autograd, or a backend. For a subclass, calling it with the original subclass arguments can re-enter that same subclass. The behavior depends on internal guards and argument dispatch, so another release should be checked against its matching source.

5. Three protocol users

The same cross-language protocol carries different operator semantics. FakeTensorMode propagates metadata, ProxyTorchDispatchMode records an ATen graph, and DTensor plans local computation and communication from placements. They share the dispatcher entry while imposing different handler state and result constraints.

5.1 FakeTensorMode: shape inference without computation

FakeTensorMode is a metadata execution environment. It represents tensors through shape, dtype, stride, and simulated device, then propagates operator outputs without reading numerical storage.

Use cases:

  • Graph construction for torch.compile: Inductor needs operator output metadata before code generation. FakeTensor execution supplies that information without running the corresponding numerical kernels.
  • Memory-planning analysis: compilers and analysis tools can estimate storage requirements from intermediate shapes, dtypes, and strides. Allocator behavior and temporary workspaces still require validation against actual execution.
  • Dynamic shapes: when input dimensions are symbolic, fake execution propagates symbolic shape expressions through intermediate tensors.

5.3 DTensor: distributed tensors

DTensor attaches a distributed placement to tensor data. When an expression such as x @ w reaches its handler, the framework derives:

  1. Input x holds 1/4 of the 0th dimension on ranks 0/1/2/3 (row-sharded);
  2. Weight w is fully replicated across all ranks;
  3. Each rank computes a local matmul for x @ w. The output remains row-sharded, so this placement requires no collective.
  4. x.T @ x produces a partial sum, which requires an all-reduce to materialize the complete result.

DTensor.__torch_dispatch__ connects each operator with its sharding propagation and communication rule. Source: torch/distributed/tensor/_api.py contains the DTensor class, while torch/distributed/tensor/_dispatch.py contains the dispatch and sharding logic.

Simplified flow of DTensor.__torch_dispatch__:

  1. Look at func to determine the op, query the "sharding propagation rule" for that op in OpDispatcher.sharding_propagator. For example the rule for aten::mm: Shard(0) @ Replicate → Shard(0).
  2. Check whether the actual placement of input tensors satisfies the rule. If not, insert collective communication (all_gather / reduce_scatter / all_reduce / all_to_all) to redistribute.
  3. Each rank invokes the underlying aten::mm for the local matmul.
  4. Wrap the output back into a DTensor with the new sharding spec.
Aside 5.3: data-driven DTensor dispatch DTensor stores placement in a tensor subclass, so every operator using that tensor inherits its distributed semantics. FakeTensorMode uses a dynamic scope to control metadata execution instead. The former attaches semantics to data; the latter attaches semantics to an execution context.

5.4 The DTensor C++ fast path

In the second half of 2025, PR #167051 moved sharding decisions for common DTensor operators into a C++ path. Base DTensor can therefore try the C++ fast path first, while ordinary Python multiple dispatch covers objects and behavior that do not match it.

The motivation is to avoid repeatedly entering a Python handler for common DTensor operations. The gain depends on the model, operator granularity, placements, and communication pattern; the PR does not establish a workload-independent microsecond cost or step-time percentage.

The C++ fast path has the following recognition and fallback relationship:

  1. In v2.12.0, DTensor recognition and dispatch live in the Python-argument multiple-dispatch path in torch/csrc/utils/python_arg_parser.cpp, not in PythonFallbackKernel.
  2. Plain DTensor, or a subclass that inherits the base __torch_dispatch__, can enter dispatchDTensorOp. Objects that do not meet those checks continue through ordinary Python multiple dispatch.

The base DTensor.__torch_dispatch__ still exists. A subclass can delegate to the base implementation and re-enter the C++ fast path, so it is inaccurate to describe the Python method as a fallback only for complex operators. See torch/distributed/tensor/_api.py.

class DTensor(torch.Tensor):
    _op_dispatcher: op_dispatch.OpDispatcher = op_dispatch.OpDispatcher()

    @classmethod
    def __torch_dispatch__(cls, func, types, args=(), kwargs=None):
        # Illustration: a subclass may delegate to base DTensor semantics.
        # python_arg_parser.cpp decides whether the fast path applies.
        def unwrap(t):
            if isinstance(t, DTensor) and type(t) is not DTensor:
                return DTensor(t._local_tensor, t._spec, requires_grad=t.requires_grad)
            return t
        args = torch.utils._pytree.tree_map(unwrap, args)
        kwargs = torch.utils._pytree.tree_map(unwrap, kwargs or {})
        return func(*args, **kwargs)

This optimization targets the common Python multiple-dispatch path for base DTensor. It does not generalize every __torch_dispatch__ handler into a C++ implementation. Fast-path coverage, subclass participation, and complex behavior remain version-specific.

6.3 The role of PreDispatch in the PT2 pipeline

PreDispatch sits above autograd. Compiler and export paths that request pre_dispatch=True can capture higher-level ATen operators before later autograd wrappers or decompositions, retaining an operator such as relu instead of immediately observing its lower-level composition. This choice shapes the graph presented to later stages:

  • Optimization input: later passes can match patterns while the higher-level operator is still present.
  • Graph readability: diagnostic graphs remain closer to the program structure at the capture boundary.
  • Export boundary: export configuration and the target operator set can continue to control decomposition timing.
PreDispatch gives the compiler stack an interception point above autograd, allowing proxy modes to retain higher-level ATen operator forms. Capture at the regular Python key instead observes the operator sequence after the existing wrapper and decomposition layers.

7. Cost model and implementation boundaries

The suitability of cross-language dispatch depends on the amount of Python-boundary work per call and whether later execution can amortize that work. This section first separates the cost sources, then defines the tasks and implementation constraints for which the protocol is appropriate.

7.1 Sources of cross-language dispatch cost

ConcretePyInterpreterVTable::dispatch pays for the cross-language path itself: the thread acquires the GIL, the dispatcher resolves the Python operator, scans mode and subclass candidates, converts arguments between IValue and Python objects, executes the handler, and converts the result back according to the schema. The cost varies with argument count, wrapper reuse, handler behavior, and GIL contention.

StageSource of costMain variables
Enter the Python runtimeGIL acquisition and Python frame setupThread contention, interpreter state

Convert arguments and resultsIValue/PyObject conversion and schema checksSchema complexity, containers, wrapper reuse
Execute the handlerPython code and nested operator callsHandler logic, redispatch count

This article gives no fixed nanosecond or microsecond estimate because public source establishes the control flow, not a constant that remains valid across hardware, Python builds, and workloads. Performance-sensitive paths should be measured per operator in the target environment. The DTensor C++ fast path demonstrates one concrete optimization direction: reduce repeated Python multiple dispatch for common operators.

7.3 Implementation constraints

Constraint 1: references among TensorImpl, PyObject, and mode state

pyobj_slot_ associates a PyObject* with TensorImpl, while the Python wrapper holds an intrusive_ptr<TensorImpl>. Storing a tensor on the mode itself can extend this reference chain for the lifetime of the mode. Long-lived modes should keep non-owning references through weakref or clear their caches explicitly in __exit__.

Constraint 2: LIFO order for nested modes

The current mode is temporarily removed while its handler runs. Calling func(*args, **kwargs) re-enters dispatch, so the next mode or a tensor subclass can still process the operator. Returning a result constructed by the handler ends that chain. super().__torch_dispatch__ follows Python inheritance and is not a substitute for mode-stack dispatch.

Constraint 3: coverage of _DISPATCH_HANDLE_DIRECTLY

Some FakeTensor queries, including size, stride, device, and dim, can be handled through _DISPATCH_HANDLE_DIRECTLY and in_kernel_invocation_manager outside the general handler path. Modes that require a complete operator log must account for the direct-handling set in fake_tensor.py. When the intended boundary is the user-facing API, __torch_function__ can be composed with the mode explicitly.

Constraint 4: the tls_on_entry invariant

The comment around lines 17-23 of PythonFallbackKernel.cpp:

// This TLS is used to track the state of the dispatcher to be able to restore
// it when calling back into python.  It has the following invariant:
//  - It must be empty while python code is executed.
//  - It should only be set once even for multiple dispatcher calls that do not come back to python.
thread_local std::optional<c10::impl::LocalDispatchKeySet> tls_on_entry;

A mode handler continues dispatch through func(*args, **kwargs), allowing the framework to maintain this TLS invariant. Calling op.redispatchBoxed(...) directly can instead trigger the "Accessing torch dispatch state outside of __torch_dispatch__ is not allowed" error.

Constraint 5: vtable disarm during Python teardown

Python teardown disarms the vtable. A C++ cache that keeps a TensorImpl with a pyobj_slot in a static container must be released before the interpreter becomes unavailable; otherwise the "attempted to call dispatch on a Tensor with nontrivial PyObject after corresponding interpreter died" assertion can fire. Such caches can be cleared before atexit or by their owners through pyobj_slot.clear() during destruction.

Constraint 6: the FakeTensorMode infrastructure slot

infra_modes_ reserves a fixed slot for FakeTensorMode, and a second push is a no-op. A nested inner FakeTensorMode therefore does not replace the outer instance. Local real execution inside a fake environment uses FakeTensorMode.disable() to suspend the mode temporarily.
