GPU Occupancy 的驻留资源模型与性能含义

Thread block 是 CUDA kernel 进入 SM 的驻留单位。一个 resident block 在执行期间持续占用 warp 上下文、寄存器、shared memory、barrier 状态和 block slot；其中任何一项只能容纳较少 block 时，SM 可同时保留的 warp 就会减少，scheduler 用来覆盖指令与内存延迟的候选也随之缩小。Occupancy 描述这组 resident warp 相对于架构上限的比例，用于定位并发驻留受哪项资源限制。

0. Occupancy 与 warp residency

一个 warp 在执行上下文已经分配到 SM 且尚未结束时处于 resident 状态；Nsight Compute 在 occupancy 语境中把同一状态称为 active warp。CUDA 将 occupancy 定义为每个 SM 的 resident warps 与架构最大 resident warps 的比值：

\[ \mathrm{Occupancy} = \frac{W_{\mathrm{resident}}}{W_{\max}}. \]

Occupancy 只判断 warp slot 是否仍被占用，scheduler readiness 则描述 warp 在当前 issue 时刻能否前进。下表给出这些名称与 occupancy 的关系，随后用状态图表示它们之间的转换。

状态含义与 occupancy 的关系
Resident / Active执行上下文已经分配在 SM 上，warp 尚未完成计入 occupancy
Stalled下一条指令在等待数据、同步或 execution pipe仍然计入 occupancy
Eligible下一条指令及其目标 pipe 已经 ready是 scheduler 的候选项
Not SelectedWarp 已经 eligible，但 scheduler 本周期选择了另一个 warp仍然计入 occupancy
Selected / IssuedScheduler 在当前 issue 时刻选中该 warp，并发射一条或多条指令反映发射，不改变 occupancy 定义
Warp slot 生命周期与 scheduler 状态

在一个 scheduler cycle 上，可以把这些集合关系写成：

\[ W_{\mathrm{active}} = W_{\mathrm{stalled}} + W_{\mathrm{eligible}}, \qquad W_{\mathrm{eligible}} = W_{\mathrm{selected}} + W_{\mathrm{not\ selected}}. \]

Selected 是当前 issue 点的调度事件，residency 则可以持续多个周期；指令发射后，scheduler 会对该 warp 的下一条指令重新判断 stalled 或 eligible。Nsight Compute Scheduler Statistics 沿用 active、eligible、issued 这三个层次，而 CUDA Programming Guide 用 active warps 除以 SM 的最大 active warps。由此，高 occupancy 只说明 SM 保留了较多 warp；其中 stalled warp 仍占用寄存器和 warp slot。Resident warp 内部的依赖状态见《GPU Scoreboard 机制：Warp 依赖跟踪、SASS 控制与 Long/Short Stall》。

1. Occupancy 计算模型

明确 occupancy 统计哪些 warp 之后，还要计算一个 SM 能接纳多少个完整 block。设每个 block 有 $T$ 个线程，warp size 为 32，则每个 block 分配的 warp 数为：

\[ W_{\mathrm{block}} = \left\lceil\frac{T}{32}\right\rceil. \]

每项 SM 资源都能给出一个 resident block 上限：

\[ B_{\mathrm{warps}} = \left\lfloor \frac{W_{\max}}{W_{\mathrm{block}}} \right\rfloor, \qquad B_{\mathrm{registers}} = \left\lfloor \frac{R_{\mathrm{SM}}}{R_{\mathrm{block}}^{\mathrm{alloc}}} \right\rfloor, \]

\[ B_{\mathrm{smem}} = \left\lfloor \frac{S_{\mathrm{SM}}}{S_{\mathrm{block}}^{\mathrm{alloc}}} \right\rfloor. \]

这里，$W_{\max}$、$R_{\mathrm{SM}}$ 和 $S_{\mathrm{SM}}$ 分别表示每个 SM 的 warp、register 与 shared-memory 容量；$R_{\mathrm{block}}^{\mathrm{alloc}}$ 和 $S_{\mathrm{block}}^{\mathrm{alloc}}$ 是一个 block 经过分配粒度取整后的实际用量。把这些资源上限与架构 block slot、barrier 上限合并，得到：

\[ B_{\mathrm{resident}} = \min\left( B_{\mathrm{warps}}, B_{\mathrm{registers}}, B_{\mathrm{smem}}, B_{\mathrm{blocks}}, B_{\mathrm{barriers}} \right). \]

理论 resident warp 数和 theoretical occupancy 分别为：

\[ W_{\mathrm{resident}} = B_{\mathrm{resident}}W_{\mathrm{block}}, \qquad \mathrm{Occupancy}_{\mathrm{theoretical}} = \frac{W_{\mathrm{resident}}}{W_{\max}}. \]

寄存器和 shared memory 都有分配粒度。$R_{\mathrm{block}}^{\mathrm{alloc}}$ 与 $S_{\mathrm{block}}^{\mathrm{alloc}}$ 表示向硬件粒度取整后的实际分配量。临界点附近应使用 CUDA Occupancy Calculator 或 NCU，把这些取整规则纳入计算。

上述最小值模型适用于普通 CTA。Thread Block Cluster 还引入 cluster size 和 GPC placement 约束，因此 cluster kernel 应使用 cudaOccupancyMaxActiveClusters() 计算可同时运行的 cluster 数，再把这层 placement 约束纳入分析。

2. H100 的 warp residency 上限

把上一节的通用模型落到具体设备，需要先代入架构容量。H100 属于 compute capability 9.0；CUDA 13.1.1 Hopper Tuning Guide 给出的上限是每个 SM 64 个 concurrent warp。Warp size 为 32，因此同一容量也可以写成 2048 resident threads，模型中的 $W_{\max}$ 取 64。

64 warps/SM 是 occupancy 计算使用的公开 residency 常量。每个 kernel 实际能够常驻多少 warp，仍由 block size、寄存器、shared memory、barrier 和 block slot 共同决定。这套驻留计算只需要每 SM 的容量；Nsight Compute 查询到的 scheduler 数与每 scheduler 最大 warp 数属于目标设备属性，用于进一步分析 scheduler 级的 readiness，而非替代 compute capability 的驻留规格。

3. H100 上的资源限制算例

考虑一个 H100 kernel：

threads_per_block       = 256
warps_per_block         = 8
registers_per_thread    = 96
shared_memory_per_block = 48 KiB

设该 kernel 的 barrier 上限高于表中的四项限制，并先按表内整数容量计算：

Registers65536$96\times256=24576$$\lfloor65536/24576\rfloor=2$

寄存器给出的上限最小，所以一个 SM 最多常驻两个 block：

\[ B_{\mathrm{resident}}=2, \qquad W_{\mathrm{resident}}=2\times8=16, \qquad \mathrm{Occupancy}=\frac{16}{64}=25\%. \]

这个结果也给出了达到满 warp residency 所需的资源预算。同样是 256-thread block，64 个 resident warp 对应 8 个并发 block，因此寄存器需要控制在约 32 registers/thread 以内，shared memory 需要控制在约 $228/8=28.5$ KiB/block 以内。分配粒度和系统保留空间可能进一步收紧边界。

每 block 的资源用量是一类限制，完整 block 的准入粒度是另一类限制。若每个 block 只有 32 个线程，warp 容量本可容纳 64 个 block，但 H100 只有 32 个 block slot，最终只能常驻 32 个 warp，理论 occupancy 最高为 50%。

Block size 与整数装箱效应

SM 以完整 block 为单位分配驻留资源，这形成了 block size 的整数装箱效应。剩余容量即使还能容纳若干 warp，也无法拆开下一个 block 填入。随着 block size 增加，resident block 数按整数台阶下降，而每个 block 占用的 warp 数同时上升，两者共同形成锯齿状的 theoretical occupancy 曲线。

仅考虑 warp slot 和 block slot 时：

\[ B_{\mathrm{resident}}^{\mathrm{warp}} = \min\left( B_{\max}, \left\lfloor \frac{W_{\max}}{W_{\mathrm{block}}} \right\rfloor \right), \qquad W_{\mathrm{block}} = \left\lceil\frac{T}{32}\right\rceil. \]

H100 的 $W_{\max}=64$、$B_{\max}=32$。假设寄存器、shared memory 和 barrier 都不构成限制，不同 block size 的装箱结果如下：

以 352-thread block 为例，每个 block 占 11 个 warp。一个 SM 可以放入 5 个完整 block，共 55 个 resident warp。余下 9 个 warp slot 小于一个 block 所需的 11 个 slot，只能闲置：

\[ \left\lfloor\frac{64}{11}\right\rfloor=5, \qquad \mathrm{Occupancy} = \frac{5\times11}{64} = 85.9\%. \]

Block 增大到 384 threads 后，每个 SM 仍可放入 5 个 block，resident warp 数升至 60。增大到 416 threads 时，单个 block 需要 13 个 warp，resident block 数从 5 降到 4，occupancy 随之落到 81.3%。同一 resident block 台阶内，block 变大通常会填入更多 warp；跨过装箱边界时，少放一个 block 会造成突降。

这条曲线的转折点并不等间距，所以它不是严格的周期函数。寄存器和 shared memory 的分配粒度还会加入新的台阶：每个 block 的资源用量先向硬件粒度取整，再参与整数除法。NCU 中看到的 theoretical occupancy 是这些限制共同作用的结果。Achieved occupancy 若出现更明显的波动，还应检查 grid wave 和 tail effect。

H100 的 64 warps/SM、32 blocks/SM 以及其他 occupancy 资源上限见 NVIDIA Hopper Tuning Guide。

5. 理论 occupancy 与实测 occupancy

Launch limiter 给出 kernel 在静态资源条件下的理论驻留上限；运行过程中，grid 规模、block 完成时刻和负载分布还会改变每个周期实际驻留的 warp 数。Achieved Active Warps Per SM 来自硬件对 resident warp 的动态计数，对应底层 metric：

sm__warps_active.avg.per_cycle_active

设第 $i$ 个 SM 在第 $c$ 个 active cycle 上有 $W_{i,c}$ 个 active warp。忽略 profiler 在实例聚合上的实现细节时，这个指标可以按下面的平均模型理解：

\[ \overline{W}_{\mathrm{active}} = \operatorname{avg}_{i\in\mathrm{SM}} \left( \frac{1}{C_i} \sum_{c=1}^{C_i} W_{i,c} \right). \]

NCU 显示的 Achieved Occupancy 再用架构最大 resident warps/SM 对它做归一化：

\[ \mathrm{Achieved\ Occupancy} = \frac{ \mathrm{Achieved\ Active\ Warps\ Per\ SM} }{W_{\max}} \times100\%. \]

Achieved Active Warps Per SM
    = sm__warps_active.avg.per_cycle_active

Achieved Occupancy
    = sm__warps_active.avg.pct_of_peak_sustained_active

例如 H100 的 $W_{\max}=64$。假设 80% 的 active cycles 有 64 个 active warp，剩余 20% 只有 16 个：

\[ \overline{W}_{\mathrm{active}} =0.8\times64+0.2\times16 =54.4, \qquad \mathrm{Achieved\ Occupancy} =\frac{54.4}{64} =85\%. \]

per_cycle_active 的分母是 SM active cycles，不是整个 GPU 的 wall-clock elapsed cycles。若需要判断 grid 是否覆盖了全部 SM，还要结合 sm__cycles_active.avg.pct_of_peak_sustained_elapsed。一个 stalled warp 仍属于 active warp，因此 Achieved Occupancy 不衡量 eligible warp 数量，也不衡量 issue efficiency。

因此，Theoretical Occupancy 描述准入上限，Achieved Occupancy 描述 active cycles 上的实际平均值。两者之间的差距通常来自：

  • Grid 规模不足，不能为每个 SM 提供足够的 block
  • 尾波中的 block 数不足，即 tail effect
  • 不同 block 或 warp 的执行时间不均衡
  • 分支导致部分 warp 提前完成
  • Thread Block Cluster 的 placement 约束
  • 并发 kernel、MPS 或资源分区改变了可用 SM 资源

调优时先看理论值及其 limiter。理论 occupancy 很低，说明 block size、寄存器或 shared memory 需要调整；理论值高而 achieved occupancy 明显偏低，应检查 grid wave、负载均衡和 kernel 尾部。

Occupancy 提供的是延迟隐藏空间。若 scheduler 已经持续找到 eligible warp，execution pipe 或内存带宽也已接近饱和，继续增加 occupancy 不会带来吞吐收益。为了提高 occupancy 强行限制寄存器，还可能产生 local-memory spilling。此时需要结合 Scheduler Statistics、Warp State Statistics 和 Compute/Memory Throughput 判断。

关于 stalled warp 的分类、PC sampling 的统计口径，以及如何从 NCU 的 Details 页追到 Source/SASS，见 GPU Warp Stall 分析：调度状态、Nsight Compute 指标与源码归因。

int max_warps_per_sm =
    prop.maxThreadsPerMultiProcessor / prop.warpSize;

nvidia-smi --query-gpu=name,compute_cap --format=csv

GPU Occupancy: Residency Resource Model and Performance Interpretation

A thread block is the unit of CUDA-kernel residency admitted to an SM. A resident block holds warp contexts, registers, shared memory, barrier state, and a block slot throughout its execution. Whichever resource admits the fewest blocks determines how many warps the SM can retain and how many scheduling alternatives are available for covering instruction and memory latency. Occupancy is the ratio of those resident warps to the architectural maximum and identifies which resource constrains concurrent residency.

0. Occupancy and warp residency

A warp is resident after its execution context has been allocated on an SM and until the warp finishes. Nsight Compute uses active warp for the same state in its occupancy metrics. CUDA defines occupancy as the ratio of resident warps on an SM to the architecture's maximum resident warps:

\[ \mathrm{Occupancy} = \frac{W_{\mathrm{resident}}}{W_{\max}}. \]

Occupancy asks whether a warp slot remains allocated, while scheduler readiness describes whether the warp can advance at the current issue point. The table relates these names to occupancy; the state diagram then shows their transitions.

StateMeaningRelationship to occupancy
Resident / ActiveAn execution context is allocated on the SM and the warp has not completedCounts toward occupancy
StalledThe next instruction is waiting for data, synchronization, or an execution pipeStill counts toward occupancy
EligibleThe next instruction and its target pipe are readyA scheduling candidate
Not SelectedThe warp is eligible, but the scheduler chose another warp this cycleStill counts toward occupancy
Selected / IssuedThe scheduler selects this warp at the current issue point and issues one or more instructionsDescribes issue activity; it does not change the occupancy definition
Warp-slot lifetime and scheduler states

For one scheduler cycle, the set relationships are:

\[ W_{\mathrm{active}} = W_{\mathrm{stalled}} + W_{\mathrm{eligible}}, \qquad W_{\mathrm{eligible}} = W_{\mathrm{selected}} + W_{\mathrm{not\ selected}}. \]

Selected is a scheduling event at the current issue point, whereas residency can persist for many cycles. After an instruction issues, the scheduler classifies the warp again from its next instruction. Nsight Compute Scheduler Statistics uses the active, eligible, and issued levels, while the CUDA Programming Guide divides active warps by the maximum active warps per SM. High occupancy therefore means that the SM retains many warps, including stalled warps that still hold registers and a warp slot. For dependency state within resident warps, see GPU Scoreboard Mechanism: Warp Dependency Tracking, SASS Control, and Long/Short Stalls.

1. Occupancy calculation model

Once the counting population is clear, the next step is to determine how many complete blocks an SM can admit. Let a block contain $T$ threads and let the warp size be 32. The number of warps allocated to one block is:

\[ W_{\mathrm{block}} = \left\lceil\frac{T}{32}\right\rceil. \]

Each SM resource gives a separate upper bound on resident blocks:

\[ B_{\mathrm{warps}} = \left\lfloor \frac{W_{\max}}{W_{\mathrm{block}}} \right\rfloor, \qquad B_{\mathrm{registers}} = \left\lfloor \frac{R_{\mathrm{SM}}}{R_{\mathrm{block}}^{\mathrm{alloc}}} \right\rfloor, \]

\[ B_{\mathrm{smem}} = \left\lfloor \frac{S_{\mathrm{SM}}}{S_{\mathrm{block}}^{\mathrm{alloc}}} \right\rfloor. \]

Here, $W_{\max}$, $R_{\mathrm{SM}}$, and $S_{\mathrm{SM}}$ denote the SM capacities for warps, registers, and shared memory. $R_{\mathrm{block}}^{\mathrm{alloc}}$ and $S_{\mathrm{block}}^{\mathrm{alloc}}$ are the per-block amounts after allocation-granularity rounding. Combining these bounds with the architectural block-slot and barrier limits gives:

\[ B_{\mathrm{resident}} = \min\left( B_{\mathrm{warps}}, B_{\mathrm{registers}}, B_{\mathrm{smem}}, B_{\mathrm{blocks}}, B_{\mathrm{barriers}} \right). \]

The theoretical resident-warp count and occupancy are:

\[ W_{\mathrm{resident}} = B_{\mathrm{resident}}W_{\mathrm{block}}, \qquad \mathrm{Occupancy}_{\mathrm{theoretical}} = \frac{W_{\mathrm{resident}}}{W_{\max}}. \]

Registers and shared memory have allocation granularities. $R_{\mathrm{block}}^{\mathrm{alloc}}$ and $S_{\mathrm{block}}^{\mathrm{alloc}}$ denote the amounts rounded to the actual hardware allocation units. Near a boundary, use the CUDA Occupancy Calculator or Nsight Compute so that these rounding rules are included.

This minimum-resource model applies to ordinary CTAs. Thread Block Clusters add cluster-size and GPC-placement constraints, so cluster kernels should use cudaOccupancyMaxActiveClusters() to calculate concurrent clusters and include that placement level in the analysis.

2. H100 warp residency

Applying the general model to a device begins with its architectural capacities. H100 has compute capability 9.0, and the CUDA 13.1.1 Hopper Tuning Guide gives a limit of 64 concurrent warps per SM. With a warp size of 32, the same capacity is 2,048 resident threads, so the model uses $W_{\max}=64$.

The value 64 warps/SM is the public residency constant used in occupancy calculations. The resident-warp count of a particular kernel is still determined jointly by block size, registers, shared memory, barriers, and block slots. This residency calculation needs per-SM capacities. Scheduler count and maximum warps per scheduler, available as Nsight Compute device attributes, support a later scheduler-level readiness analysis rather than replacing the compute-capability residency specification.

3. H100 resource-limit example

Consider the following H100 kernel:

threads_per_block       = 256
warps_per_block         = 8
registers_per_thread    = 96
shared_memory_per_block = 48 KiB

Assume the barrier limit is looser than the four limits in the table, and first calculate with the listed integral capacities:

Registers produce the smallest limit, so at most two blocks can reside on an SM:

\[ B_{\mathrm{resident}}=2, \qquad W_{\mathrm{resident}}=2\times8=16, \qquad \mathrm{Occupancy}=\frac{16}{64}=25\%. \]

The result also gives the resource budget required for full warp residency. With the same 256-thread block size, 64 resident warps require eight concurrent blocks. Register usage must therefore stay near or below 32 registers per thread, and shared-memory usage near or below $228/8=28.5$ KiB per block. Allocation granularity and system reservations can tighten these boundaries.

Per-block resource usage is one constraint; admission in complete-block units is another. A 32-thread block occupies one warp, so warp capacity alone would permit 64 blocks. H100 has only 32 block slots, which caps residency at 32 warps and theoretical occupancy at 50%.

Block size and integer packing

An SM allocates residency resources to complete blocks, creating an integer-packing effect as block size changes. Remaining capacity may hold several warps yet still be too small for the next complete block. As block size rises, resident-block count falls in integer steps while warps per block increase, and the two effects produce a sawtooth theoretical-occupancy curve.

Considering only warp slots and block slots:

\[ B_{\mathrm{resident}}^{\mathrm{warp}} = \min\left( B_{\max}, \left\lfloor \frac{W_{\max}}{W_{\mathrm{block}}} \right\rfloor \right), \qquad W_{\mathrm{block}} = \left\lceil\frac{T}{32}\right\rceil. \]

A 352-thread block occupies 11 warps. An SM can admit five complete blocks, for 55 resident warps. Nine warp slots remain, fewer than the 11 required by another block, so they stay unused:

\[ \left\lfloor\frac{64}{11}\right\rfloor=5, \qquad \mathrm{Occupancy} = \frac{5\times11}{64} = 85.9\%. \]

At 384 threads, five blocks still fit and residency rises to 60 warps. At 416 threads, each block needs 13 warps, so the resident-block count falls from five to four and occupancy drops to 81.3%. Within one resident-block step, a larger block often fills more warp slots. Crossing a packing boundary removes a whole block and causes a sudden drop.

The transition points are not equally spaced, so the curve is not strictly periodic. Register and shared-memory allocation granularities add further steps: per-block usage is rounded to hardware units before the integer division. Theoretical occupancy in Nsight Compute combines all of these limits. If achieved occupancy varies more sharply, also inspect grid waves and the tail effect.

H100's limits of 64 warps per SM, 32 blocks per SM, and the other occupancy resources are documented in the NVIDIA Hopper Tuning Guide.

5. Theoretical and achieved occupancy

Launch limiters establish the residency ceiling implied by static resources. During execution, grid size, block completion times, and load distribution change the number of warps actually resident in each cycle. Achieved Active Warps Per SM comes from a hardware count of those resident warps and corresponds to:

sm__warps_active.avg.per_cycle_active

Let SM $i$ have $W_{i,c}$ active warps in active cycle $c$. Ignoring profiler implementation details for aggregation across instances, the metric can be understood through the following average:

\[ \overline{W}_{\mathrm{active}} = \operatorname{avg}_{i\in\mathrm{SM}} \left( \frac{1}{C_i} \sum_{c=1}^{C_i} W_{i,c} \right). \]

Nsight Compute normalizes this value by the architecture's maximum resident warps per SM to display Achieved Occupancy:

\[ \mathrm{Achieved\ Occupancy} = \frac{ \mathrm{Achieved\ Active\ Warps\ Per\ SM} }{W_{\max}} \times100\%. \]

Achieved Active Warps Per SM
    = sm__warps_active.avg.per_cycle_active

Achieved Occupancy
    = sm__warps_active.avg.pct_of_peak_sustained_active

For example, $W_{\max}=64$ on H100. If 80% of active cycles have 64 active warps and the remaining 20% have 16:

\[ \overline{W}_{\mathrm{active}} =0.8\times64+0.2\times16 =54.4, \qquad \mathrm{Achieved\ Occupancy} =\frac{54.4}{64} =85\%. \]

The denominator of per_cycle_active is SM active cycles, not wall-clock elapsed cycles for the entire GPU. To determine whether the grid covers all SMs, also inspect sm__cycles_active.avg.pct_of_peak_sustained_elapsed. A stalled warp remains active, so Achieved Occupancy measures neither eligible warps nor issue efficiency.

Theoretical Occupancy therefore describes the admission ceiling, while Achieved Occupancy is an average over active cycles. Their difference commonly comes from:

  • A grid too small to supply enough blocks to every SM
  • Too few blocks in the final wave, known as the tail effect
  • Uneven execution times across blocks or warps
  • Branches that let some warps finish early
  • Thread Block Cluster placement constraints
  • Concurrent kernels, MPS, or resource partitioning that changes the available SM resources

Start tuning with the theoretical value and its limiter. Low theoretical occupancy points to block size, register use, shared memory, or another static resource. When the theoretical value is high but achieved occupancy is substantially lower, inspect grid waves, load balance, and the kernel tail.

Occupancy supplies opportunities to hide latency. Once schedulers consistently find eligible warps and the relevant execution pipe or memory bandwidth is saturated, higher occupancy may not improve throughput. Restricting registers solely to increase occupancy can also cause local-memory spills. Scheduler Statistics, Warp State Statistics, and Compute/Memory Throughput are needed to distinguish these cases.

For stall categories, PC-sampling semantics, and the path from the Nsight Compute Details page to Source and SASS, see GPU Warp Stall Analysis: Scheduler States, Nsight Compute Metrics, and Source Attribution.

7. Querying hardware and kernel limits

The specification table provides a static baseline. For analysis on a particular machine, record the target device attributes directly. The CUDA Runtime can report threads per SM and warp size:

cudaDeviceProp prop;
cudaGetDeviceProperties(&prop, device);

int max_warps_per_sm =
    prop.maxThreadsPerMultiProcessor / prop.warpSize;

The GPU model and compute capability can be queried directly:

nvidia-smi --query-gpu=name,compute_cap --format=csv

Nsight Compute exposes scheduler and warp-residency attributes:

device__attribute_num_schedulers_per_multiprocessor
device__attribute_max_warps_per_scheduler
device__attribute_max_warps_per_multiprocessor
device__attribute_limits_max_cta_per_sm

These attributes describe the profiled device rather than kernel runtime activity. The kernel's register and shared-memory usage appears in Launch Statistics and the Occupancy section, and can also be obtained at compile time with nvcc --resource-usage.
