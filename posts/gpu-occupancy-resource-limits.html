GPU Occupancy 的计算模型、资源约束与 Nsight Compute 指标

Occupancy 描述一个 SM 同时保留了多少个 warp 执行上下文。它由 block size、寄存器、shared memory、barrier 和硬件 block slot 共同决定。这个指标衡量的是可用于隐藏延迟的 warp 数量，并不直接表示计算单元利用率。

0. Occupancy 测量什么

CUDA 把 occupancy 定义为每个 SM 的 active warps 与架构最大 active warps 的比值：

\[ \mathrm{Occupancy} = \frac{W_{\mathrm{resident}}}{W_{\max}}. \]

NCU 在 occupancy 语境里使用 active warp，它与 resident warp 指向同一类状态：warp 已经占用 SM 上的执行上下文，并且尚未结束。后续调度还要经过 eligible 和 issued 两个状态。

状态含义与 occupancy 的关系
Resident / Active执行上下文已经分配在 SM 上，warp 尚未完成计入 occupancy
Stalled下一条指令在等待数据、同步或执行管线仍然计入 occupancy
Eligible下一条指令及其目标管线已经 ready是 scheduler 的候选项
Issuedscheduler 在当前 issue 时刻选中了该 warp反映发射，不改变 occupancy 定义

CUDA Programming Guide 给出的 occupancy 定义也是 active warps 与 SM 最大 active warps 的比例。一个 stalled warp 仍会占用寄存器和 warp slot，所以高 occupancy 可能同时伴随大量停顿。

1. H100 的 64 个 resident warp slot

H100 属于 compute capability 9.0。一个 H100 SM 有 4 个 warp scheduler，warp 会静态分配给其中一个 scheduler。该架构允许每个 SM 最多常驻 64 个 warp，平均分到每个 scheduler 的 residency 上限为 16 个 warp：

\[ 4\ \text{schedulers/SM} \times 16\ \text{warps/scheduler} = 64\ \text{warps/SM}. \]

Warp size 为 32，所以同一个限制也可以写成 2048 resident threads：

\[ 64\ \text{warps} \times 32\ \text{threads/warp} = 2048\ \text{threads}. \]

H100 SM 的 warp residency 与 scheduler 分区

64 是 warp execution context 的架构容量。每个 resident warp 需要程序计数器、active mask、scoreboard、同步状态和调度元数据，还要占用线程寄存器。第 65 个 warp 即使不使用 shared memory，也没有可分配的 warp slot。

CUDA Programming Guide 的 CC 9.0 章节列出 H100 SM 的 4 个 warp scheduler，并说明 scheduler 会从分配给自己的 ready warp 中发射指令。64 个 resident warp 只提供候选上下文，单周期 issue 能力由 scheduler 和目标执行管线决定。

公开规格定义了架构上限，但没有披露完整的电路预算。64 个 slot 已经与寄存器容量形成明确约束：H100 有 65536 个 32-bit registers；64 个 warp 全部常驻时共有 2048 个线程，平均每个线程最多分到 32 个寄存器。保持 register file 和 issue width 不变而增加 warp slot，常见 kernel 很难填满新增容量，scoreboard 和调度状态的成本却会继续上升。

2. Occupancy 计算模型

设每个 block 有 $T$ 个线程，warp size 为 32。一个 block 占用的 warp 数为：

\[ W_{\mathrm{block}} = \left\lceil\frac{T}{32}\right\rceil. \]

每项 SM 资源都能给出一个 resident block 上限：

\[ B_{\mathrm{warps}} = \left\lfloor \frac{W_{\max}}{W_{\mathrm{block}}} \right\rfloor, \qquad B_{\mathrm{registers}} = \left\lfloor \frac{R_{\mathrm{SM}}}{R_{\mathrm{block}}^{\mathrm{alloc}}} \right\rfloor, \]

\[ B_{\mathrm{smem}} = \left\lfloor \frac{S_{\mathrm{SM}}}{S_{\mathrm{block}}^{\mathrm{alloc}}} \right\rfloor. \]

再与架构 block slot 和 barrier 上限合并：

\[ B_{\mathrm{resident}} = \min\left( B_{\mathrm{warps}}, B_{\mathrm{registers}}, B_{\mathrm{smem}}, B_{\mathrm{blocks}}, B_{\mathrm{barriers}} \right). \]

理论常驻 warp 数和理论 occupancy 分别为：

\[ W_{\mathrm{resident}} = B_{\mathrm{resident}}W_{\mathrm{block}}, \qquad \mathrm{Occupancy}_{\mathrm{theoretical}} = \frac{W_{\mathrm{resident}}}{W_{\max}}. \]

寄存器和 shared memory 都有分配粒度。$R_{\mathrm{block}}^{\mathrm{alloc}}$ 与 $S_{\mathrm{block}}^{\mathrm{alloc}}$ 表示向硬件粒度取整后的实际分配量。临界点附近应使用 CUDA Occupancy Calculator 或 NCU，不能只算 registers/thread × threads/block。

Thread Block Cluster 还受到 cluster size 和 GPC placement 约束。Cluster kernel 应使用 cudaOccupancyMaxActiveClusters() 计算可同时运行的 cluster 数；普通的 per-SM 公式不足以描述这层调度。

3. H100 上的资源限制算例

考虑一个 H100 kernel：

threads_per_block       = 256
warps_per_block         = 8
registers_per_thread    = 96
shared_memory_per_block = 48 KiB

忽略不会成为瓶颈的 barrier，并且先按整数资源量计算：

资源H100 每 SM 容量每 block 用量允许的 resident blocks
Warp slots64 warps8 warps$\lfloor64/8\rfloor=8$
Block slots32 blocks1 block32
Registers65536$96\times256=24576$$\lfloor65536/24576\rfloor=2$
Shared memory228 KiB48 KiB$\lfloor228/48\rfloor=4$

寄存器给出的上限最小，所以一个 SM 最多常驻两个 block：

\[ B_{\mathrm{resident}}=2, \qquad W_{\mathrm{resident}}=2\times8=16, \qquad \mathrm{Occupancy}=\frac{16}{64}=25\%. \]

同样是 256-thread block，达到 64 个 resident warp 需要同时放入 8 个 block。寄存器必须控制在约 32 registers/thread 以内，shared memory 也要控制在约 $228/8=28.5$ KiB/block 以内。分配粒度和系统保留空间可能进一步收紧边界。

很小的 block 也会损失 occupancy。若每个 block 只有 32 个线程，warp 容量允许 64 个 block，但 H100 只有 32 个 block slot。最终只能常驻 32 个 warp，理论 occupancy 最高为 50%。

Block size 与整数装箱效应

Block size 与 theoretical occupancy 之间不是单调关系。SM 只能接纳完整的 block，剩余资源即使还能容纳若干 warp，也不能拆开下一个 block 填入。Block size 连续增加时，resident block 数按整数台阶下降，最终得到一条锯齿状曲线。

仅考虑 warp slot 和 block slot 时：

\[ B_{\mathrm{resident}}^{\mathrm{warp}} = \min\left( B_{\max}, \left\lfloor \frac{W_{\max}}{W_{\mathrm{block}}} \right\rfloor \right), \qquad W_{\mathrm{block}} = \left\lceil\frac{T}{32}\right\rceil. \]

H100 的 $W_{\max}=64$、$B_{\max}=32$。假设寄存器、shared memory 和 barrier 都不构成限制，不同 block size 的装箱结果如下：

以 352-thread block 为例，每个 block 占 11 个 warp。一个 SM 可以放入 5 个完整 block，共 55 个 resident warp。余下 9 个 warp slot 小于一个 block 所需的 11 个 slot，只能闲置：

\[ \left\lfloor\frac{64}{11}\right\rfloor=5, \qquad \mathrm{Occupancy} = \frac{5\times11}{64} = 85.9\%. \]

Block 增大到 384 threads 后，每个 SM 仍可放入 5 个 block，resident warp 数升至 60。增大到 416 threads 时，单个 block 需要 13 个 warp，resident block 数从 5 降到 4，occupancy 随之落到 81.3%。同一 resident block 台阶内，block 变大通常会填入更多 warp；跨过装箱边界时，少放一个 block 会造成突降。

这条曲线的转折点并不等间距，所以它不是严格的周期函数。寄存器和 shared memory 的分配粒度还会加入新的台阶：每个 block 的资源用量先向硬件粒度取整，再参与整数除法。NCU 中看到的 theoretical occupancy 是这些限制共同作用的结果。Achieved occupancy 若出现更明显的波动，还应检查 grid wave 和 tail effect。

H100 的 64 warps/SM、32 blocks/SM 以及其他 occupancy 资源上限见 NVIDIA Hopper Tuning Guide。

4. Nsight Compute 中的 occupancy limiter

NCU 的 launch__occupancy_limit_* 指标给出每项资源单独允许的 resident block 数。它们的单位都是 block。

MetricNCU UI 名称含义
launch__occupancy_limit_warpsBlock Limit Warps仅考虑 warp slot 和 block size 时允许的 block 数
launch__occupancy_limit_blocksBlock Limit SMSM 的架构 block slot 上限
launch__occupancy_limit_registersBlock Limit Registers寄存器分配允许的 block 数
launch__occupancy_limit_shared_memBlock Limit Shared Mem静态、动态及 driver shared memory 分配允许的 block 数
launch__occupancy_limit_barriersBlock Limit BarriersKernel 使用的 barrier 资源允许的 block 数

launch__occupancy_limit_warps 的名字容易造成误读。它返回 block 数：

\[ \texttt{launch\_\_occupancy\_limit\_warps} = \left\lfloor \frac{W_{\max}} {\left\lceil T/32\right\rceil} \right\rfloor. \]

H100 上的 256-thread block 占 8 个 warp，该 metric 的结果是 8 blocks，单位仍是 block。五个 limiter 的最小值决定理论 resident block 数。NCU 随后给出：

6. 理论 occupancy 与实测 occupancy

Theoretical Occupancy 由 launch configuration 和静态资源分配计算。Achieved Occupancy 是 kernel 执行期间实际 active warps 的时间平均值。两者的差距通常来自：

  • Grid 规模不足，不能为每个 SM 提供足够的 block
  • 尾波中的 block 数不足，即 tail effect
  • 不同 block 或 warp 的执行时间不均衡
  • 分支导致部分 warp 提前完成
  • Thread Block Cluster 的 placement 约束
  • 并发 kernel、MPS 或资源分区改变了可用 SM 资源

调优时先看理论值及其 limiter。理论 occupancy 很低，说明 block size、寄存器或 shared memory 需要调整；理论值高而 achieved occupancy 明显偏低，应检查 grid wave、负载均衡和 kernel 尾部。

Occupancy 提供的是延迟隐藏空间。若 scheduler 已经持续找到 eligible warp，执行管线或内存带宽也已接近饱和，继续增加 occupancy 不会带来吞吐收益。为了提高 occupancy 强行限制寄存器，还可能产生 local-memory spilling。此时需要结合 Scheduler Statistics、Warp State Statistics 和 Compute/Memory Throughput 判断。

7. 查询硬件与 kernel 上限

CUDA Runtime 可以查询 threads/SM 和 warp size：

cudaDeviceProp prop;
cudaGetDeviceProperties(&prop, device);

int max_warps_per_sm =
    prop.maxThreadsPerMultiProcessor / prop.warpSize;

设备型号和 compute capability 可以直接查询：

nvidia-smi --query-gpu=name,compute_cap --format=csv

NCU 暴露了 scheduler 和 warp residency 属性：

device__attribute_num_schedulers_per_multiprocessor
device__attribute_max_warps_per_scheduler
device__attribute_max_warps_per_multiprocessor
device__attribute_limits_max_cta_per_sm

这些属性来自 CUDA driver，不需要额外的 replay pass。Kernel 自身的寄存器和 shared memory 用量可以从 Launch Statistics 与 Occupancy section 查看，也可以在编译时使用 nvcc --resource-usage。
