GPU Occupancy 的驻留资源模型与性能含义

CUDA kernel 启动后，grid 中的 thread block 分批进入 SM。一个 SM 可以同时保留多个 block；当某个 warp 等待访存或前一条指令的结果时，scheduler 可以发射其他已就绪 warp 的指令。要增加这批可交替执行的 warp，SM 必须先为新的完整 block 分配资源。这里会遇到一个具体限制：shared memory 还有空余，warp 数也远未达到架构上限，寄存器却已经放不下下一个 block。Occupancy 的分析就从这次分配开始。

1. Occupancy 统计已经驻留的 warp

一个 warp 获得 SM 上的执行上下文后，在释放这些资源之前属于 resident warp。Nsight Compute 在 occupancy 指标中也称它为 active warp。设一个 SM 当前驻留了 $W_{\mathrm{resident}}$ 个 warp，架构允许的最大数量为 $W_{\max}$，则：

\[ \mathrm{Occupancy}=\frac{W_{\mathrm{resident}}}{W_{\max}}. \]

这个比例数的是占用中的 warp slot。等待数据的 warp 仍然驻留，也仍计入 occupancy；它能否发射下一条指令，需要 scheduler 另行判断。CUDA Programming Guide 的 occupancy 定义给出了这一统计范围。调优中需要先算清楚驻留上限，再检查这批 warp 能提供多少发射机会。

2. H100 上只能驻留两个 block 的算例

考虑一组用于手算的 kernel 资源配置：每个 block 有 256 个线程，每线程使用 96 个寄存器，每 block 使用 48 KiB shared memory。这里的寄存器数量指编译结果，shared memory 指程序申请的静态与动态用量之和。这组数值是教学设定，尚未对应某个 kernel 的性能测量。

threads_per_block             = 256
registers_per_thread          = 96
user_shared_memory_per_block  = 48 KiB

H100 的 compute capability 为 9.0。按 CUDA 13.1.1 Hopper Tuning Guide，每个 SM 最多驻留 64 个 warp、32 个 block，具有 65,536 个 32-bit 寄存器，shared-memory 容量最高为 228 KiB。以下采用 228 KiB 的 shared-memory carveout，分析普通 CTA，并假设 barrier 等其他资源不构成更紧的限制。

CUDA 还会为每个 block 保留 1 KiB shared memory，因此这个 block 在预算中占用 $48+1=49$ KiB。把每项资源单独拿出来计算，可以得到四个不同的 block 数量上限：

资源H100 每 SM 容量每 block 的预算允许的 blocks/SM
Warp slots64 warps$256/32=8$ warps$\lfloor64/8\rfloor=8$
Block slots32 blocks1 block32
Registers65,536 个 32-bit registers$96\times256=24{,}576$$\lfloor65{,}536/24{,}576\rfloor=2$
Shared memory228 KiB48 KiB 用户用量 + 1 KiB 保留量$\lfloor228/49\rfloor=4$

寄存器只允许两个 block 同时驻留。两个 block 合计占用 49,152 个寄存器，余下的 16,384 个不足以接纳第三个 block 所需的 24,576 个。Shared memory 此时只分配了 98 KiB，但它的空余无法补足寄存器的缺口。SM 因而驻留 16 个 warp，理论 occupancy 为 25%：

\[ B_{\mathrm{resident}}=2,\qquad W_{\mathrm{resident}}=2\times8=16,\qquad \mathrm{Occupancy}_{\mathrm{theoretical}}=\frac{16}{64}=25\%. \]

从资源预算归纳计算模型

SM 必须同时满足各项资源的分配条件。对于普通 CTA，把 warp、寄存器、shared memory、block slot 和 barrier 各自允许的 block 数记作 $B_{\mathrm{warps}}$、$B_{\mathrm{registers}}$、$B_{\mathrm{smem}}$、$B_{\mathrm{blocks}}$ 和 $B_{\mathrm{barriers}}$，可接纳的数量取其中最小值：

\[ B_{\mathrm{resident}}= \min\left( B_{\mathrm{warps}}, B_{\mathrm{registers}}, B_{\mathrm{smem}}, B_{\mathrm{blocks}}, B_{\mathrm{barriers}} \right). \]

若每 block 有 $T$ 个线程，warp size 为 32，则最后一个不满 32 个线程的 warp 也要占用一个 slot。因此：

\[ W_{\mathrm{block}}=\left\lceil\frac{T}{32}\right\rceil,\qquad B_{\mathrm{warps}}=\left\lfloor\frac{W_{\max}}{W_{\mathrm{block}}}\right\rfloor,\qquad \mathrm{Occupancy}_{\mathrm{theoretical}} =\frac{B_{\mathrm{resident}}W_{\mathrm{block}}}{W_{\max}}. \]

Shared memory 的预算可写为 $B_{\mathrm{smem}}=\lfloor S_{\mathrm{SM}}/S_{\mathrm{block}}^{\mathrm{alloc}}\rfloor$，其中 $S_{\mathrm{SM}}$ 是当前容量配置，$S_{\mathrm{block}}^{\mathrm{alloc}}$ 包含用户用量、driver 保留量和分配粒度取整。寄存器总量同样给出 $B_{\mathrm{registers}}\leq\lfloor R_{\mathrm{SM}}/R_{\mathrm{block}}^{\mathrm{alloc}}\rfloor$；其中 $R_{\mathrm{SM}}$ 是 SM 的寄存器总量，$R_{\mathrm{block}}^{\mathrm{alloc}}$ 是每 block 按粒度取整后的实际分配量。具体可驻留数量还受寄存器在 SM 内部的分配约束影响。

上面的 256-thread 算例用总量除法得到资源上限。推广到其他配置时，寄存器需要按目标架构的 warp 分配粒度取整，并满足 subpartition 的容量约束；不能把整个 SM 的寄存器当作可任意装填的空间。NCU 的硬件模型说明了这种分配关系，Occupancy Calculator则包含相应架构参数。临界配置应使用该工具或 CUDA Occupancy API 核算。

H100 的 228 KiB 是最大 shared-memory carveout，单 block 最多可供程序使用 227 KiB。静态分配仍限于 48 KiB，更大的动态分配需要显式 opt-in。容量配置与每 block 的 1 KiB 保留量见 Hopper shared-memory 说明。使用 Thread Block Cluster 的 kernel 还要满足 cluster placement 约束，应通过 cudaOccupancyMaxActiveClusters()计算并发 cluster 数。

3. 减少寄存器后，限制项如何变化

既然这组配置先耗尽寄存器预算，可以继续推算寄存器减少后的驻留情况。保持 256 threads/block 和 48 KiB 用户 shared memory 不变，把编译后的寄存器数量依次设为 96、64 和 32。这里改变的是资源参数；代码能否产生这些编译结果，以及改动会不会加快执行，仍需单独验证。

从 96 降到 64 registers/thread，四个 block 恰好用完 65,536 个寄存器，它们的 shared-memory 总预算为 196 KiB，也能放入当前容量。驻留数量因此从 16 个 warp 增加到 32 个。此时寄存器和 shared memory 都只允许四个 block，两项资源共同限制 occupancy。

继续降到 32 registers/thread，寄存器已经允许八个 block，shared memory 却仍然只够四个。第五个 block 需要把 shared-memory 总量推到 $5\times49=245$ KiB，超过 228 KiB。寄存器数量又减半，理论 occupancy 仍停在 50%。这时继续围绕寄存器寻找驻留收益，就选错了资源。

4. Block size 引起的整数装箱与突降

前面的三次计算保持 block size 不变。现在只改变 block size，并暂时放宽寄存器、shared memory 和 barrier 的限制，观察完整 block 的准入粒度会怎样影响驻留。这个简化条件把装箱效应单独分离出来，不能直接当作原来那个 48 KiB/block 配置的参数扫描结果。

对于 H100 的 64 个 warp slot 和 32 个 block slot，仅由这两项决定的驻留数量为：

\[ B_{\mathrm{resident}}^{\mathrm{warp}} =\min\left(32,\left\lfloor\frac{64}{W_{\mathrm{block}}}\right\rfloor\right), \qquad W_{\mathrm{block}}=\left\lceil\frac{T}{32}\right\rceil. \]

把 block size 设为 352 threads，每个 block 占 11 个 warp。SM 放入五个 block 后，还剩九个 slot，已经装不下第六个完整 block。理论 occupancy 为：

\[ \left\lfloor\frac{64}{11}\right\rfloor=5,\qquad W_{\mathrm{resident}}=5\times11=55,\qquad \mathrm{Occupancy}=\frac{55}{64}\approx85.9\%. \]

增加到 384 threads 后，每个 block 占 12 个 warp，仍可放入五个 block，驻留数升至 60，occupancy 达到 93.8%。再增加到 416 threads，每个 block 需要 13 个 warp，五个 block 需要 65 个 slot，只能退回四个 block。线程更多了，驻留数反而降到 52，occupancy 为 81.3%。

在同一个 resident-block 台阶内，增大 block 通常能填入更多 warp；跨过容量边界时，少放一个完整 block 会造成突降。把这个计算扩展到其他 block size，可以看到相同的整数装箱规律：

这些转折由整数除法决定，间隔并不固定。真实 kernel 中，寄存器和 shared memory 的用量及分配粒度还会形成自己的台阶。分析 NCU 的 block-size 曲线时，需要把装箱变化与 limiter 的变化放在一起读。

5. 理论上限与运行中的平均驻留

回到 64 registers/thread 的配置。资源预算允许每个 SM 驻留四个 block，也就是 32 个 warp，理论 occupancy 为 50%。执行期间是否一直驻留这么多 warp，还取决于 grid 能否持续提供 block，以及已经进入 SM 的工作何时结束。

只观察一个 SM，构造一个说明时间平均的教学场景：80% 的 active cycles 驻留 32 个 warp，余下 20% 的 active cycles 只剩八个。这里直接指定时间分布，不从 block 数量推断每段耗时。平均驻留数为 27.2 个 warp，对应 42.5% occupancy：

\[ \overline{W}_{\mathrm{active}} =0.8\times32+0.2\times8=27.2,\qquad \frac{\overline{W}_{\mathrm{active}}}{64}=42.5\%. \]

同样的资源配置可以得到不同的运行平均值。在一个 SM 上，若四个 block 中的三个先完成，又没有后续 block 补入，剩余一个 block 就会形成类似图中的低驻留区间。不同 warp 提前退出或不同 block 执行时间不均衡，也会改变这条时间曲线。

NCU 的 active-cycle 统计口径

NCU 的 Achieved Active Warps per SM 对应 sm__warps_active.avg.per_cycle_active，归一化后的 Achieved Occupancy 对应 sm__warps_active.avg.pct_of_peak_sustained_active。前者统计 SM active cycles 内的平均 active warp 数，后者按架构最大 resident warps/SM 表示为百分比。上面的单 SM 场景只用于解释时间加权，完整 GPU 的实例聚合交给 profiler 处理。

active 和 elapsed 的区别会影响小 grid 的判断。一个 SM 完全闲置的周期不属于它的 active cycles；仅凭 achieved occupancy，无法判断所有 SM 是否都充分参与执行。要检查 grid 对设备的覆盖，还需查看 sm__cycles_active.avg.pct_of_peak_sustained_elapsed 等活动周期指标。分母定义见 NCU Metrics Structure，上述 achieved 指标与静态理论值的区别见 NVIDIA 的说明。

Grid waves 与尾部工作

给定每 SM 的驻留 block 上限，把所有 SM 同时能够接纳的 block 看作一波工作的容量，有助于分析 grid 的供给。Grid 太小，可能既覆盖不了全部 SM，也填不满每个工作 SM 的驻留空间；最后一波剩余 block 不足，则会让部分 SM 提前结束。即便 block 数量足够，负载不均衡也可能让少量运行较久的 block 拖长 kernel 尾部，这就是分析 tail effect 时需要检查的时间分布。

因此，理论值低时应先确定静态 limiter；理论值较高而 achieved 明显偏低时，则应检查 grid 规模、launch__waves_per_multiprocessor、block 完成时间和负载分布。Cluster placement、并发 kernel、MPS 或资源分区还会改变工作的分布或可用资源，应根据实际运行环境纳入判断。

6. 把驻留分析落实到性能判断

到这里，资源算例已经回答了为何只能驻留两个 block，以及寄存器减少后为何在四个 block 处停止增长。还没有回答的是，这些变化会让 kernel 快多少。判断驻留数量是否值得增加，需要观察 scheduler 如何使用已经驻留的 warp。

Scheduler 从 active warp 中寻找下一条指令已就绪的 eligible warp，再从中选择 warp 发射指令。一个 eligible warp 若没有被本次选中，属于 not selected；指令发射后，scheduler 会重新判断它的下一条指令。NCU Scheduler Statistics用 active、eligible 和 issued 这些层次描述发射机会。Stalled warp 虽然占据驻留资源，却暂时不能提供这样的机会。

如果 scheduler 经常没有 eligible warp，更多独立工作可能帮助覆盖等待时间。若它已经能持续发射，而目标 execution pipe 或内存带宽接近饱和，增加 resident warp 的空间收益就会变小。寄存器较多的 kernel 也可能通过指令级并行隐藏延迟；为了提高 occupancy 强行压低寄存器上限，反而可能增加 spilling 和访存。CUDA Best Practices 的 block-size 讨论明确保留了这些取舍。

验证前面的资源调整时，可以围绕 96 与 64 registers/thread 的可实现版本展开。固定输入规模和计时方法，先确认计算结果一致，再核对实际寄存器用量、shared memory 和 theoretical occupancy，随后比较 kernel 时间以及 Scheduler Statistics 的 eligible/issued 状态。如果驻留从两个 block 增到四个，而运行时间没有改善，应检查新增的寄存器溢出、指令数量或其他执行瓶颈。继续降低到 32 registers/thread 已经没有理论驻留收益，更需要给出独立的性能理由。

不同结果对应不同的后续工作：资源上限已经够用时，可以沿着 Warp Stall 分析寻找发射受阻的位置；若观察到 MIO Throttle，则应继续检查具体指令和下游接收压力。在这些判断中，保留 kernel 时间作为最终评价，同时用 occupancy 解释资源预算怎样影响了可供调度的工作。

GPU Occupancy: Residency Resource Model and Performance Interpretation

After a CUDA kernel launches, its grid of thread blocks enters the SMs in batches. An SM can retain several blocks at once. When one warp waits for memory or a preceding instruction's result, the scheduler can issue instructions from other ready warps. Adding to this pool first requires enough resources for another complete block. That admission can fail while shared memory still has room and the warp count remains well below the architectural limit: the remaining registers cannot hold the next block. Occupancy analysis starts with this allocation decision.

1. Occupancy counts resident warps

A warp is resident after it obtains an execution context on an SM and until those resources are released. Nsight Compute also calls it an active warp in occupancy metrics. If an SM currently holds $W_{\mathrm{resident}}$ warps and the architecture permits at most $W_{\max}$, then:

\[ \mathrm{Occupancy}=\frac{W_{\mathrm{resident}}}{W_{\max}}. \]

This ratio counts allocated warp slots. A warp waiting for data is still resident and still contributes to occupancy. The scheduler separately determines whether it can issue its next instruction. The CUDA Programming Guide definition establishes this counting scope. Tuning requires both a residency calculation and an examination of the issue opportunities those resident warps provide.

2. An H100 example limited to two resident blocks

Consider a resource configuration for a worked calculation: 256 threads per block, 96 registers per thread, and 48 KiB of shared memory per block. The register count refers to the compiled kernel; shared memory is the sum of the program's static and dynamic allocation. These are teaching inputs, not measurements from a particular kernel.

threads_per_block             = 256
registers_per_thread          = 96
user_shared_memory_per_block  = 48 KiB

Registers65,536 32-bit registers$96\times256=24{,}576$$\lfloor65{,}536/24{,}576\rfloor=2$

Registers permit only two blocks. Together they consume 49,152 registers, leaving 16,384, fewer than the 24,576 required by a third block. Only 98 KiB of shared memory has been allocated, but that free capacity cannot make up the register shortfall. The SM therefore holds 16 warps, for 25% theoretical occupancy:

\[ B_{\mathrm{resident}}=2,\qquad W_{\mathrm{resident}}=2\times8=16,\qquad \mathrm{Occupancy}_{\mathrm{theoretical}}=\frac{16}{64}=25\%. \]

Generalizing the resource calculation

An SM must satisfy all resource requirements at once. For ordinary CTAs, let $B_{\mathrm{warps}}$, $B_{\mathrm{registers}}$, $B_{\mathrm{smem}}$, $B_{\mathrm{blocks}}$, and $B_{\mathrm{barriers}}$ be the block limits imposed by warp capacity, registers, shared memory, block slots, and barriers. The smallest determines residency:

\[ B_{\mathrm{resident}}= \min\left( B_{\mathrm{warps}}, B_{\mathrm{registers}}, B_{\mathrm{smem}}, B_{\mathrm{blocks}}, B_{\mathrm{barriers}} \right). \]

For $T$ threads per block and a warp size of 32, a partially populated final warp still occupies one slot. Hence:

\[ W_{\mathrm{block}}=\left\lceil\frac{T}{32}\right\rceil,\qquad B_{\mathrm{warps}}=\left\lfloor\frac{W_{\max}}{W_{\mathrm{block}}}\right\rfloor,\qquad \mathrm{Occupancy}_{\mathrm{theoretical}} =\frac{B_{\mathrm{resident}}W_{\mathrm{block}}}{W_{\max}}. \]

The shared-memory budget gives $B_{\mathrm{smem}}=\lfloor S_{\mathrm{SM}}/S_{\mathrm{block}}^{\mathrm{alloc}}\rfloor$, where $S_{\mathrm{SM}}$ is the configured capacity and $S_{\mathrm{block}}^{\mathrm{alloc}}$ includes user allocation, driver reservations, and allocation-granularity rounding. Total register capacity similarly provides the bound $B_{\mathrm{registers}}\leq\lfloor R_{\mathrm{SM}}/R_{\mathrm{block}}^{\mathrm{alloc}}\rfloor$, where $R_{\mathrm{SM}}$ is the SM register count and $R_{\mathrm{block}}^{\mathrm{alloc}}$ is the allocation for one block after rounding. Register distribution within the SM can further restrict the resident-block count.

The 256-thread example above uses total-capacity division to obtain its resource limits. For other configurations, register allocation must account for the target architecture's warp allocation granularity and subpartition capacities; the SM register file cannot be packed arbitrarily. The NCU hardware model describes that allocation structure, and the Occupancy Calculator includes the architecture parameters. Use it or the CUDA Occupancy API to check configurations near a boundary.

H100's 228 KiB is the maximum shared-memory carveout. A single block can address up to 227 KiB, while static allocations remain limited to 48 KiB and larger dynamic allocations require explicit opt-in. The Hopper shared-memory documentation specifies these capacities and the 1 KiB reservation per block. Thread Block Cluster kernels also have placement constraints; use cudaOccupancyMaxActiveClusters() to calculate concurrent clusters.

3. How the limiter changes as register use falls

Because registers limit the initial configuration, we can calculate what lower register counts would permit. Keep 256 threads per block and 48 KiB of user shared memory, and set the compiled register count to 96, 64, and 32 in turn. These changes vary the resource inputs. Whether code can produce each compiled configuration, and whether that code runs faster, requires separate verification.

Reducing the count from 96 to 64 registers per thread lets four blocks exactly fill the 65,536-register budget. Their total shared-memory allocation is 196 KiB, which also fits. Residency rises from 16 to 32 warps. Registers and shared memory now each permit only four blocks, so they jointly limit occupancy.

At 32 registers per thread, registers permit eight blocks but shared memory still permits four. A fifth block would require a total of $5\times49=245$ KiB, exceeding 228 KiB. The register count has halved again, yet theoretical occupancy stays at 50%. Further reducing registers cannot remove the remaining shared-memory limit.

4. Integer packing and block-size drops

The preceding calculations kept block size fixed. Now vary block size while assuming registers, shared memory, and barriers do not limit residency. This isolates the effect of admitting complete blocks. It is a different model from a parameter sweep of the original configuration with 48 KiB per block.

Considering only H100's 64 warp slots and 32 block slots gives:

\[ B_{\mathrm{resident}}^{\mathrm{warp}} =\min\left(32,\left\lfloor\frac{64}{W_{\mathrm{block}}}\right\rfloor\right), \qquad W_{\mathrm{block}}=\left\lceil\frac{T}{32}\right\rceil. \]

A 352-thread block occupies 11 warps. Five blocks leave nine slots, fewer than the next complete block requires. The resulting theoretical occupancy is:

\[ \left\lfloor\frac{64}{11}\right\rfloor=5,\qquad W_{\mathrm{resident}}=5\times11=55,\qquad \mathrm{Occupancy}=\frac{55}{64}\approx85.9\%. \]

At 384 threads, a block occupies 12 warps. Five blocks still fit, so residency rises to 60 warps and occupancy to 93.8%. At 416 threads, each block needs 13 warps. Five blocks would require 65 slots, forcing residency down to four blocks. The larger block size now gives only 52 resident warps, or 81.3% occupancy.

Within one resident-block step, increasing block size usually fills more warp slots. Crossing a capacity boundary removes a complete block and causes a sudden drop. Extending the calculation to other block sizes shows the same integer-packing pattern:

5. Theoretical capacity and average runtime residency

Return to the configuration with 64 registers per thread. Its resource budget permits four blocks, or 32 warps, per SM, for 50% theoretical occupancy. Maintaining that residency throughout execution also requires the grid to keep supplying blocks as admitted work finishes.

Consider just one SM in a teaching example of time averaging: it holds 32 warps during 80% of its active cycles and eight warps during the remaining 20%. This example specifies the time distribution directly; it does not derive interval durations from block counts. Average residency is 27.2 warps, corresponding to 42.5% occupancy:

\[ \overline{W}_{\mathrm{active}} =0.8\times32+0.2\times8=27.2,\qquad \frac{\overline{W}_{\mathrm{active}}}{64}=42.5\%. \]

The same resource configuration can produce different runtime averages. If three of four blocks on an SM finish first and no further blocks arrive, the remaining block creates a low-residency interval like the one in the figure. Early warp exits and unequal block execution times can also change the shape of this timeline.

NCU's active-cycle denominator

NCU's Achieved Active Warps per SM corresponds to sm__warps_active.avg.per_cycle_active, and the normalized Achieved Occupancy corresponds to sm__warps_active.avg.pct_of_peak_sustained_active. The first measures average active warps during SM active cycles; the second expresses the result as a percentage of the architectural resident-warp capacity. The single-SM example above illustrates time weighting. The profiler handles aggregation across instances for a complete GPU.

The distinction between active and elapsed matters for small grids. Cycles when an SM is entirely idle do not belong to its active cycles, so achieved occupancy alone cannot tell whether the grid kept every SM busy. To inspect device coverage, also check activity metrics such as sm__cycles_active.avg.pct_of_peak_sustained_elapsed. Denominator definitions are in NCU Metrics Structure; NVIDIA's explanation of achieved metrics distinguishes their runtime measurement from static theoretical values.

Grid waves and work at the tail

Given the resident-block limit per SM, the number of blocks that all SMs can admit at once provides a useful notion of a wave of work. A small grid may fail to cover every SM or fill the residency available on the SMs that do receive work. An incomplete final wave lets some SMs finish earlier than others. Even with enough blocks, load imbalance can leave a few long-running blocks extending the kernel tail. This distribution of completion times is what a tail-effect analysis must examine.

For a low theoretical value, first identify the static limiter. When the theoretical value is relatively high but achieved occupancy is much lower, inspect grid size, launch__waves_per_multiprocessor, block completion times, and load distribution. Cluster placement, concurrent kernels, MPS, or resource partitioning can also change work distribution or available resources; include them when the execution environment calls for it.

6. Turn residency analysis into a performance decision

The resource example now explains why only two blocks fit initially and why reducing registers stops increasing residency at four blocks. It has not established a speedup. Deciding whether more residency would help requires observing how the scheduler uses the warps already present.

The scheduler identifies eligible warps whose next instruction is ready, then selects a warp to issue instructions. An eligible warp that is not chosen at that issue point is not selected. After issue, the scheduler evaluates the warp's next instruction again. NCU Scheduler Statistics describes these opportunities through active, eligible, and issued warps. Stalled warps retain residency resources but cannot currently provide an issue opportunity.

If the scheduler frequently has no eligible warp, more independent work may help cover the wait. If it can already issue consistently while the target execution pipe or memory bandwidth is near saturation, extra resident warps offer less room for improvement. A kernel with more registers may also hide latency through instruction-level parallelism. Forcing a lower register limit to increase occupancy can instead add spilling and memory accesses. The CUDA Best Practices discussion of block size explicitly includes these tradeoffs.

To evaluate the change in the example, use realizable versions with 96 and 64 registers per thread. Keep input size and timing method fixed, verify that both compute the same result, and check their actual register usage, shared memory, and theoretical occupancy. Then compare kernel time and the eligible/issued behavior in Scheduler Statistics. If residency rises from two blocks to four without reducing runtime, investigate additional spilling, instruction count, or another execution bottleneck. Reducing the count further to 32 registers per thread has no theoretical residency benefit here and needs a separate performance justification.

The result determines the next investigation. Once the resource ceiling is sufficient, Warp Stall Analysis can help locate the blocked issue opportunities. If the report shows MIO Throttle, examine the affected instructions and downstream acceptance pressure. Keep kernel time as the final measure, and use occupancy to explain how resource budgets changed the work available to the scheduler.
