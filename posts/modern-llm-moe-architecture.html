现代 LLM MoE 架构：路由、分发与融合执行

Transformer 的 FFN 保存了模型中很大一部分参数，dense 执行会让每个 token 经过同一组权重，扩展模型容量也会直接增加单 token 计算量。Sparse MoE 把 FFN 权重改为条件选择，使模型容量与每次前向实际激活的计算量可以分别扩展。

条件计算把 MLP 权重选择扩展成一条运行时数据路径。Router 输出需要转换成 token permutation 和 expert offset，跨 GPU 部署还要完成两次 all-to-all，低精度 kernel 则要求额外的量化布局。MoE 因而同时是模型架构与执行系统问题。

版本范围：下文按 2026-08-07 可见的公开论文、文档和开源实现整理。讨论对象是 Transformer block 中替换 FFN/MLP 的 sparse MoE；attention 仍负责 token 之间的信息混合。

0. 模型边界

Sparse MLP-MoE 是一类条件执行的 FFN：模型包含 \(E\) 个 expert，每个 token 根据 router 分数激活其中 \(K\) 个，并将这些 expert 的输出加权合并。在 \(K \ll E\) 时，模型可以增加总参数量，而每个 token 只支付被选 expert 的计算成本。

这一定义把讨论限定在 Transformer block 内的 MLP-MoE。Embedding MoE、attention MoE、RL policy MoE 与传统 ensemble 具有不同的选择对象和执行路径，不纳入下文。后续章节沿着 router、indexer、dispatcher、expert parallel 与 MegaMoE 的顺序追踪一次完整执行。

1. MoE 对 FFN 的替换

在 dense Transformer block 中，FFN 对所有 token 使用同一组 MLP 权重。MoE block 保留 attention、residual 与 normalization 的位置，只把 FFN 替换为 router、expert 集合和 weighted combine。由此，attention 继续混合 token 信息，MoE 负责在参数空间中选择计算路径。

Dense FFN 与 MoE FFN 的位置

对第 \(t\) 个 token，这个替换可以写成：

\[ y_t = \sum_{j \in \mathrm{TopK}(r(x_t))} p_{t,j} E_j(x_t) \]

其中 \(x_t\) 是 hidden state，\(r(x_t)\) 产生 \(E\) 个 expert 的 routing score，\(\mathrm{TopK}(r(x_t))\) 给出被激活的 expert 集合。\(E_j\) 表示第 \(j\) 个 expert MLP，\(p_{t,j}\) 是合并该 expert 输出时使用的权重。

2. 从路由到执行的数据流

公式只描述每个 token 的结果，kernel 还需要知道哪些 token 属于同一个 expert。下面的 torch-like 代码把这一步展开：router 先产生 top-k expert id 与权重，indexer 再按 expert 重排 token，GroupedGEMM 执行各个 expert，最后按原 token 顺序加权回填。

# x: [T, H], T = batch * seq
# E: number of experts, K: experts per token
logits = x @ router_w                         # [T, E]
score = torch.softmax(logits, dim=-1)          # or sigmoid + normalize

topk_w, topk_e = torch.topk(score, K, dim=-1)  # [T, K]

token_id = torch.arange(T).repeat_interleave(K)
expert_id = topk_e.flatten()
gate = topk_w.flatten()

order = torch.argsort(expert_id)
x_perm = x[token_id[order]]
expert_perm = expert_id[order]
gate_perm = gate[order]

counts = torch.bincount(expert_perm, minlength=E)
y_perm = grouped_expert_mlp(x_perm, counts)

y = torch.zeros_like(x)
y.index_add_(0, token_id[order], y_perm * gate_perm[:, None])
MoE 层的数据流

生产实现会把 Python 层的 sort、prefix sum、索引、GroupedGEMM 与 combine 下沉到 CUDA kernel 和通信库中；当 expert 跨 GPU 分布时，dispatch 与 combine 之间还会加入 all-to-all。无论这些阶段是否融合，运行时都要把按 token 排列的数据转换成按 expert 排列的数据，再恢复原顺序。这次布局变换构成了 MoE 相对 dense FFN 的主要系统增量。

6. MegaMoE 执行 contract

在 DeepGEMM 与 vLLM 的公开代码语境中，MegaMoE 是面向 MoE expert 层的融合执行路径。它把 prepare/indexing、量化、dispatch、expert GEMM、activation 与 combine 中的若干阶段压缩到更少的 kernel 和中间内存访问中。模型的 routed-expert 语义保持不变，变化发生在后端执行 contract。

常规 MoE 路径与 MegaMoE 路径

vLLM 的 prepare_megamoe 给出了这个 contract 的入口：它将 hidden states 量化为 FP8，并把 routing top-k tensor 重新打包成 DeepGEMM MegaMoE kernel 使用的布局。因此，后端输入除了 x、topk_ids 与 topk_weights，还包含与 quantization、scale、layout 和 indexing 对应的 metadata。

同一个 routed-expert 模型可以映射到常规 GroupedGEMM，也可以映射到 MegaMoE 类 fused kernel。两条路径共享路由数学定义，却采用不同的量化格式、布局 metadata 和阶段划分；评估实现时应分别检查模型语义与 backend contract。

7. 执行瓶颈与约束

MoE 的动态路由会同时改变 GEMM 形状、通信量和中间布局，这些开销彼此耦合：expert histogram 决定 bucket 大小，bucket 大小影响 GroupedGEMM 利用率，expert placement 又把同一分布转换成 all-to-all 流量。

Modern LLM MoE Architectures: Routing, Dispatch, and Fused Execution

The FFN stores a large share of a Transformer's parameters. Dense execution sends every token through the same weights, so increasing model capacity also raises per-token compute. Sparse MoE makes the FFN weights conditional, allowing model capacity and the computation activated by each forward pass to scale separately.

Conditional computation extends weight selection into a runtime data path. Router output must become token permutations and expert offsets; a multi-GPU deployment adds two all-to-all phases; low-precision kernels impose quantization and layout contracts. MoE is consequently both a model architecture and an execution-system problem.

Version scope: the discussion follows public papers, documentation, and open-source implementations visible on 2026-08-07. It covers sparse MoE layers that replace the FFN/MLP in a Transformer block; attention continues to mix information across tokens.

0. Model boundary

A sparse MLP-MoE is a conditionally executed FFN with \(E\) experts. Router scores select \(K\) experts for each token, and their outputs are combined with routing weights. When \(K \ll E\), total parameters can grow while each token pays for only the selected experts.

This definition limits the discussion to MLP-MoE inside Transformer blocks. Embedding MoE, attention MoE, RL policy MoE, and conventional ensembles select different objects and follow different execution paths. The sections below trace one MLP-MoE execution through the router, indexer, dispatcher, expert-parallel runtime, and MegaMoE backend.

1. Replacing the FFN

In a dense Transformer block, every token uses the same FFN weights. A MoE block leaves attention, residual connections, and normalization in place, replacing only the FFN with a router, an expert pool, and a weighted combine. Attention continues to mix information among tokens; MoE chooses a parameter-space compute path for each token.

For token \(t\), the replacement is:

\[ y_t = \sum_{j \in \mathrm{TopK}(r(x_t))} p_{t,j} E_j(x_t) \]

Here \(x_t\) is the hidden state, \(r(x_t)\) produces scores for \(E\) experts, and \(\mathrm{TopK}(r(x_t))\) is the activated expert set. \(E_j\) denotes expert MLP \(j\), and \(p_{t,j}\) weights its output during combination.

2. Routing-to-execution dataflow

The equation specifies a token's output, but a kernel also needs to know which tokens belong to each expert. The torch-like code below makes that transformation explicit. The router emits top-k expert ids and weights, the indexer groups tokens by expert, GroupedGEMM executes the expert MLPs, and the final accumulation restores token order.

# x: [T, H], T = batch * seq
# E: number of experts, K: experts per token
logits = x @ router_w
score = torch.softmax(logits, dim=-1)          # or sigmoid + normalize

topk_w, topk_e = torch.topk(score, K, dim=-1)

token_id = torch.arange(T).repeat_interleave(K)
expert_id = topk_e.flatten()
gate = topk_w.flatten()

order = torch.argsort(expert_id)
x_perm = x[token_id[order]]
expert_perm = expert_id[order]
gate_perm = gate[order]

counts = torch.bincount(expert_perm, minlength=E)
y_perm = grouped_expert_mlp(x_perm, counts)

y = torch.zeros_like(x)
y.index_add_(0, token_id[order], y_perm * gate_perm[:, None])

Production systems lower the Python-level sort, prefix sum, indexing, GroupedGEMM, and combination into CUDA kernels and communication libraries. When experts span GPUs, dispatch and combine also contain all-to-all collectives. Fused or unfused, the runtime must transform token-major data into expert-major data and then restore the original order. That layout round trip is the main systems work added to a dense FFN.

4. Architecture and execution patterns

An MoE design chooses routing cardinality, expert granularity, shared paths, capacity policy, and parallel placement. These dimensions are independent, so one model may occupy several rows. DeepSeek-V3, for example, combines fine-grained experts, a shared expert path, and expert-parallel execution.

The model configuration therefore determines the expert histogram and communication load seen by each execution step.

6. The MegaMoE execution contract

In the public DeepGEMM and vLLM code, MegaMoE is a fused execution path for an MoE expert layer. It collapses selected parts of prepare/indexing, quantization, dispatch, expert GEMM, activation, and combination into fewer kernels and intermediate memory passes. The routed-expert model semantics stay fixed; the backend execution contract changes.

The vLLM prepare_megamoe entry point exposes that contract. It quantizes hidden states to FP8 and repacks routing top-k tensors into the layout consumed by the DeepGEMM MegaMoE kernel. Backend input therefore includes quantization scales, layout metadata, and indexing metadata in addition to x, topk_ids, and topk_weights.

Conventional MoE path and MegaMoE fused path

The same routed-expert model can map to a conventional GroupedGEMM path or a MegaMoE-style fused kernel. Both implement the same routing equation, but they use different quantization formats, metadata layouts, and stage boundaries. Implementation analysis must therefore keep model semantics separate from the backend contract.

7. Execution bottlenecks and constraints

Dynamic routing changes GEMM shapes, communication volume, and intermediate layouts together. The following costs interact: the expert histogram sets bucket sizes, bucket sizes determine GroupedGEMM utilization, and expert placement converts that same distribution into all-to-all traffic.

Cross-GPU communicationExpert parallelism requires dispatch and combine all-to-all operations.DeepEP, HybridEP, communication-compute overlap
Small decode batchesEach expert receives too few tokens to use tensor cores efficiently.Persistent kernels, expert batching, separate prefill and decode paths
Low-precision layoutFP8/FP4 scales, block layouts, and packed weights must match the kernel contract.Prepacked weights and a prepare stage that emits quantized activations and index metadata
CUDA GraphDropless execution makes shapes dynamic and full-graph capture difficult.Padding, bucketing, capture of stable subgraphs, or specialized dispatchers

Expert GEMM TFLOPS covers only the compute stage of this path. End-to-end latency also includes the router, indexer, dispatch, combine, and all-to-all phases. Throughput depends on the layout presented to each kernel, the realized \(M\) dimension of every expert, and the extent to which computation covers communication waits.
