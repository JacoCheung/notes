现代 LLM MoE 架构：路由、分发与融合执行

本文按 2026-08-07 可见的公开论文、文档和开源实现整理。MoE 不是 attention 变体,但它和 attention 一起决定了现代 Transformer block 的系统形态:attention 负责 token 之间的信息混合,MoE 通常替换 FFN/MLP,负责把每个 token 送到少量专家上计算。

0. 范围

LLM 里的 MoE 大多是 sparse MoE。模型有多个 expert,但每个 token 只激活其中 \(K\) 个。于是参数量可以增长,单 token 激活计算量却不按 expert 总数线性增长。

本文只讨论 Transformer block 里的 MLP-MoE。Embedding MoE、attention MoE、RL policy MoE 和传统 ensemble 不展开。范围收窄以后,router、indexer、dispatcher、expert parallel 和 MegaMoE 这条实现链更容易保持可追踪。

1. MoE 在 block 里的位置

Dense Transformer block 里,FFN 对所有 token 使用同一组 MLP 权重。MoE block 把这组 MLP 权重拆成多个 expert,再用 router 为每个 token 选择少量 expert。

Dense FFN 与 MoE FFN 的位置
flowchart LR
  X["hidden x [B,S,H]"] --> A["self-attention"]
  A --> N1["residual / norm"]
  N1 --> F["dense FFN: one MLP for all tokens"]
  F --> Y["output"]

  X2["hidden x [B,S,H]"] --> A2["self-attention"]
  A2 --> N2["residual / norm"]
  N2 --> R["router: token -> expert ids"]
  R --> E0["expert MLP 0"]
  R --> E1["expert MLP 1"]
  R --> E2["expert MLP ..."]
  E0 --> C["weighted combine"]
  E1 --> C
  E2 --> C
  C --> Y2["output"]

数学上可以写成:

\[ y_t = \sum_{j \in \mathrm{TopK}(r(x_t))} p_{t,j} E_j(x_t) \]

\(x_t\) 是第 \(t\) 个 token 的 hidden state。\(\mathrm{TopK}(r(x_t))\) 是 router 选出的 expert 集合。\(E_j\) 是第 \(j\) 个 expert MLP。\(p_{t,j}\) 是 combine 时的权重。

2. torch op 视角

把实现写成 torch-like 代码,MoE 层就是下面这段。真实系统会把 sort、prefix sum、all-to-all、GEMM 和 combine 拆到 CUDA kernel 或通信库里,但数据流没有变。

# x: [T, H], T = batch * seq
# E: number of experts, K: experts per token
logits = x @ router_w                         # [T, E]
score = torch.softmax(logits, dim=-1)          # or sigmoid + normalize

topk_w, topk_e = torch.topk(score, K, dim=-1)  # [T, K]

token_id = torch.arange(T).repeat_interleave(K)
expert_id = topk_e.flatten()
gate = topk_w.flatten()

order = torch.argsort(expert_id)
x_perm = x[token_id[order]]
expert_perm = expert_id[order]
gate_perm = gate[order]

counts = torch.bincount(expert_perm, minlength=E)
y_perm = grouped_expert_mlp(x_perm, counts)

y = torch.zeros_like(x)
y.index_add_(0, token_id[order], y_perm * gate_perm[:, None])
MoE 层的数据流
flowchart LR
  X["tokens x"] --> R["router matmul"]
  R --> K["top-k ids / weights"]
  K --> I["indexer: token ids, expert ids, offsets"]
  I --> D["dispatch: permute by expert"]
  D --> G["grouped expert MLP"]
  G --> U["unpermute"]
  U --> C["combine: weighted index_add"]
  C --> Y["tokens y"]

这段代码也解释了为什么 MoE 的系统复杂度高于 dense FFN。Dense FFN 是两三个大 GEMM。MoE 多了动态 top-k、索引生成、token 重排、按 expert 分桶、稀疏通信和加权回填。结构层面只增加了一个 router,实现层面却多出一条完整的数据搬运路径。

5. 演进历史

时间 阶段 变化

2020GShardGoogle 把 MoE 和自动 sharding 结合,top-2 routing 成为大规模 Transformer MoE 的经典路径。
2021Switch Transformer把路由简化成 top-1,系统更便于扩展,capacity 和 token dropping 也被工程化处理。
2021-2022GLaMdecoder-only sparse MoE 进入 LLM 主线,用稀疏激活换更大的总参数量。
2024开源 LLM MoEMixtral 8x7B 让 top-2 FFN-MoE 成为开源模型里的常见样板。
2024-2025Fine-grained + shared expertsDeepSeekMoE 和 DeepSeek-V3 把专家切得更细,并加入 shared expert。
2025-2026系统融合GroupedGEMM、DeepEP、HybridEP、FP8/FP4、MegaMoE 和 FlashMoE 类实现把重点转到通信计算 overlap 与 fused kernel。

这条历史线有个清晰转向。早期论文问的是"怎么让大模型只激活一小部分参数"。现在系统更关心"router 输出的动态 token 分布,怎么在多 GPU、低精度和 CUDA Graph 约束下获得稳定吞吐"。

6. MegaMoE

MegaMoE 这个术语需要限定语境。按 DeepGEMM 和 vLLM 当前公开代码里的用法,它不是新的模型结构,而是 MoE expert 层的融合执行路径。它的目标是把 prepare/indexer、量化、dispatch、expert GEMM、activation、combine 以及通信 overlap 做成更少的 kernel 和更少的中间内存访问。

常规 MoE 路径与 MegaMoE 路径
flowchart LR
  H["hidden states"] --> R["router top-k"]
  R --> P["prepare / indexer"]
  P --> D["dispatch"]
  D --> F1["expert FC1 GroupedGEMM"]
  F1 --> S["SwiGLU"]
  S --> F2["expert FC2 GroupedGEMM"]
  F2 --> C["combine"]
  C --> O["output"]

  H2["hidden states"] --> R2["router top-k"]
  R2 --> Q["prepare_megamoe: pack, quantize, index"]
  Q --> M["MegaMoE fused execution"]
  M --> O2["output"]

vLLM 的 prepare_megamoe 文档直接给出执行 contract:它会把 hidden states 量化成 FP8,并把 routing top-k tensors 重新打包成 DeepGEMM MegaMoE kernel 需要的布局。MegaMoE 的入口不是普通的 x, topk_ids, topk_weights 就结束了,还要满足 kernel 对 quantization、scale、layout 和 metadata 的要求。

因此 MegaMoE 可以理解为 MoE 的 "kernel contract"。模型层仍然是 routed experts,系统层换成了更激进的执行方式。这个区分需要保留:同一个 MoE 架构可以用常规 GroupedGEMM 跑,也可以用 MegaMoE 类 fused kernel 跑。

问题 为什么难 常见处理

看 MoE 性能时,不能只看 expert GEMM 的 TFLOPS。router、indexer、dispatch、combine 和 all-to-all 都在 critical path 上。MoE 的快慢往往取决于数据是否以 kernel 需要的顺序出现,以及通信空泡能不能被计算盖住。

Modern LLM MoE Architectures: Routing, Dispatch, and Fused Execution

This note reflects public papers, documentation, and open-source implementations visible on 2026-08-07. MoE is not an attention variant, but it sits next to attention in the modern Transformer block. Attention mixes information across tokens. MoE usually replaces the FFN/MLP and sends each token to a small number of experts.

0. Scope

Most LLM MoE layers are sparse MoE layers. A model owns many experts, but each token activates only \(K\) of them. Total parameters can grow while per-token activated compute stays bounded by \(K\), not by the total number of experts.

This note focuses on MLP-MoE inside Transformer blocks. It does not cover embedding MoE, attention MoE, RL policy MoE, or ordinary ensembles.

1. Where MoE sits

A dense Transformer block uses one FFN for every token. A MoE block splits that FFN into experts and uses a router to choose a few experts per token.

\[ y_t = \sum_{j \in \mathrm{TopK}(r(x_t))} p_{t,j} E_j(x_t) \]

\(x_t\) is the hidden state of token \(t\). \(E_j\) is expert \(j\). \(p_{t,j}\) is the combine weight for that expert output.

2. Torch-op view

# x: [T, H], T = batch * seq
# E: number of experts, K: experts per token
logits = x @ router_w
score = torch.softmax(logits, dim=-1)

topk_w, topk_e = torch.topk(score, K, dim=-1)

token_id = torch.arange(T).repeat_interleave(K)
expert_id = topk_e.flatten()
gate = topk_w.flatten()

order = torch.argsort(expert_id)
x_perm = x[token_id[order]]
expert_perm = expert_id[order]
gate_perm = gate[order]

counts = torch.bincount(expert_perm, minlength=E)
y_perm = grouped_expert_mlp(x_perm, counts)

y = torch.zeros_like(x)
y.index_add_(0, token_id[order], y_perm * gate_perm[:, None])

The code is the shape of most MoE systems. Production implementations replace the Python-level sort, indexing, communication, grouped GEMM, and combine with CUDA kernels and collectives. The dataflow is still router, indexer, dispatcher, expert MLP, and combiner.

5. History

The path is fairly direct. Early MoE work asked how to route examples to local experts. Sparsely-gated MoE brought conditional computation into large neural networks. GShard, Switch Transformer, and GLaM made it a Transformer scaling method. Mixtral made FFN-MoE familiar in open LLMs. DeepSeekMoE and DeepSeek-V3 moved the design toward finer expert granularity, shared experts, and more aggressive routing. The recent systems work is about grouped GEMM, expert parallel all-to-all, low precision layout, CUDA Graph constraints, and fused kernels.

6. MegaMoE

In the DeepGEMM and vLLM usage, MegaMoE is not a new model architecture. It is a fused execution path for the MoE expert layer. It tries to collapse prepare/indexing, quantization, dispatch, expert GEMM, activation, combine, and communication overlap into fewer kernels and fewer intermediate memory passes.

The vLLM prepare_megamoe API is explicit about the contract: it quantizes hidden states to FP8 and repacks routing top-k tensors into the layout consumed by the DeepGEMM MegaMoE kernel. The model layer is still routed experts. The systems layer changes how those experts execute.

7. Implementation issues

  • Routing is dynamic. Each batch produces a different expert histogram.
  • Dispatch and combine are data movement problems before they are math problems.
  • Expert parallelism adds all-to-all traffic on the critical path.
  • Decode batches often give each expert too few tokens to fill tensor cores.
  • FP8/FP4 paths require the activation layout, scale metadata, weight packing, and kernel contract to agree.
  • Dropless MoE creates dynamic shapes, which makes CUDA Graph capture and tuning harder.
