同一批 embedding 查表请求，在输入、发送和接收缓冲区中有不同的排列顺序。这个四 rank、两特征的例子逐个追踪 40 次请求，展示按目标分桶、AllToAll 交付和按特征重排的全过程。

1. 动画播放器

The same embedding lookup requests appear in different orders across input, send, and receive buffers. This four-rank, two-feature example tracks all 40 occurrences through destination bucketing, AllToAll delivery, and feature regrouping.

2. 输入与请求标识

四个 rank 都持有表 A 和表 B 的一部分行，也各自收到一批查表请求。橙色格子属于 A，蓝色格子属于 B；格子里的 0–3 表示这次请求应交给哪个 owner rank。图中保留请求出现的顺序，用 来源 rank:特征:位置 标识每个格子，其中特征 0 是 A、1 是 B。

例如，0:0:1 表示 rank 0 的 A 特征中第二次请求。它的格子写着 1，因此要发送给 rank 1。多个请求可以具有相同的 owner；每次请求都保留自己的标识，移动后仍可逐一追踪。

Rank 0[0, 1, 2, 0, 3, 0][0, 1, 3]9
Rank 1[0, 1, 1, 2, 3, 3][3, 2, 1, 0, 1]11
Rank 2[3, 1, 2, 1][3, 1, 2, 3, 1, 0]10
Rank 3[0, 0, 2, 1, 3, 3, 2][1, 2, 0]10

初始布局按 feature 排列：每个 rank 的一个连续缓冲区先放 A，再放 B。四个 rank 分别有 9、11、10、10 次请求，总计 40 次。

TorchRec 用 KeyedJaggedTensor（KJT）保存这份输入。图中的一排实心格是 values，一个展平的一维张量；下方的描边小格是 lengths，记录每个样本在每个特征下有几个 key。本例中每个 rank 只带一个样本，所以每个特征占一个 lengths 元素，rank 0 是 [6, 3]。批大小为 B 时，每个特征占 B 个元素。

3. 按目标 rank 分桶

各 rank 在发送前扫描输入，把每次请求放到对应 owner 的桶中。桶之间按目标 rank 排列；每个桶内部先 A 后 B，同一特征的相对顺序保持不变。发往同一目标的数据由此组成连续分段。

1A[1], B[1][1, 1]2
2A[2][1, 0]1
3A[4], B[2][1, 1]2

rank 0 的四段 values 长度是 [4, 2, 1, 2]。例如发往 rank 1 的分段包含 A[1] 和 B[1]，它们在输入中相隔较远，分桶后被放在一起。

分桶同时重写 lengths：每个目标 rank 下每个特征一项，rank 0 得到 [3, 1, 1, 1, 1, 0, 1, 1]。发往 rank 2 的一段是 [1, 0]，即 1 个 A、0 个 B。values 中只有 ID，一段 key 里哪几个属于 A，全靠这两个数记录。把一段的 lengths 相加，就得到这段 values 的长度。

4. AllToAll 交换与接收端重排

AllToAll 将每个发送段交给对应目标。用列表表示分段时，这一步满足：

recv[dst][src] = send[src][dst]

接收端拿到的 values 是一串没有标签的 ID。要查表，它得知道两件事：哪一段来自哪个 rank，段内哪几个属于 A。TorchRec 为此做三次 AllToAll，先交换各段的长度，再分别传 lengths 和 values。

rank 0 参与的三次 AllToAll；splits 的每组是 [lengths 个数, values 个数, 批大小]
顺序张量rank 0 发给 rank 0–3rank 0 收自 rank 0–3接收端由此得知
1splits[2, 4, 1] [2, 2, 1] [2, 1, 1] [2, 2, 1][2, 4, 1] [2, 2, 1] [2, 1, 1] [2, 3, 1]每个来源的段长与批大小
2lengths[3, 1] [1, 1] [1, 0] [1, 1][3, 1] [1, 1] [0, 1] [2, 1]段内各特征的 key 数
3values4、2、1、2 个 ID4、2、1、3 个 ID查表用的 ID

第一次调用里，每个 rank 给每个 peer 发 3 个整数：将要发给它的 lengths 个数、values 个数和自己的批大小。这是固定批大小、无权重时的情形；开启 collective 校验时还会附一个标签。rank 0 读回后得到 values 的接收长度 [4, 2, 1, 3]，也就是矩阵第 0 列，共 10 次请求；另外三个 rank 分别接收 12、8、10 次。接收端按这些长度分配缓冲区，再把它们作为后两次调用的 output_split_sizes。后两次调用在读回这些长度之后相继发起。

来源 rank 由位置决定。all_to_all_single 按 rank 顺序拼接各来源的段：先是来源 rank 0 的 4 个 key，再是 rank 1 的 2 个，依此类推，所以布局变成 来源 rank → feature。每段的起始偏移由接收端累加段长得到，不随消息传输。

特征由 lengths 决定。rank 0 收到的 lengths 是 [3, 1, 1, 1, 0, 1, 2, 1]，每个来源两项。来源 rank 3 的一段有 3 个 key，对应 [2, 1]，所以前两个属于 A，最后一个属于 B。

查表前，接收端再把同一特征的请求集中到一起。Recat 将布局改为 feature → 来源 rank：先取各来源的 A，再取各来源的 B。这一步是本地重排。

接收块：R0-A  R0-B  R1-A  R1-B  R2-A  R2-B  R3-A  R3-B

块的边界同样来自 lengths：第 k 块的长度就是它的第 k 项，rank 0 的 R2-A 块长度为 0。按块序展开，得到对接收缓冲区中 10 个元素的置换 [0, 1, 2, 4, 7, 8, 3, 5, 6, 9]，最终是 6 次 A 请求加 4 次 B 请求。lengths 按同一块序重排为 [3, 1, 0, 2, 1, 1, 1, 1]：前四项是来源 rank 0–3 的 A，后四项是它们的 B。重排后的 KJT 把四个来源的样本并成一个批，批大小为 4。批大小大于 1 时每块含多个 lengths 元素，见行分片文章中的 recat 说明。

5. Python 布局演算

下面的纯 Python 代码使用图中的 owner 标签，演算三次布局变化。每次请求用一个 Key 记录来源、特征、位置和 owner。程序验证每个阶段都保留全部请求；指定 SVG 路径后，还会逐项核对图中的 40 个格子、16 条路由计数，以及各处的 lengths 和 splits。

def stable_bucketize(keys):
    buckets = [[[] for _ in FEATURES] for _ in range(WORLD_SIZE)]
    for key in keys:
        buckets[key.owner][key.feature].append(key)
    # Destination rank is the outer dimension; feature is the inner dimension.
    return [flatten(feature_buckets) for feature_buckets in buckets]

stable_bucketize 先按 owner 和特征分组，返回四个目标段，segment_lengths 再数出每段中各特征的 key 数。接收端按来源拼接 values 和 lengths，然后调用 recat。这个函数只读 lengths 和块序，不查看 Key 里的特征字段，得到的布局与动画终点相同：

from keyflow_example import (exchange, flatten, lengths_segments, make_inputs,
                             recat, segment_lengths, stable_bucketize)

inputs = make_inputs()
send = [stable_bucketize(keys) for keys in inputs]
send_lengths = [segment_lengths(segments) for segments in send]
send_splits = [[len(segment) for segment in segments] for segments in send]

# Three exchanges: segment sizes first, then lengths and values.
recv_splits = exchange(send_splits)
recv_lengths = [flatten(blocks) for blocks in
                exchange([lengths_segments(lengths) for lengths in send_lengths])]
recv_values = [flatten(segments) for segments in exchange(send)]

lookup_lengths, lookup_values, _ = recat(recv_lengths[0], recv_values[0])
print(send_lengths[0])  # [3, 1, 1, 1, 1, 0, 1, 1]
print(recv_splits[0])   # [4, 2, 1, 3]
print(recv_lengths[0])  # [3, 1, 1, 1, 0, 1, 2, 1]
print(lookup_lengths)   # [3, 1, 0, 2, 1, 1, 1, 1]
print([key.occurrence for key in lookup_values])

下载完整演算程序和结果数据。运行 python3.11 keyflow_example.py 可打印输入、各阶段的 lengths、分段长度及 rank 0 的重排结果。程序在本地用列表模拟数据流；动画的 19.2 秒展示时长用于观察步骤。

本例对应 key 的输入分发。真实 embedding ID 的行号换算、三次调用之间的 CPU 等待，以及查表后向量的返回路径，见TorchRec Row-wise Sharding；多批次之间如何重叠通信，见TorchRec Sparse Dist Pipeline。

对应的 TorchRec 布局操作可对照固定版本的 bucketize_kjt_before_all2all 与 _recat。分段长度由 KJT.dist_splits 计算，KJTAllToAllSplitsAwaitable 交换它们，KJTAllToAllTensorsAwaitable 传输 lengths 和 values，KJT.dist_init 按块序重排；来源记录保存了原图校验值与版本链接。

6. DynamicEmb 的 hierarchical input dist

前面各节是 TorchRec 自带的 input dist。NVIDIA recsys-examples 里的 DynamicEmb 在 PR 528 中为 row-wise 分片的 EmbeddingCollection 换了一套实现，用 output_dist="hierarchical" 打开。节点内的 GPU 通过 NVLink 直接读写彼此的显存；节点之间由 GPU kernel 自己经 NCCL GIN 发 InfiniBand，中间不经过 CPU。本节用同一份 40 次请求演算它的 input dist。

例子的设定如下。4 个节点各有 1 张 GPU，所以 rank 就是节点。每个 rank 也是自己节点的 proxy，没有节点内转发这一段，凡是发给别的 rank 的 key 都跨节点。表 A 和表 B 属于同一个 lookup group。key 不带 weights。

输入已经是 unique 的。这个算子只接收 index dedup 之后的 key，所以图中最左边的 KJT 里，同一张表的同一个 key 在一个 rank 上只出现一次；每个节点只有一张 GPU，node dedup 也就不再合并任何 key。图里 KJT values 等行的实心格沿用前文的画法：格子里的数字标的是这个 key 的 owner rank，不是 key 的取值。同一个 rank 上数字相同的格子是不同的 key，只是 owner 相同。真实的 key 是 64 位的 embedding ID，owner 由它按分片规则算出。

2. Inputs in the diagram

Each of the four ranks owns a shard of tables A and B and receives its own batch of lookup requests. Orange cells belong to A and blue cells to B. The digit 0–3 inside a cell identifies its owner rank. Each occurrence retains its identity as source rank:feature:index, with feature 0 for A and 1 for B.

For example, 0:0:1 is the second A request from rank 0. Its cell contains 1, so it goes to rank 1. Cells with the same owner remain distinct requests, so we can track each through the layouts.

The initial layout is feature-major: each rank has one contiguous buffer containing A followed by B. The four ranks start with 9, 11, 10, and 10 requests, for a total of 40.

TorchRec stores this input in a KeyedJaggedTensor (KJT). The row of filled cells is its values, a flat one-dimensional tensor. The outlined cells below are its lengths, which count the keys each sample has for each feature. Every rank holds a single sample in this example, so a feature takes one lengths entry, and rank 0 has [6, 3]. With batch size B, a feature takes B entries.

3. Bucketizing by destination rank

Before sending, rank 0 scans its input, placing each request in its owner's bucket. Buckets are ordered by destination rank; each contains A followed by B, preserving order within each feature. Requests for the same destination become a contiguous segment.

The four values segments on rank 0 have lengths [4, 2, 1, 2]. Its segment for rank 1 contains A[1] and B[1]: these requests were separated in the input but become adjacent after bucketization.

Bucketizing also rewrites lengths, with one entry per feature under each destination rank. Rank 0 gets [3, 1, 1, 1, 1, 0, 1, 1]. The segment for rank 2 is [1, 0]: one A key and no B key. values holds nothing but IDs, so these two numbers are the only record of which keys in a segment belong to A. 4. AllToAll delivery and receive-side regrouping

AllToAll delivers each send segment to its destination. With each segment represented as a list, the transfer is:

recv[dst][src] = send[src][dst]

The values a receiver gets are a run of untagged IDs. Before it can look anything up, it needs to know which segment came from which rank, and which keys inside a segment belong to A. TorchRec answers both with three AllToAll calls: the ranks first exchange segment sizes, then send lengths and values separately.

The three AllToAll calls on rank 0; each splits group is [lengths count, values count, batch size]
CallTensorRank 0 sends to ranks 0–3Rank 0 receives from ranks 0–3What the receiver learns
1splits[2, 4, 1] [2, 2, 1] [2, 1, 1] [2, 2, 1][2, 4, 1] [2, 2, 1] [2, 1, 1] [2, 3, 1]Segment sizes and batch size of every source
2lengths[3, 1] [1, 1] [1, 0] [1, 1][3, 1] [1, 1] [0, 1] [2, 1]Keys per feature inside each segment
3values4, 2, 1, 2 IDs4, 2, 1, 3 IDsThe IDs to look up

In the first call, every rank sends each peer three integers: how many lengths entries and how many values it is about to send that peer, and its own batch size. That is the case for a fixed batch size without weights; with collective validation enabled, a tag is appended. Rank 0 reads back the values receive sizes [4, 2, 1, 3], the first matrix column, totaling 10 requests. The other ranks receive 12, 8, and 10. The receiver allocates its buffers from these sizes and passes them as output_split_sizes to the two calls that follow, which it issues one after the other once the sizes are read back.

Position identifies the source rank. all_to_all_single concatenates the segments in rank order: four keys from source rank 0, then two from rank 1, and so on, producing a source rank → feature layout. The receiver computes each segment's starting offset by summing the sizes before it; offsets are never transmitted.

lengths identifies the feature. Rank 0 receives [3, 1, 1, 1, 0, 1, 2, 1], two entries per source. The segment from source rank 3 has three keys and the entries [2, 1], so the first two keys belong to A and the last one to B.

Local lookup needs requests grouped by feature. Recat changes the received layout to feature → source rank: first A from every source, then B from every source. This is a local permutation.

Received: R0-A  R0-B  R1-A  R1-B  R2-A  R2-B  R3-A  R3-B
Block:      0     1     2     3     4     5     6     7
Reordered:R0-A  R1-A  R2-A  R3-A  R0-B  R1-B  R2-B  R3-B
Block permutation: [0, 2, 4, 6, 1, 3, 5, 7]

The block boundaries also come from lengths: block k is as long as entry k, and the R2-A block on rank 0 has length 0. Expanding the block order gives the element indices [0, 1, 2, 4, 7, 8, 3, 5, 6, 9] for the ten received requests. The result contains six A requests followed by four B requests. lengths is permuted in the same block order and becomes [3, 1, 0, 2, 1, 1, 1, 1]: four A entries from source ranks 0–3, then their four B entries. The regrouped KJT merges the samples of the four sources into one batch of size 4. With a batch size above 1, a block holds several lengths entries; see the recat notes in the row-wise sharding article.

5. Reproducing the example in code

The following pure Python code uses the owner labels supplied by the diagram to replay the layout changes. A Key records the source, feature, index, and owner of each occurrence. The program verifies that every stage preserves all 40 requests. When an SVG path is supplied, it also checks the cells, the 16 route counts, and every lengths and splits label against the diagram.

def stable_bucketize(keys):
    buckets = [[[] for _ in FEATURES] for _ in range(WORLD_SIZE)]
    for key in keys:
        buckets[key.owner][key.feature].append(key)
    # Destination rank is the outer dimension; feature is the inner dimension.
    return [flatten(feature_buckets) for feature_buckets in buckets]

stable_bucketize groups by owner and feature, returning four destination segments, and segment_lengths counts the keys of each feature in every segment. The receiver concatenates values and lengths by source and applies recat. That function reads only lengths and the block order, never the feature field of a Key, and produces the same layout as the final animation frame:

from keyflow_example import (exchange, flatten, lengths_segments, make_inputs,
                             recat, segment_lengths, stable_bucketize)

inputs = make_inputs()
send = [stable_bucketize(keys) for keys in inputs]
send_lengths = [segment_lengths(segments) for segments in send]
send_splits = [[len(segment) for segment in segments] for segments in send]

# Three exchanges: segment sizes first, then lengths and values.
recv_splits = exchange(send_splits)
recv_lengths = [flatten(blocks) for blocks in
                exchange([lengths_segments(lengths) for lengths in send_lengths])]
recv_values = [flatten(segments) for segments in exchange(send)]

lookup_lengths, lookup_values, _ = recat(recv_lengths[0], recv_values[0])
print(send_lengths[0])  # [3, 1, 1, 1, 1, 0, 1, 1]
print(recv_splits[0])   # [4, 2, 1, 3]
print(recv_lengths[0])  # [3, 1, 1, 1, 0, 1, 2, 1]
print(lookup_lengths)   # [3, 1, 0, 2, 1, 1, 1, 1]

6. DynamicEmb's hierarchical input dist

The sections above cover TorchRec's own input dist. In NVIDIA recsys-examples, pull request 528 gives DynamicEmb a different implementation for a row-wise sharded EmbeddingCollection, enabled with output_dist="hierarchical". GPUs of one node read and write each other's memory over NVLink. Between nodes, a GPU kernel sends over InfiniBand itself through NCCL GIN, without the CPU. This section replays its input dist on the same 40 requests.

The example makes these assumptions. Four nodes hold one GPU each, so a rank is a node. Each rank is also its own node's proxy, so there is no forwarding inside a node, and every key for another rank crosses nodes. Tables A and B belong to one lookup group. The keys carry no weights.

The input is already unique. The operator takes index-deduplicated keys only, so in the leftmost KJT a key of a table appears once on a rank; with one GPU per node, node dedup has nothing left to merge. Filled cells in KJT values and the other key rows are drawn as in the earlier figure: the digit marks the key's owner rank, not the key's value. Cells with the same digit on one rank are different keys that share an owner. A real key is a 64-bit embedding ID, and its owner follows from it by the sharding rule.

动画分三步播放，图从左到右是一次调用里数据经过的位置，五列对应下面五件事。前两件在第一步里，第三、四件在第二步里，第五件是第三步。

  1. Bucketize。按 owner 做稳定的计数排序，只写两个数组：inv 记录分桶后的第 row 行是 KJT 里的第几个 key，bucket_feature_of_row 记录这一行的 owner × 特征数 + 特征。key 留在 KJT 原地不动。TorchRec 在这一步会另外生成一份按目标排好的 values 和 lengths，也就是第 3 节的 Send buffer。
  2. Push。node_key_push 按 inv 取出 key，直接写进 window 里的 node_keys。自己拥有的 key 进 own part，是一次本地写，图中画成虚线。发往其他节点的 key 进 remote part，经 node dedup 后按 owner 节点切成 key_stage 的三段，本例中每段是一个 16 字节的 chunk 头加若干条 8 字节的 key 记录。chunk 头的方括号里依次是 record_lo, record_hi | start, end：这段记录的范围，以及它们的 embedding 行将来在本 rank proxy_rows 里的位置。
  3. Count message。rail_exchange 给每个 rail peer 做一次 GIN put，并附带一个 signal。消息的头部对所有 peer 相同，尾部是发给该 peer 的每个特征的 key 数。它承担了 TorchRec 中 splits 和 lengths 两次 AllToAll 的作用：既给出每段的长度，也给出段内每个特征有几个 key。各 rank 读到同一批头部后，各自算出同一份 rail layout，owner 不需要把布局发回来。
  4. Key put。rail_key_push 对每个 owner 再做一次 GIN put，把 key_stage 中对应的一段写进对方 rail_keys 里 rail layout 给出的位置，即图中的 slice_in，同样附带 signal。owner 在 rail_done 里等齐所有 signal。
  5. Owner tables。owner_kjt_kernel 填出 owner 的 KJT：每个特征占 4 列，第一列是自己的 own part，其余三列是其他节点，按节点序排列。embedding 行在 lookup_rows 中保持到达顺序：先是 own part，再是各来源节点的记录。两种顺序不同，kernel 因此同时写出 row_map，记录 KJT 第 i 个 key 的行号。之后 lookup 把第 i 个 key 的行直接写到 row_map[i]，这些行已经是 output dist 要发送的顺序。

The animation plays in three steps. From left to right, the figure shows where the data sits during one call, and its five columns match the five items below: the first two happen in step 1, the next two in step 2, and the last is step 3.

  1. Bucketize. A stable counting sort by owner writes two arrays only. inv says which KJT key bucketized row row is, and bucket_feature_of_row holds the row's owner × feature count + feature. The keys stay where they are in the KJT. TorchRec builds a separate copy of values and lengths ordered by destination at this point, the send buffer of section 3.
  2. Push. node_key_push reads keys through inv and stores them straight into node_keys in the window. Keys the rank owns go into the own part with a local store, drawn as a dashed line. Keys for other nodes go into the remote part and, after node dedup, into three slices of key_stage, one per owner node. In this example a slice is one 16-byte chunk header followed by 8-byte key records. The brackets of a chunk header read record_lo, record_hi | start, end: the range of these records, and where their embedding rows will sit in this rank's proxy_rows.
  3. Count message. rail_exchange sends each rail peer one GIN put with a signal. The message header is the same for every peer, and its tail holds the key count of each feature for that peer. It does the work of TorchRec's splits and lengths AllToAll calls: it gives the size of each segment and the number of keys per feature inside it. Every rank reads the same headers and computes the same rail layout, so no owner sends its layout back.
  4. Key put. rail_key_push sends each owner one more GIN put, again with a signal. It copies the owner's slice of key_stage into the owner's rail_keys at the place the rail layout gives, shown as slice_in. The owner waits for every signal in rail_done.
  5. Owner tables. owner_kjt_kernel fills the owner's KJT. A feature has four columns: the rank's own part first, then the three other nodes in node order. Embedding rows keep their arrival order in lookup_rows: the own part, then each source node's records. The two orders differ, so the kernel also writes row_map, the row of KJT key i. The lookup later writes key i's row straight to row_map[i], and those rows are already in the order the output dist sends them.

Compared with TorchRec's flow, three things change.

Rank 0's row_map is [0, 1, 2, 4, 7, 8, 3, 5, 6, 9], the same as the element permutation of recat in section 4, because rank 0 happens to be its own first column. On rank 2 the KJT columns are nodes 2, 0, 1, 3, while TorchRec orders them 0, 1, 2, 3, so lengths and row numbers no longer agree.
