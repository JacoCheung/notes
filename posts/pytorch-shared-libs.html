PyTorch Linux 共享库的构建与加载关系

import torch 是 PyTorch 在 Python 中的统一入口。Linux 动态加载器在这个入口背后装入一组分工明确的共享库：基础类型与 dispatcher、CPU 算子、CUDA 算子、Python binding 和全局依赖分别位于不同二进制中。它们的构建关系与实际 ELF 依赖共同决定符号解析和扩展加载行为，而 torch._C 只承担面向 CPython 的入口职责。

范围说明:本文以 Linux CUDA wheel 与 PyTorch v2.12.0 源码为边界。macOS、Windows、ROCm、CPU-only wheel 和本地源码构建可能采用不同的文件名、可选库与链接结构；具体环境应以已安装的 torch/lib/ 和对应版本源码为准。

1. import torch 的共享库加载起点

CUDA 版 PyTorch wheel 通常在 torch/lib/ 中携带下列共享库。构建选项会改变其中的可选项，因此这份清单用于建立分层结构，而非规定每个发行包必须包含的文件集合。

$ ls torch/lib/*.so
torch/lib/libc10.so
torch/lib/libc10_cuda.so
torch/lib/libtorch.so
torch/lib/libtorch_cpu.so
torch/lib/libtorch_cuda.so
torch/lib/libtorch_python.so
torch/lib/libtorch_global_deps.so
torch/lib/libshm.so
torch/lib/libcaffe2_nvrtc.so
torch/lib/libnnapi_backend.so
# 可选(BUILD_LAZY_CUDA_LINALG=ON):
torch/lib/libtorch_cuda_linalg.so
# 可选(USE_NVSHMEM):
torch/lib/libtorch_nvshmem.so

阅读这组二进制需要同时追踪两条关系：源码目录如何汇入 CMake target，以及 target 的链接接口如何体现在安装后的 ELF 依赖中。两者相关，却不完全相同；链接器的 --as-needed、构建开关和 wheel 打包过程都可能改变最终的 DT_NEEDED 条目。

libtorch.so 正好说明了这一区别。它对应一个以占位翻译单元创建的 wrapper target，自身实现很少，主要通过 PUBLIC 链接接口关联 torch_cpu 与当前启用的设备库。这个 CMake 角色不能直接推出某个 wheel 中 libtorch.so 的完整动态依赖。

Build and Load Relationships of PyTorch Linux Shared Libraries

import torch is PyTorch's unified Python entry point. Behind it, the Linux dynamic loader brings in shared libraries with distinct responsibilities: core types and the dispatcher, CPU operators, CUDA operators, Python bindings, and global dependencies live in separate binaries. Their build relations and concrete ELF dependencies determine symbol resolution and extension loading, while torch._C serves as the CPython-facing entry.

Scope: this article describes the Linux CUDA wheel and PyTorch v2.12.0 source. macOS, Windows, ROCm, CPU-only wheels, and local source builds can differ in file names, optional libraries, and link structure. Concrete environments should be checked against the installed torch/lib/ directory and the matching source tag.

1. Start: which .so files import torch loads

A CUDA-enabled PyTorch wheel commonly contains the following shared libraries under torch/lib/. Build options change the optional entries, so the list establishes the binary layers rather than prescribing every distribution.

$ ls torch/lib/*.so
torch/lib/libc10.so
torch/lib/libc10_cuda.so
torch/lib/libtorch.so
torch/lib/libtorch_cpu.so
torch/lib/libtorch_cuda.so
torch/lib/libtorch_python.so
torch/lib/libtorch_global_deps.so
torch/lib/libshm.so
torch/lib/libcaffe2_nvrtc.so
torch/lib/libnnapi_backend.so
# optional (BUILD_LAZY_CUDA_LINALG=ON):
torch/lib/libtorch_cuda_linalg.so
# optional (USE_NVSHMEM):
torch/lib/libtorch_nvshmem.so

Understanding these binaries requires two related views: how source directories feed CMake targets, and how target link interfaces survive in installed ELF artifacts. Linker --as-needed, build flags, and wheel packaging can all change the final DT_NEEDED entries.

libtorch.so illustrates the distinction. CMake creates it as a wrapper target from a placeholder translation unit, with little implementation of its own, and uses its PUBLIC link interface to associate torch_cpu with the enabled device libraries. That CMake role alone does not determine the complete dynamic dependency list of a particular wheel.

3. 共享库的源码归属

交互图给出整体拓扑，下面按依赖层次展开各库的源码归属与职责。先从不依赖 ATen 和 Python 的 c10 开始，再进入设备基础设施、算子实现和 Python binding。

3.1 libc10: Core Tensor 抽象

c10/CMakeLists.txt 通过 GLOB 收集这一 target 的源码：

file(GLOB C10_SRCS
  *.cpp
  core/*.cpp
  core/impl/*.cpp
  mobile/*.cpp
  macros/*.cpp
  util/*.cpp)
# 显式排除 c10/cuda/、c10/hip/

这一层提供 TensorImpl、Storage、Device、DispatchKey、Allocator、intrusive_ptr、TypeMeta，以及 c10::util 下的通用工具，如 Optional、SmallVector、ArrayRef 和错误处理宏。它构成 PyTorch C++ API 的基础类型层；标准构建中的 c10 target 位于 CUDA、Python 与 ATen target 之下。

c10 target 链接 fmt、nlohmann_json 和 moodycamel（concurrent queue），并按构建选项链接 gflags、glog 或 cpuinfo。后续 target 通过对 c10 的 PUBLIC 依赖继承这组基础类型与必要的传递链接关系。

3.2 libc10_cuda: CUDA 基础设施

c10/cuda/CMakeLists.txt 显式列出 c10_cuda target 的源码，而没有使用 glob：

add_library(c10_cuda
  CUDAAllocatorConfig.cpp
  CUDACachingAllocator.cpp
  CUDAFunctions.cpp
  CUDAStream.cpp
  driver_api.cpp
  impl/CUDAGuardImpl.cpp
  ...)

该库实现 CUDA 流（CUDAStream）、CUDA caching allocator（torch.cuda.empty_cache() 操作的对象）、CUDAGuard、CUDA device assertion 和 driver API 包装。这些组件为上层 CUDA 算子提供设备、stream、内存与运行时状态管理。

c10_cuda 以 PUBLIC 方式链接 c10 与 torch::cudart。因此，依赖 c10_cuda 的设备库可以沿 target 链获得核心类型和 CUDA runtime 的链接要求。

设备基础设施本身不承载 ATen 算子。算子层在此之上分成两部分：libtorch_cpu 提供 dispatcher、CPU 实现和框架运行时，libtorch_cuda 则复用这些机制并注册 CUDA 实现。

libtorch_cpu.so 通常是 wheel 中体积较大的共享库之一。caffe2/CMakeLists.txt 通过 ${Caffe2_CPU_SRCS} 汇集其源码，主要覆盖下列模块：

torch_cpu 以 PUBLIC 方式链接 c10，并根据构建配置链接 MKL、MKLDNN、Sleef、protobuf、flatbuffers 和 OpenMP 等依赖。它由此成为设备算子库和 C++ wrapper target 共同依赖的 ATen 与框架运行时层。

3.4 libtorch_cuda: CUDA 算子库

caffe2/CMakeLists.txt 通过 ${Caffe2_GPU_SRCS} 与 ${Caffe2_GPU_CU_SRCS} 汇集 CUDA host 代码和 device code：

torch_cuda 以 PUBLIC 方式链接 c10_cuda 和 torch_cpu：前者提供设备基础设施，后者提供 ATen dispatcher 与 native 函数注册机制。该 target 还链接 torch::cudart，并按功能开关加入 NCCL、cuFile、cuSPARSELt、cuDSS、NVTX 或 NVSHMEM。这个 target 关系使 CUDA 算子库在链接时接入同一套 dispatcher 与核心类型，而最终进程实际装入哪些 ELF 依赖仍由构建产物的 DT_NEEDED 决定。

3.5 libtorch: wrapper target

libtorch target 用链接接口聚合 CPU 与设备库，CMake 定义本身很短：

# caffe2/CMakeLists.txt:923
# Wrapper library for people who link against torch and expect
# both CPU and CUDA support. Contains 'torch_cpu' and 'torch_cuda'.
add_library(torch ${DUMMY_EMPTY_FILE})
target_link_libraries(torch PUBLIC torch_cpu_library)
if (USE_CUDA)
  target_link_libraries(torch PUBLIC torch_cuda_library)
endif()

非 MSVC 构建使用空的 empty.cpp 创建 libtorch.so,其主要职责是提供 wrapper target 的链接接口。torch target 的 PUBLIC 关系让 CMake consumer 同时获得 CPU 与当前启用的设备库；安装后 libtorch.so 保留哪些动态依赖,仍取决于具体构建产物。

在 BUILD_LIBTORCHLESS split-build 模式下,torch 会被 find_library() 找到一个已安装的外部 libtorch.so,但概念不变。

3.6 libtorch_python: Python 绑定

torch/CMakeLists.txt 定义 torch_python target，其源码列表来自 build_variables.bzl 中的 libtorch_python_core_sources：

torch/csrc/jit/python/*.cppTorchScript 的 Python 接口
torch/csrc/api/python/C++ Frontend 的 pybind 包装

算子库形成 C++ 执行层之后，torch_python 再把这一层暴露给 CPython。CMake 以 PRIVATE 方式将 torch_python 链接到 ${TORCH_LIB}；标准构建中的该变量指向 wrapper target torch，后者聚合 torch_cpu 与已启用的设备库。target 的传递链接接口与最终 ELF 的 DT_NEEDED 列表属于不同层次，因此仅凭这行 CMake 不能断言 wheel 必然经由 libtorch.so 间接加载 CPU/CUDA。其它链接项包括 Python::Module、pybind11、shm 及若干可选库。

3.7 libtorch_global_deps: RTLD_GLOBAL 预加载技巧

libtorch_global_deps 用占位源码承载一组需要提前进入全局符号空间的依赖：

add_library(torch_global_deps SHARED torch/csrc/empty.c)
target_link_libraries(torch_global_deps PRIVATE
  ${MPI_LIBRARIES}
  ${MKL_LIBRARIES}
  CUDA::cudart
  CUDA::nvToolsExt
  ...)

它的 C 代码本身只有一个 empty.c 占位符,构建配置按功能开关链接 MPI、MKL 与部分 CUDA 依赖。torch/__init__.py 在常规 Linux 启动路径中用 RTLD_GLOBAL 显式加载它:

# torch/__init__.py (节选)
def _load_global_deps():
    here = os.path.abspath(__file__)
    lib_path = os.path.join(os.path.dirname(here), "lib", "libtorch_global_deps.so")
    ctypes.CDLL(lib_path, mode=ctypes.RTLD_GLOBAL)
# ... 然后:
from torch._C import *

CMake 的公开注释给出两类动机:OpenMPI 等库会在初始化后 dlopen 插件,并假设所需符号位于全局命名空间;某些 CUDA 库又可能安装在非标准路径,局部加载后无法被后续的普通搜索找到。这里不把它概括成“所有 runtime 必须共享同一实例”,因为公开源码没有给出这样的统一保证。

3.8 辅助与可选库

  • libshm.so:torch/lib/libshm/,跨进程共享内存 Tensor 的 manager。 link torch_cpu PRIVATE。 配套还有 torch_shm_manager 可执行文件。
  • libcaffe2_nvrtc.so:位于 aten/src/ATen/cuda/nvrtc_stub/ATenNVRTC.cpp 的延迟绑定 stub。相关路径通过运行时加载取得 NVRTC 入口,从而避免在主库加载阶段建立同样的直接依赖。
  • libtorch_cuda_linalg.so:可选(BUILD_LAZY_CUDA_LINALG=ON),把 MAGMA / cusolver 相关的 linalg 算子从 libtorch_cuda.so 里拆出来 lazy load,主库不必硬链 MAGMA。
  • libnnapi_backend.so:torch/csrc/jit/backends/nnapi/ 下的 Android NNAPI TorchScript backend。固定版本的 CMake 在启用 Python 且目标不是 Darwin 时构建该 target；是否进入具体发行包仍由打包配置决定。
  • libtorch_nvshmem.so:可选(USE_NVSHMEM),用 NVSHMEM 做集体通信。

3. Source ownership by library

The graph establishes the overall topology. The sections below follow the dependency layers from c10, which is independent of ATen and Python, through device infrastructure and operator implementations to the Python bindings.

3.1 libc10: the core tensor abstraction

c10/CMakeLists.txt collects the target's sources with a GLOB:

file(GLOB C10_SRCS
  *.cpp
  core/*.cpp
  core/impl/*.cpp
  mobile/*.cpp
  macros/*.cpp
  util/*.cpp)
# explicitly excludes c10/cuda/ and c10/hip/

This layer provides TensorImpl, Storage, Device, DispatchKey, Allocator, intrusive_ptr, TypeMeta, and general utilities under c10::util, including Optional, SmallVector, ArrayRef, and error-handling macros. It forms the foundation of the PyTorch C++ API; in a standard build, the c10 target sits below the CUDA, Python, and ATen targets.

The c10 target links fmt, nlohmann_json, and moodycamel (concurrent queue), with optional links to gflags, glog, and cpuinfo. Downstream targets that depend on c10 through a PUBLIC relation inherit its core types and required transitive link interface.

3.2 libc10_cuda: CUDA infrastructure

c10/cuda/CMakeLists.txt lists the c10_cuda sources explicitly rather than using a GLOB:

add_library(c10_cuda
  CUDAAllocatorConfig.cpp
  CUDACachingAllocator.cpp
  CUDAFunctions.cpp
  CUDAStream.cpp
  driver_api.cpp
  impl/CUDAGuardImpl.cpp
  ...)

The library implements CUDA streams (CUDAStream), the CUDA caching allocator operated on by torch.cuda.empty_cache(), CUDAGuard, CUDA device assertions, and driver-API wrappers. These components provide device, stream, memory, and runtime-state management for higher-level CUDA operators.

c10_cuda links both c10 and torch::cudart as PUBLIC dependencies. Device libraries that depend on c10_cuda can therefore inherit the link requirements for the core types and the CUDA runtime along the target chain.

Device infrastructure does not itself contain ATen operators. The operator layer above it is split between libtorch_cpu, which provides the dispatcher, CPU implementations, and framework runtime, and libtorch_cuda, which reuses those mechanisms while registering CUDA implementations.

3.3 libtorch_cpu: the main CPU library (ops, autograd, JIT)

libtorch_cpu.so is commonly one of the larger shared libraries in a wheel. caffe2/CMakeLists.txt collects its sources through ${Caffe2_CPU_SRCS}, covering the following modules:

torch_cpu links c10 as a PUBLIC dependency and, according to the build configuration, links MKL, MKLDNN, Sleef, protobuf, flatbuffers, and OpenMP. It consequently serves as the ATen and framework-runtime layer shared by device operator libraries and the C++ wrapper target.

3.4 libtorch_cuda: the CUDA op library

caffe2/CMakeLists.txt collects CUDA host and device code through ${Caffe2_GPU_SRCS} and ${Caffe2_GPU_CU_SRCS}:

torch_cuda links c10_cuda and torch_cpu as PUBLIC dependencies: the former supplies device infrastructure, while the latter supplies the ATen dispatcher and native-function registration. The target also links torch::cudart and optionally NCCL, cuFile, cuSPARSELt, cuDSS, NVTX, or NVSHMEM. This target relation connects CUDA operators to the shared dispatcher and core types at link time; the final process load set still follows the built artifacts' DT_NEEDED entries.

3.5 libtorch: the wrapper target

The libtorch target aggregates CPU and device libraries through its link interface. Its CMake definition is short:

# caffe2/CMakeLists.txt:923
# Wrapper library for people who link against torch and expect
# both CPU and CUDA support. Contains 'torch_cpu' and 'torch_cuda'.
add_library(torch ${DUMMY_EMPTY_FILE})
target_link_libraries(torch PUBLIC torch_cpu_library)
if (USE_CUDA)
  target_link_libraries(torch PUBLIC torch_cuda_library)
endif()

The resulting libtorch.so contains almost no implementation of its own: non-MSVC builds use an empty empty.cpp placeholder. The torch target's PUBLIC link interface gives CMake consumers the CPU library and the enabled device library. Which dynamic dependencies remain on the installed libtorch.so is artifact-dependent.

In BUILD_LIBTORCHLESS split-build mode, torch is resolved by find_library() against an externally installed libtorch.so, but the concept is identical.

3.6 libtorch_python: the Python bindings

torch/CMakeLists.txt defines the torch_python target, whose source list comes from libtorch_python_core_sources in build_variables.bzl:

Once the operator libraries form the C++ execution layer, torch_python exposes that layer to CPython. CMake links torch_python privately to ${TORCH_LIB}, which points to the torch wrapper target in a standard build; that wrapper aggregates torch_cpu and the enabled device libraries. A target's transitive link interface is distinct from the final ELF DT_NEEDED list, so this line alone does not prove that a wheel always loads CPU/CUDA indirectly through libtorch.so. Other links include Python::Module, pybind11, shm, and optional libraries.

3.7 libtorch_global_deps: the RTLD_GLOBAL preload trick

libtorch_global_deps uses placeholder source to carry dependencies that must enter the global symbol namespace early:

add_library(torch_global_deps SHARED torch/csrc/empty.c)
target_link_libraries(torch_global_deps PRIVATE
  ${MPI_LIBRARIES}
  ${MKL_LIBRARIES}
  CUDA::cudart
  CUDA::nvToolsExt
  ...)

The C code is a placeholder empty.c; the target links MPI, MKL, and selected CUDA dependencies according to build options. In the normal Linux startup path, torch/__init__.py explicitly loads it with RTLD_GLOBAL:

# torch/__init__.py (abridged)
def _load_global_deps():
    here = os.path.abspath(__file__)
    lib_path = os.path.join(os.path.dirname(here), "lib", "libtorch_global_deps.so")
    ctypes.CDLL(lib_path, mode=ctypes.RTLD_GLOBAL)
# ... then:
from torch._C import *

The public CMake note gives two concrete motivations: libraries such as OpenMPI may dlopen plugins after initialization and expect required symbols in the global namespace; some CUDA libraries may live in non-standard locations and cannot be found by a later normal search after a local load. The source does not state a universal “single runtime instance” guarantee.

3.8 Auxiliary and optional libraries

  • libshm.so: under torch/lib/libshm/, the shared-memory manager for cross-process tensors; links torch_cpu PRIVATE. Ships alongside the torch_shm_manager executable.
  • libcaffe2_nvrtc.so: a lazy-binding stub implemented in aten/src/ATen/cuda/nvrtc_stub/ATenNVRTC.cpp. The relevant path obtains NVRTC entry points through runtime loading instead of imposing the same direct dependency at main-library load time.
  • libtorch_cuda_linalg.so: optional (BUILD_LAZY_CUDA_LINALG=ON); splits MAGMA / cusolver linalg kernels out of libtorch_cuda.so so the main library does not have to hard-link MAGMA.
  • libnnapi_backend.so: the Android NNAPI TorchScript backend under torch/csrc/jit/backends/nnapi/. In the pinned CMake, the target is built when Python is enabled and the platform is not Darwin; inclusion in a distribution still depends on packaging.
  • libtorch_nvshmem.so: optional (USE_NVSHMEM), NVSHMEM-based collective communication.

4. torch._C 的加载职责

torch._C 是面向 CPython 的薄扩展入口。它与 libtorch_python.so 的职责可以沿构建和初始化路径拆成三步：

  1. torch._C 是 Python 扩展模块。PyTorch v2.12.0 的 setup.py 用 torch/csrc/stub.c 构建这个薄扩展,并链接 torch_python。
  2. stub.c 定义 PyInit__C,其函数体调用 initModule();initModule() 才实现在 torch/csrc/Module.cpp 并由 libtorch_python.so 提供。
  3. from torch._C import * 先让动态加载器装入薄扩展及其链接依赖。CMake target 图可以说明构建关系,但不能替代具体 wheel 的 DT_NEEDED 检查。

在这个 Linux wheel 语境下，torch._C 提供 CPython 初始化入口，libtorch_python.so 承载大部分 Python binding 实现。安装产物实际加载的下游库可用 readelf -d torch/_C*.so、readelf -d torch/lib/libtorch_python.so 或 ldd 核对。

torch/__init__.py 的实际启动流程:

# 1. 先用 RTLD_GLOBAL dlopen libtorch_global_deps,把 MKL/cudart 等全局化
_load_global_deps()

# 2. 加载 _C 薄扩展及该构建产物记录的动态依赖
from torch._C import *

# 3. 显式 init ATen / c10 的全局状态
_C._initExtension(_manager_path())

5. 构建目标与安装产物的边界

CMake target 描述构建期的源码归属与传递链接接口,安装后的 .so 则由链接器和打包流程形成具体 ELF。下面汇总两类对象之间最容易混淆的对应关系。

  1. libtorch.so 由占位翻译单元创建。生成的共享对象承载 wrapper target,主要价值在 CMake target 的 PUBLIC 链接接口。
  2. caffe2/CMakeLists.txt 定义 torch_cpu 和 torch_cuda target。目录名来自项目历史，当前文件仍承担 libtorch 主要 target 的构建职责。
  3. torch_python 的 CMake target 链接 ${TORCH_LIB}。标准构建中它指向 wrapper target torch;最终 wheel 是否保留相同的间接 ELF 依赖链,需要检查产物。
  4. libtorch_global_deps 走显式预加载路径。torch/__init__.py 在常规 Linux 路径中用 ctypes.CDLL(..., RTLD_GLOBAL) 加载它。
  5. libcaffe2_nvrtc 是延迟绑定 stub。它把 NVRTC 的装载推迟到相关功能实际使用时，使基础导入路径不依赖 NVRTC 已经可用。
  6. libnnapi_backend.so 对应 torch/csrc/jit/backends/nnapi/ 的 NNAPI backend;是否随特定 Linux 包发布取决于构建与打包配置。
  7. build_variables.bzl 保存多组共享源文件列表,但不是整个源码树的唯一清单;仍需结合各级 CMake 条件阅读。

4. Loading responsibilities of torch._C

torch._C is the thin extension entry for CPython. Its relationship with libtorch_python.so follows three build and initialization steps:

  1. torch._C is a Python extension. In PyTorch v2.12.0, setup.py builds the thin extension from torch/csrc/stub.c and links it to torch_python.
  2. stub.c defines PyInit__C, whose body calls initModule(); initModule() is implemented in torch/csrc/Module.cpp and provided by libtorch_python.so.
  3. from torch._C import * asks the dynamic loader to load the thin extension and the dependencies recorded in that artifact. The CMake target graph describes build relations, not a universal wheel DT_NEEDED chain.

In this Linux wheel context, torch._C is the thin CPython-facing entry and libtorch_python.so carries most Python-binding implementation. Inspect the installed artifacts with readelf -d torch/_C*.so, readelf -d torch/lib/libtorch_python.so, or ldd to determine the actual downstream libraries.

The startup sequence in torch/__init__.py:

# 1. dlopen libtorch_global_deps with RTLD_GLOBAL so MKL/cudart symbols are global
_load_global_deps()

# 2. load the thin _C extension and the dependencies recorded by this build
from torch._C import *

# 3. explicitly init ATen / c10 global state
_C._initExtension(_manager_path())

5. Build targets and installed artifacts

A CMake target describes source ownership and transitive link interfaces during the build. An installed .so is the concrete ELF artifact produced by the linker and packaging process. The following points consolidate the correspondences that are easiest to conflate.

  1. libtorch.so is built from a placeholder translation unit. The resulting shared object carries the wrapper target, whose main role is its CMake PUBLIC link interface.
  2. caffe2/CMakeLists.txt defines the torch_cpu and torch_cuda targets. The directory name reflects project history, while the file still owns the main libtorch target definitions.
  3. The torch_python CMake target links ${TORCH_LIB}. In a standard build this points to the torch wrapper target; inspect the wheel to see whether the same indirect ELF dependency chain remains.
  4. libtorch_global_deps follows an explicit preload path. In the normal Linux path, torch/__init__.py loads it with ctypes.CDLL(..., RTLD_GLOBAL).
  5. libcaffe2_nvrtc is a lazy-binding stub. It defers NVRTC loading until the corresponding functionality is used, keeping the base import path independent of NVRTC availability.
  6. libnnapi_backend.so corresponds to the NNAPI backend under torch/csrc/jit/backends/nnapi/; whether it ships in a Linux package depends on build and packaging configuration.
  7. build_variables.bzl stores many shared source lists, but it is not the sole manifest for the whole source tree; CMake conditions must also be read.
