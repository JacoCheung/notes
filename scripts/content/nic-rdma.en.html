NICs and RDMA: from sockets to verbs

DMA allows a NIC to access host memory directly, but ordinary TCP sockets still require substantial CPU work, including protocol processing and buffer management (moving data between user and kernel memory). RDMA reduces CPU involvement: after user-space memory buffers are registered directly and access permissions are established, the application can submit read and write requests from user space, and the NIC accesses the specified remote memory directly.

A 4 KiB transfer between nodes provides a common example for comparing TCP sockets and RDMA Write. The mlx5 source shows how descriptors, doorbells and completion queues work together, and how user-space libraries and kernel drivers divide responsibility for establishing resources and permissions through device files, submitting requests from user space and reporting completion to the application.

Source baseline: Linux 6.12 and rdma-core 61.0, checked on 2026-11-10; the send wrapper uses glibc 2.40. Source links are pinned to tags or commits and collected by section in the source index. The RDMA Write sequence diagram follows source-level call order; activation bars mark each participant's logical activity scope.

1. NICs and memory

A PCIe NIC interacts with the CPU through two kinds of address. Its BARs (Base Address Registers) describe device address windows. Once the driver maps a register region, CPU loads and stores issue MMIO (Memory-Mapped I/O) accesses to the device. To access host memory, the NIC uses DMA (Direct Memory Access) mappings established through the Linux DMA API. The IOMMU is part of the host I/O subsystem. With address translation enabled, the NIC issues DMA requests using I/O virtual addresses (IOVAs). After a request reaches the host over PCIe, the IOMMU translates its IOVA to a host physical address and checks access permissions. [[dma-api|DMA addresses and mappings]] · [[vtd-arch|Host DMA remapping]]

The CPU describes where to read data and how many bytes to send, then places that descriptor in a ring in memory. The NIC reads it and executes the transfer. The conventional mlx5 send path has four steps:

StepPerformed byAction
① Write the descriptorCPUWrite a WQE (Work Queue Element) into the send queue (SQ) ring, recording the operation, buffer address and length.
② Ring the doorbellCPURecord the new producer index in the DBR (Doorbell Record) in memory, then write the doorbell register on a UAR (User Access Region) page in the BAR, an MMIO write that reaches the NIC over PCIe.
③ ExecuteNICDMA-read the WQE and the data it points to, then transmit the data.
④ CompleteNICDMA-write CQEs (Completion Queue Entries) into the completion queue (CQ) as configured, then raise an interrupt or wait for software to poll, as configured.

Software performs ① and ②; the NIC performs ③ and ④. Sockets and RDMA verbs both use this queue mechanism. The socket path in section 2 submits work from the kernel Ethernet driver; the verbs path in section 3 submits it from the user-space driver libmlx5. The hardware is shared, while request submission runs in different places.

2. The TCP socket path

A sends 4 KiB to B over an established IPv4 TCP connection using ordinary copying send() and recv() calls. For this example, each call handles all 4096 bytes. send() is declared in <sys/socket.h>; the application calls a C-library wrapper before entering the kernel. On Linux x86-64 with glibc 2.40, the path is:

User space
  send(fd, buf, 4096, 0)                    # application socket-send API
    → __libc_send()                         # glibc wrapper
    → sendto(fd, buf, 4096, 0, NULL, 0)      # select the sendto system call
                ↓ syscall: enter kernel mode

Kernel space
  __sys_sendto()
    → sockfd_lookup_light(fd, ...)          # find the socket by fd
    → __sock_sendmsg()
    → sock_sendmsg_nosec()                  # dispatch to the socket's sendmsg op
    → inet_sendmsg()                        # IPv4 socket in this example
    → tcp_sendmsg()                         # socket protocol selects TCP
    → tcp_sendmsg_locked()                  # copy 4 KiB into skb pages
    → tcp_write_xmit() … dev_queue_xmit()   # TCP/IP send path to the NIC driver
    → mlx5e_xmit()                          # DMA-map pages, write a WQE in SQ  ①
    → mlx5e_notify_hw()                     # write DBR, then UAR doorbell      ②

NIC A: DMA-read the data and transmit Ethernet frames                           ③

The NULL, 0 destination arguments tell sendto to use the socket's associated peer. After looking up the socket by fd, the kernel dispatches through its operation tables to the IPv4 and TCP implementations, then continues through the protocol stack and NIC driver. [[glibc-send|glibc send wrapper]] · [[send-syscall|x86-64 syscall table]] · [[socket-send|Kernel sendto entry]] · [[socket-dispatch|Socket dispatch]] · [[inet-send|TCP / UDP dispatch]] · [[tcp-send-entry|tcp_sendmsg]]

On this socket path, B's NIC writes into receive buffers posted by the driver. B's CPU then processes TCP/IP, and the application obtains the data through recv():

NIC B: DMA-write into a posted receive buffer, write a CQE, interrupt  ④
mlx5_eq_comp_int() → napi_schedule()       # the interrupt only schedules NAPI
mlx5e_napi_poll() → mlx5e_poll_rx_cq()     # softirq: read CQEs, build skbs
  napi_gro_receive() … tcp_v4_rcv()        # TCP processing, socket receive queue
recv(fd, buf, 4096, 0)                     # system call: copy to the user buffer

This example copies the payload once between user and kernel memory at each endpoint. The CPUs also handle system calls, protocol processing and driver queues. On receive, an interrupt schedules NAPI, which processes completion entries in batches. TCP is a byte stream: applications must use the return values of send() and recv() to handle remaining bytes. Neither system calls nor interrupts have a one-to-one relationship with the 4 KiB transfer. send(2) · recv(2)

After a copying send returns successfully, the application can reuse the portion of its source buffer accepted by the kernel, even if the peer application has not read the data. MSG_ZEROCOPY replaces the sending-side copy with page pinning and a completion notification; the buffer remains in use until that notification. Linux documents a typical benefit above roughly 10 KB per write, so the 4 KiB example here keeps the copying path. [[msg-zerocopy|MSG_ZEROCOPY]]

Ordinary socket traffic already uses local DMA. RDMA adds remote-memory operations that the NIC can execute: A names B's address and access key in the request, and B's NIC checks them before writing directly into the destination buffer. This removes the receiving protocol-stack work and user-space copy from that data delivery. [[rdma-guide|RDMA operations]]

3. The RDMA Write path

The same 4 KiB now travels as an RDMA Write over RC (Reliable Connection). Both endpoints register memory and establish a connection before A posts the write. Applications call the common verbs API; a device-specific user-space implementation, called a provider, performs the hardware operations. For ConnectX, that provider is libmlx5. The socket column compares the purpose of each step.

3ibv_reg_mr()A memory region (MR): it pins the buffer's pages, builds the NIC's address translation and access rights, and returns lkey and rkey. Local requests use lkey; rkey goes to the peer for remote access checks.This example copies data through kernel buffers
4ibv_create_cq()A completion queue (CQ): the completion ring in memory.None
5ibv_create_qp(), ibv_modify_qp()An RC queue pair (QP) with a send queue (SQ) and a receive queue (RQ). It moves through INIT, RTR and RTS and is given the peer's QP number, address and starting packet sequence number.connect() / accept()
6ibv_post_send()Posts an RDMA Write WR (Work Request). libmlx5 encodes it as a WQE in the SQ ring (①), then rings the doorbell (②).send()
7ibv_poll_cq()Checks that the CQE reports success before reusing the source buffer.send() returns

Steps 1–5 establish resources through the control path and require kernel participation. The resulting MRs, QPs and CQs can serve many transfers. Steps 6–7 form the mlx5 data path: user-space code writes queues, rings doorbells and polls completions. The endpoints also exchange QP connection parameters, and B gives A its destination address and rkey. An application can exchange these over TCP, or use rdma_cm to establish the connection and exchange memory information through its own protocol. [[rdma-cm|Connection management]]

The NICs carry out the transfer in the diagram. B's NIC locates the MR using rkey, checks the range and remote-write permission, then DMA-writes the destination. B's CPU prepared those resources during setup; this ordinary RDMA Write requires no per-transfer receive posting or interrupt handling from it. Once A polls a successful completion, it can reuse the source buffer. B's application needs a notification protocol to know when the data is ready, such as a subsequent Send or RDMA Write with immediate data. [[rdma-guide|RDMA Write and notifications]]

Aside: other verbs operations

RDMA Read reverses the data direction. A posts a read naming B's address and rkey; B's NIC returns the data, and A waits for local read completion. B's CPU does not handle each read request. Send/Recv requires the receiver to post a buffer with ibv_post_recv(); an arriving Send fills it and produces a receive CQE. RDMA Write with immediate data also consumes a receive request and produces a receive CQE, while placing the payload at the remote address specified by the sender.

Basic fetch-and-add and compare-and-swap operations act atomically on an 8-byte remote object. UD (Unreliable Datagram) is connectionless, supports Send/Recv and limits each message to the path MTU. InfiniBand and RoCE share the verbs programming model; RoCE v2 carries the InfiniBand transport in UDP/IP over Ethernet. [[rdma-guide|Operations and transport modes]]

4. Drivers and device files

Applications call both send() and ibv_post_send() from user space. The difference is when they enter the kernel and which work they delegate to it. Ordinary TCP sockets pass each send to the protocol stack. With mlx5 user-space RDMA verbs, the kernel first establishes resources, then the provider directly operates the queues and registers it has permission to access.

StageOrdinary TCP socketUser-space RDMA verbs
Establish resourcesThe socket() system call creates a communication endpoint and returns a socket fd.The library opens /dev/infiniband/uverbsN and uses ioctl / write / mmap to create queues, register memory and establish mappings.
Submit datasend() enters the kernel through a system call and hands data to the TCP/IP stack.ibv_post_send() calls the provider, which directly writes the mapped queues and doorbell.
Process each transferThe kernel protocol stack, NIC driver and NIC share the work.The provider submits descriptors, and the NIC executes RDMA operations.

A socket fd represents a communication endpoint created by socket() and installed in the process's fd table. To send data, the kernel stack calls the network driver through net_device_ops.ndo_start_xmit; mlx5e assigns mlx5e_xmit() to that callback. This kernel call path reaches the driver directly, without opening a NIC device file. [[socket-create|Socket creation]] · [[socket-fd|FD allocation]] · [[netdev-send|Network-driver dispatch]] · [[mlx5e-netdev|mlx5e callback]]

The uverbs fd is a device-resource management interface. Through it, the user-space library requests MRs, QPs, CQs and UAR mappings, while the kernel checks ownership, memory and access rights. Once mapped, the provider can submit queue work in user space. The kernel continues to manage resource lifetime, including explicit release and process exit. [[user-verbs|User-space verbs and resource management]] ConnectX divides these responsibilities among the following components:

libmlx5 providerThe mlx5 verbs implementation: it allocates SQ / CQ rings and DBRs in process memory, encodes WQEs, writes doorbells and polls CQEs. It also exposes device-specific interfaces such as mlx5dv / DevX.User space
/dev/infiniband/uverbsNlibibverbs opens it to obtain the command fd. Resource commands go through ioctl / write; mappings such as UARs go through mmap.Device file
ib_uverbs.ko, ib_core.koThe RDMA user-space interface and common object layer: they parse commands, check object ownership and permissions, pin user memory and call the device driver.Kernel

A ConnectX PCI function can expose both Ethernet and RDMA interfaces. After binding the PCI device, mlx5_core creates auxiliary devices such as mlx5_core.eth.0 and mlx5_core.rdma.0. The mlx5e driver binds .eth and is compiled into mlx5_core.ko. The separate mlx5_ib.ko module binds .rdma and depends on the mlx5 core and common RDMA modules. Control path

Creating QPs and CQs and registering MRs involves device resources, pinned memory and access permissions, which the kernel checks and establishes. The ibv_create_qp() path associates the user-space queue memory with a hardware QP:

ibv_create_qp()                 # libmlx5's create_qp()
  mlx5_alloc_qp_buf()           # allocate the SQ / RQ ring in process memory
  mlx5_alloc_dbrec()            # allocate the DBR
  ioctl / write(cmd_fd)         # system call: /dev/infiniband/uverbsN
    ib_uverbs → ib_core         # parse the command, check objects and rights
      mlx5_ib_create_qp()       # mlx5_ib.ko
        ib_umem_get()           # pin the ring's pages for NIC DMA
        mlx5_ib_db_map_user()   # pin the DBR's page
        mlx5_qpc_create_qp()    # build the CREATE_QP firmware command
          mlx5_cmd_exec()       # mlx5_core.ko's command channel

The rings and the DBR that the NIC reads live in process memory and are allocated by libmlx5; the kernel pins those pages and passes their addresses to the NIC through firmware commands. [[mlx5-create-qp|Addresses from libmlx5]] · [[mlx5-ib-qp|Pinning and commands in mlx5_ib]] The device-file mechanism itself (open returns an fd, ioctl dispatches through the driver's file-operations table, mmap establishes mappings) is covered in the device files section of the CUDA Internals post CUDA layers and the Linux driver.

Data path

ibv_post_send() and ibv_poll_cq() are inline functions in verbs.h that call the provider's function pointers without entering the kernel. [[verbs-inline|verbs.h]] libmlx5 encodes the WR as a WQE: the control segment holds the opcode and WQE index, the remote-address segment holds remote_addr and rkey, and the data segment holds the local address, length and lkey. Lines 768–769 publish queue progress. A barrier orders the WQE stores before the DBR update, which records the new producer index in its send slot. Lines 774–778 prepare write-combining access and acquire a lock if several threads share the BlueFlame register.

Lines 780–786 notify the NIC. When the conditions hold, mlx5_bf_copy() writes the WQE into the UAR page's BlueFlame buffer, delivering the descriptor directly. The conditions include one WR in this call, BlueFlame support, inline data or a preference for BlueFlame, and a WQE that fits. The other branch writes only the control segment's first 8 bytes, containing the WQE index, opcode and QP number. Both branches use MMIO.

Line 798 flushes the write-combining buffer before releasing the lock, ordering this register write ahead of another thread's submission. Line 799 switches to the other half of the BlueFlame buffer for the next doorbell. The lock and barriers preserve ordering among submitters.

ibv_poll_cq() also stays in user space: the provider checks the ownership bit to see whether the NIC has written the next CQE in the CQ ring, reads it, and writes the consumer index back to the CQ's DBR. [[mlx5-cq|mlx5_poll_cq]]

bf->reg points to the UAR mapping in the current process. libmlx5 allocates the UAR through the command fd and maps it with mmap(). mlx5_ib uses rdma_user_mmap_io() for the BAR page, selecting write-combining attributes for BlueFlame pages and uncached attributes for doorbell-only pages. Once mapped, CPU MMIO stores can notify the NIC without a system call for each doorbell. [[uar-provider|Allocation and mapping in libmlx5]] · [[mlx5-ib-mmap|mlx5_ib mmap]]
