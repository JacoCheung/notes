URLs, domains, and DNS

A web address connects two systems: DNS supplies a network address, and a web server selects a resource from the request. A domain can lead to several servers, a server can host several domains, and a page can be available under different hostnames and paths. Name resolution, application routing, and redirects control these relationships at different stages.

This article follows https://dev.example.com/ and https://example.com/dev through URL parsing, domain administration, DNS lookup, and a shared page handler. The reserved domain example.com, the DNS records, and 203.0.113.10 serve as examples. The final HTTP routing demo runs locally. [[reserved|Example domains]]

1. URL structure

1.1 Host and resource

A URL (Uniform Resource Locator) describes a resource's location and how to access it. A typical HTTP or HTTPS URL has this structure; square brackets mark optional parts:

scheme://hostname[:port]/path[?query][#fragment]

https://dev.example.com:443/guide/start.html?lang=zh#install
PartExample valuePurpose
schemehttpsSelects the access protocol. HTTPS uses an encrypted connection.
hostnamedev.example.comIdentifies the requested host; here, a domain name to resolve.
port443Selects the service port. HTTPS defaults to 443 and HTTP to 80; the default may be omitted.
path/guide/start.htmlIdentifies a resource, interpreted by the web server or application.
querylang=zhCarries query information in the request. Applications assign meaning to it; key=value is a common convention.
fragmentinstallUsually identifies a location within a page. The browser handles it; the HTTP request target excludes it.

In ://, the colon ends the scheme and the two slashes introduce the authority: the hostname and port in this example. An IP address can occupy the host field, as in http://127.0.0.1:8000/. IPv6 addresses require brackets: http://[::1]:8000/. [[uri|Generic URL structure]]

Dots and slashes take their meaning from their position. Dots in dev.example.com separate domain labels. The dot in start.html is a path character; the extension is a naming convention. Slashes separate path segments. A server can map those segments to files or pass them to a handler: /users/42 might generate a page from a database query.

1.2 Relative references

A page link may omit the hostname or even the entire path. The browser resolves it against a base URL. With https://example.com/guide/page.html as the base:

ReferenceResolved URL
./image.svghttps://example.com/guide/image.svg
../index.htmlhttps://example.com/index.html
/logo.svghttps://example.com/logo.svg
#installhttps://example.com/guide/page.html#install

As whole path segments, . means the current level and .. the parent level. A trailing slash also changes resolution: image.svg resolves to /image.svg under https://example.com/dev, but to /dev/image.svg under https://example.com/dev/. This base change can break images or scripts when an application moves to a new path. [[relative|Relative reference resolution]]

2. Domains and subdomains

2.1 The name hierarchy

DNS (Domain Name System) arranges names in a tree. A domain name becomes more specific from right to left: com is a top-level domain, example.com sits beneath it, and dev.example.com sits beneath example.com.

.                         root
└── com                   com.
    └── example           example.com.
        ├── www           www.example.com.
        └── dev           dev.example.com.
            └── api       api.dev.example.com.

Each component between dots is a label. dev is one label; dev.example.com is the complete subdomain name here. Every name in the tree is a domain name, and “subdomain” describes its relationship to an ancestor. The final dot represents the root and is usually omitted in everyday writing. [[terms|Domains, labels, and subdomains]]

“Hostname” describes a name's role in a URL; it need not identify one fixed physical machine. www, dev, and api are conventional labels. Their spelling does not cause DNS to create a website, development environment, or API service.

Name length and label count

Each DNS label can contain at most 63 bytes. An uncompressed name occupies at most 255 bytes, including each label's length byte and the final root label. With one-byte labels, 127 × (1 + 1) + 1 = 255, allowing at most 127 nonempty labels. Ordinary ASCII presentation allows up to 253 characters without the trailing root dot. Internationalized names must satisfy the limits after encoding; registration services can impose stricter naming rules. [[dns-size|DNS size limits]]

2.2 Registration and administration

Registering a domain gives its holder control beneath that name for the registration period. The holder can normally create names such as dev and api.dev beneath it without buying each one from the registrar. Address records and a configured web service make those names usable. Domain registration, DNS hosting, and the web server are separate services and can come from different providers. [[subdomains|Creating subdomain records]]

The tree also supports delegated administration. A DNS zone is a portion of the namespace managed together; its authoritative servers hold and answer for its records. An administrator can keep dev.example.com in the existing zone or add NS records assigning that name and its descendants to another set of authoritative servers. This assignment, called delegation, creates a zone boundary. Adding a label alone needs no additional server. [[delegation|Zones and delegation]]

3. DNS resolution

3.1 Names and records

A DNS query contains a name and a record type. To connect to dev.example.com, a browser can look up A or AAAA records for IPv4 or IPv6 addresses. DNS also stores aliases and delegation information:

TypeContentsExample
AAn IPv4 addressdev.example.com → 203.0.113.10
AAAAAn IPv6 addressdev.example.com → 2001:db8::10
CNAMEAnother domain name: the alias targetwww.example.com → example.com
NSAn authoritative name server for the zoneexample.com → ns1.example.net

An authoritative server holds and answers for a zone's records. A CNAME points to a domain name whose address the resolver continues to look up. Its target cannot be a full URL such as https://example.com/dev, and following it does not change the browser's address bar. [[records|Resource records]] · [[aaaa|AAAA records]]

Suppose an administrator creates these two A records. Both hostnames resolve to the same address. IN denotes the Internet class, and 300 is the TTL (Time to Live), allowing the records to be cached for 300 seconds:

example.com.      300  IN  A  203.0.113.10
dev.example.com.  300  IN  A  203.0.113.10

A name can also have several address records from which a client selects a connection target. Names and IP addresses therefore have a many-to-many relationship. These A / AAAA lookups use the hostname; /dev, query parameters, and fragments do not participate.

3.2 Recursive lookup and referrals

A client normally asks a recursive resolver to find the final answer. The lightweight component sending these requests from the operating system is called a stub resolver. A router, ISP, enterprise, or public DNS service may provide the recursive resolver.

Root and top-level domain servers are also authoritative servers, serving the root zone and a top-level domain zone respectively. The separate “authoritative server” in this example serves the example.com zone.

RoleOperators and examples
Root serversTwelve independent organizations operate the 13 root server identities, A–M. For example, Verisign operates A and J, the Internet Systems Consortium (ISC) operates F, and ICANN operates L. Each identity can be served by instances at multiple locations. [[root-operators|Full operator list]]
Top-level domain serversThe corresponding top-level domain registry is responsible. For example, [[tld-com|Verisign]] manages .com, and the [[tld-cn|China Internet Network Information Center (CNNIC)]] manages .cn.
A domain's authoritative serversThe domain holder or an authorized administrator maintains the zone's records. They can run the servers themselves or use a DNS hosting provider such as [[authoritative-hosting|Cloudflare DNS]].
Recursive resolversOperators include ISPs, enterprise or campus network administrators, and public DNS providers; individuals can also run their own. Google provides [[recursive-google|8.8.8.8]], and Cloudflare provides [[recursive-cloudflare|1.1.1.1]].

For example, a domain bought through registrar A can use the name servers assigned by Cloudflare. The registrar handles registration and renewal, Cloudflare operates the authoritative DNS service, and the domain administrator edits its records at Cloudflare. Visitors can still use Google or their ISP for recursive resolution; the two choices are independent. [[authoritative-hosting|Authoritative DNS hosting setup]]

Assume neither the client nor the recursive resolver has relevant cached records, the resolver knows how to reach root servers, and the example.com zone directly manages dev. The lookup follows the delegation chain:

{{dns-sequence}}

A root server supplies a referral to com servers. A com server supplies the delegation for example.com. An authoritative server for example.com then answers with the A record for dev.example.com. The recursive resolver returns the address to the client and caches reusable records. [[dns|Resolver algorithm]]

The resolver follows delegation boundaries. Even api.dev.example.com can be answered by the same authoritative servers if its records remain in the example.com zone. A lookup may also follow CNAME records or obtain missing name-server addresses.

3.3 Caches and resolver selection

A cache hit lets the client or resolver reuse an answer and skip some or all upstream queries. After an authoritative record changes, existing cached copies normally update as their TTLs expire. “Name does not exist” answers can also be cached, so clients that previously queried a newly created name may temporarily keep receiving a negative answer. [[negative-cache|Negative caching]]

A browser can use DoH (DNS over HTTPS) to send encrypted queries directly to its configured resolver, choosing a different entry point from the operating system. VPNs, corporate networks, and application proxies can also affect resolver selection or where resolution happens. See VPN and application proxy routing for those traffic paths. [[doh|DoH protocol]]

4. Multiple URLs, one page

4.1 Host and path routing

These URLs differ in both hostname and path:

URLHostnamePath
https://dev.example.com/dev.example.com/
https://example.com/devexample.com/dev

With the DNS configuration above, both connect to 203.0.113.10:443. The server can still distinguish their requests. In HTTP/1.1 notation:

GET / HTTP/1.1
Host: dev.example.com

GET /dev HTTP/1.1
Host: example.com

The Host field carries the requested host and, when needed, its port. HTTP/2 and HTTP/3 use the corresponding :authority pseudo-header. The server selects a site by hostname, then a resource or handler by path. Configuring several sites on the same listening address is called virtual hosting. [[host|Host and authority]] · [[nginx|Request dispatch]]

{{mapping-diagram}}

Both routes call development_page(), returning the same page. DNS resolves the names to the service's IP address, and HTTP routing selects this function. Different routing rules can send names sharing an IP to entirely different websites.

4.2 Internal routing and redirects

Several mechanisms can deliver identical page content, with different effects on the browser:

MechanismServer behaviorBrowser address
Internal routingTwo host-and-path pairs select the same handler or file and return 200 directly.Each URL remains visible.
Reverse proxyA front server forwards both requests to one backend, optionally rewriting the host and path.Internal forwarding alone preserves the original URL.
HTTP redirectThe server returns a status such as 301, 302, 307, or 308 with a destination in Location.Following it changes the URL and issues another request.

A reverse proxy keeps the backend request between servers; see [[proxy|proxy_pass]] for configuration. A redirect asks the browser to visit another address. Sites commonly use permanent redirects to consolidate entry points during migrations. A DNS CNAME changes name resolution; an HTTP redirect supplies a new URL to the browser. [[redirect|Redirection status codes]]

4.3 HTTPS and origins

HTTPS establishes a TLS (Transport Layer Security) connection before sending the HTTP request. The client normally supplies the hostname through SNI (Server Name Indication), allowing the server to select a certificate. That certificate must cover the requested name. Two HTTPS sites sharing an IP must each satisfy certificate validation. [[sni|TLS server name indication]]

For HTTP(S), a browser identifies an origin by scheme, hostname, and effective port. Thus https://dev.example.com/ and https://example.com/dev have different origins even when their content and server match. https://example.com/ and https://example.com/dev share an origin. Browser rules still govern cross-origin script and storage access. [[origin|Origin definition]]

5. Local routing demo

5.1 Two entry points

Download route_demo.py and run it with Python 3.8 or later. It serves HTTP on the loopback address. The routing table has two entries:

{{route-code}}

The server extracts the hostname from Host and the path from the request target, then uses the pair to look up ROUTES. Both entries reference the same function. This demo leaves query parameters out of routing. Start it with the following command; Ctrl-C stops it:

python3 route_demo.py --port 8000

In another terminal, send two requests. --resolve connects the specified host and port to the loopback address for that curl invocation, preserving the original HTTP hostname. --noproxy '*' makes these local requests connect directly, bypassing proxies configured in the environment. [[curl|curl address overrides]]

curl --noproxy '*' --resolve dev.example.com:8000:127.0.0.1 \
  http://dev.example.com:8000/

curl --noproxy '*' --resolve example.com:8000:127.0.0.1 \
  http://example.com:8000/dev

Both requests return 200 with byte-for-byte identical bodies:

<!doctype html><title>Development</title><h1>Shared development page</h1>

Verified locally with Python 3.11 and curl. --resolve overrides resolution only for that invocation, leaving system DNS unchanged; it does not make the example addresses resolve in a browser.

5.2 A redirect entry point

The script also redirects example.com/redirect-dev. The -I option sends a HEAD request to inspect response headers:

curl --noproxy '*' --resolve example.com:8000:127.0.0.1 \
  -I http://example.com:8000/redirect-dev
HTTP/1.1 302 Found
Location: http://dev.example.com:8000/
Content-Length: 0

Only the redirect-related headers are shown. curl stops at this response by default. Adding -L and a resolution override for the destination makes it follow Location and request the shared page:

curl --noproxy '*' \
  --resolve example.com:8000:127.0.0.1 \
  --resolve dev.example.com:8000:127.0.0.1 \
  -L http://example.com:8000/redirect-dev

The server log records a 302 for GET /redirect-dev, followed by a 200 for GET /. The internal mapping needed one request; this redirect needs a second request to retrieve the same page.
