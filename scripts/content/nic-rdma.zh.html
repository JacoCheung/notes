网卡与 RDMA：从 socket 到 verbs

DMA 技术允许网卡直接访问 host 内存，但是普通的 TCP socket 模式仍然需要 CPU 参与大量工作，比如处理协议、管理缓冲区（用户态和内核态数据搬运）。而 RDMA 则减少了 CPU 的参与：直接注册用户态内存 buffer、建立访问权限后，应用可以在用户态提交读写请求，由网卡直接访问对端指定的内存。

本文以 4 KiB 跨节点传输为例，对照 TCP socket 与 RDMA Write 的数据路径，结合 mlx5 源码解释描述符、doorbell 和完成队列的协作。重点分析用户态库与内核驱动的分工：如何通过设备文件建立资源与访问权限，如何在用户态提交请求，以及应用如何确认传输完成。

源码基线：Linux 6.12、rdma-core 61.0，核对日期 2026-11-10；send 封装采用 glibc 2.40。链接固定到 tag 或 commit，按节汇总在源码索引中。RDMA Write 序列图按源码调用顺序绘制，activation bar 标示参与者的逻辑活动范围。

1. 网卡与内存

以 PCIe 网卡为例，CPU 与网卡通过两类地址交互。网卡的 BAR（Base Address Register）描述设备的地址窗口；驱动映射其中的寄存器区域后，CPU 的 load / store 就能发起 MMIO（Memory-Mapped I/O，内存映射 I/O）访问。网卡访问主机内存则使用 DMA（Direct Memory Access，直接内存访问），由驱动通过 Linux DMA API 建立映射。IOMMU 位于主机的 I/O 子系统中。启用地址翻译时，网卡用 I/O 虚拟地址（IOVA）发起 DMA 请求；请求经 PCIe 到达主机后，IOMMU 将 IOVA 转换为主机物理地址，并检查访问权限。[[dma-api|DMA 地址与映射]] · [[vtd-arch|主机侧 DMA 重映射]]

CPU 把“源数据起始地址和字节数”写到描述符，放进内存中的环形队列；网卡读取描述符后执行传输。在 mlx5 的常规发送路径中，一次请求经过以下四步：

步骤执行者动作
① 写描述符CPU在发送队列 SQ 的环中写一个 WQE（Work Queue Element），记录操作类型、buffer 地址和长度。
② 敲 doorbellCPU先在内存中的 DBR（Doorbell Record）记下新的生产者序号，再写 BAR 中 UAR（User Access Region）页上的 doorbell 寄存器。后者是一次 MMIO 写，经 PCIe 到达网卡。
③ 执行网卡DMA 读取 WQE 及其指向的数据，按协议发往网络。
④ 完成网卡按完成配置将 CQE（Completion Queue Entry）DMA 写入完成队列 CQ，按配置触发中断，或等待软件轮询。

软件负责 ①②，网卡负责 ③④。socket 和 RDMA verbs 都使用这类队列机制：第 2 节的 socket 路径由内核以太网驱动提交工作，第 3 节的 verbs 路径由用户态驱动 libmlx5 提交。两者共用网卡，但请求提交放在不同的执行位置。

2. TCP socket 路径

A 通过一条已建立的 IPv4 TCP 连接把 4 KiB 发给 B。这里采用普通的拷贝式 send() / recv()，并取两次调用都完整处理 4096 字节的情况。send() 声明在 <sys/socket.h>，应用先调用 C 库封装，再进入内核。以 Linux x86-64 和 glibc 2.40 为例，发送路径如下：

用户态
  send(fd, buf, 4096, 0)                    # 应用调用 socket 发送接口
    → __libc_send()                         # glibc 的封装
    → sendto(fd, buf, 4096, 0, NULL, 0)      # 选择 sendto 系统调用
                ↓ syscall：进入内核态

内核态
  __sys_sendto()
    → sockfd_lookup_light(fd, ...)          # 根据 fd 查找 socket
    → __sock_sendmsg()
    → sock_sendmsg_nosec()                  # 分派到 socket 的 sendmsg 操作
    → inet_sendmsg()                        # 本例为 IPv4 socket
    → tcp_sendmsg()                         # 按 socket 的协议选择 TCP
    → tcp_sendmsg_locked()                  # 把 4 KiB 拷进 skb 的页
    → tcp_write_xmit() … dev_queue_xmit()   # TCP/IP 发送路径，交给网卡驱动
    → mlx5e_xmit()                          # DMA 映射数据页，在 SQ 环写 WQE  ①
    → mlx5e_notify_hw()                     # 写 DBR，再写 UAR doorbell      ②

网卡 A：DMA 读取数据，按以太网帧发出                                            ③

sendto 的目标地址参数为 NULL, 0，表示使用 socket 已关联的对端。内核根据 fd 找到 socket 后，经操作表选择 IPv4 和 TCP 的实现，再进入原有的协议栈与网卡驱动路径。[[glibc-send|glibc send 封装]] · [[send-syscall|x86-64 系统调用表]] · [[socket-send|内核 sendto 入口]] · [[socket-dispatch|socket 操作分派]] · [[inet-send|TCP / UDP 分派]] · [[tcp-send-entry|tcp_sendmsg]]

在这条 socket 路径中，B 的网卡先把数据写入驱动预先投递的接收 buffer。B 的 CPU 随后处理 TCP/IP 协议，应用通过 recv() 取得数据：

网卡 B：DMA 写入预先投递的接收 buffer，写 CQE，触发中断               ④
mlx5_eq_comp_int() → napi_schedule()       # 中断里只调度 NAPI
mlx5e_napi_poll() → mlx5e_poll_rx_cq()     # 软中断中读 CQE，构造 skb
  napi_gro_receive() … tcp_v4_rcv()        # TCP 处理，挂进 socket 接收队列
recv(fd, buf, 4096, 0)                     # 系统调用：拷贝到用户 buffer

这个例子中，两端各经过一次用户态与内核态之间的数据拷贝；CPU 还负责系统调用、协议处理和驱动队列管理。接收侧用中断唤起 NAPI，再批量处理完成队列。TCP 是字节流，实际程序要根据 send() 和 recv() 的返回值继续处理剩余字节，系统调用次数和中断次数都不与 4 KiB 一一对应。send(2) · recv(2)

拷贝式发送成功返回后，应用可以复用已被内核接收的那部分源 buffer；此时对端应用可能还没有读到数据。MSG_ZEROCOPY 则用页面固定和完成通知替代发送侧拷贝，源 buffer 要等通知后才能复用。Linux 文档给出的经验范围是约 10 KB 以上的写入才通常受益，因此这里的 4 KiB 例子仍采用拷贝路径。[[msg-zerocopy|MSG_ZEROCOPY]]

普通 socket 收发已经使用本机 DMA。RDMA 增加的是网卡可执行的远端内存操作：A 在请求中指定 B 的内存地址和访问 key，B 的网卡校验后直接写入该 buffer，省去本次数据交付中的接收端协议栈处理与用户态拷贝。[[rdma-guide|RDMA 操作]]

3. RDMA Write 路径

仍然传输同一块 4 KiB 数据，改用 RC（Reliable Connection，可靠连接）上的 RDMA Write。两端先注册内存、建立连接，A 再提交写请求。应用调用通用的 verbs API，由设备专用的用户态实现 provider 完成硬件操作；ConnectX 对应的 provider 是 libmlx5。表中 socket 一列用于比较各步骤的用途。

顺序verbs 调用得到什么socket 中的对应
1ibv_open_device()设备 context，内含打开 /dev/infiniband/uverbsN 得到的命令 fd。socket()
2ibv_alloc_pd()保护域 PD（Protection Domain）。QP 使用的本地 MR 属于同一 PD。无
3ibv_reg_mr()内存区域 MR（Memory Region）：固定 buffer 所在的页，为网卡建立地址翻译和访问权限，返回 lkey 与 rkey。本端提交请求时用 lkey；rkey 交给对端，用于远端访问校验。本例通过内核缓冲区拷贝数据
4ibv_create_cq()完成队列 CQ，即内存中的完成环。无
5ibv_create_qp()、ibv_modify_qp()RC 队列对 QP（Queue Pair），含发送队列 SQ 和接收队列 RQ。依次切换到 INIT、RTR、RTS，并填入对端的 QP 号、地址和起始包序号。connect() / accept()
6ibv_post_send()提交一个 RDMA Write WR（Work Request）。libmlx5 把它编码成 WQE 写进 SQ 环（①），再敲 doorbell（②）。send()
7ibv_poll_cq()检查 CQE 为成功状态后，确认请求完成并复用源 buffer。send() 返回
—无本次普通 RDMA Write 无需 B 投递接收请求。B 的 recv()

1–5 属于资源建立的控制路径，需要内核参与；建好的 MR、QP 和 CQ 可以供后续多次传输复用。6–7 是 mlx5 的数据路径，在用户态写队列、敲 doorbell 和轮询完成。双方还需交换 QP 连接参数，B 则把目标地址和 rkey 交给 A。应用可以使用 TCP 交换这些信息，也可以用 rdma_cm 建立连接，再通过应用协议交换内存信息。[[rdma-cm|连接管理]]

旁注：其他 verbs 操作

RDMA Read 把传输方向反过来：A 提交带有 B 地址和 rkey 的读请求，B 的网卡取回数据，A 等待本端读取完成。B 的 CPU 无需逐次处理读请求。Send/Recv 则要求接收方先用 ibv_post_recv() 投递 buffer；Send 到达后填入 buffer，并产生接收侧 CQE。RDMA Write with immediate 也会消耗接收请求并产生接收侧 CQE，但 payload 仍写入发送方指定的远端地址。

基本的 fetch-and-add 与 compare-and-swap 对远端 8 字节对象执行原子操作。UD（Unreliable Datagram）是无连接传输，支持 Send/Recv，单条消息受路径 MTU 限制。InfiniBand 与 RoCE 共用 verbs 编程模型；RoCE v2 将 InfiniBand 传输层封装在 UDP/IP 中，经以太网传输。[[rdma-guide|操作与传输模式]]

4. 驱动与设备文件

send() 和 ibv_post_send() 都是应用在用户态调用的函数。两者的区别在于何时进入内核，以及把哪些工作交给内核。普通 TCP socket 将逐次发送交给协议栈；mlx5 的用户态 RDMA verbs 先经内核建立资源，再直接操作获准访问的队列与寄存器。

提交数据send() 经系统调用，把数据交给内核 TCP/IP 协议栈。ibv_post_send() 调用 provider，直接写已映射的队列和 doorbell。
谁处理逐次传输内核协议栈、网卡驱动和网卡共同处理。provider 提交描述符，网卡执行 RDMA 操作。

socket fd 表示通信端点，由 socket() 创建并装入进程的 fd 表。发送数据时，内核协议栈通过 net_device_ops.ndo_start_xmit 调用网络驱动；mlx5e 将这个回调设为 mlx5e_xmit()。这条内核调用路径直接到达驱动，无需再打开网卡的设备文件。[[socket-create|socket 创建]] · [[socket-fd|fd 分配]] · [[netdev-send|网络驱动分派]] · [[mlx5e-netdev|mlx5e 回调]]

控制路径

创建 QP、CQ 和注册 MR 涉及设备资源、内存固定和访问权限，由内核检查并建立。ibv_create_qp() 的路径把用户态队列内存与网卡的 QP 资源关联起来：

ibv_create_qp()                 # libmlx5 的 create_qp()
  mlx5_alloc_qp_buf()           # 在进程内存中分配 SQ / RQ 环
  mlx5_alloc_dbrec()            # 分配 DBR
  ioctl / write(cmd_fd)         # 系统调用：/dev/infiniband/uverbsN
    ib_uverbs → ib_core         # 解析命令，检查对象与权限
      mlx5_ib_create_qp()       # mlx5_ib.ko
        ib_umem_get()           # 固定环所在的页，供网卡 DMA
        mlx5_ib_db_map_user()   # 固定 DBR 所在的页
        mlx5_qpc_create_qp()    # 组装 CREATE_QP 固件命令
          mlx5_cmd_exec()       # mlx5_core.ko 的命令通道

网卡要读的环和 DBR 都在进程内存中，由 libmlx5 分配；内核固定这些页，再通过固件命令把它们的地址交给网卡。[[mlx5-create-qp|libmlx5 传入的地址]] · [[mlx5-ib-qp|mlx5_ib 的固定与命令]] 设备文件本身的机制（open 取得 fd，ioctl 经驱动的文件操作表分派，mmap 建立映射）见 CUDA Internals 系列《CUDA 分层与 Linux 驱动》的设备文件一节。

第 798 行在释放锁之前刷新写合并缓冲，保证这一轮寄存器写入先于下一个线程的提交；第 799 行切换 BlueFlame buffer 的半区，供下一次 doorbell 使用。锁和屏障共同维护了多个提交者之间的顺序。

ibv_poll_cq() 同样停留在用户态：provider 按所有权位判断 CQ 环中的下一条 CQE 是否已由网卡写好，读出后把消费者序号写回 CQ 的 DBR。[[mlx5-cq|mlx5_poll_cq]]

bf->reg 指向 UAR 在当前进程中的映射。libmlx5 通过命令 fd 分配 UAR，再调用 mmap()；mlx5_ib 用 rdma_user_mmap_io() 映射对应的 BAR 页，BlueFlame 页采用写合并属性，doorbell-only 页采用非缓存属性。映射建立后，CPU 可用 MMIO 写指令通知网卡，无需为每次 doorbell 再执行系统调用。[[uar-provider|libmlx5 的分配与映射]] · [[mlx5-ib-mmap|mlx5_ib 的 mmap]]
