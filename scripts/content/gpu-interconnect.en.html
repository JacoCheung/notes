GPU interconnect software and drivers

A NIC takes its work from descriptor rings in memory and learns about new work through a doorbell register. This post follows one example, sending 4 KiB to another node, through sockets, RDMA verbs, GPUDirect RDMA, and the backends of NCCL, NVSHMEM and NCCL GIN. Each step changes one thing: where the payload lives, who writes the descriptor, or who rings the doorbell. Even when the CPU submits the request, GPUDirect RDMA can move the payload directly between GPU memory and the NIC.

Source baseline: Linux 6.12, rdma-core 61.0, NCCL 2.32.3 and NVSHMEM 3.8.0, checked on 2026-11-10. The source index lists the versions of the other components. Source links are pinned to tags or commits. Sequence diagrams show source-level call order; activation bars mark each participant's logical activity scope.

1. NICs and RDMA

This chapter leaves GPUs out and covers the NIC mechanisms the rest of the post relies on: descriptor rings and doorbells, the socket path, RDMA verbs and the mlx5 drivers. Readers who know verbs can skip to chapter 2.

1.1 The NIC as a PCIe device

A NIC exposes device registers through addresses in a PCIe BAR (Base Address Register). An ordinary CPU load or store to those addresses is an MMIO (memory-mapped I/O) access that travels over PCIe to the NIC. In the other direction, the NIC's DMA engine reads and writes host memory itself, at addresses the driver obtains from the Linux DMA API; with an IOMMU enabled, the IOMMU translates them as well. [[dma-api|DMA addresses and mappings]]

The driver and the NIC hand over work through descriptor rings in memory: each descriptor names an operation, a buffer address and a length, and the NIC reads the descriptors in order. An mlx5 NIC sends data in four steps:

StepPerformed byAction
① Write the descriptorCPUWrite a WQE (Work Queue Element) into the send queue (SQ) ring, recording the operation, buffer address and length.
② Ring the doorbellCPURecord the new producer index in the DBR (Doorbell Record) in memory, then write the doorbell register on a UAR (User Access Region) page in the BAR, an MMIO write that reaches the NIC over PCIe.
③ ExecuteNICDMA-read the WQE and the data it points to, then transmit the data.
④ CompleteNICDMA-write a CQE (Completion Queue Entry) into the completion queue (CQ) ring, then raise an interrupt or wait for software to poll, as configured.

Software performs ① and ②; the NIC performs ③ and ④. The Ethernet driver and RDMA use the same structure and differ in who performs ① and ②. The rest of the post changes that executor one level at a time:

LevelWho writes the WQE (①)Who rings the doorbell (②)Section
1The Ethernet driver in the kernelSame1.2
2The user-space provider libmlx5Same1.3, 1.4; chapter 2 moves the buffers into GPU memory
3A CPU proxy calling verbs on the GPU's behalfSameChapter 3

The NIC always performs ③ and ④. What changes is which memory ③ accesses and who observes the completion that ④ writes; chapter 6 collects the completion rules.

1.2 Socket baseline: the kernel writes the descriptor

A sends 4 KiB to B over TCP. The sender starts with a system call:

send(fd, buf, 4096, 0)                 # system call into the kernel
  tcp_sendmsg_locked()                 # copy 4 KiB into skb pages (kernel buffer)
  tcp_write_xmit() … dev_queue_xmit()  # add TCP/IP headers, hand off to the driver
    mlx5e_xmit()                       # DMA-map the data pages, write a WQE   ①
      mlx5e_notify_hw()                # write the DBR, then the UAR doorbell  ②
NIC A: DMA-read the data and send it as Ethernet frames                     ③

B's NIC does not know which user buffer the 4 KiB belongs to. It writes the data into receive buffers the driver posted in advance and leaves the rest to B's CPU:

NIC B: DMA-write into a posted receive buffer, write a CQE, interrupt  ④
mlx5_eq_comp_int() → napi_schedule()       # the interrupt only schedules NAPI
mlx5e_napi_poll() → mlx5e_poll_rx_cq()     # softirq: read CQEs, build skbs
  napi_gro_receive() … tcp_v4_rcv()        # TCP processing, socket receive queue
recv(fd, buf, 4096, 0)                     # system call: copy to the user buffer

Here the mlx5e Ethernet driver in the kernel performs ① and ②: level 1. A transfer therefore costs a system call and a 4 KiB copy on each side, protocol processing on both CPUs, and an interrupt on the receiver. The copy is hard to remove: the Linux documentation notes that MSG_ZEROCOPY trades the per-byte copy for page-pinning and completion-notification overhead and is generally only effective for writes over about 10 KB, so a 4 KiB send usually gains nothing from it. [[msg-zerocopy|MSG_ZEROCOPY]] End-to-end latency depends on the CPU, the NIC and interrupt coalescing and must be measured on the target machine; this post quotes no figure.

Passing through a NIC does not make a transfer RDMA. Steps ③ and ④ above are DMA by the NIC as well, but the NIC only moves bytes between its descriptor rings and the network; B's CPU decides which user buffer the data finally reaches. RDMA hands remote memory operations to the NIC: the request carries the peer's address and an access key, and the peer's NIC validates them and writes directly into the destination memory.

Aside: other verbs operations

RDMA Read runs the other way: A sends B's address and rkey, and B's NIC returns the data without either CPU. UD (Unreliable Datagram) has no connection, supports only Send/Recv and limits each message to one MTU. RoCE and InfiniBand share verbs and transport semantics; RoCE v2 carries the InfiniBand transport in UDP/IP over Ethernet.

2. GPU memory as the RDMA buffer

Now make the buffers on both sides GPU memory from cudaMalloc() and keep everything else. A's CPU still calls ibv_post_send(), libmlx5 still performs ① and ②, and the level is still 2; only the target of the NIC's DMA changes. DMA, RDMA and GPUDirect RDMA each extend the previous mechanism:

MechanismPurposeTypical data path
DMAA device directly reads or writes local memory (section 1.2).Local NIC ↔ host memory
RDMA
Remote Direct Memory Access		A NIC executes remote-memory operations: a request specifies a remote address, length and access key, and the peer's NIC checks the registered range and permissions before transferring data (section 1.3).Host A memory ↔ NIC A ↔ network ↔ NIC B ↔ host B memory
GPUDirect RDMAGPU memory joins a third-party device's DMA path. For RDMA, the NIC directly accesses registered GPU buffers.GPU A memory ↔ NIC A ↔ network ↔ NIC B ↔ GPU B memory

With GPUDirect RDMA, A's NIC reads A's GPU memory directly over PCIe in ③, and B's NIC writes B's GPU memory in ⑥, without staging the payload in host memory. The NIC reaches GPU memory through addresses the GPU exposes in a PCIe BAR, just as it reaches host memory. [[gdr-doc|GPUDirect RDMA]] What changes is registration: ibv_reg_mr() must obtain NIC-usable DMA addresses for GPU memory.

2.1 Registering GPU memory

For a host-memory MR, the kernel pins user pages to obtain DMA addresses. No host pages back an address from cudaMalloc(), so that step fails; only the NVIDIA driver can supply DMA addresses for GPU memory and manage the mapping lifetime. The RDMA and NVIDIA drivers cooperate in one of two ways:

Registration pathHost operationKernel cooperation
Peer memoryCall ibv_reg_mr() directly on the GPU address.nvidia-peermem registers with the RDMA stack as a peer-memory client. When GPU memory is registered, it calls the NVIDIA driver's nvidia_p2p_get_pages_persistent() and nvidia_p2p_dma_map_pages() to obtain the pages and their DMA addresses. The peer-memory interface comes from MLNX_OFED and is absent from upstream kernels; without it, the module fails to load. [[peermem|nvidia-peermem.c]]
DMA-BUFExport the GPU memory as a DMA-BUF fd with cuMemGetHandleForAddressRange(), then call ibv_reg_dmabuf_mr().The NVIDIA driver is the exporter, and mlx5_ib imports through ib_umem_dmabuf_get(). This requires Linux 5.12 or later, the NVIDIA open kernel modules and CUDA 11.7 or later, but not nvidia-peermem. [[dmabuf|DMA-BUF requirements]]

After registration, the data path is the same as for host memory, and later chapters reuse both paths. NCCL NET/IB, IBGDA and GPUNetIO try DMA-BUF first and fall back to peer memory; NCCL GDAKI picks one by allocation type, driver and platform capabilities, and GIN buffers backed by multiple cuMem segments require DMA-BUF. [[nccl-reg|NET/IB choice]] · [[gdaki-reg|GDAKI registration]] · [[device-doc|GIN requirements]]

Zero-copy means the payload is not staged in host memory. Connection setup, address and key exchange, queue control and completion state remain on the CPU control path; nvidia-peermem or DMA-BUF only helps establish access, and the NIC moves the payload.

3. GPU requests, CPU submits

Through chapter 2, the CPU decides when to send. Now the GPU kernel sends the 4 KiB as soon as it has computed it. It cannot call ibv_post_send(): libmlx5 is a CPU library, and the QP's software state lives in the CPU process. The direct solution is for the GPU to write a request into CPU-readable memory and for a CPU proxy thread to perform the level-2 submission on its behalf; this is level 3.

Level 3 costs a relay per request: the GPU writes host memory, a polling CPU thread discovers the request, builds the WR, writes the WQE and rings the doorbell, and completion returns through a GPU-visible counter the CPU writes. Every request passes through this thread; chapter 4 lets the GPU write the WQE itself and leaves the CPU only ②.

4. The GPU writes the WQE; the CPU only rings the doorbell

A level-3 proxy builds a WR for every request, which libmlx5 encodes as a WQE. If the GPU writes mlx5 WQEs itself, the CPU keeps only ②. That requires an SQ ring in GPU memory that the GPU can write and the NIC can DMA-read, registered with the NIC like the payload in chapter 2, and a GPU that maintains the queue state and polls the CQ. Who performs ② depends on whether the GPU can map the UAR (chapter 5); when it cannot, the CPU rings the doorbell: level 4.

NVSHMEM IBGDA's CPU modes are the simplest case. The GPU still writes WQEs but touches neither the DBR nor the UAR; one system-scope atomicMax publishes the new producer index where the CPU can read it. NVSHMEM's proxy thread polls the index and, when it advances, writes the DBR, issues a release fence and writes the control segment into the UAR. In these modes the DBR is in host memory and only the CPU maps the UAR. [[ibgda-cpu-post|GPU publishes the index]] · [[ibgda-cpu-ring|CPU rings the doorbell]] NVSHMEM_IBGDA_NIC_HANDLER selects the mode:

GPUNetIO's CPU proxy mode splits the work the same way. The device function doca_gpu_dev_verbs_submit() writes neither the DBR nor the UAR in this mode; it applies fetch_max to a producer index in registered host memory, and doca_gpu_verbs_cpu_proxy_progress() on the CPU reads the index and writes the UAR and the DBR. NVSHMEM selects this mode with NVSHMEM_GPUNETIO_NIC_HANDLER=cpu and calls the function from its proxy thread. With auto, GPUNetIO probes whether the UAR can be registered for the GPU; an explicit gpu on an unsupported platform makes QP creation fail with no fallback. [[gpu-ring-proxy|Device-side publication]] · [[gpu-cpu-db|CPU proxy progress]]

NCCL GIN's GDAKI backend uses the GPUNetIO code bundled with NCCL, and its default AUTO setting runs the same probe. If the UAR cannot be mapped into the GPU, GDAKI switches to CPU proxy mode and NCCL starts a progress thread that calls the same doca_gpu_verbs_cpu_proxy_progress(). NCCL_GIN_GDAKI_NIC_HANDLER controls the choice; the pinned version's user documentation does not list it. [[gdaki-nic-handler|GDAKI NIC handler]]

Levels 3 and 4 both run a CPU thread, but it receives different things. A level-3 proxy gets a high-level request (target PE, addresses and length, or a GIN descriptor), builds the WR and lets libmlx5 write the WQE. At level 4 the CPU sees only a producer index for WQEs the GPU has already written, and performs only ②. The GPU also polls the CQ, so completion no longer passes through the CPU. Removing the last CPU step requires the GPU to write the UAR itself.

5. The GPU rings the doorbell itself

The last step hands ② to the GPU too. Section 1.4 showed that a CPU doorbell is one store to a UAR page. To do the same, the GPU needs a mapping of that UAR page in its page table and an MMIO store that becomes a PCIe write. With both, a kernel can initiate NIC operations directly; this is GDAKI (GPUDirect Async Kernel-Initiated).

5.1 Mapping the UAR into the GPU page table

Mapped requests a GPU mapping; IoMemory declares the range to be MMIO space of a third-party PCIe device, treated as non-cache-coherent and contiguous; Portable makes the registration valid for all CUDA contexts. cudaHostGetDevicePointer() returns the address for GPU access, which can differ numerically from the CPU pointer. [[uar-cuda-api|CUDA registration semantics]] NVSHMEM stores it in dev_qp->tx_wq.bf and configures the QP with the same UAR's page_id; GPUNetIO's doca_gpu_verbs_export_uar() performs the same registration and pointer lookup for device paths such as GDAKI. Once the GPU and QP have stopped using the UAR, call cudaHostUnregister(cpu_reg) before freeing the UAR. [[uar-qp|QP UAR configuration]] · [[uar-gpunetio|GPUNetIO export]]

Inside the driver, the open I/O memory import path checks the CPU VMA for VM_IO / VM_PFNMAP, obtains the UAR page's PFN through the CPU mapping, and creates a descriptor marked MEMDESC_FLAGS_PEER_IO_MEM. The descriptor uses the ADDR_SYSMEM address class and handles GPU-visible bus addresses and IOMMU mappings. [[uar-pfn|CPU mapping and PFNs]] · [[uar-osdesc|I/O memory descriptor]]

The P2P access in the fourth post of this series also maps another device into the GPU page table: the PTE selects the peer aperture, the target is another GPU's memory, and loads and stores travel over NVLink or PCIe. The UAR mapping's PTE selects the system non-coherent aperture with a target on an MMIO page in the NIC's BAR, so a store becomes a PCIe write to the NIC. CPU-side drivers create both mappings, and later GPU accesses need no CPU involvement.

The write carries doorbell control information; the NIC then moves the payload as the WQEs describe. The PTE's PCF sets the GPU-side cache attributes, while PTX memory ordering and MMIO semantics constrain instruction behavior. In practice NVSHMEM uses its own store / barrier helpers, and GPUNetIO chooses MMIO or another supported submission branch according to the toolchain and configuration. [[ibgda-db|NVSHMEM submission order]] When several threads write the same queue together, the submitting thread must also use the library's synchronization protocol to confirm that the others have finished; letting every thread ring the same doorbell introduces queue concurrency and ordering problems.

6. Completion and ordering

The five levels change who writes the WQE and who rings the doorbell. Applications ask two other questions: when can the source buffer be reused, and when can the receiver read the data? Section 1.3 left the second open: A's CQE reports only local completion, and B needs another signal. NVSHMEM and GIN build that signal into their interfaces. The table lists each scheme's completion conditions along the timeline:

PointEstablished conditionStill required
WQE constructed (by the CPU at levels 1–3, by the GPU at levels 4–5)The request descriptor is prepared.Update the DBR in order and ring the doorbell.
Doorbell submitted (rung by the CPU at level 4)The NIC receives or can observe notification of new work.DMA, network transactions and the relevant completion.
Sender CQE appears (polled by the CPU at levels 2–3, by the GPU at levels 4–5)The local request has completed, and the source buffer can be reused.The peer program learns of the arrival only through another notification.

NVSHMEM quiet returns (called by the issuing thread)Operations previously issued by the calling thread have completed.Receiver consumption; before reusing remote storage, confirm that the receiver has finished with it or use an iteration protocol.
GIN flush returns (called by the issuing cooperative group)Put source buffers issued by the group are safe to reuse.Remote data settlement and receiver consumption; use the appropriate signals.
Receiver's signal wait returns (the sender attaches the signal with putmem_signal_nbi / ncclGin_SignalInc; the receiver waits with signal_wait_until / waitSignal)The signal API's data-completion and ordering guarantees hold, and the waiter observes the data with acquire semantics.Actual receiver computation and coordination before the next overwrite.

Visibility is a separate issue: a running kernel need not observe NIC writes to GPU memory in order. The GPUDirect RDMA documentation states that only CPU-initiated CUDA APIs order GPUDirect writes as the GPU observes them; after a third-party device has issued all its PCIe transactions, a running kernel may still see stale or out-of-order data until a later CPU-initiated CUDA submission or synchronization. [[gdr-ordering|GPUDirect memory ordering]] NVSHMEM and GIN signal interfaces include data completion and ordering in their contracts, so applications only wait on the signal. A program that writes GPU memory with plain verbs for a running kernel to read must handle this itself.

A multi-threaded implementation must also identify the data-producing threads, the threads that call the communication interface, and the memory-ordering scope. In NVSHMEM, when several threads issue operations, make sure all of them have been issued before the calling thread runs quiet. Repeated execution needs iteration-aware signals and coordination before receiver buffers are reused. [[nv-ordering|NVSHMEM memory ordering]] · [[gin-api|GIN interface contracts]]
