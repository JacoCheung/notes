GPU interconnect software and drivers

GPU communication commonly takes one of two data paths: peer-memory access over NVLink / PCIe, or RDMA through a network adapter. CUDA drivers establish GPU mappings, Linux RDMA drivers establish NIC resources, and NCCL or NVSHMEM organize transfers using those resources. Following a block of data from GPU 0 to GPU 1 reveals the roles of CPU proxies, IBGDA, GPUNetIO Verbs and NCCL GIN.

Source baseline: NCCL 2.32.3, NVSHMEM 3.8.0 and rdma-core 61.0, checked on 2026-11-09. Source links are pinned to commits. Sequences illustrate source paths; activation bars show logical activity, not measured duration.

1. Path overview

1.1 API, submission and payload

Suppose GPU 0 has produced a block that GPU 1 needs. A transfer raises three separate questions: who invokes the communication operation, who submits requests to hardware, and where the payload travels. A CPU call to ncclAllReduce() answers only the first. A CPU proxy may submit NIC requests while payload moves directly between GPU memory and the NIC.

PathApplication APIRequest submissionMain payload path
CUDA peer accessCPU establishes mappings; GPU kernel loads/storesGPU executes memory instructionsGPU ↔ NVLink / PCIe ↔ GPU
Ordinary NCCL NET/IBCPU calls a collective APICPU proxy submits NIC WRsWith GDR: GPU ↔ NIC ↔ network ↔ NIC ↔ GPU
NVSHMEM device API + proxyGPU kernel calls put/getGPU writes a request queue; CPU proxy submits WRsCan use the same GPUDirect RDMA path
NVSHMEM IBGDAGPU kernel calls put/getGPU constructs WQEs; GPU or an assisting CPU rings the doorbellGPU ↔ NIC ↔ network ↔ NIC ↔ GPU
NVSHMEM GPUNetIOGPU kernel calls put/getGPU constructs WQEs; GPU or an assisting CPU rings the doorbellGPU ↔ NIC ↔ network ↔ NIC ↔ GPU
NCCL GIN + GDAKIGPU kernel calls ncclGinGPU constructs WQEs through GPUNetIO; doorbell mode depends on configurationGPU ↔ NIC ↔ network ↔ NIC ↔ GPU
NCCL GIN + CPU proxyGPU kernel calls ncclGinGPU publishes descriptors; CPU proxy submits network requestsDepends on the selected network backend

GPU-initiated networking still needs CPU initialization, connection exchange, memory registration and kernel launch. GDAKI (GPUDirect Async Kernel-Initiated) moves supported request-submission work into the GPU; GPUDirect RDMA provides the GPU-memory data path. These are related capabilities with different responsibilities. [[gpureadme|GPUNetIO CPU / GPU roles]] · [[nccl-proxy|NCCL proxy]] · [[nv-dispatch|NVSHMEM transport dispatch]]

2. NCCL CPU proxy

In the ordinary NCCL NET/IB path, a CPU proxy progresses network requests. libnccl.so organizes the collective; the proxy submits WRs through libibverbs and libmlx5. With GPUDirect RDMA enabled, the NIC transfers GPU buffers directly. Connection and memory setup precede the chunks that reuse those resources.

2.1 Connections and queues

For GPU buffers on two hosts, setup establishes which queue to use, which memory to access, and which permissions authorize access. The CPU organizes this information for subsequent CPU or GPU submission.

ObjectMeaningRole in a write
PDProtection DomainAssociates QPs and registered memory within an access-protection domain.
MR / lkey / rkeyMemory Region and local / remote access keysIdentify NIC-accessible memory, bounds and permissions. Peers exchange remote addresses and rkeys.
QPQueue PairHolds hardware work queues. Which queue is used depends on the operation.
WR / WQEWork Request / Work Queue ElementDescribe source, size, destination and key. A WR is a software request; a WQE is its hardware queue representation.
DoorbellNotification of queue progressLets the NIC discover work. Memory records such as DBRs have distinct roles from MMIO doorbells.
CQ / CQECompletion Queue / EntryReport requested completion notifications and errors. Batching or selective signaling need not produce one CQE per WQE.

An ordinary RDMA Write accesses a remote MR without a matching receive buffer for every write. Send/Recv and some operations with immediate data have different receive-resource and notification requirements. The communication library or application must also define when the receiver can consume the buffer.

2.2 GPU memory registration

A CUDA allocation supplies a GPU virtual address. The NIC still needs its own access authorization and DMA mappings. Registration establishes NIC resources and keys; a GPU peer mapping and a NIC MR are different objects.

Registration pathHost operationKernel cooperation
Peer memoryRegister a supported GPU allocation as an MR.The RDMA driver cooperates with the GPU driver through nvidia-peermem to manage pages and DMA mappings.
DMA-BUFExport the GPU buffer as a DMA-BUF fd, then register through an interface such as ibv_reg_dmabuf_mr().GPU exporter and RDMA importer cooperate through DMA-BUF. Supported configurations can operate without nvidia-peermem.

Zero-copy here means payload can avoid staging through CPU memory. Initialization messages, address/key exchange, queue control and completion state remain. nvidia-peermem enables access; it does not forward every payload byte through the kernel.

2.3 Submission and completion

When the CPU calls ncclAllReduce(), NCCL selects an algorithm and connections, and organizes GPU kernels and any required host work. One collective may combine local peer transfers with network transfers. This sequence isolates one outgoing chunk in the ordinary NET/IB transport, assuming GPUDirect RDMA is enabled for the connection. [[nccl-api|API entry]]

{{cpu}}

sendProxyProgress() checks GPU / FIFO progress, then calls the network plugin's isend when a chunk is ready. The internal IB implementation constructs verbs work when transmission can proceed and submits through ibv_post_send(). The mlx5 userspace provider writes the queue and notifies the NIC. The NIC DMA-reads GPU payload and transmits it to the peer. [[nccl-proxy|Ready / isend / test]] · [[nccl-isend|NET/IB send]] · [[mlx5-send|mlx5 provider]]

The proxy's test path polls completion and updates GPU-visible progress. The receiver also has recvProxyProgress() for receive requests, completion and any required visibility work. The sequence summarizes that side as a remote NIC / GPU; it does not imply an absence of receiver-side CPU participation.

2.4 Path selection

The CPU submits descriptors and control information, while GPU payload can use GDR. Unavailable GDR, socket backends or other transports change the data path. NCCL's plugin interface also allows other implementations, so ncclAllReduce() does not identify a fixed verbs call chain.

Newer NCCL host APIs can select kernels that use GIN. A CPU-initiated collective can therefore contain kernel-initiated networking. The CPU proxy path in this section is defined by its actual transport and execution method. Trace analysis should check the algorithm, transport, GDR registration and proxy activity together. [[nccl-sym-gin|GIN kernel option for host APIs]]

3. NVSHMEM CPU proxy

A GPU can initiate an NVSHMEM device operation and delegate network submission to a CPU proxy. This chapter follows a remote target using the PROXY device path and IBRC host transport. Directly accessible local peers can still use loads/stores. [[nv-dispatch|Device dispatch]] · [[nv-select|Transport selection]]

3.1 PEs and the symmetric heap

NVSHMEM provides one-sided operations: a caller names a target PE and puts/gets its symmetric memory. PEs establish corresponding objects through consistent collective allocation order. A symmetric address identifies the corresponding allocation and offset at another PE; it does not require the application to assume identical numerical virtual addresses in every process. [[nv-doc|NVSHMEM programming model]]

For GPU 0 → GPU 1, both PEs allocate dst and signal. PE 0 writes PE 1's dst and publishes an ordered signal. PE 1 waits for that signal before consuming the data.

put_signal_nbi associates payload with remote notification. quiet completes prior operations issued by the calling thread, and signal_wait_until expresses the receiver's dependency. Send completion does not mean the receiver has finished computation: reusing remote storage still needs an acknowledgement or an iteration protocol. With multiple issuing threads, order their operations before the thread that calls quiet. [[nv-ordering|Memory ordering]] · [[nv-signal|Signals]]

3.2 Requests and completion

libnvshmem_host.so establishes PEs, the symmetric heap and transports. IBRC creates connections and registers GPU memory through verbs/providers. Linux ib_uverbs / ib_core, mlx5_ib / mlx5_core and GPU registration interfaces prepare resources as described under GPU memory registration.

{{nvproxy}}

The kernel publishes a request identifying the PE, addresses and length. The CPU proxy consumes it, and IBRC builds RDMA WRs and calls ibv_post_send(). CPU progress observes CQ completion; GPU quiet and the receiver signal wait follow NVSHMEM completion contracts. The CPU constructs NIC requests while payload can move directly from GPU memory through the NIC. [[nv-proxy|IBRC submission]] · [[nv-proxy-cq|IBRC completion]]

4. NVSHMEM IBGDA

IBGDA is NVSHMEM's InfiniBand GPUDirect Async transport, including an implementation that directly manages mlx5 queues. Host code establishes resources and GPU-accessible NIC mappings. Device code writes WQEs, publishes queue progress and rings the doorbell. ibgda_post_send() contains ordering operations, DBR updates and ibgda_ring_db(). Supported mlx5 configurations can also use RoCE; the name does not restrict the physical network to InfiniBand. [[ibgda-host|Host mapping]] · [[ibgda-db|GPU submission]]

4.1 Resources and configuration

IBGDA host code uses verbs / mlx5 to create QPs, CQs and MRs, then prepares GPU-accessible queues and NIC mappings. GPU memory still needs supported registration through peer memory or DMA-BUF. Device submission additionally needs queue addresses, keys and state accessible to GPU code. [[ibgda-host|IBGDA host mapping]]

4.3 Doorbell mode

NVSHMEM_IBGDA_NIC_HANDLER=auto prefers GPU doorbells and falls back to the CPU when unsupported. Explicit choices include gpu, cpu and cpu_host_memory; the latter two use different CPU-accessible memory mechanisms. [[nv-env|NIC handler configuration]]

The sequence shows direct GPU doorbells. CPU-assisted mode adds host progress: the GPU prepares WQEs and publishes pending work, while the CPU performs doorbell work. Distinguish who writes the WQEs from who rings the doorbell when interpreting performance.

5. NVSHMEM GPUNetIO

NVSHMEM selects the GPUNETIO_GDAKI device transport for this path. NVSHMEM retains PE, symmetric-address and synchronization semantics; GPUNetIO supplies queue operations. It is an alternative to IBGDA, which manages mlx5 queues directly. [[nv-dispatch|Dispatch]] · [[nv-gpunetio|QP creation]]

5.1 Resource export

GPUNetIO Verbs packages GPU NIC-queue mechanisms behind common interfaces. CPU code creates QPs, CQs and MRs through verbs / mlx5 interfaces and exports GPU descriptors. CUDA code calls functions such as doca_gpu_dev_verbs_put() to construct and submit WQEs and observe completion. Both NCCL's GDAKI backend and NVSHMEM's GPUNetIO transport can use this machinery. {{nvgda}}

After resource export, the NVSHMEM device transport delegates put / signal to GPUNetIO. Device code constructs WQEs, submits the queue and observes CQEs; the NIC executes GPU-buffer DMA and network transfer. The receiving PE consumes data under the NVSHMEM signal protocol. 5.3 CPU-assisted doorbells

NVSHMEM_GPUNETIO_NIC_HANDLER supports auto, gpu and cpu. Auto prefers the GPU and falls back to the CPU when unsupported. [[nv-env|Configuration definitions]]

In CPU-assisted mode, the GPU can still construct WQEs and poll CQEs while a CPU performs the agreed doorbell progress. This differs from a GPU publishing a higher-level request that a CPU proxy translates into verbs WRs. [[gpu-cpu-db|CPU doorbell progress]] · [[gpu-submit|Device submission]] · [[gpu-cq|Device completion]]

The open GPUNetIO project focuses on one-sided RDMA GDAKI; the full DOCA SDK provides additional features. A doca_* function name does not require installing the full SDK: the open subset supports standalone builds and project integration. NCCL's bundled GPUNetIO revision may differ from the independent snapshot; follow each project's actual call sites.

6.1 Windows and resources

Both ranks establish corresponding src / dst windows with the same bytes, initialize src, then eventually synchronize the kernel and release the device communicator, windows and allocations. Explicitly requesting GDAKI makes creation fail when that backend is unavailable.

ginType can request a particular backend; its default allows an available backend. GIN has CPU proxy, GDAKI and other implementations. The ncclGin API name alone does not determine who submits NIC work. [[gin-reqs|Resource requirements]] · [[gin-select|Backend selection]]

NCCL GDAKI contains both DMA-BUF and GPU MR registration paths. Allocation type, driver and platform capabilities determine the choice. GIN buffers backed by multiple cuMem segments require DMA-BUF. [[gdaki-reg|Registration source]] · [[device-doc|GIN requirements]]

7. NCCL GIN / CPU proxy

GIN CPU proxy retains the ncclGin rank, window and signal interfaces. A GPU kernel publishes descriptors, and host progress translates them into network operations. This path uses the built-in IB RMA backend: CPU verbs submits WRs, while a GDR-enabled NIC directly accesses registered GPU buffers. [[gin-proxy|Descriptor processing]] · [[gin-verbs|IB submission]]

7.3 Interface and responsibilities

The same ncclGin kernel remains applicable. Local-source reuse after flush and receiver signal dependencies retain their contracts. Submission changes: GDAKI constructs NIC WQEs on the GPU; GIN CPU proxy publishes GIN descriptors on the GPU and constructs network requests on the CPU. GPUNetIO CPU-assisted doorbells have another division of work: the GPU has already constructed the WQEs.

Ordinary NCCL NET/IB CPU proxies progress collective-kernel chunks; GIN CPU proxies consume GIN operations from user kernels. Both can use CPU verbs and GPUDirect RDMA, with different upper-level protocols and progress objects.
