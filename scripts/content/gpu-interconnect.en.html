GPU interconnect software and drivers

Ordinary NCCL, NVSHMEM and NCCL GIN organize GPU communication through host-called collectives, one-sided operations on symmetric memory, and networking inside user kernels. NVSHMEM and GIN offer backend choices that determine whether CPU proxies or GPU code progress requests. Drivers establish their NIC queues, GPU memory registration and address mappings. Even with CPU-proxy submission, GPUDirect RDMA can carry payload directly between GPU memory and the NIC.

Source baseline: NCCL 2.32.3, NVSHMEM 3.8.0 and rdma-core 61.0, checked on 2026-11-09. Source links are pinned to commits. Sequence diagrams show source-level call order; activation bars mark each participant's logical activity scope.

1.2 DMA and RDMA

An ordinary Ethernet NIC can receive a packet and DMA-write its data into a receive buffer in local host memory. DMA (Direct Memory Access) lets a device read and write memory through mappings prepared by its driver. The device moves the data; the CPU prepares buffers, descriptors and mappings, and handles submission and completion. [[dma-api|Linux DMA addresses and mappings]]

MechanismPurposeTypical data path
DMAA device directly reads or writes locally accessible memory.Local NIC ↔ host memory
RDMA
Remote Direct Memory Access		A NIC executes remote-memory operations. RDMA Read/Write requests specify a remote address, length and access key; the NIC checks the registered range and permissions, then transfers data.Host A memory ↔ NIC A ↔ network ↔ NIC B ↔ host B memory
GPUDirect RDMAGPU memory becomes accessible through a third-party device's direct DMA path. In RDMA networking, a NIC can directly access registered GPU buffers.GPU A memory ↔ NIC A ↔ network ↔ NIC B ↔ GPU B memory

Passing through a NIC does not make a transfer RDMA. Ordinary TCP/IP traffic also uses local DMA. RDMA adds remote-memory operations, access protection and completion mechanisms understood by the NIC; the endpoints register memory and exchange the addresses and keys needed for remote access in advance. GPUDirect RDMA extends the accessible memory to GPU buffers. [[rdma-guide|RDMA operations]] · [[gdr-doc|GPUDirect RDMA]]

Memory and queue objects

An RDMA Read needs authorized memory access, a submitted request and a completion result. These steps use the following objects.

TermMeaning and role
MR · Memory RegionA memory range registered with an RDMA device, with address bounds, access permissions and mappings. It can cover host memory or supported GPU memory.
lkey / rkey
Local / remote access key		Access identifiers obtained during MR registration. The local buffer uses lkey; a peer receives rkey for remote-memory access checks.
PD · Protection DomainAssociates local resources such as QPs and MRs, restricting which queues can use which registered memory.
QP · Queue PairContains a send queue (SQ) and a receive queue (RQ). An initiator posts RDMA Read/Write operations to its SQ; the RQ holds receive requests that supply buffers for operations such as Send.
WR · Work RequestA software operation description, such as “read 4096 bytes from B into A.” It specifies the operation, local buffer, length, remote address and rkey.
WQE · Work Queue ElementA descriptor in the work queue, encoded in a format the NIC understands. A CPU verbs provider converts WRs into WQEs; a GPU submission path can construct them in device code.
DoorbellA mechanism that notifies the NIC of new work. The mlx5 path updates a DBR (Doorbell Record) in memory with queue progress, then writes a mapped MMIO doorbell to prompt WQE processing.
CQ / CQE
Completion Queue / Entry		A CQ holds completion records called CQEs, including success or error status. The sender can select which successful requests produce CQEs and retrieve their results from the CQ.

For a CPU verbs request with completion reporting enabled, the path is: build WR → provider writes WQE → ring doorbell → NIC executes → read CQE from CQ. The MR supplies the mappings and permissions for memory access. Reading a GPU buffer with RDMA

A reads 4 KiB from B's GPU memory into its own GPU memory. Both endpoints have established a reliable-connected (RC) queue pair, or QP, and registered their buffers as memory regions, or MRs. B grants remote-read access to its source MR and gives A the remote address and rkey. A's destination MR allows local writes. A submits a request containing B's address and rkey, plus its own destination address and lkey. These keys identify the remote and local memory-access resources. [[verbs-mr|MR permissions]] · [[verbs-post-send|RDMA Read request fields]]

{{rdma-read}}

A issues the request; data flows from B to A. Steps ③ and ⑤ are local DMA operations by the two NICs; steps ① and ④ carry the RDMA request and response across the network. B's NIC validates and reads through the registered MR. This example requests a completion notification: A receives a CQE in its completion queue, or CQ, when the read completes. Before GPU code consumes the destination, the communication library or CUDA interface must also establish memory visibility. 2. Ordinary NCCL

In the ordinary NCCL NET/IB path, a CPU proxy progresses network requests. libnccl.so organizes the collective; the proxy submits WRs through libibverbs and libmlx5. With GPUDirect RDMA enabled, the NIC transfers GPU buffers directly. Connection and memory setup precede the chunks that reuse those resources.

2.1 Connections and queues

Before a cross-host transfer, the CPU prepares queues, memory addresses and access permissions for both endpoints. CPU or GPU submission code then uses this information.

Each endpoint creates a PD, associates its QP and registered MRs with that domain, and assigns CQs to the QP. The endpoints exchange connection information and the MR addresses and rkeys needed for remote access. Section 1.2 defines these memory and queue objects.

An ordinary RDMA Write accesses a remote MR without a matching receive buffer for every write. Send/Recv and some operations with immediate data have different receive-resource and notification requirements. The communication library or application must also define when the receiver can consume the buffer.

2.2 GPU memory registration

A CUDA allocation supplies a GPU virtual address. NIC access to the same buffer requires authorization and DMA mappings. Registration establishes NIC resources and keys; GPU peer mappings and NIC MRs serve distinct access mechanisms.

Zero-copy means payload can avoid staging through CPU memory. Initialization messages, address/key exchange, queue control and completion state remain on the control path. nvidia-peermem helps establish access resources; hardware moves the payload.

2.4 Path selection

The CPU proxy submits descriptors and control information, while GPU payload can use GDR. Without GDR, or with a socket backend or another transport, the data path changes. The actual ncclAllReduce() call chain depends on the selected network plugin and its implementation.

The pinned NCCL version can also select GIN kernels through its host API: the CPU initiates a collective whose kernel initiates network requests. This chapter describes the ordinary NET/IB CPU proxy transport. Identifying a path in a trace requires checking the algorithm, transport, GDR registration and proxy activity together. 3. NVSHMEM

NVSHMEM expresses one-sided communication through PEs and symmetric memory. Applications use the same put/get and synchronization interfaces; the device transport chooses peer access, CPU proxy, IBGDA or GPUNetIO according to target reachability and configuration. The network backends below use the same application example. [[nv-dispatch|Device dispatch]] · [[nv-select|Transport selection]]

3.1 PEs and the symmetric heap

NVSHMEM provides one-sided communication: a caller specifies a target PE and puts/gets its symmetric memory. PEs establish corresponding objects through consistent collective allocation order. A symmetric address identifies the corresponding allocation and offset at a peer; numerical virtual addresses need not be identical across processes. [[nv-doc|NVSHMEM programming model]]

For GPU 0 → GPU 1, both PEs allocate dst and signal. PE 0 writes PE 1's dst and publishes an ordered signal. PE 1 waits for that signal before consuming the data.

The example uses two PEs, each bound to one GPU. dst and signal are symmetric allocations; signal starts at 0 and src is ready. Each PE executes one round with one block and one thread. nvshmemx_collective_launch launches the kernel containing cross-PE waits. The [[nv-example|official ring-bcast example]] provides initialization and collective-launch code.

put_signal_nbi associates data transfer with remote notification. quiet completes prior operations issued by the calling thread; the receiver uses signal_wait_until to wait for data. Reusing remote storage also requires confirmation that the receiver has finished consuming it, or an iteration protocol. With multiple issuing threads, ensure their operations have been issued before the thread that calls quiet. [[nv-ordering|Memory ordering]] · [[nv-signal|Signals]]

3.2 CPU proxy / IBRC

An NVSHMEM kernel can delegate network submission to a CPU proxy. The sequence uses the PROXY device path for a remote target and IBRC as the host transport. Directly accessible local peers can still use loads/stores. [[nv-dispatch|Device dispatch]] · [[nv-select|Transport selection]]

libnvshmem_host.so establishes PEs, the symmetric heap and transports. IBRC creates connections and registers GPU memory through verbs/providers. Linux ib_uverbs / ib_core, mlx5_ib / mlx5_core and GPU registration interfaces prepare resources as described under GPU memory registration.

{{nvproxy}}

The kernel publishes a request containing the PE, addresses and length. The CPU proxy consumes it; IBRC builds RDMA WRs and calls ibv_post_send(). CPU progress polls the CQ and updates completion state, while GPU quiet and the receiver's signal wait follow NVSHMEM completion semantics. The CPU constructs NIC requests while payload can move directly from GPU memory through the NIC. [[nv-proxy|IBRC submission]] · [[nv-proxy-cq|IBRC completion]]

3.3 IBGDA

IBGDA is NVSHMEM's InfiniBand GPUDirect Async transport and directly manages mlx5 queues. Host code establishes resources and GPU-accessible NIC mappings; device code writes WQEs, publishes queue progress and rings the doorbell. ibgda_post_send() contains ordering operations, DBR updates and calls to ibgda_ring_db(). Supported mlx5 configurations can use RoCE as well as InfiniBand. [[ibgda-host|Host mapping]] · [[ibgda-db|GPU submission]]

Resources and configuration

IBGDA host code uses verbs / mlx5 to create QPs, CQs and MRs, then prepares GPU-accessible queues and NIC mappings. GPU memory uses supported registration through peer memory or DMA-BUF; device code receives the addresses, keys and state needed for queue submission. [[ibgda-host|IBGDA host mapping]]

Doorbell mode

3.4 GPUNetIO

GPUNETIO_GDAKI is another NVSHMEM device transport. NVSHMEM supplies PE, symmetric-address and synchronization semantics; GPUNetIO supplies queue operations. It is an alternative to IBGDA's direct mlx5 queue implementation. [[nv-dispatch|Dispatch]] · [[nv-gpunetio|QP creation]]

3.5 UAR and GPU page tables

Both IBGDA and GPUNetIO require GPU access to NIC registers for direct doorbells. Their registration code illustrates the UAR mapping below. NCCL GIN / GDAKI uses the same mechanism through GPUNetIO.

A UAR (User Access Region) exposes NIC registers to an application, including doorbell / BlueFlame registers. For a GPU to ring a doorbell directly, its virtual address must map to that region of the NIC BAR. CPU initialization establishes the mapping; the GPU then issues an MMIO store through the mapped address. [[uar-man|UAR interface]]

Registering the address

mlx5dv_devx_alloc_uar() allocates a UAR. The provider allocates resources and calls mmap through a /dev/infiniband/uverbsN file descriptor. The returned uar->reg_addr is a CPU virtual address for doorbell access in that process. The NVIDIA driver can map the same I/O region into GPU address space. Interface and responsibilities

The application can use the same ncclGin kernel, retaining local-source reuse after flush and receiver signal dependencies. GDAKI constructs NIC WQEs on the GPU. GIN CPU proxy publishes GIN descriptors on the GPU, then builds and submits network requests on the CPU. GPUNetIO CPU-assisted doorbells delegate only notification to the CPU; the GPU has already built the WQEs.

Ordinary NCCL NET/IB CPU proxies progress collective-kernel chunks; GIN CPU proxies consume GIN operations from user kernels. Both can use CPU verbs and GPUDirect RDMA, with different upper-level protocols and progress objects.
