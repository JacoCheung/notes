2. 输入与请求标识

四个 rank 都持有表 A 和表 B 的一部分行，也各自收到一批查表请求。橙色格子属于 A，蓝色格子属于 B；格子里的 0–3 表示这次请求应交给哪个 owner rank。图中保留请求出现的顺序，用 来源 rank:特征:位置 标识每个格子，其中特征 0 是 A、1 是 B。

例如，0:0:1 表示 rank 0 的 A 特征中第二次请求。它的格子写着 1，因此要发送给 rank 1。多个请求可以具有相同的 owner；每次请求都保留自己的标识，移动后仍可逐一追踪。

{{inputs}}

初始布局按 feature 排列：每个 rank 的一个连续缓冲区先放 A，再放 B。四个 rank 分别有 9、11、10、10 次请求，总计 40 次。

TorchRec 用 KeyedJaggedTensor（KJT）保存这份输入。图中的一排实心格是 values，一个展平的一维张量；下方的描边小格是 lengths，记录每个样本在每个特征下有几个 key。本例中每个 rank 只带一个样本，所以每个特征占一个 lengths 元素，rank 0 是 [6, 3]。批大小为 B 时，每个特征占 B 个元素。

3. 按目标 rank 分桶

各 rank 在发送前扫描输入，把每次请求放到对应 owner 的桶中。桶之间按目标 rank 排列；每个桶内部先 A 后 B，同一特征的相对顺序保持不变。发往同一目标的数据由此组成连续分段。

{{send-rank0}}

rank 0 的四段 values 长度是 [4, 2, 1, 2]。例如发往 rank 1 的分段包含 A[1] 和 B[1]，它们在输入中相隔较远，分桶后被放在一起。

分桶同时重写 lengths：每个目标 rank 下每个特征一项，rank 0 得到 [3, 1, 1, 1, 1, 0, 1, 1]。发往 rank 2 的一段是 [1, 0]，即 1 个 A、0 个 B。values 中只有 ID，一段 key 里哪几个属于 A，全靠这两个数记录。把一段的 lengths 相加，就得到这段 values 的长度。

四个来源 rank 的 values 分段长度组成下面的矩阵。

{{counts}}

矩阵的一行是一个发送者的 send_splits，一列是一个接收者的 recv_splits，对应图中 splits 一行左边的方括号。右边的方括号是 lengths 的分段长度：发给每个目标 rank 的 lengths 段含 A、B 各一项，即特征数乘以批大小，本例为 2。它与数据无关，所以总是 [2 2 2 2]。

4. AllToAll 交换与接收端重排

AllToAll 将每个发送段交给对应目标。用列表表示分段时，这一步满足：

recv[dst][src] = send[src][dst]

接收端拿到的 values 是一串没有标签的 ID。要查表，它得知道两件事：哪一段来自哪个 rank，段内哪几个属于 A。TorchRec 为此做三次 AllToAll，先交换各段的长度，再分别传 lengths 和 values。

{{calls}}

第一次调用里，每个 rank 给每个 peer 发 3 个整数：将要发给它的 lengths 个数、values 个数和自己的批大小。这是固定批大小、无权重时的情形；开启 collective 校验时还会附一个标签。rank 0 读回后得到 values 的接收长度 [4, 2, 1, 3]，也就是矩阵第 0 列，共 10 次请求；另外三个 rank 分别接收 12、8、10 次。接收端按这些长度分配缓冲区，再把它们作为后两次调用的 output_split_sizes。后两次调用在读回这些长度之后相继发起。

来源 rank 由位置决定。all_to_all_single 按 rank 顺序拼接各来源的段：先是来源 rank 0 的 4 个 key，再是 rank 1 的 2 个，依此类推，所以布局变成 来源 rank → feature。每段的起始偏移由接收端累加段长得到，不随消息传输。

特征由 lengths 决定。rank 0 收到的 lengths 是 [3, 1, 1, 1, 0, 1, 2, 1]，每个来源两项。来源 rank 3 的一段有 3 个 key，对应 [2, 1]，所以前两个属于 A，最后一个属于 B。

{{recv-rank0}}

查表前，接收端再把同一特征的请求集中到一起。Recat 将布局改为 feature → 来源 rank：先取各来源的 A，再取各来源的 B。这一步是本地重排。

接收块：R0-A  R0-B  R1-A  R1-B  R2-A  R2-B  R3-A  R3-B
块序号：  0     1     2     3     4     5     6     7
重排后：R0-A  R1-A  R2-A  R3-A  R0-B  R1-B  R2-B  R3-B
块置换：[0, 2, 4, 6, 1, 3, 5, 7]

块的边界同样来自 lengths：第 k 块的长度就是它的第 k 项，rank 0 的 R2-A 块长度为 0。按块序展开，得到对接收缓冲区中 10 个元素的置换 [0, 1, 2, 4, 7, 8, 3, 5, 6, 9]，最终是 6 次 A 请求加 4 次 B 请求。lengths 按同一块序重排为 [3, 1, 0, 2, 1, 1, 1, 1]：前四项是来源 rank 0–3 的 A，后四项是它们的 B。重排后的 KJT 把四个来源的样本并成一个批，批大小为 4。批大小大于 1 时每块含多个 lengths 元素，见行分片文章中的 recat 说明。

{{lookup-rank0}}

请求 0:0:1 先进入 rank 0 的 dst 1 分段，经通信到达 rank 1 的 src 0 分段，重排后位于 rank 1 的 A 区域。沿这条路径，格子的颜色、owner 和请求标识保持一致。

6. DynamicEmb 的 hierarchical input dist

前面各节是 TorchRec 自带的 input dist。NVIDIA recsys-examples 里的 DynamicEmb 在 PR 528 中为 row-wise 分片的 EmbeddingCollection 换了一套实现，用 output_dist="hierarchical" 打开。节点内的 GPU 通过 NVLink 直接读写彼此的显存；节点之间由 GPU kernel 自己经 NCCL GIN 发 InfiniBand，中间不经过 CPU。本节用同一份 40 次请求演算它的 input dist。

例子的设定如下。4 个节点各有 1 张 GPU，所以 rank 就是节点。每个 rank 也是自己节点的 proxy，没有节点内转发这一段，凡是发给别的 rank 的 key 都跨节点。表 A 和表 B 属于同一个 lookup group。key 不带 weights。

输入已经是 unique 的。这个算子只接收 index dedup 之后的 key，所以图中最左边的 KJT 里，同一张表的同一个 key 在一个 rank 上只出现一次；每个节点只有一张 GPU，node dedup 也就不再合并任何 key。图里 KJT values 等行的实心格沿用前文的画法：格子里的数字标的是这个 key 的 owner rank，不是 key 的取值。同一个 rank 上数字相同的格子是不同的 key，只是 owner 相同。真实的 key 是 64 位的 embedding ID，owner 由它按分片规则算出。

{{hier-figure}}

动画分三步播放，图从左到右是一次调用里数据经过的位置，五列对应下面五件事。前两件在第一步里，第三、四件在第二步里，第五件是第三步。

  1. Bucketize。按 owner 做稳定的计数排序，只写两个数组：inv 记录分桶后的第 row 行是 KJT 里的第几个 key，bucket_feature_of_row 记录这一行的 owner × 特征数 + 特征。key 留在 KJT 原地不动。TorchRec 在这一步会另外生成一份按目标排好的 values 和 lengths，也就是第 3 节的 Send buffer。
  2. Push。node_key_push 按 inv 取出 key，直接写进 window 里的 node_keys。自己拥有的 key 进 own part，是一次本地写，图中画成虚线。发往其他节点的 key 进 remote part，经 node dedup 后按 owner 节点切成 key_stage 的三段，本例中每段是一个 16 字节的 chunk 头加若干条 8 字节的 key 记录。chunk 头的方括号里依次是 record_lo, record_hi | start, end：这段记录的范围，以及它们的 embedding 行将来在本 rank proxy_rows 里的位置。
  3. Count message。rail_exchange 给每个 rail peer 做一次 GIN put，并附带一个 signal。消息的头部对所有 peer 相同，尾部是发给该 peer 的每个特征的 key 数。它承担了 TorchRec 中 splits 和 lengths 两次 AllToAll 的作用：既给出每段的长度，也给出段内每个特征有几个 key。各 rank 读到同一批头部后，各自算出同一份 rail layout，owner 不需要把布局发回来。
  4. Key put。rail_key_push 对每个 owner 再做一次 GIN put，把 key_stage 中对应的一段写进对方 rail_keys 里 rail layout 给出的位置，即图中的 slice_in，同样附带 signal。owner 在 rail_done 里等齐所有 signal。
  5. Owner tables。owner_kjt_kernel 填出 owner 的 KJT：每个特征占 4 列，第一列是自己的 own part，其余三列是其他节点，按节点序排列。embedding 行在 lookup_rows 中保持到达顺序：先是 own part，再是各来源节点的记录。两种顺序不同，kernel 因此同时写出 row_map，记录 KJT 第 i 个 key 的行号。之后 lookup 把第 i 个 key 的行直接写到 row_map[i]，这些行已经是 output dist 要发送的顺序。

与 TorchRec 的流程相比，变化集中在三处。
