UVM managed memory 访存路径

Managed memory 让 CPU 和 GPU 使用同一个指针访问数据。同一指针背后的物理位置可以变化，UVM 负责维护各端映射，并记录页面的驻留位置与访问权限。访问可以直接使用现有映射；遇到缺页时，UVM 根据访问需求选择补充映射、调整权限或迁移数据，再恢复执行。

本文讨论显式 cudaMallocManaged() 分配的本地访问、远程映射与页面迁移。第 2、3 章追踪 Linux UVM 独立页表实现中的缺页迁移分支，源码固定为 NVIDIA open kernel modules 615.71.10 / 6f3be8c9c3fb。PTE 使用 Hopper／Blackwell UVM 的 VER3 格式；HMM、ATS 的函数调用与页表管理路径有所不同。[[release|源码版本]] · [[mmu-blackwell|Blackwell MMU]]

1. UVM 架构

1.1 软件与硬件

UVM（Unified Virtual Memory）是 CUDA Unified Memory 的驱动实现。应用通过 libcudart.so 调用 Runtime API，或直接使用 libcuda.so.1 的 Driver API。用户态驱动经 ioctl、mmap 等内核接口建立资源；Linux 上的 nvidia-uvm.ko 管理地址空间、页面驻留、缺页与迁移，并使用 nvidia.ko 提供的 RM 资源服务。[[driver-post|CUDA 软件与驱动分层]] · [[fops|UVM 内核接口]]

{{architecture}}

cudaMallocManaged(&p, bytes) 建立一段 managed 虚拟地址区间。在支持按需分页的配置下，调用返回时可能尚未分配全部物理页。UVM 的 managed mmap 路径安装 Linux VMA 回调，并创建类型为 UVM_VA_RANGE_TYPE_MANAGED 的地址区间记录。区间下的 VA block 保存各页的驻留位置、映射和权限。[[memory-api|分配语义]] · [[mmap|VMA 回调]] · [[range-create|区间创建]] · [[block-state|逐页状态]]

1.2 映射与页面迁移

UVA 提供统一的虚拟地址空间，UVM 管理地址背后的页面。访存能否完成，取决于当前映射、权限和目标内存的可达性。图中的 managed 页驻留主机，GPU 已建立远程映射：CPU 和 GPU 各自的页表都把 p 映射到主机页 H。只要映射有效且权限满足，GPU 就能经互联读取它。[[memory-api|AccessedBy 与主机页映射]]

{{page_tables}}

Grace Hopper：CPU 直接访问 GPU 驻留的 managed 页。 在支持主机直接访问且映射已建立的配置下，CPU 可以通过 NVLink-C2C 读写 Hopper HBM 中的数据。应用等待相关 GPU 工作完成后，CPU 可通过 float value = p[i] 解引用同一个 managed 指针，页面仍可驻留显存。远程读取经互联传输所需数据并填充 CPU 缓存，无需把整个页面迁回主机内存。[[grace-memory|Grace Hopper 内存互联]] · [[host-direct|Host 直接访问]]

应用通过 cudaDevAttrDirectManagedMemAccessFromHost 查询这项能力，并用面向 Host 的 cudaMemAdviseSetAccessedBy 给出访问建议。支持情况取决于驱动的内存管理模式：CDMM 文档列出的该属性为 0，实际配置应以运行时查询为准。这里的 p 来自 cudaMallocManaged()。Grace Hopper 的 ATS 还允许 GPU 使用 CPU 页表提供的翻译；上图展示的是两套独立页表的实现。[[host-direct|访问条件]] · [[cdmm|驱动模式]] · [[hardware-coherence|ATS 与页表]]

页面何时迁移、迁到哪里，由 UVM 结合访问需求、策略和平台能力决定。 缺页可以通过补充映射或调整权限解决；迁移也可以在没有缺页时发生。

触发条件可能采取的动作
缺页：当前映射不存在或不满足访问要求根据策略选择迁移、建立可用的远程映射，或调整访问权限
显式预取：调用 cudaMemPrefetchAsync按流顺序将数据迁往指定位置，提前准备后续访问，无需等待缺页
远程访问计数：GPU 频繁访问其他处理器的内存在支持并启用 access-counter migration 时，驱动可据此迁移热点页面
内存压力：例如显存容量不足将可迁移页面移到主机内存，腾出显存

[[residency-policy|缺页后的驻留选择]] · [[memory-api|预取与显存驱逐]] · [[access-counters|访问计数器迁移]]

访问建议会影响 UVM 对驻留位置与映射的选择：

策略设置方式对迁移与映射的影响
PreferredLocation：驻留偏好cudaMemAdviseSetPreferredLocation引导 UVM 选择驻留位置；设置时不立即迁移，也不阻止后续显式预取
AccessedBy：访问方cudaMemAdviseSetAccessedBy在可达条件下建立该处理器的映射；此建议本身不要求把数据搬到访问方
ReadMostly：以读为主cudaMemAdviseSetReadMostly在支持的配置中允许建立只读副本；写入时需使其他副本失效

这些建议通过 cudaMemAdvise() 传入。PreferredLocation 是策略属性，SetPreferredLocation 是设置它的建议值；查询到的偏好位置不等于页面当前实际位置。例如，主机驻留的 managed 页配合 CPU 驻留偏好和 GPU 的 AccessedBy，可以维持图中的远程映射。[[memory-api|cudaMemAdvise 与策略查询]]

1.3 TBE 的 UVM 权重

FBGEMM GPU 的 TBE（Table Batched Embedding）将 UVM 用于大型 embedding 表。采用 MANAGED_CACHING 时，完整权重可存于 managed memory，GPU 显存用于缓存常用行。[[tbe-placement|存储选项]]

在默认分配配置 enforce_hbm=False、uvm_host_mapped=False 下，底层调用 cudaMallocManaged()，并设置 SetPreferredLocation=CPU、SetAccessedBy=当前 GPU。这组策略让权重倾向驻留主机，GPU 通过已建立的远程映射访问它。[[tbe-allocation|分配路径]] · [[tbe-managed|Managed 分配]] · [[tbe-advice|访问建议]]

tbe.prefetch() 按本批次索引把所需行填入显存缓存 lxu_cache_weights。TBE 管理 embedding 行缓存，UVM 管理底层页面的映射与迁移；这里的缓存预取与 cudaMemPrefetchAsync() 请求的页面迁移属于两个层次。[[tbe-cache|缓存分配]] · [[tbe-prefetch|缓存预取]]

2. CPU 缺页迁移

2.1 异常入口

数据驻留在显存页 D、CPU 尚无可用映射时，应用等待相关 GPU 工作完成，再由 CPU 读取 p[i]。CPU MMU 因缺少映射而产生同步缺页异常。在 Linux UVM managed VMA 路径中，Linux 内存管理调用 VMA 的 fault 回调进入 UVM，处理发生在触发缺页的 CPU 线程上下文中。[[linux-fault|Linux 的 VMA 回调]] · [[cpu-fault|uvm_vm_fault]]

uvm_vm_fault() 调用 uvm_va_space_cpu_fault_managed()，后者根据进程地址空间与故障地址定位 managed VA block，再进入 uvm_va_block_cpu_fault()。UVM 检查访问权限、选择驻留位置，并通过 uvm_va_block_service_locked() 执行页面服务。[[cpu-dispatch|区间与 block 定位]] · [[cpu-block|CPU fault 服务]]

UVM 选择迁回主机时，会按下图处理。 支持 CPU 远程访问的平台也可以保留 D，建立或恢复 CPU 映射；已有可用映射时，CPU 直接完成访问。图中的函数调用属于独立页表实现，硬件一致性平台的 ATS／Linux MM 使用各自的处理路径。[[cpu-residency|CPU fault 的驻留选择]] · [[host-direct|主机远程访问]] · [[hardware-coherence|硬件一致性页表]]

{{cpu_fault}}

2.2 迁回主机与页表更新

显存页 D 迁回主机页 H 时，uvm_va_block_make_resident_copy() 先撤销待迁移页面的旧映射，再准备目标页、复制数据。uvm_va_block_service_finish() 随后更新驻留记录并建立需要的映射。[[resident-copy|迁移准备与复制]] · [[service-finish|完成页面服务]]

  1. GPU 页表：清除旧的 p → D 映射，并使相应 GPU TLB 翻译失效，防止继续使用旧位置。[[gpu-clear|清除 GPU PTE 与 TLB 维护]] 迁移完成后，UVM 根据访问策略与目标可达性，决定是否在 GPU 页表中补建指向新主机页的 p → H 映射。[[service-finish|迁移后的映射处理]]
  2. 复制与等待：把数据从 D 复制到 H。block_map_cpu_page_to() 在插入 CPU PTE 前调用 uvm_tracker_wait()，等待先前的数据复制和 GPU 页表更新完成。[[cpu-map-wait|CPU 映射前的等待]]
  3. CPU 页表：uvm_cpu_insert_page() 调用 Linux 的 vm_insert_page()，建立 p → H。缺页处理返回后，CPU 重试原来的访存指令。CPU 页表及相关 TLB 维护由 Linux MM 负责。[[cpu-insert|插入 CPU 映射]] · [[linux-tlb|Linux TLB 规则]]

CPU 首次访问尚无物理存储的 managed 页，也会进入 CPU fault 路径，但无需从显存复制旧数据。UVM 是否同时为 GPU 建立指向主机页的 p → H system-memory 映射，仍由访问策略决定。[[service-finish|其他处理器的映射策略]]

3. GPU 缺页迁移

3.1 故障记录与调度

CPU 已写好主机页 H，GPU 尚无可用映射时，kernel 执行普通 ld.global 会遇到缺页。TLB 未命中先触发页表遍历；只有地址翻译缺失或权限不足，才需要缺页处理。若已有权限满足的主机页映射，GPU 就能直接访问它。正常 load 的地址翻译由硬件完成，不调用 CPU 上的 UVM 区间查找函数。[[ptx|GPU load 指令]] · [[mmu-hopper|页表层级]]

GPU 将可重放故障写入 fault buffer，并通过中断通知主机。nvidia.ko 的 RM 中断路径调用 uvm_isr_top_half()；UVM 将工作排入 nv_kthread_q，由 replayable_faults_isr_bottom_half() 调用 uvm_parent_gpu_service_replayable_faults()。该内核线程批量读取、合并故障，再根据 GPU 上下文和地址找到 VA space、range 与 block。批量处理使故障数、中断数和迁移次数没有一一对应关系。[[irq-top|中断入口]] · [[irq-queue|工作队列]] · [[irq-bottom|线程回调]] · [[fault-range|故障分派]] · [[fault-batch|批处理循环]]

UVM 随后选择驻留位置与访问方式。选择迁入显存时，会按下图处理；若策略允许保留 H，则可以补建 GPU 的 p → H 映射后重放，省去迁移分支中的 H2D 复制与 CPU 映射撤销。[[gpu-residency|GPU fault 的驻留选择]] · [[residency-policy|策略与可达性判断]]

{{gpu_fault}}

3.2 迁入显存与重放

UVM 将 H 迁入本地显存页 D 时，会使用与 CPU fault 相同的 VA block 页面服务；两端建立映射和恢复执行的方式不同。[[block-service|共享页面服务]]

  1. CPU 页表：block_unmap_cpu() 调用 unmap_mapping_range()，由 Linux 撤销 p → H 并处理 CPU TLB 失效。其他需要撤销的 GPU 映射也在迁移准备阶段清除。[[cpu-unmap|撤销 CPU 映射]] · [[resident-copy|撤销旧映射]]
  2. GPU 页表：准备显存页并完成 H → D 复制后，uvm_va_block_map() 进入 GPU 映射路径。驱动构造指向 D 的 PTE，提交页表写入及 GPU TLB 维护，使新的 p → D 可供硬件使用。[[gpu-map|GPU 映射]] · [[gpu-write|PTE 构造、写入与失效]]
  3. 恢复访问：push_replay_on_gpu() 提交带有 tracker 依赖的 replay，确保相关 GPU 工作完成后才重放受影响的访问。CPU 不必在每一步同步等待。[[fault-replay|依赖与 replay]]

迁移后，CPU 再次访问是否缺页，取决于当时的映射。若平台支持并已建立对 D 的远程映射，CPU 可以直接访问显存；若缺少可用映射，则通过缺页处理选择补建映射或迁移。[[host-direct|CPU 远程访问]]

4. Managed 与 pinned

4.1 页锁定与访问目标

Mapped pinned memory 的物理页驻留在主机内存，OS／驱动在分配或注册的有效期内保持页面稳定，并为 GPU 建立可访问的映射。GPU 直接读取这些页时，事务经过主机互联；managed memory 则允许 UVM 改变同一虚拟地址背后的驻留位置。[[mapped|CUDA mapped host memory]] · [[pin-linux|Linux DMA pinning]]

维度Managed memoryMapped pinned host memory
典型接口cudaMallocManagedcudaHostAlloc（mapped）+ cudaHostGetDevicePointer
物理位置由 UVM 管理，可迁移至主机或 GPU保持在主机内存，供 GPU 直接访问
GPU 指令普通 load/store普通 load/store
GPU PTE 目标随映射选择 local、peer 或 system直接映射选择 system memory
软件状态managed 区间、驻留、映射与策略主机分配、注册与页面锁定状态

Pinned 页作为 cudaMemcpyAsync 的源缓冲区时，显式复制后的 kernel 读取另一块设备内存；表中比较的是 GPU 直接读取 mapped pinned 页的情况。

4.2 Hopper／Blackwell PTE

Hopper VER3 PTE 是 64 位硬件条目；所引用的 Blackwell UVM 实现继承了 Hopper 的 PTE 构造函数。Valid 表示有效性，Address 保存页地址，Aperture 指定 local／peer／system 目标，PCF 组合编码权限、缓存与访问计数器属性。[[pte|字段定义]] · [[pte-make|PTE 构造]] · [[mmu-blackwell|Blackwell HAL]]

{{pte}}

Aperture=10/11 区分 coherent／non-coherent system memory 的访问属性，涉及 CPU 缓存的一致性处理；它们都只说明当前映射指向系统内存。PCF 的解释还依赖 Valid，无效项采用另一组编码。[[coherent|System memory 一致性定义]] · [[pte-invalid|无效项编码]]

4.3 分配身份与 PTE

PTE 没有专门的 managed 位，也没有 host-pinned 位。 GPU 只需根据当前条目完成地址翻译与权限检查。Mapped pinned 页和仍驻留主机的 managed 页，都可能表现为 system-memory 映射；页锁定和 managed 身份分别保存在 OS／驱动的软件状态中。

Managed 区间即使尚无有效叶子 PTE，UVM 仍能通过“地址空间 + 故障地址”找到它的类型、策略与页面状态。缺页也可能发生在上级页目录，单靠叶子 PTE 无法覆盖这些情况。软件记录用于识别分配与处理缺页，硬件页表保存当前地址翻译，两者共同支持访问与恢复。这是对公开实现的分析；所引资料未说明“不设置 managed 位”的官方设计理由。[[range-type|Managed 类型]] · [[fault-space|地址空间识别]] · [[fault-range|故障地址查找]]

应用查询分配类型可用 cudaPointerGetAttributes()；返回 managed 类型表示分配身份，不表示该页当前驻留在主机还是 GPU。[[pointer|指针属性 API]]
