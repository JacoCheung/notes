GPU 互联的软件与驱动

网卡从内存中的描述符环读取工作，靠一个 doorbell 寄存器得知新工作到达。本文用一个例子贯穿全文：把 4 KiB 数据发往另一个节点。这个例子依次经过 socket、RDMA verbs、GPUDirect RDMA，以及 NCCL、NVSHMEM 和 NCCL GIN 的各个后端。每一步只改其中一件事：payload 放在哪里、谁写描述符，或者谁敲 doorbell。即使请求由 CPU 提交，payload 也能经 GPUDirect RDMA 直接在显存与网卡之间传输。

源码基线：Linux 6.12、rdma-core 61.0、NCCL 2.32.3、NVSHMEM 3.8.0，核对日期 2026-11-10；其他组件的版本见源码索引。链接固定到 tag 或 commit。序列图展示源码调用顺序，activation bar 标示参与者的逻辑活动范围。

1. 网卡与 RDMA

本章与 GPU 无关，只讲后文要用到的网卡机制：描述符环与 doorbell、socket 路径、RDMA verbs，以及 mlx5 驱动的分工。熟悉 verbs 的读者可以直接跳到第 2 章。

1.1 网卡是一台 PCIe 设备

网卡通过 PCIe 的 BAR（Base Address Register）暴露一段地址，这段地址对应设备寄存器。CPU 对这段地址执行普通的 load / store，就是一次 MMIO（memory-mapped I/O）访问，经 PCIe 到达网卡。反方向上，网卡的 DMA 引擎自己读写主机内存，使用的地址由驱动通过 Linux DMA API 取得；启用 IOMMU 时，这个地址还要经 IOMMU 翻译。[[dma-api|DMA 地址与映射]]

驱动和网卡通过内存中的描述符环（descriptor ring）交接工作：每个描述符写明操作、buffer 地址和长度，网卡按序号读取。mlx5 网卡发送一次数据分四步：

步骤执行者动作
① 写描述符CPU在发送队列 SQ 的环中写一个 WQE（Work Queue Element），记录操作类型、buffer 地址和长度。
② 敲 doorbellCPU先在内存中的 DBR（Doorbell Record）记下新的生产者序号，再写 BAR 中 UAR（User Access Region）页上的 doorbell 寄存器。后者是一次 MMIO 写，经 PCIe 到达网卡。
③ 执行网卡DMA 读取 WQE 及其指向的数据，按协议发往网络。
④ 完成网卡DMA 写一条 CQE（Completion Queue Entry）到完成队列 CQ 的环中，按配置触发中断，或等待软件轮询。

①② 是软件的工作，③④ 是网卡的工作。以太网驱动和 RDMA 使用同一套结构，区别在于 ①② 由谁执行。后文逐级改变这个执行者：

级别谁写 WQE（①）谁敲 doorbell（②）章节
1内核中的以太网驱动同左1.2
2用户态 provider libmlx5同左1.3、1.4；第 2 章把 buffer 换成显存
3代表 GPU 调用 verbs 的 CPU proxy同左第 3 章
4GPUCPU第 4 章
5GPUGPU第 5 章

③④ 始终由网卡执行。变化的是 ③ 读写哪块内存，以及谁来观察 ④ 写下的完成；后者在第 6 章汇总。

1.2 Socket 基线：内核写描述符

A 用 TCP 把 4 KiB 发给 B。发送端从一次系统调用开始：

send(fd, buf, 4096, 0)                 # 系统调用，进入内核
  tcp_sendmsg_locked()                 # 把 4 KiB 拷进 skb 的页（内核缓冲区）
  tcp_write_xmit() … dev_queue_xmit()  # 加 TCP/IP 头，交给网卡驱动
    mlx5e_xmit()                       # DMA 映射数据页，在 SQ 环写 WQE    ①
      mlx5e_notify_hw()                # 写 DBR，再写 UAR doorbell        ②
网卡 A：DMA 读取数据，切成以太网帧发出                                ③

B 的网卡不知道这 4 KiB 属于哪个用户 buffer，只能先写进驱动预先投递的接收 buffer，再交给 B 的 CPU：

网卡 B：DMA 写入预先投递的接收 buffer，写 CQE，触发中断               ④
mlx5_eq_comp_int() → napi_schedule()       # 中断里只调度 NAPI
mlx5e_napi_poll() → mlx5e_poll_rx_cq()     # 软中断中读 CQE，构造 skb
  napi_gro_receive() … tcp_v4_rcv()        # TCP 处理，挂进 socket 接收队列
recv(fd, buf, 4096, 0)                     # 系统调用：拷贝到用户 buffer

这里的 ①② 由内核中的 mlx5e 以太网驱动执行，即级别 1。一次传输因此要付出两端各一次系统调用、各一次 4 KiB 拷贝、两端 CPU 的协议处理，以及接收端的中断。拷贝不容易省掉：Linux 文档指出，MSG_ZEROCOPY 用页面固定和完成通知的开销代替逐字节拷贝，通常只对约 10 KB 以上的写入有效；4 KiB 的 send 用它通常得不到收益。[[msg-zerocopy|MSG_ZEROCOPY]] 整条路径的延迟取决于 CPU、网卡和中断合并配置，需要在目标机器上实测，本文不给固定数字。

“经过网卡”不等于 RDMA。上面的 ③④ 也是网卡执行的 DMA，但网卡只在描述符环与网络之间搬运字节，决定数据最终落到哪个用户 buffer 的是 B 的 CPU。RDMA 把远端内存操作交给网卡：请求带着对端地址和访问 key，由对端网卡校验后直接写进目标内存。

旁注：其他 verbs 操作

RDMA Read 方向相反：A 发出 B 的地址和 rkey，B 的网卡读出数据返回，两端 CPU 同样不参与。Send/Recv 是双边操作：接收方先用 ibv_post_recv() 投递接收 buffer，到达的 Send 填入其中，并在接收方产生 CQE；RDMA Write with immediate 也会消耗接收方的一个接收请求，并在那里产生 CQE。原子操作（fetch-and-add、compare-and-swap）由远端网卡对 8 字节远端内存执行。UD（Unreliable Datagram）不建立连接，只支持 Send/Recv，单条消息不超过一个 MTU。RoCE 与 InfiniBand 使用同一套 verbs 和传输语义；RoCE v2 把 InfiniBand 传输层封装在 UDP/IP 中，在以太网上传输。

2. 显存作为 RDMA buffer

把例子中两端的 buffer 换成 cudaMalloc() 分配的显存，其余不变：A 的 CPU 仍调用 ibv_post_send()，①② 仍由 libmlx5 执行，级别仍是 2。改变的只有网卡 DMA 的对象。DMA、RDMA 和 GPUDirect RDMA 是逐级扩展的三种机制：

机制解决的问题典型数据路径
DMA设备直接读写本机内存（1.2 节）。本机网卡 ↔ 主机内存
RDMA
Remote Direct Memory Access		网卡执行远端内存操作：请求指定远端地址、长度和访问 key，对端网卡检查注册范围与权限后传输数据（1.3 节）。A 主机内存 ↔ A 网卡 ↔ 网络 ↔ B 网卡 ↔ B 主机内存
GPUDirect RDMA把显存接入第三方设备的 DMA 路径；用于 RDMA 时，网卡直接访问已注册的显存。A 显存 ↔ A 网卡 ↔ 网络 ↔ B 网卡 ↔ B 显存

GPUDirect RDMA 下，A 的网卡在 ③ 中经 PCIe 直接读 A 的显存，B 的网卡在 ⑥ 中直接写 B 的显存，payload 不经主机内存中转。网卡访问的是 GPU 在 PCIe BAR 上暴露的地址，读写方式与访问主机内存相同。[[gdr-doc|GPUDirect RDMA]] 变化集中在注册：ibv_reg_mr() 必须为显存取得网卡可用的 DMA 地址。

2.1 显存注册

主机内存的 MR 由内核固定用户页，得到 DMA 地址。cudaMalloc() 返回的地址背后没有主机内存页，这一步走不通；显存的 DMA 地址只能由 NVIDIA 驱动提供，映射的生命周期也归它管理。RDMA 驱动与 NVIDIA 驱动有两种协作方式：

注册路径主机侧操作内核协作
Peer memory直接对显存地址调用 ibv_reg_mr()。nvidia-peermem 向 RDMA 栈注册为 peer-memory client；注册显存时，它调用 NVIDIA 驱动的 nvidia_p2p_get_pages_persistent() 和 nvidia_p2p_dma_map_pages()，取得显存页及其 DMA 地址。peer-memory 接口来自 MLNX_OFED，上游内核没有；缺少这个接口时，模块无法加载。[[peermem|nvidia-peermem.c]]
DMA-BUF用 cuMemGetHandleForAddressRange() 把显存导出为 DMA-BUF fd，再调用 ibv_reg_dmabuf_mr()。NVIDIA 驱动作为 exporter，mlx5_ib 经 ib_umem_dmabuf_get() 导入。需要 Linux 5.12 以上、NVIDIA 开源内核模块和 CUDA 11.7 以上，不需要 nvidia-peermem。[[dmabuf|DMA-BUF 支持条件]]

注册完成后，数据路径与主机内存完全相同。后面几章的后端都复用这两种注册方式：NCCL NET/IB、IBGDA 和 GPUNetIO 先尝试 DMA-BUF，不可用时回到 peer-memory 路径；NCCL GDAKI 按分配类型、驱动和平台能力在两条路径中选择，由多个 cuMem segment 组成的 GIN buffer 必须使用 DMA-BUF。[[nccl-reg|NET/IB 的选择]] · [[gdaki-reg|GDAKI 注册]] · [[device-doc|GIN 要求]]

“零拷贝”指 payload 不在主机内存中转。连接建立、地址与 key 的交换、队列控制和完成状态仍走 CPU 的控制路径；nvidia-peermem 或 DMA-BUF 只参与建立访问资源，payload 由网卡搬运。

3. GPU 发请求，CPU 提交

到第 2 章为止，发送时机由 CPU 决定。现在让 GPU kernel 算完 4 KiB 后立即发送。GPU 不能直接调用 ibv_post_send()：libmlx5 是 CPU 上的库，QP 的软件状态也在 CPU 进程里。最直接的办法是让 GPU 把请求写进 CPU 能读的内存，由一个 CPU proxy 线程代它完成级别 2 的提交，这就是级别 3。

3.1 三种 GPU 侧接口

级别 3 的代价来自这次中转：GPU 先写主机内存，CPU 线程轮询后才发现请求；CPU 再构造 WR、写 WQE、敲 doorbell；完成也要由 CPU 写回 GPU 可见的计数。每个请求都要经过这个 CPU 线程；第 4 章让 GPU 自己写 WQE，CPU 只剩下 ②。

4. GPU 写 WQE，CPU 只敲 doorbell

级别 3 的 proxy 要为每个请求构造 WR，再由 libmlx5 编码成 WQE。如果 GPU 直接按 mlx5 格式写 WQE，CPU 就只剩下 ②。前提有两个：SQ 环放在 GPU 能写、网卡能 DMA 读的显存中，像 payload 一样按第 2 章的方式注册给网卡；GPU 自己维护队列状态，并轮询 CQ。② 交给谁，取决于 GPU 能否映射 UAR（第 5 章）；映射不了时由 CPU 代敲，这就是级别 4。

NVSHMEM IBGDA 的 CPU 模式最直接。GPU 照常写 WQE，但不碰 DBR 和 UAR，只用一次系统作用域的 atomicMax 把新的生产者序号发布到 CPU 可读的位置。NVSHMEM 的 proxy 线程轮询这个序号，发现它前进后写 DBR，执行 release 屏障，再把控制段写进 UAR。这时 DBR 放在主机内存，UAR 只映射给 CPU。[[ibgda-cpu-post|GPU 发布序号]] · [[ibgda-cpu-ring|CPU 代敲 doorbell]] NVSHMEM_IBGDA_NIC_HANDLER 决定走哪种模式：

NCCL GIN 的 GDAKI 后端用的是 NCCL 自带的 GPUNetIO，默认的 AUTO 同样先做这项探测：UAR 映射不进 GPU 时，GDAKI 自动改用 CPU proxy 模式，NCCL 另起一个 progress 线程调用同一个 doca_gpu_verbs_cpu_proxy_progress()。这一选择由环境变量 NCCL_GIN_GDAKI_NIC_HANDLER 控制，本文版本的用户文档没有列出它。[[gdaki-nic-handler|GDAKI 的 NIC handler]]

级别 3 和级别 4 都有一个 CPU 线程在运行，区别在于它拿到什么。级别 3 的 proxy 收到高层请求（目标 PE、地址和长度，或者 GIN 描述符），自己构造 WR，WQE 由 libmlx5 写；级别 4 的 CPU 只看到一个生产者序号，WQE 早已由 GPU 写好，它只负责 ②。CQ 也由 GPU 轮询，完成不再经过 CPU。剩下的这一步，要等 GPU 能直接写 UAR 才能去掉。

5. GPU 自己敲 doorbell

最后把 ② 也交给 GPU。1.4 节已经看到，CPU 敲 doorbell 只是对 UAR 页的一次 store。GPU 要做同样的事，需要两样东西：GPU 页表中指向这页 UAR 的映射，以及一条能变成 PCIe 写的 MMIO store。有了这两样，kernel 就能直接发起网卡操作，即 GDAKI（GPUDirect Async Kernel-Initiated）。

6. 完成与顺序

五个级别改变的是谁写 WQE、谁敲 doorbell。应用关心的是另外两件事：源 buffer 什么时候可以复用，接收方什么时候可以读数据。1.3 节留下的问题在这里回答：A 的 CQE 只说明本端完成，B 需要另一个信号才知道数据已经到达。NVSHMEM 和 GIN 把这个信号做进了接口。下表沿时间线列出各方案的完成条件：

接收方的 signal 等待返回（发送方用 putmem_signal_nbi / ncclGin_SignalInc 附带，接收方用 signal_wait_until / waitSignal 等待）满足该信号 API 的数据完成与顺序保证，等待方以 acquire 语义看到数据。接收 kernel 真正完成消费；下一轮覆盖前需要协调。
NCCL collective 所在 stream 完成collective 的结果对 stream 上的后续工作可见。无；proxy 进度与 chunk 完成由 NCCL 内部处理。

可见性是另一个问题：网卡写进显存的数据，正在运行的 kernel 未必按顺序看到。GPUDirect RDMA 文档指出，只有 CPU 发起的 CUDA 接口为 GPU 观察到的 GPUDirect 写入提供顺序，第三方设备的 PCIe 写全部发出后，运行中的 kernel 仍可能读到旧数据或乱序的数据，直到下一次由 CPU 发起的 CUDA 提交或同步。[[gdr-ordering|GPUDirect 的内存顺序]] NVSHMEM 与 GIN 的 signal 接口把数据完成与顺序写进了契约，应用按契约等待 signal 即可；直接用 verbs 写显存、再让运行中的 kernel 读取的程序，要自己处理这一步。

多线程实现还要明确数据生产线程、共同调用通信接口的线程，以及内存顺序的作用域。NVSHMEM 中多个线程发出操作时，应先保证这些操作都已发出，再由调用线程执行 quiet。重复执行时需要按轮次维护 signal，并协调接收 buffer 的复用。[[nv-ordering|NVSHMEM 内存顺序]] · [[gin-api|GIN 接口契约]]
