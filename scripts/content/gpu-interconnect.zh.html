GPU 互联的软件与驱动

GPU 之间的通信有两类常见数据路径：通过 NVLink / PCIe 访问另一张卡的显存，或通过网卡执行 RDMA。CUDA 驱动建立显存映射，Linux RDMA 驱动建立网卡资源，NCCL 和 NVSHMEM 在这些资源之上组织传输。同一条显存到网卡的数据通路，可以由 CPU proxy 推进，也可以由 GPU kernel 提交请求。

2. NCCL CPU proxy

普通 NCCL NET/IB 路径由 CPU proxy 推进网络请求。libnccl.so 组织 collective，proxy 经 libibverbs 与 libmlx5 提交 WR；启用 GPUDirect RDMA 后，NIC 直接搬运 GPU buffer。连接与内存注册先完成，后续 chunk 复用这些资源。

2.1 连接与队列

跨主机传输前，CPU 为两端准备队列、内存地址及访问权限。这些信息随后供 CPU 或 GPU 的提交代码使用。

对象含义在一次写入中的用途
PDProtection Domain，资源的保护域关联 QP 与注册内存的访问权限。
MR / lkey / rkeyMemory Region 及本地 / 远端访问 key标识可被网卡访问的 buffer、范围与权限；远端地址和 rkey 需要交换。
QPQueue Pair，发送 / 接收工作队列承载 WR 对应的硬件 WQE；具体使用哪条队列取决于操作类型。
WR / WQEWork Request / Work Queue Element描述源地址、长度、目标地址、rkey 等。WR 是软件请求，WQE 是硬件队列表示。
Doorbell向网卡通知队列进展的机制让 NIC 发现新工作；DBR 等内存记录与 MMIO doorbell 有不同作用。
CQ / CQECompletion Queue / Entry报告已请求的完成通知与错误。批处理或 selective signaling 下不要求每个 WQE 都生成一个 CQE。

普通 RDMA Write 直接访问远端 MR，无需为每次写入配对一个 receive buffer。Send/Recv，以及带 immediate 的某些操作，有不同的接收资源与通知要求。接收方何时消费 buffer，还需要通信库或应用定义同步协议。

2.2 显存注册

CUDA 分配提供 GPU 可用的虚拟地址。网卡访问同一段 buffer，还需要访问授权与 DMA 地址映射。内存注册为此建立 NIC 资源和 key；GPU 页表中的 peer 映射与 NIC 的 MR 分别服务于两种访问机制。

注册路径主机侧操作内核协作
Peer memory对支持的 GPU 分配执行 MR 注册。RDMA 驱动通过 nvidia-peermem 与 NVIDIA GPU 驱动协作，维护页面和 DMA 映射。
DMA-BUF导出 GPU buffer 为 DMA-BUF fd，再通过 ibv_reg_dmabuf_mr() 等接口注册。GPU exporter 与 RDMA importer 经 DMA-BUF 协作；支持的配置可不加载 nvidia-peermem。

“零拷贝”指 payload 可以避免在 CPU 内存中转。初始化消息、地址与 key 的交换、队列控制和完成状态仍由控制路径处理。nvidia-peermem 参与访问资源的建立，实际 payload 由硬件搬运。

2.3 提交与完成

CPU 调用 ncclAllReduce() 后，NCCL 选择算法与连接方式，安排 GPU kernel 和所需的主机工作。一个 AllReduce 可以同时使用节点内 peer 传输和节点间网络传输。图中展示普通 NET/IB transport 的一个发送 chunk，假设该连接已启用 GPUDirect RDMA。[[nccl-api|API 入口]]

{{cpu}}

sendProxyProgress() 检查 GPU / FIFO 进度，在 chunk 就绪后调用网络插件的 isend。内置 IB 实现在满足发送条件时构造 verbs 请求，通过 ibv_post_send() 交给 mlx5 用户态 provider。provider 写入队列并通知网卡；网卡通过 DMA 读取 GPU payload，经网络发往对端。[[nccl-proxy|proxy 的 ready / isend / test]] · [[nccl-isend|NET/IB 发送]] · [[mlx5-send|mlx5 provider]]

proxy 通过 test 轮询 completion，再更新 GPU 可见的进度。接收侧的 recvProxyProgress() 负责接收请求、完成及必要的可见性处理；这部分 CPU 协作在图中合并到了远端 NIC / GPU 一栏。

2.4 路径选择

CPU proxy 提交描述符与控制信息，GPU payload 可以走 GDR。GDR 不可用、选用 socket 后端或其他 transport 时，数据流也随之改变。ncclAllReduce() 的实际调用链取决于所选网络插件及其实现。

本文版本的 NCCL host API 也可能选择使用 GIN 的 kernel：collective 由 CPU 发起，网络请求在 kernel 内发起。本节描述的是普通 NET/IB CPU proxy transport。核对 trace 中的实际路径，需要同时查看算法、transport、GDR 注册和 proxy 活动。[[nccl-sym-gin|Host API 的 GIN kernel 选项]]

3. NVSHMEM CPU proxy

NVSHMEM kernel 可以通过 CPU proxy 提交网络操作。图示远端目标使用 PROXY device 路径，由 IBRC 主机 transport 执行网络请求；本地可直接访问的 peer 仍可走 load/store。[[nv-dispatch|device 分派]] · [[nv-select|transport 选择]]

3.1 PE 与 symmetric heap

NVSHMEM 提供一侧通信接口：调用方指定目标 PE，即可 put/get 对方的 symmetric memory。各 PE 按一致的 collective 分配顺序建立对应对象。symmetric address 标识对方对应的分配与偏移，各进程的虚拟地址数值不必相同。[[nv-doc|NVSHMEM 编程模型]]

对于 GPU 0 → GPU 1 的例子，两个 PE 各自分配 dst 和 signal。PE 0 写入 PE 1 的 dst，再发布与数据有序关联的信号；PE 1 等待信号后消费数据。

3.2 请求与完成

libnvshmem_host.so 建立 PE、symmetric heap 和 transport，IBRC 经 verbs/provider 建立连接并注册显存。Linux 的 ib_uverbs / ib_core、mlx5_ib / mlx5_core 和 GPU 内存注册接口参与资源准备，见 显存注册。

{{nvproxy}}

kernel 发布包含目标 PE、地址和长度的请求，CPU proxy 取出请求，由 IBRC 构造 RDMA WR 并执行 ibv_post_send()。CPU 轮询 CQ、更新完成状态，GPU 的 quiet 与接收端 signal wait 按 NVSHMEM 的完成语义等待。网卡请求由 CPU 生成，payload 仍可从 GPU 显存直接经 NIC 传输。[[nv-proxy|IBRC 提交]] · [[nv-proxy-cq|IBRC completion]]

4. NVSHMEM IBGDA

IBGDA 是 NVSHMEM 的 InfiniBand GPUDirect Async transport，直接管理 mlx5 队列。主机端建立资源与 GPU 可访问的 NIC 映射，设备端写入 WQE、发布队列进度并触发 doorbell。ibgda_post_send() 包含内存顺序操作、DBR 更新和 ibgda_ring_db() 调用。除 InfiniBand 外，支持的 mlx5 配置也可使用 RoCE。[[ibgda-host|主机映射]] · [[ibgda-db|GPU 提交]]

4.1 资源与配置

IBGDA 主机代码经 verbs / mlx5 建立 QP、CQ 和 MR，并准备 GPU 可访问的队列与 NIC 映射。显存通过 peer-memory 或 DMA-BUF 等受支持的方式注册；设备代码据此获得提交队列所需的地址、key 和状态。[[ibgda-host|IBGDA 主机映射]]

NVSHMEM_IBGDA_NIC_HANDLER=auto 默认优先使用 GPU；平台不支持时回退到 CPU。gpu、cpu 与 cpu_host_memory 可显式选择处理方式，后两者使用不同的 CPU 可访问内存机制。[[nv-env|NIC handler 配置]]

5. NVSHMEM GPUNetIO

GPUNETIO_GDAKI 是 NVSHMEM 的另一种 device transport。NVSHMEM 负责 PE、symmetric address 与同步语义，GPUNetIO 负责队列操作；它与直接管理 mlx5 队列的 IBGDA 是替代关系。[[nv-dispatch|分派入口]] · [[nv-gpunetio|QP 建立]]

5.1 资源导出

GPUNetIO Verbs 提供 GPU 访问网卡队列的公共接口。CPU 经 verbs / mlx5 创建 QP、CQ 和 MR，并导出设备侧描述符；GPU 调用 doca_gpu_dev_verbs_put() 等函数，构造、提交 WQE 并观察完成。NCCL 的 GDAKI 后端与 NVSHMEM 的 GPUNetIO transport 都可复用这套接口。[[gpureadme|GPUNetIO 开源实现]]

5.3 CPU 辅助 doorbell

NVSHMEM_GPUNETIO_NIC_HANDLER 支持 auto、gpu 和 cpu；auto 优先选择 GPU，不支持时回退到 CPU。[[nv-env|配置定义]]

CPU 辅助 doorbell 模式中，GPU 可构造 WQE、轮询 CQE，CPU 只负责约定的 doorbell 推进。高层请求 proxy 的分工则是 GPU 发布请求，由 CPU 构造并提交 verbs WR。[[gpu-cpu-db|CPU doorbell progress]] · [[gpu-submit|设备提交]] · [[gpu-cq|设备 completion]]

开源 GPUNetIO 聚焦 one-sided RDMA GDAKI，支持独立构建和项目集成；使用其中的 doca_* 接口无需安装完整 DOCA SDK。完整 SDK 还提供更多功能。NCCL 随版本提供的 GPUNetIO 代码可能与独立仓库快照不同，源码分析以各自调用点为准。

6.3 顺序与完成

时刻已经成立的条件接下来仍需等待的条件
WQE 已构造请求描述符已准备好。正确发布队列并通知 NIC。
Doorbell 已提交网卡收到或可以观察到新工作通知。DMA、网络事务及相应完成条件。
GIN flush 返回该 cooperative group 发出的 put 的源 buffer 可安全复用。远端数据落定、接收方消费；按 signal 等接口确认。
接收方等待关联 signal 返回满足该信号 API 的数据完成与顺序保证。接收 kernel 真正完成消费；下一轮覆盖前需要协调。

多线程实现需要明确数据生产线程、共同调用通信接口的线程，以及内存顺序作用域。直接将单线程示例扩展为每个线程各敲一次同一个 doorbell，会引入队列并发和顺序问题；共享队列时须遵循 GPUNetIO 与 GIN 的资源共享及协作约定。

7.3 接口与分工

应用可使用 同一段 ncclGin kernel，flush 的本地源复用保证与 signal 的接收端依赖保持不变。GDAKI 在 GPU 上构造网卡 WQE；GIN CPU proxy 由 GPU 发布 GIN 描述符，CPU 构造并提交网络请求。GPUNetIO 的 CPU 辅助 doorbell 只将通知步骤交给 CPU，WQE 已由 GPU 构造。

普通 NCCL NET/IB CPU proxy 推进的是 collective kernel 的 chunk；GIN CPU proxy 消费的是用户 kernel 发出的 GIN 操作。两条路径都可使用 CPU verbs 和 GPUDirect RDMA，但上层协议与进度对象不同。
