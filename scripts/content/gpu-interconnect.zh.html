GPU 互联的软件与驱动

GPU 之间的通信有两类常见数据路径：通过 NVLink / PCIe 访问另一张卡的显存，或通过网卡执行 RDMA。CUDA 驱动建立显存映射，Linux RDMA 驱动建立网卡资源，NCCL 和 NVSHMEM 在这些资源之上组织传输。沿着一块数据从 GPU 0 到 GPU 1 的过程，可以看清 CPU proxy、IBGDA、GPUNetIO Verbs 与 NCCL GIN 各自承担的工作。

1. 路径总览

1.1 API、提交与搬运

设 GPU 0 已生成一块数据，GPU 1 需要读取它。一次传输包含三个不同的问题：谁发起通信操作，谁向硬件提交请求，数据经过哪里。CPU 调用 ncclAllReduce() 只回答第一个问题。网络请求可能由 CPU proxy 提交，数据仍可直接在 GPU 显存和网卡之间传输。

2. NCCL CPU proxy

普通 NCCL NET/IB 路径由 CPU proxy 推进网络请求。libnccl.so 组织 collective，proxy 经 libibverbs 与 libmlx5 提交 WR；启用 GPUDirect RDMA 后，NIC 直接搬运 GPU buffer。连接与内存注册先完成，后续 chunk 复用这些资源。

2.1 连接与队列

以两台主机上的 GPU buffer 为例，连接建立阶段要让两端知道“通过哪条队列、访问哪段内存、凭什么权限访问”。这些信息先由 CPU 组织，再供 CPU 或 GPU 的提交代码使用。

对象含义在一次写入中的用途
PDProtection Domain，资源的保护域关联 QP 与注册内存的访问权限。
MR / lkey / rkeyMemory Region 及本地 / 远端访问 key标识可被网卡访问的 buffer、范围与权限；远端地址和 rkey 需要交换。
QPQueue Pair，发送 / 接收工作队列承载 WR 对应的硬件 WQE；具体使用哪条队列取决于操作类型。
WR / WQEWork Request / Work Queue Element描述源地址、长度、目标地址、rkey 等。WR 是软件请求，WQE 是硬件队列表示。
Doorbell向网卡通知队列进展的机制让 NIC 发现新工作；DBR 等内存记录与 MMIO doorbell 有不同作用。
CQ / CQECompletion Queue / Entry报告已请求的完成通知与错误。批处理或 selective signaling 下不要求每个 WQE 都生成一个 CQE。

普通 RDMA Write 直接访问远端 MR，无需为每次写入配对一个 receive buffer。Send/Recv，以及带 immediate 的某些操作，有不同的接收资源与通知要求。接收方何时消费 buffer，还需要通信库或应用定义同步协议。

2.2 显存注册

CUDA 分配得到的 GPU 虚拟地址，解决的是 GPU 如何访问这段内存。网卡还需要自己的访问授权与 DMA 地址映射。注册会为 buffer 建立 NIC 可用的资源和 key；GPU 页表中的 peer 映射与 NIC 的 MR 是不同对象。

注册路径主机侧操作内核协作
Peer memory对支持的 GPU 分配执行 MR 注册。RDMA 驱动通过 nvidia-peermem 与 NVIDIA GPU 驱动协作，维护页面和 DMA 映射。
DMA-BUF导出 GPU buffer 为 DMA-BUF fd，再通过 ibv_reg_dmabuf_mr() 等接口注册。GPU exporter 与 RDMA importer 经 DMA-BUF 协作；支持的配置可不加载 nvidia-peermem。

“零拷贝”在这里指 payload 可避免经过 CPU 内存中转。初始化消息、地址与 key 的交换、队列控制和完成状态仍然存在。nvidia-peermem 为访问建立条件，payload 不会逐字节经过这个内核模块。

2.3 提交与完成

CPU 调用 ncclAllReduce() 时，NCCL 为 collective 选择算法与连接方式，组织 GPU kernel 和需要的主机工作。一个 AllReduce 可以同时包含节点内 peer 传输与节点间网络传输。下面只展开普通 NET/IB transport 中一个发送 chunk，并假设这段连接已启用 GPUDirect RDMA。[[nccl-api|API 入口]]

sendProxyProgress() 检查 GPU / FIFO 的进展，确认 chunk 可发送后调用网络插件的 isend。内置 IB 实现在具备发送条件时构造 verbs 请求，交给 ibv_post_send()；mlx5 用户态 provider 写队列并通知网卡。网卡通过 DMA 读取 GPU payload，经网络发往对端。[[nccl-proxy|proxy 的 ready / isend / test]] · [[nccl-isend|NET/IB 发送]] · [[mlx5-send|mlx5 provider]]

2.4 路径选择

CPU 在这里提交的是描述符与控制信息，GPU payload 可以走 GDR。没有可用的 GDR、使用 socket 后端或遇到其他路径时，数据流会不同。NCCL 的网络插件接口也允许不同实现，因此不能把 ncclAllReduce() 等同于某条固定的 verbs 调用链。

新版 NCCL 的 host API 还可能选择使用 GIN 的 kernel。CPU 发起 collective 与 kernel 内发起网络请求可以同时成立；本节的 CPU proxy 路径，是按实际 transport 和执行方式定义的。分析一条 trace 时，应同时核对算法、transport、GDR 注册和 proxy 活动。[[nccl-sym-gin|Host API 的 GIN kernel 选项]]

3. NVSHMEM CPU proxy

NVSHMEM 的 device API 可以由 GPU 发起，再交给 CPU proxy 执行网络提交。本章以远端目标选用 PROXY、主机 transport 为 IBRC 的路径为例；本地可直接访问的 peer 仍可使用 load/store。[[nv-dispatch|device 分派]] · [[nv-select|transport 选择]]

3.1 PE 与 symmetric heap

NVSHMEM 给应用提供一侧通信接口：调用方指定目标 PE，即可 put/get 对方的 symmetric memory。各 PE 以一致的 collective 分配顺序建立对应对象。symmetric address 表达的是“对方对应的分配与偏移”；应用不应把它理解为所有进程拥有相同数值的虚拟地址。[[nv-doc|NVSHMEM 编程模型]]

对于 GPU 0 → GPU 1 的例子，两个 PE 各自分配 dst 和 signal。PE 0 写入 PE 1 的 dst，再发布与数据有序关联的信号；PE 1 等待信号后消费数据。

libnvshmem_host.so 建立 PE、symmetric heap 和 transport，IBRC 经 verbs/provider 建立连接并注册显存。Linux 的 ib_uverbs / ib_core、mlx5_ib / mlx5_core 和 GPU 内存注册接口参与资源准备，见 显存注册。

kernel 发布包含目标 PE、地址和长度的请求，CPU proxy 消费请求，再由 IBRC 构造 RDMA WR 并执行 ibv_post_send()。CPU 推进 CQ 完成；GPU 的 quiet 与接收端 signal wait 按 NVSHMEM 的契约等待。这里由 CPU 生成网卡请求，payload 仍可从 GPU 显存直接经 NIC 传输。[[nv-proxy|IBRC 提交]] · [[nv-proxy-cq|IBRC completion]]

4. NVSHMEM IBGDA

IBGDA 是 NVSHMEM 的 InfiniBand GPUDirect Async transport，包含直接管理 mlx5 队列的实现。主机端建立资源与 GPU 可访问的 NIC 映射；设备端写 WQE、发布队列进度并触发 doorbell。ibgda_post_send() 中可看到内存顺序操作、DBR 更新和 ibgda_ring_db()。这里的“IB”也不意味着底层只能使用 InfiniBand 链路：支持的 mlx5 配置还可使用 RoCE。[[ibgda-host|主机映射]] · [[ibgda-db|GPU 提交]]

4.1 资源与配置

IBGDA 的主机实现经 verbs / mlx5 建立 QP、CQ 和 MR，并准备 GPU 可访问的队列与 NIC 映射。GPU 显存仍需通过 peer-memory 或 DMA-BUF 等支持的方式注册；新增的准备是让设备代码拥有提交队列所需的地址、key 和状态。[[ibgda-host|IBGDA 主机映射]]

NVSHMEM_IBGDA_NIC_HANDLER=auto 默认优先使用 GPU；平台不支持时回退到 CPU。gpu、cpu 与 cpu_host_memory 可显式选择处理方式，后两者使用不同的 CPU 可访问内存机制。[[nv-env|NIC handler 配置]]

图中展开 GPU 直接 doorbell。CPU 辅助模式增加一次主机推进：GPU 准备 WQE 并发布待提交进度，CPU 执行 doorbell 工作。核对性能时需要区分“谁写 WQE”和“谁敲 doorbell”。

5. NVSHMEM GPUNetIO

这条路径由 NVSHMEM 选择 GPUNETIO_GDAKI device transport。NVSHMEM 保留 PE、symmetric address 与同步语义，GPUNetIO 提供队列操作。它与直接管理 mlx5 队列的 IBGDA 是两种替代实现。[[nv-dispatch|分派入口]] · [[nv-gpunetio|QP 建立]]

5.1 资源导出

GPUNetIO Verbs 把 GPU 操作网卡队列所需的机制封装成公共接口。CPU 侧经 verbs / mlx5 接口创建 QP、CQ、MR，导出 GPU 可使用的描述符；CUDA 侧调用 doca_gpu_dev_verbs_put() 等函数，构造和提交 WQE、观察完成。NCCL 的 GDAKI 后端和 NVSHMEM 的 GPUNetIO transport 都可以复用这套机制。[[gpureadme|GPUNetIO 开源实现]]

5.3 CPU 辅助 doorbell

NVSHMEM_GPUNETIO_NIC_HANDLER 支持 auto、gpu 和 cpu；auto 优先选择 GPU，不支持时回退到 CPU。[[nv-env|配置定义]]

CPU 辅助模式下，GPU 仍可构造 WQE、轮询 CQE，CPU 只承担约定的 doorbell 推进。这与“GPU 只写高层请求、CPU proxy 构造 verbs WR”的模式有不同分工。[[gpu-cpu-db|CPU doorbell progress]] · [[gpu-submit|设备提交]] · [[gpu-cq|设备 completion]]

开源 GPUNetIO 聚焦 RDMA one-sided GDAKI；完整 DOCA SDK 还覆盖更多功能。源码中的 doca_* 名称并不意味着应用必须安装整套 DOCA SDK：这个开源子集有独立构建路径，也能被项目集成。NCCL 固定版本自带的 GPUNetIO 代码与独立仓库快照可能不同，应以各自调用点为准。

6.3 顺序与完成

时刻已经成立的条件接下来仍需等待的条件
WQE 已构造请求描述符已准备好。正确发布队列并通知 NIC。
Doorbell 已提交网卡收到或可以观察到新工作通知。DMA、网络事务及相应完成条件。
GIN flush 返回该 cooperative group 发出的 put 的源 buffer 可安全复用。远端数据落定、接收方消费；按 signal 等接口确认。
接收方等待关联 signal 返回满足该信号 API 的数据完成与顺序保证。接收 kernel 真正完成消费；下一轮覆盖前需要协调。

多线程版本还必须明确哪些线程生产了源数据、哪些线程共同调用通信接口，以及内存顺序作用域。把单线程示例直接扩展为每个线程敲一次同一个 doorbell，会引入队列并发和顺序问题。GPUNetIO 与 GIN 都提供资源共享和协作范围的约定，应按 API 使用。

7.3 接口与分工

同一段 ncclGin kernel仍然适用，flush 的本地源复用保证、signal 的接收端依赖也保持不变。变化在提交链：GDAKI 在 GPU 上构造网卡 WQE；GIN CPU proxy 由 GPU 发布 GIN 描述符，再由 CPU 生成并提交网络请求。后者也区别于 GPUNetIO 的 CPU 辅助 doorbell——辅助模式中 WQE 已经由 GPU 构造。

普通 NCCL NET/IB CPU proxy 推进的是 collective kernel 的 chunk；GIN CPU proxy 消费的是用户 kernel 发出的 GIN 操作。两条路径都可使用 CPU verbs 和 GPUDirect RDMA，但上层协议与进度对象不同。
