GPU 互联的软件与驱动

普通 NCCL、NVSHMEM 与 NCCL GIN 提供了三种组织 GPU 通信的方式：CPU 发起 collective、基于 symmetric memory 的一侧通信，以及用户 kernel 内的网络操作。NVSHMEM 和 GIN 各有可选后端，决定请求由 CPU proxy 还是 GPU 推进；驱动为这些后端建立网卡队列、显存注册和地址映射。即使请求由 CPU proxy 提交，payload 仍可通过 GPUDirect RDMA 直接在显存与网卡之间传输。

源码基线：NCCL 2.32.3、NVSHMEM 3.8.0、rdma-core 61.0，核对日期 2026-11-09。图中链接固定到 commit。序列图展示源码调用顺序，activation bar 标示参与者的逻辑活动范围。

1. 通信方案与基础

1.1 三组通信方案

三组方案按应用入口和编程模型区分。GIN 属于 NCCL Device API，其 kernel 内调用方式与普通 collective API 分开讲解；表中的后端列对应各章展开的具体实现。

NVSHMEMPE 与 symmetric memory；本文使用 kernel 内的 put/get、signal、quiet。CPU proxy / IBRC
IBGDA
GPUNetIO		proxy 后端由 CPU 构造并提交网络请求；IBGDA / GPUNetIO 由 GPU 构造 WQE，doorbell 可由 GPU 或辅助 CPU 执行。
NCCL GIN用户 CUDA kernel 调用 ncclGin，使用 rank、window 和 signal。CPU proxy

应用调用位置、网卡请求提交位置与 payload 路径可以不同。CPU proxy 提交请求时，启用 GPUDirect RDMA 的 NIC 仍能直接访问显存。GDAKI（GPUDirect Async Kernel-Initiated）描述 kernel 发起网卡操作的能力；GPUDirect RDMA 描述显存与 NIC 之间的直接数据通路。[[nccl-proxy|NCCL proxy]] · [[nv-dispatch|NVSHMEM 后端分派]] · [[gin-select|GIN 后端选择]] · [[gpureadme|GPUNetIO 的 CPU / GPU 分工]]

CUDA peer / NVLink 是互联机制。GPU 通过 peer 映射 load/store 对方显存，这条路径可以被 NCCL 与 NVSHMEM 使用。NCCL Device API 中的 LSA 面向可直接 load/store 的 peer，GIN 面向网络操作。peer 访问的范围由 GPU 互联、驱动和地址映射能力共同决定，详见 CUDA peer 与 NVLink。[[device-doc|LSA 与 GIN]]

库和内核模块是完整路径的依赖。libibverbs 提供接口，libmlx5 实现 mlx5 用户态队列操作，mlx5_ib 管理内核侧 RDMA 资源，nvidia-peermem 参与显存注册协作。在支持的配置下，DMA-BUF 可替代这一注册协作机制；NCCL / NVSHMEM 仍负责上层通信语义与进度。具体依赖见 软件与驱动。[[user-verbs|verbs 与驱动分工]] · [[peermem|peer-memory]] · [[dmabuf|DMA-BUF]]

1.2 DMA 与 RDMA

普通以太网卡收到数据包后，就可以把数据 DMA 写入本机内存中的接收缓冲区。DMA（Direct Memory Access，直接内存访问）让设备按驱动建立的地址映射读写内存，数据搬运由设备完成。CPU 负责准备缓冲区、描述符和映射，并处理提交与完成。[[dma-api|Linux DMA 地址与映射]]

机制解决的问题典型数据路径
DMA设备直接读写本机可访问的内存。本机 NIC ↔ 主机内存
RDMA
Remote Direct Memory Access		网卡执行远端内存操作。RDMA Read/Write 请求指定远端地址、长度和访问 key，网卡检查注册范围与权限并执行传输。A 主机内存 ↔ A NIC ↔ 网络 ↔ B NIC ↔ B 主机内存
GPUDirect RDMA将 GPU 显存接入第三方设备的直接 DMA 路径；用于 RDMA 通信时，NIC 可直接访问已注册的显存。A 显存 ↔ A NIC ↔ 网络 ↔ B NIC ↔ B 显存

“经过网卡”不等于“远程直接内存访问”。普通 TCP/IP 收发也使用本机 DMA。RDMA 增加了网卡能够理解的远端内存操作、访问保护和完成机制；两端提前完成内存注册，并交换远端访问所需的地址和 key。GPUDirect RDMA 则把显存纳入这套访问路径。[[rdma-guide|RDMA 操作]] · [[gdr-doc|GPUDirect RDMA]]

内存与队列对象

一次 RDMA Read 需要先授权内存访问，再提交读取请求，最后取得完成结果。这几个环节分别使用以下对象。

术语含义与职责
MR · Memory Region
内存区域		向 RDMA 设备注册的一段内存，记录地址范围、访问权限和映射。它可以对应主机内存，也可以对应受支持的 GPU 显存。
lkey / rkey
本地 / 远端访问 key		注册 MR 时取得的访问标识。lkey 用于本地 buffer，rkey 交给对端，用于远端内存访问校验。
PD · Protection Domain
保护域		关联本地 QP、MR 等资源，限定哪些队列可以使用哪些注册内存。
QP · Queue Pair
队列对		包含发送队列 SQ 和接收队列 RQ。RDMA Read/Write 由发起方提交到 SQ；RQ 存放接收请求，为 Send 等操作准备接收 buffer。
WR · Work Request
工作请求		软件提交的操作描述。例如“把 B 的 4096 字节读入 A”，包含操作类型、本地 buffer、长度，以及远端地址和 rkey。
WQE · Work Queue Element
工作队列项		网卡可解析的硬件格式描述符，放在工作队列中。CPU verbs 路径由 provider 把 WR 编码为 WQE；GPU 发起路径可由设备代码构造 WQE。
Doorbell
门铃		通知网卡有新工作的机制。mlx5 先更新内存中的 DBR（Doorbell Record，队列进度记录），再写入映射的 MMIO doorbell，推动网卡处理 WQE。
CQ / CQE
Completion Queue / Entry		CQ 是完成队列，CQE 是其中的一条完成记录，包含成功或错误状态。发送侧可选择哪些成功完成的请求生成 CQE，再从 CQ 取回结果。

以启用完成通知的 CPU verbs 请求为例，路径是：构造 WR → provider 写入 WQE → 敲 doorbell → NIC 执行 → 从 CQ 读取 CQE。MR 提供请求访问内存时所需的映射与权限。[[rdma-guide|RDMA 对象]] · [[verbs-mr|内存注册]] · [[verbs-post-send|请求与完成选项]] · [[mlx5-doorbell|mlx5 门铃实现]]

一次显存 RDMA Read

A 要把 B 显存中的 4 KiB 数据读入自己的显存。两端已建立可靠连接（RC）的队列对 QP，并将相应 buffer 注册为内存区域 MR。B 授予源 MR 远端读权限，将远端地址和 rkey 交给 A；A 的目标 MR 允许本地写入。A 提交请求时指定 B 的地址与 rkey，以及自己的目标地址与 lkey。两种 key 分别标识远端和本地的内存访问资源。[[verbs-mr|MR 与访问权限]] · [[verbs-post-send|RDMA Read 请求字段]]

{{rdma-read}}

请求由 A 发出，数据从 B 流向 A。③ 和 ⑤ 分别是两端 NIC 的本地 DMA；① 和 ④ 承担网络上的 RDMA 请求与响应。B 的 NIC 使用预先注册的 MR 完成校验和读取。这个例子为 A 的请求启用完成通知，完成后 A 的完成队列 CQ 中出现 CQE；GPU 消费目标数据前，还需按所用通信库或 CUDA 接口完成可见性同步。[[rdma-guide|RDMA Read]] · [[verbs-post-send|完成通知]] · [[gdr-ordering|GPU 内存可见性]]

1.4 CUDA peer 与 NVLink

CUDA peer 路径使用 GPU 可访问的地址映射：CPU 驱动建立权限与页表，GPU 的 load/store 经 NVLink / PCIe 直接访问对端显存。这次内存访问不经过 NIC RDMA 的队列提交路径。可访问哪些 GPU，取决于互联拓扑、驱动与映射能力；NIC RDMA 则通过 QP、MR 和访问 key 建立远端内存操作。[[device-doc|CUDA P2P、LSA 与 GIN]] · [[user-verbs|RDMA 资源接口]]

2. 普通 NCCL

普通 NCCL NET/IB 路径由 CPU proxy 推进网络请求。libnccl.so 组织 collective，proxy 经 libibverbs 与 libmlx5 提交 WR；启用 GPUDirect RDMA 后，NIC 直接搬运 GPU buffer。连接与内存注册先完成，后续 chunk 复用这些资源。

2.1 连接与队列

跨主机传输前，CPU 为两端准备队列、内存地址及访问权限。这些信息随后供 CPU 或 GPU 的提交代码使用。

每端建立 PD，将 QP 与注册的 MR 关联到同一保护域，并为 QP 关联 CQ。两端交换连接信息，以及远端访问所需的 MR 地址和 rkey。对象定义见 1.2 节的内存与队列对象。

普通 RDMA Write 直接访问远端 MR，无需为每次写入配对一个 receive buffer。Send/Recv，以及带 immediate 的某些操作，有不同的接收资源与通知要求。接收方何时消费 buffer，还需要通信库或应用定义同步协议。

2.2 显存注册

CUDA 分配提供 GPU 可用的虚拟地址。网卡访问同一段 buffer，还需要访问授权与 DMA 地址映射。内存注册为此建立 NIC 资源和 key；GPU 页表中的 peer 映射与 NIC 的 MR 分别服务于两种访问机制。

注册路径主机侧操作内核协作
Peer memory对支持的 GPU 分配执行 MR 注册。RDMA 驱动通过 nvidia-peermem 与 NVIDIA GPU 驱动协作，维护页面和 DMA 映射。
DMA-BUF导出 GPU buffer 为 DMA-BUF fd，再通过 ibv_reg_dmabuf_mr() 等接口注册。GPU exporter 与 RDMA importer 经 DMA-BUF 协作；支持的配置可不加载 nvidia-peermem。

“零拷贝”指 payload 可以避免在 CPU 内存中转。初始化消息、地址与 key 的交换、队列控制和完成状态仍由控制路径处理。nvidia-peermem 参与访问资源的建立，实际 payload 由硬件搬运。

2.4 路径选择

CPU proxy 提交描述符与控制信息，GPU payload 可以走 GDR。GDR 不可用、选用 socket 后端或其他 transport 时，数据流也随之改变。ncclAllReduce() 的实际调用链取决于所选网络插件及其实现。

本文版本的 NCCL host API 也可能选择使用 GIN 的 kernel：collective 由 CPU 发起，网络请求在 kernel 内发起。本节描述的是普通 NET/IB CPU proxy transport。核对 trace 中的实际路径，需要同时查看算法、transport、GDR 注册和 proxy 活动。[[nccl-sym-gin|Host API 的 GIN kernel 选项]]

3. NVSHMEM

NVSHMEM 用 PE 和 symmetric memory 表达跨 GPU 的一侧通信。应用使用同一组 put/get 与同步接口，device transport 按目标可达性和配置选择 peer 访问、CPU proxy、IBGDA 或 GPUNetIO。以下网络后端复用相同的应用示例。[[nv-dispatch|device 分派]] · [[nv-select|transport 选择]]

3.1 PE 与 symmetric heap

NVSHMEM 提供一侧通信接口：调用方指定目标 PE，即可 put/get 对方的 symmetric memory。各 PE 按一致的 collective 分配顺序建立对应对象。symmetric address 标识对方对应的分配与偏移，各进程的虚拟地址数值不必相同。[[nv-doc|NVSHMEM 编程模型]]

对于 GPU 0 → GPU 1 的例子，两个 PE 各自分配 dst 和 signal。PE 0 写入 PE 1 的 dst，再发布与数据有序关联的信号；PE 1 等待信号后消费数据。

3.3 IBGDA

IBGDA 是 NVSHMEM 的 InfiniBand GPUDirect Async transport，直接管理 mlx5 队列。主机端建立资源与 GPU 可访问的 NIC 映射，设备端写入 WQE、发布队列进度并触发 doorbell。ibgda_post_send() 包含内存顺序操作、DBR 更新和 ibgda_ring_db() 调用。除 InfiniBand 外，支持的 mlx5 配置也可使用 RoCE。[[ibgda-host|主机映射]] · [[ibgda-db|GPU 提交]]

3.4 GPUNetIO

GPUNETIO_GDAKI 是 NVSHMEM 的另一种 device transport。NVSHMEM 负责 PE、symmetric address 与同步语义，GPUNetIO 负责队列操作；它与直接管理 mlx5 队列的 IBGDA 是替代关系。[[nv-dispatch|分派入口]] · [[nv-gpunetio|QP 建立]]

3.5 UAR 与 GPU 页表

IBGDA 与 GPUNetIO 的 GPU doorbell 都需要访问 NIC 寄存器。这里结合两者的注册代码解释 UAR 映射；NCCL GIN / GDAKI 使用 GPUNetIO 时也复用这一机制。

UAR（User Access Region）是网卡暴露给应用的寄存器访问区域，其中包含 doorbell / BlueFlame 寄存器。GPU 直接敲门铃，需要让一个 GPU 虚拟地址指向 NIC BAR 中的这块区域。CPU 在初始化时建立映射，GPU 随后通过这个地址执行 MMIO store。[[uar-man|UAR 接口]]

注册地址

mlx5dv_devx_alloc_uar() 分配 UAR。其 provider 通过 /dev/infiniband/uverbsN 的 fd 执行资源分配与 mmap，返回的 uar->reg_addr 是进程内可访问 doorbell 的 CPU 虚拟地址。NVIDIA 驱动再为同一 I/O 区域建立 GPU 映射。[[uar-provider|provider 的 ioctl 与 mmap]]

PTE 的目标与属性

公开驱动的 I/O memory 导入路径会检查 CPU VMA 的 VM_IO / VM_PFNMAP 属性，沿 CPU 映射取得设备资源的 PFN，再建立标记为 MEMDESC_FLAGS_PEER_IO_MEM 的描述符。描述符使用 ADDR_SYSMEM 地址类别，并处理 GPU 可见的总线地址及 IOMMU 映射；这里的 system aperture 也承载设备 MMIO。[[uar-pfn|CPU 映射与 PFN]] · [[uar-osdesc|I/O memory 描述符]]

Hopper 的 VER3 PTE 将权限与缓存属性合并进 PCF（Permission Control Flags）字段。公开驱动中的 Blackwell UVM 复制 Hopper 的 MMU HAL，并沿用 make_pte_hopper() 构造叶子 PTE；Blackwell 的页大小扩展由其他 HAL 成员处理。下面用这条构造路径解释两代 GPU 的 4 KiB 映射。[[uar-pte-fields|GH100 的 VER3 位定义]] · [[uar-pte-build|Hopper PTE 构造]] · [[uar-pte-blackwell|Blackwell 的 HAL 继承]]

接口与分工

应用可使用 同一段 ncclGin kernel，flush 的本地源复用保证与 signal 的接收端依赖保持不变。GDAKI 在 GPU 上构造网卡 WQE；GIN CPU proxy 由 GPU 发布 GIN 描述符，CPU 构造并提交网络请求。GPUNetIO 的 CPU 辅助 doorbell 只将通知步骤交给 CPU，WQE 已由 GPU 构造。

普通 NCCL NET/IB CPU proxy 推进的是 collective kernel 的 chunk；GIN CPU proxy 消费的是用户 kernel 发出的 GIN 操作。两条路径都可使用 CPU verbs 和 GPUDirect RDMA，但上层协议与进度对象不同。

4.5 顺序与完成

时刻已经成立的条件接下来仍需等待的条件
WQE 已构造请求描述符已准备好。正确发布队列并通知 NIC。
Doorbell 已提交网卡收到或可以观察到新工作通知。DMA、网络事务及相应完成条件。
GIN flush 返回该 cooperative group 发出的 put 的源 buffer 可安全复用。远端数据落定、接收方消费；按 signal 等接口确认。
接收方等待关联 signal 返回满足该信号 API 的数据完成与顺序保证。接收 kernel 真正完成消费；下一轮覆盖前需要协调。

多线程实现需要明确数据生产线程、共同调用通信接口的线程，以及内存顺序作用域。直接将单线程示例扩展为每个线程各敲一次同一个 doorbell，会引入队列并发和顺序问题；共享队列时须遵循 GPUNetIO 与 GIN 的资源共享及协作约定。
