UVM managed memory access paths

Managed memory gives the CPU and GPU a common pointer. UVM maintains their mappings and manages the physical pages behind that address. An access can use an existing translation or fault; UVM then decides whether to add a mapping, change permissions or migrate data before resuming it. The virtual address, current physical location, and driver-maintained page state are separate parts of this mechanism.

This article covers local access, remote mappings and migration for explicit cudaMallocManaged() allocations. Chapters 2 and 3 trace branches where Linux UVM has chosen migration in its separate-page-table implementation. Source is pinned to NVIDIA open kernel modules 615.71.10 / 6f3be8c9c3fb; PTE diagrams use the Hopper / Blackwell UVM VER3 format. HMM and ATS use different function paths and page-table management. [[release|Source revision]] · [[mmu-blackwell|Blackwell MMU]]

1. UVM architecture

1.1 Software and hardware

UVM (Unified Virtual Memory) implements CUDA Unified Memory in the driver. Applications use the Runtime API through libcudart.so or call the Driver API in libcuda.so.1 directly. The user-mode driver establishes resources through kernel interfaces including ioctl and mmap. On Linux, nvidia-uvm.ko manages address spaces, residency, faults and migration, using RM resource services supplied by nvidia.ko. [[driver-post|CUDA software and driver layers]] · [[fops|UVM kernel interfaces]]

{{architecture}}

cudaMallocManaged(&p, bytes) establishes a managed virtual range. On demand-paging configurations, physical pages need not all exist when the call returns. UVM's managed mmap path installs Linux VMA callbacks and creates a range of type UVM_VA_RANGE_TYPE_MANAGED. VA blocks beneath that range track per-page residency, mappings and permissions. [[memory-api|Allocation semantics]] · [[mmap|VMA callbacks]] · [[range-create|Range creation]] · [[block-state|Page state]]

1.2 Mappings and page migration

UVA organizes the unified virtual address space; UVM manages the pages behind it. An access depends on the current mapping, permissions and reachability of the target memory. The figure uses separate CPU and GPU page tables to show a host-resident managed page with an established GPU remote mapping: both processors map p to host page H. With a valid mapping and sufficient permissions, the GPU reads it through the interconnect. [[memory-api|AccessedBy and host-page mappings]]

{{page_tables}}

Grace Hopper: CPU access to GPU-resident managed pages. With host direct access supported and the mappings established, the CPU can read and write Hopper HBM through NVLink-C2C. After waiting for the relevant GPU work, the CPU dereferences the same managed pointer with float value = p[i]; the page can remain in VRAM. Transferring the requested data over the interconnect and filling CPU caches is distinct from migrating the page to host RAM. [[grace-memory|Grace Hopper memory interconnect]] · [[host-direct|Direct host access]]

Applications query cudaDevAttrDirectManagedMemAccessFromHost and set host cudaMemAdviseSetAccessedBy advice. Support depends on the driver's memory-management mode: the CDMM documentation, for example, lists this attribute as 0, so use the runtime result. Here p comes from cudaMallocManaged(). Grace Hopper can also use ATS to supply GPU translations from CPU page tables; the separate page tables above illustrate one implementation. [[host-direct|Access conditions]] · [[cdmm|Driver modes]] · [[hardware-coherence|ATS and page tables]]

UVM decides when and where to migrate pages using access demands, policy and platform capabilities. A fault may need only a mapping or permission update, and migration can occur without a fault.

TriggerPossible action
Page fault: a mapping is missing or cannot satisfy the accessSelect migration, establish an accessible remote mapping, or update permissions according to policy
Explicit prefetch: a cudaMemPrefetchAsync callMove data toward the specified location in stream order, preparing later accesses without waiting for a fault
Remote-access counters: a GPU frequently accesses another processor's memoryOn platforms supporting and enabling access-counter migration, use the statistics to migrate hot pages
Memory pressure: for example, insufficient VRAM capacityEvict migratable pages to host memory to free VRAM

Application advice influences residency and mapping decisions:

PolicyAdvice valueEffect on migration and mappings
PreferredLocationcudaMemAdviseSetPreferredLocationGuides residency selection; setting it neither immediately migrates data nor prevents later explicit prefetching
AccessedBycudaMemAdviseSetAccessedByEstablishes mappings for the processor where accessible; the advice itself does not require moving data to that processor

Applications pass these advice values to cudaMemAdvise(). PreferredLocation is a policy attribute, while SetPreferredLocation sets it; the queried preference need not match current physical residency. For example, a host-resident managed page with a CPU preference and GPU AccessedBy can retain the remote mapping shown above. [[memory-api|cudaMemAdvise and policy queries]]

1.3 UVM weights in TBE

FBGEMM GPU's TBE (Table Batched Embedding) uses UVM for large embedding tables. With MANAGED_CACHING, managed memory can hold the full weights while VRAM caches frequently used rows. [[tbe-placement|Storage options]]

With the default allocation settings enforce_hbm=False and uvm_host_mapped=False, the allocator calls cudaMallocManaged() and sets SetPreferredLocation=CPU and SetAccessedBy=current GPU. The weights prefer host residency, and the GPU accesses them through established remote mappings, applying the preceding section's residency and mapping policies. [[tbe-allocation|Allocation path]] · [[tbe-managed|Managed allocation]] · [[tbe-advice|Access advice]]

tbe.prefetch() uses the batch's indices to load required rows into the VRAM cache, lxu_cache_weights. TBE manages embedding rows in its cache; UVM manages the underlying pages' mappings and migration. Cache prefetching operates at a different layer from the page migration requested by cudaMemPrefetchAsync(). [[tbe-cache|Cache allocation]] · [[tbe-prefetch|Cache prefetch]]

2. CPU page-fault migration

2.1 Exception entry

Assume the data resides in VRAM page D and the CPU has no usable mapping. The application waits for the relevant GPU work, then reads p[i] on the CPU. With no usable translation, the CPU raises a synchronous page-fault exception. The following example uses Linux UVM's managed VMA path: Linux invokes the VMA's fault callback and enters UVM in the context of the faulting CPU thread. [[linux-fault|Linux VMA callback]] · [[cpu-fault|uvm_vm_fault]]

uvm_vm_fault() calls uvm_va_space_cpu_fault_managed(), which locates the managed VA block using the process address space and fault address, then calls uvm_va_block_cpu_fault(). UVM checks access permissions, selects residency and services the page through uvm_va_block_service_locked(). [[cpu-dispatch|Range and block lookup]] · [[cpu-block|CPU fault service]]

The sequence selects the branch where UVM chooses migration to the host; its function calls belong to the separate-page-table implementation above. Platforms supporting CPU remote access can also retain D and establish or restore a CPU mapping to it. With an existing usable mapping, the CPU accesses the data directly. Hardware-coherent ATS / Linux MM paths need to be followed in their respective implementation. [[cpu-residency|Residency selection for CPU faults]] · [[host-direct|Remote host access]] · [[hardware-coherence|Hardware-coherent page tables]]

{{cpu_fault}}

2.2 Migration to host and mapping updates

The sequence follows migration from VRAM page D to host page H. uvm_va_block_make_resident_copy() revokes old mappings for pages being moved, prepares destination pages and copies the data. uvm_va_block_service_finish() updates residency records and installs the required mappings. [[resident-copy|Migration preparation and copy]] · [[service-finish|Finishing page service]]

  1. GPU page table: clear the old p → D mapping and invalidate the corresponding GPU TLB translation so accesses cannot keep using the old location. [[gpu-clear|GPU PTE clearing and TLB maintenance]] After migration, UVM uses access policies and target reachability to decide whether to install a GPU p → H mapping to the new host page. [[service-finish|Post-migration mapping handling]]
  2. Copy and wait: copy D to H. Before inserting a CPU PTE, block_map_cpu_page_to() calls uvm_tracker_wait() to wait for prior data copies and GPU page-table updates. [[cpu-map-wait|Waiting before CPU mapping]]
  3. CPU page table: uvm_cpu_insert_page() calls Linux's vm_insert_page() to install p → H. After fault handling returns, the CPU retries the instruction. Linux MM owns the CPU page-table changes and associated TLB maintenance. [[cpu-insert|CPU mapping insertion]] · [[linux-tlb|Linux TLB rules]]

A first CPU touch to a managed page without physical backing uses the same CPU fault entry but needs no copy of old data from VRAM. If policy permits GPU access to the host-resident page, UVM can also install a system-memory p → H mapping for the GPU. [[service-finish|Mappings for other processors]]

3. GPU page-fault migration

3.1 Fault records and scheduling

Now assume the CPU has populated host page H, while the GPU has no usable mapping. The kernel executes an ordinary ld.global. A TLB miss triggers a GPU page-table walk; a page fault occurs only if the translation or permissions cannot satisfy the access. With a valid host-memory mapping, the GPU can read the host page directly. Normal loads use hardware translation without calling a CPU-side UVM range-lookup function. [[ptx|GPU load instruction]] · [[mmu-hopper|Page-table levels]]

The GPU records replayable faults in its fault buffer and notifies the host through an interrupt. The RM interrupt path in nvidia.ko calls uvm_isr_top_half(). UVM queues work on nv_kthread_q; replayable_faults_isr_bottom_half() invokes uvm_parent_gpu_service_replayable_faults(). This kernel thread batches and coalesces records, then uses the GPU context and fault address to locate the VA space, range and block. [[irq-top|Interrupt entry]] · [[irq-queue|Work queue]] · [[irq-bottom|Thread callback]] · [[fault-range|Fault dispatch]]

UVM then selects residency and the access method. The sequence below shows the branch that chooses migration to VRAM. If policy allows retaining H, UVM can instead install a GPU p → H mapping and replay the access, without this migration branch's H2D copy or CPU unmapping. [[gpu-residency|Residency selection for GPU faults]] · [[residency-policy|Policy and reachability checks]]

{{gpu_fault}}

3.2 Migration to VRAM and replay

This path assumes UVM chooses to migrate H to local VRAM page D. CPU and GPU fault handlers share VA-block page services, but install mappings and resume execution differently.

  1. CPU page table: block_unmap_cpu() calls unmap_mapping_range(). Linux removes p → H and handles CPU TLB invalidation. Migration preparation also clears any other GPU mappings that must be revoked. [[cpu-unmap|CPU unmapping]] · [[resident-copy|Revoking old mappings]]
  2. GPU page table: after preparing the destination and copying H → D, uvm_va_block_map() enters the GPU mapping path. The driver constructs the PTE for D and submits page-table writes and GPU TLB maintenance so hardware can use p → D. [[gpu-map|GPU mapping]] · [[gpu-write|PTE construction, writing and invalidation]]
  3. Resume access: push_replay_on_gpu() submits replay with tracker dependencies, ordering it after the required GPU work. The CPU need not synchronously wait at every step. [[fault-replay|Dependencies and replay]]

Whether a later CPU access faults depends on the CPU mapping at that time. If the platform supports a remote mapping to D and one is established, the CPU can access VRAM directly. With no usable mapping, it enters the applicable fault path, which selects a mapping update or migration. Batching also means fault records, interrupts and migrations do not have a one-to-one relationship. [[host-direct|Remote CPU access]] · [[block-service|Shared page service]] · [[fault-batch|Batch processing loop]]

4. Managed and pinned memory

4.1 Pinning and access targets

Mapped pinned memory resides in host RAM. The OS and driver keep the pages stable during registration or allocation and establish a GPU-accessible mapping. Direct GPU reads traverse the host interconnect. With managed memory, UVM can change the physical residency behind the same virtual address. [[mapped|CUDA mapped host memory]] · [[pin-linux|Linux DMA pinning]]

PropertyManaged memoryMapped pinned host memory
Typical interfacecudaMallocManagedcudaHostAlloc (mapped) + cudaHostGetDevicePointer
Physical locationUVM-managed; can migrate between host and GPUStays in host memory for direct GPU access
GPU instructionsOrdinary load/storeOrdinary load/store
GPU PTE targetLocal, peer or system, depending on the mappingSystem memory for direct access
Software stateManaged ranges, residency, mappings and policyHost allocations, registration and page pins

Pinned memory can also be a source for cudaMemcpyAsync. After that explicit copy, a kernel reads a separate device allocation; the table compares direct GPU reads from mapped pinned pages.

4.2 Hopper / Blackwell PTE

Hopper's VER3 PTE is a 64-bit hardware entry. In this source revision, Blackwell UVM inherits Hopper's PTE constructor. Valid indicates validity, Address stores the page address, Aperture selects local, peer or system memory, and PCF jointly encodes permissions, caching and access-counter policy. [[pte|Field definitions]] · [[pte-make|PTE construction]] · [[mmu-blackwell|Blackwell HAL]]

{{pte}}

Aperture=10/11 selects coherent or non-coherent system-memory attributes, which affect CPU-cache coherence handling. Both describe the current mapping's system-memory target. Interpreting PCF also requires Valid: invalid entries use a different encoding. [[coherent|System-memory coherence definitions]] · [[pte-invalid|Invalid-entry encoding]]

4.3 Allocation identity and PTEs

The PTE has no dedicated managed bit or host-pinned bit. The GPU uses the current entry for translation and permission checks. Both mapped pinned pages and host-resident managed pages can have system-memory mappings. The OS and driver track pinning and managed allocation identity in software.

A managed range can exist without a valid leaf PTE. UVM still finds its type, policy and page state using the address space and fault address. Faults can also occur at an upper page-directory level, so a leaf entry alone cannot cover every case. Software allocation records and hardware translations therefore suffice for the access and recovery paths described here. This is design analysis based on the public implementation; these sources do not give NVIDIA's official rationale for omitting a managed bit. [[range-type|Managed type]] · [[fault-space|Address-space identification]] · [[fault-range|Fault-address lookup]]

Applications can query allocation type with cudaPointerGetAttributes(). A managed result identifies the allocation, not its current host or GPU residency. [[pointer|Pointer attribute API]]
