URL、域名与 DNS

网页地址连接着两套系统：域名系统为浏览器提供服务器的网络地址，Web 服务器按请求选择资源。一个域名可以对应多台服务器，一台服务器也可以承载多个域名；同一页面还可以通过不同的域名和路径访问。域名解析、应用路由和页面跳转分别控制这些对应关系。

本文以 https://dev.example.com/ 和 https://example.com/dev 为例，解释地址的组成、域名的管理层级、DNS 的查询过程，以及两个地址如何进入同一个页面处理函数。文中的域名使用保留的 example.com，DNS 配置与 203.0.113.10 地址用于示意；最后的 HTTP 路由示例可在本机运行。[[reserved|示例域名]]

1. URL 的组成

1.1 主机名与资源位置

URL（Uniform Resource Locator，统一资源定位符）描述资源的位置和访问方式。常见的 HTTP / HTTPS 地址由以下几部分组成，方括号表示可选项：

scheme://hostname[:port]/path[?query][#fragment]

https://dev.example.com:443/guide/start.html?lang=zh#install
部分本例的值作用
schemehttps选择访问协议；HTTPS 使用加密连接。
hostnamedev.example.com标识请求的主机；这里是需要解析的域名。
port443指定服务端口。HTTPS 默认 443，HTTP 默认 80，默认端口可以省略。
path/guide/start.html标识服务器上的资源，由 Web 服务器或应用解释。
querylang=zh随请求发送的查询信息。key=value 是常见约定，具体含义由应用决定。
fragmentinstall通常标识页面内的位置。浏览器处理片段，HTTP 请求目标中不包含它。

:// 中的冒号结束 scheme，随后两个斜杠引出 authority（网络访问端点）部分，本例为主机名和端口。主机也可以写成 IP 地址，例如 http://127.0.0.1:8000/；IPv6 地址需要方括号，例如 http://[::1]:8000/。[[uri|URL 的通用结构]]

点与斜杠的含义取决于所在位置。 dev.example.com 中的点分隔域名标签；start.html 中的点属于路径字符，扩展名只是命名习惯。路径中的斜杠分隔路径段，服务器可以把这些段映射到文件，也可以交给应用函数处理。例如 /users/42 完全可以由程序查询数据库后生成。

1.2 相对地址

页面中的链接可以省略主机名甚至整个路径。浏览器把相对地址与基准 URL 合并，得到完整地址。以 https://example.com/guide/page.html 为基准：

相对地址解析结果
./image.svghttps://example.com/guide/image.svg
../index.htmlhttps://example.com/index.html
/logo.svghttps://example.com/logo.svg
#installhttps://example.com/guide/page.html#install

作为完整路径段时，. 表示当前层，.. 表示上一层。尾部斜杠也影响合并：相对地址 image.svg 在 https://example.com/dev 下得到 /image.svg，在 https://example.com/dev/ 下则得到 /dev/image.svg。应用将页面挂到新路径后，图片或脚本失效，常常与这个基准变化有关。[[relative|相对地址解析]]

2. 域名与子域

2.1 名称层级

DNS（Domain Name System，域名系统）把名称组织成一棵树。域名从右向左逐级具体化：com 是顶级域，example.com 位于它之下，dev.example.com 又位于 example.com 之下。

.                         根
└── com                   com.
    └── example           example.com.
        ├── www           www.example.com.
        └── dev           dev.example.com.
            └── api       api.dev.example.com.

点之间的一段称为标签（label）。dev 是一个标签，dev.example.com 才是这里的完整子域名。上面的每个名称都是域名；“子域”描述的是两个名称之间的包含关系。末尾的点表示根，日常书写通常省略。[[terms|域名、标签与子域]]

URL 中的“主机名”描述这个名称的用途，不代表它固定对应一台物理主机。www、dev、api 只是常见标签，DNS 不会根据它们的拼写自动分配网站、开发环境或接口服务。

域名长度与标签数量

DNS 中每个标签最多 63 字节，完整名称的未压缩编码最多 255 字节，包含每个标签的长度字节和末尾根标签。若每个标签只有 1 字节，127 × (1 + 1) + 1 = 255，因此最多可以容纳 127 个非空标签。普通 ASCII 写法不计末尾根点时，完整名称最多 253 个字符；国际化域名要按转换后的编码检查长度。实际注册平台可以有更严格的命名规则。[[dns-size|DNS 长度限制]]

2.2 注册与管理

注册一个可注册域名后，持有人在有效期内获得该名称下的管理权，通常可以自行创建 dev、api.dev 等子域名，无需逐个再向注册商购买。为子域添加地址记录，再配置网站服务，才能让它成为可访问的地址。域名注册、DNS 托管和运行网站的服务器是三项独立服务，可以由不同供应商提供。[[subdomains|创建子域记录]]

域名树也允许分工管理。DNS 区域（zone）是一段共同管理的域名空间，由其权威服务器保存并回答记录。管理员可以在现有区域中保存 dev.example.com 的记录，也可以添加 NS 记录，指定另一组权威服务器负责这个名称及其下属名称。后者称为委派，会形成新的区域边界；单纯增加一个标签则无需增加服务器。[[delegation|区域与委派]]

3. DNS 解析

3.1 名称与记录

DNS 查询包含名称和记录类型。浏览器需要连接 dev.example.com 时，可以查询它的 A 或 AAAA 记录，取得 IPv4 或 IPv6 地址。DNS 还保存名称别名、管理委派等信息：

类型记录内容示意
AIPv4 地址dev.example.com → 203.0.113.10
AAAAIPv6 地址dev.example.com → 2001:db8::10
CNAME另一个域名，即别名的目标www.example.com → example.com
NS该区域的权威名称服务器example.com → ns1.example.net

权威服务器保存并回答某个区域的记录。CNAME 的目标仍然是域名，解析器继续查询目标名称的地址。它不能填写 https://example.com/dev 这样的完整 URL，也不会把浏览器地址栏改为目标名称。[[records|资源记录]] · [[aaaa|AAAA 记录]]

假设管理员写入以下两条 A 记录，两个主机名就能解析到同一地址。IN 表示 Internet 类，300 是 TTL（Time to Live），表示记录允许缓存的时间为 300 秒：

example.com.      300  IN  A  203.0.113.10
dev.example.com.  300  IN  A  203.0.113.10

同一个名称也可以有多条地址记录，供客户端选择连接目标。因此名称和 IP 地址是多对多关系。这里的 A / AAAA 查询只处理主机名；/dev、查询参数和片段不参与这次地址解析。

3.2 递归查询与委派

客户端通常把查询交给一个递归解析器，由它寻找最终答案。操作系统中负责发出这类请求的轻量组件称为 stub resolver；递归解析器则可能由路由器、运营商、企业或公共 DNS 服务提供。

根服务器和顶级域服务器也属于权威服务器，分别负责根区和顶级域区域；本例中单列的“权威服务器”特指负责 example.com 区域的服务器。

角色维护者与实例
根服务器由 12 家独立运营机构维护 A–M 共 13 个根服务器标识。例如 Verisign 运行 A、J，互联网系统协会（ISC）运行 F，ICANN 运行 L。每个标识可由多地服务器实例提供服务。[[root-operators|完整运营名单]]
顶级域服务器由相应顶级域的注册管理机构（registry）负责。例如 .com 由 [[tld-com|Verisign]] 管理，.cn 由[[tld-cn|中国互联网络信息中心（CNNIC）]]管理。
域名的权威服务器域名持有人或授权管理员维护区域记录，服务器可以自行运行，也可以交给 DNS 托管商运行，例如 [[authoritative-hosting|Cloudflare DNS]]。
递归解析服务器由网络运营商、企业或校园网管理员、公共 DNS 服务提供者维护，个人也可以自建。例如 Google 提供 [[recursive-google|8.8.8.8]]，Cloudflare 提供 [[recursive-cloudflare|1.1.1.1]]。

例如，在注册商 A 购买域名后，可以把 NS 设置为 Cloudflare 分配的服务器：注册商办理注册与续费，Cloudflare 运行权威 DNS，域名管理员在 Cloudflare 修改记录。访问者仍可使用 Google 或网络运营商的递归解析器，两边的选择相互独立。[[authoritative-hosting|权威 DNS 托管配置]]

假设本机与递归解析器都没有相关缓存，解析器已知根服务器入口，且 example.com 直接管理 dev。一次地址查询沿管理委派向下进行：

{{dns-sequence}}

根服务器返回 com 的权威服务器线索，com 的服务器再返回 example.com 的委派信息。最后，example.com 的权威服务器回答 dev.example.com 的 A 记录。递归解析器把地址交给客户端，并缓存可复用的记录。[[dns|解析器算法]]

解析器跟随的是委派边界。即使名称写成 api.dev.example.com，若所有记录都在 example.com 区域中，仍可由同一组权威服务器回答。实际查询还可能跟随 CNAME，或补查名称服务器的地址。

3.3 缓存与查询入口

缓存命中时，客户端或递归解析器可以直接复用结果，省去部分或全部上游查询。修改权威记录后，已有缓存通常在各自 TTL 到期后更新；“域名不存在”的答案也能被缓存。因此新建记录后，先前查询过该名称的客户端可能暂时仍收到不存在的结果。[[negative-cache|否定缓存]]

浏览器也可以通过 DoH（DNS over HTTPS）直接向配置的解析器发起加密查询，从而使用不同于操作系统的查询入口。VPN、企业网络和应用代理还可能影响解析器选择或名称解析所在的位置，相关流量路径见VPN 与应用代理的路由分析。[[doh|DoH 协议]]

4. 多个 URL，同一页面

4.1 主机名与路径路由

下面两个 URL 的主机名和路径都不同：

地址主机名路径
https://dev.example.com/dev.example.com/
https://example.com/devexample.com/dev

采用上一节的 DNS 配置时，它们都能连接到 203.0.113.10:443。连接到达后，服务器仍然可以从请求中区分它们。用 HTTP/1.1 的表示形式写出两个请求：

GET / HTTP/1.1
Host: dev.example.com

GET /dev HTTP/1.1
Host: example.com

Host 字段携带请求的主机及必要的端口，HTTP/2 和 HTTP/3 使用相应的 :authority 伪首部。服务器根据主机名选择站点，再根据路径选择资源或应用处理函数。多个站点共用同一监听地址的配置称为虚拟主机。[[host|Host 与 authority]] · [[nginx|Web 服务器的请求分派]]

{{mapping-diagram}}

两条路由都调用 development_page()，所以返回相同页面。DNS 把两个名称解析到服务入口的 IP，HTTP 路由再选择这个函数。如果路由配置不同，共用 IP 的两个名称也可以访问完全不同的网站。

4.2 内部映射与重定向

同样的页面内容可以通过几种方式提供，它们对浏览器的影响不同：

机制服务器如何处理浏览器地址
内部路由两个主机名与路径组合指向同一处理函数或文件，直接返回 200 响应。保留各自的 URL。
反向代理前端服务器把两个请求转发到同一后端；转发时可改写主机名和路径。仅做内部转发时保留原 URL。
HTTP 重定向返回 301、302、307 或 308 等状态码，并通过 Location 提供目标地址。跟随重定向后变为目标 URL，并发起新请求。

反向代理把后端请求留在服务器之间完成，具体配置见 [[proxy|proxy_pass]]。重定向则让浏览器重新访问一个地址；网站迁移时常用永久重定向统一入口。DNS 的 CNAME 只改变名称查询过程，HTTP 重定向才向浏览器提供新的 URL。[[redirect|重定向状态码]]

4.3 HTTPS 与浏览器来源

HTTPS 在发送 HTTP 请求前建立 TLS（Transport Layer Security）连接。客户端通常通过 SNI（Server Name Indication）告诉服务器请求的主机名，服务器据此选择证书；证书需要覆盖客户端访问的名称。共用一个 IP 的两个 HTTPS 站点仍需各自满足证书验证。[[sni|TLS 主机名指示]]

浏览器按 scheme、主机名、有效端口 判断 HTTP(S) 页面的来源（origin）。因此 https://dev.example.com/ 与 https://example.com/dev 属于不同来源，即使页面内容和服务器相同；https://example.com/ 与 https://example.com/dev 则同源。跨来源的脚本读写与存储访问仍受浏览器规则约束。[[origin|来源的定义]]

5. 本地路由验证

5.1 两个入口

下载 route_demo.py，使用 Python 3.8 或更新版本运行。示例在本机回环地址提供 HTTP 服务，路由表的核心只有两个条目：

{{route-code}}

服务器从 Host 中取出主机名，从请求目标中取出路径，以这两个值查询 ROUTES。两个条目引用同一函数；查询参数在本例中不参与路由。启动命令如下，在终端按 Ctrl-C 停止：

python3 route_demo.py --port 8000

另开一个终端发起两个请求。--resolve 让本次 curl 调用把指定主机和端口连接到回环地址，同时保留原来的 HTTP 主机名。--noproxy '*' 使这两个本地请求直接连接，不经过环境中设置的代理。[[curl|curl 的地址覆盖选项]]

curl --noproxy '*' --resolve dev.example.com:8000:127.0.0.1 \
  http://dev.example.com:8000/

curl --noproxy '*' --resolve example.com:8000:127.0.0.1 \
  http://example.com:8000/dev

两次请求都返回 200，响应正文逐字节相同：

<!doctype html><title>Development</title><h1>Shared development page</h1>

本例已用 Python 3.11 与 curl 在本机验证。--resolve 仅覆盖该次 curl 的解析结果，不修改系统 DNS；示例地址在浏览器中不会因此自动生效。

5.2 重定向入口

同一个脚本还为 example.com/redirect-dev 配置了重定向。-I 发送 HEAD 请求，只检查响应首部：

curl --noproxy '*' --resolve example.com:8000:127.0.0.1 \
  -I http://example.com:8000/redirect-dev
HTTP/1.1 302 Found
Location: http://dev.example.com:8000/
Content-Length: 0

这里仅列出与重定向有关的首部。curl 默认停在这次响应；加入 -L 并为目标主机也配置解析后，它会跟随 Location，再请求共享页面：

curl --noproxy '*' \
  --resolve example.com:8000:127.0.0.1 \
  --resolve dev.example.com:8000:127.0.0.1 \
  -L http://example.com:8000/redirect-dev

服务日志会依次出现 GET /redirect-dev 的 302 和 GET / 的 200。内部映射只需一次请求；通过重定向取得这份页面，则需要第二次请求。
